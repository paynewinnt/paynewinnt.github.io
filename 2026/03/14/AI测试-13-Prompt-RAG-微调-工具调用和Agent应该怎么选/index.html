AI测试-13-Prompt-RAG-微调-工具调用和Agent应该怎么选

发表于 2026-03-14 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 44 分钟

一个 AI 应用回答不准确，团队最常提出五种方案：

  • 再改一版 Prompt；
  • 接一个 RAG；
  • 微调模型；
  • 给模型增加工具；
  • 做成 Agent。

这五个答案都可能正确。

也都可能把系统带向错误方向。

问题在于，它们解决的不是同一种缺口。

Prompt 主要约束当前任务。

RAG 主要提供外部知识。

微调主要改变模型的稳定行为分布。

工具调用主要读取确定性状态或产生真实动作。

Agent 主要处理需要根据观察结果动态规划的多步骤流程。

如果没有先定义问题，就很容易出现以下情况：

  • 用微调记住每天变化的价格；
  • 用 RAG 做精确余额查询；
  • 用 Agent 包装三个固定 API；
  • 用 Prompt 约束生产删除权限；
  • 用工具调用修复模型不会遵循输出格式；
  • 五种能力一次性全上，最后无法判断哪一层在失败。

技术选型真正需要回答的不是“哪个方案更先进”。

而是：

当前缺失的是指令、知识、稳定行为、真实能力，还是动态编排？

这篇文章从测试与平台工程视角，建立一套可验证的选型方法。

AI测试-04 已经讨论工具输入输出与容错。

AI测试-05 已经讨论 Agent Workflow 的状态和恢复。

AI测试-07 已经讨论测试知识库的 RAG 链路。

AI测试-08 已经讨论模型、工具、执行和证据分层。

本文不重复这些实现细节。

本文关注五类能力的边界、组合、成本、时延、维护风险，以及如何通过逐级实验决定是否真的需要增加一层。

一、先给结论：五类方案不是一条从低级到高级的升级路线

常见误解是：

仿佛系统成熟度越高，就应该不断向右升级。

这个模型是错的。

更准确的关系是：

它们可以独立出现，也可以组合。

一个高质量系统可能只有 Prompt 加一个确定性工作流。

一个复杂系统也可能使用 RAG、工具和 Agent，却完全不需要微调。

选型的第一原则是：

只为已经被实验确认的缺口增加能力。

选型的第二原则是：

每增加一层，都要同时增加该层的评测、观测、失败隔离和安全控制。

选型的第三原则是：

在可预先描述的流程中，确定性工作流通常比开放式 Agent 更容易测试和治理。

二、用决策树先做第一次分流

这张决策树不是自动生成架构的规则引擎。

它只用于第一次分流。

真正选型还要结合风险、数据、成本和实验结果。

问题 1：是否需要实时精确状态或真实副作用

如果需要：

  • 查询当前订单；
  • 读取设备在线状态；
  • 获取监控指标；
  • 计算税费；
  • 创建工单；
  • 重启服务；
  • 操作 Android 设备；
  • 修改数据库；

那么系统需要一个受治理的工具或确定性服务。

模型参数和 RAG 文档都不应该被当作真实系统状态。

问题 2：是否依赖外部、频繁变化且需要引用的事实

如果需要：

  • 当前制度；
  • 产品手册；
  • 私有故障知识；
  • 版本变更说明；
  • 测试规范；
  • 可审计的知识来源；

那么优先考虑 RAG 或结构化知识查询。

如果事实位于数据库且要求强一致，直接查询工具可能比向量 RAG 更合适。

问题 3：是否存在稳定且重复的行为差距

如果 Prompt 基线长期无法达到目标，并且：

  • 任务分布相对稳定；
  • 有足够高质量样本；
  • 输出行为可清晰评测；
  • 训练和部署成本可接受；

才进入微调候选评估。

微调解决的是行为适配问题。

它不应被当作频繁变化事实的可靠存储。

问题 4：步骤是否必须动态规划

如果流程步骤已知，使用状态机、DAG 或普通业务代码。

只有当系统必须根据中间观察选择下一步，而且分支难以预先穷举时，Agent 才可能带来净收益。

Agent 不是“模型加循环”这么简单。

它会引入状态、终止、权限、预算和错误传播问题。

三、先把业务问题描述成九个选型维度

不能用一句“想做智能客服”完成架构选型。

至少要填写下面九个维度。

1. 事实新鲜度

  • 几乎不变化；
  • 按月变化；
  • 按天变化；
  • 分钟级变化；
  • 必须读取当前事务状态。

变化越快，越不适合依赖参数记忆。

2. 事实精确度

  • 允许概括；
  • 需要语义正确；
  • 数字必须精确；
  • 状态必须强一致；
  • 结果必须来自指定系统。

精确度越高，越应该使用结构化查询和硬断言。

3. 来源可追溯性

  • 不要求引用；
  • 需要文档引用；
  • 需要版本和有效期；
  • 需要审计到原始记录；
  • 需要证明执行主体和权限。

RAG 可以帮助提供文档来源。

工具审计可以证明真实动作。

微调本身通常不能给出某条参数知识来自哪个训练样本的可靠业务引用。

4. 行为稳定性

  • 开放式创作；
  • 允许多种正确表达；
  • 需要固定分类边界；
  • 需要稳定结构；
  • 需要严格遵守业务语气和策略。

越接近后几项，越需要硬约束、验证器，必要时再评估微调。

5. 副作用

  • 只生成文本；
  • 只读外部数据；
  • 创建可撤销草稿；
  • 执行可补偿动作；
  • 执行不可逆或高风险动作。

副作用决定权限、确认、幂等和补偿设计。

它不是 Prompt 可以单独解决的问题。

6. 流程动态性

  • 单轮转换；
  • 固定多步骤；
  • 有限分支；
  • 根据观察动态分支；
  • 开放环境中的长任务。

前三类通常可以使用确定性工作流。

后两类才进入 Agent 候选。

7. 延迟预算

  • 离线批处理；
  • 数十秒可接受；
  • 数秒交互；
  • 亚秒级；
  • 实时控制。

RAG、重排、多次工具调用和 Agent 循环都会增加关键路径。

8. 数据条件

  • 没有标注数据；
  • 只有少量示例；
  • 有高质量监督数据；
  • 有成对偏好数据；
  • 有持续反馈和独立测试集。

没有数据治理能力时，微调往往只是把错误固化到参数。

9. 风险等级

  • 低风险建议；
  • 内部辅助；
  • 影响业务流程；
  • 影响资金、权限或生产；
  • 受监管或安全关键。

风险越高，越要减少开放式决策范围。

高风险任务不是不能使用 Agent。

但必须把权限、确认和验证放在模型之外。

四、Prompt：最低成本的任务契约，不是系统权限边界

1. Prompt 解决什么

Prompt 适合表达当前请求中的：

  • 角色和任务目标；
  • 输入字段含义；
  • 输出 schema；
  • 禁止事项；
  • 示例；
  • 判定标准；
  • 证据引用要求；
  • 不确定时的行为；
  • 当前上下文中的临时规则。

它的优势是：

  • 修改快；
  • 无需训练；
  • 容易做版本控制；
  • 适合快速建立基线；
  • 可以针对请求动态拼装。

2. Prompt 不解决什么

Prompt 不能可靠替代：

  • 数据库查询；
  • 权限校验；
  • 事务；
  • 幂等；
  • 强一致状态；
  • 知识版本治理；
  • 真实工具执行；
  • 稳定的外部记忆；
  • 高风险动作审批。

一句“绝对不要删除生产数据”不是权限系统。

执行器仍应拒绝未授权删除。

3. Prompt 的测试对象

Prompt 测试至少包含：

  • 模板渲染；
  • 变量转义；
  • 缺失字段；
  • 超长字段；
  • 指令冲突；
  • 示例污染；
  • 多语言；
  • 输出 schema；
  • 不确定状态；
  • 间接提示注入；
  • 版本回归。

4. Prompt 基线必须先做

在引入 RAG 或微调前，先建立最小 Prompt 基线。

基线应包含：

  • 清晰任务；
  • 少量高质量示例；
  • 结构化输出；
  • 硬验证器；
  • 固定模型快照；
  • 独立评测集。

如果基线没有测量，后续无法证明新增能力是否有效。

5. Prompt 的成本

Prompt 看起来没有训练成本，但仍有：

  • 输入 Token 成本；
  • 长示例的时延；
  • 模板维护；
  • 多模型兼容；
  • 注入风险；
  • 回归成本；
  • 规则冲突。

将所有规则不断追加到一个超长系统 Prompt，最终会形成不可维护的“文本程序”。

规则能由代码确定执行时，应由代码执行。

6. 何时只用 Prompt

适合：

  • 文本改写；
  • 摘要；
  • 低风险分类；
  • 固定输入到固定 schema 的转换；
  • 事实完全随请求提供；
  • 不需要访问外部系统；
  • 流程只有一步。

不适合：

  • 当前库存；
  • 私有知识问答；
  • 精确计算；
  • 生产操作；
  • 长期动态任务。

五、RAG：把可更新知识放到参数之外

1. RAG 解决什么

RAG 的核心是：

  1. 根据查询从外部知识源检索候选；
  2. 将候选作为上下文交给生成模型；
  3. 基于证据生成答案。

原始 RAG 工作将参数记忆与非参数记忆结合，用于知识密集型任务。

工程上最重要的价值是：

  • 知识可以独立更新；
  • 可以保留来源；
  • 可以做权限过滤；
  • 可以按版本检索；
  • 可以检查实际送入模型的证据。

2. RAG 适合什么

  • 产品文档问答；
  • 测试规范查询；
  • 故障知识检索；
  • 版本发布说明；
  • 内部流程制度；
  • 需要引用来源的技术回答；
  • 大规模非结构化资料。

3. RAG 不等于数据库

下面的问题更适合工具查询：

这些问题要求当前、精确、结构化状态。

把数据库导出成向量库再问，可能引入同步延迟、近似召回和过期答案。

RAG 适合解释“退款规则是什么”。

工具适合查询“这笔订单是否已退款”。

两者经常需要组合。

4. RAG 不能自动保证事实正确

RAG 链路仍可能失败：

  • 查询理解错误；
  • 权限过滤错误；
  • 切片丢失上下文；
  • 正确文档未召回；
  • 错误文档排名更高；
  • 文档已过期；
  • 多份文档冲突；
  • 上下文被截断；
  • 模型没有依据证据回答；
  • 引用与结论不一致。

所以 RAG 需要分层指标：

  • 检索指标；
  • 重排指标；
  • 上下文完整性；
  • 引用正确性；
  • 忠实度；
  • 最终任务成功率。

5. RAG 的维护成本

  • 数据准入；
  • 清洗；
  • 切片；
  • Embedding 升级；
  • 索引重建；
  • 权限同步；
  • 版本和有效期；
  • 冲突治理；
  • 召回评测集；
  • 引用审计。

“接入向量数据库”只是基础设施动作。

它不是 RAG 质量闭环。

6. 何时使用结构化检索而不是向量检索

如果问题可以明确映射为：

  • 主键查询；
  • 范围过滤；
  • 图关系；
  • 时间序列；
  • SQL 聚合；
  • 精确标签；

优先使用对应的确定性检索方式。

向量召回适合语义近似。

它不是所有查询的默认入口。

混合系统可以先做权限和结构过滤，再做向量召回与重排。

六、微调：改变行为分布，不是给模型安装一个实时数据库

1. 微调解决什么

广义微调是在预训练模型基础上，使用任务数据继续优化参数或适配参数。

常见目标包括：

  • 特定分类任务；
  • 固定输出风格；
  • 领域表达；
  • 结构遵循；
  • 工具选择模式；
  • 任务特定决策边界；
  • 缩短长 Prompt 中反复出现的示例。

LoRA 等参数高效方法通过冻结基础权重并训练低秩适配参数，降低可训练参数和资源需求。

这降低了部分训练成本。

它没有消除数据质量、评测、部署和版本治理成本。

2. 微调不能可靠注入频繁变化事实

这是选型中最重要的边界。

假设政策每天变化。

把今天的政策加入训练数据，不代表：

  • 模型一定准确记住每条内容；
  • 明天能自动更新；
  • 回答时能可靠区分新旧版本；
  • 能提供权威来源；
  • 能精确复述所有数字；
  • 旧参数知识完全消失；
  • 每次都能在正确条件下调用这条知识。

参数更新优化的是整体损失。

它不是按主键写入一条可查询记录。

频繁变化事实应优先放在：

  • RAG 知识源；
  • 数据库；
  • 配置中心；
  • 业务 API；
  • 可版本化规则引擎。

微调可以改善“如何使用证据”。

它不应承担“保存最新证据”的主要责任。

3. 参数知识缺少业务级来源引用

模型可能生成某个事实。

但生产系统通常无法从这次生成可靠追溯到某一条训练样本。

如果场景要求：

  • 依据哪份制度；
  • 使用哪个版本；
  • 当时是否有效；
  • 用户是否有权查看；

就需要外部证据链。

RAG 或工具返回可以携带这些元数据。

4. 何时微调有价值

满足以下条件时值得评估：

  • Prompt 基线已清楚测量；
  • 失败集中在稳定行为；
  • 任务分布相对稳定；
  • 有足够且一致的高质量样本；
  • 有独立测试集；
  • 可以承担训练、部署与回滚；
  • 收益能够抵消维护成本；
  • 安全边界仍由外部系统控制。

5. 微调数据的主要风险

标签噪声

错误或不一致标签会被模型学习。

分布偏差

训练数据来自少数产品、语言或用户。

数据泄漏

测试样本或其近重复进入训练集。

时间泄漏

使用未来政策训练，再在过去时间切片上评测。

隐私与许可

训练材料可能包含敏感数据或不允许用于训练的内容。

灾难性行为漂移

某类能力改善时，其他能力可能下降。

必须做全量回归，而不是只测目标任务。

6. 微调实验的最低对照

至少比较：

方案 模型 Prompt 外部知识 训练
Baseline 基础模型 最小模板 无 无
Prompt+Examples 基础模型 加示例 无 无
RAG Baseline 基础模型 固定 有 无
Fine-tuned 微调模型 固定 同条件 有

只有在相同知识条件和相同评测集下，才能判断行为改善是否来自微调。

如果微调组偷偷使用更多上下文，结论无效。

7. 微调上线后的回归

  • 目标任务质量；
  • 非目标通用能力；
  • 格式遵循；
  • 拒绝行为；
  • 安全样本；
  • 多语言；
  • 长尾输入；
  • 成本与时延；
  • 基础模型升级兼容；
  • 适配器版本回滚。

训练完成不是项目结束。

它只是新增了一个需要持续治理的模型制品。

1. 工具解决什么

工具适合：

  • 精确计算；
  • 查询当前状态；
  • 获取强一致数据；
  • 执行真实操作；
  • 调用已有业务能力；
  • 将复杂动作封装成受控 API。

2. 工具调用包含两个不同决策

第一，模型是否提出调用某工具。

第二，执行器是否允许并实际执行。

不能把两者合成一个动作。

模型可以生成候选意图。

执行器必须独立做：

  • 幂等校验；
  • 风险审批；
  • 超时和重试；
  • 审计。

3. 读取工具与写入工具风险不同

读取工具仍有数据泄漏风险。

写入工具还增加：

  • 重复执行；
  • 部分成功；
  • 事务失败；
  • 补偿；
  • 不可逆副作用；
  • 跨系统一致性；
  • 人工确认。

  • 可重试性；
  • 副作用；
  • 返回状态；
  • 错误分类。

4. 工具调用与 RAG 的边界

RAG 返回证据片段。

工具返回受业务系统约束的结果。

  • 正常参数；
  • 缺失参数；
  • 多余参数；

八、Agent：动态编排，不是“所有能力的高级版”

1. Agent 解决什么

Agent 适合这样的任务：

  • 下一步依赖当前观察；
  • 需要在多个工具之间选择；
  • 无法预先枚举所有路径；
  • 任务可能跨多个回合；
  • 中途需要重新规划；
  • 需要对环境变化做响应。

可以抽象为循环：

ReAct 研究探索了推理与动作交错的方式。

工程实现不必暴露或保存模型的私有推理文本。

平台需要保存的是可审计的计划摘要、工具意图、动作、观察和状态转换。

2. Agent 不提供新的事实来源

Agent 仍然依赖：

  • 模型；
  • Prompt；
  • RAG；
  • 工具；
  • 记忆；
  • 执行环境。

如果 RAG 召回错误，Agent 可能基于错误证据规划。

如果工具权限过大，Agent 会放大副作用。

如果终止条件不清，Agent 可能循环。

Agent 是编排层，不是事实层。

3. 固定流程为什么不应默认 Agent 化

假设流程永远是：

  1. 查询订单；
  2. 查询政策；
  3. 计算资格；
  4. 人工确认；
  5. 发起退款。

步骤和分支都可以明确编码。

普通状态机更容易：

  • 覆盖测试；
  • 审计；
  • 估算成本；
  • 保证终止；
  • 做事务补偿；
  • 限制权限。

把它改成自由规划 Agent，可能只增加不确定性。

4. Agent 的新增成本

  • 多轮模型调用；
  • 状态持久化；
  • 工具结果累积；
  • 上下文压缩；
  • 循环检测；
  • 预算限制；
  • 计划漂移；
  • 错误传播；
  • 人工接管；
  • 轨迹评测；
  • 更大的攻击面。

5. Agent 的最低安全边界

  • 最大步数；
  • 最大 Token；
  • 最大费用；
  • 总超时；
  • 工具白名单；
  • 每个工具的权限；
  • 高风险动作确认；
  • 幂等键；
  • 终止条件；
  • 循环检测；
  • 首错证据；
  • 人工接管；
  • 沙箱；
  • 审计轨迹。

6. Agent 测试不能只看最终答案

至少评估：

  • 任务完成率；
  • 计划有效率；
  • 工具选择正确率；
  • 参数正确率；
  • 无效步骤率；
  • 重复步骤率；
  • 预算超限率；
  • 恢复成功率；
  • 高风险越权率；
  • 最终状态正确率；
  • 证据完整率。

一个 Agent 最后碰巧成功，不代表轨迹可接受。

它可能先执行了错误动作，再通过另一个动作掩盖。

十、组合才是生产系统的常态

组合架构的核心原则是责任分离。

1. Prompt 提供当前契约

它描述：

  • 当前任务；
  • 可用上下文；
  • 输出格式；
  • 不确定行为；
  • 允许提出的工具意图。

2. RAG 提供外部证据

它返回：

  • 文档片段；
  • 来源；
  • 版本；
  • 有效期；
  • 权限；
  • 检索分数。

3. 微调模型提供行为适配

它可能更擅长：

  • 某类分类；
  • 某种结构；
  • 某种领域表达；
  • 选择工具的模式。

它仍然不拥有业务权限。

4. 工具网关提供真实能力

它负责：

  • 当前状态；
  • 确定性计算；
  • 真实副作用；
  • 鉴权；
  • 幂等；
  • 审计。

5. 工作流或 Agent 负责编排

固定流程使用确定性编排。

动态流程使用受限 Agent。

两者都需要状态、超时和错误处理。

6. 验证器负责收口

验证器不应让模型自证正确。

它应做：

  • schema；
  • 业务规则；
  • 引用；
  • 权限；
  • 状态确认；
  • 风险决策。

7. 证据层负责复盘

最终结果必须绑定：

  • 使用的 Prompt 版本；
  • 模型版本；
  • 检索片段；
  • 工具调用；
  • 状态转换；
  • 验证结果；
  • 人工确认。

十一、六种常见组合及适用边界

组合 1：Prompt + 验证器

适合：

  • 文本到 JSON；
  • 低风险分类；
  • 输入中已经包含全部事实；
  • 单步骤任务。

关键点：

  • 输出必须硬校验；
  • 不符合时进入 UNKNOWN；
  • 不要增加不必要的 RAG。

组合 2：Prompt + RAG + 引用验证

适合：

  • 内部文档问答；
  • 测试规范查询；
  • 故障知识助手；
  • 需要来源的总结。

关键点：

  • 先评测召回；
  • 再评测答案忠实度；
  • 冲突时拒绝强行作答。

组合 3：Prompt + 工具 + 固定工作流

适合：

  • 查询订单后生成说明；
  • 读取设备状态后决定测试动作；
  • 计算指标后生成报告；
  • 步骤已知的业务流程。

关键点：

  • 工具权限在模型之外；
  • 工具结果硬验证；
  • 写操作要求幂等。

组合 4：Prompt + RAG + 工具

适合：

  • 先读政策，再查实例状态；
  • 先查故障手册，再读取设备指标；
  • 既要规则依据，又要当前事实。

关键点：

  • 明确哪些字段来自文档；
  • 明确哪些字段来自业务系统；
  • 不允许模型混淆来源。

组合 5：微调模型 + RAG

适合：

  • 领域表达和任务行为需要适配；
  • 知识仍需持续更新；
  • 有训练数据与独立评测集。

关键点：

  • 微调改善使用证据的方式；
  • RAG 提供最新证据；
  • 两层分别版本化和评测。

组合 6：Agent + RAG + 工具

适合：

  • 路径需要根据环境动态变化；
  • 工具较多；
  • 任务分支难以预先穷举；
  • 可以承担多轮时延和治理成本。

关键点：

  • Agent 不绕过工具网关；
  • 每一步都写状态和证据；
  • 高风险动作需要人工确认；
  • 最大步数和费用必须硬限制。

  • 推理资源；

  • 沙箱；

  • 多轮调用；
  • 长轨迹存储；
  • 状态恢复；
  • 循环和预算治理；

十五、可维护性：变化应该落在正确的层

规则变化

如果只是输出格式或当前任务约束变化：

  • 更新 Prompt 或验证器；
  • 不应重新训练模型。

知识变化

如果政策、文档或故障知识变化：

  • 更新知识源和索引；
  • 保留版本与有效期；
  • 不应依赖重新微调。

行为变化

如果稳定任务边界长期变化：

  • 先更新 Prompt 和评测；
  • 若基线仍不达标，再评估微调。

系统能力变化

如果新增业务动作：

  • 增加工具契约；
  • 配置权限与审计；
  • 不应把 API 细节全塞进自然语言。

流程变化

如果步骤和分支已知：

  • 更新工作流；
  • 只有动态不可穷举部分才交给 Agent。

一个可维护架构的重要特征是：

每类变化只触发少数明确组件升级。

如果改一条政策必须重新训练、重写 Prompt、重建 Agent 和修改工具，说明边界已经混乱。

十六、选型实验：按能力阶梯逐级增加

1. 先建立共同评测集

评测集必须覆盖：

  • 正常主路径；
  • 长尾输入；
  • 缺失信息；
  • 冲突信息；
  • 过期知识；
  • 精确数字；
  • 权限边界；
  • 工具故障；
  • 注入攻击；
  • 高风险拒绝；
  • 多语言；
  • 成本和时延。

2. 时间切分

涉及动态知识时，按时间切分：

  • 训练或开发集只使用截止时间前数据；
  • 测试集包含之后更新的知识；
  • 评估系统是否通过外部知识正确更新。

如果微调模型在测试知识更新后仍准确，必须确认是否存在数据泄漏。

3. 能力阶梯

E0：确定性非模型基线

能用规则、搜索或程序完成的部分先做基线。

E1：Prompt 基线

基础模型加最小模板和验证器。

E2：Prompt + RAG

只为知识缺口增加检索。

E3：Prompt + 工具

只为实时状态或动作增加工具。

E4：微调候选

保持外部知识条件一致，只比较行为适配收益。

E5：Agent 候选

只在动态规划数据集上，与固定工作流比较。

4. 每级只增加一个机制

如果从 E1 直接跳到“微调模型 + RAG + Agent + 十个工具”，即使成功率提高，也无法回答：

  • 哪个组件贡献了收益；
  • 哪个组件增加了风险；
  • 能否删除某个昂贵组件；
  • 失败发生在哪一层。

总任务成功率高，仍可能存在：

十九、示例案例：用微调“记住”退款政策为什么失败

下面是一个用于说明选型方法的示例案例。

它不代表任何真实项目经历。

1. 场景

团队要做一个退款助手。

它需要回答：

  1. 当前退款政策是什么；
  2. 某订单是否符合政策；
  3. 用户确认后发起退款。

初版使用一个微调模型。

训练数据中包含当时的退款政策和大量客服问答。

离线测试看起来很好。

2. 变化

一个月后，政策从“30 天内可退”改为“部分品类 14 天，其他品类 30 天”。

模型没有立即重新训练。

它仍然多次回答统一 30 天。

更严重的是，回答没有可靠来源版本。

3. 错误修复尝试

团队追加 Prompt：

这句话没有提供最新政策。

它只表达了愿望。

模型仍可能依赖参数中的旧模式。

4. 重新拆问题

问题 A：当前政策是什么

这是动态、需要引用的外部知识。

使用 RAG 或结构化规则库。

问题 B：订单当前状态是什么

这是实时精确事实。

使用订单查询工具。

问题 C：是否符合政策

这是规则判断。

高风险情况下，优先使用确定性规则引擎。

模型可以生成解释，但不能单独决定资格。

问题 D：执行退款

这是有副作用动作。

使用受鉴权、幂等和审计保护的退款工具。

问题 E：流程是否需要 Agent

步骤和分支已知。

普通状态机足够。

不需要开放式 Agent。

问题 F：微调是否还有价值

可能有。

微调可以改善：

  • 客服语气；
  • 意图分类；
  • 从非结构化描述中抽取字段；
  • 使用证据生成一致说明。

但最新政策仍由外部系统提供。

5. 调整后架构

6. 关键测试

  • 政策更新时间晚于模型训练时间；
  • 两个品类适用不同期限；
  • 订单状态在流程中发生变化；
  • 同一退款请求重复提交；
  • 政策检索结果冲突；
  • 订单工具超时；
  • 用户无退款权限；
  • 模型解释与规则结果不一致；
  • 执行成功但响应丢失；
  • 人工确认缺失。

7. 案例结论

失败不是因为“微调没有用”。

而是因为微调被用来承担了不适合它的职责。

把动态事实移到外部知识和业务系统后，微调才能专注于稳定行为。

二十、常见误区

误区 1：Prompt 调不好就直接微调

先确认失败是稳定行为差距，而不是知识缺失、工具缺失或判定器错误。

误区 2：微调可以长期记住最新事实

不能把它当成可靠的实时知识更新机制。

动态事实应通过 RAG、数据库或工具提供。

误区 3：RAG 可以替代所有数据库查询

向量检索是近似语义召回。

精确当前状态优先使用结构化查询。

误区 4：Agent 能自动提升简单流程

固定流程 Agent 化通常增加成本和不确定性。

先与状态机做对照。

误区 5：工具 schema 写清楚就不会越权

schema 约束结构。

权限、业务规则和审批必须由执行器检查。

误区 6：RAG 有引用就一定可信

引用可能错误、过期或与结论不一致。

必须验证引用。

误区 7：微调后可以删除验证器

错误。

微调改变概率分布，不提供确定性业务保证。

误区 8：一个总成功率可以完成选型

越权、泄漏、错误写入等红线必须单独统计。

误区 9：组件越多，系统能力越强

组件越多，失败组合、时延和维护面也越大。

能力必须由可测收益证明。

误区 10：Agent 的最终答案对就算成功

轨迹可能包含错误、重复或越权动作。

最终状态和执行过程都要检查。

误区 11：模型排名可以替代场景实验

公开基准不能覆盖本地数据、工具、风险和时延。

选型必须在自己的评测集上完成。

误区 12：一次 PoC 成功就可以确定架构

PoC 通常没有覆盖数据更新、模型升级、并发、长尾和事故恢复。

生产选型还要评估生命周期。

二十一、分阶段落地路线

阶段 0：确定性边界

先明确：

  • 事实真值在哪；
  • 哪些动作有副作用；
  • 哪些规则可代码化；
  • 哪些结果必须人工确认；
  • 哪些数据不能进入模型。

阶段 1：Prompt 基线

建立：

  • 版本化模板；
  • 结构化输出；
  • 验证器；
  • 独立评测集；
  • 成本和时延基线。

阶段 2：补知识或能力

只根据失败类型增加：

  • 知识缺口加 RAG；
  • 实时状态和动作加工具；
  • 固定流程加工作流。

阶段 3：评估微调

当稳定行为差距仍然存在：

  • 准备数据；
  • 做泄漏检测；
  • 训练候选；
  • 与相同知识条件下的基础模型比较；
  • 做非目标回归。

阶段 4：评估 Agent

当固定工作流无法覆盖动态路径：

  • 定义环境；
  • 限制工具；
  • 定义状态和终止；
  • 与工作流比较；
  • 做轨迹评测；
  • 加人工接管。

阶段 5：生命周期治理

建立：

  • Prompt 版本；
  • 知识版本；
  • 模型版本；
  • 工具契约版本；
  • 编排版本；
  • 评测版本；
  • 可回滚发布；
  • 在线漂移监控。

二十四、总结

Prompt、RAG、微调、工具调用和 Agent 的区别，不在于“智能程度”。

它们对应五种不同工程职责：

  • Prompt 负责当前任务契约；
  • RAG 负责可更新、可追溯的外部知识；
  • 微调负责稳定行为适配；
  • 工具负责确定性状态和真实动作；
  • Agent 负责动态多步骤编排。

选型时先问：

  • 事实是否变化；
  • 是否要求精确与溯源；
  • 是否需要副作用；
  • 行为差距是否稳定；
  • 流程是否真的动态；
  • 风险、成本和时延是否允许。

尤其要守住一条边界：

微调不能被当作可靠注入频繁变化事实的方法。

需要更新和引用的知识放到 RAG 或规则库。

需要当前精确状态的事实通过工具查询。

需要真实副作用的动作由受治理执行器完成。

步骤已知时使用固定工作流。

只有动态分支确实无法合理穷举时，才引入 Agent。

最后，用实验而不是偏好做决策：

  1. 建立确定性与 Prompt 基线；
  2. 按失败类型增加 RAG 或工具；
  3. 在相同知识条件下评估微调；
  4. 只在动态任务上比较 Agent 与固定工作流；
  5. 同时衡量质量、红线风险、成本、时延和维护。

最好的架构不是能力最多。

而是每种能力都有明确责任、可验证收益和可控制失败边界。
