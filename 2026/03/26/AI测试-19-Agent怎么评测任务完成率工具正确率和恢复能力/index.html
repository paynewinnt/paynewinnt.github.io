AI测试-19-Agent怎么评测任务完成率工具正确率和恢复能力

发表于 2026-03-26 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 45 分钟

评测普通问答模型时，输入和输出通常都比较清楚。

输入一个问题，模型生成一段文本，再对文本做正确性、相关性和安全性判断。

Agent 不一样。

它不只是生成文本，还会在一个有状态的环境里持续执行动作：

  • 读取数据
  • 选择工具
  • 组装参数
  • 调用接口
  • 根据返回结果更新计划
  • 修改业务状态
  • 遇到故障后重试、降级或转人工

这意味着 Agent 的一次运行不是一个答案，而是一条会产生副作用的轨迹。

如果只看最后一句“任务已完成”，可能出现：

  • Agent 说完成了，但订单根本没有创建
  • 最终状态正确，但中途读取了无权限数据
  • 工具都调用成功，但参数绑定到了错误用户
  • 第一次写入已成功，响应超时后重试造成重复写入
  • 任务没有完成，却消耗了几十次工具调用才停止
  • 偶尔一次能通过，重复运行时表现极不稳定

所以 Agent 评测至少要回答两组问题。

第一组是最终状态：

  • 业务目标是否真正达成
  • 不该变化的数据是否保持不变
  • 副作用是否完整、唯一且可审计

第二组是执行轨迹：

  • 工具选得对不对
  • 参数和实体绑定是否正确
  • 调用顺序是否满足前置条件
  • 状态读取和决策是否一致
  • 故障后是否正确恢复
  • 是否越权
  • 是否在合理成本内收敛

AI测试-05-Agent Workflow执行多步骤测试任务时怎么做状态管理和失败恢复 已经讨论了状态分层、失败类型和恢复设计。

本文不再重复如何实现工作流状态机，而是进一步解决评测问题：

如何把最终状态和轨迹分开判定，如何设计任务完成、工具选择、参数、顺序、状态一致性、恢复、权限和成本指标，以及如何用模拟器、故障注入和轨迹重放建立可持续回归。

一、问题边界：Agent 评测不是聊天评分，也不是精确匹配一条标准路径

1. 本文所说的 Agent

本文关注的是能够调用外部工具并改变环境状态的 Agent。

简化执行循环如下：

工具可以是：

  • REST/RPC API
  • 数据库查询代理
  • 浏览器或移动端自动化动作
  • 文件与代码操作
  • 测试平台执行器
  • 工单、订单、支付、审批等业务系统

只要工具会读取受限数据或产生副作用，就不能只评价最终自然语言回复。

2. Agent 运行可以看成一个有状态决策过程

对评测工程来说，可以把一次运行抽象为：

其中：

  • state_t：第 t 步前的环境和会话状态
  • action_t：Agent 选择的工具及参数
  • observation_t：工具返回、异常或状态变化
  • state_(t+1)：执行动作后的新状态

评测不要求访问模型私有推理过程。

真正需要保存和验证的是可观测边界：

  • 模型收到的任务与工具定义版本
  • Agent 发出的结构化动作
  • 工具代理返回的 observation
  • 动作前后的业务状态快照
  • 策略拦截和故障注入记录
  • 最终结果与资源消耗

3. 不应该把唯一标准轨迹写死

许多任务有多条合法路径。

例如查询订单后取消，可以：

  • 先按订单号查询，再取消
  • 先按用户和时间查列表，再确认目标订单，再取消
  • 在本地已有可信订单快照时直接校验版本后取消

如果评测强制精确匹配某一串工具名，会把合法替代方案判错，也会阻碍系统优化。

更合适的契约是：

  • 必须满足的最终状态谓词
  • 必须保持的不变量
  • 必须发生或至少覆盖的能力
  • 禁止调用的工具和参数范围
  • 必须满足的关键偏序关系
  • 可接受的成本与步骤预算

4. 本文不解决什么

本文不尝试：

  • 给所有 Agent 定义一个通用排行榜
  • 评价不可观测的“思维质量”
  • 用一个加权总分替代安全门禁
  • 证明 Agent 在所有真实环境中都可靠
  • 规定某一种 Agent 框架或协议

本文目标是建立可执行、可复现、能定位失败的工程评测方法。

二、任务契约：先定义什么叫完成，才能谈完成率

1. 自然语言任务不是测试 Oracle

任务“帮用户取消刚才下错的订单”有很多隐含条件：

  • “用户”是哪一个身份
  • “刚才”对应哪个时间窗口
  • 多个订单时如何消歧
  • 哪些状态允许取消
  • 取消是否需要二次确认
  • 退款是否属于同一事务
  • 哪些字段不应被修改

如果这些条件没有转成可执行契约，最终只能靠人工看轨迹猜测。

2. 一条 Agent 评测样本应包含什么

最小契约建议包含：

  • case_id：稳定样本 ID
  • instruction：给 Agent 的自然语言任务
  • initial_state_fixture：初始环境快照
  • identity：执行身份、租户与角色
  • goal_predicates：任务目标谓词
  • invariants：全过程或终态不变量
  • allowed_tools：允许使用的工具集合
  • forbidden_actions：禁止动作与参数范围
  • ordering_constraints：关键前后关系
  • fault_plan：要注入的故障
  • budget：步骤、工具、token、时延和费用预算
  • expected_terminal_states：成功、受控降级或转人工
  • slice_tags：任务风险和能力标签

三、双层评测模型：结果和过程必须同时保留

1. 最终状态层

最终状态层回答：

  • 目标实体是否达到预期状态
  • 写入是否真实提交
  • 数量和唯一性是否正确
  • 无关数据是否保持不变
  • 任务是否以允许的终态结束

这一层尽量使用：

  • 数据库或模拟器状态
  • 业务 API 的权威读取
  • 文件系统或代码仓库快照
  • 浏览器 DOM 与后端状态联合检查
  • 可重复执行的程序断言

不要只用 Agent 自己的最终回复作为 Oracle。

2. 轨迹层

轨迹层回答：

  • 工具选择是否必要、合法
  • 参数是否通过 schema 和业务语义校验
  • 调用顺序是否满足前置条件
  • observation 与后续动作是否一致
  • 故障是否被识别和正确处理
  • 是否尝试越权或绕过策略
  • 是否在预算内收敛

3. 为什么最终状态正确仍可能失败

下面这些运行最终状态可能正确，但必须判为失败或高风险：

  • 先写入再做权限检查
  • 读取了不属于当前租户的数据
  • 第一次调用参数错误，第二次碰巧改对
  • 通过管理员工具绕过正常审批
  • 暂时破坏不变量，最后又改回去
  • 产生多次收费后再退款到正确余额

某些业务只关心终态，但高风险系统通常还关心过程中是否发生过不可接受行为。

4. 为什么轨迹合理仍不能算完成

反过来，工具和顺序看起来都合理，最终状态仍可能失败：

  • 工具返回 200，但异步任务最终失败
  • Agent 读取的是缓存状态，不是权威状态
  • 写入落在错误租户
  • 最后一步响应成功，但事务被回滚
  • Agent 忘记校验最终状态

所以轨迹得分不能代替目标状态断言。

3. Invariant Pass：全过程不变量

不变量分为：

  • 终态不变量：结束时必须满足
  • 全过程不变量：每一步都不能违反

典型不变量包括：

  • 库存不得为负
  • 不得修改其他租户数据
  • 未确认前不得产生收费
  • 同一业务意图不得重复创建资源
  • 敏感字段不得进入日志

4. Side-effect Exactness：副作用数量必须精确

对创建、发送、扣费、删除等动作，至少要检查：

  • 目标副作用数量
  • 目标实体身份
  • 副作用的幂等键
  • 是否有多余副作用
  • 是否有补偿动作
  • 补偿是否真的恢复业务语义

多创建再关闭仍会留下通知、审计和外部系统事件。

5. Final Response Accuracy：单独评价对用户的说明

最终业务状态通过后，还要检查 Agent 对用户说了什么。

例如：

  • 是否如实说明完成状态
  • 是否返回正确资源 ID
  • 是否隐瞒了部分失败
  • 是否把“已提交”说成“已完成”
  • 是否暴露敏感信息
  • 是否给出下一步或人工接管信息

这是一项独立指标。

不能反过来用自然语言回复证明业务状态。

3. Tool Selection Precision 要谨慎解释

把“标准轨迹出现过的工具”视为相关工具，可以计算类似 precision 的比例。

  • 标准轨迹可能不是唯一合法轨迹
  • 诊断性读取工具可能只在故障时才需要

所以更建议按能力和上下文定义：

  • 正常路径允许工具
  • 特定故障后允许工具
  • 永远禁止工具
  • 必须在某条件下调用的工具

这比静态工具白名单更准确。

4. 参数正确性至少分两层

第一层是 schema validity：

  • 必填字段是否存在
  • 类型是否正确
  • 枚举是否合法
  • 格式是否符合约束
  • 是否存在未知字段

第二层是 semantic correctness：

  • user_id 是否绑定目标用户
  • 时间范围是否符合“刚才”的定义
  • 数量和单位是否正确
  • 幂等键是否稳定复用
  • 资源版本是否来自最新 observation
  • 敏感字段是否不应传入

模型完全可能生成 schema 合法但业务语义错误的参数。

六、恢复能力：不是“遇错会重试”

1. 先定义哪些故障可恢复

故障至少分成：

  • 调用前失败：请求确定没有到达业务服务
  • 提交前失败：业务事务确定没有提交
  • 提交后响应丢失：副作用可能已经发生
  • 暂时性失败：限流、短暂不可用
  • 永久参数错误：输入不合法
  • 权限拒绝：当前身份不允许
  • 状态冲突：资源版本已变化
  • 部分成功：多个子动作只有一部分完成

不同故障对应不同恢复策略。

统一重试器无法安全处理这些语义差异。

“最终继续执行”不等于恢复成功。

恢复后必须重新检查：

  • 目标状态
  • 重复副作用
  • 状态一致性
  • 权限
  • 成本预算

  • 不可重复

  • 可能污染真实数据

  • 在提交前还是提交后失败
  • 返回什么错误和延迟
  • 是否真实修改环境状态
  • Agent 能看到哪部分 observation

2. 可证明未提交的失败与提交状态不明的超时完全不同

可证明未提交的失败：

  • 只有工具契约、事务回滚记录或代理侧证据明确给出 NOT_COMMITTED，才能确认副作用没有发生
  • 在满足预算时通常可以安全重试

普通网络超时或提交后响应丢失：

  • 对 Agent 来说提交状态不确定，副作用可能已经发生
  • 不能直接使用新请求 ID 重试
  • 应先用幂等键、业务键或权威读取查状态

故障注入如果只返回统一 TimeoutError，却不在测试侧记录真实提交阶段，就无法判断 Agent 的恢复是否正确。

九、可靠性指标：一次通过不代表能稳定执行

1. 同一任务要重复运行

Agent 的非确定性来自：

  • 模型采样
  • 上下文顺序
  • 工具延迟
  • 并发状态
  • 检索与缓存
  • 服务端模型更新
  • 环境中的异步事件

因此高风险样本应在受控 seed 和多 seed 下重复运行。

报告至少包含：

  • 单次任务成功率
  • 多次运行全部通过率
  • 最差轨迹
  • 严重违规出现次数
  • 工具调用和成本分布

2. pass^k 与 pass@k 不要混淆

pass@k 常表达“k 次尝试中至少有一次成功”，适合允许多次候选的任务。

若单次成功概率为 p，在独立假设下：

但生产 Agent 往往要求每次都可靠。

tau-bench 提出的 pass^k 关注连续 k 次全部通过。

在独立同分布的简化假设下：

它会随着 k 增加而降低，从而暴露“一次表现不错、长期并不稳定”的问题。

实际评测中最好直接按重复运行分组统计“全通过组比例”，不要盲目假设运行独立。

3. 为什么平均成功率不够

假设两个 Agent 都有 80% 单次成功率。

Agent A 的失败均匀分布在所有任务。

Agent B 在普通任务上几乎全对，但对退款任务持续越权失败。

平均分相同，风险完全不同。

必须按下面维度切片：

  • 只读与写入
  • 可逆与不可逆
  • 单工具与多工具
  • 正常路径与故障恢复
  • 普通权限与敏感权限
  • 短轨迹与长轨迹
  • 确定性环境与并发环境
  • 低成本与高成本任务

4. 置信区间和最差运行

样本量较小时，应报告：

  • 成功数与总数
  • 比例置信区间
  • 每个 case 的重复次数
  • 随机 seed
  • 最差运行轨迹

同一 case 的重复运行共享任务语义和环境条件，不能直接当成 IID 样本。区间估计应以 case 为聚类单位；比较两个 Agent 或两个版本时，要在 case 内保留配对关系后再做聚类 Bootstrap。

对于零容忍安全事件，即使只出现一次，也不应被置信区间或平均值淡化。

十、权限与安全：系统拦住了，不代表 Agent 通过了

1. 区分尝试越权和越权成功

至少记录两个指标：

如果策略层成功拦截：

  • 系统安全控制通过
  • Agent 轨迹仍应记录越权尝试失败

不能因为防火墙挡住了错误动作，就认为模型决策正确。

2. 权限测试不能只删掉工具

如果无权限时工具完全不出现在工具列表中，只测到了最简单情况。

还要覆盖：

  • 工具可见但调用被拒绝
  • 同名资源跨租户
  • 可读不可写
  • 只能修改部分字段
  • 权限在任务中途撤销
  • 用户要求 Agent 绕过策略
  • observation 中包含诱导越权的文本

3. 最小权限工具契约

工具层应提供：

  • 明确身份上下文
  • 参数级权限校验
  • 服务端而非仅 Prompt 侧授权
  • 审计事件
  • 幂等和版本控制
  • 可识别的拒绝码

评测要确认 Agent 在收到权限拒绝后：

  • 不伪造成功
  • 不切换到更高权限工具
  • 不通过其他字段绕过
  • 能安全终止或请求授权

4. 安全指标不进入普通加权平均

下面事件通常应是硬失败：

  • 未授权读取敏感数据
  • 未确认产生不可逆副作用
  • 试图禁用审计或安全控制
  • 在不确定提交状态下重复扣费
  • 将秘密写入最终回复或日志

即使任务完成率和工具正确率很高，也不能抵消。

十一、成本与效率：只统计 token 会漏掉真正昂贵的部分

1. Agent 成本构成

一次 Agent 运行可能包含：

  • 模型输入 token
  • 模型输出 token
  • 检索或记忆调用
  • 工具 API 费用
  • 浏览器或设备执行时间
  • 沙箱计算资源
  • 重试与补偿成本
  • 人工接管成本

因此建议记录：

  • 总步骤数
  • 模型调用数
  • 工具调用数
  • 写调用数
  • 输入/输出 token
  • 端到端延迟
  • 活跃执行时间与等待时间
  • 估算费用
  • 人工接管率

2. 成功成本和失败成本分开

可以报告：

也要单独看：

  • 成功运行的 p50/p95 成本
  • 失败运行的平均成本
  • 超预算后才失败的比例
  • 故障恢复增加的成本

一个 Agent 如果失败时无限循环，会显著拉高资源消耗。

3. 效率不能鼓励跳过安全步骤

只优化工具调用数可能导致：

  • 不查权限
  • 不校验最新状态
  • 不做提交后确认
  • 不保存证据

更合理的是在“通过全部目标和安全门禁”的运行中比较成本。

先过滤不合格运行，再做效率 Pareto 分析。

4. Budget Exhaustion 也要有正确终态

达到步骤或费用预算后，Agent 应：

  • 停止新动作
  • 取消可取消的在途调用
  • 保存已执行状态
  • 明确任务未完成
  • 提供人工接管信息

不能在最后一个预算单位上发起不可控写入，然后没有资源确认结果。

十二、模拟器设计：可重复比“看起来像生产”更重要

1. 模拟器需要提供什么

一个用于 Agent 回归的模拟器至少应支持：

  • 可加载初始 fixture
  • 确定性时钟
  • 可设置随机 seed
  • 状态版本
  • 工具 schema 和业务校验
  • 真实副作用语义
  • 幂等键
  • 故障注入
  • 状态快照和事件日志
  • 一键重置

2. 模拟器不是把 API 返回值写死

如果工具无论参数如何都返回预设成功，测不到：

  • 参数绑定错误
  • 状态冲突
  • 重复写入
  • 权限问题
  • 前置条件缺失
  • 业务不变量破坏

模拟器应该是一个简化但真实的状态机。

例如取消订单至少要考虑：

  • 订单是否存在
  • 是否属于当前用户
  • 当前状态是否允许取消
  • 版本是否匹配
  • 取消是否产生退款事件

3. 模拟器保真度分层

可以分成三层：

  1. 协议保真：schema、错误码和超时语义一致
  2. 状态保真：核心业务状态转换和不变量一致
  3. 分布保真：数据规模、延迟和故障分布接近真实环境

早期评测不必复制整个生产系统。

但涉及本次测试目标的状态语义必须准确。

4. 模拟器与真实环境互补

模拟器适合：

  • 大量重复运行
  • 高风险故障注入
  • 精确状态断言
  • CI 中快速回归

预发布真实环境适合：

  • 验证协议差异
  • 验证真实权限和网络
  • 发现模拟器遗漏
  • 测量实际延迟和依赖行为

生产影子评测适合：

  • 只读或不执行副作用的决策观察
  • 新分布发现
  • 线上策略监控

不能为了“真实”直接在生产执行不可逆测试动作。

十三、轨迹重放：先明确你想重放哪一层

1. Observation Replay

把历史工具 observation 按顺序返回给新 Agent，不再调用真实工具。

用途：

  • 比较模型或 Prompt 在同样观察下的决策
  • 复现某次异常上下文
  • 降低外部依赖变化

局限：

  • 新 Agent 可能选择不同工具
  • 历史 observation 未必适用于新路径
  • 不能验证真实工具兼容性

2. Tool Replay

重放历史动作到可重置模拟器或隔离环境。

用途：

  • 验证工具代理和状态转换
  • 重现副作用和故障阶段
  • 检查 evaluator 是否稳定

写操作不能直接重放到不可重置生产环境。

3. Decision Replay

固定模型决策输出，重新执行工具层。

用途：

  • 隔离工具或环境版本变化
  • 验证故障注入和恢复执行器
  • 比较不同工具实现

4. Full Re-run

从初始 fixture 重新运行 Agent、模型和工具。

用途：

  • 端到端回归
  • 非确定性统计
  • 发布候选验证

它最接近实际表现，但变量也最多。

5. 可重放轨迹必须保存什么

至少保存：

  • 任务契约版本
  • Agent 配置与 Prompt 版本
  • 工具 schema 版本
  • 初始状态快照
  • 每个动作和参数
  • observation 原文或结构化结果
  • 策略判定
  • 故障命中记录
  • 每步状态版本或摘要
  • 最终状态
  • evaluator 版本
  • 模型标识和采样配置
  • seed、时钟和超时设置

6. 敏感数据和重放

轨迹可能包含：

  • 个人信息
  • 访问令牌
  • 内部资源 ID
  • 业务数据
  • 模型输入中的秘密

重放存储需要：

  • 字段级脱敏
  • 凭据不落盘
  • 访问控制
  • 保留期限
  • 审计
  • 测试数据替换

不能为了可复现而复制完整生产秘密。

十四、端到端测试设计

1. 能力维度

测试集至少覆盖：

  • 单工具只读
  • 单工具写入
  • 多工具顺序依赖
  • 多工具可并行
  • 条件分支
  • 多轮用户澄清
  • 长轨迹状态保持
  • 中途权限变化
  • 故障恢复
  • 安全终止和人工接管

2. 输入变化

对同一业务目标做等价变体：

  • 同义改写
  • 信息顺序变化
  • 增加无关背景
  • 使用简称或别名
  • 明确与模糊时间表达
  • 单实体与多实体消歧
  • 中英文混合字段
  • 用户给出冲突信息

等价输入不要求轨迹完全相同，但目标和安全边界应一致。

3. 状态变化

对同一任务改变初始环境：

  • 资源存在或不存在
  • 权限允许或拒绝
  • 库存充足或不足
  • 版本一致或冲突
  • 任务已部分执行
  • 幂等请求已存在
  • 依赖正常或降级

这样可以验证 Agent 是否真正观察状态，而不是机械复用路径。

4. Metamorphic Tests

当完整标准答案难以穷举时，可以定义变形关系。

例如：

  • 只改变用户 ID，所有写入实体也必须同步改变
  • 把权限从 writer 改为 reader，写入必须被放弃
  • 把数量从 1 改为 2，创建参数和库存变化应一致
  • 增加无关只读工具，不应改变最终业务状态
  • 调换两个独立读取的顺序，不应影响结果
  • 注入一次提交前超时，不应增加最终副作用数量

变形测试适合发现硬编码、实体串线和工具诱导。

5. 对抗和安全测试

需要覆盖：

  • 用户要求忽略权限规则
  • 工具返回中包含恶意指令文本
  • observation 伪装成系统提示
  • 参数中包含路径穿越或注入载荷
  • 工具描述相似导致错误选择
  • 高权限工具名称更“方便”
  • 外部内容要求泄露会话信息

测试 Oracle 要检查动作和副作用，而不仅检查 Agent 是否在文字上拒绝。

6. 并发与状态竞争

真实环境里，Agent 不是唯一写入者。

应注入：

  • 读取后资源被其他进程修改
  • 多 Agent 同时操作同一实体
  • 异步事件延迟到达
  • 状态通知乱序
  • 锁等待或事务冲突

关键断言：

  • 是否使用版本或条件写
  • 冲突后是否重新读取
  • 是否根据新状态重新决策
  • 是否避免覆盖他人更新

7. 测试金字塔

可以分为：

不要把所有问题都留到昂贵的端到端模型运行中发现。

3. 失败分类

评测结果建议至少归类为：

  • PLANNING_ERROR：任务拆解遗漏关键目标
  • TOOL_SELECTION_ERROR：工具能力选择错误
  • ARGUMENT_ERROR：参数 schema 或语义错误
  • ORDERING_ERROR：违反前置或关键偏序
  • STATE_ERROR：使用过期或虚构状态
  • TOOL_RUNTIME_ERROR：工具实现或依赖失败
  • RECOVERY_ERROR：错误重试、补偿或终止
  • POLICY_ERROR：越权或策略违反
  • EVALUATOR_ERROR：断言或标注有误
  • INFRA_ERROR：评测基础设施异常
  • BUDGET_ERROR：未在预算内收敛

每个失败只能有一个主责任层，但可以附带次级因素。

这样能避免所有问题都被归为“模型不稳定”。

4. 失败样本包

一次失败至少输出：

  • case 契约
  • 初始状态和最终状态差异
  • 轨迹时间线
  • 工具参数及 schema 判定
  • 故障注入命中点
  • 策略允许/拒绝记录
  • 失败的目标和不变量
  • 成本与预算
  • 与上一个基线版本的轨迹差异
  • 可重放命令或入口

十七、常见误区

1. 只看最终回复

Agent 可以自信地报告一个并不存在的结果。

业务状态必须由独立 Oracle 验证。

2. 最终状态正确就算通过

中途越权、重复收费或绕过审批不能被正确终态掩盖。

3. 强制匹配唯一标准轨迹

合法路径可能不止一条。

应检查能力、偏序、不变量和禁止动作。

4. 工具返回成功就算任务成功

异步任务、事务回滚和错误租户都可能让工具级成功失真。

5. schema 合法就算参数正确

类型正确但实体绑定错误，是 Agent 工具调用最危险的问题之一。

6. 把所有错误都设成可重试

权限拒绝、永久参数错误和提交状态不明需要不同策略。

7. 只注入调用前故障

最危险的重复副作用通常发生在提交后响应丢失。

8. 防护层拦截成功就给 Agent 通过

系统控制通过不等于 Agent 决策正确。

越权尝试仍要统计。

9. 只看平均成功率

平均值会掩盖高风险切片和不稳定重复运行。

10. 用 pass@k 包装可靠性

允许多次尝试后“至少一次成功”不能代表每次执行都可靠。

11. 为了省成本跳过后置校验

成本比较应在通过安全门禁的运行之间进行。

12. 保存长思维链，却不保存状态快照

可审计动作、observation 和状态变化比不可验证的内部叙述更重要。

13. 在生产环境直接重放写轨迹

轨迹重放必须进入可重置模拟器或隔离环境。

14. 模拟器永远返回预设成功

这种模拟器只能测格式，不能测业务语义和恢复。

15. 评测平台异常也归到 Agent

模拟器、注入器和 evaluator 必须有自己的测试与错误分类。

十八、上线前检查表

任务契约

  • 自然语言任务已转成可执行目标谓词
  • 初始状态 fixture 可重复加载
  • 身份、租户和角色明确
  • 终态与全过程不变量分别定义
  • 允许工具和禁止动作明确
  • 关键偏序关系可执行校验
  • 预算和允许终态已定义
  • 高风险任务有独立切片

最终状态

  • 业务目标由权威状态验证
  • 数量使用精确断言而非仅 exists
  • 无关实体与租户保持不变
  • 副作用、补偿和异步事件均被检查
  • 最终回复与真实状态一致
  • 部分完成不会被误判为成功
  • Progress 仅用于诊断
  • 失败后环境可重置

工具与参数

  • 工具 schema 版本被冻结
  • schema validity 与语义正确性分开
  • 关键实体和租户字段使用硬断言
  • 幂等键生成和复用可追踪
  • 必要能力覆盖可统计
  • 禁止工具尝试单独记录
  • 合法替代路径不会被误判
  • 工具返回与状态副作用能关联

顺序与状态

  • 关键顺序用偏序约束表达
  • 写入前置条件已校验
  • 每步记录状态版本或摘要
  • 陈旧状态动作可识别
  • 并发冲突会触发重新观察
  • 写入后校验规则符合风险等级
  • observation 失败不会被当作成功
  • 状态不确定时不会盲目继续

故障与恢复

  • 调用前、提交前和提交后故障分别覆盖
  • 暂时、永久、权限和冲突错误分别处理
  • 故障计划带版本和 seed
  • 注入器能证明真实副作用阶段
  • 恢复成功包含目标和不变量检查
  • 不可恢复时能安全终止或转人工
  • 恢复额外调用、延迟和成本可统计
  • 重试不会覆盖首错证据

权限与安全

  • 授权在工具服务端执行
  • 越权尝试和越权成功分别统计
  • 跨租户、只读和字段级权限已覆盖
  • 权限中途变化已测试
  • 工具 observation 中的恶意指令已覆盖
  • 敏感数据不会进入日志和重放包
  • 高风险违规是硬门禁
  • 安全控制本身有独立测试

可靠性与成本

  • 关键 case 做多 seed 重复运行
  • pass^k 与 pass@k 含义未混淆
  • 报告包含成功数、总数和置信区间
  • 高风险切片展示最差运行
  • 成功与失败成本分开统计
  • 超预算后有安全终态
  • 效率只在合格运行之间比较
  • 版本回归使用同样本配对比较

轨迹与重放

  • 任务、工具、模型和 evaluator 版本完整
  • 动作、参数、observation 和策略判定完整
  • 初始状态和最终状态可恢复
  • 故障命中点可定位到提交阶段
  • Observation、Tool、Decision Replay 边界明确
  • 写轨迹只在可重置环境重放
  • 凭据和个人信息已脱敏
  • 失败包有稳定重放入口

十九、总结

Agent 评测比普通问答评测多出的核心变量，是状态和副作用。

一套可信的评测体系必须把两层分开：

最终状态层负责判断：

  • 任务是否真正完成
  • 目标数量和实体是否正确
  • 不变量是否保持
  • 副作用是否唯一、完整且可审计

轨迹层负责判断：

  • 工具是否选对
  • 参数是否通过 schema 和业务语义校验
  • 关键顺序是否满足
  • 决策是否基于当前状态
  • 故障后是否正确恢复
  • 是否尝试越权
  • 是否在预算内收敛

恢复评测不能只看重试次数。

必须通过确定性故障注入区分：

  • 请求没有发生
  • 事务没有提交
  • 事务已提交但响应丢失
  • 权限或参数永久失败
  • 状态冲突和部分成功

然后检查 Agent 是：

  • 正确恢复
  • 受控降级
  • 安全转人工
  • 还是制造重复副作用和状态污染

模拟器提供可重复状态，故障代理提供精确错误阶段，轨迹重放提供版本对比，最终状态 Oracle 提供独立真相。

四者结合后，Agent 的“不稳定”才会从模糊印象变成可测量、可归因、可修复的问题。

最终的发布原则应保持简单：

目标状态正确只是必要条件；只有轨迹合规、恢复安全、权限受控且成本可接受，Agent 才真正通过。
