AI测试-10-AI时代测试开发工程师需要建立怎样的能力图谱

发表于 2026-03-08 分类于 AI测试 本文字数： 11k 阅读时长 ≈ 40 分钟

传统测试开发工程师进入 AI 项目后，最容易出现两种误判。

第一种误判是：

“我会调用模型 API，也会写 Prompt，所以已经具备 AI 测试能力。”

第二种误判是：

“大模型输出不确定，传统自动化测试方法已经没有用了。”

这两个判断都把问题看窄了。

API 调通只说明接口可访问，不能说明系统可评测、可上线、可追踪。

输出具有概率性，也不意味着质量无法定义。

它意味着测试对象从一段确定性代码，扩展成了由模型、数据、上下文、工具、策略和运行环境共同决定的系统。

测试开发工程师真正需要完成的变化，不是把原来的技术栈全部推倒重来。

而是把已经具备的自动化、平台、性能、稳定性和安全能力，延伸到 AI 系统的新失效面。

本文给出一张面向工程交付的能力图谱。

它不讨论“如何在半年内成为 AI 专家”，也不把会使用多少框架当成能力。

它只回答三个可验证的问题：

  • 一个测试开发工程师进入 AI 项目后，必须补齐哪些能力层
  • 每一层达到什么程度，才算能够独立承担质量工作
  • 学习结果应当沉淀成什么证据，而不是停留在课程和术语上

已有的 AI 测试系列文章已经讨论过 Function Calling、Agent Workflow、RAG、平台分层和风险控制。

本文不会重复这些模块的具体实现。

本文关注的是更上层的能力组织方式，以及怎样验证这些能力已经真正形成。

一、问题边界：这里讨论的不是“AI 从业者通用技能清单”

能力图谱如果没有边界，很快就会变成名词堆砌。

机器学习、数据工程、分布式系统、安全、产品、法规都可以无限展开。

测试开发工程师不可能在每个方向上都达到研究或专家深度。

因此，本文限定四个边界。

1. 目标角色是 AI 质量工程师，不是基础模型研究员

本文中的目标角色，需要理解模型为什么会出现某类行为。

但不要求从零训练一个基础模型，也不要求推导所有优化算法。

需要理解的深度以“能够设计测试、解释指标和定位边界”为准。

例如：

  • 要理解 tokenization 会改变输入长度和边界
  • 要理解采样参数会改变输出分布
  • 要理解 RAG 的错误可能来自召回而不是生成
  • 要理解 Agent 的失败可能发生在规划、选工具、参数、执行或收口
  • 要理解推理服务的延迟至少要拆成排队、prefill 和 decode

但是否需要手写 CUDA kernel，不属于所有测试开发工程师的共同基线。

能力图谱必须围绕完整链路建立。

3. “会用”必须落到可复现证据

本文不使用“了解”“熟悉”“精通”作为最终判断。

这些词无法验收。

更可操作的能力描述应该是：

  • 能构造覆盖关键风险的评测数据集
  • 能解释一个指标的分母、采样范围和置信区间
  • 能从 trace 中区分检索失败与生成失败
  • 能为高风险工具调用设计权限、确认和回滚机制
  • 能把模型升级纳入离线回归与线上灰度
  • 能用失败样本推动数据、策略或系统修复

每项能力都应有输入、动作、产物和验收标准。

4. 能力深度由业务风险决定

同一个问答机器人和一个能够修改生产配置的 Agent，不能使用同一套质量门槛。

  • P(Failure) 是失败概率
  • Impact(Failure) 是单次失败影响

涉及资金、隐私、生产变更或设备控制的系统，则必须提高确定性校验、人工确认和审计要求。

所以能力图谱不是统一考试大纲。

它是一套根据风险选择深度的工程坐标系。

二、核心变化：从验证确定性代码，扩展到治理概率性系统

传统软件测试的许多方法仍然有效。

输入分区、边界值、状态迁移、故障注入、负载测试、安全测试和可观测性都没有失效。

变化主要发生在四个方面。

1. 期望结果从单点值扩展为约束集合

传统接口可能要求：

而 AI 输出常常有多个都合理的表达。

此时不能只比较完整字符串。

需要把期望拆成：

  • 必须出现的事实
  • 不得出现的事实
  • 结构是否合法
  • 引用是否支持结论
  • 动作是否满足权限
  • 语义是否完成任务
  • 不确定时是否正确拒答或升级

断言从单一相等，升级为多层约束。

2. 测试数据从辅助材料变成系统资产

模型行为高度依赖输入分布。

没有代表性数据集，就无法解释“通过率 90%”代表什么。

数据集必须记录：

  • 样本来源
  • 业务意图
  • 风险等级
  • 难度
  • 语言与格式
  • 期望和禁区
  • 版本
  • 审核人
  • 适用范围

AI 项目中的测试数据管理，接近代码和配置管理，而不是临时 Excel。

3. 失败不再只有代码缺陷

同一个错误答案可能来自：

  • 输入被错误规范化
  • 上下文被截断
  • 检索没有召回正确文档
  • 召回了过期文档
  • Prompt 约束不完整
  • 模型能力不足
  • 采样导致波动
  • 工具参数生成错误
  • 工具本身失败
  • 后处理错误地改写结果

如果没有链路观测，团队只会把所有问题统称为“模型幻觉”。

这种归因既无法修复，也无法形成回归测试。

4. 发布对象从代码版本扩展为行为版本

AI 功能的行为可能同时受以下版本影响：

  • 应用代码版本
  • 模型标识与权重版本
  • tokenizer 和 chat template
  • system prompt 与模板版本
  • 检索索引和知识快照
  • 工具 schema 与实现版本
  • 推理参数
  • 安全策略
  • 评测集版本

所以一次可审计发布，必须能够重建当时的行为组合。

只记录 Git commit 不再足够。

三、能力地图：一个底座、七个能力域、一条证据链

本文使用的能力地图由三部分构成。

1. 一个工程底座

工程底座包括：

  • 编程与代码质量
  • 接口和自动化测试
  • 操作系统与网络
  • 数据库与消息系统
  • 分布式系统基础
  • CI/CD
  • 性能、稳定性与安全
  • 日志、指标、追踪

这些能力并没有因为 AI 出现而贬值。

相反，模型一旦接入真实业务，最终仍然运行在普通软件系统里。

排队、超时、重试、缓存、并发、资源争用和依赖故障仍然决定可用性。

2. 七个 AI 质量能力域

七个能力域分别是：

  1. 模型认知
  2. 数据与知识
  3. 评测与实验
  4. Agent 与工具
  5. LLMOps 与可靠性
  6. 安全与治理
  7. 领域质量

它们不是七条互不相干的学习路线。

一次完整项目会同时使用它们。

例如，一个 Android 日志分析 Agent 至少涉及：

  • 模型是否能理解日志和时间关系
  • 日志数据是否脱敏、切片和保留来源
  • 根因候选如何评测
  • Agent 能否安全调用日志查询工具
  • 长日志下的成本和延迟是否可控
  • 是否会泄漏设备标识或用户数据
  • Android 故障域知识是否正确

3. 一条可交付证据链

学习过程应当沿着下面的证据链推进：

“能解释”是起点，不是终点。

如果一个人能讲清 attention，却不能构造模型升级回归集，那么能力仍停留在认知层。

如果一个人能做离线评测，却不能解释线上指标漂移，那么能力还没有进入运行阶段。

如果一个人能把 Agent 跑起来，却不能限制权限和恢复失败，那么系统仍不具备可信交付条件。

四、能力域一：模型认知，目标是解释行为而不是背网络结构

模型认知是后续测试设计的因果基础。

它至少包含五组知识。

1. 输入表示

需要理解：

  • Unicode 规范化可能改变文本
  • tokenizer 把文本映射为 token ID
  • 不同 tokenizer 的切分和长度可能不同
  • chat template 会插入角色与特殊 token
  • 截断策略可能删除系统指令或关键证据
  • 多模态输入还有图像、音频等预处理

可交付证据：

  • 一份 tokenizer 差异实验
  • 一组空白符、全半角、组合字符和长上下文边界用例
  • 一份截断前后输入可视化

2. 推理过程

需要理解：

  • embedding 与位置信息的作用
  • Transformer block 的高层数据流
  • 自回归生成为什么逐 token 进行
  • prefill 与 decode 的差异
  • KV cache 为什么影响速度和显存
  • logits 如何经过解码策略变成 token

可交付证据：

  • 一条从请求到流式输出的阶段 trace
  • 一份 TTFT、TPOT 和端到端延迟拆解
  • 一组不同输入长度和输出长度的性能曲线

下一篇《大模型从输入 Token 到生成结果到底经历了什么》会专门展开这一部分。

3. 采样与不确定性

需要理解：

  • greedy、temperature、top-k、top-p 的区别
  • 固定 seed 不一定保证跨硬件、跨版本完全复现
  • 同一语义可以有多个合格答案
  • 多次采样可以估计稳定性，但不能替代风险断言
  • 确定性任务应尽量约束输出空间

可交付证据：

  • 同一评测集在不同采样配置下的分布对比
  • 对关键结构字段使用 schema 校验的实现
  • 对高风险任务使用确定性工具结果收口的设计

4. 模型边界

需要理解：

  • 训练截止信息与当前事实不是一回事
  • 模型参数中的知识难以直接审计来源
  • 长上下文可接受不等于长上下文中的每条信息都能可靠利用
  • 模型拒答、遗漏和过度服从都可能成为失败
  • 模型能力与系统护栏是两个维度

可交付证据：

  • 能力边界说明
  • 已知失败样本库
  • 需要检索、工具或人工确认的任务分流规则

5. 模型选择与变更

测试开发工程师不一定负责最终选型，但必须能定义选择依据。

至少比较：

  • 任务质量
  • 延迟和吞吐
  • 上下文与输出限制
  • 结构化输出可靠性
  • 工具调用适配性
  • 数据与部署边界
  • 成本
  • 可观测性
  • 供应商和版本变更风险

可交付证据不是一张“模型排行榜”。

而是同一业务数据、同一评测协议、同一成本口径下的决策记录。

五、能力域二：数据与知识，目标是建立可追溯的数据生命周期

模型行为的上限和评测结论，都受数据质量制约。

数据能力至少分成四层。

1. 采集与准入

需要回答：

  • 数据为什么可以使用
  • 是否包含个人信息、密钥或受限内容
  • 数据是否代表真实输入分布
  • 是否过度集中在正常样本
  • 是否包含高风险和低频场景
  • 是否允许进入模型、知识库或评测集

可交付证据：

  • 数据来源清单
  • 准入规则
  • 脱敏策略
  • 数据所有者
  • 保留与删除策略

2. 清洗与标注

AI 评测的标注不是简单写一个标准答案。

复杂任务更适合记录：

  • 任务目标
  • 必须满足项
  • 禁止项
  • 可接受变体
  • 参考证据
  • 风险等级
  • 评分 rubric
  • 无法判断时的处理方式

可交付证据：

  • 标注指南
  • 双人复核记录
  • 分歧样本和裁决结果
  • 标注一致性指标

3. 版本与血缘

每个结果至少要能追溯到：

  • dataset_version
  • sample_id
  • source_snapshot
  • label_version
  • preprocessing_version
  • evaluator_version

如果评测集悄悄变化，趋势图会失去意义。

如果知识库更新但没有快照，历史失败无法重放。

4. RAG 知识质量

这一部分的核心不只是向量检索。

还包括：

  • 文档有效期
  • 权限继承
  • 切片边界
  • 元数据
  • 重复与冲突
  • 稀疏和稠密召回
  • 重排
  • 引用绑定
  • 无证据降级

已有《RAG + 测试知识库怎么做数据清洗召回和结果校验》讨论了具体链路。

从能力图谱角度，验收标准是：

能够把一次错误回答拆成数据错误、召回错误、排序错误、上下文组装错误或生成错误。

六、能力域三：评测与实验，这是 AI 质量工程的核心专业能力

如果只能选一个优先补齐的能力域，应当优先评测。

因为没有评测，模型选型、Prompt 优化、RAG 调整和 Agent 升级都只能靠演示印象。

1. 先定义任务，再定义指标

不同任务需要不同评测单元。

任务 主要评测对象 示例指标
分类 标签 Precision、Recall、F1
信息抽取 字段或实体 字段准确率、完整率
问答 事实与证据 正确性、忠实度、引用覆盖
摘要 事实压缩 覆盖、事实一致性、冗余
代码生成 可执行行为 编译率、测试通过率、安全规则
工具调用 调用决策 工具选择、参数正确率、任务完成率
Agent 多步骤轨迹 步骤效率、恢复率、越权率、最终成功率

一个“总体得分”不能替代分项指标。

总体分数相同的两个系统，可能一个经常答错，另一个经常拒答。

两者的业务风险完全不同。

2. 构建分层评测集

至少应包含：

  • 主干业务样本
  • 边界样本
  • 对抗样本
  • 历史缺陷样本
  • 安全样本
  • 长上下文样本
  • 多语言或格式扰动样本
  • 工具和依赖失败样本

还应区分：

  • 开发集：用于调试
  • 回归集：用于版本门禁
  • 保留集：减少过拟合评测集
  • 线上采样集：验证真实分布

3. 组合多种判定器

AI 评测不应只有 LLM-as-Judge。

更稳妥的判定顺序是：

  1. 确定性规则
  2. 结构和 schema
  3. 可执行验证
  4. 证据一致性
  5. 语义评分
  6. 人工复核

例如代码生成任务，应先编译和跑测试。

只有无法用程序直接判断的部分，才交给语义裁判。

4. 处理统计不确定性

当输出存在采样波动时，单次运行不能代表稳定性。

对二元成功指标，样本成功率可以写成：

其中 x_i \in \{0,1\}。

但仅报告 \hat{p} 不够。

还需要说明：

  • 样本数
  • 样本分层
  • 重复次数
  • 随机配置
  • 置信区间
  • 与基线的差异是否具有实际意义

对关键风险，可以使用“最差分层结果”而不是平均值作为门禁。

5. 设计回归门禁

一个可执行门禁不应该只写“总分不能下降”。

它至少包含：

  • 核心任务成功率下限
  • 高风险错误为零或极低上限
  • 各关键分层不得显著退化
  • 延迟和成本预算
  • 人工抽检规则
  • 失败样本输出
  • 阻断与豁免流程

可交付证据：

  • 版本化评测集
  • 可重复执行的 runner
  • 指标定义文档
  • 基线和候选版本对比报告
  • 失败聚类与回归用例

七、能力域四：Agent 与工具，目标是控制动作而不是欣赏规划

Agent 把模型输出从“内容”扩大成“动作”。

因此，错误的影响也从答错问题扩大为修改数据、发送请求或控制设备。

1. 工具契约

每个工具至少要定义：

  • 工具用途
  • 参数 schema
  • 业务约束
  • 权限要求
  • 超时
  • 幂等性
  • 副作用
  • 错误分类
  • 可重试性
  • 审计字段

仅有 JSON Schema 不够。

“金额是 number”不能证明这次退款被允许。

2. 状态与恢复

多步骤任务要区分：

  • 计划状态
  • 执行状态
  • 外部资源状态
  • 证据状态
  • 人工审批状态

恢复动作也要按失败类型选择：

  • 同参重试
  • 补充上下文
  • 换工具
  • 回滚
  • 跳过
  • 转人工
  • 终止

已有《Agent Workflow 执行多步骤测试任务时怎么做状态管理和失败恢复》详细讨论了这一点。

能力验收应关注：

  • 中断后能否恢复到一致状态
  • 重试是否重复产生副作用
  • 工具失败是否被错误解释成任务成功
  • 上下文污染是否跨任务传播
  • 人工接管能否看到完整证据

3. 权限与自主性分级

可以把 Agent 动作分成：

等级 动作 默认控制
A0 只读解释 日志和引用
A1 只读工具调用 工具白名单、参数校验
A2 可逆写操作 幂等、审批或自动回滚
A3 高影响写操作 强制人工确认、双人审批
A4 不可逆或跨边界操作 默认禁止或隔离环境

自主性不是越高越先进。

正确目标是风险与控制匹配。

4. Agent 评测

除了最终答案，还应记录：

  • 是否选择正确工具
  • 参数是否正确
  • 是否执行不必要步骤
  • 是否循环
  • 是否使用了过期状态
  • 是否越权
  • 是否正确处理工具错误
  • 最终状态是否与外部系统一致

轨迹是 Agent 测试的第一等证据。

只保存最终回答会丢失最有价值的故障现场。

八、能力域五：LLMOps 与可靠性，目标是让行为在生产中可运营

离线评测通过，不代表线上系统稳定。

线上还会遇到排队、限流、供应商故障、模型更新、成本波动和输入漂移。

1. 可观测性

一条 AI trace 至少应关联：

  • request_id
  • user_or_tenant_scope
  • model_route
  • model_version
  • prompt_template_version
  • input_token_count
  • retrieval_trace
  • tool_trace
  • output_token_count
  • latency_breakdown
  • finish_reason
  • safety_decision
  • evaluator_result
  • cost_estimate

敏感原文不一定可以直接记录。

可观测性设计必须同时考虑脱敏、哈希、抽样和访问控制。

2. 性能与容量

至少要理解并测试：

  • TTFT
  • token 间延迟
  • 端到端延迟
  • 输入和输出 tokens/s
  • 并发
  • 排队时间
  • 超时率
  • KV cache 或内存压力
  • 吞吐与单请求时延的权衡

平均值通常会掩盖尾延迟。

质量门槛应优先看 P95、P99 和分层结果。

3. 弹性与降级

需要设计：

  • 超时预算
  • 限流
  • 重试边界
  • 熔断
  • 备用模型
  • 规则或搜索降级
  • 缓存
  • 部分结果
  • 转人工

注意：

模型切换不是无损操作。

不同模型可能有不同 tokenizer、模板、输出格式和安全行为。

降级路径本身必须进入评测集。

4. 成本治理

成本至少拆成：

其中价格单位必须明确。

除了单次成本，还应观察：

  • 每个成功任务成本
  • 每个租户成本
  • 重试放大率
  • 无效上下文占比
  • 缓存命中率
  • 长尾任务成本

只压缩 Prompt 而不观察成功率，可能把成本降低变成质量退化。

5. 变更与发布

一次模型或策略变更应经过：

  1. 离线回归
  2. 影子流量
  3. 小流量灰度
  4. 分层指标观察
  5. 失败样本复核
  6. 扩量或回滚

可交付证据：

  • 版本清单
  • trace schema
  • 仪表盘
  • SLO
  • 容量报告
  • 灰度和回滚记录
  • 事故复盘

九、能力域六：安全与治理，目标是把模型风险转成系统控制

安全不能只靠一句 system prompt。

Prompt 是上下文，不是权限系统。

1. 威胁建模

需要覆盖：

  • 直接 Prompt Injection
  • 间接 Prompt Injection
  • 敏感信息泄漏
  • 不安全输出处理
  • 工具滥用
  • 过度授权
  • 知识库投毒
  • 模型和依赖供应链
  • 资源耗尽
  • 审计缺失

OWASP 的生成式 AI 安全资料可以作为风险清单起点。

但最终测试矩阵必须结合自己的数据流和信任边界。

2. 权限控制

需要理解：

  • 身份与模型不是一回事
  • 模型建议不能直接提升权限
  • 工具应在服务端重新鉴权
  • 租户隔离不能依赖 Prompt
  • 高风险动作需要确认和审计
  • 密钥不能进入不受控上下文

3. 数据治理

需要建立：

  • 数据分类
  • 最小化采集
  • 脱敏
  • 用途限制
  • 保留和删除
  • 供应商数据处理边界
  • 评测数据访问控制
  • 线上样本回流审批

4. 风险闭环

风险记录应包含：

  • 风险描述
  • 触发条件
  • 影响
  • 检测方法
  • 预防控制
  • 事后控制
  • 所有者
  • 接受标准
  • 剩余风险

NIST AI RMF 使用 Govern、Map、Measure、Manage 组织风险活动。

工程团队不必机械照搬名称。

但治理、场景映射、度量和处置四类活动不能缺失。

可交付证据：

  • 威胁模型
  • 攻击用例集
  • 权限矩阵
  • 数据流图
  • 风险登记册
  • 审计记录
  • 应急预案

十、能力域七：领域质量，目标是让 AI 判断服从业务事实

通用模型能力不能替代领域知识。

测试开发工程师的差异化价值，往往来自“AI 工程能力 + 深领域”。

1. Android 稳定性方向

可以建立：

  • logcat、ANR、tombstone、bugreport 的结构化解析
  • App、Framework、Native、HAL、Kernel 的故障分层
  • 根因候选必须绑定日志证据
  • 设备、版本、场景和资源状态的上下文模型
  • 错误归因的反例集

AI 可以帮助聚类和提出候选。

最终结论仍要受系统证据约束。

2. UI 自动化方向

可以建立：

  • 视觉定位与结构定位的交叉校验
  • 页面状态识别
  • 不确定时的重试或人工确认
  • 屏幕变化、动画、遮挡和多语言评测集
  • 动作前后状态证据

3. 语音 Agent 方向

需要把链路拆成：

评测不能只看最终文本。

还要看：

  • 首包延迟
  • 转写错误
  • 语义任务完成
  • 工具执行
  • TTS 可懂度
  • 打断
  • 噪声与弱网

4. 测试平台方向

平台能力应沉淀为：

  • 版本化数据集
  • 执行器
  • 评判器
  • 证据存储
  • 指标计算
  • 实验对比
  • 质量门禁
  • 线上反馈闭环

领域能力不是“知道业务术语”。

而是能够把领域事实写进数据、断言、工具约束和故障分类。

十一、能力成熟度：用五级交付能力替代“了解、熟悉、精通”

能力成熟度可以定义为 L0 到 L4。

L0：概念接触

表现：

  • 能说出术语
  • 能运行示例
  • 主要依赖教程
  • 无法解释失败原因

证据：

  • 学习笔记
  • 最小演示

风险：

  • 容易把 PoC 当成生产能力

L1：单点验证

表现：

  • 能针对一个明确问题写实验
  • 能控制部分变量
  • 能得到可重复的局部结果

证据：

  • 实验脚本
  • 输入输出样本
  • 参数和环境记录

风险：

  • 仍可能忽略完整系统链路

L2：闭环交付

表现：

  • 能把数据、执行、评测和报告连成闭环
  • 能定义通过标准
  • 能复现失败
  • 能把缺陷变成回归样本

证据：

  • 版本化评测集
  • 自动化 runner
  • 分层报告
  • 缺陷回归记录

这是独立承担 AI 质量工作的最低实用等级。

L3：生产运营

表现：

  • 能观测线上质量、延迟、成本和风险
  • 能设计灰度、降级和回滚
  • 能分析分布漂移
  • 能推动跨团队修复

证据：

  • SLO 和仪表盘
  • 线上采样评测
  • 容量与成本报告
  • 事故复盘

L4：体系治理

表现：

  • 能定义组织级标准和质量门禁
  • 能按风险分级配置控制
  • 能审计模型、数据、工具和策略变更
  • 能度量控制措施是否有效

证据：

  • 治理流程
  • 风险登记册
  • 跨项目基准
  • 审计和改进记录

成熟度不能只看最高项。

一个 Agent 工程能力达到 L3，但安全仍是 L0，不应被评价为“总体 L3”。

十四、学习路线：按交付闭环推进，而不是按热门工具推进

下面给出一条 12 个月的参考路线。

时间只是组织方式，不是统一工期。

已有较强测试平台和稳定性基础的人，可以压缩工程底座阶段。

阶段一：第 1 至 2 个月，建立模型与数据的可观察实验

目标：

  • 不再把模型当黑盒 API
  • 能解释输入、参数和输出之间的关系

任务：

  • 对同一文本比较不同 tokenizer 的 token 数和边界
  • 对 temperature、top-p 和 seed 做重复实验
  • 记录请求、token、延迟、finish reason
  • 构建 50 到 100 条小型评测集
  • 给样本定义必须项、禁止项和风险等级

交付物：

  • tokenizer 实验报告
  • 采样稳定性报告
  • dataset card
  • 最小评测 runner

阶段门：

  • 任一结果都能用相同版本和参数重放
  • 能解释失败来自输入、模型还是判定器

阶段二：第 3 至 5 个月，建立离线质量闭环

目标：

  • 从“人工看回答”升级为自动化评测

任务：

  • 组合规则、schema、执行验证和语义裁判
  • 构建分层回归集
  • 为裁判建立人工校准样本
  • 记录置信区间和分层结果
  • 把历史缺陷转成回归样本

交付物：

  • 版本化评测集
  • 评判器接口
  • 候选模型对比报告
  • CI 质量门禁

阶段门：

  • 新版本能自动与基线比较
  • 报告能直接定位退化样本，而不只有总分

阶段三：第 6 至 8 个月，建立 Agent 与可靠性闭环

目标：

  • 让模型驱动的动作可控、可恢复、可审计

任务：

  • 定义工具 schema 与业务约束
  • 建立执行状态机
  • 注入超时、重复、部分成功和依赖故障
  • 记录完整轨迹
  • 建立 TTFT、TPOT、成本和错误率仪表盘
  • 设计降级、灰度和回滚

交付物：

  • 工具契约
  • 故障注入报告
  • trace schema
  • SLO 与容量报告
  • Agent 轨迹评测

阶段门：

  • 失败后外部系统状态一致
  • 高风险动作不能绕过权限和确认
  • 线上异常能够从 trace 回到具体阶段

阶段四：第 9 至 12 个月，建立安全与领域化闭环

目标：

  • 把通用能力收敛到一个高价值领域

任务：

  • 建立威胁模型和攻击样本
  • 完成数据分类和权限矩阵
  • 选择 Android、UI、语音或测试平台中的一个主方向
  • 建立领域故障分类
  • 引入专家复核
  • 将线上失败回流到评测集

交付物：

  • 安全测试矩阵
  • 领域基准集
  • 风险登记册
  • 端到端项目
  • 运行和治理手册

阶段门：

  • 能给出项目适用边界和剩余风险
  • 能证明控制措施确实降低了风险

十五、三个递进项目：用项目证据替代课程数量

项目一：模型行为探针

范围：

  • 单模型
  • 无工具
  • 小型数据集

必须包含：

  • 输入规范化和 token 记录
  • 采样参数实验
  • 结构化输出校验
  • 重复运行
  • 延迟和 token 成本
  • 失败样本分类

验收问题：

  • 改变 tokenizer 或模板时，哪些样本受到影响
  • 同一配置的波动有多大
  • 哪些断言可确定性完成

项目二：可评测的 RAG 问答

范围：

  • 一个受控知识域
  • 有文档版本和引用

必须包含：

  • 文档准入
  • 切片和元数据
  • 检索 trace
  • 召回评测
  • 答案忠实度
  • 无证据拒答
  • 索引版本

验收问题：

  • 错误发生在召回还是生成
  • 过期文档是否被阻断
  • 引用是否真正支持答案

项目三：受控 Agent

范围：

  • 两到四个工具
  • 至少一个可逆写操作

必须包含：

  • 工具契约
  • 服务端鉴权
  • 状态机
  • 幂等和回滚
  • 故障注入
  • 轨迹评测
  • 人工接管
  • 灰度和 SLO

验收问题：

  • 工具超时后是否重复写入
  • Prompt Injection 能否改变权限
  • 中断后能否恢复
  • 最终回答和外部状态是否一致

这三个项目覆盖“理解、评测、运行、治理”的递进关系。

只做聊天 UI，无法证明这些能力。

十六、能力成长本身也需要测试设计

学习计划可以像产品一样被测试。

测试对象不是人的记忆力，而是能力证据链。

1. 功能性验收

对每个能力项检查：

  • 是否有明确任务
  • 是否有可运行产物
  • 是否有输入数据
  • 是否有期望和门槛
  • 是否有失败样本
  • 是否能由他人复现

2. 边界测试

刻意加入：

  • 超长输入
  • 非法 Unicode
  • 知识冲突
  • 工具超时
  • 无权限请求
  • 不完整证据
  • 模型不可用
  • 评判器分歧

如果项目只能处理演示路径，不能证明能力闭环。

3. 变更测试

至少执行以下变化：

  • 换一个模型
  • 换一个 Prompt 版本
  • 更新知识库
  • 修改工具 schema
  • 提高并发
  • 改变安全规则

检查评测和观测能否解释行为变化。

4. 可恢复性测试

故障注入点包括：

  • 请求发出前
  • 模型返回一半
  • 工具执行前
  • 工具执行后但状态未写回
  • 报告生成前
  • 人工审批超时

验收重点不是“有没有报错”。

而是：

  • 状态是否一致
  • 证据是否完整
  • 能否安全重试
  • 是否需要人工介入

5. 证据审查

让另一位工程师只依据文档和仓库重放实验。

如果必须依赖作者口头补充，说明证据仍不完整。

十七、示例案例：工具很多，但为什么仍无法独立承担 AI 质量工作

下面是一个用于说明方法的示例案例，不是对真实项目经历的陈述。

1. 场景

某团队要上线一个日志分析 Agent。

一位测试开发工程师已经完成：

  • 调用两个大模型 API
  • 使用一个 Agent 框架
  • 接入日志搜索工具
  • 搭建演示页面
  • 编写十几条 Prompt

团队因此判断该项目“AI 能力已经具备”。

2. 初始验收

演示使用五条人工挑选日志。

Agent 都能给出看起来合理的原因。

页面也能展示工具调用过程。

但项目没有：

  • 版本化评测集
  • 日志脱敏策略
  • 根因证据约束
  • 工具超时恢复
  • 线上 trace
  • 高风险错误门禁

3. 失败出现

扩展到一批历史日志后，系统出现三类问题：

  • 把相似关键字当成同一根因
  • 日志搜索超时后仍生成确定性结论
  • 在输出中带出设备标识

团队最初把问题归因成“模型不够强”。

4. 按能力图谱重新分析

模型认知：

  • 未测试长日志截断后关键时间线是否丢失

数据能力：

  • 样本只有正常格式，没有噪声和跨进程时间线

评测能力：

  • 没有根因候选、证据引用和拒答的分项指标

Agent 能力：

  • 工具失败没有改变任务状态

LLMOps：

  • 没有记录检索耗时和 finish reason

安全：

  • 没有对设备标识做输入输出脱敏

领域能力：

  • 没有区分相关日志与因果证据

5. 修复顺序

团队不应先换模型。

更合理的顺序是：

  1. 定义领域故障分类和证据规则
  2. 构建带时间线、噪声和反例的数据集
  3. 增加检索成功、证据充分和隐私泄漏指标
  4. 工具失败时强制进入不确定状态
  5. 记录完整 trace
  6. 增加脱敏和输出扫描
  7. 最后再比较模型

6. 案例结论

这个示例说明：

工具使用数量不能代表 AI 质量能力。

真正的能力体现在是否能把失败拆解、度量、修复并固化为回归证据。

十八、常见反模式

1. 追逐框架，不建立不变的工程概念

框架会快速变化。

数据血缘、状态机、幂等、SLO、权限和评测方法更持久。

先理解不变量，再学习框架映射。

2. 把 Prompt 技巧当成全部 AI 工程

Prompt 很重要，但不能替代：

  • 真实权限
  • 工具校验
  • 数据治理
  • 自动评测
  • 可观测性
  • 故障恢复

3. 只看模型能力，不看系统质量

模型离线回答更好，不代表端到端任务成功率更高。

新增的延迟、成本、格式波动或工具错误都可能抵消模型收益。

4. 用一个总分解释所有问题

总分容易隐藏：

  • 高风险分层退化
  • 少数用户群失败
  • 拒答率升高
  • 成本异常
  • 安全错误

报告必须保留分项和样本。

5. 只积累成功 Demo

能力证据中最有价值的部分通常是：

  • 失败分类
  • 复现条件
  • 修复前后对比
  • 剩余风险

只有成功截图，很难证明工程深度。

6. 把 LLM-as-Judge 当绝对真值

裁判模型也有偏差、位置效应、提示敏感和版本变化。

必须用人工样本校准，并与确定性断言组合。

7. 忽略传统工程能力

AI 服务仍会因为连接池、队列、缓存、数据库、网络和资源限制失败。

不应因关注模型而放弃系统工程。

8. 学习路线没有退出条件

“学习 RAG 两个月”不是可验收目标。

“在版本化数据集上区分召回失败与生成失败，并形成回归门禁”才是。

9. 用自评替代证据

自评可以启动讨论，不能作为最终结论。

每个等级都要绑定可查看、可运行、可复核的产物。

10. 同时铺开所有方向

能力图谱用于看全局，不意味着同时深挖所有领域。

更有效的方式是：

  • 共同基础达到 L1
  • 核心评测达到 L2
  • 一个领域达到 L3
  • 其他方向按项目补齐

十九、AI 质量工程能力检查表

模型认知

  • 能解释 tokenizer、模板和截断怎样改变实际输入
  • 能解释 prefill、decode 和 KV cache 的基本关系
  • 能说明采样参数对输出分布的影响
  • 不把固定 seed 误写成绝对复现保证
  • 能定义模型适用边界和降级条件

数据与知识

  • 每个样本都有来源、版本和风险标签
  • 有明确的标注指南与分歧处理流程
  • 开发集、回归集和保留集用途分开
  • 知识文档有有效期、权限和版本
  • 线上样本回流经过脱敏与审批

评测与实验

  • 指标与业务任务直接对应
  • 同时使用确定性和语义判定
  • 关键结果包含样本数与分层
  • 高风险失败有单独门禁
  • 失败样本能够进入回归集
  • 候选版本与基线使用同一协议

Agent 与工具

  • 工具有 schema、业务约束和权限约束
  • 读写动作和风险级别明确
  • 写操作考虑幂等与回滚
  • 工具失败不会被包装成任务成功
  • 轨迹、外部状态和最终结论可以关联
  • 高风险动作有人工确认

LLMOps 与可靠性

  • 请求可以追溯到模型、模板、数据和工具版本
  • 能拆解排队、推理、工具和网络延迟
  • 有质量、性能、成本和安全 SLO
  • 有灰度、降级和回滚
  • 线上漂移能触发采样评测
  • 供应商或模型不可用时有受控行为

安全与治理

  • 已完成数据流和信任边界分析
  • 权限在服务端执行，不依赖 Prompt
  • 覆盖直接和间接 Prompt Injection
  • 敏感输入输出受到控制
  • 风险有所有者、检测和处置
  • 审计记录可以回答谁在何时做了什么

领域质量

  • 有领域故障分类
  • 领域专家参与样本和 rubric 复核
  • 结论绑定可验证事实
  • 低频高风险场景进入评测集
  • 能说明 AI 不应自动决策的边界

项目证据

  • 项目不是只展示聊天页面
  • 仓库包含可运行评测
  • 报告包含失败样本而非只有总分
  • 变更前后有可比数据
  • 文档说明剩余风险
  • 第三方可以依据记录重放关键实验

二十、总结

AI 时代测试开发工程师真正需要补充的，不是一串框架名称。

而是一套把概率性能力纳入工程控制的方法。

这套能力可以概括为：

  • 用模型认知解释行为边界
  • 用数据与知识保证输入可追溯
  • 用评测与实验建立可比较结论
  • 用 Agent 工程控制动作与状态
  • 用 LLMOps 管理线上质量、性能和成本
  • 用安全与治理限制风险
  • 用领域知识约束最终事实

工程底座仍然重要。

能力成熟度也不应由“最强的一项”决定。

更合理的判断是：

关键能力是否都达到项目所需底线，并且是否有可复现证据。

当学习结果能够表现为版本化数据集、自动评测、完整 trace、故障注入报告、权限矩阵、SLO 和回归门禁时，能力才真正从“知道”进入“可交付”。
