AI测试-14-AI应用的失败模式应该怎样分类和归因

发表于 2026-03-16 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 44 分钟

AI 应用出错时，团队最常听到的判断往往是：

  • “模型幻觉了”
  • “RAG 没召回”
  • “Agent 不稳定”
  • “应该是网络抖动”
  • “裁判模型打分不准”

这些描述可能碰到了现象，却通常不足以指导修复。

一次错误答案可能源于输入解析丢字段，也可能源于上下文截断、权限过滤、旧索引、模型路由、工具契约、工作流重试或评测器漏报。

更麻烦的是，同一个请求可能同时穿过这些环节。

上游的小偏差经过下游默认值、自动重试和错误评测后，可能被放大成真正的用户影响。

如果团队把最终看到的错误直接归到模型层，就会出现三种后果：

  • 修了 Prompt，却没有修掉产生错误上下文的数据管道
  • 换了模型，却保留了危险的工具默认值和重试策略
  • 离线分数提高了，线上同类事故仍然重复发生

这篇文章不再重复前文对模型层、工具层、执行层和证据层的架构拆分。

这里聚焦一个更具体的问题：

当 AI 应用已经产生错误结果或错误动作时，怎样用统一分类、事件时间线和可证伪的归因树，找到首错、根因与放大因素。

一、问题边界：本文分析的不是“模型好不好”，而是“系统为什么失败”

先明确本文讨论的对象。

这里的 AI 应用至少包含以下一种能力：

  • 大模型生成文本或结构化结果
  • RAG 检索外部知识
  • Function Calling 或 MCP 等工具调用机制
  • 多步骤 Agent 或工作流执行
  • 规则、模型或人工组成的评测器

本文关注的是应用级失败，而不是基础模型训练阶段的全部风险。

下面几类问题会涉及，但不会展开成独立安全或算法教程：

  • 模型本身的能力边界
  • Prompt Injection 与工具越权
  • 训练数据偏差
  • GPU 内核和分布式训练故障
  • 模型榜单之间的横向排名

原因很简单：

一次生产失败不能只靠“模型能力不足”解释。

工程归因必须回答：

  1. 用户究竟受到了什么影响。
  2. 哪一个事件最先违反了系统不变量。
  3. 什么条件触发了这条失败路径。
  4. 哪些设计缺陷让错误得以产生或逃逸。
  5. 哪些因素扩大了范围、时长或损害。
  6. 什么证据能支持或推翻当前假设。
  7. 修复后如何证明同类故障被阻断。

本文也不假设每次事故只有一个根因。

复杂系统里，“唯一根因”经常只是为了报告简洁而做的过度压缩。

更实用的做法是保留一个因果集合：

  • 触发条件
  • 首错事件
  • 近因
  • 系统性根因
  • 放大因素
  • 逃逸控制
  • 缓解因素

二、先统一术语：症状、故障模式和根因不是一回事

如果术语不统一，同一场复盘里每个人说的“原因”可能完全不同。

2.1 症状：外部观察到的不符合预期

症状是观察结果，例如：

  • 回答引用了不存在的制度条款
  • Agent 创建了两条重复缺陷
  • 本应拒绝的请求被执行
  • 评测报告把错误回答判成通过
  • P95 响应时间从 4 秒升到 20 秒

症状只说明“哪里看起来不对”。

它不自动说明错误从哪里开始。

2.2 事件：时间线上可被验证的状态变化

事件应该有明确时间、主体、输入、输出和状态。

例如：

事件不是一段自由文本日志。

它应能按 trace_id、span_id、任务和版本关联起来。

2.3 故障模式：组件以什么方式偏离设计意图

故障模式描述“怎么坏”。

例如：

  • 上下文截断删除了必填业务约束
  • 检索过滤使用了错误租户
  • 工具调用超时后发生重复副作用
  • 评测器只检查措辞，没有检查真实状态

同一个组件可以有多种故障模式。

同一种故障模式也可能由不同机制导致。

2.4 触发条件：让潜在缺陷进入活跃路径的条件

触发条件并不一定是缺陷本身。

例如：

  • 会话长度首次超过上下文裁剪阈值
  • 请求落到某个租户或语言分支
  • 峰值流量触发队列等待
  • 知识库刚完成一次增量发布
  • 工具在副作用已发生后返回超时

没有触发条件，缺陷可能长期潜伏。

只删除触发条件，通常也不等于修复根因。

2.5 首错：第一个违反已声明不变量的事件

首错不是日志里最早出现的 ERROR。

它是业务时间线上第一个可以证明违反不变量的事件。

系统为每个事件定义不变量集合 I(e_i)，其中每个不变量 g 都是返回布尔值的判定函数。

  • 时间线必须足够完整
  • 不变量必须在事故前或分析时明确写出

如果没有不变量，“首错”就容易退化成主观判断。

2.6 近因：紧邻用户影响的直接机制

近因解释最后一步是怎样发生的。

例如：

  • 第二次非幂等调用创建了重复缺陷
  • 错误路由把请求发到不支持该语言的模型
  • 评测解析器把空字段转成默认满分

近因通常适合快速止血。

但只修近因，不一定能阻止同类问题换一种形式复发。

2.7 根因：修复后能显著阻断同类失败路径的系统条件

根因应当可操作、可验证，而不是抽象口号。

“模型不稳定”不是合格根因。

“上下文构建器没有把环境字段定义为不可裁剪约束，且缺少裁剪后契约校验”更接近可修复根因。

根因判断应尽量依赖干预证据：

  • 保持其他变量不变，只替换候选条件
  • 故障是否不再出现
  • 在其他同类样本上是否也成立
  • 修复是否阻断同一失败机制

因果推断里常用 do(C) 表示主动干预变量 C。

工程上不必真的计算完整因果图，但可以借用这个思想：

如果替换候选条件后失败概率没有明显变化，它就不应被轻易认定为根因。

2.8 放大因素：不制造首错，却扩大影响

常见放大因素包括：

  • 默认无限重试
  • 非幂等工具没有幂等键
  • 多租户共享错误缓存
  • 高风险动作不需要审批
  • 下游把模型输出当可信指令直接执行
  • 评测器漏报导致错误进入发布

放大因素同样值得进入高优先级修复清单。

2.9 逃逸控制：本来应该发现或阻止错误的控制点

逃逸控制回答的是：

为什么错误没有在到达用户之前被拦住？

可能包括：

  • Schema 校验没有检查业务约束
  • 检索质量门禁只看返回数量
  • 工具策略没有校验环境和租户
  • 端到端测试没有检查真实副作用
  • 裁判模型没有校准，且没有人工抽检

三、AI 应用为什么比传统服务更难归因

传统服务也有跨层故障，但 AI 应用增加了几种特殊不确定性。

3.1 输出不完全由代码路径决定

同一输入还可能受到下面因素影响：

  • 模型版本
  • 系统提示词
  • 上下文顺序
  • 检索结果
  • 采样参数
  • 服务端实现
  • 工具返回内容
  • 历史记忆

即使设置低温度或零温度，也不应把第三方推理服务视为天然逐字确定。

因此，复现包必须记录“有效输入”，而不仅是用户原始问题。

3.2 自然语言把错误伪装成合理结果

传统接口字段缺失可能直接报错。

模型却可能为缺失字段补出一个语义合理的默认值。

这会让错误继续向下传播，而不是立即失败。

3.3 检索结果同时是数据、配置和运行时依赖

RAG 的最终上下文取决于：

  • 语料版本
  • 切块策略
  • Embedding 版本
  • 索引构建时间
  • 查询改写
  • 元数据过滤
  • 重排器
  • 访问权限

只保存最终回答，几乎无法重建现场。

3.4 Agent 会产生真实副作用

当模型只能回答文本时，错误主要影响信息质量。

当模型可以调用工单、发布、数据库和设备工具时，错误会改变外部状态。

这时必须同时追踪：

  • 模型意图
  • 工具参数
  • 权限决策
  • 实际执行
  • 外部副作用
  • 补偿结果

3.5 评测器自己也可能失败

评测结果不是天然真值。

规则断言可能过窄。

裁判模型可能受措辞、顺序、长度和提示词影响。

人工标注也可能出现规范歧义和一致性问题。

所以评测器必须作为第九层参与归因，而不能站在系统之外被默认正确。

四、九层故障模型：先定位层，再定位机制

这张图把 AI 应用拆成六层主调用链和三个横切层。

六层主链负责把请求转成结果或动作：

  1. 输入层
  2. 上下文层
  3. 检索层
  4. 模型层
  5. 工具层
  6. 执行层

三个横切层影响每个决策点：

  1. 策略层
  2. 基础设施层
  3. 评测器层

分类的目标不是把事故强行塞进一个格子。

真正目标是让每个事件有明确责任边界、证据类型和验证方法。

五、第一层：输入故障

输入层是用户请求、上游系统事件或批量任务进入 AI 应用的边界。

5.1 典型故障模式

  • JSON、表单或消息格式不合法
  • 字段类型正确，但业务语义不合法
  • 编码、语言、时区或单位解析错误
  • 超长输入在入口被静默截断
  • 附件解析失败，却继续生成答案
  • 上游把空值替换成危险默认值
  • 线上输入分布偏离评测集
  • 恶意指令或间接提示注入进入系统

5.2 关键不变量

  • 必填字段在进入上下文构建前必须存在
  • 租户、环境和用户身份不得由模型猜测
  • 文档解析失败时不得伪装成空文档
  • 原始输入和规范化输入必须可关联
  • 超出限制必须显式拒绝或分段，不得静默丢失关键内容

5.3 必须保留的证据

  • 原始载荷的脱敏摘要
  • 规范化后的结构
  • Schema 版本
  • 解析器版本
  • 字符数、Token 估算和附件状态
  • 身份、租户、环境等不可推断字段

5.4 测试重点

  • 等价类和边界值
  • Unicode、混合语言和特殊分隔符
  • 超长输入和大附件
  • 空值、缺字段和类型漂移
  • 重放线上低频格式
  • 对抗输入与数据外泄检查

输入错误最容易被误归到模型层，因为模型常常会“努力回答”。

测试时应明确：模型的补全能力不能替代入口契约。

六、第二层：上下文故障

上下文不是单一 Prompt。

它通常由系统指令、开发者指令、用户输入、对话历史、长期记忆、检索片段和工具结果共同组成。

6.1 典型故障模式

  • 必要约束被上下文窗口裁掉
  • 消息角色或顺序错误
  • 旧版系统提示词与新版工具契约不兼容
  • 不同租户记忆串线
  • 历史错误结论被反复写回长期记忆
  • 工具结果没有标记可信级别
  • 上下文拼接包含相互冲突的指令
  • Token 预算按字符粗略估计，导致实际溢出

6.2 关键不变量

  • 身份、租户、环境和权限约束不可裁剪
  • 每段上下文必须记录来源与版本
  • 外部文档内容不得拥有高于系统指令的权限
  • 长期记忆写入必须有来源、有效期和撤销机制
  • 裁剪前后必须通过必填约束校验

6.3 上下文优先级不能只靠排列顺序

把关键字段放在最前面有帮助，但还不够。

更稳的做法是把上下文拆为：

  • pinned_constraints：绝不能删除的约束
  • task_context：当前任务必须信息
  • retrieved_evidence：可替换的证据
  • conversation_history：可摘要的历史
  • optional_context：预算不足时优先移除

裁剪算法应按分区降级，并在裁剪后重新验证。

6.4 测试重点

  • 从短会话逐级增加到窗口边界
  • 打乱非关键片段顺序做变形测试
  • 注入冲突指令检查优先级
  • 回放跨租户和跨会话场景
  • 比较摘要前后的关键事实保持率
  • 检查上下文构建器升级前后的差异

七、第三层：检索故障

检索故障不能只用“没有召回正确文档”概括。

RAG 链路至少包含查询构造、候选召回、元数据过滤、重排、去重、片段组装和引用映射。

7.1 典型故障模式

  • 查询改写丢失否定词或限定条件
  • Embedding 与索引版本不匹配
  • 权限过滤放在召回后，导致越权片段进入上下文
  • 时间过滤错误，召回过期制度
  • Top K 太小导致关键证据缺失
  • Top K 太大导致噪声压过关键证据
  • 重排器偏好措辞相似而非事实相关
  • 切块把条件和结论分开
  • 增量索引没有完成却提前切流
  • 引用编号与实际片段错位

7.2 检索层至少要记录两组结果

第一组是“召回候选”。

第二组是“最终进入上下文的片段”。

只记录第二组，会丢失过滤和重排过程中的证据。

建议记录：

  • 原始查询
  • 改写查询
  • 过滤条件
  • 候选文档 ID 和分数
  • 重排后顺序
  • 被剔除原因
  • 文档版本与有效期
  • 最终引用映射

7.3 关键不变量

  • 无权限文档不得进入模型上下文
  • 需要时效性的任务必须优先有效版本
  • 引用必须能反向定位到不可变文档版本
  • 检索为空时不得伪造来源
  • 索引发布必须和文档清单、Embedding 版本一致

7.4 测试重点

  • 有答案、无答案和答案冲突场景
  • 同义改写、否定表达和缩写
  • 多租户权限隔离
  • 旧版与新版文档共存
  • 索引增量发布和回滚
  • 单个关键片段缺失的故障注入
  • 召回与生成分阶段评测

前文已经讨论过 RAG 数据清洗、召回和结果校验。

这里的新增重点是：检索的每个中间决策都应进入事件时间线，才能参与事故归因。

八、第四层：模型故障

只有在输入、上下文和检索证据已经被验证后，才适合把候选原因收敛到模型层。

8.1 典型故障模式

  • 在证据不足时生成确定性结论
  • 没有遵守结构化输出约束
  • 对明确任务产生不必要拒答
  • 安全边界不足，接受恶意指令
  • 数值、日期或逻辑推理错误
  • 多语言能力不符合场景要求
  • 路由器选择了不满足任务要求的模型
  • 模型版本升级造成行为回归
  • 采样策略导致输出方差过大
  • 长上下文下忽略关键证据

8.2 模型错误不等于“答案与金标准不一致”

需要先区分：

  • 金标准是否唯一
  • 任务是否允许多种表达
  • 输入证据是否足够
  • 模型是否应拒答
  • 输出是否被后处理器破坏

对于开放式任务，模型层不变量可以是：

  • 每个事实声明有可追溯证据
  • 不确定时使用明确的不确定表达
  • 输出满足 JSON Schema
  • 禁止提出超出授权范围的工具动作

8.3 测试重点

  • 固定有效输入做多次重复运行
  • 比较不同模型版本和路由结果
  • 记录完整生成参数
  • 设计无答案和证据冲突样本
  • 对关键事实做原子级断言
  • 将格式正确率与语义正确率分开
  • 做温度、上下文长度和语言维度切片

模型层可以出现真正的能力失败。

但“模型没答对”仍然只是故障模式，不是足够深的根因描述。

九、第五层：工具故障

工具层负责把模型意图转换为受控调用。

前文对 Function Calling 的输入、输出和容错已经做过展开。

本节只从故障归因角度补充证据边界。

9.1 典型故障模式

  • 选错工具
  • 参数字段缺失或类型错误
  • 参数语法正确但业务对象错误
  • Schema 与工具实现版本不一致
  • 工具返回成功，但副作用没有发生
  • 工具返回超时，但副作用已经发生
  • 错误码被适配器吞掉
  • 返回内容包含未标记的不可信文本
  • 权限范围大于任务所需
  • 工具描述误导模型选择

9.2 三个状态必须分开

一次工具调用至少有三种状态：

  1. planned：模型提出了调用意图。
  2. accepted：策略和参数校验允许调用。
  3. committed：外部系统确认副作用已经提交。

只记录“模型调用了工具”，无法判断动作是否真正发生。

只记录 HTTP 200，也无法证明业务状态正确。

9.3 关键不变量

  • 工具参数必须通过结构与业务双重校验
  • 高风险字段不得从自然语言缺省推断
  • 副作用调用必须携带幂等键或等价防重机制
  • 超时状态必须区分“未执行”和“执行结果未知”
  • 工具返回的不可信文本不得升级为系统指令

9.4 测试重点

  • 契约测试和 Schema 兼容测试
  • 错误码、超时和部分成功
  • 副作用已发生但响应丢失
  • 幂等键重复提交
  • 权限不足和跨租户访问
  • 工具描述相似时的选择冲突
  • 返回值污染后续上下文

十、第六层：执行故障

工具层描述单次能力调用。

执行层描述多步骤任务如何推进、暂停、恢复和补偿。

10.1 典型故障模式

  • 工作流状态与真实外部状态不一致
  • 重试从错误检查点恢复
  • 并发任务覆盖同一资源
  • 失败后没有补偿已完成步骤
  • 人工审批结果没有绑定原始计划版本
  • 任务取消后后台动作仍在继续
  • 死信任务被重复消费
  • 超时预算在层间叠加失控
  • 局部成功被汇总成整体成功

10.2 关键不变量

  • 每次状态转移必须满足前置条件
  • 外部副作用必须有可验证的提交凭证
  • 重试不得重复不可逆动作
  • 审批必须绑定工具、参数、版本和有效期
  • 取消信号必须传播到所有可取消步骤
  • 聚合状态必须保留部分成功与未知状态

10.3 测试重点

  • 每个步骤前后注入故障
  • 并发、乱序和重复消息
  • 进程重启后的检查点恢复
  • 审批前后计划被修改
  • 补偿动作自身失败
  • 长任务跨版本部署
  • 外部状态与内部状态对账

十一、第七层：策略故障

策略层包括权限、风险阈值、内容安全、人工审批、模型路由和降级规则。

它可能同时影响输入、模型、工具和执行。

11.1 典型故障模式

  • 应拦截的高风险动作被放行
  • 正常任务被过度拦截
  • 多条规则冲突，执行顺序不明确
  • 规则使用危险默认值
  • 风险分数阈值未经场景校准
  • 策略版本切换没有审计
  • 模型拒答被错误覆盖
  • 人工审批被复用到不同参数

11.2 策略决策必须可解释到规则

11.3 测试重点

  • 规则边界值
  • 规则优先级和冲突
  • 默认拒绝是否生效
  • 策略热更新和回滚
  • 同一计划更换参数后重新审批
  • 高风险工具的最小权限
  • 策略服务不可用时的降级行为

十二、第八层：基础设施故障

基础设施层不只包括模型服务。

它还包括网络、网关、缓存、队列、数据库、对象存储、向量库、密钥服务和第三方 API。

12.1 典型故障模式

  • 模型服务配额耗尽
  • 队列积压导致上下文过期
  • 缓存键缺少租户或版本维度
  • 网络重试形成请求风暴
  • 向量库读到旧副本
  • 时钟漂移破坏跨系统时间线
  • 资源耗尽触发降级模型
  • 依赖返回部分数据但状态码正常
  • 可观测性采样丢失关键失败链路

12.2 基础设施错误经常是触发条件或放大因素

例如，一次网络超时本身不该创建重复工单。

真正的问题可能是：

  • 工具调用没有幂等性
  • 超时被错误解释为“未执行”
  • 工作流立即重试
  • 外部系统没有查询提交状态的接口

此时网络超时是触发条件。

非幂等设计和错误恢复策略才是更值得修复的系统条件。

12.3 测试重点

  • 延迟、超时、限流和断连
  • 缓存陈旧与缓存穿透
  • 单依赖和多依赖联合故障
  • 队列重复、丢失和乱序
  • 模型路由与降级链
  • 资源配额和背压
  • 追踪采样对失败证据的覆盖率

十三、第九层：评测器故障

评测器层负责判断“系统是否正确”。

它可能由代码断言、规则、检索校验、裁判模型和人工评审共同组成。

13.1 典型故障模式

  • 只验证回答格式，不验证事实
  • 只验证模型文本，不验证真实副作用
  • 裁判量表没有定义边界
  • 裁判模型偏好更长或更自信的答案
  • 被测输出包含影响裁判的提示内容
  • 解析失败后使用默认通过
  • 评测集标签错误或已经过期
  • 聚合分数掩盖关键风险切片退化
  • 评测器版本升级却没有重新校准

13.2 评测器必须有自己的真值和回归集

评测器不是终点。

至少需要：

  • 人工确认的校准集
  • 明确评分量表
  • 评测器版本
  • 多次评测的一致性数据
  • 与规则断言的冲突记录
  • 低置信度人工复核路径

13.3 测试重点

  • 正例、反例和近边界样本
  • 同义改写与答案顺序交换
  • 长短答案偏差
  • 提示注入式被测输出
  • 解析失败和空结果
  • 裁判版本对照
  • 分层指标与人工抽检

十四、九层故障的快速定位表

层级 首要问题 关键证据 最有效的对照实验
输入 进入系统的请求是否已变形 原始与规范化输入、Schema 绕过规范化器重放
上下文 模型实际看到了什么 完整消息、裁剪记录、Token 预算 固定模型替换上下文
检索 证据为什么入选或丢失 候选、过滤、重排、文档版本 固定查询替换索引或过滤器
模型 有效输入正确时是否仍失败 模型版本、参数、原始输出 同输入跨模型或多次运行
工具 意图是否被正确、安全地执行 参数、策略决策、提交凭证 Mock 工具与真实工具对照
执行 状态机是否正确推进 状态转移、检查点、副作用 在指定步骤注入故障
策略 为什么放行、拦截或路由 命中规则、版本、风险分 固定请求替换策略版本
基础设施 依赖异常怎样影响业务语义 时延、错误码、资源、缓存 限流、断连、延迟注入
评测器 判断本身是否可信 量表、评分明细、人工标签 人工盲评与裁判对照

这张表不能替代时间线。

它的作用是帮助测试和平台团队快速提出可验证假设。

十五、事件时间线：先恢复事实，再讨论原因

一次 AI 事故最有价值的产物通常不是截图，而是一条可重放时间线。

15.1 时间线必须回答的七个问题

对每个关键事件，至少回答：

  1. 什么时候发生。
  2. 哪个组件发起。
  3. 接收了什么有效输入。
  4. 使用了什么代码、模型、提示词、索引或策略版本。
  5. 产生了什么输出或状态变化。
  6. 是否产生外部副作用。
  7. 与前后事件如何关联。

15.3 时间戳的工程取舍

跨服务排序通常依赖墙上时钟，但墙上时钟可能漂移。

单进程耗时最好同时记录单调时钟。

因此建议：

  • occurred_at 用于跨系统对齐和人工阅读
  • monotonic_ns 用于单进程内可靠计算间隔
  • 通过 trace 父子关系修正“时间相近但顺序不明”的事件
  • 记录 NTP 状态或已知时钟偏差

不要用日志采集时间代替业务发生时间。

日志进入采集器的先后顺序不一定等于事件发生顺序。

15.4 保存摘要还是原文

事故复现需要内容，隐私治理又要求最小化留存。

可采用分层证据：

  • 常规链路保存脱敏摘要、长度、哈希和对象引用
  • 受控证据库存储加密原文
  • 访问原文需要审计和最小权限
  • 到期自动删除原文，保留不可逆统计信息
  • 敏感字段在进入外部模型前完成脱敏

“为了排障把所有 Prompt 永久记日志”不是合理方案。

十七、归因树：从首错到根因还差哪些证据

归因树不应该是一棵写满猜测的脑图。

每个节点至少要有：

  • 假设
  • 支持证据
  • 反对证据
  • 验证动作
  • 负责人
  • 当前置信度

17.1 从影响向上回溯

推荐顺序是：

  1. 定义用户影响。
  2. 恢复错误传播链。
  3. 找到首错事件。
  4. 列出触发条件。
  5. 提出根因候选。
  6. 识别放大因素和逃逸控制。
  7. 用干预和回放收口。

不要一上来就问“是谁的服务有问题”。

先问“哪一个不变量最先失效”。

十八、示例案例：一次重复建单如何被错误归因成“网络抖动”

以下为教学用示例案例，用于展示归因方法，不代表任何真实项目经历或生产事故。

18.1 场景

一个测试 Agent 接收失败用例信息，查询知识库，判断是否已有同类缺陷，并在测试环境创建新缺陷。

某次运行创建了两条内容相同的缺陷。

表面现象是：

  • 第一次工具调用在 5 秒后超时
  • 工作流重试
  • 第二次调用成功
  • 最终报告显示“缺陷创建成功”

团队最初把问题归为“网络抖动导致重试”。

18.2 还原事件时间线

序号 层级 事件 是否违反不变量
10 输入 请求明确 environment=staging 否
20 上下文 长会话裁剪掉环境字段 是，首错
30 检索 使用默认环境查询历史缺陷 是，传播
40 模型 生成建单计划，未发现环境缺失 是，逃逸
50 策略 默认低风险，允许自动建单 是，放大
60 工具 未携带幂等键，首次提交成功 是，控制缺失
70 基础设施 响应链路超时 触发重试
80 执行 把“结果未知”解释为“未执行” 是，近因
90 工具 第二次提交创建重复缺陷 用户影响
100 评测器 只检查成功文本，未查真实建单数 逃逸控制

18.3 归因结果

症状： 同一任务创建两条重复缺陷。

触发条件： 长会话触发裁剪；首次提交后的响应超时。

首错： 上下文构建器删除了不可裁剪的环境字段。

近因： 执行器把结果未知当作未执行，并重试非幂等动作。

系统性根因候选：

  • 上下文分区没有声明强制保留字段
  • 工具契约没有要求幂等键
  • 执行状态模型缺少 commit_unknown

放大因素：

  • 策略层允许危险默认环境
  • 自动重试没有副作用感知

逃逸控制：

  • 评测器没有核对外部系统提交凭证和建单数量
  • 端到端回归未覆盖“已提交但响应丢失”

18.4 怎样验证而不是争论

实验一：固定原始请求和模型，关闭上下文裁剪。

结果：环境字段保留，但超时场景仍可能重复建单。

结论：上下文问题是首错之一，却不能单独解释重复提交。

实验二：保持超时和重试，增加稳定幂等键。

结果：第二次调用返回第一次提交凭证，不再创建新单。

结论：幂等缺失是重复副作用的必要条件之一。

实验三：引入 commit_unknown 状态并先查询提交结果。

结果：超时后通过幂等键查到首次提交，工作流结束。

结论：状态模型修复可以阻断失败传播。

实验四：评测器改为检查外部建单数量。

结果：旧版本系统的重复提交被稳定识别。

结论：评测逃逸控制得到修复，但它不是产生重复建单的根因。

这个示例说明：

网络超时是真实事件，却只是触发条件；把它写成唯一根因，会错过三个可控的系统设计缺陷。

十九、测试设计：怎样让九层故障在上线前暴露

故障分类的最终价值，不是写出更漂亮的复盘，而是反向生成测试。

19.1 输入层测试

  • Schema 变异测试
  • 字段缺失和危险默认值测试
  • 超长文本与附件解析测试
  • 多语言、时区和单位测试
  • 线上分布漂移样本回放

19.2 上下文层测试

  • Token 窗口边界测试
  • 必填约束不可裁剪测试
  • 消息顺序变形测试
  • 记忆污染和租户隔离测试
  • Prompt 与工具 Schema 兼容测试

19.3 检索层测试

  • Recall@K 和关键证据命中测试
  • 权限过滤前置测试
  • 新旧文档冲突测试
  • 索引增量切换测试
  • 引用到原文版本的可追溯测试

19.4 模型层测试

  • 重复运行与方差测试
  • 无答案时拒答测试
  • 结构化输出契约测试
  • 模型和提示词版本回归
  • 原子事实与引用一致性测试

19.5 工具层测试

  • 参数结构和业务规则双重校验
  • 已提交但响应丢失
  • 幂等键冲突和重放
  • 权限最小化与越权尝试
  • 不可信工具输出注入

19.6 执行层测试

  • 每一步前后故障注入
  • 状态机非法转移
  • 检查点恢复与版本升级
  • 取消传播
  • 补偿失败和部分成功

19.7 策略层测试

  • 阈值边界
  • 规则冲突
  • 策略服务不可用
  • 审批绑定和过期
  • 默认拒绝与只读降级

19.8 基础设施层测试

  • 延迟、断连、限流和配额
  • 缓存陈旧和键碰撞
  • 队列重复与乱序
  • 依赖部分返回
  • 可观测性丢包和采样

19.9 评测器层测试

  • 人工校准集
  • 量表边界样本
  • 顺序、长度和措辞偏差
  • 解析失败默认行为
  • 多裁判和人工复核一致性

二十、建立一张故障注入矩阵

仅按组件写测试，容易漏掉传播路径。

更合适的是把注入点、期望控制和外部影响放在一张矩阵里。

注入点 注入故障 期望系统行为 禁止行为 证据
上下文 删除环境字段 契约校验失败并停止 模型猜环境 校验事件
检索 返回旧制度 新鲜度规则剔除 引用过期内容 文档版本
模型 输出非法 JSON 修复一次或明确失败 直接传给工具 原始输出
工具 已提交后超时 查询提交状态 盲目重试 幂等键与回执
执行 进程重启 从安全检查点恢复 重放不可逆动作 状态日志
策略 决策服务不可用 默认拒绝高风险动作 默认放行 降级原因
基础设施 队列重复投递 消费幂等 重复副作用 消息 ID
评测器 裁判解析失败 标记未知并复核 默认通过 解析错误

矩阵中的“禁止行为”非常重要。

它把安全与稳定性要求转成了可执行负面断言。

这里的分子和分母必须来自同一个观察窗口，且分母定义为该窗口内全部经确认故障：发布前捕获的故障加发布后逃逸到用户侧的故障。这样分子才是分母的子集；不能把“内部监控已经检测到的故障数”单独当作分母。

低风险格式错误与高风险越权动作不能简单相加。

21.3 放大系数

它可以衡量重试、广播、缓存和批处理怎样扩大一次错误。

21.4 平均发现时间和平均缓解时间

  • MTTD：首错发生到系统或人工发现
  • MTTM：发现到用户影响被控制
  • MTTR：发现到服务和数据恢复

AI 应用还应增加：

  • 首错到错误动作提交的时间
  • 错误动作到评测器判定的时间
  • 评测器低置信度到人工复核的时间

21.5 归因覆盖率

还可以分别统计：

  • 有完整有效输入的事故比例
  • 有检索候选清单的事故比例
  • 有工具提交凭证的事故比例
  • 有评测器版本的事故比例

这些指标反映的不是模型质量，而是系统是否具备可诊断性。

二十二、从日志走向 Trace：最小可观测性要求

分散日志很难表达跨层因果关系。

建议把一次用户请求或批量任务定义为根 Trace，并为以下动作建立 Span：

  • 输入解析
  • 上下文构建
  • 每次检索与重排
  • 每次模型调用
  • 每次策略决策
  • 每次工具调用
  • 每次状态转移
  • 每次评测

每个 Span 至少记录：

  • 组件和操作名
  • 开始、结束和状态
  • 父子关系
  • 模型、Prompt、索引、工具、策略版本
  • 输入输出摘要或受控引用
  • Token、候选数、重试次数等关键指标
  • 错误类型，而不只是错误字符串

OpenTelemetry 已经提供通用 Trace 模型，并持续演进生成式 AI 语义约定。

生产系统可以参考其命名，但应给自定义字段做版本管理，避免直接依赖仍可能变化的约定。

二十四、常见误区

24.1 把“模型幻觉”当作万能分类

模型生成了错误事实，不代表错误始于模型。

先检查有效上下文、检索证据和后处理链路。

24.2 把最后一个报错组件当根因

下游组件往往只是第一个显式拒绝错误数据的地方。

严格校验器报错，反而可能说明它正确阻断了上游缺陷。

24.3 用时间相关性代替因果证据

模型升级后事故增加值得怀疑，但还需要控制流量、样本、Prompt、索引和策略变化。

同时发生不等于由它造成。

24.4 强求每起事故只有一个根因

Agent 副作用事故经常需要多个必要条件共同成立。

保留 AND 因果结构比选一个“主责模块”更有工程价值。

24.5 只保存最终 Prompt

最终 Prompt 可能已经丢失查询改写、检索候选、过滤原因和记忆写入过程。

它不能替代完整链路证据。

24.6 复现一次就宣布根因成立

复现只能说明候选机制与失败相容。

还应做单变量替换、修复后回放和跨样本验证。

24.7 把评测器当绝对真值

评测器必须有校准集、版本和人工复核。

否则“线上失败率下降”可能只是漏报率上升。

24.8 为了可观测性永久保存全部敏感内容

可诊断性不能凌驾于隐私、合规和最小化原则。

应使用分级留存、脱敏、加密引用和访问审计。

24.9 行动项只写“加强监控”

行动项必须对应具体失败机制，并有可执行验证。

例如：

  • 错误写法：加强工具调用监控
  • 可验证写法：所有副作用工具强制幂等键，并在提交后超时测试中证明不会重复创建

二十五、落地检查表

25.1 分类准备

  • 是否明确九层组件边界和负责人
  • 是否为高风险链路定义核心不变量
  • 是否区分症状、首错、近因、根因和放大因素
  • 是否允许一个事故保留多个根因候选
  • 是否定义统一错误类型，而不是只记录自由文本

25.2 证据采集

  • 是否能从一个 Trace 看到完整有效输入
  • 是否记录上下文裁剪和摘要过程
  • 是否记录检索候选、过滤、重排和文档版本
  • 是否记录模型、Prompt 和生成参数版本
  • 是否区分工具计划、允许和提交状态
  • 是否记录工作流状态转移与外部副作用
  • 是否记录策略命中规则和决策版本
  • 是否记录评测器、量表和评分明细
  • 是否对敏感证据实施脱敏、加密和审计

25.3 调查过程

  • 是否先定义用户影响，再讨论组件责任
  • 是否按业务序列恢复事件时间线
  • 是否找到第一个可证明的不变量违反点
  • 是否列出支持与反对证据
  • 是否通过单变量替换验证关键候选
  • 是否区分触发条件和可修复根因
  • 是否识别错误为什么没有被控制点拦截
  • 是否评估修复后的残余风险

25.4 测试与预防

  • 是否把事故路径沉淀为回归样本
  • 是否覆盖已提交但响应丢失等不确定状态
  • 是否为副作用工具验证幂等和补偿
  • 是否对策略边界、冲突和降级做测试
  • 是否对评测器做独立校准
  • 是否在模型、Prompt、索引、策略升级时回放
  • 是否对高风险链路定期故障注入
  • 是否验证行动项真的阻断原失败机制

二十六、总结

AI 应用故障归因最重要的转变，是从“哪个模型答错了”转向“哪一个系统不变量最先失效”。

一套可落地的方法至少包括：

  1. 用输入、上下文、检索、模型、工具、执行、策略、基础设施和评测器九层分类建立共同语言。
  2. 用统一 Trace 和事件结构恢复有效输入、版本、状态转移与外部副作用。
  3. 用不变量定位首错，而不是把第一个 ERROR 当作根因。
  4. 把触发条件、近因、系统性根因、放大因素和逃逸控制分开记录。
  5. 用复现、对照、单变量干预、修复后回放和跨样本验证提升归因置信度。
  6. 把每次事故路径转成分层回归和故障注入用例。

最终目标不是给事故贴一个更精确的标签。

最终目标是让团队能够证明：

错误从哪里开始、怎样传播、为什么没有被拦住，以及修复后为什么不会以同样机制再次发生。
