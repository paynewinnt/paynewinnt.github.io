AI测试-15-高质量AI评测集怎么采集清洗标注和版本化

发表于 2026-03-18 分类于 AI测试 本文字数： 14k 阅读时长 ≈ 50 分钟

AI 应用开始做自动化评测后，团队通常很快就能得到一个分数。

真正困难的是回答：

  • 这个分数代表哪一类用户和场景
  • 样本是否覆盖低频但高风险的失败
  • 金标准由谁、依据什么证据标出来
  • 开发人员是否已经反复看过并针对它调优
  • 训练集、Prompt 示例、知识库和评测集之间是否泄漏
  • 数据变更后，上一轮结果还能不能复现
  • 新版本到底是模型变好了，还是评测集变容易了

如果这些问题没有答案，评测集就只是一个装着 JSON 的目录。

它可能适合演示，却不适合承担发布门禁。

高质量评测集应该被视为一件测量资产：

  • 有明确测量目标
  • 有目标总体和抽样设计
  • 有来源与授权
  • 有标签规范与一致性证据
  • 有污染和泄漏控制
  • 有不可变版本与数据卡
  • 有发布门禁和退役机制

前文《AI测试-07-RAG+测试知识库怎么做数据清洗召回和结果校验》关注的是知识库怎样服务在线检索。

本文不重复知识切块和召回优化。

这里关注的是另一条链路：

怎样把生产数据、专家样本、事故样本和合成样本建设成可用于比较、回归和发布决策的 AI 评测集。

一、问题边界：先区分评测数据、训练数据和观测数据

AI 系统里经常同时存在多类数据。

它们可以来源相同，但用途和治理要求不同。

1.1 训练数据

训练数据直接参与模型参数更新，或用于微调、偏好优化和蒸馏。

它的核心问题包括：

  • 许可与版权
  • 数据代表性
  • 隐私
  • 偏差
  • 污染
  • 训练过程可追溯性

本文不会展开基础模型训练数据工程。

1.2 开发数据

开发数据用于：

  • 编写和调整 Prompt
  • 选择 Few-shot 示例
  • 调规则和阈值
  • 选择模型
  • 调整 RAG 参数
  • 修复已知失败

只要开发人员看过答案并据此优化系统，这批数据就不再是独立的盲测证据。

1.3 评测数据

评测数据用于估计系统在某个目标总体上的质量，或验证特定风险是否受控。

它可能包含：

  • 稳定回归集
  • 发布门禁集
  • 能力集
  • 安全集
  • 对抗集
  • 事故回放集
  • 密封审计集

这些集合的用途不同，不能简单合并成一个总分。

1.4 线上观测数据

线上观测数据反映真实运行分布，例如：

  • 用户请求
  • 检索结果
  • 模型输出
  • 工具动作
  • 用户反馈
  • 人工接管
  • 事故记录

它是评测集的重要来源，但不能未经授权、脱敏、筛选和版本化就直接进入评测集。

1.5 本文的核心边界

本文讨论应用级评测集。

它既可以测试单一模型，也可以测试完整 RAG、Agent 或工具执行链路。

本文不提供某个通用模型榜单，也不声称一套数据能代表所有任务。

评测集质量永远相对于：

  • 预期用途
  • 目标人群
  • 风险容忍度
  • 系统版本
  • 发布决策

二、评测集不是“题库”，而是测量仪器

把评测集当题库，团队会关心题目数量。

把它当测量仪器，团队会继续关心：

  • 测量对象是什么
  • 测量误差有多大
  • 结果能泛化到哪里
  • 哪些变量被控制
  • 仪器是否经过校准
  • 仪器版本是否发生变化

它不能自动修复系统性偏差。

2.2 “一万条数据”不一定比“一千条数据”更可信

如果一万条样本里有大量模板近重复，真实独立信息可能很少。

如果它们都来自同一语言、同一租户和同一时间段，就无法代表其他场景。

如果标签规则模糊，样本越多只会更稳定地测量一个错误定义。

评测集规模必须和覆盖、独立性、标注质量一起看。

三、先定义评测目标，再讨论采集

最常见的顺序错误是先把日志倒出来，再考虑能测什么。

正确顺序应该从发布决策开始。

3.1 用决策问题约束评测目标

例如：

  • 新模型能否替换当前模型
  • 新 Prompt 是否降低了事实错误
  • RAG 索引升级是否改善过期文档问题
  • Agent 是否可以从只读工具扩展到写工具
  • 某个语言或租户是否达到开放条件
  • 一个严重事故修复是否可以关闭

不同决策需要不同样本、指标和门槛。

3.2 定义评测对象

至少区分四层：

评测对象 输入边界 输出边界 典型用途
模型 固定有效上下文 原始模型输出 比较模型能力与方差
组件 查询或工具请求 检索、解析、策略结果 定位单层回归
系统 用户请求 最终回答与工具动作 发布门禁和端到端回归
业务 真实任务 用户结果与运营影响 线上价值和风险评估

如果输入输出边界不固定，两个版本的分数差异很难解释。

3.3 定义评测单元

一条样本不一定等于一轮对话。

评测单元可能是：

  • 一个问题与答案
  • 一个事实声明
  • 一个检索查询
  • 一次工具选择
  • 一个工具参数集合
  • 一条多轮会话
  • 一个完整 Agent 任务
  • 一次事故回放

单元越大，越接近真实业务，但定位越困难。

因此常用组合是：

  • 原子级样本用于精确定位
  • 任务级样本用于验证系统行为
  • 业务级样本用于评估最终影响

3.4 定义目标总体

目标总体是希望分数推广到的对象集合。

它可以是：

  • 未来一个月的中文客服请求
  • 使用写工具的企业租户任务
  • Android 稳定性日志分析请求
  • 所有需要引用内部制度的问答
  • 某版本开放后预期出现的多轮会话

“所有用户问题”通常过于宽泛。

目标总体越模糊，抽样代表性越无法验证。

3.5 定义质量维度

不要只定义一个“正确率”。

常见维度包括：

  • 任务完成度
  • 事实正确性
  • 引用忠实度
  • 召回覆盖
  • 工具选择正确性
  • 参数正确性
  • 安全与权限遵守
  • 拒答适当性
  • 稳定性与方差
  • 延迟与成本
  • 可恢复性
  • 用户可用性

每个维度都要说明：

  • 标签类型
  • 评分规则
  • 证据来源
  • 聚合方式
  • 失败门槛

四、完整生命周期：每次更新都要重新经过治理链

评测集建设不是一次性 ETL。

推荐生命周期包括：

  1. 评测目标
  2. 样本采集
  3. 清洗去重
  4. 分层抽样
  5. 标注仲裁
  6. 版本与切分
  7. 数据卡
  8. 发布门禁
  9. 运行反馈与受控演进

“受控演进”意味着：

  • 已发布版本保持不可变
  • 新样本进入候选池
  • 候选池重新执行清洗、标注和门禁
  • 通过后发布新版本
  • 新旧版本分别计算结果
  • 变更影响有明确说明

不能把线上新失败直接追加到原文件，然后继续沿用旧版本号。

评测样本不应只有 question 和 answer。

5.2 sample_id、record_hash 和 content_dedup_hash 不能互相替代

sample_id 是业务身份。

它用于跟踪同一逻辑样本的生命周期。

record_hash 是整条版本化记录的指纹，应覆盖 split、来源、标注和分组等治理字段。

content_dedup_hash 只覆盖任务内容，例如输入、期望、约束和必要上下文，用于识别 ID、切分或来源不同但任务内容相同的精确重复。

如果修改标签仍沿用原 sample_id，应生成新的两个哈希并记录变更。

如果样本含义发生根本变化，更稳妥的方式是创建新样本并关联前身。

5.3 保存原始数据与规范化数据的关系

为了去重，团队常对文本做：

  • 空白归一化
  • 大小写归一化
  • 标点归一化
  • 模板字段替换
  • HTML 清理

这些变换可能改变语义。

因此应同时保留：

  • 受控原始引用
  • 规范化版本
  • 变换链版本
  • 原始哈希
  • 规范化哈希

不能只保存清洗后的文本而丢失来源。

六、样本来源：多源组合，而不是迷信生产日志

6.1 生产日志

优点：

  • 接近真实分布
  • 能看到真实语言和任务复杂度
  • 能发现设计阶段没有想到的长尾

风险：

  • 隐私和敏感数据
  • 用户授权与用途限制
  • 反馈选择偏差
  • 线上输出已经影响后续标注
  • 高频简单请求淹没稀有风险
  • 日志字段可能缺失

生产样本进入评测集前至少要经过：

  • 用途和权限确认
  • 去标识化或脱敏
  • 质量筛选
  • 分层抽样
  • 独立标注
  • 来源与时间记录

6.2 领域专家设计

优点：

  • 可以覆盖明确业务规则
  • 可以构造边界条件
  • 容易给出权威证据

风险：

  • 专家表达不等于普通用户表达
  • 容易偏向规范路径
  • 样本难度可能与线上不一致
  • 专家间也可能有规则理解分歧

专家样本不应全部作为“困难样本”。

它们也需要经过代表性和一致性检查。

6.3 事故与缺陷回放

优点：

  • 直接覆盖已知失败机制
  • 适合稳定回归
  • 容易关联修复和证据

风险：

  • 开发团队已经针对它调优
  • 样本数量小，不能估计总体发生率
  • 事故环境可能无法完整重建

事故样本适合作为专门回归切片。

不应混进总体随机样本后声称代表真实流量。

6.4 合成样本

合成样本可以由规则、模板或模型生成。

优点：

  • 快速扩展边界和组合条件
  • 便于生成对抗变体
  • 可以控制特定变量

风险：

  • 继承生成模型偏差
  • 语言风格单一
  • 产生不真实任务
  • 重复度高
  • 答案可能由同一模型自我确认

合成样本更适合覆盖性测试和压力测试。

如果要用于总体质量估计，应证明它和目标总体的关系，并避免把合成比例直接当线上比例。

6.5 公共基准

公共基准有利于复现和外部比较。

但需要检查：

  • 许可证和使用条件
  • 任务是否匹配业务
  • 语言和时间有效性
  • 模型是否可能见过数据
  • Prompt 模板是否改变任务
  • 分数是否能推广到应用系统

公共基准分数不能替代私有业务评测。

6.6 红队与对抗样本

这类样本专门测试：

  • 提示注入
  • 数据外泄
  • 工具越权
  • 规则绕过
  • 多轮诱导
  • 编码和混淆

它们代表风险覆盖，不代表自然发生频率。

应该单独报告通过率和严重度。

七、分层抽样：同时维护代表性和风险覆盖

完全按线上频率随机抽样，会得到大量高频简单请求。

完全按专家挑选困难样本，又无法估计正常流量质量。

更稳的设计是“双轨抽样”：

  • 代表性轨：按目标总体分层随机抽样
  • 风险轨：对关键、稀有和对抗场景设置最低配额

7.1 先定义分层维度

常见维度包括：

  • 业务场景
  • 风险等级
  • 任务类型
  • 语言和地区
  • 用户或租户类型
  • 输入长度
  • 难度
  • 是否需要检索
  • 是否调用工具
  • 工具副作用等级
  • 对话轮数
  • 时间窗口
  • 终端或渠道

维度不是越多越好。

如果每个维度组合都成为一个层，样本会迅速稀疏。

应优先选择会改变失败机制、损失或发布决策的维度。

7.2 风险等级要有业务定义

一个可参考的内部定义是：

  • 关键：可能产生不可逆动作、敏感数据泄漏或重大合规影响
  • 高：可能造成重要业务错误，需要人工恢复
  • 中：影响任务完成，但可以低成本纠正
  • 低：措辞、格式或轻微体验问题

这只是示例。

实际等级必须由业务、技术、安全和合规共同定义。

7.9 边界样本怎么设计

边界样本应围绕规则转折点：

  • Token 限制前后

  • 有证据与证据不足切换

7.10 对抗样本怎么避免“只会考固定答案”

对抗样本应按攻击机制组织，而不是只保存固定字符串。

例如“间接提示注入”可以生成：

  • 不同语言
  • 不同编码
  • 文档正文、表格、注释和工具返回中的位置变化
  • 指令显式或隐式变化
  • 单轮与多轮组合

评测目标是机制鲁棒性，不是记住某句攻击文本。

八、清洗：不是把文本变整齐，而是保证测量语义不被破坏

8.1 结构完整性检查

每条样本至少检查：

  • 必填字段
  • 字段类型
  • 枚举值
  • ID 唯一性
  • 引用是否存在
  • 标签状态
  • 来源状态
  • 时间格式
  • 版本格式
  • 切分合法性

结构正确是最低门槛。

它不能证明样本语义正确。

8.2 语义完整性检查

需要人工或规则联合检查：

  • 问题是否自洽
  • 是否存在足够信息得出金标准
  • 引用证据是否支持标签
  • 任务是否仍在预期用途内
  • 文档和业务规则是否过期
  • 答案是否存在多个合理版本
  • 拒答是否是允许结果
  • 场景标签是否准确

8.3 隐私和敏感信息处理

清洗应遵循数据最小化。

建议：

  • 只采集评测需要的字段
  • 在进入标注平台前脱敏
  • 将身份映射表与评测数据分离
  • 对敏感原文使用受控引用
  • 记录脱敏工具和规则版本
  • 定期验证重识别风险
  • 设置保留期限和删除机制

简单正则无法覆盖所有敏感信息。

高风险数据需要规则、模型检测和人工抽检组合。

8.4 精确重复

精确重复可以基于规范化内容哈希检测。

但至少要保留两种哈希：

  • 原始内容哈希
  • 规范化内容哈希

规范化过程不能删除可能改变标签的内容，例如：

  • 否定词
  • 数值单位
  • 大小写敏感标识符
  • 代码缩进
  • 标点形成的逻辑边界

8.5 近似重复

常见方法包括：

  • 字符或词 N-gram Jaccard 相似度
  • MinHash 和局部敏感哈希
  • 编辑距离
  • BM25 相似度
  • Embedding 余弦相似度
  • 规则模板签名

8.6 重复簇比单条删除更重要

去重的真正目的有两个：

  1. 避免同一模板支配指标。
  2. 防止同一语义族跨切分泄漏。

因此应为每条样本生成 duplicate_cluster。

同一簇可以保留有价值的变体，但必须：

  • 设置簇内上限
  • 在聚合时控制权重
  • 整簇进入同一个数据切分

九、污染与泄漏：高分最隐蔽的来源

9.1 训练污染

如果评测样本或近重复内容出现在模型训练数据中，分数可能反映记忆而非泛化。

对闭源模型，团队通常无法完整检查预训练数据。

可采取的务实措施包括：

  • 使用组织内部、发布时间晚于模型知识边界的私有任务
  • 对公共题目进行机制级变体，而不是只改措辞
  • 记录模型供应商对数据使用和保留的说明
  • 对异常逐字匹配做人工调查
  • 对公开基准结果明确标注污染不确定性

不能因为无法完全证明无污染，就假装污染不存在。

应在数据卡里记录已知和未知风险。

9.2 开发集泄漏

开发人员反复查看失败样本并修改 Prompt 后，这些样本已经参与优化。

它们仍可保留在回归集，用于防止旧问题复发。

但不应继续作为独立泛化证据。

9.3 Few-shot 与 Prompt 泄漏

如果评测题或近重复答案出现在 Few-shot 示例中，评测会被直接提示。

检查范围应包括：

  • 系统提示词
  • Few-shot 示例库
  • 动态 Prompt 模板
  • Agent 技能说明
  • 工具描述示例

9.4 RAG 知识库泄漏

RAG 系统本来就应该从知识库获取事实。

问题不在于“评测答案存在知识库”。

问题在于：

  • 知识库是否包含评测专用答案或评分说明
  • 检索是否读到不可用于真实业务的标签字段
  • 评测问题是否被直接写成 FAQ 标题
  • 测试数据是否进入了线上索引

需要区分“合法业务证据”和“评测标签泄漏”。

9.5 切分泄漏

随机按行切分最容易导致：

  • 同一会话的不同轮次跨集合
  • 同一模板的改写跨集合
  • 同一文档生成的问题跨集合
  • 同一客户或设备跨集合
  • 同一事故的变体跨集合

此时模型或系统可能利用共享上下文特征，得到虚高结果。

9.6 评测结果回流污染

如果平台把失败样本自动加入 Prompt、记忆或知识库，下次评测就可能看到上次答案。

线上学习和评测必须有隔离策略。

密封集尤其不能自动进入任何调优链路。

十、数据切分：按独立性单位分，而不是按行分

10.1 三类常用切分

建议至少区分：

  • 开发集：允许查看标签，用于迭代
  • 回归或发布集：版本稳定，用于持续门禁
  • 密封或审计集：限制访问，用于独立验证

还可以单独维护：

  • 事故回放集
  • 安全红队集
  • 线上影子集
  • 漂移监控集

10.2 分组切分

选择真正的独立性单位作为组：

  • 重复簇
  • 会话
  • 文档族
  • 用户或租户
  • 业务实体
  • 事故族
  • 代码仓库
  • 设备型号

同一组只进入一个切分。

10.3 时间切分

如果目标是预测未来表现，可以使用时间切分：

  • 早期数据用于开发
  • 后期数据用于评测

时间切分更接近真实发布，但也可能混入业务规则变化。

因此需要同时记录：

  • 数据时间
  • 规则有效期
  • 知识库版本
  • 系统发布版本

10.4 实体留出

如果系统需要泛化到新客户、新文档或新设备，可以按实体留出。

例如：

  • 某些租户只进入评测集
  • 某些文档族只进入密封集
  • 某些设备型号不参与开发

实体留出通常比随机行切分更严格。

10.5 切分稳定性

同一个 sample_id 不应在不同版本间无理由来回移动。

建议：

  • 使用稳定哈希分桶
  • 先按组聚合，再对组分桶
  • 在清单中记录分配算法和种子
  • 变更切分时提升数据版本并说明影响

十一、标注规范：把“我觉得对”变成可复核判断

11.1 标签必须与决策对应

不要为了字段丰富而增加标签。

每个标签都应回答：

  • 它支持什么发布决策
  • 谁能权威判断
  • 依据什么证据
  • 是名义、顺序、区间还是连续尺度
  • 不确定时怎样处理

11.2 原子事实比整段“好或坏”更可诊断

对于 RAG 回答，可以拆成：

  • 问题是否可回答
  • 是否召回必要证据
  • 每个关键声明是否被证据支持
  • 是否包含互相矛盾的声明
  • 引用是否映射到正确版本
  • 是否遗漏必要条件
  • 最终结论是否符合业务规则

整段打一个 1 到 5 分可以用于汇总。

原子标签更适合定位和修复。

11.3 一个可操作的量表示例

以“事实忠实度”为例：

分值 定义 判定证据
3 所有关键声明均被给定证据支持 声明到证据逐条映射
2 主要结论正确，但有非关键无依据细节 标出无依据细节
1 部分关键声明无依据或与证据冲突 标出关键冲突
0 核心结论无依据、相反或伪造来源 标出核心错误
U 证据不足，无法可靠判断 记录缺失证据

U 不应自动算 0，也不应自动算通过。

它应进入补证或仲裁流程。

11.4 标注指南必须包含什么

  • 任务定义
  • 适用范围
  • 标签定义
  • 正例
  • 反例
  • 边界例
  • 缺证据处理
  • 多答案处理
  • 拒答处理
  • 冲突证据处理
  • 不确定标签
  • 升级与仲裁路径
  • 版本和生效时间

只有标签名称，没有边界例，不算完整规范。

11.5 标注人员培训

推荐流程：

  1. 阅读规范。
  2. 独立完成训练集。
  3. 与权威答案比对。
  4. 讨论分歧。
  5. 修订规范。
  6. 通过资格集。
  7. 进入正式盲标。
  8. 定期插入质量控制样本。

领域任务不能只依赖通用语言能力。

标注人员还要理解业务规则和证据优先级。

11.6 盲标与双标

高风险样本建议至少双人独立标注。

盲标时尽量隐藏：

  • 被测模型名称
  • 新旧版本身份
  • 团队期望结果
  • 其他标注员答案
  • 自动裁判结果

否则容易产生锚定和确认偏差。

11.7 仲裁不等于少数服从多数

分歧可能说明：

  • 某个标注员错误
  • 规范模糊
  • 证据不足
  • 样本本身多解
  • 业务规则冲突

仲裁者应记录：

  • 最终标签
  • 采用的证据
  • 分歧原因
  • 是否需要修改规范
  • 是否需要回溯重标同类样本

如果分歧暴露规范缺陷，只修当前一条数据是不够的。

  • 混淆矩阵

  • 分层 Kappa
  • 具体分歧样本

十四、版本化：版本号必须指向不可变内容

  2. 记录变更原因。
  3. 保留旧版本清单。
  4. 重新计算受影响指标。
  5. 说明新旧分数是否可直接比较。

十五、数据卡：告诉使用者这个分数能说明什么

数据需要结构化文档，不能只靠创建者口头解释。

15.1 数据卡至少包含

基本身份

  • 数据集名称与版本
  • 所有者和维护者
  • 发布时间
  • 状态：开发、发布、弃用或归档

预期用途

  • 支持哪些决策
  • 测试哪些系统边界
  • 不适用于哪些用途
  • 目标用户和利益相关者

数据组成

  • 总样本数
  • 来源比例
  • 场景和风险分布
  • 语言、地区和时间范围
  • 各切分数量

采集与处理

  • 采样框
  • 抽样方法
  • 清洗与脱敏
  • 去重方法
  • 合成数据比例
  • 排除规则

标注

  • 标签定义
  • 标注人员资格
  • 双标比例
  • 仲裁流程
  • 一致性结果

风险与限制

  • 已知覆盖缺口
  • 污染不确定性
  • 可能偏差
  • 不稳定标签
  • 有效期
  • 隐私和许可限制

版本变更

  • 新增、删除和修改数量
  • 标签规则变化
  • 切分变化
  • 对历史分数可比性的影响

15.2 数据卡不是合规装饰

它应直接服务三类人：

  • 开发者：知道能不能用它调优
  • 评测者：知道怎样运行和解释
  • 决策者：知道分数能否支持发布

如果数据卡不能帮助这三类人做决定，就需要继续精简或补充。

十六、发布门禁：评测集自己也要通过测试

16.1 结构门禁

  • JSONL 或 Parquet 可解析
  • Schema 校验通过
  • 必填字段完整
  • ID 唯一
  • 引用可解析
  • 哈希一致

16.2 来源与授权门禁

  • 每条样本来源明确
  • 用途与授权匹配
  • 敏感字段按策略处理
  • 数据保留期限明确
  • 第三方数据许可可追溯

16.3 覆盖门禁

  • 关键场景达到最低配额
  • 高风险层无空洞
  • 语言和租户分布符合目标
  • 边界与对抗机制覆盖
  • 样本时间范围仍有效

16.4 去重与泄漏门禁

  • 精确重复率在约定范围内
  • 近重复簇已审查
  • 同一组不跨切分
  • 评测数据未进入 Few-shot 示例
  • 密封集未进入调优和知识库
  • 公共基准污染风险有记录

16.5 标注门禁

  • 所有发布样本完成标注
  • 分歧已仲裁或显式标记不确定
  • 一致性报告已生成
  • 高风险样本由合格专家复核
  • 标签有证据引用
  • 指南版本一致

16.6 可复现门禁

  • 抽样与切分算法有版本
  • 随机种子已记录
  • 转换链可重跑
  • 文件和清单哈希可验证
  • 评测执行环境有快照
  • 上一版本仍可获取

16.7 门槛必须按用途设定

不能给所有数据集规定同一个 Kappa、重复率或样本量阈值。

例如：

  • 安全密封集可能容忍刻意的机制变体，却不容忍标签歧义
  • 自然流量集可能保留真实高频模板，但聚合时要降权
  • 探索集可以包含待仲裁样本，发布集不可以

门禁规则必须写进版本清单，并由风险承担者批准。

十八、示例案例：一个高分客服评测集为什么无法支持发布

以下为教学用示例案例，用于说明数据治理问题，不代表任何真实项目经历或真实业务数据。

18.1 背景

团队为一个企业客服 RAG 系统建设了 5000 条评测样本。

新版本总体通过率达到 94%，高于旧版本的 91%。

团队准备据此全量发布。

18.2 初步检查发现

  • 约 60% 样本由 30 个 FAQ 模板改写生成
  • 同一 FAQ 的改写被随机分到开发集和发布集
  • 70% 样本是低风险事实问答
  • 权限、退费和账户冻结等高风险场景不足 2%
  • 标签由单人根据旧版答案改写
  • 标注人员知道哪个输出来自新版本
  • 知识库包含一个“评测标准答案”目录
  • 数据文件在三周内被原地修订过多次，但版本号未变

18.3 为什么 94% 不可信

第一，模板近重复让物理样本量远大于独立语义单元数。

第二，开发集和发布集共享重复簇，Prompt 调优可能直接学习了发布题型。

第三，高风险场景样本太少，总分无法说明发布风险。

第四，旧版答案参与新标签生成，可能把旧系统偏差固化成金标准。

第五，非盲标会产生版本偏好。

第六，RAG 可以检索评测专用答案，构成标签泄漏。

第七，数据集不可变性缺失，91% 和 94% 可能不是在同一测量仪器上得到。

18.4 修复方案

  1. 对 FAQ 改写做近重复聚类。
  2. 按 FAQ 族而不是按行重新切分。
  3. 保留一套按真实流量分布抽样的代表性集。
  4. 为权限、退费和账户冻结建立风险最低配额。
  5. 由两名标注员基于当前权威制度独立标注。
  6. 对分歧做专家仲裁，并更新标签指南。
  7. 从知识库移除评测专用答案，只保留合法业务文档。
  8. 发布不可变数据版本和内容哈希。
  9. 在同一版本上重新运行新旧系统。
  10. 分别报告总体加权结果和高风险切片结果。

18.5 修复后的解释

假设重新评测后出现：

  • 自然流量加权通过率仅小幅提升
  • 低风险 FAQ 提升明显
  • 权限类任务没有改善
  • 退费边界任务出现回归

这比一个 94% 总分更有价值。

它直接支持发布决策：

  • 可以逐步开放低风险 FAQ
  • 权限类维持人工复核
  • 退费场景阻断发布并继续修复

十九、测试设计：评测集应该怎样被持续测试

19.1 Schema 测试

  • 每个字段类型正确
  • 枚举没有未知值
  • 引用对象存在
  • 标签和任务类型兼容
  • 版本字段格式正确

19.2 属性测试

  • 高风险工具样本必须有权限期望
  • RAG 样本必须有证据或允许拒答
  • 多轮样本必须有稳定会话组
  • 副作用任务必须定义最终状态断言
  • 不确定标签必须有原因

19.3 分布测试

  • 各层样本数达到最低配额
  • 关键维度与采样目标差异在可解释范围
  • 单一来源或模板没有异常支配
  • 合成样本比例没有意外上升
  • 新版本分布变化有变更记录

19.4 泄漏测试

  • 精确哈希交集
  • N-gram 或 MinHash 近重复交集
  • Embedding 候选复核
  • 组键跨切分检查
  • Prompt 和 Few-shot 语料扫描
  • RAG 索引中的评测专用字段检查

19.5 标签测试

  • 金标准引用仍有效
  • 标签与证据无冲突
  • 分歧样本完成仲裁
  • 一致性按切片监控
  • 修改指南后回溯受影响样本

19.6 可重现性测试

  • 从来源快照重新构建
  • 重新构建后清单哈希一致
  • 固定种子切分一致
  • 评测运行引用明确数据版本
  • 历史报告能找到对应清单

19.7 退役测试

样本需要退役条件，例如：

  • 业务规则已经失效
  • 来源许可到期
  • 隐私要求变化
  • 标签无法重新验证
  • 样本进入调优链路，不再适合密封评测

退役不等于删除历史。

应在符合保留策略的前提下记录原因和替代样本。

二十、如何把评测集接入 CI/CD

20.1 拉取请求阶段

运行小型快速集：

  • Schema 和结构校验
  • 关键事故回归
  • 高风险工具契约
  • 变更影响相关切片

目标是快速阻断明显回归。

20.2 合并后阶段

运行稳定回归集：

  • 多模型或多次采样
  • 组件和端到端评测
  • 分层指标
  • 成本与延迟
  • 与基线的配对比较

20.3 发布候选阶段

运行发布集和受控密封集：

  • 使用冻结系统配置
  • 记录模型、Prompt、索引、工具和策略版本
  • 评测器版本固定
  • 输出逐样本证据
  • 高风险失败零容忍或按既定策略阻断

20.4 线上阶段

使用：

  • 影子流量
  • 人工抽检
  • 用户反馈
  • 低置信样本挖掘
  • 分布漂移监控
  • 事故回流候选池

线上失败进入候选池后，必须重新走治理流程。

不能自动写入密封集或覆盖既有标签。

二十一、结果比较：固定数据版本还不够

比较两个系统版本时，还要固定或记录：

  • 模型版本
  • 采样参数
  • Prompt 版本
  • 检索语料和索引版本
  • 工具 Schema 和沙箱状态
  • 策略版本
  • 评测器版本
  • 运行时间和服务区域
  • 随机种子
  • 重复运行次数

21.1 优先做配对比较

同一批样本分别运行旧版和新版，可以观察逐样本变化：

  • 旧错新对
  • 旧对新错
  • 两者都对
  • 两者都错

这比只比较两个总体比例更容易定位回归。

21.2 非确定性系统需要重复运行

如果模型输出有明显方差，单次运行不足以描述稳定性。

可以记录：

  • 每条样本通过概率
  • 多次运行方差
  • 最差运行
  • 多数结果
  • 关键风险是否出现过一次失败

高风险任务不能只看平均表现。

21.3 数据集升级时做桥接评测

如果从数据集 2.3 升到 2.4，建议：

  1. 在两个数据版本上同时运行同一个系统版本。
  2. 分开报告保留样本和新增样本。
  3. 解释标签或分布变化。
  4. 不把不可比结果直接连成趋势线。

这相当于给测量仪器换代做校准桥接。

二十二、常见误区

22.1 先追求数量，再补质量

低质量样本会形成返工债务。

尤其是来源、标签和组键缺失后，很难事后恢复。

22.2 把线上随机抽样当完整代表性

随机样本只代表采样框。

如果日志本身漏掉失败请求、未授权用户或人工接管，它仍然有系统偏差。

22.3 把困难样本比例当自然发生率

风险集可以过采样。

但总分需要重加权，并单独报告风险切片。

22.4 只用字符串哈希去重

精确哈希无法发现模板改写和近重复。

还需要近重复候选、组级切分和人工复核。

22.5 Embedding 相似就自动删除

语义接近不等于标签相同。

否定、数值和权限边界尤其容易被误删。

22.6 同一模型生成问题、生成答案并担任裁判

这种闭环会放大同源偏差。

至少需要规则、独立模型、权威证据或人工评审中的其他信号。

22.7 一致率高就认为标签可靠

类别极不平衡时，标注员全部选多数类也会得到高一致率。

应同时看 Kappa 或 Alpha、混淆矩阵和分层结果。

22.8 所有不确定样本都删除

不确定可能正是业务边界模糊的信号。

应该区分证据不足、规则冲突、多解和标注错误。

22.9 原地修正评测集

原地修正会破坏历史报告可复现性。

任何用于决策的数据都应发布新版本。

22.10 用一个总分做发布门禁

总分可能掩盖关键风险回归。

应设置：

  • 总体指标
  • 关键切片指标
  • 严重失败计数
  • 不确定结果比例
  • 延迟和成本约束

22.11 把密封集无限重复使用

使用次数越多，团队越可能间接针对它优化。

密封集需要访问审计、使用预算和定期轮换。

22.12 数据卡写完就不更新

数据组成、授权、业务规则和污染风险都会变化。

数据卡必须随版本发布。

二十三、建设顺序：从最小可信集开始

如果团队刚开始建设，不必一次做成大型平台。

第一阶段：定义可测量对象

  • 明确一个发布决策
  • 固定系统输入输出边界
  • 选择 3 到 5 个关键质量维度
  • 定义 10 到 20 个核心风险层

第二阶段：建立最小数据契约

  • sample_id
  • 输入与期望
  • 来源
  • 分层标签
  • 标注状态
  • 组键
  • 切分
  • 内容哈希

第三阶段：建设小型高质量集

  • 代表性样本
  • 高风险最低配额
  • 事故回放
  • 双人标注
  • 专家仲裁

先把 300 条做可信，通常比快速堆到 10000 条更有价值。

具体数量仍应由统计目标和风险决定。

第四阶段：自动化门禁

  • Schema
  • 哈希
  • 去重
  • 泄漏
  • 覆盖
  • 标注状态
  • 清单生成

第五阶段：版本和数据卡

  • 不可变发布
  • 变更记录
  • 可重现构建
  • 历史版本访问
  • 用途和限制说明

第六阶段：线上反馈闭环

  • 低置信样本发现
  • 事故候选池
  • 漂移检测
  • 人工复核
  • 受控发布新版本

二十四、落地检查表

24.1 目标与范围

  • 是否从明确发布或比较决策出发
  • 是否定义评测对象和输入输出边界
  • 是否定义评测单元
  • 是否定义目标总体和采样框
  • 是否写清预期用途与禁止用途
  • 是否分别定义总体质量与高风险底线

24.2 采集

  • 每条样本是否有来源、时间和授权依据
  • 生产日志是否经过最小化和脱敏
  • 专家样本是否覆盖普通用户表达
  • 合成样本是否标记生成器和 Prompt 版本
  • 事故样本是否与总体随机样本分开
  • 公共数据的许可证和污染风险是否记录

24.3 抽样与覆盖

  • 是否定义场景、风险和关键分层维度
  • 是否保留自然分布代表性轨
  • 是否为低频高风险层设置最低配额
  • 过采样后是否使用正确权重
  • 是否报告关键切片而不只报告总分
  • 是否检查有效样本量和模板集中度

24.4 清洗与去重

  • 是否同时保留原始和规范化内容哈希
  • 规范化是否保留否定、数值和标识符语义
  • 是否检测精确重复和近重复
  • 近重复是否以候选簇方式人工复核
  • 是否限制单一模板簇权重
  • 是否记录清洗和脱敏工具版本

24.5 污染与切分

  • 是否扫描训练、开发、Prompt 和 Few-shot 泄漏
  • 是否检查 RAG 索引中的评测标签泄漏
  • 是否按重复簇、会话、文档族或实体切分
  • 密封集是否与调优链路隔离
  • 切分算法、组键和随机种子是否记录
  • 是否记录无法验证的预训练污染风险

24.6 标注

  • 标签是否直接支持评测决策
  • 是否有正例、反例、边界例和不确定处理
  • 高风险样本是否双标和专家复核
  • 标注是否对模型版本和其他答案盲化
  • 是否计算并解释一致性
  • 是否按场景和标签检查分歧
  • 仲裁是否记录证据和规范变更

24.7 版本与发布

  • 发布版本是否不可变
  • 是否有文件级和清单级哈希
  • 是否保存数据血缘和转换版本
  • 是否有数据卡与变更记录
  • 历史报告是否能找到确切数据版本
  • 数据集升级是否做桥接评测
  • 是否有数据退役和替代流程

24.8 门禁与运行

  • 评测集自身是否通过结构和语义检查
  • 发布门槛是否按用途设定
  • 是否固定被测系统和评测器版本
  • 非确定性任务是否重复运行
  • 是否保留逐样本证据而不只保留总分
  • 线上反馈是否先进入候选池
  • 密封集是否有访问审计和使用预算

二十五、总结

高质量 AI 评测集不是一批“看起来像真实问题”的样本。

它是一套可审计的测量系统。

建设时需要同时守住八件事：

  1. 从发布决策反推评测目标、对象、单元和目标总体。
  2. 组合生产、专家、事故、合成和对抗来源，并记录授权与血缘。
  3. 用代表性抽样和风险最低配额同时覆盖高频流量与低频严重失败。
  4. 通过精确去重、近重复聚类和组级切分控制模板支配与泄漏。
  5. 用证据化量表、盲标、双标和仲裁建立可信标签。
  6. 用一致率、Kappa 或 Alpha 发现规范与标注系统问题，而不是机械追求阈值。
  7. 用不可变版本、内容哈希、清单和数据卡保证结果可复现、可解释。
  8. 让评测集先通过来源、覆盖、标签、泄漏和可重现性门禁，再承担模型发布门禁。
