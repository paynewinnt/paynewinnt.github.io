AI测试-11-大模型从输入Token到生成结果到底经历了什么

发表于 2026-03-10 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 42 分钟

调用大模型接口时，客户端看到的动作通常很简单：

但在这段等待时间里，系统至少可能经历：

  • 请求校验
  • 身份认证和限流
  • 模型路由
  • chat template 拼装
  • 文本规范化
  • tokenization
  • 截断和填充
  • 调度与动态批处理
  • embedding
  • 多层 Transformer 计算
  • KV cache 写入
  • logits 处理
  • token 选择
  • 停止条件判断
  • detokenization
  • 流式分块和网络返回

只看最终文本，会把这些阶段压缩成一个黑盒。

黑盒一旦输出错误、首字慢、流式卡顿或成本异常，测试就很容易只剩下一个模糊结论：

“模型不稳定。”

这个结论通常无法指导修复。

本文从测试开发视角，沿着一次请求的内部路径向下拆解。

目标不是复现某一个供应商的私有实现。

目标是建立一组足够稳定的观察点：

  • 输入在哪一步发生变化
  • 首 token 为什么慢
  • 后续 token 为什么逐个生成
  • KV cache 保存了什么
  • logits 怎样变成最终 token
  • 停止和流式返回有哪些协议边界
  • 每一阶段可以怎样测试和定位

一、问题边界：本文讲的是常见路径，不是所有模型的唯一实现

开始之前，必须先把适用范围说清楚。

本文重点描述：

服务端常见的、自回归生成文本的 Transformer 类大模型，尤其是 decoder-only 模型。

这条路径对理解大量聊天和文本生成系统很有帮助。

但不能据此声称所有模型实现都完全相同。

1. 架构可能不同

实际模型还可能是：

  • encoder-decoder
  • 多模态 Transformer
  • Mixture of Experts
  • 使用滑动窗口或稀疏注意力的模型
  • 使用状态空间模型或混合结构的模型
  • 带检索、外部记忆或专用适配器的模型

它们的输入表示、缓存形式和计算路径可能不同。

2. 注意力实现可能不同

常见差异包括：

  • Multi-Head Attention
  • Multi-Query Attention
  • Grouped-Query Attention
  • 局部或滑动窗口注意力
  • 稀疏注意力
  • IO-aware 的精确 attention kernel
  • 厂商自定义融合 kernel

数学目标相近，不代表内存布局、性能和缓存大小相同。

3. 生成策略可能不同

除了逐 token 自回归生成，还可能使用：

  • beam search
  • speculative decoding
  • assisted decoding
  • grammar-constrained decoding
  • 一次预测多个候选 token 的方法
  • 推理阶段的并行或分离式服务

因此，后文所说“每步生成一个 token”是理解基本自回归路径的基线。

优化实现可能在一次计算中验证或接纳多个 token。

4. 托管 API 的可见性有限

自建推理服务可以观测：

  • tokenizer 输出
  • 调度队列
  • prefill 时间
  • decode 时间
  • KV cache 利用率
  • 每步 logits 或 token

托管 API 往往只暴露：

  • 请求参数
  • 最终或流式响应
  • token 用量
  • 部分 finish reason
  • 总体延迟

测试设计必须区分白盒、灰盒和黑盒能力。

不能要求一个黑盒 API 提供不存在的内部指标。

但可以通过输入长度、并发、输出长度和重复实验推断边界。

二、先建立完整链路：模型计算只是中间一段

一次请求可以拆成四层。

1. 接入层

负责：

  • HTTP、gRPC 或其他协议
  • 身份认证
  • 租户识别
  • 请求大小限制
  • 限流与配额
  • 参数 schema 校验
  • 内容策略预检查
  • request_id 和 trace_id

这一层出错时，模型甚至没有开始运行。

2. 编排层

负责：

  • 模型选择
  • 版本路由
  • Prompt 模板
  • RAG 上下文
  • 历史会话裁剪
  • 工具定义
  • 安全策略
  • 输出格式约束

客户端发送的 messages，不一定等于模型真正看到的输入。

编排层可能在前后插入大量内容。

3. 推理层

负责：

  • tokenizer
  • token ID
  • embedding
  • Transformer block
  • KV cache
  • logits
  • decoding

这是本文的核心。

4. 返回层

负责：

  • token 解码为文本
  • 输出后处理
  • 内容过滤
  • tool call 结构组装
  • 流式协议
  • usage 统计
  • finish reason
  • 连接关闭

返回层同样可能制造错误。

例如模型已经生成正确 JSON，但后处理器截断了最后一个括号。

测试不能把所有最终输出问题都归到模型计算。

三、请求预处理：模型真正看到的内容可能已经和请求体不同

假设客户端发送：

服务端实际执行前可能做以下处理。

1. 参数默认值合并

客户端没有显式提供的参数，可能来自：

  • API 默认值
  • 模型默认 generation config
  • 租户策略
  • 场景模板
  • 服务端强制上限

测试记录不能只保存客户端请求。

还应尽可能保存“生效后的配置”。

例如：

2. chat template 拼装

聊天模型通常不会直接接收 JSON。

服务端会按模型约定把角色和内容序列化。

概念上可能类似：

不同模型的：

  • 角色标记
  • 分隔符
  • 起止 token
  • tool call 表示
  • assistant generation prompt

都可能不同。

错误模板会使同一模型表现显著变化。

模型升级测试必须把 chat template 当成版本对象。

3. RAG 和工具信息注入

真实输入还可能加入：

  • 检索文档
  • 文档引用编号
  • 工具 schema
  • 用户权限
  • 当前时间
  • 会话摘要
  • 安全规则

这些内容都会占用 token。

它们之间的顺序也会影响截断结果和模型注意范围。

4. 长度预算与截断

设：

  • N_s 为系统与策略 token 数
  • N_h 为历史会话 token 数
  • N_r 为检索上下文 token 数
  • N_u 为当前用户输入 token 数
  • N_o 为预留输出 token 数
  • N_{ctx} 为允许的上下文总预算

必须满足：

超出预算后，系统必须选择删什么。

常见策略包括：

  • 删除最早会话
  • 摘要历史
  • 减少检索片段
  • 截断用户输入
  • 降低最大输出长度
  • 拒绝请求

每一种策略都改变行为。

最危险的做法是无记录地左截断或右截断。

因为它可能删掉安全指令、问题结尾或关键证据。

5. 输入规范化

部分 tokenizer 或业务预处理会进行：

  • Unicode 规范化
  • 空白处理
  • 大小写转换
  • 控制字符过滤
  • 特殊 token 转义

但这不是所有 tokenizer 的统一规则。

测试必须以实际 tokenizer 和配置为准。

需要覆盖：

  • NFC、NFD、NFKC 等差异
  • 全角和半角字符
  • 不可见字符
  • 零宽字符
  • 换行风格
  • 组合字符
  • emoji 和罕见字符

四、Tokenization：模型处理的是 ID 序列，不是“一个词一个 token”

原始文本会经过 tokenizer，得到 token ID。

概念上可以写成：

每个 t_i 是词表中的整数 ID。

1. token 不等于单词

一个 token 可能是：

  • 一个完整单词
  • 单词的一部分
  • 一个汉字
  • 多个汉字的片段
  • 标点
  • 空白及其组合
  • 一个字节片段
  • 特殊控制标记

因此，不要用“字数除以固定比例”作为精确 token 计数。

预算必须使用目标模型对应的 tokenizer。

2. 常见子词算法

常见 tokenizer 可能使用：

  • BPE
  • WordPiece
  • Unigram
  • byte-level 变体
  • SentencePiece 实现的子词模型

它们的训练目标和切分方式不同。

同一句话在两个模型中可能得到完全不同的 token 数。

3. tokenizer 是一条流水线

以常见 tokenizer 库的抽象为例，可能包含：

  1. Normalizer
  2. Pre-tokenizer
  3. Subword model
  4. Post-processor
  5. Decoder

其中某些步骤可以不存在。

Post-processor 可能加入：

  • BOS
  • EOS
  • CLS
  • SEP
  • 角色相关特殊 token

所以“文本本身 100 token”和“最终模型输入 100 token”不是同一件事。

4. token ID 必须和模型权重匹配

tokenizer 的词表和模型 embedding 表存在契约。

如果误用另一个 tokenizer：

  • token ID 语义会错位
  • 特殊 token 可能错误
  • 输入长度可能变化
  • 输出 detokenization 可能异常

即使服务没有报错，模型行为也可能已经失真。

5. tokenization 的测试观察点

白盒测试应记录：

  • tokenizer 名称或文件哈希
  • tokenizer 版本
  • chat template 版本
  • 规范化后的文本
  • token ID
  • token piece
  • special token
  • 截断位置
  • 最终输入长度

黑盒测试至少记录：

  • 原始请求
  • 服务报告的 input token 数
  • 模型版本
  • 模板或应用版本

6. tokenizer 回归用例

建议建立固定语料：

  • 中英文混排
  • 数字与单位
  • URL
  • JSON
  • shell 命令
  • 代码
  • emoji
  • 组合字符
  • 全半角
  • 连续空格和换行
  • 特殊 token 外观字符串
  • 极长无空格文本

升级 tokenizer 或模板时，对比：

  • token 数
  • token ID
  • 特殊 token 位置
  • 截断结果

token ID 本身只是索引。

1. embedding 不是静态“词义字典”

embedding 给出初始向量。

token 在当前句子中的最终上下文表示，要经过多层 Transformer。

同一个 token 出现在不同上下文中，后续隐藏状态会不同。

2. 输入和输出权重可能共享

部分模型会让输入 embedding 与最终输出投影共享权重。

这通常称为 weight tying。

但不是所有模型都必须这样做。

测试人员不应把它作为统一假设。

3. 量化会改变数值表示

推理服务可能使用：

  • FP32
  • FP16
  • BF16
  • INT8
  • 更低比特量化
  • 混合精度

量化目标通常是在质量、显存和速度之间取舍。

它可能引入输出变化。

量化版本应作为独立候选进入评测，而不是只跑性能。

八、Prefill：一次并行处理输入，并建立第一批 KV cache

对于长度为 N 的 Prompt，模型先处理全部输入 token。

这个阶段通常称为 prefill，也常被叫作 prompt processing。

1. prefill 做什么

对每一层，模型会：

  • 计算输入 token 的隐藏状态
  • 生成对应的 Key 和 Value
  • 应用 causal attention
  • 保存后续 decode 需要的 KV
  • 得到最后输入位置的输出 logits

由于完整 Prompt 已知，各输入位置可以进行高度并行的矩阵计算。

2. 第一个输出 token 从哪里来

输入序列经过最后一层后，取最后一个有效位置的隐藏状态。

再经过最终 normalization 和词表投影，得到下一个 token 的 logits。

这次“下一个 token”就是第一个生成 token。

3. prefill 为什么影响首 token 延迟

Prompt 越长，通常需要处理的计算越多。

首个输出必须等待：

  • 排队
  • 输入处理
  • prefill
  • 第一次 token 选择
  • detokenization
  • 首个流式块传输

因此 TTFT 常随输入长度增加。

但真实结果还受：

  • 批处理
  • 硬件
  • attention kernel
  • prefix cache
  • 调度
  • 网络

影响。

不能只用一个线性公式预测。

4. dense attention 的复杂度

标准 dense self-attention 的注意力分数矩阵随序列长度平方增长。

概念计算复杂度包含：

FlashAttention 等方法通过减少不同存储层级之间的数据搬运来提升实际效率。

它不等于把标准精确 attention 的数学关系简单改成线性。

滑动窗口、稀疏或其他架构则可能有不同复杂度。

5. prefix cache

如果多个请求共享相同前缀，服务可能复用已计算的 KV。

例如共享 system prompt 或固定文档。

测试 prefix cache 时必须区分：

  • 冷启动
  • 热缓存
  • 部分前缀命中
  • 租户隔离
  • 模板微小变化
  • 缓存失效

缓存命中会显著改变 TTFT。

基准测试若混合冷热请求，结论会失真。

九、KV Cache：用显存换取 decode 阶段的重复计算

自回归生成第 t 个 token 时，需要关注之前所有可见 token。

如果每一步都重新计算历史 token 的 Key 和 Value，会产生大量重复工作。

KV cache 保存各层历史 token 的 K、V。

1. 每一层都有缓存

缓存不是只保存一次。

对每个 Transformer layer，都要保存历史 token 对应的 K 和 V。

decode 新 token 时：

  • 只为新 token 计算新的 K、V

1. 输出投影

高层形式：

有些实现没有 bias。

有些实现与输入 embedding 共享权重。

仍然要以目标模型为准。

2. logit processor

在采样前，服务可能修改 logits：

  • 禁止特定 token
  • 强制最小长度
  • repetition penalty
  • presence penalty
  • frequency penalty
  • grammar 或 schema 约束
  • safety 约束
  • forced token

这些处理属于实际生成配置的一部分。

测试时应记录生效策略。

3. 温度

温度 \tau > 0 时：

温度越低，分布通常越尖锐。

温度越高，分布通常越平坦。

数学上 \tau = 0 不可直接代入。

许多 API 把 temperature 为 0 当作 greedy 或近似确定性模式，这是接口约定。

4. greedy

greedy 每步选择：

它减少采样随机性。

但不保证跨服务、跨硬件、跨版本绝对一致。

并列分数、数值精度、kernel、并行规约和模型版本都可能影响结果。

5. top-k

top-k 只保留分数最高的 k 个候选。

其余候选被屏蔽，再重新归一化。

k=1 接近 greedy。

6. top-p

top-p，也称 nucleus sampling：

  1. 按概率从高到低排序
  2. 选择累计概率达到阈值 p 的最小候选集合
  3. 在该集合中重新归一化采样

候选数量会随当前分布变化。

7. 多个采样策略的组合

服务可能按特定顺序组合：

  • penalties
  • temperature
  • top-k
  • top-p
  • min-p
  • grammar

精确顺序是实现细节。

同名参数也可能有边界差异。

跨服务对比时必须核对文档和实测。

8. seed 的边界

seed 控制伪随机数生成器的起点。

在相同实现、模型、参数、执行路径和硬件条件下，它有助于复现。

但以下变化都可能破坏逐 token 一致：

  • 模型版本
  • tokenizer
  • chat template
  • kernel
  • 数值精度
  • batch 组成
  • 分布式执行
  • 服务端采样实现
  • 未公开的默认参数

测试报告应写“在给定环境下可重复”，不要写“固定 seed 绝对确定”。

十二、Decode：把第一个 token 追加回上下文，再继续预测

prefill 得到第一个输出 token 后，系统进入 decode 循环。

1. 一次基本循环

每一步大致执行：

  1. 将上一步选中的 token 作为当前输入
  2. 查 embedding
  3. 经过各层 Transformer
  4. 为当前 token 生成新的 K、V
  5. 将新的 K、V 追加到 cache
  6. 使用当前 Query 关注历史 cache
  7. 得到下一 token 的 logits
  8. 应用 logit processor 和采样
  9. 检查停止条件
  10. 将增量结果交给返回层

2. 为什么 decode 很难完全并行

第 t+1 个输出依赖第 t 个输出。

在基本自回归路径中，未来 token 尚未确定。

因此输出序列沿时间维度存在依赖。

服务可以：

  • 同时批处理多个请求的当前 step
  • 使用 speculative decoding 验证多个候选
  • 优化 kernel 和内存访问

但不能简单地把未知的完整输出一次性独立算完。

3. prefill 和 decode 的资源特征不同

prefill 对完整输入进行大量并行计算。

decode 每步处理的新 token 很少，但要读取模型权重和不断增长的缓存。

在常见硬件和负载下：

  • prefill 往往更偏计算密集
  • decode 往往更容易受到内存带宽和调度影响

这是常见经验，不是对所有模型、batch 和硬件的绝对结论。

4. 连续批处理

生产服务会同时处理多个长度不同的请求。

continuous batching 可以在每个调度迭代中：

  • 接纳新请求
  • 推进已有 decode
  • 移除已完成请求
  • 重新组织 batch

它提高硬件利用率。

同时也引入：

  • 请求间干扰
  • 排队变化
  • 长短请求公平性
  • prefill 对 decode 的阻塞
  • 尾延迟

5. chunked prefill

长 Prompt 的 prefill 可以拆成多个 chunk，与其他请求的 decode 交错。

它可能改善调度公平性。

但 chunk 大小会在 TTFT、decode 延迟和吞吐之间产生取舍。

测试不能只看单一吞吐峰值。

6. prefill/decode 分离

一些大规模服务会让不同 worker 分别承担 prefill 和 decode。

此时新增观察点：

  • KV cache 传输
  • 路由
  • worker 间网络
  • cache 格式
  • 失败恢复

如果只记录总延迟，就看不到 KV 传输成为瓶颈。

十三、停止条件：结束不只由 EOS 决定

生成循环必须在某个条件下结束。

常见停止条件包括：

  • 生成 EOS token
  • 达到 max_new_tokens
  • 达到总上下文上限
  • 命中 stop token ID
  • 解码文本命中 stop string
  • grammar 或 schema 完成
  • tool call 结构完成
  • 安全策略中止
  • 服务超时
  • 客户端取消
  • 资源或调度错误

1. EOS token

EOS 是词表中的特殊 token。

模型可能生成它。

服务也可能有多个结束 token。

2. 长度停止

需要区分：

  • max_length：总长度概念
  • max_new_tokens：新增输出长度概念

不同 API 命名和优先级可能不同。

测试必须根据实际接口验证。

3. stop string

stop string 是文本级条件。

它可能跨越多个 token。

还可能跨越多个流式 chunk。

实现不能只检查当前 chunk。

通常需要保留足够的尾部缓冲。

4. 停止文本是否包含在输出中

不同服务可能：

  • 删除 stop string
  • 保留 stop string
  • 返回到前一个 token 边界
  • 因 tokenizer 边界产生部分文本

必须用契约测试固定行为。

5. finish reason

返回结果应尽量区分：

  • stop
  • length
  • tool_call
  • content_filter
  • cancelled
  • timeout
  • error

不要把所有非完整结果都写成 success。

十四、Detokenization：token piece 需要重新组成可读文本

采样得到 token ID 后，decoder 把它还原为文本片段。

这个过程可能处理：

  • 子词连接
  • 空白标记
  • byte-level 字节
  • Unicode
  • 特殊 token 过滤

1. 一个 token 不一定立刻形成完整字符

byte-level tokenizer 可能让一个 Unicode 字符跨多个 token 或字节片段。

返回层必须正确缓冲。

否则流式输出可能出现替换字符或乱码。

2. 每次全量解码与增量解码

实现可能：

  • 每步重新解码完整序列
  • 维护增量 decoder 状态
  • 对特殊边界做额外清理

它们在性能和边界行为上不同。

3. 后处理风险

常见后处理包括：

  • 去除特殊 token
  • trim 空白
  • JSON 修复
  • Markdown 清理
  • 敏感信息过滤
  • 引用重写

后处理可能破坏模型原始输出。

测试证据最好同时保存：

  • raw token IDs
  • raw decoded text
  • postprocessed text

托管 API 无法获取 raw token 时，至少保留原始响应 chunk。

十五、流式返回：一个 chunk 不等于一个 token

许多 API 使用 Server-Sent Events 或类似机制返回增量结果。

测试人员最容易误判：

“收到一个 data chunk，就代表模型生成了一个 token。”

这通常不成立。

1. chunk 可能包含什么

一个 chunk 可能包含：

  • 角色信息
  • 空 delta
  • 一个 token 对应文本
  • 多个 token 合并文本
  • tool call 的部分参数
  • finish reason
  • usage
  • keepalive
  • done 标记

2. token 边界、字符边界和网络边界不同

三个边界不能混为一谈：

  • tokenizer token 边界
  • Unicode 字符边界
  • TCP 或 HTTP chunk 边界

流式解析器必须按协议组帧，而不是按 socket read 次数解析业务对象。

3. SSE 的基本注意点

如果使用 SSE，需要处理：

  • 多行 data 字段
  • 空行分隔事件
  • comment 或 keepalive
  • UTF-8 增量解码
  • done 标记
  • 中途断连
  • 重连是否允许
  • 最终 usage 是否单独返回

4. 首字节不等于首个有效 token

连接可能先收到：

  • HTTP header
  • keepalive
  • 空 delta
  • role chunk

因此性能指标要区分：

  • TTFB：首字节时间
  • TTFT：首个有效输出 token 或内容时间

不同工具的定义可能不同。

比较数据前必须统一口径。

5. 取消请求

客户端断开后，服务端应尽快：

  • 取消调度
  • 释放 KV cache
  • 停止计费或记录实际用量
  • 标记 cancelled
  • 保留必要审计

如果只关闭网络连接但推理继续，会浪费容量。

取消测试要同时检查服务端资源。

十六、性能指标：把“模型很慢”拆成可定位时间线

定义以下时间点：

  • t_0：客户端发出请求
  • t_a：服务端接受请求
  • t_q：进入推理队列
  • t_p：开始 prefill

二十、示例案例：首 token 变慢并且拒答率下降，为什么不一定是模型升级

下面是一个用于说明定位过程的示例案例，不是对真实项目经历的陈述。

1. 场景

团队把日志问答服务从版本 A 升级到版本 B。

观察到：

  • P95 TTFT 从 700ms 上升到 1.4s
  • UNKNOWN 拒答率从 18% 降到 3%
  • 人工感觉回答更“积极”
  • 最终答案事实错误增加

团队最初认为：

  • 新模型计算更慢
  • 新模型更愿意回答

2. 先看版本组合

审计记录显示本次同时变化了：

  • 模型权重
  • tokenizer
  • chat template
  • RAG 文档数量
  • 默认最大历史轮数

这不是单变量模型升级。

3. 看 token 和截断

版本 A：

  • system 与策略：420 token
  • 历史：600 token
  • 检索：1400 token
  • 用户问题：80 token
  • 总输入：2500 token

版本 B：

  • system 与策略：510 token
  • 历史：1500 token
  • 检索：3600 token
  • 用户问题：90 token
  • 总输入：5700 token

TTFT 上升首先与输入长度增长一致。

4. 看模板和截断策略

版本 B 的模板新增了工具说明。

服务仍使用固定上下文预算。

超限后执行左截断。

结果：

  • system prompt 开头的“证据不足返回 UNKNOWN”被部分删除
  • 更多检索文档进入输入
  • 模型因此更少拒答
  • 但没有证据时也更容易猜测

5. 看 trace

阶段指标显示：

  • queue time 基本不变
  • retrieval time 增加
  • prefill time 显著增加
  • decode ITL 基本不变

所以“整个模型都变慢”不准确。

主要变化在检索输入和 prefill。

6. 修复

团队按以下顺序修复：

  1. 将安全和任务约束放入不可静默截断区
  2. 对历史会话先摘要再拼装
  3. 限制检索 token 预算
  4. 记录每一类上下文 token 数
  5. 增加截断事件
  6. 将 UNKNOWN 和无证据猜测加入分项门禁
  7. 在相同模板与相同 token 预算下重新比较模型 A、B

7. 案例结论

最终现象同时涉及：

  • 上下文编排
  • tokenization
  • 截断
  • prefill 性能
  • 行为安全约束

如果只比较最终文本和总延迟，就会把系统变更错误归因给模型权重。

二十一、常见误区

1. 一个 token 就是一个汉字或一个英文单词

错误。

token 边界由 tokenizer 决定。

预算和成本必须使用真实 tokenizer 或服务 usage。

2. temperature 为 0 就能保证永远完全一致

错误。

它通常减少采样随机性。

但版本、数值精度、执行路径和服务默认值仍可能改变结果。

3. KV cache 保存的是完整 Prompt 文本

错误。

它通常保存各层 attention 需要的 Key 和 Value 张量。

原始文本应由应用或证据系统另行管理。

4. 使用 KV cache 后 attention 不再看历史

错误。

新 Query 仍然要关注历史 K、V。

cache 避免的是重复计算历史 K、V，不是删除历史依赖。

5. context window 越大，模型就能同样可靠地使用每个位置

错误。

接口可接受长度、模型有效利用能力和业务准确率是三个不同问题。

必须做位置和干扰测试。

6. 每个 SSE chunk 就是一个 token

错误。

网络 chunk、SSE event、文本 delta 和 tokenizer token 的边界可能都不同。

7. TTFT 就等于 prefill

错误。

客户端 TTFT 还可能包含网络、网关、排队、预处理和首块回传。

8. tokens/s 可以直接跨模型比较

不完整。

不同 tokenizer 的 token 粒度不同。

跨模型还应比较字符、任务、质量和成本。

9. FlashAttention 把标准 attention 的数学复杂度变成线性

不准确。

FlashAttention 的关键贡献是 IO-aware 的精确 attention 计算，减少高带宽内存访问。

不要把实际加速与数学依赖关系混为一谈。

10. 输出错误一定发生在模型里

错误。

模板、检索、截断、采样、停止、detokenization 和后处理都可能制造最终错误。

11. 模型升级只需要跑答案准确率

错误。

还要测试 tokenizer、模板、性能、缓存、流式协议、成本和安全。

12. 平均延迟足以表示体验

错误。

长尾 TTFT 和 token 间停顿更容易破坏交互体验。

至少看 P50、P95、P99 和最大间隙。

二十三、总结

从客户端看，大模型像一个文本接口。

从系统内部看，它是一条由输入治理、离散表示、张量计算、缓存、采样和协议返回组成的流水线。

对常见自回归 Transformer，可以用两阶段理解核心推理：

  • prefill 并行处理完整 Prompt，建立各层 KV cache，并产生第一个输出 token
  • decode 利用 cache 逐步生成后续 token，直到命中停止条件

在这条链路上，几个最重要的测试结论是：

  • 模型真正看到的是模板化、tokenize 后且可能被截断的输入
  • token 不是字、词或网络 chunk 的固定同义词
  • KV cache 用内存换取历史 K、V 的重复计算
  • logits 还要经过约束和采样才能变成 token
  • 固定 seed 不能替代版本和环境记录
  • TTFT、ITL、端到端延迟必须分开定义
  • 最终错误可能来自模型前、模型内或模型后
  • 所有模型、tokenizer、模板、推理和调度变更都应进入回归

理解这条路径的价值，不是为了在测试报告中加入更多术语。

而是为了把“模型不稳定”拆成可观察、可注入、可比较、可修复的具体阶段。
