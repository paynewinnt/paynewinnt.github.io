AI测试-20-非确定性AI应用怎么做稳定的自动化回归测试

发表于 2026-03-27 分类于 AI测试 本文字数： 13k 阅读时长 ≈ 45 分钟

传统自动化测试默认一个重要前提：

相同代码、相同输入和相同环境，应该得到相同结果。

这个前提让回归测试可以直接使用二元结论：

  • 以前通过，现在失败，通常就是回归
  • 以前失败，现在通过，通常就是修复
  • 连续执行结果不同，通常就是脚本或环境不稳定

AI 应用打破了这个简单模型。

相同 Prompt、相同模型名称、相同检索库，连续调用两次仍可能得到不同措辞、不同工具参数，甚至不同任务结果。

如果系统还包含 RAG、Agent、外部工具和 LLM Judge，随机性会沿调用链逐层放大：

  • 检索结果顺序发生轻微变化
  • 模型选择了不同但都合理的计划
  • 工具响应时间改变了后续分支
  • Judge 对边界样本给出不同评分
  • 并发执行改变了共享环境状态

于是一个看似简单的问题变得很难：

候选版本从 89% 上升到 91%，究竟是真改进，还是一次随机波动？

反过来也一样：

一次关键用例失败，究竟应该阻断发布，还是可以用“模型有随机性”解释掉？

这篇文章不讨论如何让模型绝对确定。

绝对确定通常既做不到，也不是产品真正需要的目标。

本文要解决的是更工程化的问题：

在承认输出具有随机性的前提下，怎样构建一套结果稳定、结论可解释、失败可复现的自动化回归体系。

前面的文章已经讨论过 AI 测试平台分层、状态管理、证据链以及误判治理。

本文只聚焦回归判定本身，重点包括：

  • 随机性来自哪里
  • 为什么必须重复运行
  • 通过率怎样配合置信区间解释
  • 为什么候选版本要和基线做 paired comparison
  • 分层门禁怎样兼顾速度与可信度
  • 基线应该冻结什么
  • 噪声预算与 flaky eval 怎样治理
  • 一次结论需要保存哪些可复现证据

一、先划清问题边界：我们要稳定的是“决策”，不是“每个字”

讨论非确定性回归前，必须先区分三个层次。

1. 文本不一致不等于任务失败

下面两个回答措辞不同：

如果业务目标是“正确取消订单并说明退款路径”，两个回答可能都通过。

对全文做精确字符串比较，只会把自然语言的正常变化误报成回归。

因此回归对象应优先是：

  • 最终业务状态
  • 必须满足的事实
  • 不允许出现的风险
  • 工具调用与副作用
  • 可接受的质量区间

而不是表面措辞。

2. 输出可变不等于行为可以失控

模型可以用不同方式表达同一个结论。

但下面这些约束不应该靠概率解释：

  • JSON 必须满足 Schema
  • 不得调用未授权工具
  • 不得泄漏敏感字段
  • 退款金额必须与订单一致
  • 只读任务不得产生写操作
  • 工具失败后不得编造成功结果

这些是硬约束。

只要一次违反，就应该形成明确失败证据。

不能因为总体通过率仍然很高，就把安全、权限和数据完整性问题平均掉。

3. 自动化结果稳定不等于线上质量一定稳定

离线回归只能覆盖评测集代表的分布。

它不能自动证明：

  • 真实用户输入没有分布漂移
  • 外部知识库始终及时更新
  • 线上限流和超时不会改变行为
  • 第三方模型服务没有静默变更
  • 用户对答案质量的定义没有变化

所以完整质量闭环至少包含：

  • 离线自动化回归
  • 灰度或影子流量
  • 线上指标与失败采样
  • 用户反馈和人工复核

本文主要讲第一项，但会说明它怎样与后面三项衔接。

二、把 AI 回归重新定义成一个统计决策问题

传统单元测试常把一次执行当成事实。

非确定性 AI 回归更接近一次受控实验。

设：

  • C 表示固定的用例集合
  • B 表示基线系统
  • N 表示候选系统
  • Y(i, r, v) 表示系统版本 v 在用例 i 第 r 次试验的结果

我们真正关心的通常不是某一个 Y，而是：

也就是在声明好的条件下，系统完成任务的概率。

候选版本的回归判定可以进一步写成：

然后根据业务风险预先选择一种假设：

  • 优越性：候选必须显著优于基线
  • 非劣性：候选允许轻微波动，但不能差过容忍边界
  • 等效性：候选与基线差异必须落在上下两个等效边界内

大多数模型、Prompt 或检索策略升级更适合使用非劣性思路。

因为升级可能主要为了：

  • 降低时延
  • 降低 Token 成本
  • 修复某一类风险
  • 增加新能力

只要求“平均分必须严格更高”会阻止很多有价值的工程改进。

更合理的发布问题是：

在关键能力不退化、整体质量不低于容忍边界的前提下，候选版本是否带来了目标收益？

非劣边界必须在运行前确定

设业务允许的最大退化为 m：

如果 m = 0.02，表示候选最多允许下降 2 个百分点。

这个数不能看完结果再决定。

否则团队很容易根据结果临时移动门槛：

  • 下降 1.8% 时说 2% 可以接受
  • 下降 2.4% 时又说 3% 也不明显
  • 关键用例失败时再把它改成普通用例

预先声明的边界，才是门禁。

事后解释的边界，只是为结果找理由。

三、随机性到底来自哪里

把所有波动都归因于 temperature，是最常见也最危险的简化。

真实 AI 应用至少有六层随机性。

1. 模型生成层

常见因素包括：

  • temperature
  • top_p
  • top_k
  • 候选采样
  • 服务端动态批处理
  • 浮点计算和并行归约差异
  • 模型服务内部路由
  • 未公开的服务端修订

即使设置 temperature 为 0，也不应直接承诺逐字节复现。

原因可能包括：

  • 多个 Token 的概率非常接近
  • 后端计算路径发生变化
  • 服务商更新了权重、推理栈或安全策略
  • 请求被路由到不同硬件或模型快照

seed 如果接口支持，可以帮助降低变化。

但 seed 更适合视为“可复现提示”，不是跨时间、跨后端的绝对保证。

2. Prompt 与上下文组装层

系统 Prompt 看似没变，最终输入仍可能变化：

  • 时间、地域和用户状态被动态注入
  • 历史会话截断位置变化
  • Few-shot 样本顺序变化
  • 字典或集合遍历顺序不稳定
  • 模板依赖项被独立更新
  • Token 超限后采用了不同压缩结果

所以只记录一个 Prompt 文件名不够。

必须同时记录：

  • 模板身份
  • 模板版本
  • 渲染后内容摘要
  • 上下文选择策略
  • 截断与压缩参数

3. RAG 检索层

RAG 的随机性和漂移来自：

  • 文档集合发生变化
  • Chunk 切分策略变化
  • Embedding 模型变化
  • 索引重建
  • 近似最近邻搜索
  • 同分文档排序不稳定
  • 过滤条件依赖动态权限
  • Reranker 版本变化

两个请求即使查询文本相同，也可能拿到不同证据。

模型输出变化可能只是检索输入变化的结果。

如果回归记录里没有保留文档 ID、版本、排名和分数，就无法分清：

  • 是生成模型退化
  • 是检索召回退化
  • 是知识本身发生了变化

4. Agent 规划与工具层

Agent 通常不是一次生成，而是一个多步闭环：

任一步差异都可能改变后续轨迹。

常见变量包括：

  • 工具返回顺序
  • 网络抖动和超时
  • 重试次数
  • 外部状态变化
  • 工具 Schema 变化
  • 幂等键缺失
  • 并发任务争用同一资源

因此 Agent 回归不能只保存最终答案。

至少还要保存：

  • 每一步选择
  • 工具参数
  • 工具结果
  • 状态变更
  • 重试和异常
  • 最终环境状态

5. Judge 与评分层

如果用另一个模型做裁判，评测系统本身也具有随机性。

Judge 的变化可能来自：

  • 评分 Prompt 变化
  • Rubric 边界不清
  • Judge 模型变化
  • 输出解析失败
  • 样本顺序偏差
  • 位置偏差
  • 对长答案的注意力偏差

这意味着评测分数不是天然真值。

Judge 必须像被测系统一样：

  • 版本化
  • 回归测试
  • 与人工标注校准
  • 监控分歧率
  • 保存评分证据

6. 评测基础设施层

最后一层噪声来自测试系统：

  • 共享环境不干净
  • Mock 数据随时间变化
  • 并发任务相互污染
  • 队列超时
  • 账号额度不足
  • 日志或产物丢失
  • 测试 Harness 自己升级

如果不把这类失败单独识别，团队会得到两个错误结论：

  • 把平台故障当成模型回归
  • 把模型失败当成平台偶发问题

四、整体策略图：从单次结果转向分层证据

这张图表达四个关键原则。

第一，先冻结比较合同，再运行任务。

第二，基线和候选应尽量在相同任务、相同试验槽位和相同时间窗口中比较。

第三，硬约束与统计质量分开判定。

第四，回归结论必须能下钻到原始输入、调用轨迹和评分证据。

这四点缺一不可。

只有重复运行，没有冻结合同，得到的是不可解释的重复。

只有平均通过率，没有关键风险门禁，得到的是被平均数掩盖的事故。

只有统计结论，没有证据归档，得到的是无法定位和复现的数字。

五、先建立“可复现合同”

非确定性系统做不到保证输出完全一致。

但可以保证比较条件被明确记录。

这就是可复现合同。

一份最小合同至少包含下面六组信息。

1. 被测系统版本

  • 应用提交 SHA
  • Prompt 模板 ID 与版本
  • Prompt 渲染器版本
  • 模型请求名称
  • 可获得时记录解析后的模型或快照标识
  • 采样参数
  • 工具集合版本
  • Agent Harness 版本
  • 安全策略版本

2. 数据与检索版本

  • eval suite ID
  • dataset revision
  • case ID
  • 输入内容摘要
  • 知识库 snapshot
  • Chunker 版本
  • Embedding 模型标识
  • 索引构建版本
  • Reranker 版本
  • 过滤策略版本

3. Judge 版本

  • grader ID
  • Rubric 版本
  • Judge Prompt 摘要
  • Judge 模型标识
  • 解析器版本
  • 校准集版本
  • 人工复核策略

4. 执行环境

  • 环境 ID
  • 区域
  • 依赖服务版本
  • 固定时钟或时间窗口
  • 账号与权限角色
  • 并发配置
  • 超时与重试策略
  • Feature Flag 快照

5. 随机控制

  • seed，如果接口支持
  • trial_slot
  • 执行顺序
  • baseline 与 candidate 的交替策略
  • 重试是否计入试验
  • 模型服务返回的请求 ID

6. 证据完整性

  • 原始响应摘要
  • 工具调用轨迹
  • 最终状态快照
  • 评分明细
  • Artifact URI
  • Artifact 内容摘要
  • 生成时间
  • 保留策略

六、冻结基线到底要冻结什么

“冻结基线”经常被误解成保存一个总分。

总分远远不够。

真正需要冻结的是一个可审计的基线包。

基线包的最小内容

  • 用例输入与分层标签
  • 每个用例的期望约束
  • 基线系统版本清单
  • 每个 trial 的原始结果
  • 判废记录
  • 确定性断言结果
  • Judge 评分明细
  • 聚合算法版本
  • 置信区间算法与参数
  • 通过门槛和非劣边界
  • 全部 Artifact 摘要

冻结输出不等于永远不重跑基线

这里需要区分两种基线。

1. 历史制品基线

历史制品基线用于回答：

  • 上一个发布版本当时表现如何
  • 当时使用了什么数据和规则
  • 为什么当时允许发布
  • 当前结果与历史趋势是否一致

它必须不可变。

2. 同期控制基线

同期控制基线用于回答：

  • 在今天的外部环境下，旧版本和新版本谁更好
  • 第三方模型服务或知识依赖是否共同漂移
  • 当前时间窗口是否存在系统性噪声

它需要与候选版本在同一时间窗口重跑。

当上游模型是可变的托管服务时，只拿今天的候选结果与三个月前的基线分数比较，会把时间漂移混入版本差异。

更稳妥的做法是同时保留：

  • 不可变的历史基线包
  • 本次实验重跑的同期控制组

交替执行减少时间偏差

如果一次运行持续数小时，不要先跑完全部基线，再跑全部候选。

服务负载、知识库和网络状态可能随时间改变。

目标是让两个版本承受尽量相似的外部条件。

七、为什么必须重复运行

一次运行只能观察一个样本。

它无法告诉我们：

  • 通过是稳定能力还是偶然命中
  • 失败是稳定缺陷还是低概率波动
  • 候选版本的方差是否变大
  • Judge 是否在边界样本上反复翻转

假设一个任务真实成功概率是 0.8。

一次执行仍有 20% 概率失败。

如果只跑一次：

  • 失败会让团队误以为能力为 0
  • 通过又会让团队误以为能力为 1

两个结论都过度自信。

重复次数不能一刀切

试验次数应由四个因素决定：

  • 需要识别的最小质量变化
  • 当前结果方差
  • 可接受的误判风险
  • 成本与反馈时间

工程上可以采用分层预算：

  • 提交级：核心用例每个 1 次
  • 合并级：高风险用例每个 1 到 3 次
  • 夜间级：分层用例每个 5 到 20 次
  • 发布级：根据历史方差做功效或精度预算

这里的数字只是运行层级示例，不是通用标准。

真正的次数应根据本系统历史数据计算。

自适应重复比固定重复更省成本

可以先运行较少次数，再根据结果决定是否追加：

  1. 先运行 3 次
  2. 如果全通过且历史稳定，进入下一用例
  3. 如果结果翻转或靠近门槛，追加到 8 次
  4. 如果区间仍跨过门槛，追加到预设上限
  5. 达到上限仍不确定，结论标记为 inconclusive

关键约束是：

  • 追加规则必须预先声明
  • 不能只对候选失败追加，直到它通过
  • baseline 与 candidate 要使用对称规则
  • 多次查看结果会影响传统显著性解释

如果需要严格的序贯统计，应使用专门的序贯检验方法。

简单平台至少要避免“失败就一直重跑”的选择性停止。

八、通过率必须和置信区间一起报告

设一共运行 n 次，其中 x 次通过。

样本通过率是：

如果 10 次通过 9 次，p_hat = 90%。

如果 1000 次通过 900 次，仍然是 90%。

但两者可信程度完全不同。

因此报告不能只写 90%，还要写区间。

为什么不优先使用简单正态区间

常见的简单区间是：

它在样本较少或通过率接近 0、1 时可能表现较差，甚至给出小于 0 或大于 1 的边界。

二元结果更适合优先使用 Wilson score interval。

Wilson 区间

令 z 为置信水平对应的标准正态分位数。

95% 置信水平通常使用约 1.96。

例如 10 次通过 9 次，95% Wilson 区间仍然会比较宽。

这提醒我们：

90% 只是点估计，不代表已经精确知道真实通过概率。

正确解释置信区间

频率学派的 95% 置信区间，不应被简单解释为：

“真实通过率有 95% 概率落在这个已计算出的区间里。”

更准确的工程表达是：

如果按同样方法反复抽样并构造区间，长期看约 95% 的区间会覆盖真实参数。

博客和测试报告不必展开统计哲学。

但至少要避免把区间当成模型质量的概率承诺。

Wilson 区间也有前提

它把观测近似看成独立同分布的 Bernoulli 试验。

AI 回归里经常存在聚类：

  • 同一个 case 重复 10 次
  • 同一用户下有多个相似输入
  • 同一文档派生出多个问题
  • 同一故障簇有大量样本

把这些记录全部当成完全独立，会让区间过窄。

因此 Wilson 区间适合作为：

  • 单一同质层的诊断
  • 快速展示二元比例不确定性

跨任务总门禁更建议同时使用：

  • 以 case 为单位的 paired bootstrap
  • 分层 bootstrap
  • 聚类稳健方法

九、先按任务聚合，再跨任务汇总

假设：

  • case A 重复 20 次
  • case B 重复 2 次

直接把 22 次试验放在一起计算 micro pass rate，case A 的权重会是 case B 的 10 倍。

这不一定符合业务价值。

更合理的计算顺序通常是：

  1. 先计算每个 case 的通过率
  2. 再按业务权重聚合 case

micro 与 macro 都应保留

micro pass rate 回答：

所有物理试验中，有多少比例通过？

macro quality 回答：

把每个任务视为质量单位，平均完成能力如何？

两者可能差异很大。

如果高频重复的简单任务全部通过，micro 很高。

但少量关键复杂任务持续失败，macro 或关键层指标会更差。

因此报告至少要包含：

  • 总体 micro
  • case-level macro
  • 分层 macro
  • critical case 明细
  • 每个 case 的重复结果分布

分层不能只在报告里展示

评测集通常应提前定义层：

  • 业务域
  • 风险等级
  • 输入难度
  • 是否调用工具
  • 是否依赖检索
  • 单轮或多轮
  • 新鲜样本或历史失败样本

门禁也应按层执行。

否则某一大类简单样本可以掩盖小类关键回归。

十、paired comparison：比较同一批任务上的变化

如果基线和候选使用不同任务集合，差异会混入任务难度。

最简单的控制方式是配对：

  • 同一个 case
  • 同一个数据快照
  • 同一个 grader
  • 同一个 trial_slot
  • 尽量接近的执行时间

然后先在配对内计算差值。

二元结果的配对矩阵

对每一对二元结果，可以形成四格表：

基线 候选 含义
通过 通过 共同通过
通过 失败 回退，记为 b
失败 通过 改进，记为 c
失败 失败 共同失败

McNemar 检验关注的是不一致对 b 与 c。

直觉上：

  • 如果 b 与 c 接近，变化方向没有明显倾向
  • 如果 c 明显多于 b，候选更可能改进
  • 如果 b 明显多于 c，候选更可能回退

在不一致对较少时，应考虑精确二项版本，而不是只依赖大样本卡方近似。

不要只看 p-value

p-value 回答的是在特定零假设下，数据有多异常。

它不直接回答：

  • 回退是否达到业务不可接受程度
  • 改进是否值得增加成本
  • 关键用例是否可以失败
  • 区间是否足够窄

所以发布门禁更适合组合：

  • 预先声明的非劣边界
  • 配对差值区间
  • critical case 硬门禁
  • 成本和时延约束
  • McNemar 或其他统计诊断

配对不等于共享随机数

很多托管模型无法让基线和候选真正使用同一随机流。

即使都传同一个 seed，也不能假设它们得到了严格相同的随机扰动。

这里的 pairing 主要控制：

  • 任务组成
  • 数据快照
  • Judge
  • 执行时间
  • 环境状态

它仍然比两组完全独立抽样更有解释力。

十一、pass@k 不能随便当成生产成功率

当一个任务运行 k 次，只要至少一次成功就算通过，得到的是 pass@k 类指标。

如果每次独立且单次成功概率为 p：

这个数会随着 k 增大而上升。

因此 pass@k 适用于：

  • 产品确实会生成 k 个候选并选择
  • 产品确实允许最多 k 次重试
  • 用户可以从 k 个结果中挑选

它不适用于：

  • 线上只调用一次
  • 测试失败后人工挑一个最好结果
  • 为了让报表好看而增加重跑次数

还要区分“至少一次成功”和“持续稳定”

如果关心连续 k 次全部成功，在独立假设下是：

两者回答完全不同的问题。

例如单次成功率 0.8：

  • 至少一次成功会随重试快速提升
  • 连续全部成功会随次数快速下降

测试报告必须明确指标语义。

不要只写一个含糊的 “pass@5 = 95%”。

还要说明：

  • 五次是否都对用户可用
  • 谁负责选择成功结果
  • 重试成本是否计入
  • 重试是否产生副作用

十二、噪声预算：先证明评测系统值得信任

噪声预算不是允许模型随便失败。

它约束的是评测过程自身的健康度。

可以至少监控三类噪声。

1. invalid trial rate

判废试验比例：

合法判废原因应预先列举，例如：

  • 测试环境整体不可用
  • 必需的 Mock 服务未启动
  • 观测产物写入失败，无法评分
  • 基线和候选没有获得同一数据快照

下面这些通常不能直接判废：

  • 模型超时
  • 工具参数错误
  • 产品重试耗尽
  • 输出不满足 Schema

因为它们可能就是被测系统的失败。

2. outcome flip rate

在完全相同声明配置下，同一 case 的结果反复翻转，说明它是 flaky eval 或被测能力不稳定。

如果某 case 有 n 次试验，其中 x 次通过，所有无序试验对中的结果分歧率是：

当全通过或全失败时，flip rate 为 0。

当通过与失败接近各半时，flip rate 较高。

注意：

低 flip rate 不代表质量高。

一个稳定失败的用例，flip rate 也是 0。

所以必须同时看：

  • pass rate
  • flip rate

3. judge disagreement rate

在人工校准集上：

对于多级评分，还应监控：

  • 绝对误差
  • 严重分歧率
  • 分层混淆矩阵
  • 不同 Rubric 维度的偏差

噪声超预算时怎么办

正确动作不是提高容忍阈值。

而是：

  1. 将本次回归标记为不可信或 inconclusive
  2. 阻止不可靠结果自动放行
  3. 定位噪声来自环境、Harness、Judge 还是数据
  4. 修复后按同一冻结合同重跑
  5. 保留原始失败运行，不覆盖证据

十三、flaky eval 应当怎样识别和治理

flaky eval 的操作性定义可以是：

在声明的系统版本、输入、数据、评分和环境都未变化时，同一用例的最终判定仍会翻转。

它可能来自被测系统，也可能来自测试系统。

先做归因，不要直接 quarantine

建议按下面顺序排查：

第一步：检查输入是否真的相同

  • 模板摘要是否一致
  • 检索文档是否一致
  • 时间与用户状态是否一致
  • Feature Flag 是否一致
  • 工具 Schema 是否一致

第二步：检查确定性断言

  • JSON 解析是否偶发失败
  • 断言是否依赖无序集合
  • 浮点比较是否没有容差
  • 文本归一化是否不一致
  • Harness 是否存在竞态

第三步：检查 Judge

  • Rubric 是否存在边界歧义
  • Judge 输出是否解析失败
  • 同一答案重复评分是否翻转
  • 位置顺序是否影响比较结果

第四步：检查模型与工具轨迹

  • 是否选了不同计划
  • 哪个工具调用首次产生分叉
  • 工具是否依赖动态外部状态
  • 超时和重试是否改变最终结果

quarantine 不是删除

高噪声用例可以暂时从“阻断式总门禁”移到专门的 flaky suite。

但必须满足：

  • 仍然持续运行
  • 仍然计入质量健康报告
  • 有 owner
  • 有原因分类
  • 有修复期限
  • 不得从历史趋势中静默消失

否则 quarantine 会变成失败样本回收站。

建立 flaky eval SLO

可以按评测套件跟踪：

  • 结果翻转用例占比
  • 无效试验占比
  • Judge 分歧率
  • 无 owner 的 flaky 用例数
  • 超期未修复数
  • 因 flaky 导致的门禁重跑成本

这些指标用于治理评测系统。

不要把它们与产品成功率混成一个分数。

十四、分层门禁：一次提交不需要跑完整统计实验

可信不等于每次都昂贵。

可以把门禁拆成四层。

L0：硬约束门禁

触发时机：

  • 每次提交
  • Prompt 或工具 Schema 变化

覆盖：

  • 输出 Schema
  • 必要字段
  • 权限边界
  • 敏感数据
  • 工具副作用
  • 关键事实

特点：

  • 速度快
  • 尽量确定性
  • 一次违规即可阻断

L1：快速配对回归

触发时机：

  • 合并请求
  • 小范围配置变化

覆盖：

  • 核心业务样本
  • 历史高频失败
  • 关键风险簇
  • 候选与基线配对差
  • 时延和成本粗门槛

特点：

  • 少量 trial
  • 快速反馈
  • 边界结果进入 L2，不自动放行

L2：统计回归

触发时机：

  • 夜间构建
  • 发布候选版
  • 模型或检索重大升级

覆盖：

  • 完整分层样本
  • 每 case 多次试验
  • 配对 bootstrap
  • Wilson 诊断
  • flaky eval 健康度
  • Judge 校准

特点：

  • 输出非劣、改进、回退或不确定
  • 保存完整证据包

L3：线上验证

触发时机：

  • 灰度发布
  • 模型服务迁移
  • 知识库大规模更新

覆盖：

  • 影子流量
  • 真实输入分层
  • 任务完成率
  • 用户结果
  • 线上失败预算
  • 漂移与回滚信号

特点：

  • 不依赖离线评测集假装覆盖所有真实场景
  • 将新失败脱敏后回流到候选样本池

十六、测试设计：回归体系本身也要被测试

一个统计公式正确，不代表平台实现正确。

  • Dataset revision 不为空

  • 两边数据 snapshot 不同

平台应该：

  • 标记缺失配对
  • 保留原始记录
  • 根据预先规则判定失败或 invalid
  • 不得自动删除不完整记录

3. 统计函数单元测试

Wilson 区间至少覆盖：

  • 0/1
  • 1/1
  • 0/n
  • n/n
  • 小样本
  • 大样本

McNemar 至少覆盖：

  • b = 0, c = 0
  • b = c
  • 只有回退
  • 只有改进
  • 不一致对很少

bootstrap 至少覆盖：

  • 单个 case
  • 全部差值为 0
  • 差值正负混合
  • 固定 seed 重复结果一致

4. 门禁边界测试

门槛附近最容易出现比较符号错误。

必须覆盖：

  • 正好等于质量下限
  • 正好等于非劣边界
  • 浮点误差附近
  • invalid rate 正好等于预算
  • critical delta 正好为 0

门禁规范要明确使用：

  • 大于
  • 大于等于
  • 小于
  • 小于等于

不要把这个决定留给实现人员猜。

5. 并发与幂等测试

回归平台常并发执行大量试验。

需要验证：

  • 相同 run ID 重复提交不会重复计数
  • 相同 trial ID 只能产生一个最终态
  • 迟到结果不会覆盖已确认结果
  • 重试有独立 attempt ID
  • 聚合只读取完整快照
  • 任务取消后不会继续写入成功

6. 判废规则测试

为每个 invalid reason 建立合成故障：

  • 环境服务不可达
  • Artifact 存储失败
  • 模型自身超时
  • 工具返回业务错误
  • Judge 解析错误

然后确认只有预先声明的基础设施原因被判废。

尤其要防止把模型超时和产品失败判成 invalid。

7. Judge 稳定性测试

在人工校准集上重复评分：

  • 同一答案重复评分
  • 候选顺序交换
  • 无关措辞扰动
  • 长短答案对比
  • 边界分数样本
  • 明确违规样本

观察：

  • 一致率
  • 位置偏差
  • 严重分歧
  • 各 Rubric 维度偏差

8. 证据可回放测试

随机抽取一个已完成 trial，验证仅依靠证据包能回答：

  • 输入是什么
  • 使用了哪个版本
  • 检索到了什么
  • 调用了哪些工具
  • 最终环境状态是什么
  • 为什么被判为通过或失败
  • 聚合时如何影响门禁

如果只能看到一段最终回答，就不算可回放。

十七、示例案例一：平均分提升，却被关键回退阻断

下面是一个示例案例，只用于说明判定方法，不代表任何真实项目数据。

某客服 Agent 候选版本调整了检索 Prompt。

运行结果：

指标 基线 候选
总体 attempt 通过率 89.2% 91.0%
普通咨询 91.5% 94.1%
政策引用 84.0% 90.2%
退款金额正确性 99.8% 98.7%
平均 Token 2400 2150

只看总体结果，候选更好：

  • 通过率提高
  • Token 降低
  • 政策引用改善

但“退款金额正确性”属于 critical 层。

配对明细发现：

  • 8 个 case 从基线通过变成候选失败
  • 2 个 case 从基线失败变成候选通过
  • 失败集中在优惠券与现金混合支付

进一步查看轨迹：

  • 检索结果正确
  • 模型正确识别原始金额
  • 新 Prompt 要求“用一句话直接给出退款结论”
  • 模型省略了优惠券不可现金退回的约束

正确门禁结论应是：

这不是统计方法失效。

恰恰是分层硬门禁避免了平均值掩盖高风险回退。

十八、示例案例二：候选下降其实来自 Judge 波动

下面同样是一个示例案例。

候选版本的会话礼貌度从 4.42 降到 4.31。

团队最初认为 Prompt 变差。

但复查发现：

  • 确定性任务完成率没有下降
  • 人工抽检差异很小
  • 同一批答案重复送 Judge 三次，边界样本评分频繁变化
  • Judge 模型在运行前一天被替换
  • grader manifest 只记录了模型别名，没有记录可用的修订信息

将原始答案固定后，旧 Judge 和新 Judge 的配对结果显示：

  • 新 Judge 对短回答普遍降低约 0.2 分
  • 基线历史分数来自旧 Judge
  • 候选分数来自新 Judge

所以原比较把“裁判变化”误当成“被测系统变化”。

正确处理是：

  1. 将本次结果标记为不可信
  2. 冻结同一个 Judge 与 Rubric
  3. 同期重跑 baseline 和 candidate
  4. 补充 Judge 版本与校准集字段
  5. 为 Judge 建立独立升级门禁

十九、示例案例三：不断重跑把失败洗成成功

这是第三个示例案例。

某回归平台的规则是：

单次成功概率约为 0.7 时，三次内至少一次成功的理论概率是：

报表看起来接近 97.3%。

但线上产品并没有自动重试。

真实用户只得到一次调用。

这套回归把“测试系统允许三次挑最好结果”误当成“产品单次成功率”。

修复方式：

  • 所有 attempt 独立留证
  • 首次成功率作为主门禁
  • 重试后成功率作为辅助指标
  • 明确重试时延与 Token 成本
  • 只有线上同样具备重试策略时，才把最终成功率当业务指标

二十、可复现证据：复现条件，不强求复现每个 Token

对非确定性系统，“复现”应该分成三层。

1. 条件复现

能够恢复：

  • 输入
  • 系统版本
  • 数据快照
  • 采样参数
  • 工具版本
  • Judge 版本
  • 执行策略

这是最低要求。

2. 轨迹回放

不重新调用外部系统，直接查看：

  • 渲染后的 Prompt
  • 检索文档
  • 模型原始响应
  • 工具请求与响应
  • 状态变更
  • Judge 评分

它用于解释“当时为什么得到这个结论”。

3. 再执行

使用同一合同重新运行。

结果不一定逐字相同，但应能判断：

  • 是否落在历史分布内
  • 同一失败是否高概率重现
  • 修复是否改变失败方向
  • Judge 是否仍然给出相同结论

证据包建议结构

每个文件应有内容摘要。

JSON 如果用于签名或跨系统一致摘要，需要定义规范化方式。

不能假设普通 JSON 序列化天然具有稳定字节表示。

可以参考 RFC 8785 的 JSON Canonicalization Scheme。

证据保存还要考虑隐私

完整 Prompt 和工具结果可能包含：

  • 用户身份
  • 订单数据
  • 内部文档
  • 访问令牌
  • 商业敏感信息

因此证据链不等于无限制记录原文。

至少要实现：

  • 采集前字段分类
  • 默认脱敏
  • 密钥与 Token 禁止入库
  • 内容与元数据分库存储
  • 最小权限
  • 保留期限
  • 删除与审计

调用链的隐私设计会在下一篇文章展开。

二十一、从失败结果到可执行归因

一个回归失败至少要落到下面某个责任域。

PRODUCT

  • Prompt 逻辑错误
  • 模型能力不足
  • RAG 召回错误
  • 工具选择错误
  • 产品重试失败

EVAL_DATA

  • 期望过期
  • 样本歧义
  • 标签错误
  • 业务规则变更未同步

GRADER

  • Rubric 不清
  • Judge 翻转
  • 解析器错误
  • 位置偏差

INFRA

  • 环境不可用
  • Artifact 丢失
  • 调度器故障
  • 共享状态污染

UNKNOWN

  • 证据不足
  • 暂时无法定位

UNKNOWN 不能被当成普通失败长期堆积。

它反映的是可观测性缺口。

团队应跟踪：

  • UNKNOWN 占比
  • 平均归因时间
  • 重复 UNKNOWN 模式
  • 因证据缺失无法判定的发布次数

二十二、报告应该怎样展示

一份面向发布决策的报告，建议按下面顺序展示。

第一屏：结论

  • PASS / BLOCK / INCONCLUSIVE
  • 阻断原因
  • 比较合同摘要
  • 主指标与非劣边界
  • critical 回退数
  • 噪声预算状态

第二屏：质量差异

  • baseline 与 candidate 点估计
  • 配对差值区间
  • 分层差异
  • 改进与回退 case 数
  • 成本和时延变化

第三屏：稳定性

  • 每 case 通过率
  • flip rate
  • invalid rate
  • Judge 分歧
  • 历史趋势

第四屏：证据

  • 回退 case 列表
  • 第一次分叉位置
  • Prompt / retrieval / tool / output 差异
  • Artifact 链接
  • owner 与处置状态

不要只给一个总分

总分适合排序。

它不适合单独承担发布决策。

一个 92.3 分无法告诉读者：

  • 是哪类任务变差
  • 区间有多宽
  • 是否存在权限违规
  • Judge 是否稳定
  • 结果能否复现

二十三、常见误区

误区 1：temperature 设为 0 就可以只跑一次

temperature 为 0 可以降低一部分生成随机性。

它不能冻结：

  • 模型服务实现
  • RAG
  • 工具
  • 环境
  • Judge

仍然需要版本记录和风险分层。

误区 2：设置 seed 就能跨时间完全复现

seed 只能在提供方承诺的边界内使用。

模型、后端和参数变化后，不应假设相同 seed 得到相同输出。

误区 3：候选通过率高于基线就可以发布

点估计可能来自噪声。

还要看：

  • 配对差值
  • 置信区间
  • 关键层
  • 成本
  • 时延
  • 风险违规

误区 4：样本越多越好

大量重复、同质、低价值样本会制造虚假的精确度。

样本需要：

  • 覆盖真实分布
  • 覆盖高风险尾部
  • 去重
  • 分层
  • 版本化

误区 5：失败重跑通过后就算通过

这会隐藏真实单次失败率。

除非线上产品也有完全相同的重试与选择策略。

误区 6：flaky 用例移出门禁就解决了

移出主门禁只是暂时隔离。

没有 owner、期限和持续运行，问题只会被隐藏。

误区 7：p-value 小就表示改进很大

统计显著不等于业务重要。

样本足够大时，很小差异也可能得到很小的 p-value。

仍要检查效果量和业务边界。

误区 8：置信区间跨 0 就等于两个版本完全一样

它通常只表示当前数据不足以排除某些差异。

可能是：

  • 真差异很小
  • 样本太少
  • 方差太大
  • 配对设计不佳

正确结论可能是 inconclusive，而不是“完全相同”。

误区 9：Judge 给出的数字就是客观真值

Judge 是测量工具。

测量工具也需要校准、版本化和误差监控。

误区 10：保存最终答案就足够复现

没有 Prompt、检索、工具和评分轨迹，只能看到症状。

无法解释第一次分叉发生在哪里。

二十四、落地检查表

回归合同

  • 是否冻结 dataset revision
  • 是否记录 Prompt 模板与渲染摘要
  • 是否记录模型名称、可用修订和采样参数
  • 是否记录 RAG 全链路版本
  • 是否记录工具与 Agent Harness 版本
  • 是否冻结 Judge、Rubric 与校准集
  • 是否记录执行环境、并发、超时和重试策略

试验设计

  • baseline 与 candidate 是否使用同一批 case
  • 是否采用 trial_slot 配对
  • 是否交替或随机区组执行
  • 重复次数是否与风险和历史方差匹配
  • 是否避免只对失败结果选择性重跑
  • 是否预先声明追加试验规则

指标

  • 是否同时报告点估计和区间
  • 是否区分 micro 与 macro
  • 是否按风险和业务域分层
  • 是否使用 case 级配对差
  • 是否预先声明非劣边界
  • 是否分开报告首次与重试后成功率

噪声治理

  • invalid reason 是否预先定义
  • 是否避免把产品超时判成环境无效
  • 是否监控 flip rate
  • 是否监控 Judge 分歧
  • flaky eval 是否有 owner 和期限
  • 噪声超预算时是否返回 inconclusive 或 block

风险门禁

  • 权限和安全违规是否一次即阻断
  • critical case 是否独立门禁
  • 总体平均分是否无法掩盖关键回退
  • 时延和成本是否与质量一起评估
  • 是否有明确回滚条件

证据

  • 是否保存每个物理 attempt
  • 是否保存渲染 Prompt 与摘要
  • 是否保存检索文档身份与顺序
  • 是否保存工具参数、结果与副作用
  • 是否保存最终环境状态
  • 是否保存 Judge 评分明细
  • Artifact 是否有摘要、权限和保留策略
  • 是否可以从门禁结论下钻到单个 trial

二十五、总结

非确定性 AI 应用并不意味着自动化回归失效。

它意味着回归测试需要从“一次执行给一个布尔值”升级为“受控比较给一个带证据的决策”。

一套可信方案至少需要：

  1. 冻结系统、数据、Judge 和环境构成的比较合同
  2. 在同一 case 和 trial_slot 上配对 baseline 与 candidate
  3. 通过重复试验估计能力与波动
  4. 同时报告通过率、置信区间和 case 级差值
  5. 用分层硬门禁保护关键风险
  6. 用噪声预算约束 Harness、环境和 Judge
  7. 把 flaky eval 当成评测系统缺陷持续治理
  8. 保存足以解释和回放每次结论的证据

最终应该追求的不是：

每次都生成完全相同的答案。

而是：

在相同、可审计的条件下，系统质量落在可接受范围；当它偏离时，门禁能稳定发现，证据能解释原因，团队能重复验证修复。

这才是非确定性系统真正可依赖的自动化回归。
