AI测试-18-RAG系统怎么评测召回率忠实度和答案可追溯性

发表于 2026-03-24 分类于 AI测试 本文字数： 11k 阅读时长 ≈ 42 分钟

RAG 系统上线后，团队最常见的评测方式是准备几十个问题，然后让人看答案“像不像对的”。

这种方式可以发现明显问题，却很难支持持续回归。

因为一个错误答案背后至少可能有五种原因：

  • 正确资料根本不在知识库里
  • 资料在库里，但检索器没有找到
  • 检索找到了，但重排或上下文截断把它丢掉了
  • 正确证据已经进入上下文，但生成模型没有遵循
  • 答案本身正确，但引用绑定到了错误来源

如果评测只输出一个“答案得分”，这五种原因会被压成同一个数字。

数字降低时，团队只能反复尝试：

  • 换 Embedding 模型
  • 调大 top_k
  • 修改 Prompt
  • 换一个生成模型
  • 增加上下文窗口

其中一些改动甚至会让系统更差。

例如盲目增大 top_k，可能提高检索召回，却同时引入重复、冲突和过期资料，降低上下文精度与生成忠实度。

所以，RAG 评测的核心不是找到一个万能指标，而是建立一条可以定位责任层的证据链：

语料是否具备答案 → 检索是否找到证据 → 上下文是否保留证据 → 生成是否忠于证据 → 引用是否准确覆盖关键陈述。

上一篇 AI测试-07-RAG+测试知识库怎么做数据清洗召回和结果校验 已经讨论了数据清洗、召回链路和结果校验。

本文不重复知识库建设过程，只回答更窄、也更难的问题：

如何把 RAG 的检索与生成分开评测，如何定义 Recall@k、MRR、nDCG、context precision/recall、faithfulness、answer relevance、citation correctness/completeness，以及如何从端到端失败反推责任层。

一、问题边界：本文评测的不是“模型聪不聪明”

1. 先定义被测系统

本文所说的 RAG 系统至少包含下面几个阶段：

不同系统可能省略某些阶段，也可能增加路由、缓存、多跳检索或工具调用。

但只要最终答案依赖外部知识，就应该至少区分：

  • 检索输出：召回了哪些文档或分片，顺序如何
  • 最终上下文：真正发送给生成模型的内容是什么
  • 模型回答：产生了哪些可验证陈述
  • 引用结果：每条陈述绑定了哪些来源

如果平台只保存最终答案，后面的评测只能做结果抽检，无法做工程归因。

2. 本文不解决什么

本文不试图解决以下问题：

  • 通用大模型排行榜如何设计
  • 如何训练 Embedding 或重排模型
  • 如何决定具体供应商和模型版本
  • 如何用一个分数替代全部人工判断
  • 如何证明模型在所有未来输入上都不会幻觉

评测给出的不是绝对安全证明。

它提供的是：

  • 在明确任务边界内可重复的质量测量
  • 版本变更前后的可比较结果
  • 失败样本可以落到责任层的诊断依据
  • 高风险查询进入人工复核或拒答的门禁信号

3. 评测对象必须版本化

一次可复现的 RAG 评测，至少要冻结以下版本：

  • 评测集版本
  • 语料快照版本
  • 文档解析和分片策略版本
  • Embedding 模型及其参数
  • 索引构建参数
  • 查询改写策略
  • 检索和重排配置
  • 权限过滤规则
  • Prompt 版本
  • 生成模型标识与采样参数
  • 引用抽取和答案后处理版本
  • 自动裁判版本

“今天和昨天用同一批问题”不等于可比较。

只要语料、索引、模型、Prompt 或裁判中任意一项变化，分数变化就可能来自新的变量。

二、先画出分层评测栈

这张图里最重要的不是指标名称，而是指标所属的统计层级。

1. 评测契约层

评测契约回答：

  • 用户真正想解决什么问题
  • 哪些资料在评测时有效
  • 哪些证据算相关
  • 哪些陈述必须有来源
  • 哪些问题应该拒答
  • 哪些权限条件必须满足

没有这一层，后面的指标都没有稳定分母。

2. 检索层

检索层只观察候选排序，不调用生成模型。

典型输入是：

  • query
  • 语料快照
  • 相关性标注 qrels

典型输出是：

  • 排序后的文档或分片 ID
  • 每个候选的检索分数
  • 过滤、融合、重排过程

这一层适合使用 Recall@k、MRR 和 nDCG@k。

3. 上下文层

上下文层评测的不是检索器返回了什么，而是生成模型最终看到了什么。

两者可能不同，因为中间还有：

  • 权限过滤
  • 父子分片展开
  • 去重
  • 重排
  • 上下文长度预算
  • 模板占用
  • 截断

这一层适合使用 context precision、context recall、重复率、冲突率和预算利用率。

4. 生成层

生成层观察模型是否：

  • 回答了用户问题
  • 只陈述上下文能够支持的事实
  • 正确处理冲突和时效性
  • 在证据不足时拒答

这一层的核心指标包括 faithfulness 和 answer relevance。

若有标准答案，还可以补充 answer correctness，但它不能替代 faithfulness。

5. 引用与端到端层

引用层观察：

  • 引用是否真的支持它所绑定的陈述
  • 需要证据的陈述是否都附有引用
  • 链接是否可访问
  • 引用版本是否与生成时一致

端到端层观察任务是否完成、响应是否及时、成本是否可接受。

端到端指标适合做发布门禁，分层指标适合做故障定位。

三、评测数据集：没有可靠标注，指标只会精确地制造误导

1. 一条样本不应只有问题和标准答案

检索与生成分层评测要求更丰富的数据契约。

最小样本建议包含：

  • case_id：稳定的样本标识
  • query：用户原始问题
  • normalized_intent：评测人员确认的意图
  • query_type：事实、流程、比较、多跳、拒答等类型
  • corpus_snapshot：语料快照
  • qrels：相关文档与相关性等级
  • required_evidence_units：回答所需的最小证据单元
  • reference_claims：允许出现的关键事实
  • must_not_claim：禁止无依据生成的事实
  • expected_behavior：回答、澄清或拒答
  • permission_context：用户可访问的知识范围
  • slice_tags：用于分层统计的标签

只有标准答案而没有 qrels，无法直接评价检索。

只有 qrels 而没有原子事实，无法可靠评价回答覆盖与引用完整性。

2. 文档、分片与证据单元必须分开

RAG 系统常以 chunk 为检索单位，但业务知识通常属于 document，答案依据则可能只是一句话或一行表格。

因此至少要区分：

  • document_id：稳定的源文档身份
  • chunk_id：特定解析和切片版本下的分片身份
  • evidence_unit_id：可支持一个原子事实的最小证据单元

否则切片策略一改，所有标注都可能失效。

一个更稳的做法是：

  • 以 document_id + source_version 绑定资料版本
  • 以字符区间、段落 ID 或结构化字段定位证据
  • 在构建索引时再把证据映射到当前 chunk

这样既能评价当前检索单元，也能跨切片版本复用高价值标注。

3. qrels 不是“标准答案文档列表”那么简单

qrels 是 query relevance judgments，即查询与资料之间的相关性判断。

对 RAG 来说，相关性可以设为分级标签：

  • 0：无关或会误导
  • 1：主题相关，但不足以独立支持答案
  • 2：包含部分必要证据
  • 3：包含关键且直接的答案证据

等级定义必须写进标注规范。

不同团队可以使用不同等级，但不能让标注人员按“感觉重要”自由发挥。

对只关心是否命中的 Recall@k，可以把 rel >= 2 视为相关。

对 nDCG，可以直接保留分级相关性，让排名靠前的高价值证据获得更高增益。

4. 证据充分性要考虑组合关系

有些问题只需要一份资料。

有些问题需要同时满足：

  • 规则定义
  • 适用条件
  • 例外条款
  • 当前版本信息

这时不能把四份资料都简单标成“任意命中一份即成功”。

这样才能区分：

  • 命中了某个相关片段
  • 找全了生成正确答案所需的证据

5. 必须保留不可回答和需要澄清的样本

如果评测集全部有答案，模型会学到错误先验：每个问题都应该给出确定结论。

至少应包含：

  • 语料中不存在答案
  • 资料已经过期
  • 多份资料互相冲突
  • 用户缺少访问权限
  • 问题条件不完整
  • 问题要求超出知识库边界

这类样本的正确行为可能是：

  • 明确拒答
  • 说明证据不足
  • 请求补充条件
  • 提示联系有权限的角色

拒答不是低质量回答，而是 RAG 安全边界的一部分。

6. 查询切片决定平均分是否可信

总平均分很容易掩盖关键退化。

建议至少按下面维度切片：

  • 事实查询与流程查询
  • 单跳与多跳
  • 精确实体与模糊描述
  • 短问题与长上下文问题
  • 常见问题与长尾问题
  • 新文档与旧文档
  • 单语言与混合语言
  • 有权限、无权限和权限变更
  • 可回答、不可回答和需澄清
  • 高风险与普通风险

发布门禁要同时检查总分与关键切片。

四、检索评测：Recall@k、MRR 和 nDCG 各自回答什么

1. 先固定统计单位

计算检索指标前，必须明确：

  • 一条结果是文档、chunk 还是 evidence unit
  • 相同父文档的多个 chunk 是否去重
  • 相关性的二值阈值是什么
  • 权限过滤在指标计算前还是计算后
  • 没有相关文档的问题如何处理
  • 指标是 macro average 还是按流量加权

若线上系统按 chunk 返回，离线标注却只在 document 级计算，重复 chunk 可能让排名看起来很好，却没有增加任何新证据。

建议同时保留：

  • chunk 级指标：观察索引与切片的直接行为
  • parent document 级指标：消除同源重复
  • evidence coverage：观察回答所需事实是否真正覆盖

2. Recall@k：前 k 个结果找回了多少相关资料

对查询 q，设相关资料集合为 R_q，前 k 个检索结果为 TopK_q。

数据集级别一般对每条查询的 Recall@k 取宏平均：

Recall@k 适合回答：

  • 检索器有没有把需要的资料找回来
  • 增大候选集是否真的提高覆盖
  • 查询改写是否漏掉了某类证据

它不回答：

  • 相关结果是否排在最前面
  • 返回结果里有多少噪声
  • 模型是否使用了证据
  • 最终答案是否正确

3. 不要把 HitRate@k 当作 Recall@k

HitRate@k 通常定义为：前 k 个结果只要命中至少一个相关资料就记为 1。

如果每个问题只有一个相关文档，HitRate@k 与 Recall@k 可能数值相同。

一旦问题需要多份证据，两者含义完全不同。

例如需要 4 份证据，检索只找到 1 份：

  • HitRate@5 = 1
  • Recall@5 = 0.25

前者说明“至少碰到了一点”，后者才说明“证据远未找全”。

4. MRR：第一个相关结果出现得有多早

对查询 q，设第一个相关结果的排名为 rank_q。

如果前 k 或完整结果中没有相关项，该查询的 RR 通常记为 0。

MRR 适合：

  • 单一事实问答
  • 用户主要看第一条结果的检索产品
  • 关注第一份可用证据能否尽早进入上下文的场景

MRR 的局限是：只看第一个相关结果。

第二、第三份必要证据是否缺失，不会影响 RR。

所以多证据 RAG 不能只看 MRR。

5. nDCG@k：高相关结果是否按价值排在前面

nDCG 适用于分级相关性。

六、生成评测：忠实、相关和正确不是一回事

1. 先把答案拆成原子陈述

对整段答案直接打一个 1 到 5 分，难以解释。

更稳的方法是先拆成 atomic claims。

例如答案：

连续三次健康检查失败后，节点会进入待摘除状态；如果处于发布保护期，则延迟摘除，并在保护期结束后重新检查。

可以拆成：

  1. 连续三次失败会进入待摘除状态
  2. 发布保护期会阻止立即摘除
  3. 保护期结束后会重新检查

每条 claim 再判断：

  • 是否需要外部证据
  • 上下文是否支持
  • 是否与上下文矛盾
  • 是否附有正确引用
  • 对最终决策的重要性权重

这比给整段答案一个“基本正确”更适合回归分析。

2. Faithfulness：答案有没有超出给定证据

一个清晰的加权定义是：

判断标签至少可以分为：

  • SUPPORTED：上下文明确支持
  • CONTRADICTED：上下文明确反驳
  • NOT_ENOUGH_INFO：上下文不足以判断
  • NOT_APPLICABLE：礼貌语、结构提示等不需要外部证据

后两类不能混淆。

“请先确认环境名称”可能不需要知识证据。

“该功能从 4.2 版本开始支持”则必须有证据。

3. Faithfulness 不等于事实正确性

如果知识库里是一条过时规则，模型完全照着回答：

  • faithfulness 可以很高
  • 对现实世界的 factual correctness 仍可能很低

所以语料时效性要单独治理。

评测报告至少要带上：

  • 文档版本
  • 生效时间
  • 失效时间
  • 抓取或入库时间
  • 评测快照

忠实度只能说明模型是否遵循了给定上下文，不能替语料背书。

4. Answer relevance：回答是否对准问题

Answer relevance 关注的是响应与用户意图的关系。

典型扣分情况包括：

  • 只复述背景，没有回答结论
  • 回答了邻近问题
  • 用户问操作步骤，答案只给概念解释
  • 用户问当前版本，答案讲历史版本
  • 大量无关内容淹没关键结论

它仍不等于正确性。

一段答案可能：

  • 非常切题但完全错误
  • 完全忠于上下文但没有回答用户问题
  • 最终结论正确但给了错误理由

因此 answer relevance、faithfulness 和 answer correctness 必须分列。

5. 有标准答案时如何评价正确性

标准答案不应要求逐字匹配。

可以把参考答案拆成：

  • 必须覆盖的事实
  • 允许省略的补充信息
  • 禁止出现的错误陈述
  • 关键条件和例外
  • 预期动作或决策

再使用：

  • 结构化字段精确断言
  • 数字和实体规范化匹配
  • 原子事实覆盖率
  • 语义裁判
  • 人工复核

高风险字段，例如金额、版本、权限和操作命令，优先使用确定性断言。

不要让 LLM 裁判替代本来可以精确判断的规则。

6. 冲突资料必须有专门测试

当上下文里同时存在新旧规则，正确行为不一定是“选择语义更像问题的那一条”。

系统可能需要：

  • 根据生效时间选最新有效版本
  • 根据产品、地区、租户过滤
  • 明确指出冲突并请求人工确认
  • 拒绝给出高风险动作

测试时应记录：

  • 冲突是否在检索阶段已存在
  • 重排是否把旧文档放得更靠前
  • Prompt 是否告知模型版本规则
  • 回答是否暴露冲突
  • 引用是否对应实际采用的规则

七、引用评测：有链接不等于可追溯

1. 先定义引用的最小契约

一条可追溯引用至少应包含：

  • 稳定的来源 ID
  • 来源版本
  • 文档标题或可识别名称
  • 精确定位信息，例如章节、段落或行号
  • 用户可访问的链接
  • 与答案陈述的绑定关系

只在答案末尾列出三篇“参考文档”，无法确认哪篇支持哪句话。

2. Citation correctness：引用是否支持对应陈述

可以把每个 claim-citation 对作为统计单元：

需要单独记录的失败类型包括：

  • 来源与问题相关，但不支持该陈述
  • 来源支持相反结论
  • 引用章节错误
  • 链接指向同名但不同版本文档
  • 引用存在，但用户无权访问
  • 引用锚点失效

“文档主题相关”不能代替“文档蕴含该陈述”。

3. Citation completeness：需要证据的陈述是否都被覆盖

一种加权定义是：

关键条件可以设置更高权重。

例如：

  • 主结论权重 2
  • 风险提示权重 2
  • 补充背景权重 1

这样，漏引一个决定操作安全的例外条款，不会和漏引一条背景说明产生相同影响。

4. correctness 与 completeness 必须同时看

极端例子一：只给一条完全正确的引用。

  • Citation correctness 很高
  • 大量关键陈述没有引用，completeness 很低

极端例子二：每句话都挂一个链接，但链接经常不支持陈述。

  • Completeness 表面很高
  • Correctness 很低

所以“引用数量”不是质量指标。

5. 引用可访问性是独立指标

链接可能在生成时有效，评测时已经：

  • 返回 404
  • 跳转到登录页
  • 权限失效
  • 锚点漂移
  • 文档内容已被覆盖更新

建议额外统计：

对审计要求高的场景，还应保存内容摘要哈希或不可变快照标识。

八、自动裁判怎么用：把模型当测量仪器，而不是答案本身

1. 判定优先级

建议按下面顺序选择裁判：

  1. 确定性程序断言
  2. 结构化规则与领域解析器
  3. 经过校准的模型裁判
  4. 人工专家

并不是人工永远最差或模型永远最差，而是要把成本放在真正存在语义歧义的地方。

例如：

  • 引用链接是否存在：程序判断
  • 数值是否超过上限：程序判断
  • 一句话是否被某段复杂条款支持：模型初判 + 人工抽检
  • 高风险冲突是否可接受：领域专家判断

2. 模型裁判必须输出结构化理由

裁判输出建议包含：

confidence 不能被当作真实概率，除非经过单独校准。

它更适合用作人工复核队列的排序信号。

3. 校准集不能与日常回归集混用

应准备一批由多人复核的裁判校准样本，覆盖：

  • 明确支持
  • 明确矛盾
  • 证据不足
  • 部分支持
  • 数值和时间边界
  • 否定关系
  • 条件与例外
  • 多段证据联合支持

用这些样本检查：

  • 与专家一致率
  • 各标签 precision/recall
  • 高风险错误漏判率
  • 不同答案长度上的偏差
  • 不同语言上的偏差
  • 位置和格式敏感性

裁判 Prompt 或模型变化后，应先重跑校准集，再用于正式门禁。

4. 防止裁判偏差

常见偏差包括：

  • 偏爱更长、更流畅的答案
  • 偏爱与参考答案措辞相似的答案
  • 看到模型名称后产生先验
  • 对答案中的自信语气误判
  • 忽略否定词、时间条件或权限条件

控制手段包括：

  • 隐去被测模型身份
  • 随机交换候选答案顺序
  • 以原子陈述而不是整段答案判断
  • 要求裁判引用证据位置
  • 对争议样本使用多裁判或人工复核
  • 记录裁判版本并做稳定性测试

九、端到端归因：用反事实实验隔离检索与生成

1. 为什么正常链路不能直接归因

生产链路中的答案由检索和生成共同决定。

答案错误时，只观察一次运行无法知道：

  • 是没有证据
  • 是证据位置太靠后
  • 是上下文噪声太多
  • 是模型忽略了正确证据
  • 是引用后处理出错

需要控制变量。

2. 三组核心实验

对同一条 query 固定：

  • Prompt
  • 生成模型
  • 采样参数
  • 输出解析器
  • 答案裁判

只改变上下文来源。

A. 生产检索上下文

使用真实检索、重排、过滤和截断结果。

它测量当前端到端表现。

B. Oracle 上下文

直接把人工确认的最小充分证据交给生成模型。

它绕开检索器，用于测量生成上限和 Prompt 能力。

C. 空或无关上下文

移除证据，或者放入明确无关的控制文本。

它用于检查：

  • 模型是否会无依据作答
  • 拒答规则是否有效
  • 参数记忆是否绕开知识边界

3. 诊断矩阵

生产上下文 Oracle 上下文 典型归因
失败 通过 检索、重排、过滤或上下文预算
失败 失败 生成、Prompt、答案解析或标注契约
通过 通过 当前样本通过，继续看鲁棒性与成本
通过 失败 优先检查非确定性、缓存、实验污染或裁判错误

第三组空上下文再补充安全判断：

  • 应拒答且正确拒答：通过
  • 应拒答但给出确定结论：失败
  • 回答碰巧正确但没有证据：仍按不忠实处理

4. 进一步的反事实扰动

除了替换为 Oracle 上下文，还可以做：

  • 打乱相关证据顺序
  • 把关键证据放到上下文尾部
  • 加入主题相近但结论相反的文档
  • 加入旧版本资料
  • 删除一个必要证据单元
  • 替换实体名称
  • 保持语义不变地改写问题
  • 增加无关长文本

这些测试可以回答：

  • 模型是否存在位置偏差
  • 版本和冲突规则是否有效
  • 多跳证据是否真正必要
  • 查询改写是否保持意图
  • token 预算是否过于脆弱

5. 最小追踪记录

一次运行建议至少记录：

这条轨迹已经能看出：

  • 检索曾找到例外条款
  • 例外条款在 token budget 阶段被丢弃
  • 生成模型没有机会看到完整规则

因此首要责任层是上下文拼装，不是生成模型。

十、测试设计：从离线基准到持续质量门禁

1. 离线评测流水线

一条可维护的离线流程可以拆成：

失败样本包应包含：

  • 输入契约
  • 检索列表
  • 最终上下文
  • 模型回答
  • 原子 claim 判断
  • 引用判断
  • 版本和耗时
  • 与基线的差异

只输出 CSV 总分不够定位问题。

2. 门禁不要只使用绝对阈值

绝对阈值适合定义最低底线。

版本回归还应加入相对变化：

  • 总体分数不得显著下降
  • 高风险切片不得下降
  • 严重错误数量不得增加
  • p95 延迟和成本不得超过预算
  • 不可回答样本的错误作答率不得上升

  • 当前可接受基线
  • 人工表现或规则系统表现
  • 线上错误成本
  • 样本量和置信区间

3. 每次变更跑什么

不同改动应触发不同范围：

变更 最小必跑评测
文档更新 受影响查询 + 时效性 + 冲突测试
切片策略变化 全量检索、上下文覆盖、重复率
Embedding 变化 全量 Recall/MRR/nDCG + 关键切片
重排器变化 排序指标 + 上下文预算测试
Prompt 变化 Oracle-context + 忠实度 + 拒答
生成模型变化 全量生成、引用、非确定性与成本
权限规则变化 越权与误拒绝专项测试
裁判变化 裁判校准集 + 历史结果重判

4. 非确定性要用重复运行表达

即使 temperature 为 0，服务实现、模型更新和并行调度也可能使输出变化。

对关键样本建议重复运行，至少记录：

  • 平均值
  • 标准差或分位数
  • 单次最差结果
  • 通过率
  • 严重错误出现次数

高风险门禁更应关注：

  • pass rate over repeated runs
  • worst-case unsupported claims

而不是只看均值。

5. 统计置信度和样本量

当评测集只有 20 条样本时，一条样本就会改变 5 个百分点。

报告分数时建议同时给出：

  • 分子和分母
  • 样本数
  • 查询切片分布
  • 置信区间或 bootstrap 区间
  • 配对样本变化

比较两个版本时，应优先做同一批 query 的配对比较。

不要只比较两个独立均值。

同一 query 重复运行时，run 之间通常相关。Bootstrap 应以 query/case 为聚类重采样单位；候选与基线的比较还要在每个 case 内保留配对关系，不能把所有重复运行平铺后当成独立样本。

6. 线上评测与离线评测互补

离线评测适合：

  • 可重复回归
  • 精细标注
  • 快速版本比较
  • 故障归因

线上监控适合发现：

  • 新问题分布
  • 语料更新滞后
  • 实际权限组合
  • 用户改写和追问行为
  • 延迟与成本异常
  • 用户反馈中的长尾失败

线上样本进入离线集前要：

  • 脱敏
  • 去重
  • 确认合法使用范围
  • 人工标注意图和证据
  • 防止把生产数据直接泄漏到开发环境

十一、失败案例：高 Recall 为什么仍然生成了错误答案

以下为说明评测方法而构造的示例案例，不代表真实项目经历。

1. 场景

一个运维知识助手回答：

节点连续三次健康检查失败后会立即被摘除吗？

知识库中有两条必要证据：

  • 规则 A：连续三次失败进入待摘除状态
  • 规则 B：发布保护期内延迟摘除，保护期结束后重新检查

规则 B 是决定“是否立即”的关键例外。

2. 表面评测结果

某版本的离线结果为：

  • Recall@10 = 1.00
  • MRR = 1.00
  • 答案：会立即摘除
  • 答案相关性很高

团队最初怀疑生成模型没有理解例外。

3. 分层检查

继续检查后发现：

  • 候选检索前十名包含规则 A 和规则 B
  • 前三名包含多个规则 A 的重叠 chunk
  • 上下文去重只按完全相同文本哈希，未识别重叠片段
  • Prompt 和工具说明占用了较多 token
  • 规则 B 在最终截断时被移除

因此：

  • Retrieval Recall@10 = 1.00
  • Parent-level Recall@10 = 1.00
  • Final Context Recall = 0.50
  • Duplicate Ratio 较高
  • “立即摘除”没有被最终上下文支持，因此 Faithfulness 也失败
  • Answer Correctness 和 Citation Completeness 失败

4. Oracle 实验

把规则 A 和规则 B 的最小证据直接放入上下文后，模型稳定输出：

不一定立即摘除。连续三次失败会进入待摘除状态，但发布保护期内会延迟执行。

Oracle-context 通过，说明生成器在证据完整时具备处理例外的能力；它不能反向证明当前运行的生成层没有问题。

5. 根因和修复

主导根因属于上下文拼装层：

  • 近重复去重不足
  • 预算分配没有优先保留必要证据
  • 只监控候选 Recall，没有监控最终 Context Recall

同时存在生成层的次级失败：证据只支持“进入待摘除状态”，模型却扩写成“立即摘除”。因此生成侧还需要无依据断言门禁或证据不足时的保守表达。

修复包括：

  • 以父文档区间识别重叠 chunk
  • 对规则和例外建立 evidence group
  • 在截断前优先覆盖不同必要证据组
  • 增加 final context recall 和 duplicate ratio 门禁
  • 保留 Oracle-context 对照测试

这个案例说明：

高检索召回只能证明“曾经找到”，不能证明“模型真正看到”。

十二、常见误区

1. 用最终答案正确率评价检索器

生成模型可能依靠参数记忆碰巧答对。

也可能在正确上下文下答错。

因此答案正确率不能直接作为检索质量。

2. 把 Recall@k 和 HitRate@k 混用

多证据问题里，两者差异很大。

报告必须写清公式、阈值和统计单位。

3. 只测候选列表，不测最终上下文

重排、过滤、去重和截断都会改变证据集合。

缺少 final context 记录就无法定位这一层。

4. 只看 faithfulness，不看语料正确性

模型忠于旧资料仍然会给出过时答案。

语料版本和有效期必须独立校验。

5. 把 answer relevance 当作 correctness

切题不代表正确。

流畅也不代表有证据。

6. 有引用就算可追溯

引用必须支持具体陈述，并且关键陈述都要覆盖。

否则只是链接装饰。

7. 让模型裁判所有字段

版本号、金额、数量、权限和链接状态通常可以确定性判断。

不应把可精确计算的问题重新变成概率判断。

8. 用一个加权总分掩盖严重失败

越权检索、危险指令和高风险无依据陈述应设硬门禁。

不能用延迟优秀或普通问题得分高来抵消。

9. 评测集只有成功问题

没有不可回答、冲突和缺权限样本，就测不出拒答边界。

10. 更换裁判后直接比较历史分数

裁判是测量系统的一部分。

裁判变了，应先在校准集上验证，并考虑重判历史样本。

11. 所有查询只看宏平均

宏平均让每条 query 权重相同，但不一定符合业务风险。

应同时报告宏平均、业务流量权重和高风险切片。

12. 看到 Recall 低就直接增大 top_k

更大的候选集会增加延迟、token 和噪声。

应先分析漏召回类型，再决定改查询、索引、召回器还是候选数量。

十三、上线前检查表

评测契约

  • 每条样本都有稳定 case_id
  • 评测集和语料快照可追溯
  • 查询意图和预期行为已标注
  • qrels 的相关性等级有统一规范
  • 必要证据单元和组合关系已定义
  • 不可回答、冲突和澄清样本已覆盖
  • 权限上下文属于测试输入
  • 高风险样本有独立标签和权重

检索与上下文

  • Recall@k、HitRate@k 没有混用
  • MRR 用于适合首个命中的场景
  • nDCG 使用明确的分级相关性
  • chunk 与 parent document 指标分别统计
  • 最终上下文而非仅候选列表被保存
  • context precision/recall 的实现、统计单位与 NA 口径明确
  • 重复率、冲突率和截断原因可观测
  • 权限过滤前后结果可审计

生成与引用

  • 答案被拆成可验证的原子陈述
  • faithfulness 与 correctness 分开
  • answer relevance 不被当作正确率
  • 拒答和证据不足行为有专项断言
  • citation correctness 按 claim-citation 对计算
  • citation completeness 覆盖关键陈述
  • 引用链接、版本和定位信息可验证
  • 高风险无依据陈述使用硬门禁

裁判与统计

  • 确定性规则优先于模型裁判
  • 模型裁判有独立校准集
  • 裁判版本和结构化理由被保存
  • 报告包含样本量、分子和分母
  • 关键指标按查询切片展示
  • 版本比较使用同样本配对结果
  • 非确定性任务做重复运行
  • 争议样本进入人工复核队列

持续交付

  • 生产上下文、Oracle 上下文和空上下文都有对照
  • 各类变更映射到最小回归集
  • 绝对阈值和相对退化同时检查
  • 严重安全错误不能被总分抵消
  • 延迟、token 和成本纳入报告
  • 失败样本包能还原完整链路
  • 线上反馈经过脱敏和标注再进入评测集
  • 历史基线和配置均可复现

十四、总结

RAG 评测最重要的能力，不是产生更多分数，而是让每个分数都能回答明确问题。

检索层：

  • Recall@k 说明证据找全了多少
  • MRR 说明第一份相关证据出现得多早
  • nDCG 说明高价值证据是否排在合理位置

上下文层：

  • context relevance ratio 说明输入里有多少有效信息；若使用 context precision，必须注明具体框架或公式
  • context recall 说明回答所需证据是否真正进入模型窗口

生成层：

  • faithfulness 说明陈述是否受给定上下文支持
  • answer relevance 说明回答是否对准用户意图
  • correctness 说明答案是否满足参考事实或业务断言

引用层：

  • citation correctness 说明引用是否支持绑定陈述
  • citation completeness 说明关键陈述是否都有证据覆盖

端到端失败时，不要立即换模型。

先做生产上下文、Oracle 上下文和空上下文三组控制实验，再结合 trace 判断问题发生在：

  • 语料
  • 检索
  • 上下文拼装
  • 生成
  • 引用
  • 权限和治理

最终，一个可持续迭代的 RAG 系统应该做到：

端到端分数可以决定是否发布，分层证据可以解释为什么失败，原始轨迹可以支持复现和修复。
