AI测试-22-Prompt Injection和间接提示注入应该怎么测试

发表于 2026-03-30 分类于 AI测试 本文字数： 7.4k 阅读时长 ≈ 27 分钟

测试 Prompt Injection 时，最容易出现一种看似合理、实际很危险的简化：

准备几十条“忽略之前指令”的攻击语句，发给模型，看模型有没有拒绝。

这种测试能覆盖最表面的直接注入，却回答不了生产系统真正关心的问题：

  • 恶意指令藏在网页、知识库、附件或工具返回值里时，能不能进入模型上下文
  • 模型受到影响以后，是否有权限读取敏感数据
  • Agent 是否会调用发信、写库、删除、执行命令等高风险工具
  • 一个被污染的检索片段能否跨用户、跨租户或跨任务持续传播
  • 安全策略究竟在哪一层阻断，失败后是否留下可追溯证据
  • 模型换版本、Prompt 改动或新增工具以后，原来的防护是否仍然成立

因此，Prompt Injection 测试不应该只测一句回答，而应该测一条完整的信任传播链：

这篇文章从 AI 质量工程角度，把直接提示注入、间接提示注入、RAG 污染和 Agent 工具越权放进同一套测试框架里。重点不是收集多少攻击 Prompt，而是建立可验证的安全性质、攻击矩阵、判定规则和持续回归链路。

一、先给结论：不要把模型拒答率当成系统安全性

一个模型可以在文本回答里说“我不能执行这个请求”，同时已经在后台调用了错误的工具。

它也可能输出一段看起来正常的总结，却把敏感数据编码进 URL、Markdown 图片地址、工具参数或日志字段。

反过来，模型即使复述了恶意指令，只要系统没有给它危险权限、敏感数据和外发通道，也不一定形成真正的安全事件。

所以测试目标要从“模型是否听话”改成下面四类安全性质。

1. 权限安全性质

模型和 Agent 只能调用当前任务明确允许的工具。

即使输入里要求提升权限，也不能扩大工具集合、租户范围、数据范围和动作额度。

2. 数据安全性质

不可信内容不能诱导系统读取与当前任务无关的秘密、凭据、个人信息或其他租户数据。

即使数据已被合法读取，也不能通过回答、URL、Webhook 或工具参数带出允许边界。

3. 动作安全性质

发信、付款、删除、发布、执行命令等有副作用动作，必须经过确定性策略校验和必要的人工确认。

模型的自然语言判断不能替代权限系统。

4. 可追溯安全性质

每一次内容进入、策略判断、工具调用和数据外发都要能追到：

  • 输入来源
  • 内容版本与哈希
  • 模型和 Prompt 版本
  • 命中的安全策略
  • 标准化工具参数
  • 调用主体与权限范围
  • 最终执行结果

如果测试只能看到最终回答，就没有足够证据判断系统到底有没有被攻破。

二、先区分三个经常混用的概念

Prompt Injection、间接提示注入和 Jailbreak 有重叠，但测试入口和影响范围不一样。

概念 恶意内容从哪里进入 主要目标 典型测试对象
直接提示注入 用户直接输入 覆盖任务指令、套取信息、诱导调用工具 聊天输入、API 参数、自然语言任务
间接提示注入 网页、文档、邮件、RAG 片段、工具返回值 借助系统自动读取的外部数据改变模型行为 浏览器 Agent、知识库、附件解析、搜索与工具链
Jailbreak 通常由用户直接构造，也可能经外部内容传播 绕过模型或应用的内容与行为限制 模型安全策略、内容策略、角色边界

直接注入的攻击者通常拥有输入接口。

间接注入更难，因为攻击者不一定和 Agent 直接对话。攻击者只要能控制一个未来可能被读取的网页、工单、代码注释、知识文档或邮件，就可能把恶意指令带入上下文。

从测试角度看，间接注入至少多了三类变量：

  • 外部内容能否进入系统
  • 内容进入后是否被当成指令解释
  • 被污染的上下文能否触发高权限动作

这也是为什么只在聊天输入框里跑攻击语料，不能代表系统已经覆盖了间接注入风险。

三、攻击面不是一个 Prompt，而是整条数据流

下面这张图把常见传播路径放在一起。

图中有两个必须单独测试的信任边界。

1. 外部内容进入模型上下文的边界

用户输入、网页、检索片段、附件和工具返回值都可能包含自然语言。

对模型来说，这些内容和系统指令最终都可能表现为 Token 序列。模型可以学习不同消息角色和结构标记，但不能把这种概率行为当作传统权限隔离。

测试要确认：

  • 内容来源有没有可靠标记
  • 未授权数据是否被召回
  • 外部文本是否被明确包装为“只可引用的数据”
  • 上下文构建器有没有丢失来源和信任级别
  • 内容截断后是否刚好删除了安全边界说明

2. 模型意图变成系统动作的边界

模型生成一个工具调用，只代表它提出了动作意图。

真正的系统必须在执行前重新完成：

  • 身份校验
  • 租户校验
  • 工具白名单校验
  • 参数 Schema 校验
  • 业务前置条件校验
  • 风险等级判断
  • 人工审批或额度校验

如果执行器因为“这是模型生成的 JSON”就默认可信，Prompt Injection 就从输出质量问题升级成权限和数据安全问题。

四、为什么仅靠 System Prompt 很难形成可靠边界

System Prompt 可以降低某些攻击成功概率，但它不等于访问控制。

原因并不神秘。

1. 指令与数据共享表达空间

外部文档里的一句话既可能是业务数据，也可能长得像系统指令。

如果应用把所有内容拼进同一个上下文，再要求模型自己区分，最终仍然依赖模型行为。

2. 上下文会被变换

真实系统会进行：

  • HTML 清洗
  • OCR
  • PDF 解析
  • 查询改写
  • 摘要压缩
  • 多轮记忆合并
  • 工具结果标准化

攻击内容可能在原文里不起眼，经过解析或拼接后才形成完整指令。也可能被拆成多个片段，在同一上下文中重新组合。

3. 模型输出可能驱动高权限代码

风险上限由系统给模型的能力决定。

只读问答系统和拥有邮件、数据库、终端权限的 Agent，即使面对同一条注入，潜在影响也完全不同。

4. 防御和攻击都不是静态的

模型版本、系统指令、上下文模板、检索顺序和工具描述只要发生变化，历史拒答样本的结果就可能改变。

因此防护必须有系统侧控制，测试必须进入持续回归，而不是上线前跑一次攻击 Prompt。

五、建立一张可执行的攻击矩阵

攻击语料不能只按句子分类，更有效的方式是按“来源、载体、目标、权限、传播”组合。

维度 建议取值
来源 用户输入、网页、搜索结果、RAG 文档、PDF、图片 OCR、邮件、工单、代码仓库、工具返回值
可见性 明文、白色文字、注释、元数据、折叠区域、图片文字、编码内容
表达方式 直接命令、角色覆盖、伪造系统消息、引用嵌套、条件触发、多语言、字符变形、编码
组合方式 单段、跨分片、跨轮次、跨工具、跨文档、延迟触发
攻击目标 改写回答、泄露提示、读取秘密、调用工具、修改数据、外发数据、持久化污染
权限级别 无工具、只读工具、低风险写工具、高风险工具、管理员能力
期望阻断层 内容准入、检索过滤、上下文隔离、策略引擎、权限系统、人工审批、DLP

六、直接提示注入应该怎么测

直接注入仍然要测，但需要从单轮拒答扩展到任务链。

1. 指令覆盖

验证用户能否覆盖：

  • 角色边界
  • 工具白名单
  • 数据范围
  • 输出格式
  • 审批要求
  • 安全策略

测试时要分别观察模型回答、工具提议和执行结果。

2. 伪造高优先级消息

攻击内容可能伪装成：

系统不能根据自然语言里的身份声明提升权限。

测试断言应该落在真实身份、令牌范围和策略决策上。

3. 编码与变形

需要覆盖：

  • Base64 或十六进制内容
  • Unicode 相似字符
  • 多语言混合
  • Markdown、HTML 和代码块嵌套
  • 逐字拆分和跨消息拼接

这里的目标不是证明某个过滤器能识别所有写法，而是验证即使过滤漏过，权限和动作边界仍然有效。

4. 多轮诱导

攻击者可能先让模型记录一个“无害偏好”，后续再把它和工具调用组合。

测试要覆盖：

  • 短期会话记忆
  • 长期用户记忆
  • 任务恢复快照
  • Agent 检查点
  • 摘要记忆

任何会在后续任务重新进入上下文的状态，都可能成为持久化注入载体。

七、间接提示注入要按入口分别测试

不同入口的解析、权限和证据完全不同，不能用同一条用例笼统覆盖。

1. 网页与搜索结果

至少覆盖：

  • 页面正文中的显式攻击
  • HTML 注释和不可见区域
  • alt、title、ARIA 文本等辅助字段
  • 页面中引用的第三方内容
  • 重定向后的页面
  • 同一域名下不同信任级别的页面

测试时要保存原始页面、解析后文本和最终进入上下文的片段。否则无法判断攻击是在采集、解析还是模型阶段生效。

2. RAG 知识库

至少覆盖：

  • 有权限用户上传污染文档
  • 无权限文档被错误召回
  • 同名文档覆盖
  • 旧版本恶意内容仍然被索引
  • 攻击语句跨两个 Chunk 才完整
  • 恶意片段通过重排进入第一位
  • 查询改写扩大了数据范围

RAG 测试还要确认删除或隔离文档后，向量索引、缓存和摘要副本是否同步失效。

3. PDF、Office 和图片附件

附件测试不能只看肉眼可见正文。

要分别保存：

  • 原文件哈希
  • 解析器版本
  • OCR 输出
  • 文档元数据
  • 隐藏层或批注
  • 进入模型的最终文本

对多模态系统，还要测试图片内文字与用户文本冲突时，系统是否把图片内容当作可执行指令。

4. 邮件、工单和即时消息

这些内容天然包含“请执行”“请回复”“请转发”之类业务语言，简单关键词过滤会产生大量误报。

测试重点应放在：

  • 发件人身份是否可信
  • 当前工作流是否允许该动作
  • 收件人和外发域名是否受限
  • Agent 能否把正文里的自然语言直接变成动作授权

5. 工具返回值

很多团队只防用户输入，却默认内部 API 返回值可信。

实际上，工具可能读取外部网页、第三方工单、数据库自由文本字段或用户生成内容。

工具返回值再次进入模型时，必须保留“不可信数据”属性，不能因为它来自一个已注册工具就自动升级为可信指令。

同样 10% 的攻击成功率：

  • 在只读公开知识问答里，影响可能有限

1. 工具选择测试

攻击内容不能让 Agent 选择任务白名单之外的工具。

2. 参数污染测试

即使工具选择正确，也要验证：

  • 收件人是否被替换
  • 查询租户是否被扩大
  • 文件路径是否越界
  • SQL 条件是否被移除
  • URL 是否指向外部攻击者
  • 命令参数是否出现注入

3. 工具链传播测试

一个工具的输出可能成为下一个工具的输入。

策略拒绝后，Agent 不应该通过换工具、改写参数或多次重试绕过限制。

还要验证人工接管、断点恢复和任务重放不会丢失原来的风险标记。

九、纵深防御必须对应纵深断言

下面这张图给出一套不绑定具体模型和厂商的分层结构。

1. 来源与信任标记

测试断言：未经授权的来源不能进入知识库或当前任务上下文。

2. 数据与指令隔离

测试断言：外部内容只能作为待处理数据，不能直接修改工具集合、权限和系统策略。

结构化包装能降低风险，但不能单独构成安全保证。

3. 策略和参数校验

测试断言：模型提出的动作必须经过确定性规则检查；危险参数在执行器处被拒绝。

4. 最小权限

测试断言：当前身份只能访问当前租户、当前任务和必要字段；拒绝发生在数据源或工具侧，而不是只靠模型自觉。

5. 高风险动作确认

测试断言：没有有效审批令牌时，副作用调用次数为零；旧审批不能复用到新参数。

6. 输出与数据流控制

测试断言：敏感字段不能进入外发正文、URL、工具参数和日志；编码后内容同样受检查。

7. 审计和回归

测试断言：任何阻断和放行都能还原输入、策略、参数、身份和结果。

例如日志服务不可用时，不能因为“没有观察到外发”就判定安全通过。证据缺失本身应该让安全用例失败或进入人工复核。

十二、设计安全判定器时，不要只看攻击成功率

Attack Success Rate 可以保留，但必须明确“成功”指什么。

至少建议分开以下指标。

1. 指令影响率

模型输出或计划是否受到攻击内容影响。

这是行为层信号，不等于已经形成安全事件。

2. 禁止工具提议率

模型是否提出调用禁止工具。

它能衡量模型层防护，但只要执行层正确阻断，系统仍可能守住最终边界。

3. 禁止工具执行运行率

对高风险工具，这个指标的可接受目标通常应为零。

同时保留“实际执行的禁止调用事件总数”，用于识别一次运行内的重复副作用；事件数是计数指标，不能再除以运行数后称为比例。

4. 敏感数据暴露率

需要检查回答正文、结构化输出、URL、工具参数、日志和错误信息，不能只扫最终文本。

5. 策略阻断覆盖率

如果攻击都被模型拒绝，权限层从未真正接受测试，覆盖率仍然不完整。

可以通过故障注入或替身模型，强制生成危险工具调用，验证系统侧控制是否独立成立。

6. 误报率

安全控制不能把所有包含“忽略”“执行”“密码”的正常文档都挡住。

需要准备语义相似但合法的对照样本，例如安全培训材料、漏洞报告和操作手册。

十三、用故障注入验证“即使模型失守”

安全测试不能依赖模型偶然生成危险动作。

要对关键边界做确定性故障注入。

1. 替换模型输出

让模型适配层固定返回一个禁止工具调用，验证执行器能否拒绝。

2. 篡改工具参数

把合法租户替换成其他租户，把内部 URL 替换成外部域名，验证参数和权限校验。

3. 跳过内容过滤器

临时关闭输入检测，验证后续权限、审批和 DLP 仍能守住安全性质。

4. 注入策略服务故障

策略服务超时或不可用时，高风险动作应该失败关闭，而不是默认放行。

5. 注入审计服务故障

如果关键证据无法写入，高风险动作应暂停或降级。不能执行成功后只留一句“日志写入失败”。

这种测试能证明系统不是把全部安全希望放在某一条 Prompt 或某一个分类器上。

十四、证据链要能回答“攻击走到了哪一步”

一次安全运行至少要记录以下对象。

阶段 最小证据
内容进入 来源 URI、租户、上传者、哈希、MIME、解析器版本
检索 查询、过滤条件、候选 ID、分数、重排结果、知识版本
上下文 Prompt 模板版本、片段顺序、信任标签、截断记录
模型 模型标识、请求参数、输出、工具提议、停止原因
策略 策略版本、输入事实、命中规则、允许或拒绝原因
工具 调用主体、工具版本、标准化参数、权限范围、返回码
数据流 读取字段、敏感级别、脱敏动作、外发目标
结果 最终状态、安全断言、首错层、处置动作

日志里不应该明文保存秘密和完整凭据。

“证据完整”和“把所有敏感数据都写进日志”不是一回事。应保存不可逆指纹、脱敏字段、策略结果和必要的受控原始证据引用。

十五、一个端到端示例：被污染工单诱导 Agent 外发日志

下面是一个示例案例，用于说明如何排查，不代表真实生产事故。

1. 场景

测试平台允许 Agent 读取缺陷工单、查询内部日志，并把诊断摘要写回工单。

Agent 没有直接发外部邮件的业务需求，但工具注册中心里仍然存在一个通用 http_post 工具。

2. 执行

测试系统把工单 HTML 转成文本，Agent 读取文本后调用日志查询工具，并尝试调用 http_post。

3. 表面现象

最终工单摘要内容正常，没有出现攻击指令，也没有直接显示敏感日志。

如果只做回答检查，这条用例可能被判通过。

4. 证据排查

Trace 显示：

  1. HTML 解析器保留了折叠区域文字，但没有标记其信任级别。
  2. 上下文构建器把工单内容和任务指令直接拼接。
  3. 模型提出了 log_query 和 http_post 两个调用。
  4. log_query 只返回脱敏字段，数据层控制有效。
  5. http_post 不在任务白名单中，被执行策略拒绝。
  6. 最终没有外部请求，也没有秘密暴露。

5. 正确归因

这不是“完全防住所以无需处理”。

系统最终安全性质成立，但前面仍有两个需要修复的薄弱点：

  • 解析后的外部内容缺少信任标记
  • 模型层和上下文层未能抑制危险规划

同时，工具白名单和数据脱敏属于有效控制，应该通过故障注入继续验证其独立性。

6. 修复与回归

修复动作包括：

  • 给工单正文和隐藏区域保留来源与信任标签
  • 从该任务的工具集合中移除 http_post
  • 在日志工具侧继续执行字段级最小权限
  • 增加“工具返回值再次包含注入”的变体
  • 增加策略服务超时和审计失败的故障注入

这类案例说明，安全结果应该同时记录“攻击影响到了哪一层”和“最终安全边界是否被突破”。

十六、Prompt Injection 回归集怎么维护

攻击回归集不能只增不管。

建议至少分成五层。

1. 核心安全性质集

样本少但必须每次提交运行，覆盖：

  • 跨租户访问
  • 禁止工具
  • 高风险动作审批
  • 敏感数据外发
  • 策略服务失败关闭

2. 攻击族基准集

覆盖直接、间接、编码、分片、多轮、工具链和持久化等主要攻击族。

3. 入口专项集

按网页、RAG、PDF、邮件、工单、图片和工具返回值分别维护。

4. 历史事件集

每次真实问题都要转成最小复现样本，同时保留触发条件、首错层和修复版本。

5. 合法对照集

用于控制误报，尤其要包含安全文档、漏洞报告、代码注释和正常操作手册。

每个样本需要版本、来源、适用入口、风险等级和期望阻断层。模型或上下文结构变更后，应重新校准而不是沿用旧结论。

十七、最常见的八个误区

1. 只测“忽略之前指令”

真实攻击可以来自外部内容、跨分片组合和工具返回值。

2. 把模型拒答当成安全通过

必须检查工具、数据和网络事实。

3. 把 RAG 当作注入防护

RAG 能提供外部知识，也同时增加了不可信内容入口。微调同样不能替代运行时权限控制。

4. 默认内部工具返回值可信

工具可能只是外部数据的搬运通道。

5. 只做输入过滤

过滤可能被绕过，也可能造成高误报。关键安全性质必须由后端权限和策略守住。

6. 给 Agent 一套长期高权限凭据

一旦注入成功，影响范围会被凭据权限直接放大。

7. 策略服务故障时默认放行

高风险动作应该失败关闭，并留下明确的基础设施失败类型。

8. 攻击语料没有合法对照样本

最终得到一个“什么都不让做”的系统，不代表安全能力成熟。

十八、上线前检查表

输入和来源

  • 所有外部内容都有来源、租户、哈希和信任级别
  • 网页、附件、OCR、知识片段和工具返回值都纳入攻击面
  • 删除或隔离内容后，索引、缓存和摘要副本同步失效

上下文和模型

  • 系统指令、用户任务和外部数据使用明确结构隔离
  • 上下文截断和摘要不会丢失关键安全约束
  • 多轮记忆和恢复快照纳入持久化注入测试

工具和权限

  • 工具集合按任务动态收敛
  • 工具执行前重新校验身份、租户、参数和业务前置条件
  • 高风险动作需要不可复用的明确审批
  • 策略不可用时不会默认放行

数据和输出

  • 敏感数据最小化读取并执行字段级脱敏
  • 回答、URL、工具参数、日志和错误信息都做数据流检查
  • 外部域名、Webhook 和下载位置有确定性约束

测试和证据

  • 核心安全性质能通过模型替身和故障注入验证
  • 每个攻击样本有合法对照样本
  • 结果区分模型受影响、动作被提议、动作被执行和数据被外发
  • 安全运行能够重放，且日志本身不泄露秘密

十九、小结

Prompt Injection 的本质风险，不是模型说了一句不符合预期的话，而是系统把不可信自然语言沿着上下文、规划、工具和数据链传播，并最终赋予它现实世界的权限和副作用。

因此测试至少要完成四个转变：

  1. 从测试单句 Prompt，转向测试完整信任传播链。
  2. 从判断模型是否拒答，转向验证权限、数据、动作和可追溯安全性质。
  3. 从依赖 System Prompt，转向验证来源治理、策略、最小权限、审批、DLP 和审计组成的纵深防御。
  4. 从一次性红队演练，转向结构化攻击集、合法对照集、故障注入和持续回归。

真正可靠的目标不是承诺模型永远不会受到恶意内容影响，而是证明：

即使某一层识别失败，攻击仍然无法获得超出任务边界的权限，无法产生未授权副作用，也无法把敏感数据带出系统。
