AI测试-12-Token-Embedding-Attention和上下文窗口如何影响测试结果

发表于 2026-03-12 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 45 分钟

同一段需求，只改了一个空格，模型为什么突然不再输出合法 JSON？

同一份证据，放在上下文开头能回答，放到中间却经常漏掉，应该归因于什么？

向量检索召回了“语义很像”的文档，为什么金额、版本号和否定条件恰好是错的？

接口声称支持很长的上下文，为什么最后几段日志仍然像是没有被看见？

这些现象经常被笼统地归为“模型不稳定”。

这个归因太粗。

它既不能指导修复，也不能形成可回归的测试。

测试开发工程师真正需要建立的是一条可验证的机制链：

链路中的每一层都可能把“人看起来等价”的输入变成不同的模型输入，也可能让“已经放进窗口”的信息没有被稳定利用。

这篇文章不讨论如何训练一个基础模型，也不重复 RAG 数据清洗、Agent 状态管理或工具权限治理。

相关工程边界已经分别在 AI测试-07、AI测试-05 和 AI测试-09 中展开。

本文只回答一个更基础的问题：

Token、Embedding、Self-Attention、位置机制和上下文窗口，分别怎样影响测试结果，以及怎样用对照实验把故障归因到可操作的层级。

一、先限定问题边界：窗口长度不是上下文质量

讨论上下文能力时，至少要分开四个概念。

1. 最大可接受长度

这是接口或模型允许提交的最大上下文规模。

它通常以 Token 数量表达，而不是字符数、字数或文件大小。

不同服务对“输入与输出是否共享同一总预算”的定义可能不同。

工具定义、系统消息、图片、缓存前缀以及协议包装是否计入，也必须以目标服务的文档和实测为准。

因此，平台不能只保存一个营销页面上的窗口数字。

它应保存模型快照对应的实际限制和请求用量。

2. 实际进入模型的长度

调用方 SDK、应用代码、API 网关、RAG 拼装器和模型服务都有可能裁剪输入。

一次请求被接口接受，不代表每个原始片段都被完整送达。

如果平台只保存“召回过哪些文档”，却没有保存“最终纳入了哪些片段”，截断就会被误判成模型遗漏。

3. 模型有效利用的长度

信息在窗口内，并不意味着模型对每个位置、每类任务都能同样稳定地利用它。

长上下文研究观察到过明显的位置效应。

但位置效应不是所有模型、所有任务都必然呈现同一种曲线。

正确做法是针对自己的模型快照和任务，做位置扫描，而不是把论文结论直接当成本地结论。

4. 业务上可信的上下文

上下文越长，可能包含的过期资料、重复片段、互相矛盾的规则和非可信指令也越多。

模型“看到了”错误资料并据此作答，与模型“没有看到”正确资料，是两种完全不同的故障。

前者属于上下文治理和冲突处理。

后者可能属于截断、位置利用或任务表达。

把四个概念混在一起，会导致三个典型错误：

  • 用扩大窗口修复上下文污染；
  • 用重复提示修复静默截断；
  • 用更高向量相似度阈值修复数字和否定关系错误。

二、建立一张工程视角的机制图

这张图需要读出五个工程事实。

第一，模型接收的不是“文档”，而是经过拼装、规范化和分词后的 Token 序列。

第二，Token ID 会先被映射到向量，顺序还需要通过某种位置机制进入计算。

第三，Self-Attention 不是一次全局搜索，而是在多层、多头、残差路径中反复更新表示。

第四，自回归模型每生成一个 Token，都会把已生成内容作为后续步骤的上下文。

第五，测试中常见的边界漂移、截断、位置弱化和上下文污染发生在不同阶段，证据也不同。

所以，“答案错了”只是最终症状。

要进行机制归因，还需要保存：

  • 完整且按顺序排列的消息；
  • 经过模板渲染后的最终文本或可验证摘要；
  • 模型和 Tokenizer 标识；
  • 输入、输出和缓存 Token 用量；
  • 最大输出长度与结束原因；
  • 采样参数；
  • 检索片段 ID、版本、哈希和顺序；
  • 工具定义版本；
  • 重复运行次数与每次原始输出。

缺少这些信息时，任何关于“上下文没有生效”的结论都只能算假设。

三、Token：模型处理的边界不是人类看到的词

1. Token 是词表中的离散单元

设词表大小为 |V|。

Tokenizer 会把文本 x 转换为一个整数序列：

这些单元可能是：

  • 完整词；
  • 子词；
  • 单个汉字；
  • 多个汉字组成的片段；
  • 标点与前导空格的组合；
  • UTF-8 字节片段；
  • 特殊控制标记。

具体边界取决于模型使用的 Tokenizer、词表、规范化规则和特殊标记协议。

不能假设“一个汉字就是一个 Token”。

也不能假设“一个英文单词就是一个 Token”。

更不能把某个模型的经验比例用于另一个模型的预算。

2. 为什么要使用子词或字节级单元

如果只按完整单词建词表，词形变化、专业术语、新名字和多语言文本会造成严重的未登录词问题。

子词方法通过复用较小片段，在词表规模与表达能力之间折中。

SentencePiece 展示了一种直接从原始句子训练子词模型的语言无关方法。

不同实现可能采用 BPE、Unigram、WordPiece 或字节级方案。

测试关注的不是背诵算法名，而是确认：

  • 目标模型使用哪个 Tokenizer；
  • 规范化是否会改变全半角、空白或 Unicode 形式；
  • 特殊消息边界会增加多少开销；
  • Tokenizer 版本是否与线上模型一致。

3. “语义等价”不代表 Token 序列等价

下面几组输入对人来说接近，但可能产生不同切分：

它只说明模型接收到的离散序列不同。

如果测试结果随边界变化稳定漂移，才有理由继续调查 Token 敏感性。

4. 中文、代码和结构化数据的风险更容易被低估

自然语言测试集常只覆盖完整句子。

生产输入却经常混合：

  • 中文描述；
  • 英文类名；
  • 路径；
  • UUID；
  • 时间戳；
  • 十六进制地址；
  • JSON；
  • 堆栈；
  • shell 命令；
  • 带单位的数字。

这些内容可能具有较低的压缩效率，从而消耗更多 Token。

标识符还可能被拆成多个片段。

模型可以通过上下文组合这些片段，但精确复制能力不能由“语义理解能力”替代。

订单号、版本号、金额、哈希和错误码应优先走程序化校验。

5. Token 边界如何影响测试结果

影响至少分为四类。

预算影响

同样字符数的两段文本可能占用不同 Token 数。

如果预算器按字符裁剪，某些语言、代码或日志输入会更早越界。

匹配影响

测试若要求模型原样返回一个罕见 ID，ID 被拆得越碎，生成时需要连续做对多个选择。

不能据此推导一个固定错误概率，但应把精确复制单独纳入评测。

模板影响

分隔符、前导空格和特殊标记会改变消息模板形成的序列。

提示模板升级必须和模型升级一样进行回归。

成本与时延影响

许多推理服务按 Token 计量。

输入 Token 增加通常还会增加预填充阶段的计算和内存压力。

具体时延关系受实现、硬件、批处理与缓存影响，不能用单一线性公式代替实测。

工程上需要同时做两件事。

请求前

  • 使用与线上模型匹配的 Tokenizer；
  • 计算每个上下文片段的 Token 数；
  • 保留输出空间；
  • 按业务优先级决定删除、压缩或拒绝；
  • 生成纳入清单和排除清单；
  • 禁止无记录的尾部裁剪。

请求后

  • 记录服务端返回的输入 Token 用量；
  • 将服务端用量和本地估算做差；
  • 记录输出 Token 用量；
  • 记录结束原因；
  • 对异常差值告警；
  • 在模型或 SDK 升级后重新标定。

预算偏差不能直接说明发生截断。

它只是提示“本地看到的请求”和“服务端计量的请求”并不一致。

五、Token 边界测试怎么设计

Token 测试不应该只是统计长度。

至少要覆盖以下等价变换。

空白变换

  • 无空格；
  • 单空格；
  • 多空格；
  • 制表符；
  • 换行；
  • Windows 与 Unix 换行；
  • 行尾空格。

标点变换

  • 中文与英文标点；
  • 全角与半角；
  • 连字符、短横线和下划线；
  • 冒号前后空格；
  • 引号类型；
  • Markdown 分隔符。

Unicode 变换

  • 组合字符与预组合字符；
  • 不可见字符；
  • 零宽字符；
  • 非断行空格；
  • 大小写；
  • 规范化形式。

业务字段变换

  • 数字是否带千分位；
  • 日期格式；
  • 版本号前缀；
  • 路径分隔符；
  • UUID 大小写；
  • JSON 字段顺序；
  • 错误码前缀。

观测指标

  • 输入 Token 数；
  • 输出是否满足 schema；
  • 精确字段复制正确率；
  • 任务成功率；
  • 重试次数；
  • 输入成本；
  • 首 Token 时延；
  • 总时延。

测试必须保持语义和预期不变。

如果同时改变语义、长度和格式，就无法判断是哪个因素导致差异。

经过多层注意力和前馈网络后，同一个 Token 在不同上下文中的隐藏状态会不同。

因此，固定的 Token Embedding 与上下文化后的隐藏状态不能混为一谈。

2. 检索 Embedding 又是另一层产品能力

RAG 常用的文本 Embedding 通常由专门的编码模型生成一个句子或片段向量。

它可能使用池化、专门训练目标和不同维度。

不能拿“生成模型内部 Token Embedding”的解释，直接替代“检索向量”的行为说明。

二者共同使用向量，但用途、训练目标和评测方式不同。

4. 相似但错误的高风险模式

否定词变化

“允许”和“不允许”只差一个否定成分。

数字变化

“超时 5 秒”和“超时 50 秒”语义主题高度相似。

方向变化

“服务 A 调用服务 B”和“服务 B 调用服务 A”词集合近似。

版本变化

“适用于 2.9”与“适用于 2.10”只差很少字符。

权限范围变化

“管理员可删除”和“普通用户可删除”可能被召回到一起。

时间状态变化

旧政策和新政策可能只是日期不同。

这些字段需要元数据过滤、词法召回、重排、规则校验或结构化查询共同处理。

不能仅通过提高一个全局余弦阈值解决。

5. Embedding 测试集必须包含 Hard Negative

随机选择完全无关的负样本太容易。

真正有价值的负样本应当“看起来很像，但业务上不能使用”。

每个查询至少准备：

  • 一个正确正样本；
  • 一个主题相同但版本错误的负样本；
  • 一个数字不同的负样本；
  • 一个否定关系相反的负样本；
  • 一个权限范围错误的负样本；
  • 一个过期负样本；
  • 一个来源等级不足的负样本。

然后分别计算：

  • Recall@K；
  • Precision@K；
  • MRR 或 nDCG；
  • 正负样本间隔；
  • 关键负样本进入 Top-K 的比例；
  • 元数据过滤前后的变化；
  • 重排前后的变化。

如果业务风险不对称，还需要对错误类型加权。

例如，召回一个无关帮助文档可能只是低质量。

召回一条过期的生产变更指令可能导致事故。

这两类 False Positive 不应具有相同权重。

2. Self-Attention 不是一次计算

真实 Transformer 通常包含：

  • 多个注意力头；
  • 多层注意力模块；
  • 前馈网络；
  • 残差连接；
  • 归一化；
  • 位置机制；
  • 可能存在的稀疏或高效注意力实现。

一个头在一层里的权重，不能代表模型的完整推理过程。

把某张注意力热力图当作最终解释，风险很高。

它最多是某个内部信号。

还必须用输入干预和行为变化做验证。

3. 注意力权重高不等于因果重要性

如果移除一个片段后结果不变，仅凭它获得较高注意力权重，不能证明它决定了答案。

反过来，一个片段在某个头上的权重不高，也不能证明它没有通过其他层、其他头或残差路径影响输出。

更可靠的黑盒测试方法是：

  • 删除该证据；
  • 替换该证据；
  • 移动该证据；
  • 加入矛盾证据；
  • 保持长度不变地置换该证据；
  • 比较输出和置信统计。

这类干预实验直接观察行为变化。

4. 序列长度增加带来的计算压力

标准稠密注意力中的 QK^T 会形成与序列长度平方相关的矩阵。

因此，从理论基线看，注意力计算和内存会随长度快速增长。

生产系统可能通过 FlashAttention、分页 KV Cache、稀疏注意力、滑动窗口、分块或其他实现优化。

不能仅凭模型名称推断服务端具体实现。

测试应观测：

  • 预填充时延；
  • 首 Token 时延；
  • 解码吞吐；
  • 峰值显存或服务端资源；
  • 超时率；
  • 并发下的排队时延；
  • 长输入对其他请求的干扰。

“窗口支持”属于功能能力。

“在目标并发和 SLA 下可用”属于系统能力。

二者必须分别验证。

八、位置：没有位置信息，顺序就会丢失

1. 顺序为什么必须显式进入模型

Self-Attention 的基础计算本身不会天然理解序列位置。

“A 调用 B”和“B 调用 A”包含相同 Token 集合，但顺序语义不同。

模型需要某种位置表示把顺序关系带入计算。

原始 Transformer 论文使用正弦和余弦位置编码。

后续模型也可能采用学习位置、相对位置、旋转位置编码等方法。

具体实现属于模型架构事实，不能在供应商未披露时猜测。

2. RoPE 的测试意义

RoPE 通过对查询和键应用与位置相关的旋转，把相对位置信息带入点积关系。

理解它的工程价值不是为了在黑盒 API 上恢复内部角度。

而是认识到：

  • 位置不是普通文本字段；
  • 超出训练分布的长度可能涉及外推问题；
  • 不同位置扩展技术可能改变长上下文表现；
  • 模型升级后必须重跑位置敏感测试。

九、上下文窗口：容量、协议和输出共同竞争预算

1. 上下文中不只有用户输入

一次聊天或 Agent 请求可能包含：

  • 系统指令；
  • 开发者指令；
  • 用户问题；
  • 历史对话；
  • RAG 文档；
  • 工具 schema；
  • 工具返回；
  • 图片或音频表示；
  • 安全策略；
  • 输出格式示例；
  • 已生成的输出。

用户看到的文本可能只是总上下文的一部分。

当工具数量增加时，schema 本身也可能成为显著开销。

当历史对话持续累积时，旧轮次可能挤压当前证据。

2. 输出预算不足也是上下文故障

模型正确理解任务，但输出在 JSON 中段结束，会表现为解析失败。

这不等于模型不会生成 JSON。

需要先查看：

  • 结束原因；
  • 实际输出 Token 数；
  • 最大输出限制；
  • 是否触发服务端内容过滤；
  • 是否发生网络中断；
  • 流式响应是否被客户端提前关闭。

测试报告不能把所有不完整输出都归为 schema failure。

3. KV Cache 不等于无限记忆

自回归解码常缓存历史 Token 的 Key 和 Value，以避免每一步重复计算全部历史。

KV Cache 是推理优化和状态载体。

它不会把窗口外信息变回窗口内信息。

会话缓存、Prompt Cache 和业务长期记忆也不是同一个概念。

测试平台应分别记录：

  • 请求实际上下文；
  • 服务端缓存命中信息；
  • 业务记忆读取结果；
  • 会话摘要版本；
  • 模型可见的最终内容。

十、截断：先确认信息是否真的进入模型

1. 截断可能发生在五个位置

数据源层

日志采集器只保留尾部，原始首错已经丢失。

检索层

召回器返回了文档，但重排或 Top-K 限制排除了关键片段。

拼装层

Prompt Builder 为满足预算主动裁掉某些文档。

网关层

网关按照自己的估算压缩历史或拒绝超限请求。

模型服务层

服务端拒绝、裁剪或按产品规则处理过长输入。

各层必须有独立事件。

只看最终错误码无法还原裁剪位置。

2. 静默截断为什么危险

如果系统悄悄删除内容后继续请求，模型可能给出流畅答案。

用户看到的是“有答案”，而不是“证据缺失”。

在高风险任务中，正确行为通常应是：

  • 拒绝继续；
  • 明确报告缺失；
  • 重新检索；
  • 分阶段处理；
  • 请求用户缩小范围。

平台不应把流畅性当作完整性证据。

3. 用边界哨兵检测截断

可以在每个候选片段加入机器可核对的 ID：

这并不要求模型复述所有 ID。

平台应在发送前保存最终片段清单和哈希。

测试任务可以额外询问某个唯一哨兵，验证该位置是否仍可访问。

哨兵法的限制是：

  • 模型未回答哨兵不必然说明哨兵被截断；
  • 它也可能是位置利用失败；
  • 因此还要核对请求构建日志和服务端用量。

只有“请求证据”和“行为证据”一致，才可以确认截断。

4. 不要默认“保留最后 N 个 Token”是合理策略

保留尾部可能删除系统约束。

保留头部可能删除用户当前问题。

只保留最近对话可能丢掉最初的任务定义。

更可靠的裁剪策略需要优先级：

  1. 不可删除的系统安全约束；
  2. 当前任务与输出契约；
  3. 已验证的关键证据；
  4. 当前工具状态；
  5. 必要历史摘要；
  6. 可丢弃的示例和低相关背景。

当高优先级内容仍然超限时，应拒绝或拆分任务。

十一、上下文污染：信息更多也可能让结果更差

1. 污染不是单纯“内容太长”

污染指加入的内容降低了任务信噪比或引入错误约束。

常见污染源包括：

  • 过期文档；
  • 重复文档；
  • 互相矛盾的规则；
  • 未标明来源的人工笔记；
  • 与任务相似但不适用的版本；
  • 网页中的间接提示注入；
  • 历史轮次中的旧目标；
  • 工具返回里的错误说明文本；
  • 自动摘要遗漏的限定条件。

2. 长度效应和污染效应必须分开

假设加入一段旧政策后准确率下降。

可能有两个原因：

  • 上下文更长导致位置或预算变化；
  • 旧政策与新政策产生冲突。

应设计等长对照：

组别 总 Token 新政策 旧政策 无关填充
Clean 相同 有 无 有
Conflict 相同 有 有 无
Old only 相同 无 有 有

如果 Clean 明显优于 Conflict，才支持“冲突污染”假设。

如果两组都随长度下降，更可能存在长度或位置问题。

3. 污染降级指标

设干净基线准确率为 A_{clean}，注入某类污染后的准确率为 A_c。

还应记录污染导致的具体错误：

  • 错误引用率；
  • 过期规则采用率；
  • 冲突未报告率；
  • 越权指令服从率；
  • 无证据断言率；
  • 拒绝率变化。

仅报告总准确率会掩盖高风险少数错误。

4. 对抗污染不等于再写一句“忽略错误资料”

提示词约束是控制的一部分，但不能替代：

  • 来源白名单；
  • 版本与有效期过滤；
  • 权限过滤；
  • 内容去重；
  • 冲突检测；
  • 指令和数据隔离；
  • 输出引用校验；
  • 高风险场景的程序化拒绝。

上下文是数据面。

系统约束和执行器是控制面。

不能让数据面里的任意文本覆盖控制面权限。

十二、把机制问题转成可度量指标

1. 精确成功率

硬断言应包括业务字段，而不仅是文本相似。

例如：

  • JSON 可解析；
  • status 等于 DENY；
  • policy_version 等于 7；
  • evidence_id 属于允许集合；
  • 金额精确相等。

2. 指令保持率

给上下文加入多个可独立检查的约束。

约束应分级。

安全约束失败不能被普通格式约束成功抵消。

3. 精确复制率

适用于错误码、版本号、订单号和哈希。

4. 位置敏感度

除了 \Delta_{position}，还应报告每个位置的置信区间。

样本量较小时，不能把 7 次成功对 6 次成功解读成稳定差异。

可使用二项比例的 Wilson 区间。

5. Token 效率

这个指标用于比较同一任务的上下文拼装方案。

它不是跨任务模型排名。

6. 截断拒绝正确率

当必需证据无法完整纳入时，系统应该拒绝。

还要统计错误拒绝，避免系统为了安全而不可用。

7. 冲突显式化率

高风险问答不应在证据冲突时强行选择一个答案。

十三、对照实验：一次只改变一个变量

1. 固定项

每轮实验必须固定：

  • 模型快照；
  • API 版本；
  • Tokenizer；
  • 系统指令；
  • 输出 schema；
  • 温度与其他采样参数；
  • 最大输出长度；
  • 干扰材料集合；
  • 请求并发；
  • 重试策略；
  • 判定器版本。

如果服务支持 seed，可以记录并使用。

但 seed 不应被当作跨硬件、跨服务实现的绝对可重复保证。

2. 变量项

一次只改变一种：

  • 分隔符；
  • 证据位置；
  • 上下文长度；
  • 污染类型；
  • 文档顺序；
  • 重复数量；
  • 证据版本；
  • 输出预留。

3. 重复次数

生成式模型存在采样和服务波动。

一次运行只能证明“这一次发生了什么”。

不能证明稳定概率。

重复次数取决于：

  • 预期差异大小；
  • 可接受误差；
  • 调用成本；
  • 风险等级；
  • 是否需要统计显著性。

对于质量门禁，应预先规定样本量和通过规则。

不要看到结果后再挑一个有利阈值。

4. 基线组

每个实验都需要一个最小干净基线。

基线只保留：

  • 必要系统约束；
  • 唯一正确证据；
  • 当前问题；
  • 输出格式。

如果基线本身不稳定，先不要扩大上下文。

5. 位置组

关键证据依次放在：

  • 最前；
  • 前四分之一；
  • 中间；
  • 后四分之一；
  • 最后。

其他段落做位置轮换，保证总长度不变。

6. 截断组

逐级增加填充长度。

每一级都保存：

  • 本地 Token 数；
  • 服务端 Token 数；
  • 片段纳入清单；
  • 边界哨兵结果；
  • 结束原因。

7. 污染组

分别注入：

  • 重复；
  • 过期；
  • 数字冲突；
  • 否定冲突；
  • 低权威来源；
  • 间接指令；
  • 不相关长文本。

不要一次混合所有污染。

否则只能得出“脏上下文更差”，无法制定具体治理动作。

脚本使用服务端返回的 usage.prompt_tokens 校验长度控制。比较 position-middle 与 middle-with-conflict 时，如果两组的 prompt_tokens 不一致，就应把该对样本标为无效，继续按目标模型的真实 Tokenizer 调整中性块，不能用字符数相近代替等 Token。若需要报告证据的 Token 相对位置，也必须用同一模型版本的 Tokenizer 对最终消息模板和上下文前缀重新计数；relative_char_position 只用于发现明显的构造错误。

因为重试会掩盖首错。

如果平台需要重试，应分别保存：

  • 首次结果；
  • 重试触发原因；
  • 重试参数是否变化；
  • 每次结果；
  • 最终对用户展示的结果。

如何解读结果

如果所有位置都失败：

  • 先检查任务和 schema；
  • 检查模型是否能完成干净基线；
  • 检查 NEEDLE 是否实际进入请求；
  • 不要先下“中间信息弱化”结论。

如果只有中间显著下降：

  • 增加重复次数；
  • 交换干扰文档顺序；
  • 核对总 Token 数；
  • 排除中间位置恰好发生裁剪；
  • 再判断位置敏感。

如果加入冲突后下降：

  • 比较等长 Clean 组；
  • 检查输出引用；
  • 判断模型是否采用过期来源；
  • 检查系统是否应该报告冲突而不是选择答案。

如果输出经常不是 JSON：

  • 检查输出预算和结束原因；
  • 单独评测 schema 遵循；
  • 不要把格式失败算作证据检索失败。

十五、诊断矩阵：从症状到可证伪假设

诊断矩阵的核心不是“看到症状就套答案”。

而是为每个假设规定最小证据。

假设 H1：Token 边界敏感

支持证据：

  • 语义不变；
  • 只有边界写法变化；
  • Token 切分或数量变化；
  • 结果差异可以重复；
  • 模型、采样和长度均固定。

反证：

  • 不同写法最终 Token 序列相同；
  • 差异只出现一次；
  • 同时改变了字段含义；
  • 输出被截断。

假设 H2：发生截断

支持证据：

  • 最终请求构建日志显示片段被排除；
  • 服务端返回超限或结束原因；
  • 边界哨兵在固定长度阈值后消失；
  • 输入用量与期望不一致；
  • 缩短输入后同一证据恢复。

反证：

  • 最终序列确认包含完整证据；
  • 证据移动到其他位置即可恢复；
  • 输入长度远低于实测边界；
  • 同位置短文本也失败。

假设 H3：位置利用不足

支持证据：

  • 同一证据只改变位置；
  • 总长度不变；
  • 干扰项不变；
  • 位置准确率曲线可重复；
  • 请求未发生裁剪。

反证：

  • 不同位置伴随不同文档；
  • 中间位置刚好存在冲突；
  • 样本量不足；
  • 模型快照发生变化。

假设 H4：上下文污染

支持证据：

  • 等长条件下，注入特定污染后下降；
  • 移除污染后恢复；
  • 错误答案能追踪到污染来源；
  • 冲突检测未触发或来源优先级错误。

反证：

  • 仅长度增加就同样下降；
  • 污染内容未进入最终请求；
  • 基线本身不稳定；
  • 判定器把合理拒绝误判为失败。

十六、示例案例：审批码在上下文中间“消失”

下面是一个用于说明诊断方法的示例案例。

它不是对任何真实项目经历的陈述。

1. 场景

一个发布审批助手读取 30 份变更材料。

系统要求返回：

权威文档 policy-v7 明确写着：

模型偶尔返回 ALLOW，并引用另一份旧文档 policy-v3。

2. 最初的错误归因

团队最初认为：

模型窗口太小，没有看到 policy-v7。

于是把文档拼得更长，并在 Prompt 里重复三次“请认真阅读全部文档”。

错误率反而上升。

3. 第一轮：确认是否截断

测试保存最终片段清单。

policy-v7 的开始、结束哨兵都在请求中。

服务端输入用量也低于实测上限。

输出结束原因正常。

这组证据不支持截断假设。

4. 第二轮：做位置扫描

保持 30 份文档内容不变。

只交换 policy-v7 的位置。

示例结果：

位置 成功次数 总次数
开头 19 20
前四分之一 18 20
中间 12 20
后四分之一 17 20
结尾 19 20

这支持位置敏感假设。

但仍不能解释为什么错误答案恰好来自 policy-v3。

5. 第三轮：等长污染对照

测试构造三组：

  • Clean：policy-v7 加等长无关文档；
  • Conflict：policy-v7 加过期 policy-v3；
  • Old only：只有 policy-v3。

Conflict 组显著低于 Clean 组。

错误输出多次引用 policy-v3。

这说明问题不是单纯“中间弱化”。

过期文档冲突放大了位置敏感。

6. 根因拆分

该示例至少包含两个机制：

  1. 模型在此任务和上下文结构下表现出位置敏感；
  2. 系统没有在模型调用前处理版本冲突。

第一项属于模型行为和上下文组织。

第二项属于知识治理。

把两者合并成“模型没认真读”，没有工程意义。

7. 修复

系统做了以下调整：

  • 检索阶段按 policy_id 聚合版本；
  • 只保留当前有效版本；
  • 将证据版本和有效期写入结构化元数据；
  • 发现冲突时输出 UNKNOWN 并列出冲突；
  • 先抽取 gate_code，再生成解释；
  • 关键字段用程序精确校验；
  • 将位置扫描纳入模型升级回归。

修复后的重点不是某次回答正确。

而是：

  • 过期文档不会进入正常决策上下文；
  • 冲突不会被静默吞掉；
  • 精确字段有硬断言；
  • 模型升级后可以重复验证。

十七、按故障层选择修复，不要统一“调 Prompt”

1. Token 边界问题

优先动作：

  • 输入规范化；
  • 使用稳定的结构化字段；
  • 固定分隔符；
  • 记录模型对应 Tokenizer；
  • 关键 ID 由程序传递和校验；
  • 对格式等价变换做变形测试。

不推荐：

  • 仅凭字符数估算预算；
  • 通过更多自然语言描述精确 ID；
  • 用一个模型的 Token 比例外推所有模型。

2. Embedding 相似性问题

优先动作：

  • 建 Hard Negative；
  • 混合词法与向量召回；
  • 加版本、权限和时间过滤；
  • 对候选进行重排；
  • 对数字、否定和主体关系做硬校验；
  • 对高风险证据要求引用。

不推荐：

  • 把余弦阈值当成真值阈值；
  • 只测随机无关负样本；
  • 仅凭召回分数决定可执行动作。

3. 位置利用问题

优先动作：

  • 删除无关上下文；
  • 把当前任务和输出契约保持清晰；
  • 将检索与证据抽取分阶段；
  • 关键证据附近保留来源和字段名；
  • 对目标模型做位置扫描；
  • 模型升级后重新标定。

不推荐：

  • 无限重复同一指令；
  • 把关键证据复制到所有位置；
  • 将论文中的位置曲线当作本地固定规律。

4. 截断问题

优先动作：

  • 请求前精确预算；
  • 明确输出预留；
  • 保存纳入与排除清单；
  • 超限时拒绝或拆分；
  • 记录结束原因；
  • 核对本地与服务端用量。

不推荐：

  • 静默删除尾部；
  • 只保留最近消息；
  • 把不完整 JSON 当成模型格式能力差。

5. 上下文污染问题

优先动作：

  • 来源分级；
  • 版本和有效期；
  • 去重；
  • 冲突检测；
  • 指令与资料隔离；
  • 输出引用校验；
  • 高风险不确定状态。

不推荐：

  • 依靠一句“忽略错误内容”；
  • 把所有召回内容无差别拼接；
  • 让低信任文档覆盖系统策略。

十八、测试平台应怎样记录上下文证据

一条可审计的上下文记录可以采用下面的 JSON 结构。

敏感正文是否落盘需要遵守数据策略。

无法保存正文时，至少保存可复现的版本、哈希和受控引用。

这个结构有四个作用。

可复现

知道模型、Tokenizer、模板、证据版本和顺序。

可归因

能够区分召回、拼装、截断、生成和判定。

可审计

知道模型依据了什么，排除了什么。

可回归

模型、模板或检索策略升级后，可以重放同一组上下文条件。

二十、常见误区

误区 1：字符数可以稳定换算 Token 数

错误。

语言、格式、词表和 Tokenizer 都会影响切分。

应对目标模型实测。

误区 2：Embedding 相似度高就说明答案正确

错误。

相似度不是蕴含、有效期、权限或精确数字校验。

误区 3：注意力权重就是模型解释

不充分。

单层单头权重不能代替行为干预和因果证据。

误区 4：信息在窗口里，模型就一定能使用

错误。

窗口容量和有效利用是两个维度。

误区 5：中间失败一定是 Lost in the Middle

错误。

先排除截断、冲突、长度变化和随机波动。

误区 6：扩大窗口总会改善效果

错误。

更长的上下文也可能带来更多噪声、冲突、成本和时延。

误区 7：温度设为 0 就完全确定

不应这样假设。

服务实现、并行计算、模型快照和其他采样细节仍可能带来差异。

应以重复试验观察实际稳定性。

误区 8：截断只发生在模型服务

错误。

采集、检索、拼装、网关和客户端都可能先裁剪。

误区 9：重复关键指令可以解决位置问题

重复会消耗预算，也可能引入冲突。

更好的方法是缩短上下文、结构化证据和分阶段处理。

误区 10：模型换代后旧结论仍然成立

不一定。

Tokenizer、模板、位置机制和服务实现都可能变化。

必须重跑基线。

二十一、上线前检查表

输入与 Tokenizer

  • 是否记录模型快照和 Tokenizer 标识；
  • 是否使用目标 Tokenizer 计算预算；
  • 是否覆盖中文、英文、代码和结构化数据；
  • 是否测试空格、标点和 Unicode 等价变换；
  • 是否对关键 ID 做精确断言；
  • 是否比较本地和服务端 Token 用量。

上下文拼装

  • 是否保存最终纳入片段的顺序；
  • 是否保存被排除片段及原因；
  • 是否为输出保留明确预算；
  • 是否禁止静默截断；
  • 是否区分系统指令、证据和非可信数据；
  • 是否有版本、有效期和来源等级。

位置与长度

  • 是否做至少五个位置的扫描；
  • 是否保持总长度和干扰项一致；
  • 是否在多个长度档位运行；
  • 是否覆盖边界附近和明确超限；
  • 是否记录结束原因；
  • 是否对每个位置重复足够次数。

Embedding 与召回

  • 是否包含否定、数字、版本等 Hard Negative；
  • 是否评估过滤前后的差异；
  • 是否评估重排前后的差异；
  • 是否把高风险错误单独加权；
  • 是否要求关键结论携带来源；
  • 是否用程序校验精确字段。

污染与安全

  • 是否测试重复、过期和矛盾资料；
  • 是否做等长 Clean 对照；
  • 是否测试间接提示注入；
  • 是否在冲突时进入 UNKNOWN 或人工复核；
  • 是否阻止资料文本提升自身权限；
  • 是否保存冲突检测结果。

观测与回归

  • 是否保存原始输出和首错；
  • 是否区分首次和重试结果；
  • 是否记录时延、成本和用量；
  • 是否记录判定器版本；
  • 是否在模型、模板、SDK、网关升级后重跑；
  • 是否按失败类型输出诊断，而不是统一标记模型错误。

二十二、总结

Token 决定模型看到的离散边界和实际预算。

Embedding 把离散单元映射到连续空间，但相似性不等于业务真值。

Self-Attention 让序列中的信息发生交互，但它不是一次万能检索，也不能用单张权重图解释完整行为。

位置机制让顺序进入计算，而长上下文中的位置鲁棒性必须通过目标任务实测。

上下文窗口描述容量边界，不等于实际送达、有效利用或业务可信。

对测试开发工程师而言，最重要的不是把这些术语背下来。

而是把每个机制变成可证伪的假设：

  • 怀疑 Token，就做等义边界变换并记录真实切分；
  • 怀疑截断，就核对最终请求、用量、哨兵和结束原因；
  • 怀疑位置，就做等长位置扫描；
  • 怀疑污染，就做等长冲突注入；
  • 怀疑 Embedding，就构造业务 Hard Negative；
  • 怀疑模型不稳定，就先固定模型、模板、参数和判定器并重复运行。

只有这样，“模型没有理解上下文”才会从一句模糊判断，变成可以定位、修复和回归的质量问题。
