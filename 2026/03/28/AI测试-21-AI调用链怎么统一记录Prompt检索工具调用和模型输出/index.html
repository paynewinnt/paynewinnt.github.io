AI测试-21-AI调用链怎么统一记录Prompt检索工具调用和模型输出

发表于 2026-03-28 分类于 AI测试 本文字数： 12k 阅读时长 ≈ 42 分钟

一个普通 HTTP 接口失败时，测试和运维通常会沿着下面的线索定位：

  • request ID
  • 服务日志
  • 数据库调用
  • 下游 RPC
  • 错误码
  • 时延分布

AI 应用的链路更长。

一次用户请求可能先后经过：

  • Prompt 模板渲染
  • 历史会话裁剪
  • 查询改写
  • 向量检索
  • 文档重排
  • 第一次模型生成
  • 工具参数解析
  • 外部工具执行
  • 第二次模型生成
  • Guardrail
  • LLM Judge
  • 结果持久化

最终现象可能只是：

如果系统只记录最终 Prompt 和最终回答，团队很难回答：

  • 慢在排队、检索、模型首 Token，还是工具重试
  • 错在知识没有召回，还是模型忽略了正确证据
  • 工具到底有没有执行成功
  • 模型说“已经完成”时，外部状态是否真的改变
  • Judge 为什么给出失败
  • 这次请求使用的是哪一版 Prompt、索引和工具 Schema
  • 日志里是否已经泄漏了用户隐私或访问令牌

因此 AI 可观测性的目标不能只是“多打印一些日志”。

它需要把 Prompt、Retrieval、Model、Tool、Judge 和最终 Outcome 放进同一条可关联、可查询、可脱敏的证据链。

本文从平台工程和测试视角，设计一套不绑定单一厂商的统一调用链模型。

核心思路来自分布式追踪和 OpenTelemetry，但不会把系统锁死在某个后端产品上。

本文重点解决：

  • Trace、Span、Event、Log、Metric、Artifact 分别记录什么
  • trace ID 与业务 ID 怎样分工
  • Prompt 和 RAG 怎样版本化
  • 模型逻辑调用与物理重试怎样建模
  • TTFT、总时延和 Token 怎样定义
  • 失败原因怎样归到第一个有意义的责任层
  • 敏感内容怎样在采集前脱敏
  • 怎样测试调用链自身是否完整、准确和可用

一、问题边界：可观测性不是无限制记录原文

在进入数据模型前，先明确四个边界。

1. 调用链不是模型思维读取器

可观测系统应记录可被系统直接观察的事实：

  • 输入消息
  • 模型响应
  • 工具调用
  • 工具结果
  • 检索文档
  • 外部状态
  • 评分结果
  • 时延与资源使用

它不应该声称还原模型内部真实推理过程。

如果服务提供了 reasoning summary 或其他可见字段，应把它当成一种模型输出 Artifact。

不能把它等同于完整、忠实的内部因果解释。

2. Trace 不应该成为内容数据库

Trace 后端擅长：

  • 按 trace ID 查询
  • 展示父子 Span
  • 聚合状态和时延
  • 定位错误节点

它通常不适合长期存放：

  • 完整 Prompt
  • 大段检索文档
  • 工具返回的大型 JSON
  • 图片和音频
  • 长篇 Judge 理由

这些内容既大，又可能高度敏感。

更合理的设计是：

  • Trace 保存可索引元数据
  • Artifact 存储保存受控内容
  • Trace 通过 URI 与摘要关联 Artifact

3. 记录到遥测系统不等于可以公开访问

AI 调用内容可能包含：

  • 个人身份信息
  • 用户会话
  • 医疗或财务信息
  • 内部知识库
  • 源代码
  • API Key
  • Cookie
  • 工具访问令牌

因此采集策略必须先于导出策略。

“先全部写到 Trace，再在查询界面隐藏”并不安全。

敏感内容一旦进入采集管道、队列和后端副本，泄漏面已经扩大。

4. 可观测性不能替代业务真值

Trace 可以告诉我们模型调用成功并返回 200。

它不能自动证明：

  • 订单真的创建成功
  • 退款金额正确
  • 引用内容符合最新政策
  • 回答对用户有帮助

所以调用链必须同时保留两类结果：

  • operation status：这一跳技术上是否完成
  • business outcome：最终业务目标是否达成

二者不能混为一个 success 字段。

二、为什么普通日志在 AI 链路里很快失效

很多系统最初使用下面的日志：

单看每一行都没有错。

但它存在七个结构性问题。

1. 无法可靠关联

并发请求混在同一个日志流里。

如果每一行没有统一 trace ID，无法确认哪些记录属于同一用户请求。

2. 无法表达父子关系

一次模型逻辑调用可能重试三次。

普通日志很难直接表达：

  • 哪个是逻辑操作
  • 哪个是物理 attempt
  • 哪次失败
  • 哪次最终成功

3. 无法表达并行与异步

Agent 可能并行调用多个工具。

消息队列 Consumer 可能在 Root 请求结束后继续执行。

线性日志顺序不等于真实因果顺序。

4. 字段语义不统一

不同组件可能分别使用：

  • model
  • model_name
  • deployment
  • engine
  • provider_model

如果没有语义约定，跨组件查询和聚合会不断写适配代码。

5. 无法区分大内容与索引字段

团队为了定位问题，往往直接把 Prompt 和响应打印进日志。

结果是：

  • 日志量快速膨胀
  • 高基数字段拖慢查询
  • 隐私范围失控
  • 保留和删除难以治理

6. 时延定义不一致

“模型耗时 5 秒”可能指：

  • 从业务层开始组装请求到返回
  • 从网络请求发出到首 Token
  • 从网络请求发出到最后 Token
  • 包含重试后的总逻辑耗时
  • 单次物理请求耗时

没有边界定义，数字不可比较。

7. 成功状态容易说谎

HTTP 200 只说明服务返回成功。

返回内容可能：

  • 解析失败
  • 被 Guardrail 拒绝
  • 没有满足任务
  • 工具调用参数非法
  • 引用不存在

所以 AI 链路需要比普通 success 日志更细的状态模型。

三、统一观测模型：六类对象各负其责

先定义六个基础对象。

1. Trace

Trace 表示一个端到端工作流。

常见边界是：

Trace 负责回答：

  • 这次请求经历了哪些阶段
  • 阶段之间是什么因果关系
  • 总体在哪里失败或变慢

2. Span

Span 表示一个有开始和结束时间的操作。

典型 Span：

  • prompt.render
  • retrieval.query
  • retrieval.rerank
  • model.generate
  • tool.execute
  • judge.evaluate

Span 适合记录：

  • 操作名称
  • 开始与结束时间
  • 父 Span
  • 属性
  • 状态
  • 事件
  • Link

3. Event

Event 是 Span 生命周期中的一个时间点。

适合表示：

  • 收到首 Token
  • 开始重试
  • Guardrail 拒绝
  • 流式连接被用户取消
  • Artifact 写入完成

如果一个动作有独立持续时间并且对性能分析有价值，更适合建 Span。

如果只是瞬时状态变化，更适合建 Event。

4. Log

Log 用于记录离散业务或诊断事件。

结构化 Log 应附带：

  • trace_id
  • span_id
  • severity
  • event.name
  • error.type
  • 经过脱敏的字段

这样 Log 可以和 Trace 相互跳转。

5. Metric

Metric 用于低成本聚合趋势：

  • 请求量
  • 错误率
  • TTFT 分布
  • 端到端时延
  • Token 使用
  • 工具失败率
  • 检索空结果率

Metric 不适合携带：

  • 用户 ID
  • Prompt 摘要
  • 文档 ID 列表
  • request ID

这些高基数标签会导致时序数量爆炸。

6. Artifact

Artifact 保存需要受控访问的大内容：

  • 脱敏后的 Prompt
  • 检索片段
  • 模型完整输出
  • 工具参数与结果
  • 图片、音频
  • Judge 理由
  • 环境状态快照

Trace 中只保存：

  • artifact URI
  • 内容摘要
  • 数据分类
  • 大小
  • 编码
  • 保留策略 ID

四、拓扑图：父子 Span、重试与异步 Link

图中有三个重要设计。

1. Root Span 覆盖业务工作流

Root Span 不应只覆盖第一次模型 HTTP 请求。

它应覆盖用户可感知的完整业务边界。

否则：

  • 工具调用发生在 Trace 外
  • 第二次模型总结无法关联
  • 端到端时延被低估

2. 逻辑调用与物理 attempt 分开

假设模型调用最多重试两次。

可以建模为：

逻辑 Span 表示业务层看到的一次调用。

attempt Span 表示实际发出的每一次请求。

这样可以同时得到：

  • 逻辑成功率
  • 首次成功率
  • 重试次数
  • 每次物理错误
  • 重试增加的时延和 Token

3. 异步关系使用 Span Link

一个 Span 在标准父子模型里只有一个直接父上下文。

但异步和批处理经常存在多来源关系：

  • 多个请求合并成一个 Batch
  • 消息 Consumer 与 Producer 分离
  • 工具结果晚于 Root 请求到达
  • 一个评测任务引用多个生产 Trace

这时不要伪造树形父子关系。

使用 Span Link 表达关联更准确。

五、ID 体系：Trace ID 不是所有 ID 的替代品

一条调用链通常至少需要八类 ID。

1. trace_id

表示端到端 Trace。

W3C Trace Context 中 trace ID 是 16 字节，也就是 32 个小写十六进制字符。

全 0 是非法值。

它用于跨服务传播和关联 Span。

2. span_id

表示一个 Span。

W3C Trace Context 中 span ID 是 8 字节，也就是 16 个小写十六进制字符。

全 0 同样非法。

3. parent_span_id

表示直接父操作。

它帮助后端重建 Trace 树。

4. request_id

表示 API Gateway 或业务服务的一次请求。

它可能早于 Trace 创建，也可能由外部系统定义。

request ID 适合业务查询，但不应替代 trace ID 的分布式传播语义。

5. session_id

表示多轮会话。

一个 session 通常包含多个 Trace。

不要把整个长会话都做成一个持续数小时的 Span。

更稳妥的是：

  • 每轮请求一个 Trace
  • session ID 用作关联字段
  • 长期异步任务单独建 Trace，并通过 Link 关联

6. eval_run_id

表示一次评测或回归运行。

一个 eval run 通常包含成百上千个 Trace。

它适合放在 Trace 属性或受控 Baggage 中，但要注意基数和信任边界。

7. tool_call_id

关联：

  • 模型提出的工具调用
  • 工具执行 Span
  • 工具返回结果
  • 后续模型消息

同一工具的重试还应有独立 attempt ID。

8. artifact_id

表示内容证据对象。

它应支持：

  • 权限检查
  • 生命周期
  • 摘要校验
  • 删除
  • 访问审计

传播规则

跨 HTTP、RPC 或消息边界时：

  1. 上游注入当前上下文
  2. 下游校验并提取
  3. 下游创建新的 Span
  4. 新 Span 使用提取到的上下文作为远端父

常用 Web 和 RPC 框架的 OpenTelemetry Instrumentation 可以自动完成。

自定义协议和消息体需要显式适配。

不要信任外部输入的 traceparent

traceparent 是外部输入。

服务应：

  • 校验长度和字符
  • 拒绝非法全 0 ID
  • 限制 Header 大小
  • 防止解析异常
  • 在安全边界评估是否重新开始 Trace

W3C 规范允许在特定信任边界重启 Trace。

如果重启，为了内部调查可以在受控字段中记录旧 Trace 的 HMAC 关联值。

不要把未经信任的原始值直接传播到所有内部系统。

tracestate 不能放业务秘密

tracestate 用于厂商或追踪系统的扩展状态。

它不应该保存：

  • 用户名
  • 邮箱
  • 订单号
  • Prompt
  • Token
  • 内部权限

W3C 规范明确要求不要在 tracestate 中放个人可识别信息。

Baggage 也要谨慎

Baggage 会随上下文跨服务传播。

它适合低敏、必要的关联信息。

它不自动等于安全存储。

建议只允许白名单字段，例如：

  • environment
  • deployment_ring
  • eval_suite

不要传播：

  • 原始 user ID
  • 会话内容
  • API Key
  • 文档正文
  • 权限 Token

  • score type
  • producer revision
  • rank

  • 私钥
  • 数据库密码

P3 不应进入遥测和 Artifact。

应在采集前直接删除。

脱敏顺序

推荐顺序：

  1. 字段白名单
  2. Secret 检测与丢弃
  3. PII 识别
  4. 确定性字段遮盖或 Tokenization
  5. 内容截断
  6. Artifact 加密
  7. 写入摘要和分类
  8. 导出遥测

不要先导出，再依赖 Collector 末端补救。

业务 SDK 端和 Collector 端可以双层防护。

Prompt 中的嵌套敏感信息

只按 JSON 字段名脱敏不够。

Prompt 可能把敏感字段嵌入自然语言：

因此需要：

  • 结构化字段脱敏
  • 文本内容检测
  • 工具参数专用规则
  • 模态专用规则

图片和音频也可能含个人信息。

保留与删除

需要明确：

  • Trace 保留多久
  • Artifact 保留多久
  • 哪些场景允许延长
  • 用户删除请求怎样传播
  • 摘要和索引是否同步删除
  • 备份何时过期

Trace 和 Artifact 分库存储后，删除流程必须能跨库追踪。

权限

至少区分：

  • 只看聚合 Metric
  • 查看 Trace 元数据
  • 查看脱敏 Artifact
  • 查看高敏 Artifact
  • 导出
  • 修改保留策略

所有 Artifact 访问都应有审计。

二十一、采样：Trace 可以采样，核心指标不能跟着丢

生产环境全量保存 Trace 成本可能过高。

常见策略包括：

1. Head Sampling

在 Trace 开始时决定是否采样。

优点：

  • 简单
  • 开销可控

缺点：

  • 决策时还不知道最终是否失败或变慢

2. Tail Sampling

在看到较完整 Trace 后决定是否保留。

可以优先保留：

  • ERROR
  • policy blocked
  • critical outcome failure
  • P99 慢请求
  • 多次重试
  • Judge 低分
  • 人工标记请求

代价是 Collector 需要缓存 Trace，并承担更高资源开销。

3. 分环境策略

建议：

  • 单元与集成测试：100% 元数据 Trace
  • 离线 eval：100% Trace，内容按评测策略
  • 预发布：高采样率
  • 生产正常流量：概率采样
  • 生产错误与慢请求：Tail Sampling 高保留

Metric 不应依赖 Trace 样本

如果错误率直接从 10% Trace 样本计算，低频错误可能被漏掉。

核心 Counter 与 Histogram 应由请求路径通过独立的 Metrics API 发射，不依赖某条 Span 最终是否被保留。

它们不应因为某条 Trace 被丢弃就消失。

Collector 只能基于已经到达它的 Span 派生 span metrics。Head Sampling 在 SDK 中丢弃的 Span 无法被 Collector 恢复；只有完整 Span 先到达指标处理器，再执行 Tail Sampling 等保留决策时，Collector 派生指标才可能覆盖全量。因此发布门禁和核心 SLO 不应默认依赖采样后的 Trace 反推。

采样状态不是安全授权

W3C trace-flags 中 sampled 位是追踪建议。

它不是：

  • 用户授权
  • 内容记录授权
  • 高敏数据访问授权

是否记录 Prompt 原文必须由独立隐私策略控制。

二十二、异步、消息队列与批处理怎么关联

1. Producer / Consumer

任务入队时创建 PRODUCER Span。

Worker 消费时创建 CONSUMER Span。

提取消息中的 Trace Context 作为父或 Link，取决于消息模型与生命周期。

2. 长时间任务

如果任务可能运行数小时：

  • API 接收请求形成一个短 Trace
  • 后台任务形成新的 Trace
  • 使用 Span Link 或 job ID 关联

不要让一个同步 Root Span 长时间悬挂。

3. 模型 Batch

多个用户请求可能合并成一次模型 Batch。

一个 Batch Span 不可能同时拥有多个父。

可以：

  • 每个请求保留自己的逻辑 Span
  • Batch 物理 Span 使用 Links 指向所有请求上下文
  • Batch 响应再按 item ID 分发

4. Fan-out / fan-in 工具

Agent 并行调用三个搜索源时：

  • 每个工具独立 Span
  • 它们共享同一个规划父 Span
  • 汇总操作建立 fan-in Span

时间轴能够直接看出：

  • 哪个工具最慢
  • 哪个工具失败
  • 是否等待了非必要分支

二十三、缓存怎么建模

缓存命中会让调用链形态变化。

建议将“获取模型结果”与“实际生成”分开理解。

缓存命中

此时没有真实 provider 调用。

不要伪造一个 model.generate Span。

记录：

  • cache status
  • cache policy version
  • cache key HMAC
  • cached artifact digest
  • age
  • saved latency
  • estimated saved usage

缓存未命中

缓存键不能泄漏 Prompt

不要把原始 Prompt 直接作为可检索 cache key 写入 Trace。

可以保存：

  • HMAC key reference
  • key schema version
  • hit / miss

二十四、可观测性平台的测试设计

调用链不是加上 SDK 就算完成。

需要专门验证它是否准确。

1. Schema 合同测试

对每类 Span 验证：

  • 必填字段
  • 数据类型
  • 单位
  • 枚举值
  • 敏感分类
  • 属性大小
  • 稳定性版本

不合规字段应在 CI 中失败。

2. 拓扑测试

构造固定工作流，验证：

  • 只有一个 Root
  • parent_span_id 存在
  • 不出现环
  • 同一 Trace ID 贯穿同步链路
  • 逻辑 Span 包含 attempt
  • 异步关系使用 Link

3. 传播测试

覆盖：

  • HTTP
  • gRPC
  • 消息队列
  • 定时任务
  • WebSocket
  • 流式响应

重点检查：

  • traceparent 注入与提取
  • 非法 Header
  • 超长 Header
  • 安全边界重启
  • sampled flag

4. 时间完整性测试

验证：

  • duration 非负
  • start 早于 end
  • TTFT 不大于 TTLT
  • generation duration 非负
  • 同进程单调时钟
  • 并行 Span 不被错误相加

5. 重试测试

注入：

  • 429
  • 连接超时
  • 读超时
  • 5xx
  • 用户取消

验证：

  • 每个 attempt 都存在
  • retry event 有原因与退避
  • 最终逻辑状态正确
  • 首次成功率可计算
  • Token 不重复或漏计

6. Retrieval 测试

验证：

  • 空召回
  • top_k
  • 文档顺序
  • Rerank
  • ACL 过滤
  • Corpus snapshot
  • 文档 Artifact

7. Tool 测试

验证：

  • Schema 校验失败
  • 权限拒绝
  • 幂等重试
  • 部分成功
  • 回滚
  • 最终业务状态

8. Judge 测试

验证：

  • Rubric 版本
  • Judge 超时
  • 输出解析失败
  • 评分明细
  • Artifact 关联
  • 人工校准引用

9. 隐私测试

构造包含下面内容的合成输入：

  • 邮箱
  • 手机号
  • 身份标识
  • API Key 形态字符串
  • Cookie
  • 数据库连接串
  • 工具嵌套参数

检查所有出口：

  • Span attributes
  • Events
  • Logs
  • Metric labels
  • Collector queue
  • Artifact
  • Exporter debug log

不能只检查最终 Trace UI。

10. 采样测试

验证：

  • 正常请求按比例采样
  • 错误请求被 Tail Sampling 保留
  • 慢请求保留
  • Trace 丢弃后 Metric 仍增加
  • Artifact 策略不依赖 sampled 位

11. 性能开销测试

观测系统本身会带来：

  • CPU
  • 内存
  • 序列化
  • 网络
  • 队列
  • 存储

至少测量：

  • SDK 增加的 P50 / P95 时延
  • 高并发下 Span 丢弃率
  • Exporter 队列深度
  • Collector CPU 与内存
  • 后端写入失败
  • Artifact 上传对主链路影响

Artifact 上传适合异步时，要保证：

  • Trace 先记录 pending
  • 上传完成后可关联
  • 上传失败有状态
  • 不阻塞业务成功
  • 关键证据场景可选择同步保证

12. 故障降级测试

可观测后端不可用时，业务系统不应整体瘫痪。

需要定义：

  • Span Buffer 上限
  • 丢弃策略
  • 本地回退
  • 错误计数
  • 告警
  • 高敏内容是否禁止落本地磁盘

二十七、示例案例三：HTTP 200 掩盖业务失败

这是第三个示例案例。

退款 Agent 的所有模型和工具请求都返回 HTTP 200。

但用户投诉仍在增加。

统一 Outcome 后发现：

  • 工具调用成功
  • 工具参数中的 order_id 来自旧会话
  • 错误订单被查询，但只读操作没有报错
  • 模型根据错误订单回答
  • Judge 只检查语言完整性，没有核对订单关联

  • session state version
  • tool args digest
  • order reference HMAC
  • business outcome assertion
  • Judge 中的实体一致性 Rubric

只有最后一个接近用户真正关心的结果。

二十八、常见误区

误区 1：把所有内容直接写入 Span 最方便

短期方便。

长期会遇到：

  • 隐私
  • 基数
  • 存储
  • 删除
  • 权限

Trace 应做索引，内容应做受控 Artifact。

误区 2：一个 request ID 足以贯穿所有系统

request ID 没有统一的父子 Span 与跨厂商传播语义。

应该保留业务 request ID，同时使用标准 trace context。

误区 3：模型 HTTP 200 就把 Span 标成全链路成功

传输成功不等于：

  • 解析成功
  • 工具成功
  • 业务成功
  • Judge 通过

状态需要分层。

误区 4：只记录模型名，不记录 Prompt 与索引版本

AI 输出由完整上下文决定。

没有 Prompt、数据和工具版本，模型名无法解释差异。

误区 5：直接把所有子 Span 时长相加

并行 Span 会重复计时。

应分析端到端时间轴和 Critical Path。

误区 6：只在异常时创建 Trace

没有正常样本，就无法建立：

  • 时延基线
  • Token 基线
  • 正常拓扑
  • 错误对比

可以采样正常 Trace，但不能完全没有。

误区 7：Metric 从采样 Trace 临时计算就够了

采样会扭曲低频事件和请求量。

核心 Metric 应独立产生。

误区 8：trace-flags sampled 表示允许记录内容

sampled 是追踪采样提示。

它不是隐私同意或数据访问授权。

误区 9：错误发生最早的 Span 就一定是根因

最早故障、终态原因和兜底缺陷可能不同。

应分别记录 first fault、terminal cause 和 contributing factors。

误区 10：接入 OpenTelemetry 就自动拥有正确语义

OpenTelemetry 提供数据与传输基础。

业务仍需定义：

  • Span 边界
  • 属性语义
  • Outcome
  • 隐私
  • 版本
  • 失败分类

误区 11：哈希后的内容就不是敏感信息

低熵内容可被枚举。

稳定摘要还可能形成跨系统关联标识。

应结合 HMAC、权限、最小化和保留策略。

误区 12：可观测后端不可用时可以阻塞主业务

大多数场景不应如此。

需要有界队列、丢弃计数和降级。

关键审计场景则应提前定义更强的一致性要求。

二十九、落地检查表

Trace 边界

  • Root Span 是否覆盖完整用户工作流
  • 多轮会话是否使用 session ID 关联多个 Trace
  • 长任务是否拆成独立 Trace 并使用 Link
  • 异步与批处理是否没有伪造多父关系

ID 与传播

  • 是否使用合法 trace ID 与 span ID
  • 是否传播 W3C traceparent
  • 是否校验外部 Trace Context
  • 安全边界是否有明确重启策略
  • tracestate 与 Baggage 是否禁止个人信息和秘密
  • request、session、eval run 与 trace ID 是否各司其职

Prompt

  • 是否记录模板 ID、版本和摘要
  • 是否记录渲染策略与截断策略
  • 是否默认关闭 Prompt 原文 Span 属性
  • 原文 Artifact 是否先脱敏再写入
  • 摘要是否用于完整性而不是冒充匿名化

Retrieval

  • 是否记录 Corpus snapshot
  • 是否记录 Index、Embedding、Chunker 与 Reranker 版本
  • 是否记录文档 ID、版本、Rank 与 Score Type
  • 是否区分空召回、召回失败和模型未使用证据
  • ACL 过滤版本是否可查

Model

  • 是否区分逻辑调用和物理 attempt
  • 每次重试是否单独留痕
  • 是否记录 requested 与 resolved model
  • TTFT 起点与首 Token 定义是否明确
  • 是否记录 usage 和 finish reason
  • 取消、限流、超时是否有稳定 error.type

Tool

  • tool name、version 与 schema digest 是否齐全
  • args 是否脱敏并有摘要
  • 是否记录权限决策
  • 是否记录副作用等级和幂等键
  • 是否验证最终业务状态
  • 模型声称成功是否不能替代工具 Outcome

Judge 与 Guardrail

  • 是否各自建立 Span
  • 是否记录 Rubric 和 Grader 版本
  • 是否保存评分理由 Artifact
  • 是否区分质量低分和风险拒绝
  • Judge 自身失败是否不会归到被测模型

指标

  • 是否有端到端时延
  • 是否分别统计 TTFT 与 TTLT
  • 是否按 P50、P95、P99 查看分布
  • 是否独立统计 Token 与估算成本
  • 价格表是否版本化
  • Metric 标签是否低基数
  • Trace 采样是否不影响核心计数

隐私

  • 是否采用字段白名单
  • Secret 是否在采集前丢弃
  • 是否对嵌套自然语言做内容检测
  • Trace 与 Artifact 是否分权
  • 是否有保留、删除和备份策略
  • Artifact 访问是否审计
  • Debug Exporter 和 Collector 日志是否纳入检查

测试

  • 是否有 Span Schema 合同测试
  • 是否有拓扑和传播测试
  • 是否有重试、异步与批处理测试
  • 是否有时间完整性测试
  • 是否有隐私泄漏合成测试
  • 是否测量 SDK、Exporter 与 Collector 开销
  • 可观测后端故障时是否验证业务降级

三十、总结

AI 可观测性真正要解决的，不是“把 Prompt 打进日志”。

它要建立的是一套统一、克制、可验证的数据模型：

  1. 用一个 Trace 表示完整 AI 工作流
  2. 用 Span 拆开 Prompt、Retrieval、Model、Tool 和 Judge
  3. 用父子关系表达直接因果，用 Link 表达异步和批处理
  4. 用逻辑 Span 与 attempt Span区分调用和重试
  5. 用标准 Trace Context 跨服务传播
  6. 用独立业务 ID 关联 session、eval run 和 Artifact
  7. 用明确边界定义 TTFT、总时延、Token 和成本
  8. 用 first fault、terminal cause 和 contributing factors 做失败归因
  9. 用 Trace 做索引、Metric 做聚合、Artifact 保存受控证据
  10. 默认 Content-Off，在采集前完成分类、脱敏和 Secret 丢弃

当这套链路建立后，一次 AI 失败不再只剩一句：

平台应该能够给出更具体的答案：

这种答案才能驱动修复、回归和发布决策。
