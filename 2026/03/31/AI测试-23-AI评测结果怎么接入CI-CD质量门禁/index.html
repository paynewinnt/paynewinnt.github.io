AI测试-23-AI评测结果怎么接入CI-CD质量门禁

发表于 2026-03-31 分类于 AI测试 本文字数： 7.2k 阅读时长 ≈ 26 分钟

AI 评测平台跑出一张分数表，并不代表它已经进入研发流程。

只要评测结果还停留在报告页面里，发布人员就会继续面对这些问题：

  • Prompt 改了两行，是否必须完整回归
  • 知识库更新以后，应该测检索还是测最终回答
  • 候选模型总分提高，但安全样本退化，能不能发布
  • 同一版本重复运行结果波动，下降 1% 算真实回退还是随机噪声
  • LLM-as-Judge 自己不稳定，门禁到底应该相信谁
  • 评测服务超时，是代码失败、环境失败，还是可以重跑后放行
  • 离线评测通过以后，线上灰度发现成本翻倍或工具误调用，如何自动回退
  • 特殊业务需要带风险发布，谁能豁免，豁免多久，证据保存在哪里

传统单元测试通常有比较明确的布尔结果：断言通过或失败。

AI 系统则同时存在非确定性输出、语义判定、分层风险、数据版本和外部模型依赖。把一个平均分和一条 score >= 0.8 写进流水线，形式上有门禁，实际上很容易误放行或长期误阻断。

这篇文章讨论的重点，是怎样把 AI 评测结果变成一套可以执行、解释、审计和回滚的 CI/CD 质量门禁。

一、先给结论：质量门禁控制的是发布风险，不是追求一个最高总分

一个可用的 AI 质量门禁，至少要同时回答六个问题：

  1. 这次变更影响了什么。
  2. 哪些风险必须重新验证。
  3. 候选版本相对基线在哪里变好或变差。
  4. 观察到的差异是否超过随机波动和评测器误差。
  5. 哪些指标属于不可妥协的硬底线。
  6. 离线结论失败时如何阻断，线上结论失效时如何回滚。

因此，门禁不应该只有“通过”和“失败”两个内部状态。

更合理的状态包括：

对外的流水线最终仍可以映射成成功、等待审批或失败，但内部必须保留真实原因。

二、为什么传统“测试通过率门禁”不够

AI 应用不是只有模型。

一次行为变化可能来自：

  • 模型标识或服务版本
  • System Prompt 和模板
  • Few-shot 示例
  • 温度、Top-p、最大输出长度等生成参数
  • 检索索引、Embedding、切片和重排
  • 工具描述、Schema 和权限策略
  • Agent 编排和状态恢复逻辑
  • 评测数据集
  • 规则判定器和 LLM 裁判
  • 外部 API 与运行环境

如果流水线只记录 Git Commit，就无法完整复现一次评测。

如果只看总通过率，也会掩盖局部风险。

例如：

总分提高不能抵消安全底线下降。

这说明 AI 门禁必须同时具备：

  • 版本指纹
  • 分层评测
  • 硬门禁
  • 相对退化判断
  • 统计不确定处理
  • 线上护栏

三、第一步不是跑评测，而是给变更做分类

不同变更需要触发不同评测。

1. Prompt 变更

可能影响：

  • 指令遵循
  • 输出格式
  • 工具选择
  • 拒答边界
  • 回答风格和长度

至少触发 Prompt 核心集、工具调用集、安全集和格式集。

2. 模型或推理参数变更

可能影响几乎所有生成行为。

应触发完整离线评测，并根据风险决定是否做影子流量或金丝雀发布。

3. RAG 数据与检索变更

更新单篇知识文档和更换 Embedding 模型不是同一风险等级。

需要区分：

  • 内容增删改
  • 权限元数据变化
  • 切片策略变化
  • 索引重建
  • 召回参数变化
  • 重排模型变化

这类变更至少要分别评测检索和生成，不能只看最终答案。

4. 工具和 Agent 变更

工具 Schema、新增权限、重试策略和编排顺序变化，可能产生现实副作用。

应触发：

  • Schema 测试
  • 权限测试
  • 轨迹评测
  • 故障恢复测试
  • 幂等与补偿测试
  • Prompt Injection 安全集

5. 评测器变更

规则、阈值、裁判 Prompt 或裁判模型变化，会改变“尺子”。

不能直接拿新尺子得到的分数和旧历史基线比较。必须先在校准集上做一致性分析，再建立新基线。

四、建立变更风险分级

可以用四个维度做初步分级。

维度 低风险 中风险 高风险
影响范围 单一文案或非关键场景 一个业务域或一种能力 全局模型、Prompt、检索或执行链
权限与副作用 只读、无敏感数据 内部写操作、可补偿 外发、删除、支付、终端、管理员能力
可逆性 立即回滚，无数据影响 需要迁移或重新执行 不可逆动作或已产生外部影响
可观测性 结果易验证 部分依赖语义评测 结果延迟、隐蔽或难以获得真值

风险级别不应该只影响审批流程，还应该决定：

  • 评测集范围
  • 重复运行次数
  • 允许的退化预算
  • 是否需要人工复核
  • 灰度比例和时长
  • 线上回滚条件

五、把评测套件拆成多层，不要每次都跑同一批

质量门禁既要快，也要覆盖风险。

一种实用分层如下。

1. L0：确定性静态检查

秒级到分钟级完成：

  • Prompt 模板可渲染
  • 变量完整
  • JSON Schema 合法
  • 工具描述和参数兼容
  • 安全策略可加载
  • 数据集格式和引用完整
  • 模型配置在允许清单中

2. L1：核心冒烟评测

选取数量少、价值高、历史稳定的样本：

  • 核心任务
  • 关键格式
  • 典型工具调用
  • 高风险拒绝
  • 历史严重缺陷

它适合每次 Pull Request 运行，但不能代替完整评测。

3. L2：完整离线回归

按业务、语言、难度、风险、输入长度、工具和数据来源分层运行。

这层用于发现局部退化，并形成候选与基线的配对结果。

4. L3：鲁棒性与安全评测

覆盖：

  • Prompt Injection
  • 越权与数据泄漏
  • 长上下文和噪声
  • 检索污染
  • 工具失败
  • 限流、超时和重试
  • 对抗与边界样本

5. L4：影子与金丝雀验证

离线数据无法完全代表真实流量。

线上阶段观察：

  • 任务完成率
  • 人工接管率
  • 用户纠正率
  • 工具失败和副作用
  • 时延与 Token 成本
  • 安全护栏命中
  • 业务结果

六、分层门禁的完整流水线

下面这张图展示了从变更到灰度的主链路。

这条链路有三个重要原则。

1. 先快后慢

确定性失败应尽早反馈，不必等待昂贵模型调用完成。

2. 先硬底线后综合收益

越权、泄漏和关键任务失败不能被平均分抵消。

3. 离线通过不等于直接全量

离线评测证明候选版本在已知样本上满足条件，线上灰度用于验证流量分布、依赖和业务行为。

要比较候选和基线，至少需要冻结以下信息：

八、指标必须分层，否则平均数会隐藏风险

至少建议从五个层级组织指标。

1. 输入和检索层

  • 权限过滤正确率
  • Recall@k
  • MRR 或 nDCG
  • 上下文相关性
  • 引用覆盖率

2. 模型输出层

  • Schema 合法率
  • 事实支持率
  • 任务相关性
  • 拒答正确率
  • 敏感信息暴露率

3. Agent 轨迹层

  • 工具选择正确率
  • 参数正确率
  • 非必要工具调用数
  • 状态一致性
  • 故障恢复率

4. 系统质量层

  • 端到端任务完成率
  • P50/P95/P99 时延
  • 首 Token 时延
  • 单任务 Token 和费用
  • 超时、限流和基础设施失败率

5. 业务与风险层

  • 高价值任务完成率
  • 人工接管率
  • 错误动作成本
  • 安全事件数
  • 用户纠正和投诉率

门禁策略应该引用这些分层指标，而不是重新把它们压成一个不可解释的综合分。

综合分可以用于趋势观察，不能代替硬门禁。

九、先定义不可妥协的硬门禁

硬门禁应该少而明确。

常见例子包括：

  • 禁止工具实际执行次数必须为零
  • 跨租户读取次数必须为零
  • 敏感凭据暴露次数必须为零
  • 核心结构化输出合法率必须达到明确底线
  • 高风险动作未经审批的执行次数必须为零
  • 关键业务任务完成率不得低于发布底线
  • 评测证据不完整时不能自动发布

硬门禁不能依赖单个 LLM 裁判给出模糊分数。

安全和权限性质应尽量从系统事实、工具审计、数据库访问和网络记录中判定。

十、绝对阈值和相对退化要同时使用

只用绝对阈值有一个常见问题：

候选有提升，却可能仍未达到业务可用底线。

十一、尽量使用同一样本的配对比较

候选和基线如果在不同样本上运行，差异可能来自样本分布。

更稳妥的方式是：

  1. 对同一批样本分别运行基线和候选。
  2. 保留每个样本的结果对。
  3. 统计候选胜、平、负以及风险变化。
  4. 对差异做配对 Bootstrap、置换检验或适合当前指标的区间估计。

门禁关注的是差异分布，而不是两个独立平均数。

对于布尔任务，还可以把样本分成：

基线 候选 含义
失败 成功 修复
成功 成功 稳定通过
失败 失败 持续失败
成功 失败 新增回退

“新增回退”通常比总通过率更适合直接进入缺陷和门禁分析。

十二、非确定性结果必须带不确定区间

如果一条样本运行一次就决定发布，模型随机性和服务波动可能直接变成门禁噪声。

1. 重复运行

对关键非确定性样本运行多次，记录：

  • 通过次数
  • 失败次数
  • 结果类别分布
  • 工具轨迹差异
  • 时延和成本波动

重复次数应该由风险和历史方差决定，不是所有样本固定跑十次。

2. 比例指标的区间

假设 n 次运行中有 k 次通过，点估计是：

但门禁不应只看 p_hat。小样本下可以使用 Wilson 区间或 Bootstrap 区间表达不确定性。

例如绝对底线是 90%，更保守的规则可以检查置信区间下界是否仍达到底线。

独立性假设必须写进统计口径。同一个 case 的多次运行共享输入、环境和业务风险，不能把所有 run 当成相互独立的 Bernoulli 样本。更稳妥的做法是以 case 为聚类单位做 Bootstrap；比较候选与基线时，在同一 case 内保留配对关系，再重采样 case 组。

3. 不确定不是通过

如果候选和基线的差异区间跨越退化预算，合理状态是 REVIEW 或扩大样本，而不是自动选择有利结论。

4. 控制多重比较

当平台同时检查几十个切片和指标时，总会有少数指标偶然波动。

应提前定义关键指标、探索指标和告警规则，避免看到波动后临时挑选解释。必要时使用多重检验控制，但更重要的是把发布决策聚焦在预先声明的风险指标上。

十三、为门禁保留明确的三个决策区

1. 通过区

满足所有硬底线，关键分层未超过退化预算，证据完整，统计不确定可接受。

通过后仍然进入灰度，而不是直接证明全量安全。

2. 人工复核区

适用于：

  • 样本不足
  • 置信区间跨越预算
  • 两个裁判明显分歧
  • 低风险场景小幅退化但有明确业务收益
  • 评测数据不能代表新功能

人工复核要补充结论和证据，不能只点一个“强制通过”。

3. 阻断区

适用于：

  • 硬安全性质失败
  • 关键任务明确退化
  • 评测集或证据链损坏
  • 候选版本与声明版本不一致
  • 已过期豁免仍被使用

十八、评测器本身也要有门禁

AI 门禁最大的自指问题，是用一个不稳定的 LLM 去判断另一个 LLM。

1. 规则判定优先

能够通过 Schema、数据库状态、工具记录、字符串规则或业务计算得到的事实，不要交给 LLM 裁判。

2. 裁判版本必须固定

记录裁判模型、Prompt、Rubric、示例和参数版本。

3. 用人工校准集验证裁判

至少观察：

  • 与人工标签的一致性
  • 不同类别的偏差
  • 顺序交换后结果变化
  • 对长度、风格和自家模型的偏好
  • 重复评分稳定性

4. 裁判变化要重建基线

新旧裁判的分数不能直接拼成一条趋势线。

可以在同一校准集上双跑一段时间，建立映射和差异报告，再切换门禁基线。

5. 分歧进入复核区

多个裁判或规则与裁判分歧时，应输出分歧类型和样本，不应该简单多数投票后删除原始证据。

十九、正确处理 Flaky Eval 和基础设施噪声

最危险的做法，是失败后不断重跑，直到某次通过。

这会系统性地选择有利随机结果。

1. 预先定义重试策略

只对明确的可重试基础设施失败重试，例如连接中断、限流和临时服务不可用。

语义评分低不能自动当成基础设施失败。

2. 保留所有尝试

重试不能覆盖首错结果。报告要记录每次尝试、错误类型和最终收口方式。

3. 对不稳定样本单独治理

标记历史方差、评测器分歧和环境依赖。

不稳定样本不能被静默删除。应修复判定、增加重复次数、降低其作为硬门禁的权重，或转入专项人工评测。

4. 设定噪声预算

平台可以记录每个套件的历史波动范围。当整体波动突然扩大时，优先检查模型服务、评测器和数据版本，而不是立即归因给业务代码。

二十、豁免必须是有期限的风险接受

某些发布确实可能需要带已知风险上线。

但豁免不能是一条永久的 allow_failure: true。

一个合格豁免至少包含：

豁免过期后必须自动失效。

下一次发布不能默认继承上一次风险接受。

二十一、离线门禁后还需要线上护栏

离线评测存在三类天然限制：

  1. 样本分布不完全等于真实流量。
  2. 外部依赖、网络和权限环境可能不同。
  3. 真实用户会产生评测集没有覆盖的新任务。

因此发布阶段至少要考虑：

1. 影子流量

候选版本处理真实请求副本，但不产生用户可见回答和副作用。

适合对比质量、时延、成本和工具规划。

涉及敏感数据时，要确保影子链路具有相同的数据保护和授权基础，不能为了评测复制到不受控环境。

2. 金丝雀发布

让少量受控流量使用候选版本，并设置：

  • 最大流量比例
  • 最短观察时间
  • 样本量要求
  • 自动停止条件
  • 自动回滚目标

3. 线上硬护栏

权限、审批、速率、成本和数据外发控制必须在运行时持续执行，不能因为离线评测通过就关闭。

4. 延迟结果回填

某些任务的真实质量要到工单关闭、用户确认或业务结果产生后才能知道。

这些结果应回填到发布记录和评测数据闭环中。

二十二、一个示例：总分提高但退款 Agent 被门禁阻断

下面是一个示例案例，用于说明决策过程，不代表真实生产事故。

1. 变更

团队更换模型并修改工具描述，希望减少无效追问。

2. 快速评测

Schema、核心问答和禁止工具测试全部通过。

3. 完整评测

总体任务完成率从 90.8% 提升到 93.1%。

但“高风险退款”切片出现：

轨迹分析发现，候选模型更倾向于在缺少订单状态时直接生成退款工具参数。

4. 门禁判断

退款参数正确率低于绝对底线，同时相对基线退化超过预算。

总体分数提升不能覆盖这个切片，门禁状态为 BLOCK。

5. 修复

团队没有简单提高 Prompt 强度，而是在执行层增加确定性前置条件：

  • 订单必须属于当前用户
  • 状态必须允许退款
  • 金额必须来自订单系统
  • 超额度必须人工审批

同时修改工具描述和专项评测样本。

6. 重新评测与灰度

候选通过硬门禁后先进入 5% 金丝雀。

线上继续观察退款失败率、人工接管率和审批拒绝率。任何未经审批的高额退款调用都会触发自动回滚。

这个案例说明，门禁真正保护的是高风险业务边界，不是评测报告的平均分。

  • 灰度配置、线上指标和回滚目标

二十四、最常见的十个错误

1. 只设一个总分阈值

平均分会掩盖高风险切片退化。

2. 只有绝对阈值，没有相对基线

候选可能大幅回退后仍然达到低门槛。

3. 只有相对提升，没有业务底线

从很差提升到稍差仍然不可用。

4. 候选和基线使用不同数据集或不同裁判

分数差异失去可比性。

5. 每个样本只运行一次

非确定性噪声会直接决定发布结果。

6. 失败后一直重跑到通过

这会选择性忽略不利结果。

7. 评测基础设施错误被当成质量通过

没有证据不等于没有问题。

8. 开发变更同时降低门禁阈值

考试对象不能未经独立审查修改自己的及格线。

9. 豁免永久有效

风险接受必须限定版本、范围、责任人和过期时间。

10. 离线通过后直接全量

真实流量和外部依赖仍需要灰度验证和运行时护栏。

二十五、质量门禁成熟度可以分四级

第一级：报告化

能够稳定跑评测并生成报告，但发布仍靠人工看总分。

第二级：基础门禁化

核心指标进入 CI，有固定基线和硬门禁，失败能阻断。

第三级：风险分层化

变更会触发不同套件，支持样本级配对、统计区间、人工复核和有期限豁免。

第四级：持续交付闭环

离线评测、影子流量、金丝雀、线上护栏、自动回滚和真实结果回填形成闭环。

成熟度提升的重点不是堆更多指标，而是让每个发布决策都有稳定输入、明确规则和可追溯证据。

二十六、落地检查表

版本和变更

  • 模型、Prompt、检索、工具、策略、数据集和评测器都有版本指纹
  • 变更能够自动分类并映射到风险等级
  • 候选与实际构建产物指纹一致

评测设计

  • 快速集、完整集、安全集和线上集职责分开
  • 指标按业务、风险、语言、工具等维度切片
  • 候选和基线尽量使用同一样本配对比较
  • 非确定性样本有重复运行和不确定区间

门禁策略

  • 硬安全性质不会被综合分抵消
  • 同时设置绝对底线与相对退化预算
  • REVIEW、BLOCK 和 INFRA_ERROR 原因明确
  • 门禁策略变更需要独立审查

评测器

  • 确定性事实优先使用规则和系统状态
  • LLM 裁判经过人工校准并记录版本
  • 裁判切换时不会直接拼接新旧分数
  • 裁判分歧会保留原始证据并进入复核

发布和审计

  • 豁免限定版本、范围、责任人和过期时间
  • 离线通过后仍有影子或金丝雀策略
  • 线上有明确回滚指标和稳定回滚目标
  • 发布证据包可以重放和审计

二十七、小结

把 AI 评测接入 CI/CD，不是把一个分数写进 if 条件，而是把发布风险变成一套可执行决策。

完整链路应该做到：

  1. 根据变更内容和风险选择评测范围。
  2. 冻结模型、Prompt、数据、工具、策略和评测器版本。
  3. 同时检查硬底线、绝对质量和相对退化。
  4. 使用样本级配对结果和不确定区间控制随机噪声。
  5. 把通过、复核、阻断、基础设施错误和豁免分开记录。
  6. 离线通过后继续使用灰度、线上护栏和自动回滚。
  7. 为每次发布保存能重放的完整证据包。

最终，质量门禁应该能清楚回答：

这个版本为什么可以发布，哪类风险仍然存在，证据是否足够可信，以及线上行为偏离预期时系统会怎样停下来。

只有回答到这一步，AI 评测才真正从一份报告变成持续交付系统的一部分。
