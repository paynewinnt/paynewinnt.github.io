AI测试-16-AI测试怎么组合确定性断言和语义断言

发表于 2026-03-20 分类于 AI测试 本文字数： 9.8k 阅读时长 ≈ 35 分钟

传统自动化测试习惯把断言写成一个布尔表达式：

进入 AI 应用后，这个模型很快会失效。

用户问“退款失败后应该先检查什么”，系统可能生成几十种措辞不同、但都合理的回答。

这时做字符串全等，会把正确改写判成失败。

如果把断言全部换成向量相似度或大模型评分，另一个问题又会出现：

  • JSON 少了必填字段，却因为解释文字相似而被判通过
  • 工具声称执行成功，真实订单状态却没有变化
  • 回答引用了不存在的文档，但语气完整、结构漂亮
  • 高风险动作越过审批，语义评分仍然很高
  • 模型输出“差不多正确”，平台却无法说明证据在哪里

因此，AI 测试的核心不是在“硬断言”和“软评分”之间二选一。

真正需要解决的是：

哪些事实必须由确定性断言证明，哪些质量只能用语义断言估计，两者冲突时谁优先，以及不确定样本由谁处理。

这篇文章从测试平台工程视角，建立一套可实现、可校准、可审计的组合断言方法。

前面的 AI 测试系列已经讨论过视觉误判、证据链以及幻觉和越权风险。

本文不再重复这些风险的概念说明，而只聚焦最终结果如何被判定。

一、先明确问题边界：断言对象不是一段文本

AI 应用的输出经常表现为自然语言，但一次任务的真实结果通常远大于这段文本。

以“查询订单并给出退款建议”为例，完整结果至少包括：

  • 用户原始请求
  • 解析出的订单 ID
  • 检索到的制度文档
  • 调用订单工具时的参数
  • 工具返回的订单状态
  • 工作流执行前后的状态快照
  • 模型生成的解释和建议
  • 引用的证据标识
  • 模型、提示词、工具和知识库版本
  • 超时、重试与降级记录

如果测试只拿最终回答做语义比较，就等于主动丢掉了最容易验证的事实。

更合理的断言对象应写成一个证据包：

组合断言是在这个证据包上工作，而不是只在 output.text 上工作。

1. 本文所说的确定性是什么

确定性断言是指：

给定同一份已冻结的输入和证据，规则执行应得到同一个结果。

典型对象包括：

  • JSON Schema
  • 类型、范围和枚举
  • 权限规则
  • 状态迁移规则
  • 数据库不变量
  • 引用是否存在
  • 哈希是否匹配
  • 工具调用是否在白名单
  • 时间窗口是否满足

这里有一个重要限制。

确定性规则只能证明“证据是否满足规则”，不能自动证明上游证据本身绝对真实。

如果测试环境返回了错误的订单状态，规则仍可能稳定地给出错误结论。

所以确定性不等于真值，它强调的是可重放、可解释和无随机性。

2. 本文所说的语义是什么

语义断言用于评价难以被有限规则完整形式化的质量，例如：

  • 回答是否真正回应用户问题
  • 表达不同但含义是否等价
  • 摘要是否覆盖关键事实
  • 解释是否忠实于给定证据
  • 建议是否完整且没有明显跑题
  • 两个开放式方案哪个更符合评分细则

它可以由以下组件实现：

  • Embedding 相似度
  • 文本分类器
  • 自然语言推断模型
  • 规则与统计特征组合模型
  • LLM-as-Judge
  • 人工评审

语义断言不必然“不稳定”。

冻结模型、参数、模板和输入后，它可以高度可重复。

但它依然是测量模型，不应被当作事实本身。

3. 不在本文展开的内容

本文不讨论模型训练、微调和奖励建模。

也不把某个厂商模型或评测框架当成默认答案。

不同模型的能力和成本会变化，但下面的分层原则不依赖具体供应商：

  1. 可形式化事实优先硬验证。
  2. 开放质量按维度做语义测量。
  3. 不确定性必须显式进入决策。
  4. 阈值必须用业务数据校准。
  5. 最终结论必须能够追溯到原始证据。

二、为什么单一断言会系统性失真

组合断言不是为了让架构看起来更完整，而是因为单一方法存在结构性盲区。

1. 字符串全等：高精度外表下的高漏报

严格相等会失败。

模糊字符串匹配也可能因为分词、同义改写和句序变化而失败。

这类断言适合验证 ID、枚举、协议字段和固定文案，不适合直接验证开放式回答。

2. 关键词包含：容易被“提到但说错”绕过

如果断言只要求包含“订单状态”和“支付渠道”，下面的回答也会通过：

关键词存在不代表命题成立。

否定关系、条件关系、主体客体和时间顺序都可能被忽略。

3. 单一相似度：把“像”误当成“对”

向量相似度适合发现语义接近，但不能天然保证事实正确。

下面两句话可能非常接近：

它们共享大量词汇和主题，结论却相反。

如果只用一个相似度阈值，否定词、数字、实体和状态差异可能被高相似度掩盖。

4. 单一 LLM Judge：把另一个模型误当真值

大模型能够理解复杂评分标准，但同样可能：

  • 忽略隐藏在长回答中的事实错误
  • 偏爱更长、更流畅或格式更整齐的回答
  • 对同一答案重复评分时发生漂移
  • 被候选文本中的指令干扰
  • 在缺少证据时补全一个看似合理的判断

因此，Judge 应处理硬规则无法覆盖的部分，而不是替代数据库、Schema 和状态机。

5. 单一总分：掩盖致命维度

假设一个回答的评分如下：

维度 分数
相关性 0.95
表达清晰度 0.92
完整性 0.88
事实正确性 0.20

简单平均得到 0.7375。

如果平台阈值是 0.70，它会通过。

但事实正确性只有 0.20，在退款、支付或设备操作场景中显然不可接受。

正确做法是给关键维度设置最低门槛，而不是让强项补偿致命短板。

三、建立五层断言栈

一条可维护的判定链路可以拆成五层：

  1. 结构断言
  2. 规则断言
  3. 状态断言
  4. 证据断言
  5. 语义断言

前四层主要处理可以被形式化的事实。

第五层处理开放式质量。

策略聚合层再根据优先级、风险和阈值输出：

  • PASS
  • REVIEW
  • FAIL

顺序很重要。

如果结构已经非法，就没有必要花费模型调用去评价文案是否优美。

如果关键状态迁移失败，语义评分再高也不能把任务改判成功。

2. 第二层：规则断言

Schema 能验证形状，但不能表达所有业务不变量。

例如：

  • decision=approve 时，必须存在审批工具返回
  • 风险等级为 high 时，不允许自动执行退款
  • 置信度低于 0.6 时，决策只能是 escalate
  • 引用类型为 policy 时，文档状态必须是 active
  • 输出订单 ID 必须与输入订单 ID 完全一致

这些规则应落在普通代码、规则引擎或策略引擎中。

不要把它们只写进 Prompt。

Prompt 是给模型的行为提示，不是系统强制约束。

3. 第三层：状态断言

AI Agent 经常调用工具并改变外部世界。

只验证模型“说已经完成”没有意义。

状态断言至少要比较：

  • 动作前状态
  • 预期迁移
  • 动作后状态
  • 是否发生重复副作用
  • 最终状态是否来自权威数据源

4. 第四层：证据断言

生成式系统容易给出“听起来有依据”的结论。

证据断言要把依据变成可解析对象。

最低要求包括：

  • 每个 evidence_id 在证据仓中存在
  • 证据属于当前任务和当前租户
  • 证据版本没有过期
  • 引用片段可以在原文定位
  • 工具返回与状态快照时间一致
  • 结论涉及的关键实体出现在证据中
  • 引用没有被候选回答自行伪造

证据断言能够证明引用存在，但通常不能单独证明“证据足以支持结论”。

后一个问题属于忠实度或蕴含关系，需要语义断言或人工判断。

5. 第五层：语义断言

当前四层都通过后，才进入开放式质量评估。

语义断言不应该只返回一个总分。

至少应按任务拆成多个维度：

  • correctness：结论是否正确
  • relevance：是否回应用户问题
  • completeness：是否覆盖必要步骤
  • groundedness：是否被证据支持
  • clarity：表达是否清晰
  • actionability：建议是否可以执行

并不是每个任务都需要全部维度。

测试设计应先写质量定义，再选择评估器。

四、语义断言应该选哪一种评估器

不同评估器回答的问题不同。

不要因为 LLM Judge 表达能力强，就把所有语义检查都交给它。

1. Embedding 相似度

Embedding 把文本映射到向量空间。

常见的余弦相似度为：

它适合：

  • 同义改写检测
  • 意图与参考主题匹配
  • 聚类后的近邻检查
  • 从多个参考答案中寻找最近语义

它不适合单独验证：

  • 数字是否精确
  • 否定关系是否正确
  • 工具是否真实执行
  • 引用是否存在
  • 多步骤约束是否全部满足

相似度值也没有跨模型的统一意义。

换一个 Embedding 模型、归一化方式、文本切分方式或语言分布，阈值都可能改变。

2. 任务分类器

如果语义目标可以稳定归入有限类别，分类器通常比通用 Judge 更便宜、更稳定。

例如：

  • 是否包含拒答
  • 是否属于某类故障原因
  • 用户意图分类
  • 是否出现敏感信息
  • 回答是否包含下一步行动

分类器需要代表性标注数据，并应报告每类 Precision、Recall 和混淆矩阵。

不能只看总体 Accuracy，因为多数类可能掩盖少数高风险类。

3. 自然语言推断或蕴含判断

当问题是“证据是否支持结论”时，可以把任务表达为：

目标类别是：

  • entailment
  • contradiction
  • neutral

这种形式比泛化相似度更贴近事实支持关系。

但模型仍可能受领域术语、长上下文和隐含条件影响，因此高风险场景要用人工集校准。

4. LLM-as-Judge

Judge 适合评价：

  • 多条件完整性
  • 开放式方案质量
  • 长文本忠实度
  • 无法用固定特征表示的表达质量
  • 按 Rubric 做分项解释

它的代价是：

  • 延迟更高
  • 成本更高
  • 对 Prompt 和顺序敏感
  • 输出存在随机性
  • 需要额外做偏差与一致性验证

下一篇会单独拆解 Judge 的评分规则和偏差控制。

本文只强调一点：

Judge 的结果必须作为一个带误差的测量值进入策略层，不能覆盖硬事实。

5. 人工评审

人工不是免费的真值机器。

评审者也会有领域差异、疲劳和标准漂移。

但人工在以下位置不可替代：

  • 定义质量维度
  • 建立黄金评测集
  • 仲裁高风险灰区
  • 发现自动评估器的新型偏差
  • 校准模型升级后的分数变化

合理目标不是完全消灭人工，而是把人工预算投入信息量最大的样本。

1. 为什么硬门禁不能与语义分数平均

假设：

  • Schema 分数：1.0
  • 状态一致性：0.0
  • 相关性：0.95
  • 清晰度：0.95

平均分是 0.725。

这个数字没有业务意义。

状态不一致不是“少得一点分”，而是任务结果没有被真实系统证实。

因此关键硬断言只能是门禁，不应参与加权补偿。

2. 哪些断言应该设为关键门禁

判断标准不是“是否容易实现”，而是失败后能否被其他维度补偿。

通常不可补偿的包括：

  • 协议结构非法
  • 身份、租户或对象 ID 不匹配
  • 权限越界
  • 禁止工具被调用
  • 核心状态未发生或迁移路径非法
  • 关键引用不存在
  • 金额、数量和时间等关键事实错误
  • 高风险任务缺少审批

可进入语义层的通常包括：

  • 表达是否自然
  • 是否充分回应用户
  • 建议步骤是否完整
  • 摘要是否遗漏次要信息
  • 多个合理方案之间的偏好

六、灰区不是失败设计，而是可靠系统的必要状态

很多平台只定义 PASS 和 FAIL。

这会迫使不确定样本被硬塞到某一边。

对概率评估器来说，最危险的不是分数低，而是分数接近边界且平台假装它确定。

1. 双阈值的含义

设：

  • T_fail：低于它时，自动失败风险可接受
  • T_pass：高于它时，自动通过风险可接受
  • [T_fail, T_pass)：进入人工复核

双阈值允许平台分别控制两类错误：

  • 把坏结果放过去的漏报
  • 把好结果拦下来的误报

它也允许业务显式控制复核量。

阈值间距越宽，自动决策更保守，人工量通常越大。

阈值间距越窄，自动化率更高，但边界错误可能增加。

2. 误报和漏报必须绑定业务语义

先定义“正类”是什么。

假设正类定义为“结果可发布”。

那么：

  • FP：实际不可发布，却被系统判为可发布
  • FN：实际可发布，却被系统判为不可发布

在支付建议场景，FP 可能导致错误动作进入生产，成本很高。

在文案润色场景，FN 主要增加人工复核，成本较低。

两个场景不应该共用同一阈值。

4. 为什么不能拍脑袋设成 0.8

0.8 没有脱离上下文的普遍含义。

它依赖：

  • 评分模型
  • Prompt 和 Rubric
  • 分数是否校准
  • 数据集难度
  • 语言和领域
  • 正负样本比例
  • 文本长度
  • 是否提供参考答案
  • 是否使用多次采样

同一个 0.8 在两个任务上可能对应完全不同的错误率。

阈值必须从代表性数据中估计。

七、阈值校准的可执行步骤

阈值校准不是在测试集上不断试到结果好看。

推荐按下面流程执行。

1. 先冻结质量定义

明确：

  • 哪个输出算可发布
  • 哪些错误是不可补偿错误
  • 哪些样本必须人工处理
  • 每个维度的评分锚点
  • 人工分歧如何仲裁

如果质量定义还在变，阈值没有稳定含义。

2. 建立有分层的标注集

数据至少覆盖：

  • 明显正确
  • 明显错误
  • 接近边界
  • 格式正确但事实错误
  • 事实正确但表达不同
  • 引用存在但不支持结论
  • 长回答中的局部错误
  • 不同语言和长度
  • 不同业务风险等级
  • 真实流量中的高频与长尾任务

不要只随机抽样。

随机样本通常包含大量容易样本，不能充分暴露边界行为。

3. 划分校准集与最终测试集

校准集用于选择阈值。

最终测试集只用于一次性评估泛化效果。

如果在同一数据上选阈值又报告效果，会产生乐观偏差。

4. 扫描候选双阈值

对于每组 T_fail < T_pass：

  1. 计算自动通过样本中的 FP
  2. 计算自动失败样本中的 FN
  3. 计算灰区比例
  4. 计算成本函数
  5. 检查风险约束
  6. 选择满足约束且成本较低的组合

5. 按切片检查

总体指标通过后，还要分组检查：

  • 任务类型
  • 风险等级
  • 语言
  • 输入长度
  • 是否有参考资料
  • 模型版本
  • 工具调用类型
  • 新旧用户或数据来源

总体 Precision 很高，不代表每个关键切片都安全。

6. 上线后监控分布漂移

至少监控：

  • 分数分布
  • 灰区比例
  • 自动通过比例
  • 人工推翻率
  • 每个切片的 FP/FN
  • Judge 或分类器失败率
  • 输入长度和语言分布
  • 阈值版本

如果分数分布明显改变，旧阈值可能已经失效。

十、指标体系：既看分类错误，也看系统运营

1. 基本分类指标

以“可发布”为正类：

它回答：自动放行的结果中，有多少真的可发布。

它回答：所有可发布结果中，有多少被自动识别出来。

如果关注“不可发布风险”的召回，应把风险样本定义为正类后重新计算。

不要混用正类定义。

2. 灰区指标

至少记录：

  • review_rate：进入人工复核的比例
  • review_overturn_rate：人工推翻自动倾向的比例
  • gray_zone_positive_rate：灰区中实际可发布比例
  • time_to_review：人工复核耗时
  • reviewer_disagreement：评审者分歧率

如果灰区样本几乎都被判为同一类，说明阈值可能可以收窄。

如果灰区推翻率很高，说明评估器在边界附近缺少区分力。

3. 硬门禁指标

硬门禁也要监控：

  • 每条规则命中次数
  • Schema 失败字段分布
  • 状态迁移失败类型
  • 缺失证据比例
  • 规则版本变化前后命中差异
  • 同一样本重放一致性

某条规则突然大量命中，可能是模型退化，也可能是上游协议升级但 Schema 未同步。

4. 分数质量指标

语义分数应检查：

  • 与人工标签的排序相关性
  • 同一样本重复评分方差
  • 不同裁判间一致性
  • 分数与文本长度的相关性
  • 分数分布漂移
  • 不同群组的错误率
  • 分数是否集中在少数刻度

一个总是输出 0.8 左右的评估器，看似稳定，实际上没有区分力。

5. 端到端指标

最终要回到业务结果：

  • 错误放行率
  • 风险漏检率
  • 自动化覆盖率
  • 单样本评测成本
  • P50/P95 判定延迟
  • 人工节省时长
  • 线上申诉或纠错率
  • 模型升级后的回归失败数

评估器的离线分数提升，不必然带来系统收益。

十一、测试设计：不要只测几个正例

组合断言需要分别验证“规则正确”和“协作正确”。

1. 结构断言测试

覆盖：

  • 缺失每一个必填字段
  • 类型错误
  • 空字符串与纯空白
  • 数值边界 0 和 1
  • 越界值 -0.01 和 1.01
  • 非法枚举
  • 重复证据 ID
  • 未声明字段
  • Unicode 与转义字符
  • 超长字段

同时验证错误路径是否准确。

2. 规则断言测试

每条规则至少包含：

  • 正常通过样本
  • 单条件失败样本
  • 多条件同时失败
  • 边界值
  • 缺失依赖字段
  • 规则冲突
  • 旧版本兼容

规则测试应该完全脱离模型执行，保证快速、稳定。

3. 状态断言测试

覆盖合法和非法迁移矩阵。

例如：

before after expected
processing manual_review PASS
processing refunded PASS 或按业务约束
processing rejected FAIL
refunded processing FAIL
refunded refunded PASS，且无重复副作用

还要模拟：

  • 工具超时但状态已改变
  • 工具返回成功但状态未改变
  • 重试产生重复流水
  • 状态读取延迟
  • 多个系统状态不一致

4. 证据断言测试

覆盖：

  • ID 存在且属于当前任务
  • ID 不存在
  • 跨租户引用
  • 已过期文档
  • 引用片段无法定位
  • 同名不同版本文档
  • 结论中的实体不在证据中
  • 工具时间戳晚于回答时间
  • 候选文本伪造证据 ID

5. 语义断言测试

测试集不能只有明显好坏样本。

应加入最小对照：

  • 同义改写，标签不变
  • 只改变否定词，标签翻转
  • 只改变关键数字，标签翻转
  • 增加无关段落，相关性下降
  • 删除必要步骤，完整性下降
  • 引用真实但不支持结论，忠实度下降
  • 表达更流畅但事实不变，正确性不应上升
  • 答案变长但信息不变，总体不应自动变好

这类反事实样本比随机样本更能定位评估器盲区。

6. 组合策略测试

至少覆盖下列四象限：

硬断言 语义断言 预期
通过 高分 PASS
失败 高分 FAIL
通过 低分 FAIL
通过 灰区 REVIEW

第二行最关键。

它证明高语义分不能覆盖硬事实失败。

还要验证：

  • 多个硬断言失败时是否完整报告
  • 某个语义评分缺失时是否进入复核
  • 评估器超时时是否安全降级
  • 阈值配置非法时是否拒绝启动
  • 旧报告是否能用旧策略重放

十三、常见误区

1. 把所有检查都写进 Prompt

“请确保字段完整、不要编造、严格遵守状态”只是模型提示。

它不能替代运行时验证。

可由程序验证的约束应落到程序。

2. 认为确定性断言不需要版本

规则会随业务变化。

如果报告不记录规则版本，历史结果无法重放，也无法解释同一样本为什么前后结论不同。

3. 认为语义分数是概率

Judge 输出 0.9 不一定表示“有 90% 概率正确”。

除非经过明确校准，否则它只是某个评估器在某套量表上的分值。

4. 所有任务共用一个阈值

故障摘要、退款建议和营销文案的错误成本完全不同。

阈值至少要按任务和风险等级区分。

5. 用平均分掩盖关键失败

事实正确性、权限和状态一致性通常不可被表达质量补偿。

关键维度要设最低门槛或硬门禁。

6. 只优化 Accuracy

类别不平衡时，高 Accuracy 可能来自始终预测多数类。

应报告混淆矩阵、Precision、Recall、灰区和成本。

7. 只在容易样本上校准

容易样本会让任何评估器看起来可靠。

校准集必须包含边界、反事实和高风险长尾。

8. 评估器失败时默认通过

超时、解析失败和缺分都属于未知。

未知不应自动转化为成功。

9. 忽略人工评审分歧

如果人类对质量定义都不一致，自动评估器很难学到稳定边界。

应先测人工一致性，再讨论模型相关性。

10. 只保存最终标签

只保存 PASS 无法审计。

至少保留硬规则结果、分项分数、阈值、证据、版本和原始判词。

十四、上线前检查表

1. 问题定义

  • 已明确断言对象是完整证据包，而不是只有最终文本
  • 已定义可发布、不可发布和必须复核的边界
  • 已标出不可补偿的关键错误
  • 已定义正类，避免 Precision/Recall 语义混乱
  • 已按风险等级区分决策策略

2. 确定性断言

  • 输出协议有版本化 Schema
  • 业务不变量由代码或策略引擎执行
  • 状态迁移检查前态、后态和路径
  • 副作用动作有幂等断言
  • 证据 ID、归属、版本和时间有效
  • 规则失败能定位到具体字段或规则 ID
  • 所有规则版本进入审计报告

3. 语义断言

  • 每个维度都有清晰定义和评分锚点
  • 选择的评估器与要测的构念一致
  • 没用相似度替代数字、实体和状态验证
  • 分项分数在聚合前完整保留
  • 关键维度设置独立下限
  • 模型、Prompt、参数和参考资料均可追溯
  • 评估失败进入复核或安全失败

4. 阈值与数据

  • 阈值来自代表性标注集而非经验数字
  • 校准集和最终测试集相互独立
  • 数据包含明显样本、灰区和反事实样本
  • 已显式定义 FP、FN 和 REVIEW 成本
  • 已设置自动通过 Precision 等风险约束
  • 已按任务、语言、长度和风险做切片
  • 已为指标报告样本量和不确定性

5. 运行与审计

  • 报告包含原始证据和内容哈希
  • 决策能按历史版本重放
  • 监控灰区比例和人工推翻率
  • 监控分数与输入分布漂移
  • 有阈值和策略回滚机制
  • 高风险自动通过仍经过独立授权控制
  • 定期把人工分歧样本补入回归集

十五、总结

AI 测试里的断言不是从 assert equal 升级成 similarity > 0.8。

它需要一套分层测量和决策系统。

可以形式化的内容，包括结构、规则、状态和证据，应该优先使用确定性断言。

难以完全形式化的相关性、完整性和忠实度，再交给 Embedding、分类器、蕴含模型或 LLM Judge。

两类结果不能简单平均。

关键硬门禁失败时必须失败；语义分数处于不确定区域时应进入人工复核；只有硬约束通过且各关键语义维度越过通过阈值时，才允许自动通过。

阈值也不是模型附赠的常数。

它必须用代表性数据、误报漏报成本、人工容量和风险约束共同校准，并在上线后持续监控漂移。

最终，一条可信的 AI 断言应该能够回答六个问题：

  1. 判了什么？
  2. 根据什么证据？
  3. 哪些是硬事实，哪些是模型判断？
  4. 使用了哪个规则、模型和阈值版本？
  5. 不确定性有多大？
  6. 为什么是通过、复核或失败？

只有这些问题都能回答，AI 测试结果才真正具备工程上的可验证性。
