AI测试-69-测试开发工程师怎样用90天完成一个可展示的AI质量工程项目

发表于 2026-07-03 分类于 AI测试 本文字数： 19k 阅读时长 ≈ 1:08

90 天能不能完成一个有深度的 AI 质量工程项目？

如果目标是训练一个基础模型、搭建全功能平台、覆盖所有 AI 风险并达到生产成熟度，90 天不够。如果目标只是接一个聊天接口、做一个网页、准备几张效果截图，三天就可能完成，但它几乎不能证明测试开发能力。

可行的中间目标是：选择一个自己理解的真实问题，把范围缩到一个端到端闭环，交付可运行代码、版本化数据、自动评测、Trace、发布 Gate、故障注入、值班 runbook 和可复核证据。项目不需要假装生产可用，但必须让评审者能够在一台普通电脑上重跑、看到失败、定位原因并验证修复。

本文给出一个完整构造项目：StabilityLens，Android 稳定性故障分诊助手的离线质量工程系统。输入是经过脱敏的故障摘要，候选系统输出故障类别、应收集证据、允许引用的 runbook 和下一步动作。项目不连接真实设备、不读取真实公司日志、不调用真实模型，也不自动重启、清数据或提交缺陷。重点不是“AI 回答很聪明”，而是测试开发工程师怎样证明它在已定义范围内可评测、可追踪、可阻断、可恢复。

本文资料边界截至 2026-07-03（含）。项目名称、组织、用户、数据规模、时间预算、指标、阈值、故障、收益和面试结果全部是构造示例。示例不推荐具体模型、云服务、评测平台或商业产品；读者可以把相同骨架替换成客服问答、RAG、工具调用、语音 Agent 或内部知识助手。

一、90 天项目的目标不是“功能最多”，而是“证据闭环最短”

1.1 一个可展示项目至少回答六个问题

只展示最终准确率，无法证明数据有没有泄漏、样本是否被删、失败是否重试到消失。只展示架构图，无法证明代码能运行。只展示 CI 绿灯，无法证明门槛与真实风险有关。90 天的工作应围绕这六个问题收敛。

1.2 为什么选择熟悉领域

AI 质量工程需要领域 oracle。测试开发工程师已经熟悉 Android Crash、ANR、Watchdog、Native Crash、重启、资源异常和日志证据，就不必先花两个月学习一个陌生业务。领域知识可以直接转成：

  • case 的预期分类和禁止结论；
  • 必须收集的 logcat、traces、tombstone、pstore、bugreport 等证据；
  • “信息不足”时的正确拒绝与补采动作；
  • 高风险动作边界，例如不得直接建议清除用户数据；
  • 故障 slice、排查顺序和验收门槛。

这也体现能力迁移：传统测试中的需求、数据、自动化、稳定性、故障注入和报告，被扩展到概率性候选系统，而不是被新框架替代。

1.3 90 天完成不等于 90 天生产上线

本文的完成定义是 portfolio-grade engineering prototype：

  • 单机、离线、标准库即可运行核心闭环；
  • 数据全部为构造或公开可再分发的脱敏材料；
  • 候选通过统一 adapter 接入，默认使用确定性 fixture；
  • 至少一套 baseline、一个 candidate 和一个故意失败版本；
  • 质量、可靠性、安全和证据门有明确分母；
  • 故障注入与 runbook 实际演练过；
  • README、ADR、报告、复盘和限制声明齐全；
  • 不承诺生产容量、真实模型质量、法规符合性或通用化能力。

生产系统还需要身份、权限、密钥、部署、容量、真实流量保护、事件响应、数据治理和长期值班。把原型边界写清，比在 README 中写“production ready”更专业。

二、贯穿问题：Android 稳定性分诊为什么值得做

2.1 当前工作流

构造团队每周处理约 180 个稳定性失败记录。值班人员先读测试任务、设备状态和现象，再判断是 App Crash、ANR、Native Crash、system_server Watchdog、Kernel Panic、资源压力还是证据不足；之后决定收集哪些材料并转给相应 owner。

抽样 120 个工单得到构造基线：

指标 分子 / 分母 基线
首次分类可用率 首次分类无需改 / 有完整复核的工单 82 / 120 = 68.3%
证据清单完整率 必需证据齐全 / 有完整复核的工单 71 / 120 = 59.2%
中位初始分诊耗时 从接单到首次可执行结论 18 分钟
P90 初始分诊耗时 同一时间定义 47 分钟

这些数字是构造示例。真实项目必须说明抽样时间、工单类型、复核者和排除项，不能把一段忙碌周的数据外推到全年。

输入：一个经过脱敏的故障摘要，包含现象、时间、进程、重启原因片段和已存在证据 ID。

输出：

2.3 项目的验收问题

三、第一次错误决策：先做聊天界面，后补评测

3.1 为什么当时看起来合理

第一周很容易选择“先看到效果”：用一个模型接口接收日志，页面左边上传、右边展示分析，再做漂亮 loading 和 Markdown。两天内就能录屏，项目看起来进展很快。

3.2 第 9 天出现的问题

  • 同一个输入重复运行三次得到两个类别，却没有 candidate 版本和参数；
  • 页面只保存最终文本，无法知道引用来自哪个 runbook 版本；
  • 10 条 Demo 都由开发者挑选，没有失败样本和明确分母；
  • 输出说“主线程 Binder 等待导致 ANR”，但输入中没有 traces；
  • 接口超时后页面自动重试，两个结果谁是最终结果没有记录；
  • 为了让演示稳定，开发者不断修改 Prompt，却没有任何回归集。

3.3 根因不是“前端浪费时间”

真正的错误是交付顺序。界面成为项目主干，数据、运行身份、判定和证据被当成附属功能。没有最小评测闭环时，任何 Prompt 调整都无法判断改善还是只适配 Demo。

四、验收合同：第 1 天就写下“什么叫完成”

4.1 功能与质量门

构造 acceptance-contract@3：

阈值是构造值。permission slice 要求 100%，但有限样本通过仍不证明不存在未知越权；它表达的是已登记 critical case 不允许用平均分抵消。

4.2 验收状态不是 PASS/FAIL 两个词

作品集可以只实现 PASS/FAIL 的代码主路径，但报告必须理解其他状态。最危险的做法是把没跑、没记录、没权限查看都写成 PASS。

4.3 Definition of Done

项目完成必须同时满足：

  • clean checkout 后按 README 在 10 分钟内跑通离线示例；
  • 最大 Python 示例至少包含 18 个独立测试；
  • dataset 摘要与报告中的摘要一致，篡改一条 case 会被发现；
  • 每条结果有 terminal status，每次 attempt 有 Trace；
  • Gate 能阻断平均分掩盖弱 slice、critical unsafe action 和 Trace 缺失；
  • 至少完成 timeout、malformed output、wrong citation、evidence tamper 四类注入；
  • runbook 由另一名测试者按演示脚本执行一次；
  • README、ADR、报告、复盘与限制声明可被独立阅读；
  • 公开仓库不包含真实日志、账号、密钥、模型凭据或内部文档。

五、最小可用架构：一个仓库、四条链路

架构刻意保持小：

5.1 数据链

case 从 data/cases/*.jsonl 进入 manifest。每条保存 case ID、slice、risk、输入、预期分类、必需证据、允许引用和禁止动作。manifest 保存文件、case 数、摘要、来源类别、允许用途和 split。

5.2 执行链

Runner 接收明确的 run_id + dataset_digest + candidate_id + runner_version + retry_policy。候选只能通过 adapter 返回结构化对象。故障注入器在 adapter 边界产生 timeout、malformed 或 wrong citation，避免把测试钩子散进业务代码。

5.3 判定链

第一版只用确定性 oracle：Schema、分类枚举、必需证据集合、引用白名单、动作相等和禁止动作。语义 Judge 可以以后加入，但不是核心依赖。这样评审者无需 API Key 就能重跑，也能解释每个失败。

5.4 证据链

每次 attempt 写 Trace；每个 case 写评判结果；Gate 保存门槛、分子、分母、失败原因和版本；最终证据包对 README、ADR、run report、evaluation、runbook 和 drill postmortem 做摘要清单。

六、仓库结构：让读者从入口走到证据

单篇文章的代码把这些职责放在一个文件里方便运行。真实仓库按职责拆分，但不需要在第 1 天建立插件系统、数据库、消息队列和微服务。

七、Dataset：案例数量不是资产，版本和边界才是

7.1 从 12 条开始，而不是先追求 1,000 条

第 1 至 10 天先构造 12 条：每个主要类别至少一条正常、一条边界；其中 3 条必须是证据不足或危险动作。目标是验证数据结构和 evaluator，而不是得出统计结论。

permission_safety 8 禁止清数据、刷机、绕权限和泄露路径
合计 72 主 slice 互斥，属性可交叉

第 31 至 45 天由独立复核者再建立 48 条 held-out，最终评测分母是 120 条。规模仍小，因此报告只声明“覆盖登记 case”，不宣称代表所有 Android 稳定性问题。

7.2 case schema

输入只保留完成任务所需信息。真实日志先做授权、最小化和脱敏；公开作品集优先完全构造数据，避免“删了设备号”就误以为可以公开整份 bugreport。

7.3 Dataset Card

至少回答：

  • 数据用途与明确禁止用途；
  • 构造、公开或内部来源及许可/授权；
  • 时间、设备、语言、类别和风险分布；
  • 标注指南、复核流程与争议处理；
  • dev/held-out 如何隔离，谁能看到标签；
  • 重复、近似、污染和泄漏检查；
  • 已知缺口，例如没有厂商私有 Watchdog 和真实多语言日志；
  • 版本变化、废弃 case 和兼容策略。

7.4 版本摘要解决什么

规范化 JSON 后计算摘要，可以发现 case 内容、顺序或标签变化。它不能证明标签正确，也不能证明数据合法。dataset_digest 必须同时进入 run、Trace 和 report，避免报告引用另一个数据版本。

7.5 分母不从结果反推

Dataset manifest 预先声明 expected case ID。Runner 只返回 118 条时，coverage 是 118/120，不是对 118 条计算 100%。缺失两条要解释为 candidate failure、runner failure、invalid 或 unknown；未经批准不能从 manifest 删除。

八、Runner：确定性地运行一个非确定性候选

8.1 Runner 固定的不是答案，而是实验条件

每次 run 固定：

  • dataset digest 和 case 顺序；
  • candidate ID、模型/fixture/Prompt/参数版本；
  • runner version、timeout、max attempts 和 backoff；
  • 并发、随机种子与缓存策略；
  • evaluator 与 gate policy；
  • fault plan；
  • started/ended 时间和环境摘要。

候选输出仍可能不同，但差异有可比较边界。

8.2 Attempt 与 Case Result 分开

一次 case 可能先 timeout 再成功。Trace 至少有两个 attempt：

只保存最终成功会掩盖依赖不稳定和重试成本。只按 attempt 算准确率又会把一次用户任务拆成两个分母。报告同时给 case 级结果和 attempt 级可靠性。

8.3 重试边界

timeout 可以重试，但总 deadline 与最大次数固定；malformed output 是否重试要预注册；危险动作不应通过“再问一次直到安全”从安全分母中消失。工具副作用场景还要有幂等与最终状态对账，本项目没有写操作，明确不证明副作用安全。

8.4 Fixture Candidate 的价值

确定性 fixture 不是伪造模型成绩，而是基础设施 oracle：

  • Runner、Trace、Evaluator 和 Gate 有稳定预期；
  • 无网络即可执行 CI；
  • 可以构造 timeout、坏结构和危险动作；
  • 接真实候选时，基础设施回归和候选行为回归能分开。

作品集报告必须把 fixture 结果标为 synthetic candidate，不能写成“模型准确率 90%”。

九、Trace：让一次失败能回到具体版本和 attempt

9.1 最小字段

真实项目还需要 Prompt、检索、模型、工具和策略 span。作品集先保证字段含义稳定、版本完整、敏感内容不进入普通 Trace。

9.2 Trace coverage

若 case 有结果但 Trace 丢失，质量结果不能被称为可复核。Gate 可以将其阻断或标为 UNPROVEN。Trace 本身也不是事实真值：候选可能返回错误内容，Collector 也可能在写入前丢失；需要外部 case manifest 与报告对账。

“有一条 terminal Trace”仍不足以进入分子。Gate 应先确认它的 run_id、dataset_digest、candidate_id 和 runner_version 与当前 run 一致，再检查同一 case 的 attempt 从 1 连续、每个 attempt 唯一、只有一个终态，并且终态 attempt 与 CaseResult.attempts 对得上。否则，从另一次 run 复制的 Trace，或重复写入的终态，都会虚假填平 coverage 缺口。本文后面的离线 Gate 和反例测试实现了这些关联约束。

9.3 高基数和隐私

case ID 可以作为离线 Trace 属性，真实生产环境不应把完整问题、日志、用户 ID 和任意错误文本都变成高基数 metric label。原文放受控对象，Trace 保存引用、摘要、分类和版本。OpenTelemetry 提供 Trace/Span/Metric/Log 的通用语义，本项目的 case_id、candidate_id 和 fault 是自定义字段，不自动成为标准属性。

十、Gate：阻断原因必须比一个红灯更具体

10.1 case pass 是合取关系

某个回答分类正确但建议清数据，case 必须失败且触发 critical safety gate。引用白名单只证明引用 ID 在允许集合，不证明引用内容真的支持结论；真实项目还要对 runbook 版本和支持关系做 oracle。

10.2 四类门

门 分母 构造阈值
overall quality 通过 case / expected case >= 0.85
slice quality slice 通过 / slice expected 各 slice 独立
critical safety 危险结果 / critical case 0
trace coverage 完整 terminal trace / expected case 1.00
timeout recovery 恢复成功 case / 注入 timeout case >= 0.90

没有注入 timeout 时，recovery 分母为零，状态应是 UNPROVEN 或该次 run 不适用，不能写 100%。本文演示要求 fault run 必须包含注入分母。

同一批 case 同时运行 baseline 与 candidate 时，最有信息量的不是两个独立总分，而是逐 case 的配对变化：

Baseline Candidate Case 数 解释

10.5 Invalid、Fail 和 Unknown 的统计处理

一次结果无法解析，可能是候选输出坏结构，也可能是 Runner 版本错误。两者都不能从分母消失：

用于严格发布门时，可报告 106/120；用于诊断候选行为时，可另外报告 106/117，但必须同时显示 2 个 invalid 和 1 个 unknown。只有当整次 run 的预注册无效条件满足，例如 dataset digest 错、Evaluator 加载了错误 policy，才把整个 run 标为 INVALID 并重新执行。不能逐条挑出失败后把分母改成“可用结果”。

10.6 小样本结果怎样诚实表达

120 条 held-out 对总体通过率只能给有限精度，对只有 8 条的 permission slice 更不能得出“真实逃逸率为零”。8/8 的正确措辞是“在这 8 条登记 critical case 中未观察到逃逸”。报告还要写：

  • case 是否独立，是否多个 case 来自同一模板；
  • slice 分布是否接近目标任务，而不是为了凑均衡；
  • 标签由几人复核，争议率是多少；
  • 同一候选重复运行时类别是否变化；
  • 哪些 case 在 Prompt 或 fixture 开发时已经可见；
  • held-out 是否有精确或近似内容泄漏。

如果接入真实非确定性候选，可以对每条重复三次，同时报告 case pass、attempt pass 和 instability。三次都通过仍不能证明未来必然通过，但能区分持续错误与偶发波动。

10.7 Gate 阈值的变更纪律

看到 candidate 只有 84.2%，再把 overall 从 0.85 降到 0.84，属于结果驱动调门。阈值可以改变，但需要：

  1. 记录原阈值、失败结果和业务影响；
  2. 说明原门是否设计错误，还是组织决定接受更高风险；
  3. 由 acceptance owner 而非候选作者批准；
  4. 保存有效期、补偿控制和下一复核条件；
  5. 若阈值已被 held-out 结果影响，另建未见数据验证新策略。

这套纪律防止项目通过“调到绿”为结束。作品集里保留一次失败 policy 和后续 ADR，会比只保留最终绿色配置更能证明判断能力。

14.2 ADR 证明决策过程，不证明结果正确

十七、代码的设计边界：通过测试不等于项目已经生产可用

17.1 Dataset 摘要是变更检测，不是数据真实性证明

代码把完整 case manifest 纳入摘要，并把独立的 trusted_dataset 冻结进 Gate Policy。Gate 的 expected 分母、slice 和 risk 都从这个受信清单读取，只把 Run 自报清单用于对账；删掉失败结果与对应 Trace 不能缩小分母。标签被改后摘要变化，旧 policy 会拒绝运行；但摘要不能判断新标签是否由有资格专家复核，也不能判断输入是否泄露真实数据。生产系统需要数据 owner、审批、访问、血缘、分割隔离和删除流程。

17.2 Fixture Adapter 是基础设施测试替身

它按 case ID 返回确定性对象，能够测试 Runner 和 Gate。真实模型不会知道 case ID，也不应访问 expected oracle。接入真实候选时，adapter 只能接收输入和允许上下文；held-out 标签应留在 evaluator 边界。fixture 的 100% 只证明这套构造响应符合构造 oracle。

17.3 Fault Injector 不模拟真实网络全部语义

timeout 是本地抛出的异常，没有覆盖连接建立、流式半包、服务端已计算但客户端取消、429 的 Retry-After、DNS、代理或账单状态。它验证状态机基础，再由集成测试补真实协议故障。

17.4 Trace ID 是确定性摘要，不是安全令牌

代码用 run/case/attempt/candidate 生成可复现 ID，没有随机性，也没有签名。它适合教学对账，不适合作为访问凭据或不可伪造证据。生产 Trace ID 与 W3C Trace Context 传播还需要符合所用 SDK 和协议。

17.5 Gate 的 timeout recovery 有意拒绝零分母

Gate Policy 冻结 expected_timeout_case_ids，恢复率分母来自预注册 fault plan，观测注入集合则从通过 Schema 与状态机校验的 Trace 推导。缺少计划内注入、出现计划外注入，或 Run 自报 had_timeout_injection 与 Trace 不一致都会阻断；完全没有 timeout 时报告 0 / expected 和 timeout_recovery_unproven，不会把 0/0 记成 100%。常规质量 run 与 fault run 可以分开，发布 Gate 再要求两份受信报告；单文件示例把它们合并以突出分母。

17.6 Evidence Manifest 需要包外信任

验证函数接收 trusted_manifest。如果攻击者可以同时改文件和传入的新 manifest，验证仍会通过。生产环境需要由 CI、制品系统或有权签发者把 manifest 绑定到提交、工作流和身份，并处理撤销、保留与访问。GitHub artifact attestation 可以帮助建立构建来源，但不能替代业务评测真实性与数据授权。

十八、一次完整排障：绿色质量，为什么 Gate 仍然阻断

18.1 场景

第 71 天演示彩排，fixture 的 120 条 case 全部通过，slice 表全绿，critical unsafe 为零；Gate 却返回 trace_coverage=119/120，状态 FAIL。开发者第一反应是“只是少一条 Trace，不影响答案”，准备手工把 coverage 改为 100%。

18.2 判断顺序

  1. 固定 run_id=run-drill-071，禁止覆盖原报告；
  2. 从 dataset manifest 得到 expected 120，不从结果目录计数；
  3. terminal results 为 120，说明候选和 evaluator 都完成；
  4. terminal Trace case ID 只有 119，缺 SL-REBOOT-034；
  5. attempt 日志显示该 case 先 timeout，第二次成功；
  6. Trace writer 以 case_id 作为去重键，第一次 timeout 与第二次 terminal 共用键；
  7. 异步刷新乱序到达时，timeout 记录覆盖了 terminal 记录；
  8. JSON report 从内存结果生成，因此质量全绿；证据存储却无法证明最终 attempt。

18.3 根因

去重身份设计错了。Attempt Trace 应使用 (run_id, case_id, attempt)，case terminal summary 才使用 (run_id, case_id)。把两层身份压成同一键，让重试证据互相覆盖。

18.4 修复

  • Trace store 的唯一键改为 attempt identity；
  • terminal summary 引用 final attempt trace ID；
  • 同一 attempt 同摘要允许幂等重传，同 ID 异摘要隔离；
  • 增加乱序、重复、进程重启和 partial flush 测试；
  • Gate 继续使用外部 expected case manifest；
  • 原 run-drill-071 保留 FAIL，新 run 使用 run-drill-072。

18.5 为什么不能手工改成 100%

质量结果可能确实正确，但“可追溯”门失败也是事实。手工改报告会让未来无法区分候选错误和证据链错误。更诚实的状态是：行为评测观察为通过，交付证据不完整，因此不能形成可复核发布结论。

Action Owner 完成定义
attempt/terminal 身份分离 Runner 乱序与重复测试通过，旧 run 不重写
Trace coverage 对账 Gate expected/result/terminal trace 三方逐 ID 报告

离线 fixture 的通过率只验证工程链。即使接入一个真实模型，120 条小样本也只覆盖固定日期、语言和故障类型。

24.2 不能证明生产可靠性与容量

本地 timeout 不代表真实网络、服务端队列、限流、流式中断和跨区域故障。没有持续负载、容量和长期运行证据，不能宣称 SLO。

24.3 不能证明自动动作安全

项目是只读建议，没有工具鉴权、幂等、审批、外部状态对账和补偿。把它改成自动清理设备或提单会产生新的高风险系统，必须重新建模。

24.4 不能证明数据合规

使用构造数据降低公开风险，不代表真实项目已经满足隐私、版权、劳动、合同或行业要求。适用性由有权角色按具体事实判断。

24.5 不能证明指标带来因果收益

时间和完整率前后变化受到人员、任务和并行流程影响。没有可比对照和足够样本时，只能作为试点观察。

24.6 不能证明证据不可伪造

SHA-256 manifest 能发现相对受信 manifest 的变化，不能自己提供签发身份、可信时间和完整性根。生产制品需要外部信任与访问控制。

24.7 不能证明已经“掌握 AI”

项目证明的是：能够把一个 AI 问题变成数据、执行、观测、门禁和证据。模型、数据工程、安全、LLMOps 和领域能力仍需通过后续项目持续扩展。

二十六、结语：90 天只做一个闭环，但把它做到能失败、能定位、能复核
