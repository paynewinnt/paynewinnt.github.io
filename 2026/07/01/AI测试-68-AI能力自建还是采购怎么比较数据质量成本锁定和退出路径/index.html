AI测试-68-AI能力自建还是采购怎么比较数据质量成本锁定和退出路径

发表于 2026-07-01 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:02

“自建还是采购”看起来像一道财务选择题：采购上线快，自建可控；把两边报价放进表格，开会选一个总分高的方案即可。

AI 能力进入真实业务后，这种比较方式很容易选错对象。

采购的可能只是模型推理，也可能连同知识库、评测、策略、日志和运营控制面一起采购；自建可能只是统一网关与质量系统，也可能真的包含训练、推理、容量和值班。两份都叫“AI 平台”的方案，责任边界可以完全不同。一个候选在公开 Demo 上回答更漂亮，不代表它能处理本组织的权限、拒答、故障和退出；一份单价更低的报价，也不包含评测、人审、合规取证、故障兜底与迁移期间双跑的成本。

更关键的是，采购决定并不会把风险转交给供应商。最终用户看到的是组织提供的功能，数据是否越界、错误动作是否发生、服务是否可恢复、供应商停止服务后能否退出，仍需要由采用方给出证据。

因此，本文不提供“自建优于采购”或“采购优于自建”的通用结论，而是建立一套可以执行、复核和重跑的决策系统：

本文资料边界截至 2026-07-01（含）。全文中的组织、供应商、产品、报价、调用量、团队规模、指标、权重、阈值、事故和收益均为构造示例，不对应真实公司，也不推荐任何具体商业产品。标准和框架用于提供风险、质量、成本与工程过程的共同语言，不替组织作法律、采购或财务判断。

一、先定义决策对象：不是“模型”，而是一组可运营能力

1.1 三种范围经常被混在一起

同一句“采购 AI 能力”至少可能表示三件事：

范围 采购内容 组织仍需承担的能力
模型能力 推理端点、模型版本和用量额度 数据准备、Prompt、评测、网关、策略、可观测、回退
应用能力 问答、检索、工作流或 Agent 产品 业务事实源、权限、集成、验收、运营、事故和退出
托管平台 模型、数据、编排、评测、监控与控制台 需求、监督、风险接受、供应商治理、外部对账和退出

如果候选 A 报的是推理单价，候选 B 报的是包含知识库与人工服务的年费，直接比较价格没有意义。决策记录必须先固定“能力边界”，写明每个功能由谁建设、谁运行、谁证明、谁在事故时值班。

本文的“自建”也不等于从零训练基础模型。构造案例中的自建候选使用可替换的离线推理夹具，组织自己负责网关、知识摄取、策略、评测、证据和运行；采购候选提供端到端托管应用；组合候选采购推理能力，但把数据、策略、评测、Trace 与业务工具适配器留在组织控制域。

1.2 决策单位是一个版本化 bundle

每个候选必须以不可含糊的 bundle 进入评估：

只写“候选 H”会让后续复测失去对象。模型、数据驻留声明、API、价格、SLA 或导出格式任一变化，都可能形成新 bundle，需要按变更风险决定重跑哪些证据。

1.3 什么不能由一次选型证明

  • 盲测领先不能证明未来版本仍领先，也不能证明未覆盖业务 slice 的质量。
  • 通过安全样本不能证明不存在未知攻击路径。
  • 当前区域内处理不能证明支持工单、遥测、备份和管理员控制面都在同一区域。
  • 提供 OpenAPI 文件不能证明行为、限流、错误语义、向量、策略和运营流程可替换。
  • 合同写有“可导出”不能证明数据能在退出时限内完整、可校验地导出。
  • 删除证明只能覆盖声明并被验证的存储面，不能证明未知副本绝对不存在。
  • TCO 模型只能在明确假设和情景内比较，不能把三年预测伪装成确定账单。
  • 组合方案降低单点集中风险，不代表复杂度和责任边界自动下降。

这些否定边界不是免责文字。它们决定后面需要保存哪些分母、未知项和演练证据。

二、贯穿构造案例：Orion 服务政策助手

2.1 业务问题

构造组织准备给 240 名一线服务人员提供政策助手 Orion。助手读取 320 份内部政策文档，回答退换、保修、账户和服务中断问题，并给出引用。它只能建议下一步，不能直接退款、改账户或向用户作赔付承诺。预计基准负载为每天 18,000 次请求，峰值每秒 14 次，覆盖中文、英文、日文和西班牙文。

真实问题不是“需要一个聊天机器人”，而是：

这句话同时包含用户结果、风险边界和退出目标。它比“准确率达到 90%”更接近可验收问题。

2.2 三个候选

候选 构造方案 初始吸引力 隐藏责任
B：自建 自有网关、检索、规则、评测、运行，使用本地可替换模型适配器 数据与运行控制强 需要容量、模型适配、值班和持续评测投入
P：采购 托管知识库、问答、控制台与分析 六周可上线，公开 Demo 分高 控制面驻留、遥测、导出、版本变更和退出依赖供应商
H：组合 采购两个推理端点，自有数据、检索、策略、评测、Trace 和工具层 交付速度与控制折中 双适配器、路由、对账和合同治理增加复杂度

供应商名称、产品能力和数字都没有使用真实对象。候选 P 和 H 中的“供应商”只是教学角色。

2.3 第一版失败决策

第一版决策表只放了五列：公开基准、演示观感、首年报价、上线周期和厂商案例。候选 P 以 92/100 获胜。试点接入两周后才发现：

  1. 内容数据声明在目标区域处理，但管理控制台、支持诊断包和用量遥测可能跨区；
  2. 导出只包含文档原文件，不包含切片 ID、权限映射、反馈标签和评测历史；
  3. API 返回引用文本，却不返回稳定证据 ID，无法与内部文档版本对账；
  4. 价格只包含推理，超额检索、日志保留、私有连接和高级支持另计；
  5. 合同允许提前通知后替换底层模型，但没有兼容窗口和回归协作义务；
  6. 所谓“标准 API”没有统一错误码、幂等语义和流式中断行为。

这不是供应商“隐瞒一切”的故事。根因是决策系统没有要求这些事实以可验证证据进入分母。团队用销售演示回答了工程问题，用首年价格回答了生命周期问题，用接口形状回答了可替换性问题。

修复动作不是立即改选自建，而是撤回原评分，重新建立需求合同和证据包。候选 P 仍可以参评，但未知项不再默认记满分。

三、问题合同：先约束“为什么做”，再约束“买什么”

3.1 Problem Contract

问题合同至少包含七组字段：

字段 Orion 构造内容 验证证据
用户与任务 240 名服务人员查询已批准政策 任务清单、用户访谈记录、现状时间样本
业务结果 查找耗时下降，首次回复无需返工比例提升 工单事实源、抽样方案、前后对照
禁止结果 不直接执行写操作，不承诺未授权赔付 工具白名单、禁止声明集、审计 Trace
数据边界 内部政策与用户问题分级处理 数据清单、流向图、驻留证据
风险等级 权限泄露和高风险错误为硬阻断 风险登记册、批准阈值
运行目标 峰值容量、延迟、可用、降级和恢复 负载模型、SLO、演练报告
退出目标 2 小时内恢复关键查询，10 个工作日完成受控导出 出口 SLO、替代演练、导出 manifest

合同要保存 problem_contract_id 和批准者。后面所有 benchmark、报价和方案必须引用同一个合同版本。否则候选可以通过悄悄缩小问题来提高分数，例如把困难的无证据拒答从评测范围移除。

3.2 Requirement Contract：硬门与偏好分开

需求合同中的条件分为三类：

硬约束：不满足就不具备进入加权排名的资格。例如受限内容不得用于供应商通用训练、内容面与控制面必须符合批准区域、任何高风险权限泄露为零、退出替代演练在 2 小时内通过。

目标门槛：当前版本应达到，失败时可以明确阻断或由有权角色限期接受风险。例如每个业务 slice 的最低通过率、P95 延迟、服务成功率、导出完成率。

偏好：多个合格方案之间的取舍。例如更短交付周期、更低三年 TCO、更高控制度。偏好才适合进入权重，不应让低价格抵消数据驻留失败。

3.3 需求追踪不是文档链接

每条关键需求至少追踪到四个对象：

“需求文档里写过数据保护”不代表它已经进入架构、合同和验收。缺少任何一段，状态应是 UNPROVEN，不是 PASS。

四、决策架构：硬门、证据和偏好不能揉成一个总分

图中的顺序不可交换。先固定问题与候选 bundle，再收集相互独立的证据，执行硬门，最后才对合格候选做偏好评分和敏感性分析。

4.1 四个职责角色

角色 责任 不能单独完成的动作
Problem Owner 批准任务、收益和禁止结果 不能批准自己无法承担的数据例外
Evidence Custodian 保管盲测标签、数据清单和证据 manifest 不能修改候选实现以帮助通过
Evaluator 执行 benchmark、故障注入和统计 不能在看到候选结果后改门槛
Decision Authority 接受权重、例外、合同和组合策略 不能把未知证据默认为通过

小团队可以一人兼多个工作，但高风险硬门的设计、执行与接受不应全部由同一身份完成。职责分离是为了避免候选实现者同时决定“什么叫通过”。

4.2 Evidence Manifest

每次比较生成一份 manifest：

摘要只帮助发现对象变更，不证明对象内容真实。供应商声明仍需要合同、技术测试、审计材料或独立验证支持；内部构造的 benchmark 也可能有标签错误和覆盖缺口。

五、盲测 benchmark：用业务 slice 比较行为，不比较演示技巧

5.1 先冻结协议，再接触候选结果

Orion 的盲测流程分为七步：

  1. Problem Owner 批准任务、禁止结果和业务 slice；
  2. Evidence Custodian 从政策事实源构造输入、证据和预期约束；
  3. case ID 随机化，候选只看到输入和允许上下文，不看到标签与阈值；
  4. 候选通过同一适配接口执行，固定超时、重试和并发；
  5. Runner 保存输入摘要、候选 bundle、Trace、输出、引用 ID、错误码和时间；
  6. 确定性判定先运行，人工/语义复核只处理预注册争议项；
  7. 解盲后按 slice 报告分子、分母、无效、未知和置信区间，不只给总分。

候选开发者可以获得开发集，但不能获得 held-out 标签。若供应商需要调试失败样本，只提供经过批准的开发副本或抽象错误类别；把全部盲测答案回传给候选，会把验收变成针对测试集优化。

八、三年 TCO：建设、运行、评测、合规和退出都要进入账本

8.1 TCO 的五类成本

建设/采购包括需求、架构、集成、数据迁移、适配器、网络、身份、初始评测和上线演练；不能只放许可证。

运行包括推理、存储、网络、日志、支持、值班、容量冗余、人工复核、缺陷修复和供应商管理。

评测包括数据采集、标注、专家复核、Runner、Judge 校准、每次模型/Prompt/索引变更回归与生产抽样。

合规/治理包括风险评审、隐私与安全评估、合同、审计证据、访问复核、事件响应和控制维护。具体法律适用性由有权职能判断。

退出包括持续维护可移植接口、定期导出、替代环境、双跑、迁移、删除验证、合同结束支持和剩余承诺费用。

8.2 不把人员写成免费资源

构造 TCO 使用“有效投入月 × 全负担月成本”，而不是只算新增招聘。现有工程师投入两个月仍然有机会成本。共享平台成本按可解释分配键进入：

分配键可以是计算、存储、Trace 量或支持工时，但要说明为什么与成本因果相关。为了让某候选更便宜而随意把共享成本放到别处，会污染比较。

九、可移植接口不是可替换性

9.1 六层锁定面

锁定面 表现 可验证问题
协议 私有 SDK、流式事件、错误码、批量格式 标准适配器能否通过契约测试
数据 专有切片、向量、反馈、ACL、评测历史 导出是否完整、带版本和关系
行为 Prompt、工具选择、拒答和引用语义依赖模型 替代候选能否通过相同业务门
工作流 专有 Agent 状态、审批、重试与人工接管 中断状态能否迁移或安全终止

拥有 OpenAPI 3.1.1 描述，只能提高协议层可检查性。两个端点即使接受相同 JSON，也可能在 tokenization、上下文截断、工具并行、内容策略、流式结束、超时后状态和限流上不同。

9.2 Portability 的四个等级

P1 是文件可移动，P3 才接近可替换。即使达到 P3，也只对演练 bundle、数据范围和负载成立。

9.3 自建同样会锁定

自建会锁定在内部代码、少数维护者、特定硬件、训练格式、隐式 Prompt 和缺少文档的运营习惯上。供应商集中风险有外部形态，内部关键人集中也是真实锁定。候选 B 的风险登记册因此包含：

  • 两名模型适配器维护者均离岗时的接管时间；
  • 本地推理硬件停产或驱动升级；
  • 自定义向量格式无迁移工具；
  • 评测标签只保存在个人目录；
  • 值班只会重启，不会解释质量门失败。

十一、合同不是法律附件孤岛，而是技术控制的外部边界

11.1 数据与使用条款

合同/数据处理附表需要与数据流对应，至少明确：

  • customer content、metadata、telemetry、support data 的定义；
  • 每类数据的处理目的、区域、子处理者、保留和访问；
  • 是否用于通用训练、产品改进、人工复核和安全分析；
  • 新用途、新区域和新子处理者的通知、异议与退出机制；
  • 支持访问的案件、批准、最小字段、时限和审计交付；
  • 事故通知所需事实、时间线、日志和协作方式。

“不会使用客户数据训练”仍需问：是否用于人工质量检查、缓存、滥用检测或特征提取；派生对象是否受同一约束。

11.2 服务与变更条款

需要把技术版本化责任写进去：

  • 服务 SLI 的分子、分母、排除项和测量点；
  • 模型、策略、API、限流、地区和数据处理变化的通知期；
  • 重大变化的兼容窗口、旧版可用期和回归协作；
  • 故障时的状态、RCA、证据交付和恢复沟通；
  • 组织拥有独立质量门，供应商 SLA 不替代业务验收。

11.3 退出条款

  • 导出对象清单、格式、关系、版本、摘要与费用；
  • 出口 SLO 的起止时间、暂停条件和失败补救；
  • 迁移期双跑、只读访问和技术协助；
  • 主库、索引、备份、支持副本与子处理者删除状态；
  • 合同终止后验证窗口和证据保留；
  • 供应商破产、停售或服务不可用时的应急路径。

条款本身不是技术验证。最有效的合同验收是让供应商在签约前或可退出试点期执行一次小规模导出、导入和删除演练。

十二、组合策略：降低集中风险，同时接受更多系统复杂度

12.1 Orion 的最终构造策略

重新评估后，Orion 选择候选 H 作为主方案，但不是“买两个模型”这么简单：

路由不是按最低单价随机分配，而是按数据分类、语言、能力、错误预算和候选健康决定。高风险问题只有通过当前 bundle 评测和区域门的端点才可接收。

12.2 组合方案新增的失败面

  • 两个端点的 token、工具、拒答和流式行为不同；
  • 路由可能让某个供应商只收到困难样本，指标不可直接比较；
  • 双供应商都依赖同一上游基础设施时，表面冗余不独立；
  • 为维持低用量备用端点，缓存、配额和模型可能长期未热；
  • 分散采购降低集中度，却增加合同、账单、密钥和事故协调成本；
  • 自有网关成为新的集中点，需要容量和灾备。

因此，组合策略的验收还包括相关故障分析。只有故障域足够独立、备用路径持续演练，第二供应商才是恢复能力，不是采购清单上的装饰。

十五、怎样读这段实现，而不是把它当成采购评分器

15.1 CandidateEnvelope 只提供教学级变更检测

代码用 SHA-256 对规范化 JSON 摘要，并把候选绑定到 decision_id。它能在内存测试中发现 envelope 签发后候选字段被改，也能阻止把另一场决策的 envelope 直接重放。

它不提供生产身份、数字签名、可信时间、密钥管理或不可抵赖。生产证据需要由有权系统签发并验证授权、版本、撤销和存储完整性。摘要相同也不代表供应商声明为真。

15.2 严格分母故意把未完成留在结果里

SliceResult.strict_rate() 使用 passed / expected，同时约束 passed <= completed <= expected。这样环境失败不会静默缩小分母。真实平台还应区分候选失败、Runner 失败、数据失败和基础设施失败，并由预注册规则决定是记失败、记 unknown 还是整次 run 无效。

15.3 TCO 缺一类就拒绝计算

Candidate.tco() 要求 build、run、evaluate、govern、exit 五类都出现，且总额必须有限并大于零。单条成本可以是零，但仍要有证据来源；本例没有验证财务来源是否权威，也没有实现折现、税费、汇率、合同阶梯和概率模拟。

15.4 portable_interface 没有进入退出硬门

字段存在是为了测试一个重要反例：即使接口声明可移植，替代验收或 RTO 失败仍会阻断。真正退出能力由外部分母、验证导出、删除面、替代业务门和恢复时间共同决定。

15.5 权重错误测试揭示了一个代码问题

test_negative_weight_is_rejected 直接验证 tco 负权重被拒绝；test_extreme_finite_weights_are_normalized_without_overflow 则先按最大权重缩放，再归一化，避免有限大数求和溢出。生产实现还应分别覆盖未知键、缺键、NaN、Infinity、总和为零和微小浮点误差，并断言原因码。

十六、第二次失败：总分稳定，输入证据却已经过期

16.1 现象

候选 H 上线评审前一天，决策报告仍显示五个敏感性场景中四个第一。质量、TCO、退出均为绿色。工程人员却发现供应商在 21 天前发布了新的流式协议，并把旧协议支持期缩短到 90 天。

16.2 排查顺序

第一步不是重跑所有 benchmark，而是检查证据 manifest 的新鲜度：候选 bundle 引用 api-contract@1.4，供应商变更通知对应 1.5，当前生产默认仍是 1.4，但新租户已经默认 1.5。

第二步核对候选是否仍是同一个评估对象。由于新合同承诺和默认行为改变，Decision Authority 将 H 标记为 STALE_EVIDENCE，暂停上线批准。

第三步做差异测试：Schema 表面相同，但 1.5 在客户端取消后仍发送最终 usage event；旧适配器把它当第二个 completion，导致同一 request 出现两个终态 Trace。

第四步检查成本与退出：新增 event 使 Trace 量上升 18%，同时旧协议兼容层维护进入退出成本。TCO 变化不足以改变排名，但 evidence bundle 必须更新。

16.3 根因

决策系统有版本字段，却没有为外部证据设置 review_at 和变更订阅责任。报告可以数学上正确，输入世界却已经改变。总分稳定不等于决策有效。

16.4 修复

  • 候选 manifest 增加 API、模型、区域、子处理者、价格和退出计划的新鲜度策略；
  • 重大变更通知进入同一变更队列，按影响映射重跑证据；
  • Runner 增加流式多终态契约测试；
  • 成本账本把 Trace 增量和兼容层维护纳入 High 情景；
  • 合同要求重大兼容变化提供通知和测试窗口；
  • 每季度替代演练不只切端点，也切协议版本。

修复后没有重新“相信 H”，而是重新签发 H-r4 bundle，执行受影响的 112 条契约、可靠性和退出测试，再更新决策记录。

十八、持续治理：选择完成后，决策系统才开始工作

18.1 复核触发器

固定季度复核只是兜底。以下事件应触发影响评估：

  • 模型、API、策略、安全过滤或区域能力变化；
  • 数据分类、业务用途、用户群或写操作范围变化；
  • 子处理者、支持路径、控制面或训练用途变化；
  • 价格、最低承诺、汇率、配额或团队成本明显变化；
  • SLO 消耗、质量 slice、攻击逃逸或人工接管趋势变化；
  • 收购、停售、重大事故或供应商财务风险；
  • 替代演练失败、导出格式变化或删除证明缺口。

触发后不一定重做整个采购。影响矩阵决定重跑数据、质量、成本、合同或退出中的哪一部分，但旧证据与替换原因都要保留。

十九、收益与代价：把“可控”翻译成可观察变化

19.1 构造收益

采用重建后的决策系统，Orion 试点得到以下构造结果：

  • 需求变更引起的候选范围争议从 11 项降为 2 项，因为每项绑定 owner 和证据；
  • 480 条主集和 160 条安全集可在同一 runner 重放，候选比较不再依赖 Demo；
  • 权限 slice 从总分中独立出来，试点前阻断 4 次标题级越权；
  • 成本模型加入评测、治理和退出后，首年“便宜 31%”改为三年 Base 情景“差 3.5%”，避免错误确定性；
  • 第一次替代演练用 78 分钟恢复关键路径，并提前发现流式协议差异；
  • 业务抽样中查找中位耗时从 210 秒降到 92 秒，但报告保留并行变更和样本选择限制。

这些数字只属于构造案例。真正收益必须由组织自己的事实源、对照设计和时间窗口支持。

19.2 明确代价

  • 建立盲测集、标签和人工复核需要领域专家时间；
  • 自有网关、Trace、双适配器和 bundle registry 增加代码与值班面；
  • 退出演练需要备用容量和迁移窗口，短期看不到直接收入；
  • 对外部声明做证据化会拉长试点前期；
  • 严格分母会让指标比“成功请求内准确率”难看；
  • 多供应商治理增加合同、账单、安全和事故协调成本；
  • 权重敏感性会暴露决策分歧，无法用一个漂亮总分快速结束讨论。

这些代价不能被称为纯浪费。它们购买的是未知可见性、决策可复核性和退出选择权；是否值得仍取决于问题风险和业务价值。

二十、这套方法仍然不能证明什么

20.1 不能证明未来价格和需求

Low/Base/High 是条件情景，不是概率保证。模型价格、能耗、汇率、人员和业务量都可能超出范围。敏感性分析只是展示当前结论依赖哪些假设。

20.2 不能证明 benchmark 等于生产

480 条样本覆盖的是登记 slice。新政策、用户表达、对抗方式、长尾语言和交互上下文仍可能产生未知失败。线上抽样、事故回灌和定期重构数据不可省略。

20.3 不能证明第三方声明绝对真实

合同、问卷、审计报告和技术探针都有范围与时间窗。证据一致会提高信心，不会变成全知证明。无法独立观察的控制要保留为依赖与限制。

20.4 不能证明删除了未知副本

删除证明只覆盖资产登记、合同和验证列明的存储面。未知导出、终端下载、非法复制或法定另行保留需要分别处理。

20.5 不能证明组合方案没有共同故障

两个供应商可能共享网络、身份、云区域、基础模型或组织自己的网关。只有依赖图、故障注入和真实切换能逐步识别相关性。

20.6 不能把标准符合性自动变成产品安全

NIST 和 ISO 提供风险、过程与质量语言。是否满足某标准、是否可认证、是否符合法规，需要按正式范围和有权评估判断；本文的映射不是合规声明。

二十一、执行清单

21.1 问题和需求

  • 问题合同写清用户任务、业务结果、禁止结果、数据、运行和退出目标。
  • 自建、采购、组合候选采用相同能力边界和 owner matrix。
  • 硬约束、目标门槛和偏好已分开，低成本不能抵消硬失败。
  • 每个候选固定模型、API、数据、策略、报价和退出计划版本。
  • 未证明状态显示为 UNPROVEN，不默认 PASS。

21.2 盲测和统计

  • benchmark 在接触候选结果前冻结协议、case manifest、阈值和重复次数。
  • 开发集与 held-out 集隔离，标签和阈值由 Evidence Custodian 管理。
  • 业务 slice 互斥主分层与交叉属性都能报告。
  • expected、completed、invalid、unknown、passed 都有显式分母。
  • 总平均不能覆盖高风险 slice，安全集单独报告严重度。
  • 重复运行、不稳定率和统计区间不会被解释成生产确定性。

21.3 数据和控制

  • 内容、知识、输出、遥测、控制、支持、安全、备份和训练面逐项建图。
  • 区域、子处理者、人工访问、保留和用途有合同与技术证据。
  • 正常、错误、重试、支持和导出路径执行 canary 故障注入。
  • 自有 Trace、策略和数据版本足以在供应商控制台不可用时排障。
  • 外部证据有 owner、review_at 和变更触发器。

21.4 TCO

  • 建设、运行、评测、治理和退出五类成本全部入账。
  • 人员按有效投入和全负担成本计算，现有人员不记为免费。
  • 数量、费率、币种、时间、包含项、排除项和来源可追踪。
  • Low/Base/High 覆盖用量、上下文、人审、变更和退出双跑。
  • 同时报告总 TCO、每合格请求、每验收回答和可验证价值分母。
  • 成本预测明确不确定性，不把供应商报价当最终账单。

21.5 锁定和退出

  • 协议、数据、行为、工作流、运营和商务锁定分别登记。
  • 导出 expected registry 由独立事实源维护，不由导出包自报分母。
  • 文件可解析、关系可重建、替代系统可验收是不同等级。
  • 退出 SLO 定义时钟起止、暂停、恢复后置条件和失败处置。
  • 删除证明逐存储面表达，并保留未知副本限制。
  • 每季度或重大变更后执行替代演练，备用路径保持热度。

21.6 决策和合同

  • 权重由跨职能角色在最终结果前批准，所有值都有解释。
  • 至少运行平衡、安全、成本、交付和主权/退出情景。
  • 报告排名稳定性、接近程度和翻转条件，不只报一位小数总分。
  • 例外保留失败事实、风险接受者、补偿控制和到期日。
  • 合同的数据、变更、SLO、事故、导出、迁移和删除条款可被技术演练。
  • 选择后按变更与证据新鲜度持续复核。

自建与采购不是身份立场。一个方案可以采购模型而自建质量系统，也可以采购平台却保留独立数据、Trace、门禁与退出路径。决定质量的不是“代码归谁写”，而是问题是否清楚、责任是否闭合、证据是否独立、失败是否可见、成本是否完整、退出是否演练。

如果这些问题只能用销售演示、总分和“以后可以迁移”回答，决策还没有完成。把硬门、盲测、全生命周期成本和退出演练做成持续工程能力，才能让采购速度不以失去控制为代价，也让自建控制不以低估维护成本为代价。
