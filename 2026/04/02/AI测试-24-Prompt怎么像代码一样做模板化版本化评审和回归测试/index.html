AI测试-24-Prompt怎么像代码一样做模板化版本化评审和回归测试

发表于 2026-04-02 分类于 AI测试 本文字数： 8.1k 阅读时长 ≈ 30 分钟

Prompt 只存在于在线控制台、配置中心文本框或某段业务代码里时，第一次修改通常很快：改一句要求，手工试几条问题，观察回答似乎更好，然后发布。

真正困难的部分从第二次修改开始：

  • 当前线上到底使用哪一版 System Prompt
  • 模板正文、Few-shot、工具描述和输出契约是不是同一次发布
  • 某个变量为空时，渲染结果会不会留下半句指令
  • 两个版本之间改的是措辞、权限边界，还是输出字段
  • 评审人看到的是模板原文，还是生产中真正送给模型的消息
  • 回归失败来自 Prompt，还是模型、检索数据或工具 Schema 同时发生了变化
  • 灰度指标恶化时，能否回到一个已经验证过且能够重新构建的版本
  • 日志和测试样本里是否保存了用户隐私、密钥或内部策略全文

这些问题不能靠“给 Prompt 加一个版本号”解决。Prompt-as-code 的核心，是把 Prompt 从一段可随手编辑的字符串，升级成具有源码、依赖、契约、测试、构建产物、发布记录和回滚目标的软件资产。

这篇文章聚焦这条工程链路。非确定性结果如何做统计比较，已经在 AI测试-20 中展开；这里不重复置信区间和多次采样，而是回答一个更靠前的问题：一次 Prompt 变更究竟改了什么，测试执行的是否就是准备发布的那份产物。

一、先给结论：版本化对象不是一段文本，而是完整 Prompt 包

生产行为通常由下面这些内容共同决定：

只给模板正文打版本，仍然无法复现行为。例如正文没有变化，但工具描述把“查询订单”改成“查询并更新订单”，权限风险已经变化；Few-shot 示例把退款状态从 REVIEW 改成 APPROVED，模型也可能跟随示例改变决策。

因此，一次可发布版本至少应生成两个标识：

  • source_revision：源码仓库的提交或不可变修订，用于追溯谁改了什么。
  • artifact_fingerprint：对规范化 Prompt 包计算的内容指纹，用于证明测试、灰度和线上请求使用同一产物。

人类可读版本号负责沟通，内容指纹负责核验。两者职责不同，不能互相代替。

二、Prompt-as-code 解决什么，不解决什么

Prompt-as-code 适合解决四类问题。

1. 可追溯性

每个线上请求能追到模板、变量契约、示例、工具、输出结构和模型配置的具体修订。

2. 变更控制

变更通过 Pull Request 进入，评审人能看到结构化差异、风险标签、回归证据和发布计划，而不是只收到一张聊天截图。

3. 可重复验证

同一份源码经过确定性构建得到同一指纹。离线测试、影子流量、灰度和生产日志都记录该指纹。

4. 可恢复性

回滚目标是已经构建、测试并签名或校验过的历史产物，不是在故障现场手工把几段文字改回去。

它不直接解决以下问题：

  • 模型输出天然非确定
  • 评测集没有业务代表性
  • 模型提供商在固定别名下改变了后端行为
  • RAG 索引或工具服务的数据状态不可重放
  • 高风险动作缺少后端权限校验

Prompt 工程化能让变化变得可见和可控，却不能把概率模型变成纯函数，也不能替代权限系统与运行时观测。

三、先确定边界：什么内容应该进入 Prompt 包

建议按照“会不会改变模型可见上下文或可执行能力”判断，而不是按照文件类型判断。

资产 是否纳入版本 原因
System / developer / user 模板 是 直接改变指令与上下文结构
变量 Schema 与渲染规则 是 决定动态数据怎样进入模板
Few-shot 示例 是 示例本身会影响输出行为
工具描述与参数 Schema 是 改变工具选择和参数生成
输出 Schema 是 改变下游接口契约
模型标识与采样参数 是 参与可重复性和风险评估
检索文档正文 通常单独版本 体量和生命周期不同，但产物需引用其 revision
用户原始输入 否 属于运行时数据，不应进入源码
密钥与访问令牌 否 只能保存秘密引用，不得进入 Prompt 包
线上实验流量 否 属于观测数据，记录产物指纹即可

检索语料、模型和 Prompt 可以分属不同仓库，但发布清单必须引用不可变版本。否则“Prompt v2.3.0”仍然可能对应多种生产行为。

五、模板不是字符串拼接，变量必须有契约

以下写法看起来简单，却埋了几个问题：

  • user_text 可以为空、超长或包含伪造指令。
  • 固定指令和不可信数据没有结构边界。
  • “紧急”的业务定义不明确。
  • “退款”把模型判断直接连到高风险动作。
  • 拼接后的实际 Prompt 无法从源码 diff 中直接看到。

更合适的模板先声明数据边界：

变量契约至少包含：

字段 类型 必填 长度/枚举 信任级别 日志规则
tenant_id string 是 ^[a-z0-9_-]{3,32}$ 系统生成 可记录
language string 是 zh-CN/en-US 系统生成 可记录
customer_message string 是 1..8000 字符 用户不可信 仅哈希或脱敏摘要
current_policy object 是 固定字段 策略服务 记录 revision，不记敏感正文

模板引擎还要明确四件事：

  • 缺少变量是立即失败，还是允许默认值。
  • 多余变量是拒绝，还是静默忽略。
  • 字符串是否做 HTML/XML/JSON 对应转义。
  • 列表和对象使用结构化序列化，还是调用隐式 str()。

默认值尤其需要谨慎。权限、租户、币种、地区和动作额度缺失时，不适合自动补一个“常用值”；这会把输入错误变成业务错误。

六、角色边界要由消息结构表达

把所有内容放进一个 user message，再在文字里写“以下是系统规则”，并不等于真正的消息角色。

这也是 Prompt-as-code 与 Prompt Injection 测试的分工：前者保证安全约束的版本、评审和回归可追踪；后者验证即使模型受影响，系统权限边界仍然有效。

七、版本号怎么设计：兼容性语义比数字大小更重要

可以借用语义版本的表达方式，但需要给 Prompt 定义自己的升级规则。

  • PATCH：不改变变量、输出和权限契约的文字修正，例如错别字、等价澄清。
  • MINOR：向后兼容地增加能力，例如新增可空输出字段、增加一个已授权意图类别。
  • MAJOR：删除或重命名字段、改变默认动作、扩大工具权限、改变拒答边界，或要求调用方同步迁移。

这个分类不是靠提交者主观选择，而应由自动 diff 给出最低建议级别。例如输出 Schema 删除必填字段、变量类型变化或新增高风险工具，至少触发 MAJOR 或组织定义的高风险审批。

版本号也不能证明内容唯一。如果同一个 2.3.0 可以在控制台里被覆盖，所有历史测试都会失去意义。发布仓库应禁止覆盖已发布标签，制品库应按内容寻址。

RFC 8785 定义了 JSON Canonicalization Scheme，可用于需要跨实现一致 JSON 表示的场景。工程实现可以采用兼容库；如果只使用语言自带的键排序序列化，则应明确它是项目内规范，不要声称完全符合 JCS。

指纹输入中不应出现：

  • 构建时间
  • 本机绝对路径
  • 随机生成的 ID
  • 密钥和真实用户数据
  • 未固定顺序的文件遍历结果

指纹应同时写入测试报告、部署清单、请求追踪和回滚记录。

九、语义 diff 不能只看新增和删除的字符

普通文本 diff 仍然有价值，它适合发现措辞和示例变化。但 Prompt 包还需要结构化 diff，因为下面几类变化可能只改一行，却有完全不同的风险：

变化 语义 默认风险
System 中把“不得执行”改成“谨慎执行” 权限边界放宽 高
新增一个必填变量 调用方可能无法渲染 高
变量最大长度从 2000 到 8000 成本、截断和注入面变化 中
删除输出枚举值 下游兼容性变化 高
新增只读工具 行为和数据访问面变化 中
新增写工具 副作用和权限面变化 高
Few-shot 顺序变化 示例权重和缓存前缀变化 中
只改注释 不进入产物 低

十、评审要同时看源码、渲染结果和测试证据

Prompt Pull Request 至少包含五个视图。

1. 原始文本 diff

用于检查措辞、歧义、冲突指令、示例质量和不必要的重复。

2. 结构化契约 diff

用于检查变量、输出、工具和依赖兼容性。

3. 代表性渲染快照

选择正常、空边界、最长输入、多语言、包含特殊字符和恶意文本的 fixture，展示实际消息数组。模板原文正确，不代表渲染后仍然正确。

4. 样本级回归差异

不能只给“总分 +1.2%”。应列出哪些 case 改善、哪些退化、哪些从结构错误变成通过，以及关键风险是否保持底线。

5. 发布与回滚计划

写明灰度范围、观察窗口、硬回滚指标、稳定回滚指纹和是否涉及缓存失效。

评审职责也要分开：语言和任务设计由 Prompt owner 负责，输出兼容性由调用方负责，工具权限由安全或平台 owner 负责，关键业务规则由领域 owner 负责。一个“AI 专家已看过”不能覆盖所有责任。

十一、静态检查先挡住不需要调用模型的错误

静态检查成本低、结论确定，适合每次提交运行：

  • manifest、变量 Schema、输出 Schema 可解析
  • 所有模板变量都已声明，所有必填变量都有 fixture
  • 不存在未使用变量和无法到达的条件分支
  • 角色只来自允许集合，消息顺序符合应用约定
  • 示例符合输入和输出契约
  • 工具引用存在，revision 不使用 latest
  • 高风险动作词与允许工具不冲突
  • Prompt 和 fixture 中没有密钥模式、真实手机号、邮箱或身份证号
  • Token 预算估算没有超过上下文与输出上限
  • 产物构建两次得到同一指纹

十三、离线回归要分成四层

Prompt 改动后的回归不应只有一批端到端模型样本。

1. 模板契约测试

完全不调用模型，验证：

  • 必填、类型、长度、枚举和多余字段
  • 空值、Unicode、换行、引号、XML/JSON 特殊字符
  • 条件分支和循环边界
  • 消息角色、顺序和 Token 预算
  • 产物指纹稳定性

2. 静态安全测试

扫描秘密、个人数据、内部地址、越权工具、危险默认值和不可信变量的错误插值位置。

3. 行为回归

使用冻结模型快照、工具替身和固定检索 fixture，验证任务成功、格式、拒答边界、工具选择和关键业务规则。

4. 集成与发布验证

在真实 API 适配器中检查消息映射、超时、截断、工具调用、观测字段和灰度路由。这里验证的是集成事实，不是重新发明离线评分。

十四、一张可执行的 Prompt 测试矩阵

维度 正常样本 边界样本 失败断言
变量 合法租户、常规消息 空、超长、未知枚举、额外字段 构建失败且不调用模型
编码 中文、英文 Emoji、组合字符、控制字符 无乱码，规范化策略明确
结构 单轮工单 多段文档、长历史 角色和分隔结构不丢失
安全 普通请求 直接注入、间接注入、秘密模式 权限不扩大，日志不泄密
输出 route/ask/escalate 无法判断、证据冲突 符合输出契约并显式降级
工具 只读查询 未授权写工具、非法参数 执行器拒绝且留证据
兼容 当前调用方 旧调用方、旧 Schema 兼容策略与版本级别一致
预算 短输入 最大输入、最大示例集 截断不删除安全约束
发布 稳定版本 候选灰度、回滚 指纹贯穿且路由可逆

渲染测试通过不代表安全通过。恶意文本作为数据进入模板是正常的，真正断言是它不能改变工具权限、跨租户范围和外发边界。

十五、Prompt 评审中的安全与敏感数据边界

Prompt-as-code 会把更多上下文放进仓库和 CI，因此也会扩大泄露面。

1. 源码里只保存变量名，不保存真实秘密

错误示例：

正确边界不是改成 {{db_password}} 后把密码渲染进模型，而是模型根本不接触数据库凭据。工具执行器持有受限凭据，模型只生成受 Schema 约束的业务参数。

2. Fixture 必须合成或脱敏

历史事故样本可以保留结构和触发条件，但姓名、手机号、订单号、访问令牌和内部 URL 应替换。脱敏后还要验证攻击模式没有被破坏。

3. 渲染快照不是普通日志

渲染 Prompt 可能包含客户数据、检索片段和内部策略。需要设置字段级脱敏、访问控制、加密、保留周期和删除链路。日常指标通常只需要保存指纹、模板版本和变量长度，不需要保存完整正文。

4. 第三方评测器也是数据接收方

如果把候选输出和原始输入发送给另一个模型做 Judge，数据边界已经扩大。评审清单要记录提供商、区域、保留策略和允许字段。

5. 远程 Prompt 控制面不能绕过代码评审

控制台编辑适合实验，但生产别名如果可以被直接覆盖，仓库中的审批和测试都会失效。更稳的流程是控制台导出或 API 拉取后形成源码变更，再由流水线发布不可变版本；紧急修改也要生成事后可审计记录。

十六、灰度发布要按产物指纹路由

灰度不能只写“10% 使用新 Prompt”，而要能回答这 10% 实际用了什么。

按用户或租户稳定分桶，可以减少同一会话在两个 Prompt 间来回切换。涉及多轮状态时，路由键还应绑定会话创建时的版本，避免历史由旧 Prompt 产生、当前轮突然换成新 Prompt。

灰度观测至少按候选和基线分别记录：

  • 任务成功率和关键切片
  • 输出契约失败率
  • 工具提议、拒绝和实际执行率
  • 人工升级率与撤销率
  • 输入、输出 Token 和缓存命中
  • 时延、超时与提供商错误
  • 投诉、人工修改和延迟业务结果

十七、回滚不是把 Git 指针退回去

一次可靠回滚包含五个动作：

  1. 路由控制面停止向候选指纹分流。
  2. 新请求切到稳定产物，已有会话按策略结束或迁移。
  3. 取消候选关联的缓存、异步任务和待执行高风险动作。
  4. 验证稳定产物、工具 revision 和输出 Schema 与当前调用方仍然兼容。
  5. 保存触发指标、首个异常样本、时间线和回滚完成证据。

只回滚 Prompt 可能仍然失败。例如候选同时要求下游升级到输出 Schema v3，而数据库已经只接受 v3；回到输出 v2 会造成新的解析错误。发布单元必须按照兼容性设计决定是原子回滚整组依赖，还是让调用方支持双版本窗口。

稳定版本也不能用“上周那个版本”表示。它应该是不可变的 artifact fingerprint，并且在当前模型与工具环境中仍有有效的冒烟证据。

十八、一个完整失败案例：Prompt 本文只改一行，退款建议却翻倍

1. 场景

客服分类 Prompt 原规则是：

为了减少追问，候选版本改成：

提交只显示一行替换，手工测试十条普通工单均通过。

2. 执行

候选通过基本格式测试后灰度到 10% 租户。30 分钟内总体满意度代理指标略升，但 refund 工具提议率从 0.8% 上升到 2.1%。执行器因权限策略拒绝了大部分调用，所以没有实际退款事故。

3. 表面现象

第一反应可能是模型随机波动，或新流量里退款用户更多。只看最终回答，部分样本只是礼貌地建议“立即处理”，无法看出工具层发生了什么。

4. 证据排查

按时间顺序检查：

  1. 灰度分桶稳定，候选与基线租户结构接近。
  2. 两组使用同一模型快照和工具 revision。
  3. artifact_fingerprint 能把异常全部聚集到候选版本。
  4. 语义 diff 报告把“不得建议退款”识别为删除，但当时只标记普通文案变化。
  5. 渲染快照显示 Few-shot 中仍有一个退款示例；删除硬约束后，示例成为最强动作暗示。
  6. 工具轨迹证明权限层成功拒绝，问题发生在规划和工具提议层，不是执行器越权。

5. 根因

根因不是“模型突然变差”，而是三项工程缺口叠加：

  • 权限否定句没有被静态规则识别为安全性质。
  • 回归门禁只看最终分类，没有断言禁止工具提议率。
  • 评审页面没有把正文和 Few-shot 组合后的有效语义一起展示。

6. 修复

  • 立即按指纹回滚，确认拒绝率恢复。
  • 把“不得建议或调用退款”改为不可删除的策略片段，由 manifest 引用。
  • 后端允许工具集合移除 refund，而不是只依赖 Prompt 禁止。
  • 新增 forbidden_tool_proposal_rate 和 forbidden_tool_execution_rate 两个断言。
  • 语义 diff 对权限短语删除、工具集合扩大和高风险示例变化自动提升风险级别。
  • 将该工单缩减成历史事故 fixture，加入正常对照与注入变体。

这个案例说明，Prompt-as-code 的价值不在于让每次文案修改更慢，而在于让一行文字背后的权限含义、回归范围和回滚动作变得可见。

十九、常见的十个失控点

1. 一个巨大的 prompt.txt 包含全部内容

职责、变量、示例和策略无法独立 diff，改动范围越来越难判断。

2. 只记录人类版本号，不记录内容指纹

同名版本被覆盖后，测试结论无法对应生产内容。

3. 模板允许缺变量时静默替换为空串

权限、租户和业务条件可能变成语义完整但错误的句子。

4. 只测试模板，不测试渲染消息

转义、条件块、角色映射和截断问题全部漏掉。

5. 所有变化都由通用平均分评审

权限扩大、关键字段删除和安全样本退化会被普通样本抵消。

6. 把在线控制台当作唯一真源

生产编辑绕过源码评审，仓库版本与真实版本分叉。

7. Prompt 中嵌入真实秘密

秘密会进入模型输入、追踪、缓存、评测和故障证据，泄露面迅速扩大。

8. 回滚只回模板，不检查依赖兼容性

旧 Prompt 可能无法与新工具或新输出 Schema 共存。

9. 用 LLM 生成 diff 结论后直接放行

解释可以辅助评审，确定性兼容和权限规则不能外包给概率判断。

10. 只保存成功版本，不保存失败证据

历史问题无法转成回归样本，同类事故会换一种措辞再次出现。

二十、什么时候适合采用，什么时候不要硬套

以下信号出现时，Prompt-as-code 的收益通常明显：

  • Prompt 由多人维护，且有独立调用方
  • 存在工具、RAG、结构化输出或高风险业务动作
  • 需要审计、灰度、回滚或多环境发布
  • 同一任务维护多语言、多租户或多个模型版本
  • Prompt 变更频繁，历史回归已经难以解释

以下场景可以先保持轻量：

  • 单人、短期、无真实用户数据的探索原型
  • 只做一次性的离线内容处理，失败可人工检查
  • 尚未定义任务成功标准，连最小样本集都不存在

轻量不等于完全无记录。至少保存模板、模型、输入样本、输出和实验结论。等任务进入生产，再迁移到包、契约和流水线。

也不要把 Prompt 包做成一个试图兼容所有模型、所有任务的通用 DSL。提供商消息角色、工具能力和上下文行为存在差异。更稳的抽象是保留业务契约，针对每个适配器生成明确产物，并分别测试。

二十一、落地检查表

包和契约

  • 固定指令、变量、示例、工具和输出结构是否拆分清楚
  • 变量是否声明类型、必填、长度、枚举、信任级别和日志策略
  • 缺失和多余变量是否默认失败
  • 不同上下文是否采用对应转义或结构化序列化
  • 模型、工具、检索与策略是否引用不可变 revision

版本和构建

  • 版本升级规则是否对应兼容性和风险语义
  • 已发布版本是否禁止覆盖
  • 规范化构建是否排除时间、路径、秘密和随机值
  • 同一源码重复构建是否得到同一指纹
  • 指纹是否进入测试、部署、请求追踪和回滚记录

评审和测试

  • PR 是否同时展示文本 diff、语义 diff 和代表性渲染快照
  • 权限、工具、Schema 和示例变化是否自动选择评审人
  • 是否先运行模板契约和静态安全检查
  • 行为回归是否使用冻结依赖和样本级证据
  • 高风险性质是否独立门禁，无法被平均分抵消
  • 测试 fixture 是否合成或完成不可逆脱敏

安全和隐私

  • Prompt 包、示例和 CI 日志中是否没有真实密钥
  • 模型是否只接触业务参数，不接触工具凭据
  • 渲染 Prompt 是否按敏感证据管理
  • 不可信变量是否与固定指令明确分隔
  • 高风险动作是否在模型外进行确定性权限和业务校验

发布和恢复

  • 灰度是否按稳定键和产物指纹路由
  • 是否定义硬回滚指标、观察窗口和稳定目标
  • 多轮会话如何固定或迁移版本是否明确
  • 回滚是否覆盖缓存、异步任务和依赖兼容性
  • 事故是否会沉淀成最小 fixture 与长期回归项

二十二、小结

把 Prompt 当作代码，不是把 .txt 放进 Git 就结束。

完整链路应该做到：

  1. 把角色、模板、变量、示例、工具、输出和运行时依赖组成完整 Prompt 包。
  2. 用严格变量契约阻断空值、额外字段、错误类型和错误转义。
  3. 同时保留人类版本号、源码 revision 和规范化内容指纹。
  4. 用文本 diff 读措辞，用结构化 diff 识别兼容、权限和供应链风险。
  5. 评审时查看真实渲染消息、样本级回归证据和发布计划。
  6. 先运行确定性静态检查，再运行模型行为评测和集成验证。
  7. 把 Prompt Injection、敏感数据和工具权限放进测试边界，但不让 Prompt 替代后端安全控制。
  8. 按产物指纹灰度和回滚，确保测试对象、发布对象和故障证据是同一份内容。

最终需要建立的不是一个更复杂的 Prompt 编辑器，而是一条可回答以下问题的工程链：

这次到底改了什么，为什么允许发布，生产实际运行的是哪份产物，出现偏差时能否带着证据恢复到已验证状态。

当这些问题都有确定答案时，Prompt 才真正从“调出来的一段话”变成可维护的软件资产。
