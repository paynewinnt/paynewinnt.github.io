AI测试-26-模型API怎么处理超时限流重试幂等和供应商故障

发表于 2026-04-06 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:03

模型 API 返回一次 200，并不代表调用链已经具备稳定性。

一次生成请求至少可能经历：本地排队、连接池等待、DNS、TCP、TLS、请求体上传、供应商排队、首 Token 等待、流式读取、结果解析、工具参数校验和结果持久化。任何一段都可能超时；任何一次超时都可能发生在“服务端尚未收到请求”“服务端正在计算”“服务端已完成但响应丢失”三种完全不同的状态。

如果客户端把这些状态统一处理成“异常后再调一次”，会同时制造四类问题：

  • 原请求其实仍在执行，重试把供应商负载和费用放大；
  • 429 本来要求降速，重试反而消耗更多请求和 Token 配额；
  • 流式结果已经生成一半，新响应被拼到旧缓冲区，得到重复或损坏内容；
  • 模型输出驱动了工具或外部动作，网络断开后无法确认动作是否已经提交，再试一次产生重复副作用。

因此，模型 API 客户端不能只是一层 SDK 包装。它应该把模型调用视为一个有成本、可能产生副作用、结果可能不确定的远程依赖，并给每次逻辑操作建立明确的截止时间、尝试预算、速率预算、Token 预算、幂等意图、故障分类和对账路径。

本文重点解决下面这些工程问题：

  • connect、read 和 overall deadline 分别约束什么；
  • 429、5xx、网络错误、超时和流式中断怎样分类；
  • Retry-After、指数退避和 jitter 怎样共同决定下一次尝试；
  • 为什么最大重试次数不能替代总时间预算；
  • 请求限流、Token 限流和并发隔离怎样一起工作；
  • 幂等键能保证什么，不能保证什么；
  • “服务端可能已经处理”时为什么不能直接重试；
  • 熔断、隔离和供应商切换怎样避免把局部故障扩大；
  • 怎样用无真实密钥的 Python 骨架和故障注入测试验证这些性质。

一、先明确边界：模型调用不是纯函数

把模型调用看成下面这个函数很方便：

但真实调用并不满足纯函数的几个关键条件。

1. 同一输入不保证同一输出

即使请求参数完全相同，采样、服务端实现、模型版本和并发执行都可能让输出发生变化。幂等键解决的是“同一业务意图是否被重复执行”，不是“同一 Prompt 是否生成相同文字”。

2. 调用本身会消耗稀缺资源

一次失败尝试仍可能消耗：

  • 请求速率额度；
  • 输入和输出 Token 配额；
  • 供应商计费；
  • 本地连接、线程、协程和内存；
  • 用户端到端延迟预算。

OpenAI 的官方限流文档明确提醒，未成功请求也会计入每分钟限制。这个事实说明“失败就立即重发”不仅不能绕过限流，还可能让恢复窗口越来越远。其他供应商是否采用完全相同的计数口径，需要按各自文档和实际响应头确认，不能从一家供应商外推成通用规则。

3. 模型响应可能触发外部副作用

模型生成文本通常只是成本副作用，但 Agent 场景还可能把输出解释成：

  • 发邮件；
  • 创建工单；
  • 修改订单；
  • 执行脚本；
  • 写数据库；
  • 调用付款或退款接口。

模型流里出现一个工具调用片段，不代表工具已经获得执行资格。更稳妥的边界是：先完整接收并校验模型终态，再由独立执行器使用自己的幂等键、权限和事务规则提交动作。

4. 超时只说明调用方不再等待

超时不是远端取消确认。

调用方在 5 秒时停止等待，服务端可能：

  • 从未收到请求；
  • 已收到但尚未排到；
  • 正在推理；
  • 已生成完整结果；
  • 已把结果写入服务端状态，但响应在网络中丢失。

所以超时后的业务状态可能是 NOT_STARTED、IN_PROGRESS、COMPLETED 或 UNKNOWN。客户端不能仅凭一个 ReadTimeout 推导远端没有执行。

二、三类超时必须分开

“模型超时设置为 30 秒”这句话信息不足。至少需要定义 connect timeout、read timeout 和 overall deadline。

1. Connect timeout

connect timeout 约束建立可用连接的阶段，可能包括：

  • 从连接池获取连接；
  • DNS 查询；
  • TCP 建连；
  • TLS 握手；
  • 代理或网关隧道建立。

不同 HTTP 客户端对这些阶段的归属并不完全相同。有的库把连接池等待单独称为 pool timeout，有的把 DNS 和 TLS 部分计入 connect timeout，有的底层 socket 配置只覆盖其中一段。配置之前要先读当前客户端的精确定义，并用故障注入验证，不要只依赖参数名字。

连接超时通常意味着还没有得到可用连接，但仍不能笼统声称“请求一个字节都没有发出”。如果传输库不能暴露请求发送阶段，就应使用保守分类，而不是猜测。

2. Read timeout

read timeout 通常约束等待下一段响应数据的最长空闲时间。

它不一定等于完整响应允许持续的总时间。流式生成每隔几秒返回一段数据时，每次读取都可能没有超过 10 秒，但整个响应可能持续数分钟。

它应该使用单调时钟计算剩余时间，避免系统时间校准让 duration 变成负数或突然增长。

三、怎样为超时选择初始值

AWS Builders Library 的超时文章给出一个实用思路：先选择可接受的错误超时比例，再观察下游时延分布，按相应分位设定初始值，同时为跨地域和互联网网络增加合理余量。

把这个方法迁移到模型 API 时，需要再增加三个变量。

1. 按请求类别建立分布

短分类、长文本生成、图像理解和工具规划的时延分布不同。不能用一个全局 P99 作为所有请求的 read timeout。

至少可以按以下维度分桶：

  • 供应商、模型或部署；
  • 流式与非流式；
  • 输入 Token 档位；
  • 最大输出 Token 档位；
  • 工具数量和 Schema 大小；
  • 区域与网络路径；
  • 优先级或服务等级。

2. 观察 TTFT 和完整时延

流式接口要分别看首个可用 Token 时间和最后一个 Token 时间。首字节很快但后续长时间停顿，和首 Token 本身很慢，是不同故障。

3. 警惕过紧分布

如果供应商正常 P99.9 为 990 毫秒，把超时设为 1 秒看似合理，实际上只留下 10 毫秒余量。小幅网络变化就会制造大量错误超时。AWS 文章也提醒，分布很紧时需要额外留垫片，而不是机械等于某个分位。

一次常见故障发生在新连接阶段：系统平时复用连接，稳态时延很低；部署后新实例必须建立 TLS，连接阶段刚好超过过紧超时，导致上线时集中失败。解决方式不只是把总超时调大，还包括在接流量前预热连接，并把连接建立与请求读取分别观测。

四、错误分类：先判断“能否通过重试改变结果”

HTTP 状态码是分类输入，不是完整结论。同一个 429 可能表示瞬时速率限制，也可能表示账户配额或计费额度耗尽；前者等待后可能恢复，后者在配置改变前不会恢复。

一个内部错误模型至少应包含：

1. 连接和网络错误

现象 远端状态 默认判断 需要额外信息
DNS 失败 通常未连接 可重试，但先受预算约束 是否为长期配置错误
连接被拒绝 通常未发送 短暂故障可重试 目标地址和熔断状态
TLS 校验失败 未建立可信连接 不重试 证书、SNI、时钟与信任链
写请求时断开 可能部分发送 条件重试 方法幂等性、发送进度
读超时 请求通常已发送 远端状态未知 幂等、查询和成本策略
流中断 已收到部分结果 不直接拼接重试 是否有恢复协议和序号

TLS 证书错误、域名配置错误和不受支持的协议版本不会因为指数退避自动修复。把所有 NetworkError 放进同一重试装饰器，是第一类常见错误。

2. 429

RFC 6585 定义 429 为给定时间内请求过多，响应可以携带 Retry-After。但 RFC 不规定服务端按用户、资源、整套服务还是其他方式计数，也不保证每个服务都会发送这个状态。

客户端还要读取供应商错误体，区分：

  • request rate exceeded；
  • input token rate exceeded；
  • output token rate exceeded；
  • 突增触发的 acceleration limit；
  • 月度、日度、项目或账户配额耗尽；
  • 计费或权限状态不满足。

只有明确会随时间恢复的限制才适合自动退避。需要人工扩容、充值或修改权限的错误应快速失败并告警。

3. 5xx

常见可重试候选包括 500、502、503 和 504，但也不能写成“所有 5xx 永远重试”。

  • 500 可能是供应商临时错误，也可能由一个稳定触发服务端缺陷的请求造成；
  • 502 可能来自网关和上游连接；
  • 503 通常表示临时不可用或过载，RFC 9110 允许服务端用 Retry-After 建议等待时间；
  • 504 表示网关没有及时得到上游响应，此时上游是否完成仍可能未知；
  • 501 表示方法或能力未实现，重试通常没有意义。

当相同请求在短时间内连续触发同一 500，继续重试的边际收益会迅速下降。客户端需要总尝试上限，熔断器还要从整体窗口判断依赖是否已进入系统性故障。

4. 4xx

400、401、403、404、413 等通常要求修改请求、凭据、权限或资源，不应原样自动重试。

408、409 和 425 等状态需要结合具体 API 契约。不能因为它们“看起来临时”就放进通用模型客户端白名单。供应商文档和端点语义应进入适配器，而不是散落在业务代码里。

5. 解析和业务错误

HTTP 200 后还可能出现：

  • JSON 不完整；
  • 流没有终止事件；
  • 工具参数不符合 Schema；
  • finish reason 表示长度截断；
  • 内容被安全策略阻断；
  • 返回的模型或版本与预期不一致。

这些错误有的可以用修正后的请求再试，有的应作为正常业务终态，有的说明供应商协议异常。它们不应伪装成网络重试。

五、供应商差异必须保留，不能被一个统一枚举抹平

统一网关需要统一调用入口，但不应该假装各家错误语义相同。

1. OpenAI

OpenAI 官方错误文档把 429 至少区分为请求速率过高和当前配额耗尽。前者可以降速并退避，后者需要检查计划、余额或支出上限，原样重试不能恢复。官方文档还列出 500 和 503 的短暂服务端错误，并建议等待后重试。

限流文档提供 x-ratelimit-* 系列响应头来描述请求和 Token 的 limit、remaining 与 reset；这些字段是 OpenAI 当前 API 契约的一部分，不应被改名后假设其他供应商也有同样含义。排障时还要保留 x-request-id。

2. Anthropic

Anthropic 官方错误文档中，429 是 rate_limit_error，全局高流量过载使用单独的 529 overloaded_error，504 是处理超时。其限流文档描述了请求、输入 Token 和输出 Token 等维度，并在限流响应中提供 retry-after 与 anthropic-ratelimit-* 响应头。

另一个关键差异是：Anthropic 文档明确指出，SSE 流可能在 HTTP 已返回 200 后再发生错误。这时不能继续使用“只按 HTTP 状态码分类”的逻辑，必须解析流事件并把终态完整性纳入判断。

3. Google Gemini API

Google Gemini API 的官方排障文档使用 429 RESOURCE_EXHAUSTED 表示速率或相关配额耗尽，503 UNAVAILABLE 表示服务暂时过载或不可用，504 DEADLINE_EXCEEDED 表示未能在截止时间内完成。文档建议对明确的临时错误使用指数退避。

这里的字符串、状态结构和 SDK 异常类型都与前两家不同。适配层应该保留原始状态、原始错误码和原始响应头，再映射到内部低基数分类；只保存一个 provider_error 会丢掉恢复决策所需信息。

4. SDK 默认重试不能当稳定标准

供应商 SDK 可能内置重试，默认次数和状态集合会随版本变化。工程上需要：

  1. 锁定并记录 SDK 版本；
  2. 阅读该版本的重试实现；
  3. 明确选择由 SDK、统一网关还是业务层负责重试；
  4. 在调用链中暴露每个物理 Attempt；
  5. 升级 SDK 时重新跑故障注入。

文章中的任何尝试次数都只是策略示例，不是供应商永久默认值。

十、并发、请求速率和 Token 速率是三种不同控制

1. 并发限制

并发限制约束在途请求数量，主要保护：

  • 本地连接池；
  • 线程或协程；
  • 流式缓冲；
  • 供应商同时处理能力；
  • 下游故障时的堆积范围。

慢请求会长时间占用并发，即使 RPS 不高也可能耗尽系统。

2. 请求速率限制

请求 Token Bucket 控制单位时间开始多少次 Attempt。注意计数对象是物理 Attempt，而不是逻辑请求。一次重试同样会消耗发送速率。

5. 排队也必须有上限

限流器不能无限等待令牌。排队时间属于 overall deadline。等待超过准入预算时应返回明确的本地拥塞结果，避免请求还没发到供应商就耗尽用户时间。

十一、幂等不是一个 Header，而是端到端契约

RFC 9110 说明，客户端不应自动重试非幂等方法，除非能确认该请求语义实际幂等，或能确认原请求从未应用。POST 默认不是幂等方法。

IETF HTTPAPI 工作组曾发布 Idempotency-Key Header 的 Internet-Draft，用于讨论让 POST、PATCH 等请求可安全重试的协议方式。但它是工作草案，不是已经发布的 RFC；具体服务是否支持、键保留多久、并发重复怎样响应，必须以服务自身契约为准。

1. 调用方生成业务意图 ID

同一逻辑操作的所有 Attempt 复用同一个幂等键：

逻辑 ID 用于端到端关联，Attempt ID 区分物理调用。不能每次重试都生成新幂等键，那相当于告诉服务端这是新意图。

2. 服务端原子记录键和结果

AWS《Making retries safe with idempotent APIs》强调调用方提供唯一请求标识，并由服务端识别重复意图。真正可靠的实现还需要把幂等记录与业务变更放在一致性边界里，否则会出现：

  • 记录了键但业务没有执行；
  • 业务执行了但键没有记录；
  • 两个相同键并发通过首次检查；
  • 重试得到一个语义完全不同的响应。

服务端通常需要保存：调用主体、幂等键、请求指纹、状态、结果引用和过期时间。

3. 相同键、不同参数必须拒绝

哈希请求参数不能自动代表同一业务意图。两个完全相同的“创建实例”请求，可能是重试，也可能是用户真的要创建两个实例。更明确的方式是让调用方表达意图。

同一个幂等键再次出现但参数指纹不同，应返回冲突或校验错误，而不是复用旧结果或执行新动作。

4. 幂等键有生命周期

服务端不可能永久保留所有键。调用方必须知道去重窗口：

  • 窗口内的迟到请求怎样处理；
  • 资源删除后旧键重放得到什么；
  • 窗口过期后是否可能再次执行；
  • 跨租户键是否隔离；
  • 键冲突和低熵枚举如何防护。

本地进程内的 set() 只能防同一进程短时间重复，进程重启、水平扩容和跨区域后都会失效。高风险动作需要持久化幂等账本。

5. 模型供应商不支持幂等键时怎么办

不能随意发送一个 Idempotency-Key Header 并假设供应商会去重。未知 Header 可能被忽略，也可能被网关拒绝。

这时可以做三层收敛：

  1. 在自有 AI 网关按逻辑操作 ID 去重并缓存已完成结果；
  2. 把模型生成限定为“成本副作用”，明确重试可能产生重复费用；
  3. 把真正的外部工具动作放到支持幂等和对账的独立执行器。

自有网关去重也不能让两次模型输出天然一致。它只能选择复用第一次已完成结果，而不是重新采样后宣称等价。

十三、流式中断不能把两次输出直接拼接

流式响应在中断前可能已经返回：

  • 普通文本增量；
  • 结构化 JSON 的前半段；
  • 工具名称但没有完整参数；
  • 一个工具调用的完整参数但没有终止事件；
  • usage 或 finish reason 尚未到达。

1. 只有终态确认后才能提交结构化结果

对工具调用和 JSON 输出，应先写入临时缓冲区，完成下面检查后再提交：

  • 收到协议定义的正常终止事件；
  • 序列号连续；
  • JSON 可以完整解析；
  • Schema 校验通过；
  • finish reason 符合业务预期；
  • 没有后续错误事件。

中途解析出一个看似完整的对象，也不能立刻执行工具，因为后续流可能修正、追加或报告错误。

2. 重试时替换，不是追加

如果协议没有官方恢复游标，新的 Attempt 是一次新的生成。客户端应丢弃或标记旧的未完成缓冲，重新生成完整结果。把新流追加到旧流会产生重复段落、非法 JSON 和错误工具参数。

3. 给用户展示与业务提交分开

UI 可以显示 provisional token，但要能在中断时标记“输出未完成”。外部动作和持久化结果只能消费 committed result。

4. 记录部分成本和证据

流中断时可能拿不到最终 usage。仍应记录：已接收字节、已接收事件数、最后序列号、首 Token 时间、供应商 request ID、Attempt ID 和本地估算。估算不能冒充供应商账单事实。

十四、熔断器和隔离舱解决的不是同一个问题

1. 熔断器

熔断器观察一段窗口内的依赖健康：

熔断维度至少要考虑供应商、区域、模型和端点。把所有模型放进同一个熔断器，某个预览模型过载可能连带阻断稳定模型。

熔断器的错误样本也要区分：

  • 401 不应证明供应商整体不可用；
  • 单个超大请求 413 不应打开全局熔断；
  • 500、503、连接失败和高比例 read timeout 更能反映依赖健康；
  • 本地队列超时不能错误归因给供应商。

2. 隔离舱

隔离舱限制一个故障域最多占用多少并发、连接和队列。即使熔断器还没达到打开阈值，慢供应商也不能耗尽全部 Worker。

可以按以下维度拆池：

  • 在线与离线任务；
  • 高优先级与普通流量；
  • 主供应商与备用供应商；
  • 短请求与超长生成；
  • 不同租户或业务域。

3. 为什么只靠超时不够

超时会在到期后释放资源，但大量慢请求在到期前已经占满并发。隔离舱负责限制损失上限，熔断器负责在系统性故障时减少新工作，超时负责给单次等待设边界，三者需要同时存在。

十九、故障注入测试矩阵

1. Deadline

  • 准入等待计入 overall deadline；
  • 每次 Attempt 的 timeout 不超过剩余时间；
  • 退避后剩余预算不足时不再发送；
  • 流持续返回小块时仍受 stream duration 和 overall deadline 限制；
  • wall clock 跳变不影响单调预算。

2. Error classification

  • 400、401、403、413 不被原样重试；
  • 429 的速率限制与配额耗尽分开；
  • 500、502、503、504 保留原始状态与错误体；
  • TLS 校验错误不进入指数重试；
  • 本地拥塞不被标成供应商故障。

3. Retry-After 与 jitter

  • 相对秒数和 HTTP 日期都能解析；
  • 非法、负值和超大值有确定行为；
  • 实际等待不早于有效 Retry-After；
  • jitter 分布不会在固定边界同步；
  • 所有 sleep 都可被 Trace 观察。

4. Amplification

  • SDK、网关和业务层只有一个物理重试责任点；
  • 最大物理 Attempt 数可从配置推导；
  • 失败压测时 amplification ratio 有上限；
  • 重试流量不会挤占健康请求的全部并发；
  • 429 期间发送速率实际下降。

5. Rate 与 Token

  • 请求 Bucket 按物理 Attempt 扣减；
  • Token Bucket 使用输入估算和输出预留；
  • 成功后根据 usage 校正；
  • 超时且 usage 未知时不乐观全额退款；
  • 在线和离线任务使用独立配额。

6. Idempotency

  • 同一逻辑调用复用同一键；
  • 不同业务意图不复用键；
  • 相同键不同参数被拒绝；
  • 两个并发重复请求只执行一次；
  • 进程重启和跨实例后仍可去重；
  • 去重窗口过期行为有契约；
  • 供应商不支持时不会伪造承诺。

7. Streaming

  • HTTP 200 后错误事件能被识别；
  • 未收到正常终止事件不提交结果；
  • 新 Attempt 不追加到旧的半截缓冲；
  • 工具参数只有完整校验后才执行；
  • 用户取消能停止读取，并尽力传播取消，但不假设远端必然停止计费。

8. Circuit 与 failover

  • 熔断按供应商、模型和区域隔离；
  • 401、413 不错误打开全局熔断；
  • HALF_OPEN 只放有限探针；
  • 备用供应商有独立并发池；
  • 不可移植请求不会自动切换；
  • UNKNOWN_COMMIT 先对账再切换；
  • 切换后仍不突破全局尝试和成本预算。

  • 使用已知输入和已接收输出做下界估算，再增加未知余量；
  • 对成本敏感任务暂停后续大请求，直到速率窗口恢复；
  • 把“估算消费”和“供应商确认消费”分成两个指标。

4. 并发槽位何时释放

只有物理 Attempt 退出传输阶段后，才能释放并发槽位。逻辑请求进入退避时不应继续占用连接和执行槽，但可以保留轻量状态。

用户取消后，本地读取任务要尽快结束；如果协议支持取消，应向下游传播。即使本地槽位已释放，仍不能保证供应商立即停止计算，所以 Token 和费用账本仍可能处于未知状态。

5. 公平性和优先级

一个大 Token 请求不应永久挡住所有小请求，也不能因为小请求不断到来让大请求永远饥饿。可以结合：

  • 在线、离线独立队列；
  • 加权公平队列；
  • 按等待时间逐步提升优先级；
  • 大请求并发上限；
  • 租户级保底与上限；
  • deadline-aware 调度。

优先级只能决定资源竞争顺序，不能绕过供应商硬限制和安全预算。紧急请求若没有 Token，也不能凭一个 priority=high 强行发送。

6. 联合准入的测试

故障注入至少覆盖：

  • 请求额度充足但 Token 不足，不占住并发；
  • Token 充足但并发已满，不提前长期冻结 Token；
  • 等待时间超过 deadline，零次发送并返回本地原因；
  • 两个实例同时争抢最后额度，只有一个成功预留；
  • 预留成功后进程崩溃，租约到期能回收并留下审计；
  • 实际 usage 超过预留，后续额度正确收紧；
  • UNKNOWN_COMMIT 时额度按保守策略处理；
  • 在线流量在批处理打满自身配额后仍可获得保底资源。

只有这些断言通过，限流器才是在保护系统，而不是把供应商拒绝转化成本地隐蔽排队。

二十一、为幂等与未知状态建立持久化账本

进程内重试循环只能处理当前连接生命周期。服务重启、消息重复投递、跨区域接管和迟到响应，都需要持久化操作账本。

1. 最小数据模型

principal_scope 防止不同租户碰巧使用相同键后读到彼此结果。request_fingerprint 用于发现相同键被不同参数复用。指纹计算前要先做确定性规范化，例如稳定 JSON 字段顺序、明确缺省值和排除每次变化的 Trace 字段；否则语义相同的重试会得到不同摘要。

指纹不是授权。服务端仍要重新校验当前调用主体、租户和权限，不能因为知道一个幂等键就返回原结果。

2. 状态转换

推荐保留比 success/fail 更细的状态：

第一次请求以原子条件写入 RECEIVED。同键同指纹的并发请求看到 RUNNING 时，不应该再启动第二个执行器；它可以等待原结果、返回处理中，或订阅完成通知。同键不同指纹直接返回冲突。

3. 租约解决 Worker 崩溃

执行 Worker 获取带期限的 owner lease，并在运行期间续约。进程崩溃后，其他 Worker 只有在租约过期并完成远端状态检查后才能接管。

不能在租约一过期就立即重做。旧 Worker 可能只是与账本网络分区，仍在供应商侧执行。接管流程应先根据 provider request ID、任务 ID 或业务资源状态对账。

4. 迟到响应怎样处理

调用方已经超时后，旧 Attempt 的响应仍可能到达。响应处理器要用 Attempt ID 做条件更新：

  • 当前账本仍指向该 Attempt，可以写入终态；
  • 新 Attempt 已经接管，旧响应只作为对账证据，不能覆盖新状态；
  • 两个 Attempt 都声称成功时，检查幂等服务是否返回同一结果；
  • 对成本副作用，累计两次已确认 usage；
  • 对业务写操作，发现重复资源立即进入补偿和告警。

“最后到达者覆盖”会把时间顺序误当业务权威，不能用于分布式操作账本。

5. 对账 Worker 的判断顺序

如果模型供应商没有按 request ID 查询能力，工具侧仍要具备业务对账。例如创建工单后网络断开，可以按业务幂等键查询工单系统，而不是重新让模型生成一次再盲目创建。

6. 账本保留和清理

清理策略至少考虑：

  • 最大网络迟到时间；
  • 队列最大重投周期；
  • 业务资源生命周期；
  • 争议与审计保留期；
  • 敏感字段最小化；
  • 键过期后客户端可能重放的行为。

删除账本前可以保留不含敏感内容的墓碑摘要，用于阻止过期边界附近的重复执行。墓碑保留多久仍是业务契约，不能无限增长。

二十二、用指标证明恢复策略没有隐藏风险

1. 首次成功率

它比最终成功率更早暴露供应商和网络退化。最终成功率不变而首次成功率下降，说明重试正在掩盖问题。

2. 重试恢复率

恢复率很低表示当前错误不适合重试，或退避、预算和供应商选择不合理。按错误类型拆分后，可能发现 503 有恢复价值，而某类稳定 500 几乎从不恢复。

3. 放大比

需要同时看均值和高峰。均值 1.05 可能掩盖某个区域故障时瞬间达到 8。告警应结合错误率、物理 RPS 和供应商剩余额度。

4. 预算浪费

可以记录：

如果大量请求把时间耗在本地排队后才失败，说明准入过晚；如果第二次 Attempt 总在发出后马上被 overall deadline 取消，说明最小 Attempt 预算设置不合理。

5. 不确定状态与重复副作用

duplicate_side_effect_total 对高风险操作应是硬错误，不应该被最终任务成功率抵消。unknown_commit_total 突然增加通常指向网络、网关或流协议问题。

6. 切换质量

供应商切换不能只统计 availability。还要比较：

  • failover success；
  • failover 后的任务正确率和 Schema 合法率；
  • P95/P99 额外时延；
  • Token 和费用变化；
  • 安全拒答和工具选择变化；
  • 因不兼容而拒绝切换的请求比例。

7. 指标基数

Metric 标签适合放供应商、模型族、区域、错误类型、Attempt 序号和流量类别。request ID、幂等键、用户 ID 和完整模型名快照可能产生高基数，应保留在 Trace 或日志里。

8. 一次容量与恢复演练

演练可以按四阶段执行：

继续条件：

  • amplification ratio 在设计上限内；
  • 在线保底并发仍可用；
  • 没有 Retry-After 前的提前发送；
  • UNKNOWN_COMMIT 和重复副作用不增加；
  • 备用供应商质量门禁通过。

停止条件：

  • 物理 RPS 超过供应商或测试环境约定；
  • 本地队列持续增长且无法在 deadline 内清空；
  • 出现跨租户额度干扰；
  • 出现任何重复高风险动作；
  • 遥测丢失到无法判断 Attempt 数量。

演练结束后要逐步恢复流量，不能一次性释放积压队列。所有等待请求同时醒来会再次形成恢复洪峰。

二十三、一个示例故障案例：三层重试把短暂 429 放大成持续过载

下面是一个可复现的故障案例，用于说明排查链路，不代表真实生产事故数据。

1. 场景

在线客服 Agent 的正常流量约为 80 个逻辑请求每秒。业务层、统一网关和供应商 Python SDK 都配置了重试。业务层最多三次，网关最多三次，SDK 也启用了自己的默认重试。三个层级不知道彼此已经重试。

某次批处理任务和在线流量共用 Token 配额，供应商开始返回 429。

2. 时间线

3. 表面现象

最初看到的指标是：

  • 供应商 429 增加；
  • 网关 P99 上升；
  • 最终成功率只小幅下降；
  • 应用 CPU 并不高。

如果只看最终成功率，容易得出“供应商偶尔限流，重试已经兜住”的结论。

4. 关键证据

补齐逻辑请求与物理 Attempt 后，证据变成：

同一个 logical request ID 下出现多个网关 Attempt，每个网关 Attempt 里面又有 SDK 重试。业务层第三次重放还生成了新的逻辑 ID，使一部分放大流量最初无法关联。

5. 排除错误方向

排查先排除了：

  • 应用 CPU 和内存不足；
  • 单个模型版本性能退化；
  • DNS 或 TLS 故障；
  • 用户请求长度突然增长；
  • 单一区域网络丢包。

真正的先发异常是批处理 Token 速率上升，随后 429，接着物理 Attempt 放大，再之后才是本地并发耗尽。时间窗口对齐说明本地超时是伴生结果，不是首因。

6. 根因

根因不是单独的“限流”，而是五个设计缺口叠加：

  1. 三层独立重试，最大放大倍数没有被计算；
  2. SDK Attempt 对网关不可见；
  3. 在线和批处理共享 Token Bucket；
  4. 退避缺少充分 jitter，大量实例在相同边界重发；
  5. 只限制逻辑 RPS，没有限制物理 Attempt 和在途并发。

7. 修复

修复顺序如下：

  1. 立即暂停批处理，释放 Token 预算；
  2. 临时把网关最大物理 Attempt 收紧，并打开 429 熔断阈值；
  3. 关闭 SDK 不透明重试，由统一客户端持有唯一 overall deadline；
  4. 在线、离线分别使用请求、Token 和并发配额；
  5. 处理 Retry-After，使用 Full Jitter；
  6. 给业务重放复用 logical request ID 和幂等意图；
  7. 新增 amplification ratio、first-attempt success 和本地准入拒绝指标；
  8. 用合成 429 故障压测验证恢复曲线。

8. 回归结果怎样判断

修复是否有效不能只看“最终成功”。回归需要同时满足：

  • 注入 429 后物理发送速率下降；
  • amplification ratio 不突破策略上限；
  • 在线流量仍有独立并发可用；
  • Retry-After 前没有提前重发；
  • 退避时间在窗口内分散；
  • overall deadline 到期后没有后台继续重试；
  • 限流解除后通过少量探针平滑恢复，而不是瞬时洪峰。

二十四、第二个示例：流中断后重复执行工具

1. 场景

模型通过 SSE 返回一个创建工单的工具调用。客户端边接收边解析参数，看到 JSON 暂时合法后立即调用工具。随后模型流中断，统一重试装饰器重新发起生成。

第二次生成再次返回同一工具调用。工具 API 没有幂等键，最终创建两张工单。

2. 现象与误判

模型客户端只记录第一次 stream_read_error 和第二次 200。最终响应正常，所以业务 Trace 被标成成功。重复工单被误判为用户重复提交。

3. 正确排查

沿 tool call ID 对齐后发现：

  • 第一次流没有正常终止事件；
  • 工具执行发生在流终态之前；
  • 第二次模型 Attempt 生成了新的 tool call ID；
  • 两次工具参数的业务指纹相同；
  • 工具端没有业务幂等键和调用来源记录。

4. 修复

  • 模型流只写 provisional buffer；
  • 收到完整终态并通过 Schema、权限和策略检查后，才创建待执行命令；
  • 工具幂等键从业务意图生成，不使用模型生成的 tool call ID；
  • read timeout 后将模型 Attempt 标记为 incomplete，不追加新流；
  • 工具结果和模型生成分别建状态机；
  • 重放测试断言业务动作执行次数始终为一。

这个案例说明，模型请求幂等和工具副作用幂等是两层契约。前者不能替代后者。

二十五、常见错误做法

1. 所有异常都用一个重试装饰器

结果是认证失败、Schema 错误、TLS 错误和配额耗尽都被重复发送。分类应靠结构化状态和阶段，不靠异常消息字符串。

2. 每次 Attempt 都有完整 timeout

逻辑请求总时延会随尝试次数线性增长，最终突破上游 deadline。每次 Attempt 必须从剩余总预算派生。

3. 只设置 max retries

它无法约束 Retry-After、排队和慢 Attempt 的总耗时，也无法表达成本预算。

4. 429 立即重试

失败尝试可能继续计入限制，还会加重恢复压力。应遵守可用的 Retry-After、主动降速并加入 jitter。

5. 同时在 SDK、网关和业务层重试

最坏放大倍数是各层尝试数相乘。需要指定唯一物理重试责任点。

6. 把 GET/POST 的 HTTP 方法直接等同于业务幂等

HTTP 方法的幂等语义是基础，不代表应用内部所有副作用都被正确去重。反过来，POST 也可以通过明确契约实现业务幂等。

7. 有 Idempotency-Key Header 就认为安全

如果服务端没有原子去重、参数指纹、生命周期和并发规则，这个 Header 只是一个字符串。

8. read timeout 等于远端失败

它只证明客户端没有及时读到结果。远端可能已经完成并计费，写操作还可能已经提交。

9. 流中断后继续拼接新响应

没有恢复协议和序列号时，两次生成不存在可安全拼接的边界。

10. 供应商切换只改模型名

工具协议、Token、拒答、输出结构和数据治理都可能变化。切换前需要适配和持续回归。

11. 熔断器全局共享

一个模型或租户的故障会阻断所有请求。熔断和隔离维度应对应实际故障域。

12. 超时后立即归还全部 Token 预留

远端可能仍在执行。过度乐观的本地账本会继续放入新请求，再次撞到供应商限制。

二十六、适用边界与升级方向

1. 什么时候短重试有效

适用于：

  • 明确的临时网络故障；
  • 供应商短暂 500/502/503；
  • 带可接受 Retry-After 的瞬时 429；
  • 操作无外部副作用，或有明确幂等契约；
  • 剩余 deadline 足够完成有效 Attempt。

2. 什么时候不应同步重试

不适用于：

  • 认证、权限、参数、请求体大小错误；
  • 额度耗尽或长期配置问题；
  • 远端提交状态未知且没有对账能力；
  • Retry-After 已超过用户同步预算；
  • 长任务本来就不适合维持同步连接；
  • 供应商处于系统性故障且熔断已打开。

3. 什么时候升级成异步任务

当请求预计持续时间大于稳定网络连接窗口，或用户不需要同步等待时，可以使用持久化任务：

异步并没有消灭超时和幂等，只是把它们从一次 HTTP 连接转移到可持久化状态机。任务重复投递、Worker 崩溃和回调重放仍要使用同一个业务意图 ID。

4. 什么时候不要自动供应商切换

  • 法规或数据驻留不允许；
  • Prompt、工具或文件依赖供应商专有状态；
  • 备用模型没有通过任务和安全评测；
  • 输出差异可能触发不可逆动作；
  • 主请求处于 UNKNOWN_COMMIT；
  • 剩余预算只够快速失败，不够生成可靠结果。

二十七、上线检查清单

Deadline

  • connect、pool、read、stream duration 和 overall deadline 定义清楚；
  • overall deadline 使用单调时钟；
  • 上游 deadline 能传递到模型客户端；
  • 每次 Attempt 从剩余预算派生 timeout；
  • 排队、Retry-After、退避和切换都计入总预算；
  • 没有把文章示意值写成产品默认值。

Retry

  • 有稳定错误分类，不匹配异常文本；
  • 429 能区分速率、Token、突增和配额问题；
  • 只重试明确临时错误；
  • 正确解析并尊重 Retry-After；
  • 使用有界指数退避与 jitter；
  • 最大 Attempt 和总预算同时生效；
  • SDK 隐式重试已关闭或完全可观测；
  • 重试责任层唯一。

Admission

  • 并发、请求速率和 Token 速率分别控制；
  • 物理 Attempt 消耗请求预算；
  • 输入估算与输出预留进入 Token 准入；
  • 在线与离线流量隔离；
  • 本地排队有上限并可观测；
  • 故障期间健康流量不会被全部挤出。

Idempotency

  • 逻辑请求 ID、幂等键和 Attempt ID 分开；
  • 同一意图的所有重试复用原键；
  • 相同键不同参数被拒绝；
  • 去重记录和业务变更具有一致性保障；
  • 去重窗口和迟到请求有文档；
  • 不把 IETF 草案或自定义 Header 冒充供应商承诺；
  • 模型生成幂等与工具动作幂等分别验证。

Streaming 与 Unknown

  • 200 后的流错误能够进入失败分类；
  • 未完成流只作为 provisional 数据；
  • 完整终态前不会执行工具；
  • 中断重试会替换旧缓冲，不直接拼接；
  • read timeout 后能区分失败和未知；
  • UNKNOWN_COMMIT 有查询、幂等重放或人工对账路径。

Circuit 与 Provider

  • 熔断器按真实故障域拆分；
  • HALF_OPEN 探针数量受控；
  • 备用供应商资源池独立；
  • 请求有明确可移植等级；
  • 切换前检查 Token、Schema、工具、策略和数据边界；
  • 备用链路用合成流量持续演练；
  • 所有供应商的原始错误和 request ID 都被保留。

Observability 与 Test

  • 逻辑请求和每个物理 Attempt 都有 Span；
  • first-attempt success 与 logical success 分开；
  • 有 retry amplification ratio；
  • 有 retry delay、queue delay 和 remaining deadline；
  • 故障注入覆盖网络、HTTP、流、限流、熔断和对账；
  • SDK 升级会重新执行故障注入；
  • 日志不包含密钥、完整敏感 Prompt 和工具秘密。

二十八、小结

模型 API 稳定性不是给 SDK 加一个 max_retries=3。

可靠的调用链需要同时守住下面这些约束：

  1. 用 connect、read、stream duration 和 overall deadline 描述不同等待边界；
  2. 让所有 Attempt、退避、排队和切换共享同一个总时间预算；
  3. 按传输阶段、HTTP 状态、供应商错误体和远端提交可能性分类；
  4. 尊重有效的 Retry-After，并使用有界指数退避和 jitter 打散恢复流量；
  5. 用全局尝试上限阻止 SDK、网关和业务层产生乘法放大；
  6. 同时控制并发、请求速率和 Token 速率；
  7. 把幂等设计成调用方意图、服务端原子去重、参数指纹、结果复用和生命周期组成的契约；
  8. 把 read timeout、流中断和无终态响应纳入 UNKNOWN_COMMIT，而不是直接当失败重试；
  9. 用熔断减少对故障依赖的新压力，用隔离舱限制慢请求的损失范围；
  10. 把供应商切换当成经过能力、协议、安全和数据治理回归的新执行路径；
  11. 保存 trace ID、逻辑请求 ID、Attempt ID 和供应商 request ID，让每次恢复决策可以重放；
  12. 用无密钥故障注入证明预算、次数、幂等和副作用边界真的成立。
