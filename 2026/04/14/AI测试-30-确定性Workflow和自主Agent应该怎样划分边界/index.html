AI测试-30-确定性Workflow和自主Agent应该怎样划分边界

发表于 2026-04-14 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:03

Agent 项目最容易在命名阶段就失去边界。

只要系统里有一次模型调用、一个工具接口和一段循环，方案文档就可能把它称为“自主 Agent”；只要画出几个固定方框，另一份文档又可能把同一套系统称为“Workflow”。命名本身不是主要风险，真正危险的是控制权没有被说清：

  • 谁决定下一步做什么
  • 谁能扩大工具和数据权限
  • 谁判断业务前置条件已经满足
  • 谁允许产生写入、发布、付款或删除等副作用
  • 进程崩溃后从哪里继续
  • 同一步被重复投递时如何避免重复执行
  • 任务何时停止、何时转人工、何时补偿
  • 模型输出与业务事实冲突时听谁的

如果这些问题的答案都是“让模型根据上下文判断”，系统就不只是灵活，而是把流程控制、权限控制和事务语义一起交给了概率组件。

如果这些问题的答案全部被硬编码，系统又可能退化成一条不能适应未知输入的流水线：模型只负责填空，遇到任何未预设分支就失败。

更可执行的做法不是在 Workflow 和 Agent 之间选一个标签，而是先确定每一种控制权应该落在哪一层，再选择最简单且足够的复杂度。

Anthropic 在 Building effective agents 中给出了一个非常有用的架构区分：

  • Workflow：模型和工具沿预定义的代码路径被编排。
  • Agent：模型动态决定过程和工具使用方式，并控制如何完成任务。

这个定义关注的是“过程由谁决定”，不是模型调用次数，也不是有没有工具。一个包含十次模型调用的固定链仍然是 Workflow；一个只有三步、但由模型根据环境动态选择下一步的系统，已经具有 Agent 属性。

本文沿用这一区分，但把它进一步落到测试和生产控制层。重点不是重复 AI测试-19 中的任务完成率、工具正确率等通用 Agent 指标，而是回答另一个问题：

如何选择单次调用、链式 Workflow、路由、并行、编排者-工作者、评估者-优化者或自治 Agent；如何把关键业务约束、权限、副作用、恢复和终止留在确定性控制层；以及怎样证明这个边界在崩溃、超时和重复执行时仍然成立。

3. “有外层状态机”也不代表内部不是 Agent

外层状态机限定 Agent 能在什么阶段做什么，Agent 在阶段内部动态探索。这样的混合架构通常比“全流程自治”更容易审计，也比“全部写死”更能处理开放问题。

边界判断不能只看架构图上是否画了循环，而要逐项检查：

  • 下一步候选集合是否有限
  • 分支条件由规则还是模型决定
  • 模型能否创建新的子目标
  • 模型能否增加工具、权限或预算
  • 模型输出是否可直接产生副作用
  • 模型能否宣布任务成功
  • 代码能否在任何一步强制停止

二、复杂度阶梯：从一次调用到自治 Agent

复杂度不是成熟度。层级越高，通常意味着可处理的问题更开放，同时也增加状态、延迟、成本和失败组合。选择时应从最低层开始，只有低层方案在冻结评测集上明确达不到目标，才向上升级。

L0：单次模型调用

结构：

适合：

  • 分类、抽取、改写、摘要
  • 输入和输出边界清楚
  • 一次上下文能容纳必要证据
  • 结果可以由 Schema、规则或人工快速验证

主要优点是链路短、延迟低、证据简单。主要限制是复杂任务被压进一个 Prompt 后，模型同时承担理解、规划和生成，错误难以定位。

不要因为输出偶尔不稳定就立即增加 Agent。先检查输入质量、上下文选择、示例、工具接口和评测 Oracle。Anthropic 的官方工程文同样强调先使用能够满足需求的最简单方案；这是架构经验，不是对某个模型或业务的性能保证。

L1：Prompt Chaining

结构：

适合任务可以稳定拆成固定阶段，并且每个中间产物都有清楚验收标准的场景。例如：

  • 先生成测试点，再按风险覆盖规则检查，再生成用例
  • 先抽取事实，再验证来源，再生成报告
  • 先生成大纲，再检查章节契约，再写正文

它用更多调用和延迟换取更小的单步难度。失败可以定位到具体阶段，也可以在门禁处提前停止。

不适合的问题是：执行前无法知道要经历哪些阶段，或者下一步强依赖调查中才发现的新线索。为了覆盖所有可能性而写出几十个条件分支，通常说明任务已经超过固定链的舒适区。

L2：Routing

结构：

适合输入天然分成几个稳定域，每个域需要不同 Prompt、模型、工具或风险策略。例如：

  • 普通咨询、退款、技术支持进入不同处理链
  • 代码、日志、文档进入不同分析器
  • 低风险只读任务与高风险写任务采用不同审批级别

路由器可以是规则、传统分类器或 LLM，但类别集合、默认分支、置信不足处理和权限映射应由代码控制。

路由最常见的错误不是分类准确率低，而是未知类别被默认送进高权限通道。安全默认值应是拒绝、降级到只读流程或转人工，而不是“选一个最接近的工具继续”。

L3：Parallelization

结构有两类：

适合子任务真正独立，或者需要多个互补视角的场景。例如：

  • 分别检查安全、事实、格式和引用
  • 对互不依赖的文档分片并行抽取
  • 用多个固定检查器审查一段代码

并行不等于多 Agent。子任务如果在启动前已经确定，每个工作单元只是一次受限调用，它仍然是 Workflow。

并行化前必须识别共享状态。如果两个分支会修改同一文件、同一订单或同一发布状态，简单并行会把模型问题升级为并发一致性问题。此时要么隔离工作区并在后面确定性合并，要么保持串行。

L4：Orchestrator-Workers

结构：

它与固定并行最大的区别，是子任务在运行时由编排者根据输入动态产生。复杂代码修改、开放检索和未知文件范围的调查常适合这一模式。

Anthropic 把它列为一种 Workflow 模式，是因为外部控制拓扑仍然预定义：先拆分、再执行工作单元、再综合。模型在“如何拆”上拥有动态决策权，但不能因此自动获得无限委派、任意权限和任意终止权。

这一层已经需要任务合同、子任务去重、数量预算、结果 Schema 和聚合验收。第 31 篇会专门讨论多 Agent 调度；本文只强调，动态拆分不应该绕过外层控制器。

L5：Evaluator-Optimizer

结构：

适合同时满足两个条件的任务：

  1. 质量标准能够明确表达。
  2. 根据具体反馈进行迭代确实能改善结果。

例如代码生成后运行测试、报告生成后核对引用、翻译后检查术语一致性。

如果循环次数、通过阈值、允许修改范围和终止原因由代码规定，它仍可以是受控 Workflow。评估者即使也是 LLM，也只能提出评分和反馈，最终验收应优先使用测试结果、Schema、业务状态和可核验证据。

最危险的写法是“直到评估者满意”。它没有最大迭代次数，也没有进展定义。生成者和评估者可能反复改写措辞，持续消耗 Token，却没有业务质量增量。

L6：自治 Agent

结构：

适合：

  • 所需步骤和分支无法提前枚举
  • 环境会在执行中提供新证据
  • 任务有可观察的进展和成功条件
  • 工具结果能够提供环境真值
  • 错误动作可被限制、验证或恢复
  • 任务价值足以支付更高延迟和成本

自治 Agent 不适合把模糊目标直接接到不可逆高权限工具上。开放探索和高风险执行应拆开：Agent 可以调查并提出行动计划，确定性控制层负责校验、审批和提交。

三、选择矩阵：先问任务属性，再选架构名称

下面的矩阵不是通用评分公式，而是一份设计评审模板。每个结论都要在本系统评测集上验证。

判断维度 低复杂度信号 升级 Workflow 的信号 升级 Agent 的信号
路径可预测性 一次调用可完成 阶段固定、分支有限 步骤数和工具序列无法预知
输入分布 单一且稳定 可分成少量稳定类别 新线索持续改变任务边界
子任务关系 无需拆分 可提前拆分、依赖清楚 必须运行后才能决定如何拆

环境反馈 不需要 固定节点读取 每一步都可能改变下一计划

一个实用的决策顺序如下：

  1. 单次调用加检索和示例是否已经达到质量底线。
  2. 如果没有，失败是否能通过固定阶段拆分解决。
  3. 输入是否存在稳定类别，可以路由到专用链。
  4. 独立工作是否能并行，聚合规则是否清楚。
  5. 子任务是否必须动态生成，但外部拓扑仍可固定。
  6. 反馈是否能形成有界优化循环。
  7. 只有路径确实无法硬编码时，才扩大 Agent 的过程决策权。

用增量收益覆盖增量复杂度

架构升级至少要比较四类变化：

这里不能把不同单位硬加成一个漂亮总分。更合适的做法是建立 Pareto 比较：在满足安全、任务完成和证据完整硬门禁后，观察质量、时延和成本是否存在不可替代的改善。

例如 Orchestrator-Workers 相比固定并行只提升 0.5 个百分点，却把 P95 时延提高两倍、失败归因时间提高三倍，就没有足够证据证明升级合理。反过来，如果固定链在开放任务上持续遗漏未知分支，而 Agent 把关键覆盖率从不可用提升到发布底线，复杂度可能值得承担。

所有数字都应来自同一任务集、同一版本合同和同一评测口径，不能拿厂商案例数字替代本系统实验。

四、真正的边界不是 Prompt，而是控制面与执行面

可靠的混合架构通常至少分成四个面。

1. 目标与策略面

负责定义：

  • 任务目标与非目标
  • 允许的数据范围
  • 允许工具和参数边界
  • 风险等级
  • 审批要求
  • 成本、时延、步骤和委派预算
  • 成功、失败、转人工和取消条件

这些内容应版本化，并由代码读取。Prompt 可以向模型解释规则，但不能成为唯一执法点。

2. Agent 决策面

负责处理无法预先硬编码的部分：

  • 根据当前证据形成调查计划
  • 在允许集合中选择下一个只读或可逆动作
  • 提出修改方案
  • 分析工具错误和测试失败
  • 判断还缺少什么信息

模型输出在这一层只是提案。提案必须是结构化的，并带上动作目的、证据引用和预期后置条件。

3. 确定性控制面

负责：

  • 校验动作 Schema
  • 重新执行身份与权限检查
  • 检查业务前置条件
  • 绑定稳定幂等键
  • 检查预算和循环进展
  • 写入待执行事件与检查点
  • 调用工具代理
  • 核对权威后置状态
  • 决定重试、补偿、暂停或转人工
  • 宣布最终终态

模型不能通过输出“已经审批”让控制器跳过审批，也不能通过输出“任务完成”替代终态 Oracle。

4. 工具与环境面

工具服务本身还要执行最小权限和业务约束。

即使控制器有缺陷，工具端也不应接受：

  • 跨租户资源 ID
  • 超出角色范围的动作
  • 缺少版本号的并发写入
  • 缺少幂等键的关键写请求
  • 未经批准的高风险动作
  • 已过期或范围不匹配的批准令牌

这不是重复校验，而是纵深控制。Agent、控制器和工具服务处在不同信任边界，任何一层都不能把上游自然语言当作授权事实。

六、状态模型：不要把对话历史当作任务状态

对话上下文只能帮助模型继续推理，不能承担持久化工作流状态。

生产任务至少需要三类状态：

1. 控制状态

  • 当前阶段
  • 状态版本
  • 下一步允许转换
  • 已消耗步骤、Token、费用和时长
  • 当前审批、租约和截止时间
  • 控制器与策略版本

2. 业务状态

  • 被操作资源身份和版本
  • 已完成目标
  • 未完成目标
  • 已产生副作用
  • 可用补偿及执行结果
  • 权威系统回执

3. Agent 工作状态

  • 当前计划摘要
  • 已确认事实和证据引用
  • 未解决问题
  • 最近一次动作提案
  • 可丢弃的临时推理上下文

三者不能混成一段“memory”。控制状态和业务状态必须能够在不调用模型的情况下读取、校验和恢复。Agent 工作状态可以被压缩，但压缩不能删除权限、审批、未决副作用和预算等控制事实。

  1. 允许进入它的前置状态是什么。
  2. 进入时必须持久化哪些事实。
  3. 在该状态允许哪些动作。
  4. 离开时必须满足什么后置条件。

  • action_id
  • 工具名和标准化参数摘要
  • 稳定幂等键
  • 预期副作用类型
  • 调用截止时间
  • 提交结果不明确时的权威查询方法
  • 对应补偿定义

如果进程在请求发出后、响应写入前崩溃，新进程才能判断下一步应该查询、重试还是转人工。

终态也要有业务含义

  • SUCCEEDED：所有目标和不变量由独立 Oracle 验证通过。
  • FAILED：任务未完成，但没有未决副作用，失败原因完整。
  • MANUAL_REVIEW：存在需要人判断的冲突、未知提交结果或补偿风险，交接包完整。
  • CANCELLED：收到有效取消请求，所有可取消操作已停止，不能遗留无人管理的在途写入。

不能把“循环结束”直接映射为 SUCCEEDED，也不能把“达到 Token 上限”写成普通 FAILED 后丢掉现场。

一个可恢复检查点至少包含：

检查点要使用乐观版本或事务写入。旧进程不能在新进程已经推进到版本 18 后，再把版本 16 的快照覆盖回来。

固定每 30 秒保存一次无法保护关键副作用边界。更稳的触发点包括：

  • 每次模型提案被接受后
  • 每次工具调用准备完成、请求发出前
  • 每次工具回执写入后
  • 每次业务后置条件验证后
  • 每次审批状态变化后
  • 每次预算或阶段变化后
  • 进入任何终态前

十、重试：必须按失败语义分流

统一的 except Exception: retry() 会制造最难排查的重复副作用。

至少区分以下情况：

失败类型 可观察事实 建议动作
调用前失败 请求确定未发出 在预算内退避重试
提交前拒绝 服务确认没有提交 修正可修参数或按策略重试
提交后响应丢失 副作用可能已经发生 先按幂等键或业务键查询，禁止盲重试
限流或短暂不可用 服务明确可重试 遵守 Retry-After，并使用有上限退避
参数永久错误 Schema/业务规则拒绝 返回 Agent 修正一次或直接失败，不原样重试
权限拒绝 当前主体无权 不重试，不让 Agent更换身份，转人工或终止
版本冲突 资源已被并发修改 重新读取权威状态，再重新规划
部分成功 一部分效果已提交 对照效果登记逐项确认、补偿或接管

超时本身不能说明请求失败。HTTP 客户端看到超时，只能说明它没有在截止时间内获得确定响应。业务事务可能尚未开始、正在执行、已提交或回执丢失。

因此关键写工具必须提供至少一种可恢复能力：

  • 服务端幂等键
  • 按请求 ID 查询
  • 条件写和资源版本
  • 可验证的业务唯一键
  • 明确的事务回执

如果这些能力都没有，高风险写动作不适合交给长循环 Agent 自动执行。

十一、补偿不是数据库回滚

长任务跨越多个系统时，通常无法依赖一个全局 ACID 事务。补偿的作用是执行一个新的业务动作，尽量抵消已经提交的效果。

例如：

  • 创建临时工作区的补偿是删除隔离工作区
  • 部署金丝雀的补偿是回滚到已知稳定版本
  • 预留资源的补偿是释放预留
  • 创建草稿工单的补偿是关闭草稿并标记原因

但以下动作并不一定可完全补偿：

  • 已发送的外部邮件无法真正“撤回”收件人已读内容
  • 已泄露的数据无法通过删除日志恢复秘密性
  • 已触发的第三方 Webhook 可能继续产生下游效果
  • 删除后重建资源未必保留原身份、时间和引用关系

所以每种副作用都要在工具注册表中声明：

补偿顺序通常与效果顺序相反，但不能只根据栈机械倒放。系统要考虑依赖关系、外部状态变化和补偿本身失败。经典 Saga 论文提供了长事务拆分与补偿思路；将其用于 Agent 时仍要按实际业务重新定义补偿语义，不能把论文模型直接当成所有外部 API 的一致性保证。

十二、Replay：先说明重放的是哪一层

“支持重放”至少有四种不同含义。

1. 事件重放

从不可变事件重建控制状态，不重新调用模型和工具。

用途：

  • 检查快照是否正确
  • 修复投影或报表
  • 定位状态转换错误

2. Observation Replay

固定历史工具结果，让新模型或新 Prompt 在同样观察下重新决策。

用途：

  • 隔离模型变化
  • 复现某一步为什么选择错误
  • 比较决策策略

它不能证明新模型在真实环境里会收到同样 observation。

3. Decision Replay

固定历史动作提案，在隔离模拟器中重新执行控制器和工具代理。

用途：

  • 验证权限和状态机升级
  • 验证故障注入
  • 检查幂等与补偿

写动作只能进入可重置环境，不能直接对生产重放。

4. Resume

从最近安全检查点继续真实任务。

Resume 不是把最后一句对话重新发给模型。恢复器必须先：

  1. 获取运行租约，阻止两个恢复进程并行推进。
  2. 重放检查点后的事件。
  3. 查询所有未确认动作的权威状态。
  4. 校验控制器、策略和工具版本兼容性。
  5. 重新计算剩余预算和截止时间。
  6. 决定继续、迁移、补偿或转人工。

只要存在 ACTION_PREPARED 但没有 ACTION_CONFIRMED，恢复器就不能直接再次调用工具。

十三、超时要分四层，不要只设一个 HTTP timeout

1. 工具调用截止时间

限制一次外部调用等待多久。达到截止时间后得到的是“不确定 observation”，不是自动得到“未提交”。

2. 单步截止时间

限制一次 Agent 决策、工具执行和后置校验总共多久。工具很快，但模型反复修参数也可能超出单步预算。

3. 阶段截止时间

例如调查阶段最多 10 分钟、自动修改阶段最多 15 分钟、审批等待最多 2 小时。阶段过期后的处置不同。

4. 全任务截止时间

超过用户承诺时间或业务窗口后，即使还有 Token，也不应继续执行。控制器要停止新动作、处理在途副作用并生成交接包。

超时规则需要与取消传播结合。父任务取消后：

  • 未启动动作不再启动
  • 可取消的只读调用发送取消
  • 已提交写操作进入确认或补偿
  • 不可取消的外部任务继续被观察，不能成为孤儿
  • Agent 获得的是受控的取消事实，不是自行决定忽略取消

十四、循环预算：限制次数还不够，还要限制“没有进展”

至少建立以下预算：

  • 最大模型调用数
  • 最大工具调用数
  • 最大写动作数
  • 最大同类错误重试数
  • 最大连续无进展步骤数
  • 最大 Token 和费用
  • 最大墙钟时间
  • 最大审批等待时间
  • 最大子任务数量和委派深度

其中“无进展”需要可执行定义。例如 AI 回归修复任务可以把进展定义为：

  • 新增了已验证证据
  • 缩小了根因候选集合
  • 改变了失败测试集合
  • 通过了一个此前失败的硬门禁
  • 产生了可验收的新补丁

下面这些不算进展：

  • 用不同措辞重复同一计划
  • 对同一错误原样重试
  • 重复读取相同版本文件
  • 评估者只改写反馈但没有新增断言
  • 子任务返回已有证据的摘要

当连续无进展达到阈值时，控制器应停止循环，保存证据并转人工。不能让 Agent 自己通过“这次可能会不同”扩大预算。

十五、人工升级不是失败兜底，而是正常终态

适合人工接管的条件包括：

  • 业务目标存在无法消解的歧义
  • 工具提交状态无法权威确认
  • 策略版本变化导致旧任务不能安全迁移
  • 补偿可能造成更大损失
  • 需要新增权限或扩大数据范围
  • 达到循环、成本或时间预算
  • 关键证据冲突且没有程序 Oracle
  • 高风险动作等待明确批准

  • 相同幂等键配不同参数会明确冲突
  • 按幂等键可以查询提交结果
  • 权限在服务端重新校验
  • 版本冲突不会被最后写入覆盖
  • 回执能够关联 effect、资源版本和审计主体
  • 超时发生在提交前和提交后时可区分或可查询

5. 版本迁移测试

长任务可能跨越部署。要保存旧版快照，验证新控制器：

  • 能读取并迁移允许迁移的状态
  • 遇到策略语义变化时暂停，而不是猜测字段
  • 不会用新工具 Schema 重放旧动作
  • 保持原审批范围和幂等键
  • 迁移失败能生成完整人工接管包

第二，SUCCEEDED 不是唯一合格终态。审批过期和补偿风险场景进入 MANUAL_REVIEW，只要副作用受控、证据完整，就属于预期收口。

二十一、可观测性：要能证明控制器守住了边界

状态机能够恢复，不等于现场能够排查。长任务跨越模型、工具、事件存储、审批和发布系统后，同一个动作至少会出现四个时间：

  • 控制器准备动作的时间
  • 工具服务接收请求的时间
  • 业务副作用真正提交的时间
  • 回执被执行器持久化的时间

只记录一条“工具调用耗时 8 秒”，无法判断超时发生在提交前还是提交后。事件结构应分别保存 occurred_at、observed_at 和 recorded_at，并保留来源系统时钟、请求 ID、动作 ID、幂等键、资源版本和 effect ID。跨系统时钟可能存在偏差，所以因果关系优先依靠事件关联和版本，而不是仅靠毫秒时间排序。

1. Trace 不能只有模型 Span

一次动作至少需要下面的关联结构：

trace_id 用于串起技术调用，run_id 用于标识业务任务，action_id 用于标识一次逻辑动作，attempt_id 用于区分网络尝试，effect_id 用于标识实际副作用。四者不能合并成一个 ID。

同一逻辑动作可能有三次网络尝试，但只能对应一个副作用；同一次运行可能有多个动作；一次工具调用也可能产生多个需要分别登记的效果。ID 层级混乱时，重复调用、重复效果和正常重试会被报表混成同一件事。

5. 一次值班排查的判断顺序

假设出现“任务一直停在 WAITING_TOOL”告警，排查顺序可以固定为：

  1. 确认当前运行租约和 fencing token，排除双执行器。
  2. 读取最后一个 ACTION_PREPARED，核对动作、工具和幂等键。
  3. 在工具端按请求 ID 与幂等键查询，判断是否已有 effect。
  4. 对齐工具接收时间、业务提交时间和回执记录时间。
  5. 若已提交，补记可验证回执并执行后置 Oracle；不得再次写入。
  6. 若确认未提交，检查错误分类、截止时间和剩余重试预算。
  7. 若仍未知，停止该工具的新高风险动作，保存证据并转人工。
  8. 修复后用同一故障阶段重跑恢复测试，而不是只跑正常路径。

这个顺序先处理副作用事实，再处理模型为何选择该动作。反过来先阅读 Agent 文本，很容易花时间讨论计划是否合理，却忽略外部系统已经提交。

6. 隐私和证据完整性要同时满足

可观测性不意味着把完整 Prompt、凭据和业务数据写进每条日志。建议把内容与元数据分开：

  • Trace 保存摘要、引用、版本和策略结果
  • 敏感原文进入受控 Artifact 存储
  • 凭据只保存不可逆指纹或密钥引用
  • 参数日志执行字段级分类和脱敏
  • 人工接管按任务临时授权读取必要原文
  • 证据有保留期限、删除流程和访问审计

如果脱敏后无法判断资源绑定是否正确，可以保存稳定的测试别名或带权限控制的加密引用，而不是直接记录个人信息。证据必须足以验证边界，又不能因为排查系统本身扩大泄漏面。

二十二、最容易失控的十二种设计

1. 用 Prompt 写权限

“不要访问其他租户”只能帮助模型理解意图，不能替代服务端授权。测试要直接伪造越权提案，确认控制器和工具都拒绝。

2. 模型可以自行添加工具

动态发现工具可以改善可用性，但发现结果必须进入受限注册表和审批策略。模型不能根据工具描述自行获得新权限。

3. 把工具超时当成未执行

这是重复付款、重复创建和重复部署的直接来源。提交状态不明必须先查询。

4. 每次重试生成新幂等键

幂等键绑定业务意图，不绑定某一次网络尝试。同一意图的恢复和重试必须复用稳定键。

5. 只保存最新快照

快照损坏或被旧进程覆盖后没有重建依据。事件日志与快照应能互相校验。

6. 恢复时重新问模型“刚才做到哪里”

模型只能根据残缺上下文推断，无法知道外部事务真相。恢复先读事件和权威状态，再构建必要上下文。

7. 模型自己判断“测试通过”

测试进程退出码、报告摘要、样本级硬门禁和制品摘要应由程序读取。模型可以分析失败，不能伪造通过。

8. 评估者-优化者没有循环上限

两个模型可能持续互相提出风格建议。每轮必须检查可量化进展和预算。

9. 所有错误都进入补偿

补偿本身也是副作用。只有已确认效果、定义了业务补偿且风险可接受时才执行。

10. 人工审批只绑定一句自然语言

“同意发布”如果没有绑定动作摘要、制品、主体、期限和次数，可能被复用到另一个版本。

11. 部署时直接升级所有在途任务

状态 Schema、工具语义或策略变化可能破坏恢复。长任务需要版本固定、兼容迁移或新旧执行器并存。

12. 只测正常退出，不在缝隙中杀进程

最危险的错误发生在“已经产生效果但尚未记账”的几毫秒。故障注入必须命中这些语义边界。

二十三、什么时候不应该继续升级为 Agent

出现以下条件时，固定 Workflow 通常更合适：

  • 流程来自法规、审计或明确 SOP，分支必须可证明
  • 输入类别稳定，路由后步骤清楚
  • 每一步都有高风险副作用，开放探索价值很低
  • 低延迟要求无法容纳多轮观察与规划
  • 任务一次调用已达到质量和成本目标
  • 工具没有幂等、查询和隔离能力
  • 环境无法安全模拟或重置
  • 没有可靠终态 Oracle
  • 无法提供人工接管和运行可观测性

此时可以让模型负责理解、生成候选或解释错误，但不必让它控制过程。

二十四、什么时候可以扩大 Agent 自治范围

满足下面条件后，才有证据逐步扩大：

  • 固定链在真实任务上持续遗漏无法枚举的分支
  • Agent 在隔离环境中显著改善关键任务结果
  • 工具接口清楚、权限最小、错误语义可区分
  • 副作用可验证、幂等或可安全补偿
  • 全过程有事件、状态和成本 Trace
  • 循环、时间、Token、写动作和委派都有硬预算
  • 关键动作有独立策略与必要审批
  • 故障注入证明崩溃恢复不会重复或越权
  • 终态由独立 Oracle 验证
  • 人工接管能够从保存的事实继续

影子提案还有一个重要价值：它能够发现 Workflow 中没有覆盖的新路径，而不立刻承担副作用风险。可以统计 Agent 提出的合法新动作中，有多少确实带来新的已验证证据；如果大部分提案都被策略拒绝、与固定流程重复或没有新增进展，说明扩大自治的收益尚未成立。

放权实验必须能够一键收回

每一级自治能力都应有独立 Feature Flag 和工具策略版本，回退不是只改一句 Prompt。发生以下信号时，控制器应自动收回到上一层：

  • 越权或未批准动作出现一次
  • 重复副作用超过零容忍门禁
  • 未决动作积压超过恢复时限
  • 无进展循环显著增加
  • 人工接管包缺少权威状态
  • 成本或 P95 时延持续超过预算
  • 新控制器版本无法安全恢复旧任务

收回后，已启动任务不能被粗暴清空。执行器要冻结新动作，逐项确认在途副作用，把兼容任务交给旧控制器继续，不能兼容的任务进入人工接管。这样“关闭 Agent”才是一个有状态的运行操作，而不是前端按钮消失后让后台任务继续失控。

二十五、落地检查表

架构选择

  • 是否先验证单次调用能够达到什么水平
  • 失败是否可以通过固定阶段、路由或并行解决
  • 动态拆分是否真的需要运行时模型决策
  • 评估者-优化者是否有清楚 Rubric 和进展定义
  • Agent 带来的质量增量是否覆盖延迟、成本和运维复杂度
  • 厂商案例是否只作为架构经验，没有被当作本系统性能保证

控制权

  • 模型输出是否被定义为提案而不是授权
  • 权限、租户和资源范围是否由可信策略重新校验
  • 模型是否不能增加自己的工具、凭据和预算
  • 高风险副作用是否需要确定性条件与必要审批
  • 成功终态是否由独立 Oracle 验证
  • fail-open 和 fail-closed 策略是否按风险明确

状态与检查点

  • 控制状态、业务状态和 Agent 工作状态是否分开
  • 每个状态的进入条件、允许动作和离开条件是否明确
  • 检查点是否保存控制器、策略和工具版本
  • 未决动作是否保存幂等键、查询方式和效果类型
  • 状态版本是否防止旧执行器覆盖新状态
  • 事件能否重建快照并解释第一次分叉

副作用与恢复

  • 关键动作是否先持久化 intent 再调用工具
  • 同一业务意图的重试是否复用稳定幂等键
  • 提交状态不明时是否先查询而不是盲重试
  • 每种副作用是否声明可逆性和补偿语义
  • 补偿失败是否有人工接管和截止时间
  • 取消后是否没有无人管理的在途动作

超时与预算

  • 工具、单步、阶段和全任务截止时间是否分开
  • 是否限制模型、工具、写动作、Token、费用和委派
  • 是否定义连续无进展而不只定义最大轮次
  • 预算耗尽时是否停止新副作用并保存现场
  • 审批过期后是否需要重新批准
  • Agent 是否不能自行扩大预算

测试与证据

  • 状态转换表是否有正反单元测试
  • 不变量是否通过属性测试覆盖随机事件序列
  • 模型越权、伪造审批和假完成提案是否被注入
  • 是否在提交前后、回执前后和快照前后杀进程
  • 是否验证双执行器、迟到响应和事件重复
  • 量化结果是否明确标注数据来源、样本量和适用边界

人工接管

  • 接管条件是否是稳定规则而不是 Agent 自由选择
  • 交接包是否包含权威状态、副作用、未决动作和截止时间
  • 推断与已验证事实是否明确分开
  • 人工决定是否绑定具体动作和制品摘要
  • 接管后恢复是否继续沿用原幂等键和状态版本
  • 人工处理结果是否回写事件和回归样本

二十六、总结

Workflow 和 Agent 的差异不在于调用了几次模型，而在于过程控制权由预定义代码还是模型动态决定。

即使任务需要 Agent，关键控制仍应留在确定性层：

  • 策略和权限
  • 工具与参数边界
  • 幂等键
  • 写前登记
  • 状态转换
  • 检查点和恢复
  • 超时与预算
  • 补偿与取消
  • 人工审批
  • 最终成功 Oracle

Agent 最适合处理的是开放调查、候选生成、动态计划和失败分析。确定性控制器负责把这些提案限制在可观察、可验证、可停止、可接管的边界内。

最后的验收标准不是“Agent 大多数时候会遵守 Prompt”，而是：

即使模型提出错误动作、工具在提交后丢失响应、执行器在任意检查点崩溃、审批过期或循环失去进展，系统仍不会扩大权限、重复关键副作用或伪造成功，并且能够用完整证据恢复、补偿或转人工。

达到这个标准，Workflow 才真正承担了控制面，Agent 的自主性也才有可靠的工程边界。
