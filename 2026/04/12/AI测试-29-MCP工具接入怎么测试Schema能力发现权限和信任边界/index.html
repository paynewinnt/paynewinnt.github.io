一个 MCP Server 接入 Host 后，最容易完成的验证是：

这只能证明一条最顺的协议路径暂时可用，不能证明：

  • Client 与 Server 真正协商了兼容版本和能力；
  • tools/list 的所有分页都被读取；
  • Tool Schema 能约束模型生成的参数和服务端执行；
  • Schema 或工具描述变化后，旧授权不会继续生效；
  • 超时或取消后，高风险副作用没有发生；
  • OAuth Token 只被目标 Server 使用，没有向下游透传；
  • 同名工具不会被另一个 Server 替换；
  • Tool Description 没有把恶意指令带入模型上下文；
  • Tool Result 不会被当成可信指令继续驱动下一步；
  • 本地 Server 进程只能访问被授权的文件和网络；
  • 用户看到并同意的动作，与最终执行参数完全一致；
  • 审计记录能够还原 Server、Schema、授权、调用和外部结果。

MCP 解决的是 LLM 应用与外部数据、工具之间的互操作问题。它提供统一消息、生命周期、能力和数据结构，但不会自动替业务系统完成授权，也不会自动给本地进程加沙箱。

因此，MCP 接入测试不能停在“协议通了”。需要同时验证三类边界：

  1. 互操作契约：消息、版本、能力、Schema、分页、错误和 Transport 是否符合规范。
  2. 产品信任契约：Server 身份、工具变化、用户同意、最小权限和结果信任如何治理。
  3. 执行安全契约：文件、网络、进程、凭据和业务副作用是否被确定性代码限制。

一、版本和资料边界

本文以 2026-07-26 为资料截止日期，协议行为固定对照 MCP 官方发布的 2025-11-25 稳定规范，不引用截止日期之后的 RC、草案实现或未发布行为。

关键事实优先来自：

  • modelcontextprotocol.io 的 2025-11-25 版本化规范；
  • 官方 modelcontextprotocol/modelcontextprotocol 仓库中的 Schema 与文档；
  • 官方 MCP Security Best Practices；
  • 与工具投毒相关的原始安全研究。

文章中的“建议增加工具指纹”“跨 Server 名称空间”“副作用幂等键”等内容属于 Host 或业务系统需要补充的工程控制，不会伪装成 MCP 规范已经提供的保证。

2025-11-25 规范还包含实验性的 Tasks 能力。本文聚焦已经足以构成大多数工具接入风险的基础协议、Tools、Resources、Prompts、生命周期、Transport 和授权；实验能力不会被写成所有实现都必须支持的稳定前提。

二、先给结论：能力协商表示“支持”，不表示“获准”

下面三个判断必须分开。

1. Server 声明支持 tools

初始化响应包含：

它表示当前协议会话可以使用 Tools Primitive，并可能发送工具列表变化通知。

它不表示：

  • 当前用户有权调用每个工具；
  • Host 已经同意把所有工具暴露给模型；
  • Server 描述真实可信；
  • 工具进程被沙箱隔离；
  • 某次调用参数已获得用户确认。

2. OAuth Token 具有某个 Scope

它表示授权服务器授予了一组 Token 权限声明。资源 Server 仍需校验受众、过期、签名和具体业务对象权限。

Scope 也不表示用户同意模型在此时以这组参数执行副作用操作。

3. 模型选择了某个工具

它只是模型生成的一项调用提议。真正执行前，Host 或 Tool Gateway 仍需完成：

  • 工具白名单；
  • Schema 校验；
  • 参数规范化；
  • 身份、租户和资源授权；
  • 敏感数据外发检查；
  • 用户同意；
  • 幂等和并发前置条件；
  • 沙箱或执行策略。

只有双方正确实现规范时，MCP 才能提供互操作契约。即使完全符合协议，业务安全仍然需要额外控制。

四、Host、Client、Server：安全责任不能推给“协议层”

1. Host

Host 是包含和协调多个 Client 的 LLM 应用。根据官方架构，它负责：

  • 创建和管理多个 Client；
  • 控制连接权限和生命周期；
  • 实施安全策略和同意要求；
  • 处理用户授权决策；
  • 协调模型集成和采样；
  • 聚合多个 Client 的上下文。

生产实现里，Host 还应承担：

  • Server 信任清单和安装来源；
  • 工具全局名称空间；
  • Schema/Description 指纹；
  • 参数展示和确认；
  • DLP 与外发目标控制；
  • Tool Result 的不可信数据标记；
  • 本地进程沙箱和环境变量收敛；
  • 跨 Server 数据流策略；
  • 全链路审计。

2. Client

每个 Client 由 Host 创建，并与一个特定 Server 维持一条隔离的、有状态的连接。官方架构描述的是一个 Client 对一个 Server 的 1:1 关系。

Client 负责：

  • 初始化和版本协商；
  • 能力交换；
  • 双向消息路由；
  • 订阅和通知；
  • Transport 细节；
  • 请求 ID、超时、取消和响应匹配；
  • 保持 Server 之间的连接边界。

Client 不应把 Server A 的会话 ID、Token、游标或结果直接复用给 Server B。

3. Server

Server 提供聚焦的能力，可以是本地进程，也可以是远程服务。它通过 MCP 暴露 Tools、Resources、Prompts 等 Primitive。

Server 需要：

  • 正确声明能力；
  • 验证工具输入和资源 URI；
  • 实施访问控制和速率限制；
  • 清理工具输出；
  • 遵守 Transport 和授权契约；
  • 不接受错误受众的 Token；
  • 不把 Client Token 原样透传给下游。

4. LLM 不属于授权边界

模型可以参与工具选择和参数生成，但不能作为唯一策略执行器。

自然语言描述适合帮助模型理解“工具做什么”，不适合证明：

  • 当前用户是谁；
  • 可以访问哪个租户；
  • 文件路径是否越界；
  • 收件人是否允许；
  • 金额是否需要审批；
  • 生产环境是否允许写入。

这些事实必须由 Host、Server 和下游业务系统用确定性数据校验。

五、Base Protocol：先把 JSON-RPC 的基本错误测全

MCP 消息使用 JSON-RPC 2.0，并要求 UTF-8 编码。

1. Request

请求必须包含字符串或整数 ID，不能使用 null，并且请求方不能在同一会话里复用已经使用过的请求 ID。

测试至少覆盖：

  • 缺少 jsonrpc；
  • jsonrpc 不是 2.0；
  • ID 为 null、布尔值、对象或数组；
  • 同一会话重复 ID；
  • method 为空或未知；
  • params 类型错误；
  • 超大消息；
  • 非 UTF-8 数据；
  • 同一个 ID 返回两次结果；
  • 返回 ID 与请求 ID 不一致。

2. Result Response

成功响应需要同一个 ID 和 result 对象：

Client 不能只按收到顺序匹配响应，因为并发请求可能乱序返回。

3. Error Response

错误响应包含整数 code、字符串 message 和可选 data。能够读取请求 ID 时，错误必须带回相同 ID。

Client 需要区分：

  • JSON-RPC 结构错误；
  • MCP 方法参数错误；
  • Transport HTTP 错误；
  • Tool Execution Error；
  • 本地超时和取消；
  • 授权失败。

把所有错误都包装成“工具执行失败”，会破坏重试和归因。

4. Notification

通知没有 ID，接收方不得发送响应：

测试要检查 Server 不会给 Notification 回一个伪响应，也要检查 Client 不会把没有 ID 的消息放进等待响应表。

六、生命周期：initialize 必须是第一段业务交互

MCP 生命周期包含初始化、正常操作和关闭。

八、Tools、Resources、Prompts 的控制者不同

1. Tools：模型可发现并提议调用

Tools 被设计为 model-controlled，但规范不强制具体 UI。安全上，Host 应让用户知道哪些工具暴露给模型，并对敏感操作提供确认。

2. Resources：由应用决定如何纳入上下文

Resources 由 URI 唯一标识，可以通过列表、读取、模板和可选订阅提供数据。Host 可以让用户选择，也可以按应用策略自动纳入。

应用自动纳入不代表资源可信。文件、数据库字段、网页和工单都可能包含不可信自然语言或敏感数据。

3. Prompts：面向用户选择的模板

Prompts 被设计为 user-controlled，通常由用户显式选择。Server 可以返回带参数的结构化消息。

Prompt 模板来自 Server，仍需校验输入输出，不能因为叫“模板”就跳过 Prompt Injection 和资源越权测试。

4. 三者不能互相替代权限检查

  • Resource 可读不表示可以把内容发送给另一个 Server；
  • Prompt 可选不表示其中引用的 URI 自动获权；
  • Tool 已发现不表示可以调用；
  • Tool Result 返回资源链接不表示当前 Client 自动有权读取。

十二、取消和超时：停止等待不等于撤销副作用

MCP 支持可选的 notifications/cancelled：

接收方应尝试停止处理和释放资源，但规范允许接收方在请求未知、已经完成或无法取消时忽略通知。网络延迟还可能让取消晚于实际执行。

因此取消是协作信号，不是事务回滚保证。

1. 取消测试的竞态

至少构造：

对只读查询，目标可以是停止计算和释放资源。

对转账、发送邮件、删除文件等副作用操作，必须额外查询业务状态。收到取消后不能直接向用户显示“操作已撤销”。

2. 超时测试

生命周期规范建议所有请求设置可配置超时；超时后发送取消并停止等待。收到 Progress 可以重置普通计时，但仍应有最大超时，防止恶意或故障 Server 用无限进度通知长期占用资源。

需要验证：

  • 首字节超时与总超时；
  • Progress 洪泛；
  • 超时后到达的晚响应被忽略；
  • 晚响应 ID 不会匹配到新请求；
  • Tool 进程和子进程被回收；
  • HTTP/SSE 连接被正确关闭；
  • 外部副作用通过 operation_id 查证；
  • 重试沿用同一个幂等意图，而不是重复创建动作。

3. initialize 不能被 Client 取消

规范明确规定 Client 不能取消 initialize。测试夹具如果收到针对初始化请求的取消，应验证实现不会进入半初始化可用状态。

本地 Server 以 Host 进程能够授予的权限运行。配置中的可执行文件、参数、工作目录和环境变量都属于供应链和代码执行边界。

安装或首次连接时应展示完整命令和来源，不能截断危险参数。执行环境需要：

  • 最小文件系统目录；
  • 最小网络出口；
  • 独立临时目录；
  • 受限环境变量；
  • CPU、内存、进程和时间配额；
  • 不继承不必要的 SSH Agent、云凭据和代理 Token；
  • 可审计的子进程树。

MCP Security Best Practices 明确建议本地 Server 使用沙箱和最小默认权限。这里的沙箱由 Host/操作系统实现，不是 stdio framing 自动提供。

3. 退出与回收

Client 关闭 stdio Server 时，规范建议先关闭子进程输入，等待退出，必要时再逐步终止。测试应模拟：

  • Server 正常退出；
  • 忽略 EOF；
  • 忽略终止信号；
  • 留下孙进程；
  • 持有临时文件和端口；
  • Crash 后快速重启循环。

关闭完成后，旧进程不能继续访问用户数据或接受调用。

十四、Streamable HTTP：同时测试 HTTP、SSE、会话和 Origin

Streamable HTTP 使用 HTTP POST 发送每条 JSON-RPC 消息。Client 的 Accept 需要同时支持 application/json 和 text/event-stream，Server 对请求可返回单个 JSON 或 SSE 流。

1. Origin 与本地绑定

官方 Transport 规范要求 Server 校验所有传入连接的 Origin；存在且非法时返回 HTTP 403。Local Server 应优先绑定 127.0.0.1 而不是 0.0.0.0，并为连接提供适当认证，防止 DNS Rebinding 访问本地 MCP 服务。

测试覆盖：

  • 无 Origin 的非浏览器合法 Client；
  • 允许列表 Origin；
  • 大小写、端口和尾点变体；
  • null Origin；
  • 恶意 Origin 返回 403；
  • Host Header 与 Origin 不一致；
  • DNS Rebinding 模拟；
  • Server 是否意外监听所有网卡。

2. HTTP 状态与 JSON-RPC 状态分开

Notification 或 Response 被接受时，Server 返回 202 且无 Body；Request 则返回 JSON 或 SSE。测试不能把任意 HTTP 200 都当作业务成功。

授权错误、Origin 拒绝、会话不存在和 JSON-RPC Error 属于不同层，需要分别保存。

3. Session ID 不是认证凭据

Server 可在初始化响应的 MCP-Session-Id Header 中分配加密安全、全局唯一的会话 ID。后续 HTTP 请求必须携带它。

但官方安全指导明确要求：Server 不能把 Session 当作认证。每个入站请求仍需验证授权，并建议把 Session 与授权用户绑定。

测试包括：

  • 缺失 Session ID；
  • 猜测和重放 Session ID；
  • 用户 A 的 Session 配合用户 B 的 Token；
  • 多实例共享队列中的 Session 注入；
  • Server 终止 Session 后返回 404；
  • Client 收到 404 后重新 initialize；
  • 日志和 URL 中不泄漏 Session ID。

4. SSE 恢复和重复交付

SSE 可用 Event ID 和 Last-Event-ID 恢复。Event ID 是特定 Stream 内的游标，Server 不能跨 Stream 重放。

测试要注入断线、重连、重复 Event、乱序 Event 和错误 Stream ID。Host 还需保证同一个 Tool Result 不会因为重放触发第二次业务副作用。

十五、HTTP 授权：Token 受众正确仍不等于业务对象有权

2025-11-25 授权规范针对 HTTP Transport，授权本身是可选能力；HTTP 实现支持时应遵循该框架，stdio 不使用这套流程，通常从环境获得凭据。

1. Client、Resource Server 和 Authorization Server

受保护 MCP Server 充当 OAuth Resource Server；MCP Client 代表资源所有者发起访问；Authorization Server 负责授权交互和签发 Token。

2. Resource Indicator 和 Audience

Client 在授权请求和 Token 请求中需要使用 resource 指明目标 MCP Server。Server 必须确认 Token 是专门签发给自己的受众。

负向测试包括：

  • Server A 接受签给 Server B 的 Token；
  • Token 缺少目标受众；
  • 路径级 Server 使用了错误 Canonical URI；
  • 重定向后把 Token 发给不同 Host；
  • Token 被写入 Query String；
  • 同一逻辑 Session 后续请求漏带 Authorization Header。

3. 禁止 Token Passthrough

MCP Server 不应把从 Client 收到的 Token 原样转发给下游 API。若 Server 要调用第三方 API，它应作为独立 OAuth Client 获得面向下游受众的另一枚 Token。

测试可给入站 Token 放入唯一金丝雀值，并检查：

  • 下游 HTTP Header；
    -错误日志；
  • Trace Baggage；
  • Tool Result；
  • 缓存键；
    -异常响应。

任何下游出现原 Token 都应阻断发布。

4. 最小 Scope 和逐步提升

Client 初始只请求完成基础发现或只读操作所需的最小 Scope。高权限操作第一次出现时，由 Server 通过精确 WWW-Authenticate Challenge 指明新增 Scope，再走 Step-up 授权。

需要测试：

  • 初次连接请求所有写权限；
  • Server 每次返回整个 Scope 目录；
  • 用户拒绝提升后 Client 无限循环；
  • Scope 语义静默变化；
  • Token 声称有 Scope，但业务资源 ACL 拒绝；
  • 降权 Token 是否仍能用于低风险功能；
  • 提升后是否只重试有限次数。

5. OAuth 不替代用户动作确认

OAuth Consent 通常授权 Client 访问一类资源。一次具体的删除、付款或外发仍可能需要 Host 的参数级确认和业务审批。

用户确认界面应显示规范化后的：

  • Server 身份；
  • Tool 名称与风险；
  • 目标资源；
  • 关键参数；
  • 数据将发往哪里；
  • 副作用和可撤销性；
  • 授权有效期。

执行前再次比较同意摘要，防止确认后参数被模型或重试逻辑替换。

十六、Tool Result 必须按不可信输入处理

工具来自已注册 Server，不代表结果内容可信。

Tool 可能读取：

  • 用户可编辑的工单；
  • 网页和搜索结果；
  • 邮件正文；
  • 数据库自由文本字段；
  • 第三方 API；
  • 被污染的文件；
  • 另一个模型生成的内容。

这些结果重新进入模型时，可能包含：

Host 需要保留：

  • Server 和 Tool 来源；
  • 结果 MIME/Content Type；
  • 结构化 Schema 验证结果；
  • 数据分类；
  • 外部来源和信任级别；
  • 污染标签；
  • 可传递到哪些后续 Tool；
  • 是否允许进入 Prompt。

结果验证的四层断言

  1. 结构：ContentBlock 和 structuredContent 满足协议及 outputSchema。
  2. 来源：结果确实来自本次 Server、Tool 和 request ID。
  3. 业务：订单、文件或状态与权威系统一致。
  4. 安全：结果不会作为指令提升权限，不会携带秘密去往其他 Server。

只做第一层仍然可能安全失败。

十七、恶意描述、名称碰撞和 Server 替换

官方规范要求 Client 把不可信 Server 的 Tool Annotation 视为不可信。更广义地，Tool Description 也是 Server 提供给模型的自然语言，应纳入不可信输入和变更审计。

1. Tool Poisoning

恶意指令可以藏在看似正常的 Tool Description 中，诱导模型读取秘密、修改其他 Tool 参数或隐瞒行为。原始安全研究把这一类问题称为 Tool Poisoning。

测试不能只搜索 ignore previous instructions。需要覆盖：

  • 多语言和编码；
  • Markdown/HTML 隐藏段；
  • Description 要求读取额外文件；
  • Description 要求把信息放入可疑参数；
  • 对另一个可信 Tool 的行为指令；
  • 伪造 System 或管理员消息；
  • 通过多个 Tool Description 拼接的指令。

2. 名称碰撞和 Shadowing

两个 Server 都可以合法提供 send_email。如果 Host 只把短名称交给模型或授权缓存，恶意 Server 可能影响本应由可信 Server 执行的行为。

控制包括：

  • 内部执行 ID 带 Server Trust ID；
  • 模型看到清晰来源；
  • 同名 Tool 默认告警或需要显式选择；
  • 一个 Server 的 Description 不得修改另一个 Tool 的策略；
  • 调用时按不可变绑定路由，不能再按名称全局搜索。

3. Server 替换

本地包更新、远程 DNS/证书变化、配置路径被修改或注册表条目被接管，都可能让同一显示名背后变成另一个实现。

MCP 初始化的 serverInfo.name/version 是对端自报信息，不足以单独证明软件供应链身份。

Host 可以额外固定：

  • 本地二进制或包锁摘要；
  • 启动命令和参数；
  • 代码签名或发行来源；
  • 远程 Origin、证书和部署身份；
  • Registry 条目和版本；
  • 首次审批的 Tool Manifest 摘要。

任何关键值变化都触发隔离、重新扫描和重新同意。

Server 初次接入时提供无害描述，用户批准后再通过更新或 list_changed 改成恶意定义。原始研究把这种批准后改变描述的行为称为 Rug Pull。

Tools 之外：Resources 与 Prompts 的专项契约

只测 tools/list 和 tools/call 会留下两个缺口：Resource 可能把本地文件、数据库记录或远程内容带入上下文；Prompt 可能把 Server 提供的消息模板与嵌入内容带入模型。它们不一定执行外部动作，却同样可以造成跨租户泄露、上下文污染和间接 Prompt Injection。

Resource 契约至少要覆盖以下断言：

  1. 能力门控：Server 未声明 resources 能力时，Client 不能发送 resources/list、resources/read 或订阅请求。Server 声明 subscribe: false 时，即使实现恰好接受了订阅，也不应当被 Host 当作可用能力。
  2. URI 身份：对列表中每个 URI 做语法、方案和业务范围校验。file:///etc/hosts、file:///Users/alice/private.txt 和 db://tenant-b/orders 即使形式合法，也不因此属于当前租户可读范围。URI 是资源标识，不是授权凭据。
  3. 分页与变化：对 resources/list 复用 Tool 列表的完整性、无重复、有界终止和不透明 Cursor 属性；再验证 listChanged 声明与列表变化通知一致。不得因为 URI 排序改变就产生大量虚假变更告警。
  4. 读取一致性：resources/read 返回的每个 Content 都应与请求 URI 及授权决定关联。文本内容要限制编码、大小和 MIME；二进制 Blob 要验证 Base64、解码后大小和实际类型，不能只相信 Server 声明的 mimeType。
  5. 模板展开：对 resources/templates/list 中的 URI Template 使用空值、超长值、保留字符、路径穿越片段和不同租户 ID 做展开测试。展开后的 URI 必须重新走完整授权，不能因为模板本身在 Manifest 里就自动允许所有实例。
  6. 订阅生命周期：订阅成功、资源更新、取消订阅、Client 断线和会话终止后都要检查服务端订阅数。过期会话不得继续收到通知，重连也不能把旧租户的订阅绑到新会话。

Prompt 契约需要另一组断言：

  1. prompts/list 的分页、重名、参数列表和 listChanged 行为要与能力声明一致；缺少的必填参数、未声明参数、超长值和控制字符必须在 prompts/get 边界产生可归因错误。
  2. Prompt 的名称和参数合法，不代表返回消息可信。消息里若出现“忽略 Host 规则”、伪造系统指令、敏感资源引用或要求调用高权工具，Host 应当保留来源标记，并继续受策略层和用户同意约束。
  3. 对同一 Prompt 的空参数、边界参数和攻击参数做差分测试，并对返回的角色、Content Type、嵌入资源和字节上限做独立校验。不能把“能在 UI 中展示”当成“可以无损进入模型上下文”。
  4. Prompt 由用户选择的交互预期，不应被 Server 变成隐式自动触发。测试应用未打开选择面板、用户取消、快速切换 Server 和恢复会话等路径证明 prompts/get 没有意外发生。

一个有效的跨类型用例是：恶意 Server 在 Prompt 里嵌入一个名为“当前项目说明”的 Resource，Resource 内容要求模型调用另一个 Server 的 send_email。正确结果不是依靠模型“自觉忽略”，而是来源被标记为不可信，跨 Server 参数无法继承授权，邮件策略再次检查收件人和正文，未获有效同意时网络调用数为零。

测试判定器：不要用一个 pass 覆盖四种真相

MCP 系统中的“成功”至少有四个互相独立的判定器。测试平台应同时记录四个结果，不应合并成单一布尔值：

判定器 回答的问题 证据 典型假阳性
协议判定器 JSON-RPC 与当前 MCP 版本是否合规 原始帧、ID、Method、Error Code、能力快照 HTTP 200 就判成功
契约判定器 输入和输出是否符合版本化 Schema Manifest 摘要、Schema 版本、校验错误 只校验 inputSchema
策略判定器 谁在什么范围内得到什么允许 用户/租户、Scope、同意记录、对象级 ACL、策略版本 OAuth 成功就认为授权完整
事实判定器 外部世界实际发生了什么 网络、文件、进程、数据库、消息队列和业务终态 相信 Tool Result 自称“已完成”

判定器的关键是使用独立证据。例如发送邮件时，不用 Tool Result 作为发送成功的唯一依据，而是在隔离的测试 SMTP 端点记录收件人、正文摘要和幂等键。修改文件时，对沙箱目录做前后快照，同时检查沙箱之外的哨兵文件保持不变。调用付款工具时，对测试账本和事件流查询，并以业务 ID 去重，不使用模型最终回答作为财务真值。

为了让失败可重放，证据链中至少保留：

  • 不可变的 trace_id、session_id、request_id 和重试序号；
  • Host、Client、Server 版本及 Server 身份验证结果；
  • 初始化时协议版本、能力快照和完整 Manifest 的内容摘要；
  • 参数原文的受控摘要、规范化后参数和 Schema 校验结果；
  • 授权主体、租户、对象、Scope、策略决定、同意摘要和到期时间；
  • 请求发送、取消、超时、Server 确认和业务终态的单调时间序列；
  • 进程、网络目的地、文件路径、数据库行数等外部事实的受控摘要；
  • 结果来源、Content Type、字节数、截断事件、过滤事件和是否进入模型上下文。

审计也不应成为新的泄露面。Token、Cookie、密码、完整邮件正文和私密文件不能为了“可调试”就原样持久化。测试需同时验证审计脱敏、字段级访问控制、保留期、删除传播和导出权限。只有能证明“谁在什么时候依据哪个契约作了什么决定，外部世界发生了什么”，这条链才足以支持失败归因。

二十四、能力发现和变化的组合测试

能力测试不能只覆盖“全部能力开启”。至少组合下面几组 Server 声明。

组合 Server Capabilities Client 允许行为 负向断言
C1 {} 只有 Base Protocol/Lifecycle 不得调用 Tools/Resources/Prompts
C2 tools:{} list/call Tools 不依赖 list_changed 通知
C3 tools:{listChanged:true} Tools + 列表变化通知 通知后重新拉取并校验

动态变化的六条断言

  1. notifications/tools/list_changed 只在声明后按能力处理。
  2. 通知没有 ID，Client 不发送响应。
  3. 收到通知不会立刻信任新 Tool，而是触发完整分页刷新。
  4. 刷新结果按 Server Trust ID 保存，不能覆盖别的 Server。
  5. 新增、删除和修改分别生成不同审计事件。
  6. Description、Schema、Annotation、风险或身份变化会重新计算授权范围。

无通知变化

如果 Server 没声明 listChanged，Client 不能等待一个永远不会来的通知。每次新会话仍应重新获取列表；长会话是否周期刷新由产品定义。

无论采用哪种策略，执行时都应绑定调用所依据的 Manifest Version。Server 在调用瞬间使用另一套实现时，服务端审计和输出异常检测要能发现差异。

二十五、分页和列表一致性的属性测试

固定两页样例不足以发现边界问题。可以生成不同数量和页大小的 Tool 列表，验证以下属性。

1. 完整性

遍历到缺少 nextCursor 后，收集到的 Tool 集合应与 Server 的当前快照一致。

2. 无重复

同一 (server_trust_id, tool_name) 不应在最终激活列表中出现两次。发现重复时应中止激活，不采用“最后一条覆盖”。

3. 顺序无关

Server 改变分页顺序，不应改变已批准 Tool 与执行 ID 的绑定，也不应改变权限。

4. Cursor 不透明

Client 只原样回传 Cursor。测试给 Cursor 加入斜杠、等号、Unicode 或随机字节编码，Client 不能解析出页码后自行加一。

5. 有界终止

Server 重复返回同一个 Cursor 时，Client 在有限页数内停止并报告 PAGINATION_LOOP。它不能无限请求，造成资源耗尽。

6. 会话隔离

从 Session A 获得的 Cursor 传入 Session B 时，应由 Server 拒绝或由 Client 禁止。即使某个 Server 恰好接受，也不能把这种未定义复用写成 Client 依赖。

7. 变化期间一致性

列表在分页中途改变时，可能出现缺失和重复。因为基础分页契约没有替应用保证强快照一致性，Host 可采用：

  • Server 提供列表版本扩展时固定版本；
  • 完成后再拉取一次摘要确认；
  • 收到 list_changed 后废弃本轮分页并重试；
  • 对高风险 Server 暂停自动激活，进入人工复核。

二十六、Schema 测试要同时检查语法、兼容性和权限语义

1. 语法有效

Schema 本身符合声明方言，引用可解析，正反样本验证结果与规范一致。

2. Client 与 Server 一致

同一组参数在 Host 和 Server 应得到相同校验结论。若使用不同 JSON Schema 实现，重点覆盖：

  • format 是断言还是 Annotation；
  • default 是否自动填充；
  • 浮点边界；
  • Unicode 长度；
  • unevaluatedProperties；
  • 条件 Schema；
  • $ref 与递归。

两端语义不一致时，模型可能在确认后仍被 Server 拒绝，或者 Host 允许了 Server 实际会解释的额外字段。

3. 向后兼容

对每次 Manifest 变化分类：

“Schema 向后兼容”不等于“安全权限兼容”。把文件路径从固定项目目录放宽为任意字符串，可能不破坏 JSON 客户端，却显著扩大访问范围。

4. 业务约束

JSON Schema 可以表达类型和部分结构，但不适合单独决定：

  • 当前用户是否拥有订单；
  • 退款是否超过剩余额度；
  • 路径是否位于授权根目录；
  • URL 解析后是否属于允许域名；
  • 收件人是否在组织策略内；
  • SQL 查询是否跨租户；
  • 当前操作是否需要二次审批。

这些约束必须在 Server/业务服务端根据当前状态执行，并有独立测试。

二十七、用户同意测试：确认的是最终动作，不是一个模糊工具名

一个有效同意至少绑定：

1. 确认前参数变化

模型先生成参数 A，策略规范化为 B，界面必须展示 B。用户确认后执行器收到 C 时，应拒绝并重新确认。

2. 确认后 Manifest 变化

Tool 的 Description、Schema 或风险级别变化，旧同意不再适用。仅 Tool Name 相同不能延续授权。

3. 批量确认

“允许本次任务的所有操作”需要列出工具集合、目标和限制。新增 Tool、外部域名或更高 Scope 不能被旧批量同意覆盖。

4. 自动允许

低风险只读 Tool 可以由用户配置自动允许，但仍应有：

  • 资源范围；
  • 数据分类；
  • Server 身份；
  • Manifest 摘要；
  • 到期时间；
  • 随时撤销；
  • 异常行为暂停。

“Always Allow”不应等于对未来任意版本、任意参数和任意目的永久授权。

5. 拒绝与取消

用户拒绝后，网络层实际 tools/call 次数必须为零。用户在执行中取消，则界面需要区分“已请求取消”“已停止”和“动作已经完成”。

二十八、敏感数据外发测试：追踪数据流，不只扫描最终文本

测试可以在不同来源放入不可用于真实系统的金丝雀：

随后检查所有可能出口：

  • Tool Arguments；
  • Resource URI；
  • Prompt 参数；
  • HTTP Header 和 Body；
  • URL Query；
  • DNS 名称；
  • stderr、日志和 Trace；
  • Tool Result；
  • 模型最终回答；
  • 另一个 MCP Server 的输入。

允许的数据流也要验证目的

用户要求“把本地报告上传到批准的内部工单”时，文件内容可以进入指定 Tool，但不能同时进入：

  • 未批准的遥测；
  • 第三方分析 Server；
  • Tool Description 指定的隐藏 URL；
  • 错误详情；
  • 长期记忆。

因此 DLP 断言应是 (data_class, source, destination, purpose) 四元组，而不是简单禁止所有敏感字符串。

二十九、失败排查：按协议层、策略层和执行层找首错

现象一：模型看不到新工具

排查顺序：

  1. 初始化响应是否声明 tools；
  2. Client 是否完成 initialized；
  3. tools/list 是否遍历所有分页；
  4. 是否出现非法 Cursor 或循环；
  5. Tool Schema 是否被静态校验拒绝；
  6. Manifest 是否处于待审或隔离；
  7. Host 是否因名称碰撞改写内部 ID；
  8. 模型上下文是否因预算裁剪未包含定义。

如果工具停在安全审查状态，就不应通过扩大模型上下文解决。

现象二：tools/call 返回 200，但任务失败

依次区分：

  • HTTP 成功；
  • JSON-RPC 是 result 还是 error；
  • isError 是否为 true；
  • structuredContent 是否通过 outputSchema；
  • 业务状态是 accepted、processing、completed 还是 rejected；
  • 模型是否错误总结；
  • 下游是否发生副作用。

HTTP 200 只能证明 Transport 收到了一段响应。

现象三：更新 Server 后权限突然扩大

检查：

  • 二进制、证书、Endpoint 或 Registry 身份是否变化；
  • serverInfo 是否只靠自报值匹配；
  • Tool Manifest 摘要差异；
  • Description 和 Schema 的安全差异；
  • 旧自动允许记录是否只绑定 Tool Name；
  • OAuth Scope 是否新增；
  • 沙箱目录和网络规则是否变化。

现象四：超时后出现重复业务动作

对齐时间线：

如果第一次已经 Commit，根因不是“第一次失败”，而是 Host 把未知终态当作未执行，并且没有稳定幂等键或状态查询。

现象五：可信 Tool 发生异常外发

不能只检查该 Tool 的 Description。还要检查：

  • 另一个 Server 的恶意描述是否 Shadow；
  • Resource 或 Tool Result 是否包含间接注入；
  • 模型是否改变了目标参数；
  • 用户确认摘要与执行摘要；
  • 网络策略是否允许任意域名；
  • 可信 Tool 本身是否缺少服务端 DLP。

三十一、案例二：退款调用超时后被执行两次

1. 场景

远程 Server 调用支付系统创建退款。第一次 tools/call 已经在支付系统提交成功，但 Server 返回 SSE Result 前连接断开。

Host 10 秒超时，发取消后立即用新 Request ID 和新随机幂等键重试。

2. 表面现象

第二次调用返回成功，模型告诉用户“退款已处理”。后台出现两笔退款。

3. 排查证据

  • 第一次 Tool Trace 没有 Result；
  • 支付系统有第一次 operation_id；
  • 取消到达时第一次已 Commit；
  • 第二次参数业务意图相同，但幂等键不同；
  • Host 把 timeout 分类成 definite_failure；
  • 没有状态查询 Tool。

4. 根因

超时表示结果未知，不表示副作用未发生；取消也不能撤销已经提交的外部事务。

5. 修复

  • 幂等键由稳定业务意图生成并跨重试复用；
  • 超时状态改为 UNKNOWN_OUTCOME；
  • 重试前按幂等键查询；
  • Server 返回 operation_id 后即写入审计；
  • UI 显示“正在确认结果”，不显示失败；
  • 重试次数受限；
  • 支付系统对同一幂等键只接受一次。

3. 失败点

  • Host 把“可信 Server 的 Result”错误标为 trusted；

三十四、从 0 到 1 的接入顺序

第一阶段：只接一个只读、低敏 Server

完成：

  • 固定规范版本；
  • 生命周期和 Tools 契约；
  • Server 来源与 Manifest；
  • 无副作用只读范围；
  • 最小文件/网络权限；
  • Tool Result 不可信标记；
  • 完整审计。

第二阶段：加入多个 Server

补充：

  • 全局名称空间；
  • Client 1:1 隔离；
  • 跨 Server 数据流；
  • Shadowing 和名称碰撞测试；
  • 不同信任级别；
  • Context 与 Tool 预算。

第三阶段：加入远程授权和写操作

补充：

  • OAuth 资源绑定；
  • Token 受众和不透传；
  • 精确 Scope 与 Step-up；
  • 参数级用户同意；
  • 幂等、取消和未知终态；
  • 业务真值回查。

第四阶段：允许动态更新和规模化接入

补充：

  • Registry 和供应链策略；
  • Manifest Pinning；
  • 自动差异分类；
  • 隔离和重新审批；
  • 大规模分页与资源预算；
  • 持续安全回归；
  • Server 撤销和应急停用。

每个阶段都以安全性质和可恢复性为退出条件，不以“接入数量”作为成熟度指标。

三十五、限制和仍需单独处理的问题

1. 规范符合不能证明实现无漏洞

消息完全符合 Schema，Server 代码仍可能有路径穿越、注入、竞态和越权。

2. Description 扫描不能识别所有恶意语义

关键词、分类器和 LLM 审查都会漏报或误报。Manifest 审查只能降低风险，真正边界仍由权限、数据流和沙箱守住。

3. Tool Result 真实性需要业务真值

outputSchema 只能校验结构。Server 可以返回结构正确但内容错误的数据。

4. 用户确认可能疲劳

每次弹窗会降低可用性，但无限自动允许扩大风险。需要按副作用、数据敏感度、目的和 Manifest 版本设计有限授权，不存在一套适合所有产品的固定频率。

5. stdio 与 HTTP 风险不同

stdio 减少网络暴露，但本地进程可能直接拥有用户权限；HTTP 易做服务端隔离，却增加授权、Session、Origin、SSE 和网络攻击面。

6. 取消不提供事务语义

外部系统是否可撤销、如何幂等和如何查询终态，需要 Tool 自己设计。

7. 实验能力需要独立评估

2025-11-25 的实验 Tasks 等能力不能因为出现在 Schema 中，就默认成为所有 Client/Server 的稳定依赖。采用前应固定版本、能力和降级策略。

8. 截止日期之后的变化不在本文结论内

协议会继续演进。升级到新稳定版本时，应按 Changelog、Schema Diff、授权变化和安全指导重新执行契约与风险评审，而不是直接沿用本文对旧版本的断言。

三十六、上线前检查清单

版本和生命周期

  • 测试和生产固定 2025-11-25 或明确支持版本集合
  • initialize 是第一段交互，Client 检查 Server 返回版本
  • initialized 前双方只发送规范允许的消息
  • 重连后不复用旧请求 ID、Cursor、Session 和能力缓存
  • 每个请求 ID 在同一会话唯一，响应按 ID 关联
  • Notification 不带 ID，接收方不返回响应

能力和发现

  • Client/Server 只使用已协商能力
  • 子能力 listChanged、subscribe 分别判断
  • tools/resources/prompts 列表完整遍历不透明 Cursor
  • 有重复 Cursor、最大页数和列表大小保护
  • 列表变化后重新校验完整 Manifest
  • 能力与列表缓存绑定 Server Trust ID 和会话

Schema

  • 缺省方言按 JSON Schema 2020-12，显式方言有支持策略
  • inputSchema 是有效对象，无参数工具明确拒绝额外字段
  • required、additionalProperties、边界、组合 Schema 有正负样本
  • Host 和 Server 对同一参数的校验语义一致
  • 规范化后再做路径、URL、租户和业务授权
  • outputSchema 存在时结构化结果被验证
  • TextContent 与 structuredContent 不一致时拒绝机器处理

名称和 Manifest

  • Tool 内部执行 ID 包含 Server Trust ID
  • 同名 Tool 不发生静默覆盖
  • Description、Schema、Annotation 和执行元数据计算摘要
  • 本地二进制/包或远程部署身份被固定和审计
  • Manifest 变化使旧审批和自动允许重新评估
  • Server 自报 name/version 不作为唯一身份凭证

调用和错误

  • Protocol Error、Tool Execution Error、HTTP Error 和业务状态分别记录
  • 输入校验错误作为可控 Tool Error 处理，重试有预算
  • 高风险参数变化重新确认
  • 业务 accepted/processing/completed 不混成一个 success
  • 超时进入未知终态时先查询，不盲目重试
  • 副作用 Tool 使用稳定幂等键

取消、进度和资源

  • 所有请求有可配置普通超时和最大超时
  • Progress 不能无限延长最大超时
  • 取消竞态不会谎报外部动作已回滚
  • 晚响应不会匹配新请求或重复触发处理
  • stdio 子进程、孙进程、临时文件和端口能被回收
  • SSE 重连、重复和跨 Stream Event 已测试

Transport

  • stdio stdout 只写逐行 JSON-RPC，日志写 stderr
  • 环境变量只传递必要凭据，不继承整个用户环境
  • 本地 Server 使用文件、网络、进程和资源沙箱
  • Streamable HTTP 校验 Origin，非法 Origin 返回 403
  • 本地 HTTP 只绑定受控接口并要求认证
  • MCP-Session-Id 不被当成认证，并绑定授权用户
  • HTTP 状态、JSON-RPC 状态和业务状态分别判断

授权和同意

  • HTTP Token 每次请求携带且不出现在 Query String
  • Server 验证 Token 受众、有效期和当前权限
  • 入站 Token 不透传给下游，金丝雀测试为零
  • Scope 最小化，高权限通过精确 Step-up 获取
  • Tool 执行前重新检查租户和业务对象 ACL
  • 用户同意绑定 Server、Manifest、规范化参数、目标和有效期
  • 用户拒绝后实际 tools/call 次数为零

内容信任和数据流

  • Tool Description、Annotation、Prompt 和 Resource 按来源审查
  • Tool Result 即使来自可信 Server 也按内容来源标记
  • 外部自由文本不能成为权限或系统指令
  • 跨 Server 数据流有来源、分类、目的和目标策略
  • 回答、参数、URL、Header、日志和错误都纳入 DLP
  • 当前任务不需要的高风险 Tool 不暴露给模型

审计和恢复

  • Server/Tool Manifest、Consent 和 Invocation 可完整关联
  • Trace 保存版本、摘要、原因码，不保存秘密明文
  • 审计失败时高风险动作失败关闭或进入明确复核
  • Server 撤销后可以快速停用全部 Client 会话和凭据
  • 故障恢复不会重新启用已隔离 Manifest 或过期同意
  • 每个真实问题都转成固定夹具和负向回归

三十七、小结

MCP 让 Host、Client 和 Server 能用一致方式交换上下文、发现能力和调用工具。这项互操作价值很重要，但协议连接成功只是质量工作的起点。

可靠接入需要完成七个转变：

  1. 从“能列出工具”，转向验证版本、生命周期、能力和完整分页。
  2. 从“有 Schema”，转向验证方言、边界、两端一致性和业务授权。
  3. 从“调用返回成功”，转向区分 Transport、Protocol、Tool 和业务终态。
  4. 从“取消了请求”，转向验证副作用、幂等和未知终态恢复。
  5. 从“Server 已信任”，转向分别治理 Server 身份、Description、Result 和跨 Server 数据流。
  6. 从“OAuth 已授权”，转向受众绑定、最小 Scope、业务 ACL 和参数级用户同意。
  7. 从“协议保证安全”，转向由 Host 策略、Server 访问控制、下游真值和操作系统沙箱共同兜底。

2025-11-25 稳定规范明确了互操作契约，也明确把大量安全责任留给实施者。测试结论因此要写得足够准确：

MCP 能规定双方怎样表达能力、请求和结果；它不能证明 Tool 描述诚实、结果可信、用户已同意、业务对象有权或本地进程已经隔离。后者必须用确定性策略、真实副作用证据和负向故障注入单独证明。
