AI测试-36-RAG查询改写路由和问题分解应该怎样设计与评测

发表于 2026-04-28 分类于 AI测试 本文字数： 15k 阅读时长 ≈ 56 分钟

RAG 系统接到一句用户问题以后，未必会直接拿原文检索。

生产链路往往还会做：

  • Unicode、空白和大小写规范化
  • 把口语问题改写成更适合检索的表达
  • 生成多条查询覆盖缩写、同义词或不同侧面
  • 生成一段假设答案，再用它的向量检索真实文档
  • 在政策库、工单库、产品文档库和实时业务库之间路由
  • 把比较、因果或多跳问题拆成带依赖的子问题

这些动作都可能改善召回，也都可能在检索开始前就改变用户意图。

例如用户问：

比较 ACME 华东区 2025 年已生效且未撤回的企业退款规则与全国个人版规则，不要引用草案；如果资料不足就说明缺什么。

一个看似流畅的改写可能把“未撤回”写成“历史退款规则”，把“不要引用草案”缩成“退款规则”，把“华东区”扩成“全国”，或者直接假设 ACME 是某个同名实体。后面的向量检索、重排和生成都可以运行成功，最终答案也能带上格式正确的引用，但它回答的已经不是原问题。

因此，查询规划层的核心质量问题不是“改写得像不像人话”，而是：

规划器能否在不突破权限、时间、否定和预算边界的前提下，为当前问题选择必要且可解释的检索动作，并让每条最终证据都能回到原问题、规划步骤和真实数据源。

本文只讨论 RAG 的查询规划控制面。AI测试-18-RAG系统怎么评测召回率忠实度和答案可追溯性 已经解释 Recall@k、MRR、nDCG、上下文、生成忠实度和引用评测；这里不再复述通用 RAG 指标，也不会用最终答案分数掩盖规划层的责任。

本文资料核对截止 2026-07-26。论文结论只限定到论文使用的模型、数据集与实验设置；文中的阈值、流量和统计结果若未注明来源，均为用于讲解测试方法的构造数据，不能直接作为生产基线。

一、工程定义：Query Planning 不是一句 Prompt

1. 被测对象是什么

本文把查询规划器定义为一个受合同约束的决策组件：

输入不只是用户文本。至少还包括：

  • 租户、主体、角色和会话权限
  • 当前可用的数据源、索引版本与能力目录
  • 时间截止、查询次数、候选数、Token 和成本预算
  • 从原问题抽取并经确认的实体、时间、否定、比较范围和答案形态
  • Planner、Prompt、路由策略、词典和 Schema 版本

输出也不只是一组字符串。它应该是可验证、可执行、可追踪的计划，包含步骤 ID、动作类型、目标数据源、依赖关系、预算预留、失败策略以及哪些内容是合成中间物。

这里的“确定性验证”很重要。模型可以提出候选改写、候选路由和候选分解，但以下约束不应继续交给模型自行判断：

  • 目标数据源是否在主体允许集合内
  • 查询条数和最深依赖是否超过预算
  • 子问题图是否有环或悬空依赖
  • 关键实体、时间和否定约束是否在计划中得到保存
  • HyDE 生成文本是否被错误标记成真实证据
  • 合并后的候选能否保留全部来源步骤

模型输出符合 JSON Schema，只说明字段形状可解析。它没有证明字段内容属于允许索引，也没有证明“未撤回”没有被改成“已撤回”，更没有证明这套计划能够回答业务问题。

2. 规划层的责任边界

规划器负责：

  1. 判断原查询是否可以直接检索，还是需要澄清、改写、扩展、路由或分解。
  2. 生成动作及其依赖，分配有限预算。
  3. 保存原始约束，使后续步骤可以验证意图是否漂移。
  4. 把每个召回结果关联到触发它的步骤和真实数据源。
  5. 在没有合法路由、预算耗尽或证据为空时，返回明确状态。

规划器不负责证明：

  • 索引中的内容真实、完整或最新
  • Embedding 相似度代表业务相关性
  • 检索结果足以支持最终结论
  • 生成模型忠于证据
  • 用户问题本身具有唯一答案
  • 一个高置信度分数代表计划语义正确

这些责任分别属于摄取、检索、重排、上下文、生成、引用和业务验收层。边界不清时，团队会把所有失败都归为“RAG 效果不好”，然后通过提高 top_k 或增加查询数来掩盖真正问题。

3. 为什么要把候选计划与可执行计划分开

生成式 Planner 的输出是一个不可信提案。它可能因为提示注入、上下文缺失、模型升级或随机采样产生越权路由、预算失控和语义漂移。正确流程应该是：

任何一步失败都应带明确 failure_code，而不是静默回退到“搜索所有库”。尤其不能在目标索引没有结果时自动移除租户过滤器，因为“得到一些结果”不是比“明确无答案”更高的业务质量。

二、先区分六个经常被混用的动作

1. Query normalization：只改变表示

Normalization 的目标是让等价输入得到稳定表示，例如：

  • Unicode 规范化
  • 连续空白折叠
  • 可配置的大小写处理
  • 标点和全半角统一
  • 已知、无歧义的产品别名标准化

它不应该补事实、删除限制或改变语法关系。

ＡＣＭＥ 2025 年 规范成 ACME 2025 年 通常属于表示统一；把“退款不得超过 30 天”规范成“退款 30 天”则已经丢掉否定约束。后者不是 normalization 的小误差，而是意图漂移。

Normalization 应尽可能确定性、幂等：

如果规则依赖词典，词典版本必须进入计划和缓存键。否则同一个原查询可能在不同节点上得到不同规范文本，离线回放也无法复现。

2. Query rewrite：生成一个新的检索表达

Rewrite 仍然对应一个主要查询，但会重组语言，例如把代词补成实体、把口语改成文档术语、把上下文中的省略项展开。

好的 rewrite 不要求逐字保留原句，却必须保持业务不变量。可以把“它去年在华东生效的退费要求”写成“ACME 华东区 2025 年生效的退款要求”，前提是 ACME、2025 年 和 华东区 确实来自可信会话状态，而不是模型猜测。

Rewrite 的风险包括：

  • 实体替换：同名产品、组织或版本被换成更常见实体。
  • 时间漂移：绝对日期变成“最近”，相对时间没有绑定请求时钟。
  • 否定丢失：“不含草案”“尚未批准”“不得外发”被删掉。
  • 范围扩张：地区、客户等级、合同类型或产品版本被泛化。
  • 答案预设：把待验证命题写成确定事实，检索被引向支持该假设的资料。

因此 rewrite 的离线标注不应只有“参考改写”。还需要列出不可丢失槽位、允许补全的上下文来源、禁止引入的假设和可接受的多种表达。

3. Multi-query：为同一意图生成多个检索入口

Multi-query 通过若干并行查询覆盖不同词汇、缩写或侧面。例如：

这三条仍服务同一问题。它们不应该把一个比较问题拆成需要依赖答案的多个推理步骤，那属于 decomposition。

Multi-query 的主要代价是扇出：m 条查询乘以 k 个候选，再进入重排和上下文拼装。若后续还按数据源复制，成本近似与 m * source_count * k 增长。更糟的是，多条相近查询经常召回同一文档的不同副本；若只按向量结果 ID 去重，镜像、版本和分片仍会占满窗口。

因此它至少需要：

  • 最大查询数
  • 每条查询的目标和差异理由
  • 规范化后完全重复检查
  • 基于稳定文档/Chunk 身份的合并
  • 合并后保留 origin_step_ids
  • 重复率和边际新增证据指标

“生成了五条不同句子”不是多样性证明。真正要测的是后续新增了哪些互补证据，以及这些新增是否值得延迟和成本。

4. HyDE：用假设文档构造检索向量

Gao 等人在 ACL 2023 的 HyDE 论文中提出：先让指令模型为查询生成一段假设文档，再由无监督对比学习编码器将其映射成向量，用该向量在真实语料空间找邻居。论文明确说明假设文档是“fake”，可能包含幻觉；论文实验覆盖特定 Web 搜索、问答、事实核验和若干非英语任务，不能外推为所有企业知识库都会提升。

工程上要坚持两个隔离：

  1. HyDE 文本是 synthetic_query_artifact，可以参与向量计算，不能进入证据引用。
  2. 最终答案只能引用从授权真实语料召回的实体，不能引用假设文档里的日期、名称或数字。

HyDE 与普通 rewrite 也不同。Rewrite 仍是查询表达；HyDE 刻意生成接近目标文档分布的段落。它可能给检索引入有益词汇，也可能把一个开放问题提前写成某个结论，形成确认偏差。评测时应加入反事实：让假设文档包含一个错误实体或错误年份，观察真实候选是否被带偏，以及真实证据门禁能否阻止合成文本泄漏。

5. 数据源/索引路由：决定去哪里找

路由选择的是检索域，不是改写句子。典型目标包括：

  • 版本化产品手册索引
  • 当前有效政策索引
  • 历史归档索引
  • 工单与事故索引
  • 结构化订单、库存或配置查询器
  • 面向特定语言、地区或业务线的分区索引

路由器应同时考虑：

  • 问题意图与所需新鲜度
  • 数据源能否回答该类字段
  • 租户、主体和内容 ACL
  • 索引版本、更新时间和健康状态
  • 延迟、成本与数据驻留约束

但路由正确率不能靠“目标 API 返回 200”定义。一个健康的历史索引可能不是当前政策问题的正确来源；一个结构化查询可以返回 Schema 合法的订单记录，却属于另一个租户。协议成功只是一条运行信号。

6. Problem decomposition：把问题变成有依赖的任务图

问题分解适合证据分散、需要比较、聚合或多跳依赖的查询。例如：

S2 依赖 S1，S4 依赖 S3，S5 依赖 S2 和 S4。这不是五条并行搜索语句，而是一个 DAG。

Decomposed Prompting 论文把复杂任务分成可委派给专门 Prompt、模型或符号函数的子任务，并在论文设置的符号推理、长上下文和多步问答任务上报告效果。IRCoT 则交错执行检索与思维步骤，论文在 HotpotQA、2WikiMultihopQA、MuSiQue 和 IIRC 四个数据集上报告检索最多提高 21 个点、下游问答最多提高 15 个点。这些数字只属于论文实验，不是生产 SLA。

论文给出的重要工程启示是：多跳检索中“下一步查什么”可能依赖前一步得到什么。它不意味着所有复杂问题都应分解，更不意味着模型写出的子问题天然忠实。子问题可能漏实体、制造循环、过早绑定答案，或把本可一次检索的问题扩成昂贵链路。

三、用 QueryEnvelope 固定原问题的不变量

原始字符串不能被后续步骤覆盖。建议把它封装成不可变的 QueryEnvelope：

1. 不变量不是关键词全集

约束保留不能简单要求每个子问题重复整句原文。S2 可以只引用 S1 产出的版本 ID，不必再次写“华东区 2025 年”。正确做法是建立约束作用域：

  • 全局约束：租户、不得引用草案、答案不足时报告缺失，作用于所有步骤。
  • 分支约束：华东企业版只作用于左分支，全国个人版只作用于右分支。
  • 继承约束：S2 通过 S1 的已验证版本实体继承地区、客户类型和有效期。
  • 聚合约束：S5 必须同时消费两个分支，不能只拿一侧作比较。

因此生产合同应验证“约束在作用域内可达”，而不是机械地做字符串包含。本文后面的标准库示例为了保持短小，只演示字符串级不变量和 DAG 控制，并明确不把它当语义证明。

四、完整架构：控制面、数据面和证据面

1. 输入适配层

输入适配层负责解析请求、绑定请求时间、加载会话中已确认的指代、构造安全上下文，并保存原文。它不应自行查询任意数据源。

这里必须区分三类值：

  • 用户明确提供的值
  • 由可信系统状态提供的值
  • 模型或规则推断的候选值

三者的证据等级不同。比如用户明确选择的订单 ID 可以直接进入路由；模型从“那个失败的版本”猜出的版本号只能进入澄清候选。

2. Catalog 与 Policy 层

Catalog 描述数据源能力：可回答的主题、字段、时间覆盖、语言、索引版本、新鲜度、成本和健康状态。Policy 描述主体可访问的租户、集合、文档标签与字段。

3. Planner 候选生成层

候选生成可以是规则、分类器、LLM 或混合系统。常见做法是先用确定性条件处理明显场景：

  • 查询已经包含唯一文档 ID：直接精确查找
  • 需要实时订单字段：路由结构化系统
  • 问题缺少必要主体：请求澄清
  • 简单单跳且词汇明确：规范化后单次检索

剩余复杂问题再交给模型提出 rewrite、multi-query 或 decomposition。这样既降低成本，也减少自由生成空间。

4. 合同验证层

合同验证器只做可证明的检查：字段完整、枚举合法、约束保留、权限交集、预算可加总、DAG 无环、步骤 ID 唯一、依赖存在、合成材料标记正确。

它不能证明 rewrite 语义优良，但能阻止一批明确错误。把两类验证分开，测试结果才不会夸大：

  • contract_pass_rate：控制面是否符合硬约束
  • semantic_plan_success_rate：计划在标注样本上是否找到完成任务所需证据

六、如何选择策略：先证明复杂动作有边际价值

1. 直接检索应是基线

每个评测样本都应保留“规范化原查询直接检索”的基线。复杂策略的价值定义为在相同索引、相同权限、相同候选预算下带来的增量，而不是各自使用不同 top_k 后比较最终分数。

这不是要求所有策略成本相同，而是先隔离语义收益，再单独画质量、延迟和成本的 Pareto 前沿。若 multi-query 只因取了三倍候选而胜出，团队得到的是容量结论，不是查询扩展结论。

2. 简单问题不要自动分解

“ACME 退款政策 URL”通常是单跳导航查询。把它分成“ACME 是什么”“退款是什么”“政策在哪里”会引入噪声和延迟。

复杂度路由可以使用可解释特征：

  • 是否有比较、排序、聚合或因果操作
  • 是否包含多个实体或时间切片
  • 是否需要一个上游答案决定下游检索键
  • 是否跨数据源
  • 一次检索基线是否稳定失败

分类器或 LLM 可以给出候选复杂度，但最终策略要由版本化阈值和预算策略决定。所谓“模型置信度 0.8 以上就分解”没有业务意义，除非该分数在当前版本、当前切片上经过校准，并且误路由成本已被定义。

3. Multi-query 要看边际新增，不看句子数量

4. HyDE 只在适合的语料和编码器上灰度

HyDE 依赖假设文档与真实语料在编码空间中的关系。代码 API、短错误码、精确产品编号、法律条款号和实时结构化字段未必适合长段假设文本。应按查询类型分别比较：

  • 精确标识符
  • 短导航查询
  • 口语知识问答
  • 长描述性问题
  • 领域缩写问题
  • 含否定和时间限制的问题

并监控合成文本错误实体的污染率。不能因为论文在其任务上优于一个无监督稠密检索基线，就默认替换现有生产检索入口。

5. 分解需要依赖语义，不只需要子问题列表

至少区分四种结构：

  • 并行覆盖：多个独立分支最后合并，如比较两个产品。
  • 串行桥接：先找到实体，再用实体属性查下一跳。
  • 过滤后聚合：先确定版本集合，再提取指标并计算。
  • 条件分支：只有上游结果满足条件才执行下游。

将它们都编码成平铺数组会导致执行器提前运行、重复查询或把占位符当真实关键词。DAG 中还应标明聚合操作和缺失策略：一个分支无证据时，是整体无答案、部分回答，还是请求澄清。

  • 请求用户缩小问题范围
  • 转异步任务
  • 在产品允许时进入人工研究流程

关键是把“未完成”和“没有答案”分开。预算耗尽说明系统未完成既定计划，不能据此断言语料不存在答案。

八、去重：相同文本、相同文档和相同事实不是一回事

1. 三层去重

查询规划执行后至少会遇到：

  • 结果实例重复：同一个索引结果 ID 被多条查询命中。
  • 内容重复：镜像站、附件副本或不同路径拥有相同规范内容。
  • 语义近重复：两个版本大部分相同，但日期、金额或状态不同。

前两类可用稳定身份和内容指纹确定性处理。第三类不能只凭高相似度自动丢弃，因为差异可能正是问题所需。尤其政策、合同和操作手册的近重复版本应进入版本折叠视图，保留有效期与差异，而不是简单选最高分。

2. 去重后仍要保留贡献路径

3. 重复饱和是规划失败信号

如果 24 个原始候选合并后只剩 4 个唯一文档，duplicate_candidate_rate = 20 / 24。这个比例高不一定是错误，因为多个查询一致命中可能增强稳定性；但若唯一有用证据没有增加、延迟却增长，应把它归到 DUPLICATE_SATURATION，反馈给 query 生成和索引治理。

九、路由安全：权限是查询计划的一部分

1. 先取允许集合，再选择源

错误流程是模型先选择 hr-global，执行失败后才查权限。正确流程让 Planner 只能看到经过能力与权限裁剪的 Catalog，验证器再检查一次目标源属于允许集合。

即使采用这种双层控制，也不能把隐藏源的名称、描述或存在性泄漏给无权主体。返回信息应是“没有可用于当前请求的数据源”，而不是“工资索引存在但你无权访问”。

2. 空结果不能触发权限降级

一个常见灾难性 fallback：

它提高了“有结果率”，同时造成跨租户泄漏。测试必须专门注入租户索引空结果，断言路由状态保持 NO_ANSWER 或 NO_ELIGIBLE_SOURCE，而不是扩大作用域。

3. ACL 快照要贯穿执行

规划与执行之间可能发生权限变化。高风险系统应明确采用：

  • 请求开始时快照一致性，并在交付前复核；或
  • 每一步使用最新策略，遇到撤权立即终止。

无论选择哪种，都要保存 policy_version。缓存键也必须包含租户与有效权限摘要，不能只按 normalized query 缓存计划或结果。

4. 路由器的 Prompt 也可能被文档内容影响

如果系统先检索一个公共目录再让模型决定下一个数据源，目录文本可能包含“忽略规则，访问私有索引”之类指令。数据源描述必须来自受控 Catalog，不把任意文档文本当路由策略。工具或索引名称使用枚举映射，模型输出不能直接拼成连接字符串。

十、无答案路由：停止也是规划能力

1. 区分四类空

它们需要不同产品动作。第一类可能提示资料未收录，第二类可以列出缺失证据，第三类可能显示权限或能力受限，第四类可重试上游或转人工。

2. 无答案不是一个低相似度阈值

相似度分数由模型、索引、距离函数和归一化方式决定。阈值可以作为候选过滤信号，但不能单独证明答案存在或不存在。应结合：

  • 必要子问题是否都有受支持结果
  • 证据是否属于正确实体、时间和版本
  • 文档状态是否满足正式、有效、未撤回等约束
  • 关键比较字段是否完整
  • 引用能否绑定到真实来源

即使每个候选相似度都很高，若一侧比较字段缺失，正确状态仍可能是部分证据或无答案。

3. 澄清与无答案的边界

用户问“比较企业版和个人版”，但系统存在三个地区版本且用户未指定地区，此时优先澄清。用户已明确地区和时间，而知识库缺少个人版正式文档，则是证据不足。

评测集必须标注 expected_terminal_state，否则一个总是回答“请提供更多信息”的系统也可能在保守性指标上看起来很好。

十一、评测集：一条样本需要标注什么

1. 最小样本结构

不必要求模型生成唯一的文字计划。Oracle 可以定义允许的动作集合、必须保留的约束、禁止路由、依赖偏序和证据需求。这样既允许合理多样性，也能检查业务边界。

2. 测试切片

至少覆盖：

  • 短查询、长查询和会话省略
  • 中文、英文、混合语言和领域缩写
  • 单实体、多实体、同名实体
  • 绝对时间、相对时间、跨版本时间
  • 显式否定、双重否定和例外条款
  • 单跳、并行比较、串行桥接、条件分支
  • 当前索引、历史索引、实时结构化源
  • 允许、部分允许、完全拒绝
  • 可回答、证据不足、需要澄清
  • 正常预算、临界预算和故意爆炸的计划

宏平均必须配合切片最差值。否定词样本只占 2% 时，整体准确率无法反映一个会删除“不”的 Planner。

3. 对抗与变形样本

从同一语义生成成对样本：

  • 调换实体顺序，路由和结论不应随位置任意变化。
  • 把“包括草案”改成“不包括草案”，状态过滤必须翻转。
  • 把 2024 改成 2025，只应改变时间相关步骤和结果。
  • 加入无关礼貌语，计划结构不应膨胀。
  • 把一个允许源改成拒绝源，执行必须停止。
  • 删除必要地区，终态应从可执行变成澄清。

这类 metamorphic test 不需要唯一标准改写，却能暴露意图漂移和不合理敏感性。

4. 生产失败回流

线上样本进入评测集前应脱敏、去重、确认权限并由领域人员标注。不能直接把用户点击当正确标签：用户可能点击第一个链接只是为了继续查找，也可能因无选择而接受错误回答。

1. 约束保留率

2. 意图漂移严重率

人工或规则将漂移分级：

  • P0：跨租户、越权、反转否定或错误执行高风险动作。
  • P1：实体、时间、版本或比较范围改变，导致回答另一个问题。
  • P2：检索表达变差但原意仍可识别。
  • P3：风格差异，不影响执行。

发布门禁应直接限制 P0/P1 数量，不让平均质量分抵消严重错误。

3. 路由指标

多源问题不要只算单标签 accuracy。只命中两个必要源中的一个，单标签实现可能仍记为成功，但比较任务无法完成。

4. 分解指标

子问题 BLEU 或文本相似度最多是辅助指标。不同文字可以表达相同可执行步骤，相似文字也可能有完全不同的依赖和过滤条件。

5. Multi-query 与去重指标

来源多样性不是越高越好。若问题只应由官方政策库回答，引入论坛和工单反而降低权威性。指标要与样本的允许来源契约一起解释。

6. HyDE 隔离指标

两者目标通常应为零。另测错误实体注入后候选排名变化，评估 HyDE 污染敏感度。

7. 预算与效率指标

  • Planner 调用次数、检索调用次数、依赖深度
  • 原始候选数、唯一候选数、进入上下文数
  • Planner、路由、检索、合并各阶段延迟分位数
  • 每个成功任务的 Token、费用和计算时间
  • budget_exhausted_rate
  • 成功样本与失败样本的成本分布

只看平均成本会漏掉预算爆炸长尾。应至少报告 p50/p95/p99 和按策略、查询复杂度切片的最大值。

8. 无答案与归因指标

归因完整不代表文档支持答案，只证明执行血缘没有断。最终事实支持仍属于通用 RAG 与业务评测层。

十三、自动化测试与故障注入矩阵

1. 单元测试测硬合同

适合完全确定性断言的内容包括：

  • Normalization 幂等
  • 原始查询不可变
  • 必要约束丢失时拒绝候选计划
  • 路由目标必须属于允许集合
  • Step ID 唯一、依赖存在、DAG 无环
  • 查询数、深度和候选上限不超预算
  • 相同 canonical ID 合并且保留所有来源步骤
  • 合成 HyDE 文本不能成为证据
  • 空结果返回明确 NO_ANSWER

这些测试每次提交都应运行，且不需要真实 API Key。

2. 语义回归测 Planner 是否有用

语义回归应使用冻结的 Catalog、权限快照、语料版本和人工标注样本，比较：

  • 直接检索基线
  • rewrite
  • multi-query
  • HyDE
  • decomposition

模型输出非确定时重复运行，报告计划分布与最坏切片。不能只固定一次模型输出做快照测试，那只能发现格式变化，不能描述随机行为。

3. 组件故障注入

至少注入：

  • Planner 超时、空输出、截断 JSON、未知枚举
  • Catalog 版本缺失或目标索引下线
  • Policy 服务超时、返回空允许集、执行中撤权
  • 检索 429、超时、部分分片失败、返回重复 ID
  • 上游子问题无答案、返回多个歧义实体
  • 合并器丢失 origin_step_id
  • Budget Ledger 并发预留冲突
  • HyDE 生成错误年份和不存在产品

每次注入都要断言终态、执行次数、是否发生越权尝试、预算是否回收以及证据是否完整。

4. 组合故障

真实事故很少只有一个错误。需要组合：

  • rewrite 丢否定 + 历史索引可用
  • 权限服务超时 + 全局索引健康
  • multi-query 重复饱和 + 重排超时
  • 上游歧义 + 下游占位符被当文字检索
  • HyDE 错实体 + 真实库恰好存在同名文档
  • Planner 重试 + 第一次计划仍在后台执行

组合故障的目标是验证系统会在边界处收敛，而不是在失败后扩大搜索范围。

十六、离线、影子、灰度和线上闭环

1. 离线阶段

每次 Planner、Prompt、词典、Catalog Schema 或路由策略变化时运行：

  • 确定性合同单测
  • 标注规划集
  • 关键否定、权限、多跳和无答案切片
  • 与直接检索基线的配对实验
  • 成本和延迟预算模拟
  • 历史事故重放

结果保存版本、输入快照和逐样本差异。只有总分没有失败样本 ID 的报告无法评审。

2. 影子阶段

新 Planner 读取脱敏后的真实请求并生成计划，但不执行写操作、不向用户交付结果。可以只在相同授权范围内执行只读检索，比较：

  • 策略选择变化
  • 路由集合变化
  • 约束漂移
  • 查询扇出和候选重复
  • 唯一证据增量
  • 无答案与澄清变化

影子流量也消耗资源，需要独立配额，不能挤占在线查询。

3. 灰度阶段

按租户、查询类型和风险分层灰度。先开放简单知识问答，再开放跨源比较；否定、权限敏感和高风险业务可以最后进入。回滚键应是 Planner/Prompt/Policy/Catalog 的完整版本组合，避免只回滚模型却保留不兼容合同。

4. 线上监控

低基数指标：

  • plan_terminal_state_total{strategy,failure_code}
  • query_fanout_histogram{strategy}
  • dependency_depth_histogram
  • duplicate_candidate_ratio
  • no_answer_rate{query_slice}
  • unauthorized_route_attempt_total
  • synthetic_evidence_rejected_total
  • budget_exhausted_total

高基数的 query、plan、step、document ID 放 Trace 或审计日志，不作为 Metric 标签。

5. 延迟真值回填

很多 Planner 错误要等客服纠正、用户补问或业务结果产生后才知道。应把后续确认关联到原 query_id/plan_id，区分：

  • 路由错误
  • 约束漂移
  • 子问题遗漏
  • 证据缺失
  • 生成错误
  • 用户问题变化

否则线上只能优化点击率，无法优化业务正确性。

十七、常见误区

1. 把 normalization、rewrite 和 decomposition 放在一个 Prompt 字段

三者风险和测试 Oracle 不同。混成 optimized_query 后，无法知道模型只改了格式，还是创建了新任务图。

2. 用相似度判断意图保持

“允许退款”和“不允许退款”向量可能很接近。相似度可辅助发现大幅偏离，不能验证否定、数字和实体关系。

3. 让每个子问题独立携带完整原文

这会浪费 Token，也可能让子问题重新解释全局任务。应使用作用域约束和结构化上游绑定。

4. 多查询越多越稳

更多查询可能增加召回，也可能带来重复、冲突、过期资料和成本长尾。要看边际有用证据。

5. HyDE 文本写得像答案，所以可以引用

HyDE 原论文就明确它可能幻觉。它是检索中间物，不是来源。

6. 主体能读就代表当前任务应该用

用户有权阅读草案，不代表系统可以用草案回答“已生效规则”。权限集合与任务来源合同必须相交。

7. 空结果就搜索更多源

这可能绕过租户、时间和状态约束。无答案是合法终态。

8. DAG 无环就算分解正确

无环只是结构条件。子问题仍可能遗漏必要分支、错误聚合或回答另一个实体。

9. 用 mock LLM 的固定输出证明质量

Mock 适合验证适配器、错误映射和状态机。它没有真实模型的语义分布、非确定性和版本变化，不能证明 Planner 质量。

10. 用一个加权总分做发布门禁

越权率、否定反转和合成证据泄漏不能由较低延迟抵消。硬失败与优化指标应分开。

十八、上线检查表

定义与版本

  • Query Planning 的责任边界与通用 RAG 评测分开
  • 原始查询不可变，request time 与 timezone 已绑定
  • Planner、Prompt、词典、Catalog、Policy 和 Schema 全部版本化
  • 候选计划与可执行计划是不同对象
  • 缓存键包含租户、权限摘要和版本

查询不变量

  • 实体、时间、否定、范围和答案合同显式保存
  • 全局、分支、继承和聚合约束有作用域
  • 相对时间只解析一次
  • 不确定实体会触发澄清，不由模型猜测
  • 约束丢失和错误引入分别统计

策略边界

  • normalization、rewrite、multi-query、HyDE、路由和分解分别建模
  • 简单查询有直接检索基线
  • Multi-query 记录每条查询目标和边际贡献
  • HyDE 文本标记 synthetic 且不能进入引用
  • 分解使用 DAG、输入绑定和聚合缺失策略

权限与路由

  • Planner 只看到裁剪后的数据源目录
  • 执行前再次验证目标源属于允许集合
  • 主体可读集合与任务允许来源分开
  • 空结果不会移除租户、ACL、时间或状态过滤
  • 权限变更的一致性策略和 policy_version 明确

预算与执行

  • 所有步骤共享绝对 deadline、查询、候选、Token 和成本预算
  • 扇出前计算最坏上界
  • 预算使用原子预留与结算
  • 取消会传播到未完成步骤
  • 预算耗尽、依赖失败和无答案是不同终态

去重与归因

  • 文档和 Chunk 有跨查询稳定身份
  • 精确重复、内容重复和近重复版本分开处理
  • 合并保留全部 origin_step_ids 和原始排名
  • 每个被用候选可回到真实源、索引生成号和权限决策
  • 合成材料与真实证据严格隔离

评测与发布

  • 评测集覆盖否定、时间、同名实体、权限、多跳和无答案
  • 有变形测试与历史事故回放
  • 硬合同测试与语义质量测试分开报告
  • 论文数字没有外推成生产保证
  • 影子与灰度有独立预算、回滚键和延迟真值回填

十九、总结

RAG 查询规划不是在检索前“润色一下问题”。它是一层会改变搜索空间、权限边界、成本结构和证据路径的控制面。

一套可评测的实现应做到：

  1. 用 QueryEnvelope 保存原文、实体、时间、否定、答案合同和安全上下文。
  2. 明确区分表示规范化、单查询改写、多查询、HyDE、数据源路由和问题分解。
  3. 把模型输出当 CandidatePlan，再由确定性合同验证权限、预算、DAG 和合成材料边界。
  4. 用共享预算限制查询扇出、依赖深度、候选数、Token、成本和 deadline。
  5. 按稳定身份去重，同时保留每个候选的来源步骤和原始排名。
  6. 把 NO_ANSWER、NEEDS_CLARIFICATION、DENIED 和系统失败建成不同终态。
  7. 用约束保留、路由、依赖、边际证据、重复、预算和归因指标评价规划层，不重复用最终答案总分代替归因。
  8. 通过否定词删除、越权源、依赖环、错误 HyDE、重复饱和和预算爆炸等故障注入验证控制面。
  9. 用真实标注集、反事实和线上延迟真值评价语义质量，不声称 mock LLM 能证明模型可靠。

最终要证明的不是“Planner 总能生成一个合法 JSON”，而是：

它只在原问题、权限和预算允许的范围内扩展检索；每次扩展都能解释为何发生、带来了什么证据；条件不满足时能够明确停止。
