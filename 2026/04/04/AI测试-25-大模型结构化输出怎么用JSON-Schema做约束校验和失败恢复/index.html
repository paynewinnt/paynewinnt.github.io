AI测试-25-大模型结构化输出怎么用JSON Schema做约束校验和失败恢复

发表于 2026-04-04 分类于 AI测试 本文字数： 9.4k 阅读时长 ≈ 34 分钟

让大模型“只输出 JSON”，第一版通常会这样写：

顺利时，模型确实会返回：

接入生产链路以后，问题很快会从“有没有 JSON”扩展成另一组问题：

  • JSON 能解析，但缺少下游必填字段
  • 字段存在，但类型从数字变成字符串
  • 枚举值拼写正确，却不是当前业务状态机允许的值
  • 时间看起来像 ISO 8601，实际不存在或没有时区
  • Schema 校验全部通过，但退款金额超过可退余额
  • 模型安全拒答，返回的是提供商定义的 refusal，而不是业务 Schema
  • 输出因为 Token 上限被截断，前半段恰好像一个可解析对象
  • 一轮返回多个并行工具调用，应用只处理了第一个
  • 严格模式在某个提供商和模型上可用，迁移后却使用了不支持的 Schema 关键字
  • 校验失败后无条件重试，最终造成重复扣款、重复发信或成本放大

结构化输出的工程目标不是“看起来像 JSON”，而是建立一条分层验证和恢复链路：

这篇文章围绕一个关键判断展开：

语法有效 != Schema 有效 != 业务有效。

提供商的约束解码可以降低某些格式错误，但不能替代本地校验、业务校验、权限控制和失败恢复。

一、先给结论：把结构化输出当作不可信外部输入

即使输出来自启用了 strict 的模型接口，应用仍然应该把它放在外部输入边界处理。

原因有五个：

  1. strict 是具体提供商、接口、模型和 Schema 子集上的能力，不是 JSON Schema 标准的通用运行模式。
  2. 拒答、截断、内容过滤、网络错误和超时可能绕开正常结构化结果。
  3. Schema 描述结构约束，不知道订单余额、用户权限和当前数据库状态。
  4. 工具调用参数即使结构正确，也可能请求未授权或不可逆动作。
  5. 下游代码、SDK 和代理层可能在反序列化、精度、重复键或字符编码上产生新的差异。

因此，接收端至少保留下面九种互斥结果，而不是一个 valid: true/false：

不同结果对应不同恢复动作。把它们全部捕获成 parse failed，会让重试、告警和根因分析失去方向。

二、先拆清四个经常混用的层次

1. JSON 语法有效

输出能被 JSON 解析器接受。例如：

这里只证明括号、引号、转义和字面量符合解析器规则。不证明字段完整、类型正确或金额合理。

2. JSON Schema 有效

解析后的实例满足指定 dialect 的 Schema，例如 Draft 2020-12：

  • 根节点类型正确
  • 必填字段存在
  • 没有未声明字段
  • 字符串符合 pattern 或 format 的既定校验策略
  • 枚举、数组长度和数值范围符合约束

3. 提供商约束有效

提交给模型接口的 Schema 落在该提供商、接口和模型支持的子集中，响应也处于文档承诺的正常终态。

完整 JSON Schema Draft 2020-12 合法，不代表某个约束解码器接受它。反过来，提供商接受一个 Schema，也不代表它实现了 Draft 2020-12 的全部 vocabulary。

4. 业务有效

输出满足实时业务事实：

  • amount <= refundable_balance
  • 币种与订单一致
  • 当前操作者有权处理该租户
  • 状态迁移从 paid 到 refund_review 合法
  • 证据引用属于当前请求且没有过期
  • 幂等键没有执行过

这一层不能只靠模型和静态 Schema 判断。

三、JSON Schema 是 dialect，不是一个模糊的“JSON 规则”

Schema 文档应该显式声明 dialect：

不声明版本时，不同验证器可能按不同 draft 解释关键字。Draft 2020-12 对数组元组、动态引用、unevaluatedItems 和 format vocabulary 等内容有明确设计，不能把旧 draft 的用法直接混入。

生产契约至少记录：

  • Schema dialect URI
  • Schema 自身版本与内容摘要
  • 本地验证器名称和版本
  • 是否启用 format assertion
  • 提供商适配后的 Schema profile 与摘要
  • 业务规则版本

四、设计 Schema 前先定义输出状态机

以退款资格判断为例，先不要急着列字段。先定义允许结果：

再定义每个状态的最小证据：

状态 必须有 不应表达
approved 订单、币种、建议金额、规则证据 “可能”“不确定”
review 升级原因、缺失证据 自动执行批准

Schema 可以约束共同结构，跨字段和实时状态由业务验证器收口。不要为了把所有业务规则都塞进 JSON Schema，而构造一个提供商无法支持、维护者也难以理解的巨大条件表达式。

五、一个完整的 Draft 2020-12 Schema

下面的 Schema 用于应用本地验证。它不等于任何提供商约束解码器必然支持的输入。

这里有几个有意的选择。

1. 金额使用字符串

JSON number 在不同语言和序列化链中可能进入二进制浮点。财务金额更适合使用固定小数字符串，再在业务层解析成 Decimal。Schema 的 pattern 只控制表现形式，不负责币种小数位和余额比较。

2. 所有字段都 required，可空值显式使用 null

“字段缺失”和“字段存在但当前无值”是两种状态。显式 null 能让调用方稳定反序列化，也能避免模型随意省略字段。但这不是所有 API 的唯一正确设计；是否采用取决于兼容策略。

3. 根对象关闭 additionalProperties

模型多生成一个 approved_by 或 execute_now 不应被静默接收。对动作型输出，额外字段可能代表未建模意图。

4. 证据只传引用

输出保存 record_id，后端按当前租户重新读取可信事实。不要让模型生成整份“证据对象”后直接当成数据库事实。

七、枚举能限制拼写，不能代替状态机

枚举适合限制有限集合：

它能拒绝 approve、APPROVED 和 unknown_status，但不能判断当前订单是否允许从 shipped 进入 approved。

枚举设计需要处理三个演进问题：

  1. 新增枚举值对旧消费者可能是破坏性变化。
  2. 使用 OTHER 可以提高前向兼容，却可能掩盖真实未知状态。
  3. 把业务描述直接作为枚举会造成文本和机器状态耦合。

更稳的做法是使用稳定机器码，并把显示文案放在应用层。遇到未知枚举时进入显式人工升级或版本协商，不要自动映射成最接近的值。

八、联合类型最容易制造“看起来灵活”的歧义

联合可以用 anyOf、oneOf，也可以对简单类型使用数组：

三者语义不同：

  • anyOf：至少一个分支通过。
  • oneOf：恰好一个分支通过。
  • 类型数组：实例类型属于列出的类型之一。

oneOf 的分支如果重叠，实例可能同时匹配两个分支，反而失败。例如一个整数同时满足“number”和“integer”分支。测试中要准备每个分支的正例、负例和交叉样本。

九、format 默认不等于强校验

Draft 2020-12 将 format 拆分为 annotation 和 assertion vocabulary。验证器是否把 format: "date-time" 当成失败条件，取决于 dialect、实现和配置。

  • 2026-02-29T10:00:00Z：2026 不是闰年

  • 2026-04-04T10:00:00+08:00：合法偏移

即使 format 通过，业务仍要判断时间是否在允许窗口、是否晚于订单创建时间，以及未来时间是否合理。

十、不要忽略重复键和数字精度

RFC 8259 指出对象名称应唯一，但不同实现对重复键的可观察行为可能不同。安全边界上应使用能拒绝重复键的解析配置，否则日志、签名端和执行端可能看到不同含义。

数字也有类似问题：

进入只精确表示 IEEE 754 双精度整数范围的环境后，值可能失真。订单号、长 ID、金额和高精度小数适合使用字符串，并由业务类型解析。

十一、提供商约束解码只是第一道结构防线

约束解码通常在生成阶段限制下一 Token，使结果落入某个 Schema 描述的语言。它比“在 Prompt 里要求 JSON”更可靠，但工程边界必须写清。

1. OpenAI Structured Outputs 的适用范围

按 2026-07-26 检索的 OpenAI 官方指南，Structured Outputs 支持 JSON Schema 的一个子集，并区分结构化文本输出与 function calling。指南同时列出以下接口约束：

  • 根必须是 object，根级不能是 anyOf
  • 字段或函数参数需要全部列入 required，可用与 null 的联合表达可空
  • object 需要设置 additionalProperties: false
  • 部分组合关键字不受支持，特定模型类型还有额外限制
  • JSON mode 只保证 JSON 语法，不保证 Schema adherence
  • 安全拒答通过单独 refusal 信号表达，可能不符合业务 Schema
  • 输出达到 max_output_tokens 时可能以 incomplete 终态结束

这些是 OpenAI 对相应 API、支持模型和检索日文档的说明，不是 JSON Schema 2020-12 的通用要求。接入时应根据目标模型和 API 重新读取 supported schemas 页面，不能把文章里的列表长期固化成平台能力表。

2. Anthropic 工具调用的适用范围

按同一检索日期，Anthropic 官方工具文档使用 input_schema 描述客户端工具参数，并提供 strict: true 的严格工具使用能力。工具调用返回 tool_use 内容块，应用执行后以对应 tool_result 继续对话。

这描述的是 Claude 工具输入，不应直接等同于任意文本响应都受同一 Schema 约束。具体 Schema 子集、支持模型、工具选择与 strict 组合需要以目标接口文档为准。

3. 维护两份 Schema，而不是假装一份到处通用

推荐保留：

适配器可以从领域模型生成提供商 profile，但生成结果必须做快照、差异和兼容测试。提供商 Schema 负责提高生成成功率，领域 Schema 才是接收端最终结构合同。

十二、响应处理顺序不能从 json.loads 开始

正确顺序先看外层响应终态：

  1. HTTP、SDK 或流是否完整结束。
  2. 提供商是否返回 error、rate limit、content filter 或 refusal。
  3. 是否因输出 Token 上限、连接中断而 incomplete。
  4. 响应中有文本、单个工具调用还是多个工具调用。
  5. 只有正常结构化候选，才进入 JSON 解析和 Schema 校验。

如果先从返回对象里找一段文本执行 json.loads，拒答可能被误判为语法错误；截断可能触发盲目重试；包含多个工具调用时还可能只取到第一个参数块。

Schema 枚举越界 SCHEMA_ERROR 不做模糊映射
Schema 联合分支歧义 SCHEMA_ERROR 修复 Schema 设计
Schema format 失败 SCHEMA_ERROR 明确验证器配置后处理
业务 金额超余额 BUSINESS_ERROR 重新读取事实后最多重算一次
业务 跨租户证据 BUSINESS_ERROR/SECURITY 不重试，阻断并告警
工具 一轮多个并行调用 逐调用进入对应验证链 每个调用独立校验与执行决策
工具 call ID 重复或结果缺失 TOOL_PROTOCOL_ERROR 不猜测对应关系

测试报告要保存失败所在层、JSON Pointer 路径、Schema revision、提供商终态和重试决策。只保存异常字符串，无法统计哪一类契约最不稳定。

十六、拒答不是 Schema 失败

用户输入触发安全策略时，提供商可能返回显式拒答。这个结果通常不会符合业务定义的 RefundDecision，但它也不是模型“忘了输出 JSON”。

这会把一个稳定拒答变成重复请求，增加成本且不改变结果。

正确顺序先识别 refusal，再按产品策略：

  • 对终端用户展示安全说明
  • 对可能的误拒答进入人工复核
  • 保存安全类别和产物版本，不保存不必要的敏感全文
  • 不把 refusal 计入普通 JSON 语法失败率

业务层自己的“无法判断”也不应伪装成提供商拒答。前者可以用 decision=review 表达，后者来自外层响应协议。

十七、截断和流式输出要等完整终态再执行

流式结构化输出会持续产生片段。中间片段即使暂时能解析，也不应触发业务动作。

针对截断：

  1. 检查外层状态和 incomplete_reason。
  2. 不把部分对象送入业务层。
  3. 判断输出预算是否合理，Schema 是否过度冗长。
  4. 只读、无副作用任务可以提高预算后有限重试。
  5. 已经开始副作用的 Agent 必须先查询幂等结果，不能直接重放整轮。

十八、并行工具调用不能当成一个 JSON 对象

一个 assistant turn 可能包含多个工具调用块。每个块都有自己的 call ID、工具名和参数对象。

风险场景包括：

  • 第一个调用只读，第二个调用写入，代码只检查第一个
  • 两个调用使用同一幂等键
  • 一个调用创建资源，另一个依赖其 ID，却被并行执行
  • 一个参数合法，另一个跨租户，批处理仍整体放行
  • 返回工具结果时漏掉一个 call ID，下一轮上下文错位

Anthropic 官方文档在检索日说明，同一响应可包含多个 tool_use 块，执行顺序由应用决定；有依赖或副作用的工具不适合无条件并行。不同提供商的块结构和控制参数不同，适配器必须分别实现协议测试。

十九、失败恢复不是统一 retry(3)

重试策略应由错误类别、幂等性和事实新鲜度决定。

1. 配置错误

提供商拒绝 Schema、模型不支持 strict、关键字超出子集。这是确定性配置问题，同样请求重试三次没有价值。应阻断发布并修正 profile。

2. 瞬时传输错误

限流、连接重置和服务暂时不可用可以退避重试，但要设置总时间预算、抖动和熔断。对动作型任务，先用幂等键查询是否已经执行。

3. JSON 或 Schema 错误

非 strict 或降级模式下，可以把结构化、裁剪后的验证错误反馈给模型做一次修正：

不要把完整内部 Schema、堆栈和敏感实例原样拼回 Prompt。若第二次仍失败，进入降级或人工处理，而不是无限自我修复。

4. 业务错误

先判断事实是否可能变化。余额刚被其他请求更新时，可以重新读取可信状态并重新决策；跨租户、越权、非法状态迁移则应直接阻断和审计。

5. 拒答

拒答通常不靠原样重试恢复。需要修改请求范围、移除不必要敏感内容，或进入人工渠道。

6. 截断

可以提高输出预算、简化 Schema 描述或拆分任务，但必须使用原始输入和新的 attempt ID，不能把不完整 JSON 当作可信前缀继续补写后直接执行。

二十、重试必须有幂等、预算和证据

每一次 attempt 至少记录：

停止条件要预先定义：

  • 最大 attempt 数
  • 最大累计 Token、费用和墙钟时间
  • 不可重试错误集合
  • 副作用状态未知时的人工接管
  • 连续同类失败触发熔断

为了提高成功率而“重试到有一个通过”会造成选择偏差，也可能把真实兼容问题掩盖成偶发噪声。报告应保留每次物理 attempt，不只保存最后一次成功。

二十一、一个完整失败案例：Schema 全绿，退款金额仍然错误

1. 场景

系统根据订单、支付和客服证据生成退款建议。候选输出是：

JSON 可解析，Draft 2020-12 校验也通过。

2. 现象

执行器准备创建 299 元退款，但订单实时可退余额只有 99 元。PAY-OLD-9 来自同一用户的上一笔订单，不属于当前请求允许证据集。

3. 错误方向

如果只排查 Schema，会尝试给 amount 增加一个静态 maximum。但不同订单余额不同，写死上限既不能解决当前问题，也可能阻断合法高金额订单。

4. 证据排查

按照验证层追踪：

  1. 提供商响应 completed，无 refusal 和截断。
  2. JSON 严格解析通过，无重复键。
  3. Schema revision 正确，所有结构约束通过。
  4. 业务验证读取当前订单，发现 299.00 > 99.00。
  5. 证据绑定检查发现 PAY-OLD-9 不在当前请求允许 ID 集合。
  6. 工具执行日志显示动作尚未开始，幂等键未消费。

首错层明确落在 BUSINESS_ERROR，而不是模型传输或 Schema。

5. 根因

RAG 查询按用户 ID 检索支付记录，没有同时限定订单 ID；模型引用了格式完全正确、业务归属错误的记录。Schema 只能证明 record_id 是字符串，不能证明它属于当前订单。

6. 修复

  • 检索层增加租户和订单过滤，并记录召回证据 ID。
  • 输出只允许引用本轮上下文中下发的证据 ID。
  • 业务层重新查询余额、币种和订单状态，不信任模型复制的事实。
  • 执行器使用幂等键，并在落库前再次比较可退余额。
  • 新增跨订单、过期证据、并发退款和余额变化测试。
  • 将“Schema 通过但证据越界”单独计入安全和数据质量指标。

这个案例说明，结构化输出能把错误变得更容易定位，却不会自动让内容成为事实。

二十二、排查顺序：先找首个失效边界

线上出现“结构化输出失败”时，可以按以下顺序缩小范围：

  1. 对齐请求时间、request ID、attempt 和产物版本。
  2. 检查 HTTP/SDK/流终态，不先看拼接后的文本。
  3. 确认是否 refusal、content filter、rate limit 或 incomplete。
  4. 确认实际使用的 provider profile、strict 参数和模型 ID。
  5. 使用原始字节做严格 JSON 解析，检查 BOM、编码、重复键和尾随内容。
  6. 用记录的 dialect、Schema revision 和验证器配置重放。
  7. 根据 JSON Pointer 定位第一个 Schema 失败关键字。
  8. Schema 通过后，重放业务事实、权限、租户和状态机。
  9. 工具场景检查全部 call ID、参数、执行顺序、幂等与结果映射。
  10. 修复后同时补正常对照和历史失败样本。

不要先用正则提取大括号、删除 Markdown 或自动补字段。这些“修复”会改变证据，甚至把拒答和越权意图包装成一个可执行对象。原始输出必须不可变保存，任何修复结果使用新的 attempt 标识。

二十三、观测指标要按失败层分开

建议至少监控：

只看最终成功率会隐藏两个风险：

  • 首次失败率持续升高，只是被重试掩盖，成本和时延已经恶化。
  • 业务错误被人工修正后算成功，但上游检索或模型质量正在退化。

指标还要按模型、Schema revision、Prompt 指纹、业务域、语言和输入长度切片。平均数无法解释某个新枚举值只在旧移动端消费者上失败。

二十四、结果验收怎么写才不变成宣传数据

可以先用固定失败注入集建立工程验收表，而不是编造一个通用“准确率提升”：

验收项 目标
正常完成且业务有效 100% 进入 ACCEPTED
refusal 100% 进入 PROVIDER_REFUSAL，不触发 JSON 重试
截断 100% 在完整性层阻断，不执行部分对象
缺必填/额外字段/枚举越界 100% 给出 Schema 路径和关键字
超额、跨租户、非法状态 100% 在业务/安全层阻断
多工具调用 100% 逐调用校验并保持 call ID 映射
相同幂等键重放 0 次重复副作用

本文示例脚本的结果是七个 fixture 被稳定分成一个接受和六种预期失败路径。它证明分类器骨架可执行，不证明某个真实模型的业务准确率。真实收益需要在目标提供商、模型、数据和业务环境中另行评测。

二十五、常见的十二个错误

1. 把“请输出 JSON”当作结构约束

Prompt 指令不能替代解析器和 Schema。

2. 把 JSON mode 当成 Schema strict

语法保证与字段、类型、枚举保证是不同能力。

3. 把完整 Draft 2020-12 直接提交给所有提供商

约束解码通常只支持子集，且会随接口和模型变化。

4. 忘记 required

定义 properties 不会自动让字段必填。

5. 只在根关闭 additionalProperties

嵌套对象仍可能接收未声明字段。

6. 默认 format 会被强制验证

Draft、vocabulary 和验证器配置会影响结果。

7. 用浮点数处理金额和长 ID

跨语言链路可能出现精度和序列化差异。

8. 先解析文本，再看 refusal 和 incomplete

外层协议错误被错误归类成 JSON 失败。

9. 自动修补半截 JSON 后执行

补出来的结构不代表模型完成的意图。

10. Schema 通过就直接调用高风险工具

还缺租户、权限、状态、额度、幂等和审批检查。

11. 并行工具调用只处理第一个

未校验调用可能仍被执行，结果映射也会错位。

12. 所有失败统一重试三次

配置错误、拒答、安全错误和副作用未知状态需要不同策略。

二十六、什么时候使用约束输出，什么时候换一种设计

结构化输出适合：

  • 信息抽取、分类、路由和规则建议
  • 生成工具调用参数
  • 下游需要稳定机器接口
  • 输出字段和状态集合可以明确建模
  • 接收端能够执行本地与业务二次校验

不适合直接承担：

  • 最终权限判断
  • 高精度财务计算
  • 数据库事实查询
  • 无 Schema 上限的开放式长文
  • 不可逆动作的唯一审批依据

如果 Schema 为了容纳自然语言任务而出现几十层联合、动态字段和大量自由对象，可能说明任务边界没有拆清。可以把流程分成“模型提取候选事实 -> 确定性代码计算 -> 模型解释结果”，让每一层做擅长的工作。

二十七、上线检查表

Schema 设计

  • 是否显式声明 dialect、$id、版本和内容摘要
  • required、nullable 和字段缺失语义是否明确
  • 根及嵌套对象的 additionalProperties 策略是否明确
  • 枚举是否使用稳定机器码并有演进策略
  • 联合分支是否互斥、可测试且不依赖模糊匹配
  • format assertion 是否在验证器中显式配置
  • 金额、长 ID 和高精度值是否避免浮点歧义

提供商适配

  • 是否为每个提供商维护独立 Schema profile
  • strict、支持子集、模型和 API 范围是否按当前官方文档核对
  • Schema 注册错误是否在发布前合约测试中发现
  • refusal、content filter、incomplete 和 error 是否有独立分支
  • 文本结构化输出和工具参数是否没有混为同一协议

接收和校验

  • 是否先检查外层终态，再解析 JSON
  • 是否拒绝重复键、尾随内容和非对象根值
  • 是否使用记录版本的 Draft 2020-12 验证器
  • Schema 通过后是否执行跨字段、实时事实、租户和权限校验
  • 错误是否包含层级、JSON Pointer、关键字和规则 ID

工具和副作用

  • 多个工具调用是否全部遍历并分别校验
  • call ID、工具名、参数和结果是否一一对应
  • 有依赖或副作用的调用是否避免无条件并行
  • 执行前是否重新校验权限、状态、额度和审批
  • 是否使用幂等键并能查询未知执行状态

恢复和观测

  • 不同错误类别是否映射到不同恢复动作
  • 重试是否有次数、时间、Token 和费用预算
  • 原始响应是否不可变保留，修复尝试是否使用新 attempt
  • 首次接受率和重试后接受率是否分开统计
  • 安全与业务错误是否不会被自动放宽 Schema 掩盖
  • 无法安全恢复时是否有人工升级入口和完整证据

二十八、小结

大模型结构化输出要从“格式提示”升级成“分层契约”。完整方案至少做到：

  1. 区分 JSON 语法、JSON Schema、提供商约束和业务有效性。
  2. 明确 JSON Schema dialect、验证器配置、Schema revision 和 format 策略。
  3. 正确使用 required、additionalProperties、枚举、联合、格式和精度边界。
  4. 把提供商 strict 限定在具体接口、模型和支持子集，不写成行业标准。
  5. 先识别 refusal、截断和传输终态，再进入 JSON 解析。
  6. 即使约束解码成功，也在接收端运行完整 Schema 与业务二次校验。
  7. 对并行工具调用逐个校验、保留 ID 映射，并在执行前重查权限和状态。
  8. 按失败类别决定重试、降级、阻断和人工升级，使用幂等与预算控制副作用。
  9. 保存原始证据和每次 attempt，让失败可以重放而不是被最后一次成功覆盖。

最终可信的结论不是：

模型已经返回 JSON。

而是：

响应完整且协议终态正常；实例通过明确版本的 Schema；内容与当前业务事实、权限和状态一致；任何失败都被正确分类，并能在不扩大副作用的前提下恢复。

只有到这一层，JSON 才从输出样式变成可以进入生产系统的接口契约。
