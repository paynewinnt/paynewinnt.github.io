AI测试-37-知识库摄取流水线怎么处理解析清洗去重权限和数据血缘

发表于 2026-04-30 分类于 AI测试 本文字数： 15k 阅读时长 ≈ 56 分钟

很多 RAG 问题在用户发起查询之前就已经发生了。

一份政策 PDF 上传成功，解析器返回 200，向量索引也显示新增了若干 Chunk，但真实链路可能同时存在：

  • 文件扩展名与真实 MIME 不一致，选错解析器
  • UTF-8、GB18030 或 Windows-1252 被误判，关键字符变成替换符
  • 扫描页没有触发 OCR，附件后半段完全缺失
  • 双栏正文阅读顺序错乱，表格行列被压平成无意义文本
  • 页眉清理规则误删否定词或章节标题
  • 新版本因“相似度 98%”被当成旧版本副本
  • Chunk ID 每次重跑都变化，引用、反馈和删除无法关联
  • 上游 ACL 获取失败后默认公开，跨租户内容进入共享索引
  • 解析器升级后结果改变，却没有保存版本和血缘
  • 质量门禁只检查“正文非空”，部分解析也被标成成功

这类系统的检索接口可以完全健康，最终答案也可能引用一个真实存在的 Chunk，但 Chunk 本身已经缺页、错序、过期或越权。Schema 合法、向量相似、模型置信度高、索引写入成功和 HTTP 200，都不能证明摄取结果具有业务正确性。

因此，知识库摄取的工程目标不是“把文件转成文本并写进向量库”，而是：

从不可变源字节出发，在受限执行环境中完成可验证的类型识别、解析、OCR、结构保留、规范化、身份生成、版本与重复治理、ACL 绑定和原子发布，并让每个可检索 Chunk 都能追溯到源版本、处理活动、软件版本和授权快照。

本文聚焦摄取控制面和数据面，不重复 AI测试-18 的通用 RAG 召回、生成忠实度和引用评测。资料核对截止 2026-07-26；涉及 Apache Tika 时限定到当时的稳定版 3.3.2，Tika 4.0.0-beta-1 只视为测试中的预发布分支；Tesseract 能力限定到官方 5.x 用户手册；OpenLineage 对象模型限定到规范页显示的 1.52.0。文中未注明外部来源的阈值与统计结果均为构造数据。

一、工程定义与边界：摄取不是一次 ETL 函数调用

1. 被测系统

本文把摄取流水线定义为：

一条摄取请求至少产生三个不同对象：

  • Run：某次执行，有唯一运行 ID、开始结束时间和状态事件。
  • DocumentVersion：某个业务文档的一次不可变源版本。
  • IndexGeneration：一批经过门禁、准备对查询可见的索引快照。

Run 重试不应创造新的业务文档版本；相同源版本用新解析器重放，也不应覆盖旧解析产物。DocumentVersion 与 Run 混在一个 ID 里，会让重试、回滚、删除和血缘全部失真。

2. 摄取层负责什么

摄取层负责：

  1. 保存可重放的源字节、源元数据和来源授权快照。
  2. 在资源和权限受限的环境中识别、解析和提取结构。
  3. 记录内容缺失、乱码、OCR、表格和解析警告。
  4. 生成稳定文档、版本和 Chunk 身份。
  5. 区分精确重复、规范内容重复、近重复和业务版本关系。
  6. 将有效 ACL 绑定到发布单元，默认拒绝不完整权限。
  7. 通过质量门禁后原子发布，并保留回滚点。
  8. 记录从源到索引的可查询血缘。

3. 摄取层不负责证明什么

即使所有门禁通过，也没有证明：

  • 文档作者陈述的事实真实
  • 文档已获得业务或法律批准
  • 某个 Chunk 对具体查询相关
  • Embedding 表达了精确业务语义
  • 生成模型会正确使用内容
  • ACL 上游系统本身没有配置错误
  • 文档中不存在未知恶意载荷

质量门禁证明的是“满足当前明确合同”，不是“内容绝对正确和安全”。尤其是恶意代码扫描阴性，只表示当前扫描器和规则未检出，不能成为无风险证明。

4. 信任边界

以下全部视为不可信输入：

  • 文件名、扩展名、上传者声明的 Content-Type
  • 文档内嵌元数据、作者、创建时间和页数
  • 压缩包目录、相对路径和嵌套对象
  • PDF、Office、图片、字体、宏、脚本和外部链接
  • OCR 识别文本
  • 连接器返回的内容与 ACL
  • 解析器标准输出、警告和退出码

解析器也是攻击面。它处理高度复杂的二进制格式，可能耗尽 CPU、内存、磁盘和进程数，也可能触发依赖漏洞。因此解析任务要与在线检索、控制面数据库和凭据环境隔离。

二、完整架构：从落地区到原子发布

1. Source Connector

连接器从文件系统、对象存储、文档管理系统、Wiki、代码仓库或数据库读取内容。每次拉取要保存：

  • connector_id 与版本
  • 上游原生对象 ID
  • 上游版本 token、ETag 或修订号
  • 读取时间和源 URI
  • 原始声明 MIME、文件名和大小
  • 原始 ACL 或权限引用
  • 删除、移动、重命名事件

不要用 URL 作为唯一文档身份。重命名会改变 URL，而同一路径也可能被另一个对象复用。优先使用上游稳定原生 ID；没有稳定 ID 时，需要明确设计身份迁移和冲突处理。

2. Immutable Landing Zone

源字节先写入不可变落地区，再进入解析。落地区对象由租户命名空间、源对象 ID、源版本和原始 SHA-256 关联。写入后验证长度和摘要，禁止解析器直接覆盖源对象。

保存源字节的价值包括：

  • 解析器升级后可重放
  • 事故中可以核对是否源文件已损坏
  • 可以比较不同解析器输出
  • 可以证明某个索引版本来自哪组输入
  • 上游删除后按保留策略执行撤回或审计

保留源字节必须遵守数据最小化、加密、访问控制和保留期限。可重放不是无限期保存所有敏感文件的理由。

3. Admission 与恶意内容扫描

在解析前检查：

  • 压缩前大小、声明大小与实际大小
  • 允许 MIME 与格式集合
  • 最大文件、页、对象和附件数量
  • 最大嵌套层级、解压后总量和压缩比
  • 加密或密码保护状态
  • 恶意代码扫描结果与签名版本
  • 是否包含宏、脚本、外部引用或嵌入对象

超过限制进入 SECURITY_QUARANTINE 或明确拒绝。不能让异常文件在主 worker 上“试试看能不能解析”。

4. Detector

Detector 综合：

  • 上游 Content-Type
  • 文件名扩展
  • 魔数或字节特征
  • 容器内部结构
  • 字符编码信号

RFC 6838 定义了用于 HTTP、MIME 等协议的媒体类型规范与注册程序。媒体类型是内容标签，不是对字节真实性的证明。工程上应保存每种信号及其冲突，而不是只保留最终一个字符串。

Apache Tika 官方将其描述为可通过统一接口检测并提取一千多种文件类型的元数据和文本。截止 2026-07-26，官网列出的稳定发布是 3.3.2；4.0.0-beta-1 是 beta，并存在默认内容处理器等变化。生产验证必须写明具体 Tika、解析模块和配置版本，不能只写“使用 Tika”。

6. Parse、OCR 与结构提取

解析输出不应只有纯文本。至少保留：

  • 页、段落、标题、列表和阅读顺序
  • 表格、行、列、合并单元格和表头关系
  • 图片、图注、脚注、页眉页脚和附件引用
  • 字符或块的页面坐标
  • 解析警告、缺失字体、损坏对象和跳过原因
  • 原始页数、成功页数与失败页数

OCR 应按页或区域决策，而不是“整个文档有文本就不 OCR”。混合 PDF 常常前半是数字文本，后半是扫描附件。Tesseract 官方 5.x 手册说明它是开源 OCR 引擎，可通过命令行或 API 从图片提取印刷文本，并支持多种语言；这没有保证页面布局、表格关系或业务字段自动正确恢复。

7. Canonical Normalizer

Normalizer 把不同解析器产物映射到内部规范内容模型，执行受控 Unicode、换行、空白和结构规则。它不能覆盖原始解析产物。每条规则有版本、适用 MIME 和可逆证据。

8. Identity、Version 与 Duplicate Analyzer

这一层计算原始内容摘要、规范内容摘要、业务文档身份、版本身份、Chunk 身份和近重复候选簇。它只提出关系，不可仅凭相似度自动决定两个版本业务等价。

9. ACL Resolver

ACL Resolver 读取源权限快照、展开用户组或策略引用、应用租户边界和 deny 规则，生成可验证的有效 ACL。ACL 不完整、过期或解析失败时默认隔离，不发布成公共内容。

10. Staging、Quality Gates 与 Publisher

所有 Chunk、ACL、Embedding、关键词索引项和血缘先写 staging generation。门禁通过后，Publisher 核对 manifest，再以原子别名或生成号切换使其可见。中途失败继续服务旧 generation，不能让半批数据对查询可见。

三、数据模型：不要把所有对象都叫 document

1. SourceObject

SourceObject 描述一次读取到的不可变源版本。源 URI 是属性，不是主键。

加入租户是为了防止不同租户恰好使用相同上游 ID 时身份碰撞。加入原始摘要可以发现上游重复使用版本 token 却改变内容的异常。

3. ParsedArtifact

解析器返回成功不代表所有页成功。页数、对象数、警告和覆盖率是门禁输入。

1. 扩展名只是一条弱信号

2. MIME 冲突策略

策略可以按风险分级：

  • 扩展名与字节一致：进入对应沙箱解析器。
  • 声明 MIME 与字节不一致，但真实格式在允许集合：记录冲突并按真实格式处理。
  • 容器与内部对象冲突：展开前执行更严格配额。
  • 检测不确定或 polyglot：隔离人工分析。
  • 可执行、脚本或未知格式：拒绝或进入专门分析环境。

不要“先按扩展名解析，失败再遍历所有解析器”。这既放大攻击面，也让资源预算不可控。

3. 字符编码

文本输入应按顺序考虑：

  • BOM
  • 协议或格式内明确编码声明
  • 受支持编码的严格解码
  • 检测器候选与可解释分数
  • 替换字符和非法序列计数

WHATWG Encoding Standard 定义了 Web 平台的编码、解码和错误处理算法；具体企业摄取系统可以支持更多业务编码，但必须固定实现和失败策略。不要默认 errors="replace" 后继续发布，因为金额符号、姓名和否定字符可能已损坏。

建议保留：

替换字符比例很低也不保证无害。一个唯一产品编号中的一个字符损坏，业务影响可能高于正文中一百个装饰符号。

4. Unicode 规范化

Unicode Standard Annex #15 定义 NFC、NFD、NFKC、NFKD。选择哪种形式是产品决策：

  • NFC 通常保留兼容字符差异，适合一般规范文本。
  • NFKC 会做兼容等价折叠，利于某些搜索一致性，却可能改变代码、单位、数学符号或标识符表示。

规范化前后都应可追踪。代码块、哈希、序列号和法律标识可能需要不同策略，不能整篇无条件 NFKC 后丢弃原文。

五、解析、OCR 和表格：提取到文字不等于提取了意义

1. 按页判断 OCR

文档级规则“只要有文本层就不 OCR”会漏掉混合扫描页。每页至少评估：

  • 文本字符数和覆盖面积
  • 图片面积占比
  • 是否只有不可见或重复文本层
  • 字体、旋转和页面方向
  • 是否存在大表格或表单
  • 解析警告

OCR 结果与原生文本层要分别保存，可按区域对齐，而不是直接覆盖。若两者冲突，质量报告应暴露冲突并按文档类型选择策略。

2. OCR 质量不能只看引擎置信度

需要领域标注集计算字符错误率、词错误率和关键字段准确率，并按语言、字体、分辨率、旋转、印章、背景和表格切片。引擎自报 confidence 没有经过当前语料校准时，不能作为发布真值。

对金额、日期、版本号和否定词可设置高风险字段规则。例如 O 与 0、1 与 l、中文“一”与短横线的混淆，可能改变合同编号和期限。

3. 阅读顺序

双栏 PDF 常见错误是把左栏第一行、右栏第一行、左栏第二行交错拼接。检测方法包括：

  • 坐标投影与列聚类
  • 标题和段落连续性检查
  • 句子异常截断率
  • 与页面渲染的抽样对照
  • 在黄金页面上比较块顺序

纯文本看起来“每个字都在”，仍可能无法还原句义。解析覆盖率必须包含顺序和结构，不只包含字符数量。

4. 表格

表格中的值依赖表头、行标签、合并单元格和脚注。例如：

若压平成 地区 企业版 个人版 华东 45 天 30 天 华南 不适用 30 天，模型可能尚能猜出简单关系；遇到跨页表头、嵌套表头和脚注条件就容易错配。

建议同时保存：

  • 结构化单元格图
  • Markdown 或 HTML 文本投影
  • 表格前后解释段落
  • 页面截图或坐标引用
  • 跨页表头继承关系

表格评测要测行列关系和关键单元格，不只测文本 token 覆盖。

5. 图片、公式和图表

若图片本身承载业务信息，单纯 OCR 可能不足。图表需要坐标轴、图例和数据点；公式需要保留结构；流程图需要节点与边。系统无法可靠提取时应标为 UNSUPPORTED_CONTENT_REGION，而不是静默忽略后仍把文档标记为完整。

六、规范化和清洗：保留语义，再减少噪声

1. 原始层、解析层和规范层都要保留

推荐三层：

检索投影可以去掉页面坐标和部分装饰，但引用与审计仍能回到 canonical block 和原始页面。若只保存最终纯文本，任何清洗误删都无法重算或解释。

2. 页眉页脚去除

可基于跨页重复位置和文本模式识别，但要考虑：

  • 首页标题与后续页眉可能相同
  • 章节标题可能在每页重复，却仍是 Chunk 上下文
  • 页脚可能包含版本、密级或有效期
  • “仅供草案评审”看似重复噪声，实际是关键状态

因此删除规则应产出 removed_blocks，保留原因、规则版本和原坐标。高风险元数据可以从正文移到结构字段，而不是丢弃。

3. 空白与断词

PDF 抽取常产生行尾断词、软连字符和字符间空格。修复要按语言和块类型：英文 refund-\npolicy 可能需要合并，代码中的连字符不能删，中文逐字空格可以折叠，但表格列间空格可能是边界。

不要用一条全局正则把所有空白变成一个空格。结构先于字符串清洗。

4. 模板和导航噪声

HTML 导航、Cookie 文案、侧栏和相关链接可以去除，但规则要基于 DOM 区域或模板指纹，而不是关键词。正文真的讨论“Cookie 设置”时，关键词删除会破坏内容。

5. 敏感数据处理

敏感数据策略至少区分：

  • 不允许摄取：在落地区门禁后拒绝并按策略销毁。
  • 允许保存但限制访问：加密并绑定严格 ACL。
  • 允许检索脱敏版本：保存受控原文与脱敏派生物的血缘。
  • 仅允许特定字段：结构化抽取并丢弃其余内容。

脱敏不是简单正则替换。姓名、账号、地址、健康信息和自由文本需要不同检测与人工复核。NIST SP 800-122 提供保护个人可识别信息保密性的指导，但具体识别范围仍取决于适用法律、组织政策和业务上下文。

七、稳定身份：可重放、可删除、可引用的基础

1. 为什么随机 UUID 不够

每次摄取给 Document 和 Chunk 新 UUID，写入很方便，却会导致：

  • 重放产生重复索引项
  • 用户反馈无法关联新版本
  • 删除事件不知道应撤回哪些 Chunk
  • 引用 URL 在重建后失效
  • 无法比较 parser 升级前后差异
  • 缓存持续命中旧身份

运行 ID 可以随机，内容身份应可重算。

2. 摘要的角色

FIPS 180-4 定义 SHA-224、SHA-256、SHA-384、SHA-512 等安全散列算法。本文示例使用 SHA-256 生成内容指纹和稳定测试 ID。摘要用于完整性、相等性和寻址，不证明来源可信；攻击者提供的恶意文件也能拥有合法 SHA-256。

3. 四种身份不要混用

它们回答不同问题。源对象相同但内容不同是新版本；原始字节不同但规范内容相同可能只是序列化变化；规范内容相近可能是重要修订。

4. 稳定性范围要写清

Chunk ID 可以承诺：

  • 同一源版本、同一 canonicalizer 和 chunker 配置重放稳定。
  • parser 或规则版本改变时，生成新的派生产物和 manifest。
  • 跨文档版本通过 lineage 关联，不承诺 ordinal 永远不变。

如果团队要求跨小修订保持引用 ID，需要额外做结构锚点匹配和一对一映射，并处理拆分、合并和移动。不能假设内容相似就能唯一对应。

八、精确重复、近重复和版本关系

1. 原始字节精确重复

raw_sha256 相同表示字节相同。可以复用不可变 blob 存储，但不能自动复用 ACL、租户和生命周期。

2. 规范内容精确重复

不同 PDF 元数据或压缩方式可能解析出相同 canonical content。可以复用部分派生计算，但仍要保留各自 SourceObject、DocumentVersion 和权限关系。

3. 近重复

近重复可使用字符或词 shingle、MinHash、SimHash 或领域结构特征产生候选簇。相似度阈值必须按文档类型校准。政策文档 99% 相同的 1% 可能正包含新金额、否定词和有效期。

4. 版本与重复是两个轴

同一 Document 的新 Version 可能内容变化很大；不同 Document 也可能内容完全相同。版本由来源身份和业务生命周期定义，重复由内容关系定义。把两个轴压成一个 is_duplicate 布尔值，会错误删除合法版本或保留无意义镜像。

5. 删除和撤回

上游删除事件要生成 tombstone：

  • 标明删除对象和观察时间
  • 停止新查询返回对应版本
  • 使缓存失效
  • 从在线 generation 撤回 Chunk
  • 保留满足审计要求的最小血缘
  • 按保留策略清理源字节与派生物

“不再抓取”不会自动删除旧向量。删除也要经过可验证发布事务。

九、ACL、租户和索引隔离

1. ACL 不是查询后的装饰过滤器

若无权 Chunk 已进入模型上下文，生成后再删引用已经太晚。权限至少在三处执行：

  1. 摄取发布：Chunk 必须带有效 ACL。
  2. 检索候选：按当前主体过滤。
  3. 上下文拼装：再次验证，防止缓存或适配器错误。

多层检查减少单点失效，但都必须使用一致的租户和策略语义。

2. 默认拒绝

以下情况都不应默认公开：

  • ACL API 超时
  • 组展开不完整
  • 未知主体类型
  • 父目录策略缺失
  • deny 规则解析失败
  • 策略版本不兼容
  • 文档移动期间权限状态不确定

正确动作是 ACL_QUARANTINE 或保持旧已验证版本，等待权限恢复后重放。

3. Allow 与 deny

若系统支持显式 deny，求值顺序必须固定。一个常见模型：租户先匹配，命中 deny 立即拒绝，否则至少命中一个 allow 才允许。嵌套组、有效期和资源继承要有深度限制与循环检查。

4. 相同内容跨租户

两个租户上传相同公开手册，可以在底层 blob 层做加密且受控的存储去重，但 Document、Version、ACL、索引身份和审计仍应租户隔离。不要因为内容 hash 相同，就把租户 A 的检索缓存直接返回给租户 B。

5. Embedding 也可能泄漏

向量不是脱敏文本。攻击、日志、近邻查询或错误工具可能泄漏信息。Embedding 存储、备份、导出和删除应继承内容安全等级；不能把“不可读的浮点数组”视为公开数据。

6. 权限变更

内容没变但 ACL 变了，也应生成新的安全派生状态和发布 generation。content_version 与 acl_version 分开，这样可以只重建过滤元数据，又不把旧权限缓存继续使用。

  • 事件 Schema 和生产者版本
  • 幂等事件 ID
  • Run 内状态单调约束
  • 输入输出摘要核对
  • 时钟与时间语义
  • 权限和敏感字段最小化
  • 事件存储完整性与保留策略

有 lineage 字段、PROV JSON-LD 或 OpenLineage 事件，不等于处理真的发生。发布门禁应将 manifest 与可查询血缘做一致性检查。

十一、质量门禁、隔离区和重放

1. G1 接收与安全门禁

检查源字节摘要、大小、解包预算、嵌套深度、恶意代码信号、加密状态和沙箱退出原因。任何资源上限触发都保存具体限制与消费量，不能只记 parser failed。

2. G2 格式与解析门禁

检查 MIME 信号一致性、编码、页数、附件、解析警告、OCR 决策和解析覆盖。对 86 页文档只解析 70 页，即使正文非空也不能标成完整成功。

3. G3 内容与结构门禁

检查乱码、空块、阅读顺序、标题层级、表格结构、重复页眉、关键字段和内容区域支持率。阈值按文档类型设定：代码文档、合同、幻灯片和扫描表单不能共享一个“平均每页字符数”。

4. G4 身份与重复门禁

检查稳定 ID 可重算、同源版本 token 冲突、摘要碰撞处理、版本序列、近重复决策和 Chunk 映射。相似版本必须保留差异证据。

5. G5 ACL 与租户门禁

检查租户、允许主体、deny、来源快照、策略版本、有效期和每个 Chunk 的绑定。任何未绑定 Chunk 都使 manifest 失败，不能在发布后“异步补 ACL”。

6. G6 发布完整性门禁

核对预期与实际：

只有全部一致才切换 generation。切换操作需要幂等，同一 manifest 重试不会生成两份在线数据。

7. 隔离区

隔离记录包括：

  • 不可变输入引用
  • 失败阶段和机器分类
  • 检测、解析、资源和安全证据
  • pipeline、parser、policy 版本
  • 是否含敏感内容及访问范围
  • 处置负责人、状态和保留期限

隔离区不是垃圾桶。它需要容量、告警、SLA、访问审计和自动过期；否则失败文档永久滞留，知识库新鲜度逐渐下降。

8. 重放

重放必须从不可变输入开始，创建新 run_id，固定新 pipeline 配置，保留 replay_of_run_id 和修复原因。不要从上一次残缺的“清洗文本”继续，因为无法知道缺失发生在哪一步。

重放前后对比：

  • 页面和块覆盖
  • canonical hash
  • Chunk 一对一、拆分、合并和删除映射
  • ACL 变化
  • 索引候选和引用影响
  • 资源与延迟

十二、解析器沙箱和恶意文档

1. 资源消耗攻击

需要测试：

  • 极高压缩比和递归压缩包
  • 海量小文件、字体、图片或对象
  • 超大画布、超高 DPI 和超多页
  • 无限或极深 XML 实体展开
  • 特制 PDF 对象图和交叉引用
  • OCR 极端噪声导致超长运行

每类限制要在解析前和运行时共同执行。只设置墙钟超时可能让 worker 在超时前耗尽共享内存或磁盘。

2. 路径和文件系统

归档解包要拒绝绝对路径、.. 跳转、符号链接逃逸和设备文件。输出目录每任务独立，文件名不直接作为宿主路径。即使文件最终不发布，也不能允许它覆盖配置或其他任务产物。

3. 外部访问

文档可包含外部图片、模板、字体和链接。解析 worker 默认禁网，避免 SSRF、数据外发和不稳定依赖。确需拉取资源时，使用独立、允许清单化的抓取服务，固定大小和 MIME，并把外部对象作为新的 SourceEntity 进入血缘。

4. 宏、脚本和主动内容

摄取通常只需静态提取，不应执行 Office 宏、PDF JavaScript、嵌入程序或 HTML 脚本。解析器配置和依赖升级需要安全回归，未知主动内容进入隔离。

十四、自动化测试与失败注入

1. 格式与编码夹具

为每个支持格式建立最小、复杂、损坏和恶意四类夹具：

  • 正常文本、错误 BOM、非法 UTF-8、混合换行
  • 数字 PDF、扫描 PDF、混合 PDF、加密 PDF、截断 PDF
  • 单栏、双栏、旋转页、跨页表格、合并单元格
  • Office 宏、嵌入对象、外链模板
  • ZIP 嵌套、路径逃逸、压缩比边界

夹具保存预期 MIME、页数、块、关键字段、警告和终态。

2. Golden Artifact

对高风险代表文档保存人工确认的 canonical 结构和渲染截图。Parser 升级时比较：

  • 新增、删除和移动块
  • 文本差异
  • 表格关系差异
  • OCR 差异
  • Chunk 边界和 ID 差异
  • 质量指标与资源变化

不要只比较全文 hash；任何合理 parser 升级都会改变格式细节，需要语义化差异报告。

3. 属性测试

可以验证：

  • 相同输入和版本配置重放生成相同 DocumentVersion/Chunk ID
  • Normalizer 幂等
  • 每个 published Chunk 恰有一个有效 ACLBinding
  • 任意 Chunk 可沿 lineage 回到一个 SourceBlob
  • manifest 数量等于 staging 实际数量
  • deny 主体永远不能因 allow 组而通过
  • 跨租户相同源 ID 产生不同 Document ID

4. 故障注入点

注入：

  • 连接器读到一半断开
  • blob 写入后摘要不一致
  • Detector 超时或 MIME 冲突
  • Parser crash、OOM、超时或输出超限
  • OCR 服务部分页失败
  • Normalizer 规则异常删除全部内容
  • Chunker 在中间崩溃
  • ACL API 超时、组图有环、策略版本未知
  • Embedding 批次部分成功
  • lineage 事件发送失败或重复
  • alias 切换前后进程崩溃

期望断言不是“最终重试成功”这么简单，还包括没有半成品在线可见、旧 generation 仍可服务、预算被释放、隔离证据完整以及重放不会重复发布。

5. 组合故障

需要组合：

  • 混合 PDF 缺页 + OCR 超时
  • 近重复新版本 + ACL 变严
  • Parser 升级 + Chunk ID 漂移 + 旧缓存
  • 连接器重复事件 + Publisher 重试
  • 上游删除 + lineage 服务不可用
  • MIME 欺骗 + 沙箱资源耗尽

组合测试验证状态机和事务边界，不让一个局部成功覆盖另一个严重失败。

1. 业务现象

新旧正文大部分相同，近重复分数为 0.982。事故版本配置把 score >= 0.98 直接标为 exact duplicate，并复用 rev-18 的 Chunk 清单。这个规则忽略：

  • 源版本 token 不同
  • 新版页数增加 16
  • 新 ACL 快照不同
  • 差异页恰好未被解析

6. ACL 为什么也回退到旧值

ACL Resolver 获取 acl-901 时第一次超时。为提高吞吐，代码按 document_id 查最近一次已发布 ACL，拿到 rev-18 的“全体客服”，然后继续发布。系统没有标记 fallback，也没有设置有效期。

内容复用与 ACL 复用被放在同一个“duplicate optimization”分支中，导致新版本即使内容相同，也继承旧权限。第三根因是ACL fail-open 和生命周期耦合错误。

十七、发布、回滚和重建

1. Generation 发布

每次发布生成不可变 generation：

在线 alias 从 441 原子切到 442。切换前验证文档、Chunk、ACL、Embedding、词法索引和血缘。切换后运行只读烟雾查询和权限探针；失败立即切回 441。

2. 增量发布与全量重建

增量发布适合小变更，但容易积累孤儿 Chunk、旧 ACL 和删除遗漏。定期全量重建可以核对源清单与在线状态。两者都应产出相同 manifest 语义，并用差异工具解释偏差。

3. Parser 升级

Tika、PDF 库、OCR 模型或表格解析器升级属于数据变更，不只是依赖补丁。流程：

  1. 安全公告和兼容性评审。
  2. 黄金语料和恶意夹具回归。
  3. 双跑旧新解析器，生成结构差异。
  4. 影子索引比较检索和引用。
  5. 按 MIME、租户和风险灰度。
  6. 保留旧 ParsedArtifact 和 generation 回滚。

4. Embedding 升级

Embedding 版本属于派生产物版本。可以复用 canonical Chunk，但不能覆盖旧向量后继续用旧缓存。manifest 记录模型与参数，回滚时索引和查询编码器必须成对切换。

5. 删除保证

删除需要覆盖：

  • 在线向量和词法索引
  • 缓存与预计算结果
  • staging 与失败批次
  • 允许删除的源和派生对象
  • 备份与保留例外
  • 血缘中的最小审计记录

对用户承诺删除前，先定义各层完成时间和不可删除的合规依据。

十八、常见误区

1. 解析器成功就是文档成功

进程成功可能伴随缺页、警告、空表格和错误顺序。必须看覆盖与结构。

2. 文件扩展名决定解析器

扩展名和声明 MIME 都可错误或恶意，需要字节与容器检测。

3. OCR 只在整篇没有文本时触发

混合 PDF 会漏掉扫描附件。应按页或区域判断。

4. 全文变成纯文本后再清洗

结构一旦丢失，无法可靠恢复表格、列表、标题和引用坐标。

5. NFKC 对所有内容都安全

兼容折叠可能改变代码、单位和标识符。规范策略要按块类型。

6. SHA-256 相同就能共享 ACL

内容相同不代表租户、主体、生命周期或授权相同。

7. 相似度高就自动覆盖旧版本

关键业务变化通常只占很少文本。近重复是关系，不是等价证明。

8. ACL 可以索引后异步补

无 ACL Chunk 一旦在线就可能泄漏。权限是发布门禁。

9. 向量无法反推出原文，所以不敏感

Embedding 仍继承内容安全等级和删除义务。

10. 有血缘 JSON 就可追溯

事件可能缺失、伪造或与 manifest 不一致。血缘也要校验。

11. 隔离后人工改一段文本再重新入库

这会丢失修复来源。应固定修复配置并从不可变源重放；人工修正文档则创建新的受控 SourceVersion。

12. Mock parser 通过就能上线真实格式

Mock 只能验证状态机和适配器。真实解析器的资源、安全和语义行为需要真实夹具。

十九、上线检查表

源与身份

  • 连接器保存稳定原生 ID、源版本、URI、读取时间和删除事件
  • 源字节先进入不可变落地区并核对大小与 SHA-256
  • Document、DocumentVersion、Run、Chunk 和 IndexGeneration 身份分开
  • 相同输入与固定配置重放 ID 稳定
  • 跨租户相同源 ID 不会碰撞

MIME、编码与解析

  • 扩展名、声明 MIME、字节特征和容器结果分别记录
  • MIME 冲突、polyglot 和未知格式有明确策略
  • 编码严格解码，非法序列和替换字符可观测
  • Parser、模块、配置、镜像和依赖版本固定
  • 页数、块数、警告和失败区域进入门禁

OCR 与结构

  • OCR 按页或区域触发，混合 PDF 有回归样本
  • OCR 语言模型与版本记录
  • 双栏、旋转、跨页表格、合并单元格和脚注有黄金夹具
  • 表格保留行列与表头关系
  • 不支持区域会明确标记，不静默丢弃

清洗与规范化

  • 原始、parser-native、canonical 和 retrieval projection 分层保存
  • Unicode 形式及其适用块类型明确
  • 页眉页脚删除有证据和可回溯规则
  • 代码、序列号、金额、日期与否定词有保护测试
  • Normalizer 幂等且版本化

去重与版本

  • 原始精确重复、规范精确重复、近重复和业务版本分开
  • 近重复不会仅凭阈值自动覆盖高风险版本
  • 差异区域、决策者和规则版本可追踪
  • 插入、拆分、合并和移动 Chunk 有跨版本映射
  • 删除和撤回会清理在线索引与缓存

ACL、租户与敏感数据

  • ACL 缺失、超时或未知时默认隔离
  • allow、deny、组继承、有效期和租户边界有矩阵测试
  • 每个 published Chunk 有一个有效 ACLBinding
  • 内容版本与 ACL 版本分离
  • 原文、脱敏派生物和 Embedding 使用匹配的安全等级

沙箱与恶意文档

  • Parser 禁网、非特权、只读输入且任务环境隔离
  • CPU、内存、磁盘、进程、文件、输出和墙钟均有限制
  • 归档路径逃逸、递归解包、超高压缩比和海量对象有测试
  • 宏、脚本和外部资源默认不执行
  • Parser crash、OOM、超时和安全拒绝分别分类

血缘、门禁与发布

  • 每个 Chunk 可回到 SourceBlob、DocumentVersion、Run 和处理版本
  • W3C PROV/OpenLineage 映射与内部 Schema 版本固定
  • 血缘事件幂等、鉴权并与 manifest 对账
  • 所有产物先写 staging generation
  • manifest 全量一致后才原子切换，旧 generation 可回滚

隔离与重放

  • 隔离保存输入引用、失败证据、版本、负责人和期限
  • 隔离队列有容量、告警和处理 SLA
  • 重放创建新 Run，不覆盖旧证据
  • 重放从不可变源开始并固定修复配置
  • Parser 升级有双跑、差异、影子、灰度和回滚

二十、总结

知识库摄取是 RAG 的数据供应链。它决定模型最终看到的内容是否完整、结构是否正确、身份是否稳定、版本是否新鲜、权限是否收敛，以及引用能否回到真实来源。

完整工程应做到：

  1. 把连接器输出视为不可信输入，先保存不可变源字节和授权快照。
  2. 结合声明、扩展名、字节和容器识别 MIME，严格处理编码冲突。
  3. 在禁网、低权限、资源受限的沙箱中运行解析和 OCR。
  4. 按页或区域处理混合扫描文档，保留表格、阅读顺序、坐标和警告。
  5. 分层保存原始、解析、规范与检索投影，所有清洗规则可回溯。
  6. 区分源身份、原始摘要、规范摘要、版本和 Chunk 身份。
  7. 把精确重复、近重复和业务版本建成不同关系，不让相似度替代版本判断。
  8. 在发布前绑定 ACL、租户和敏感数据策略，任何不确定权限默认隔离。
  9. 用 W3C PROV 的 Entity/Activity/Agent 和 OpenLineage 的 Job/Run/Dataset 记录互补血缘。
  10. 通过六层质量门禁、隔离区、不可变重放和原子 generation 发布阻止半成品上线。
  11. 用真实格式夹具、黄金结构、恶意输入、权限矩阵和组合故障验证系统。
  12. 分别报告覆盖、新鲜度、版本、ACL、血缘和隔离指标，不用一个“摄取成功率”隐藏长尾。

最终需要证明的不是“文件已经进了向量库”，而是：

每个在线 Chunk 都来自已知源版本，经过已知处理活动，保留必要结构，绑定当前有效权限，通过明确质量门禁，并能在错误发生时被隔离、重放、撤回和解释。
