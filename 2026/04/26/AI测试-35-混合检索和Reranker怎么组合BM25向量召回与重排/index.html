一、工程定义与边界：混合检索优化的是候选排序，不是自动证明答案正确

1. 被测系统的最小边界

本文定义的混合检索系统包含：

两路召回可以并行，但它们不能各自解释一套不同的租户、ACL、有效期和删除状态。否则融合的不是两个相关性信号，而是两个不同授权宇宙。

2. 四个不同的“成功”

层级 成功条件 不能推出什么
协议 两路请求返回、重排服务返回 200 候选相关或有权限
候选 相关文档进入 union pool 最终排序正确
排序 qrels 下 Recall/MRR/nDCG 达标 生成答案忠实
业务 用户任务和业务断言通过 所有未来查询都正确

Schema 合法、相似度高、rerank score 高或 HTTP 200 都不能替代业务正确性。

3. 本文不讨论什么

  • 不重新讲通用 qrels 标注流程
  • 不把检索分数解释成模型置信度
  • 不讨论生成模型的忠实度和引用完整性
  • 不给出跨业务通用的候选深度和阈值
  • 不声称混合检索必然优于最佳单路

本文要建立的是一套能回答“哪一路贡献了哪个候选、融合为何改变顺序、重排为什么增益或退化、成本增加在哪里”的工程证据。

上线配置至少版本化：

2. 词频不是线性奖励

同一个词出现 20 次，不应简单比出现 2 次高 10 倍。BM25 的分母让词频收益逐渐饱和，减少关键词堆叠的影响。

但如果 Chunk 本身由重叠产生大量重复，BM25 仍可能让多个相似块占据候选池。去重和 Chunk 设计不能交给词频公式自动解决。

3. 长度归一化不是“越短越好”

b 调节文档长度相对平均长度的影响。过强归一化可能让极短标题或残缺块获得不合理优势；过弱则可能让长文档因词项数量多而占优。

Chunk 策略变化会改变 avgdl 和 tf 分布。因此重新切片后，即使 BM25 参数不变，分数也不是原版本的同一量尺。

4. 分词器决定 BM25 看见什么

中文、代码、错误码和产品型号尤其依赖 analyzer：

  • ERR-42 是否被拆成 err 和 42
  • C++、C# 的符号是否丢失
  • 退款审核 被切成哪些词
  • 大小写与全半角是否统一
  • 同义词是在索引时还是查询时扩展
  • 停用词是否误删业务缩写
  • 拼音、繁简和词干化如何处理

测试必须保存 analyzer 版本，并使用 _analyze、explain 或等价官方能力验证真实 token。只在应用代码中打印原始 query 无法解释词法召回。

5. BM25 的强项

典型强项包括：

  • 错误码、订单号、法规条款号
  • 人名、产品名、接口名
  • 引号短语和精确术语
  • 新出现、Embedding 训练中未覆盖的 token
  • 用户明确输入的稀有词

这些不是绝对结论。若 analyzer 把标识符拆坏，BM25 同样会失败。

6. BM25 的弱项

  • 同义改写没有词项重叠
  • 口语现象与正式文档术语不同
  • 多语言对应词
  • 语义相近但表述不同
  • 上下位概念和隐含关系

查询扩展和同义词词典可以缓解，但它们也会引入新版本、歧义和召回噪声。

四、Dense Retrieval：压缩语义表达，但会丢失精确词法信号

1. 双编码器为什么适合第一阶段召回

双编码器分别计算：

文档向量可以离线预计算并建立 ANN 索引，在线只编码查询再搜索。

2. Dense 的强项

  • “快递一直没到”与“物流包裹长时间未到货”
  • 用户现象描述与知识库标准术语
  • 同义、近义和部分跨语言表达
  • 没有精确词项重叠的语义匹配

3. Dense 的弱项

  • 稀有错误码和新产品编号
  • 数字、版本号、否定词等细粒度差异
  • 长文档中的局部精确事实
  • 训练域外的新术语
  • 很相似但业务条件相反的政策

例如“退款可以撤销”和“退款不可撤销”共享大部分词。单向量表示可能把二者放得很近。候选召回可以容忍一些近似，但最终排序必须专项验证否定、时间、主体和条件。

至少保存：

  • query/document encoder 工件
  • 输入前缀与模板
  • tokenizer 和最大长度
  • pooling
  • 输出维度与归一化
  • distance
  • ANN 索引版本和参数
  • Chunk 文本版本

同维度模型不可混用，cosine 或 dot 也不是业务置信度。具体数学与索引测试见 AI测试-34。

六、两路原始分数为什么不能直接比较

1. 数值范围不同

BM25 分数受：

  • 语料大小与 document frequency
  • analyzer
  • 文档长度
  • 查询词数
  • 字段与 boost
  • 实现公式

影响。

Dense 分数受：

  • 模型和归一化
  • cosine、dot、L2
  • 量化与 ANN
  • query 和文档分布

影响。

一个 BM25 12.4 与 cosine 0.82 没有天然可加意义。

2. 同一路分数也未必跨 query 可比

长 query 的 BM25 可能累加更多词项；某些 dense query 的最近邻整体更集中。用全站统一 raw score 阈值做“相关/不相关”判断，必须先验证不同切片分布。

3. 直接加权对单位缩放敏感

假设：

只要 dense 服务把 cosine 从 [0,1] 改成百分制，排序就会剧烈变化，即使 dense 内部排名完全没变。

存在问题：

  • 加入一个极端候选会改变其他所有候选的值
  • 单元素或全同分数需要特殊处理
  • 两路候选窗口变化会改变尺度

5. 什么时候可以做加权分数融合

需要至少完成：

  • 固定各路分数定义和版本
  • 在独立校准集上学习转换
  • 对查询切片验证稳定性
  • 对模型、analyzer、语料变化设置重校准触发器
  • 防止训练集和发布评测集重用
  • 保存校准器版本和特征

可以使用逻辑回归、isotonic regression、learning-to-rank 或其他明确方法，但输出仍是排序信号，不自动成为业务正确概率。

6. Score calibration 必须说明“对什么条件成立”

校准器不能只留下一个权重文件。训练样本必须同时保存 query 切片、召回器版本、候选窗口、语料快照和标签来源，因为它学到的是“在这套候选生成条件下，某个分数对应怎样的相对证据”。若上线时把 BM25 窗口从 50 扩到 500，候选池会出现更多低分词法命中；若 dense 模型升级，余弦分布和难负例组成也会变化。即使校准器代码没有改，输入分布已经不是训练时的分布。

可执行的验收应至少包含三组对照。第一组固定两路排名，只改变 raw score 的单位，确认基于排名的 RRF 不变，并确认加权方案要么经过对应转换，要么明确失败。第二组固定 query，分别在旧、新候选窗口上重放，比较同一文档的转换后分数、最终名次和入选原因。第三组按错误码、自然语言、短 query、长 query、低频语言等切片检查校准残差，防止全局平均掩盖局部偏移。

还要区分“缺失”与“零分”。某文档没有进入 dense 窗口，表示 dense 没有观察到它，不等于 dense 判断它不相关；把缺失直接填成零，会让窗口大小偷偷参与最终排序。数据模型应保存 observed_by_sparse、observed_by_dense 和各自 rank，校准器对缺失值采用经过验证的显式策略。发布日志记录 calibrator_version、训练快照和特征模式；任一召回器、分词器、模型或窗口契约变化，都触发重新回放，而不是沿用旧权重。

九、Cross-Encoder：让查询与文档做完整交互，代价是每对都要推理

1. 计算边界

典型 Cross-Encoder 输入：

模型在同一次 Transformer 前向中让 query token 与 document token 交互，输出一个相关性分数。

与双编码器相比，它通常不能把最终文档表示完全离线复用，因为分数依赖具体 query-document 对。因此在线成本大致随重排对数 R 增长，还受序列长度、模型规模和 batch 影响。

Nogueira 与 Cho 的 BERT passage reranking 原始工作展示了把 BERT 用于查询相关段落重排；论文报告的提升只属于其 TREC-CAR、MS MARCO 等实验，不是任何业务上的默认增益。

2. Cross-Encoder 的优势

  • 精细 token 交互
  • 能利用词序、否定、局部匹配
  • 适合对较小候选池做高质量排序
  • 可以针对业务 relevance 标注训练

3. Cross-Encoder 的失败面

  • 领域或语言不匹配
  • 训练负样本与生产候选分布不同
  • 输入截断丢失关键段落
  • query 与标题/正文拼接模板变化
  • 长短文档偏差
  • 分数未校准却被解释为概率
  • batch 中超长样本拖慢尾延迟
  • 模型升级改变分数分布

Reranker 返回一个浮点数，只证明模型完成计算。它不会自动识别租户权限，也不会保证业务条件正确。

4. 训练候选分布要匹配上线候选

如果 Cross-Encoder 只用 BM25 hard negatives 训练，上线却接收 BM25+dense 的混合候选，dense 带来的语义近似负例可能是新分布。

至少按来源分析：

  • sparse-only 候选的排序质量
  • dense-only 候选的排序质量
  • both 候选
  • exact identifier
  • 否定与时间条件

训练数据和线上候选生成器是一个联合版本。

十一、重排深度：质量增益、序列长度、batch 与尾延迟一起决定

1. Rerank depth 不是越大越好

若 R 从 20 增加到 100：

  • 相关文档若原本排在 50，可能被救回
  • 每 query 推理对数增加 5 倍
  • batch 等待和显存压力增加
  • 超长候选更可能触发截断或 OOM
  • 并发下排队时间可能非线性增加

必须画质量与成本曲线，而不是只选最高离线 nDCG。

仅记录 truncated=true 不足以排障。每个重排输入至少应留下 tokenizer 版本、模板版本、原始 token 数、实际 token 数、query 与文档的预算分配、保留区间以及输入内容的脱敏哈希。对于标题、章节路径、正文和代码块分配独立区间时，还应记录哪个字段被完整保留、哪个字段被裁掉。这样才能区分模型能力退化、代表 Chunk 选错和关键句根本没有进入模型三种原因。

回归集应专门放置成对探针：唯一判别句分别位于段首、段中和段尾；肯定句与否定句只差一个关键词；错误码在标题出现但正文不出现，或反过来出现。用生产 tokenizer 和生产模板重放，断言关键 token 是否存在于实际输入，并比较截断前后的名次变化。若服务不能接受超长全文，所谓“截断前”可以用离线滑窗或结构化摘要作诊断基线，但必须标记为诊断实验，不能冒充线上可达结果。

事故证据应保存候选进入 reranker 前的 rank、实际输入哈希、截断策略、rerank raw score 和最终 rank。出于隐私要求无法保存正文时，可保存受控证据库的文档版本、字段 token 区间和带密钥哈希，并由有权限的离线作业复现。没有这条证据链，团队看到相关文档从融合第一掉到最终第八时，无法判断该调模型、改 Chunk 代表选择，还是调整输入预算。

5. Batch 的两面性

更大 batch 可能提高吞吐，但在线系统还要考虑：

  • 等待凑 batch 的时间
  • 不同长度 padding 浪费
  • 大 query 把其他请求拖入同一 batch
  • deadline 不同
  • 取消请求是否仍占计算
  • GPU OOM 后整批失败

应报告 pairs/s、query/s、queue p95、compute p95 和端到端 p95，而不只报模型纯推理吞吐。

十二、去重：先定义“同一项”，再决定保留哪一个 Chunk

1. 三种去重粒度

精确 Chunk 去重

同一 chunk_id 被两路命中，只保留一次，保留两路 rank 和 score。

内容去重

不同 ID 但标准化正文哈希相同，只保留权威来源或最新 revision。

Parent 聚合

同一文档的多个重叠 Chunk 只保留有限数量，避免一个 parent 占满 top-k。

三者目标不同。Parent 聚合过早会丢掉真正最相关的段落定位。

2. 融合前还是融合后

若同一 parent 的三个 Chunk 在 BM25 列表占据前三名：

  • 融合前按 parent 去重，它只获得一个 rank 贡献
  • 融合后去重，它可能凭多个 Chunk 挤压其他文档

因此策略必须固定并进入实验。本文夹具在每一路先按 canonical_id 保留最高排名，再做 RRF。

3. 代表 Chunk 的选择

融合到 canonical document 后，reranker 仍需要具体文本。代表 Chunk 可以取：

  • 两路中最佳 rank 的 Chunk
  • 原始分数最高但需路内比较
  • 合并相邻 Chunk 后的窗口
  • parent 中重新做局部选择

选择规则会改变重排输入，必须记录 representative_chunk_id。只保存 canonical ID 无法重现模型看到的内容。

4. 多样性不是去重的同义词

去重消除同一内容，多样性约束控制同一主题、来源或 parent 的占比。多样性可能牺牲纯相关排序，需要独立业务目标和评测，不能混进一个不透明后处理器。

十三、权限过滤：两路同域、融合后复核、缓存按主体分区

1. 理想执行顺序

最终复核是纵深防御，不能替代第一阶段约束。把未授权正文发送给外部 reranker，即使最后不返回，也已经发生数据暴露。

2. 两路过滤能力可能不同

BM25 引擎可能原生支持布尔 filter；向量引擎可能使用 pre-filter、post-filter 或迭代扫描。两路都写 tenant=A 不代表执行质量相同。

要分别记录：

  • eligible count
  • raw candidate count
  • rejected count
  • returned count
  • stop reason
  • filter plan

向量过滤执行与选择率问题详见 AI测试-34。

3. 权限变化时缓存失效

候选缓存和 rerank 缓存键至少包含：

只按 query 缓存融合结果会把其他用户的候选和分数带进当前请求。

4. 权限过滤要处理请求期间的时序竞争

一次查询会跨越多个时间点：t0 解析主体与策略版本，t1 两路召回，t2 发送重排，t3 返回结果。若文档在 t1 后撤权或改租户，单纯复用召回时的布尔值会产生检查与使用之间的竞争。请求契约应携带不可歧义的 principal_scope_hash、policy_version 和 corpus_snapshot；候选携带自身 acl_revision。最终复核比较这些版本，并按业务安全策略决定重新鉴权、丢弃变化候选或整次失败关闭。

需要明确“撤权何时生效”的服务级契约。例如强隔离系统可以规定：只要最终复核发现策略版本前进，就必须重新鉴权，且不得用数量不足为理由补回旧候选。允许快照一致性的系统也要给出最大陈旧窗口，并确保外部 reranker 接收文本前已经满足该快照。最终过滤只能阻止返回，不能撤销此前向外部服务发送未授权正文造成的暴露。

时序测试不能只构造静态无权限用户。测试应在 sparse 返回后、dense 返回后、发送 reranker 前和 reranker 返回后四个屏障分别注入撤权，断言外发集合与最终集合符合契约；同时检查缓存键是否随 policy_version 变化。证据至少包含各阶段看到的策略版本、候选 ACL revision、复核结果和拒绝原因，才能区分过滤计划错误、缓存污染与并发撤权。

5. Always-on 混合与查询路由怎样选择

最简单的部署方式是每条查询都同时执行 BM25 和 dense。它的优点是行为固定、证据完整，适合作为第一版基线；缺点是即使某类查询明显只需要一条链路，也要承担双路延迟、资源和故障面。

查询路由器可以根据可解释特征选择：

  • 包含错误码、引号短语、长数字或产品型号时，提高稀疏路窗口
  • 口语化长描述、同义改写或跨语言查询时，提高稠密路窗口
  • 两类信号都存在时继续双路
  • 路由不确定时使用完整混合，而不是无证据地关闭一条路

路由特征本身必须版本化。正则表达式、语言识别器、query 分类模型和阈值任意一项变化，都会改变候选来源。不能只在最终 trace 中写 route=hybrid，还要记录触发特征、路由器版本和每路实际窗口。

路由器也会误判。例如 ERR42 登录后仍然扣款 同时包含精确错误码和自然语言现象；只走 BM25 可能错过语义说明，只走 dense 又可能弱化标识符。测试集要覆盖这种混合意图，并分别统计：

6. 动态候选预算不能由最高分单独决定

另一种优化是根据查询难度动态选择 Ls/Ld/M/R。例如两路头部高度一致、排序间隔稳定时减少重排深度；两路分歧大、候选来源单一或权限过滤后结果不足时扩大候选。

难点在于“头部分数高”不等于“答案已正确”。BM25 raw score 和 dense score 不可直接比较，reranker score 也不是业务置信度。动态控制器应使用经过验证的结构信号，例如：

  • 两路 canonical top-k 的集合重叠
  • 相关候选来源的历史切片表现
  • 过滤后剩余候选数
  • RRF 头部名次间隔
  • query 是否含高精度标识符
  • 当前剩余 deadline、队列和资源水位

自动化测试要验证单调和边界行为：剩余时间减少时不能反而扩大昂贵重排；权限过滤后候选不足时不能用非法候选补齐；控制器异常时回到已评测的静态配置；同一版本、同一输入和同一资源快照应得到可复现决策。

动态策略发布前应与静态配置做配对回放。报告至少包含质量差值、节省的 query-document 对数、端到端尾延迟、fallback 比例以及受伤害查询清单。它只有在明确 Pareto 改善时才值得增加这一层控制复杂度。

注入：把相关文档放在 sparse rank 51，而 Ls=50。

期望：union Recall 下降；诊断落到候选窗口，reranker 不被误责。

期望：canonical 去重和 parent cap 生效；来源贡献仍可审计。

注入：exact identifier 文档进入 fusion top-1，重排器把它压出 top-k。

8. 输入截断

注入：关键否定句放在 Chunk 尾部，超过 reranker 最大长度。

期望：truncation 字段可见；否定切片退化；结构化截断策略进入修复实验。

9. GPU OOM 或 batch 部分失败

注入：混入超长候选，降低显存预算。

期望：整批错误不会静默丢候选；fallback 状态明确；已取消请求停止占用资源。

注入：候选召回后、rerank 前撤销用户权限。

注入：只在一个节点修改 rank_constant 或窗口。

6. 修复候选

方案 A：跳过所有错误码 query 的 reranker

简单，但路由规则覆盖有限，可能漏掉“错误码 + 现象”的混合 query。

方案 B：把 exact identifier 作为 reranker 特征或训练样本

从模型层修复，需要标注、训练与泛化验证。

方案 C：融合分数与 reranker 学习排序

若 query 含高精度标识符，且权威字段精确匹配、权限和版本均通过，则保证至少一条匹配文档留在最终前 m。这是一条业务规则，需要 false positive 测试，不能对所有 token 生效。

  • p95 与 batch 容量达标
  • 无跨租户和旧 revision
  • Δrerank_vs_fusion 按切片可见
  • 失败样本已进入固定回归集

8. 事故教训

Reranker 成功返回、Schema 正确、分数非空，都不等于排序正确。若没有保存 fusion 前后的候选，团队很可能错误地去调 Embedding 或增大 top-k。

二十二、另一个高风险失败：去重后代表 Chunk 继承了错误权限

1. 场景

同一 parent 下有两个 Chunk：

  • chunk-public：公开摘要
  • chunk-finance：财务审批细节

两者错误地共享同一个 canonical ID。BM25 命中公开摘要，dense 命中财务块。融合代码按 dense rank 选择 chunk-finance 作为代表文本，但 canonical 对象沿用了公开标记。

2. 为什么最终复核可能漏掉

如果最终复核只检查 canonical document 的聚合 ACL，而不检查代表 Chunk revision，财务正文会被发送给 reranker甚至返回。

3. 修复

  • 权限粒度与 evidence unit 粒度一致
  • canonical 聚合不能扩大任一 child 权限
  • representative_chunk_id 必须独立复核
  • reranker 发送前按具体 Chunk 授权
  • 不同 ACL 的 Chunk 不允许合并成同一可替换候选

这说明去重不是纯排序后处理，它会改变安全主体。

二十五、常见误区

1. BM25 分数加 cosine

两路量纲和分布不同，直接相加对单位变化敏感。

2. 把 min-max 当校准

候选池变化会改变所有归一化值，它没有建立稳定相关概率。

3. RRF 无需调参

窗口、rank constant、权重、去重和 tie-break 都会改变结果。

4. 两路各取 10，融合就一定有 20

两路重叠、canonical 去重和权限过滤都会改变并集大小。

5. 候选越多越安全

更大池增加成本、噪声和超时；要看 union Recall 的边际收益。

6. Cross-Encoder score 是置信度

未经校准的相关性分数不是业务正确概率。

7. Reranker 一定改善排序

领域错配、截断和训练候选分布差异都可能造成退化。本文夹具实际展示了退化。

8. ColBERT 只是 Cross-Encoder 加速版

Late interaction 保留可预计算的 token 表示，计算边界、存储和索引方式不同。

9. 去重只影响展示

去重会改变 RRF 投票、代表 Chunk、权限和最终证据。

10. 最后过滤权限就足够

未授权正文可能已经进入外部 reranker。权限应在召回范围、发送前和返回前多层执行。

11. HTTP 200 就算成功

可能是单路降级、rerank fallback、空候选或错误排序。状态要分层。

12. 只看全局 nDCG

exact identifier、否定、语言或小租户切片可能严重退化。

13. 重排深度直接照搬论文

论文深度、硬件、数据和模型属于其实验。生产配置必须本地测量。

14. 构造数据结果代表真实收益

本文的 1.0 和 0.8 只用于验证骨架与失败证据。

二十八、总结

BM25、dense 和 Reranker 分别解决不同问题：

  • BM25 保留精确词法、稀有标识符和字段信号
  • dense 补充同义改写和语义近邻
  • 融合把不同量尺的候选收敛成一个可解释列表
  • Reranker 在有限候选上做更细粒度交互

实现时最重要的边界包括：

  1. BM25 raw score 与 dense raw score 不可天然比较。
  2. RRF 不依赖原始量纲，但依赖候选窗口、rank constant、去重和 tie-break。
  3. 候选没有进入 rerank input，Reranker 无法救回。
  4. Cross-Encoder、single-vector bi-encoder 和 ColBERT late interaction 的预计算与交互位置不同。
  5. 重排深度必须与 batch、序列长度、排队和尾延迟一起评估。
  6. 去重会改变投票、代表文本和权限，不只是 UI 清理。
  7. 权限必须在召回范围、发送给 reranker 前和最终返回前形成纵深防御。
  8. Reranker 返回分数或 HTTP 200 不代表业务排序正确。

最终报告不能只有“混合检索 nDCG 提高”。它还要说明：

  • 哪些相关候选来自 BM25-only、dense-only 和 both
  • union 到 fusion 丢了什么
  • fusion 到 rerank 改善或伤害了哪些切片
  • 每一层增加了多少延迟和资源
  • fallback 请求占多少
  • 是否存在任何越权、删除失效或不可重放结果

只有候选来源、融合贡献、重排输入和最终结果都能还原，团队才有能力在质量下降时修改正确的那一层。
