AI测试-32-Human-in-the-loop怎么设计审批点置信度阈值和审计证据

发表于 2026-04-20 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:01

给 Agent 加一个“执行前请确认”的弹窗，并不等于完成了 Human-in-the-loop 设计。

如果所有请求都要求人工确认，系统很快会变成一条昂贵、拥堵而且没有判断力的审批队列。审核人连续看到几百个相似请求后，最常见的动作不是逐项核实证据，而是机械点击“同意”。低风险请求被无意义地阻塞，高风险请求反而淹没在噪声里。

如果只在模型“置信度低”时转人工，问题同样没有解决。分类分数、Token 概率、模型自报的“90% 确定”都不天然等于答案正确概率；即使某个分数经过校准，它也只对校准数据、模型版本、任务切片和时间窗口成立。一个高置信度动作仍可能越权、不可逆、金额过高，或者缺少完成判断所必需的证据。

真正需要设计的是一套控制面：

这篇文章以“客服 Agent 处理退款、修改地址和发送通知”为贯穿场景，讨论怎样选择审批点、怎样使用置信度、怎样实现审批状态机，以及怎样测试 TOCTOU、防重放、双人审批、超时和审计证据。

本文讨论的是工程控制和测试方法，不替代具体行业的法律、合规或内部授权要求。文中阈值与量化结果用于展示设计和验收方法，不是可以直接复制到生产环境的通用标准。

一、先给结论：Human-in-the-loop 不是让人确认所有请求

一套可用的人工介入机制，至少要满足下面七个条件。

  1. 介入强度由风险决定。 只读查询、可撤销草稿和不可逆付款不应该使用同一种审批方式。
  2. 审批点放在风险产生之前。 已经完成外发、删除或扣款后再让人看结果，只能叫事后复核，不能阻止该次伤害。
  3. 审批对象是确定动作快照。 审核人批准的是“为订单 A 退款 800 元到原支付渠道”，不是“允许 Agent 继续运行”。
  4. 审批不是长期授权。 执行时仍要检查身份、权限、资源版本、额度、策略和幂等状态。
  5. 置信度只是证据之一。 它必须经过校准，并与硬规则、证据完整度、任务外分布信号共同使用。
  6. 拒绝、过期和取消都是正常终态。 系统不能把它们包装成工具报错后自动换一种方式继续执行。
  7. 人也会犯错。 界面、队列、排班和指标要主动控制自动化偏见、审批疲劳和橡皮图章行为。

NIST AI RMF 的 GOVERN 3.2 要求定义并区分人机配置与监督角色，MAP 3.5 要求依据组织政策定义、评估并记录人工监督过程。这个要求的重点不是“页面上出现一个人”，而是角色、过程、证据和责任边界能够被验证。

OpenAI 的 Agent 构建实践指南把“超过失败阈值”和“高风险动作”列为两类典型人工介入触发器，并用敏感、不可逆或高影响动作说明风险维度。这个框架比“模型不确定就找人”更完整，因为风险既来自模型能力，也来自动作本身。

二、贯穿场景：一个客服 Agent 实际会遇到哪些动作

假设客服 Agent 能处理以下任务：

  • 查询订单、物流和会员信息
  • 根据政策计算可退金额
  • 生成退款方案
  • 调用支付服务发起退款
  • 修改尚未出库订单的收货地址
  • 给客户发送邮件或短信
  • 遇到政策例外时创建人工工单

这些动作不能简单分成“模型回答”和“人工审批”两类。更有用的拆分是观察影响、权限和可逆性。

动作 主要影响 可逆性 权限与数据 合适的控制
查询公开物流节点 只读 无副作用 低敏感 自动执行，保留访问日志
查询完整地址和电话 隐私暴露 读取本身不可撤回 个人数据 权限与目的校验，必要时脱敏
生成退款草案 不直接改变业务状态 可删除 内部数据 自动生成，结果校验

退款 800 元 明显财务影响 补偿复杂 高权限 工具执行前单人审批

修改已出库地址 可能误投和泄露 很难恢复 地址、物流权限 硬规则拒绝，不给人工按钮绕过

表中“自动执行”不表示没有控制，只表示不进入同步人工队列。它仍需要认证、授权、策略、数据最小化、幂等和审计。

同样，“人工审批”也不表示人可以突破所有硬规则。如果订单已出库，业务系统明确禁止修改地址，那么审批页面不应该提供“仍然同意”的后门。人工只能在组织预先授予的裁量空间里作决定。

三、Human-in-command、on-the-loop 和 in-the-loop 分别解决什么

欧洲委员会发布的可信 AI 伦理指南使用了 Human-in-the-loop、Human-on-the-loop 和 Human-in-command 三种监督方式。工程实现中可以按下面的操作边界理解，但仍应在本组织策略里写出自己的精确定义。

1. Human-in-command：人决定系统能不能做这类事

Human-in-command 关注系统级控制权，例如：

  • 哪些业务可以使用 Agent
  • 哪些工具永远不向模型开放
  • 自动退款最高额度是多少
  • 哪些地区、用户或数据类别禁止自动处理
  • 何时暂停某个模型、某个策略或整个 AI 功能
  • 谁承担残余风险并批准上线

它通常落在产品治理、风险委员会、服务所有者和事件指挥流程中，不要求某个人逐条批准每个请求。

如果系统没有 Human-in-command，前线审核人即使能拒绝单次动作，也无法处理“这个系统根本不应该继续用于该场景”的问题。

2. Human-on-the-loop：人持续观察并能接管运行系统

Human-on-the-loop 关注运行监督，例如：

  • 监控自动执行比例、失败率、人工接管率和风险切片
  • 抽样复核已自动执行的低风险动作
  • 观察模型、证据和业务分布漂移
  • 在异常趋势出现时收紧阈值、降低额度或暂停能力
  • 在事故中执行 kill switch、隔离队列和回滚

它适合高频但单次低风险、可观测且可补偿的动作。关键前提是监控信号足够快，接管动作确实能限制后续影响。若损害在监控发现前已经不可逆地扩散，只靠 on-the-loop 不够。

3. Human-in-the-loop：人在特定决策周期内作出明确决定

Human-in-the-loop 关注单次运行中的暂停和恢复：

  • Agent 提交一份计划，等待人确认范围
  • 工具即将产生副作用，等待人批准具体参数
  • 结果准备外发，等待人检查内容
  • 异常超出自动恢复范围，转交人处理

它不是“人重新完成全部工作”，而是把最需要判断或授权的节点交给具备责任和证据的人。

四、四类审批点：Plan、Tool、Result 和 Exception

审批点应围绕风险首次变得具体的位置设计，而不是统一塞在对话结束前。

1. Plan approval：先批准范围，不批准未知动作

计划审批适合长任务、多步骤任务和会访问多个系统的任务，例如：

审核人批准的是目标、数据范围、工具范围和预算。计划后来新增“实际退款”时，原计划批准不能自动覆盖新增动作。

计划审批的测试重点包括：

  • Agent 是否在批准后悄悄扩展工具集合
  • 计划摘要是否遗漏高风险步骤
  • 模糊描述能否掩盖真实参数
  • 批准的租户、用户和资源范围是否传递到每个子步骤
  • 重新规划后是否重新计算风险

2. Tool approval：副作用执行前绑定规范化参数

工具审批是最关键的一层。页面要展示规范化后的真实调用参数，而不是模型生成的自然语言摘要。

如果模型摘要写“退款 800 元”，参数却是 80000 美元分单位，审核人必须看到货币、最小金额单位和目标渠道。前端友好文案可以存在，但不能代替机器实际执行的字段。

3. Result review：检查要发布或交付的结果

结果复核适合：

  • 对外发送的法律、医疗、财务或高声誉风险内容
  • 大规模批量生成结果
  • 需要领域专家确认的判断
  • 工具已完成只读分析，但结论可能影响后续人工决策

结果复核不能弥补执行前控制。先退款再检查退款说明，无法阻止错误退款。它应该保护“发布结果”这个动作，而不是用来解释已经发生的副作用。

结果页面需要同时展示：

  • 最终输出
  • 关键来源和引用位置
  • 缺失或冲突的证据
  • 使用的模型、Prompt、检索与政策版本
  • 与输入数据相关的限制
  • 审核人可以执行的修订、拒绝和升级动作

4. Exception escalation：异常升级不是无限重试后的垃圾桶

异常升级适合系统不能安全自动收敛的情况：

  • 连续多次无法确认客户身份
  • 工具返回“提交状态未知”
  • 证据互相冲突
  • 政策没有覆盖当前例外
  • 风险评分超出自动策略范围
  • 审批超时但业务仍需要处理

异常包应包含已经做过什么、哪些动作可能已产生副作用、当前资源状态、剩余预算和下一步可选动作。只发一句“Agent 失败，请人工处理”，会迫使人工从头排查，也容易重复执行未知状态的操作。

金额与数据 sensitivity 财务和信息敏感度如何 高额交易、身份信息、医疗或密钥
证据 evidence 决策所需事实是否齐全且新鲜 来源缺失、状态冲突、数据过期
不确定性 uncertainty 输入是否在已知分布内，判断是否稳定 校准置信度低、多模型分歧、异常输入

六、置信度不能直接等于正确概率

“模型置信度 0.9”这句话必须继续追问：

  1. 这个数从哪里来？
  2. 它预测的事件是什么？
  3. 在什么数据上校准？
  4. 哪个模型和 Prompt 版本产生？
  5. 对当前业务切片是否仍有效？

1. 常见分数表达的是不同对象

分数来源 它实际表达什么 不能直接推导什么
分类器 softmax 最大值 类别分布中的相对分数 该业务决策正确概率
Token log probability 给定上下文时某个 Token 的条件概率 整个答案事实正确率
多次采样一致率 在当前采样配置下输出是否一致 一致答案一定正确
LLM 自报“90%” 模型生成的一段文本 经过统计校准的概率
Judge 分数 某评测器按某量表的判断 真实业务结果概率
检索相似度 查询与片段在某表示空间的接近程度 片段足以支持结论

Guo 等人在《On Calibration of Modern Neural Networks》中把校准问题表述为：预测的概率估计应当代表真实正确可能性，并展示了现代神经网络可能校准不良。这个结论不能机械外推到所有生成式任务，但足以说明一个工程原则：未经目标事件和部署数据验证的分数，不应被命名为“正确概率”。

七、把置信度、规则和证据完整度组合起来

一个容易落地的方式是把决策拆成三层。

第一层：确定性资格检查

回答“系统是否允许考虑自动执行”：

  • 身份是否已验证
  • 主体是否有当前权限
  • 工具是否在任务允许清单
  • 金额、地区、数据类型是否在自动范围
  • 动作是否可幂等或可靠补偿
  • 关键资源是否有版本号

任一硬条件失败，不进入置信度计算。

第二层：证据充分性检查

回答“是否具备作出该判断的事实”：

证据完整度不应该由模型凭感觉打分，而应尽可能由字段存在性、来源、签名、版本、新鲜度和冲突规则计算。

第三层：统计不确定性与任务可靠性

只有前两层通过后，才使用经过校准的任务分数、分布外检测、采样分歧和历史切片表现决定自动、复核或升级。

这种顺序能避免两个错误：

  • 用高置信度覆盖权限失败
  • 用低置信度掩盖证据管道缺陷

八、审批界面也属于安全控制

人工审核不是把 JSON 扔给运营人员。界面决定了审核人是否有机会发现问题。

1. 展示差异和证据，不展示冗长推理

审批页应优先展示：

  • 将要发生的动作和副作用
  • 与现状相比会改变什么
  • 金额、货币、对象、收件人和数据范围
  • 关键证据原文与来源
  • 缺失、过期或冲突项
  • 命中的策略和需要人工判断的原因
  • 回滚或补偿方式

不需要展示模型私有思维链。自然语言理由可以作为摘要，但决定性事实要来自结构化证据和业务系统。

2. 避免 Automation Bias

自动化偏见会让审核人过度依赖系统建议，并忽略冲突证据。Skitka、Mosier 和 Burdick 的原始研究讨论了自动化建议如何影响决策。落实到界面，可以采用以下控制：

  • 高风险场景先要求审核人选择结论，再显示模型建议
  • 把支持证据和反对证据并列展示
  • 不用醒目的绿色默认选中“批准”
  • 批准和拒绝都要求选择结构化原因，高风险批准补充说明
  • 随机插入经过标记的校验样本，测量审核质量而非只测速度
  • 定期让审核人处理无模型建议的对照样本

“隐藏建议”不适合所有场景。它会增加处理时长，也可能让新手缺少支持。是否使用应通过对照实验比较准确率、漏审率和时延，而不是当成固定教条。

3. 控制审批疲劳

需要监控：

  • 每人每小时审批量
  • 连续工作时长
  • 单条停留时间分布
  • 批准率是否异常接近 100%
  • 同类风险下不同审核人的分歧
  • 被后续事实推翻的比例
  • 队列等待时间和超时率

若一个审核人在 90 秒内批准 50 个复杂退款，请求都“合法通过”并不能证明控制有效。系统应触发速率限制、二次抽样或轮换，而不是奖励吞吐量。

4. 批量审批只适合同质、可界定的对象

批量审批必须保证：

  • 每项动作属于同一策略和风险等级
  • 审核人看得到总金额、最大金额和异常项
  • 每项仍有独立快照和审计记录
  • 任一项参数变化只使该项失效
  • 高风险或异常项自动从批次剥离

把 999 个低额退款和 1 个高额退款折叠成“批准 1000 项”，会把最需要关注的风险隐藏起来。

十、审批数据模型：最少要保存哪些字段

一条审批记录可以分成身份、动作、风险、证据、决定和执行六组字段。

1. 敏感内容不要全部复制进审批表

审批记录可以保存 Artifact 引用、内容摘要、数据分类和受控访问位置。完整身份证、地址、对话和支付信息应按最小化原则存放在适当的数据域中，并设置独立权限、保留期和访问审计。

2. 哈希证明的是一致性，不自动证明真实性

action_digest 能帮助判断审核后动作是否变化，但前提是规范化算法稳定、摘要来源可信、记录没有被整体替换。单纯给 JSON 做 SHA-256 不能证明记录由谁创建，也不能阻止拥有数据库写权限的人同时改内容和摘要。

更强的证据需要组合：

  • RFC 8785 一类确定性 JSON 规范化
  • 服务身份签名或受控 MAC
  • 追加写事件存储
  • 独立审计域或 WORM 保留
  • 密钥轮换和签名验证记录
  • 数据库与对象存储访问审计

  • 租户与代表用户

十二、防重放：批准一次只能执行绑定动作一次

防重放至少要处理四条路径。

1. 用户重复点击

前端禁用按钮只能改善体验，不能形成安全保证。后端要用比较并交换或唯一约束，保证一个审批只能从 APPROVED 被一个执行者领取。

2. 网络超时后客户端重试

重试必须携带同一 idempotency_key。如果第一次可能已经提交，客户端应先查询结果，不能生成新键再次写入。

3. 旧审批被复制到新请求

审批令牌或内部引用应绑定：

  • approval_id
  • action_digest
  • tenant_id
  • audience
  • expires_at
  • 一次性 nonce

服务端从数据库读取真实记录，不能只相信客户端传来的“approved=true”。高风险审批对象不适合放在可分享 URL 或浏览器本地存储中。

4. 已执行记录被再次恢复

运行状态恢复时，Agent 必须读取审批终态和下游业务结果。EXECUTED 不能恢复成 APPROVED，也不能因为对话重放再次发起工具调用。

4. 状态机测试

对每个状态验证所有非法迁移，而不是只测成功路径：

并发测试要让多个执行器同时领取同一记录，最终只能有一个获得执行权。只在单线程单元测试里验证 status，无法发现数据库隔离级别、缓存延迟和消息重复投递带来的竞态。

5. 影子策略比较

新策略先对真实流量做只读影子判定，不改变当前决策。比较：

  • 自动范围扩大或缩小了多少
  • 哪些风险切片发生决策变化
  • 新旧策略与最终业务真值的差异
  • 人工队列峰值是否会超过容量
  • 阈值变化是否集中影响某类用户

不能只报告“人工量下降 20%”。如果下降全部来自高额退款被自动化，这个数字反而是风险信号。

十五、审计证据：要重建一次决定，而不是堆日志

一条可审计链路至少要回答：

  1. 谁发起了什么任务，代表谁行动。
  2. 系统当时看到了哪些业务事实。
  3. 哪个模型和哪套策略提出了什么动作。
  4. 为什么需要或不需要人工介入。
  5. 审核人实际看到了哪个快照。
  6. 谁在什么时间作出什么决定，具有什么授权。
  7. 执行时哪些事实发生变化。
  8. 下游系统最终产生了什么业务结果。

1. 事件而不是覆盖式字段

不要只在一行记录上更新 status。追加事件能保留中间过程：

事件链哈希可以暴露部分删改，但不是完整防篡改方案。攻击者若能重写所有事件和根锚点，仍能伪造整条链。根摘要应周期性锚定到独立审计域，并限制能够同时修改业务数据、审批数据和审计证据的主体。

2. 审批证据和执行证据分开

审批证据说明“允许尝试执行”，执行证据说明“实际发生了什么”。后者至少包括：

  • 执行器身份和版本
  • 下游请求 ID
  • 幂等键
  • 请求参数摘要
  • 开始、提交和确认时间
  • 下游返回类型
  • 提交状态是成功、失败还是未知
  • 最终业务对象 ID 和版本
  • 后置条件验证结果

模型说“退款成功”不是执行证据，HTTP 200 也不一定是业务成功。必须查询退款账本或使用下游返回的稳定资源标识验证结果。

3. 审核人看到的页面也要版本化

如果审计只能看到原始 JSON，却不知道界面是否截断了金额、隐藏了货币或把警告折叠起来，就无法判断审核人是否获得了知情决策条件。

建议记录：

  • review_ui_version
  • presentation_schema_version
  • 展示字段清单与摘要
  • 被折叠或脱敏的字段
  • 证据加载失败项
  • 页面语言与时区
  • 决定前停留时长

不需要录制审核人的全部屏幕或键盘。证据留存也要遵守隐私、劳动关系和最小化原则。

4. 保留期要按证据类型区分

身份、财务和安全事件可能需要不同保留期。原始对话、附件和个人数据不应因为审批日志存在就永久保存。设计时需要给每类 Artifact 配置：

删除主数据后，还要检查搜索索引、缓存、Trace、评测样本和审核截图是否保留了副本。

十六、超时、取消和长时间审批

OpenAI Agents SDK 的 Human-in-the-loop 文档展示了工具调用产生 interruption、将运行转换为可持久化 RunState、批准或拒绝后恢复原运行的机制。这说明暂停和恢复可以成为 Agent 运行时的一等状态，但业务系统仍要负责审批记录、授权、过期和副作用一致性。

1. 超时不是自动拒绝的同义词

到达 expires_at 后，应将审批标记为 EXPIRED。业务层可以再决定：

  • 通知用户重新发起
  • 重新读取状态并创建新审批
  • 转入人工工单
  • 在明确低风险场景改走确定性路径

不能因为“没人处理”就默认批准，也不能把旧动作原样重新排队而不刷新证据。

2. 取消要传播到所有运行分支

用户取消任务后，需要同时处理：

  • 待审批记录
  • Agent 暂停状态
  • 已排队但未执行的工具消息
  • 并行子 Agent
  • 计划中的后续通知
  • 已经提交但状态未知的副作用

取消不等于回滚。若退款已提交，系统应转入确认或补偿流程，而不是把状态简单写成 CANCELLED。

3. 长时间审批必须重新验证环境

审批可能跨小时甚至跨天。恢复时至少检查：

  • 模型和工具版本是否仍可用
  • 策略是否紧急变更
  • 审批人角色是否被撤销
  • 原始用户授权是否仍有效
  • 资源是否已被其他流程处理
  • 输入 Artifact 是否仍可访问且未被替换

序列化 Agent 状态不能冻结现实世界。恢复动作必须把持久状态与当前事实重新对齐。

十七、责任边界：人批准了，不等于系统免责

审批系统需要把责任拆清。

角色 主要责任 不应承担的责任
产品/业务所有者 定义允许场景、风险容忍度和结果责任 逐条判断底层技术故障
策略所有者 维护硬规则、阈值、额度和职责分离 用规则替代所有领域判断
模型/Agent 团队 提供版本、评测、限制和运行证据 把审批当作模型缺陷的永久遮挡层
工具服务团队 认证授权、幂等、副作用和状态查询 相信模型文本代表授权
审核人 在授权范围内依据展示证据作决定 为隐藏字段、错误界面或系统缺陷背锅
质量与风险团队 独立验证控制有效性、抽样和演练 代替业务所有者接受残余风险

“由人工批准”不能成为免责字段。如果系统展示错误金额、遗漏冲突证据或让无权限人员审核，根因仍是系统控制失效。

十八、三个完整失败案例与排查

案例一：审批 800 元，实际执行 8000 元

场景： Agent 生成 800 元退款，审核人批准。批准后，模型收到一条新消息，重新规划时把金额改成 8000 元，工具层继续复用了旧 approval_id。

现象： 审批记录显示 800 元，支付账本显示 8000 元；Agent 最终回复仍写“已按批准金额退款”。

排查顺序：

  1. 用支付资源 ID 找到实际下游请求。
  2. 比较工具参数摘要和审批 action_digest。
  3. 检查恢复后的 Agent 是否重新生成工具调用。
  4. 检查执行器是否只验证 APPROVED，没有重算摘要。
  5. 对齐审批、重规划、工具提交和支付确认时间。

根因： 审批绑定运行而不是绑定动作，执行器没有实施快照比较。

修复： 将规范化参数、货币、目的地、资源版本和证据摘要写入动作摘要；任何变化创建新审批；支付服务再次执行金额与审核额度校验。

回归： 修改金额、货币、目的地、订单 ID、工具版本和资源版本，旧审批都必须拒绝；只改变无业务意义的 JSON 字段顺序，摘要保持稳定。

案例二：批准率 99.7%，但风险没有下降

场景： 所有退款都进人工队列。工作日峰值每小时约 1800 条，审核人需要在平均 12 秒内处理一条才能清空队列。

现象： 批准率 99.7%，中位处理时长 2.4 秒，夜班和队列积压时批准率更高。上线报告把“人工覆盖率 100%”写成安全成果。

排查顺序：

  1. 按审核人、时段、队列长度和风险等级切分处理时长。
  2. 检查拒绝、修改和升级是否真正改变后续动作。
  3. 加入已知错误的校验样本，测量检出率。
  4. 对比有模型建议与无模型建议的审核准确率。
  5. 访谈审核人，检查页面是否需要切换多个系统取证。

根因： 队列容量与介入范围不匹配，界面把模型建议设为默认批准，审核控制退化为橡皮图章。

修复： 低风险请求改为自动加抽样；高风险请求显示差异和反证；限制连续审批速率；根据风险动态分配领域审核人；把有效干预率和校验样本检出率纳入 SLO。

回归： 在不同队列压力下重复盲测，确认高风险错误检出率不会随积压显著下降，并为超载设置自动收紧或暂停策略。

案例三：两个人批准，实际是同一责任主体

场景： 高额退款要求两人审批。值班经理拥有个人账号和一个共享“财务值班”账号，先后使用两个账号完成批准。

现象： 数据库中有两个不同 actor_id，形式上满足 approval_count == 2；事后无法确定共享账号由谁操作。

排查顺序：

  1. 检查两个身份的稳定人员 ID、认证方式和登录设备。
  2. 检查共享账号策略和 MFA 事件。
  3. 比较两个决定的时间、IP、会话和管理链。
  4. 检查策略是否只按账号字符串去重。

根因： 身份模型把账号当作人员，职责分离没有绑定可问责主体。

修复： 禁止共享账号参与高风险审批；使用稳定 workforce identity；两人必须来自允许的不同职责域；每次决定要求强认证并保存授权快照。

回归： 覆盖账号别名、委托身份、临时角色、同管理链、发起人自批、角色在审批中途被撤销等组合。

2. 指标不能激励错误行为

把“每小时审批数”作为核心绩效，会推动快速点击；把“拒绝率”作为安全指标，会推动无意义拒绝；把“自动率”作为产品目标，会推动阈值放宽。

更合理的是组合结果、成本和控制指标，并对高风险切片设置硬底线。任何效率提升都不能以越权、重复副作用、证据缺失或申诉上升为代价。

二十、人工决定不是天然真值：反馈闭环怎么建立

审批数据看起来天然带有“批准”和“拒绝”标签，因此很容易被直接拿去训练模型或调整阈值。这样做会把人的偏见、界面缺陷和旧策略一起固化进下一版系统。

审核人回答的是“在当时证据和授权范围内是否允许执行”，不一定回答“模型判断是否客观正确”。例如审核人因为客户关系选择特批退款，并不表示模型引用的退款条款正确；审核人因为证据加载失败而拒绝，也不表示请求本身不合规。

1. 把三类标签分开

至少要区分：

标签 回答的问题 典型来源
审批决定 当时是否授权该动作 审核人和审批策略
过程质量 模型、证据和工具过程是否符合要求 独立评测、Trace 和规则
业务真值 最终事实是否证明决定正确 支付账本、申诉、退货完成和后续调查

一条“已批准且退款成功”的记录仍可能存在政策引用错误，只是审核人依据其他事实作出了正确决定。训练任务模型时，应选择与目标事件一致的标签，不能把 approved=1 直接当成 model_correct=1。

2. 记录决定理由，但不要让理由码替代证据

3. 处理选择偏差

进入人工队列的样本本来就集中在低置信、高金额或异常场景。如果只用这些样本评估模型，会高估整体错误率；如果只用自动路径中容易获得的成功结果，又会低估隐藏错误。

更合理的数据设计包括：

  • 从自动路径按风险与置信区间分层抽样复核
  • 为阈值上下两侧保留足够样本
  • 记录每条样本被选择的策略和概率
  • 对没有及时业务真值的记录标记 outcome_pending，不强行贴标签
  • 分开报告人工队列、自动队列和全量估计
  • 阈值实验使用受控灰度，避免同时改变模型、界面和策略

当抽样概率不同，需要在统计估计中使用适当权重，并报告有效样本量。不能把过采样的高风险数据按原始条数直接当作生产分布。

4. 处理审核人分歧

对同一快照进行盲审，可以估计任务本身是否具有清晰标准。分歧应按原因拆开：

  • 政策文本含糊
  • 证据不足
  • 审核人领域知识不同
  • 界面展示不一致
  • 允许合理裁量
  • 某位审核人持续偏离校验集

不能简单用多数票制造真值。高风险争议样本应由独立领域专家裁决，并保留原始分歧；允许裁量的场景可以将标签定义为分布或多种可接受动作，而不是强迫唯一答案。

5. 延迟真值要能回填原运行

退款是否正确可能要等客户申诉、商品回收或财务对账后才能确认。回填记录至少包含：

6. 反馈数据也要经过隐私与安全治理

审批备注可能包含身份证号、电话、病史、内部账号或审核人的主观评价。进入评测集或训练集前要重新执行数据最小化、授权、脱敏、保留期和删除传播。审核人为了完成业务写下的备注，不自动获得“可用于模型训练”的用途授权。

最终的反馈闭环应该把人工介入当作一个需要评测的数据生成过程：既测审核正确性，也记录样本选择机制和标签来源。只有这样，阈值调整才是在减少真实风险，而不是让下一版模型更像上一版审核流程。

二十一、故障演练：人工介入链路也要定期注入故障

演练一：策略服务不可用

注入： 高额退款请求到达时，策略服务持续返回超时。

期望： 支付工具不执行；请求标记为策略基础设施错误或升级；用户看到明确延迟状态；恢复后重新读取当前订单，不直接复用旧决定。

证据： 工具调用计数为零、策略错误类型、升级工单、恢复后的新资源版本。

演练二：审批期间资源变化

注入： 第一位审核人批准后，由另一路径完成退款并把订单从 rv-188 更新到 rv-189。

期望： 第二位审核或执行时发现版本冲突；旧审批不能执行；系统查询现有退款并收敛到“已处理”。

演练三：审计存储不可用

注入： 决策事件写入独立审计域失败。

期望： 高风险动作按策略失败关闭或进入可靠本地 Outbox；不能先执行再丢证据；Outbox 恢复后顺序补写且能验证完整性。

低风险只读动作可以采用不同策略，但必须事先写清降级边界。

演练四：审核队列超载

注入： 将高风险请求突增到平时五倍，并让一半审核人不可用。

期望： 不降低高风险审批要求；低优先级请求明确延迟；暂停非关键自动任务；触发值班扩容和用户通知；超时请求变为 EXPIRED。

演练五：旧审批重放

注入： 捕获一个已执行审批引用，在新会话、不同租户和过期时间后分别重放。

期望： 因终态、租户、摘要、audience 或有效期失败；下游幂等键不产生第二个业务对象。

演练六：校准漂移

注入： 在影子流量中增加一个历史校准集未覆盖的新语言和新政策表达。

期望： 分布外比例和可靠性偏差告警；自动覆盖收紧；新切片进入标注和校准流程，而不是用全局平均掩盖。

每次演练都应记录首错时间、控制触发时间、最大影响、人工响应时间、恢复条件和遗留风险。只验证“最后没出事故”无法说明是哪一层控制起效。

二十二、什么时候不应该强行加入同步人工审批

1. 人无法在时间窗口内作出更好判断

毫秒级风控、机器控制和大规模流式过滤可能没有同步人工窗口。这时更适合 Human-in-command 设定边界、Human-on-the-loop 监督、确定性保护和事后抽样，而不是制造一个无法兑现的按钮。

2. 审核人拿不到独立证据

如果页面只展示模型结论和模型理由，人没有额外数据、领域知识或授权，审批不会自然提升质量。应先改善证据、工具和职责，再决定是否保留人工节点。

3. 硬禁止可以直接自动拒绝

明确越权、非法参数、跨租户和超过系统上限的请求应由确定性控制拒绝。把它们交给人工容易形成绕过硬规则的渠道。

4. 可逆低风险动作适合自动加抽样

例如保存内部草稿、查询公开信息或创建不外发的建议，可以自动执行并按风险抽样。同步审批成本可能高于动作风险。

5. 高风险领域不能只依赖通用审核人

医疗、信贷、招聘、保险、司法和关键基础设施可能需要特定资质、解释、申诉和记录要求。一个普通客服点击确认不等于满足领域监督义务。具体设计应由领域、法律、合规和受影响群体共同评估。

二十三、从 0 到 1 的落地顺序

阶段一：先收紧高风险动作

  1. 建立工具和动作清单。
  2. 标记副作用、权限、金额、数据和可逆性。
  3. 写出不可越过的硬规则。
  4. 为高风险工具增加执行前审批。
  5. 绑定规范化参数、资源版本、有效期和幂等键。

这一阶段宁可覆盖范围小，也要证明审批确实能阻断动作。

阶段二：建立证据和状态机

  1. 实现六态审批模型和合法迁移。
  2. 保存审批快照、决定事件和执行结果。
  3. 处理超时、取消、恢复和重复消息。
  4. 增加单人额度、双人审批和职责分离。
  5. 建立故障注入与并发测试。

阶段三：校准并释放低风险流量

  1. 收集具有真实结果的历史样本。
  2. 按业务和风险切片校准任务分数。
  3. 影子比较新旧策略与队列容量。
  4. 只扩大可逆、可观测、证据完整的自动范围。
  5. 保留随机抽样和自动收紧机制。

阶段四：持续治理

  1. 监控自动化偏见和审核疲劳。
  2. 定期复核阈值、角色、额度和保留期。
  3. 将线上错误转成策略与回归样本。
  4. 演练策略故障、身份故障、队列超载和重放。
  5. 让业务所有者定期确认残余风险是否仍可接受。

二十四、上线前检查清单

场景与风险

  • 每种动作都记录影响范围、可逆性、权限、金额和数据敏感度
  • 硬禁止与可裁量风险明确分开
  • 风险阈值按业务、租户和地区版本化
  • 自动路径只覆盖已证明可接受的风险切片
  • 系统级暂停和回滚责任人明确

置信度与证据

  • 每个分数都定义了预测事件，不称未经验证的分数为正确概率
  • 校准集、模型版本、Prompt 版本和适用切片可追溯
  • 同时报告覆盖率、选择性风险、样本量和漂移
  • 证据完整度由来源、版本、新鲜度和冲突规则计算
  • 权限和硬规则不会被置信度覆盖

审批点与界面

  • Plan、Tool、Result 和 Exception 的职责没有混用
  • 副作用动作在执行前暂停
  • 审核人看到规范化参数、差异、反证和缺失证据
  • 批准不是默认选项，高风险决定有结构化原因
  • 监控审批疲劳、异常速度和校验样本检出率

状态与并发

  • PENDING/APPROVED/REJECTED/EXPIRED/CANCELLED/EXECUTED 语义明确
  • 终态不会被恢复成可执行状态
  • 双人审批验证稳定人员身份和职责分离
  • 并发领取只能有一个执行者成功
  • 取消和超时会传播到 Agent、队列和工具分支

TOCTOU 与防重放

  • 审批绑定工具、参数、租户、资源版本、证据摘要和有效期
  • 执行时重新鉴权、重新检查策略和业务不变量
  • 下游副作用支持稳定幂等键与结果查询
  • 已执行、已拒绝和已过期审批不能重放
  • 提交状态未知时进入查询或对账，不盲目换键重试

审计与责任

  • 决策事件、审批证据和执行证据能够关联同一 Trace
  • 审核页面版本和展示字段可追溯
  • 敏感 Artifact 使用独立权限、加密和保留策略
  • 审计链的防篡改边界和密钥责任明确
  • 审核人、策略所有者、工具团队和业务所有者责任清楚

测试与演练

  • 决策表、单调性、变形、状态机和并发测试进入 CI
  • 覆盖策略不可用、身份不可用、审计不可用和队列超载
  • 覆盖审批后参数变化、资源变化和角色撤销
  • 使用已知错误的校验样本测量人工控制有效性
  • 每次真实事件都沉淀为最小复现样本和故障演练

二十五、小结

Human-in-the-loop 的目标不是把责任转移给一个按钮后面的人，而是让系统在风险真正需要人类判断或授权的节点停下来，并给人足够、独立、可理解的证据。

完整设计应形成下面这条闭环：

  1. 用影响、可逆性、权限、金额和数据敏感度确定动作固有风险。
  2. 用硬规则先守住不可越过的权限与业务边界。
  3. 用证据完整度、经过校准的不确定性和分布外信号选择自动、复核、审批或升级。
  4. 把审批绑定到规范化动作快照，而不是模糊的 Agent 运行。
  5. 用明确状态机处理批准、拒绝、过期、取消和执行。
  6. 执行前重新鉴权和比较资源版本，控制 TOCTOU。
  7. 用一次性消费、下游幂等和最终状态查询防止重放与重复副作用。
  8. 同时测量队列效率、人工判断质量和控制是否真正阻断错误。
  9. 保存足以重建决定与业务结果的审计证据。
  10. 通过故障注入和定期演练验证人工链路在压力下仍然有效。

最终需要证明的不是“每个高风险请求都有人点过同意”，而是：

系统知道什么风险需要人介入，人知道自己批准的确切动作，批准后的任何变化都会使旧授权失效，而且每次决定与执行都能被独立复核。
