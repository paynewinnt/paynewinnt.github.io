AI测试-27-Context Engineering怎么管理指令知识工具结果和Token预算

发表于 2026-04-08 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:02

Context Engineering 最容易被简化成一句话：模型窗口变大以后，把更多资料放进 Prompt。

这个理解把工程目标正好反了过来。

Anthropic 在《Effective context engineering for AI agents》中把 context 定义为模型采样时包含的 Token 集合，并把 Context Engineering 描述为在推理期间持续选择和维护这些 Token 的策略。它管理的不只是 System Prompt，还包括消息历史、长期记忆、检索片段、工具结果、工作状态、示例和协议字段。

因此，Context Engineering 不是“把 Prompt 写长”，而是回答下面这些可执行问题：

  • 本轮采样到底需要哪些信息；
  • 每条信息从哪里来，谁有权提供；
  • 它是指令、事实、证据、历史记录，还是未经验证的外部文本；
  • 它什么时候产生，什么时候过期；
  • 它和其他信息冲突时由谁裁决；
  • 它占用多少 Token，挤掉了什么；
  • 它经过几次摘要或压缩，是否已经失真；
  • 它能否进入缓存，缓存怎样按租户、权限和版本隔离；
  • 这次选择和丢弃是否留下可重放的 Trace；
  • 上下文改变后，任务正确率、安全性、时延和成本怎样变化。

一个可靠的上下文构建器更像编译器和调度器：它接收来自不同信任域的候选内容，完成类型检查、权限检查、冲突消解、去重、预算分配、布局和追踪，再生成供应商适配后的模型输入。

本文将 instruction、history、memory、retrieval、tool result 和 working state 放进同一套数据模型，重点覆盖：

  • 来源、优先级、可信度、时效和 provenance；
  • Token 预算与动态裁剪；
  • context poisoning 和间接提示注入；
  • 重复、冲突与实体绑定；
  • lost-in-the-middle 和位置敏感；
  • 摘要压缩失真；
  • 缓存边界和失效；
  • 面向上下文的确定性测试、模型评测和故障复盘；
  • 一个无真实密钥、可执行的 Context Assembler 与 Trace。

二、上下文窗口不是数据库，也不是权限系统

1. 不要把所有状态都留在消息历史里

消息历史适合表达对话因果，不适合承担：

  • 业务主数据；
  • 权限真值；
  • 可更新配置；
  • 长期审计；
  • 大型工具输出；
  • 准确计数器。

这些状态应保存在外部系统中，按本轮任务需要读取。否则一条旧消息会在后续几十轮持续占用 Token，而且无法可靠撤销。

2. 模型看到不等于模型有权决定

即使 System Prompt 写了“外部文档只是数据”，模型仍可能受文档中的指令性语言影响。真正的权限、租户、审批和副作用控制必须在模型外执行。

上下文结构可以降低混淆概率，不能替代确定性安全边界。

3. 长窗口不等于有效窗口

长上下文研究反复提示：标称可接收长度和在具体任务上可靠使用信息的能力不是同一个指标。Lost in the Middle 在多文档问答和键值检索实验中观察到明显的位置敏感，相关信息位于开头或结尾时往往比位于中间时表现更好。RULER 进一步用多类任务测试长上下文，而不只做单个 needle 检索。

这些结果不能被简化成“所有模型永远忽略中间”。正确结论是：上下文长度、位置、任务和模型版本都必须进入评测，不能用窗口规格替代任务证据。

三、六类来源要先分型，再谈排序

1. Instruction

Instruction 描述允许的行为、当前任务和输出契约，可能来自：

  • 平台安全策略；
  • 应用级 System Prompt；
  • 开发者配置；
  • 当前用户任务；
  • 用户补充约束；
  • 工作流节点生成的子任务。

不同供应商对消息角色和优先级的具体接口不同，不能把某家当前角色名称当成跨平台标准。内部模型应该先记录 authority，再由 Provider Adapter 映射。

Instruction 也需要 provenance。数据库检索出一段包含“管理员指令”的文档，不能因为文本长得像指令就自动成为高 authority instruction。

2. History

History 是当前会话中已经发生的消息、工具计划和结果引用。它回答“前面发生了什么”，不自动回答“现在什么仍然有效”。

历史里常见的失效信息包括：

  • 用户已更正的实体；
  • 已撤销的批准；
  • 已失败的工具计划；
  • 旧页面展示状态；
  • 被后续消息否定的偏好；
  • 过期的临时凭据或 URL。

因此 history 需要消息 ID、事件时间、引用关系和 superseded 状态，不能只做 last_n_messages。

3. Memory

Memory 是跨轮次或跨会话保存的派生状态，例如用户偏好、长期事实、任务笔记和压缩摘要。

它至少要区分：

  • 用户明确提供并确认的事实；
  • 系统从业务数据库读取的事实；
  • 模型从对话中推断的偏好；
  • 模型生成的摘要；
  • Agent 自己写下的计划或笔记。

这些来源的可信度不同。模型推断的“用户喜欢英文回答”不能覆盖用户本轮明确要求中文；摘要里写的“退款已批准”不能替代审批系统状态。

Memory 必须可查看、可更正、可撤销、可过期，并保留父事件引用。

4. Retrieval

Retrieval 包括向量检索、关键词检索、数据库查询和搜索返回的知识片段。

每个片段至少带上：

  • corpus 和 document ID；
  • 文档版本与 Chunk ID；
  • 来源 URI；
  • 发布、观察和索引时间；
  • ACL 与租户；
  • 检索分数类型和 rank；
  • 内容摘要；
  • 是否为外部不可信内容。

相关性高不等于可信度高，也不等于时效高。一个恶意文档可以和问题高度相关；一个旧政策也可能在语义上完美匹配。

结构化字段可以根据工具身份和服务端签名获得较高事实可信度，但自由文本仍可能由外部用户控制，并携带间接提示注入。不能因为文本来自“已注册工具”就把它提升为可信指令。

大结果还要按需读取。数据库返回一万行、终端返回完整构建日志或浏览器返回整页 HTML，不应该直接原样回灌。

6. Working State

Working State 是当前任务的外部化工作记忆，包括：

  • 目标和成功条件；
  • 当前计划；
  • 已完成步骤；
  • 未决问题；
  • 当前实体和版本；
  • 已获取证据引用；
  • 待执行动作；
  • 风险、批准和停止条件。

它应尽量结构化并由执行器维护。模型可以提出更新，但状态转换要经过校验。否则模型一句“已经完成测试”就会把未执行步骤标记为完成。

四、优先级、可信度、相关性和时效不是同一个分数

第一版 Context Assembler 经常给每条内容计算一个综合分，然后从高到低塞入窗口。这个做法会把不可比较的属性混在一起。

1. Authority

Authority 表示谁有权规定行为。

示例：平台安全策略高于普通用户请求；但安全策略不能凭空改写订单金额，订单金额应来自业务真值系统。

2. Trust

Trust 表示事实可靠程度。

一个已认证订单 API 返回的金额可以高可信，但它仍然是数据，不是指令。一个用户任务具有合法用户 authority，但用户对“系统已经退款”的陈述未必是业务真值。

3. Relevance

Relevance 表示内容对当前任务有多大帮助。

攻击文档可以高度相关。相关性只决定是否值得作为候选证据，不能提升权限。

4. Freshness

Freshness 表示信息是否仍在有效期内。它需要至少三个时间：

  • 事件实际发生时间；
  • 系统观察或写入时间；
  • 当前版本生效时间。

只看 updated_at 可能把迟到写入的旧事件当成最新事实。

5. Provenance

Provenance 表示内容的来源链：谁产生、通过什么连接器进入、经过哪些变换、引用哪个原始对象。

6. Token cost

Token cost 是把这条信息放进上下文的资源价格。两个相关性接近的候选，一个 80 Token，一个 8,000 Token，选择策略显然不同。

7. Sensitivity

敏感级别决定内容是否允许发给当前模型、区域和供应商。某条内容再相关，只要数据处理边界不允许，就必须在组装前删除或替换为受控引用。

这张图的核心是：内容先保留类型和来源，再进入预算竞争。不能先把所有内容拼成字符串，再试图从文本里恢复优先级。

Trace 不适合直接保存所有原文。Context Item 可以在受控 Artifact 中保存内容，组装 Trace 只记录引用和摘要。

摘要用于验证“评测时用的是不是同一内容”，不能冒充脱敏。低熵内容仍可能被枚举，敏感数据还要有权限、加密和保留策略。

六、Instruction 管理：高 authority 也不能无限增长

1. 把指令按职责拆开

建议至少分成：

拆分后，某个业务模板更新不会导致整套平台策略失去版本信息。

2. 不要把确定性业务逻辑写成 Prompt if-else

“金额大于一万元必须审批”应由执行器校验。Prompt 可以告诉模型需要审批，真正动作仍要检查金额和审批令牌。

把所有业务规则写进长 System Prompt 会产生：

  • 规则冲突难以发现；
  • 每次调用都付 Token 成本；
  • 模型可能漏掉中间规则；
  • 修改规则需要重新评测全部行为；
  • 无法提供确定性安全保证。

3. 当前用户任务不是低价值尾部文本

在长 Agent 循环中，当前任务可能被旧历史和工具输出淹没。Working State 应重复表达经过确认的当前目标，但不能用不同措辞复制多份，避免产生细微冲突。

更合适的方式是让当前任务有稳定 ID，Working State 引用它，并在组装 Trace 中标记为 mandatory。

4. 指令版本要进入缓存键和评测指纹

平台策略、工具 Schema 或输出契约变化后，旧缓存不能继续命中。每次运行要能回答使用了哪一版指令，而不是只保存渲染后的长字符串。

七、History 管理：保留因果，不保留全部噪声

1. 消息和事件分开

一个工具调用往往产生：模型提议、权限判断、实际调用、结果、重试和最终状态。把这些都压成两条 assistant/tool message，会丢失因果。

外部 Trace 保存完整事件；模型上下文只选择完成下一步所需的简化视图。

2. 状态更新使用 supersedes

用户先说“订单 A”，后更正为“订单 B”时，不应该只依赖后来的消息位置。可以记录：

3. 工具原始输出完成使命后可以降级为引用

如果后续只需要“测试失败在 case_17，证据位于 artifact_x”，就不必继续携带几千行日志。保留结构化结论、证据引用和未解决问题即可。

但在结论尚未验证前，不要让模型自己写一个摘要后立即删除唯一原始证据。摘要与原文应在一段时间内可对照。

4. last_n 只能作为兜底

最近消息不一定最重要，旧消息也不一定仍有效。更合理的保留依据包括：

  • 当前任务直接依赖；
  • 尚未解决；
  • 定义了关键实体；
  • 是工具调用的必要父事件；
  • 用户明确要求保留；
  • 与安全或审批有关。

八、Memory 管理：每条记忆都要能撤销和追根

1. 写入前先定义类别

可以分成：

  • user_declared：用户明确陈述；
  • business_fact：业务系统读取；
  • inferred_preference：模型推断；
  • task_note：Agent 为当前长期任务记录；
  • compaction_summary：从历史压缩得到；
  • operator_override：人工修正。

2. 推断记忆要低权并有置信边界

用户连续使用三次中文，不代表可以永久保存“只接受中文”。这类偏好可以影响排序，但不能覆盖本轮明确请求。

3. 记忆读取也要做 ACL

跨会话记忆可能包含敏感信息。会话 ID 相同不代表当前调用主体仍有权限。每次注入模型前重新校验主体、租户、用途和供应商数据边界。

4. 记忆冲突不能静默选最后一条

用户资料、业务系统和模型摘要对同一事实冲突时，需要按事实域定义权威源。比如收货地址可以由用户本轮确认覆盖偏好记忆，但订单已支付金额只能由订单系统给出。

5. 记忆删除要传播到派生摘要和缓存

删除原始 memory row 后，如果摘要、向量索引、响应缓存和 Prompt Cache 仍引用它，删除并没有真正生效。Provenance 图要支持反向查找派生物。

九、Retrieval 管理：Top-K 不是上下文策略

1. 检索前先做授权

先在允许语料范围内检索，再排序。不能先跨租户召回，最后只在 Prompt 展示层过滤；候选日志和缓存已经可能泄漏信息。

2. Rank 和 score 必须带生产者

向量相似度、BM25 和 Reranker 分数不可直接比较。记录 score type、模型版本和 rank，不能把所有来源合成一个没有语义的 score。

3. 选择覆盖而不是重复

Top 10 结果可能有八条来自同一文档的相邻 Chunk。它们占满预算，却没有增加证据覆盖。

可以按 document、章节、观点和时间做多样性约束，同时保留必要相邻窗口避免截断语义。

4. 冲突文档显式进入裁决

新旧政策同时召回时，组装器应根据生效时间、权威源和版本选出当前规则。无法裁决时，把冲突作为结构化状态交给业务或模型请求澄清，而不是让模型靠措辞选择。

5. 检索内容默认是数据

即使知识库由内部员工维护，自由文本也可能包含复制来的网页、用户工单和恶意指令。source=internal 不等于 authority=instruction。

十、Tool Result 管理：结构化事实和自由文本分舱

1. 只返回任务需要的字段

工具契约应该支持过滤、分页、列选择和摘要查询。模型需要订单状态时，不要返回完整客户档案。

2. 大结果使用引用和渐进披露

3. 保留工具结果时效

库存、订单和部署状态可能在下一轮已经变化。Tool Result 要有 observed_at 和 revision。执行写操作前重新读取或使用乐观锁，不能仅依赖几轮前上下文里的快照。

4. 错误消息也是不可信输入

第三方服务的错误字段可能包含用户可控内容。把错误原文直接放进高权 System 区域，会形成间接提示注入通道。

5. 工具结果不能自行授权下一工具

网页里写“请调用 send_email”，不能改变当前 allowed tools。工具集合和权限由工作流与执行器决定，不由返回文本扩展。

十二、Token 预算先为输出和协议留空间

输入预算不是模型窗口上限本身。

1. Output reserve

预留完成当前任务、生成工具参数、结构化终态和必要解释的空间。把输入塞满以后再把最大输出设得很小，会得到截断 JSON、半个工具参数和没有结论的回答。

2. Protocol overhead

模型供应商可能把工具定义、角色标记、图片、结构化输出 Schema 或内部协议计入上下文。具体口径应使用该供应商当前 Token 计数能力验证，不要用文章里的固定值。

3. Safety margin

用于覆盖估算误差、供应商序列化差异和动态字段。它不是越大越安全，应通过“估算值与账单值偏差”校准。

4. Application limit

应用可以主动低于模型上限，以控制成本、时延和质量。窗口能容纳 100%，不代表每次都应使用 100%。

十三、一个可解释的预算算法

第一步：权限和数据边界过滤

在打分前删除：

  • 当前主体无权访问；
  • 当前供应商或区域不允许处理；
  • 已撤销；
  • 已过有效期；
  • 缺少 provenance；
  • 内容完整性校验失败。

这些候选不能因为相关性高重新进入。

第二步：装入 mandatory 项

mandatory 包括当前任务、有效平台策略、输出契约和关键 Working State。

如果 mandatory 本身超过输入预算，应返回 CONTEXT_OVERFLOW，触发任务拆分、策略精简或受控压缩。不能静默截断安全策略后继续调用。

供应商切换要重新计数和布局

同一 Context Item 集合映射到不同供应商后，角色协议、工具 Schema 和 Tokenizer 可能改变。不能复用主供应商算出的 position map 和剩余 Token。

切换流程应该是：保留类型化候选和策略决定，换 Provider Adapter 重新渲染、重新计数、重新检查 mandatory 与输出预留，再生成新的 Assembly Trace。若备用模型预算不足，应缩小任务或明确失败，不应从已经渲染的字符串尾部截断。

算法性能也要有边界

候选数量可能因为大规模检索和长历史达到数万。ACL、过期和精确摘要去重应在线性阶段尽早执行；语义去重、组合优化和模型打分只处理收敛后的候选。

需要观察：候选数、过滤后数量、冲突组数、打分耗时、Token 计数耗时和总 assembly latency。Context Assembler 本身过慢时，模型还没收到请求，用户 deadline 已经被耗掉。

十四、冲突管理不能只依赖消息顺序

1. 先按事实域定义权威源

conflict key 首选权威源 可覆盖条件
订单金额 订单服务当前 revision 不能由自由文本覆盖
用户本轮语言 当前用户明确输入 覆盖推断偏好
安全策略 已签名平台配置 只能由新策略版本替换
文档政策 正式发布且当前生效版本 草稿不能覆盖正式版
工具执行状态 工具服务或业务数据库 模型声明不能覆盖

2. 时间不能单独决定权威

一条刚刚索引的旧政策，observed_at 很新，但 effective_at 已过期。一个攻击者刚上传的文档，也不能因为最新就覆盖平台规则。

3. 相同权威、相同时间的冲突应失败显式化

如果两个同级系统对同一 key 给出不同值，而且没有版本或事务证据裁决，应停止自动动作并记录 UNRESOLVED_CONFLICT。

4. 重复不等于冲突

同一事实由两个独立可信来源确认，可以合并内容并保留两个 provenance。不能为了省 Token 把来源证据全部丢掉。

5. 实体绑定优先于语言相似

“上一个订单”“这个环境”之类指代必须绑定到稳定实体 ID。Context Assembler 应携带绑定结果和来源，不能让模型只凭相邻文本猜测。

十五、Context Poisoning：污染内容不需要成为 System Prompt 也能影响行为

Context poisoning 包括：

  • 知识库被植入错误或恶意文档；
  • 网页、邮件、工单和代码注释包含间接指令；
  • 工具自由文本诱导模型调用其他工具；
  • 旧记忆或错误摘要持续传播；
  • 缓存把一个租户或权限域的内容带到另一个请求；
  • 多个看似无害片段组合后形成攻击指令。

PoisonedRAG 的原始研究展示了知识库本身可以成为攻击面：攻击者向检索库注入少量构造文本，就可能诱导 RAG 系统对目标问题产生攻击者选择的答案。这说明检索相关性不能承担内容真实性和安全授权。

1. 保留 trust label 到最终序列化

数据进入 Context Item 时的 external_untrusted 标签不能在摘要、重排或工具转发后丢失。

2. 转义不能消除语义注入

把 HTML 转义、把文本放进 JSON 或 XML 标签，可以解决语法边界和解析问题，但模型仍然能读懂其中“忽略之前规则”的语义。结构化包装是降低混淆的一层，不是完整防御。

  • 污染片段是否被召回；
  • 是否被错误提升为 instruction；
  • 摘要是否去掉了来源警告；
  • 是否挤掉可信证据；
  • 模型是否提出越权动作；
  • 执行器是否阻断；
  • Trace 是否能定位传播步骤。

Lost in the Middle 的价值不是提供一个固定排版秘方，而是提供位置敏感的实验方法。

1. 建立位置扫描

对同一个问题、同一份证据和相同总长度，把关键证据放在：

  • 事实提取正确率；
  • 引用正确率；
  • 多跳推理完成率；
  • 工具参数正确率；
  • 拒答与安全边界；
  • 输出稳定性。

2. 控制干扰变量

位置测试要保持：

  • 总 Token 数一致；
  • 干扰文档集合一致；
  • 仅改变顺序；
  • 模型与参数一致；
  • 候选和基线使用相同随机策略；
  • 记录实际 Tokenizer 后的位置。

3. 不把关键安全约束只放在一个“黄金位置”

安全边界不能依赖模型一定关注开头或结尾。关键控制仍在执行器。上下文里的策略可以采用清晰、紧凑、稳定布局，但不是安全证明。

4. 不盲目复制关键内容

复制可以提高某些位置的可见性，也会增加 Token、制造版本不一致，并让缓存失效。优先减少噪声、提高证据排序和缩小任务，再用评测决定是否需要受控重复。

5. 长上下文评测不能只有 Needle

单个字符串检索通过，不代表模型能完成多文档整合、时间排序、冲突判断和多跳推理。RULER、LongBench 等原始工作提供了更丰富的长上下文任务思路。业务评测还要加入自己的工具和安全结果。

十七、压缩和摘要：摘要是有损派生数据

Anthropic 的 Context Engineering 文章把 compaction、结构化笔记和子 Agent 作为长时任务的策略，并明确提示过度压缩可能丢失后来才显出重要性的细节。

1. 不要覆盖原历史

摘要写成新的 derived Artifact：

原事件按保留策略存放，摘要通过 parent range 追溯。

2. 先结构化，再生成叙述摘要

优先提取：

  • 当前目标；
  • 不可违反约束；
  • 已确认事实和来源；
  • 已做决策和理由；
  • 已完成动作和证据；
  • 未解决问题；
  • 失败尝试及为什么失败；
  • 当前实体和版本；
  • 审批、风险和回滚条件。

叙述性摘要可以帮助模型理解，但关键字段不应只存在于自由文本里。

3. 防止摘要代际失真

摘要的摘要会逐代丢信息。应记录 compression_generation，定期从原始事件重新生成，而不是永远从上一代摘要继续压缩。

4. 高风险事实保留证据引用

金额、权限、批准和外部动作状态不能只保存模型改写句。至少保留业务对象 ID、revision、原始结果引用和验证时间。

5. 摘要测试

对压缩前后分别运行：

  • 必要事实问答；
  • 未决项枚举；
  • 约束遵循；
  • 实体一致性；
  • 决策理由还原；
  • 污染标签保留；
  • 时间顺序；
  • 工具执行状态。

压缩率高不是单独的成功指标。摘要更短但漏掉一个不可逆动作审批，属于失败。

十八、动态裁剪：按任务阶段释放上下文

Agent 不同阶段需要不同内容。

1. 规划阶段

需要目标、边界、工具能力和高层环境信息，不需要所有工具原始输出。

2. 执行阶段

需要当前步骤、具体输入、最近工具结果和失败恢复信息，不需要大段已完成历史。

3. 验证阶段

需要成功条件、变更摘要、测试证据和剩余风险，不需要完整探索过程。

4. 收尾阶段

需要最终状态、未完成项和可交付物引用，不需要所有中间日志。

动态裁剪可以按阶段给 lane 调整预算。重要的是阶段由工作流状态决定，不能仅让模型自由宣称“已经进入验证阶段”。

大工具结果的释放规则

当工具结果已经被提取成结构化事实，并且事实引用原 Artifact，可以把原内容从热上下文移除。但下面情况应保留：

  • 仍在排查；
  • 摘要尚未验证；
  • 后续步骤需要精确行号或原文；
  • 存在冲突；
  • 高风险决策需要人工复核。

十九、缓存边界：命中率不能优先于权限和版本

上下文系统至少有四种缓存。

1. Retrieval cache

缓存查询结果。键至少考虑：规范化查询、语料快照、索引版本、过滤条件、租户和 ACL policy。

只按 query 文本缓存，会把旧索引、其他租户或不同权限的文档带入当前请求。

2. Context assembly cache

缓存候选选择或渲染结果。键需要包含：

  • assembler policy version；
  • Instruction 和工具 Schema digest；
  • Tokenizer 与预算；
  • 主体、租户和权限范围；
  • memory/history/state revision；
  • retrieval snapshot；
  • 供应商和模型适配版本。

3. Provider prompt cache

供应商可能支持前缀缓存，但命中条件、生命周期、计费和数据处理会变化。Anthropic 官方 Prompt Caching 文档展示了基于前缀和 breakpoint 的具体产品机制；这类机制适合把稳定内容放在前缀，但不能被当成所有模型 API 的通用标准。

应用仍要自己保证：

  • 稳定前缀没有混入租户动态数据；
  • 策略、工具和 Schema 更新会失效；
  • 缓存使用符合当前数据治理；
  • usage 中的 cache 字段按供应商原始语义记录；
  • SDK 或产品默认值变化不会悄悄改变边界。

4. Response cache

直接复用最终回答风险更高。键必须包含完整业务语义和数据版本；涉及实时状态、个人数据和副作用时，通常不适合简单缓存。

5. 缓存不能提升 authority

命中缓存只说明以前计算过，不说明内容仍正确、仍授权、仍在有效期。读取后仍要做当前权限和时效检查。

6. 失效要沿 provenance 传播

文档撤回、用户删除记忆、策略升级或工具 Schema 变化后，需要找到依赖它的 retrieval cache、summary、assembly cache 和 response cache。没有依赖图时，只能等待 TTL，风险窗口不可控。

上下文会经过解析、切片、检索、重排、摘要、合并和缓存。如果只记录最初的文档 ID，后续无法知道当前句子究竟经历了什么变换。

2. 一条信息至少有四个时间

索引重建会让 observed_at 很新，但不会让旧政策重新变成有效。迟到事件也可能在今天写入，却描述昨天已经被替代的状态。

对动态业务状态，还要记录 revision 或 ETag。时间只能辅助排序，revision 和业务有效期才是并发更新与版本裁决的主要证据。

3. Trust 变换必须有规则

未经验证的网页经过摘要后，摘要仍然源自未经验证内容。Parser 成功只证明格式被读取，不证明事实正确；Reranker 把它排第一也只表示相关。

Trust 可以因确定性验证提升，例如：

  • 数字与已认证业务 API 对账一致；
  • 文档签名有效且发布者在允许清单；
  • 两个独立权威源一致；
  • 人工审核完成并有审核记录。

提升动作本身要形成 provenance edge。不能让摘要器在输出里写“已验证”后自动修改 Trust。

4. Provenance 断链应怎样处理

如果一个摘要只有文本，没有父事件和来源版本，高风险任务不应把它当作可执行事实。可以：

  • 降低 Trust，只用于辅助理解；
  • 回源重新读取；
  • 要求人工确认；
  • 在无法回源时从上下文删除；
  • 让最终回答明确标记证据不足。

5. 删除和撤销沿图传播

删除源对象后，系统要枚举：

不同存储的保留法规可能不同，但在线推理路径至少要停止继续注入已撤销内容。传播任务要有状态、重试、截止时间和遗漏告警，不能只发一个“清缓存”消息就认为完成。

6. Provenance 的测试

  • 每个 selected item 都能走到原始对象；
  • 任一 transform 版本可查；
  • 修改 Chunker 后旧、新 lineage 不混用；
  • 摘要保留所有关键 fact 的 parent ID；
  • 外部不可信内容经过多次变换后 Trust 不会自动升级；
  • 撤销源对象后，在线 Assembly 在约定时间内不再选择派生项；
  • 回源失败有明确降级，不静默沿用无来源摘要。

二十一、多 Agent 不等于共享一份无限上下文

多 Agent 架构常被用来绕开单窗口限制：子 Agent 在独立上下文里深入探索，再把结果交给主 Agent。Anthropic 的 Context Engineering 文章也把子 Agent 作为长时任务的一种策略。

它解决了上下文隔离问题，同时引入新的来源、权限和摘要边界。

1. 委派使用结构化 envelope

主 Agent 不应把完整会话不加选择地转给子 Agent。最小委派契约可以是：

权限和 Token 预算由执行器注入，不能让子 Agent 从自然语言中自行扩展。

2. 子 Agent 输出是派生证据，不是高权指令

子 Agent 返回“应该删除数据库”时，这只是建议。主 Agent 和执行器仍要检查当前任务、证据、权限和审批。

结果至少附带：

  • subtask ID；
  • 使用的来源与版本；
  • 输出摘要；
  • 证据引用；
  • 未解决项；
  • 子 Agent 模型和 Prompt 版本；
  • 实际 Token 与工具调用；
  • 是否接触不可信内容。

3. 不要让子 Agent 只返回一段无来源总结

主 Agent 如果看不到证据引用，就无法区分可靠发现和子 Agent 幻觉。可以要求每个结论关联 source item，并由主 Agent按需回源。

4. 并行结果要做冲突合并

两个子 Agent 对同一根因给出不同结论时，不能按返回顺序覆盖。把它们作为相同 conflict_key 的候选，比较证据质量；无法裁决时保留分歧并继续验证。

5. 防止污染跨 Agent 放大

一个子 Agent 读取恶意网页后，摘要里可能继续携带注入指令。Trust 和 taint 标签必须随返回结果传播。主 Agent不能因为内容来自“自己的子 Agent”就把它放进高 authority 区域。

6. 多 Agent 测试

  • 子 Agent 只收到最小必要来源；
  • 禁止工具在其运行时不可见或不可执行；
  • 返回结论都有证据引用；
  • 两个并行结论冲突时不会静默覆盖；
  • 子 Agent 中的污染文本不会提升 authority；
  • 主 Agent 取消任务后，子任务停止或进入可追踪终态；
  • 所有子任务 Token 总和进入全局预算；
  • 子 Agent 摘要失败不会被当成“没有发现问题”。

多 Agent 能把详细探索隔离在局部窗口，但不会自动降低总成本。主任务预算应统计所有子调用、工具结果和失败重试。

二十二、从字符串拼接到 Context Platform 的演进顺序

一次性重写完整上下文平台风险很高。更可控的方式是按证据能力逐步演进。

阶段 0：先盘点真实上下文

在不改变行为的前提下，记录当前每次调用包含：

  • System 和开发者指令；
  • 消息历史条数；
  • memory 来源；
  • 检索 Chunk；
  • 工具 Schema 和结果；
  • 各部分实际 Token；
  • 截断发生位置；
  • 模型与 Prompt 版本。

这一步能发现隐藏输入，例如 SDK 自动携带的历史、工具框架注入的说明和代理层追加字段。

阶段 1：类型化和 Trace

不改变排序，只把每段包装成 Context Item，补 ID、kind、provenance、tenant、版本和 Token。上线时比较新旧渲染摘要，确保行为等价。

阶段验收：每个最终 block 都能追到来源，每个候选有选择终态。

阶段 2：权限、时效和冲突前置

先引入确定性过滤：ACL、过期、撤销和同 key 冲突。这些控制不依赖模型评分，收益清晰。

阶段验收：跨租户候选为零；旧政策不会覆盖当前版本；无法裁决的冲突进入明确状态。

阶段 3：预算和 lane

在有真实 Token 基线后，加入输出预留、mandatory、lane cap 和大工具结果引用。先以 shadow 模式计算新选择，不直接影响生产回答。

比较：required recall、Token、时延、任务结果和 dropped reason。只有关键集不退化才切流。

阶段 4：Compaction 与 Memory 治理

给摘要增加结构、父事件和 fidelity eval；给 memory 增加类型、作用域、TTL、撤销和用户修正入口。

这一步风险高于普通去重，因为它会主动改变模型可见历史。应从长任务和低风险流量开始灰度。

阶段 5：缓存和多 Agent

等版本、权限和 lineage 已完整，再增加 Assembly Cache、Provider Prompt Cache 和子 Agent 委派。否则缓存会固化错误，多 Agent 会扩大不可追踪输入。

  • 执行器拒绝越权动作；

7. Cache isolation

至少测试：

  • tenant A 写入后 tenant B 同 query 不命中；
  • ACL 收紧后旧缓存不返回；
  • Policy、Schema、模型适配器更新会失效；
  • 删除 memory 后 summary 和 assembly cache 不再引用；
  • 缓存 miss/hit 的模型行为在允许误差内等价。

8. 端到端任务结果

最终仍要看：

  • 任务完成率；
  • 事实支持率；
  • 工具参数正确率；
  • 禁止动作执行次数；
  • P95/P99 时延；
  • 输入 Token、输出 Token 和费用；
  • 人工接管和澄清率。

上下文精度提高但任务质量下降，说明选择函数或模型布局仍有问题。

二十七、变形测试比固定样本更容易发现上下文缺陷

对一个基准 case 自动生成变体：

1. Noise insertion

插入不同长度的无关文档，期望核心事实和动作不变，Token 增长受 lane cap 控制。

2. Position permutation

打乱同级证据顺序，期望事实结论稳定；若不稳定，进入位置专项分析。

3. Duplicate amplification

复制同一 Chunk 多次，期望去重后 Token 基本不变，来源引用被合并。

4. Staleness

把有效期改到过去，期望候选在评分前被删除。

5. Authority inversion attack

在外部文档中加入伪造 SYSTEM 文本，期望 metadata 不变、工具权限不扩大。

6. Conflict injection

加入同级不同值，期望 UNRESOLVED_CONFLICT，而不是随机回答。

7. Budget shrink

逐步缩小输入预算，观察先丢哪些候选。mandatory 被截断前应明确失败。

8. Revocation

撤销某文档 ACL 或删除记忆，期望所有派生缓存和摘要在规定时间内失效。

变形测试验证的是不变量，比只保存“这次回答文本等于某句”更适合非确定模型。

二十八、一个示例故障案例：摘要、旧记忆和工具输出共同覆盖当前约束

下面是一个可复现的示例故障，用于展示证据链，不代表真实生产事故数据。

1. 场景

一个运维 Agent 负责分析部署失败。当前任务明确要求：

Agent 已运行二十多轮，历史接近应用预算上限。系统使用一个通用摘要器压缩旧消息，再把最近十条消息、全部工具结果和 Top 8 检索片段拼接。

2. 时间线

3. 表面现象

最终回答写着“已完成故障恢复”，语言流畅，模型和工具接口都返回 200。普通回答评测可能判定成功。

真正的业务错误有两个：

  • 本应只读，却执行了重启；
  • 当前目标是 staging-eu，却使用旧 memory 中的 staging-us。

4. 排查证据

原系统只保存最终 Prompt，无法解释每段来源。补做重放后，逐层证据显示：

  1. 原始用户约束存在于 compaction 范围内；
  2. 摘要 Artifact 没有 constraints 结构，只生成了一段自由文本；
  3. 摘要没有 parent item 和 omission 清单；
  4. memory 没有 task scope 和有效期；
  5. 工具结果的工单正文被整体标成 trusted_tool；
  6. Context Assembler 按 relevance/token 排序，但没有 authority 与 trust；
  7. 截断器直接从前部删除 Token，没有 mandatory 保护；
  8. 执行器把模型工具调用当成授权。

5. 首错层和扩大因素

首错层是 compaction 丢失不可违反约束。旧 memory 和工具文本扩大了模型偏移，按 Token 前截断让原始证据彻底消失，执行器缺少权限校验则把上下文错误升级为现实副作用。

不能把根因简化成“模型没听话”。即使换一个更强模型，四个结构性缺口仍然存在。

6. 修复顺序

  1. 立即关闭该工作流的写工具，只保留诊断能力；
  2. 把目标环境和只读模式放入结构化 Working State，并由执行器读取；
  3. 给 task.target_environment 建立 conflict_key，当前任务覆盖旧 task memory；
  4. memory 增加 task scope、来源、TTL 和 supersedes；
  5. 工具结构化字段与自由文本拆分，工单正文保持 untrusted data；
  6. compaction 使用结构化 schema，constraints、unresolved、approval 为必填；
  7. mandatory 超预算时失败，不再从头静默截断；
  8. 重启工具要求任务白名单、目标环境绑定和人工审批；
  9. 新增位置扫描、压缩忠实度和旧 memory 冲突回归。

7. 回归验收

同一案例生成以下变体：

  • 工单注入文本位于开头、中间和结尾；
  • 日志从 2,000 增加到 40,000 Token；
  • memory 分别为同任务旧值、其他任务值和已过期值；
  • compaction 发生零次、一次和三次；
  • 当前目标环境在会话中被用户更正；
  • 写工具可见但未授权；
  • 策略服务超时。

硬断言：任何变体中 restart_service 实际执行次数都为零；目标环境只能来自当前 Working State；上下文超预算要返回明确错误；每个丢弃项都有 Trace；摘要后 constraints 召回率为 100%。

二十九、常见误区

1. 窗口越大，放得越多越好

更多 Token 会增加成本、时延、冲突和注意力竞争。有效信息密度比填满比例重要。

2. Context Engineering 就是 Prompt Engineering 改名

Prompt Engineering 关注指令和示例的表达；Context Engineering 还管理历史、记忆、检索、工具、工作状态、预算、缓存和生命周期。

3. 所有内容算一个 relevance score

相关性不能替代 authority、trust、freshness 和 ACL。高相关攻击内容仍然不可信。

4. 最近消息永远最重要

最近工具输出可能只是噪声，较早的当前任务约束仍然 mandatory。应该按依赖和状态选择。

5. 工具结果来自内部 API，所以都可信

结构化字段和自由文本来源不同。工具可能只是外部内容的搬运通道。

6. 摘要成功生成就代表压缩正确

摘要是模型输出，需要测试必要事实、约束、未决项和 provenance。多代摘要尤其容易失真。

7. 把 System Prompt 复制到多个位置更安全

复制会增加 Token 和版本冲突，而且不能替代执行层权限。

8. 只要 JSON 转义就没有 Prompt Injection

转义保护语法，不会让模型看不懂恶意语义。

9. Cache hit 表示内容可继续使用

缓存命中不证明当前授权、版本和有效期。读取时仍需校验。

10. 只测最终回答

没有 Assembly Trace 就无法判断缺失发生在召回、选择、压缩、位置还是模型使用。

11. Token 预算用字符数除以四

语言、代码、图片和模型 Tokenizer 差异很大。固定公式只能做明确标记的粗略回退。

12. 冲突交给模型理解

模型可能根据措辞、位置或长度选择，而不是根据业务权威。能够确定性裁决的冲突应在组装前解决。

三十、什么时候该用什么策略

1. 小型单轮分类

固定短指令、当前输入和少量示例通常足够。引入长期 memory 和复杂检索反而增加变量。

2. 企业知识问答

重点是 Retrieval provenance、ACL、版本、冲突、引用和位置评测。History 只保留实体澄清与本轮目标。

3. 长时 Agent

需要 Working State、结构化笔记、compaction、按需工具读取和外部 Artifact。不要让完整工具轨迹永久留在窗口。

4. 高风险动作 Agent

上下文层负责减少错误意图，执行层负责身份、权限、审批、幂等和最终状态。任何摘要和缓存都不能成为授权来源。

5. 超长文档分析

先按任务做检索、分块、分层摘要和证据引用，再用位置扫描验证。整份文档一次塞入只有在质量、成本和时延评测证明合适时才采用。

6. 什么时候不要过度设计

如果任务固定、输入短、没有外部知识和多轮状态，一套清晰 Prompt 加确定性输入校验可能已经足够。Context Item 平台的复杂度应由真实来源、生命周期和风险驱动。

三十一、上线检查清单

数据模型

  • instruction、history、memory、retrieval、tool result、working state 类型分开；
  • 每个 item 有稳定 ID、来源、版本、摘要和 Token 口径；
  • authority、trust、relevance、freshness 分开；
  • tenant、ACL、sensitivity 在组装前校验；
  • conflict_key 和 parent_ids 可追溯。

Instruction 与状态

  • 平台策略、应用策略、当前任务和输出契约分别版本化；
  • 确定性业务规则没有只写在 Prompt；
  • 当前目标和实体存在结构化 Working State；
  • completed 有执行证据；
  • 并发状态更新使用 revision 或 compare-and-set。

History 与 Memory

  • 旧实体和撤销信息有 supersedes；
  • 选择依据不是单纯 last_n；
  • 推断记忆低权、可过期、可更正；
  • 记忆读取重新做当前权限检查；
  • 删除能传播到摘要、索引和缓存。

Retrieval 与 Tool

  • 授权过滤先于召回或至少在数据源边界执行；
  • 文档版本、生效时间、rank 和 score type 完整；
  • 近重复 Chunk 不会占满预算；
  • 工具结构化事实和自由文本分开；
  • 大工具结果使用引用和渐进读取；
  • 外部文本不会提升为 instruction 或扩展工具权限。

Token 与裁剪

  • 输入预算扣除了输出、协议和安全余量；
  • Tokenizer 身份和 exact/estimate 状态已记录；
  • mandatory 超预算会失败显式化；
  • lane cap 防止单一来源独占；
  • 每个候选都有 included/dropped/compacted 终态；
  • 位置策略经过当前模型和任务评测。

Compaction

  • 摘要是派生 Artifact，没有覆盖原历史；
  • constraints、decisions、unresolved、evidence 结构化保留；
  • 有 parent range、模型和 Prompt 版本；
  • compression generation 可查；
  • 定期从原事件重建，避免多代漂移；
  • 压缩前后有忠实度回归。

Cache

  • Retrieval cache 包含 corpus、filter、tenant 和 ACL 版本；
  • Assembly cache 包含策略、状态、Tokenizer 和预算；
  • 稳定前缀不混入跨租户动态数据；
  • 策略、Schema、权限和来源撤销会失效；
  • 不把供应商当前默认 TTL 或阈值写成稳定标准；
  • Cache hit 后仍检查授权和时效。

Test 与 Trace

  • 有 required、forbidden、stale 和 conflict 上下文标注；
  • 有 position × length 扫描；
  • 有 noise、duplicate、poison、revocation 变形测试；
  • 有跨租户缓存隔离测试；
  • Assembly Trace 能覆盖每个候选；
  • 最终任务、工具、安全、Token、时延和费用共同评测；
  • 执行器在模型受污染时仍能阻止越权副作用。

三十二、小结

Context Engineering 的核心不是寻找一段越来越长的“完美 Prompt”，而是管理模型采样时的有限工作集。

一套可落地的方法应该做到：

  1. 把 instruction、history、memory、retrieval、tool result 和 working state 建模成不同类型；
  2. 为每条内容保留 provenance、authority、trust、freshness、sensitivity 和 Token 口径；
  3. 让权限、过期和数据边界过滤发生在相关性评分之前；
  4. 用事实域权威、版本和有效时间解决冲突，无法裁决时显式失败；
  5. 先为输出、协议和估算误差预留，再给各来源分配输入预算；
  6. 对 mandatory、lane cap、去重、效用和位置建立确定性策略；
  7. 把外部文档和工具自由文本始终当作数据，防止 metadata 自我升级；
  8. 把 compaction 视为有损派生过程，保留父事件、结构化关键字段和忠实度测试；
  9. 让缓存键包含租户、权限、策略、Schema、数据和 Tokenizer 版本，并支持撤销传播；
  10. 用 Assembly Trace 记录每个候选为何进入、被替换、被压缩或被丢弃；
  11. 用位置扫描、冲突、污染、预算、缓存隔离和变形测试验证上下文；
  12. 让执行器继续承担权限、审批、幂等和副作用边界，不把安全押在模型注意力上。
