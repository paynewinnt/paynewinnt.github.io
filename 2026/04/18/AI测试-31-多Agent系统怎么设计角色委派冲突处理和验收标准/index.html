AI测试-31-多Agent系统怎么设计角色委派冲突处理和验收标准

发表于 2026-04-18 分类于 AI测试 本文字数： 18k 阅读时长 ≈ 1:07

把一个 Agent 改成三个角色很容易：

真正困难的是回答后面的工程问题：

  • Planner 拆出的任务是否覆盖了原目标
  • 两个 Worker 是否在重复做同一件事
  • 子任务缺少输入时能不能继续向下委派
  • 多层委派什么时候停止
  • Worker 看到的是共享上下文还是隔离上下文
  • 两个 Agent 得出相反结论时由谁裁决
  • Reviewer 是否真的读取了原始证据，而不是只相信摘要
  • 一个 Worker 超时会不会阻塞整个系统
  • Lead Agent 崩溃后任务和结果归谁接管
  • 最终回答有没有丢掉反例、限制和不确定性
  • 多花的 Token、工具调用和协调时间是否换来了可证明的质量收益

如果这些问题没有协议化，多 Agent 只是在单 Agent 的非确定性之外，再增加消息乱序、上下文丢失、重复劳动、角色冲突、递归委派和聚合失真。

Anthropic 在 How we built our multi-agent research system 中公开了一个具体的生产案例：Lead Researcher 根据问题动态创建并行 Subagent，Subagent 独立搜索并压缩结果，Lead 再综合，最后由 Citation Agent 处理引用。官方文章同时明确了代价和边界：协调复杂度快速增长、Token 消耗显著增加、同步等待会形成瓶颈，而需要所有 Agent 共享同一上下文或包含大量相互依赖的任务并不适合这种架构。

该案例最有价值的部分是架构经验，不是其中的内部评测数字。官方报告的质量、Token 和时延结果来自特定 Research 任务、模型组合、工具与评测集，不能外推成“多 Agent 普遍优于单 Agent”的保证。

本文从质量工程角度解决六个问题：

  1. 什么时候多 Agent 才真正值得引入。
  2. supervisor/worker、peer、pipeline 等拓扑怎样选择。
  3. 任务合同、委派深度、共享状态和隔离状态怎样设计。
  4. 冲突、循环委派、重复劳动、合并和终止怎样收口。
  5. 怎样实现可恢复的调度与事件模型。
  6. 怎样评测任务分解、覆盖、委派、冲突、聚合、端到端质量、成本和时延。

本文不会把某个框架的角色配置语法当成架构结论。框架可以减少样板代码，但无法替代任务语义、权限边界、状态一致性和验收 Oracle。

一、先定义什么才算多 Agent

1. 多次模型调用不等于多 Agent

下面是一条固定 Workflow：

三个模型调用都沿预定义路径执行，没有各自持续观察环境、选择工具和调整计划。它是多模型或多节点 Workflow，不一定是多 Agent 系统。

下面这条链也不必称为多 Agent：

任务在运行前已经拆好，工作单元没有自主委派和持续决策。这更接近并行化 Workflow。

2. 本文所说的多 Agent

本文把 Agent 定义为：在给定目标、状态和工具边界内，能够根据环境反馈持续决定下一步动作的执行单元。

多 Agent 系统至少包含两个这样的决策循环，并通过任务、事件或 Artifact 发生协作：

即使多个 Agent 使用同一个底层模型，只要拥有不同任务、上下文、工具、状态和生命周期，系统仍然是多 Agent。反过来，使用多个不同模型但都由固定代码一次调用，也不自动构成多 Agent。

3. 系统可以是混合的

实际系统常同时存在：

  • 确定性外层 Workflow
  • 动态 Supervisor Agent
  • 自主 Worker Agent
  • 固定的规则验证器
  • 非 Agent 的并行工具调用
  • 最终人工审批

因此评审时应画出每个节点的控制权，而不是只写“采用 Multi-Agent Framework”。

二、先建立一个强单 Agent 基线

在证明多 Agent 有价值前，至少要有一个可比较的单 Agent 基线：

  • 使用同等级模型
  • 拥有等价工具和数据权限
  • 有清楚的任务 Prompt 和输出合同
  • 允许合理的上下文压缩与外部记忆
  • 有相同终态 Oracle
  • 在同一冻结任务集上重复运行
  • 保存 Token、工具调用、时延和失败证据

如果基线只是“一次随便提问”，多 Agent 使用十几个调用、更多上下文和更强工具，比较结果只说明投入的计算更多，不能证明协作拓扑本身更有效。

至少建议做两组比较。

1. 等总预算比较

约束单 Agent 与多 Agent 的总 Token、工具调用和最大墙钟时间接近，用来观察同等资源下，任务分解与独立上下文是否带来收益。

2. 等产品约束比较

两边都满足同一时延上限、费用上限和安全门禁，允许系统自行使用资源，用来判断真实产品条件下哪种方案更合适。

还可以增加一个“等模型调用次数”诊断，但不要把它当唯一公平条件。多个 Agent 的价值之一就是并行使用独立上下文，完全固定调用结构可能消除待测差异。

三、多 Agent 真正可能优于单 Agent 的六个条件

1. 任务具有可并行的宽度

任务可以分成多个相对独立的方向，且每个方向都需要实质调查。例如：

  • 同时检查多个独立代码仓库
  • 对多个国家或供应商分别搜集一手资料
  • 对安全、性能、兼容性和合规性做不同证据链审查
  • 在多个互不依赖的数据源中寻找候选项

关键是“独立”，不是“看起来有多个章节”。如果每个子任务都必须等待前一个结论，增加 Agent 不会产生并行收益。

2. 单 Agent 上下文成为真实瓶颈

多个 Worker 可以拥有独立上下文，把大量原始材料压缩成带证据的 Artifact，再把必要信息交给 Supervisor。

但上下文瓶颈必须通过证据确认，例如：

  • 单 Agent 经常因上下文截断遗漏早期约束
  • 多个资料域无法同时放入可用窗口
  • 工具轨迹过长导致后续引用错误
  • 独立任务之间几乎不需要共享原文

仅因为模型支持创建 Subagent，就主动把短任务拆开，反而会增加信息传递损失。

3. 子任务需要不同工具、权限或专业提示

例如：

  • 代码审查 Worker 只有仓库只读与测试工具
  • 资料核验 Worker 只有官方站点和论文检索工具
  • 安全 Worker 使用威胁模型和策略检查器
  • 合并 Worker 只能读取已验收 Artifact，不能重新修改源数据

角色差异应落实到任务和能力，不是只在 Prompt 里写“你是一名安全专家”。如果所有角色使用同一上下文、同一工具和同一目标，所谓专业化可能只是不同人设。

4. 结果可以独立验收并可靠合并

子任务最好产生结构化、可引用的结果：

  • 文件和行号
  • 测试输出
  • 原始资料 URL 与具体主张
  • 数据摘要与查询版本
  • 风险、证据、置信和未决项

如果 Worker 只能返回一段无法验证的长摘要，Supervisor 会成为“摘要的摘要”生成器，错误和限定条件会在层层转述中丢失。

5. 任务价值足以覆盖协调成本

多 Agent 会增加：

  • 更多模型输入输出 Token
  • 更多工具调用
  • 调度、状态和 Artifact 存储
  • 冲突检测与仲裁
  • 更复杂的 Trace 与值班
  • 更长的尾部时延

低价值、低延迟的简单任务通常不值得付这笔成本。

6. 能定义协作质量，而不只看最终答案

如果系统只能给最终回答打一个模糊分，就无法区分：

  • Supervisor 拆错了
  • Worker 被分配到错误角色
  • 两个 Worker 重复劳动
  • 证据冲突没有上报
  • 合并阶段丢失了正确发现
  • 任务其实没覆盖完整

多 Agent 上线前需要能观测任务图、委派、结果合同、冲突和合并来源。

四、明确不适合多 Agent 的信号

出现下面的条件时，强单 Agent 或确定性 Workflow 通常更合适：

  • 任务主要是严格顺序链，几乎没有可并行分支
  • 所有步骤频繁读写同一共享状态
  • 每个 Worker 必须看到全部原始上下文才能正确行动
  • 任务很短，协调开销大于执行本身
  • 最终结果无法分块验收，也没有可靠合并方法
  • 关键动作不可逆且多个 Agent 可能竞争执行
  • 低时延是硬约束
  • 工具没有租户、幂等、版本和审计能力
  • 无法限制递归委派和总预算
  • 单 Agent 已稳定达到质量底线

一个典型反例是“让多个 Agent 同时修改同一个配置文件”。如果没有隔离分支、所有权和确定性合并，系统会遇到覆盖、冲突和语义漂移。此时更好的方案可能是一个 Agent 生成补丁，多个只读检查器并行审查，再由确定性工具合并。

六、拓扑决定信息怎么流动，也决定故障怎样放大

1. Supervisor / Worker

结构：

优点：

  • 权责清楚
  • 容易限制委派深度和总量
  • 适合独立分支并行
  • 最终聚合有明确所有者

风险：

  • Supervisor 成为单点和上下文瓶颈
  • 分解错误会系统性遗漏
  • Worker 结果经过 Supervisor 压缩后可能失真
  • Supervisor 可能过度创建或过早终止子任务

Anthropic Research 系统采用的就是这一类 Orchestrator-Worker 架构。应把它理解为开放研究任务上的具体设计经验，而不是对所有编码、事务或共享状态任务的推荐。

2. Peer / Debate

结构：

适合：

  • 需要暴露不同假设
  • 结论可以通过证据或形式规则仲裁
  • 角色之间确实拥有不同信息或方法

风险：

  • 多数意见不等于正确
  • 同模型实例可能产生相关错误
  • 权威、终止和最终责任不清楚
  • 争论轮次增加后可能偏离原问题
  • Agent 会互相迎合或重复已有论点

多 Agent Debate 的原始研究在特定推理与事实任务上报告过改善，后续研究也观察到问题漂移和低质量反馈。工程结论应该是“把 Debate 当成待评测策略”，而不是“增加讨论轮数就会更可靠”。

3. Pipeline

结构：

优点：

  • 阶段职责清楚
  • 每段可以使用不同工具和权限
  • 容易设置中间产物合同

风险：

  • 上游错误逐级传播
  • 后续 Agent 只看到摘要，丢失原始证据
  • 每一段都可能改写目标
  • 串行链无法获得并行时延收益

Pipeline 更接近动态节点组成的 Workflow。每段是否需要真正自治，应单独判断，不要让所有阶段都拥有完整工具集。

4. Blackboard / Shared Artifact

多个 Agent 不直接复制长消息，而是把结构化发现、代码、报告和证据写入公共 Artifact 空间，通过引用协作。

优点：

  • 降低层层摘要损失
  • 产物有独立版本和所有者
  • Supervisor 可以只传引用
  • 便于审计和增量合并

风险：

  • 共享可变状态产生覆盖和竞态
  • 低质量内容污染后续 Agent
  • 缺少 Schema 时公共空间会变成无序聊天记录

更稳的做法是 Artifact 默认不可变，更新产生新版本；共享索引只保存元数据和引用，写入要经过 Schema、权限和来源校验。

八、任务合同：委派的不是一句话，而是一份可验收工作单

Anthropic 官方工程文强调，子 Agent 需要目标、输出格式、工具和来源指导以及明确边界。短而模糊的委派会导致重复、遗漏或理解偏差。

一份最小任务合同建议包含：

合同里的四种边界

目标边界说明要完成什么和明确不做什么。

数据与权限边界限制可见仓库、资料域和工具。

资源边界限制时间、Token、调用、子任务数量和深度。

验收边界规定结果 Schema、证据和完成条件。

缺少任一层，Worker 都可能返回“内容很多但不可验收”的结果。

九、任务图：委派必须形成有向关系，而不是聊天串

调度器至少维护：

  • task_id
  • parent_task_id
  • root_task_id
  • delegation_path
  • depth
  • 依赖集合
  • 所有者或租约
  • 输入 Artifact 版本
  • 输出 Artifact 版本
  • 状态和版本
  • 创建、开始、截止和结束时间

一个任务只有在所有依赖完成且输入版本冻结后才能进入 READY。Worker 返回结果后也不能直接把父任务标成完成，必须经过合同验证和合并。

委派深度要双重限制

只设置 max_depth=3 不够。一个 Agent 在每层创建 20 个子任务，三层理论上就会形成大量节点。

至少同时限制：

  • 每个任务最大子任务数
  • 整个运行最大任务数
  • 最大委派深度
  • 每种角色的并发数
  • 全局 Token 和工具预算
  • 同一 dedup_key 的活动任务数

还要保留一部分预算用于合并、冲突处理和证据验证。把预算全部花在创建 Worker 上，最后没有资源综合结果，是常见的“搜索很多、交付失败”。

禁止循环委派

调度器应拒绝：

  • 子任务目标与祖先 dedup_key 相同
  • 委派路径中角色与规范化范围重复
  • 子任务依赖其后代
  • Worker 把原任务不加拆分地重新委派
  • 已取消或过期任务继续创建子任务

语义去重可以用模型辅助，但硬循环检测必须使用任务 ID、祖先链、规范化范围和有向图算法完成。

十、共享状态与隔离状态：默认隔离，按合同共享

1. 每个 Agent 的私有工作状态

适合保存：

  • 当前计划
  • 临时查询
  • 未验证候选
  • 局部工具结果
  • 可丢弃草稿

这些内容不应自动广播给所有 Agent。否则一个 Worker 的错误假设会污染整个系统，消息量也会快速增长。

2. 共享的规范状态

只保存已经过格式校验、来源标记和版本控制的内容：

  • 任务合同
  • 任务状态与租约
  • 已验收 Artifact 引用
  • 结构化 Claim 与证据
  • 冲突记录
  • 预算账本
  • 控制器事件

共享状态应由调度器或专用存储控制，不由多个 Agent直接覆盖。

3. Artifact 优先于长消息传递

Worker 生成完整结果文件，再向 Supervisor 返回轻量引用：

4. 共享写入必须有版本和所有权

对规范化结果使用：

  • 不可变 Artifact
  • 内容摘要
  • 乐观版本
  • 单任务单写者
  • 合并请求
  • 冲突记录

不要建立一个所有 Agent 都能随意追加和改写的“大记忆”。共享可变自然语言状态几乎无法做精确并发控制和回放。

十四、角色设计：角色必须对应责任、能力和禁止项

一个可执行角色定义至少包括：

字段 作用
role_id 稳定身份，不依赖显示名称
responsibilities 该角色必须完成的责任
allowed_task_types 能接收的任务类型
allowed_tools 可调用的工具集合
data_scopes 可读数据和租户范围

角色不要按人格命名

“乐观者”“怀疑者”“天才程序员”很难映射到权限和验收。更合适的角色是：

  • repository-auditor
  • primary-source-verifier
  • test-evidence-worker
  • conflict-arbiter
  • artifact-merger

这些名称仍然不能代替合同，但至少表达可执行责任。

Reviewer 不能天然高于 Worker

Reviewer 也可能遗漏、迎合或错误理解。它的权限应该是读取候选结果、运行验证器、提出带证据的拒绝原因；不能因为角色叫 Reviewer 就无条件覆盖程序测试和一手证据。

如果 Reviewer 与 Worker 冲突，仲裁依据应是证据优先级、业务规则和可执行 Oracle，不是角色名称。

专业化需要真实差异

可以通过以下方式形成真实专业化：

  • 不同工具和数据源
  • 不同输入范围
  • 不同输出 Schema
  • 不同验收 Rubric
  • 不同模型能力或上下文配置
  • 独立执行以降低路径依赖

只替换 System Prompt 中的一句角色说明，却让所有 Agent 看到相同信息、使用相同工具，不能假设它们会产生独立且互补的能力。

十五、委派正确性：先判断“该不该委派”，再判断“派给谁”

一次委派有四层正确性。

1. 必要性

子任务是否真的无法由当前 Agent 在现有上下文和预算内直接完成。把一个简单查找再委派出去，会增加延迟和传递误差。

2. 完整性

子任务集合是否覆盖父任务的必要目标、约束和风险。分解成三个仓库审计任务，却漏掉共享 SDK 和部署配置，仍然是不完整分解。

3. 互斥性

子任务范围是否重叠。完全互斥不总是目标，安全复核可能有意交叉，但重叠必须是设计出来的，而不是 Supervisor 无意识重复。

4. 能力匹配

被选 Worker 是否拥有正确工具、数据范围、上下文容量和输出能力。角色名称匹配不等于工具可用。

十六、冲突不是异常字符串，而是一等数据结构

两个结果冲突时，不要把长文本再次交给 Supervisor，让它自由选择。先把冲突规范化：

按冲突类型选择仲裁方式

冲突类型 示例 优先仲裁方式
事实冲突 API 是否在超时后可能提交 原始协议、官方文档、可重复实验
代码行为冲突 两个 Worker 对调用路径结论不同 静态引用、测试、运行 Trace
策略冲突 是否允许访问某数据 确定性策略引擎，不交给投票
范围冲突 谁负责共享 SDK 任务图和所有权注册表
资源冲突 两个任务申请同一写租约 调度器、版本和锁
解释冲突 风险是否足以阻断 预定义 Rubric，必要时人工
偏好冲突 报告采用哪种措辞 产品所有者或稳定风格规则

多数投票为什么不够

多个 Agent 可能：

  • 使用同一个模型并产生相关错误
  • 都引用同一份错误摘要
  • 被第一个 Agent 的结论锚定
  • 因角色 Prompt 相似而缺少独立性

三比一只能说明输出数量，不能证明事实。对可验证事实，证据和测试优先；对权限和策略，确定性规则优先；对不可消解的高风险解释，人工决策优先。

仲裁也必须有预算

冲突不能无限讨论。可以限制：

  • 最多一轮补证据
  • 最多一次独立复现实验
  • 最多一个专用 Arbiter
  • 达到截止时间仍不确定则保留冲突并转人工

正确终态可以是“报告明确保留未解决冲突”，不必为了看起来完整而强行生成一致答案。

十八、合并：从 Claim 和 Artifact 合并，不从摘要印象合并

最终报告的每个关键主张至少要保留：

  • claim_id
  • 来源任务
  • 证据引用
  • 证据版本
  • 支持或反对关系
  • 限制条件
  • 冲突状态
  • 合并器版本

合并过程可以分三层。

1. 结构合并

确定性地合并字段、列表和唯一键，检查 Schema、重复 ID 和缺失必填项。

2. 证据合并

把指向同一事实的 Claim 聚类，保留不同证据和反例。冲突不能在这一层被悄悄覆盖。

3. 叙述合并

模型根据已经验收的 Claim 生成可读报告。生成后再做引用完整性、数字一致性、限制保留和请求覆盖检查。

防止“传话损失”

Supervisor 不应该只看到 Worker 的 200 字摘要。需要下钻时，应读取原 Artifact。对于代码、表格和图形，最好让专业 Worker 直接产出最终 Artifact，Supervisor 只负责登记和引用，不再重新生成一份近似版本。

聚合忠实度的核心断言

  • Worker 明确标记的关键风险没有被删除
  • 已接受的反例和限制仍然出现在最终结果
  • 最终数字能追到同一版本原始证据
  • 未解决冲突没有被改写成确定结论
  • 没有生成 Worker 结果中不存在的新事实
  • 引用确实支持相邻主张

十九、终止：完成、停止和放弃必须分开

一个多 Agent 运行可以结束于：

  • SUCCEEDED：覆盖、证据、冲突和终态 Oracle 全部通过
  • PARTIAL 或 MANUAL_REVIEW：部分结果可交付，但有明确缺口或冲突
  • FAILED：目标未完成，失败归因清楚，没有未决副作用
  • CANCELLED：取消已传播，所有租约和在途动作收口
  • BUDGET_EXHAUSTED：达到预算，保存已有 Artifact 和未完成图

不建议把“所有 Worker 都返回了”当完成条件。可能出现：

  • 原目标没有被完整拆分
  • Worker 返回结果被 Schema 拒绝
  • 关键冲突未解决
  • 合并器丢失必要主张
  • 最终业务状态未达到

可执行成功条件

停止创建新任务要早于预算耗尽

当剩余预算只够合并、验证和交接时，Supervisor 应进入“禁止新委派”状态。否则最后一批 Worker 即使有价值，也可能没有资源被验收和合并。

Straggler 处理

一个慢 Worker 不应无限阻塞整次运行。可以根据任务合同选择：

  • 等待，因为它覆盖关键唯一需求
  • 复制执行，但只接受一个 fencing token 对应的结果
  • 使用已验收部分结果并明确缺口
  • 取消低价值分支
  • 转人工补充

不能简单取最快结果，因为最快 Worker 可能证据最少。

二十一、评测设计：要区分“多花算力”与“协作有效”

1. 测试集必须包含适合和不适合切片

如果评测集全部是天然可并行的宽度搜索，多 Agent 当然更容易占优；如果全部是强顺序任务，结论又会反过来。

至少建立以下切片：

切片 任务特征 想验证的问题
独立宽度 多个互不依赖的信息域或仓库 并行 Worker 是否提高覆盖、降低墙钟时间
动态分解 子任务只能根据初步发现确定 Supervisor 是否比固定分片更有效
强顺序依赖 后一步依赖前一步完整结果 多 Agent 是否只增加传递损失
共享状态 多角色频繁操作同一对象 冲突、一致性和锁成本是否不可接受
长上下文 单 Agent 容易截断或遗忘 独立上下文和 Artifact 是否改善保留
专用工具 不同任务需要不同受限工具 角色路由是否正确且更安全
冲突证据 故意提供相反但可验证的资料 系统能否检测、仲裁或保留不确定性
低价值短任务 一次调用即可完成 调度器能否拒绝不必要委派
Straggler 一个分支显著变慢 系统是否安全降级而非无限等待
部分失败 一个 Worker 或 Artifact 失败 父任务能否正确收口和交接

如果多 Agent 只在第一类切片改善，却在共享状态和低价值任务上恶化，正确结论不是“整体采用多 Agent”，而是只路由适配任务。

二十四、完整案例：跨仓库 Payment API v2 迁移审计

本节是为说明设计、排查和验收而构造的案例。仓库、数据和结果均为示例，不代表真实生产项目，也不是任何模型或框架的性能保证。

1. 业务目标

一个支付 API 即将从 v1 迁移到 v2。系统需要审计 12 个服务仓库、1 个共享 SDK 仓库和 2 份部署配置，输出：

  • 所有 v1 Endpoint 使用位置
  • v2 的请求、响应、错误码和幂等变化
  • 每个仓库需要修改的文件和测试
  • 跨仓库共享风险
  • 无法确认的问题
  • 证据支持的迁移顺序

任务只读，不允许自动修改代码或部署。主要证据来自冻结仓库 tree、供应商官方 v2 文档、契约测试和历史 Trace 的脱敏样本。

2. 为什么考虑多 Agent

这个任务有明显宽度：多数业务仓库可以独立审计，各自上下文较大，最终结果能按统一 Schema 产出。共享 SDK 和部署配置需要单独所有者，跨仓库冲突可以通过代码引用、官方文档和契约测试仲裁。

但它不是完全并行：

  • 所有仓库依赖同一共享 SDK
  • 幂等和超时语义会影响全局迁移顺序
  • 最终不能简单拼接 15 份报告

因此采用“确定性清单 + Supervisor/Worker + Artifact 合并 + 有限仲裁”的混合拓扑，而不是自由 Peer 群聊。

3. 第一版多 Agent 设计

第一版给 Lead Agent 一句任务：

子 Agent 没有统一合同和 dedup_key，可以继续创建子 Agent，结果只返回自然语言摘要。

运行后表面上很活跃：

  • 创建了 18 个 Worker
  • 执行了 263 次仓库搜索
  • 生成了 41 页报告
  • 14 个 Worker 声称完成

实际验收发现：

  • 4 个 Worker 重复审计 orders 仓库
  • 共享 SDK 没有主 owner
  • billing 和 settlement 两个仓库完全遗漏
  • 一个 Worker 又委派两个 Agent“审计所有支付相关仓库”
  • 7 个结果没有文件位置，只写“可能需要修改”
  • 两个 Worker对超时后的提交语义给出相反结论
  • Lead 在最终报告中选择了其中一个，却没有保留冲突
  • 最慢 Worker 卡住 22 分钟，Lead 同步等待，其他结果无法提前验收

最终报告内容很多，但必要仓库覆盖只有 11/15，关键超时结论没有可靠证据，不能用于迁移决策。

第一步由确定性清单生成器读取冻结仓库目录，得到 15 个必需范围和稳定版本。

第二步，Supervisor 只决定每个范围是否需要额外专项，例如某仓库发现自定义重试器后，可创建一个深度为 1 的“重试语义测试”子任务。它不能改变必需范围，也不能创建“审计全部仓库”这种无界任务。

第四步，证据验证器检查每条 breaking change 是否具有仓库位置、官方文档或可重复契约测试。

第五步，Claim 索引按规范化 subject 和 predicate 检测跨仓库冲突。事实冲突优先读取供应商官方 v2 语义，并运行隔离契约测试；仍无法确认则保留未决状态。

二十六、怎样正确引用 Anthropic 官方案例

Anthropic 的多 Agent Research 工程文报告了几个引人注意的内部结果，包括特定 Research Eval 上多 Agent 相对单 Agent 的表现、Token 使用以及并行搜索带来的时延改善。

引用这些数字时必须同时保留上下文：

  • 任务是开放、宽度优先的研究搜索
  • 架构是 Lead Agent 加并行 Subagent 和 Citation Agent
  • 使用的是文章明确描述的模型组合与工具
  • 结果来自 Anthropic 内部评测和实现
  • 官方同时指出多 Agent Token 消耗高、协调复杂
  • 共享上下文和高依赖任务并不适合
  • 同步等待仍然是其当时架构的瓶颈

可以迁移的工程经验包括：

  • 让 Supervisor 给出清楚的目标、边界、输出和工具指导
  • 根据任务复杂度限制 Agent 数量和调用预算
  • 使用独立上下文处理宽度搜索
  • 通过 Artifact 降低层层摘要损失
  • 为长任务做持久执行、检查点和恢复
  • 同时使用确定性保护和 Agent 适应性
  • 从小规模真实任务开始建立评测和完整 Trace

不能直接迁移的结论包括：

  • 某个内部提升百分比会在代码、客服或事务任务复现
  • 更多 Agent 必然提高质量
  • 更多 Token 本身证明协作更有效
  • 并行一定降低尾部时延
  • 研究系统的角色与 Prompt 可以原样用于高风险写操作

官方案例应该帮助形成假设和故障清单，最终架构仍由本系统的配对评测、成本和风险门禁决定。

二十七、常见失败模式及排查顺序

1. 分解遗漏

现象： 所有 Worker 都完成，但最终目标缺章节、缺仓库或缺风险。

排查： 先对照 requirement registry，不先看最终文风。检查规划时是否每个必要需求都有 owner。

修复： 必需范围由确定性清单或标注契约提供；动态 Supervisor 只能细化，不能删除。

2. 委派错位

现象： Worker 反复换工具，最终说无数据。

排查： 核对任务所需工具、数据范围与 Worker 能力注册表。

修复： 分配前做能力子集校验，无法满足就拒绝调度，而不是让 Worker 自己找替代权限。

3. 循环委派

现象： 任务数快速增长，目标文字高度相似。

排查： 查看祖先链、规范化范围和 dedup_key，定位第一次重复。

修复： 图级无环校验、最大深度、最大任务数和重复签名拒绝同时启用。

4. 重复劳动

现象： 工具调用很多，新增证据很少。

排查： 比较 Worker 的文件、查询和证据集合，不只比较任务标题。

修复： 覆盖登记、范围所有者、结果订阅和有意复核标记。

5. 共享状态污染

现象： 一个 Worker 的错误假设被后续所有角色引用。

排查： 找到该 Claim 第一次进入规范共享状态的事件，检查是否未经证据验收。

修复： 私有草稿与共享 Claim 分离，Artifact 不可变，只有验收结果进入共享索引。

6. 冲突被多数意见掩盖

现象： 最终报告很确定，但原结果存在反例。

排查： 按 subject/predicate 重建 Claim 组，检查 Merger 是否删除 minority Claim。

修复： 事实冲突按一手资料和实验仲裁，无法解决就显式保留。

7. Supervisor 成为瓶颈

现象： Worker 很快完成，但 Lead 长时间处理消息和摘要。

排查： 拆分 Worker 执行、消息等待、Artifact 读取、合并和仲裁 Span。

修复： 结构化结果、批量验收、Artifact 直传和分层合并；不要让 Lead 重写所有产物。

8. Straggler 阻塞

现象： 绝大多数任务完成，运行仍无法收口。

排查： 检查慢任务是否在关键路径、是否有唯一必要覆盖、是否仍持有有效租约。

修复： 按价值选择等待、复制、降级或转人工，并为复制任务使用 fencing token。

9. 聚合幻觉

现象： 最终报告出现没有 Worker 支持的数字或结论。

排查： 从最终句子反查 Claim lineage；无法关联即为无来源新增。

修复： 叙述生成只读取 accepted Claim，生成后执行主张和引用对齐门禁。

10. 错误终止

现象： Lead 因“信息足够”提前停止，或因不断找新方向无法停止。

排查： 对照覆盖、冲突、预算和停止事件，确认终止由哪个条件触发。

修复： 成功条件、禁止新委派阈值、无进展预算和人工升级条件由控制器执行。

11. 线上协调成本突然升高

现象： 最终质量没有明显变化，但 Token、任务数和 P95 时延持续上升。

排查： 不先归因于模型“变啰嗦”，而是按运行阶段拆开规划、Worker 执行、消息等待、Artifact 验收、冲突仲裁和合并成本。检查任务复杂度路由是否漂移、Supervisor 是否创建更细的任务、工具失败是否触发额外委派，以及 Merger 是否重复读取大 Artifact。

修复： 冻结复杂度分类器和 Supervisor 版本做同期对照；为简单任务设置禁止委派路径；对同一 dedup_key 复用结果；给合并保留摘要索引但允许按需读取原文；按任务价值设置最大并发和总计算，而不是只限制单个 Worker。

12. 任务完成后仍有孤儿 Worker

现象： 主运行已经结束，工具调用和 Artifact 写入仍在继续，甚至迟到结果触发新合并。

排查： 从终态事件反查全部后代任务和租约，检查取消是否只通知直属子任务、Worker 是否忽略租约过期、消息消费者是否仍接受终态运行的事件。

修复： 终止前进入 DRAINING 阶段，停止新委派，向全部后代传播取消，回收租约，等待不可取消只读调用结束；终态之后的写事件由运行版本门禁拒绝并进入审计队列。不能依赖 Agent 收到一句“请停止”后自觉退出。

13. 版本升级破坏在途任务

现象： 部署新 Prompt、任务 Schema 或合并器后，旧 Worker 结果大量被拒绝，或者新 Supervisor 无法理解旧任务图。

排查： 核对运行、合同、角色注册表、Artifact Schema 和 Merger 版本，确认是业务失败还是协议版本不兼容。检查部署是否把所有在途任务强制切到新版本。

修复： 每个运行固定协议版本；新旧调度器并存直到旧任务排空；确需迁移时使用显式迁移器并对历史快照做回放测试。新版本不能静默重解释旧 Artifact，也不能用新 Rubric 改写已接受结果。

14. 可观测性记录了消息，却无法还原因果

现象： 日志能看到数百条 Agent 消息，但无法判断哪个委派导致遗漏、哪个结果覆盖了冲突。

排查： 检查事件是否具备 run_id、task_id、parent_task_id、causation_id、任务版本、Artifact 摘要和 Claim 血缘。仅有时间戳和自然语言内容无法可靠重建因果，跨服务时钟偏差还会制造错误顺序。

修复： 让调度器生成结构化事件，Agent 只提供提案和结果；技术 Trace、任务图和业务 Claim 使用稳定 ID 关联。内容原文进入受控 Artifact 存储，Trace 保存摘要和引用，避免为了排查把敏感上下文广播到所有日志。

二十八、什么时候不要硬套多 Agent

以下场景更适合单 Agent、固定并行或确定性 Workflow：

  • 一次调用或短链已经稳定完成
  • 子任务无法独立验收
  • 绝大多数步骤共享同一上下文
  • 多个角色会竞争同一写资源
  • 没有任务合同、Artifact 和事件基础设施
  • 没有可靠冲突仲裁依据
  • 成本或尾时延预算很紧
  • 没有能力做配对评测和故障恢复
  • 任务价值不足以覆盖协调成本

多 Agent 不是解决单 Agent 质量问题的默认方式。检索错误、工具描述不清、权限混乱和终态 Oracle 缺失，在多 Agent 中只会被放大。

二十九、上线前检查表

是否值得采用

  • 是否已有使用同等级模型和工具的强单 Agent 基线
  • 是否同时做等总预算和等产品约束比较
  • 任务是否存在真实独立宽度或上下文瓶颈
  • 子任务是否能独立验收并产生带证据 Artifact
  • 多 Agent 的关键质量增量是否可重复
  • 不适合切片是否保持单 Agent 或 Workflow 路由

拓扑与角色

  • Supervisor、Peer、Pipeline 或混合拓扑的选择理由是否明确
  • 每个角色是否有稳定 ID、职责、工具、数据和禁止项
  • Reviewer 是否也受证据和权限约束
  • 高风险写入是否保持单一确定性所有者
  • Supervisor 单点和上下文瓶颈是否有恢复方案
  • Straggler 策略是否按任务价值配置

任务合同与委派

  • 每个任务是否有目标、非目标、输入、输出和验收
  • 是否有稳定 dedup_key、父任务和委派路径
  • 深度、每层子任务数和全局任务数是否同时限制
  • 是否为合并、验证和冲突预留预算
  • 任务能力要求是否与 Worker 注册表校验
  • 循环委派和无意重复是否被调度器拒绝

状态与事件

  • 运行状态与单任务状态是否分开
  • 事件是否有唯一 ID、版本、因果和关联字段
  • 重复、乱序和迟到事件是否安全处理
  • 租约是否配合 fencing token 阻止旧 Worker
  • 取消是否传播到全部后代和在途工具
  • 长任务跨部署是否有版本兼容与恢复测试

共享与隔离

  • Agent 私有草稿是否不会自动进入规范共享状态
  • 共享 Artifact 是否不可变并带内容摘要
  • Claim 是否有来源、限制和冲突状态
  • 多 Agent 是否不能同时覆盖同一规范结果
  • 敏感数据是否按任务合同最小共享
  • Artifact 是否有访问控制、保留和删除策略

冲突与合并

  • 冲突是否按 subject/predicate 结构化检测
  • 事实、策略、资源、解释冲突是否使用不同仲裁方式
  • 多数投票是否不会替代一手证据和程序 Oracle
  • 仲裁是否有轮次、工具、Token 和时间预算
  • 最终结果是否保留关键限制、反例和未决冲突
  • 每个关键主张是否能反查 Claim 与 Artifact

评测与故障注入

  • 是否评价分解、覆盖、委派、冲突和聚合，而不只看终态
  • 端到端成功是否与成本和尾时延一起报告
  • 是否包含独立宽度、强顺序和共享状态切片
  • 是否完成固定并行、动态分解和冲突仲裁消融
  • 是否注入 Supervisor 崩溃、Worker 迟到、Artifact 篡改和 Merger 丢失
  • 所有量化结论是否标注来源、样本、版本和适用边界

三十、总结

多 Agent 真正有价值的前提，不是“任务看起来复杂”，而是复杂性具有可以并行、隔离、验收和合并的结构。

适合多 Agent 的信号包括：

  • 多个独立调查方向
  • 单上下文成为已验证瓶颈
  • 子任务需要不同工具或数据范围
  • Worker 能产出独立、带证据的 Artifact
  • 最终 Claim 可以结构化合并
  • 任务价值覆盖额外成本

不适合的信号包括：

  • 强顺序依赖
  • 高频共享可变状态
  • 不可逆写动作竞争
  • 没有终态 Oracle
  • 低延迟和低价值短任务
  • 无法限制委派、恢复状态和追踪证据

一套可控的多 Agent 系统至少需要：

  1. 强单 Agent 基线和公平资源比较。
  2. 明确的 Supervisor、Peer、Pipeline 或混合拓扑。
  3. 带目标、范围、能力、预算和验收的任务合同。
  4. 运行状态、任务状态、事件版本、租约和 fencing token。
  5. 私有工作状态与规范共享 Artifact 的隔离。
  6. 循环委派、重复劳动和任务爆炸控制。
  7. 以一手证据、测试和策略为依据的冲突仲裁。
  8. Claim 级血缘和聚合忠实度门禁。
  9. 覆盖、委派、冲突、端到端、成本和时延的分层评测。
  10. Supervisor、Worker、消息、Artifact、Merger 全链路故障注入。

最终验收标准不应该是“多个 Agent 完成了一次热闹的讨论”，而应该是：

每个必要目标都有明确 owner，每次委派都满足能力和预算合同，每个关键结论都能追到独立证据；重复、乱序、迟到、冲突和局部失败不会破坏规范状态；只有覆盖、聚合、硬门禁和终态 Oracle 全部通过，系统才宣布成功。

只有做到这一步，多 Agent 才是可验证的协作系统，而不是多个非确定性对话的叠加。
