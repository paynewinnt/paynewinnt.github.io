AI测试-34-Embedding和向量检索怎么理解相似度切片索引和元数据过滤

发表于 2026-04-24 分类于 AI测试 本文字数： 18k 阅读时长 ≈ 1:06

向量检索最容易制造一种错觉：系统返回了一个带很多小数位的相似度，于是结果看起来既科学又可信。

但 0.873421 只说明某个实现按照某个向量、某个距离函数和某个索引状态算出了一个数。它没有自动回答下面这些问题：

  • 查询向量和库内向量是否来自同一个 Embedding 模型及同一套前处理
  • 这个数是 cosine similarity、cosine distance、inner product，还是平方 L2 距离
  • 数值越大越近还是越小越近
  • 文档是否切在了能够独立表达事实的位置
  • ANN 索引是否漏掉了 Flat 精确检索本应找到的近邻
  • 租户、权限、时效和删除状态是在搜索前约束，还是在固定候选窗口之后才过滤
  • 返回不足 k 是因为合法资料确实不够，还是因为后过滤把候选全部丢掉
  • 一个“近”的分片是否真的满足当前业务问题

最后一项尤其重要。

相似度是候选排序信号，不是业务正确性证明。Schema 合法、索引命中、数据库查询成功或 HTTP 200 也都不能补上这层证明。业务相关性、证据充分性与端到端回答质量，仍然要由任务标注和业务断言验证。

AI测试-18-RAG系统怎么评测召回率忠实度和答案可追溯性 已经完整讨论了 qrels、Recall@k、MRR、nDCG、权限过滤前后评测和端到端归因。本文不重复那套通用 RAG 评测，而是专门回答更靠近检索引擎内部的四个问题：

  1. cosine、dot product、L2 到底在比较什么，归一化改变了什么。
  2. Chunk、Embedding 模型和索引如何组成一份不能随意拆开的版本契约。
  3. Flat、IVF、HNSW、PQ 在速度、内存、构建、增删和近似损失之间怎样取舍。
  4. metadata pre-filter、post-filter、迭代扫描和多租户隔离为什么必须放进同一套实验。

资料与产品行为截至 2026-07-26。本文提到的 Faiss 行为限定在其官方仓库与 Wiki 所描述的索引实现；提到的 pgvector 过滤与迭代扫描行为限定在 pgvector 0.8.x 官方 README，其中迭代索引扫描明确从 0.8.0 开始提供。其他向量数据库即使使用同名索引，也应重新核对其版本文档和执行计划。

一、工程定义：被测对象不是“向量库”，而是一份检索契约

1. 一次检索包含哪些状态

从工程视角看，一次向量检索可以写成：

任何一个参数变化，都可能改变结果。

因此，“模型没变，只把 HNSW 的 efSearch 从 40 调到 80”是一次检索版本变化；“索引没变，只把权限过滤从搜索前移到返回前”也是一次更危险的版本变化；“维度相同，所以把查询模型升级了，旧库不用重建”则直接破坏了表示空间契约。

一个可上线的检索版本至少要有下面四组标识：

  • 数据版本：语料快照、文档 revision、解析器、切片 manifest、元数据和删除墓碑。
  • 表示版本：模型供应方、模型名、工件摘要、维度、池化、文本前处理、归一化和存储精度。
  • 索引版本：索引类型、训练数据摘要、构建参数、构建时间、实现和库版本。
  • 查询版本：距离方向、k、候选预算、过滤执行方式、超时、稳定排序和失败语义。

只记录 index_name=knowledge_base 不够。这个名字无法说明其中混了几代向量，也无法在事故后重放当时的候选集合。

2. 本文所说的“正确”分成四层

为了避免把不同问题塞进一个“准确率”，本文使用四层边界：

层级 要回答的问题 主要证据
数学层 距离实现是否符合声明，排序方向是否正确 手算向量、性质测试、数值容差
索引层 ANN 相对同集合 Flat 精确结果漏了多少 exact top-k、ANN top-k、参数和扫描证据
过滤层 合法候选集合和执行顺序是否正确 tenant、ACL、时间、删除状态、选择率、拒绝数
业务层 找到的内容是否真的支持任务 qrels、业务断言、证据单元；详见 AI测试-18

ANN recall@k 属于索引层。它把 Flat 的精确近邻当作 oracle，测量近似算法是否保留了近邻。

业务检索 Recall@k 属于业务层。它把人工或业务规则标注的相关资料当作 qrels，测量候选是否覆盖任务需要。

两者名称相似，分母完全不同。ANN recall 很高，只能说明 ANN 接近当前向量空间里的精确排序；如果 Embedding 本身把错误资料排得最近，业务召回仍然会失败。

3. 明确不在本文中证明的事情

本文不会用相似度阈值证明答案正确，也不会用 ANN recall 代替业务相关性标注。

本文也不讨论：

  • 生成模型是否忠于上下文
  • 引用是否支持最终陈述
  • 通用 qrels 如何标注
  • MRR、nDCG 的完整推导
  • 一个 Embedding 模型在公开榜单上的综合优劣

这些问题需要独立实验。本文只把进入后续 RAG 或搜索链路之前的候选检索层做成可测、可复现、可排障的系统。

在线查询要在请求开始时冻结：

  • 请求租户和主体身份
  • 权限组或资源范围快照
  • 查询时点 as_of
  • 查询模型和前处理版本
  • 距离函数及排序方向
  • 过滤表达式和执行策略
  • k、ANN 搜索深度、最大扫描量和截止时间

  1. 业务可消费的最终候选。
  2. 可排障的检索证据。

检索证据不必记录全部敏感正文，但至少应记录：

如果系统只保存最终五个分片，事故发生后就无法判断第六个相关分片是被 ANN 漏掉、被权限过滤、被候选窗口截断，还是在相同分数下被不稳定 tie-break 打乱。

3. 控制面与数据面要分开

索引文件、向量和元数据属于数据面；模型版本、索引别名、搜索参数和过滤计划属于控制面。

控制面发布应满足：

  • 配置不可变并带版本号
  • 索引别名切换原子化
  • 查询模型与索引模型成对发布
  • 新旧索引可以并行影子查询
  • 回滚能恢复完整组合，而不是只回滚一个参数
  • 审计记录能说明谁在何时把哪一组合设为生产版本

否则一次“只改参数”的紧急操作，很可能让查询模型指向新版本、索引别名仍指向旧向量，造成静默混用。

三、Embedding 是坐标系，不是可以跨版本拼接的业务字段

1. 一个向量真正依赖什么

Embedding 向量并不只由模型名决定。它通常还依赖：

  • tokenizer 和词表版本
  • 输入前缀、任务指令或模板
  • 截断长度和截断方向
  • 大小写、Unicode、空白、HTML 等前处理
  • 查询编码器与文档编码器是否共享参数
  • 池化方式
  • 模型工件权重
  • 输出维度
  • 是否归一化
  • float32、float16 或量化存储

所以 dimension=768 只是形状检查，不是兼容证明。

两个模型完全可能都输出 768 维，但每个轴表达的方向不同。把模型 B 的查询向量拿去搜索模型 A 的库，在数学上仍能算 dot product，在工程上却相当于把不同坐标系里的坐标直接相乘。结果有数值，并不代表数值有语义。

2. 查询模型和文档模型也不能凭名字猜一致

有些稠密检索器使用共享编码器，有些使用独立的 query encoder 和 passage encoder。DPR 原始工作就是双编码器结构：查询和段落分别编码，再用向量相似度完成高效候选检索。

这意味着版本契约应明确写出：

不能因为两端来自同一个模型家族，就省略角色配置。把 document prefix 用到 query，可能维度和协议都正确，排序分布却整体漂移。

3. 模型升级必须重建或明确做迁移

安全迁移通常有三种形式：

全量重建后原子切换

新模型重算全部文档，建立新索引，完成离线和影子评测，再同时切换查询模型与索引别名。它最容易解释，但需要额外存储和构建时间。

双写双读迁移

迁移窗口内，新文档同时写入两代索引；在线请求由旧版服务，新版做影子查询。待历史语料回填完成再切换。实现复杂度更高，但适合持续更新的大库。

显式映射或蒸馏空间

只有当团队真的训练并验证了跨空间映射，且误差进入评测契约时，才可以讨论不重算全部向量。不能把“维度相同”冒充映射已成立。

cosine 关注夹角，理论取值在 [-1, 1]。越大通常越相似。

实现时要处理三个边界：

  1. 零向量没有可定义的方向，分母为零。
  2. 浮点误差可能让结果略超出理论边界，展示时可以裁剪，排序证据应保留原始值。
  3. 某些产品返回 cosine distance = 1 - cosine similarity，此时越小越近。

五、Chunk 设计：向量检索的最小排序单元必须能回到证据单元

1. Chunk 太大和太小分别怎样失败

Chunk 太大时：

  • 多个主题被压进一个向量，主导主题掩盖局部事实
  • 查询只匹配一小段，返回却携带大量无关内容
  • 更新一个段落需要重算大块内容
  • reranker 和生成上下文承担更高 token 成本
  • 权限或有效期若在块内不一致，元数据无法准确表达

Chunk 太小时：

  • 标题、条件、例外和结论被拆开
  • 代词和省略语失去上下文
  • 一个事实需要多个分片组合才能完整解释
  • overlap 产生大量近重复，挤占 top-k
  • 过滤与去重成本上升

2. 优先利用文档结构

对政策、技术文档和知识库，切片通常应先尊重：

  • 标题层级
  • 段落和列表
  • 表格行列关系
  • 代码块和配置块
  • 问答对
  • 版本章节与生效条款
  • 页面、节和原始偏移

固定窗口可以作为兜底，但不应抹掉结构。

  • 增加存储和索引规模
  • 让同一事实占据多个 top 位
  • 让 ANN recall 看起来稳定，却降低有效信息密度

4. Chunk ID 不应依赖数组下标

如果 chunk_id=document_id + position，在文档开头插入一段后，后续所有 ID 都会变化，导致：

  • 增量更新被放大成全量删除和重写
  • 线上反馈无法关联新版本
  • 缓存和引用失效
  • A/B 结果难以配对

  • revision
  • 结构路径或内容边界
  • 内容哈希
  • 切片策略版本

5. Chunk 评测不靠平均长度

平均 token 数只能看成本。质量检查还应包括：

  • 空块、超短块和超长块比例
  • 标题孤立比例
  • 表头与表体分离比例
  • 列表条件被切断比例
  • 句子中间截断比例
  • overlap 重复率
  • 一个 parent 占据 top-k 的集中度
  • 关键证据跨块组合比例
  • 权限或有效期在块内不一致的记录数

可以做确定性变形测试：同一文档只改变无意义空白、换行或 HTML 属性顺序，若业务内容未变，chunk 边界和内容哈希应按契约保持稳定。若解析器升级有意改变边界，就必须生成新的 manifest 并重跑检索实验。

七、Flat 精确检索：没有基线，就无法量化 ANN 丢了什么

1. Flat 的含义

Flat 精确检索对合法候选集合中的所有向量计算同一距离，再做全排序或精确 top-k 选择。

它的主要价值不是生产吞吐，而是：

  • 作为 ANN recall 的 oracle
  • 验证距离实现和排序方向
  • 验证过滤集合
  • 对照索引参数变化
  • 重放失败查询
  • 校验量化或半精度损失

Faiss 官方索引表把 IndexFlatL2 和 IndexFlatIP 列为 exhaustive exact search；未压缩 float32 向量的索引存储量按表中口径约为每向量 4 * d 字节，不含应用侧正文、元数据和其他运行开销。

2. Flat 基线必须使用同一合法集合

错误对照常见于：

二者候选宇宙不同，交集下降不代表 ANN 算法差。

正确对照需要冻结：

  • 同一语料快照
  • 同一活跃和删除状态
  • 同一 tenant、ACL、时间和类别过滤
  • 同一向量版本与精度
  • 同一距离函数与方向
  • 同一 k
  • 同一 tie-break 规则

然后比较 ANN 和 Flat 的 ID 集合。

3. Tie 会让精确答案不唯一

当多个候选距离完全相同或在数值容差内相同，单一有序列表并不一定是唯一真值。

工程上有三种处理方式：

  1. 使用稳定二级排序，如 distance ASC, chunk_id ASC。
  2. 对第 k 位边界的等距集合采用集合容忍。
  3. 同时报告严格有序一致率与距离容忍下的集合 recall。

若生产索引和基线使用不同浮点精度，边界 tie 更常见。测试不应把无业务影响的等距交换误报为严重回归，也不能因为“只是 tie”忽略二级排序不稳定导致的分页重复。

4. Flat 也可能写错

把代码命名为 brute_force 不会自动让它正确。基线需要独立验证：

  • 小向量手算
  • cosine、dot、L2 的性质测试
  • 单位向量等价排序
  • 零向量和 NaN 行为
  • 空候选和 k > N
  • 稳定 tie-break
  • 与第二种实现做差分

基线代码与 ANN 包装器若复用同一个错误的 score 转换，二者会“完美一致”地出错。因此关键数学函数应使用已知样例和独立实现交叉验证。

3. IVF 依赖训练分布

  • 训练样本是否覆盖所有租户、语言和类别
  • 是否被头部租户或重复内容主导
  • 增量数据与训练时分布是否漂移
  • 空列表和超长列表比例
  • 查询落到的 probe 列表长度分布
  • 新类别出现后 recall 是否下降

所以 IVF 实验要分别控制：

  • probe 数
  • 每个 probe 的扫描量
  • 过滤发生位置
  • 合法候选选择率
  • 是否按租户或类别分区训练

只记录“top_k=10”无法解释失败。

九、HNSW：多层近邻图换取查询速度，也带来内存与维护成本

1. 原始算法边界

Malkov 与 Yashunin 的 HNSW 原始论文提出分层的 navigable small world 图。元素以随指数衰减概率进入更高层；查询从稀疏高层开始导航，再在更密的低层细化。

直观理解是：

  • 高层长边负责快速接近目标区域
  • 低层短边负责局部精细搜索
  • 搜索维护候选队列，在预算内探索图邻居

它是近似算法。图搜索没有访问全部节点时，就不存在“必然返回精确 top-k”的保证。

2. 三个常见参数

以 Faiss 和多种常见实现的命名为例：

  • M：图中连接规模的重要参数。更大通常增加内存、构建成本，并可能提高可达性和 recall。
  • efConstruction：构建时探索深度。更大通常改善图质量，但降低构建或写入速度。
  • efSearch：查询时动态候选规模。更大通常提高 recall，也增加延迟。

具体含义、默认值和约束属于实现与版本。不能把 pgvector 的默认值直接当成 Faiss 或其他产品的参数契约。

pgvector 0.8.x README 说明其 HNSW 相对 IVFFlat 在速度与 recall 权衡上通常更好，但构建更慢、内存更多，而且无需 IVFFlat 那样的训练步骤。这是该产品文档给出的实现比较，不是所有数据集上的无条件定律。

3. 图质量会受写入顺序和分布影响

实验应覆盖：

  • 随机打乱写入顺序的多次构建
  • 按租户、时间或类别排序写入
  • 批量初建与持续增量写入
  • 热门区域高密度、长尾区域稀疏
  • 删除和更新后的图
  • 不同随机种子

若只有一次构建结果，就无法判断 0.5 个百分点的 recall 变化来自参数还是随机建图差异。

4. 删除能力必须限定到具体实现

Faiss IndexHNSW Wiki 明确写明其实现不支持直接移除向量，因为这会破坏图结构。这个限制不能外推为“HNSW 算法永远不能删除”。不同数据库会使用逻辑删除、图修复、版本替换、后台重建或自身维护机制。

测试方案应针对实际产品回答：

  • 删除何时对查询不可见
  • 旧节点是否仍占内存和搜索预算
  • 更新是原位、删除加插入，还是整段重建
  • vacuum、compaction、reindex 会阻塞什么
  • 副本间删除可见延迟多大

pgvector 0.8.x 支持 PostgreSQL 的 insert、upsert、update 和 delete 语义，其 README 同时提醒 HNSW 索引 vacuum 可能较慢，并给出先并发 reindex 再 vacuum 的运维建议。它与 Faiss IndexHNSW 的库级操作模型不是同一层，不应混写成一个能力表。

  2. 读取候选的原始或更高精度向量。
  3. 用原始距离重新排序。

它能修复候选池内部的距离近似错误，但无法救回第一阶段没有召回的向量。

如果系统为了节省内存完全不保存原始向量，就要明确接受无法做原向量重排和某些排障对照的限制。

4. PQ 的专项测试

  • 码本训练样本代表性
  • 不同子空间方差是否极不均衡
  • 重构误差分布
  • top-k 边界距离间隔与翻转率
  • 长尾语言和业务切片 recall
  • float32、float16、PQ 的逐级损失
  • 压缩后内存、缓存命中与实际吞吐
  • 重排读取导致的随机 I/O

“索引小了 8 倍”不能单独成为发布结论。要同时报告它在本实验数据上的质量、延迟和资源变化。

十一、索引选择：先用约束排除，再找 Pareto 前沿

1. 四类索引的工程对照

十四、多租户隔离：检索质量问题不能覆盖授权问题

1. 候选不可见与结果不可见是两道防线

理想情况下，未授权向量不进入该请求的可搜索宇宙。即使底层实现采用共享图，也应保证过滤和返回路径不会泄露：

  • 文档 ID
  • 标题或摘要
  • 距离分数
  • 命中数量
  • 存在性
  • 时间侧信道中可利用的信息

融合或 rerank 后再做一次权限复核可以作为纵深防御，但不能替代召回前的范围约束。后置复核主要防止缓存污染、映射错误和下游代码缺陷。

2. 安全门禁必须是计数为零

以下指标不做平均：

一次跨租户泄漏不能被 99.99% 正确率抵消。

3. 负向测试要主动构造“更相似的非法文档”

如果非法文档离查询很远，过滤错误可能一直不暴露。

测试集应刻意构造：

  • 其他租户中与 query 完全相同的向量
  • 当前租户已过期但文本完全匹配的旧政策
  • 当前租户中 ACL 不允许但更相似的财务文档
  • 已删除但仍在图中的热门分片
  • 可访问 parent 下不可访问 child，及其反向组合

预期结果不是“非法文档排在后面”，而是它们永远不能进入最终结果和可见证据。

4. 过滤缓存也要测试隔离

故障注入包括：

  • 故意从缓存键移除 tenant
  • 让 ACL policy version 变化但缓存不失效
  • 并发切换用户身份
  • 主副本权限快照短暂不一致
  • filter service 超时

安全默认值应是拒绝或明确不可用，不是退化成全库搜索。

1. 插入成功不等于所有查询副本可见

一次写入可能经过：

应分别记录每段时间，而不是只记录接口耗时。

建议定义：

按 p50、p95、p99 和最大值报告，并区分新增、更新、删除。

2. 更新通常是新版本替换

正文变化后，旧向量不再对应当前内容。稳妥流程是：

  1. 创建新 revision 和新 chunk manifest。
  2. 生成新向量并完成一致性检查。
  3. 新 revision 进入可见集合。
  4. 旧 revision 原子失效。
  5. 后台回收旧向量和索引空间。

若先删除旧版再生成新版，会出现资料空窗；若先发布新版但旧版未失效，会出现双版本冲突。选择哪种一致性模型，要由业务风险决定并通过并发测试验证。

3. 删除要区分逻辑不可见与物理回收

删除 SLA 至少有两个时点：

  • 查询不可见时间：任何新请求都不能返回该对象。
  • 物理回收时间：向量、图节点、缓存和备份按策略回收。

安全门禁首先盯查询不可见。即使底层图暂时保留墓碑节点，最终返回路径也必须排除它；同时要监控墓碑积累对搜索效率和 recall 的影响。

4. 索引退化需要触发重建

重建触发器可能来自：

  • tombstone 比例
  • 更新率
  • IVF 列表不均衡
  • 查询分布或语料分布漂移
  • ANN recall 下降
  • 图访问节点数上升
  • PQ 重构误差上升
  • 库版本升级

重建过程要有双容量预算、快照一致性、追赶增量、原子切换和回滚。仅在单副本上原地重建会把性能实验变成可用性事故。

十九、失败注入：主动让索引在可控方式下犯错

1. 模型空间混用

注入方式：查询携带 model_v2，索引 manifest 是 model_v1。

期望：入口硬失败，错误包含双方版本，不执行检索。

禁止行为：只检查维度后继续搜索。

2. 漏归一化

注入方式：随机选一批库向量乘以 10，查询保持不变。

期望：若契约要求单位向量，写入校验拒绝；若业务有意使用 inner product，则结果变化应符合该契约。

这项测试用于区分“归一化 bug”与“本来就允许范数承载信号”。

3. IVF 训练漂移

注入方式：索引只用旧领域训练，再写入一个向量分布明显不同的新领域。

观察：列表长度、probe 命中、ANN recall、查询延迟。

期望：监控能够识别切片退化并触发重训评审，而不是只看全局均值。

4. HNSW 搜索预算缩小

注入方式：逐级降低 efSearch，或限制访问节点数。

观察：每条 query 的 ANN recall 与延迟配对变化。

期望：找到性能质量前沿；低于门槛时阻断发布。

5. PQ 精度下降

注入方式：降低 code 预算或使用更激进精度，再对候选做和不做原向量重排。

观察：量化重构误差、候选 recall、边界翻转、内存。

期望：能分辨候选遗漏和候选内部错序。

6. 过滤选择率骤降

注入方式：把测试 tenant 的合法集合从全库 10% 降到 0.01%，并放入更相似的非法向量。

观察：returned_k、扫描轮数、节点访问、p95、stop reason。

期望：不越权；预算不足时明确返回 insufficient_candidates_after_filter，而不是伪装完整结果。

7. 删除传播延迟

注入方式：删除一个原 top-1 分片，同时暂停某个索引消费者或副本同步。

观察：各副本首次不可见时间、缓存命中、墓碑 watermark。

期望：超出删除 SLA 立即告警并停止向不一致副本路由。

8. 构建中断与索引损坏

注入方式：构建过程中终止进程、截断产物、让 manifest 与数据文件摘要不一致。

期望：不发布半成品；启动时校验失败；旧索引继续服务；修复过程有审计。

9. 过滤服务超时

注入方式：ACL 解析超时或返回未知策略版本。

期望：安全失败。不能去掉过滤后继续检索，也不能复用其他用户的上一次权限集合。

10. 浮点与 tie 扰动

注入方式：把 top-k 边界向量调整到距离差小于 float16 量化误差。

期望：报告边界不稳定；稳定二级排序生效；业务关键结果不能只依赖不可分辨的小数差。

2. 第一轮误判

团队先怀疑：

  • Embedding 模型不理解该租户术语
  • 新文档尚未写入索引
  • HNSW efSearch 太低

于是把 efSearch 提高一倍。p95 上升到 121 ms，返回条数略有改善，但仍不稳定。

4. 根因

根因是三项设计叠加：

  1. T-317 只占共享索引极小比例，选择率很低。
  2. 更大的头部租户有大量语义近似政策，占满固定全局候选窗口。
  3. 过滤只在 ANN 扫描后执行，没有迭代补扫，也没有结果不足状态。

把 efSearch 调大只让图搜索更准确地找到全局近邻，不能保证合法租户候选进入固定窗口。

5. 为什么监控没有提前发现

  • ANN recall 使用全库 Flat，未按合法集合对照。
  • 报告只有平均 recall，没有按 tenant 规模和选择率切片。
  • HTTP 200 被计为成功，returned_k < requested_k 没有单独指标。
  • trace 没有记录各过滤原因。
  • 压测数据按租户均匀构造，没有模拟头部租户密集近重复。

6. 修复方案

短期：

  • 对结果不足启用带硬预算的迭代扫描。
  • 输出 returned_k 和 stop_reason。
  • 按选择率动态设置初始候选预算，但不把估算当保证。
  • 为小租户失败样本建立过滤后 Flat 回归。

中期：

  • 按租户规模分层路由。
  • 大租户独立分区；小租户按稳定哈希桶或业务域分区。
  • 对合法子集很小的请求直接做预过滤精确搜索。
  • 在融合或返回边界再次做权限复核。

长期：

  • 把 tenant/ACL 纳入检索计划选择器。
  • 按选择率、访问节点和质量自适应选择 Flat、局部 ANN 或迭代扫描。
  • 将跨租户和结果不足纳入发布硬门禁。

二十一、指标口径：质量、性能、资源、新鲜度和安全分开报告

1. 数学与表示健康

分母分别是写入向量数或查询向量数。查询和文档要分开报告。

2. ANN 质量

severe_miss_rate 必须由业务定义，例如 ANN recall@10 小于某门槛的 query 比例。示例门槛不能跨业务复用。

3. 过滤完整性

当合法集合本来不足 k 时，应单独标记 eligible_count < k，避免把正确的短结果当索引故障。

4. 性能

分阶段记录：

报告 p50、p95、p99、最大值、样本量和并发。平均延迟无法说明尾部扫描失控。

5. 资源

“每向量字节”要说明是否包含原始向量、图、ID、倒排列表、删除标记和数据库页开销。

6. 新鲜度与维护

按操作类型分别统计。更新成功率不能代替更新可见延迟。

7. 安全硬门禁

这些计数为零时，也只说明所测样本未发现违规，不是对所有未来输入的形式化证明。仍需持续监控、最小权限和纵深防御。

二十二、性能实验设计：避免把缓存、并发和过滤混成一个数字

1. 数据规模阶梯

至少覆盖：

  • 小规模：验证数学和执行计划
  • 中规模：参数扫描和快速回归
  • 目标规模：容量结论
  • 超目标规模：观察退化形态与安全余量

向量维度、元数据宽度和重复度也要接近真实分布。只复制同一向量到一百万条，会形成异常 tie 和图结构，不能代表生产。

2. 查询工作负载

包含：

  • 热门 query 重复
  • 长尾 query
  • 过滤选择率从高到极低
  • 不同 tenant 规模
  • 有结果、合法集合不足和完全无结果
  • 新写入目标
  • 已删除目标
  • top-k 边界非常接近的查询

查询比例要同时报告“实验均匀采样”和“生产流量加权”。前者发现长尾问题，后者估算容量。

3. 并发模型

单线程延迟优秀，不代表目标并发下稳定。需要控制：

  • 到达率
  • 并发数
  • 查询和写入混合比例
  • 批量构建是否同时运行
  • 多租户公平性
  • 超时后的后台取消

扫描预算增大可能在单请求上提高 recall，却在并发下占满 CPU 或内存带宽，反过来让更多请求超时。

4. 结果必须带置信范围或重复运行

索引构建和系统负载存在波动。至少对关键配置多次构建或多次运行，报告：

  • 重复次数
  • seed
  • 中位数与区间
  • 最差一次
  • 异常 run 是否剔除及理由

不能挑最快的一次延迟和最好的一次 recall 拼成一条不存在的配置。

二十三、常见误区

1. 维度相同就认为模型兼容

维度只证明数组长度相同。模型空间、前处理和角色必须全部匹配。

2. 把 cosine 当概率

cosine 是几何相似信号，不是未经校准的业务正确概率。

3. 忘记距离方向

cosine similarity 和 inner product 通常越大越近；L2 与 cosine distance 通常越小越近。日志和 API 必须明确。

4. 把平方 L2 当普通 L2

排序相同，数值和阈值不同。Faiss METRIC_L2 返回平方 L2。

5. 用 ANN recall 证明业务召回

ANN recall 只证明近似索引接近 Flat。业务相关性仍需 qrels 和任务断言。

6. 没有 Flat 基线就调参数

只看最终答案变化，无法分辨 Embedding、索引、过滤和生成责任。

7. 只在全库测 ANN recall

生产若有过滤，oracle 也必须使用同一合法集合。

8. 认为 HNSW 一定优于 IVF

真实取舍受实现、数据、内存、构建、过滤和维护约束。官方产品比较不能替代本地实验。

9. 认为 HNSW 都不能删除

Faiss IndexHNSW 的直接移除限制是具体实现行为。数据库产品可能提供逻辑删除和维护流程。

10. 把 metadata post-filter 当无成本 WHERE

固定 ANN 窗口会被非法候选占满，低选择率下返回不足。

11. 为了凑足 k 用未授权结果补齐

这是权限漏洞，不是召回优化。

12. Chunk 只按平均 token 数验收

平均长度不反映条件切断、结构丢失、重复和权限不一致。

13. PQ 只报压缩比

必须同时报告候选 recall、量化错序、重排成本和真实内存。

14. 只看 HTTP 成功率

返回 200 可能同时发生结果不足、旧版本、越权或距离方向错误。

15. 构造数据的数字直接进入容量规划

构造夹具验证逻辑，不代表真实维度、硬件、数据分布和并发。

二十四、从 0 到 1 的实施顺序

阶段一：先建立精确、可审计的最小系统

  • 冻结 Embedding 契约
  • 建立稳定 chunk ID 和 manifest
  • 实现 Flat exact search
  • 实现 tenant、ACL、时间和删除过滤
  • 保存原始距离与稳定排序
  • 用手算样例和纯 Python 夹具验证

阶段二：建立真实基线

  • 固定语料与查询快照
  • 生成 eligible Flat top-k
  • 按选择率和 tenant 规模切片
  • 明确业务 qrels 与 ANN oracle 的区别
  • 建立失败样本包

阶段三：引入 ANN

  • 选择一到两种候选索引
  • 扫描参数并找 Pareto 前沿
  • 加入过滤执行实验
  • 加入并发和增删测试
  • 把 ANN recall、returned_k 和 p95 一起门禁

阶段四：压缩与规模化

  • 在 float32 基线上逐步引入 half precision 或 PQ
  • 分解候选损失和量化损失
  • 评估原向量重排
  • 设计重建、切换和回滚
  • 建立线上影子和持续 recall 抽样

二十五、上线检查表

表示契约

  • query 与 document encoder 的工件 ID 已冻结
  • 输入角色、前缀、截断和前处理已版本化
  • 维度、dtype、归一化和距离函数一致
  • 零向量、NaN、Infinity 有明确失败语义
  • 模型版本不匹配会在检索前硬失败
  • 新旧模型没有混写到同一无版本索引

Chunk 与数据

  • chunk policy 和 parser 有版本
  • chunk_id 可稳定追踪到文档 revision 和原文偏移
  • 标题、列表、表格和代码块边界已抽检
  • overlap 重复和 parent 集中度已测量
  • 正文哈希、向量哈希和元数据版本可以对账
  • 语料快照和删除 watermark 可复现

距离与 Flat

  • cosine、dot、L2 的方向和转换已记录
  • 平方 L2 与普通 L2 没有混用阈值
  • 单位向量等价关系有自动化测试
  • Flat oracle 通过手算和第二实现差分
  • tie-break 稳定且分页一致
  • Flat 与 ANN 使用同一合法候选集合

ANN 索引

  • 索引类型和参数限定到具体产品版本
  • 构建训练数据和 seed 可追溯
  • IVF 的列表分布、probe 和漂移已评估
  • HNSW 的构建顺序、搜索深度和内存已评估
  • PQ 的重构误差、候选损失和重排收益已评估
  • ANN recall@k 按关键切片报告
  • 参数变更有配对样本和回滚版本

过滤与隔离

  • tenant 和 ACL 被定义为授权边界
  • 过滤选择率分布已测量
  • pre-filter、post-filter 或 iterative 行为与产品文档一致
  • 结果不足有 returned_k 和 stop_reason
  • 迭代扫描有节点、probe、轮数和 deadline 上限
  • 更相似的跨租户、过期和未授权候选已做负向测试
  • 返回边界有权限纵深复核
  • 过滤缓存键包含权限与版本上下文

增删与运维

  • 插入、更新、删除可见延迟分别有 SLA
  • 逻辑不可见与物理回收口径分开
  • 副本 watermark 和缓存失效可观测
  • 墓碑、图退化或分布漂移有重建触发器
  • 重建支持快照、增量追赶、原子切换和回滚
  • 半成品或摘要不一致的索引无法发布

性能与证据

  • 目标规模、维度、并发和过滤分布接近生产
  • 冷热缓存条件已说明
  • p50、p95、p99 与样本量完整
  • 内存口径说明包含哪些结构
  • 构造数据数字没有冒充生产结论
  • SearchTrace 能还原 raw candidates、过滤拒绝和最终结果
  • 跨租户、越权和超删除 SLA 计数为零

二十六、总结

Embedding 和向量检索真正难的地方，不是调用一个 similarity_search()，而是维护一套在数学、数据、索引、过滤和权限上都一致的检索契约。

距离层要记住：

  • dot product 同时受方向和库向量范数影响
  • cosine 去除范数影响，但零向量没有定义
  • L2 越小越近，Faiss METRIC_L2 返回平方 L2
  • 单位向量上 cosine、dot 与平方 L2 排序等价，但数值不相同
  • 相似度不是业务正确概率

数据层要做到：

  • Embedding 模型、前处理、角色、归一化和维度共同版本化
  • 不同模型空间不能因为维度相同就混用
  • Chunk 保留结构、证据边界、权限一致性和稳定 lineage
  • 向量、正文、元数据与删除状态可以逐条对账

索引层要建立：

  • Flat 精确基线
  • IVF 的训练与 probe 实验
  • HNSW 的图、内存、搜索深度和实现级增删约束
  • PQ 的压缩、量化损失与原向量重排对照
  • ANN recall@k 相对同一合法集合 Flat 的清晰口径

过滤层要明确：

  • pre-filter 改变可搜索宇宙
  • post-filter 会让固定候选窗口在低选择率下返回不足
  • iterative scan 要有硬预算和停止原因
  • tenant 与 ACL 是授权边界，不能靠相关性参数“尽量过滤”

最终发布决策必须同时看质量、延迟、资源、新鲜度和安全。

一个相似度分数可以解释“在当前向量空间里有多近”；只有完整的版本、Flat 对照、过滤证据和业务标注，才能继续解释“为什么返回它，以及它是否应该被当前用户看到”。
