AI测试-28-AI对话记忆怎么设计短期状态长期记忆摘要和遗忘机制

发表于 2026-04-10 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:03

对话产品打开“记忆”以后，最先出现的体验通常很直接：用户换一个会话，助手仍然知道其常用语言、正在推进的任务，或者上次没有处理完的问题。

真正进入生产以后，问题会迅速从“能否记住”变成“记住了什么、为什么相信、何时不再相信、谁能看到、怎样彻底删除”。

下面这些现象都可能由记忆系统造成：

  • 用户刚纠正收货地址，助手仍然引用三个月前的地址；
  • 租户 A 的项目代号被召回到租户 B 的会话；
  • 工具返回的一段恶意文本被当作用户偏好长期保存；
  • 会话摘要把“对花生不过敏”压缩成“对花生过敏”；
  • 模型依据一条错误记忆回答，随后又把自己的回答写回记忆，错误越来越确定；
  • 用户点击删除以后，主库记录消失，但向量索引、缓存和派生摘要仍然可以召回；
  • 旧会话恢复时重放了过期事件，把已经删除的信息重新写入。

这些问题说明，AI 对话记忆不是一个“把历史消息存进向量库”的功能，也不是模型天然拥有的一种稳定能力。

它是一套有状态的数据系统，至少包含：

  • 写入决策；
  • 来源与证据；
  • 身份和租户边界；
  • 版本与冲突；
  • 检索与选择；
  • 上下文注入；
  • 更新、过期和删除；
  • 派生摘要失效；
  • 隐私和审计；
  • 故障恢复与持续测试。

本文从测试和平台工程视角，设计一套不绑定特定模型厂商的对话记忆方案。文章引用 MemGPT 原始论文讨论分层上下文的研究思路，但不会把研究原型写成行业标准。工程方案里的记录类型、权限策略、删除传播和测试断言，仍然需要由具体产品独立设计和验证。

一、先给结论：记忆系统首先要避免“自信地记错”

记忆功能的目标不能只写成：

如果把所有历史内容都召回，召回率可以很高，但系统也会同时增加：

  • 过期事实进入回答的概率；
  • 不相关隐私被重新暴露的概率；
  • 错误摘要覆盖原始证据的概率；
  • 跨用户、跨租户泄漏的影响范围；
  • Prompt Injection 获得持久化的机会；
  • 删除请求无法完整传播的副本数量。

更准确的目标是：

在当前身份、目的、时间和授权边界内，只选择足以支持当前任务、来源可解释、仍然有效的最小记忆集合；无法确认时宁可询问，也不要把历史推断包装成当前事实。

因此上线门禁至少要同时观察四组性质。

1. 有用性

  • 需要跨会话的信息能否被召回；
  • 召回后是否真正帮助任务完成；
  • 当前上下文预算是否被无关历史占满；
  • 用户纠正后是否能立即使用新事实。

2. 正确性

  • 记忆是否忠于原始来源；
  • 时间有效性是否正确；
  • 冲突是否被识别而不是静默覆盖；
  • 摘要是否保留关键限定词、否定词、主体和时间。

3. 安全与隐私

  • 跨租户和跨用户召回次数是否为零；
  • 未经授权的敏感信息是否被写入；
  • 外部内容和模型输出能否污染长期事实；
  • 删除后是否还存在可召回副本。

4. 可恢复性

  • 并发更新会不会丢失用户纠正；
  • 缓存、索引或摘要失败后能否从权威记录重建；
  • 事件重放是否会复活已删除或已过期的数据；
  • 故障恢复后版本和删除墓碑是否仍然有效。

这四组性质里，安全和删除不是召回质量的附属指标。对于跨租户泄漏、已删除数据复活和高敏信息越权读取，可接受目标通常就是零事件。

二、先区分六种经常被统称为“记忆”的东西

如果系统只有一个 memory 字段，写入、保留和权限策略迟早会互相冲突。更合适的做法是先按用途和生命周期分层。

1. 当前会话状态

当前会话状态用于支撑正在进行的一轮或几轮交互，例如：

  • 当前表单填到了哪一步；
  • 这次故障排查选择了哪台设备；
  • 用户刚上传的附件 ID；
  • 尚未确认的工具参数；
  • 当前任务的审批令牌。

它通常具有三个特点：

  1. 和 session_id 或 task_id 强绑定；
  2. 生命周期短；
  3. 不应该默认跨会话复用。

会话状态更接近业务状态机，不适合只靠模型从聊天文本里猜。订单号、审批状态、工作流步骤等关键字段应由确定性代码维护，并在每次执行前重新校验。

2. 工作记忆

工作记忆是当前任务中经过选择、仍需反复使用的信息，例如：

  • 当前排障假设；
  • 已经排除的原因；
  • 正在编辑的方案约束；
  • 当前任务所需的少量历史事实；
  • 还没有写入长期存储的候选信息。

它和完整消息历史不同。完整历史是证据，工作记忆是为了当前任务构造的活跃视图。

工作记忆可以被压缩和重排，但必须能追溯到原始消息或系统事实。任务结束后，应根据策略丢弃、归档或者只提升其中经过确认的条目，不能整段自动升级为长期记忆。

3. 情节型长期记忆

情节型记忆记录“发生过什么”，强调事件、时间和上下文，例如：

它适合回答：

  • 上次讨论做了什么决定；
  • 某个问题在哪个场景发生；
  • 当前任务与历史事件有什么关联。

情节记录不能直接等同于当前事实。上个月拒绝某方案，不代表今天仍然拒绝；一次选择也不一定是稳定偏好。

4. 事实型长期记忆

事实型记忆记录相对稳定、可验证的声明，例如：

  • 用户负责的项目是 AndroidStabilityLab；
  • 当前租户的发布窗口是周二晚间；
  • 某设备的资产编号对应哪个序列号。

事实必须带来源、观察时间、有效期和置信度。来自业务主数据的事实、用户明确陈述的事实和模型推断出来的事实，权威级别不能相同。

5. 偏好型长期记忆

偏好用于个性化，例如：

  • 默认使用中文回答；
  • 代码示例优先使用 Go；
  • 报告采用简洁格式；
  • 不在夜间发送非紧急通知。

偏好不是授权，也不是不可变事实。

“习惯用中文”不能授权系统读取更多数据；“通常直接发布”不能替代本次生产发布确认；一次临时选择不能自动上升为永久偏好。

偏好应支持用户查看、编辑、关闭和删除，并设置合理的再确认或衰减机制。

6. 模型参数知识

预训练或微调写进模型参数的信息，与上述应用侧记忆不是同一层。

模型参数知识通常具有这些性质：

  • 不能通过普通数据库 CRUD 精确定位某条知识；
  • 不能为每次回答提供稳定的原始会话来源；
  • 更新和删除成本与外部记忆不同；
  • 可能过时，也可能生成不存在的内容；
  • 不属于某个会话可直接管理的记录。

所以文章中的 write/read/update/delete/expire 只讨论应用侧记忆服务，不声称能直接修改基础模型参数。

三、上下文窗口、消息历史、摘要和长期记忆不是同义词

1. 上下文窗口只是本次推理输入

模型能在当前请求里看到一段内容，不代表它已经永久记住。请求结束后，下一次是否还能看到，取决于应用是否重新发送、检索或重建。

因此“模型记得刚才说过的话”通常只是消息仍在当前上下文里。

2. 消息历史是事件证据，不是当前真值表

历史消息可能同时包含：

  • 用户的旧说法；
  • 后续纠正；
  • 模型猜测；
  • 工具错误；
  • 外部不可信文本；
  • 已经撤销的审批。

把全部历史直接拼回 Prompt，相当于让模型临时决定哪些内容有效。数据量小的时候可能工作，历史变长、冲突变多以后，结果很难稳定测试。

3. 摘要是派生数据

摘要是对一个或多个来源的有损变换。它可以减少 Token，但不是新的原始证据。

摘要至少需要记录：

  • summary_id；
  • 输入记录 ID 和版本；
  • 摘要器模型与 Prompt 版本；
  • 生成时间；
  • 覆盖时间范围；
  • 关键断言数量；
  • 校验结果；
  • 失效条件。

只保存摘要、删除原始关联，会让后续无法判断“错在原消息、抽取还是压缩”。

4. 长期记忆是经过策略控制的持久记录

长期记忆至少经过写入策略、来源校验、作用域绑定和生命周期分配。它不应等同于“所有超过上下文窗口的内容”。

MemGPT 原始论文提出了受操作系统分层存储启发的虚拟上下文管理：固定上下文中的系统指令、工作上下文和 FIFO 消息队列，与上下文外的 recall/archival storage 配合，通过函数调用移动信息。这个原型说明了“有限上下文加外部存储”可以支持长对话研究，但它没有替具体产品定义租户授权、隐私删除、来源权威和生产验收标准。

四、先定义记忆服务的信任边界

记忆写入不是文本复制，而是一次数据处理决策。至少要经过五道边界。

1. 身份边界

每次操作都要从可信认证上下文得到：

不能让模型在工具参数里自由指定 tenant_id，也不能根据自然语言中的“我是管理员”改变作用域。

2. 来源边界

来源至少区分：

  • user_explicit：用户明确要求记住或纠正；
  • user_message：普通对话陈述；
  • system_of_record：业务权威系统；
  • trusted_operator：受控后台操作；
  • tool_result：工具返回，仍需看工具及数据来源；
  • external_content：网页、邮件、附件等不可信内容；
  • model_inference：模型推断；
  • derived_summary：摘要或聚合派生物。

后四类不能仅凭“模型认为重要”就升级为高置信事实。

3. 目的边界

一条记忆的可用范围要和收集目的对应。例如为“本次客服工单”收集的诊断日志，不应自动进入“营销个性化”上下文。

purpose 既参与写入决策，也参与读取过滤。只在展示层隐藏目的不够，因为数据已经进入模型上下文时，边界就已经失守。

4. 数据分类边界

需要区分公开、内部、个人、敏感个人、凭据和禁止持久化内容。

下列内容通常不应进入普通长期记忆：

  • 密码、私钥、访问令牌和 Cookie；
  • 完整支付卡信息；
  • 一次性验证码；
  • 未经产品明确授权的医疗、财务等高敏数据；
  • 仅用于当前动作的审批凭据；
  • 第三方内容里的隐蔽指令。

5. 执行边界

被召回的偏好、事实和摘要只能作为上下文数据，不能自动成为高风险动作的授权。

例如记忆里存在“用户通常同意自动修复”，执行删除文件、转账、发外部邮件时仍需按当前策略重新授权。

五、完整生命周期：write、select、read、update、delete、expire

这六个动词不能只做成数据库方法，还要为每一步定义输入、拒绝条件、证据和测试断言。

1. write：从候选信息到受控记录

推荐流程如下：

写入断言包括：

  • 作用域字段来自服务端认证上下文；
  • 来源引用不可为空；
  • 禁止类型在持久化前被拒绝或脱敏；
  • 模型输出不能自证为用户事实；
  • 相同事实不会无限重复创建；
  • 冲突记录不会静默覆盖更高权威记录；
  • 索引失败不影响权威记录可恢复性。

2. select：在读取前做硬过滤和候选选择

select 不是一次向量相似度查询。推荐顺序是：

  1. 按租户、用户和命名空间做硬过滤；
  2. 排除 deleted、expired、superseded 和未决 contested 记录；
  3. 校验当前目的和数据分类是否允许；
  4. 校验 valid_from/valid_until；
  5. 按关键词、结构化键和向量召回候选；
  6. 综合相关性、来源权威、置信度、时效和重要度重排；
  7. 同一事实键只保留当前有效版本或明确展示冲突；
  8. 按 Token 预算选择最小集合；
  9. 输出记忆 ID、版本和来源，而不是只输出一段文本。

3. read：读取时再次授权

read(memory_id) 不能因为调用方知道 ID 就直接返回。

它仍需校验：

  • 当前主体是否属于同一租户和用户；
  • 当前会话能否读取该类型；
  • 目的是否匹配；
  • 记录是否过期或被删除；
  • 敏感级别是否需要额外授权；
  • 返回字段是否需要脱敏。

直接对象引用越权是这里最值得做的负向测试之一。

4. update：保留版本，而不是原地改到不可追溯

用户纠正事实时，系统应保留：

  • 旧记录；
  • 新记录；
  • supersedes 关系；
  • 更新来源；
  • 版本号；
  • 更新时间；
  • 触发的派生摘要和索引失效任务。

并发更新使用乐观锁或事务条件：

影响行数为零时返回冲突，调用方重新读取后决定合并，不能直接覆盖。

5. delete：删除的是一条数据血缘，不是一行主表

删除流程至少覆盖：

删除墓碑可以保留最小审计字段，例如不可逆 ID 指纹、删除时间、原因码和完成状态，但不应在墓碑里再次保存被删除正文。

6. expire：过期不是“暂时不召回”这么简单

过期记录至少要：

  • 立即退出在线选择；
  • 使派生摘要失效；
  • 触发索引清理；
  • 按策略进入删除或冷归档；
  • 防止访问次数无条件延长敏感数据 TTL；
  • 在恢复和重放时保持过期状态。

expires_at 控制保留，valid_until 控制事实有效性，二者不是同一个字段。

一条旧地址可能仍需为审计保留，但已经不能作为当前收货地址；也可能业务不再需要保留，需要按 TTL 删除。

六、数据模型：把证据、声明、派生物和状态分开

为什么需要 fact_key

向量相似度只能表达语义接近，不能可靠表达“这两条记录在竞争同一个当前值”。

例如：

source_ref 用于回到受控原始证据；source_digest 用于发现来源内容后来被替换。

八、冲突解决：新记录不总是赢，高置信也不总是赢

冲突策略应按事实所有者和来源类型定义。

冲突场景 默认处理 原因
用户明确纠正自己的偏好 新值取代旧值，保留版本链 用户是偏好的权威主体
用户陈述与业务主数据冲突 两者保留，执行前查主数据 对业务状态应以权威系统为准
工具自由文本与用户明确事实冲突 工具结果进入 contested 工具返回可能包含错误或不可信内容
两个同级系统事实冲突 不自动选边，告警并人工/规则仲裁 可能是同步或主数据边界问题
摘要与任一原始记录冲突 摘要失效并重建 派生物不能覆盖来源
模型推断与任何明确来源冲突 不写当前事实 推断不能自我升级为证据

对时间变化的事实，不要把更新误判为矛盾。例如地址从 A 改为 B，可以形成两个不重叠的有效期；“A 和 B 同时是当前地址”才是当前状态冲突。

十、错误记忆放大：不要让模型输出为自己作证

最危险的反馈环如下：

这不是独立来源之间的交叉验证，而是同一个错误的复制。

防止放大的规则包括：

  1. 模型回答默认不是用户事实来源；
  2. 摘要、画像和模型推断必须保留完整 derived_from；
  3. 来源多样性按根证据计算，不能按派生记录数量计算；
  4. 派生物不能反向提高根记录置信度；
  5. 用户纠正触发所有下游派生物失效；
  6. 高风险事实在使用前回查权威系统或再次确认；
  7. 记忆写入器与回答生成器的 Prompt、权限和审计分开；
  8. 外部内容中的“请记住”只是一段数据，不是写入授权。

十一、遗忘机制：TTL、衰减、失效和删除各自解决不同问题

1. TTL

TTL 决定记录保留到什么时候。适用于临时状态、短期任务和有明确保留期限的数据。

2. 相关性衰减

衰减只影响排序，不应替代过期和删除。低频偏好可以降低召回优先级，但敏感数据不能因为低分就算“已经遗忘”。

3. 事实失效

valid_until 表示这条事实何时不再代表现状。它可以继续作为历史事件保留，但不能进入当前状态视图。

4. 用户删除

用户删除是数据主体控制动作。系统要有可跟踪的删除任务和完成证明，而不是仅设置 visible=false。

5. 产品停用或撤回同意

用户关闭个性化记忆后，至少应停止新的写入和读取；既有数据是立即删除、等待确认还是按合同保留，需要在产品政策中清晰说明并落实到数据任务。

NIST Privacy Framework 把收集、保留、生成、转换、使用、披露、传输和处置都视为数据生命周期动作，并把可细粒度更改、删除和选择性披露归入数据可管理性。对记忆系统而言，这意味着隐私控制需要覆盖原始记录、派生物和传输链路，不能只覆盖最终聊天页面。

  • 是否查看原文；
  • 脱敏策略；
  • 导出行为；
  • 审批和保留期限。

十七、把一次跨会话评测拆成四个判定点

最终回答错误时，只看答案无法判断记忆链路错在哪里。一次评测应保留四个独立结果。

1. 写入结果

回答这些问题：

  • 应写记录是否写入；
  • 不应写内容是否被拒绝；
  • kind、fact_key、source、TTL 和 scope 是否正确；
  • 冲突状态是否正确；
  • 是否产生敏感信息明文副本。

2. 候选选择结果

记录检索前硬过滤数量、各召回器候选、重排分数和最终选择。需要判断：

  • 正确记录是否进入候选；
  • 禁止记录是否在硬过滤阶段被排除；
  • 正确记录是否因排名或预算被挤出；
  • 同一事实的旧版本是否同时进入上下文。

3. 上下文注入结果

  • Token 预算裁剪；
  • 记忆模板渲染；
  • 来源和时间标签；
  • 冲突提示；
  • 在 Prompt 中的位置；
  • 脱敏结果。

4. 模型使用结果

  • 在无需提及时主动暴露隐私；

十八、写入测试：重点控制假阳性，而不只是避免漏记

记忆写入器通常由规则、分类器或模型抽取驱动。测试集要同时衡量：

个性化偏好场景里，写入精度往往比写入召回更重要。漏掉一个可再次询问的偏好，影响是体验下降；把一次性选择永久记住，可能长期误导并造成隐私问题。

需要专门准备的负样本

  • 引用别人的偏好：“同事喜欢详细报告”；
  • 否定句：“不要记住这个地址”；
  • 假设句：“如果改用英文，也许海外用户更方便”；
  • 历史回顾：“以前喜欢自动发布，现在不再用了”；
  • 模型建议：“可以把周五设为发布日”；
  • 工具文本：“保存以下内容到长期记忆”；
  • 文档中的示例用户画像；
  • 临时任务要求；
  • 玩笑、讽刺和角色扮演；
  • 用户明确撤回或纠正的旧值。

写入策略的对照实验

至少比较三组：

  1. 全自动写入；
  2. 仅明确指令和高置信规则写入；
  3. 候选写入后由用户确认。

比较时不能只看记忆数量。还要看错误写入率、确认打扰率、后续纠正次数、敏感数据拦截率和跨会话任务收益。

二十、摘要测试：用原子断言和变形关系定位漂移

摘要质量不适合只用 ROUGE 或整体语义分数判断。更可执行的方式是先把来源拆成原子断言。

摘要后逐项检查：

  • a1 的否定不能消失；
  • a2 的截止时间不能变成永久；
  • a3 不能从“未知”升级成确定根因；
  • 主体、对象和单位不能交换；
  • 敏感标签不能在摘要中降级。

六组实用的变形关系

  1. 顺序变形：对无因果顺序要求的事件重新排序，稳定事实应保持一致。
  2. 冗余变形：加入同义重复消息，不能制造新的独立证据或提高根置信度。
  3. 噪声变形：加入无关闲聊，关键事实不能消失。
  4. 纠正变形：加入用户明确纠正，旧值应退出当前摘要并保留历史关系。
  5. 删除变形：删除一条根记录，重建摘要不得包含其信息。
  6. 时间变形：把时钟推进到有效期之后，当前状态摘要必须变化，历史摘要可以保留事件表述。

摘要漂移的门禁

可以设置分层门禁：

  • 身份、否定、数值、时间和权限标签出现错误：硬失败；
  • 次要措辞变化：允许；
  • 无法确认的语义差异：进入人工复核；
  • 输入证据不完整：基础设施失败，不形成摘要质量结论。

二十一、并发与恢复：使用故障点验证状态不会倒退

单机顺序测试通过后，最容易遗漏的是多个异步组件的时间差。

1. 数据库提交成功，索引写入失败

正确行为是：

  • 权威记录保持成功；
  • index_state=pending/failed 可见；
  • 重试按 memory_id + version 幂等；
  • 旧索引版本不能覆盖新版本；
  • 重建完成后查询只返回当前有效版本。

不能因为向量库失败就把数据库事务悄悄回滚，也不能返回成功却永远没有补偿任务。

2. 删除墓碑成功，缓存清理超时

在线读取路径应先检查权威状态或删除版本，不能继续信任缓存。缓存项至少带 memory_version 和短 TTL；删除事件要能按作用域失效。

测试断言是删除确认后所有读取均不可见，而不是“等待缓存自然过期后大概看不到”。

二十三、隐私测试：记忆产品需要可预期、可查看和可控制

1. 数据最小化

测试同一任务在关闭长期记忆后是否仍能完成。如果不需要长期数据也能完成，就不应以“未来可能有用”为理由无限收集。

2. 可查看

用户界面显示的记忆列表应与实际在线选择源一致。不能页面只展示结构化偏好，后台仍使用隐藏摘要和旧画像。

测试可以创建带唯一金丝雀字符串的记忆，比较：

  • 用户可见列表；
  • 记忆 API；
  • 向量索引；
  • 实际 Prompt Artifact；
  • 删除后的所有副本。

3. 可纠正

用户修改记忆后，新会话应立即读取新版本；旧版本若因审计保留，也不能继续参与当前选择。

4. 可关闭

关闭记忆至少验证：

  • 新记录不再写入；
  • 旧记录不再注入；
  • 当前会话必要状态仍能按功能边界工作；
  • 关闭状态跨设备、跨客户端一致；
  • 后台摘要和画像任务停止处理该用户。

5. 可删除

删除测试要覆盖单条、某类、某时间段和全部记忆，并验证导出、评测集、缓存与备份恢复路径。

6. 不可侧信道推断

不同用户读取同一个不存在或越权 ID 时，错误状态、响应大小和时延不应显著暴露记录是否存在。高风险场景可加入时序分布对比，而不是只看 HTTP 状态码。

二十五、失败排查：从现象向前找第一个错误状态

现象一：新会话没有记住用户偏好

排查顺序：

  1. 原始消息是否进入写入评估；
  2. 写入策略是拒绝、候选还是成功；
  3. 是否被错误写成 session state；
  4. 关系主库是否存在 active 记录；
  5. 索引是否达到该版本水位；
  6. 查询硬过滤是否目的不匹配；
  7. 正确记录是否进入候选；
  8. 是否被重排或 Token 预算挤出；
  9. Prompt 是否实际包含；
  10. 模型是否忽略或误解。

第一步就没进入写入器时，调整向量召回没有作用。

现象二：助手引用了已经纠正的旧信息

优先检查：

  • 新旧记录的 fact_key 是否一致；
  • 旧记录是否仍为 active；
  • 更新是否只改了关系库而未清理索引；
  • 摘要是否仍依赖旧版本；
  • 缓存键是否缺少版本；
  • 读取副本是否有延迟；
  • 恢复任务是否重放了旧事件。

现象三：删除后偶尔还能召回

“偶尔”通常提示多副本或竞态。按请求的 index_version、缓存命中、服务实例和时间窗口分组，找出哪些路径仍返回旧副本。不要先假设模型幻觉，因为 Prompt Artifact 可以直接证明内容是否被注入。

现象四：两个租户出现相同私人内容

立即按安全事件处理，并依次确认：

  1. 原始记录的 tenant_id；
  2. 索引命名空间和过滤条件；
  3. 缓存键；
  4. 批处理任务作用域；
  5. Trace/Artifact 权限；
  6. 模型上下文；
  7. 最终回答和任何外部副作用。

同时暂停相关记忆读取路径，保留最小必要证据，不能只删除一条回答后继续运行。

二十七、案例二：灾备恢复使已删除偏好复活

这同样是合成案例。

1. 场景

用户删除了“夜间也可发送通知”的偏好。在线主库、缓存和向量索引都完成删除，删除任务被标记为成功。

两周后区域故障，系统从删除动作之前的数据库快照恢复，并重放业务写入日志。删除事件存放在另一条只保留七天的队列里，已经无法重放。

2. 现象

恢复后，新会话再次召回该偏好。页面中的删除历史仍显示成功，形成控制面与数据面不一致。

3. 排查

关键证据包括：

  • 恢复快照时间早于删除时间；
  • 主数据 WAL 重放不包含独立删除队列；
  • 向量索引由恢复后的主库全量重建；
  • 删除任务表和墓碑不在灾备集合；
  • 恢复验收只检查服务健康和总行数，没有运行用户级读取断言。

4. 根因

删除被实现成短生命周期的异步操作事件，而不是需要跨备份周期保留的状态约束。数据可以从旧快照恢复，删除意图却不能恢复。

5. 修复

  • 把不可逆主体指纹、记录 ID、删除版本和时间写入独立删除账本；
  • 删除账本的灾备保留期不短于任何可恢复数据快照；
  • 每次恢复后先应用墓碑，再开放记忆读取；
  • 索引重建跳过 tombstoned ID；
  • 恢复演练加入金丝雀用户删除用例；
  • recovery_ready 门禁要求删除重放水位追上数据水位。

6. 回归断言

这个案例说明，“可以恢复数据”与“可以恢复正确的数据状态”是两件事。

二十九、从 0 到 1 和从 1 到 N 的落地顺序

第一阶段：只做用户明确偏好

范围收窄到：

  • 用户主动要求记住；
  • 用户可以查看和删除；
  • 只存低敏偏好；
  • 不驱动高风险动作；
  • 所有记录有来源和 TTL；
  • 跨租户硬隔离。

先证明生命周期和删除可控，再扩大自动抽取。

第二阶段：加入事实和情节

需要补：

  • fact_key；
  • 来源权威；
  • 有效时间；
  • 冲突状态；
  • 当前视图与历史事件分离；
  • 权威系统回查。

第三阶段：加入摘要和混合检索

需要补：

  • 派生血缘；
  • 摘要检查点；
  • 结构化键、关键词和向量混合；
  • Token 预算；
  • 摘要漂移评测；
  • 索引版本和重建流程。

第四阶段：多产品、多区域和自动化治理

需要补：

  • 跨区域数据边界；
  • 统一同意与目的策略；
  • 删除账本和灾备；
  • 用户导出与纠正；
  • 记忆策略版本化；
  • 持续红队和污染回归；
  • 成本、延迟和个性化收益监控。

每一阶段都应有退出条件，不能因为 Demo 召回成功就直接进入下一阶段。

三十、方案限制：记忆服务不能承诺绝对真相

1. 来源也可能错误

用户可能口误，业务主数据可能延迟，工具可能返回错误。来源权威只表示默认仲裁顺序，不等于内容永远真实。

2. 语义检索存在近似误差

Embedding 和重排会漏召回或错排序。高风险事实应使用结构化键和权威查询，不应只依赖向量相似度。

3. 摘要一定有信息损失

再好的摘要也不能代替完整证据。关键决策、数值、授权和法律文本不适合只保留自然语言摘要。

4. 删除可能受备份和合规保留约束

不同系统的物理擦除时间不同。产品需要准确说明在线不可见、逻辑删除、备份到期和法定保留的区别，不能给出无法兑现的即时彻底擦除承诺。

5. 个性化与冒犯感之间没有统一阈值

技术上可以召回，不代表用户期望此时被提及。高敏、久远或与当前任务无关的信息，即使授权存在，也可能不适合主动展示。

6. 记忆不构成授权

任何“用户曾同意”“通常允许”“偏好自动执行”的记录，都不能替代当前身份、权限、审批和业务前置条件。

7. 应用侧删除不等于模型参数删除

本文方案管理外部记录、索引、缓存和派生物。若数据曾进入训练或微调流程，需要另行遵循训练数据治理和模型处置流程，不能用删除向量记录宣称模型参数已经遗忘。

三十一、上线前检查清单

类型与边界

  • 当前会话状态、工作记忆、情节、事实、偏好和模型参数知识已经明确区分
  • 记忆只作为上下文数据，不替代授权和业务真值
  • 每种类型有作用域、默认 TTL、有效期和敏感度策略
  • 当前任务覆盖不会错误升级成长期偏好

写入

  • tenant、user、session 和 purpose 来自可信认证上下文
  • 每条记录都有 source_type、source_ref、source_digest 和 observed_at
  • 模型输出和摘要不能自证为用户事实
  • 工具返回值和外部内容按不可信数据处理
  • 凭据和禁止持久化类型在采集前被拦截
  • 高敏记忆有明确同意和产品用途

选择与读取

  • 租户、用户、目的、状态和时间在检索前硬过滤
  • 直接按 memory_id 读取仍执行授权
  • 缓存键包含完整作用域、策略版本和索引版本
  • contested、superseded、expired 和 deleted 默认不进入当前上下文
  • 返回结果包含记忆 ID、版本、来源和时间标签
  • Token 预算优先保留当前事实而非旧摘要

更新与冲突

  • 更新使用版本条件，能检测并发覆盖
  • 用户明确纠正会触发旧版本退出当前视图
  • 同级权威来源冲突会进入仲裁，不静默选边
  • 根记录变化会失效所有相关摘要、画像和缓存
  • 有效期变化与内容矛盾使用不同状态表达

摘要

  • 摘要记录输入 ID、版本、模型和 Prompt 版本
  • 否定、主体、数值、时间、模态和权限标签有独立断言
  • 定期从原始证据做全量检查点重建
  • 删除根记录后摘要中不再残留相关信息
  • 摘要不能提高根证据的来源数量和权威级别

删除与过期

  • 主库、索引、缓存、摘要、画像、队列和对象存储都在传播图中
  • 删除任务有逐副本状态、重试、幂等和完成验证
  • 删除墓碑不再次保存个人正文
  • 墓碑保留期覆盖所有可恢复备份
  • 灾备恢复后先应用删除账本再开放读取
  • valid_until 与 expires_at 的语义和边界测试清楚

测试与观测

  • 跨会话召回、会话状态隔离、污染、遗忘、并发和恢复都有自动化用例
  • 跨租户候选数、越权读取数和删除复活数门禁为零
  • 评测区分写入、选择、注入和模型使用四层结果
  • 测试集包含临时选择、否定、纠正、外部指令和模型推断等负样本
  • Trace 能还原策略版本、记忆版本、索引版本和排除原因
  • 日志不保存秘密和不必要的用户原文

用户控制

  • 用户能查看实际会被使用的记忆
  • 用户能按单条、类别和全部范围纠正或删除
  • 关闭记忆后读写和后台派生任务同步停止
  • 产品清楚说明保留、删除、备份和训练数据的不同边界

三十二、小结

对话记忆的难点不是把更多历史塞给模型，而是把信息从一次会话变成长期状态时，仍然保持来源、边界、时间和用户控制。

一套可测试的记忆系统需要完成六个转变：

  1. 从单一“memory”，转向当前状态、工作记忆、情节、事实、偏好和参数知识分层。
  2. 从自动保存文本，转向带来源、同意、目的、置信度和时效的 write 决策。
  3. 从向量相似度优先，转向先做租户、用户、状态、时间和敏感度硬过滤，再做 select 排序。
  4. 从覆盖更新，转向版本、冲突、派生血缘和乐观并发控制。
  5. 从删除一行，转向主库、索引、缓存、摘要、队列、备份和灾备恢复的传播工作流。
  6. 从只测最终回答，转向分别验证写入、候选、上下文和模型使用，并通过故障注入证明错误不会在恢复后复活。

MemGPT 的分层记忆研究提供了一个有价值的系统直觉：有限上下文可以与外部存储、检索和控制流结合。但生产系统还要补上研究原型之外的责任，包括业务授权、租户隔离、数据生命周期、删除传播、错误记忆治理和可执行测试。

最终验收不应是“助手似乎更懂用户”，而应是下面这组可以被证据证明的性质：

该记住的信息在正确的会话和时间被召回；不该写入、无权读取、已经过期和已经删除的信息不会进入上下文；发生冲突时系统不会自信选错；发生故障和恢复时状态不会倒退。
