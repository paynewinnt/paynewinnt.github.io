AI测试-33-AI功能怎么做模型降级功能熔断和确定性兜底

发表于 2026-04-22 分类于 AI测试 本文字数： 16k 阅读时长 ≈ 1:01

AI 服务出现超时后切换到另一个模型，看起来是一条很自然的高可用方案。

但“另一个模型返回了 HTTP 200”不等于业务已经恢复。

备用模型可能：

  • 不支持原来的工具调用或结构化输出
  • 使用不同的安全边界和停止原因
  • 对同一 Prompt 有不同语义理解
  • 缺少主模型依赖的长上下文、图片或函数能力
  • 生成格式合法但业务含义错误的字段
  • 成本更高，切换后迅速耗尽预算
  • 延迟更低但核心任务成功率明显下降
  • 返回一段流畅答案，却没有完成 Agent 原本应执行的动作

更危险的是静默 fallback。用户和下游系统仍以为自己拿到“完整 Agent”结果，实际上系统已经退化到过期缓存、规则模板或能力明显不同的小模型。请求成功率看起来恢复，错误业务结果却悄悄增加。

因此，AI 韧性设计不能只做“模型报错就换供应商”。它需要同时回答：

这篇文章以“客服与履约 Agent”为贯穿场景，建立从完整 Agent 到明确不可用的能力阶梯，并给出熔断、隔舱、超时预算、兼容契约、恢复探测、故障注入和确定性兜底的完整实现方法。

文中的阈值和量化结果用于说明验收口径，不是跨业务通用配置。供应商错误语义以 2026-07-26 可访问的官方文档为准，接入时仍应按实际 API、SDK 版本和合同重新核对。

一、先给结论：降级的目标是保留可信能力，不是保住 HTTP 200

一套可用的 AI 降级系统至少要遵守八条原则。

  1. 先定义功能阶梯，再写 fallback。 每一级明确保留、删除和禁止的能力。
  2. 故障信号不只来自异常码。 质量、延迟、配额、成本、安全和供应商故障要分别处理。
  3. 熔断器保护依赖和本系统资源。 它不能证明备用结果语义正确。
  4. 每次尝试共享一个端到端预算。 备用路径不能在用户截止时间之后才返回“成功”。
  5. fallback 必须通过质量和契约门槛。 Schema 合法只是最低条件，权限、语义和业务不变量也要验证。
  6. 静默降级有明确边界。 只要能力、数据新鲜度或承诺发生实质变化，用户和下游就应收到机器可读与可理解的状态。
  7. 恢复比切出更难。 Half-Open 探测、冷启动预热、滞回、灰度回切和自动回滚缺一不可。
  8. 明确不可用也是正确结果。 当剩余路径无法满足最低质量或安全要求时，停止比编造一个看似正常的答案更可靠。

Microsoft 的 Circuit Breaker Pattern 将熔断器描述为 Closed、Open、Half-Open 状态机：持续故障达到阈值后快速失败，等待恢复窗口，再允许有限探测。它解决的是“是否继续调用一个可能失败的依赖”，不是“应该返回什么业务答案”。

AWS 关于超时、重试、退避与抖动的官方资料强调：超时或失败不代表副作用没有发生，重试可能放大已经过载的依赖；有副作用的接口需要可靠幂等语义。把这些原则放到 Agent 工具链中，意味着模型调用、检索调用和业务写操作不能共享一条粗糙的“失败就重试”逻辑。

二、贯穿场景：客服与履约 Agent 到底承诺了什么

假设一个 Agent 对用户承诺：

  • 读取当前订单、物流和退款政策
  • 理解用户问题
  • 必要时查询知识库
  • 计算允许的退款或补偿方案
  • 在权限范围内调用业务工具
  • 给出带依据的结果
  • 高风险动作进入人工审批

它依赖：

一次供应商故障不一定要求整套功能下线。例如主模型不可用时，已识别的“查询物流”意图仍可走确定性工作流；但“根据多份争议证据决定高额赔付”不能降级成关键词规则后自动执行。

所以第一步不是给供应商排优先级，而是给业务能力写最低契约。

1. 任务最低契约

这些值必须来自本业务评测和风险容忍度。它们的作用是明确：某个候选路径即使技术可用，只要不能满足任务最低契约，就不能作为该任务的自动 fallback。

2. 不同请求可以有不同最低阶梯

请求 最低可接受能力 不可接受降级
查询已知订单物流 确定性 API + 模板 使用过期且无时间标记的缓存
总结公开帮助文档 检索 + 带引用模板 无来源的自由生成
生成客服回复草稿 小模型 + 人工发送 自动外发未经复核的草稿
高额退款判断 受限工作流 + 人工审批 关键词规则自动退款
修改收货地址 当前状态 API + 硬规则 用缓存判断是否已出库
安全事件解释 受控证据 + 专门流程 换供应商绕过安全阻断

降级策略必须与请求能力契约一起计算，而不是全站共享 fallback_model=...。

三、六类信号：不要只在模型抛异常时降级

1. 质量信号

质量故障往往返回 200：

  • 结构化字段合法但含义错误
  • 引用不存在或不支持结论
  • 工具选择率、任务完成率突然下降
  • 输出语言、格式或品牌约束持续偏离
  • 线上纠正率、申诉率和人工接管率升高
  • Judge 与确定性业务事实发生分歧

质量信号通常比基础设施信号慢。可以分层处理：

不能等待月度真值才停止明显错误，也不能让不稳定 Judge 独自触发全局熔断。同步硬事实优先，统计信号需要样本量、时间窗和迟滞。

2. 延迟信号

延迟问题不仅是单次超时：

  • 首 Token 时间持续抬升
  • 完整响应时间超过剩余预算
  • 队列等待占据大部分端到端时延
  • 检索、工具或 Judge 的尾延迟扩大
  • 流式连接中途停顿
  • 超时后后台任务仍持续消耗资源

应分别记录排队、连接、首字节、首 Token、生成和后处理时间。只看模型 API 总耗时，无法判断换模型是否真的有用。

3. 配额信号

配额包括：

  • 每分钟请求和 Token 限额
  • 并发连接与 Batch 容量
  • 项目、区域、模型部署和租户级额度
  • 供应商的动态加速限制
  • 自己系统的线程、队列和连接池上限

同样是 HTTP 429，语义可能不同。OpenAI 官方错误文档区分请求速率过高与账户配额耗尽；Google Vertex AI 文档说明 429 可能来自配额或共享容量；Anthropic 文档将 429 用于速率限制，并另有 529 表示暂时过载。路由器必须解析供应商的结构化错误和响应头，不能把所有 429 都重试两次后切换。

4. 成本信号

成本故障可能来自：

  • Prompt 异常膨胀
  • Agent 循环和工具重试
  • 主模型切换到更昂贵备用模型
  • 缓存命中率下降
  • 长上下文或高推理配置被误用
  • 供应商价格和计费单位变化

成本策略不能在响应生成一半时粗暴截断并把残片当结果。更合适的是在路由前计算预算，在每一步消耗后更新剩余预算，并为停止状态提供明确说明。

5. 安全信号

安全信号包括：

  • Prompt Injection 或越权意图
  • 敏感数据即将外发
  • 内容安全策略命中
  • 工具参数超出允许范围
  • 模型输出无法通过安全后置校验
  • 安全服务本身不可用

安全失败通常不应该触发“换一家模型再试”。如果系统因为主模型拒绝危险请求就切备用供应商，fallback 变成了安全绕过。安全信号应进入统一策略，决定拒绝、收紧功能、转人工或明确不可用。

6. 供应商与依赖故障

包括连接错误、5xx、过载、区域故障、模型撤下、SDK 不兼容和响应协议变化。即使官方文档把某类 5xx 标为可重试，也要受当前端到端预算、幂等性和本地熔断状态约束。

供应商状态页只能作为辅助证据。真实故障可能只影响某个区域、模型、租户或请求形态；状态页也可能晚于用户侧异常。

四、先区分六个经常混用的机制

机制 解决的问题 不解决的问题
Retry 短暂、随机故障可能再次成功 持续故障、语义不兼容、非幂等副作用
Failover 同等能力实例或区域故障切换 备用能力是否真的等价
Fallback 用另一种结果或路径完成目标 结果是否满足原始质量承诺
Degradation 明确减少功能以保留核心能力 隐藏能力缺失
Circuit Breaker 暂停调用持续失败的依赖 选择正确业务结果
Load Shedding 在过载时拒绝低优先级工作 让被拒绝工作自动变正确

这些机制需要组合，但触发条件和指标应分开。一次请求可能先在主模型做一次预算内重试，随后熔断器打开，路由器降到受限工作流；低优先级的批量摘要则直接负载丢弃，不与在线客服争抢资源。

五、建立六级功能阶梯

下面这张图把候选能力从完整 Agent 排到明确不可用。

L0：完整 Agent

保留：

  • 多步规划
  • 多模型或多 Agent 协作
  • 检索、工具和结果验证
  • 允许范围内的副作用
  • 完整引用与个性化

入口条件是所有关键依赖、预算和安全控制健康。这里的“完整”也不表示无约束，仍要经过权限、审批和质量门禁。

L1：受限 Workflow

把开放式规划收敛成确定步骤：

禁用动态工具发现、自由循环、外部写操作和未经验证的多跳推理。适合模型部分可用但 Agent 编排或工具可靠性下降的情况。

L2：单模型或小模型

保留分类、抽取、改写和简单问答，删除复杂规划与高风险动作。切换前必须验证：

  • 上下文长度与多模态能力
  • 结构化输出和工具协议
  • 目标语言与领域质量
  • 安全行为和拒绝语义
  • 成本与延迟上限

“更小”不等于“更差”，但也不天然等价。只有在目标切片达到最低契约时才可使用。

L3：缓存或检索结果

可以返回：

  • 经过权限过滤的最近稳定答案
  • 当前仍有效的政策片段
  • 只读知识检索和引用
  • 已完成异步任务的持久结果

必须展示数据时间和能力限制。涉及订单状态、价格、库存、权限、医疗和安全事实时，过期缓存往往不可接受。

L4：确定性规则

适合边界清晰的任务：

  • 根据订单状态映射固定说明
  • 计算明确公式
  • 校验格式和权限
  • 返回静态帮助入口
  • 创建不带 AI 判断的人工工单

确定性规则不是“万能兜底”。它只覆盖预先定义的输入域，无法处理的请求要明确拒绝或升级，不能用默认分支猜测。

L5：人工或明确不可用

当自动路径都不满足最低契约时：

  • 创建带上下文的人工工单
  • 告知用户当前无法可靠完成
  • 提供预计恢复方式或替代入口
  • 保存未执行动作和已有证据

不能承诺一定有人立刻处理，除非人工队列有真实容量和 SLO。人工系统不可用时，应返回明确不可用，而不是继续降低安全要求。

七、质量门槛：备用路径成功返回以后还要过什么检查

1. Schema 门槛

  • JSON 可解析
  • 版本受支持
  • 必填字段存在
  • 类型、枚举、长度和数值范围正确
  • 未知字段按明确策略处理

2. 语义门槛

  • 状态码与自然语言结论一致
  • 金额、货币和单位一致
  • 引用真正支持对应断言
  • partial 不被写成 completed
  • 不把“未知”默认成 false、0 或空列表
  • 备用模型没有删掉关键否定词

  • 当前用户只能访问自己的订单
  • 已退款订单不能再次生成可执行退款
  • 已出库地址不能由低权限路径修改
  • 高额动作仍需要审批
  • 降级不能扩大工具和数据权限

4. 安全门槛

  • 输入与输出安全策略仍生效
  • 敏感字段脱敏一致
  • 供应商切换不改变数据驻留和发送范围
  • 安全服务不可用时按风险失败关闭
  • 拒绝原因不会泄露策略细节或秘密

5. 任务质量门槛

同步可做轻量验证，离线和近实时继续观察：

  • 任务完成率
  • 引用支持率
  • 工具参数正确率
  • 用户纠正率
  • 人工接管率
  • 关键切片的选择性风险

如果低级路径无法同步证明正确，至少应将它限制为草稿或人工输入，不能直接产生高风险副作用。

八、静默 fallback 为什么危险

静默降级会造成三个层面的错误。

1. 用户基于错误能力假设行动

界面仍显示“智能订单助手”，用户以为系统读取了当前订单，实际回答来自昨天缓存。用户可能因此错过改址时限。

2. 下游把降级结果当完整数据

主模型输出 risk_reason 和 evidence_ids，备用模型适配器用空数组填充缺失字段。下游看到 Schema 合法，误以为“没有风险、没有证据”，而不是“该能力未执行”。

3. 监控把错误结果计为可用

HTTP 成功率恢复到 99.9%，但用户纠正率和错误退款率上升。若可用性 SLI 只看 2xx，错误预算不会被消耗，系统会长期留在有害降级状态。

4. 哪些变化可以不打扰用户

只有当候选路径在用户可观察契约上等价，才可以透明切换，例如：

  • 同模型同版本的健康区域切换
  • 无语义变化的实例级故障转移
  • 已验证等价的缓存命中
  • 不影响内容和承诺的内部重试

只要数据新鲜度、功能范围、质量保证、处理主体或后续动作发生变化，就应提供至少一种可见性：

  • 用户界面提示
  • API degradation_level
  • 响应头或事件字段
  • 管理后台状态
  • 审计与告警

提示不应只写“体验可能受影响”。更有用的是说明当前可完成什么、不能完成什么、数据截至何时，以及是否需要用户重新确认。

九、超时预算：每次尝试不能各拿一整份 SLO

假设端到端 SLO 是 4.5 秒：

这不是固定分配，而是预算模型。每一步开始前都读取绝对 deadline，计算剩余时间。主模型已经花了 4 秒后，备用模型不能再拿 4.5 秒。

1. 区分四类超时

  • 连接超时：建立连接最长多久
  • 首响应超时：多久必须看到首字节或首 Token
  • 空闲超时：流式事件之间允许停顿多久
  • 总截止时间：整个业务请求最晚何时完成

只设置 SDK 默认超时，可能无法覆盖排队、DNS、TLS、流式中断和后处理。

2. 给 fallback 留预算，但不要永久预留

主路径可以根据历史尾延迟和任务价值设置尝试上限。若 fallback 本身无法在剩余预算内达到最低质量，应该尽早返回异步受理或不可用，而不是发起注定迟到的调用。

3. 超时后停止后台浪费

取消信号要传播到：

  • 模型流
  • 检索与重排
  • 并行候选
  • Judge
  • 工具调用
  • 队列任务

如果供应商不支持真正取消，也要停止读取、限制并发并把仍在运行的请求计入资源和成本指标。

十、熔断器：按依赖、能力和错误类型分区

下面这张图展示熔断、隔舱和恢复回切的关系。

1. Closed

正常允许请求，使用滑动时间窗记录符合条件的失败。不要永久累加历史错误；偶发失败不应在低流量一周后才凑够阈值。

触发可以组合：

不同信号可使用不同熔断器。供应商连接故障打开“调用熔断”，质量回退打开“能力质量门”，安全事件则进入“安全停用”，避免所有原因都压成一个 OPEN。

2. Open

请求快速失败或进入预先验证的降级阶梯，不再占用主依赖资源。Open 状态需要记录：

  • 打开原因
  • 触发窗口和样本量
  • 首次与最近故障时间
  • 下次探测时间
  • 当前退化级别
  • 影响的模型、区域、租户和能力

Open 不是返回任意默认值的许可。Microsoft 文档提到某些场景可以返回有意义的默认值；对 AI 功能而言，“有意义”必须通过业务契约证明。

3. Half-Open

只允许有限探测，成功达到恢复条件才回 Closed；任何关键失败可以重新 Open。探测应：

  • 使用专门并发槽，防止用户流量洪峰
  • 覆盖代表性请求，而不只发一个“你好”
  • 同时验证质量、延迟、安全和 Schema
  • 预热连接、模型容器、Prompt 缓存与检索缓存
  • 保存探测版本和证据

单次健康检查成功不能证明复杂 Agent 已恢复。

4. 熔断键的粒度

过粗：一个模型在某区域失败，全球所有模型都被熔断。

过细：每个用户一个熔断器，永远达不到有效样本量，持续轰击故障依赖。

打开阈值和关闭阈值不要相同。例如错误率超过 30% 打开，连续五个探测窗口错误率低于 5%、质量门槛全部通过才允许灰度回切。还可设置最短停留时间，避免几分钟内反复切换。

十一、Bulkhead：熔断前先阻止一个故障吃光所有资源

Microsoft Bulkhead Pattern 的核心是把资源分池，使一个元素失败时其他元素还能工作。AI 调用可以按以下边界隔离：

  • 在线请求与离线批任务
  • 高优先级用户与普通流量
  • 不同供应商、区域和模型部署
  • 生成、Embedding、Judge 和安全检查
  • 不同租户或风险等级
  • 工具读操作与写操作
  • Half-Open 探测与用户请求

1. 可隔离的资源

  • 并发信号量
  • 线程或协程池
  • HTTP 连接池
  • 队列与消费者
  • Token、请求和成本预算
  • 缓存分区
  • 进程、容器或部署单元

只为每个供应商建独立熔断器，却共享同一个 500 连接池，慢供应商仍可能占满连接并拖垮健康路径。

2. 隔舱的代价

资源利用率会下降，配置和容量管理更复杂。分区太细会浪费容量，太粗又无法隔离。需要观察每个隔舱的队列、拒绝率、并发、等待时间和 SLO，而不是只看全局平均。

3. 不要让 fallback 争抢主路径最后的资源

故障时备用流量会突然增加。如果备用模型、缓存刷新和人工工单都使用同一线程池，fallback 本身会形成第二次雪崩。每一级要有容量上限和负载丢弃策略。

十二、Retry、Backoff、Jitter 和 Idempotency

1. 只重试可恢复错误

可考虑重试：

  • 短暂连接失败
  • 明确过载或临时不可用
  • 有 Retry-After 且预算允许的限流
  • 可证明没有副作用的读取超时

通常不应原样重试：

  • 认证与权限失败
  • 无效参数、上下文超长和 Schema 错误
  • 安全拒绝
  • 余额或长期配额耗尽
  • 业务不变量失败
  • 已知不兼容的模型能力

供应商 SDK 可能已经自动重试。自定义客户端、网关和业务层再次重试会乘法放大请求。必须盘点每一层的默认行为，尽量只在一个合适层重试。

2. 使用带上限的指数退避和抖动

固定间隔会让大量客户端同时再次冲击恢复中的服务。抖动用于打散相关重试，但仍需：

  • 最大尝试次数
  • 最大退避
  • 绝对截止时间
  • 本地重试预算或 Token Bucket
  • 熔断器打开后立即停止

3. 模型调用幂等不等于 Agent 任务幂等

重复生成文本可能只增加成本，但模型结果可能驱动工具。以下轨迹很危险：

4. 同一幂等键不能承载不同意图

如果参数改变，必须拒绝同键复用；如果只是网络重试，应保持同键。服务端需要把键、主体、参数摘要和结果原子关联，并定义保留窗口。

F12 缓存过期 回源或不可用 不隐藏 as_of 时间
F13 工具提交状态未知 查询幂等结果 不换键重试写操作
F14 人工队列满 明确延迟或不可用 不自动放宽审批策略
F15 主模型恢复但冷启动很慢 受控探测与预热 不直接全量回切

2. 组合故障比单点故障更接近真实事故

生产事故经常是组合：

因此至少测试：

  • 主模型慢 + 备用模型配额低
  • 检索失败 + 缓存过期
  • 熔断打开 + 配置中心不可用
  • Half-Open + 突发流量
  • 模型恢复 + Prompt 新版本同时发布
  • 供应商故障 + 人工队列容量下降
  • 超时 + 下游写操作提交状态未知

组合测试要观察首个故障如何被放大，而不是只检查最终有没有 fallback。

3. 负载测试要覆盖切换瞬间

稳态压测主模型和备用模型都通过，不代表切换安全。需要模拟：

  • 在峰值流量时打开熔断器
  • 一秒内把 80% 流量转到备用路径
  • 备用缓存同时大量未命中
  • 连接池和 DNS 刚开始建立
  • 预热 Prompt 与模型容器尚未准备
  • 人工升级事件瞬间增长

观察队列、连接、CPU、内存、Token 速率、配额、缓存击穿和下游数据库，不只看路由器自身耗时。

4. 契约测试要使用真实适配器录制样本

供应商模拟器适合稳定复现，但协议兼容还应使用脱敏的真实响应样本覆盖：

  • 正常完成
  • 内容过滤停止
  • 最大 Token 截断
  • 流式中途错误
  • 工具调用和并行工具调用
  • 未知错误类型
  • 新增响应字段
  • 用量缺失或延迟返回

解析器遇到未知枚举时应保留原值并安全失败，不能因为字符串匹配失败就当作普通完成。

十七、供应商错误语义要标准化，但不要抹平差异

内部可以定义：

每个适配器负责将官方错误、SDK 异常、响应头和错误体映射到内部类型，同时保存：

1. 为什么不能只按 HTTP 状态码

相同状态码可能有不同恢复动作；不同供应商也可能用不同状态码表达过载。错误映射需要版本化，并用官方样例和故障注入验证。

2. 为什么不能匹配错误消息文本

消息可能本地化、变化或包含动态内容。优先使用 SDK 类型、结构化 type/code 和状态码组合。未知错误保留原始请求 ID，进入保守路径。

3. 错误映射本身也会故障

若适配器把认证失败映射成临时故障，会不断重试无效凭据并触发告警噪声；若把过载映射成永久失败，会过早放弃可恢复请求。映射表变化应经过代码审查、契约测试和灰度。

4. 供应商自动重试必须进入 Trace

Anthropic 官方错误文档说明其 SDK 对部分瞬时故障默认进行有限次数指数退避重试；其他 SDK 也可能有自己的默认策略。无论使用哪家供应商，Trace 都应记录逻辑调用和每个物理 attempt，避免看到一次业务调用却实际发送多次请求。

十八、恢复探测：从 Open 回到 Closed 不能靠一个健康检查

1. 探测集覆盖真实能力

可以维护轻量但有代表性的探测：

  • 短文本结构化输出
  • 长上下文关键信息提取
  • 中文与英文
  • 工具 Schema 生成但不执行副作用
  • 安全拒绝样本
  • 引用与证据绑定
  • 流式完整性

每个探测使用固定输入和确定性断言，必要时辅以稳定评测器。不要把用户秘密或生产高风险动作放入健康探测。

2. 控制 Half-Open 并发

集群中每个实例各放一个探测，会瞬间形成探测风暴。可以使用租约、协调存储或集中控制面，确保每个熔断键只有有限探测者。即使采用本地熔断，也要用全局流量上限保护恢复中的供应商。

3. 冷启动要单独建模

恢复后第一次请求可能需要：

  • 建立连接和 TLS
  • 拉起模型容器
  • 加载适配器或 Tokenizer
  • 预热 Prompt 缓存
  • 重新填充检索和应用缓存
  • 建立限流器状态

冷启动慢不等于服务仍故障，也不能让真实用户承担全部预热。探测策略可区分冷启动预算与稳态预算，并设置最大预热成本。

4. 恢复条件包含质量，不只包含 2xx

至少要求：

  • 连接和协议成功
  • Schema 与工具契约通过
  • 核心探测质量门通过
  • 安全探测行为符合预期
  • 延迟回到恢复阈值以下
  • 连续多个窗口稳定

如果供应商恢复后模型修订已变化，需要按模型变更处理，不能因为 API 名称相同直接恢复全量。

十九、灰度回切：恢复路径需要自己的发布策略

1. 建议的回切阶段

比例只是示例。每级持续多久取决于流量、真值延迟和风险，不能只按固定五分钟推进。

2. 按故障域回切

如果事故只影响某区域或某模型，不必一次恢复所有租户。回切单元可以与熔断键、隔舱和发布单元对齐，使问题重新出现时影响受控。

3. 回切期间避免结果摇摆

同一会话或同一长任务在模型之间反复切换，可能造成语气、工具状态和事实不一致。需要明确粘性策略：

  • 无状态只读请求可以按次路由
  • 有状态会话绑定模型与 Prompt 修订
  • 长任务恢复时检查状态兼容
  • 高风险动作绑定原审批快照

粘性不能阻止安全回退。原路径被紧急停用时，应结束或迁移任务，并明确告知能力变化。

4. 回切失败要自动退回稳定层

每级配置：

  • 质量退化阈值
  • 延迟和错误率阈值
  • 安全硬门禁
  • 最小样本量
  • 自动回退目标
  • 决策证据和责任人

不要在事故压力下临时讨论“要不要回去”。

二十、可观测与审计字段

一次路由至少记录以下结构化信息：

1. Metric 维度要控制基数

provider、model_family、region、operation、level、reason_code 可以作为受控维度；request_id、完整错误消息和用户输入不应作为 Metric Label。高基数字段放 Trace 或受控日志。

2. 同时记录技术结果和业务结果

这样才能避免 2xx 掩盖质量失败。

3. 记录首错与终因

第一次异常可能是主模型超时，最终不可用可能是备用路径不支持当前语言。两者都要保留：

  • first_fault
  • terminal_cause
  • contributing_factors

否则复盘会把所有问题归咎于最后一个候选。

4. 内容日志仍遵循最小化

路由审计通常只需要内容摘要、契约版本、评测结果和 Artifact 引用。不要为了排查 fallback 把完整 Prompt、个人信息和模型输出无条件写入所有 Span。

二十一、SLO 和错误预算必须包含质量降级

传统可用性可以定义：

AI 功能的 good 至少应满足：

1. 按能力级别报告

  • 完整能力成功率
  • 受限能力成功率
  • 确定性兜底成功率
  • 人工受理率与队列 SLO
  • 明确不可用率
  • 静默降级违规率

一个请求降到 L4 并正确告诉用户，可以算“核心服务可用”，但不能算“完整 Agent 可用”。两条 SLO 要分开。

2. 质量错误也消耗预算

如果结果后来被证明确认错误、引用不支持或动作没有完成，应回填并消耗相应质量预算。真值延迟会让预算回算，因此看板要显示已确认和待确认比例。

3. 错误预算驱动变化速度

Google SRE 的错误预算策略示例把预算用于平衡可靠性与变更速度。放到 AI 路由上，可以约定：

  • 质量预算耗尽时暂停扩大自动范围
  • 单次事故消耗超过阈值时必须复盘
  • fallback 长时间处于低级能力时暂停非必要模型变更
  • 预算恢复前优先修复评测、隔舱和降级能力

错误预算不是允许伤害的额度。越权、数据泄漏和未审批财务写入仍是硬事件，不进入普通平均预算抵消。

二十二、路由配置与紧急开关也要按发布系统治理

模型、阈值、超时、候选顺序和熔断键通常由配置驱动。这样便于快速止损，也意味着一次错误配置可以绕过经过测试的代码，在几秒内改变全量流量。

1. 配置必须是不可变版本

每次路由决定保存完整版本，而不是只写“当前配置”：

配置中心的可变键可以指向版本，但历史版本内容不能被覆盖。事故回放必须知道某次请求实际读取了哪个版本。

2. 多项变更要原子生效

切换备用模型时，往往需要同时更新：

  • 候选模型修订
  • Prompt 与工具 Schema
  • 输出适配器
  • 质量阈值
  • 成本和 Token 上限
  • 探测集版本

如果节点先看到新模型、后看到旧适配器，会出现短暂但真实的协议错误。应发布一个包含全部引用的路由清单，节点只有在下载并验证所有依赖后才原子切换到新版本。

3. 配置读取失败不能任意猜默认值

节点启动或配置中心中断时，可以使用最近一次经过验证的本地稳定快照，但要满足：

  • 快照签名或摘要有效
  • 仍在允许有效期内
  • 紧急撤销列表可以独立送达
  • 当前软件版本兼容该配置
  • 使用旧快照被明确记录和告警

若没有可信快照，高风险能力应关闭。代码内的“默认主模型 + 无熔断”通常不是安全默认值。

4. 紧急开关按能力和故障域设计

只提供一个全站 AI 总开关会迫使值班人员在“全部关闭”和“继续冒险”之间选择。更实用的开关包括：

开关语义要正向、清晰，避免 disable_fallback=false 这类双重否定。高影响开关需要权限控制、强认证、原因、作用范围和审计。

5. 紧急覆盖必须过期

事故中临时把超时从两秒改成十秒，可能缓解错误率，却长期占满线程；临时提高备用配额，也可能形成持续成本风险。覆盖项应包含：

  • owner
  • reason
  • incident_id
  • scope
  • created_at
  • expires_at
  • rollback_target

过期后回到明确版本，不是继续沿用“直到有人想起来”。若仍需保留，应重新评估并创建新变更。

6. 控制面和数据面分离

配置中心、实验平台或管理后台故障不应阻塞每个在线请求。数据面使用本地已验证快照做判定；控制面负责发布新版本、收集状态和紧急撤销。

但分离会带来传播延迟。需要监控：

  • 期望配置版本
  • 每个实例观测版本
  • 落后实例数和最长落后时间
  • 校验失败原因
  • 紧急撤销传播完成率

发布完成条件不是“配置中心写入成功”，而是目标故障域内足够实例已经加载并报告新版本，未加载实例被摘流或保持受控旧路径。

7. 配置变更也要跑评测和灰度

候选顺序、质量阈值和 fallback 能力都可能改变业务结果。提交配置时至少执行：

  • Schema 与引用完整性检查
  • 禁止环路和不可达路径检查
  • 最低能力契约静态检查
  • 历史故障 Trace 重放
  • 代表性离线评测
  • 容量与最坏成本估算
  • 小故障域灰度和自动回滚

事故紧急变更可以缩短流程，但不能跳过硬安全校验和版本记录。事后要将临时操作转成经过测试的正式策略或彻底撤销。

路由系统本身也需要稳定降级：当实验服务不可用、指标延迟或控制面分区时，应停留在已知稳定状态，而不是根据不完整信号频繁切换。

二十三、五个完整失败案例与排查

案例一：HTTP 成功率恢复，错误物流答案上升

场景： 主模型持续 503，路由器切到通用小模型。小模型不调用订单 API，而是根据用户文本猜测物流状态。

现象： 2xx 从 82% 回到 99.8%，延迟下降；两小时后用户纠正率和人工投诉上升。

排查：

  1. 按 degradation_level 切分业务结果。
  2. 检查备用路径是否满足 CURRENT_ORDER 能力。
  3. 比较主备模型工具调用轨迹。
  4. 检查适配器是否用默认值填充 order_source。
  5. 对齐熔断打开、路由切换和投诉开始时间。

根因： 路由策略按技术可用排序，没有做能力匹配；监控只看 HTTP。

修复： 订单问题只允许 L1 确定性工作流或 L4 当前状态模板；没有实时订单数据时明确不可用；SLO 加入来源和新鲜度门槛。

回归： 注入模型成功但不调用工具、工具返回空、订单 API 过期和跨租户缓存，均不得输出确定物流结论。

案例二：Schema 兼容把“未知”变成“无风险”

场景： 主模型输出 risk_flags，备用模型不支持该字段。适配器为了通过 Schema 填充空数组。

现象： 下游自动发送结果，因为 risk_flags.length == 0；实际备用路径根本没有执行风险检测。

排查：

  1. 查看原始供应商响应和规范化结果。
  2. 检查字段默认值与迁移脚本。
  3. 比较 omitted_capabilities 是否存在。
  4. 复查消费者对空、未知和未执行的语义。

根因： 结构兼容覆盖了能力缺失，三态被压成二态。

修复： 使用 null + capability_status=NOT_RUN；消费者遇到未执行时停止自动外发；契约测试加入缺字段和未知枚举。

案例三：多层重试把轻微过载放大成全面故障

场景： SDK 默认重试两次，服务网关重试两次，Agent 节点再重试整个步骤两次。

现象： 单次用户请求最多触发 27 个物理调用；供应商错误率从 8% 迅速升到 70%，备用路径也被打满。

排查：

  1. 从一个 Trace 展开所有物理 attempt。
  2. 检查 SDK、代理、服务和 Agent 的重试配置。
  3. 比较原始请求速率与供应商实际请求速率。
  4. 查看退避是否有抖动、是否尊重 deadline。

根因： 每层都把重试当作局部优化，没有全链路预算。

修复： 只在客户端适配层保留一次受控重试；禁用其他默认重试；加入 Retry Token Bucket、熔断和统一 deadline；记录每个 attempt。

案例四：Half-Open 探测引发第二次故障

场景： 200 个路由实例在同一时间到达恢复窗口，各自允许十个探测请求。

现象： 供应商刚恢复就收到 2000 个突发调用，再次过载；熔断器在 Open 和 Half-Open 之间振荡。

排查：

  1. 检查状态迁移是否只在本地保存。
  2. 统计同一熔断键的并发探测量。
  3. 对齐恢复时间与突发流量。
  4. 检查是否有最短停留和关闭迟滞。

根因： Half-Open 没有全局探测预算，也没有灰度回切。

修复： 集中租约限制探测者；独立探测隔舱；连续多窗口成功后仅恢复 1% 流量；失败立即退回稳定路径。

案例五：缓存兜底造成跨租户数据泄漏

场景： 为提高降级命中率，缓存键只使用规范化问题文本“我的订单到哪了”。

现象： 供应商故障期间，一个用户看到另一个租户的订单摘要。

排查：

  1. 用响应中的订单 ID 反查缓存写入者。
  2. 检查缓存键是否包含租户、主体和权限摘要。
  3. 检查读取时是否重新授权。
  4. 查看同一缓存对象的访问日志和传播范围。

根因： 把语义缓存当作公共内容缓存，没有安全分区。

修复： 私有结果默认不做跨主体语义复用；键绑定租户和权限范围；读取时重新校验；清理所有派生缓存与索引；将泄漏样本加入故障演练。

二十四、降级演练：要验证切出、稳定运行和回切三段

演练一：供应商区域故障

注入： 对主模型某区域返回持续 503，其他区域正常。

期望： 只打开对应区域和模型熔断；低风险请求切到已验证同等区域；高风险有状态任务不跨不兼容区域恢复；其他模型不受影响。

观察： 熔断命中率、备用容量、数据驻留、端到端时延、质量切片和回切时间。

演练二：无异常码的质量退化

注入： 模型返回合法 JSON，但把 10% 的 order_status 从 SHIPPED 改成 DELIVERED。

期望： 同步业务事实校验阻断；质量门打开而供应商基础设施熔断保持独立；错误不交付用户。

演练三：配额耗尽

注入： 模拟账户配额耗尽与短时速率限制两种 429。

期望： 前者不做指数重试并触发容量告警；后者在 Retry-After 和 deadline 允许时有限退避；两者审计原因不同。

演练四：备用路径冷启动

注入： 主路径 Open，备用模型第一次调用需要八秒预热。

期望： 在线请求不无限等待；预热使用独立隔舱；可安全回答的请求走确定性层；预热完成后先灰度而非全量切换。

演练五：工具状态未知

注入： 支付工具完成提交后丢失响应。

期望： 路由器不能通过换模型重新生成一次写操作；使用原幂等键查询；状态未知时转对账或人工；最终只产生一个退款对象。

演练六：人工系统不可用

注入： 所有自动路径都不达质量底线，同时工单 API 超时。

期望： 返回明确不可用和可重试标识；不把危险请求放入无界本地内存队列；若使用可靠队列，记录接受语义、容量和过期时间。

演练七：恢复后模型语义变化

注入： 同一公开模型名恢复，但工具参数枚举行为变化。

期望： 合成探测和影子流量发现契约差异；保持 Open 或质量门阻断；固定修订或更新适配器后重新灰度。

演练结束条件不能只写“服务恢复”。要验证：

  • 错误流量已经停止
  • 所有积压任务有明确状态
  • 重复副作用完成对账
  • 熔断与路由配置回到预期版本
  • 备用容量释放但仍可再次启用
  • 用户可见状态恢复
  • 事件样本进入回归集

1. 结果分母要一致

对比前后版本时固定：

  • 业务和风险切片
  • 流量时间窗
  • 真值成熟度
  • 排除条件
  • 路由策略版本
  • 用户重试去重规则

否则故障期间大量用户重试会让请求级成功率和用户级成功率得出不同结论。

2. 报告不确定性

低频高风险事件样本少，应报告计数和区间，不能把 0/20 写成“零风险”。延迟真值未回填的请求单列，不默认成功。

3. 收益包含代价

分层降级增加：

  • 备用容量和隔舱成本
  • 合约与适配器维护
  • 评测和探测流量
  • 状态机与审计复杂度
  • 用户提示与客服培训

只有错误损失、恢复时间和业务连续性收益超过这些成本，方案才有价值。

二十六、边界：哪些场景宁可停，也不要自动 fallback

1. 备用路径改变法律或合规处理主体

跨供应商、跨区域或跨数据域可能改变数据处理和保留条件。未经预先批准不能在事故中临时切换。

2. 无法验证语义兼容

高风险工具、医疗建议、信贷决策、安全处置和法律结论若没有足够评测与领域审核，不应把通用小模型作为自动兜底。

3. 关键数据无法保证新鲜

订单状态、价格、库存、权限、账户余额和风险名单若过期会改变动作，缓存只可用于说明服务状态，不能驱动写操作。

4. 副作用状态未知

付款、退款、删除和外发在超时后无法确认时，先查询、对账或人工处理。切换模型重新规划会扩大重复风险。

5. 安全控制不可用

高风险场景不能通过关闭安全检查恢复“可用性”。可以收敛到只读、静态帮助或明确不可用。

6. 人工队列没有真实容量

“转人工”不是无限容量 fallback。队列满时要有优先级、接受上限、过期和用户承诺，不能悄悄丢工单。

二十七、从 0 到 1 的实施顺序

阶段一：先定义契约和阶梯

  1. 列出所有 AI 能力、依赖和副作用。
  2. 为每种请求定义最低能力、质量、安全和时限。
  3. 设计 L0 到 L5 的保留与删除能力。
  4. 给降级响应增加机器可读状态。
  5. 禁止没有验证的通用 fallback。

阶段二：收敛错误、预算和重试

  1. 标准化供应商错误并保留原始请求 ID。
  2. 盘点 SDK、代理和业务层重试。
  3. 建立绝对 deadline、退避、抖动和重试预算。
  4. 为业务副作用补幂等键和结果查询。
  5. 将逻辑调用与物理 attempt 全部写入 Trace。

阶段三：熔断与隔舱

  1. 按真实故障域设计熔断键。
  2. 分离基础设施、质量和安全门。
  3. 隔离供应商、任务、优先级和探测资源。
  4. 配置 Half-Open 并发、迟滞和最短停留。
  5. 压测故障切换瞬间与备用容量。

阶段四：恢复和持续验证

  1. 建立代表性合成探测和影子请求。
  2. 预热冷启动依赖。
  3. 按故障域做 1% 到全量的受控回切。
  4. 将质量降级纳入 SLO 和错误预算。
  5. 定期执行组合故障和恢复演练。

二十八、上线前检查清单

能力与契约

  • 每种请求都有最低能力、质量、安全、时限和数据新鲜度要求
  • L0 到 L5 明确保留、删除和禁止的能力
  • 备用模型经过目标任务和风险切片评测
  • 部分完成不会声明为完整完成
  • 不满足最低契约时能够明确不可用

信号与路由

  • 质量、延迟、配额、成本、安全和供应商信号分别建模
  • 不只依赖 HTTP 状态和供应商状态页
  • 路由策略按请求能力匹配候选
  • 安全拒绝不会触发换模型绕过
  • 成本和配额策略不会扩大高风险权限

超时与重试

  • 使用绝对端到端 deadline，而不是每级完整超时
  • 连接、首响应、空闲和总超时边界明确
  • SDK、代理、网关和业务层重试已盘点
  • 重试有上限、退避、抖动和本地预算
  • 超时后取消传播并统计后台残余消耗

幂等与副作用

  • 写操作使用稳定幂等键并绑定主体和参数摘要
  • 同键不同意图会被拒绝
  • 提交状态未知时先查询或对账
  • Agent 整体重试不会重复工具副作用
  • 后置条件验证进入业务结果

熔断与隔舱

  • 熔断键与真实供应商、区域、模型和能力故障域一致
  • Closed、Open、Half-Open 状态和事件可观测
  • 基础设施熔断、质量门和安全停用没有混成一个状态
  • 在线、批量、备用、探测和不同优先级资源隔离
  • 备用路径有容量上限和负载丢弃策略

数据与 Schema

  • 内部标准契约与供应商原始响应分离
  • 停止原因、工具参数、用量和错误映射版本化
  • 未执行能力使用未知或缺失状态，不伪装成空值
  • 缓存键包含租户、权限、版本和新鲜度
  • 跨模型语义差异经过契约与离线评测

可见性与审计

  • 实质降级向用户和 API 下游显式表达
  • 响应说明省略能力、数据时间和下一步
  • 每个候选 attempt、质量门和最终路由可以关联
  • 首错、终因和贡献因素分别记录
  • 内容日志遵循脱敏、权限和保留策略

恢复与演练

  • Half-Open 探测有全局并发控制和独立隔舱
  • 探测覆盖质量、安全、Schema、延迟和真实能力
  • 冷启动、缓存预热和连接预热有预算
  • 回切使用影子、灰度、迟滞和自动回退
  • 定期演练组合故障、备用过载、状态未知和人工不可用

指标与错误预算

  • 完整能力、核心能力、降级能力和不可用分别报告
  • SLI 同时包含时限、安全、质量和降级可见性
  • 延迟业务真值能够回填原始路由
  • 高风险安全事件不被普通错误预算抵消
  • 预算耗尽会触发暂停扩量和可靠性改进

二十九、小结

AI 功能降级不是在异常处理里多写几个 except，也不是维护一串模型名称。它是业务能力、分布式系统和质量工程共同组成的控制面。

完整链路应做到：

  1. 从质量、延迟、配额、成本、安全和供应商六类信号判断故障。
  2. 用请求最低契约选择完整 Agent、受限工作流、小模型、缓存检索、确定性规则或人工不可用。
  3. 让所有候选共享端到端 deadline、成本和重试预算。
  4. 用 Circuit Breaker 减少对持续故障依赖的无效调用，用 Bulkhead 限制故障扩散。
  5. 用幂等键和最终状态查询保护 Agent 工具副作用。
  6. 用内部标准契约、能力标记和语义评测控制模型差异。
  7. 对任何实质能力变化提供用户可见和机器可读的降级状态。
  8. 恢复时经过有限探测、冷启动预热、影子比较和灰度回切。
  9. 把质量错误、静默降级和错误业务结果纳入 SLO 与错误预算。
  10. 通过组合故障演练证明切出、稳定降级和恢复三段都可控。

最终需要证明的不是“主模型挂了还能返回内容”，而是：

无论依赖怎样失败，系统只会交付当前证据和能力真正支持的结果；能力不足时会明确收敛，而不会用一个流畅、成功但错误的 fallback 掩盖风险。
