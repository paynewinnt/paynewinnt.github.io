AI测试-55-AI工具调用怎么落实最小权限沙箱授权和副作用隔离

发表于 2026-06-05 分类于 AI测试 本文字数： 25k 阅读时长 ≈ 1:31

模型返回了一个符合 JSON Schema 的工具调用，应用也成功解析了函数名和参数，能不能直接执行？

不能。

Schema validation 只说明数据形状满足约定。它没有证明当前主体有权操作这个资源，没有证明模型提出的 tenant 与认证会话一致，没有证明用户批准的是最终这组参数，没有证明能力尚未过期、没有被重放，也没有证明执行器只能访问批准的文件和网络目标。即使工具返回 HTTP 200，也只可能说明目标接受了请求；它不自动证明业务已经提交，更不证明应用随后观察到的状态与提交一致。

工具调用把概率生成系统接到了可产生副作用的确定性系统上。安全边界不能依赖模型“记住不要越权”，也不能依赖一段系统 Prompt 充当访问控制策略。模型可以提出 intent；授权决策、能力签发、执行边界验证、目标提交和结果观察必须由模型外的可审计组件完成。

一、边界：本文测试授权与副作用协议，不实现通用安全内核

本文关注 AI 工具调用从意图到观察的应用层契约：

  • 主体、租户、资源、动作和条件如何形成授权请求；
  • 高风险动作怎样逐次审批；
  • 授权怎样绑定最终规范化参数摘要；
  • 短时能力怎样过期、单次消费和撤销；
  • 执行器怎样在启动前复验能力；
  • 沙箱怎样限制文件、进程、资源和网络出口；
  • 目标接受、业务提交和状态观察怎样分开；
  • 重试怎样通过幂等键避免重复提交；
  • 补偿为什么是新的受权动作，而不是自动回滚；
  • 策略、时钟、观察器和审计失败时怎样 fail closed。

本文不提供：操作系统逃逸、容器突破、真实 OAuth 凭据、云权限提升、供应链利用或远程攻击步骤。内存模拟器不能证明真实内核、容器运行时、服务网格、API 网关或账务系统安全。

NIST SP 800-207 将零信任重点放在资源保护，并明确不因网络位置或资产所有权隐式授予信任；认证与授权是离散功能。NIST SP 800-162 对 ABAC 的定义把主体、对象、操作和环境条件放进策略判断。本文借用这些原则构造测试架构，不宣称实现某个标准即可自动合规，也不把零信任简化成产品名。

二、先拆掉十个看似合理的结论

2.1 “工具在 allowlist 中，所以调用被授权”

反例：invoice.pay 是允许注册的工具，但当前用户只能读取发票；或者允许支付租户 Aurora 的 INV-C55-0042，模型却把资源改成 Boreal 的发票。工具名 allowlist 只能减少可调用接口，不能替代主体、资源、动作、参数和条件授权。

2.2 “参数通过 Schema，所以业务请求安全”

反例：amount_cents 是合法整数，但从已批准的 120000 改成 920000；beneficiary_id 是合法字符串，但换成另一个收款方；endpoint 是合法 URI，却不是批准的资源服务器。结构有效不等于语义授权。

2.3 “用户刚才说过可以，所以后续都算授权”

反例：用户批准了查看草稿，模型随后执行支付；批准了发票 A，参数最终指向发票 B；批准在 10 分钟内执行，能力一小时后仍被复用。授权应逐次绑定明确动作和最终参数，不能从模糊会话文本推导永久能力。

2.4 “Bearer token 有 scope，所以参数已绑定”

反例：token 的 scope 允许 invoice.pay，但 token 本身没有绑定具体发票、金额、收款方和请求体。RFC 8707 可以帮助限制资源 audience，RFC 9449 的 DPoP 可以把 token 约束到持有密钥的发送方和请求方法/URI；但 RFC 9449 明确指出 DPoP 本身不是访问控制机制，且不覆盖一般请求体完整性。应用仍需做细粒度策略和参数绑定。

2.5 “运行在沙箱里，所以越权调用也没关系”

反例：沙箱允许访问账本服务，当前主体却无权支付这张发票。沙箱限制执行器的技术能力；业务授权限制某个主体在某个条件下能做什么。两者互补，不能互换。

2.6 “执行器已经启动，所以工具执行成功”

反例：执行器启动后被网络出口策略拒绝，目标根本没收到请求；或者目标校验失败，没有接受；或者接受后事务回滚。executor_started 只是调用边界已经开始。

2.7 “目标返回 200，所以业务已经提交”

反例：200 表示异步任务已受理，最终业务仍可能失败；返回体来自代理缓存；目标响应在事务提交前生成；观察器随后读到旧状态。目标协议和业务 postcondition 必须分别定义。

2.8 “请求超时，所以可以原样重试”

反例：目标已提交支付，但响应在返回途中丢失；无幂等键的重试产生第二次支付。超时代表客户端不知道，不代表目标没做。先查询、对账或使用稳定幂等键，不能用异常类型猜提交状态。

2.9 “有补偿接口，所以副作用可逆”

反例：发送的邮件已被阅读，删除不能抹去认知；资金冲正产生新账务记录、费用和时间差；公开发布的内容已被缓存。补偿是新的业务动作，有独立权限、失败模式和后果，不是时间倒流。

2.10 “审计日志有记录，所以事后能还原”

反例：日志只有工具名，没有主体、资源、参数摘要、能力 ID 和各阶段状态；或者日志由模型自由生成；或者 committed 与 observed 被压成 success=true。可审计性来自结构化、不可混淆的事实，不是有一行文本。

三、贯穿威胁前提：模型、用户、工具与基础设施各能做什么

本文使用以下构造威胁模型：

  1. 模型可以提出任意已注册或未注册工具名、参数和值；其输出不可信。
  2. 用户可以提出合法或越权请求，也可能误解审批界面；认证会话主体是权威来源。
  3. 检索文档和工具结果可能包含不可信指令，但不能直接签发权限。
  4. 能力票据可能被复制、过期或重放；执行器必须在本地边界复验。
  5. 策略服务、时钟、目录、观察器和审计 sink 可能不可用；默认不能把 unavailable 当 allow。
  6. 目标服务可能在响应丢失前已经提交；重试层可能重复调用。
  7. 沙箱策略可能配置过宽，出口代理可能被错误改成 wildcard。
  8. 人工审批可能过期、由请求者本人完成，或只绑定展示文本而未绑定规范化参数。
  9. 本文攻击者不能突破 Python 进程，也不接触真实网络；所有故障由显式内存 flag 注入。

系统承诺：模型不拥有隐式执行权；未授权、过期、摘要不符、重放、策略未知或出口越界都在副作用前拒绝；高风险提交有独立审批；提交状态不明时冻结并对账；补偿重新授权。

四、贯穿构造场景：发票支付助手

构造应用 LedgerGarden 为 tenant-aurora 提供发票助手。对象完全虚构：

支持四个动作：

action 副作用级别 典型权限
invoice.read L0 读取 主体可读该资源即可
invoice.prepare L1 本地草稿 单任务临时能力，无外发
invoice.pay L3 高风险提交 双人审批、单次能力、幂等、读回
invoice.reverse L3 补偿动作 新审批、新能力、引用原回执

4.1 合法流程

buyer-a 请求支付 INV-C55-0042。应用把模型输出编译为只含声明值的 ToolIntent，另从认证层取得模型不可写的 AuthContext；两者不互相覆盖，声明冲突直接拒绝。规范化参数并计算摘要后，独立审批人 approver-c55 只看到最终资源、金额、收款方、用途和摘要；审批十分钟内有效。策略决策点确认可信主体、资源、动作、条件和审批后，签发一次性能力。执行器复验认证绑定、审批、摘要、时间、audience、单次状态和出口，再调用内存账本。目标接受并提交后，观察器独立读回 PAID。

4.2 不合法变体

  • 模型把金额改为 920000，但继续提交旧能力；
  • 模型把 endpoint 改为其他 .invalid 主机；
  • 能力过期后重放；
  • 请求者自己批准高风险动作；
  • 策略服务超时，适配器错误返回 allow；
  • 目标提交后回包丢失，重试层使用新幂等键；
  • 观察器返回旧状态，应用仍显示完成；
  • 用支付能力调用 reverse。

每个变体都必须在明确阶段失败，失败后 business_committed 不能被默认填 false 或 true。

五、状态机：把“执行成功”拆成七个事实

5.1 intent

模型或用户提出结构化动作。记录原始提议、解析版本、认证主体、会话 tenant、资源、动作、参数、purpose 和风险级别。存在 intent 不代表任何授权。

5.2 authorization

策略决策点基于权威身份和资源属性返回 allow、deny 或 indeterminate。indeterminate 包括策略不可用、属性缺失、时间不可信和审批无法验证。高风险系统把 indeterminate 当 deny，并保留原因。

5.3 capability issuance

只有 allow 才能签发能力。能力至少绑定：subject、tenant、resource、action、purpose、audience、参数摘要、not-before、expiry、唯一 ID、最大使用次数和审批 ID。它不是模型可编辑的 JSON，也不从 Prompt 中解析。

5.4 executor_started

执行器完成本地验证并准备进入受限运行环境时置 true。若摘要不符、过期、重放或出口不允许，必须保持 false。不能在函数入口第一行无条件置 true，否则指标无法判断授权逃逸。

5.5 target_accepted

目标验证协议、业务前置条件和幂等语义后接受请求。连接建立不等于接受；HTTP 状态也必须按目标合同解释。异步 202 可能只表示排队。

5.6 business_committed

目标的业务 postcondition 已成立，例如发票状态变为 PAID 且账本只增加一次。它需要回执、事务 ID 或查询证据，不由模型文本决定。

5.7 observed

应用通过独立读回、事件或账本对账确认状态。观察器失败或读到旧状态时是 unknown。committed=true, observed=false 是重要运营状态：副作用可能已发生，但用户界面不能声称已确认。

六、统一数据模型：意图、决策、能力、执行 Trace 分开

6.1 ToolIntent

这里的 claimed_subject 与 claimed_tenant 是模型提议，不是认证事实。策略入口还必须接收一份模型不可写的 AuthContext：

会话主体、工作负载身份、tenant、角色、认证强度和 epoch 都来自认证/IAM 层。模型声明只与它做冲突检测；声明一致也不产生权限，声明冲突则拒绝。策略不能把 ToolIntent.claimed_subject 复制成“可信 subject”，也不能用模型提供的 tenant 选择授权域。epoch 用于识别撤销或权限变更后的旧会话；高风险动作在 epoch 不可确认时 fail closed。只在授权时查一次仍然不够：执行器必须在消费 capability、写入 executor_started 和接触目标之前重新查询权威授权目录的当前 epoch 与撤销状态，目录已推进到 18 时，携带 epoch 17 的旧 AuthContext 即使尚未到期也必须拒绝。

6.2 AuthorizationDecision

decision 保存使用了哪些属性，不只保存 allow。后续调查需要知道策略是依据旧资源状态还是新状态。

6.3 Capability

能力中的 subject 与 tenant 来自 AuthContext，不来自 ToolIntent；能力还绑定工作负载身份、认证上下文摘要、epoch 和审批快照摘要。真实系统还需要完整性保护、签发者验证、密钥轮换和撤销机制。本文内存对象不是安全 token，只演示字段契约和消费逻辑。

6.4 ExecutionTrace

阶段字段不可由一个 success 反推。对提交后丢包，target_accepted 和 business_committed 可能是 unknown；Trace 应允许三值状态或单独 outcome，不能强行填 false。binding_verified、egress_allowed、approval_valid 和 duplicate_suppressed 都只是生产者结论。Evidence Gate 必须重新比较原始摘要与 endpoint，验证审批快照签名，并把 Trace 中的 commit ID、回执、资源版本、业务摘要和幂等键与目标权威签名记录逐项对账。Gate 的 attempt/event 分母来自执行前签名清单，不从收到的 Trace 反推，因此删除一条 Trace 不能让缺口消失。

七、授权元组：主体、资源、动作、条件缺一不可

NIST SP 800-162 的 ABAC 定义包括 subject、object、requested operation 和 environment conditions。应用实现可以使用 RBAC、ReBAC、ABAC 或组合，但评测数据必须能回答完整授权问题：

7.1 主体

区分最终用户、代理服务、执行器 workload identity 和目标服务。模型本身通常不是业务授权主体。服务代用户执行时，要同时保存 user delegation 与 service identity，不能只写“assistant”。

7.2 资源

资源使用稳定 ID 和权威 tenant，不能只靠自然语言名称。“最新发票”“这个文件”在授权前必须解析成唯一对象；解析不唯一则拒绝。

7.3 动作

read、prepare、submit、delete、reverse 是不同动作。一个宽泛 write scope 难以表达审批和副作用差异；至少在应用策略层进一步细分。

7.4 条件

包括资源状态、金额、时间窗、设备/工作负载身份、数据地域、目的、审批和风险信号。条件应来自权威属性源，并记录 freshness。缺失条件不默认满足。

7.5 purpose

相同主体对相同资源的读取，可能只在特定业务目的下允许。purpose 不能由模型自由填一个看似合理的字符串；它应来自已批准工作流或用户明确选择，并进入能力绑定。

八、参数与摘要绑定：审批的是最终语义，不是漂亮的展示文本

8.1 规范化对象

参数摘要必须基于明确规范化规则。字段顺序、数字表示、Unicode、默认值、空字段和时区都可能让“看起来一样”的对象摘要不同，或让“语义不同”的对象被错误合并。本文代码使用受限 JSON 类型、排序键和固定分隔符；真实跨语言系统可评估 RFC 8785 JSON Canonicalization Scheme 是否适用，但仍要定义业务默认值和字段语义。

8.2 摘要覆盖什么

至少覆盖 tenant、resource、action、purpose、参数和幂等键。只摘要 params 而不含 resource，旧审批可能被移到另一个对象；只摘要 UI 展示字段，隐藏参数仍可变化。

8.3 TOCTOU

授权后到执行前，资源状态或策略可能变化。短 TTL 降低窗口，但不能完全消除。高风险执行器应复验能力和关键资源前置条件；若发票已支付或金额变化，目标拒绝。

8.4 摘要不是授权

摘要保证“当前对象与批准对象一致”的一部分完整性语义，不回答主体是否有权，也不证明参数本身安全。必须先有策略决策，再用摘要绑定。

九、逐次能力：短时、窄范围、单次消费

9.1 为什么不用长期万能 token

长期 token 被 Prompt、日志或进程错误暴露时，影响范围大；一个能调用所有工具的 token 让执行器绕过业务边界。逐次能力把 blast radius 限制在一个主体、资源、动作和参数组合。

9.2 过期语义

验证 not_before <= executor_start < expires_at，并定义时钟来源与偏差。时钟不可用或回拨超过容忍范围时，高风险动作 fail closed。不能只在签发时检查 expiry。

9.3 单次消费

能力在进入副作用边界前原子消费。若消费后目标调用状态未知，不能复用同一能力；恢复流程可在对账后签发新能力，并保留同一业务幂等键。

9.4 撤销

资源关闭、用户离职、审批撤回和事故冻结都可能在 TTL 内发生。高风险系统需要短 TTL 加撤销/策略版本机制。只依赖 token 自包含且不查询状态，会扩大撤销延迟。

十、OAuth 与应用能力的边界

10.1 scope

RFC 6749 定义 OAuth 2.0 授权框架及 scope 机制。scope 是授权服务器与资源服务器约定的权限表达，不自动具备某个业务领域需要的对象、参数和审批语义。文章中的 capability 是应用层构造，不声称等同任何 RFC token。

10.2 resource audience

RFC 8707 定义 resource indicator，帮助客户端请求面向特定 protected resource 的 token。限制 audience 可以减少 token 在错误资源服务器使用，但仍要由资源服务器判断具体对象和动作。

10.3 sender constraint

RFC 9449 的 DPoP 用 proof-of-possession 将 token 约束到持有密钥的发送方，并绑定 HTTP method 与 URI 等信息。规范也明确：DPoP proof 本身不是认证或访问控制机制，且一般不保证请求 body 和全部 header 的完整性。参数摘要绑定仍是应用责任。

10.4 OAuth 安全 BCP

RFC 9700 在 2025 年更新并扩展 OAuth 2.0 安全最佳实践，包括 sender-constrained token 等建议。采用 BCP 能减少协议层风险，却不能替代业务最小权限、沙箱、副作用状态机和人工审批。

十一、执行器：第二个策略执行点

授权服务检查过，不代表执行器可以盲信调用请求。执行器至少验证：

  • capability issuer 与完整性；
  • audience 是否是当前执行器；
  • subject、tenant、resource、action、purpose 是否一致；
  • 规范化参数摘要是否一致；
  • not-before、expiry、撤销与使用次数；
  • approval ID 是否适用高风险动作；
  • sandbox profile 与 action 是否匹配；
  • endpoint、method、path、DNS/服务身份是否在允许集合；
  • idempotency key 是否符合业务作用域；
  • Trace 和审计 sink 是否可用。

任一关键字段无法验证时拒绝。执行器不接受模型提供任意 shell、URL、文件路径或环境变量；工具适配器把结构化业务参数映射到固定实现。

十二、沙箱与网络出口：限制技术能力，不代替业务授权

12.1 文件系统

L0 读取工具只挂载必要只读数据；L1 草稿使用任务专属临时目录、配额和生命周期；L2/L3 工具通常不需要通用文件系统。路径由应用生成，不把模型文本直接拼接成本地路径。

12.2 进程与系统调用

优先专用适配器，不提供通用 shell。需要执行受控二进制时固定镜像、入口点、参数 schema、资源限制和系统调用策略。本文不提供逃逸测试步骤；真实平台由专业安全测试验证。

12.3 网络出口

按 workload identity、目标服务、端口、协议、方法和用途限制。DNS allowlist 单独使用可能受解析变化影响；生产实现结合服务身份、TLS 验证、代理策略和审计。模型不能通过参数改写 host。

12.4 凭据

执行器只在调用时获得面向目标、短时、最小 scope 的凭据，不把长期 secret 放入 Prompt、环境转储或模型可见错误。凭据的 issuer、audience 与 rotation 由平台实现，本文代码没有凭据。

12.5 资源限制

CPU、内存、执行时间、并发、输出大小和网络字节都有上限。资源耗尽本身可能导致重试风暴和审计缺口，应进入故障注入。

十三、副作用隔离矩阵：风险越高，证据要求越强

13.1 L0 纯读取

仍需资源授权、字段最小化和租户隔离。读取没有业务写入，不代表没有隐私或数据泄漏后果。

13.2 L1 本地草稿

草稿不应自动外发。文件/对象绑定 owner、任务 ID 和 TTL；任务结束清理。网络默认关闭，避免“保存草稿”变成上传。

13.3 L2 可逆写入

例如创建未发布工单或修改可恢复配置。要求逐次能力、幂等键、版本前置条件和显式补偿。可逆只表示有设计过的补偿路径，不表示无成本。

13.4 L3 高风险提交

资金、删除、公开发布、权限授予和外部通信使用最窄执行器、明确人工审批、一次能力、短 TTL、业务唯一键、独立观察和事故冻结。审批绑定最终参数摘要。

十四、人工审批：确认的是哪一个动作

14.1 审批界面必须显示关键语义

展示主体、资源、动作、金额/范围、接收方、目的、不可逆后果和过期时间。摘要值可以用于机器绑定，但人不能只看一串 hash；界面展示的规范化对象必须与 hash 输入一致。

14.2 请求者与审批者分离

高风险流程要求审批者不是请求者，并由权威身份目录验证审批者身份、激活状态、角色、tenant、可批准 action、resource scope、金额上限和当前权限 epoch。任意非请求者字符串并不等于合格审批者。模型不能扮演审批者，普通会话中的“好的”也不自动构成审批记录。

14.3 审批必须是权威注册记录或可验证签名快照

执行链只接受审批服务按固定 Schema 签发的不可变快照，至少绑定审批 ID、请求者、请求者认证 epoch、审批者、审批者角色与 epoch、tenant、action、resource、金额、批准上限、最终参数摘要、签发时间、失效时间和审批权威 ID。策略与执行器都验证快照完整性和当前目录状态；只在 UI 或 Trace 中写 approval_valid=true 不构成证据。发布 Gate 还要直接消费完整签名快照，用预注册 intent、AuthContext 和 executor_started_at 独立调用审批验证器；两个相等但由调用者重算的摘要也不能替代有效签名。

示例用 Python 标准库 HMAC 表达“快照不可被调用者静默修改”的协议，但代码中的固定测试 key 不是生产密钥。生产实现应使用独立审批服务、受保护签名密钥或服务端注册记录，并保留撤销、轮换、重放防护和审计链路。

14.4 任何参数变化都使旧审批失效

包括默认值补全、endpoint 变化、资源重解析、金额、收款方、时间窗和幂等键。若变化仅是已定义的无语义格式差异，应由规范化规则在审批前消除。

策略通过后到执行器启动前，审批也可能过期、审批者角色可能撤销或 epoch 可能变化。因此执行器必须重新验证审批快照；L3 一旦 executor_started=true，Trace 就必须已有有效审批证据，不能等 business_committed=true 后才检查。

14.5 拒绝和超时同样要有证据

审批超时是 deny/expired，不是等待时执行。拒绝原因可以反馈给模型用于重新规划，但不能让模型自行改写成允许动作。

十五、幂等、重试和提交不确定窗口

RFC 9110 将请求方法的幂等性定义为多次相同请求的预期服务器效果与一次相同。业务工具不能仅凭使用 PUT 或 POST 推断端到端幂等；目标系统需要用业务键实现并记录。

15.1 幂等键作用域

键至少绑定 tenant、resource、action 和规范化参数摘要。相同键配不同参数必须拒绝，不能返回旧成功。键由工作流生成，不由模型随意更换。

15.2 提交后丢包

若目标提交后响应丢失，客户端看到 timeout。状态应是 UNKNOWN_COMMIT_STATE。恢复顺序：查询目标幂等记录或资源状态；若需要重试，保留同一业务幂等键并重新授权。不能直接生成新键。

15.3 重试预算

限制次数、退避和并发，防止故障放大。每次重试记录 parent request、capability 和同一幂等键。高风险动作默认不由通用 HTTP 库透明重试。

15.4 观察一致性

读回可能受缓存和复制延迟影响。定义权威观察源、最大等待和 pending 状态。观察不到不是提交失败；UI 显示“确认中”，后台对账升级。

十六、补偿：新的动作、新的授权、新的证据

invoice.reverse 不复用 invoice.pay 能力。它需要：

  • 原支付回执和业务键；
  • 当前账本状态；
  • reverse 权限与审批；
  • 新参数摘要和新 capability；
  • 补偿幂等键；
  • 手续费、时间和不可恢复后果说明；
  • 独立提交与观察 Trace。

补偿失败时不能把原动作标成未发生。报告分别写 original commit、compensation intent、compensation committed 和 final observed state。

十七、Fail closed：unknown 不能变 allow

以下条件对 L3 动作默认拒绝：

  • 策略服务不可用；
  • 主体、资源 tenant 或 purpose 缺失；
  • 参数无法规范化或摘要失败；
  • 时钟不可用、过期或偏差超限；
  • approval 无法验证、过期或摘要不符；
  • capability 状态存储不可用；
  • sandbox profile 或出口策略缺失；
  • 审计 Trace 无法写入；
  • 目标提交状态 unknown 时尝试新的非幂等调用。

fail closed 不等于吞掉错误。系统返回可区分 reason code，保留拒绝证据，允许人工接管。否则运营会通过反复点击绕过保护。

十八、指标与分母：阶段转换率不能混成一个 success rate

18.1 授权通过率

它描述工作流，不是越高越好。攻击或误请求增多会让通过率下降，这可能说明策略正常工作。

18.2 授权逃逸率

分母为执行前 manifest 中被策略拒绝或无法判定的有效测试 intent。目标是构造门禁中的 0，不用正常 allow 请求稀释，也不允许通过删除拒绝 Trace 缩小分母。

18.3 参数绑定违规率

若执行器在摘要校验前就置 started，这个指标会模糊；因此阶段时间点必须精确定义。

18.4 过期或重放启动率

挑战 run 由外部预注册 manifest 固定；Trace 缺失或 collector 不完整本身就是门禁失败，不能把挑战 run 从分母移除。

18.5 目标接受率

下降可能来自业务预置条件，而非授权错误。按 reason code 切片。

18.6 业务提交率

对于异步目标，只有达到业务 postcondition 才计 committed。

18.7 观察完整率

目标端签名提交清单提供独立分母；观察器失败、unknown commit 或整条 Trace 丢失都不能删除提交。unknown 另外按 aging 和对账状态报告。

18.8 重复副作用率

按业务键而不是 HTTP request ID 计算。两个不同 request ID 可能是同一副作用重试。

稳定业务键不包含 HTTP request ID、capability ID 或每次重试新生成的 idempotency key；否则双能力提交会被拆成两个“正常”分母。Gate 不用 duplicate_suppressed 决定是否排除记录，而是按目标权威签名的提交事实去重：只有业务摘要、幂等键、commit ID、回执和资源版本全部相同，且另一条已收集 Trace 指向同一签名记录，才是同一副作用的重复回显。布尔值为 true 但签名记录不同或没有既有匹配时，该提交仍进入分母并产生 duplicate-claim-without-authoritative-match。同一 business key 存在两个不同签名提交记录时，无论布尔值怎样填写都触发硬失败。

18.9 人工审批覆盖

审批存在但签名不可验证、目录身份不存在、角色或 tenant 不符、action/resource 越权、金额超限、审批者等于请求者、epoch 过旧、已过期或摘要不符，都不进入分子。覆盖率在 executor_started 阶段先检查一次，在 commit 阶段再报告一次；前者是安全门，后者是结果指标。

18.10 沙箱拒绝与出口覆盖

报告已批准目标覆盖、拒绝尝试数和策略 unknown。拒绝数不是越低越好；故障注入应产生预期拒绝。真正门禁是未批准出口到达 target 的次数。

二十、故障注入：必须在副作用前杀死不安全路径

20.1 skip_parameter_binding

签发能力后修改 memo 或金额。正常执行器会先因审批快照不再匹配而拒绝，即使错误跳过参数摘要比较，审批重验证仍应阻断。构造故障同时跳过参数绑定与执行器审批重验证后，目标可能提交；Evidence Gate 从原始 params_digest 与 capability_digest 复算 binding，并在 executor_started 阶段检查审批，仍会硬失败。

20.2 allow_expired_capability

把执行时间推进到 expiry 后。期望：不启动执行器、不消费目标。故障实现若启动，stale capability 硬门失败。

20.3 disable_single_use

重复提交同一 capability。期望：第二次在执行器边界拒绝；目标调用计数不增加。幂等是后续防线，不能替代 capability replay 防护。

20.4 wildcard_egress

执行适配器把目标改成未批准 .invalid endpoint，并把沙箱出口错误设成 wildcard。期望：权威 allowlist 对账仍让发布失败。模拟器不会发起真实网络请求。

20.5 policy_fail_open

让策略服务不可用，适配器错误生成 effect=ALLOW, policy_indeterminate=true。期望：issuer 同时要求明确 allow、有效审批和 policy_indeterminate=false，因此拒绝签发 capability，而不是把清理责任留给执行器。

20.6 lost_response_after_commit

内存账本先提交再抛出丢包异常。期望：客户端状态 unknown；使用同一幂等键、重新授权后恢复同一回执，账本 commit count 仍为 1。

20.7 stale_observer

目标已提交，观察器返回旧 OPEN。期望：business_committed=true、observed=false，Gate 阻断“已完成”呈现并触发对账。

20.8 fabricated_stage

构造 business_committed=true 但 target_accepted=false 的 Trace。期望：阶段一致性检查失败，证明审计消费者不会盲信 success flag。

20.9 identity_confusion

认证主体是 unknown-user，模型却声明 claimed_subject=buyer-a；或者认证 tenant 是 tenant-aurora，模型声明另一个 tenant。期望：策略只使用独立 AuthContext 做授权，并把声明冲突作为拒绝信号。不能从模型声明回填 AuthContext。

20.10 untrusted_approval

分别注入任意审批者字符串、无审批角色账号、跨 tenant 审批者、低金额权限审批者和修改过字段但保留旧签名的快照。期望：审批权威或策略在 capability 签发前拒绝。再把合法审批的失效时间推进到 executor start 之前，期望：执行器重新验证并保持 executor_started=false。

20.11 forged_evidence_boolean

构造 binding_verified=true，但原始参数摘要不相等；再构造 egress_authoritatively_allowed=true，但实际 endpoint 与批准 endpoint 不同。期望：Gate 不读取布尔值作为最终事实，而是复算原始字段并失败，同时报告生产者结论与原始证据冲突。

20.12 dual_capability_commit

为同一 tenant、resource、action 和 purpose 生成两个 request、两个 idempotency key 和两个 capability，让两个隔离目标都返回真实 commit。期望：单条 Trace 都可能看似正确，但 Gate 按稳定 business key 聚合后发现两个非去重提交，并报告 duplicate-business-commit 与 multiple-capabilities-committed-same-business。对照组使用新 capability、同一 idempotency key，目标返回同一 commit 且 duplicate_suppressed=true，不应误报为第二次副作用。

20.13 auth_epoch_advanced_before_executor

先完成授权和 capability 签发，再把权威授权目录中的 buyer-a epoch 从 17 推进到 18。期望：执行器重新查询目录后返回 auth-epoch-stale，不消费 capability、不写 executor_started，目标调用数为 0。仅复验旧 AuthContext.valid_at() 会漏掉这个撤销窗口。

20.14 forged_duplicate_claim

构造同一 business key 下两个真实签名提交，使其业务摘要相同，但幂等键、commit ID、回执和资源版本不同，再把第二条 Trace 的 duplicate_suppressed 改成 true。期望：Gate 仍把它计作第二次提交，同时报告去重声明没有权威匹配。对照组的两个 Trace 必须指向完全相同的签名目标记录才可折叠。

20.15 missing_preregistered_trace

执行前在外部证据注册表冻结两个 attempt 及其必需阶段事件，两个目标提交后只向 Gate 提交第一条 Trace。期望：签名 collector proof 的 attempt 集与 manifest 不一致，第二条目标提交也无法与已收集 Trace 对账；Gate 报告 missing attempt、collector coverage 缺口和 orphan target commit，观察完整率为 1/2，不能得到虚假的 100%。

20.16 forged_approval_at_gate

把审批快照签名改成伪值，再让 approval_valid=true 且 Trace 与 capability 中两个摘要都等于伪快照的新摘要。期望：摘要相等检查本身通过，但 Gate 使用预注册 intent/AuthContext 和执行时间重新验证审批签名，最终报告 approval-evidence-invalid 与 L3-start-without-valid-approval。

二十一、只用 Python 标准库的离线可执行示例

下面程序实现完整内存授权与执行协议。它没有网络客户端、shell、真实 secret 或文件操作。.invalid endpoint 只作为字符串进入 allowlist 比较；InMemoryLedger 是唯一目标。

21.1 代码如何落实阶段拆分

ToolExecutor.execute 只有在 AuthContext、权威授权目录当前 epoch/撤销状态、审批快照、能力字段、摘要、时间、重放和出口检查完成后才消费 capability 并设置 executor_started=true。目录查询不是签发时结果的副本；签发后推进 epoch 的回归测试证明旧 AuthContext 不能重放。L3 审批在同一边界重验，而不是等账本提交后补查。目标拒绝时 target_accepted=false；提交后回包丢失时下游状态为 None 并标记 UNKNOWN_COMMIT_STATE；权威读回成功后才设置 observed=true。

evaluate_traces 不信任单一 outcome，也不信任 binding_verified、egress_authoritatively_allowed、approval_valid 或 duplicate_suppressed 自报值。它先验证外部 AttemptManifest 和 CollectorProof 的签名及完整集合，再把每条 Trace 与预注册 intent、AuthContext、capability 和 required events 绑定；随后独立验证审批快照与目标签名提交记录，并检查阶段顺序。构造一个伪造的 confirmed Trace 会被阶段门杀死；删除 Trace 会留下 manifest 和目标对账缺口；同一 business key 的多个不同签名提交则由跨 Trace 聚合门阻断。

21.2 能力对象为什么不是生产 token

Capability 是不可变内存数据，绑定了可信 principal、tenant、workload identity、AuthContext 摘要和 epoch，而不是模型声明。程序没有 capability 签名、issuer key、token serialization 或真实 credential。它只演示必须绑定的字段与单次消费。生产系统要使用平台支持的身份和 token 机制，并验证完整性、issuer、audience、rotation 与撤销；不能复制这个 dataclass 冒充安全实现。

21.3 参数绑定故障为何能提交又被门禁拦住

测试先批准原始 intent，再只修改目标不关心的 memo。正常执行器会被审批重验证和参数绑定两道防线拦住。故障用例有意同时跳过两道执行前检查，账本才可能提交；Trace 中原始摘要仍不一致，且审批无效。Gate 不采信布尔标记，从摘要复算 binding，并在 executor_started 阶段检查审批，因此失败。这证明“业务结果看似正确”不能掩盖批准对象被篡改。

21.4 身份与审批反例证明了什么

认证主体为 unknown-user、模型声明为 buyer-a 时仍然拒绝；模型 tenant 与认证 tenant 冲突也拒绝。审批反例覆盖任意字符串、错误角色、跨 tenant、金额超限、签名篡改、执行前过期，以及把伪造快照的两个摘要同时改成相同值。最后一种反例说明 Gate 必须验证完整签名快照，不能把“两个摘要相等”误当成审批权威。ApprovalAuthority 的目录与 HMAC 只用于离线协议演示：固定测试 key 公开存在，不能部署到生产；它证明的是验证输入和 fail-closed 路径，而不是密码学系统已经安全。

21.5 wildcard 出口为何没有真实网络风险

endpoint_override 只是字符串。即使注入 wildcard_egress，执行器仍调用本地 InMemoryLedger.apply，没有任何网络库。Gate 使用权威 action→endpoint 映射复核，检测到 unapproved-target.invalid 后失败。这验证配置漂移门，不提供实际外发能力。

21.6 丢包与幂等怎样验证

第一次调用在内存账本提交后抛出 LostResponseAfterCommit，Trace 保持 unknown；第二次重新审批并签发新 capability，但保留同一个业务幂等键。账本返回原签名提交记录，payment_commits 仍为 1。duplicate_suppressed 只是便于观察的响应字段；Gate 是否折叠两条记录取决于二者能否与同一权威提交记录逐字段对上。这个测试同时证明：单次 capability 与业务幂等解决不同问题。

21.7 双能力与幂等回显怎样区分

Gate 先验证每个 TargetCommitRecord 的权威 ID、字段完整性和 HMAC，再将其与 Trace 的 business digest、idempotency key、commit ID、回执和资源版本逐项比较。相同签名记录天然只计一次，不需要信任布尔值；两个不同签名记录即使把 duplicate_suppressed 都写成 true，也仍是两个提交。新 capability 使用同一 idempotency key 并返回同一签名记录时，只是重复观察同一副作用，不误算第二次提交。

21.8 预注册证据为何不能由 Trace 反推

AttemptManifest 在执行前固定 attempt key、原始 intent、AuthContext、capability、审批 ID 和必需阶段事件；CollectorProof 在收集后签名实际拿到的 attempt/event 集合。Gate 同时要求 manifest、proof、Trace 和目标记录闭合。若只收到一个 Trace，不能现场用这个 Trace 重新生成更小分母；测试辅助函数的固定 HMAC 仅用于演示这个信任域，生产中注册者、collector、目标和 Gate 应使用独立服务身份与密钥。

21.9 补偿为何独立

支付 capability 的 action 是 invoice.pay，拿它调用 invoice.reverse 会在执行器字段比较时拒绝。合法 reverse 需要新的 intent、approval、decision、capability、idempotency key 和观察结果。最终状态 REVERSED 不会删除原 payment_commits=1 的历史事实。

21.10 这个 mock 不能证明什么

它不证明真实 OAuth、DPoP、服务网格、容器、内核、账本事务、时钟、分布式锁、IAM 目录、审批签名服务或审批 UI 安全。内存 registry 没有并发和持久化；HMAC 使用公开测试 key；摘要没有跨语言互操作验证；观察器没有复制延迟；.invalid endpoint 没有 TLS。它提供可执行协议契约和故障门禁，不是生产安全库。

23.6 止损与恢复

关闭 L3 透明重试；所有 commit unknown 转人工/对账队列；同一 workflow 使用稳定业务幂等键；registry 不可用时 fail closed；审批绑定 digest；UI 引入“确认中”。补偿由独立审批流程决定，不自动执行。

23.7 修复复验

复验 600 个构造 L3 case、200 个 timeout 位置变体、100 个 replay、100 个 stale observer 和全部历史回放。数字只描述构造测试集。

结果要求：每个业务键最多一次 commit；提交后丢包保持 unknown；新 capability + 同一幂等键恢复原回执；过期/重放目标调用数为 0；参数变化启动数为 0；观察器旧读不会显示完成。

23.8 发布决定

先只开放 L0/L1；L3 在内部门控 tenant 灰度，人工审批和对账值班在线后再扩。任何 duplicate commit、authorization escape、binding violation 或 unknown 积压超门槛都停止扩量。这里的阈值由构造项目 owner 批准，不是行业标准。

二十五、上线监控：看状态转换，也看拒绝是否失效

25.1 授权监控

按 action、tenant、policy version 和 reason 监控 grant/deny/indeterminate。突然 100% allow 可能是 fail-open，突然 100% deny 可能是属性源故障。

25.2 capability 监控

监控签发到使用延迟、过期、重放、撤销、audience mismatch 和 registry 可用性。长期未使用 capability 应过期，不延长为“方便重试”。

25.3 stage funnel

分别计数 intent、authorization granted、executor started、target accepted、committed 和 observed。任何逆序或 committed 无 observed 都告警。漏报某个 stage 进入 unknown，不补默认值。

25.4 幂等与对账

按业务键统计 commit count；按 idempotency key 检查参数摘要一致；对 unknown commit 设置 aging SLO。对账结果回写原 Trace，而不是生成无关联新记录。

25.5 沙箱与出口

监控 deny、policy version、workload identity 和实际目标。预期故障注入应产生 deny；deny 突然归零可能是策略未执行。

25.6 人工审批

监控自批、未知审批身份、角色/tenant/action/resource/金额 scope 拒绝、epoch 撤销、签名失败、过期、摘要 mismatch、审批后参数变化和高风险 executor start 无有效 approval。审批 UI、目录或签名验证版本变化触发回归。

25.7 并发双提交不能只靠 capability 单次消费

单次 capability 只能防止同一能力被再次使用，不能阻止两个并发工作流各自获得一张合法能力。假设两个浏览器标签都在发票为 OPEN 时完成审批，各自拿到不同 capability 和不同幂等键；若目标只检查权限，不检查资源版本，两次提交仍可能依次发生。

因此，高风险 intent 还应绑定授权时看到的资源版本或业务前置条件，例如 invoice_version=17、state=OPEN。目标提交使用 compare-and-set、唯一业务约束或等价事务机制：第一笔把版本推进到 18 后，第二笔必须因 version mismatch 拒绝。测试同时启动两个已授权 intent，不能只断言“有一个成功”，还要断言 commit count 恰好为 1、失败者停在 target rejected、两个 Trace 都没有被错误写成 authorization failure。

并发测试要覆盖 barrier 前后不同插入点：两次授权同时完成、第一次消费能力后暂停、第一次提交后响应未回、观察器旧读时第二次启动。这样才能区分 capability registry、目标事务和观察一致性各自承担的责任。

25.8 策略快照与执行时策略之间要有明确合同

AuthorizationDecision 保存 policy_version 和属性快照，但执行器究竟接受旧决策到 TTL 结束，还是要求当前策略版本完全一致，必须按风险写明。若管理员在能力有效期内撤销 buyer-a 的支付权限，单靠五分钟 expiry 仍留下窗口；若任何无关策略发布都使全部能力失效，又可能造成大面积不可用。

一种可测试做法是给撤销敏感维度维护 authorization epoch：主体停用、资源冻结、审批撤回或 L3 权限变化会推进相关 epoch；capability 绑定签发时 epoch，执行器在消费 capability 和写 executor_started 之前向权威目录重查。普通文案或无关资源策略变化不推进该 epoch。故障注入应在签发后推进 epoch，确认 capability 使用次数和目标调用数都为 0，并验证 reason 是 stale authorization，而不是模糊 timeout。

25.9 分布式时钟错误会同时破坏过期、审计和重放判断

签发者、执行器、目标和审计系统可能使用不同节点时钟。只写“TTL 五分钟”并不足够：要规定权威时间源、允许偏差、闰秒/回拨处理和时间不可用时的动作。高风险 capability 若发现本地时间早于最近可信时间，不能继续接受看似尚未过期的票据。

测试至少构造执行器快两分钟、慢两分钟、时钟回拨、签发时间在未来和审计事件乱序。允许的 clock skew 是项目配置，不是行业常数；它越宽，重放窗口越大。报告应同时保存 wall clock 与单调时钟用途：wall clock 用于跨系统证据，单调时钟适合本进程超时，两者不能互相替代。

25.10 审计证据要能证明阶段，又不能成为新的高权限通道

每个阶段事件包含 request、parent workflow、decision、capability、参数摘要、幂等键、资源版本、目标回执和观察来源。事件按稳定 ID 关联，避免把模型生成的自然语言当权威日志。写入失败对 L3 fail closed，但审计系统也不能接收完整 Prompt、长期 token 或不必要业务正文。

“日志不可变”不是只计算一串 hash。还要控制谁能追加、谁能查询、时间顺序怎样校验、保留多久、删除例外如何审批，以及采集器丢事件怎样被对账发现。attempt 与必需 event 清单应由执行前的外部注册表固定，collector 对实际集合出具完整性证明，目标端再提供独立签名 commit 清单。测试关闭某个 stage collector 或删除整条 Trace，期望 evidence completeness 下降并阻断发布；不能让缺失事件从 funnel 分母消失。

25.11 代理循环需要动作预算和重新授权边界

一个代理可能在目标拒绝后自动反思、改参数、换工具并再次尝试。如果执行预算只按对话轮数计算，十轮内仍可能产生多个 L2/L3 intent。工作流应按副作用级别设置动作预算、并发预算、累计金额/对象范围和最大重新规划次数。达到预算后进入人工接管，不让模型用换一种措辞绕过。

重新规划只继承上下文，不继承旧授权。资源、动作或任何摘要字段变化都创建新 intent；L3 重新展示并审批。测试让模型连续提出原请求、参数微调、替代 endpoint 和补偿动作，确认每个变化都有独立 decision，且旧 capability 的目标调用数保持不变。

25.12 证据保留要支持恢复，而不是只支持追责

提交 unknown 时，恢复器需要足够信息查询目标：业务幂等键、资源 ID、动作、参数摘要、目标 audience 和最近可信回执。若为了数据最小化把这些字段全部删掉，系统只能盲目重试；若保留完整请求和凭据，又扩大敏感面。设计应保留恢复所需的不可逆摘要和稳定标识，将原始敏感参数放在更窄、短期的受控存储。

恢复测试在进程重启后只加载持久化的最小证据，验证能查询到原 commit、关联原 workflow，并签发新 capability 完成观察或经批准补偿。若必须依赖内存对象才能恢复，生产发布门应失败。

二十六、这套方案不能证明什么

  1. 不能证明模型永远不会提出危险 intent；目标是危险 intent 无法越过确定性边界。
  2. 不能证明真实 sandbox 或容器没有逃逸漏洞；需要平台与安全验证。
  3. 不能证明 OAuth token、DPoP 或服务身份配置正确；本文只有字段模型。
  4. 不能证明 JSON 摘要在所有语言和数字实现中互操作；需独立规范化测试。
  5. 不能证明目标系统的事务、幂等和回执可靠；内存账本只是契约替身。
  6. 不能因 observed=true 就证明外部世界所有后果都已知，例如邮件被阅读或资金已清算。
  7. 不能把补偿成功写成原副作用从未发生。
  8. 不能替代真实数据保护、财务控制、变更管理或法律义务评估。
  9. 不能用总体 success rate 证明高风险 L3 安全。
  10. 不能把人工审批当作无错误 Oracle；审批界面、身份和疲劳仍需测试。

二十七、常见误区

27.1 Prompt 写“不要越权”

这是行为提示，不是策略执行点。

27.2 工具 schema 兼任权限

Schema 约束形状，不判断主体与资源关系。

27.3 给代理一个全能 service account

模型任意 intent 都继承过宽权限，违背最小权限。

27.4 只校验工具名

资源、动作、参数、用途、时间和 audience 没有绑定。

27.5 在签发时检查一次 expiry

执行时可能已过期，必须边界复验。

27.6 scope 当请求体签名

scope 不自动绑定金额和收款方；DPoP 也不普遍覆盖 body。

27.7 沙箱当业务授权

技术上可访问目标，不等于当前用户有权操作对象。

27.8 透明重试所有 POST

提交状态未知时可能重复副作用。

27.9 每次 retry 生成新幂等键

目标无法识别同一业务动作。

27.10 capability 可无限复用

扩大重放窗口，审批无法对应具体执行。

27.11 target accepted 等于 committed

异步受理、事务回滚和业务前置条件被忽略。

27.12 timeout 等于未执行

丢包可能发生在提交后。

27.13 observed 由模型总结

观察必须来自权威目标或独立证据。

27.14 自动补偿所有失败

补偿也可能越权、失败或产生新后果。

27.15 success boolean 覆盖所有阶段

无法区分拒绝、启动、接受、提交、观察和 unknown。

27.16 policy unavailable 默认 allow

基础设施故障变成授权逃逸。

二十八、从零到一的实施顺序

阶段一：资产与动作盘点

列出每个工具能访问的资源、动作和副作用级别；删除不需要的通用工具。

阶段二：结构化 intent

把模型输出解析为受限业务对象；独立传入模型不可写的 AuthContext；模型声明只做冲突检测，未知和冲突拒绝。

阶段三：确定性授权

实现可信 subject/tenant/role/auth-strength/epoch 与 resource/action/condition/purpose 策略和 deny reason；策略 unavailable fail closed。

阶段四：逐次 capability

绑定 AuthContext 摘要、workload identity、auth epoch、params digest、audience、TTL、使用次数和审批快照；执行器本地复验。

阶段五：专用执行器与沙箱

每个风险族使用固定适配器、最小文件/进程/网络能力和短时目标凭据。

阶段六：副作用协议

定义幂等键、target accepted、business committed、观察、unknown、对账和补偿。

阶段七：人工审批

高风险动作展示最终语义并绑定摘要；审批来自权威目录和可验证快照，校验身份、角色、tenant、action/resource、金额、有效期和职责分离。

阶段八：故障注入与灰度

杀死身份混淆、伪造审批、参数、过期、重放、出口、原始证据伪造、双 capability 提交、丢包、观察和 policy fail-open 门；从 L0/L1 到 L3 分级开放。

二十九、可执行检查清单

问题边界

  • 已列出模型、用户、文档、工具和基础设施威胁前提；
  • 已声明不依赖模型拒绝充当安全边界；
  • 已区分授权、沙箱、协议和业务控制；
  • 测试不包含真实越权、逃逸、凭据或生产副作用；
  • 构造数字和阈值没有冒充行业事实。

Intent 与身份

  • 主体来自认证上下文，不信任模型自报；
  • tenant 来自权威会话与资源目录；
  • AuthContext 独立包含 session/workload identity、角色、认证强度和 epoch；
  • 模型 subject/tenant 声明只用于冲突检测，不能构造 AuthContext；
  • 旧 auth epoch、过期上下文和强度不足在授权前拒绝；
  • capability 消费前从权威目录重查当前 epoch/撤销状态，旧 AuthContext 不可重放；
  • 资源解析为稳定唯一 ID；
  • action 使用业务语义，不只用宽泛 write；
  • purpose 来自批准工作流；
  • 未知字段、未知动作和冲突字段默认拒绝；
  • intent 原文与结构化结果均可审计。

授权

  • 策略至少覆盖 subject、resource、action、conditions；
  • 资源和主体 tenant 一致性被验证；
  • 关键属性有来源、版本和 freshness；
  • policy unavailable 返回 indeterminate 并 fail closed；
  • deny reason 可区分但不泄漏不必要资源信息；
  • 授权后资源关键状态在执行点复验。

参数与能力

  • 规范化规则覆盖字段顺序、数字、Unicode、默认值和时间；
  • digest 包含 tenant、resource、action、purpose、params 和幂等键；
  • capability 绑定 subject、audience、not-before、expiry；
  • capability 绑定 trusted tenant、workload identity、AuthContext 摘要和 auth epoch；
  • capability 默认 max_uses=1；
  • 执行器原子消费并支持撤销；
  • 摘要不符、过期、重放、错误 audience 都在 started 前拒绝；
  • capability 不是模型可编辑对象。

人工审批

  • L3 展示最终资源、动作、金额/范围、接收方与后果；
  • UI 展示对象与 digest 输入一致；
  • 请求者不能自批；
  • 审批身份来自权威目录或可验证签名快照，不接受任意字符串；
  • 审批校验角色、tenant、action、resource、金额上限和权限 epoch；
  • 审批有 TTL、action、resource 和 params digest；
  • 策略决策与 executor start 都验证审批有效性；
  • Gate 使用完整签名审批快照独立验证，不信任 approval_valid 或相等摘要；
  • 任何语义参数变化使旧审批失效；
  • 审批超时或服务不可用不会执行。

沙箱与出口

  • 工具使用专用适配器，不接受通用 shell；
  • 文件挂载最小、只读优先、草稿任务隔离；
  • CPU、内存、时限、并发和输出有配额；
  • 网络按 workload、目标、方法和用途 allowlist；
  • 模型参数不能改 host/path/method；
  • 目标凭据短时、窄 scope、模型不可见；
  • sandbox policy 缺失时 L2/L3 fail closed；
  • 平台逃逸由独立安全测试覆盖。

副作用与状态

  • intent、authorization、executor_started 独立记录；
  • target_accepted、business_committed、observed 独立记录；
  • unknown 使用三值状态，不补 false；
  • target 合同定义接受与提交的证据；
  • 幂等键按业务动作稳定生成；
  • Trace 记录稳定 business/resource key、资源版本、capability ID 和目标 commit ID；
  • commit ID、回执、资源版本、业务摘要和幂等键与目标签名记录对账；
  • 同一键不同参数明确拒绝；
  • 高风险动作不透明自动重试；
  • 提交 unknown 进入查询/对账；
  • 观察器使用权威来源并处理旧读。

补偿

  • 补偿被建模为独立 action；
  • 补偿需要新 intent、approval、capability 和幂等键；
  • 原回执与当前状态进入前置条件；
  • 补偿失败不会改写原提交事实；
  • 不可恢复后果在审批界面说明。

指标与门禁

  • authorization escape 的分母是 deny/indeterminate intents；
  • binding violation 的分母是 executor_started；
  • target acceptance 与 commit 使用阶段条件分母；
  • observation completeness 不删除失败观察器；
  • duplicate commit 按业务键而非 request ID；
  • 同业务键的双 capability 真实提交是硬失败，幂等回显必须匹配同一签名目标记录；
  • duplicate_suppressed 只作诊断字段，不能从提交分母中自行删记录；
  • L3 approval coverage 验证独立、有效、摘要绑定；
  • Gate 从原始摘要和 endpoint 复算，不信任 binding/egress 布尔值；
  • Gate 使用执行前 attempt/event manifest、collector proof 和目标 commit 对账固定分母；
  • 低风险请求不稀释高风险硬门；
  • success total 不替代阶段 funnel。

故障注入

  • 参数变化在 started 前拒绝；
  • skip-binding 故障能杀死发布 Gate；
  • expired capability 目标调用数为 0；
  • allow-expired 故障被 stale 门杀死；
  • capability replay 在目标前拒绝；
  • wildcard egress 被权威 allowlist 对账发现；
  • policy indeterminate 即使误标 ALLOW，issuer 仍拒绝签发；
  • 模型身份/tenant 冒充不能改变可信 AuthContext；
  • 任意字符串、错误角色、跨 tenant、超金额和篡改审批都拒绝；
  • L3 审批在 executor start 前过期时目标调用数为 0；
  • capability 签发后推进 auth epoch 时，使用次数和目标调用数均为 0；
  • 伪造 binding/egress 布尔值被原始证据复算发现；
  • 伪造 duplicate_suppressed 不能隐藏第二个签名 commit；
  • 删除 Trace 不能缩小预注册 attempt/event 分母；
  • 两个相等伪审批摘要和 approval_valid=true 仍被签名验证拒绝；
  • 两个 capability 对同一 business key 的真实提交被聚合门阻断；
  • 提交后丢包保持 unknown；
  • 同幂等键恢复不会二次 commit；
  • stale observer 不会显示完成；
  • 伪造阶段顺序被 Gate 拒绝；
  • pay capability 不能执行 reverse。

发布与运营

  • BLOCK、LIMIT、CANARY、RELEASE 条件明确；
  • L0/L1/L2/L3 分级开放；
  • policy、capability registry、observer 和 audit 有健康门；
  • unknown commit 有 aging SLO 和人工接管；
  • 配置、模型、Prompt、工具和 endpoint 变化触发重评测；
  • 事故证据包含阶段、摘要、能力、回执与观察；
  • 剩余风险和不能证明的事项写入发布记录。

三十、总结

AI 工具调用的安全目标不是让模型更听话，而是让任何模型输出都只能在确定性、最小权限和可审计的协议里产生副作用。

一个完整请求同时包含模型提议和独立可信 AuthContext。主体、租户、角色、认证强度与 epoch 来自认证层；资源、动作、条件、purpose 和最终参数进入确定性授权。L3 审批来自权威身份目录和可验证快照。授权通过后签发短时、单次、窄 audience、身份与摘要绑定的 capability；执行器再次验证并进入专用沙箱；网络出口和目标凭据最小化；目标接受、业务提交和独立观察分别留证；提交状态不明时使用同一业务幂等键对账；补偿重新授权。

测试也必须保持这些边界。Schema 通过不等于授权，scope 不等于请求体绑定，沙箱不等于业务权限，HTTP 成功不等于提交，timeout 不等于未执行，补偿不等于回滚。每个故障注入都要验证副作用次数和阶段状态，而不只看返回码。

最终可信的发布结论应能回答：认证层确认的主体和 workload identity 是谁，模型声明是否冲突；谁凭什么权威角色和额度批准了哪个资源上的哪个动作；批准是否绑定最终参数且在执行启动时仍有效；能力何时签发、何时消费；执行器实际访问了什么；同一 business key 有多少真实 target commit；应用依据什么观察确认；未知怎样冻结；重试与补偿为什么没有扩大副作用。回答不了这些问题，就还没有把工具调用变成可控的生产能力。
