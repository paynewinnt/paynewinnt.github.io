AI测试-56-模型数据Prompt插件和MCP的供应链风险怎么治理

发表于 2026-06-07 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:13

一个 AI 应用已经完成依赖扫描，结果是“0 个严重漏洞”，是否可以批准上线？

不能。扫描器看到的也许只是 Python 包和容器层，而真正决定行为的模型权重、Tokenizer、数据快照、Prompt 模板、路由规则、插件包、MCP Server、工具 Schema 和运行时配置可能完全不在扫描清单里。即使所有文件都被扫描过，“没有命中已知规则”也只是一条有限观测：它既不能证明工件来自批准的发布者，也不能证明扫描后部署的仍是同一份比特，更不能证明一份合法签名的工件没有恶意逻辑。

供应链治理真正要回答的是一组可以独立验证的问题：

本文把“模型供应链”扩展为“AI 应用工件供应链”。模型只是其中一个节点。数据和 Prompt 可以改变模型行为，工具 Schema 可以改变模型能做什么，插件与 MCP Server 可以把文本建议变成外部动作，容器和代码则决定这些工件怎样被加载、验证和调用。治理对象必须覆盖整个可执行闭包，而不是只给模型文件加一个哈希。

本文资料边界截至 2026-06-07（含）。文中的公司、工件、digest、阈值、扫描结果、事件时间线和发布结论全部是构造示例，用于说明可复现方法，不代表任何真实供应商或系统。示例中的 HMAC 只用于标准库离线测试，它不是生产公钥签名方案；示例中的哈希链也不是生产级透明日志或 Merkle inclusion proof。

一、先划边界：本文治理可交付工件，不承诺“绝对可信”

供应链控制的目标不是给制品贴上“安全”标签，而是降低替换、伪造、来源不明、过程偏离、依赖失察和撤回不及时的风险，并留下足以作决定和响应事故的证据。以下边界必须在评测方案第一页写清楚：

  • 身份边界：本文用内容 digest 标识不可变工件。名称、标签、下载 URL、模型别名和容器 tag 都只是可变定位符，不能独立充当身份。
  • 来源边界：签名和 attestation 只有在信任根、签名者身份、声明语义、验证策略和吊销状态都明确时才有意义。“有签名”不是结论。
  • 完整性边界：digest 匹配说明验证时的字节与预期字节相同，不说明这些字节无漏洞、无偏见、无后门或适合当前用途。
  • 过程边界：provenance 说明某个 builder 声称怎样产生工件；其可信度受 builder 的隔离、身份、记录完整性与验证策略约束。
  • 清单边界：SBOM 或 AI BOM 是已声明组成的机器可读视图。清单完整度未知时，不能把“清单中没有风险项”外推到“发布集中没有风险项”。
  • 行为边界：静态扫描只能覆盖它知道的格式、规则和漏洞情报。Prompt 注入、工具越权、后门触发、模型行为漂移仍需要独立行为测试。
  • 运行边界：构建仓库中的 digest 通过不代表线上实例实际加载了该 digest。必须有 served digest 或等价的运行时事实。
  • 组织边界：职责分离、审批、例外到期和应急撤回是系统的一部分，不能用一个 CI job 的绿色状态代替。

本文不重复常规漏洞扫描器选型，也不把软件成分分析等同于完整治理。本文关心的是怎样建立对象身份、谱系、证据门禁和运行时闭环，以及怎样测试这些控制在被绕过、证据缺失和撤回事件中确实会失败。

二、六个常见反例：先拆掉错误的安全推理

2.1 “SHA-256 一样，所以来源可信”

反例：攻击者先发布恶意模型，再把其 SHA-256 写进一个未经保护的清单。下载方重新计算得到相同值，只证明它拿到的正是清单描述的恶意字节。digest 解决“是否为同一内容”，不回答“谁批准了这个内容”和“它是否适合生产”。

正确做法是把 digest 作为签名或 attestation 的 subject，并验证签名者与 builder 是否符合当前策略。即使这样，也只证明受信主体对该声明负责，不自动证明声明中的工件安全。

2.2 “签名验证成功，所以工件没有被攻击”

反例：受信发布账号被盗，攻击者使用合法凭据签署了恶意插件；或者签名者本来就没有权限为生产 MCP Server 签名；又或者验证器只检查密码学有效性，没有检查证书身份、issuer、subject、有效期和策略允许的 signer-builder 组合。

签名验证必须回答“哪一个密钥或身份对哪一段规范化消息作了认可”。它不证明签名前发生了代码审查，不证明 signer 没有失陷，也不证明工件行为正确。密钥撤销和身份事件必须进入持续决策，而不是只在首次下载时验证一次。

2.3 “透明日志里有记录，所以发布可信”

反例：一个未经授权的签名事件被公开写入日志。日志的价值是使事件可发现、可审计，并提供条目存在及日志一致性的密码学证据；它不会把未经授权的事件变成授权事件。监控方仍需发现异常身份、撤销信任并处置受影响发布。

透明日志也不证明工件经过安全测试。它记录“某声明在某时可见”，而不是替声明内容背书。

2.4 “SBOM 完整，所以所有 AI 工件都在里面”

反例：容器 SBOM 列出操作系统包和 Python wheel，却没有模型权重、Prompt、远程 MCP Server、运行时下载的数据索引和工具 Schema。SBOM 对其声明范围可能是完整的，但发布闭包仍不完整。

正确做法是先定义发布集的工件类型和关系，再选择 SPDX、CycloneDX 或内部扩展表达。格式能力不能替代采集能力，composition=complete 也必须说明对哪个对象、生命周期阶段和依赖边界完整。

2.5 “容器 digest 固定，所以运行行为固定”

反例：容器启动后按别名下载 model:stable，从远程 Prompt Hub 取 production 模板，再连接 DNS 指向的 MCP Server。容器自身没有变化，三个外部工件都可以变化。

运行时 manifest 必须固定所有会影响行为或能力的工件，远程服务至少要固定可验证的 server identity、部署版本、工具目录 digest 和授权策略。无法固定的对象要被明确标成动态依赖，并采用更严格的运行时验证与变更触发。

2.6 “扫描无告警，所以可以自动通过”

反例：扫描器不支持量化模型格式，把文件当作 opaque blob；插件中有合法但过宽的文件删除能力，没有任何已知 CVE；Prompt 把不可信工具输出置于系统指令之前；MCP Tool Annotation 自称只读，但服务实际执行写操作。扫描器可能诚实地返回零告警，覆盖率却接近零。

因此扫描结果至少有 PASS、FAIL、UNKNOWN 三种状态，还要报告适用范围、规则版本、数据库时间和被跳过对象。UNKNOWN 不能从分母删除，更不能被 UI 渲染成绿色。

三、贯穿构造场景：企业知识助手的六类工件

本文使用一个完全虚构的“Northlake 变更助手”贯穿设计。它回答内部变更问题，并通过 MCP 工具读取工单、生成变更草稿，但不能直接批准或执行变更。

发布合同规定：模型、数据、Prompt、代码、容器、MCP Server、Tool Schema 和插件策略八类工件缺一不可；所有 release 引用必须落到内容 digest；模型与容器必须有受信 builder 产生的 provenance；数据必须有来源、许可和过滤 attestation；MCP Server 与 Tool Schema 必须成对批准；任何签名者或 subject 被吊销时，受影响发布自动转为 DENY。

这个场景特意把 Tool Schema 当独立工件。因为 tools/list 中名称、描述、输入 Schema、输出 Schema和 annotations 的变化，可能改变模型的选择与调用参数。MCP 2025-06-18 规范明确把 Tool Annotation 描述为提示，并要求客户端把来自不可信 Server 的 annotation 视为不可信。即使协议消息合法，应用仍要对工具身份、参数约束、授权和副作用建立自己的策略。

四、分层架构：让“是什么、谁声明、谁批准、实际运行什么”分开

架构中有五条不能合并的数据链：

  1. 内容链：原始字节经过规范化或打包后得到 digest。它回答对象身份。
  2. 谱系链：materials、参数、builder、步骤与 products 构成有向图。它回答声明的生产过程。
  3. 证据链：签名、attestation、扫描报告、测试报告和日志 inclusion proof 分别带自己的 subject digest。
  4. 决策链：策略版本读取证据，产生带范围、期限和理由的 approval receipt。
  5. 运行链：实例启动和每次请求记录实际 served digest，证明批准对象与服务对象是否一致。

如果把五条链压成一个 trusted=true，事故时就无法区分：是工件字节变化、证明失效、策略升级、审批过期，还是线上实例没有加载批准版本。数据模型必须保留这些状态的独立性。

4.1 控制平面和数据平面

控制平面保存 manifest、BOM、attestation、策略、审批与吊销。数据平面加载模型、Prompt、插件和工具。两者通过不可变 release_id 与 digest 集合连接。运行时不能只上报 model_name=northlake-7b，而要上报实际模型 manifest digest、Prompt bundle digest、容器 digest、MCP Server deployment digest 和 Tool Schema digest。

控制平面出错时，系统应 fail closed 还是进入只读降级，取决于业务风险。例如读取公开知识可以在短时验证服务不可用时使用缓存的未过期 approval；执行工单操作则必须阻断。这个选择要写进能力合同，不能在异常处理代码里临时决定。

4.2 Registry 不等于信任根

Artifact Registry 负责存储和寻址，不应因为“位于公司仓库”就自动受信。仓库账号可能失陷，复制任务可能传错对象，保留策略可能删除证明。验证器必须从独立配置读取允许的 signer、issuer、builder、predicate type、策略版本和吊销源。

同理，BOM 生成器、扫描器和 attestation 生成器都是供应链中的工具，也要有版本身份。否则工具升级改变输出语义，历史结果无法解释。

五、统一数据模型：不要让一个 version 字段承载所有含义

5.1 ArtifactDescriptor

每个工件至少包含：

对目录型工件不能随意拼接文件名后求哈希。应定义稳定 manifest：路径使用统一编码和分隔符，记录每个文件的 digest、长度和 media type，按明确顺序序列化，再对 manifest 求 digest。否则操作系统遍历顺序、时间戳和压缩元数据会制造不必要差异。

Prompt bundle 不只是 .txt。它通常还包括变量 Schema、默认值、消息角色、工具注入位置、转义规则和模板引擎版本。只哈希正文会漏掉能改变语义的部分。

5.2 Attestation

Attestation 是“某个声明者针对某个 subject 作出的、带类型的声明”，不是通用真相对象：

扫描报告、测试报告、来源证明和构建 provenance 应使用不同 predicate type。一个 passed=true 无法说明通过了什么、采用什么分母、规则版本是什么、未知项如何处理。

5.3 ReleaseManifest

Release manifest 固定一次发布允许加载的完整集合：

manifest 自身也必须有 digest 和签名。审批对象应是 manifest digest，而不是一组容易在 UI 中被替换的显示名称。

5.4 ApprovalReceipt

审批收据至少记录：

证据更新后，旧审批不能静默继承。若只是漏洞库刷新且结果不变，也应生成新 evidence set 和新收据，保留两次决定关系。

5.5 RevocationEvent

撤回对象可以是 signer、builder、artifact digest、attestation digest、supplier 或 release。事件必须包括生效时间、原因、发布者、严重度和替代对象。删除仓库中的坏文件不是撤回；已经缓存或运行的实例仍可能继续服务。

5.6 RuntimeObservation

运行时观测需要区分“实例声明”和“独立核验”：

进程自报适合可观测性，但被攻陷进程可以撒谎；sidecar 或 admission controller 提供更独立的证据。不同测量源的可信边界应写入报告。

六、威胁模型：先说攻击者能改哪里，再谈控制

供应链测试至少覆盖以下能力，不要只写“恶意攻击者”：

能力 受影响入口 需要验证的控制
能上传同名工件，不能取得签名身份 Registry tag、模型别名 digest pinning、签名 subject 绑定
能控制开发者工作站 本地构建、Prompt 上传 受控 builder、服务端取源、职责分离
能修改训练数据源的一小部分 爬取源、标注队列 数据来源、写入者、异常与投毒测试
能取得合法发布身份 签名服务、CI OIDC 最小权限、builder-signer 配对、日志监控、快速撤回
能修改远程 MCP Server 服务部署、DNS、工具目录 server identity、TLS/授权、schema digest、served digest
能控制扫描器输出 报告上传或回调 报告签名、subject 绑定、多源核验、未知处理
只能读取公开制品和证明 Registry、透明日志 不应泄漏秘密；公开元数据最小化
内部审批者越权 approval API 双人规则、范围约束、不可变审计

威胁模型还要写明非目标。例如本文不试图用 digest 防止运行中内存篡改，不用 SBOM 检测所有模型后门，不用签名替代供应商尽调。非目标不是漏洞，而是提醒架构必须叠加其他控制。

七、digest、签名和透明日志：三种证据分别能证明什么

7.1 Digest

对字节串 x 使用密码学哈希：

验证者重新计算并与预期 d 比较，可以支持“当前字节与被标识字节一致”。它不能证明：

  • d 来自可信渠道；
  • 内容由某个主体创建；
  • 内容在创建前经过评审；
  • 内容无已知或未知漏洞；
  • 模型没有投毒、偏见或隐私泄露；
  • 当前运行实例实际加载了这份内容。

算法名必须与值绑定，不能只存裸十六进制。对大模型分片应先建立分片 manifest，防止只验证其中一片。

7.2 签名

签名验证在受信公钥、算法和消息规范化正确的前提下，支持“对应私钥对这段消息生成了有效签名”。生产策略还必须检查 signer identity、issuer、证书用途、时间、subject digest 和授权范围。

签名不能证明签名者没有被入侵，也不能证明声明真实。若 CI 把错误的模型 digest 放进 attestation，合法签名只是完整地保护了错误声明。因此证明生成要尽量由受控平台从实际产物读取 subject，减少调用者自由填写。

7.3 Transparency log

透明日志通常提供可追加、可验证的日志结构及 inclusion/consistency 证据。它支持审计某个签名事件曾被记录，并使异常签名更容易被监控者发现。它不能证明：

  • 记录的签名者有业务授权；
  • 声明内容正确；
  • 工件经过扫描或行为测试；
  • 监控者一定看见并及时响应；
  • 私有部署的日志没有因信任根配置错误而被替换。

Sigstore 的官方文档把短期证书、身份绑定和 Rekor 透明日志组合起来。采用这类方案时，验证策略仍要固定预期 issuer、identity 和日志信任根，不能只运行一个默认 verify 命令就把输出解释成安全结论。

八、Provenance：证明生产关系，不是复制构建日志

SLSA Build Provenance 使用 in-toto Statement 表达 subject，并在 predicate 中描述 buildDefinition 和 runDetails。关键字段包括 buildType、外部参数、已解析依赖、builder identity 与运行元数据。截至本文资料边界，当前 Approved Specification 是 2025-11-24 发布的 SLSA 1.2；它引入 Source Track，并与 1.1 向后兼容。Build Provenance 的 predicate URI 仍是 https://slsa.dev/provenance/v1，不能把浏览器地址中的规范小版本误写成 predicate type。

8.1 subject 必须绑定最终产物

最危险的实现错误之一是“签名正确，subject 错位”。例如构建 A 产生 digest aaa，上传步骤却把 tag 当前指向的 bbb 填进证明；或者证明针对未量化模型，部署的是量化后模型。门禁必须同时验证：

任何一边不匹配都应 DENY，而不是重新签一个未知对象。

8.2 materials 要覆盖真正影响产物的输入

模型构建的 materials 不只包括训练代码和数据，还可能包括基座模型、Tokenizer、词表、适配器、训练配置、随机种子、编译器、量化配置和后处理脚本。SLSA 对 resolved dependencies 的完整度有具体语义和级别边界，不能把 best effort 字段宣传成绝对完整。

Prompt 发布也可以建模成构建：materials 是模板源、变量 Schema、策略片段和模板引擎；product 是规范化 Prompt bundle。MCP Tool Schema 抓取则应记录 server release、协议版本、抓取器和授权上下文，避免把未经认证环境的 tools/list 当成生产真值。

8.3 builder identity 表示信任闭包

SLSA 文档强调 builder identity 表示受信构建平台的闭包，并要求消费者接受特定 signer-builder 组合。把同一个 builder.id 同时用于隔离托管 runner 和开发者自托管 runner，会混淆不同安全属性。不同模式应使用不同 identity 和策略。

8.4 in-toto 的布局与 Link 适合表达步骤约束

in-toto 1.0 通过由项目所有者签署的 layout 描述步骤、授权 functionary、materials 和 products 规则，functionary 生成 Link metadata。它可以验证步骤是否按布局留下了授权证据，但 target file 对框架仍是 opaque；“流程符合布局”不等于文件功能正确。

对 AI 流水线可把 curate-data → train → evaluate → package → approve 建成步骤。评测步骤的 byproduct 应保存报告 digest，而不是只存退出码 0；客户端 inspection 还要核验报告 subject、数据集版本和硬门结果。

九、SBOM 与 AI BOM：格式选型之前先定义完整度

SPDX 3.0.1 的范围包括软件、构建信息、AI 模型、数据集、来源与完整性、漏洞和元素关系。CycloneDX 1.7 可以表达组件、服务、依赖、机器学习模型、配置、formulation 和声明。两种规范都能承载丰富信息，但组织是否采集、验证和维护这些信息是另一回事。

9.1 发布集需要哪些对象

一个最低 AI BOM 不应只列包名：

  • 模型基座、微调权重、适配器、量化产物和 Tokenizer；
  • 训练、评测、检索与运行数据快照；
  • Prompt bundle、策略、模板引擎与输出 Schema；
  • 应用源码提交、二进制、容器、基础镜像与系统包；
  • 插件包、配置、权限声明、远程服务和协议版本；
  • MCP Server、Tool Schema、resource/prompt 定义及授权配置；
  • 构建、扫描、评测、签名和 BOM 生成工具；
  • 关系边：trainedOn、derivedFrom、contains、dependsOn、connectsTo、evaluatedWith、approvedAs。

定义某个发布的必需工件集合为 R，BOM 中可用 digest 唯一解析的工件为 B：

分母 R 来自预先批准的发布合同，不是扫描器“发现了多少”。如果分母由发现结果自己决定，漏掉整个 MCP Server 仍可得到 100%。

9.3 BOM 生成时点

源码阶段 BOM、构建阶段 BOM、打包阶段 BOM 和部署阶段 BOM 的观察范围不同。源码 BOM 可能看见声明依赖，容器 BOM 看见实际安装包，运行 BOM 看见动态插件和远程服务。它们应当关联，而不是互相覆盖。

9.4 BOM 不能证明什么

BOM 不自动证明组件实际被执行，不证明未列组件不存在，不证明版本无漏洞，不证明许可证判断正确，也不证明远程服务当前仍是登记版本。BOM 是查询和决策的索引，不是终局安全证书。

十、逐类工件治理：同一个 digest 模板不够

10.1 模型权重与 Tokenizer

模型 release manifest 应固定所有分片、索引、配置、Tokenizer、特殊 Token、生成配置和适配器。只固定权重而让 Tokenizer 随版本更新，会改变输入切分和特殊指令边界。量化、合并 LoRA、格式转换都是派生构建，应产生新 digest 和 provenance，不能沿用父模型审批。

模型卡可以描述预期用途和限制，但不是可执行门禁。权重扫描还处在有限能力阶段，结果为零告警时必须报告支持的格式和检测类型。

10.2 数据与标签

数据 identity 应基于规范化快照或记录 manifest，并保存来源、采集许可、用途限制、去重、过滤、标注规则和写入者。对持续增长数据源，latest 不是可重放训练输入。应在训练开始时冻结 snapshot，并在 provenance 中绑定。

数据来源证明不等于数据质量证明。合法来源仍可能包含标签错误、敏感信息和投毒；来源不明的数据即使离线指标很好，也可能因授权和撤回能力不足而被拒绝。

10.3 Prompt 与策略

Prompt 的规范化要谨慎。随意去空格、重排 JSON 键或统一换行可能改变模型输入。规范化算法必须由工件类型定义，并保留实际发送字节的 digest。模板变量 Schema、消息角色、escaping、工具描述插入点和引用规则都应进入 bundle。

在线 A/B Prompt 也要生成发布身份。实验平台不能绕过生产审批，把任意文本注入 system message。

10.4 代码与容器

代码遵循常规 SSDF、依赖锁定、构建隔离、代码审查和漏洞响应。NIST SP 800-218 的 SSDF 是高层安全开发实践集合，不是某个工具的认证；SP 800-218A 在 2024 年为生成式 AI 和双用途基础模型补充了社区 Profile。采用这些实践应映射到本组织证据，而不是写一句“符合 SSDF”。

容器必须使用 manifest digest，不使用浮动 tag 作审批对象。入口脚本、模型挂载、启动参数、证书和网络策略可能在部署层注入，因此容器 digest 也不是完整运行身份。

10.5 插件

插件清单除代码外还要记录安装来源、主机 API 版本、权限、文件和网络范围、自动更新策略、配置 Schema 与撤回通道。插件市场评分不是供应链证明。插件更新若扩大权限，即使代码签名者不变，也应重新审批能力合同。

10.6 MCP Server 与 Tool Schema

MCP Server 是远程或本地可执行依赖。治理至少包括：

  • 固定协议修订与客户端兼容范围；
  • 验证 server identity、传输和授权资源边界；
  • 对 tools/list 规范化后计算 Tool Schema digest；
  • 单独比较工具新增、删除、名称、描述、输入/输出 Schema 和 annotation；
  • 不把 readOnlyHint、destructiveHint 等 annotation 当作可信授权事实；
  • 通过沙箱行为测试验证副作用，而不是相信描述；
  • 对本地 Server 固定可执行文件、依赖、启动参数、工作目录和环境变量；
  • 对远程 Server 记录 deployment identity，并在连接和调用时持续核验；
  • 工具目录变化通知只能触发重新发现，不能自动批准新工具。

MCP 规范定义协议互操作，应用负责业务授权。一个符合 JSON-RPC 和 Tool Schema 的调用仍可能越权。

十一、七道信任门：让每个失败都有明确原因

门禁顺序不是为了让最后一个绿色覆盖前面的红色。每一门都保留 PASS、HOLD、DENY 和 reason code：

  1. 身份门：manifest 是否只含内容 digest，下载内容重新哈希是否一致，media type 是否符合预期。
  2. 来源门：签名密码学是否有效，signer/issuer 是否被策略允许，签名或 subject 是否已吊销，证明是否过期。
  3. 构建门：attestation subject 是否等于候选 digest，builder、buildType、materials 和外部参数是否符合策略。
  4. 清单门：必需工件和关系是否完整，未知完整度是否显式保留。
  5. 风险门：漏洞、许可、秘密、数据、模型与行为测试是否完成；扫描不支持时是 HOLD。
  6. 审批门：职责分离是否满足，审批对象是否为当前 manifest 和 evidence set，例外是否过期。
  7. 运行时门：实例实际 served digest 是否与批准集合一致，动态 MCP Schema 是否漂移。

可操作的发布规则是：

HOLD 表示证据不足，不表示已发现恶意；DENY 表示违反明确硬门。两者都不能发布，但响应流程不同。

十二、指标体系：所有比例先写清分母

12.1 工件覆盖率

“verified”要求 digest 可解析且内容可重算，不是仅有名称。按 kind 同时报最差切片，避免八个 Python 包掩盖一个缺失模型。

12.2 Provenance 覆盖率

有效意味着签名、subject、predicate、builder、时效和吊销均通过。无法读取证明属于分母内失败或未知，不能删除。

12.3 材料解析覆盖率

分母来自构建类型合同。例如模型训练要求 base model、dataset、code、config、tokenizer 五类边，少一类即不完整。

12.4 签名身份合规率

密码学有效但 signer 未授权计入分母且失败。不要只报 signature_valid_rate。

12.5 证据新鲜度

对证据 e：

不同证据有效期不同。构建 provenance 可以长期绑定不可变产物，漏洞扫描会随情报快速老化，MCP Schema 观测可能要求分钟级。

12.6 未知率

未知率要作为硬门。扫描超时、格式不支持、日志不可用和解析失败都属于 unknown，而不是 pass。

12.7 Served Digest 一致率

同时报告观测覆盖：

没有上报的实例不能从分母消失。匹配率 100% 而覆盖率 40% 没有发布意义。

12.8 撤回传播时间

分别报告发现、决策和收敛，不能只报工单关闭时间。

12.9 可重建率

分母只包含环境和输入成功解析、构建完整执行的尝试；失败尝试另报。可重建性不等于安全性，但不匹配是值得调查的可重复性信号。

12.10 扫描声明覆盖率

这个指标不能简单混合字节和组件，应按格式切片报告。模型文件 95% 字节不受支持时，包扫描的“100% 组件成功”不能掩盖空白区。

十三、可重建性：有价值的差分证据，不是来源证明

可重建构建的工程目标是：给定相同源码、依赖和构建指令，不同参与者能够产生按定义逐字节相同的产物。它有助于发现未声明输入、时间戳、随机性、环境污染或构建平台差异。

AI 工件的重建要区分：

  • 确定性打包、Prompt 编译、Schema 规范化通常可以要求 bit-for-bit；
  • 模型训练受并行计算、硬件内核和随机性影响，bit-for-bit 可能不可行；
  • 无法逐字节重建时，应定义更弱但明确的派生一致性，例如配置、数据、代码、种子和训练轨迹证明，再独立比较行为指标；
  • 行为近似不能替代内容身份，两个输出相近的模型仍是两个不同工件。

重建方也可能使用同一个被攻陷编译器或恶意源，因此“两个构建相同”不等于工件安全。独立性、环境差异和信任根需要另外分析。

十四、扫描与行为测试：把覆盖范围和未知写进报告

14.1 依赖与漏洞扫描

对代码、容器和插件执行组件发现、漏洞关联和可利用性分析。数据库时间、规则版本、忽略项和 VEX/例外依据都要绑定到报告。没有已知 CVE 只说明当前情报和识别范围内未命中。

14.2 秘密与危险配置扫描

查找密钥、过宽权限、调试入口、未固定下载、关闭证书验证和任意命令执行配置。规则无命中仍需行为测试确认工具能力。

14.3 数据扫描

检查来源完整度、许可、敏感字段、重复、异常标签和构造投毒信号。数据扫描器不能证明没有未知敏感信息，也不能仅凭异常值判断存在攻击者。

14.4 模型扫描

检查格式解析、安全反序列化、元数据、已知恶意结构和策略限制。对于 opaque 权重，报告应直说无法理解其行为。模型安全要继续通过红队、后门、隐私和任务评测获取证据。

14.5 Prompt、插件和 MCP 行为测试

在无真实副作用的沙箱中验证：不可信内容不能改写系统策略；只读工具不会写；Schema 边界拒绝额外字段；权限外资源不可见；工具描述变化触发重评；网络出口和文件根符合能力合同。行为测试通过也只覆盖已测试场景。

十五、审批：批准的是证据快照和范围，不是一个名字

审批界面必须展示 immutable manifest digest、关键工件 digest、证据状态、未知项、例外和部署范围。审批 API 接受的参数也必须包含这些值，防止审核时看 A、落库时批准 B。

高风险发布至少职责分离：提交者不能独自批准；构建平台身份与人工审批身份分开；例外需要风险 owner 和到期日。自动门禁通过后，人工审批仍只处理业务剩余风险，不应手工覆盖 digest 或签名失败。

审批收据应带 evidence set digest。证据集合的规范化可以按 (predicate_type, subject_digest, attestation_digest) 排序后哈希。新增或替换任一报告都会改变集合身份，迫使重新决策。

十六、撤回与吊销：删除不是处置

供应链事件常见四类撤回：

  1. 身份撤回：签名密钥、OIDC identity 或 builder 失陷；影响其授权时间窗内签署的声明。
  2. 工件撤回：某个 digest 被确认有风险；影响所有包含或派生自它的 release。
  3. 证明撤回：评测报告错误、BOM 生成器有缺陷；工件本身未必恶意，但批准依据失效。
  4. 供应商撤回：来源整体失信；需要按 supplier relation 查影响闭包。

反向谱系查询应从撤回节点沿 derivedFrom、trainedOn、contains、connectsTo 和 approvedAs 找到发布，再找到环境、实例和请求。只查当前生产会漏掉灰度、缓存、灾备和待发布制品。

撤回事件必须幂等、可重放且优先级高于缓存 approval。验证服务不可用时，高风险动作应使用最近的有效撤回快照并 fail closed。

十七、运行时 served digest：把发布承诺变成可观察事实

部署系统在 admission 时验证 manifest，进程启动后仍要报告实际加载对象。模型服务常有启动后下载、热更新、路由和多副本，只有运行时观测能发现：

  • 镜像批准但挂载模型错误；
  • Prompt Hub 热更新绕过发布；
  • MCP Server 未变，Tool Schema 已改变；
  • 路由把一部分租户发送到未批准模型；
  • 回滚只改 deployment，却未清空旧 worker；
  • 缓存实例继续服务被撤回 release。

served digest 不应通过模型名称反查，应由加载器对实际字节或稳定 manifest 计算。对远程 MCP 无法读取服务字节时，至少使用服务端发布证明、部署 identity 和工具目录 digest，并明确其证据强度低于本地内容测量。

十八、自动化：事件驱动重评，不靠季度表格

以下事件都应触发重新求值：

  • 新 artifact、attestation、BOM 或扫描报告到达；
  • 漏洞库、许可策略或 signer allowlist 更新；
  • 签名者、builder、工件或 supplier 被撤回；
  • MCP tools/list 变化或 server deployment 变化；
  • Prompt、模型路由、插件权限和网络策略变化；
  • approval 或例外到期；
  • served digest 不匹配或观测过期；
  • 构建不可重建或证据解析器升级。

推荐三层执行：提交时做格式和本地关系校验；候选构建后做完整证明与行为测试；发布及运行时持续做 digest、吊销和能力一致性检查。昂贵扫描可异步，但未完成状态必须保持 HOLD。

18.1 策略求值要使用同一个证据时点

供应链状态持续变化：漏洞库更新、签名者撤回、扫描报告到期、MCP 工具目录刷新。如果验证器先读取 approval，几秒后读取 revocation，再从缓存取旧 BOM，就可能把不同时间的事实拼成一个从未真实存在过的“绿色快照”。

工程上需要给一次求值分配 evaluation_id 和逻辑时点。证据仓库提供一致快照，或者每个对象带单调 revision，验证器确认读取期间 revision 未变化。决定中记录 evaluated_at、各数据源 revision 与新鲜度。若求值过程中发生更高优先级撤回，结果作废并重算。

这不是要求所有系统使用分布式强一致事务，而是要求团队明确一致性模型。最终一致 Registry 可以使用“候选保持 HOLD，直到所有必需证据在同一 revision fence 内可见”；高风险撤回则通过单独的强优先通道覆盖缓存。

18.2 防止检查与使用之间的替换

典型 TOCTOU 错误是：验证器检查 tag 指向 digest A，部署器随后仍按 tag 拉取，此时 tag 已移动到 B。解决方法不是把两步做得更快，而是让验证结果直接产出不可变对象引用，部署器只接受该 digest。

同样，MCP Client 不能在审批时对一台预发布 Server 抓取 Schema，运行时却只按域名连接任意后端。批准对象应包含可验证 deployment identity 和 Schema digest；连接后重新协商并比较。如果服务端无法提供稳定身份，风险合同要把它视为动态第三方服务，而不是伪装成本地不可变工件。

18.3 证据规则要满足单调安全性

对扩展字段和新证据类型，安全策略应尽量满足：忽略一个不理解的字段，不会把 DENY 变成 ALLOW；缺少一项必需证明，不会因为其他证明更多而通过；新增撤回，不会被旧 approval 覆盖。

18.4 规范化失败必须可见

JSON Tool Schema 看似适合排序键后哈希，但数组顺序、数字表示、Unicode、默认值、$ref 和扩展关键字都可能影响语义。不能随便写一个 json.dumps(sort_keys=True) 就宣称得到跨实现规范 digest。应选择明确的 canonicalization 规范，固定解析器版本，并把原始字节 digest 与语义规范化 digest 都保存。

二者用途不同：原始 digest 验证传输比特；规范化 digest 帮助比较语义等价对象。若规范化器不认识新关键字，结果应 UNKNOWN，不能删除字段后继续比较。Prompt 更不能默认去除空白，因为空白、消息边界和转义可能改变模型输入。

18.5 证据图必须满足的结构不变量

除了每个文件可解析，还要验证整个图：

  • 每个 release manifest 只有一个不可变 digest；
  • 每个必需 kind 恰好解析到一个批准 subject，除非合同明确允许模型池；
  • 每个派生产物至少有一条到直接材料的边；
  • 关系端点必须存在，不能悬空；
  • 禁止派生环，除非关系类型明确允许运行时反馈环且带时间版本；
  • approval 指向的 evidence set 中，所有 subject 都属于当前 manifest 或其允许的材料闭包；
  • runtime observation 不得混用两个不兼容 release 的工件；
  • revocation 的影响闭包计算要有完整度与截止 revision。

例如模型 r12 的 provenance 若指向数据 d7，而 release BOM 却声明 trainedOn d8，不应任选一个解释；这是一条冲突证据，必须 DENY 并调查生成链。

18.6 供应商尽调与单个制品验证是两层控制

NIST SP 800-161 Rev.1 从组织、多层风险管理和整个生命周期讨论 C-SCRM。落到 AI 服务时，供应商评估要覆盖开发实践、人员与访问控制、漏洞响应、数据处理、分包商、终止服务和事件通知；单个 artifact 验证则覆盖具体 digest、证明和行为。前者不能替代后者，后者也无法回答供应商是否有持续交付和响应能力。

第三方模型 API 可能没有可下载权重 digest。此时“工件身份”要转换为服务合同：供应商模型版本、区域、API 行为版本、输出字段、数据使用承诺、变更通知和回退窗口。证据强度与本地可验证权重不同，报告必须明确，不能用一个营销模型名假装内容可验证。

18.7 证据保留也有机密性风险

Provenance 和 BOM 可能暴露内部仓库、构建参数、数据路径、供应商、工具能力和漏洞状态；透明日志可能公开身份与项目关联。公开性不是默认正确。设计时要区分可公开 subject 与受限 predicate，把秘密从 attestation 中移除，只记录受控引用或 digest。

删除敏感字段后仍要保证证据可验证。不能先把访问令牌写进 provenance，再寄希望于 Registry ACL。日志一旦公开通常难以撤回，因此在上传前进行 Schema 级秘密扫描，并把检测器失败设为 HOLD。

18.8 定期重验证矩阵

不同工件变化速度不同，建议按触发和最长周期组合：

对象 事件触发 构造最长重验证周期 重点

十九、故障注入：证明门禁在错误证据下会红

最低故障矩阵包括：

注入 预期首错门 不应发生
下载后修改一个字节 身份门 DENY 重新计算 digest 后继续发布
把有效 attestation 绑定到另一个 subject 构建门 DENY 因签名有效而通过
使用合法密钥签署未授权 kind 来源门 DENY 只验证密码学
删除 Tool Schema BOM 项 清单门 DENY 以其他工件覆盖率平均

approval 引用旧 evidence set 审批门 DENY 沿用历史绿色结果

线上热更 Prompt 运行时门 DENY 只比较容器 digest
透明日志不可达 按策略 HOLD 或缓存验证 自动跳过日志证明
反向谱系缺边 响应完整度告警 宣称影响面为零

注入必须针对隔离 registry 和构造工件，不接触真实生产凭据。测试成功不是“攻击成功”，而是控制能够识别预期偏差。

二十、完整可执行的 Python 标准库示例

下面的程序构造八类工件、HMAC 测试证明和签名扫描报告、简化追加哈希链、BOM、签名审批与运行时观测。它演示 subject 绑定、关系边与材料 digest 交叉绑定、buildType/materials/external parameters 策略、扫描身份与 ruleset、冲突扫描、严格数值、可信时间窗、类型化撤回、证据集合和 served digest 门禁。所有内容均为内存中的构造数据，无网络、无 API Key、无第三方包，也没有省略实现。

20.1 示例验证了什么

这个离线示例验证的是门禁语义：篡改或不可用内容、错绑 subject、伪造证明、额外材料、未批准的外部参数值、未来时间证明、BOM 漏项、关系图悬空/非法边/环、扫描未知、冲突、非法数值或严重发现、签名者撤回、运行时 Prompt 漂移、旧审批和日志链损坏都会进入预期状态。材料集合不是“至少包含”关系，而是与策略批准闭包精确相等；model trainedOn dataset、container contains code 还会把当前 manifest 中目标工件的 digest 加入来源材料闭包，因此替换数据集却沿用旧模型证明会失败。

扫描报告也不再依赖可自报的 scanner 名称。报告签名覆盖 subject、scanner、scan type、ruleset、状态、finding 数、适用性和时间，并验证日志包含、报告撤回与 scanner 撤回。finding 数必须是非负整数，适用性和策略阈值必须是 [0,1] 内有限数；规范 JSON 禁止 NaN，非法报告进入未知，非法策略直接拒绝，不能借浮点比较语义伪装成通过。

审批也不是任意字符串。示例构造并验证签名收据，将 ALLOW 决定、受信身份、职责角色、release 范围、签发/到期时间、manifest、policy 与 evidence set 一起纳入签名；策略同时限制签发新鲜度和最大有效期，检查审批者及具体收据撤回，并拒绝构建签名者审批自己的发布。artifact_coverage 的分子只包含 Registry 可解析、kind 匹配、重新哈希一致且未吊销的必需工件，不再把 manifest 中出现一个名称当成已验证。测试还特意断言即使全部门通过，security_proven 仍为 False，防止调用方把有限检查包装成安全证明。

20.2 示例不能证明什么

HMAC 是共享秘密校验，连审批者身份也只是测试密钥映射，不具有生产公钥签名、企业身份认证、硬件密钥保护和不可抵赖语义；职责分离校验也只比较身份字符串，没有覆盖代理审批、临时授权和组织关系变化。追加哈希链没有真正透明日志的独立见证、Merkle inclusion/consistency proof 和可用性保证；内存 registry 没有并发、缓存、最终一致性和权限问题；关系图只验证结构闭包而不解释每种领域关系的业务真值；示例也没有解析真实 SLSA、SPDX、CycloneDX、OCI 或 MCP Schema。

因此代码适合做策略状态机和故障注入的最小回归，不应直接成为生产验证器。生产实现应使用成熟的格式解析、密码学和策略引擎，并对其自身供应链建立验证。

二十一、自动化执行流程：从候选到运行时

21.1 候选入库

上传端先计算 digest，Registry 以 digest 地址存储。服务端重新哈希，不信任客户端提交值。工件 metadata 通过 Schema 校验后进入 QUARANTINED，不能立即被生产引用。

21.2 证明收集

受控 builder 生成 provenance；数据管道生成来源和过滤 attestation；BOM 生成器输出工件与关系；扫描器和行为评测器分别输出带 subject 的报告。收集器拒绝未知 predicate 主版本，不把解析失败丢弃。

21.3 策略求值

验证器读取固定策略 digest，检查 signer-builder 组合、材料、BOM 完整度、扫描适用性、硬错误和例外。结果写成机器可读 reason code，同时保存原始证据 digest。

21.4 审批与分发

审批者看到不可变证据快照并批准特定范围。分发器只接受有效 approval receipt 与 manifest digest，不接受模型名或 tag。生产 admission 再次验证，避免决策到部署之间被替换。

21.5 运行与持续核验

实例上报实际 served digest；控制平面比较集合和观测新鲜度。MCP 工具目录变化、吊销或策略升级触发重新求值。无法验证时按能力合同阻断高风险动作或切入批准的只读降级。

二十二、完整构造发布案例：零严重告警仍被阻断

下面是一个构造案例，所有数字与时间均为示例。

22.1 变更背景

团队准备发布 rel-2026-0607-17。主要变化是模型从 r11 更新到 r12，Prompt v31 增加对工单工具的解释，MCP Server 从 1.5 升到 1.6。CI 页面显示：容器依赖扫描 0 个 Critical、0 个 High；模型文件扫描 0 告警；单元测试全绿。

若只看摘要，这次发布似乎风险很低。但门禁输出：

门 构造结果 原因
身份 PASS 八类工件均为 digest 地址，重新哈希一致
来源 PASS signer 与 issuer 合规，未撤回
构建 PASS model/container provenance subject 正确
清单 DENY BOM 中 Tool Schema 仍指向 v8，manifest 是 v9
风险 HOLD 模型扫描器对新量化格式 applicability=0
审批 DENY approval receipt 引用旧 evidence set

“0 告警”的模型扫描报告同时写着 format unsupported，聚合 UI 却只读取 finding 数。Tool Schema v9 新增字段 include_private_comments，且 annotation 仍声称工具只读。旧审批是发布经理在 v8 证据上签发的。

22.2 证据冻结

响应者先冻结 release manifest、八个工件、BOM、attestation、扫描原始输出、策略、approval receipt 和日志 inclusion bundle。没有立即重跑覆盖原报告，因为重跑会丢失当时“unsupported 被显示为绿色”的检测缺口。

反向谱系显示 MCP Server 1.6 来自提交 mcp-91c，Tool Schema v9 抓取自预发布环境；BOM 生成任务错误地从缓存读取 v8。代码审查进一步发现新增参数由服务端忽略只读策略，可能返回内部评论。没有证据表明发生真实数据泄露，因为发布尚未进入生产。

22.3 首错层分析

首个供应链偏差是 BOM 生成器缓存键没有包含 server deployment digest。第二个检测缺口是扫描聚合器把 UNSUPPORTED 映射成“0 findings”。第三个流程问题是审批 API 只验证 release_id 字符串，没有验证 manifest 与 evidence set digest。

这三个问题分别属于清单、风险与审批层，不能归结为“模型不安全”。工件是否存在恶意逻辑仍未知；已有证据只足以阻断发布。

22.4 修复

团队执行以下构造处置：

  1. BOM 缓存键加入 server 和 Tool Schema digest，并把完整度声明限定到当前 release manifest；
  2. 聚合器把 unsupported、timeout 和 parser error 统一映射为 HOLD，UI 显示适用性分母；
  3. Tool Schema v9 删除未批准字段，MCP Server 增加服务端字段 allowlist 和沙箱行为测试；
  4. 审批 API 强制提交 manifest digest、policy digest 和 evidence set digest；
  5. 生成全新 release rel-2026-0607-18，不复用原 approval；
  6. 在灰度实例核验模型、Prompt、Server 与 Tool Schema served digest。

22.5 复验与决定

构造复验得到：必需工件 8/8、关系 4/4、provenance 8/8、扫描可适用 8/8、未知 0、行为测试 126/126、运行观测实例 12/12，served set 完全匹配。风险 owner 批准 10% 只读流量 24 小时，之后按观测扩大。

最终结论不是“供应链安全”，而是：在固定的八类工件、证据版本、策略、只读能力和灰度范围内，所有预注册硬门通过，当前剩余风险被接受。写入能力仍未获批。

二十三、事故案例：合法签名者失陷后的撤回闭环

另一个构造事故发生在发布后一周。监控在透明日志发现 ci@northlake.example 于非工作窗口签署未知插件 digest。身份团队确认用于 CI 的 OIDC 配置被错误放宽，攻击者可能在 40 分钟窗口内取得合法身份。

23.1 不能只撤销未来证书

如果只修复 OIDC 配置，窗口内已经签署的声明仍会通过离线验证。事件处理必须创建 signer revocation，带 effective_from 和调查时间窗；策略引擎重新求值窗口内所有 attestation。

23.2 影响闭包

谱系查询发现该 signer 在窗口内签署 4 个 attestation，涉及 2 个插件 digest；一个进入测试 release，一个尚未被 manifest 引用。生产 release 使用的是窗口前签署版本，因此没有直接命中。但是测试环境曾调用其中一个插件，访问的是构造数据集。

报告应写：生产影响“未发现”，不是“证明没有”；测试影响“确认存在”；由于测试日志覆盖率 97%，剩余 3% 请求归为未知并进入凭据轮换范围。

23.3 处置与恢复

团队冻结 signer，撤回两个插件 digest，停止受影响测试实例，轮换可能暴露的测试凭据，从已知良好提交在新 builder identity 下重建并重新签署。旧 attestation 保留用于取证，不从日志删除。恢复发布使用新 release_id 和 approval receipt。

23.4 事故指标

构造时间如下：日志异常出现 10:02，监控告警 10:07，吊销生效 10:14，最后受影响实例停止 10:21。因此 T_detect=5m、T_decide=7m、T_contain=19m。这些数字不能证明没有数据访问，只衡量控制面响应。

二十四、这些控制明确不能证明什么

即使全部检查通过，也不能得出以下结论：

  • 不能证明模型没有未知后门、偏见、幻觉或隐私泄露；
  • 不能证明训练数据全部合法、准确、无敏感信息；
  • 不能证明 Prompt 在所有攻击输入下都保持边界；
  • 不能证明插件和 MCP Server 没有运行时漏洞；
  • 不能证明受信 builder、signer、扫描器和审批者永不失陷；
  • 不能证明 BOM 之外绝无动态依赖；
  • 不能证明透明日志始终可用或监控者必然响应；
  • 不能证明可重建的恶意工件会变安全；
  • 不能证明一个 release 的证据适用于另一个 digest、环境或能力范围；
  • 不能把当前无告警外推成未来无风险。

这些不是削弱供应链治理，而是防止把证据用到它不支持的结论上。可靠系统通过多层控制缩小不确定性，并把剩余未知写进决策。

二十五、常见实现误区

25.1 只固定模型名称

名称解决发现，digest 解决身份。生产审批必须落到后者。

25.2 attestation 自己声明 subject，验证器不重算

证明必须与实际下载内容和 release manifest 双向绑定。

25.3 把所有证明塞进一个 JSON

不同 predicate 的语义、签名者和有效期不同，应独立验证并组合决策。

25.4 用 BOM 发现结果当完整度分母

分母必须来自发布合同，否则完全漏掉一类工件也可显示 100%。

25.5 把 Tool Annotation 当权限

annotation 是提示，授权要由可信策略和服务端强制执行。

25.6 只在 CI 验证一次

撤回、动态工具和运行时加载要求持续验证。

25.7 用 tag 关联扫描报告

tag 会移动，所有证据 subject 必须是 digest。

25.8 扫描异常自动重试到绿色

原始失败和未知会被覆盖。应保留每次尝试及最终决策规则。

25.9 approval 只存用户名和 release_id

必须绑定 manifest、policy 和 evidence set digest。

25.10 回滚到“上一个版本”

上一个版本也可能被撤回。回滚目标必须是当前仍有效的已批准 digest 集合。

二十六、从零到一的实施顺序

阶段一：盘点行为闭包

列出能改变回答、权限或外部动作的全部工件和远程服务。先解决“有哪些”，再采购工具。

阶段二：建立不可变身份

为文件、目录、Prompt bundle、模型分片和 Tool Schema 定义规范化与 digest。淘汰生产浮动引用。

阶段三：建立 release manifest 与关系

固定必需 kind、关系和能力合同。把分母变成可执行 Schema。

阶段四：接入 provenance、BOM 与签名

从高风险模型、容器、插件和 MCP 开始。验证 subject、signer、builder 和完整度，不只生成文件。

阶段五：实现多状态门禁

支持 PASS/HOLD/DENY，未知硬门，证据新鲜度和 approval receipt。

阶段六：运行时测量与撤回

上报 served digest，建立反向谱系，演练 signer 和 artifact 撤回。

阶段七：持续改进

用事故和故障注入发现缺边、盲区和过宽信任根，更新发布合同和测试覆盖。

二十七、可执行检查清单

工件身份

  • 模型、数据、Prompt、代码、容器、插件、MCP Server 和 Tool Schema 均有独立 kind。
  • 所有生产引用最终解析为内容 digest，禁止浮动 tag 作为审批对象。
  • 目录、模型分片和 Prompt bundle 有版本化规范化算法。
  • Registry 服务端重新计算 digest，不盲信上传值。
  • media type、大小和来源 URI 与 digest 一起记录。

Provenance 与签名

  • attestation subject 与下载内容和 release manifest 三方一致。
  • predicate type 固定主版本，未知语义不会被忽略。
  • signer、issuer、builder 和 buildType 由策略 allowlist 限制。
  • materials 覆盖真正影响产物的输入，缺失按 kind 失败。
  • 证明生成由受控 builder 读取实际产物，不由调用者自由填写。
  • 签名、证书、日志和策略信任根可轮换、可撤回。
  • 透明日志 inclusion 失败不会静默降级。

BOM 与关系

  • BOM 格式和版本固定，解析失败为 unknown。
  • 必需工件分母来自发布合同，不来自发现结果。
  • 模型、数据、Prompt、插件和远程服务都在声明范围内。
  • trainedOn、derivedFrom、contains、connectsTo 等关系可反向查询。
  • 完整、部分、未知的语义按生命周期阶段记录。
  • BOM 生成器自身版本和 digest 被记录。

扫描与测试

  • 扫描报告绑定 subject digest、规则版本、数据库时间和适用范围。
  • unsupported、timeout、parser error 显示为 HOLD，不是零告警。
  • 静态扫描与模型、Prompt、插件、MCP 行为测试分开。
  • 工具只读、参数边界、授权和副作用通过沙箱验证。
  • “扫描无告警”从未被描述成安全证明。
  • 故障注入覆盖内容篡改、错 subject、缺 BOM、旧审批和 served drift。

MCP 与插件

  • 协议修订、Server identity、部署版本和 Tool Schema digest 固定。
  • Tool Annotation 只作不可信提示，不作授权依据。
  • tools/list 变化触发重评，不自动批准。
  • 本地 Server 的二进制、依赖、启动参数和环境均在 manifest 中。
  • 远程 Server 有授权资源边界、最小 scope 和运行时观测。
  • 插件自动更新不能绕过 release manifest。

审批与运行

  • approval 绑定 manifest、policy 和 evidence set digest。
  • 审批范围含环境、流量、能力和到期日。
  • 提交、构建、签名和审批职责适当分离。
  • 线上实例上报实际 served digest，且有观测覆盖率指标。
  • Prompt 热更、模型路由和 MCP Schema 漂移均能被发现。
  • 高风险能力在验证服务异常时有明确 fail-closed 或批准降级策略。

撤回与事故

  • signer、builder、artifact、attestation、supplier 和 release 均可撤回。
  • 撤回事件有生效时间、原因、发布者和替代对象。
  • 反向谱系能定位环境、实例、请求和缓存。
  • 删除工件不会替代吊销与实例收敛。
  • 定期演练 signer 失陷、Tool Schema 漂移和验证服务不可用。
  • 报告分别给出已确认、未发现和未知影响。

二十八、总结

AI 供应链治理的核心不是收集更多徽章，而是建立可验证的对象关系：内容 digest 固定“是什么”，签名表达“谁认可哪段声明”，透明日志提高签名事件的可审计性，provenance 描述“怎样产生”，BOM 描述“由什么组成”，策略和审批决定“在什么范围内可用”，served digest 验证“实际上线了什么”，撤回机制回答“失信后怎样收敛”。

这些证据互补但不互相替代。digest 不证明来源，签名不证明安全，日志不证明授权，BOM 不证明完整，provenance 不证明行为正确，可重建性也不证明没有恶意。把边界写清楚，反而能让每个控制承担它真正擅长的任务。

对测试开发而言，最重要的产物不是一张绿色扫描截图，而是一套能够被反例击穿、被故障注入验证、被运行时事实持续核对的决策系统。当模型、Prompt、插件或 MCP Server 任何一个节点变化时，系统都能明确说出受影响对象、缺失证据、阻断原因和恢复条件，这才是可运营的 AI 供应链治理。
