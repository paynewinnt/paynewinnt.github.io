AI测试-61-AI事故怎么做发现止损回滚复盘和评测集回灌

发表于 2026-06-17 分类于 AI测试 本文字数： 26k 阅读时长 ≈ 1:35

AI 服务的错误率从 8% 降回 0.2%，接口恢复 200，发布平台显示已经回滚。事故是不是结束了？

不一定。

模型可能已经停止生成错误工具参数，但在途重试队列还在重复提交；Prompt 回到了旧版，路由缓存却继续把一部分会话送往故障模型；知识索引别名切回去了，旧快照却重新暴露了已撤销权限；退款接口返回 200，但把“元”当成“分”，用户实际只收到应退金额的百分之一；线上症状暂时消失，评测系统却把本次事故样本同时加入训练集和回归集，下一版通过的原因只是记住了答案。

因此，AI 事故响应不能缩成“报警、回滚、写复盘”三个按钮。它必须回答：

本文资料边界截至 2026-06-17（含）。组织、产品、账号、金额、阈值、时间线、影响规模、告警和事故均为构造示例，不代表任何真实公司、模型、供应商或生产事故。严重度、角色、时限和门槛也都是教学用构造值，实际组织应按用户伤害、业务风险、法规、合同、值班能力和系统架构批准自己的制度。

一、边界：AI 事故响应不是模型专属救火流程

1.1 本文覆盖的对象

AI 应用是社会技术系统。一次事故可能跨越：

层 典型对象 典型失败
用户与业务 对话、申请、退款、付款、客服承诺 错误决定、金额错误、歧视性结果、用户无法完成任务
模型与 Prompt 模型版本、系统指令、输出约束 幻觉、拒绝退化、工具参数错误、越权建议
知识链路 摄取、权限、索引、检索、引用 旧政策、撤销内容复活、ACL 泄露、引用不支持结论
工具与工作流 适配器、Schema、队列、幂等、补偿 重复副作用、单位错、目标接受但业务未提交
策略与身份 授权、风险规则、人工审批 默认放行、特征缺失、审批旁路、代理链错误
路由与基础设施 多模型路由、缓存、区域、容量 cohort 残留、跨区域数据、回滚后容量崩溃
观测与治理 SLI、评测、审计、响应流程 只看 HTTP、证据丢失、沟通混乱、回灌污染

本文关注端到端响应和学习闭环，不重复讲通用日志采集、单一模型评测或 SRE 基础设施细节。相关能力是前置条件，但 AI 事故需要额外处理概率输出、版本组合、工具副作用、知识时效、评测污染和难以复现等问题。

1.2 通过本文流程不能证明什么

  • 事故关闭不证明系统以后不会发生同类或变体事故；它只说明批准范围内的恢复和跟踪条件满足。
  • 回滚到“已知好版本”不证明当前依赖和数据仍与它兼容。
  • 一次安全复现不证明所有受影响用户、语言、租户和时间窗已经识别。
  • 复盘中的根因标签不证明存在唯一根因；复杂事故通常是多个控制条件共同成立。
  • 评测集加入一个事故样本不证明风险已覆盖；还需要变体、对照、反例和生产监控。
  • 没有用户投诉不证明没有影响；投诉分母、发现渠道和用户可见性可能不足。
  • HTTP、进程健康、模型成功率或平均质量恢复，都不能单独证明业务副作用正确。
  • 本文引用的 NIST 与 Google 资料提供框架和实践，不替组织规定强制严重度、角色或时限。

二、事件、信号、告警、事故和问题不能混用

2.1 Event

Event 是某件可观察事实，例如 refund.create 返回 200、模型输出 Schema 无效、业务账本金额与请求不一致、用户点击重试。事件可以正常，也可以异常。

2.2 Signal

Signal 是从一个或多个事件形成的风险迹象，例如“退款金额比订单应退金额小 99%”“某语言的工具参数校验失败率上升”。Signal 可以来自指标、评测、审计对账、用户报告、红队、供应商通知或人工观察。

2.3 Alert

Alert 是按规则把 Signal 交给特定响应者的动作。一个好告警应描述用户症状或即将发生的硬资源风险，给出范围、置信度、runbook 和可执行下一步。Alert 可以是误报，也可能漏报；告警触发不自动等于事故成立。

2.5 Problem、defect 与 action item

Defect 是一个可修复缺陷；Problem 是可能跨多个事故的系统性问题；Action item 是降低检测、响应、恢复或复发风险的可验证工作。一次事故可以有多个 defect，一个 defect 也可能不是唯一根因。关闭事故不应自动关闭 problem 和 action item。

三、十个会拖延或误导响应的反例

3.1 “等根因明确再声明事故”

反例：工具正在产生不可逆付款，团队用 40 分钟争论是模型还是 Prompt。影响持续扩大。事故声明只需要达到协调和止损门槛，不需要先证明根因。可以先写 cause=UNKNOWN，用明确决策记录关闭高风险工具。

3.2 “模型输出错了，回滚模型即可”

反例：故障只发生在 Prompt v42 与工具 Schema v5 组合，旧模型也会按 Prompt 生成同样字段；或模型回滚后，路由的 12% 黏性会话仍指向新部署。模型只是版本图中的一个节点。

3.3 “Prompt 是文本，回滚没有兼容性”

反例：旧 Prompt 使用 amount_cents，当前工具只接受 amount_minor；旧 Prompt 依赖模型支持某种严格 JSON 模式；会话历史里已注入新版系统指令。文本也有接口、状态和依赖。

3.4 “知识快照切回去风险最小”

反例：旧快照包含后来撤销的员工权限，或缺少最近生效的退款上限。知识回滚必须验证权限、时效、删除与索引 Schema，不能只按离线准确率挑旧版本。

3.5 “kill switch 会丢证据，先不要关”

反例：为了观察更多样本，让真实退款工具继续执行。证据价值不能凌驾于用户止损。正确方式是先禁副作用、切到模拟或人工路径，同时冻结已有版本、请求摘要、队列和目标流水。

3.6 “接口 200，所以回滚成功”

反例：目标接受请求并返回 200，但金额单位错误；异步账本稍后提交 8 元而不是 800 元。恢复要验证业务后置条件、对账和用户状态。

3.7 “没有新错误就是恢复”

反例：流量被全量切到人工，AI 错误自然归零，但人工队列积压 18 小时，用户仍无法完成退款。隔离路径的容量、等待时间和用户结果也在恢复门禁中。

3.8 “把事故原始对话加入回归集最真实”

反例：对话包含个人数据和内部订单，且同一原文随后进入微调训练。回归准确率升高可能来自记忆，数据处理目的也可能越界。应先抽象最小场景、审批、脱敏、分割和登记血缘。

3.9 “复盘无责，所以不能讨论操作错误”

反例：为了避免责备，复盘只写“系统复杂”。无责不是无事实。可以具体记录当时谁拥有什么信息、哪个界面误导、哪个权限过宽、哪个 runbook 缺失，同时关注系统条件与改进，不进行人格归因。

3.10 “action item 建票就完成学习”

反例：所有任务标为 P2，没有 owner、到期、完成证据和复发监控；三个月后相同事故重演。action item 的价值在风险下降证据，不在票数。

五、从 Signal 到 Incident：声明门槛和状态机

5.1 声明输入

Incident Commander 或预先授权值班角色评估：

  • 是否有已确认用户或业务后置条件失败；
  • 是否存在未经授权、不可逆或高成本副作用；
  • 是否涉及个人数据、安全、歧视、权利或监管报告可能性；
  • 影响范围、地域、租户和产品是否已知；
  • 影响扩散速度和当前暴露流量；
  • 能否快速撤销或补偿；
  • 观测可靠性和未知程度；
  • 是否需要多个团队、外部供应商或沟通角色协调。

声明决策不应依赖一个加权总分把严重硬门平均掉。例如一个已确认未经授权付款，即使流量很小，也可以触发最低严重度硬门。总分可用于排序，但不可逆伤害、安全或法律触发器必须单独判断。

5.2 构造状态机

这不是只能向前的流水线。RECOVERING 期间发现新副作用，可以回到 CONTAINING；MONITORING 发现复发也重新声明或重开。状态 API 不能接收“impact_stopped=true 加几个 evidence ID”就推进：它只消费可信证据目录签发的摘要，解析后核对事故 ID、来源状态、目标状态、证据类型、签发身份/角色、观测时间、签发时间、载荷和签名。操作者角色来自可信 IAM 快照，不来自请求正文；转换时间不得早于信号、上一状态或当前状态证据。

状态历史保存解析后的完整不可变 evidence snapshot、证据集合摘要、actor、可信角色、转换时间和理由，而不只保存以后可能失效的引用 ID。这样审计者能判断“当时凭什么进入该状态”，也能发现用未来证据关闭过去状态、把别的事故证据移植过来或用普通查看者身份推进状态的行为。

5.3 事件与事故的多对多

多个告警可能属于同一事故，例如金额对账、用户投诉和退款适配器版本异常；一个告警也可能揭示多个事故，例如同一供应商故障同时影响退款和订单取消，但两者止损、用户沟通和恢复条件不同。合并或拆分是显式决策，不能只按时间相近自动聚类。

关键决策至少记录：

八、观测、推断、根因与决策：四层证据语言

8.1 Observation

Observation 是可回到证据对象的陈述，例如：

  • 目标退款流水 R-901 的 amount_minor=800；
  • 批准记录的 amount_minor=80000；
  • 三个受影响 Trace 都命中 router branch legacy-sticky-hk；
  • adapter v4 日志出现 fallback reason UNKNOWN_AMOUNT_MINOR。

观察也有质量：来源可能迟到、采样、受时钟影响或被篡改。记录来源和限制，不把“仪表盘显示”当天然真值。

8.2 Inference / Hypothesis

“旧适配器把元当成分”是推断。它可由观测支持，但需安全复现、版本对照和反事实验证。假设有 proposed/supported/refuted/inconclusive，不能因为第一个猜测最合理就改名为根因。

8.3 Root cause / contributing conditions

构造复现证明：同样请求只在 prompt42 + router17 legacy branch + adapter4 fallback 组合失败；adapter5 正常；prompt41 与 adapter4 使用旧字段也正常。团队把“兼容分支允许不认识的新字段回退到显示金额”定义为直接技术原因，把“发布包没有覆盖黏性路由的组合测试”和“业务金额对账不在同步发布门禁”定义为促成条件。

根因不是“某工程师忘记测试”。复盘继续问为什么发布系统允许不完整依赖包、为什么 Schema 版本未硬拒绝、为什么小 cohort 没有基线、为什么用户结果对账延迟 10 分钟。

8.4 Decision

决策是基于当时事实与不确定性采取的可追责选择。后来发现假设错误，不代表当时止损决定错误；反之，结果碰巧没扩大，也不能证明冒险继续运行是好决定。复盘应评价决策过程、信息界面和授权边界。

九、先隔离和止损，再做精细归因

9.1 止损优先级

Nova 构造 runbook 按风险选择：

  1. 在策略层把 refund.create 真实执行切为 DENY_AUTOMATION；
  2. 撤销工具代理的退款写凭据，保留只读对账；
  3. 新请求路由到人工队列并展示明确等待状态；
  4. 暂停相关重试队列，按幂等键盘点在途状态；
  5. 保留用户查询与只读回答，但隐藏未经确认的退款承诺；
  6. 对已提交 case 启动业务对账和补偿，不盲目重放；
  7. 固定故障发布包、路由规则、队列水位和目标流水摘要。

策略 kill switch 与凭据撤销是两层控制。只改 Prompt 为“不要退款”仍信任模型遵循；只关路由可能遗漏异步任务；只撤凭据可能让重试队列持续制造噪声。高风险动作需要模型外强制边界。

9.2 隔离的副作用也要测

全量转人工会增加队列、用户等待和人工错误；关闭写工具可能让用户重复提交；冻结重试可能延迟合法退款。IC 要记录这些二次影响，给人工容量和用户沟通设置 SLO。止损不是无代价，但代价应被显式管理。

9.3 在途与不确定提交

网络超时或暂停队列时，任务可能处于：

UNKNOWN 不能当失败后直接重试。先用幂等键向目标系统和业务账本对账；目标不支持幂等时，需要人工确认和更严格补偿流程。事故工具应能导出每个任务的阶段、最后证据和下一安全动作。

9.4 保全证据不能延长伤害

证据 Lead 固定：发布清单和摘要、Prompt/策略/路由版本、知识快照 ID、工具 Schema、受影响 Trace 与业务流水、审批和决策日志、告警状态、队列元数据。用户原文只在明确必要和授权范围内保存；普通战情频道使用假名和摘要。

故障组件仍运行以“多收样本”通常不可接受。可以把流量复制到无副作用沙箱、回放已授权最小样本，或用构造 case 复现。证据保存与隐私、保留、访问控制一起设计。

十、回滚对象：模型、Prompt、知识、工具、策略和路由

10.1 发布包而不是六个“latest”

一个可回滚发布包至少固定：

每个引用是不可变版本或摘要，不能用供应商可漂移别名。发布平台验证依赖图后生成签名/批准清单。所谓“已知好”还要记录当时在哪些流量、任务和风险切片上通过；它不是永久好。

10.2 模型回滚

检查旧模型是否仍可用、区域和数据处理约束是否满足、Prompt 使用的工具调用和结构化输出能力是否支持、上下文窗口是否足够、Tokenizer 和费用是否变化。供应商别名可能已经指向新 revision，应使用可获得的固定部署标识和本地验证证据。

模型回滚后要处理会话：旧会话历史可能包含新版工具结果或系统指令；KV/prefix cache 可能继续复用；异步任务已保存新模型输出。可选择排空、新建会话、标记需要重新规划，不能只切新请求比例。

10.3 Prompt 回滚

Prompt 是接口消费者。检查变量名、知识字段、工具名、参数单位、reason code、引用格式、输出 Parser 和安全策略。旧 Prompt 若生成旧 Schema，而当前 adapter 不再兼容，应同时回滚 adapter 或启用经过验证的转换器。

模板缓存、边缘缓存、A/B 分桶、会话系统消息和 agent memory 都是隐藏状态。回滚后用版本回显和 Trace 证明目标 cohort 真正使用旧 Prompt。

10.4 知识回滚

知识快照必须同时固定内容、解析器、chunk、Embedding、索引、ACL、生效时间和删除水位。旧快照可能包含已撤销文档或缺少新政策，所以回滚前执行：

  • 权限差分：旧快照是否暴露当前不应访问的对象；
  • 时效差分：其政策是否仍有效；
  • 删除差分：已删除主体数据是否被旧备份复活；
  • Schema 差分：当前 Prompt/Retriever 能否解释旧 metadata；
  • 引用差分：返回引用能否回到仍存在的权威原文。

若旧知识不安全，宁可切只读人工或小型批准事实集，也不能为了质量快速恢复过期快照。

10.5 工具适配器回滚

先盘点在途和已提交副作用，再换代码。旧适配器是否能读取新队列消息？单位、枚举、必填字段、幂等键和目标 API 是否兼容？凭据 scope 是否已变化？补偿动作是否仍匹配？

安全策略是对新写入先停，再在沙箱验证旧 adapter，最后对新幂等键小流量开放。旧消息可以由专用迁移消费者处理，不能让旧代码把未知字段默认为零或自由文本 fallback。

10.6 策略回滚

旧政策不一定仍合法或符合业务规则。检查特征定义、身份源、工具阶段、生效日期、人工例外和审批状态。缺特征时，高风险动作应默认拒绝或转人工，不能沿用缓存 ALLOW。

回滚后要验证 deny/allow/require-approval 三类边界，以及理由码和审计。策略引擎健康不代表授权正确。

10.7 路由回滚

路由控制谁看到哪个发布包，也控制地区、租户、风险、容量和隐私边界。检查黏性会话、边缘缓存、异步消费者、影子流量和 fallback。回滚目标必须有容量；否则质量事故可能变成可用性事故。

每个 cohort 记录当前 bundle 回显，直到受影响 branch 流量归零。仅看配置中心值不足以证明边缘节点和长会话已收敛。

Nova 先保持工具写关闭，在隔离租户部署 prompt41 + adapter4.8.2 + router16 已知好包，运行构造订单和经过授权的最小生产回放；通过后只开放内部 canary 的模拟工具，再开放 1% 新请求但仍人工确认，最后按观察窗逐级恢复真实执行。

十二、恢复条件：接口、业务、质量、安全、审计和容量共同通过

12.1 恢复不是一个布尔值

建议把恢复拆成：

事故可以在可信止损证据表明 impact_stopped 后继续处理历史补偿；也可以服务稳定但证据仍不完整。这个标签是报告中的语义状态，不是允许调用者自填后推进状态机的布尔开关。对外“已缓解”“已恢复”“已解决”应有组织统一含义，避免不同角色使用同一个词表达不同状态。

12.2 用户症状门禁

按受影响 cohort 测量任务成功、等待、重试和投诉。Nova 至少分 zh-HK + VIP + sticky-session、其他 zh-HK、其他 VIP 和总体。总体恢复可能掩盖小 cohort 仍失败。

分母不能只包含得到最终结果的用户；中途放弃、被路由人工但超时、重复提交也属于 eligible。无数据切片报告 UNKNOWN，不以总体值填充。

12.3 业务后置条件门禁

对每个退款建立批准、请求、目标接受、业务提交和用户显示的配对：

金额匹配率分母排除缺任一金额的 case，但必须并列报告 reconciliation coverage；否则把未知 case 排除会制造 100%。未经授权副作用和重复提交是硬门，不能用平均金额误差抵消。

12.4 AI 质量门禁

固定故障场景、相邻正常场景、语言/租户/风险切片，测：意图金额、工具字段、拒绝、澄清、政策引用和人工转交。评测必须固定候选发布包与 judge/规则版本，保留逐 case 结果。

故障 case 通过只是必要条件。回滚可能修复金额字段却让普通问答拒绝率升高，或旧模型无法处理新知识格式。需要非回归切片与硬错误门。

12.5 安全与策略门禁

  • 无批准的退款提交必须为零；
  • 超阈值退款必须进入人工批准；
  • 工具 kill switch 在策略和凭据层均有效；
  • 模型自由文本不能绕过结构化 adapter；
  • Prompt 注入和越权测试不退化；
  • 数据地域、租户与知识 ACL 仍满足批准约束；
  • 缺失特征或未知 Schema 时高风险动作 fail-closed。

“零”需要有覆盖分母。例如只观察 3 个 canary 不足以证明所有路径无越权；声明应写“在已执行的 N 个预注册路径中为零”。

12.6 审计与证据门禁

每个 canary 退款必须能关联 proposal、authorization、executor、target 和 business outcome。Trace 采样不能使审计事件缺失；发生重试时 Attempt 和幂等键一致；路由回显与实际 bundle 匹配；时钟、迟到和 duplicate conflict 无未解决高风险异常。

如果业务恢复但审计 coverage 只有 80%，可以继续保持工具受限或由风险接受者显式批准临时状态，不能把 evidence gap 隐藏在“服务已好”的更新里。

12.7 容量、成本与降级门禁

回滚模型可能更慢、更贵、配额更小；人工队列可能持续增长；关闭缓存会抬高延迟。监控候选路径的吞吐、P95/P99 延迟、队列年龄、拒绝、限额和单位任务成本。恢复方案必须能持续，而不是在低流量 canary 上短暂绿。

12.8 连续观察窗

定义预注册的连续观察窗，例如三个 15 分钟窗口，每个达到最小样本并通过硬门。这里的数字是构造示例。窗口摘要由恢复服务从 manifest、时间边界、逐 Attempt 结果、bundle 回显、评测运行和计数重新规范化计算，调用者不提交摘要真值。Tracker 跨窗口拒绝重复 Attempt Group、业务幂等键、目标回执和评测运行 ID；因此换 window_id、平移时间或重新包装同一份结果不能累计绿色 streak。

零流量窗口不算通过；流量显著偏离生产分布要标记。高风险、低频动作可以用更长时间和主动 canary，不能为了快速关闭把分母降到 1。外部 attempt manifest 还要在进入门禁前验证资源、收款方、币种、金额范围、幂等键和预期回执的语义及唯一性；两端恰好填成同一个空字符串或负数不构成业务匹配。

十三、发现与响应指标：用分布和分母，不把均值当绩效

13.1 时间点定义

可计算检测延迟、确认延迟、声明延迟、止损时间和恢复时间，但要声明起点。若 t_impact_start 只能事后估计，应保留置信范围。把 alert 到 close 叫统一 MTTR 会混淆不同改进方向。

13.2 检测覆盖率

生产事故没有可知的“全部事故”分母，因此不能从历史告警直接算真实召回。可以对预注册演练和注入集计算：

并报告生产中的来源分布：用户报告、业务对账、质量评测、安全监控、供应商、工程发现。注入覆盖只对场景库有效，不能证明未知事故会被发现。

13.3 影响范围

exposed 由版本、路由和时间 Trace 确定。不能用“错误日志数 / 总请求”代替，因为错误可能没有日志，正常日志也可能业务错误。未知单列，直到对账完成。

13.4 止损有效性

若分子非零，先检查在途任务、缓存、旁路和时钟，不急于把 t_contain 后移美化指标。止损时刻是决策与控制生效的证据点。

13.5 回滚成功率

按 rollback attempt 记录 compatible, deployed, traffic_converged, all_recovery_gates_passed。只有最后一项才是端到端成功。HTTP 健康成功率只是子指标。

不同事故难度差异大，这个比例不适合作为个人绩效。更有价值的是失败原因：依赖不兼容、状态未排空、容量不足、验证缺口或再次触发影响。

13.6 恢复门禁 coverage

门禁为 UNKNOWN 不算通过。每个 gate 还要有最小样本、证据时间和适用切片。一个总布尔值之外，保留逐门结果。

13.7 复发指标

“同一事故是否复发”需要可计算 signature，例如 amount_unit_mismatch + legacy_adapter_branch，也要监控相邻变体，如不同货币、负数、四舍五入和其他 sticky cohort。窗口有效性必须来自监控事实源签发的证据，而不是调用者传入 valid_window。若存在数据迟到、分母损坏或校验失败的窗口，精确复发率为 UNKNOWN，同时报告保守区间：

因此“零复发”只在没有 invalid/unknown 缺口、且已监控窗口和签名范围明确时成立。无效窗口不是绿色，也不能从分母中静默删除。

13.8 Action item 指标

跟踪到期完成率、逾期风险、验证失败、重新打开和与复发的关联。简单关闭率容易鼓励拆小票或无证据关闭。高风险 action item 要求独立验证和生产控制证据。

13.9 不迷信平均事故时长

事故时长通常偏斜，少数大事故占据大量影响。报告中位数、分位数、按严重度和类型分层，并保留个案影响。Google SRE 的官方 incident metrics 资料也提醒，在事故数量较少且分布复杂时，简单均值可能不适合趋势决策。本文不复制其模拟结果，只采用“不要让单一均值替代上下文”的方法边界。

十四、证据保全：保存当时世界，而不是事后重新解释

14.1 必要对象

Nova 构造事故固定：

  • 发布包 manifest、组件摘要、批准与流量计划；
  • 模型部署可得版本、Prompt、Parser、参数；
  • 知识 snapshot、ACL 摘要、摄取水位、索引别名；
  • 工具 Schema、适配器版本、幂等键摘要、队列状态；
  • 策略 bundle、特征版本、人工批准；
  • 路由规则、cohort 分配、缓存版本与实际回显；
  • 审计事件、业务流水、用户结果和对账报告；
  • 告警、战情决策、沟通版本和时间线；
  • 已知缺口、迟到、采样与时钟质量。

14.2 最小化和访问

保全不等于把所有用户对话贴到战情频道。每个对象标明目的、分类、访问者、保留和冻结范围。能用事件 ID、摘要、字段化金额和构造复现替代原文时不复制原文。必须查看原文时使用受控工作区和审批，访问本身审计。

14.3 易失证据顺序

优先固定会快速变化的路由分桶、队列水位、缓存、供应商 response ID、临时配置和在途状态；随后固定不可变发布对象。操作前记录快照，避免排障命令改变状态后失去原貌。不要执行危险的广泛清理来“恢复”，再发现无法对账。

14.4 证据缺口

模型供应商可能不提供精确 revision，Trace 可能采样，用户结果可能异步迟到。缺口写成：缺什么、为何缺、影响哪些结论、有什么替代证据、是否能补。不能用推断值填入观察列。

十五、沟通：固定事实、未知、动作和下一更新时间

15.1 内部战情更新模板

文章正文是中文，模板保留英文只是展示固定字段；真实组织可本地化。每次更新有版本和作者，修改历史可追踪。

15.2 不提前宣布根因

可以说“当前三个 case 都命中 legacy branch”，不能在未复现时说“根因是路由”。可以说“工具写已关闭”，不能说“影响已停止”，除非目标业务流水证明没有新的提交。事实和结论的时态要准确。

15.3 分层受众

响应团队需要操作细节；管理层需要影响、风险、决策和资源；客服需要可执行话术和受影响用户识别；用户需要清晰影响、当前状态、可行替代和后续安排；法务、隐私、安全与监管沟通由有授权角色按适用范围决定。不要把内部未经证实假设复制到外部更新。

15.4 固定更新节奏

即使没有新事实，也按严重度约定节奏更新“无变化、仍在做什么、下一检查点”。这减少重复询问和旁路决策。节奏是构造策略，不同组织可以调整。

十七、复盘：还原系统如何允许事故，而不是寻找一个犯错的人

17.1 复盘触发

构造规则要求：SEV-0/1、真实资金/权限/数据影响、显著近失或可跨系统学习的事故必须复盘。低等级重复事件也可触发问题复盘。触发标准公开，避免只对显眼团队追责。

17.2 复盘最小结构

  1. 摘要：用户影响、范围、时长与当前状态；
  2. 时间线：当时可见事实、决策和角色；
  3. 检测：为何在第三笔才发现，哪些信号缺失；
  4. 响应：哪些止损有效，哪些操作增加认知负担；
  5. 技术分析：触发组合、反事实、直接原因和促成条件；
  6. 恢复：回滚兼容、验证门禁和历史对账；
  7. 沟通：受众、节奏、误解和改进；
  8. 做得好的与偶然幸运：不要把幸运写成控制；
  9. Action item：owner、到期、风险、完成证据；
  10. 评测与监控回灌：最小化、分割、变体和复发签名；
  11. 未解决问题和证据限制。

17.3 五问不能替代因果证据

可以连续追问为什么，但每一层要有证据或标为假设。复杂系统可能有并行条件，不必强行收敛到单根。Nova 的触发图是：

17.4 做得好与幸运

“三笔后对账告警”是已有控制；“恰好没有大额上万元订单命中”是幸运。复盘把幸运转为 action item，例如把金额错误设置为每笔硬门和实时流式对账，而不是庆祝影响小。

17.5 无责不等于无责任

Google SRE 的官方 postmortem 资料强调开放、无责地从失败学习，并跟踪 action item。本文采用系统学习取向：参与者基于当时信息和工具行动；同时，owner 仍对修复、期限和验证负责。故意违规、恶意行为或组织纪律问题有独立流程，不应通过技术复盘隐瞒，也不应让其阻断系统改进。

十九、从事故证据到评测资产：五层隔离

19.1 原始事故证据层

包含受控日志、对话、业务流水和版本，只为调查、修复和批准目的使用。访问严格，保留按适用规则。它不是默认训练数据池，也不是评测文件目录。

19.2 最小场景抽象层

质量团队提取失效机制：

删除姓名、订单号、真实文本和无关业务细节，替换成构造实体。金额可以保留能触发单位问题的构造值。抽象过程保存 source incident ID 的受限血缘，但评测运行者不需要原文访问。

19.3 候选 case 审批层

检查：目的与权限、敏感信息、版权/合同、真值、最小化、可执行性、owner、失效机制、适用切片和过期规则。真值由业务和工程至少双人复核。不能因为来自事故就假设标签正确。

19.4 Held-out 回归层

事故核心机制和预注册变体进入只读回归集，ID 与内容摘要登记。模型开发和 Prompt 优化只看到失败类别或汇总，不默认看到全部答案。最终发布评测在隔离流水线运行。

19.5 训练/开发层

若组织决定生成训练样本，应从场景模板另行构造，经过数据治理并与 held-out case 去重。训练集可以包含同类概念，但不能包含回归 case 的精确内容、答案泄漏、唯一 canary 或可逆改写。开发集和最终回归集目的不同。

二十、污染控制：不仅查字符串重复

20.1 污染路径

  • 事故原文进入微调或检索知识库；
  • 回归问题和答案贴到 Prompt 仓库、工单或模型 memory；
  • 评测 judge 使用了同一事故答案模板；
  • 合成器对 held-out case 只做轻微改写后放入训练；
  • 工程师手工针对 case ID 写特判；
  • 线上缓存或会话把评测答案带入后续运行；
  • 第三方模型供应商将提交内容用于训练，取决于实际合同与配置。

20.2 登记与隔离

为每个 case 保存规范化摘要、语义家族、来源、split、允许用途和 lineage。训练构建前对 exact hash、规范化文本、实体替换模板、n-gram/近似和语义候选做扫描；发现候选后人工判定。没有任何单一相似度阈值能证明无污染。

20.3 Canary 不是秘密答案

可以在 held-out case 中加入不影响任务语义的唯一标记，检测训练或日志泄漏。但标记本身要受控，不能出现在开发报告；模型未输出 canary 也不能证明没有语义记忆。Canary 是一条信号。

20.4 变体设计

Nova 的回归家族至少包括：

  • CNY、JPY 等小数位不同货币，但真值按货币规则生成；
  • 8、800、800.05、上限边界和四舍五入；
  • 新 Prompt 配旧 adapter、旧 Prompt 配新 adapter、未知字段；
  • sticky 与非 sticky、缓存刷新前后；
  • HTTP 200 但业务金额错、HTTP 超时但业务已提交；
  • 重试两次但幂等只提交一次；
  • 高额需审批、低额自动、缺审批默认拒绝；
  • 多语言表达改变但结构化金额真值不变。

变体不是越多越好。每个变体对应失效机理、预期关系和独立 oracle，避免生成一堆同义句制造虚假覆盖。

20.5 回灌不能代替生产监控

离线回归证明已知场景在固定条件下通过。路由、缓存、在途队列和目标系统状态只能在线验证，因此 action item 还要增加 unknown bundle exposure、金额对账、unknown outcome age 和 fallback reason 监控。学习闭环必须同时修改评测、发布门禁、运行监控和 runbook。

二十四、完整离线实现：事故状态机、兼容回滚与污染门禁

下面的 Python 构造示例只使用标准库，在内存中运行，不访问网络、不调用模型、不读取 API Key、不执行系统命令，也不会产生真实工具副作用。它实现：

  • Signal 到 Incident 的显式声明，以及由 HMAC 构造证据目录、可信角色、来源/目标状态和单调时间共同约束的语义状态门；
  • 同时考虑确认影响、规模、速度、不可逆性、权利影响和未知范围的构造严重度硬门；
  • Observation、Hypothesis、RootCause 与 Decision 分离；
  • 工具 kill switch、凭据撤销和队列暂停；
  • 模型、Prompt、知识、工具、策略、路由发布包兼容检查，以及绑定精确组件清单的批准评测；
  • 由外部可信 attempt manifest 固定分母，并校验对象、收款方、币种 allowlist、正数金额范围、幂等键和回执唯一性的恢复门禁；
  • 服务端规范化窗口摘要，以及跨窗口 Attempt Group、幂等键、回执和评测运行 ID 的重放阻断；
  • 证据最小化与 canary secret 拦截；
  • action item 的证据目录与授权独立验证；
  • 事故场景最小化、登记后完整性复核和 held-out/train 精确污染阻断；
  • 消费监控 authority 证据、把 invalid window 纳入 unknown 分母并报告上下界的复发监控。

24.1 为什么状态机允许从 CLOSED 回到 TRIAGING

关闭是基于当时范围的决策，不是抹除事实。若同一影响窗口发现漏掉的副作用，组织可以先重开分诊、补充 Signal，再重新声明和定级；若是新的独立暴露，也可创建关联事故。生产系统要记录重开原因、严重度和新时间线，不能覆盖原关闭证据。

示例中的 TransitionEvidence 只携带 catalog digest。IncidentRecord 解析可信快照后验证 actor role、事故 scope、精确来源/目标状态、证据 authority 和时间单调性；CLOSED 还要求三窗恢复、对账、补偿、通知决定与独立风险批准五类对象同时成立。保存进 history 的是完整 snapshot 与集合摘要，伪造 ID、任意非空说明、自报布尔值、倒退时间和未授权角色都不能推进状态。

24.2 为什么恢复门禁不以 HTTP 为输入

RefundOutcome 保存 HTTP 只是证据字段，business gate 故意不把 200 作为成功 oracle。外部签发且摘要锚定的 attempt manifest 固定 eligible 分母；清单本身先拒绝空白或非规范资源/收款方/幂等标识、非 allowlist 币种、非正数或越界金额、重复 Attempt/幂等键/预期回执。每条结果再同时匹配这些真值、目标回执和用户可见终态，并且无未授权、恰好一次提交。遗漏失败结果会先让 reconciliation coverage 失败，HTTP 不能替代任何领域后置条件。

24.3 为什么零安全失败仍可能不通过

当 safety_total=0 时，safety_failed=0 只是没有运行测试，不是零风险。示例要求最小样本。实际低频高风险场景还应结合主动 canary、形式化策略检查、历史曝光和更长观察窗。

24.4 为什么污染控制只称“精确碰撞阻断”

示例 registry 在登记时深拷贝规范化结构并保存真值摘要，后续登记或统计前重新核验已登记内容；原地修改会被拒绝，完全相同 case 也不能跨 split。轻微改写、实体替换和语义等价仍需要更复杂的候选检索与人工复核；标准库例子没有假装解决语义污染。正文要求把 exact、near-duplicate、模板和语义血缘分层检查。

24.5 为什么三个绿色窗口不能来自重放

RecoveryTracker 不再信任调用方提供的 evidence_digest，而是从完整窗口对象规范化计算摘要和去掉展示性 window/time 字段的重放指纹。它同时拒绝重复 window ID、时间倒序、时间重叠、cohort 变化，以及跨窗口复用的 Attempt Group、业务幂等键、目标回执和质量/安全评测运行 ID。路由门也按每个 eligible attempt 核对 bundle ID 与完整 manifest digest，而不是把一个成功回显写成 1/1。因此仅更换 window ID 或时间外壳不能制造“连续恢复”。

24.6 教学摘要仍不是生产签名和身份系统

TrustedEvidenceCatalog 的 HMAC secret、注入的 actor_roles、AttemptManifest.signed_by、批准评测的 signature、授权 verifier 集合和 SHA-256 都是构造信任边界。测试代码能够调用 issue() 是为了生成夹具，不代表业务调用者拥有签发权限。生产实现必须把 issue/resolve 权限分离，并从 IAM、KMS/HSM、签名时间戳、撤销状态和不可变证据服务取得这些事实；actor_roles 也必须是服务端 IAM 快照，不能来自请求正文。示例只演示消费可信快照后的门禁语义，不声称 HMAC 内存目录等价于生产身份系统。

二十七、不能证明什么：给关闭报告加一页限制

27.1 “没有复发”只对监控签名和窗口成立

若 30 个可信有效窗口没有 amount-unit-schema-mismatch，且不存在 invalid/unknown 缺口，可以说该签名在这些窗口未观察到，不能说所有金额错误永不复发。只要存在一个无效窗口，精确值就保持 UNKNOWN 并报告上下界，不能删除该窗口后宣布零复发。新币种、不同工具、供应商变更和用户行为仍可能产生未知变体。

27.2 “根因已验证”只对构造反事实成立

复现和反事实支持 adapter fallback 是本次直接原因，但不能证明组织不存在其他潜在单位错误。根因结论受证据完整性、实验环境和版本可复现性限制。

27.3 “影响全集已对账”依赖事实源完整

路由曝光、工具日志和目标业务流水可能共享缺口。报告应列出每个事实源覆盖、迟到和时间边界。若第三方只保留部分流水，影响上界仍有未知。

27.4 “回归通过”不证明生产状态安全

离线 case 没有真实缓存、队列、区域配额和供应商漂移。它支持发布包在测试条件下满足 oracle；在线 canary、业务对账和策略硬门仍必须存在。

27.5 “无精确污染”不等于无语义污染

摘要 registry 只能证明没有精确重复。模型可能看过等价模板、答案或事故概念，尤其使用外部模型时训练语料不可完全观察。报告要说明能检查的本地 lineage 与未知供应链边界。

27.6 “无责复盘”不证明行动项会完成

文化与文档无法替代资源、owner、优先级和验证。action item 逾期、风险接受和复发应进入治理节奏。

二十八、执行清单

28.1 事故前准备

  • 模型、Prompt、知识、工具、策略和路由以不可变发布包登记。
  • 发布包包含结构、语义、状态、数据、行为和容量兼容 manifest。
  • 高风险工具有模型外 kill switch、短期凭据、幂等键和只读对账。
  • 业务后置条件 SLI 与 HTTP/Schema 指标分离。
  • 人工降级路径有容量、优先级、等待 SLO 和用户话术。
  • 事故严重度、声明角色、IC/OL/CL/Evidence 职责和升级路径已批准。
  • 证据访问、最小化、冻结、保留和导出流程已演练。
  • 已知好包定期验证，不使用漂移 latest 作为唯一回滚点。

28.2 检测与声明

  • Signal 保存用户症状、业务不变量、证据、范围和时间。
  • 告警可操作，包含 runbook、owner 和用户影响语义。
  • 事故声明是显式决策，允许 cause 为 UNKNOWN。
  • 严重度硬门覆盖未授权副作用、资金、数据、权利和不可逆影响。
  • 范围未知和扩散速度不会被低已确认数量平均掉。
  • 合并或拆分多个告警有记录，不只按时间自动聚类。

28.3 观测与证据语言

  • Observation 引用可复核 evidence ID、来源和限制。
  • Hypothesis 有 proposed/supported/refuted/inconclusive 状态。
  • Root cause 至少有安全复现、版本对照或反事实证据。
  • Decision 记录可见事实、未知、选项、预期效果、abort 和复核时间。
  • 战情频道不把推断写成已确认事实。
  • 用户原文与秘密不会因排障复制到低权限渠道。

28.4 隔离与止损

  • 先阻断高风险副作用，再做精细根因分析。
  • 策略 kill switch、凭据撤销、队列暂停和路由隔离是独立控制。
  • 在途任务使用明确状态，UNKNOWN 不自动重试。
  • 目标系统按幂等键对账，补偿不覆盖原流水。
  • 人工路径的容量与二次伤害纳入监控。
  • 证据保全不要求故障组件继续影响真实用户。
  • containment 生效后仍有新增提交会立即重开止损分析。

28.5 回滚

  • 候选包每个组件有固定版本、摘要和批准评测证据。
  • 模型能力、地区、上下文和供应商 revision 可验证。
  • Prompt 变量、输出 Schema、工具名、单位、Parser 和策略兼容。
  • 知识回滚检查 ACL、删除、时效、Schema 和引用。
  • 工具回滚前盘点在途、队列格式、幂等和目标合同。
  • 策略回滚不复活失效规则，缺特征高风险默认拒绝。
  • 路由检查黏性会话、缓存、异步任务、区域和容量。
  • 无法证明兼容时使用整包、转换、排空或隔离，不强行拼接。
  • 回滚有 canary、扩流级别、abort 条件和再次 kill switch。

28.6 恢复

  • 明确 technical stable、impact stopped、reconciled 和 closed 的不同含义。
  • 用户任务成功按受影响 cohort 测量，放弃和超时进入分母。
  • 业务 gate 验证金额、币种、对象、终态、幂等和 exactly-once。
  • 可信 attempt manifest 拒绝空对象/收款方/币种/幂等、非正数或越界金额和重复回执。
  • 金额匹配与 reconciliation coverage 并列报告。
  • AI 质量包含故障 case、邻接正常 case 和风险切片。
  • 安全策略硬门、知识 ACL 和地域约束通过。
  • 审计阶段 coverage、bundle 回显、Attempt 与时钟质量通过。
  • 容量、人工队列、延迟、配额和成本可持续。
  • 零分母和过小样本为 UNKNOWN/FAIL，不算绿。
  • 连续观察窗通过，任一硬门失败回到止损或回滚。

28.7 沟通与影响处置

  • 更新固定 status、confirmed、scope、unknown、actions、workaround、next update。
  • 外部沟通不包含未经证实根因或无授权敏感细节。
  • 即使无新事实也按节奏更新。
  • 暴露、受影响、未提交、未知和未暴露有可审计分类。
  • 补偿使用差额和新幂等键，提交前再次对账其他渠道。
  • 服务恢复、用户处置、通知和补偿分别有 owner 与状态。

28.8 复盘与 action item

  • 时间线记录当时可见信息，不用事后知识重写决策背景。
  • 直接原因、促成条件、检测缺口、响应和沟通都分析。
  • 做得好与偶然幸运分开。
  • 无责语言具体描述系统条件，不回避事实。
  • Action item 对应风险，有 owner、due、acceptance、证据和独立验证。
  • 临时缓解、永久修复和风险接受分开跟踪。
  • 逾期、重开和复发进入治理，而不是只统计关票率。

28.9 评测回灌与污染

  • 原始事故证据与训练、开发、held-out 存储和权限分离。
  • 场景通过 allowlist 最小化，不复制真实用户、订单和对话。
  • 业务 owner 复核真值，AI 质量 owner 复核可执行 oracle。
  • Case 登记 source incident、failure family、split、摘要、用途和过期。
  • 训练前查 exact、near-duplicate、模板和语义候选。
  • Held-out 答案不进入 Prompt、工单、检索知识或模型 memory。
  • 事故核心机制配有金额、币种、Schema、路由、超时和幂等变体。
  • 回灌同时产生发布门禁、生产监控和 runbook 改进。
  • 评测报告明确无法证明外部模型训练语料完全无污染。

28.10 复发监控与演练

  • 直接失效签名和邻接风险都有分母、阈值、owner 和 runbook。
  • 监控窗口有效性来自可信证据；无流量或数据无效进入 unknown 分母和上下界，不能静默删除。
  • 临时高灵敏度监控有复核和退役决定。
  • Tabletop 分批给证据，测试未知下的决策，不提前公布根因。
  • 技术演练使用隔离目标，不制造真实业务副作用。
  • 演练覆盖误报、错误初始假设、回滚不可用、知识 ACL 和污染阻断。
  • 演练发现的流程/控制问题进入 action item 并验证关闭。

三十、结语：回滚的是发布包，恢复的是用户与业务事实

AI 事故最容易出现两种假确定性：第一种是看到模型或 HTTP 指标变绿，就宣布恢复；第二种是找到一个看似合理的技术原因，就把事故学习压成一条回归题。

更可靠的闭环是：

回滚成功不是“旧版本正在运行”，而是受影响路径确实收敛到兼容包，新增伤害停止，历史副作用被对账，业务后置条件持续满足，证据边界被诚实声明。复盘成功也不是“文档已经发布”，而是具体风险通过可验证 action item、评测资产和复发监控真正下降。
