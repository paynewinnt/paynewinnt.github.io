AI测试-60-AI审计日志怎么设计留存脱敏访问控制和证据导出

发表于 2026-06-15 分类于 AI测试 本文字数： 31k 阅读时长 ≈ 1:51

一次 AI 助手调用返回了正确答案，应用日志里也有一行 request completed，这能不能证明：谁在什么身份下请求了什么、系统使用了哪版模型和策略、模型提出过哪些动作、工具最终执行了什么、敏感字段没有泄露、记录没有被改过，并且六个月后仍能把证据完整导出？

不能。

普通运行日志主要服务于诊断，审计事件服务于责任界定和控制验证，证据包则服务于一个明确调查问题。三者可以共享采集设施，却不能因为都叫“日志”就混成同一份自由文本。200 OK 可能发生在工具提交失败之后；同一个 Trace 可能包含模型重试、工具重试和人工批准；一个看似完整的 Prompt 原文可能恰恰违反目的限制；一条连续哈希链也只能说明链内已记录对象的某些变化能够被发现，不能证明生产者当时说的是真话，更不能证明本应产生却没有产生的事件。

因此，AI 审计能力真正要回答的是：

本文资料边界截至 2026-06-15（含）。全文的组织、系统、用户、账号、事件、阈值、时间线、性能数字和事故均是构造示例，只用于展示测试方法，不代表任何真实机构、法规结论或线上事故。法律部分只讨论工程如何表达适用性、依据、目的、期限、冻结和删除；具体义务取决于司法辖区、主体角色、行业、合同与案件状态，应由有授权的法务和隐私职能确认。

一、边界：审计日志不是“把所有东西永久保存”

1.1 本文测什么

本文把被测对象分为六层：

层 被测对象 关键问题
事件契约 event type、schema、identity、version 同一事实能否被稳定解释和去重
源端保护 字段分级、最小化、脱敏、秘密拦截 不必要或禁止的数据是否在离开进程前被移除
采集关联 Trace、Span、Attempt、时钟、序列 多次尝试与最终结果是否被正确关联
证据存储 追加写、分区、检查点、保留、冻结、删除 记录何时可查、何时必须保留、何时必须删除
访问与导出 身份、目的、审批、break-glass、manifest 谁能看到哪些字段，导出是否可复核且不越权
测量与响应 coverage、迟到、重复、链断、泄漏、恢复 控制失效能否被发现、阻断、调查和修复

1.2 本文不证明什么

即使本文所有测试通过，也不能自动推出以下结论：

  • 不能证明每个事件的业务陈述真实。被攻陷的生产者可以把假值按合法 Schema 写入一条完整哈希链。
  • 不能证明日志是“完整世界模型”。覆盖率只对已经定义并能获得分母的事件机会成立。
  • 不能证明某个访问或保留策略在所有地区合法。控制实现正确不等于法律适用性判断正确。
  • 不能证明 Token、假名或摘要永远无法被关联。可链接性取决于密钥、映射表、辅助数据与攻击者能力。
  • 不能证明删除后任何物理痕迹都不存在。备份、缓存、搜索索引、导出副本和下游系统必须分别纳入删除证明。
  • 不能用一条日志替代模型评测、业务后置条件和人工证据。审计记录描述发生了什么，不负责证明决定本身合理。
  • 不能把“存得更多”当成“更可审计”。过度记录会扩大泄露面、访问面、成本和错误解释空间。

这组否定边界很重要。审计系统最危险的失败，不只是“没有日志”，还包括用一个看似权威的证据包制造超出证据范围的确定性。

二、先把四类记录分开

2.1 运行日志

运行日志用于排障和容量管理，例如超时、队列深度、缓存命中、解析异常。它可以有采样，可以按工程需要改变文本，也可以在较短时间后滚动删除。运行日志里的 user=alice prompt=... 并不会因为方便排障就自动成为合格审计事件。

2.2 审计事件

审计事件描述一个治理上有意义的状态变化或决定，例如：

  • 身份 service:assistant-gateway 代表用户 usr_tok_8... 请求读取资源 contract/C-204；
  • 策略 access-policy@17 作出 DENY，理由码为 REGION_SCOPE_MISMATCH；
  • 模型尝试 attempt-03 提出调用 payment.release，但执行策略拒绝；
  • 调查员经批准读取某个事件集合，结果中高敏字段按 mask-v4 掩码；
  • 一个法律冻结被创建、缩小、复核、解除；
  • 一个到期分区完成删除，删除证明引用对象摘要而不保留对象内容。

审计事件应是结构化、版本化、可枚举的事实陈述。自由文本可以作为受限补充，但不能承载唯一关键语义。

2.3 证据对象

证据对象是被审计事件引用的外部对象，例如经过授权保存的策略快照、模型清单、审批票据、工具响应摘要或加密内容对象。事件里通常保存对象 ID、版本、摘要、分类和存储域，而不是把整段原文复制进每条日志。

2.4 证据包

证据包是针对一个问题构造的有限导出。例如“案件 CASE-2048 中，2026-06-08 09:00 至 09:20 是否有未授权付款提交”。它至少包含查询范围、事件文件、对象文件、manifest、每个对象摘要、链检查点、Schema 与解释器版本、脱敏配置、生成者、审批依据、已知缺口和验证说明。

证据包不是数据库的 ZIP 备份，更不是把管理员当前能看到的一切打包出去。导出动作本身也是一次受控处理，必须再次产生日志。

三、八个常见误判与反例

3.1 “有 request ID，就能串起全链路”

反例：网关收到一次请求，模型因超时重试三次，第三次提出工具动作；工具代理又因网络不确定重试两次，其中第一次其实已提交。所有记录共用同一个 request_id，调查者无法区分哪一次模型输出对应哪一次工具提交。

正确做法是同时保留稳定的业务交互 ID、分布式 Trace ID、每一段 Span ID、模型 Attempt ID、工具 Attempt ID，以及它们的父子关系。稳定 ID 用于“这是同一件事”，Attempt 用于“这是第几次尝试”，幂等键用于“这些尝试是否应该只产生一次副作用”。

3.2 “记录完整 Prompt 最容易审计”

反例：Prompt 包含用户身份证号、未公开合同、访问令牌和检索文档原文。一次调查只需要证明策略版本和决策输入类别，却导出了全部原文。结果是审计系统本身成为高价值泄露源。

可审计性来自恰当字段、版本、摘要、引用和受控证据对象，不来自无限复制。若某类案件确需原文，应独立定义目的、加密域、访问审批和更短保留期限；默认路径只记录足够的摘要与分类元数据。

3.3 “哈希链通过，所以日志真实完整”

反例一：生产者在事件生成前就把 decision=DENY 伪造成 ALLOW，之后按顺序正确计算哈希。链完全通过，内容仍然是假的。

反例二：采集器在一天结束前漏掉一整段事件，然后从当前头重新开始新链；如果没有受信任的外部检查点、预期序号和覆盖率分母，链内依然连续。

反例三：攻击者删除整个未锚定分区以及关于该分区存在过的目录。仅靠分区内部哈希无法发现。

所以，哈希链是完整性控制的一部分。它擅长发现链内记录被改、重排、插入或删除造成的连续性变化；它不证明采集真实性、业务正确性或全局完整性。检查点应被独立锚定，覆盖率应从业务事实源建立分母，高风险决定应有多源对账。

3.4 “去重就是按 Trace ID 留一条”

反例：同一个 Trace 中的三个模型尝试是三个不同事件；两个采集器重复发送同一个事件才是重复。按 Trace 去重会丢掉合法尝试，按整行文本去重又会因 observed time 不同保留重复副本。

去重键应是源端生成、在重传中保持不变的 event_id，并辅以生产者序号和内容摘要检测“同 ID 不同内容”。Attempt ID 解决尝试区分，不承担事件去重。

3.5 “日志时间排序就是事实顺序”

反例：工具节点时钟快 90 秒，采集器因队列积压晚到 8 分钟。按 occurred_at 排序会把工具执行放在批准之前，按 observed_at 排序又会把迟到的策略拒绝放到结果之后。

应同时保留源事件时间和首次观察时间，并记录时钟质量、单调序号、父事件和因果关系。没有可靠时钟时，结论应降级为部分顺序，而不是伪造精确时间线。

3.6 “break-glass 就是临时管理员权限”

反例：值班人员以紧急为由获得全库查询，导出与事故无关的用户原文，权限一周后才回收，事后也没有复核。

break-glass 应缩短某些审批等待，不应取消身份认证、目的限制、字段掩码、范围约束、期限、通知和事后复核。它必须有明确事件影响、资源范围、最长 TTL 和自动撤销，并由独立人员复核使用记录。

3.7 “法律冻结等于永久保留全部日志”

反例：一个案件只涉及 30 个主体和两天范围，系统却冻结所有租户的全量 Prompt，且没有复核日期。冻结扩大了隐私风险，也使到期删除长期失效。

冻结必须引用有权确认的依据，限定主体、资源、事件类型、日期和证据对象，记录开始、到期或复核时间。冻结暂停匹配范围内的删除，不会自动扩大访问目的，也不重置未冻结记录的保留时钟。

3.8 “导出成功且文件能打开，所以证据完整”

反例：导出任务只拿到两个分区中的一个；对象存储里有三份引用文档缺失；脱敏器版本没有记录；manifest 是导出完成后人工补写，文件摘要也未覆盖。压缩包能打开，却无法知道缺了什么。

合格导出必须对预期分区、查询条件、事件数量、对象数量、缺失项、策略版本和每个文件摘要作出机器可检验的声明。无法获取的对象应进入 gaps，不能静默忽略。

四、贯穿构造场景：付款审查助手 Aster

本文使用一个完全虚构的采购付款审查助手 Aster。所有账号、金额、日期和阈值均为构造示例。

Aster 接收采购人员提交的发票，检索合同与验收记录，调用模型生成付款建议，再由策略引擎决定是否允许调用 payment.release。高于 500,000 元或供应商银行账户刚变更的付款，需要两名不同审批人。工具具有真实副作用，因此每个提交必须带业务幂等键。

构造事件 interaction-8042 的正常事实链是：

  1. 用户 U-017 通过企业身份系统登录，代表业务部门提交资源 invoice/INV-2048；
  2. 网关创建 trace_id=T-8042，在源端把用户 ID 假名化为租户域 Token；
  3. 第一次模型尝试因超时结束，未提出工具动作；
  4. 第二次模型尝试引用合同 C-77@v12，提出释放 620,000 元；
  5. 策略 payment-policy@31 因金额和账户变更作出 REQUIRE_DUAL_APPROVAL；
  6. 第一名审批人批准，第二名审批人拒绝，最终决定为 DENY；
  7. 工具代理收到拒绝结果，没有开始调用付款系统；
  8. 证据账本保存结构化事件、策略与合同版本摘要，不保存银行账号原文、访问令牌或合同全文。

后续构造事故中，采集器错误地丢失了第二名审批人的拒绝事件，查询界面只看到第一名批准。与此同时，一个管理员为排障临时关闭了字段拦截，导致 17 条事件的自由文本中出现银行账号尾部之外的更多数字。本文将用这个场景测试覆盖度、秘密扫描、哈希边界、break-glass、冻结、删除和证据导出。

4.1 审计问题先于字段设计

团队先列出必须回答的问题：

  • 谁以什么认证强度代表哪个主体发起交互？
  • 被访问或变更的是哪个资源的哪个版本？
  • 模型每次尝试看到哪组证据摘要、使用哪版 Prompt 和模型？
  • 工具动作是被提出、被授权、执行器开始、目标接受，还是业务提交成功？
  • 哪个策略版本基于哪些可记录输入作出什么决定？
  • 人工审批是否满足人数、职责分离、顺序和有效期？
  • 记录是否迟到、重复、冲突或缺失？
  • 谁因什么目的查询、解密或导出了哪些字段？
  • 哪条保留规则适用，是否被合法冻结，最终如何删除？

如果一个字段不能支持已批准问题、控制或后置条件，就不应因为“以后可能有用”直接进入审计事件。反过来，如果一个问题必须回答，却没有稳定分母、身份或版本字段，增加存储时长也补不回来。

五、威胁模型：审计系统也处在攻击面内

5.1 需要覆盖的角色

角色 合法能力 主要风险
业务用户 发起 AI 交互、查看自己的结果 否认动作、诱导日志写入秘密、越权查询他人资源

5.2 假设与不可信边界

构造系统假设身份提供方、策略仓库和外部检查点服务分别受控，但不假设它们永不失陷。生产服务到采集器的网络可能重试、断开和乱序；源节点时钟可能偏移；管理员可能拥有基础设施权限；模型输出完全不可信；用户输入可能专门包含形似日志字段、换行、控制字符和秘密。

必须测试的攻击或失效包括：

  • 删除、插入、重排或修改链内事件；
  • 把同一 event_id 以不同内容重放；
  • 生成新的合法哈希链以替换尚未外部锚定的分区；
  • 整个生产者停止发事件，但采集器自身仍健康；
  • 用 Prompt 注入伪造 decision=ALLOW 文本混入日志查看器；
  • 通过高基数字段或自由文本绕过字段分级；
  • 在 Token 域间复用同一假名，造成不必要跨目的关联；
  • 利用 break-glass 查询无关主体；
  • 用无限法律冻结逃避删除；
  • 只删除主存而保留索引、缓存和导出副本；
  • 在证据导出后替换文件但不更新 manifest。

六、参考架构：在源端减数据，在证据边界加声明

6.1 业务事实源

审计事件应尽量在事实首次成立的位置产生。策略引擎记录自己的决定，工具代理记录执行器是否开始，目标系统记录是否接受和提交，审批系统记录审批动作。让网关事后根据一行响应猜测所有阶段，会把观察变成推断。

高风险动作采用多源对账：AI 侧记录 tool.proposed、策略侧记录 action.authorized、工具侧记录 executor.started、目标侧记录 business.committed。缺任一阶段都应表现为未知或未完成，不能把后续阶段反推成前序证据。

6.2 源端最小化与隔离

字段分类器在事件离开进程前执行。已知禁止字段直接拒绝；允许假名化的身份在本地完成；自由文本经过结构化提取、长度限制和秘密模式扫描。处理失败的事件进入受限隔离通道，只保存最少错误元数据，不能退化成“原样写入以免丢日志”。

隔离通道也不能成为原文垃圾桶。它只应保存事件 ID、Schema 版本、生产者、错误码、字段路径、内容摘要和受限恢复引用。真正需要人工查看的原对象进入独立审批域。

6.3 关联与质量校验

采集层执行 Schema、枚举、时间格式、事件 ID、生产者序号、父引用和字段策略校验。校验失败要计入分母并告警；不能因为坏记录未进入主账本，就把主账本的“有效率”报告成 100%。

occurred_at 表示源端认为事件发生的时间，observed_at 表示采集器首次看到事件的时间。两者都保留，才可区分源时钟问题和传输迟到。OpenTelemetry Logs Data Model 也区分 Timestamp 与 ObservedTimestamp；本文借用这种语义，不声称本文自定义审计 Schema 就等同于 OpenTelemetry 的规范格式。

6.4 追加式证据账本

账本按租户、风险域和时间分区，使用确定性序列化计算事件摘要，并把前一个摘要纳入当前记录。周期性检查点写入权限独立的锚定域。追加写存储、防覆盖权限、对象版本和检查点一起降低静默修改风险。

这里的关键不是“区块链”标签，而是可验证属性：谁能追加、谁能删除、能否覆盖、序号是否连续、检查点何时产生、锚点是否独立、恢复后如何证明版本，以及控制失败是否报警。

6.5 查询与导出

查询代理先评估访问目的、案件、角色、主体范围、时间范围、字段级权限和结果上限，再生成短时授权。结果集在服务端脱敏，查询条件、命中数量、返回数量和导出对象摘要被再次审计。调查员不能直接获得底层对象存储全读权限。

导出器以冻结的查询计划工作。它先声明预期分区和对象，再获取内容，最后生成 manifest 和完整性报告。任何缺失都进入 gaps；是否允许交付由案件策略决定，而不是导出器把缺失项吞掉。

七、事件数据模型：一个决定不是一行 message

7.1 顶层信封

建议的最小顶层结构如下：

event_type + schema_version 决定解释方式。生产者版本用于发现某次部署改变了发事件行为。classification 是整条记录的最高分类提示，不能代替字段级策略。顶层不提供万能 details 让任意对象穿透，否则所有契约最终都会退化成不可治理 JSON。

7.2 event identity

event_id 表示一个已声明事实的唯一事件实例，应在源端首次创建时生成，重传保持不变。它必须满足：

  • 同一事件重试发送仍使用同一 ID；
  • 不同模型尝试、不同审批动作、不同工具阶段使用不同 ID；
  • 接收端遇到相同 ID 和相同规范化内容时可幂等确认；
  • 相同 ID 却内容摘要不同属于冲突，必须隔离和报警；
  • 不把包含 PII 的业务键直接编码到 ID；
  • ID 的唯一性不被解释为事件内容真实。

自增序号可帮助检测生产者局部缺口，但不能单独作为全局 ID。服务重启、分片切换和灾备恢复必须定义序号 epoch。随机 ID 可降低碰撞，却无法显示缺口，因此通常同时保存生产者序号。

7.3 actor、subject、resource、action

这四个概念必须分开：

字段 含义 Aster 构造示例 常见错误
actor 实际发起或执行动作的身份 service:assistant-gateway 只写最终用户名，丢失服务代理
subject 动作代表或影响的主体 user-token:U-017、供应商 Token 把受影响供应商误写成 actor
resource 被读取、判断或变更的对象 invoice/INV-2048@v7 只有 URL，没有稳定资源版本
action 企图或已经发生的动作 payment.release:proposed 用 called=true 混淆提出与提交

代理链应显式表达：用户授权前端，前端调用 AI 网关，AI 网关代表本次交互调用策略与工具。记录 actor.type、假名 ID、认证上下文摘要、delegation chain 和服务工作负载身份。不要把一个可编辑的显示名当身份主键。

subject 可能有多个，例如付款同时影响采购部门、供应商和批准人。只有与审计目的有关且有合法依据的主体才进入事件；不能为了以后画像把所有可推断关系都展开。

7.4 policy 与 decision

一个可复核决定至少包含：

不要只记自然语言“高风险，需审批”。原因码必须稳定、可枚举，显示文本可以本地化。input_digest 对规范化后的允许字段计算，用来确认复算输入是否一致；如果原输入按策略不能保存，摘要只能证明后来提供的同一对象与摘要匹配，不能恢复内容，也不能证明原对象合法。

策略版本必须对应不可变快照。仅记录 latest 或 Git 分支名会让六个月后的复算使用不同内容。策略编译器、规则数据和特征定义也要有版本，避免“文件没变但解释器变了”。

八、Trace 与 Attempt：相关不等于相同

8.1 四种关联 ID

ID 生命周期 目的
interaction_id 一次用户可感知业务交互 把异步和跨 Trace 的业务过程归为同一件事
trace_id 一次分布式调用链 与 W3C Trace Context 和遥测关联
span_id Trace 中一个操作段 表示父子调用和局部时间
attempt_id 某模型、工具或导出步骤的一次尝试 区分重试、超时后不确定和最终采用结果

W3C Trace Context 规定 traceparent 和可选 tracestate 的传播格式与处理规则。它解决跨系统追踪上下文互操作，不定义 AI 审计语义，也不应承载个人数据、授权决定或秘密。tracestate 不是把任意业务身份传播给所有下游的容器。

8.2 模型 Attempt

每次模型调用保存独立 Attempt：模型供应商/部署 Token、模型版本或可获得标识、Prompt 模板版本、参数、输入证据集合摘要、开始/结束状态、Token 用量、输出对象摘要、停止原因和错误类。对不允许保存的 Prompt/输出原文只保存受控对象引用。

最终采用哪一次输出必须由单独事件声明。不能根据“最后一条模型日志”推断，因为异步迟到会改变展示顺序。未采用的尝试仍可能包含安全事件或成本事实，保留规则可与采用结果不同。

8.3 工具 Attempt 与不确定提交

工具动作至少拆成：

网络超时后，调用方不知道目标是否提交，状态必须是 unknown，随后用幂等键向目标对账。把超时直接记成 failed 可能诱发重复付款；把 HTTP 200 直接记成 committed 又可能忽略业务异步失败。

8.4 sampled Trace 不能决定审计采集

分布式追踪可以采样，关键审计事件通常不能随 Trace sampling 一起丢弃。TraceFlags 中 sampled 位描述追踪采样决定，不代表审计事件是否必须保留。正确实现允许未采样 Trace 仍产生必要审计事件，并保存 Trace ID 以供关联；不能把“没有 Span”解释成“业务没发生”。

九、时间、顺序、迟到与重复

9.1 双时间模型

对有两个时间戳的记录定义：

若源时钟可信且 delivery_delay 超阈值，可标记迟到。如果结果显著为负，应优先标记 CLOCK_SKEW_SUSPECTED，不能把负迟到当成“超快传输”。时钟可信度来自同步状态、偏移测量和节点元数据，而不是时间字符串有 Z。

9.2 因果顺序优先于墙钟总序

父事件、生产者序号、Trace 父子和状态机约束共同提供部分顺序。例如 business.committed 必须引用一个已存在或最终可解析的 executor.started，审批事件不能引用未来才创建的请求。跨系统墙钟只用于辅助时间窗，不应覆盖明确因果边。

9.3 重复与冲突

定义三种情况：

  • duplicate_same：同一 event ID、规范化载荷摘要相同，属于重传；
  • duplicate_conflict：同一 event ID、载荷摘要不同，属于高风险冲突；
  • semantic_repeat：不同 event ID 表述相同业务动作，是否重复取决于幂等键和状态机。

接收端可幂等丢弃 duplicate_same 的第二份存储，但必须计数；duplicate_conflict 进入隔离且阻断相关证据导出；semantic_repeat 不能只靠日志系统自动删除，否则可能掩盖真实重复副作用。

十、字段分级：先决定能否记录，再决定如何保护

10.1 字段级分类表

等级 构造字段 默认处理 典型访问
PUBLIC event type、公开 Schema 版本 可记录 平台运维
INTERNAL 服务版本、非敏感 reason code 明文结构化 工程与审计角色
CONFIDENTIAL 租户、资源 Token、策略输入摘要 假名化、加密存储 案件范围内调查员
RESTRICTED 直接身份映射、原文证据、银行账号 独立对象域、字段级授权 双人批准、短时访问
SECRET API Key、访问 Token、私钥、会话 Cookie 禁止进入日志 不存在日志访问路径

分类必须落实到字段路径和事件版本，而不是在 Wiki 写一句“日志可能含敏感信息”。Schema 注册表保存 purpose、classification、transform、retention_class、allowed_roles 和 export_policy。新增字段默认拒绝或进入严格等级，不能默认继承最低分类。

10.2 最小化与目的限制

对每个字段执行四问：

  1. 它支持哪个已批准审计问题或控制？
  2. 不保存它会失去什么可验证能力？
  3. 能否用枚举、布尔、桶、摘要或受控引用代替原值？
  4. 谁在多长时间内需要访问，何时必须删除？

例如调查只需判断金额是否跨过双审批阈值，可以记录 amount_band=GT_500K 和策略输入摘要，而不是全量金额。但财务对账可能依法或按合同需要准确金额，此时应在该适用范围的证据对象中保存，并与通用 AI 运行日志分离。最小化不是一律删字段，而是让精度、目的、保留和访问相匹配。

10.3 数据主体和业务资源不是同一分类轴

一个资源 ID 可能不直接识别人，却可与租户内部目录组合后关联个人；一个错误堆栈可能意外包含 Prompt；一个模型输出摘要本身不含原文，却能用于字典攻击验证候选文本。分类要考虑辅助数据和威胁模型，不能只靠字段名正则。

十一、tokenization、pseudonymization 与 redaction 不能混称匿名化

11.1 Redaction

Redaction 删除或掩盖值，例如只保留银行账号后四位。它适合展示和导出，但被掩码版本是否足够唯一、是否仍可与其他数据关联，需要单独评估。****1234 不是自动匿名。

11.2 Pseudonymization

假名化用受控转换把直接标识替换为稳定 Token，使同一目的域内可以关联事件。本文构造实现使用 HMAC 作为确定性假名演示：

密钥按租户、目的和轮换 epoch 分域，避免跨目的全局关联。HMAC 密钥保存在密钥系统，不写入日志。假名化数据仍可能是个人信息；掌握映射或辅助数据的一方可能重新关联，因此不能宣称匿名化。

标识规范化必须由具体命名空间声明。不能对所有身份一律转小写，否则会错误合并大小写敏感 ID；本文构造代码只去除首尾空白，并用测试固定大小写仍然可区分。

11.3 Tokenization

Tokenization 通常把原值替换为随机或格式保持 Token，并在受限 Token vault 保存映射。它便于撤销和精细解 Token，但 vault 成为高价值系统。审计事件只保存 Token 与 vault domain，不保存映射。查询者即使能读账本，也不应自动有 de-tokenize 权限。

11.4 不可逆摘要的边界

对低熵值直接做无盐 SHA-256 不等于安全假名化。手机号、邮箱、员工号等候选空间可枚举，攻击者能离线比对。需要稳定关联时使用有密钥的 PRF/HMAC；不需要关联时应删除或随机化。摘要轮换还要定义旧新 epoch 的关联窗口，避免为了迁移永久保留全局映射。

11.5 自由文本的最后一道闸

模型输出和错误 message 不接受“调用方已脱敏”的信任。源端应执行：长度上限、控制字符处理、秘密模式检测、结构化 allowlist、注入字符转义和高熵 Token 检测。检测不是完美 DLP，因此高风险事件默认只存对象摘要和类型化结果，原文走独立证据对象路径。

十二、密钥与原文不落日志

以下内容应列入不可覆盖的禁止规则：

  • API Key、OAuth access/refresh token、session cookie、Authorization header；
  • 私钥、数据库连接凭据、云临时凭据、Token vault 映射；
  • 未经批准的完整 Prompt、模型输出、检索文档和工具响应；
  • 支付卡安全码、认证秘密和可直接重放的签名材料；
  • 为了“证明加密”而记录的明文加密密钥或完整 KMS 响应。

秘密扫描失败时，生产请求是否继续与审计事件是否入账是两个决定。可以让业务按风险策略继续，同时把审计事件隔离并告警；也可以对高风险工具动作执行 fail-closed。无论哪种，都不能在异常处理里 logger.exception(payload) 把原文重新泄露。

要专项测试异常路径：序列化失败、超长字段、下游 500、重试耗尽和 DLP 自身崩溃。秘密最常从错误日志、调试开关和 fallback formatter 泄露，而不是设计好的正常事件。

十三、不可变与追加证据：定义可发现的篡改，而不是许愿

13.1 确定性序列化

同一个逻辑事件必须在不同验证端得到同一字节序列。JSON 需要固定字符编码、键排序、数字表达、时间格式和缺省字段规则。更稳妥的做法是规定规范格式或使用有明确 canonicalization 的编码。本文离线示例采用 json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False) 作为构造约定，不把它宣称为跨语言通用标准。

计算摘要前要排除哪些派生字段也必须固定。例如 record_hash 本身不进入 payload，observed_at 若由接收端添加，就要决定它属于受保护记录还是外层接收信封。修改规则后应升级 ledger format version，不能让旧验证器悄悄用新算法。

13.3 检查点和独立锚

检查点至少按风险确定频率。高风险工具动作可以分钟级或事件数级锚定，低风险读操作可以更宽。锚定目标应与账本写权限分离，例如独立安全域的对象版本、签名服务或外部透明记录。锚服务不只“签当前头”：它还要保存已签的 partition + record_count + head_hash，新检查点必须严格向前，且旧 record_count 处的头仍等于历史承诺。攻击者重算旧历史再提交一个“新 checkpoint”时，签名域应以 equivocation 拒绝，而不是帮它覆盖旧锚。

证据包中的 ledger-proof.json 携带到受信检查点为止的链承诺。离线验证器从 genesis 重算序号、前序摘要和记录摘要，再将链头与独立签名检查点比较；每个导出事件还要引用该链证明中的 sequence、payload digest 和 record hash。缺证明、证明头不匹配或检查点不在独立信任库中都不能验证为完整。本文不限定某个产品，也不把“WORM”名称当作已验证能力。

检查点签名能把验证绑定到持有签名密钥的身份，但仍不能证明生产事件真实。签名密钥被盗、签名服务接受恶意头、锚定策略停用，都可能生成“密码学有效但业务错误”的检查点。因此签名验证、密钥状态、锚定覆盖率和业务覆盖率是不同指标。

十四、访问控制：能查日志的人不应天然能看原文

14.1 授权输入

每次查询或导出至少评估：

角色只是授权输入之一。AUDITOR 不意味着能跨租户浏览所有 Prompt；同一调查员处理案件 A，不自动能读取案件 B。目的、案件、主体和时间构成属性约束，字段级策略决定返回明文、假名、掩码还是拒绝。

14.2 审批和职责分离

构造策略规定：普通低敏查询可由值班调查员在已分配案件内执行；受限原文揭示需要数据所有者，以及隐私或安全审批人两名不同身份；全量导出还需证据保管人批准。申请人不能批准自己的申请，服务账号不能扮演人工批准人，同一人的两个角色也不算两人。批准人姓名不能直接来自请求参数：授权服务必须从可信身份目录解析有效状态、角色和认证上下文，再用案件分配记录确认谁是该案件的数据所有者、调查员与独立复核人。两个任意字符串、两个存在但未分配的账号，或者只有全局角色却没有案件职责的账号都必须拒绝。

审批不是请求中的 approvers=["owner-c", "privacy-b"]。可用的审批收据由独立审批服务在受信认证上下文中签发，绑定 decision、approver、role、request ID、完整 scope digest、签发时间和到期时间。授权服务必须从审批服务 introspection 获取“未撤销且仍在有效窗”的收据，再重做申请人不能自批、两个不同身份和职责分离检查。调用者自己构造 dataclass、填两个姓名或计算 SHA-256 都不会进入该服务的收据注册表。

签发的 grant 也由该可信服务持有与签名，并绑定申请人、目的、案件、租户、事件类型、最高字段分类、到期、允许的导出时间窗、字段 allowlist，以及独立业务事实源生成的 expected-event manifest ID、digest 和全部事件 ID。导出器每次向服务 introspect grant，不接受只有 grant_id 或自计算 scope digest 的对象。调用者可缩短时间、减少事件类型或字段，不能向十年前扩展、加入 private_note，也不能通过少选 expected ID 把 coverage 分母从 100 变成 1。

14.3 break-glass 状态机

一个可测试状态机是：

激活前仍要通过强认证，并由可信 IAM 确认请求者具有预授权的 on-call/incident-responder 角色，且被分配到一个仍处于有效状态的事故。事故记录绑定案件、租户、允许事件类型、事件指挥和通知对象；激活需要事件指挥批准，并向数据所有者和安全值班发送可审计通知。仅提交非空 incident_id 不是有效控制，匿名用户、弱认证账号、未分配值班人员和伪造审批人都必须拒绝。

事件指挥的决定同样不是一个 approved_by 字符串。审批服务签发绑定全部 break-glass scope 的收据，通知服务为每个政策要求的接收者签发 delivery receipt；只有指挥收据有效、通知集合完全匹配时才能签发会话。会话令牌绑定请求者、事故、案件、租户、事件类型、最高分类、批准收据、通知收据和短 TTL，并由服务端注册表持有。查询代理每次 introspect 会话与关联收据，再检查撤销/到期、实时身份状态和当次查询范围；改一个租户或换一个批准人即使重算普通 SHA-256 也无法成为服务端会话。权限自动到期，不依赖人工记得回收。

测试不只验证“能打开”。还要注入时钟推进、撤销、身份禁用、范围扩大和审批服务不可用，确认过期后访问被拒、缓存 Token 不能延长权限、查询代理失败时不回退到底层共享账号。

14.4 审计审计系统

至少记录以下元事件：Schema 发布、字段分类变化、保留规则变化、访问策略变化、检查点失败、查询、字段揭示、导出、冻结、冻结解除、删除、恢复和管理员权限变化。元事件进入权限独立的控制账本，避免管理员先改策略再删访问痕迹。

但递归不能无限。需要明确根信任边界，例如平台控制面事件写入独立安全域并周期外部锚定，由不同团队监控。任何根边界都仍有残余风险，应在威胁模型中声明。

十五、留存、法律冻结与删除：一个状态机，不是一列天数

15.1 保留规则是带适用条件的版本化对象

不要在代码中写一个全局 retention_days=365。保留决策输入至少包括：

  • 司法辖区与组织角色；
  • 事件类型和数据分类；
  • 处理目的与业务/安全需要；
  • 主体、租户、合同和行业范围；
  • 记录创建时间与业务关闭时间；
  • 是否存在有效冻结；
  • 来源法规、合同、政策和批准版本；
  • 热存、冷存、索引、备份和导出副本的分别期限。

规则输出 retention_class、到期计算基点、热/冷转换、删除方式、复核日期和依据引用。系统保存当时采用的规则版本，后续规则变化通过迁移计划处理，不能静默重算所有历史记录。

15.2 法规原文只给约束，不替组织生成统一天数

《中华人民共和国个人信息保护法》第十九条规定，除法律、行政法规另有规定外，个人信息保存期限应为实现处理目的所必要的最短时间。这不是“所有日志保存 N 天”的数字答案，而是要求把目的、必要性和例外依据落实到规则。

欧盟 GDPR 第 5 条的 storage limitation 原则同样要求，个人数据以可识别数据主体的形式保存不超过处理目的所需时间，并对为公共利益归档、科研或统计等情形设有条件。具体能否适用、哪些主体权利或限制生效、法律请求如何处理，取决于适用法和事实。工程系统应记录批准的法律判断结果及范围，不自行推导法律结论。

NIST SP 800-92 是日志管理指导，NIST SP 800-53 AU 控制族包含事件类型、记录内容、容量、失败响应、时间戳、保护、保留和生成等控制。它们可帮助设计控制，但不是对所有私营组织直接设定统一法定期限的法规。文章中的任何构造期限都不得被复制为合规结论。

15.5 删除与追加账本的张力

追加写不等于永不删除。常见实现把账本按保留类和时间分区，对分区加密并在到期后删除对象与密钥，保留不含原文的最小 tombstone。若同一链跨越不同保留义务，删除中间记录会破坏验证，因此分区边界必须在设计时与保留类对齐。

删除证明可以包含：分区 ID、原对象摘要、记录数、适用规则版本、删除任务、执行时间、各副本结果和验证者。它证明系统执行并观察到规定删除步骤，不是物理世界“任何副本绝不存在”的绝对证明。搜索索引、缓存、灾备、离线导出和调查工作副本需要各自确认。

15.6 冻结优先级与失败模式

删除工作流在提交前和执行前各检查一次冻结，避免检查后新建或解除冻结的竞态。DeletionPlan 必须由保留引擎签发并保存在服务端计划仓库，绑定 plan ID、object ID、rule version、计划时间、hold state digest 和当时 blocker 快照。执行器首先按 plan ID 取服务端原件并验签，请求中的对象必须与原件完全相等；然后它从当前冻结库重算 active hold IDs 和状态摘要，不读调用者自报的 blocking_hold_ids。因此把 blocker 改成空数组会被当作伪造计划，冻结状态变化则返回 PLAN_STALE。若冻结服务不可用，高风险删除应 fail-closed 并报警；但长期 fail-closed 也会违反删除要求，所以要有恢复 SLO、积压监控和授权降级流程。

故障注入包括：冻结在删除计划后创建、范围解析器返回空、时区边界、规则版本缺失、冷存恢复失败、密钥删除成功但对象删除失败、索引删除成功但主对象失败。最终状态不能只看一个 API 的 200。

十六、证据导出：manifest 既描述内容，也描述未知

16.1 导出工作流

一个可复核流程是：

  1. 导出器先 introspect 可信服务持有的 grant，从其中读取已批准的案件、租户、最大时间窗、事件类型、最高分类、字段 allowlist 和外部 expected-event manifest；
  2. 生成不可变 ExportScope：时间、事件类型和字段只能缩小，expected IDs 必须与可信 manifest 完全相等，不允许缩小 coverage 分母；
  3. 对每条候选记录在服务端重新校验案件、时间、租户、事件类型和分类，只允许同时“在 scope 内且位于 expected ID 白名单”的记录进入输出；
  4. 从独立锚服务验证签名 checkpoint，用它检查当前账本，并生成可离线重算到该链头的 ledger-proof.json；
  5. 在导出服务端按固定 profile 生成脱敏副本，并为每条导出记录绑定 source sequence、payload digest 与 record hash；
  6. 生成 manifest、完整性报告和 coverage 报告，对每个文件计算摘要；预期项缺失、越界、链证明失配或输出出现多余项时，完整性门禁失败；
  7. 将 manifest 摘要提交到包外独立信任域形成锚，再由独立验证器重算 checkpoint 信任、链证明、manifest、文件、实际事件集和 coverage；
  8. 验证器自行计算 complete = gaps 为空 且 expected = declared = actual 且 report 一致，不相信 manifest 的布尔值；
  9. 将导出交付、下载、过期和销毁再次审计。

16.2 manifest 最小字段

manifest 自身也计算摘要，并由组织批准的包外信任域签名或锚定。锚不能只作为同一个压缩包里的另一份可替换文件；验证器必须从独立通道取得可信 manifest 摘要、签名者、密钥标识和验证链。若没有外部锚，只能报告 UNKNOWN，不能因为文件与包内 manifest 自洽就返回成功。签名和证书链验证细节应使用成熟密码库与密钥服务；本文标准库示例以包外 HMAC 夹具固定“替换文件并重算 manifest 仍失败”这一行为，不提供生产数字签名实现。

16.3 完整性、真实性、完整覆盖是三个问题

  • 文件完整性：交付后文件字节是否与 manifest 摘要一致；
  • 账本连续性：导出的链段是否与受信任检查点一致；
  • 来源真实性：事件是否由声称生产者在当时产生，需身份、签名或受控通道等证据；
  • 业务真实性：事件陈述是否符合目标事实，需多源对账和业务证据；
  • 覆盖完整性：所有应产生的事件是否存在，需外部分母。

把这几项都写成 integrity=true 会误导。尤其是“文件摘要与同包 manifest 一致”只证明包内自洽，manifest 与文件可以被一起替换；只有再匹配独立信任域中的锚，才能把这次验证连接到受信任版本。同样，complete=true 不是证据；验证器必须从可信 expected manifest、实际 NDJSON、declared IDs、gaps 和 verification report 重算。任何 unresolved gap、重复 ID、集合不等或报告分母不一致都应使完整性失败，即使攻击者之后又为篡改过的 manifest 获得了一个新包锚。导出报告应逐项给出 PASS/FAIL/UNKNOWN/NOT_APPLICABLE、验证方法、范围和缺口。

十七、指标：没有分母的“日志量正常”不是覆盖率

17.1 Schema 有效率

分母包括进入校验入口的有效、无效和隔离记录，不包括根本没发出的事件。因此它只能说明“收到的记录有多少合约有效”，不能说明业务事件覆盖。

17.2 业务事件 coverage

对每个有独立事实源的机会建立预期键：

Aster 的双审批分母来自审批工作流已创建的两个 approval slot，而不是账本中出现了几条审批事件。若 slot 2 的拒绝事件丢失，则 coverage 为 1/2，不能因为现有一条记录 Schema 有效而报告 100%。预期源自身的可用性也要报告；分母未知时 coverage 是 UNKNOWN，不是 1。

17.3 决策证据完整率

required_stage_keys 由策略结果决定。例如 REQUIRE_DUAL_APPROVAL 必须有两个不同批准 slot 的终态和最终合并决定；DENY 且未调用工具不要求 business.committed。分母是已进入终态的合格决定，未终态流程另报 age 与 stuck rate，不能从分母删除后制造好看结果。

17.4 重复率和冲突率

重传频繁可能是采集不稳定；冲突即使只有一条也应高优先级。分母不要用最终去重后记录数，否则重复率会失真。

17.5 迟到率与时钟异常率

无时间戳、时钟不可信和真正迟到分开。只对可信时钟计算迟到，且同时报告排除比例。否则把所有坏时钟排掉会让 late rate 看似优秀。

17.6 Trace 与 Attempt 关联完整率

eligible attempts 是模型和工具实际开始的尝试。未采样 Trace 不要求 Span 已导出，但仍要求合法 Trace ID 和审计父关系。孤儿事件、循环父引用和跨租户引用分别计数。

17.7 秘密泄漏逃逸率

真实秘密分母通常不可完全知道，不能声称“扫描零命中所以泄漏率为零”。可维护两个指标：

前者测已知故障注入召回，后者分母受抽样与报告偏差影响。生产门禁还应规定任何确认的 SECRET 落日志为硬失败。

17.8 访问与 break-glass 指标

拒绝数量高可能是攻击，也可能是策略或 UI 配置错误，不能直接等价为安全变差。break-glass 使用次数也不是越低越好；关键是必要性、范围、TTL、复核和结果。

17.9 留存与删除指标

分母排除“有效且匹配”的冻结，不排除冻结状态未知。未知应阻断删除并计入治理告警。各副本注册表不完整时，删除完成率只能对已登记副本成立，报告要声明这个边界。

17.10 导出指标

有未解决 gap 的证据包是否允许作为“不完整材料”交付由案件规则决定，但完整性门禁必须失败，UI 必须醒目标记，API 不能仍返回 complete=true。事件文件只能包含冻结 scope 中授权且 expected 的交集；越界记录不能因为“有助调查”被顺手打包。验证器失败时不允许“先交付后补摘要”。

十八、自动化门禁：把契约、隐私、连续性和可恢复性分开测

18.1 Schema CI

每个事件版本提交时执行：必填字段、枚举、向后/向前兼容、未知字段策略、示例解析、最大长度、高基数预算和字段分类覆盖。破坏性变化使用新主版本，并有双写、读取兼容和退役时间窗。

Schema 测试还要验证语义，不只是 JSON 类型。例如 decision=DENY 不得同时有 authorized=true；span_id 存在时必须有 trace_id；business.committed 必须有幂等键和目标凭证摘要；SECRET 字段永远不在 allowlist。

18.2 隐私 CI

构造包含 API Key、JWT 形状、Cookie、银行账号、邮箱、换行注入、Unicode 同形字符和超长 Prompt 的事件。断言秘密不出现在主账本、隔离元数据、异常日志和导出包。对假名化断言同域稳定、跨域不相等、密钥不出现在对象中；对 redaction 断言边界字符和嵌套数组同样处理。

正则测试必须有误报样本，避免把普通 UUID 全部当秘密导致业务静默关闭日志。失败策略按风险定义：禁止字段硬拒绝，未知自由文本可隔离，非敏感格式错误可丢弃但计入 coverage 缺口。

18.3 账本与恢复 CI

注入单条修改、删除、插入、重排、重复、相同 ID 不同内容、检查点过期、锚服务不可用和灾备恢复。额外必测“篡改旧记录并重算全链，然后请求新 checkpoint”：链内验证可以继续为绿，但独立锚域必须因历史前缀与旧锚冲突而拒绝。离线验证器还要重算 ledger-proof.json 并将每个导出 event 的 source commitment 与证明对齐。

还要做“合法伪造”反例：创建一条内容虚假的事件，按正确算法追加，断言链验证通过。这不是让测试接受假事实，而是固定系统边界，防止产品文档误称哈希链能证明来源真实。

18.4 访问与导出 CI

使用角色、租户、目的、案件、字段级别和时间范围生成组合。验证申请人自批、任意字符串审批、伪造/撤销 grant、角色存在但案件未分配、过期授权和缓存 Token。break-glass 还要覆盖伪造 commander receipt、伪造或缺失 notification receipt、会话改写、关联批准撤销和过期。导出器必测十年前时间扩展、未批准字段、expected 分母缩小、跨租户和额外事件。导出包需注入字节改写、删文件、多事件、链证明改写、重算包内 manifest，以及“加 unresolved gap 但保留 complete=true 并重新锚定 manifest”；验证器都要根据自行重算的事实失败。

18.5 留存演练

用可控时钟推进 HOT→COLD→DELETE_DUE→DELETED，期间创建、缩小、解除冻结。验证同一 hold version 不能覆盖，解除者必须具备可信角色并提交授权、证据和原因。DeletionPlan 还要注入未登记 plan ID、签名改写、object 替换和“将 blocker 改为空”，执行器必须拒绝；冻结状态变化则使服务端旧计划返回 PLAN_STALE。删除覆盖主对象、索引、缓存与登记副本，删除证明不泄露原内容。

二十、完整离线实现：审计账本、访问、保留与导出

下面是一个只使用 Python 标准库的构造示例。它不连接网络、不调用模型、不读取环境密钥、不执行系统命令，也不实现生产级 KMS、WORM 或数字签名。代码的目的，是把关键语义做成可运行断言：

  • 事件 ID 的幂等重传与冲突载荷必须分开；
  • actor 原始标识经按租户和目的分域的 HMAC 假名化；
  • 禁止字段或 canary secret 在源端被拒绝；
  • 哈希链能发现链内修改，但一条内容虚假的合法事件仍可通过链验证；
  • coverage 使用外部预期事件键作为分母；
  • 迟到和时钟异常分别计算；
  • 普通受限访问使用可信审批服务签发的 scope-bound receipt 与 grant，导出前每次 introspect 注册、签名、时效和撤销状态；
  • break-glass 要求可信 commander 批准收据和完整的通知 delivery receipts，并签发可 introspect、绑定全部范围和 TTL 的服务端会话；
  • 法律冻结不可覆盖，删除计划由服务端签发并持有，执行时重算 active holds，伪造 blocker 不能绕过；
  • ExportScope 的最大时间、字段 allowlist 与 expected-event manifest 来自批准 grant，调用者只能缩窄，不能扩大或缩小 coverage 分母；
  • 账本 checkpoint 由独立信任域签发并保存历史承诺，证据包内的链证明可重算到受信链头；
  • manifest 验证必须接收包外可信锚，并从 gaps、expected、actual 和 report 重算 complete。

20.1 代码为何故意保留“虚假但链合法”的测试

很多演示只测试改一条记录后哈希失败，于是读者容易把“tamper-evident”扩大成“truth-evident”。test_valid_chain_cannot_prove_a_producer_statement_is_true 固定了能力边界：构造的 ALLOW 事实并没有外部依据，但因为它从一开始就按合法格式写入，链验证应当通过。真正的业务真实性要靠生产者身份、多源对账、批准记录和目标系统事实。

20.2 为什么示例没有生产级数字签名

Python 标准库没有提供适合本文直接拼装的现代非对称签名方案与证书生命周期。FixtureApprovalService、FixtureLedgerAnchorTrustDomain 和 FixtureManifestTrustDomain 分别用不同 HMAC 域与服务端注册表模拟审批签发、账本检查点锚定和包 manifest 锚定。这些 key 只是单进程离线测试夹具：不提供第三方可验证性，也不证明真实服务已完成密钥分域。生产实现应采用组织批准的密码库、硬件或云密钥服务，将审批 API 认证、签名权限、验证信任库和证据存储分域，明确 audience、算法、密钥用途、轮换、吊销、时间戳和验证链。

20.3 为什么保留引擎只删除“已登记副本”

软件无法删除它不知道的副本。示例用 copies 注册表强调删除证明的范围：主对象、索引和备份都显示 DELETED，但这仍只证明构造注册表里的步骤。生产系统需要资产发现、导出副本 TTL、缓存策略和下游处理者协议；报告必须说“对已登记副本完成”，不能写“所有地方绝对不存在”。

20.4 构造 IAM 与会话令牌的能力边界

TrustedIdentityRegistry 是测试夹具，不是生产身份系统。它用内存中的 active、role、case assignment 和 incident assignment 让授权条件可运行，并没有实现目录同步、账号生命周期、设备信任、MFA 证明或撤权传播。代码中 issue_access_approval、issue_break_glass_approval 和 record_notification 的方法调用代表“已通过受信服务 API 认证的内部 RPC”，不代表生产端可接受普通业务请求传入的姓名。真实实现必须在服务边界校验批准人的会话、强认证、CSRF/重放防护和当次操作意图。测试通过只说明本文列出的反例被拒绝，不能据此宣称身份基础设施已达到生产强度。

20.5 链证明和脱敏副本之间还剩什么边界

ledger-proof.json 证明某个 event ID 与原始 payload digest 位于到受信 checkpoint 为止的链中；source_integrity 将导出事件指向该承诺。但因为导出文件已经脱敏，离线验证者没有原始 payload，不能仅凭 digest 重做每一个脱敏转换。若案件要求第三方重演 redaction，需在更受限的验证环境提供原对象、固定 redaction 工具与可验证执行证明。本例只声明链归属、服务端导出和包完整性，不把它扩大成“任何验证者都已独立复现脱敏”。

二十一、完整构造事故：链是绿的，证据仍然缺了一块

21.1 事故前状态

Aster 的审批系统承诺：每个高额付款请求创建两个 approval slot；每个 slot 必须产生一个终态事件，状态为 APPROVED、REJECTED 或 EXPIRED。审计平台从审批数据库的 slot 表建立 coverage 分母。事件通过两个采集器发送到追加账本，每五分钟生成检查点。

21.3 为什么哈希链没有在 09:20 报错

拒绝事件是在进入账本之前被 Schema 校验隔离的。链只覆盖实际追加的事件，因此剩余记录的序号、前序摘要和检查点都一致。链变绿是符合设计的，不能把它当成事故检测失败。真正发现缺口的是：审批 slot 的外部分母为 2，而账本只匹配 1。

如果团队没有 slot 表，只监控“每分钟日志条数”和“链验证率”，本次缺失很可能被正常流量噪声掩盖。这说明 coverage 要按业务义务建模，不能从日志自身反推分母。

21.4 如何保全证据而不继续扩散原文

响应团队没有把 17 条运行日志复制到普通工单。它执行以下构造控制：

  1. 对原运行日志对象按对象 ID 和时间范围创建冻结，保存对象摘要；
  2. 停止普通搜索索引继续摄取该字段，索引副本进入同一冻结范围；
  3. 由两名不同批准人授权受限证据查看，在隔离环境生成掩码副本；
  4. 原对象只在受限域可见，工单保存事件 ID、摘要、分类和影响计数；
  5. 所有查看与导出产生元审计事件，并绑定 INC-AUDIT-17；
  6. 对 fallback 配置、Schema 版本、部署制品和检查点生成只读快照；
  7. 向法务/隐私职能提交适用性事实，由有权角色决定通知和保留范围。

冻结依据、通知义务和后续期限不能由工程文章直接给结论。构造系统只保证这些决定能以版本化对象进入工作流。

推断 同一 fallback 路径可能影响该部署窗口内所有校验失败事件 需要查询部署和错误分母

决策 停用 fallback、冻结范围、轮换暴露账号相关凭据、通知评估 由事件指挥和授权职能记录

“17 条确认”不自动等于“总共只有 17 条”。团队又检查所有生产者收到的事件数、隔离队列、运行日志对象、搜索索引和导出历史，直到各来源分母可对账。无法验证的离线副本进入限制声明。

21.6 恢复门禁

不能因为新版本开始写日志就结束事故。构造恢复条件是：

  • 新旧生产者兼容矩阵通过，隔离积压为零；
  • 受影响业务事件 coverage 对等待窗后达到预注册阈值；
  • canary secret 在正常、异常、重试和 fallback 路径均为 100% 被阻断；
  • 新写分区链与外部检查点连续；
  • 访问策略、break-glass 到期和受限原文审批回归通过；
  • 运行日志主对象、索引和导出副本清单完成影响确认；
  • 法律冻结范围由授权角色复核；
  • 独立验证器能验证证据包，且 manifest 显示重放、迟到和历史缺口；
  • 连续两个观察窗没有同类 Schema 隔离异常。

“HTTP 正常”“链验证通过”“当前 DLP 零命中”都只是条件之一。

二十二、测试策略：从单事件到证据包灾备

22.1 单元层

  • 每个事件类型的必填、枚举、跨字段不变量；
  • actor/subject/resource/action 映射；
  • Attempt 与幂等键状态机；
  • 假名同域稳定、跨域隔离；
  • secret、控制字符、嵌套数组和异常 formatter；
  • 规范化序列化与摘要固定向量；
  • 审批 receipt 的签名、角色、案件、scope、时效、撤销与 grant introspection；
  • break-glass 的 commander receipt、通知 delivery receipt、会话注册、签名、scope、TTL 和撤销；
  • 保留规则边界、不可变冻结版本、服务端 deletion plan、当前 hold 重算和时区；
  • ExportScope 不得扩大时间/字段，也不得缩小 expected manifest 分母；
  • 独立 checkpoint 签名、历史前缀、链证明、manifest 文件集合及包外锚；
  • complete 从 gaps、expected、declared、actual 和 verification report 重算。

22.2 组件层

  • 生产者升级与旧采集器、旧生产者与新采集器兼容；
  • Collector 重试、背压、磁盘满、重启和检查点恢复；
  • 相同 event ID 的同载荷与冲突载荷；
  • 索引失败不影响主账本，但查询 freshness 明确降级；
  • KMS 或 Token vault 不可用时不回退明文；
  • 访问审批服务不可用时底层存储仍不可直读；
  • 导出中途失败后重试保持 export ID、授权 scope 与对象一致性；
  • 锚服务不可用时验证结果为 UNKNOWN，不能回退到只信包内 manifest。

22.3 端到端层

从一个构造高额付款开始，产生两次模型 Attempt、双审批、一拒绝、策略 DENY 和工具未开始。验证每个事实源的事件、父关系、版本、摘要、分类、coverage 分母、查询权限和证据包。然后分别删除其中一阶段，确认状态变为 INCOMPLETE/UNKNOWN，而不是自动推断。

22.4 灾备层

恢复账本对象、检查点、Schema、保留规则、Token epoch 元数据和访问策略。验证冷备重建后的每个分区头与独立锚一致，查询结果数量与原快照一致，冻结仍生效，已删除对象不被旧备份重新索引。灾备成功不能只看进程启动和 HTTP 200。

二十三、发布与运营清单

23.1 事件契约

  • 每个 event type 有 owner、schema version、目的、分母来源和保留类。
  • event ID 在源端生成，重传保持不变，同 ID 异载荷会隔离告警。
  • actor、subject、resource、action、policy、decision 分字段表达。
  • interaction、Trace、Span、Attempt 和幂等键的生命周期已文档化。
  • proposal、authorized、executor started、target accepted、business committed 不坍缩。
  • 原因码可枚举，策略与解释器都引用不可变版本。
  • Schema 破坏性变化有兼容窗口、双写或迁移方案。

23.2 隐私与秘密

  • 每个字段有 classification、purpose、transform、retention 和 export policy。
  • 新字段默认拒绝或严格分类，不默认进入自由 details。
  • API Key、Token、Cookie、私钥和认证材料有不可覆盖禁止规则。
  • Prompt、输出和检索原文默认使用受控对象引用，不复制到普通日志。
  • 假名密钥按租户、目的和 epoch 分域，密钥不落日志。
  • Token vault 读取与账本读取是不同权限。
  • 正常、异常、重试、超时和 fallback 路径均做秘密故障注入。
  • 产品文档不把 pseudonymization 或 redaction 宣称为匿名化。

23.3 完整性与覆盖

  • 规范化字节、域分隔、分区、序号和 genesis 定义固定。
  • 检查点频率按风险确定，锚定权限与账本写权限分离。
  • 锚服务拒绝与已锚历史前缀冲突的新 checkpoint，无法用重算全链覆盖旧头。
  • 证据包链证明可重算到受信 checkpoint，导出 event 与 source commitment 一一对齐。
  • 验证器能定位修改、删除、插入、重排和检查点不匹配。
  • 有测试明确证明“虚假内容也可进入合法链”。
  • coverage 分母来自独立业务事实源，未知分母不会记成 100%。
  • Schema 无效与隔离记录进入质量分母。
  • 重复同载荷、同 ID 冲突和业务重复副作用分别报告。
  • occurred、observed、时钟质量和迟到分别保存。

23.4 访问与 break-glass

  • 授权同时约束身份、目的、案件、租户、主体、时间、事件类型和字段。
  • 批准人来自可信 IAM，角色与案件分配同时有效；任意字符串和未分配全局角色会被拒绝。
  • 受限字段采用两类不同身份的可签名审批 receipt，grant 由可信服务持有且每次 introspect 签名、scope、撤销与有效期。
  • 查询代理服务端脱敏，调查员没有底层全读共享账号。
  • 查询、揭示、下载和导出本身产生审计事件。
  • break-glass 有强认证、预授权 responder、有效 incident assignment、commander 批准、最小范围、TTL、通知、自动撤销和复核。
  • break-glass 会话绑定可 introspect 的 commander 批准和每个必需通知收据，关联收据撤销后会话立即不可用。
  • break-glass 不默认解除 RESTRICTED 掩码或扩大导出权限。
  • 过期、撤销、跨租户、结果超限和缓存授权均有负向测试。

23.5 保留、冻结与删除

  • 保留期限不是全局常数，规则保存适用范围、依据、目的和版本。
  • 具体法律与合同判断由有授权职能确认，工程不自行解释成统一天数。
  • HOT、COLD、HOLD、DELETE_DUE、DELETED 的流转和访问行为可测试。
  • 冻结有 authority、范围、批准、review_at 和不可变版本；同一 hold/version 不能覆盖。
  • 解除追加 superseding 版本，并校验 actor 的解除角色、授权、证据、原因和时间。
  • 冻结只暂停匹配对象删除，不扩大访问，不重置原保留时钟。
  • deletion plan 由服务端签发并持有；执行时取原件、验签并重算 active holds，请求者无法清空 blocker。
  • 主对象、索引、缓存、备份和导出副本分别登记与验证。
  • tombstone 只保存必要证明，不保留已删原文。

23.6 导出与调查

  • 导出先 introspect grant；时间、事件类型和字段只能缩小，expected IDs 必须与可信 manifest 完全相等。
  • 只有同时满足授权 scope 和 expected ID 的记录进入包；范围外、缺失或多余事件触发失败。
  • 字段脱敏在导出服务端执行，调用者不能通过参数绕过 profile。
  • manifest 覆盖每个文件的路径、字节数、摘要和记录数。
  • gaps、重复、冲突、迟到、重放、链断和未知范围不会被静默忽略。
  • redaction profile、查询、审批快照、工具版本和检查点被固定。
  • 独立验证器必须接收包外可信 manifest 锚；缺锚为 UNKNOWN，修改一字节、删/加文件或重算包内 manifest 都会失败。
  • 验证器不信任 complete 布尔值；任何 gap、expected/declared/actual 不等或 verification report 分母不一致都会失败。
  • 导出声明哈希链不能证明采集事实真实，也不能证明未定义分母的完整性。
  • 交付副本有接收者、目的、到期、下载和销毁记录。

23.7 运行与事故

  • 采集停止、隔离增长、迟到、时钟、重复冲突、链断和锚定失败均有告警。
  • 高风险动作与目标系统按幂等键对账。
  • 告警 runbook 明确如何止损而不复制敏感原文。
  • 恢复门禁同时看 coverage、秘密阻断、链、访问和导出，不只看 HTTP。
  • 每个 action item 有 owner、到期、完成证据和复发监控。
  • 定期演练 break-glass、法律冻结、删除竞态、冷存恢复和证据包验证。

二十四、一手资料与适用边界

以下资料均在本文发布日期 2026-06-15 之前发布或形成对应固定版本。标准与框架提供控制语言和设计依据，不自动构成对任意组织的强制法律义务；法规是否适用及如何解释必须结合具体事实。

  1. NIST SP 800-92, Guide to Computer Security Log Management，2006 年 9 月最终版。用于日志管理基础设施、流程与组织实践边界；它不是逐产品实施手册，也不提供所有场景统一保留期限。
  2. NIST SP 800-53 Rev. 5, Security and Privacy Controls for Information Systems and Organizations，参照 AU（Audit and Accountability）控制族讨论事件、内容、容量、失败、时间、保护、保留与生成。控制需要按组织风险和适用基线裁剪。
  3. W3C Trace Context, Recommendation 23 November 2021。用于 traceparent、tracestate 与 Trace ID/parent ID 传播语义；它不定义审计授权、Attempt、个人身份或业务提交状态。
  4. OpenTelemetry Specification v1.55.0, Logs Data Model。固定到 v1.55.0，引用 Timestamp、ObservedTimestamp、TraceId、SpanId、Resource、Attributes 与 EventName 等逻辑字段。本文自定义审计事件不是 OpenTelemetry 合规声明。
  5. 《中华人民共和国个人信息保护法》原文，中国人大网，特别关注第十九条的最短必要保存期限原则。适用性、例外和具体期限由有权职能根据事实确认。
  6. Regulation (EU) 2016/679, Official Journal text on EUR-Lex，特别关注第 5 条的数据最小化、目的限制与 storage limitation 等原则，以及其他条款对权利、限制和安全的完整上下文。本文不提供欧盟法律意见。

二十五、结语：可信证据首先要诚实描述边界

AI 审计日志的质量，不取决于每天写入多少 TB，而取决于能否把一个治理问题拆成可区分的事件、身份、尝试、决定和结果；能否只保存完成该目的所需的数据；能否在重试、迟到、乱序、缺失和攻击下维持可解释状态；能否让访问、冻结、删除和导出都留下自身证据。

前两个问题可以较多借助摘要、链和检查点；后三个问题需要身份、多源证据、状态机和外部分母。把它们压成一个绿色 integrity=true，才是审计系统最需要避免的假确定性。
