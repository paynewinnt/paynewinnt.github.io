AI测试-62-AI编码助手怎么评测正确性安全性可维护性和开发收益

发表于 2026-06-19 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:12

一个 AI 编码助手用了 90 秒生成补丁，仓库里 436 个测试全部通过，静态扫描也没有报高危问题。这能否证明补丁正确、安全、可维护，并且确实提高了开发效率？

不能。

测试可能只覆盖旧行为，没有覆盖需求真正要求的新不变量；候选补丁可能在错误的 base commit 上生成，却被应用到了已经变化的工作树；助手可能为了让测试变绿而删掉断言、扩大 mock、把失败路径改成静默成功；代码没有直接包含秘密，却新增了来源不明的依赖；评审者最终花了 70 分钟拆掉看似聪明的抽象；“节省时间”的计时又可能只算生成过程，没有算上下文整理、等待、评审、返工、回滚和逃逸缺陷。

更关键的是，通过测试不证明代码正确。它只说明：在一个被记录的仓库状态、工具链、测试集合、输入数据和执行环境中，被实际运行的那些检查没有观察到失败。未表达的需求、不可达或未执行的路径、错误 oracle、真实并发、生产数据分布、依赖供应链和观察窗之后才暴露的缺陷，都不在这句话的证明范围内。

因此，评测 AI 编码助手不是比较“谁写得更像代码”，而是回答一组可以复核的问题：

本文资料边界截至 2026-06-19（含）。文中的组织、仓库、服务、人员、任务、代码、commit、摘要、密钥、依赖、缺陷、时间、样本量、比例、阈值和实验结果均为构造示例，不代表任何真实公司、项目、模型、供应商或线上数据。所有门槛只用于演示如何把判断写成可执行合同；实际值应由代码所有者、安全、质量、平台和业务风险负责人结合语言、系统关键度、法规、历史基线与可用样本共同批准。

一、先限定评测对象：评的是任务闭环，不是聊天窗口

1.1 最小评测单元

1.2 四个互相独立的问题

问题 主要证据 不能替代的证据
助手能否解决任务 目标行为、回归、负向和系统测试 代码风格分、生成解释、测试数量
候选能否安全进入评审 隔离执行、秘密扫描、危险能力和依赖审查 “模型受过安全训练”、普通单元测试
代码是否值得长期接管 变更范围、复杂度、API、可测试性、评审返工 当前一次运行成功
使用助手是否有净收益 成对任务的总周期、质量、返工与逃逸缺陷 token 数、接受率、生成时间

把四个问题压成一个 0 到 100 的“AI 编码质量分”会掩盖硬失败。一个补丁即使节省 40 分钟，只要引入秘密或越权依赖，就不能用效率加分抵消安全失败；一个结构优雅的补丁如果不满足任务合同，也不能因为可维护性高而发布。

1.3 本文流程不能证明什么

  • 不能证明未表达需求已经被满足。合同遗漏的业务规则不会因测试全绿自动出现。
  • 不能证明所有输入和调度都正确。有限样本只能支持声明范围内的结论。
  • 不能证明模型“理解”了仓库。结果评测关注可观测产物与过程边界，不推断内部认知。
  • 不能证明无漏洞。静态规则、依赖数据库和故障注入都有盲区与时效边界。
  • 不能证明补丁在所有部署组合中安全。运行时配置、数据、权限、基础设施和下游状态需要另行验证。
  • 不能证明一次实验结果适用于所有语言、团队、任务难度和助手版本。
  • 不能把公共 benchmark 分数直接当成本仓库收益。benchmark 的任务分布、环境、污染风险和完成定义可能不同。
  • 不能把“评审接受”当成永久正确；评审本身也有漏检、疲劳和上下文缺失。

二、十二种看似合理但会误导结论的方案

2.1 只统计代码补全接受率

接受一个补全只说明开发者当时把文本放进了编辑器。它可能随后被修改、回退，也可能只是注释或样板代码。分母还是“展示过的建议”，不是“满足完成定义的任务”。接受率可以分析交互摩擦，不能独立支持开发收益或代码质量结论。

2.2 把旧测试全绿当成需求正确

旧测试保护的是已经表达过的行为。新任务可能要求新的并发不变量、权限边界或错误语义。候选完全不改代码，旧测试照样全绿。正确性门禁至少要证明目标测试在基线失败或确实区分旧行为与新行为，同时运行回归和负向路径。

2.3 让助手自己写测试、自己实现、自己判分

同一生成上下文可能把同一个误解同时写入实现与测试。例如需求要求“同一幂等键重复请求返回首次结果”，助手却把它理解为“同一用户的所有请求都去重”；实现和测试可以一致地错。由助手生成候选并不禁止，但 oracle、隐藏风险用例和最终证据签发者要独立。

2.4 用 diff 行数代表生产力

行数多可能是重复、无关重构或生成文件；行数少也可能完成复杂修复。生产力的目标是以可接受质量完成有价值任务。更合适的结束点是“补丁通过独立门禁、完成评审返工并被接受”，而不是最后一个字符生成完成。

2.5 只挑成功任务计时

助手卡住后切回人工、生成了五个被拒候选、超时或无法构建，这些都消耗资源。如果把它们从分母删除，报告测到的是“已知助手能做的成功子集”。分配后退出、失败和切回人工都要按预先定义规则保留。

2.6 在开发者日常工作树直接执行候选

模型输出是不可信输入。候选代码可以读取环境变量、访问凭据、联网、修改仓库外文件或启动子进程。仅使用 git diff 事后看变化不能恢复已经泄露的秘密。执行应在短生命周期、无生产凭据、最小文件系统和网络权限的隔离环境中完成。

2.7 只扫描新增代码里的字符串秘密

秘密可能来自被移动的历史内容、生成日志、测试快照或补丁上下文；代码也可能新增读取秘密并外传的路径而不包含任何秘密字面量。需要同时扫描补丁、结果树、构建日志和制品，并检查数据流、危险能力和网络边界。

2.8 依赖安装成功就视为安全

依赖名称可能拼写相近，版本可能越过批准范围，锁文件可能未更新，下载来源和摘要可能改变，传递依赖可能新增安装脚本。供应链门禁要比较依赖图、来源、锁定摘要、许可证和漏洞/维护状态；高风险新增依赖需人工批准。

2.9 把低复杂度等同于可维护

一个 15 行函数可以通过动态反射、全局状态和隐式约定制造很高理解成本；一个 40 行显式状态机反而更容易审计。复杂度是线索，不是裁判。API 兼容、局部性、命名、重复、测试可读性、错误语义、观察性和回滚方式都要进入评审。

2.10 不记录评审返工

助手可能把开发者编码时间换成评审者解谜时间。只记“从提示到 PR”会把成本转移误报为收益。评审等待时间、主动评审分钟、阻塞意见、返工轮次、修复分钟和最终拒绝都需要独立记录。

2.11 对不同任务做未配对均值比较

助手组恰好拿到文档、样板和熟悉模块，基线组拿到并发事故，均值差主要来自任务组合。更可靠的做法是按风险、规模、语言和熟悉度分层，采用随机分配或成对/交叉设计，并保存分配前的纳入规则。

2.12 用一次无缺陷观察宣称“缺陷下降”

逃逸缺陷是稀有、迟到且受流量影响的事件。10 个任务没有缺陷并不等于缺陷率为零，更不能说明下降。报告要给分母、观察时长、流量机会、区间和未知；样本不足时结论应是“暂未观察到”，而不是“已经证明安全”。

三、贯穿构造案例：QuotaHub 的幂等预留修复

3.1 系统与缺陷

本文使用虚构的多租户配额服务 QuotaHub。API POST /reservations 接收：

目标不变量是：

  1. 同一租户、同一资源、同一幂等键的重试只能形成一次预留，并返回首次结果；
  2. 同一幂等键如果金额不同，应返回冲突，不能静默复用；
  3. 不同租户或不同资源即使键相同，也不能互相碰撞；
  4. 数据库提交成功但响应丢失时，重试仍能查询原结果；
  5. 未授权租户不能借幂等查询判断其他租户是否存在；
  6. 旧客户端没有幂等键时维持已有拒绝语义，不自动生成弱键。

基线 8f31c2a 的内存缓存只以 idempotency_key 作为键。tenant-a 使用 batch-7 后，tenant-b 的同名请求错误复用了 A 的预留结果。公开回归测试只覆盖单租户重试，因此全部通过。

3.2 构造任务合同

合同不仅写“修复幂等 bug”。它给出行为、禁止动作、允许范围、完成定义和证据要求。base_tree_digest 防止相同 commit 名称下的脏工作树被当成基线；依赖锁和工具链摘要另存，避免“同一个 commit”却在不同解释器或依赖图上运行。

3.3 三个候选为什么不能只看测试全绿

候选 A：按用户去重。 它把缓存键改成 (tenant_id, user_id)。公开的同用户重试测试通过，但同一用户连续发起两个不同作业时第二个被吞。目标测试缺少“相同用户、不同幂等键”反例时，这个错误不会出现。

候选 B：修改数据库唯一索引。 方案本身可能合理，却触碰 migrations/，超出本次可回滚范围；同时生成了一个新迁移但没有提供双写和回滚设计。它应进入重新规划，不应偷偷扩大当前任务合同。

候选 C：扩大 mock。 它把存储层 mock 改成永远返回首次对象，使“响应丢失后重试”测试变绿，但没有执行真实事务语义。代码覆盖率上升，风险覆盖反而没有建立。

最终构造补丁使用 (tenant_id, resource, idempotency_key) 作为唯一逻辑键，在事务内比较规范化请求摘要；冲突返回稳定错误码；查询始终先做租户授权；提交记录和响应分离，使响应丢失重试读取已提交结果。是否采用数据库索引属于另一个显式任务，不在本次补丁里顺手完成。

四、冻结任务合同：先定义什么叫“完成”

4.1 合同字段分四层

层 字段 作用
身份层 contract ID、版本、owner、批准者 防止口径在结果出来后改变
仓库层 commit、tree、submodule、lock、toolchain 摘要 确定补丁所基于的世界
行为层 前置条件、输入类、后置条件、不变量、错误语义 让“修复”成为可观察判断
治理层 允许路径、禁止能力、测试层、评审、预算、停止规则 限制候选如何到达完成状态

合同摘要必须覆盖所有会改变结论的字段。不能只对任务文本做哈希，却把必跑测试、允许依赖和阈值放在可修改数据库列中。合同修订产生新版本，并明确旧候选能否迁移；默认做法是重新评测。

4.2 需求要写成可证伪陈述

“提升健壮性”“优化幂等逻辑”“符合最佳实践”无法生成可靠 oracle。更可执行的表达是：

“不得新增业务提交”需要从业务账本或可信 fake 中取证，不能只断言 HTTP 状态。安全条件“不得泄露首次请求内容”也要设计负向响应检查。

4.3 允许修改范围不是风格限制

路径范围控制了 blast radius、评审负担和回滚边界。候选认为需要改迁移、公共 API 或部署配置时，应输出“合同不足”并请求重新规划。把越界变化自动丢弃也不够：丢弃后补丁可能语义残缺，所以门禁应拒绝整个候选并保留理由。

4.4 完成定义不能由候选自报

构造完成状态只由证据服务推进：

候选可以提供说明，但不能把自己标为 SECURITY_CLEARED。测试运行器、安全扫描器和评审身份分别来自可信目录；证据绑定合同、快照和补丁摘要，并有签发时间、工具版本和撤销状态。

五、仓库快照和补丁身份：避免在错误世界里得到正确结果

5.1 commit 不等于完整工作区

一个 Git commit 能标识提交对象，但实际评测还可能受以下对象影响：

  • 未提交和未跟踪文件；
  • submodule 指针及其工作区；
  • Git LFS 对象是否完整；
  • 稀疏检出配置；
  • 生成代码和缓存；
  • 依赖锁、包索引来源和本地覆盖；
  • 编译器、解释器、构建镜像、环境变量；
  • 测试选择参数和 shard 清单。

因此快照 manifest 至少记录 commit、tree、脏状态、submodule、lock、toolchain、runner image 和测试 manifest 摘要。需要重现时从内容寻址对象恢复，而不是依赖开发者仍保留原目录。

5.2 patch 摘要应覆盖最终内容，不只覆盖聊天文本

助手可能先输出 diff，工具再自动格式化、解决冲突或补写文件。评测对象应是最终候选树相对基线树的规范化差异，同时保存原始建议和转换步骤。Git 的补丁上下文用于定位应用位置，但 git apply 成功只说明上下文可应用，不证明语义正确。

测试、扫描和评审证据全部绑定 patch_subject_digest。如果评审阶段修改代码，产生新摘要，必要门禁重新执行。

5.3 不接受路径解析歧义

候选路径需要统一为仓库相对 POSIX 路径，拒绝绝对路径、..、空路径、重复规范化结果和大小写冲突。符号链接必须在隔离环境中解析并限制到允许根。只用字符串前缀判断 src/quota 会错误接受 src/quota_evil；只在应用后看 git status 又可能太晚。

5.4 证据防重放

以下重放都应失败：

  • 在补丁 A 上通过的测试报告贴给补丁 B；
  • 合同 v1 的安全批准贴给扩大权限的 v2；
  • base commit 相同但依赖锁变化后复用旧扫描；
  • 已撤销 runner 身份签发的新报告；
  • 超过最大证据年龄的评审批准；
  • 只改报告中的 patch_id，不重新签名。

证据主键必须包含合同摘要、快照摘要和补丁摘要；验证端从可信目录读取签发者角色与密钥状态，不能相信报告自带的 role=security-scanner。

六、参考评测架构：控制面不执行不可信候选

6.1 合同与快照服务

合同服务保存版本、审批、适用任务和门槛；快照服务解析 Git 对象、依赖锁、工具链和测试清单，签发不可变 manifest。二者是后续证据的信任根，不应由助手工作进程写入。

6.2 生成控制器

生成控制器只给助手完成任务所需的最小上下文。它记录允许工具、读写范围、每次工具调用、退出原因、token/等待时间和所有候选，不把失败尝试从收益分母删除。网络默认关闭；需要读取文档或依赖元数据时走允许列表代理并保存响应摘要。

6.3 隔离执行器

候选在一次性环境中应用和运行，环境不含开发者 SSH key、云凭据、生产配置和宿主 Docker socket。资源限额、超时、进程数、文件系统挂载、系统调用、网络和制品出口都有明确策略。运行器输出结构化测试观察，不允许候选直接写最终 PASS 记录。

教学代码不会声称 Python 进程级限制就是生产沙箱。真正执行任意候选代码需要操作系统或虚拟化级隔离、独立凭据边界和出口控制；容器是否足够取决于威胁模型。

6.4 独立检查与人工评审

安全扫描解析最终树和依赖图；维护检查比较基线与候选；人工评审围绕任务语义、架构和残余风险。检查器可并行，但每项都签发绑定同一主体的证据。最终门禁只消费已验证证据，不读取助手自然语言总结。

七、正确性要分层：一个绿色测试集合不等于一个结论

7.1 第 0 层：候选完整性

先检查补丁能否无歧义应用、结果树是否与摘要一致、文件模式与编码是否合理、生成文件是否按政策处理。应用失败、冲突被自动猜测、格式化后摘要未更新，都应停止后续判分。

7.2 第 1 层：构建与静态语义

包括语法、类型、链接、Schema、代码生成一致性和静态契约。这层发现“代码不能成为可执行系统”，但不证明业务行为。若仓库原本存在基线告警，应把“新增告警”和“历史告警”分开，不能让助手借修复任务清空无关告警，也不能用历史噪声掩盖新增风险。

7.3 第 2 层：目标行为区分

目标测试需要在批准基线上表现为失败、缺失行为或可区分状态，在候选上通过。对于 QuotaHub，至少包含：

  • 跨租户同键不会碰撞；
  • 同租户同资源同键同载荷只提交一次；
  • 同键不同载荷返回冲突；
  • 提交后响应丢失再重试仍返回原 ID；
  • 授权失败不泄露是否存在；
  • 同用户不同键形成两个独立预留。

如果基线也通过所谓目标测试，先确认任务是否已修复、测试是否失去区分力或环境是否错误，不能直接给助手记成功。

7.4 第 3 层：回归与公共契约

运行受影响模块、调用者、序列化、错误码和公共 API 回归。补丁删除一个公共符号但仓库内没有调用，并不代表外部用户安全。公共契约需要独立清单、兼容性测试或明确版本升级决定。

7.5 第 4 层：负向与对抗路径

测试无效输入、边界值、权限不足、重复和乱序、超时、部分提交、取消、并发、资源耗尽和恶意 payload。负向测试的 oracle 不能只要求“没有崩溃”，还要检查无副作用、错误稳定、敏感信息不泄露和后续请求可恢复。

7.6 第 5 层：系统后置条件

高风险补丁不能停在 mock。应在隔离数据库、队列或可信模拟器上核对业务事实：提交次数、唯一约束、事务状态、事件数量、审计记录和补偿行为。QuotaHub 的核心分母是“有机会产生预留的请求”，分子是“恰好一个符合合同的业务提交”，不是 HTTP 200 数。

7.7 第 6 层：隐藏与新鲜任务

公开测试可能被助手直接优化，也可能曾进入训练数据。隐藏测试要保护 oracle 和关键变体，同时避免把安全建立在“答案永远保密”的幻想上。更重要的是持续加入发布日期新、来源隔离、人工核验的真实任务形态，并登记污染风险。

八、安全评测：把候选当成不可信供应链输入

8.1 威胁主体和资产

候选风险不只来自“恶意模型”。训练或检索内容可能被污染，issue 和代码注释可能包含间接指令，依赖元数据可能被篡改，工具适配器可能权限过宽，开发者也可能无意中把真实秘密放入上下文。需要保护的资产包括源码、秘密、个人数据、制品签名、依赖凭据、CI 身份、生产网络和代码评审信任。

8.2 上下文进入模型前

  • 只提供任务需要的文件和历史，不默认发送整个单体仓库；
  • 秘密检测在上传前执行，敏感内容按目的最小化；
  • issue、文档、注释和工具输出都标记为不可信数据，不让其中的指令提升权限；
  • 保存内容来源与许可边界；
  • 企业代码是否允许发送到特定服务由合同、隐私和安全职能确认；
  • 提示日志不默认保存完整源码与凭据。

8.3 候选生成和工具调用期间

文件读取、搜索、写入、命令执行、网络请求和包安装是不同能力。每项采用最小授权，路径和参数做结构化校验；危险副作用需要独立批准。助手要求 curl ... | sh、读取 ~/.ssh 或连接生产数据库时，控制器应拒绝并记录，而不是寄希望于系统提示说“请安全”。

8.4 候选静态检查

至少覆盖：

  • 高置信秘密、私钥、令牌和凭据模式；
  • eval、动态执行、危险反序列化、命令拼接、shell=True；
  • 路径遍历、弱随机数、禁用 TLS 校验、宽松 CORS；
  • 授权检查删除或位置变化；
  • 日志新增敏感字段；
  • 依赖新增、来源变化、版本放宽和安装脚本；
  • CI、发布、权限和基础设施配置变化；
  • 生成二进制、超大文件和混淆内容。

规则命中不是漏洞证明，未命中也不是安全证明。高危模式可作为阻断硬门，其他项进入带代码位置的人工审查。

8.5 动态故障与攻击验证

在允许执行后，注入无权限身份、恶意路径、异常依赖响应、超时、磁盘满、并发重试和伪造配置。观察的不只是进程退出码，还包括网络出口、文件写入、子进程、审计事件和业务副作用。对 QuotaHub，应验证跨租户请求不会因缓存命中绕过授权，且错误响应不返回其他租户的预留 ID。

8.6 依赖风险是图，不是一行 diff

新增顶层包可能带来多级传递依赖；同名包可能来自不同 registry；锁文件未变化可能表示实际构建仍解析浮动版本。证据应包含前后依赖图、来源、版本、摘要、许可证、已知漏洞检查时间和批准人。没有网络的离线评测可以核对允许列表与锁摘要，但不能声称掌握发布日之后才披露的漏洞。

8.7 安全通过的有限含义

构造结论可写为“在扫描规则 S、依赖情报快照 V、隔离策略 I 和动态场景 D 范围内未发现阻断项”。不要写“AI 生成代码是安全的”。NIST SSDF 提供安全软件开发实践框架，OWASP 资料给出不安全输出处理、供应链和过度自主等风险视角，但都不会替组织自动生成本仓库的完整测试集。

九、可维护性：评估未来修改者需要承担什么

9.1 变更局部性

先问任务是否以最小必要范围完成。无关重命名、格式化全文件、抽象整个模块和顺手升级依赖都会扩大评审面积。局部性不是追求最少行，而是让每个变化都能追溯到合同、测试或必要重构理由。

9.2 复杂度和控制流

记录新增分支、嵌套、异常路径、状态数和函数长度的变化。阈值用于触发审查，不自动决定好坏。一个显式列出五种事务状态的状态机可能比三层隐式 fallback 更长，却更可维护。

9.3 公共 API 与错误语义

函数名还在不等于兼容。参数默认值、异常类型、返回顺序、序列化字段、线程安全和副作用都可能变化。公共 API 删除应是硬门；语义变化需要契约测试、迁移说明和版本决定。

9.4 可测试性与可观察性

候选是否引入全局时间、随机数、隐藏网络、静态单例或难以替换的客户端？失败时是否有稳定 reason code、关联 ID 和必要指标？为了测试而暴露内部实现也会造成脆弱耦合。目标是能从公共行为和受控依赖观察不变量。

9.5 重复与抽象债务

生成式助手容易在相邻文件复制现有模式，看起来一致，却让修复点倍增；也可能过早抽象一个只出现一次的变化。重复检测与评审要结合业务语义：两段文本相似不一定同因变化，两段文本不同也可能重复同一策略。

9.6 测试代码也进入维护预算

新增 20 个测试如果依赖 12 层 fixture、真实睡眠和内部调用顺序，可能比生产补丁更贵。评审同时记录测试运行时间、fixture 扇出、共享状态、断言表达力和失败诊断。第 63 篇会进一步讨论 AI 生成测试的晋级与淘汰。

9.7 人工评审不是免费 oracle

评审记录至少包含主动分钟、等待时间、轮次、阻塞意见、意见类型、返工分钟和最终状态。评审者需要看到合同、差异、风险影响、测试证据和未知，而不是被迫从聊天记录重建意图。助手解释可以辅助导航，不能替代代码和独立证据。

十、开发收益实验：把速度、质量、返工和缺陷放进同一张表

10.1 先定义估计对象

“AI 提升开发效率”缺少对象。至少要明确：

优先估计“被分配使用助手”的效果，因为它保留失败、拒绝和放弃。只分析实际采用建议会被选择偏差影响：容易任务更可能采用，困难任务更可能切回人工。

10.2 随机、成对与交叉设计

任务无法真正重复，因为开发者做过一次就知道答案。可采用三种构造设计：

  1. 分层随机并行：按任务类型、风险、估算规模和仓库熟悉度分层，再随机分配助手或基线；适合任务池较大。
  2. 匹配对：历史上相似但不同的任务成对，一项分到助手，一项分到基线；匹配质量必须记录。
  3. 交叉顺序：开发者在不同但匹配任务上交替使用两种方式，随机 AB/BA 顺序；分析时考虑学习、疲劳和时期效应。

不应让管理者临时把紧急缺陷放到基线、把样板任务放到助手。分配在任务开始前完成，并保存纳入、排除和退出规则。

10.3 时间分解

墙钟周期与主动人时要分开。模型等待可能增加墙钟但不占满人；评审等待可能不增加主动人时，却延迟交付。两个指标都可报告，不能混成一个“节省小时”。

10.4 质量不是一个平均分

构造联合结果至少包括：

  • 合同目标测试通过且基线可区分的任务比例；
  • 回归、负向和安全硬门失败任务数；
  • 人工评审发现的阻塞缺陷，按类型和严重度分层；
  • 返工轮次与分钟；
  • 观察窗内逃逸缺陷及暴露机会；
  • 回滚、紧急修复和支持工单；
  • 无法判定或证据不完整的任务数。

不能把安全高危和命名建议简单加权平均。硬门单独判定，连续指标用于比较成本和趋势。

原始缺陷数不能在暴露机会不同的任务间直接相减。构造脚本把评审阻塞、逃逸缺陷和安全失败的预注册负担除以完整观察窗内的暴露机会；一个任务只有在两个 arm 都完成规定观察时才进入质量差分析。观察未完成是证据缺失，不是零缺陷。

10.5 成对差与统计不确定性

对每个匹配任务对计算：

负的时间差表示助手更快。时间和返工差保留所有已分配的完整任务对；失败、超时和切回人工按预注册封顶或生存分析规则计时，不能删除。另外报告两个 arm 的接受完成率及其差，防止“一分钟失败退出”被当成提速。

报告中位数、均值、分位数和明确方法的不确定性区间；小样本同时展示每一对，不让汇总隐藏长尾。二元胜负可以给精确符号检验或二项区间，但“未达到统计显著”不等于效果为零，“达到显著”也不等于工程价值足够大。

门槛应在看结果前批准。例如构造试点要求：安全硬门零失败；助手完成率达标且相对基线不劣；每个质量对都完成批准观察窗；质量负担率的区间上界不超过批准非劣界；总周期差的区间上界小于 0；至少 24 个完整任务对；退出任务保留。这里的 24、界值和区间水平都是构造值，不是行业标准。

10.6 稀有缺陷的分母

逃逸缺陷率不能写成“缺陷数 / 生成代码行”。更有解释力的分母可能是进入观察窗的已接受任务、运行事务机会、受影响请求或部署小时，并按风险类别分层。零缺陷时给上界而不是写 0 风险；观察窗不足标记右删失或 UNKNOWN。

10.7 外推边界

实验结果只适用于参与者、仓库、任务分布、助手配置和时间窗口。开发者熟悉度会变化，助手版本也会变化；上线后需要分层监控和定期复验。公共 SWE-bench 说明了以真实 issue、仓库快照和可执行测试评估代码修复的价值，但本地采购或上线决策仍需本组织任务、风险合同与开发流程证据。

十一、指标与分母：拒绝没有机会集合的百分比

11.1 任务完成率

超时、放弃、切回人工和证据缺失都留在分母，另给原因。若任务在开始前因环境故障被双方共同排除，应按预注册规则处理并报告数量。

11.2 首候选通过率

它衡量一次生成质量，不等于最终任务完成率。没有形成完整候选的已分配任务在任务完成率里仍存在。

11.3 必需测试执行完整率

SKIP、NOT_RUN、超时、环境错误不进入分子。通过率的分母只能是实际完成执行的测试，因此还要同时报告执行完整率，避免 10 个测试只跑 2 个且都通过就写 100%。

11.4 评审返工率

同时报告返工分钟和轮次。一个任务有 20 条命名意见，可能不如一条跨租户隔离缺陷严重，所以意见数量只用于工作量，不直接当质量。

11.5 逃逸缺陷率

尚未完成观察窗的任务单列。按请求机会计算时，分母换成真正经过变更路径的请求，不用全站请求稀释。

11.6 证据可复核率

缺少任一关键对象的结果不能标成 PASS，只能进入 UNKNOWN 或基础设施失败。

十二、联合门禁：PASS、DENY 和 UNKNOWN 都要有可行动理由

12.1 硬门

构造硬门包括：

  • base commit、tree、lock、toolchain 或 patch 摘要不匹配；
  • 路径越界、公共 API 未批准删除、依赖未经批准新增；
  • 高置信秘密、危险执行、越权网络或权限扩大；
  • 合同必需测试缺失、未运行、跳过、失败或 runner 不可信；
  • 人工评审仍有阻塞意见；
  • 证据签名无效、过期、签发者撤销或跨合同重放。

任一项失败即 DENY。不要用复杂度低、测试多或节省时间抵消。

12.2 预算门

复杂度增量、变更文件数、运行时间、评审轮次和返工分钟可以作为预算。超过预算不一定永远拒绝，但至少要求重新设计或升级批准。预算值按模块历史分布和风险批准，不照搬本文数字。

12.3 UNKNOWN 不是失败的委婉说法

测试环境不可用、依赖情报过期、隐藏测试清单丢失、观察窗未完成，都意味着证据不足。把 UNKNOWN 当 PASS 会放大风险，把它一律当代码失败又会污染模型能力分析。运营上可以阻断发布，分析上仍保留独立状态。

12.4 最终声明模板

这个报告把拒绝、预算和未知分开，排障者能直接知道先处理什么。

十四、完整离线实现：补丁证据门禁与成对收益分析

下面的脚本只依赖 Python 标准库，不调用真实模型、远程仓库、漏洞服务或外部执行环境。它演示的是控制面：如何把合同、仓库快照、候选补丁、静态检查、可信测试证据、人工评审与成对实验绑定起来。为避免制造错误安全感，脚本不会执行候选源码；生产系统应把任意代码执行放到独立沙箱，由可信 runner 签发结果。

将代码保存为 coding_assistant_gate.py 后直接运行：

14.1 代码刻意把测试结果当“外部证据”

evaluate_patch 不会调用候选函数，也不相信候选提供的 tests_passed=true。示例把每个签发身份固定在独立 EvidenceSigner 中，TrustStore 只暴露验证接口，调用方不能通过验证目录选一个任意 issuer 伪造证据。可信 runner 对测试观察签发证明，控制面再验证：

  • 签发者当前是否具备 runner 角色；
  • 签发时是否在有效期且验证时未撤销；
  • 证据是否绑定当前合同和补丁；
  • 快照、base commit、runner image、测试 manifest 是否一致；
  • 必需 ID 与层是否完整；
  • 是否出现失败、错误、跳过、未运行和重复 ID。

这仍只是同进程 HMAC 教学模型，类的可见性不等于真实的密钥隔离。生产系统需要 runner 自己验证恢复出的快照、实际应用补丁、执行沙箱并对完整制品签名；签发服务与验证端应跨进程或主机隔离，任务进程不能读取签发密钥。优先使用非对称签名或受保护的远程签发器，不要把控制面与 runner 的共享 HMAC key 暴露给候选代码。

14.2 为什么静态检查由控制面重算

路径、文本秘密、AST 危险调用、公共符号和简化复杂度直接从候选内容计算，避免助手上传一份“零风险扫描结果”。脚本把这些规则做成硬门，便于展示主体绑定；现实中的数据流分析、编译语言语义、间接调用和依赖来源远比示例复杂，需要语言工具链与专用扫描器。

示例也故意不执行 local_modules 的导入分类，因为仅凭模块名无法可靠区分标准库、本仓库模块、workspace 包和外部包。生产实现应从构建系统和锁文件解析依赖图，而不是用 import 字符串猜测供应链。

14.3 为什么公共 API 删除直接阻断

代码比较基线与候选的顶层公开函数/类。这个检查只能发现“名字消失”，发现不了参数、异常和行为兼容变化，因此它是下限。真实仓库还需 API 描述、类型签名、ABI、序列化和消费者契约测试。

14.4 为什么成对实验保留 SWITCHED

切回人工是助手策略的真实结果。脚本允许 FAILED、TIMEOUT 和 SWITCHED，它们保留在随机分配完成率的分母中；若缺少完整质量观察，脚本记为不完整对并阻断收益 PASS，不会用零缺陷填补。若任务最终没有完成，实验合同还应预先规定封顶时间、失败成本或生存分析口径，而不是事后填一个有利数字。

14.5 bootstrap 区间的边界

教学脚本用固定种子对成对均值做 percentile bootstrap，便于复现。time_ci 等字段是构造性不确定区间，不应被解读为在当前小样本下已证明具有 95% 频率学覆盖率。它没有处理聚类、交叉顺序、开发者随机效应、时期变化、多重比较和右删失，也不保证小样本覆盖率。正式实验应在设计阶段确定统计模型，并公开单任务差、缺失与敏感性分析。

14.6 44 个测试实际在保护什么

测试覆盖合同和快照摘要变化、快照布尔状态、路径遍历、越界路径、错误 base、脏快照、依赖新增、秘密、eval、shell=True、语法错误、公共 API 删除、变更预算、跨补丁与跨合同重放、角色伪造、签名篡改、证据过期与撤销、非整数验证时间、验证目录无签发 API、必需测试缺失/跳过/重复、测试 ID 与 layer 错配、runner image 错配、评审阻塞与轮次预算，以及成对实验的缺对、重复 arm、顺序错配、安全硬门、完成率、暴露机会分母、未完成观察窗、质量非劣和全部失败任务保留。

它们证明的是示例控制逻辑对这些构造攻击的响应，不证明该脚本适合直接处理不可信生产代码。

十六、一个实际排障链：全绿报告为何无法复现

16.1 现象

候选 P09 在助手报告中显示 436/436 回归通过，独立 runner 恢复同一 commit 后却有 17 个序列化测试失败。重新运行有时又全部通过。

16.2 先对齐证据键

排查顺序不是立刻改测试，而是依次核对：

  1. contract digest 是否相同；
  2. base commit 与 tree digest 是否相同；
  3. dependency lock 与实际解析图是否相同；
  4. runner image、环境变量允许列表和 locale 是否相同；
  5. test manifest、shard、随机种子与命令参数是否相同；
  6. patch digest 是否在格式化后更新；
  7. 测试是否读写共享缓存或时间。

16.3 证据

两个报告的 commit 都是 8f31c2a，但助手工作区的 tree 多了一个未提交的 tests/conftest.py。该文件把时区固定为 UTC，并提供全局缓存清理 fixture；独立 runner 从 commit 恢复，既没有这个 fixture，也没有清理。助手报告中的 tree digest 实际为空字段，平台旧版只核对 commit。

16.4 根因

直接原因是测试依赖未提交 fixture；控制缺陷是快照合同没有强制 tree digest，runner 允许空值；流程因素是开发者把本地工作树当成了仓库基线。把 17 个失败标成 flaky 只会掩盖快照不一致。

16.5 修复与防复发

  • 从内容寻址快照启动所有 runner，不挂载开发者工作区；
  • tree、lock、runner image 和 test manifest 任一缺失均为 UNKNOWN 并阻断；
  • 在预检中拒绝脏工作区，或把经过批准的工作区内容显式做成新快照；
  • fixture 提交后生成新合同版本并重新跑基线与候选；
  • 故障注入中加入“同 commit、不同 tree”和“格式化后补丁摘要变化”。

修复后，17 个失败稳定复现并在 fixture 正式提交后消失。这个排障说明：可复现性首先是输入身份问题，不是多重跑几次求一个绿色结果。

  • 隔离环境不含个人或生产凭据，不挂载宿主敏感 socket。
  • 定义合同、快照、补丁和证据的摘要算法与版本。
  • 准备 runner、scanner、reviewer 的独立身份、撤销和时效检查。
  • 预注册任务纳入、随机、退出、时间与质量指标。

18.2 每个任务开始时

  • 行为要求写成可证伪的前置条件、动作、后置条件和错误语义。
  • 指定允许路径、禁止路径、依赖与公共 API 政策。
  • 冻结 commit、tree、lock、toolchain、runner 和测试 manifest。
  • 基线目标测试能区分缺陷，无法区分时先修测试设计。
  • 明确安全硬门、维护预算、人工审批和观察窗。

18.3 候选生成后

  • 计算最终候选树的补丁摘要，格式化或人工修改后重新计算。
  • 检查路径规范化、模式、生成文件、依赖图和公共契约变化。
  • 扫描补丁、结果树、日志和制品中的秘密与危险能力。
  • 在隔离环境完成构建、目标、回归、负向、安全和系统后置条件。
  • 报告实际执行分母、失败、跳过、超时和未知。
  • 人工评审看到合同、风险、差异和证据，不只看助手总结。

18.4 评审与发布后

  • 记录主动评审、等待、轮次、返工、拒绝和切回人工。
  • 任何代码变化使旧主体证据失效，按影响范围重新验证。
  • 观察真实变更路径的业务机会，不用全站流量稀释缺陷率。
  • 关联逃逸缺陷、回滚和支持工单，同时保存归因置信度。
  • 将最小失效机制回灌 held-out 任务，不直接复制敏感事故原文。
  • 工具、模型、runner、规则或任务分布变化后重新验证实验结论。

十九、适用边界与仍待解决的问题

19.1 不同任务需要不同 oracle

纯函数修复可以精确比较结果；并发、性能、迁移和用户界面任务可能需要统计、时序、视觉或人工 oracle。不能为了统一评分，把所有任务压成测试退出码。高风险数据迁移还要验证备份、回滚、对账和真实规模演练。

19.2 benchmark 与生产仓库互补

公开 benchmark 适合比较可复现任务和研究系统边界，但会受任务代表性、环境构建、测试充分性、历史公开和污染影响。内部任务贴近实际，却更难共享和独立复核。更合理的组合是：公共可复现基准用于外部比较，新鲜内部 held-out 任务用于本地决策，生产缺陷用于持续校准。

19.3 安全扫描有时效

发布日期当天未公开的漏洞无法被当时情报发现；依赖维护状态也会变化。证据必须记录情报快照时间，运行期持续监控新披露，并准备依赖替换与撤销。一次扫描不是永久证明。

19.4 评审者可能适应或过度信任助手

长期使用可能提高评审效率，也可能造成自动化偏见。可以盲化部分实验、交叉评审、抽样二审并比较“有/无助手来源标签”的缺陷发现，但这些设计也会改变日常工作，应单独说明。

19.5 生产力不是压缩人力的单一指标

助手可能把时间释放到设计、测试和用户问题，也可能增加认知切换与监督。任务周期、主动人时、满意度、学习和长期所有权需要一起观察。任何人员决策都不应仅依赖助手日志或单一速度指标。

19.6 代码归属、许可和隐私需要独立治理

本文只给工程证据结构，不作法律结论。训练数据来源、输出许可、保密义务、个人数据和跨境处理应由有权限的法律、隐私与采购职能判断；技术扫描不能替代这些决定。
