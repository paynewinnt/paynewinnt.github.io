AI测试-67-LLMOps怎么管理模型Prompt数据评测和发布版本

发表于 2026-06-29 分类于 AI测试 本文字数： 22k 阅读时长 ≈ 1:20

生产告警出现后，值班人员把模型从 model-v12 切回 model-v11，接口错误率很快下降。这个动作能不能称为“LLM 应用已经回滚”？

未必。

Prompt 仍然要求新版模型支持的严格 JSON；Retriever 仍读取新版索引 Schema；工具接口已经从 amount_cents 改成 amount_minor；Policy 依赖新版风险特征；Judge 和发布评测集也在上周更换。只切模型可能暂时降低一个表面指标，却把系统放进一个从未评测过的组合。

LLM 应用真正的发布身份不是某个模型名，也不是一个 Git Commit，而是一个有依赖关系的版本闭包：

LLMOps 的核心工作，是让这组对象能够被登记、追溯、重建、评测、提升、观测和整体回退。它不需要被包装成一套与软件工程完全不同的营销名词；更准确的理解是：在已有 DevOps、DataOps 和 MLOps 方法上，处理更大的版本面、概率行为、外部 Provider、自然语言接口、检索数据、工具副作用和持续评测。

本文资料边界截至 2026-06-29（含）。文中的“星港发布系统”、组织、租户、项目、模型、版本、流量、成本、阈值、指标、审批、时间线、故障和结果均为构造示例，不代表任何真实公司、供应商或线上事故。示例使用 Python 标准库 HMAC 表达签名收据的绑定关系，只用于教学；生产实现还需可信身份、密钥托管、轮换、撤销、时间源、透明度记录或组织批准的签名基础设施。

一、先给结论：版本号只有在对象和依赖都固定时才有意义

一次可发布版本至少要回答：

  1. 每个组件的内容字节是什么，摘要如何计算；
  2. 可读版本、Alias 和内容身份之间是什么关系；
  3. 哪个组件依赖哪个组件，依赖语义是什么；
  4. 当前组合是否满足能力、Schema、ACL、地域和副作用合同；
  5. 哪个评测 Snapshot、Judge 和 Gate 证明它可以进入下一环境；
  6. 发布包由谁构建、谁批准、谁部署，角色是否分离；
  7. Shadow 与 Canary 的分母、置信区间和用户影响是什么；
  8. 线上漂移发生在输入、检索、输出、策略还是业务后置条件；
  9. 回滚时恢复的是哪个完整 Bundle，在途状态怎样处理；
  10. 从空环境重新取得所有内容后，能否重建并得到相同摘要。

只记录 model=gpt-x、prompt=v7 仍然不够。供应商模型名可能指向浮动 revision，prompt=v7 可能只是数据库自增 ID，数据别名可能在运行时移动。可复现身份需要内容摘要、来源、解析时刻和适用范围。

二、贯穿项目：星港退款 Agent 的七节点版本图

构造系统“星港退款 Agent”接受用户请求，检索退款规则，决定是否调用退款查询或提交工具，并由策略层限制金额、地区和人工审批。一次候选发布包含：

组件 构造版本 关键合同
Model refund-model@12 支持结构化输出和工具调用
Prompt refund-prompt@31 输出 payment-v2 参数，使用 chunks-v3
Data refund-kb@20260627 索引 Schema chunks-v3，ACL epoch 7
Retriever refund-retriever@9 Embedding、切片、索引和 ACL epoch 7
Tool refund-tool@18 输入 payment-v2，幂等键必填
Policy refund-policy@22 消费 tenant、risk、amount 特征
Eval refund-eval@14 release-v4 Snapshot、Judge 与 Gate

构造日流量为 180 万次交互，工作日峰值 70 QPS；Candidate 先在 Shadow 接收复制输入，再以 1%、5%、20% 扩大 Canary。所有数字只用于演示容量、分母与回滚方法。

三、第一版失败：七个仓库各自有“最新版本”

3.1 Git Commit 无法表达外部对象

应用代码记录了 Git SHA，但 Prompt 在管理后台编辑，知识索引由定时任务覆盖，模型通过 Provider Alias 选择。回看同一个 Commit，实际行为已经不同。第一版事故复盘只能列出“当时大概是 v12”，无法重建。

修复后，Git SHA 仍然重要，但只是版本图中的一个来源节点。运行时只接受已解析的内容摘要和签名 Bundle；后台 Alias 移动不会改变已部署 Manifest。

3.2 “Staging/Production”标签被当成版本

一个 Registry Tag Production 从模型 11 移到 12，发布记录只保存 Tag。两周后查询 Tag 已指向 14，审计页面错误地显示历史发布使用模型 14。环境状态和对象身份混在了一起。

最终把可变 Alias 用于人类查找，把不可变版本与摘要用于 Manifest。Deployment Record 保存当时完整 Bundle digest，不在查询时重新解析 Alias。

3.3 Prompt 回滚造成工具 Schema 错位

Prompt v30 输出 amount_cents，Tool v18 只接受 amount_minor。模型回滚期间同时把 Prompt 切回 v30，但 Tool 未回退，导致 Parser 大量失败。第一版没有兼容性合同，只在端到端评测里偶然发现。

修复后，Prompt、Tool 和 Policy 都声明 Schema；Bundle 构建时做确定性合同检查，离线评测再验证语义。确定性不兼容不需要浪费模型调用才能发现。

3.4 知识快照回滚复活已撤销权限

旧 Data Snapshot 离线准确率更高，但包含后来撤销的合同访问关系。把索引 Alias 切回旧版后，低权限账号重新检索到受限片段。数据版本不只有内容和质量，还包括 ACL、删除、时效和来源状态。

最终要求 Retriever 与 Data 的索引 Schema 和 ACL epoch 一致；旧快照若不满足当前访问合同，不能作为普通回滚目标。

3.5 Canary 只看平均延迟和 HTTP 错误

Candidate 的 HTTP 指标正常，却把 0.6% 的退款请求送到错误工具动作。平均回答得分略升，工具副作用没有独立分母。发布扩到 50% 后才被业务对账发现。

修复后，Canary Gate 同时使用 eligible、routed、observed、valid、business-committed 和 reconciled 分母；高风险副作用硬门不被平均质量抵消。

四、MLOps 与 LLMOps：继承关系，不是二选一

4.1 共同基础

两者都需要：

  • 代码、数据、模型和环境版本；
  • 实验跟踪与指标口径；
  • Registry、Lineage 和可重复构建；
  • 训练/构建、验证、批准和部署分离；
  • Shadow、Canary、监控和回滚；
  • 数据质量、漂移、成本、权限和审计。

传统 MLOps 的模型签名、训练数据血缘、特征 Schema、离线/在线一致性和监控方法仍然有效。

4.2 LLM 应用扩大的版本面

LLM 应用通常增加：

  • 自然语言 Prompt、Few-shot、模板变量和上下文装配；
  • 外部模型 Provider 与不可完全观察的 revision；
  • RAG 数据、切片、Embedding、索引、重排和 ACL；
  • Tool 描述、参数 Schema、幂等和副作用；
  • Agent 路由、Memory 和多步状态；
  • LLM-as-Judge、rubric、Parser 和评测污染；
  • 内容安全、越权、提示注入和成本长尾。

这些对象变化频率不同，却共同决定行为。因此“模型没变”不能证明系统没变。

4.3 不需要为每个对象另建一套孤岛

可以复用 Git 管理文本和代码、DVC 或对象存储管理大数据、MLflow 类 Registry 管理模型与实验、OpenLineage 类事件表达数据作业血缘、OpenTelemetry 关联运行 Trace，再由发布 Manifest 把它们连接起来。关键不是选一个声称包办全部的产品，而是让跨系统身份和摘要能闭合。

五、版本图：节点、边和闭包

5.1 节点必须内容寻址

每个 Artifact 至少保存：

artifact_id 是可读身份，content_digest 是字节身份。相同可读版本出现不同摘要应视为冲突，不允许“修一下 v31”。修复产生 v32。

5.2 边需要语义

图中的边不是装饰。至少表达：

  • Prompt 需要 Model capability；
  • Prompt 产生 Tool input Schema；
  • Prompt 使用 Retriever context Schema；
  • Retriever 从哪个 Data Snapshot/Index 构建；
  • Retriever 和 Data 使用哪个 ACL epoch；
  • Policy 限制哪些 Tool action 和输入字段；
  • Eval 针对哪个任务 profile、合同和风险面；
  • 每个派生 Artifact 由哪些输入材料与 process 产生。

单纯保存“相关对象列表”无法判断方向、闭包和重建顺序。

5.3 图快照不能跟随 Registry 新增对象

Registry 会不断加入 Prompt v32、Model v13。旧 Bundle 的 graph digest 应只覆盖当时选中节点和它们之间的依赖边，而不是整个持续增长的 Registry。否则新增一个无关版本会让历史 Bundle 无法验证。

5.4 依赖闭包

若选中 Retriever r9，它依赖 Data d20260627；Manifest 缺少 Data 即不闭包。若 Prompt p31 同时依赖 Tool t18 和 Model m12，只登记 Prompt 内容而在运行时解析“当前 Tool/Model”也不闭包。

构建器应拒绝：

  • 悬空依赖；
  • 同一必需 Kind 出现两个版本；
  • 图中环；
  • 跨租户未授权边；
  • 依赖对象已撤销或不可解析；
  • 选中节点摘要与 Registry 不一致。

六、Registry 与 Lineage：登记事实，不替代来源证明

6.1 Registry 的职责

Registry 提供不可变 Artifact、Alias、Tag、Owner、状态和查询。MLflow 官方工作流已经把 Alias 与 Tag 用作灵活组织方式，并说明固定 Stage 的局限。工程上仍需注意：Alias 可被重新指向，适合表达 champion、candidate 等当前意图，不适合作为历史部署身份。Alias 写入必须携带读取时得到的 revision，以 compare-and-swap 原子更新；过期 revision 返回冲突，不能让两个发布任务静默覆盖彼此。

6.2 Lineage 的职责

Lineage 至少回答：

OpenLineage 的 Job、Run、Dataset 和 Facet 对数据作业很有帮助，但 LLM 发布还需自定义或旁路保存 Prompt、Tool、Policy、Approval 和 Deployment 语义。不能因为发出了一个 lineage event，就声称 Artifact 内容可信或作业完整。

6.3 设计时血缘与运行时血缘

设计时图描述“声明依赖什么”；运行时 Trace 描述“这次实际解析和调用了什么”。两者必须对账。Manifest 声称 Retriever r9 使用 Data d27，但运行 Trace 显示索引 Alias 解析到 d28，发布应立即进入配置偏离，而不是等质量指标变坏。

6.4 删除与撤销

Artifact 不可变不等于永远可用。数据删除、许可到期、模型供应商撤回、密钥泄漏或安全缺陷都可能让版本进入 REVOKED。历史 Manifest 保留摘要和状态变化，新的构建与提升拒绝使用；运行中如何停止由风险等级和事故流程决定。

七、兼容性合同：把可确定问题挡在评测前

7.1 四类合同

合同 例子 检查时机
能力合同 Model 支持 tool/json/vision Bundle 构建
数据合同 index Schema、ACL epoch、语言 构建与重建
接口合同 Prompt 输出与 Tool 输入 静态、集成
行为合同 安全、质量、业务后置条件 离线、Shadow、Canary

前面三类能确定检查的内容不应全部推给昂贵、概率性的端到端评测。行为合同则不能只靠 Schema。

7.2 Prompt 也是接口

Prompt 的变量名、必填上下文、输出格式、Tool 名称、单位、错误处理和拒答语义都属于接口。文本 diff 很小，也可能是破坏性变更。Prompt Registry 应保存渲染前模板、渲染器、变量 Schema、System/User role 结构、Few-shot、规范化方式和内容摘要。

7.3 Data/ Retriever 合同

Data Snapshot 除内容摘要外，还需：

  • 文档 Schema 与切片 Schema；
  • Embedding 模型和维度；
  • 索引算法与参数；
  • ACL 字段、继承规则和 epoch；
  • 删除与时效水位；
  • 来源许可与分类；
  • 可重建 Job 与输入材料。

Retriever 版本必须绑定这些条件。只切索引 Alias 不足以证明权限与内容一致。

7.4 Policy/Tool 合同

Policy 读取 tenant_id、risk_level、amount_minor，Tool v18 必须提供相同字段语义。字段缺失时是 DENY、REVIEW 还是默认值，也要写入合同。高风险动作不能因旧 Policy 不认识新字段而默认 ALLOW。

八、签名发布包：冻结组合与供应链陈述

8.1 Manifest

签名 Manifest 至少覆盖：

签名对象不应包含可变 Alias。签名前先规范化序列化，拒绝 NaN、重复键、顺序歧义和未知类型。

8.2 签名证明的边界

有效签名可以说明持有对应密钥的一方对这些字节作了认证；它不自动证明：

  • Builder 没有被攻陷；
  • Artifact 来源合法；
  • 评测结论正确；
  • 生产部署的字节与 Manifest 一致；
  • 外部 Provider 模型没有浮动；
  • 所有依赖都已被列出。

因此还需要可信 Builder、材料 Provenance、审批、部署验证和运行时对账。本文示例不接受请求体自报的 Builder 或 Signer：身份必须来自受信目录，租户或角色变化提升单调 epoch，撤销后旧 epoch 的 Bundle 不再具有继续提升资格；runner_digest 也必须能从内容库取回字节并重新计算，而不是一个无人验证的标签。

8.3 SLSA 与 in-toto 怎样借鉴

截至本文资料边界，SLSA Build Provenance v1.2 的结构包括 in-toto Statement 的 subject，以及 predicate 中的 buildDefinition、runDetails、builder.id 和 resolvedDependencies；materials 是旧版字段名，不应继续当作 v1.x Schema 字段。规范还要求消费者只接受预期的 signer-builder 组合。LLM 发布包可以借鉴其“陈述绑定 Artifact、验证者按策略消费”的模式，但本文自定义 HMAC Bundle 既不是完整 in-toto Attestation，也不因字段相似就获得任何 SLSA Build Level。模型、Prompt 和数据的生成链与软件构建不完全相同，仍需定义自有 predicate、信任根和验证策略。

九、从开发到生产的提升流程

9.1 DEV：允许快，但仍保存身份

开发阶段可以使用小样本、Stub 和非生产 Provider，但每个实验仍记录版本图、参数、Dataset 和结果。探索性 Alias 可以频繁移动，进入候选构建时解析为固定 ID。

9.2 STAGING：重建和集成

预发从空工作区按 Manifest 拉取对象，验证摘要、依赖闭包和兼容合同；使用隔离 Tool 目标做集成评测。不能把开发机器打包后的目录直接复制过去，因为本地残留文件会掩盖缺失依赖。

9.3 SHADOW：观察真实分布，不产生真实副作用

Shadow 复制符合授权的线上输入到 Candidate，Candidate 输出不返回用户、不调用真实写工具。要分别记录：

Shadow coverage 是 valid / eligible 或预先定义的分层分母，不是 valid / started。选择器若只挑容易样本，离线结果再好也不能代表线上分布。

9.4 CANARY：有限真实影响

Canary 需要稳定 cohort 和 abort 条件。1% 流量不等于风险只有 1%：若高金额用户集中被路由，或一个请求能产生不可逆副作用，影响可能不成比例。门禁同时观察：

  • 用户任务成功、放弃、人工升级；
  • 工具提议、授权、执行、目标接受和业务提交；
  • 安全、隐私和关键 Slice；
  • p95/p99 延迟、队列和 Provider 限流；
  • 每有效任务成本；
  • Candidate 与当前生产 Baseline 的配对或可比 cohort；
  • 观测覆盖和对账水位。

9.5 PROD：Alias 是路由意图，Deployment Record 才是事实

生产 Alias 指向 Bundle B 只表达控制面意图。部署代理应在每个实例启动时报告实际 Manifest digest；路由层记录请求落到哪个 digest；监控对比 desired、scheduled、ready、receiving traffic 和 business committed。只有这样才能发现旧 Pod、黏性会话、区域缓存和异步 Worker 仍运行 Bundle A。本文代码把观测结果签成 DeploymentProof，绑定 tenant + environment + action + from/to bundle + components + observed_at + executor epoch；证明还要求目标实例全部接流、旧 Bundle 新请求为零、队列和 Tool 已对账、Smoke 通过。current 状态按 (tenant, environment) 建键，另一个租户同名环境不能覆盖或充当前部署事实。

十、分母、区间和提升门禁

10.1 离线分母

离线评测使用不可变 expected manifest。无效 Judge、Provider 超时和缺失不能从分母静默删除。质量比例对 valid 计算，同时并列 coverage；coverage 不足为 UNKNOWN。

10.2 Shadow 分母

构造窗口：

若只报告 117,980 条中的通过率，会遗漏 2,020 条未形成有效判断的流量。还要按语言、租户、风险、长度和 Tool 路径比较 selected 与 eligible，检查选择偏差。本文把 eligible、selected、started、served、evaluated、tool-authorized、business-committed 和 reconciled 作为同一份签名 Evidence 的分母清单；Shadow 的 eligible 或 expected 为零、清单缺失、关系倒置或 coverage 不足都只能得到 UNKNOWN。

10.3 Canary 分母

Canary 至少有流量分母、质量分母和业务分母：

分母 用途
eligible 路由覆盖
assigned cohort 稳定性
served 用户可见行为
evaluated 质量判断
tool_authorized 权限正确性
business_committed 副作用正确性
reconciled 延迟终态确认

不能用 served 作为业务成功分母后忽略仍在异步提交的请求。Canary 同时检查 selected/eligible、served/selected 和 reconciled/business_committed；分母关系由不可变数据结构校验，任一必需覆盖不足进入 UNKNOWN，不能删除未观测请求后只对成功子集计算 PASS。

10.4 置信区间与停止规则

本文代码对二项比例使用 Wilson 区间。实际 Canary 还要考虑用户内相关性、时间趋势、重复会话和多指标监控。若每五分钟看一次，直到“显著”为止，会增加偶然放行概率。观察窗、最小样本、最大时长、扩流级别和提前停止条件应在发布前固定。

10.5 Gate 顺序

  1. 校验当前身份、Bundle 签名、Runner 字节、重建和兼容合同；
  2. 校验 Evidence 签名及其 tenant、Bundle、phase 和 Policy digest；
  3. 同时计算硬失败与证据缺口：硬失败存在时 BLOCK 优先，否则缺口为 UNKNOWN，只有无原因才 PASS；
  4. 校验前一环境确实记录了同租户、同一 Bundle；
  5. 校验 Approval 的角色、epoch、环境、有效期，以及精确 Evidence 和 Policy digest；
  6. 校验新鲜、签名且范围一致的部署观测证明，再写入 Deployment Record。

十一、漂移：先定位哪一层变了

“线上漂移”不是一个统一指标。至少拆成：

  • 输入主题、语言、长度、风险和用户 cohort 漂移；
  • 检索命中、空结果、引用覆盖、ACL 拒绝和文档新鲜度；
  • 输出长度、格式、拒答、Tool 选择和安全标签；
  • Provider latency、错误、finish reason 和可观察 revision；
  • Judge 分数分布与人工一致性；
  • 业务成功、投诉、人工接管和副作用对账；
  • Token、缓存、重试和每有效任务成本。

Population Stability Index、距离或分布检验只是信号。阈值要结合样本、季节性和影响；漂移也不等于质量下降。节假日咨询主题变化可能是正常业务变化，却要求重新确认评测代表性。

监控发现漂移后，先固定窗口和 Bundle，再按版本图逐层对比。不要直接自动重训或改 Prompt；如果漂移来自路由错误、ACL 缺失或 Provider revision，修改模型可能扩大问题。

十二、完整回滚：恢复 Bundle，也恢复运行语义

12.1 回滚目标来自已验证历史

回滚选择的是同一租户历史 Deployment Record 中实际运行、且在当前合同 epoch 和有效时间窗下仍可重建的完整 Bundle。历史上通过不等于今天仍合法；合同已替换、Runner 字节缺失、Builder/Signer 已撤销或内容重算不一致时，普通回滚必须停止。不能在事故现场拼装：

除非这个组合事先构建、签名和评测过，否则它是新候选，不是回滚。

12.2 历史好版本可能已经不再可用

  • 旧 Provider 模型已下线；
  • 旧 Data 包含已删除内容；
  • 旧 ACL 不满足当前权限；
  • Tool API 已移除旧 Schema；
  • 安全 Policy 已因漏洞撤销；
  • 当前流量超过旧版本容量；
  • 数据库迁移已不可逆。

因此发布前持续维护可回滚性：保留兼容窗口、转换器、双读、旧镜像和定期重建演练。无法完整回滚时，选择停用高风险功能、只读模式、人工路径或前向修复，而不是强行切 Alias。

12.3 在途状态

切换 Bundle 之前盘点：

  • 黏性会话与 Memory 使用哪个 Prompt/Model；
  • Queue 中消息使用哪个 Schema；
  • 已授权未提交 Tool Call；
  • Provider 异步 operation；
  • Retriever 缓存和索引 Alias；
  • 各区域和 Worker 的实际 digest；
  • 成本与审计事件是否仍在到达。

高风险任务可以按旧 Bundle 排空，也可以取消后对账；不能让新 Worker 用新 Schema 接管旧消息却不转换。

12.4 回滚完成的证明

控制面 Alias 已移动只是开始。至少验证：

  • 全部接收流量实例报告目标 Bundle digest；
  • 旧 Bundle 新增请求降到零，允许的在途集合可解释；
  • Tool 和业务账本后置条件正确；
  • ACL、删除和地域约束未倒退；
  • 关键故障 Case 与邻接正常 Case 通过；
  • Trace、成本和对账 coverage 达标；
  • 连续观察窗没有再次触发 abort。

这些事实必须由受信部署观察身份签名，证明精确绑定当前生产 Bundle、回滚目标 Bundle、目标组件集合和租户。风险与部署审批再绑定该 proof_digest 和当前 policy_digest；缺证明、拿提升证明冒充回滚、跨 Bundle/租户复用、旧 Bundle 仍接收新请求或证明过期，都不能生成 ROLLBACK Record。

十三、审批与职责分离

13.1 四种角色

角色 能做什么 不能单独做什么
Builder 读取批准材料并生成签名 Bundle 批准自己的质量与风险
Quality approver 审阅评测设计和结果 改 Bundle 后沿用旧批准
Risk approver 审阅高风险 Slice、例外和补偿控制 直接部署
Deployer 对目标环境执行提升/回滚 自签质量和风险结论

小团队可以由较少的人承担多个日常职责，但高风险发布的同一次决定仍应明确哪些身份不能合并。自动化服务身份也要进入职责分离检查。

13.2 Approval Receipt 必须绑定什么

批准 Prompt v31 不能自动批准 Prompt v32；批准 Staging 不能直接用于 Production；角色已撤销或收据过期后不能从缓存继续使用。

13.3 Emergency rollback 也要最小控制

事故中可以减少普通提升步骤，但回滚目标、操作者、风险批准、原因、时间和前后 Bundle 仍应记录。break-glass 不是共享管理员密码，也不意味着可以拼接未验证组件。紧急动作后补做完整恢复验证和复核。

十四、重建验证：从空环境证明 Manifest 可用

14.1 为什么“文件还在”不够

工作目录可能有未登记的模板、缓存索引、环境变量或本地 wheel。日常部署持续成功，可能只是复用了脏环境。重建验证从空目录和最小身份开始：

  1. 验证当前 Builder/Signer epoch、可信 signer-builder 组合和 Bundle 签名；
  2. 按 Artifact ID 获取 Registry 记录；
  3. 从内容库下载字节并重算摘要；
  4. 验证选择图依赖闭包；
  5. 取回 Runner/Adapter 字节并核对 Manifest digest；
  6. 验证 Compatibility Contract 在构建时和当前时刻都有效且未被更高 epoch 替换；
  7. 构建运行镜像或部署描述；
  8. 运行确定性合同测试和最小离线评测；
  9. 比较产物摘要与 Manifest；
  10. 保存重建 Evidence。

14.2 可重复与可再现

同样材料、同样构建器得到逐字节相同产物是强可重复性目标；外部模型或时间敏感索引未必能做到字节相同。此时应明确哪些部分可重建、哪些只能验证固定引用和行为合同，不能把“接口还能调用”写成完全可再现。

14.3 外部 Provider 的版本边界

若 Provider 只提供模型 Alias，没有固定 revision，Manifest 要保存请求标识、区域、Endpoint、当时返回的可观察元数据和验证窗口，并把不可固定风险写进 Gate。对稳定性要求高的路径可以选择提供更强版本承诺的服务、保留多 Provider 回退或加大在线监控。

十五、权限、租户与审计

Registry、内容库、Lineage、Approval、Deployment 和 Evidence 都带 tenant。共享基础模型可以属于受控公共域，但 Prompt、Data、Policy 和 Trace 默认不能因模型共享而跨租户。调用者提交的 Principal 不是信任来源；平台只接受身份管理锚登记的当前主体，角色或租户变化必须提升 epoch。部署当前态和历史查询都必须先按 tenant 分区，再按 environment 或 record 定位。

权限测试至少覆盖：

  • Artifact editor 不能给自己发 Production approval；
  • Deployer 不能覆盖 Registry 历史内容；
  • Quality approver 不能读取不在评审范围内的 Prompt 原文；
  • Builder 只能读取本 Bundle 所需 Secret 和输入材料；
  • 跨租户 Artifact ID 即使存在也不能加入图；
  • Evidence 查询和导出自身产生审计事件；
  • Alias 移动需要 owner、原因和 compare-and-set；
  • 撤销角色 epoch 后，旧 Approval Receipt 立即失效；
  • 备份恢复不会恢复已撤销 Alias、角色或数据访问。

审计事件区分 bundle.built、approval.issued、promotion.requested、deployment.observed、rollback.executed 和 recovery.verified。一个 deployment.success 无法表达这些不同事实。

十九、一次值班排查：Alias 已回滚，错误仍在增长

19.1 现象

构造时间 14:06，Canary Bundle B 的工具参数错误上升。14:08 将 Production Alias 切回 Bundle A，控制面显示成功；14:12 错误仍以每分钟 36 次增长。

19.2 证据顺序

先看路由记录，新的同步请求已落到 A。再看工具提交 Trace，新增错误来自异步 refund-worker；Worker 的实际 digest 仍是 B。部署系统只更新 API Deployment，没有更新消费同一 Queue 的 Worker。

继续核对 Queue message Schema。B 已写入 8,412 条 payment-v2 消息，A 的 Worker 只理解 payment-v1。直接把 Worker 切 A 会把在途消息变成新的失败。

最后核对目标系统：其中 127 条已经被 Tool 接受，不能重新投递；其余消息尚未提交。错误增长不是 Alias 缓存，也不是 Provider 模型继续漂移。

19.3 止损

  • 暂停新的退款写动作，保留查询与人工路径；
  • 冻结 Queue 水位、Bundle、Worker digest 和目标回执；
  • 将已接受 127 条按幂等键对账；
  • 对未接受 v2 消息使用经过测试的 v2→v1 转换器，无法转换的隔离；
  • 更新 API、Worker、Prompt、Tool adapter 和 Policy 到完整 Bundle A；
  • 验证所有实例、区域和队列消费者报告 A digest；
  • 用事故 Case、相邻正常 Case 和业务账本连续验证。

19.4 根因与修复

20.1 变更提案：先回答“为什么必须一起变”

构造需求是把退款规则引用从段落级升级为条款级，并让高金额退款先进入人工复核。改动表面上只有两项业务要求，影响图却包含：

Change Proposal 保存需求 ID、风险、受影响节点、未变节点的复用依据、迁移策略、预期评测、回滚约束和 owner。没有发生字节变化的 Model 与 Tool 仍出现在 Bundle 中，因为“继续使用它们”也是一个需要固定的决定。

影响分析不是从文件 diff 猜测。系统沿图反向查找 Data 的消费者，得到 Retriever、Prompt 和 Eval；沿 Tool Schema 查找 Prompt 与 Policy。若某条依赖没有被建模，影响分析会漏项，所以生产事故发现的隐式依赖要回写图 Schema 和合同测试。

20.4 Bundle 与 Provenance：签名前冻结可重建材料

Release Builder 使用工作负载身份读取批准 Artifact。它不能读取任意租户对象，也不能把本地未登记文件打包。Manifest 形成后，对规范化字节签名，得到构造 Bundle digest rb_b7f…。

构建服务同时输出 Provenance，声明输入 resolvedDependencies、builder.id、buildDefinition、runDetails 和产物 subject。签名服务只接受来自批准 Builder identity 的摘要，不接受客户端上传任意 Manifest 后代签；验证者只信任配置中的 signer-builder 组合。Builder 与 Signer 分开可以降低构建进程直接使用长期密钥的暴露面。

在透明度或外部检查点可用的设计中，还可以把 Bundle 声明追加到独立记录，降低攻击者同时改 Registry 和历史声明的能力。本文不假设单一日志能证明所有来源真实；验证策略仍需信任根、撤销状态和材料审核。

20.7 Approval：批准的是同一个 Bundle 与证据集合

Quality approver 检查 Dataset 代表性、Judge 校准、分母、区间和失败 Case；Risk approver 检查 ACL、高金额动作、缺字段默认行为、补偿控制和回滚可用性；Deployer 检查环境容量、实例清单、Queue Schema、abort 和 runbook。

三份收据都绑定 B2 digest、目标环境、Evidence digest、角色 epoch 和有效期。进入 Shadow 时使用 Shadow 目标收据，不能拿 Staging 收据复用。若期间 Bundle、合同或关键 Evidence 任一摘要变化，旧收据仍是有效历史记录，但不适用于新请求。

审批页面应展示签名对象的固定内容，而不是先展示 Alias，点击批准后服务端再解析。否则审批者看到 p33，最终收据可能绑定 Alias 后来指向的 p34。

20.11 生产漂移：信号要回到版本图

上线第三天，jurisdiction.missing 比例从 2% 升到 11%，但错误率没有上升。调查先确认 Bundle 和 Provider revision 未变，再发现上游订单系统逐步迁移，部分地区尚未提供 jurisdiction。

这是输入和上游 Schema 漂移，不是模型质量漂移。Policy 正确把缺字段送人工，安全底线通过，但人工队列超过容量。处理方案可能是暂停上游迁移、补字段、扩人工容量或为低风险场景设计经批准的降级，不应自动微调模型绕过 Policy。

漂移事件引用 affected cohort、开始时间、分母、版本和 runbook。临时阈值调整生成新 Policy Artifact 和 Bundle，不能直接编辑生产数据库常量。

  • B1 签名、内容和图仍可重建；
  • B1 Data 满足当前删除与 ACL；
  • Tool 仍兼容 B1；
  • B2 写入的 Queue 消息能否由 B1 消费；
  • 在途 Tool Call 的接受与提交状态；
  • B1 容量是否能承接全部流量。

发现 320 条 B2 消息使用新字段。演练没有强行让 B1 Worker读取，而是暂停 Queue，用签名转换器生成 B1 Schema，原消息与转换结果通过 lineage 关联；已被 Tool 接受的 7 条只对账、不重放。

20.13 一次提升最终形成的证据目录

目录是逻辑结构，不要求所有内容放在同一个 ZIP。每个对象可位于适合的受控系统，通过摘要和访问策略关联。Evidence Bundle 对特定审批或调查按最小范围导出，并声明不能提供的对象和原因。

20.14 为什么这条链仍然不是绝对证明

即使所有签名和测试通过，也只能在声明的信任与样本边界内作结论：

  • Builder 或来源账号可能在签名前已被攻陷；
  • 外部 Provider 内部 revision 可能不可见；
  • held-out 可能不代表未来生产分布；
  • Shadow 选择器可能漏掉未识别风险；
  • Canary 小流量难以观察稀有伤害；
  • 业务事实源和审计生产者也可能错误；
  • 回滚后的用户影响和历史副作用不会自动消失。

因此 LLMOps 不是“把全部风险变成一个签名绿色勾”。它把对象、决定、缺口和责任边界结构化，让自动化知道何时可以继续，也知道何时必须停止并交给有权限角色判断。

20.15 兼容窗口：版本图还要表达时间

组件 A 与 B 在静态 Schema 上兼容，不代表任何时间都能任意组合。Tool v18 可能承诺在 30 天内同时接受 payment-v1 和 payment-v2；Data d28 的旧 ACL 读取接口可能只保留到迁移完成；Provider 可能公告某模型在指定日期下线。Compatibility Contract 因此还需要 valid_from、valid_until、弃用状态和迁移前置条件。

构造 Tool 的兼容窗口到 2026-07-15。Bundle B1 使用 payment-v1，当前仍可回滚；若事故发生在 7 月 16 日，Rebuilder 即使能取回所有字节，也要把 Tool 合同判断为过期。此时可选动作是启用保留的 v1 Adapter、执行经过验证的消息转换、停用写工具或做前向修复，不能因为 B1 曾经是 Production 就忽略时间条件。

时间判断必须使用受信时钟并记录 Policy 版本。客户端传入 now=2026-06-01 不能让过期 Bundle 重新合法。离线灾备环境若无法获得可信时间和撤销状态，验证结论应是 UNKNOWN，不能降级为只验内容摘要。

数据库与事件迁移也有双版本窗口。先让消费者理解 v1/v2，再让生产者写 v2，观察所有消费者水位，最后停止 v1。回滚期间若旧消费者仍存在，Queue 保留 Schema version；没有转换器的消息进入隔离。把字段原地改义而不增加版本，会让旧 Bundle 看似兼容、实际解释不同。

20.16 Registry 竞态：Alias 移动需要 compare-and-set

两个发布任务可能同时把 candidate 从 p31 指向 p32 和 p33。若 API 只有无条件 PUT，较晚请求会覆盖较早请求，审批者也不知道自己的选择已被替换。Alias 更新应带 expected revision：

Alias 事件保存 old target、new target、old/new revision、actor、purpose 和关联 proposal。删除 Alias 也追加事件。历史部署页面读取 Deployment Record，不通过当前 Alias 反查。

Artifact 上传采用两阶段处理：先把字节写入隔离区并计算摘要，再做恶意内容扫描、Schema、来源和租户检查，最后原子发布 Registry 记录。上传成功但 Registry 事务失败时，孤立 Blob 由回收任务按引用关系清理；不能让未登记 Blob 被 Bundle Builder 通过猜测摘要直接读取。

同 Artifact ID 的并发注册若内容相同可幂等返回，内容不同必须冲突。冲突不是“最后一次编辑获胜”，而是来源系统或构建过程违反不可变合同的高价值信号，需要保留双方摘要和主体。

20.17 发布系统自身的容量与止损

发布高峰可能同时构建数百个大索引。控制面要限制每租户并发、内容下载带宽、重建 CPU/内存、签名请求和 Provider 评测预算。高优先级安全回滚不能排在普通实验后面，但优先级也不能由请求者任意填写；它来自可信事故或发布策略。

发布控制面自身发生故障时，应有独立 kill switch：停止 Alias/Deployment 写入，保留只读查询和当前生产路由。若 Approval 服务不可用，普通提升等待；紧急回滚使用事先批准的最小路径和独立审计。不能在依赖服务失败时自动变成“任何管理员都能部署”。

20.18 日常巡检：验证可回滚性，而不是等事故发现

每周选择当前 Production 和上一个已知好 Bundle，从空环境执行签名、内容、图、合同和最小评测重建；在隔离环境演练实例收敛和 Queue Schema。结果记录成功率没有意义，巡检需要列出具体不可用原因和恢复时限。

建议关注：

  • 历史 Bundle 中已撤销或即将过期 Artifact；
  • Provider 下线公告与浮动 revision；
  • 内容库缺失、复制延迟和摘要不符；
  • 签名根、Approval key 与角色 epoch 状态；
  • 当前 Queue 中最老 Schema；
  • 旧 Tool Adapter 与数据转换器是否仍可执行；
  • 回滚容量与预热时间；
  • 最近一次业务后置条件演练。

若上一个版本因 ACL 或安全缺陷已不可用，立即构建新的回滚候选并完成最小生产验证，而不是继续在面板上标记 rollback_ready=true。可回滚性是一项持续状态，有 owner、分母、证据和到期，不是一条发布时填写后永久有效的元数据。

20.19 多区域发布：同一 Bundle 也可能产生不同运行事实

Bundle digest 相同，只能说明期望组件相同。区域 A 与区域 B 可能连接不同 Provider Endpoint、Secret、知识副本和 Tool 目标，也可能处于不同数据驻留规则。Deployment Record 因此还要绑定 region、runtime profile 和外部依赖解析结果。

扩区顺序先选择一个可止损区域，验证数据复制水位、ACL、Provider 配额、时钟、Trace 出口和业务对账，再逐区推进。全局平均值可能掩盖单一区域零 coverage；每个区域都有 expected instances、served、valid 和 reconciled 分母。

回滚也按区域记录 desired 与 observed。若区域 B 因网络分区没有收到控制命令，全局 Alias 已切回不能算完成。路由层可先摘除 B，阻止新流量，再等待实例收敛或人工处理。恢复后重新验证 B 的 Bundle、数据水位和在途副作用，不直接把流量加回。

跨区域证据导出遵守原数据分类和目的。为了统一排障把所有 Prompt 汇总到一个低权限中心，会破坏原隔离设计。更合适的方式是中心汇总摘要、状态和最小诊断字段，需要原文时在对应区域按案件范围揭示。

二十二、代码中的关键边界

22.1 Alias 为什么不进入 Manifest

代码先用固定 Artifact ID 构建 Bundle。测试随后用 expected revision 把 candidate Alias 从 Prompt 31 移到 32，Bundle 1 摘要仍不变；第二个持有旧 revision 的写入会冲突。若运行时按 Alias 取 Prompt，签名 Manifest 就失去约束力；若 Alias 无 CAS，并发发布还会发生静默丢失更新。

22.2 Graph digest 为什么只覆盖选择闭包

Registry 和图可以继续加入新版本。旧 Bundle 的 graph digest 只对选中七节点和它们之间的边计算，因此无关新增版本不会破坏历史验证；Prompt 31 改为 32 时，选择图与 Bundle 摘要都会变化。

22.3 Compatibility Contract 为什么与 Eval 互相绑定

合同要求 Eval Artifact 声明相同 contract ID 与 profile，避免拿开发评测套件证明生产合同。它仍然不能防止 Eval 数据本身错误，所以发布还需要 Dataset、Judge 和结果证据。

22.4 Approval 为什么检查当前 epoch

收据签发后，角色可能撤销。只验证历史签名会继续接受已经失去权限的批准。示例将当前 Identity Directory epoch 与收据绑定，并要求同一收据同时匹配 Bundle、tenant、environment、精确 evidence_digest 和 policy_digest；更换任一对象都必须重新审批。生产还需要受信时间、撤销传播、密钥状态和离线验证策略。

22.5 回滚为什么只接受历史 Production Bundle

Controller 在同一 tenant 内查找历史 Production PROMOTE 记录，按当前合同重新验证 Bundle 与 Runner 字节，并把目标 Manifest 的全部 components 写入 ROLLBACK Record。一个从未在生产验证的 Bundle 即使签名正确，也不是普通回滚目标。ROLLBACK 还需要签名恢复证明，精确绑定当前 Bundle、目标 Bundle、组件集合、实例收敛、旧流量归零和对账状态；审批绑定该证明与当前 Policy。

22.6 Builder、Signer 与 Runner 为什么分别校验

Manifest 中的 built_by 和 runner_digest 只是声明。验证器还要从受信身份目录取得当前 Builder/Signer epoch，检查允许的 signer-builder 组合，并从内容库取回 Runner 字节重算摘要。客户端自报角色、未知 Signer、已撤销 epoch、缺失 Runner 或同摘要下的字节替换都不能靠一个外层签名变成可信发布。

22.7 为什么部署状态必须同时绑定 tenant 和环境

production 不是全局唯一键。示例把当前态存为 (tenant_id, Environment)，DeploymentProof、Approval、Evidence、Bundle 和历史记录也逐层重复绑定 tenant。回归测试在同一个 Controller 内依次提升两个租户的 Staging Bundle，证明后一次写入不会覆盖前一租户，也不能把前一租户的 from_bundle_digest 当作本租户部署事实。

二十四、发布与回滚清单

24.1 Artifact 与图

  • 七类 Artifact 有固定 ID、内容摘要、来源和 tenant。
  • 同可读版本异摘要被拒绝。
  • Alias 只用于发现，不用于历史身份；移动使用 expected revision CAS。
  • 图无环、无悬空边、无未授权跨租户依赖。
  • Manifest 覆盖选择闭包，不受无关 Registry 新增影响。
  • 撤销、删除和不可解析状态会阻断新构建。

24.2 合同与评测

  • Model capability 满足 Prompt。
  • Prompt、Tool、Policy Schema 与单位一致。
  • Data、Retriever 的索引 Schema 和 ACL epoch 一致。
  • Eval profile、contract、Snapshot、Judge 与 Gate 固定。
  • expected、valid、missing 和 excluded 分开。
  • 关键风险先于平均效用。
  • 区间、最小样本和观察窗预先确定。

24.3 提升

  • Bundle 验证当前 Builder/Signer epoch 与允许的 signer-builder 组合。
  • 空环境重建逐项验证 Artifact 与 Runner 字节、构建时/当前合同。
  • Builder、Quality、Risk、Deployer 收据满足职责分离。
  • 收据绑定 Bundle、tenant、环境、Evidence、Policy、epoch 和到期。
  • Shadow 不产生真实副作用。
  • Canary cohort 稳定，abort 与扩流级别固定。
  • 实际实例 digest 与控制面意图对账，并形成新鲜、签名的 DeploymentProof。

24.4 回滚

  • 目标来自已验证历史 Deployment Record。
  • 目标组件当前仍可用且满足 ACL、删除和安全要求。
  • Queue、会话、缓存、异步 operation 和 Tool Call 已盘点。
  • 无法兼容时使用排空、转换、隔离或停用。
  • 回滚记录保存前后完整 Bundle、组件和恢复 proof digest。
  • 用户、业务、安全、审计、容量和成本连续验证。
  • 旧 Bundle 不再产生无法解释的新提交。

二十五、边界与取舍

25.1 不必把所有文本都放进模型 Registry

Prompt 可以由 Git 管理，数据可由 DVC/对象库管理，模型可由 MLflow 类 Registry 管理。统一的是 Artifact identity、Lineage 和 Manifest，不一定是物理存储。

25.2 内容摘要不等于语义版本

摘要能识别字节变化，不能告诉修改是否兼容。兼容合同、评测和变更说明共同提供语义。

25.3 签名不等于安全发布

签名材料可能恶意但签名有效。可信来源、Builder 隔离、审查、评测和运行时验证缺一不可。

25.4 Shadow 不等于无风险

复制真实输入本身涉及目的、隐私、地域和 Provider 处理。即使不回用户、不调工具，也要获得授权并最小化内容。

25.5 Canary 不替代离线 held-out

线上样本有真实分布，却可能难以获得及时真值并影响用户；离线集可控但可能偏离生产。两者互补，不能互相替代。

25.6 完整回滚不保证完全恢复

Bundle 恢复后仍需处理已发生副作用、在途队列、用户影响和数据状态。回滚是恢复技术状态的手段，不是事故关闭条件。
