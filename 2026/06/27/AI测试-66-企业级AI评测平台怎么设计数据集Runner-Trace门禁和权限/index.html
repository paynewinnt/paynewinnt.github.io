AI测试-66-企业级AI评测平台怎么设计数据集Runner-Trace门禁和权限

发表于 2026-06-27 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:14

一个评测页面显示候选版本得分 91.4，基线得分 89.7，平台也给出了绿色 PASS。这个结论能不能直接进入发布流水线？

还不能。至少要继续追问：

  • 91.4 的分母是哪一个不可变数据集快照，运行期间有没有被编辑；
  • 开发集、回归集和发布保留集是否出现同源问题、同一事故变体或近重复内容；
  • Runner 超时重试时，外部模型是否被重复调用、重复计费，工具类用例是否产生了重复副作用；
  • Candidate 与 Baseline 是否在同一批 Case、同一 Judge 版本和同一环境上配对；
  • 被排除的 83 条数据为什么排除，它们是否被悄悄移出了分母；
  • 总分上涨时，付款、隐私、越权和低资源语言 Slice 是否退化；
  • Trace 能否区分一次 Run、一个 Case、一次 Attempt 和一个 Provider Call；
  • 提交者是否能读取另一个租户的数据、借用管理员密钥，或导出带原始 Prompt 的证据；
  • 绿色结论来自质量通过，还是来自评测基础设施漏数、Judge 不可用或查询超时。

企业级 AI 评测平台不是把若干脚本包进 Web 页面。它承担的是一条可复核的测量链：

一、平台真正管理的是测量合同

1.1 从脚本到平台，增加的不是按钮

单机脚本可以读取一个 JSONL，循环调用模型，再输出平均分。只要参与者少、数据不敏感、运行频率低、结果不控制发布，这种方式成本最低，也最容易调试。

平台化发生在测量合同开始跨人、跨环境和跨时间复用之后。此时需要稳定回答：

  1. 测什么：Snapshot、Split、Case、Oracle 和 Slice 的固定身份是什么。
  2. 测谁：模型、Prompt、Retriever、Tool、Policy、Judge 与运行参数组成什么被测版本。
  3. 怎样测：Runner 镜像、适配器、超时、重试、并发和随机种子是什么。
  4. 怎样算：分母、排除规则、聚合公式、置信区间和配对方式是什么。
  5. 怎样判：硬门、退化预算、不确定状态、审批和豁免是什么。
  6. 谁能做：租户、角色、目的、环境和数据分类怎样共同限制操作。
  7. 怎样复核：Trace、成本账本、审计事件和证据包能否重建结论。

平台只是这些合同的执行者。UI 上的分数、排行榜和趋势线是投影，不是事实源。

1.2 三类“成功”必须分开

一次 Run 至少有三个独立结论：

结论 回答的问题 典型失败
执行成功 计划内 Case 是否得到终态 队列丢任务、Provider 超时、Runner 被驱逐
测量有效 分母、版本、Trace、Judge 和排除是否可信 漏数、混入旧 Snapshot、Judge 版本漂移
质量通过 有效结果是否满足 Gate 安全 Slice 失败、配对退化、成本越界

Run.status=COMPLETED 只能说明执行状态。若 10,000 个预期 Case 只回收 9,100 个，不能把 9,100 个结果算完后称为“质量通过”；若 Judge 整体不可用，也不能把全部样本记成失败来污染产品质量趋势。更合适的状态是 INFRA_ERROR 或 UNKNOWN，发布侧仍然阻断自动提升，但原因不会被伪装成模型退化。

1.3 适用边界

本文适合以下场景：

  • 多项目共用评测执行能力；
  • 数据集、模型或 Prompt 需要版本化复现；
  • 结果进入 CI/CD、灰度或风险审批；
  • 存在个人信息、内部文档、密钥或高风险工具；
  • 需要跨租户隔离、成本归集和审计导出；
  • 每天有大量异步 Case，需要队列、限流和故障恢复。

若只有一个不影响发布的离线探索任务，先保留命令行工具、内容摘要和测试记录通常更经济。平台不应成为所有实验的强制入口，也不能替代业务专家对 Oracle、风险和适用性的判断。

二、贯穿项目：星港客服助手的评测链

构造项目“星港客服助手”服务三个业务租户：

租户 评测对象 高风险 Slice 数据约束
tenant-retail 订单与退款问答 金额、币种、重复退款 订单样例去标识化
tenant-enterprise 合同知识助手 ACL、引用、过期条款 内部文档不可跨租户
tenant-support 工单 Agent 工具越权、PII、升级人工 工具目标只能是模拟环境

平台每天接收约 420 个 Run、约 168 万个 Case Attempt；峰值是工作日下午代码合并窗口。上述数字全部是构造值。一个 Run 同时评测 Candidate 与 Baseline，使用同一 Snapshot 和 Judge；高风险用例默认不访问真实业务目标。平台保留摘要、版本和受控证据引用，普通 Trace 不保存完整用户原文。

第一次平台化的目标很克制：替代四套互不兼容的 Python 脚本，让发布流水线能获得一个稳定的 Gate Decision。项目没有先做排行榜，也没有先建设复杂工作流编排；先固定对象身份、执行幂等和证据分母。

三、第一版为什么失败

3.1 CSV 就地更新让历史结果失去语义

第一版把 dataset.csv 放在共享目录。业务同学修正答案时直接覆盖文件，Runner 在任务开始时只记录路径。上午和下午两个同名 Run 实际读取了不同字节，但报告都写“dataset=v7”。出现回归后，无法判断是模型变化还是答案变化。

修复不是给 CSV 增加 updated_at。最终做法是把每个发布数据集转换成规范化 manifest，对 Case 内容、Oracle、Slice、来源分类和 Split 分别计算摘要，形成不可变 Snapshot。可读别名 refund-regression@current 只是指针；RunSpec 在提交时必须把指针解析成固定 Snapshot ID，之后不再跟随别名。

3.2 Runner 把超时理解成“没有发生”

Provider 在第 58 秒已经接受请求并生成结果，网关响应在返回途中超时。Runner 使用新请求 ID 重试，造成两次计费。工具型用例更危险：若适配器连到可写测试目标，新 ID 可能产生两次副作用。

修复后，逻辑调用键由 tenant + run + case + role + provider_version 确定。超时只增加 Attempt ordinal，不改变逻辑调用键。适配器需要声明是否支持幂等；不支持且结果未知的高风险调用进入 UNKNOWN_COMMIT，不能自动重试。成本账本按 Provider Call ID 幂等入账。

3.3 平均分掩盖安全退化

候选版本通用问答提高 3.8 个百分点，但 tool.permission.high 的 40 条用例失败 3 条。总分仍上涨，第一版 Gate 放行。问题根因不是公式算错，而是把不同风险当成可互相补偿的效用。

修复后，平台先计算不可补偿硬门，再看配对效用变化。关键 Slice 只要发生规定严重度失败就 BLOCK；总体分数只能在硬门通过后参与判断。

3.4 “失败样本不计入”制造了虚假高分

Judge 解析失败的 Case 被 SQL 查询 WHERE score IS NOT NULL 排除。Provider 越容易输出异常格式，分母反而越小，剩余样本分数越高。

最终把 expected、started、provider_completed、judge_valid、excluded_by_policy、missing 分开。任何排除都需要版本化原因码和批准策略；技术失败不从预期分母消失。

3.5 缓存键没有租户和版本

第一版缓存只使用 Prompt 摘要。两个租户出现相同问题时，租户 B 可能读到租户 A 的结果摘要；Provider 配置变化后也可能复用旧答案。即使答案文本相同，这仍然破坏了隔离和证据血缘。

修复后的缓存键至少绑定租户、Snapshot Case、被测版本组合、适配器版本、推理参数、策略和目的。涉及受限数据时还要考虑是否根本不允许跨 Run 缓存。

四、三平面架构与信任边界

平台拆成控制面、隔离执行面、证据与决策面，不是为了增加服务数量，而是为了限制每个组件能作出的声明。

4.1 控制面

控制面管理 Dataset Registry、RunSpec、Policy、身份、配额和 Secret 引用。它可以批准“运行什么”，但不直接生成质量结果。Dataset Registry 只接受新 Snapshot，不提供覆盖历史对象的更新接口。

4.2 执行面

执行面领取租约、解析只读 Snapshot、调用 Provider/Judge 适配器并提交结果。Runner 只获得本次 Run、当前租户、当前 Provider 所需的短期能力；它不能修改 Dataset、Gate Policy 或给自己签发发布批准。

4.3 证据与决策面

Trace Store 保存结构化 Attempt 和摘要引用；Aggregator 根据冻结口径计算分母、区间和 Slice；Gate Engine 消费聚合产物和版本化策略。Evidence Exporter 只导出明确范围内的证据，并把缺口写入 manifest。

4.4 平台不应自证一切

如果 Runner、Aggregator、Gate 和 Evidence Signer 共用一个管理员身份，那么被攻陷的 Runner 可以伪造结果、改策略并给自己签名。至少要把以下权力分离：

  • Dataset 发布者不能单独批准生产 Gate；
  • Runner 不能写 Policy Registry；
  • Gate 服务读取冻结结果，不能回写 Case；
  • Evidence Signer 使用独立服务身份；
  • 审计导出审批人与数据集维护者不是默认同一角色；
  • 平台管理员不自动拥有每个租户的明文证据读取权。

五、对象模型：先定义身份，再定义页面

5.1 Dataset、Snapshot、Case 和 Split

对象 是否可变 关键字段
Dataset 可变元数据容器 tenant、name、owner、classification
Snapshot 不可变 snapshot_id、manifest_digest、schema、created_by
Case Snapshot 内不可变 case_id、input_ref/digest、oracle、group_id、slice
Split Snapshot 内声明 train、dev、eval、held_out

Dataset 名称不能作为执行身份。refund-safety 可以持续增加版本；真正进入 Run 的是 snap_9f…。Case ID 也不能只由数组下标生成，否则插入一条记录会改变后续全部身份。更稳的方式是让 Case ID 来自稳定业务键或受控生成过程，同时用内容摘要发现“同 ID 异内容”。

5.2 Run、Shard、Task、Attempt 和 Call

Run 是一次冻结测量；Shard 是调度分片；Task 是一个 Case 在一个被测角色上的逻辑工作；Attempt 是基础设施尝试；Call 是 Provider 识别的一次幂等调用。

Attempt 可以多次，Result 只能有一个已接受内容。重复提交相同摘要是幂等，重复提交不同摘要是冲突，必须隔离并告警。

5.3 Metric、Slice、GatePolicy 和 Decision

MetricDefinition 固定方向、值域、分母、无效值处理、聚合公式和版本；SliceDefinition 固定成员条件和最小样本；GatePolicy 固定硬门、统计条件、成本预算和 UNKNOWN 处理；Decision 保存输入摘要、结论、原因码和策略版本。

页面临时筛选出来的“准确率”不能直接成为 Gate 输入。否则同名指标会随查询条件改变。

六、Dataset Registry：不可变 Snapshot 是复现起点

6.1 Snapshot manifest 应包含什么

一个可执行 manifest 至少包含：

原始文本可以保存在受控对象域，manifest 使用引用和摘要。摘要不自动匿名化，也不消除字典攻击；它解决的是身份和完整性关联，不是隐私豁免。

6.2 不可变不等于永不删除

不可变表示同一 Snapshot ID 的字节和语义不能被覆盖。若数据保留规则要求删除受限原文，可以让受控对象进入删除状态，同时保留最小 tombstone、摘要和删除证明。此后 Snapshot 可能从 AVAILABLE 变为 RESTRICTED 或 UNRESOLVABLE，历史报告仍能说明当时引用了什么，但不能假装仍可完整重跑。

6.3 Split 防泄漏要同时看四层

  1. 稳定组隔离：同一事故、会话、文档、用户或模板族的变体只能进入一个 Split。
  2. 精确内容隔离：规范化后的同内容不能跨 Split。
  3. 近重复筛查：n-gram、MinHash、Embedding 等方法发现候选，再由规则或人工确认。近重复算法有误报漏报，不能写成“已证明无污染”。
  4. 来源隔离：held-out 的答案、解释和失败标签不能通过 Prompt、工单、检索库、Few-shot 或模型 Memory 回流到开发链。

只随机打乱 Case 再按 8:1:1 切分，容易把同一文档的相邻切片、同一用户会话和同一事故的措辞变体分散到不同 Split，离线结果会过度乐观。

6.4 Snapshot 发布门禁

发布前检查：

  • Case ID 唯一且合法；
  • 同一 ID 的内容摘要未被历史版本静默改写；
  • group、exact content 和已知来源不跨 Split；
  • Oracle 有 owner、版本和适用范围；
  • Slice 字段属于受控词表，关键 Slice 有预期分母；
  • PII/Secret 分类完成，禁止字段未进入普通对象域；
  • 变换程序、Schema 和依赖摘要可追溯；
  • 空 Split、零分母、异常膨胀和大量删除需要显式复核。

七、Runner：隔离、租约、重试和幂等

7.1 状态机

推荐把 Run 与 Task 分开建模：

SEALED 表示预期清单与已收结果已冻结，Aggregator 才能开始。不能一边持续补结果，一边让 Gate 查询动态表。

7.2 租约不是 exactly-once

队列提供的是工作分发。Worker 在租约到期前可能已完成外部调用却来不及确认，另一个 Worker 会再次领取。即使底层使用 Kubernetes Job，官方文档也明确提示，在某些条件下同一程序可能启动多次。因此业务层仍需：

  • 逻辑 Task ID；
  • Attempt ID；
  • 稳定 Provider request key；
  • 结果 compare-and-set；
  • 成本账本幂等键；
  • 对未知副作用的对账状态。

“队列只投递一次”不能作为正确性前提。

本文代码里的 LeaseManager 对 (tenant_id, run_id, case_id) 做原子领取，每次重新领取产生严格递增的 fencing token。Runner 在外部调用前后及 Result 提交时都验证当前 token；过期 Worker 即使稍后恢复，也不能提交旧结果。稳定 request key 仍然必须保留，因为 fencing 只能拒绝平台内的迟到提交，不能撤销已经到达外部 Provider 的调用。

7.3 错误分类决定是否重试

类别 示例 动作
输入永久错误 Schema 不兼容、Case 缺字段 不重试，记录数据错误
权限永久错误 Secret scope 错、租户不匹配 不重试，安全告警
可确认未提交 连接前失败、Provider 明确 429 同键退避重试
结果可查询 Provider 接受后超时，有 operation ID 同键查询或恢复
提交状态未知 非幂等工具超时 不盲重试，进入对账
Worker 中断 驱逐、进程崩溃 重新领取 Task，沿用逻辑键

重试预算需要区分 Provider、Judge 和基础设施；一个 Case 最多三次不能被解释成三层各三次后再由网关重试三次。总尝试上限和成本上限应由 RunSpec 固定。

7.4 隔离边界

Runner 默认采用：

  • 每个租户或分类域独立 Namespace/Worker Pool；
  • 只读挂载 Snapshot，临时盘按 Run 擦除；
  • 非 root、只读根文件系统、最小 Linux capability；
  • 默认拒绝网络，只放行指定 Provider/Judge Endpoint；
  • CPU、内存、临时盘、时限、并发和出站字节配额；
  • Secret Broker 按租户、Provider、Run 和 TTL 签发；
  • 高风险 Tool Case 只指向模拟器或隔离沙箱；
  • Runner 镜像用摘要引用，不跟随可变 tag。

容器隔离不是任意不可信代码的万能安全边界。若允许用户上传执行代码，还要评估更强沙箱、系统调用、内核、供应链和逃逸风险。

八、Provider 与 Judge 适配器

8.1 统一的是合同，不是假装供应商相同

ProviderAdapter 可以统一这些字段：

  • 逻辑请求键与供应商请求 ID；
  • 模型标识、区域、Endpoint 和可观察 revision；
  • 输入/输出对象引用与摘要；
  • timeout、rate limit、retry-after 和错误分类；
  • 输入、缓存、输出或推理用量；
  • latency、finish reason 和内容过滤状态；
  • 供应商是否承诺幂等、是否支持查询已接受任务。

但不同供应商的 Token 口径、缓存计费、批处理、模型浮动版本和内容过滤语义并不天然可比。适配器应保留原始单位和转换版本，不能只输出一个看似统一的 tokens=123。

8.2 Judge 是版本图中的被依赖对象

LLM-as-Judge 至少固定：

  • Judge 模型与可观察 revision；
  • Judge Prompt、rubric、few-shot 和输出 Schema；
  • 温度等参数；
  • Parser 和无效输出处理；
  • 是否盲化 Candidate/Baseline 位置；
  • 人工校准集和一致性报告；
  • 敏感内容是否允许发送给该 Judge。

Judge 分歧不是简单多数投票就能消失。高风险 Case 可以优先使用确定性 Oracle、结构校验、模拟工具后置条件和人工复核；Judge 适合承担明确 rubric 下的有限语义判断。

九、Trace：记录尝试，不默认复制内容

9.1 关联键

推荐同时保留：

键 生命周期
trace_id 一次端到端 Run 或一个可控子链
run_id 一次冻结评测
case_id Snapshot 内的稳定 Case
task_id case + role 的逻辑任务
attempt_id 一次基础设施尝试
provider_call_id Provider 识别的调用
idempotency_key 重试时保持稳定的逻辑请求身份

一个 Trace Span 成功不等于业务 Result 已提交。事件要区分 provider.accepted、provider.response_observed、judge.completed 和 result.committed。

9.2 内容记录边界

OpenTelemetry 的生成式 AI 语义约定提醒输入输出消息可能包含敏感信息。平台不能因为观测 SDK 支持字段就默认开启全文。普通 Trace 更适合保存：

  • 内容对象 ID、摘要、分类和长度；
  • 受控的错误码与结构统计；
  • 版本、用量、延迟和 finish reason；
  • 是否执行脱敏、脱敏策略版本；
  • 原文是否存在于受限 Evidence Vault。

禁止把 API Key、Cookie、Authorization、系统 Prompt 原文、用户 PII 和受限文档复制进标签。高基数字段也不能无界进入 Metrics。

9.3 Trace 完整性

完整性至少检查：

  • 预期 Task 是否都有终态；
  • Attempt 序号和父子关系是否合理；
  • 同 event ID 是否出现异载荷；
  • Provider 成功是否对应成本项；
  • Result 是否引用 Candidate、Baseline 和 Judge 证据；
  • 迟到事件是否在 Seal 前进入；
  • 缺失、重复和冲突是否进入分母。

Trace 只能证明平台记录了哪些陈述。它不能单独证明 Provider 返回内容真实、外部副作用正确或所有事件都被采集。高风险结果仍需目标系统、账本或独立业务事实源对账。

示例为每个事件绑定 tenant_id、完整 RunSpec digest、Case、Attempt、fencing token、可信 Runner 身份及其当前 epoch，并由 TraceStore 使用该来源的受信密钥签名。完整性判断还要求 result.committed 精确引用同一个已签名 Result；来自其他租户、其他 RunSpec、旧 epoch 或不同 fence 的事件不能补齐当前分母。

十一、Gate：先完整性，再硬门，再统计收益

11.1 状态语义

状态 含义 发布动作
PASS 证据充分，硬门和统计条件满足 可进入下一环境
BLOCK 已有充分证据表明触碰底线 阻断并要求修复
UNKNOWN 分母、Trace、样本或依赖不足 阻断自动提升，修复测量链
REVIEW 处于批准的人工权衡区 等待有权限角色决策
WAIVED 风险被有期限地接受 附补偿控制、owner 和到期

UNKNOWN 与 BLOCK 都可以让 CI 失败，但运营含义不同。把 Provider 故障算成模型 BLOCK 会让质量趋势失真；把质量失败算成“平台不稳定”则可能绕过底线。

11.2 判断顺序

  1. 校验 RunSpec、Snapshot、Policy、Runner 和适配器摘要；
  2. 校验 expected manifest 与 Result 集合；
  3. 校验 Trace、冲突、迟到和 Judge 有效性；
  4. 检查秘密泄漏、租户越界和不可授权副作用等硬安全门；
  5. 检查关键 Slice 的严重失败；
  6. 检查总体和 Slice 的区间；
  7. 检查 Candidate/Baseline 配对退化；
  8. 检查延迟、容量和成本预算；
  9. 生成原因码、证据引用和下一动作。

平均分只处在后半段。

零有效结果时，区间和平均成本都表示为 None，而不是 NaN 或无穷大。Gate 会生成 PASS_RATE_DENOMINATOR_MISSING、COST_DENOMINATOR_MISSING 等 UNKNOWN 原因，因此缺失证据既不会崩溃，也不会被序列化成一个看似可比较的数值。

11.3 策略也要不可变

GatePolicy 应包含 metric definition digest、Snapshot selector、阈值、最小分母、区间方法、关键 Slice、成本单位、UNKNOWN 行为、批准者和有效期。运行结束后再修改阈值重算可以用于分析，但不能覆盖原始 Decision；应生成新的 policy digest 和 Decision。

十二、RBAC、租户边界、Secret 与 PII

12.1 授权不是只有角色

有效授权至少是：

dataset-editor 可以发布自己租户的 Snapshot，不等于能提交生产 Gate；eval-operator 可以运行，不等于能查看受限原文；auditor 可以导出批准案件范围，不等于拥有底层对象库全读。

平台级运维为了修复队列而拥有 Kubernetes 权限，也不应自动获得 Prompt 明文。控制平面权限和数据平面权限应分离。

代码中的 IdentityDirectory 是显式信任锚：只有持有管理密钥的一方能登记、换代或撤销主体；每次租户或角色变化都必须提升 epoch。业务 API 会把传入 Principal 与目录当前记录逐字段比较，因此调用者自行构造 runner、auditor 等角色，或重放旧 epoch，都无法通过授权。

12.2 每一层都要带 tenant_id

租户边界不能只依赖页面路由。以下对象和键都要绑定租户：

  • Registry 主键与对象存储前缀；
  • Queue、Lease、Result 和缓存；
  • Secret scope 和 Provider 账号；
  • Trace Resource、日志索引和指标维度；
  • 成本账本与预算；
  • GatePolicy 和 Evidence Export；
  • 加密密钥或密钥派生域；
  • 备份恢复和删除任务。

测试要主动尝试“合法主体 + 合法对象 ID + 错误租户参数”的组合，防止 confused deputy。

12.3 Secret 只以引用进入 RunSpec

RunSpec 保存 secret://provider/acct-7，不保存值。Runner 在执行前用工作负载身份向 Broker 换取短期凭据，Broker 同时校验租户、Provider、环境和 Run。Secret 不写入 Trace、异常、命令行、缓存键或证据包。

调试时打印整个请求对象是常见泄漏路径。日志拦截需要覆盖成功、异常、重试、超时、SDK debug 和 fallback，不只是主流程。

12.4 PII 最小化

数据集发布流程应先判断字段是否对 Oracle 必要。订单号、姓名、邮箱通常可以替换为保持关系但不保留身份的构造值；无法去标识化的 Case 进入更严格域。摘要和 Tokenization 仍可能可链接，不应宣称匿名。

十三、接口、目录与事件细节

13.1 最小目录

Schema 与消费者代码一起评审。事件字段废弃采用双读或版本迁移，不能在生产表里静默改含义。

13.2 Run 提交接口

服务端解析所有可变别名，返回冻结 RunSpec digest。相同幂等键、相同主体、相同请求摘要返回原 Run；同键异请求返回 409，而不是覆盖。

13.3 事件信封

occurred_at 与 observed_at 分开，便于识别迟到和时钟问题。事件去重使用 event ID，同 ID 异载荷进入隔离；不能使用“最后写入覆盖前值”。

十六、一次值班排查：得分上涨但 Gate 变 UNKNOWN

16.1 现象

构造时间 10:12，tenant-enterprise 的发布 Run 显示 Candidate 通过率从 87.2% 升到 90.1%，Gate 却是 UNKNOWN。页面同时出现 TRACE_COVERAGE=96.8%。发布人员最初怀疑平台误判，希望手工改成 PASS。

16.2 排查顺序

第一步核对 RunSpec 与 expected manifest，确认预期 25,000 个 Case，Result Store 有 24,992 个终态，说明不是大量任务丢失。

第二步按 Case 对 Trace 完整性分组，发现 801 个 Case 缺少 provider.response_observed，但都有 result.committed。缺失集中在 10:03 到 10:07，且只来自 runner image sha256:72c…。

第三步对齐 Collector 指标。10:02:48 开始，Trace exporter 队列满；Runner 的结果提交使用数据库通道，Trace 使用异步出口，因此结果成功而事件丢弃。HTTP 和 Provider 指标正常只是伴生现象。

第四步检查发布变更。新镜像把 exporter 队列从 20,000 改成 2,000，且在队列满时只打印 debug 日志。根因不是模型质量，也不是 Aggregator SQL。

16.3 止损与修复

  • 暂停依赖该 Runner digest 的自动 Gate；
  • 保留 Result、Runner 本地 spool、Collector 指标和镜像配置；
  • 回滚 Runner 镜像，恢复有界磁盘 spool；
  • 将“证据出口持续失败”改为高风险 Run 的 Seal 阻断条件；
  • 重跑同一 Snapshot、Candidate、Baseline、Judge 和 Policy；
  • 新 Run 达到 100% 必需 Trace coverage 后重新计算；
  • 增加 exporter 队列 80%、丢弃、spool 年龄和 Seal backlog 告警。

原 Run 保持 UNKNOWN，不用新结果覆盖。最终 Candidate 是否 PASS 由新 Run 独立决定。这个处理保留了测量历史，也避免把平台故障误写成模型回退。

17.2 Planning：预期分母必须先于结果存在

Planner 在 Snapshot 内选择 held_out，应用已签发的静态 Case selector，形成 expected-manifest。这个 manifest 包含预期 Case ID、group、Slice、执行角色和逻辑 Task ID，不依赖 Result Store。这样，即使整个 Runner 集群没有启动，平台仍知道原本应执行多少工作。

构造 Run 有 25,000 个 Case，每个 Case 有 Candidate、Baseline 和 Judge 三个逻辑角色。Planner 不简单生成 75,000 条互不相关消息，而是保留 Case 级 join key，确保后续配对。按估算 Token、风险等级和 Provider 限额把 Case 分为 320 个 Shard；高风险 Tool Case 进入仅能访问模拟器的 Worker Pool，普通文本 Case 进入无业务网络权限的 Pool。

Shard 大小需要平衡：

  • 太大时，一个长尾 Case 会拖慢整个 Shard，Worker 崩溃后的恢复成本也高；
  • 太小时，队列、Pod、Trace 和数据库元数据开销超过模型调用；
  • 将不同租户混入同一 Shard 会扩大缓存、临时盘和诊断权限边界；
  • 将超长 Case 与短 Case 随机混排会造成租约频繁过期；
  • 按预估长度分桶有助于容量，但不能改变 Slice 分母或抽样权重。

Planner 输出也要有摘要和 Schema 版本。Task 表不是 expected manifest 的替代，因为 Task 创建中途失败时，数据库里实际存在的行数恰恰是不完整的。

17.3 Lease 与取消：停止调度不等于任务已停止

Worker 使用 compare-and-set 领取 Lease，保存 leased_by、lease_epoch、expires_at 和 Attempt ordinal。续租只允许当前 epoch 的持有者；旧 Worker 恢复网络后提交过期 Lease 的结果，Result Store 会拒绝或隔离，不能采用“最后写入者获胜”。

取消 Run 时至少区分：

状态 取消动作 结果处理
PENDING 不再发 Lease 标记未开始
LEASED 未调用 撤销租约 不产生 Provider Call

正确处理是：

  1. 原 Run 保留 612 预期、611 有效和当时的 Oracle 版本；
  2. Oracle 缺陷作为 Dataset Incident 登记；
  3. 修复后发布新 Snapshot；
  4. 以同一 Candidate/Baseline/Judge/Policy 发起新 Run；
  5. 对比两个 Run 时明确 Dataset 已变化，不称为纯模型差异。

17.10 这次演算最终留下什么

一次被 BLOCK 的 Run 仍然是有效平台产物。它留下：

  • 可复现的 Snapshot、版本组合和运行合同；
  • 25,000 条预期分母及互斥终态；
  • Candidate/Baseline 配对转移和统计区间；
  • 一条关键 Slice 失败及其受控证据引用；
  • Provider 重试、成本和 Trace 完整性；
  • 原始 Decision 与后续可能的 Waiver；
  • 可供发布系统和调查者分别使用的最小证据包。

平台的目标不是让更多 Run 变绿，而是让绿色、红色和未知都有稳定语义。

17.11 数据库一致性：不能用一个大事务包住外部模型

Provider 调用可能持续数十秒，Judge 还可能异步返回。把数据库事务从领取 Task 一直保持到外部响应，会长期占用连接与锁；事务失败也无法撤销已经发生的外部调用。更合适的边界是用状态机、唯一约束和 outbox/inbox 协调：

  • 领取 Lease 与追加 task.leased outbox 在一个本地事务中完成；
  • 外部调用使用由已提交 Task 状态派生的稳定请求键；
  • 响应先按 call ID 进入 inbox，同 ID 异载荷隔离；
  • Result compare-and-set 与 result.committed outbox 同事务；
  • 异步发布失败可重放 outbox，不重新调用 Provider；
  • 聚合只读取已经 Seal 的版本，不依赖跨库瞬时 join。

这仍不是分布式 exactly-once。它把不可避免的重复变成可识别身份，把每个本地状态变化变成可重放事实。数据库唯一键至少覆盖 tenant_id + run_id、run_id + case_id + role、provider_call_id 和 event_id。只对自增主键做唯一约束，不能阻止业务重复。

读副本也可能制造错误判断。Result 已提交到主库，Aggregator 从延迟副本读取时会看到缺失；若平台立即 Seal，就把复制延迟写成 coverage 缺口。可以在 Seal 中固定数据库水位或日志位置，等待证据存储达到同一水位，再开始聚合。等待超时进入 UNKNOWN，不能悄悄切到一个没有一致性声明的数据源。

Schema 迁移要考虑长时间 Run。若 RunSpec v2 在执行途中升级到 v3，旧 Runner 写出的事件仍需被当前 Collector 明确接受或隔离。推荐先让消费者兼容新旧版本，再发布生产者，最后停止旧写入；破坏性字段变更使用新 event type 或 schema version。直接复用旧字段名表达新含义，会让历史报表看似连续、实际不可比较。

17.12 缓存：命中结果也必须生成本次运行证据

缓存可以显著降低构造成本，但它不是绕过 Runner 和 Trace 的捷径。一个可复用结果至少绑定：

若这些条件有一个无法证明，默认重新执行。缓存条目需要来源 Run、创建时间、有效期、数据分类和撤销状态。命中时仍然生成本次 Run 的 cache.lookup、cache.hit、Result 引用和成本状态，并在 Summary 中把 fresh 与 reused 分开。否则一次全缓存 Run 会没有 Trace，或者被错误统计成 Provider 延迟为零、成本为零。

对于随机采样、时间敏感知识、会话状态和供应商浮动模型，缓存可能改变被测语义。此时即使键完全相同，也只能用于开发加速，不能进入发布 held-out Gate。缓存策略本身应属于 RunSpec，不能由 Worker 根据本地是否有文件临时决定。

缓存删除也有租户边界。Dataset 撤销、Secret 泄漏、Judge 缺陷或 Provider 版本认定不可用时，需要按依赖摘要定位受影响条目。只设置固定 TTL 会让错误证据在到期前继续复用；只按 Prompt 摘要清理又会漏掉相同 Prompt 的不同策略和租户。

17.13 运营 SLO：可用性要围绕“形成结论”定义

平台接口返回 200 并不等于用户按时得到有效 Gate。更有意义的构造 SLI 包括：

  • Admission 在预算时间内返回冻结 Run ID 的比例；
  • 在声明 deadline 前达到 Seal 的 Run 比例；
  • Seal 后在预算时间内形成 Decision 的比例；
  • expected manifest 与有效 Result 的 coverage；
  • 必需 Trace、成本和版本证据完整率；
  • 因平台原因进入 UNKNOWN 的 Run 比例；
  • 各租户 p95 队首等待和饥饿时间；
  • Evidence Export 在批准范围内完整生成并验证通过的比例。

质量 BLOCK 不应降低平台可用性 SLI，因为平台正确拒绝了版本；Provider 不可用导致 UNKNOWN 是否计入平台 SLI，要按责任域分别展示。只做一个“Run 成功率”会鼓励把 UNKNOWN 改成产品失败，或把质量 BLOCK 从统计中随意删除。

每个告警都应指向明确 runbook。例如 seal_backlog_age 告警先核对 expected manifest、Task 终态、Result 水位和 Trace checkpoint，再判断是 Queue、Provider、数据库复制还是 Collector。cost_per_valid_result 上升则先拆 fresh/cache、Candidate/Baseline/Judge、重试和无效结果，不先归咎于模型价格。

灾备验证也以证据闭合为目标。恢复后随机选择已封存 Run，核对 Snapshot 可解析、Result 集合与 Seal 一致、Trace checkpoint 可达、Gate 可重算、原 Decision 摘要不变、租户授权仍生效。仅验证服务进程启动和首页可访问，无法证明平台恢复了测量能力。

17.14 删除与保留：四类对象不能使用同一 TTL

Dataset 原文、Trace 元数据、聚合 Summary 和审批证据的目的不同，保留期限也不应共享一个全局数字。受限 Prompt 可能需要更短期限，Snapshot manifest 和 Decision 摘要可能因复现、合同或风险治理需要保留更久；具体期限由有权限职能结合适用规则批准。

删除流程要覆盖对象库、搜索索引、缓存、临时盘、导出副本和备份恢复路径。某个 Case 受删除请求影响时，平台要判断是否删除原文、撤销可重跑能力、保留最小 tombstone，并标记哪些历史 Evidence Bundle 需要到期或通知接收者。不可变 Snapshot 不应被解释为绕过删除义务。

法律冻结或事故保全只暂停匹配对象的删除，不自动扩大读取权限，也不把原保留时钟重置为无限期。创建、复核、缩小和解除冻结都追加版本；Runner 和 Exporter 每次访问时读取当前有效状态，不能永久信任缓存的旧授权。

十九、代码中的关键判断

19.1 为什么 Snapshot ID 来自 manifest

同一规范化 manifest 会生成同一 ID，使发布重试幂等；内容、Oracle、Split 或 Slice 变化都会形成新 ID。示例没有实现近重复检测，因为那需要额外算法和阈值治理；代码只把精确内容和 group 隔离做成可确定执行的硬约束。

19.2 为什么 Trace 只保存 payload digest

示例主动拒绝 prompt、input、output、secret 等原文字段，再保存 payload digest；事件信封本身由当前 epoch 的可信 Runner 来源签名。生产系统通常还需要受限 Evidence Vault、字段级 Schema、加密、保留、撤销和可验证导出。签名能认证“谁对哪个摘要作了陈述”，仍不能证明外部 Provider 内容或副作用真实。

19.3 为什么重试记录两个 Attempt，却只有一个费用

Stub Provider 在构造的 c1 上先“提交”响应再抛出瞬时错误。Runner 第二次沿用同一 request key，Provider 返回同一 call ID；CostLedger 按 call ID 只入账一次。这个测试模拟网络不确定性，不宣称所有真实 Provider 都提供同样语义。不支持幂等和查询的副作用调用不能照搬自动重试。

不同 Worker 不能同时靠“先查 Result 再执行”争抢同一 Case。代码先取得带递增 fence 的 Lease，ResultStore 再把 tenant、RunSpec、Snapshot、Runner epoch 和 fence 一起签名并原子提交；旧 Worker 的迟到提交会被拒绝。

19.4 为什么 Gate 同时保留 BLOCK 和 UNKNOWN 原因

若一个 Run 既有安全 Slice 明确失败，又缺少部分 Trace，安全失败已经足以 BLOCK，同时仍应显示证据缺口。代码让 BLOCK 优先，但不丢 UNKNOWN 原因。生产策略还可以加入 REVIEW、WAIVED、严重度、双审批和到期处理。

19.5 统计实现的边界

Wilson 区间适合演示二项比例；配对差值代码使用正态近似，样本少、相关性强或分布离散时并不充分。生产评测应根据指标性质选择 exact、bootstrap、置换检验、cluster-aware 方法或预先批准的统计计划，并报告多重比较和停止规则。

  • 缺失、无效、政策排除与迟到；
  • Slice 重叠、小样本和总体方向相反；
  • Candidate/Baseline 配对错位；
  • 非有限阈值、错误方向和单位不一致；
  • Judge 漂移与人工校准集退化。

20.4 运行测试

  • Worker 驱逐、重复领取和租约过期；
  • Provider 接受后断连、429、5xx 和长尾；
  • Trace Collector、Result Store、Registry 和 Secret Broker 故障；
  • Queue 公平性、配额、取消和优先级反转；
  • Seal 与迟到结果竞态；
  • 预算耗尽、价格表变化和最终账单对账。

20.5 上线前检查

  • RunSpec 只引用不可变 ID 或 digest，不保留可变别名。
  • Snapshot 有 group、exact content、来源和近重复筛查记录。
  • held-out 答案与开发、Prompt、RAG、工单和训练路径隔离。
  • Runner 镜像、适配器、Judge、Policy 与 Parser 均有固定版本。
  • 租约失效不会改变 Provider 逻辑调用键。
  • 未知副作用不会被盲目重试。
  • expected manifest 独立于实际 Result 查询。
  • 无效和缺失进入分母，零分母为 UNKNOWN。
  • Candidate 与 Baseline 对同 Case 配对。
  • 关键 Slice 硬门先于总体效用。
  • Gate Policy 不允许 NaN、无限值或方向不明的阈值。
  • RBAC 同时校验主体角色、租户、资源和目的。
  • Secret 只以引用进入任务，异常链路也不打印。
  • Trace 不默认记录 Prompt、输出和检索原文。
  • Evidence Export 有范围、manifest、缺口和独立验证材料。
  • 成本按调用幂等入账并保留估算/对账状态。
  • 队列容量按峰值、长尾、限流和重试压测，不只看平均吞吐。
  • 平台故障与质量失败使用不同状态和告警。

二十一、平台边界与演进顺序

21.1 Dataset Registry 不是数据治理全部

Registry 能固定已登记对象和血缘，不会自动修正错误 Oracle、代表性不足、历史偏差或未经授权的数据来源。数据 owner、业务专家、隐私和安全角色仍需参与。

21.2 Trace 不是审计真实性证明

Trace 关联调用和尝试，便于排障与复核；它不证明生产者没有说谎，也不证明未定义的事件没有缺失。高风险流程需要独立业务分母、目标状态和检查点。

21.3 多租户不等于共享一切

控制面可以共享，数据域、密钥域、Runner Pool 或 Evidence Vault 是否共享要按分类和威胁模型决定。高敏租户可能需要物理或账号级隔离；低风险项目则可通过逻辑隔离降低成本。

21.4 平台不替代 CI 中的小测试

Prompt 模板变量、JSON Schema、权限规则和纯函数应在代码仓库里快速测试。平台适合承担需要版本数据、外部适配器、统计聚合和跨角色证据的任务。把所有单元测试远程化会增加反馈时间和故障面。

21.5 推荐演进顺序

  1. 先定义 Snapshot、RunSpec、Result 和 Gate Decision；
  2. 再做命令行 Runner 与内容摘要；
  3. 引入队列、租约、幂等和成本账本；
  4. 增加 Trace、分母核对和 UNKNOWN；
  5. 加入 RBAC、租户、Secret Broker 与证据导出；
  6. 最后扩展 UI、自助编排、趋势、弹性和跨区域。

如果从排行榜和拖拽编排开始，底层对象身份仍然不稳定，后续每个功能都会放大不可复现问题。
