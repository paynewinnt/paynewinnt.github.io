AI测试-59-Model-Card-System-Card和AI风险分级怎样进入交付流程

发表于 2026-06-13 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:01

发布页面上有一份 Model Card，能不能说明整个 AI 产品已经经过风险评估？

不能。

Model Card 可能只描述基础模型，而真实产品还包含 System Prompt、检索库、权限过滤、路由、工具、缓存、UI 和人工流程。模型本身不能调用外部系统，不代表接入工具后的应用没有副作用；模型卡上的评测通过，也不代表生产 Prompt、地区政策和数据权限仍处在同一证据边界。

再换一个问题：团队写了一份很长的 System Card，列出几十项测试和缓解措施，是否就可以上线？

仍然不能。

文档存在不等于引用的工件是当前候选，不等于风险都有负责人，不等于残余风险被明确接受，也不等于审批绑定了文档生成后的最终内容。一个可以在批准后继续被编辑的 Markdown 文件，无法单独证明谁批准了什么版本。

一、边界：四类工件回答四个不同问题

本文使用四类交付物：Model Card、System Card、Risk Register 和 Release Evidence Bundle。它们可以互相引用，但不能互相替代。

交付物 主要主体 核心问题 时间属性 不能替代什么
Model Card 一个固定模型工件或模型服务版本 模型为哪些用途开发、如何评测、在哪些因素和限制下表现怎样 随模型版本更新 不能代表具体应用的数据流、工具和运营控制
System Card 一个固定系统版本及其部署语境 模型与 Prompt、RAG、工具、UI、人怎样组合，系统风险和缓解证据是什么 随系统与场景更新 不能替代持续风险台账或发布审批快照
Risk Register 风险场景及其全生命周期状态 风险如何发生、影响谁、控制是什么、残余风险和 owner 是谁 持续演化 不能证明某个候选已跑完指定评测
Release Evidence Bundle 一个 exact release candidate 此刻要发布的工件、Card、风险、评测、适用性和审批是否一致、有效且完整 不可变发布快照 不能代替上线后的监控、事故响应和重评测

1.1 Model Card 的原始边界

Mitchell 等人在 2019 年 Model Cards 原论文中提出一种模型报告框架，讨论模型详情、预期用途、影响表现的因素、指标、评测与训练数据、定量分析、伦理考虑、 caveat 与建议。论文用两个监督学习模型作示例。它提供了重要的透明度结构，但不是对所有现代生成式 AI 系统都具有法律效力的统一模板，也没有声称一张卡能证明产品安全。

工程上应把 Model Card 绑定到不可变 checkpoint、权重摘要或可识别的托管模型版本。若供应商无法提供精确工件摘要，Card 必须声明版本识别限制、观察时间和重新验证策略；不能把一个滚动别名永久当成同一模型。

1.2 System Card 的实践边界

“System Card”在行业实践中常用来描述模型经过训练、后训练、产品控制和部署后的整体安全评估。OpenAI 的 GPT-4 System Card 与 GPT-4o System Card 是官方实例：它们记录风险识别、评测、外部红队、缓解、已观察到的挑战和系统层考虑。实例说明了系统级报告可以比模型性能表更广，但System Card 不是一个全球统一的法定模板，不同机构、系统和用途的章节、证据强度与披露边界可以不同。

本文把 System Card 定义为组织内部的版本化系统事实与证据视图。这个定义用于工程交付，不宣称得到任何监管机构的认证。

1.3 Risk Register 的边界

Risk Register 是活的治理记录。每项风险至少包含场景、来源、受影响对象、已有控制、证据、剩余不确定性、残余风险、负责人、状态、下一次评审时间和触发条件。它允许一项风险从 identified 进入 mitigating、mitigated、accepted、transferred 或 closed，并保存历史。

风险“closed”不等于永远消失。关闭依据若过期、作用域改变或事故复发，应重新打开。把 Risk Register 导出成发布附件时，应生成带摘要的快照，不应让后续台账编辑改变旧发布记录。

1.4 Release Evidence Bundle 的边界

Evidence Bundle 是机器可验证的发布清单。它不必是一份 PDF，可以是结构化 manifest 加不可变附件。核心是：发布候选、Card、风险快照、评测结果、适用性记录和审批都通过稳定 ID 与内容摘要绑定。

Bundle 通过只能证明预注册门禁在生成时满足。它不能证明上线后没有漂移，也不能证明未覆盖用途安全。因此还要包含监控、回滚、过期和重评测触发器。

二、九个常见反例：为什么“文档齐全”仍可能假合规

2.1 Model Card 与生产模型不是同一个版本

反例：Card 标题写 model-x-latest，评测在 4 月完成，供应商 6 月静默更新了服务端模型。应用仍引用旧 Card，却没有保存返回版本或行为漂移证据。

修复不是改标题日期，而是让候选 manifest 记录模型标识、可用摘要、区域和观察窗口；不能精确固定时，设置短有效期和核心哨兵重跑。证据不能比主体更确定。

2.2 Model Card 通过，系统仍会越界

反例：模型隔离测试只生成文本，生产系统却增加了可写工具；参数绑定器把模型建议直接映射成动作。模型卡没有覆盖授权、幂等、审批和补偿，系统风险完全不同。

System Card 必须描述组件、信任边界和副作用阶段；工具权限变化应触发安全、权限、业务后置条件和事故演练重评测，而不是仅重跑文本 benchmark。

2.3 System Card 很完整，但不知道对应哪个配置

反例：文档写“启用了敏感信息过滤”，没有过滤器版本、阈值、执行顺序和配置摘要。生产中一个地区节点把过滤放在日志写入之后，文档仍然“正确”描述了设计意图。

Card 中的人类叙述要连接到结构化 component manifest。每项关键控制至少有 control_id、owner、implementation_ref、version、placement、evidence_ids 和运行状态。设计存在与控制有效是两项证据。

2.4 风险分数低，所以无需证据

反例：用 likelihood × impact 得到 4 分，低于 5 分就跳过测试。但 likelihood 来自没有线上数据的主观估计，impact 也没有考虑不可逆影响和受影响群体。乘法制造了精确感，没有消除不确定性。

内部风险等级可以帮助分配证据强度，却必须保留依据、置信、未知和 override。任何 forbidden use、critical hard risk、法律适用性未决或高影响不可逆场景都可以独立阻断，不能被一个总分平均。

2.5 风险有缓解措施，所以 residual risk 已接受

反例：Risk Register 写着“增加人工复核”，却没有人工容量、SLA、权限、抽检结果和超时动作。状态被改成 mitigated，实际上控制从未验证。

缓解计划、控制已实现、控制有效、残余风险接受必须分开。接受需要具名、有权限的 owner、适用范围、理由、补偿控制和到期时间；高风险硬门不能用普通风险接受绕过。

2.6 审批人都点过同意，所以候选可以发布

反例：安全负责人批准后，工程师又更新 Prompt 和检索过滤；审批系统只保存“已批准”，没有绑定内容摘要。最终上线的不是审批时看到的候选。

审批应绑定 pre-approval manifest digest。任何进入摘要的字段变化都使旧审批失效，重新计算 diff、证据和所需角色。不能允许批准后原地编辑附件。

2.7 评测报告存在，所以风险证据覆盖为 100%

反例：风险 R-17 引用了报告 eval-92，报告确实存在，但评测对象是旧 Prompt，数据只覆盖英文，结果字段是 unknown。引用完整不等于证据有效。

证据映射至少检查：风险 ID、控制 ID、主体摘要、数据快照、切片、结果、unknown、生成时间、有效期和适用 change types。文件能打开只是最弱的完整性检查。

2.8 内部 T3 等于欧盟 AI Act 的 high-risk

反例：组织把内部工程等级命名为“高风险”，然后在材料中写“属于/不属于 EU high-risk”。内部等级基于自己的产品策略；欧盟法规分类取决于官方条款、附件、系统用途、运营者角色和具体事实。二者可能相关，但不是同一个分类器。

正确做法是保留独立 regulatory_applicability_record，记录 jurisdiction、角色、事实、依据、结论状态、专业 owner、官方来源、评审日期和到期触发。内部代码只能检查记录是否完成，不能凭 T1–T4 自动产出法律结论。

2.9 Card 公开得越详细，透明度越高

反例：System Card 披露了可被利用的检测阈值、内部端点、未修复漏洞复现细节或个人信息。透明度与安全、隐私、知识产权和攻击面之间需要分层披露。

可以区分内部完整 Card、审计者视图、客户/用户公开摘要。任何删减都要有 reason code，公开摘要不能反过来成为内部发布证据的唯一来源。

三、贯穿构造场景：客服草稿助手 Aurora Assist 7.2

本文使用一个完全虚构的系统 Aurora Assist。它为客服人员生成回复草稿，不直接发送，不自动改变账户状态。版本 7.2 准备把基础模型从 model-a17 升级到 model-a18，同时更新 System Prompt 和引用格式。

3.3 四类工件

候选发布需要：

  1. model-card/model-a18/v3：模型版本、训练知识边界、 intended/forbidden use、模型隔离评测与限制；
  2. system-card/aurora-7.2/v1：组件、数据流、控制、系统评测、红队、运营和限制；

四、证据驱动交付架构

图中的 Card 编译器不是生成文案的语言模型，而是一个结构化证据装配器。它可以把结构化字段渲染成人类可读 Markdown/PDF，但发布门禁读取的是经过 Schema 校验的事实与引用。

4.1 Source of truth

不同事实有不同 owner：

事实 推荐来源 不可靠替代
模型工件与版本 artifact/model registry 或供应商固定版本记录 手写 Card 标题
系统组件 构建 manifest、部署配置、SBOM/AI BOM 架构图中的“latest”
intended/forbidden use 产品能力合同与批准策略 README 中的泛化描述
评测结果 不可变 run record 与数据快照 粘贴到文档的百分比
风险状态 有审计历史的 Risk Register 发布会议纪要
适用性 专业 owner 的版本化记录与官方来源 内部风险分数自动推导
审批 绑定 manifest digest 的批准记录 聊天消息“看过了”

Card 不应成为所有事实的唯一编辑入口。它是这些事实的投影视图；源记录更新后生成新版本，并保留旧版本对应的发布历史。

4.2 Evidence compiler

编译过程至少执行：

  1. 解析 exact release candidate 和 component digests；
  2. 检查 Model Card 与模型主体一致；
  3. 检查 System Card 与系统 manifest、模型引用和 intended use 一致；
  4. 解析 active risks、控制与 evidence IDs；
  5. 验证评测主体、数据、结果、unknown、覆盖和有效期；
  6. 根据 version diff 计算需要重跑的证据类型；
  7. 检查 known limitations 是否有 owner、监控和使用限制；
  8. 检查残余风险接受是否有权限、理由和到期；
  9. 检查监管适用性记录是否完成且未过期；
  10. 计算 pre-approval digest，再收集绑定该摘要的角色审批。

任何缺失都输出结构化 BLOCK 或 UNKNOWN，不能让生成模型自动补一句“已充分评估”。

4.3 Immutable bundle

Bundle 中每个引用都带稳定 ID、版本、内容摘要和取得时间。审批完成后生成最终包并写入只追加 registry。部署控制面只接受已签名/已验证的 Bundle ID；环境中实际组件摘要必须与 Bundle 匹配。

若需要紧急回滚，应选择一个仍在有效期内、环境兼容且已批准的旧 Bundle。不能只把模型版本改回去，却保留新 Prompt、旧风险台账和未知策略组合。

4.4 Continuous loop

上线后的事件、漂移、申诉、控制失效和监管变化不会修改旧 Bundle，而是创建新风险事件或新候选。这样才能回答“某天某次发布依据什么证据”。

五、Model Card：围绕模型主体写，不把系统能力塞进去

5.1 Model details

至少记录：

  • 模型 ID、版本、权重或服务标识、提供者、许可和取得方式；
  • 模型类型、输入/输出模态、上下文与接口约束；
  • 训练/后训练已知边界、知识时间信息和不公开项；
  • 运行所需依赖、量化/微调/适配器和派生关系；
  • Card owner、批准状态、生成时间和有效期。

不能取得的训练信息明确写 not provided，并说明由此限制了哪些评估。不要用推测填空。

5.2 Intended use 与 out-of-scope use

Model Card 的 intended use 应描述模型层能力和预期使用条件，例如“在人工复核下生成客服草稿”，而不是直接声称“符合所有客服法规”。还要列出合理预见但未评测的 use，以及明确 forbidden use。

模型 intended use 与系统 intended use 必须求交集。模型允许某用途，不代表系统数据、UI 和控制足以支持；系统选择的用途若不在模型 Card 范围，发布门禁应要求补证据或阻断。

5.3 Factors、metrics 与 disaggregation

原始 Model Cards 论文强调影响表现的相关因素与分条件结果。生成式系统可以扩展为语言、文档类型、会话长度、用户角色、输入噪声、上下文质量和工具状态，但每个指标要写清任务、Oracle、分母、unknown 和不确定性。

模型卡不能只列一个 benchmark 总分。对 Aurora，需要模型隔离的引用完整性、拒答/过度拒答、事实支持、结构输出和语言切片；但端到端 ACL、检索和 UI 指标属于 System Card。

5.4 Known limitations

限制不是“模型可能出错”这样的空话。每项至少包含：

例如“在未覆盖语言上引用 span 解析不稳定，所以路由器禁用该语言”是可执行限制；“结果仅供参考”不是控制。

5.5 Model Card 不能证明什么

  • 不能证明应用的检索权限正确；
  • 不能证明生产 Prompt 与模型评测 Prompt 相同；
  • 不能证明最终 UI 强制人工复核；
  • 不能证明工具没有副作用；
  • 不能证明供应商滚动别名没有变化；
  • 不能证明产品在未列语言和受众上的质量；
  • 不能替代系统级事件、监控和回滚证据。

六、System Card：把模型放回真实系统与使用场景

6.1 System boundary

System Card 首先回答“系统是什么”：入口、身份、数据源、模型、Prompt、检索、工具、策略、后处理、UI、人和外部依赖。边界图要标信任域、数据类别、权限检查和副作用点。Card 里的 system ID 与部署 manifest 必须一致。

同一个模型用于离线总结和自动账户动作，是两个风险完全不同的系统。不要用一个通用 System Card 覆盖所有产品。

6.2 数据与控制流

对 Aurora，应记录：

每个控制写明 placement 和 fail behavior。ACL 超时是 fail closed、人工升级还是继续？引用验证失败会删除草稿还是只打警告？这些不是实现细节，而是 residual risk 的决定条件。

6.3 System-level evaluation

System Card 应把模型隔离与端到端结果分开：

  • 模型隔离：基础回答、拒答、引用、语言和长上下文；
  • 组件：ACL、Prompt assembly、遮盖、引用解析、UI 状态机；
  • 端到端：真实入口与身份、权限、检索、模型、后处理和人工确认；
  • 红队：跨租户、提示注入、工具/权限和信息泄漏；
  • 故障：依赖超时、旧缓存、部分部署、日志丢失和回滚；
  • 运营：延迟、容量、人工复核、SLO、告警与事件演练。

一份 System Card 可以引用这些报告，但不能只抄最高分。FAIL、unknown、样本不足和未覆盖切片必须可见。

6.4 Mitigation evidence

每个 mitigation 连接到：风险、实现、验证、运行监控和 owner。

如果只能说“我们有过滤”，证据链仍不完整。

6.5 System Card 不是统一法定模板

官方 System Card 实例可以作为报告方法参考，但不能据此声称所有组织必须采用同一章节，也不能把“发布了 System Card”写成监管认证。系统 Card 的公开范围、内部深度、独立评审和更新周期应由用途、风险和适用要求决定。

七、Risk Register：从风险句子走到责任与残余风险

7.1 风险要写成场景

“幻觉风险”太宽，无法映射控制。更可测试的写法是：

场景包含触发条件、系统行为、使用者路径和影响。然后才能设计时效过滤、引用 entailment、UI 警示、抽样复核和回滚。

7.2 最低字段

字段 要回答的问题
risk_id / version 哪项风险、何时发生过变化
scenario 条件、失败链和影响是什么
affected_parties 谁可能受到影响，是否有脆弱群体
impact / likelihood / exposure / uncertainty 依据是什么，哪些仍未知
inherent_tier 控制前需要多强证据
controls[] 预防、检测、响应和恢复分别是什么
evidence_ids[] 哪些评测支持控制有效
residual_risk 控制后仍剩什么及边界
status / owner 当前动作与最终责任人
accepted_by / expires_at 谁在何范围和期限接受
reopen_triggers[] 哪些变化必须重新评估

7.3 风险状态机

建议状态至少区分：

证据 FAIL 或过期会把 MITIGATED 退回 VALIDATING/MITIGATING；事故命中 reopen trigger 会重新打开。不能只允许状态向“完成”方向移动。

7.4 Residual risk acceptance

接受不是“修不了先上”。记录中要有：

  • 具体剩余风险和受影响范围；
  • 为什么现有控制与业务价值支持接受；
  • 哪些用途、地区、用户或流量被排除；
  • 监控与自动止损；
  • 接受人权限；
  • 到期时间与再评审触发；
  • 用户告知或人工监督条件。

forbidden use、未关闭 critical hard gate 和明确法律阻断不能通过普通接受流程绕过。哪些风险允许接受，由组织政策与适用要求决定。

八、内部风险分级：决定证据强度，不冒充法律分类

图中的 T1–T4 是本文构造的内部工程分级，不是 NIST 等级，也不等于 EU AI Act 或任何法规类别。

8.1 分级主体是 system × use × context

风险等级不能只绑定模型名。建议主体写成：

同一模型用于内部离线草稿可能是 T1/T2，用于高影响自动决策可能是 T4。用途或权限改变就要重新分级。

8.2 分级依据

至少考虑：

  • 影响严重度与受影响对象；
  • 暴露规模、频率和持续时间；
  • 自动性、用户依赖和人工可纠正性；
  • 错误可逆性、发现时延和补救成本；
  • 数据敏感性、权限和跨边界处理；
  • 模型能力、工具副作用和攻击面；
  • 证据成熟度与不确定性；
  • 适用的合同、行业和监管要求。

ordinal 字段可以形成矩阵用于排序，但不要把 4×3×2=24 当成真实概率或货币损失。分级报告保留 rationale、证据、unknown、override 和批准人。

8.3 四级构造门禁

  • T1 探索：离线隔离，无真实用户和业务依据；需要来源、数据权限、基础测试、owner 和到期；
  • T2 辅助：低影响、可撤销、人审；需要 Model/System Card、核心质量/安全/隐私证据、监控与回滚；
  • T3 重大：广泛外部暴露、实质用户影响或工具动作；需要风险—控制—证据全映射、独立保留集、红队、故障、SLO、跨职能审批和事件演练；
  • T4 严重：潜在生命、基本权利或系统性影响，难逆转或高自主；默认阻断，逐项授权，并增加独立验证、硬风险、分阶段能力和高级风险接受。

证据要求单调增强，但不是“凑齐更多文档”。T3 的 ACL 隔离失败，不能靠多上传三份报告通过。

8.4 Risk tier override

以下情况可直接提升等级或阻断：

  • intended use 发生实质变化；
  • 引入写工具、自动执行或更高权限；
  • 面向未成年人或其他需额外保护群体；
  • 数据敏感性或跨地区处理扩大；
  • 事故显示先前 likelihood 假设错误；
  • 监管适用性未决且潜在义务重大；
  • 关键控制没有可验证证据；
  • 系统难以回滚或影响不可逆。

降级需要新证据和批准，不能因为项目延期临时改等级。

8.5 用反事实问题校验分级是否真的绑定场景

分级评审不应只让参会者给影响和概率打分。更有效的方法，是逐项提出会改变等级或门禁的反事实：

  • 如果草稿从“必须人工确认”改为自动发送，等级和必要证据会怎样变化？
  • 如果只读检索增加一个可写账户工具，哪些风险从信息错误变成真实副作用？
  • 如果用户能够看见引用与撤回发送，错误可逆性是否真的提高，还是只把责任转给用户？
  • 如果系统扩展到未验证语言、未成年人受众或新的地区，哪些 Card、适用性和评测立即过期？
  • 如果监控在 24 小时后才能发现错误，当前 impact 与 recovery 假设是否仍成立？
  • 如果人工复核队列在高峰时跳过确认，所谓 human-in-the-loop 是否只是流程图上的控制？
  • 如果同一输出被下游另一个服务自动执行，本系统的“仅建议”边界是否已经失真？
  • 如果供应商无法提供精确模型版本，怎样缩短证据有效期并扩大在线哨兵？

这些问题把分级从抽象模型标签拉回真实数据流和使用路径。评审记录应保存关键反事实、回答依据和触发器。下一次组件或业务变化命中触发器时，流水线自动打开重新分级任务，而不是等待年度审查。

8.6 不确定性本身会提高证据要求

风险未知不能默认按最低等级处理。若影响可能很高，但 likelihood 因缺少数据无法估计，可以通过限制用途、缩小流量、增加人工监督和收集证据来降低暴露；在证据形成前，发布决定应是 RESTRICT 或 BLOCK。把 unknown 填成“低概率”只是让表格完整，没有降低风险。

内部等级还应记录置信来源：历史事故、生产样本、受控实验、专家判断或纯假设。两个同为 T3 的系统，如果一个有稳定在线证据，另一个主要依赖假设，后者需要更短复审周期和更强灰度，而不是因为标签相同就获得相同权限。

九、风险—控制—评测映射：引用存在不等于证据有效

9.1 Evidence record

每条评测证据至少包含：

result 应支持 PASS、FAIL、UNKNOWN。流水线错误、Judge 无结果、样本不足和主体不匹配属于 UNKNOWN 或 INVALID，不是 PASS。

9.2 Evidence coverage

设 active risk r 的内部权重为 w_r，其所有必要证据均存在、主体匹配、PASS 且未过期时 covered(r)=1：

这个指标适合展示整体证据完整性，但不能抵消 hard gate。一个 critical risk 未覆盖，即使其他风险让 coverage 达到 99%，仍应 BLOCK。权重依据、必要证据集合和过期规则必须预注册。

还要报告：

  • active risk 总数与 covered 数；
  • hard risk 的 PASS/FAIL/UNKNOWN；
  • 每类 required evidence 是否存在；
  • 每种 change type 是否有新鲜证据；
  • 卡片中引用但 Bundle 中缺失的 orphan refs；
  • Bundle 中存在但没有风险/控制消费的 orphan evidence。

9.3 评测覆盖与风险覆盖不同

评测覆盖描述任务、语言、切片和数据是否被测；风险证据覆盖描述每项风险是否有合适证据。一个英文准确率评测可能覆盖大量 case，却没有覆盖 ACL 风险；一项精确的权限测试 case 很少，却是某风险的关键证据。

9.4 Evidence freshness

有效期取决于主体稳定性和风险。确定性 ACL 组件测试可能在代码摘要不变时长期有效；远程模型行为、生产分布和人工流程证据有效期更短。不要给所有报告统一 365 天。

证据可以因以下事件提前失效：组件变更、数据漂移、事故、策略更新、Judge 缺陷、法规适用性变化、供应商模型漂移或控制监控异常。

9.5 证据独立性与相关失败

五份由同一脚本、同一数据和同一 Judge 生成的报告，不是五份独立证据。若 Judge 把带引用的流畅回答普遍判为正确，质量、安全和风险报告可能一起假绿。Evidence record 应保存共同依赖，并在汇总时标注相关性。

高风险门禁可以要求至少一种不同机制的证据，例如确定性后置条件、盲化人工复核、独立数据源或不同实现的检测器。这里的“独立”不是要求外部机构参与所有测试，而是要求团队知道哪些结论共享同一个可能失效的 Oracle。

第三方评测也不能天然当独立真值。要核对其主体版本、任务、数据、冲突关系和适用切片；只有名称相同但配置不同的 benchmark 结果不能直接合并。无法复现的外部数字可以作为背景，不应成为唯一发布硬门。

9.6 证据中的负结果与未决项

Card 不应只渲染 PASS。对每个 FAIL/UNKNOWN，要写明受影响风险、当前能力限制、owner、下一步和决定。若某切片样本不足，正确表达是“证据不足且该切片未获发布授权”，不是“尚未发现问题”。

负结果也有有效期和主体。修复后不能删除原失败，而应新增复测证据，通过 supersedes 或 retest_of 连接。这样事故调查可以看到失败、修复和独立复测的完整时间线，避免只剩最终绿色报告。

十、版本 diff：什么改变，就重测什么；无法判断时保守扩展

10.1 变更分类

Change type 至少影响的证据
MODEL_ARTIFACT 模型质量、安全、偏差/公平、性能、成本和系统回归
SYSTEM_PROMPT 指令层级、内容安全、引用、结构化输出和端到端回归
RETRIEVAL_DATA/PIPELINE 权限、时效、召回、引用、泄漏、摄取和回滚
TOOL_PERMISSION 最小权限、授权、参数绑定、副作用、幂等、补偿和红队
SAFETY_POLICY eligibility、漏拦截、误拒答、改写、升级和一致性
ROUTER 候选适用、Fallback、隐私、成本、延迟和最差切片
JUDGE/ORACLE 历史结果重判、Judge 偏差、unknown 和门禁可信度
UI/HUMAN_FLOW 告知、人工复核、过度依赖、申诉和无障碍
OBSERVABILITY 检测覆盖、告警、证据完整性与事故响应

映射是最低集合，不是上限。组合变化会产生交互，需要端到端回归。

10.2 Semantic diff

文本行 diff 不够。Prompt 改一个标点可能无行为影响，也可能改变结构协议；工具 Schema 字段顺序变化可能触发模型行为。应同时计算：内容摘要、结构 diff、政策规则 diff、权限 diff、数据快照 diff和行为哨兵 diff。

10.3 Re-evaluation triggers

即使没有代码提交，下列事件也可触发：

  • 托管模型滚动更新或行为哨兵漂移；
  • intended/forbidden use 或目标用户变化；
  • 新地区、角色、语言、渠道或模态；
  • 事故、near miss、投诉或申诉聚类；
  • 风险接受、证据或适用性记录到期；
  • 监控显示控制有效性下降；
  • 官方法规、标准或合同要求变化；
  • 上游/下游依赖的安全公告或撤回。

触发器应创建新评审任务，不原地把旧 Card 日期改成今天。

十一、审批：角色、职责和绑定摘要

11.1 谁批准什么

  • model owner：模型身份、来源和模型层证据；
  • system owner：系统边界、组件、部署和运行责任；
  • product owner：intended/forbidden use、用户影响和能力限制；
  • safety/security/privacy owner：对应风险与控制证据；
  • domain owner：业务真值、人工流程和影响边界；
  • regulatory applicability owner：适用性事实、角色、官方依据和未决项；
  • risk acceptance authority：在授权范围和期限内接受残余风险；
  • release authority：确认门禁与灰度条件并批准部署。

一个人可以承担多个角色，但记录中不能把组织名当责任人。高等级系统应考虑职责分离和独立复核。

11.2 Approval state

审批至少有 APPROVE、APPROVE_WITH_RESTRICTIONS、REJECT、NEEDS_INFORMATION，并绑定 manifest digest、角色、批准人、时间、范围、限制和到期。NEEDS_INFORMATION 不能被流水线当作软通过。

11.3 Exception

例外记录要写缺失门禁、业务理由、补偿控制、适用流量、负责人、监控、自动停止和到期。例外不能覆盖 forbidden use 或组织定义的 non-waivable hard gate。到期自动 BLOCK，而不是等人发现。

十二、监管适用性：单独记录，不让代码作法律判断

12.1 NIST AI RMF 的正确位置

NIST AI RMF 1.0 是自愿、非行业特定、面向风险管理的框架，Core 使用 GOVERN、MAP、MEASURE、MANAGE 四类功能。它可以帮助组织设计责任、场景映射、测量和风险处置，但不是产品认证，也不自动满足某项法律。

NIST AI 600-1 是面向生成式 AI 的 AI RMF Profile，提供跨生命周期的风险与行动参考。组织可以把其建议映射到 Risk Register、System Card 和证据门禁，但要保留适用性选择和实现证据，不能把“引用了 NIST”写成“符合 NIST 认证”。

12.2 欧盟 AI Act 的限定说明

欧盟《人工智能法案》正式文本是 Regulation (EU) 2024/1689。官方 Article 113 规定总体上自 2026-08-02 起适用，同时列出若干更早或更晚适用的章节和条款。本文发布日期 2026-06-13 时，部分规定已按 Article 113 的阶段安排适用，而总体适用日期尚未到来。项目必须核对当时生效部分、后续修订/指南、具体角色和事实，不能只写一个统一日期。

法案对 prohibited practices、high-risk AI systems、特定透明度义务以及 general-purpose AI models 等有不同结构。高风险分类涉及 Article 6 与相关附件；高风险系统的风险管理、技术文档和向 deployer 提供信息等要求分布在相应条款；GPAI 与具有 systemic risk 的 GPAI 又有单独章节和义务。某系统是否落入这些范围，取决于用途、产品关系、运营者角色、市场/使用地域和事实，不由本文内部 T1–T4 自动决定。

12.4 监管映射不是文档复制

若适用要求涉及风险管理、技术文档、日志、透明度、人类监督、准确性/稳健性/网络安全或上市后监控，应把每项义务映射到现有控制和证据。一个 System Card 可以作为部分输入，但不应假设它天然等同于法定技术文档。映射由专业 owner 维护，并明确哪些证据另存于受控附件。

十三、自动化：Card as code，而不是 prose as truth

13.1 Schema 与 lint

为四类工件定义版本化 Schema，校验 required fields、枚举、时间、稳定 ID、摘要格式和引用存在性。lint 还应检查：

  • intended/forbidden use 冲突；
  • Card 主体与候选摘要不一致；
  • active risk 无 owner、控制或 evidence；
  • mitigation 写了“人工复核”却没有 queue/SLA/monitor；
  • known limitation 没有受影响范围和限制；
  • evidence FAIL/UNKNOWN 被当 PASS；
  • residual acceptance 缺权限或过期；
  • applicability 未决；
  • approvals 绑定旧 digest；
  • 变更类型没有对应重评测。

13.2 生成式辅助的边界

语言模型可以根据结构化事实起草摘要、统一术语或发现缺失问题，但不能成为 source of truth，也不能自动决定风险关闭、适用性或批准。生成内容必须标来源，关键数字和结论回到 evidence record。

13.3 三层验证

  1. Schema/引用完整性：字段存在、类型正确、ID 可解析、digest 匹配；
  2. 语义一致性：intended use、风险、控制、证据与限制逻辑一致；
  3. 执行真实性：部署环境实际组件、权限、监控和回滚与 Bundle 相同。

只做第一层会得到格式正确的空文档，只做第三层又无法解释治理依据。

13.4 CI 与发布流水线

  • PR：Schema、unit test、diff 分类、引用 lint；
  • nightly：过期扫描、orphan evidence、供应商版本哨兵；
  • release candidate：重评测矩阵、完整 bundle compile、角色审批；
  • deploy admission：签名、digest、环境 manifest 和作用域匹配；
  • post-deploy：证据新鲜度、风险触发、incident/complaint 和 rollback drill。

十六、示例代码的证据边界

正常构造 Bundle 有三个 active risk，五种 T3 所需证据，两个 change types，一个唯一 jurisdiction 适用性记录和六类审批角色。候选的 system digest 由 system ID、版本、模型摘要与排序后的组件清单确定性计算；审批同时绑定用途、地区、当前摘要和有效期；全部引用、摘要、时间因果与 back-reference 一致时，门禁通过，风险证据覆盖为 100%。

代码刻意不做三件事：

  1. 不根据内部 Tier 自动判断 EU AI Act 分类；
  2. 不根据报告文件名推断评测有效；
  3. 不允许审批在内容变化后继续有效；
  4. 不允许 CLOSED 跳过 owner、控制、证据、关闭依据和重开条件，也不允许关闭时间早于关闭证据生成时间；
  5. 不允许同一当前摘要上的 REJECT 或 NEEDS_INFORMATION 被另一个 APPROVE 淹没。

rebind_bundle 在测试中模拟“内容合法变化后重新计算摘要并重新绑定构造审批”，方便只测试语义门禁。test_manifest_tamper... 则故意不 rebind，证明批准后修改会被完整性检查发现。示例把 Bundle 快照限制为每个 jurisdiction 一条适用性记录、每个角色恰好一个当前权威决定，并使用构造的 30 天审批新鲜度上限；真实审批历史应在只追加存储中用显式版本与 supersedes 关系保留，不能靠元组顺序推断哪个决定更新。真实系统还应使用签名、受控身份、时间戳和只追加存储，教学 SHA-256 不能单独证明签署者身份。

风险 coverage 只在所有列出的证据都 current/pass 时记覆盖。生产系统还应区分必要/辅助证据、控制层级、切片 coverage 和证据独立性；示例把它们简化为紧凑的确定性规则。

十八、完整构造事故案例：部署组件与 Bundle 漂移

另一个构造事故发生在发布后第 12 天。运维为修复延迟，临时把引用验证器从 citation-check-7 切到 citation-check-fast，没有经过 release pipeline。新组件只检查引用 ID 存在，不检查段落是否支持 claim。

18.1 观测

  • 在线支持率没有明显下降；
  • 传统健康检查全绿；
  • 抽样复核发现“答案正确但引用旧条款”的比例上升；
  • deploy admission 只在首次发布检查，运行中没有 drift reconciliation；
  • System Card 仍写着 entailment verification 已启用。

18.2 直接原因、贡献因素与检测缺口

  • 直接原因：未经批准的组件替换改变引用控制语义；
  • 贡献因素：紧急变更流程没有生成新候选，组件名相似且配置界面允许绕过；
  • 检测缺口：运行时没有持续比对 Bundle manifest，也没有引用支持率的实时 hard gate。

不能把“System Card 过期”当直接原因。Card 是旧事实快照，真正的控制缺陷是部署漂移未被阻止和发现。

18.3 止损与证据保全

系统回滚到 citation-check-7，冻结临时组件，保留受影响时间窗的 deployment events、manifest、sample IDs 和用户可见输出摘要。Risk Register 重开 R-STALE-CITATION，旧 Bundle 保留不修改；新候选补充 runtime drift monitor、紧急变更审批和定期 reconciliation。

18.4 重评测

复测不仅跑原事故样本，还包括旧/新政策、正确答案错误引用、错误答案正确文档、引用不可达、超时和回滚组合。System Card v2 明确引用验证的 placement、fail behavior 和 monitor；新审批绑定 v2 和新的 Bundle。

十九、Card 发布与披露策略

19.1 内部完整视图

包含工件摘要、详细风险、未修复项、阈值、故障证据、适用性和审批。访问按角色控制，修改走版本流程。

19.2 审计/客户视图

根据合同与适用要求提供必要证据，保留稳定 ID，使接收方能追踪版本。敏感安全细节可进入受控附件，但不能把所有限制删掉后仍声称完整。

19.3 公开视图

解释 intended use、forbidden use、系统边界、主要评测、已知限制、用户控制和反馈渠道。公开数字要带版本、日期、任务、分母和适用范围。红队细节可以延迟或抽象披露，避免增加现实攻击面。

19.4 三种视图的一致性

三者由同一结构化事实生成，公开视图只是经过批准的字段投影。若内部 Card 标记某语言未验证，公开页面不能写“支持全球语言”。披露差异要有 policy 与 owner。

二十、落地路线

阶段一：建立 release candidate identity

先让模型、Prompt、检索、工具、策略、UI 和监控有稳定版本/摘要。没有 exact candidate，所有 Card 都只能是模糊说明。

阶段二：把四类工件分开

Model Card 围绕模型，System Card 围绕系统，Risk Register 管生命周期，Bundle 管一次发布。定义 Schema、owner 和引用。

阶段三：风险—控制—证据最小闭环

为高优先级风险建立场景、控制、评测和 monitor。FAIL/UNKNOWN、过期和主体不匹配必须阻断。

阶段四：风险分级与变更矩阵

按 system × use × context 分级，定义 T1–T4 最低证据和审批；建立 component change → re-evaluation 映射。

阶段五：适用性与审批摘要

建立独立 jurisdiction/role/facts 记录，由专业 owner 评审；计算 pre-approval digest，所有批准绑定摘要。

阶段六：部署 admission 与持续 reconciliation

部署前比对 Bundle，运行中持续检查组件漂移、证据过期和风险触发。紧急变更也创建新候选和时限，不旁路证据链。

阶段七：事故与披露闭环

事故重开风险、生成新评测和 Card；旧 Bundle 永久保留。内部、审计和公开视图由同一事实源生成。

二十一、可执行检查清单

主体与边界

  • release candidate 有唯一 ID、系统摘要和完整 component manifest；
  • 模型权重/API 版本可识别，无法固定时限制证据有效期；
  • Model Card 主体与候选模型完全匹配；
  • System Card 主体、模型引用和部署系统完全匹配；
  • system boundary 包含入口、身份、数据、模型、Prompt、RAG、工具、UI、人和外部依赖；
  • intended use 具体到系统、角色、人工监督和输出用途；
  • forbidden use 有技术阻断，不只是免责声明；
  • 模型 intended use 与系统 intended use 求交集；
  • 新用途、新权限和新地区创建新评审，不沿用旧结论；
  • 所有构造案例和数字明确标注，不冒充生产事实。

Model Card

  • 模型详情、来源、许可、版本和知识/训练边界明确；
  • 未提供信息写明 unknown，不由作者猜测；
  • factors 与切片对应真实用途；
  • metrics 给任务、分母、unknown、区间和版本；
  • 模型隔离结果没有冒充端到端系统结果；
  • intended、out-of-scope 与 forbidden use 分开；
  • known limitation 有受影响范围、限制、owner 和 review trigger；
  • 托管滚动版本有哨兵和短有效期；
  • Card 更新生成新版本，不覆盖旧发布记录；
  • Card 未声称代表工具、权限、UI 和运营控制。

System Card

  • 组件与数据/控制流来自部署 manifest；
  • 信任边界、权限和副作用点明确；
  • 每个关键 mitigation 有 control ID、实现、证据、monitor 和 owner；
  • fail-open/fail-closed/升级行为有显式合同；
  • 模型隔离、组件、端到端、红队、故障和运营证据分层；
  • FAIL、UNKNOWN 和未覆盖切片没有从摘要消失；
  • 人工监督有 UI 强制、培训、容量、SLA 和抽检；
  • 系统限制连接到路由或能力限制；
  • System Card 未被描述为统一法定模板；
  • 公开 Card 与内部事实源一致，删减有审批与理由。

Risk Register

  • 风险写成触发条件—系统行为—使用路径—影响场景；
  • affected parties、可逆性、暴露和不确定性明确；
  • inherent risk 与 residual risk 分开；
  • 每项 active risk 有具名 owner；
  • 控制涵盖预防、检测、响应与恢复；
  • mitigation planned、implemented、validated 分开；
  • evidence IDs 与 back-reference 完整；
  • OPEN 和 VALIDATING 风险不能伪装成 MITIGATED；
  • residual acceptance 有权限、范围、理由、监控和到期；
  • non-waivable hard gate 不能被普通例外绕过；
  • 到期、事故和变更能自动 reopen；
  • 发布使用不可变风险快照，后续台账不改旧 Bundle。

证据与指标

  • evidence record 绑定 model/system/prompt/policy/data/judge 版本；
  • PASS、FAIL、UNKNOWN、INVALID 分开；
  • 报告存在不等于主体和有效期正确；
  • 风险引用与 evidence back-reference 双向校验；
  • required evidence kind 随内部 tier 增强；
  • 每个 change type 有 current PASS 证据；
  • RiskEvidenceCoverage 报分子、分母、权重和 unknown；
  • hard risk 不被 coverage 均值抵消；
  • 评测 coverage 与风险 evidence coverage 分开；
  • orphan refs 和 orphan evidence 都有告警；
  • 证据有效期按主体与风险定义，不统一一年；
  • 远程模型、生产分布和人工流程有更短复审策略。

风险分级

  • 分级主体是 system × use × context，不是模型名；
  • 影响、规模、自主性、可逆性、数据和不确定性有依据；
  • ordinal 乘积不被冒充真实概率；
  • rationale、unknown、override 和批准人保留；
  • 新工具、权限、受众和地区触发重新分级；
  • 降级需要证据与批准，不因排期改变；
  • T1–T4 是内部工程等级，未映射成法定类别；
  • T4 默认阻断和逐项授权可执行；
  • forbidden use 独立硬门；
  • 高等级只增加证据，不覆盖已失败 hard gate。

适用性

  • 每个目标 jurisdiction 有 system/use facts、role 和专业 owner；
  • 依据链接到当时有效的官方文本；
  • 适用、不适用、未决和假设分开记录；
  • UNRESOLVED 不被代码自动补成结论；
  • 内部 tier 不自动决定 EU AI Act 分类；
  • provider、deployer 等角色按具体事实评审；
  • 阶段适用日期按 Article 113 等官方条文核对；
  • obligations 映射到控制和证据，而不是复制条文；
  • System Card 不自动等同于法定技术文档；
  • 适用性记录有 review due 和变化触发；
  • 本文或自动化输出不被当作法律意见。

审批与发布

  • pre-approval manifest 包含所有 Card、风险、证据和适用性摘要；
  • 每个审批绑定当前 manifest digest；
  • 批准后任何内容变化使旧审批失效；
  • required roles 由 tier、风险和适用性共同决定；
  • APPROVE_WITH_RESTRICTIONS 的限制可被部署控制执行；
  • NEEDS_INFORMATION 与 REJECT 不会软通过；
  • 例外有补偿控制、流量、监控、owner 和到期；
  • deploy admission 比对环境与 Bundle；
  • 回滚选择完整、已验证的旧 Bundle，不只换模型；
  • 运行中持续 reconciliation，发现组件漂移；
  • 紧急变更不旁路新候选与时限；
  • 旧 Bundle 只追加保留，事故后不原地修改。

自动化与故障注入

  • 四类工件有版本化 Schema；
  • lint 检查 intended/forbidden 冲突和缺 owner；
  • MODEL_DIGEST_DRIFT 会阻断；
  • STALE/FAILED/UNKNOWN evidence 会阻断相应风险；
  • UNRESOLVED_APPLICABILITY 会阻断或限制；
  • APPROVAL_ON_OLD_DIGEST 会阻断；
  • UNCOVERED_CHANGE 会要求重评测；
  • EXPIRED_ACCEPTANCE 会 reopen 风险；
  • MISSING_LIMIT_MONITOR 会阻断高等级发布；
  • FORBIDDEN_USE 无法靠审批文本绕过；
  • 生成式辅助只能起草，不关闭风险或给法律结论；
  • mutation survived 会进入门禁缺口评审。

二十二、总结

第一原则，是把 Model Card、System Card、Risk Register 和 Release Evidence Bundle 分开。Model Card 描述模型，System Card 描述整套系统与部署场景，Risk Register 管风险状态和责任，Bundle 证明某个 exact candidate 在某个时点具备哪些有效证据与审批。任何一份都不能独自代表“AI 已安全合规”。

第二原则，是让 Card 从证据生成，而不是在发布末尾补文案。模型、Prompt、RAG、工具、策略、UI、评测和控制都有稳定 ID 与摘要；Card 的数字回到 run record；风险回到 control 和 evidence；审批回到 manifest digest。这样文档才是交付系统的一部分。

第三原则，是按 system × use × context 分级。内部 T1–T4 只决定工程证据、审批和运营强度，不等于 EU AI Act 或任何法定分类。监管适用性必须独立记录 jurisdiction、角色、事实、官方依据、专业 owner、未决项与有效期，代码不自动给法律结论。

第四原则，是让 diff、过期和事故真正改变发布状态。模型摘要漂移、工具权限增加、风险接受到期、证据主体不匹配、审批绑定旧内容，任何一个都应把候选从绿变红。旧 Bundle 永久保留，新事实创建新版本。
