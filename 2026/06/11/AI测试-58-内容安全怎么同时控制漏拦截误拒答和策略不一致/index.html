AI测试-58-内容安全怎么同时控制漏拦截误拒答和策略不一致

发表于 2026-06-11 分类于 AI测试 本文字数： 17k 阅读时长 ≈ 1:02

一个 AI 助手把所有请求都拒绝，漏拦截率可以看起来是零。这个系统安全吗？

不一定，而且通常不可用。

另一个助手回答了绝大多数正常问题，平均“安全准确率”达到 99.8%，但在某个低流量语言、未成年人受众和编码变形组合上漏掉了一条 critical 规则。这个平均数能支持上线吗？

也不能。

内容安全不是“给每段文本打一个安全或不安全标签”这么简单。生产系统必须先知道哪一版策略适用于哪个产品、地区、受众、语言、渠道和会话上下文，再区分允许回答、安全改写、拒答、人工升级、策略不适用与基础设施无结果。最后还要验证实际响应有没有保留安全意图、有没有泄漏受限内容、等价请求是否得到一致处置，以及申诉后暴露出的误拒答能否进入受控修复。

因此，内容安全测试真正要回答的是：

本文资料边界截至 2026-06-11（含）。文中的平台、策略代号、请求标签、阈值、样本量、指标、灰度结果、事故时间线与改进效果均为构造示例，不代表任何真实企业、供应商、模型或线上流量。为避免传播有害操作内容，全部安全测试输入都使用 [RISK_*]、[SAFE_*]、[ENCODED_VARIANT] 等惰性占位标签；这些标签只表达测试类别，不携带可执行做法。

一、边界：本文测试策略执行质量，不替组织决定什么内容应被禁止

内容安全工程至少有三个容易混淆的层次：

  1. 政策与价值判断：哪些内容在特定产品、地区、受众和场景下应允许、限制、拒绝或升级；
  2. 技术执行：分类器、规则、模型、上下文解析和响应控制能否按批准政策行动；
  3. 质量证据：测试能否发现漏拦截、误拒答、改写失败、不一致和不可判定状态，并支持有限范围的发布结论。

本文集中讨论后二者。测试可以发现策略冲突、覆盖缺口和执行偏差，却不能仅凭一个 benchmark 决定社会规范，也不能把某家供应商的政策当作普遍标准。高影响场景还需要领域负责人、法律与合规人员、受影响群体代表以及安全负责人参与定义边界；技术团队不能把这些判断藏进一个没有版本号的 Prompt。

本文也不重复 AI测试-47 的红队攻击面管理。红队测试关心攻击者如何跨输入、检索、工具、身份和输出链路突破控制；本文关心内容安全控制本身如何定义动作、构造双侧测试集、校准阈值、核算分母、比较切片并完成发布闭环。二者共享证据，但问题不同：红队发现新的失败方式，内容安全评测决定这些失败如何被政策化、度量和持续控制。

1.1 本文能够支持的结论

  • 某个固定版本系统在已声明策略作用域和测试切片内，观察到了怎样的漏拦截、误拒答、安全改写、升级和不一致表现；
  • 某个阈值或策略变更在配对保留集上改善了哪些指标，又损害了哪些指标；
  • 某类 critical case 是否出现观察失败，以及在给定样本量下失败率统计上界有多大；
  • 某个语言、地区、受众、会话或变形切片是否缺乏最低覆盖；
  • 某个候选版本是否满足预注册的灰度门禁、人工容量和回滚条件。

1.2 本文不能证明的事项

  • 测试通过不等于系统对所有未知表达、文化语境或未来攻击都安全；
  • 零个观察到的 critical miss 不等于真实失败概率为零；样本量和统计上界必须一起报告；
  • 一个拒答分类器判断为 REFUSE 不等于最终响应没有泄漏，也不等于拒答理由恰当；
  • 一个外部 Judge 认为“安全”不等于政策真值；Judge 自身也有偏差、漂移和不确定状态；
  • XSTest、HarmBench 或其他公开基准上的结果不能直接替代当前产品、策略、语言和受众上的发布证据；
  • 英文单轮文本通过不能外推到其他语言、多轮、语音、图片、文档或工具执行；
  • 内容安全门禁不能替代权限、隐私、供应链、审计和事故响应控制。

二、先拆掉八个会让报表“假绿”的结论

2.1 “拒答越多，系统越安全”

反例：把安全请求 [SAFE_HOMONYM]、合法健康科普 [SAFE_EDU_CONTEXT] 和风险请求 [RISK_CRITICAL_A] 全部拒绝，确实没有直接放出受限内容，但产品已经失去核心能力。更严重的是，团队可能把“全部拒绝”当作低风险回滚，长期掩盖策略资格判定、上下文理解和安全改写都没有真正工作。

正确做法是把安全性和有用性设为并列门禁。漏拦截率只在应该阻断或升级的可判定请求上计算；误拒答率只在应该允许或可以安全改写的可判定请求上计算。两者不能相减成一个总分。系统必须同时证明“该拦的拦住”和“该帮的能帮”。

2.2 “总体准确率高，所以 critical 风险可接受”

反例：构造保留集中有 99,999 个简单安全请求和 1 个 critical 请求。系统只错最后一个，总体准确率仍是 99.999%，但真正需要硬门的风险完全失守。

内容安全指标必须按严重度分层。critical_miss_count > 0 可以直接阻断发布；在零观察失败时，仍需报告 one-sided upper bound，说明当前样本量最多支持什么范围的声明。高严重度事件不能乘一个很小的流量权重后消失，更不能与大量容易的安全样本平均。

2.3 “基础设施超时可以算拒答，因此也是安全的”

反例：安全分类服务超时，应用返回空白或通用错误。评测脚本看到没有有害文本，就把它记成拒答通过。实际上，这次请求既没有完成政策判断，也没有执行一个可审计的拒答动作；生产重试、客户端兜底或旁路还可能随后给出不同结果。

INFRA_NO_RESULT 必须是独立状态。它进入可用性和降级策略分母，不进入漏拦截、误拒答或拒答正确率分母。产品可以针对不同风险层选择显式保守降级，但“降级选择”与“模型判断正确”仍是两条证据。

2.4 “模型给出拒绝措辞，所以策略执行正确”

反例：输出前半段声称不能帮助，后半段却复述了受限细节；或者应当安全改写的请求被模板统一拒绝；或者应人工复核的高影响个案被永久拒绝。关键词分类器都可能把它们判成正确拒答。

动作只是第一层。最终响应还要经过内容后置条件：是否包含受限信息、是否保留允许的安全意图、是否泄漏内部策略细节、是否给出批准的替代路径、是否正确附加升级 ID。action == REFUSE 不能替代响应语义验证。

2.5 “同义改写结果不同，说明模型随机”

反例：英文原句先通过 Unicode 规范化再检测，另一种编码形式却在策略路由之后才解码；或者多轮请求的历史只传给主模型，没有传给安全分类器；或者地区字段在移动端缺失，系统选择了默认政策。表现为“同义句不一致”，首错层其实是数据流和版本路由。

一致性实验必须保存实际输入字节摘要、规范化结果、上下文包、策略版本、检测信号、阈值、随机种子和最终动作。只有确认批准的变形轴之外其余变量冻结，才能把差异归到模型或分类器行为。

2.6 “一个全局阈值可以管理全部标签”

反例：某检测器对 [RISK_CRITICAL] 和 [RISK_CONTEXTUAL] 的分数分布完全不同，对低资源语言又普遍偏低。用同一个 0.7 阈值，看起来整体折中最好，却在 critical 小样本和某语言上产生不可接受漏拦截。

阈值应绑定任务、标签、严重度、语言或其他必要切片，并在独立校准集上选择。阈值过多会引入样本稀疏和维护复杂度，因此要由证据决定分层，不是每个字段任意拆分。无法稳定校准的区域应进入迟疑区和人工升级，而不是伪造高置信度。

2.7 “策略不一致只影响体验，不影响安全”

反例：同一风险请求在网页端拒答，在 API 渠道允许；第一轮拒答，换一种安全等价表达后允许；新政策在主区域生效，旧版本仍驻留于缓存节点。攻击者会沿最弱通道重试，运营人员也无法向用户解释规则。

一致性不是要求所有地区、受众和上下文输出相同。正确目标是：在策略语义等价且作用域相同的成对样本中，决策应稳定；在策略明确要求不同的样本中，差异应与版本化规则一致。盲目追求全局同答，反而会抹掉合法的上下文差异。

2.8 “申诉翻转越少，系统越准确”

反例：申诉入口难找、处理周期太长或高风险人群不愿申诉，翻转率会很低；另一个系统主动抽样复核边界请求，翻转率反而更高。二者不能直接比较。

申诉指标至少要分开：可申诉曝光量、申诉提交率、可受理率、人工翻转率、处理时延、策略缺口率和再次发生率。申诉数据有自选择偏差，适合发现问题与构造保留集，不应直接当总体误拒答率估计。

三、工程词典：先把六种状态分开

内容安全评测最危险的错误之一，是把所有非正常回答都压成 blocked=true。本文使用下面的状态模型。

状态/动作 工程定义 是否进入语义质量分母 典型后置条件
POLICY_INELIGIBLE 当前策略包无法对该产品/地区/受众/渠道/时间作出有效判断 否，单独统计作用域缺口 必须显式升级、路由或停止，不得补成安全
ALLOW 策略允许完成请求 是 最终回答仍需满足普通质量、隐私和权限约束
SAFE_REWRITE 原始请求含受限部分，但存在批准的安全帮助路径 是 去除受限内容，保留可服务意图，不能变相全拒
REFUSE 在当前作用域下应明确拒绝 是 拒答边界一致，不泄漏受限内容，不扩大政策范围
ESCALATE 证据不足、冲突、特定高影响场景或迟疑区需要人工/专门流程 是 创建可追踪工单，满足 SLA、权限和最小披露
INFRA_NO_RESULT 超时、依赖错误、解析失败、模型无响应等导致没有完成政策决策 否，进入可用性分母 执行风险分层降级并记录真实原因

3.1 Policy eligibility 不是模型置信度

policy_eligible 表示：在评测时点，批准的策略是否覆盖这个产品能力、地区、受众、语言、渠道和上下文类型，并且 Oracle 是否能够给出有效期望动作。它是治理和数据条件，不是检测器输出的概率。

例如，策略只批准了文本通道，语音转写片段不应被硬塞进文本准确率；一个新地区尚未完成适用性评审，也不应默认沿用其他地区策略。正确状态是 POLICY_INELIGIBLE，随后按产品设计升级或关闭能力。把这些样本排除后必须报告排除数量和原因，否则团队可以靠缩小 eligibility 获得虚高质量。

3.2 漏拦截不是“动作不相等”的同义词

漏拦截关注受限结果是否穿透控制。假设 Oracle 期望 REFUSE，实际 ALLOW 并输出受限内容，这是明确 miss；实际 ESCALATE 虽然动作不完全一致，但没有直接穿透，可以记作路由偏差而非内容泄漏。反过来，Oracle 期望 SAFE_REWRITE，实际动作也是 SAFE_REWRITE，但改写仍保留受限细节，它仍是 miss。

所以至少需要两个字段：action_match 与 containment_postcondition。只比较枚举会漏掉“名义拒答、实际泄漏”，只看最终文本又无法识别“安全但走错流程”。

3.3 误拒答与正确安全改写必须分开

误拒答包括：应 ALLOW 却 REFUSE，以及应 SAFE_REWRITE 却把可服务部分全部拒绝。后者常被安全报表忽略，因为系统没有输出风险内容；对用户和业务来说，它仍是可以避免的能力损失。

升级需要有批准原因和容量模型。所有低置信度请求都升级，会把分类问题转化成人工队列事故。每类升级应记录 reason_code、严重度、所需角色、最长等待、超时动作、用户通知和复核结果。评测不仅测 escalation recall，还测不必要升级率、队列峰值、超时率和最终处置一致性。

5.1 请求封装与规范化层

最低输入包应包含：

  • 原始内容摘要与规范化内容摘要，敏感原文按最小化原则受控存储；
  • 会话 ID、轮次、引用前文和工具结果的稳定 ID；
  • 产品能力、渠道、租户、地区、受众和语言来源；
  • 字符编码、Unicode 规范化方式、解码链和变形检测结果；
  • 请求时间、客户端版本和上游身份/权限结论；
  • 允许参与政策判断的上下文，以及因权限或保留政策被省略的字段。

规范化顺序是安全边界的一部分。若检测器看的是原始字节，主模型看的是解码文本，二者可能对同一请求形成不同语义。工程上应保存阶段摘要和规范化 manifest，在不长期留存敏感正文的前提下支持定位。

Unicode NFC/NFKC、大小写折叠、URL 解码或转写不是可以无条件串联的“清洗”。兼容规范化可能改变标识符语义，多次解码可能制造新内容，语言检测也可能因短文本不可靠。每一步必须绑定字段类型和产品合同，并通过变形测试证明不会把安全输入误变成风险，也不会让风险载荷绕过检测。

一个生产栈可能组合确定性规则、轻量分类器、生成模型分类、会话模型和外部服务。组合并不自动更安全。需要记录每个信号的：版本、输入视图、输出标签、原始分数、校准分数、缺失状态、耗时和解释码。

5.5 响应控制与后置条件层

响应控制器负责真正执行动作：允许时调用主模型，改写时删除或替换受限槽位，拒答时使用与策略相符的边界说明，升级时创建工单并停止自动决策。之后仍需验证最终输出。

例如，SAFE_REWRITE 的输入模板可能正确，但主模型又从会话历史恢复了受限片段；REFUSE 模板可能拼接了调试字段；ESCALATE 可能创建失败却向用户显示“已提交”。因此，评测要覆盖动作选择和执行结果两个阶段。

5.6 人工、申诉与持续监控层

人工判定不是无限容量的真值服务。需要盲化必要字段、角色权限、冲突仲裁、质量抽检和 SLA。申诉结果分为：模型执行错误、策略解释错误、策略本身缺口、用户补充上下文后动作改变、人工错误。只有经过审核的稳定结论才进入 case 库或策略更新，不能把单个操作员的临时判断直接训练进系统。

八、Oracle 与标注：动作、内容和策略依据三层分开

8.1 Policy Oracle

Oracle 输入固定策略快照和完整上下文，输出 eligibility、期望动作、匹配规则与后置条件。标注人员不应先看模型输出再决定标准，否则容易向当前系统行为靠拢。

对每个 case，标注界面应隐藏模型身份并展示最小必要上下文。争议项进入双人独立标注和仲裁，保存分歧原因。若策略本身冲突，状态应为 POLICY_DISPUTED 或 INVALID_ORACLE，不能强迫标注员选一个答案后进入模型分母。

8.2 Response Oracle

动作判定可用确定性字段，但最终内容通常需要多个检查：

  • 是否出现 case 明确禁止的占位槽位或语义；
  • SAFE_REWRITE 是否保留允许目标和必要事实；
  • 拒答是否夹带受限信息或不必要扩大禁区；
  • 升级是否创建工单、带正确策略版本并停止自动执行；
  • 输出语言是否与用户和产品要求一致；
  • 结构化 action 与自然语言是否矛盾。

能用结构化 Oracle 的内容不要交给通用 Judge。剩余语义可用盲化人工或经过验证的 Judge，但 Judge 失败、拒绝判定和分歧必须记 unknown。用被测模型自己判断自己是否安全，最多是辅助信号。

8.3 Benchmark 只能提供局部探针

XSTest 原论文包含 250 条安全提示，分为十类，用于系统检查“表面类似风险表达但实际安全”的过度安全行为；另有 200 条 unsafe contrast prompts。这个规模与分类是论文测试套件的事实，不是所有产品应采用的安全/风险比例，也不代表其 unsafe 对照在每个应用都必须使用同一动作。文章引用它，是为了说明误拒答需要专门、功能化测试。

HarmBench 原论文在其标准化自动红队框架中比较了 18 种红队方法和 33 个目标 LLM/防御组合。这个数字只描述论文实验，不证明某个当前系统覆盖了 18 种真实攻击，更不证明通过 HarmBench 就具备生产安全。若复用其数据或分类器，要固定仓库版本、行为子集、生成参数、判定器版本和适用边界，并补充自己的政策与 benign 对照。

9.2 漏拦截率

对要求 containment 的 case，定义后置条件 leak_i，它综合动作和最终内容。按严重度 s：

如果产品把 SAFE_REWRITE 定义为可服务路径，那么把它全拒绝就是误拒答。也可以进一步拆成 SafeAllowRefusalRate 与 RewriteOpportunityLostRate，避免大量 ALLOW 样本掩盖稀少但重要的改写能力。

同时报告两个组成项：containment_success 与 intent_preservation。只报合取指标虽然严格，却无法定位是安全边界失败还是帮助能力失败。

9.5 人工升级指标

队列创建成功不等于案件完成。还要报告撤回、重复、超时、权限拒绝、证据不足和人工分歧。若升级队列已经饱和，继续提高 escalation recall 可能造成更大延迟，灰度前需要容量压测。

对于 critical，最差切片是辅助展示，硬门仍对每个观察失败生效。不能因为失败切片样本少而忽略；小样本只意味着失败率估计不精确，不意味着已观察到的失败不存在。

十、阈值与校准：分数不是政策，校准也不是永久属性

10.1 三套数据不能混用

  • 训练/规则开发集：用于学习分类器或编写规则；
  • 校准集：用于选择阈值、迟疑区和必要的切片修正；
  • 发布保留集：阈值冻结后评估，不参与调参。

同一事故样本反复用于调 Prompt、调阈值再汇报性能，会产生乐观偏差。修复可以在开发集中使用该样本，但发布结论需要未参与修复的同家族保留变体。

10.2 校准对象要写清楚

二元风险检测器可报告 reliability diagram、Brier score、ECE 或分位表现，但要声明正类定义、采样分布和权重。一个在平衡测试集上“70% 校准”的分数，不能直接当生产后验概率；生产先验和采样方式不同。

阈值选择应基于成本和硬约束，例如：critical recall 必须满足下界，误拒答率不得超过上限，迟疑区流量不得超过人工容量。不能先看结果再挑一个让候选版本通过的阈值。

10.3 多标签和严重度阈值

可采用分标签阈值或分层裁决：先对 critical 高召回筛查，再对可改写类别判断，最后处理普通 allow。这样的级联会改变后续阶段分布，因此每层既要测局部指标，也要测端到端动作。上游全拒绝会让下游看似无 miss，却不代表整栈正确。

10.4 迟疑区与 abstention

若分数位于 [t_low, t_high]，或关键上下文缺失，系统可以升级而不是强行二分。迟疑区要监控：占比、切片、人工翻转、SLA 和成本。模型置信度高但策略条件缺失时仍应 abstain；eligibility 和置信度不能互相替代。

10.5 漂移触发再校准

以下变化至少触发核心保留集重跑，必要时重新校准：

  • 模型、Prompt、分类器、规范化器或聚合逻辑变更；
  • 策略版本、标签定义、受众或地区作用域变化；
  • 语言、渠道、会话长度和编码分布漂移；
  • 新事故、新申诉聚类或人工翻转结构变化；
  • 供应商未说明的模型行为漂移；
  • 上游转写、OCR 或富文本解析版本变更。

再校准不是在生产故障后直接移动阈值。要先构造配对证据，检查漏拦截与误拒答的双侧影响，再经过审批和灰度。

十一、自动化测试矩阵：组件、模型隔离与端到端三轨并行

11.1 确定性组件测试

适合放在每次提交的 CI 中：

  • policy bundle Schema、签名、有效期和 precedence；
  • eligibility 对产品/地区/受众/语言/渠道的边界；
  • Unicode、编码和解码顺序；
  • 多标签合并、阈值边界与迟疑区；
  • no-result、retry 和降级状态机；
  • response controller 是否真正移除受限占位槽位；
  • escalation 工单幂等、SLA 字段和权限；
  • 指标分母、加权、pair 完整性和最差切片。

11.2 模型隔离轨

绕过产品检索和 UI，只固定策略与上下文，测模型或分类器对标签家族、语言、多轮和变形的行为。它能帮助区分模型使用失败与应用数据流失败，但不能支持应用上线结论。

11.3 生产端到端轨

通过真实入口、身份、上下文封装、策略路由、检测、主模型、响应控制和审计链。只有这条轨能发现移动端漏传 audience、API 节点缓存旧 policy、转写器先后顺序不同等系统问题。

11.4 双侧生成器

安全测试不能只生成攻击变体。每个风险词面家族至少同时生成：

  • 明确应拒绝的 inert risk case；
  • 表面相似但语义安全的 benign contrast；
  • 可以安全改写的 mixed-intent case；
  • 缺上下文应升级的 ambiguous case；
  • 策略不适用或缺字段的 eligibility case；
  • 基础设施故障 case。

生成器必须证明变体关系。自动改写可能改变安全语义，不能因为“看起来像同义句”就继承标签。高风险生成结果先进入隔离环境和人工审查，只保存必要的占位表示与 manifest。

11.5 CI、夜间和发布前分层

  • PR CI：策略解析、指标分母、关键标签边界和少量等价 pair；
  • 夜间：全语言 × 受众 × 多轮 × 变形的 targeted matrix，带固定种子；
  • 候选发布：冻结阈值后的独立保留集、生产联合分布、critical 扩展集和故障注入；
  • 上线后：只读影子、分层抽样人工复核、申诉流、策略版本一致性和 no-result 监控。

十二、故障注入：测试系统必须会因为真实错误而变红

注入 预期观测 不应出现的假绿
STALE_POLICY policy version mismatch，动作可能偶然相同 只比动作后通过
DROP_AUDIENCE eligibility mismatch 或错误默认策略 缺字段自动当 adult
DROP_HISTORY 多轮 critical miss / missed escalation 只测当前 turn
ENCODING_BYPASS 变形切片 miss、pair inconsistency 规范化后只测一份

BAD_REWRITE restricted material 或 intent loss 只看 action 枚举

每个注入要有预期首错层、指标变化和发布结果。长期存活的 mutation 说明断言只验证了实现细节，没有验证风险后置条件。

十四、如何理解示例输出，而不是把教学代码搬进生产

正常 fixture 中有 7 个 policy-eligible case 和 1 个作用域外 case。作用域外 case 不进入语义分母，但仍保留在总尝试和 coverage gap 中。所有 eligible case 正常完成时，四种动作、两组完整等价 pair、三个 critical containment case 和五个注册切片都通过。

注入 TIMEOUT 后，semantic denominator 从 7 变成 6，InfraNoResultRate 变成 1/7；它没有增加拒答数，也没有改善 miss。pair 的预期成员来自独立只读 manifest，不从本次到达的 case 反推，所以成员在执行前或执行中丢失都会进入 IncompletePairRate。重复 case ID、NaN/Inf、非正权重、非法 cell 和非法门槛在计算前直接拒绝，不能利用 IEEE NaN 比较的特性 fail-open。注入 ALL_REFUSE 后 critical miss 仍为零，但误拒答、安全改写和 exact-action 门禁失败；注入 ENCODING_BYPASS 后，一个 critical miss 同时打破硬门和等价 pair 一致性。

示例中的 severity == 4、0.50 上界阈值和构造权重都不是行业标准。代码明确使用 z≈1.64485 的单侧 95% Wilson 上界，并只把 severity == 4 的 containment-required 语义结果放入 critical 分母；高严重度 benign allow case 不能稀释它。样本仅有 3 个，所以默认 0.50 只是让教学基线可运行的宽松构造门槛，不应搬到生产。生产实现还需要：加权置信区间、会话或 case 家族聚类、分层抽样纳入概率、人工 unknown、更多 postcondition Oracle、证据持久化和独立审批；正式报告应预注册区间方法、单侧/双侧口径、置信水平与最小样本。

十五、完整构造发布案例：一次平均值通过、critical 切片失败的灰度

下面是 Atlas-Learn 4.18 的完全构造案例。

15.1 候选变更

候选版本同时包含：

  • 主模型从 model-a17 升级到 model-a18；
  • lang-q 分类器阈值从 0.74 调整到 0.69；
  • 编码规范化器从 norm-5 升级到 norm-6；
  • 策略保持 safety-policy-2026.06；
  • 安全改写 Prompt 增加更明确的安全意图保留槽位。

发布团队预注册门禁：观察到的 critical miss 必须为零；critical 一侧上界低于批准值；总体 miss 不超过 0.8%；误拒答不超过 2.5%；正确安全改写不低于 96%；required escalation recall 不低于 98%；policy version mismatch 为零；RiskCoverage 不低于 97%；所有关键组合切片达到最小样本。

这些阈值仅为构造示例。它们不构成任何实际系统建议。

15.2 离线结果

构造的生产加权总体结果是：miss 0.31%、误拒答 1.9%、正确安全改写 97.4%、升级召回 99.1%。若只看四个平均数，候选似乎通过。

但切片报告显示：lang-q × youth × R-B × encoded × multi-turn 的 120 个 critical case 中出现 2 个 miss；等价 pair 中原始表达拒答、编码变体允许。RiskCoverage 达标也不能挽救这个结果，因为 hard gate 已失败。团队将结论写成“候选被阻断，已观察到特定组合上的 critical miss”，而不是“总体仍有 99% 安全”。

15.3 首错层定位

Trace 显示：

  1. 请求入口收到的原始内容和测试 manifest 正确；
  2. norm-6 能把 [ENCODED_VARIANT] 还原成规范标签；
  3. 主模型使用的是规范化结果；
  4. critical 检测器却在规范化之前读取原始视图；
  5. 多轮历史聚合又只把最近一轮传给检测器；
  6. 策略裁决器把缺失 critical 信号当成低分，而不是 missing signal。

所以根因不是“模型不够安全”，而是三个系统条件组合：检测器输入视图错误、会话上下文缺失、聚合器错误处理 missing。候选模型只是与同批变更一起出现，不能从时间相关性直接归因。

15.4 修复与反例验证

修复把所有文本检测统一放到字段类型感知的规范化层之后；检测器接收批准的会话摘要与风险状态；任何 mandatory signal 缺失都进入 INFRA_NO_RESULT，再按 critical 路径保守降级。团队没有单纯降低全局阈值，因为那会增加安全请求误拒答。

复测包含：原失败 case、同家族未参与修复的保留变体、XSTest 风格的 benign lexical contrast、正常多轮安全请求、所有语言和渠道，以及 TIMEOUT、STALE_POLICY 与 ALL_REFUSE mutation。只有修复既杀死 critical miss，又不让误拒答和安全改写退化，才进入下一次灰度。

15.5 灰度与止损

构造灰度分四阶段：内部只读回放、1% 影子、1% 用户流量、10% 用户流量。每阶段冻结最短观察窗和最低 case 数，同时要求：

  • critical 在线哨兵零观察 miss；
  • policy version mismatch 和 mandatory-signal missing 均在上限内；
  • benign control 的误拒答不超过预算；
  • 安全改写 intent preservation 不退化；
  • 人工升级队列 P95 等待和积压不超容量；
  • 申诉入口、工单回查和一键回滚可用。

自动止损不是把所有请求永久拒绝。回滚优先恢复上一个已验证版本；若只有某切片失守，能力合同可临时限制 lang-q 多轮编码输入并显式说明范围，同时保留正常安全流量。

十六、完整构造事故案例：误拒答激增但“安全率”没有报警

另一个构造事故发生在 2026-06-03。运营发现学习类安全请求申诉突然增加，但安全大盘仍显示 99.96%。

16.1 时间线

  • 09:10：策略控制面发布 2026.07，新增一个 multi-label precedence；
  • 09:22：两个边缘节点仍缓存 2026.06，但日志只写 policy=latest；
  • 10:05：[SAFE_HOMONYM] 的 youth + zh 请求在旧节点被统一 REFUSE；
  • 12:40：申诉团队发现同一请求重复提交后有时允许、有时拒绝；
  • 13:15：安全看板的“通过率”只计算风险请求拒答，没有 benign denominator；
  • 14:00：团队冻结策略扩散并把流量切回已确认节点；
  • 16:30：补齐不可变 policy version 和 benign control 告警后完成验证。

16.2 事故为何没有被原指标发现

原报表把 refused / risk_flagged 称为安全率。它既没有测应允许请求，也没有记录每个节点解析出的具体策略版本。缓存旧版导致的误拒答不会进入分子或分母；同一 case 的跨节点不一致也因没有 pair_id 而不可见。

16.3 修复闭环

修复包括：每次 decision 保存不可变版本摘要；发布时对所有节点做版本收敛证明；在用户流量中注入不含敏感内容的 benign sentinel；申诉样本进入隔离、去重和双人标注；策略 diff 自动生成受影响 case 列表；门禁增加 FalseRefusalRate、PairInconsistency 和 PolicyVersionMismatch。

事故复盘不声称“缓存是唯一原因”。直接原因是旧策略被执行，贡献因素包括日志版本不可审计、benign 指标缺失和灰度未覆盖边缘节点，检测缺口则是申诉量没有按政策版本聚类。三类结论分别记录，避免把监控缺口误写成根因。

十七、灰度、在线抽样与申诉闭环

17.1 影子评估

候选安全栈可以在不影响用户响应的情况下影子运行，但影子不是零风险：它仍处理真实数据、产生费用并可能触发外部服务。必须遵守数据最小化、权限、地区和留存规则。若候选 ESCALATE 会创建真实工单或调用工具，要在沙箱中拦截副作用。

影子差分记录 incumbent 与 candidate 的 action、reason、policy version 和 postconditions。分歧先按 critical、策略版本和 benign false refusal 排序，再抽样人工复核。不能把 incumbent 当真值；二者一致也可能共同错误。

17.2 在线抽样

生产抽样同时包含：独立概率样本、风险分层加抽、固定 benign sentinel、事故触发样本和申诉样本。只有概率样本能按纳入概率估计总体；风险和事故样本用于发现问题与硬门，不能直接混入总体率。每种 membership 可同时存在，去重时保留概率身份。

人工复核有延迟和拒绝标注。报告要给 label completeness 与 response propensity；若某语言更难标注，完整样本可能偏向主流语言。缺失真值不能补成安全。

17.3 申诉机制

申诉入口应告诉用户哪类决定可复核、需要什么上下文、预计时限和隐私处理。内部记录原 decision、策略版本、可见上下文、人工 verdict 和翻转原因。策略变化后翻转不等于当时系统错误，因此要区分 execution_error、oracle_error、policy_changed、new_context 和 human_error。

申诉回灌先生成 case 家族，再切分开发与保留变体。直接把申诉原文放进 Prompt 会造成隐私、评测污染和过拟合风险。

十八、发布报告怎么写才不越界

一份负责任的报告分三层：

Observation

Inference

Decision

Observation 不能直接写成 Cause，Inference 不能伪装成普遍规律，Decision 还要绑定责任人、期限和回滚动作。

十九、落地路线

阶段一：把状态和分母做对

先实现 policy eligibility、四种动作、infra no-result、Oracle unknown 和不可变策略版本。没有这些字段，不要急着做复杂总分。

阶段二：建立双侧最小保留集

每个主要风险家族同时有拒答、允许、安全改写和升级 case，覆盖至少一个上下文、一个多轮、一个语言变体和一个编码变体。critical 另设硬门。

阶段三：补后置条件和 mutation

验证最终内容，不只看动作。用 ALL_REFUSE、BAD_REWRITE、TIMEOUT、STALE_POLICY 和 ENCODING_BYPASS 证明测试会失败。

阶段四：构建 coverage 与最差切片

从产品承诺、生产联合分布、历史事故和威胁模型生成注册单元，分别计算 traffic/risk coverage；建立最小样本和 unknown 规则。

阶段五：校准、发布保留集和灰度

冻结阈值后跑独立保留集，配对比较候选与基线；灰度同时看漏拦截、误拒答、改写、升级、no-result 和人工容量。

阶段六：申诉、事故和漂移闭环

把申诉翻转和在线抽样转成受控 case 家族，按版本聚类；任何策略、模型、检测、规范化、渠道和分布变化触发相应范围重评测。

二十、可执行检查清单

策略边界

  • 每个策略包有不可变 ID、版本、有效期、审批和回滚记录；
  • 产品、能力、地区、受众、语言、渠道和模态作用域明确；
  • POLICY_INELIGIBLE 与低置信度、拒答和基础设施故障分开；
  • 多标签 precedence 是批准规则，不是隐式最大分；
  • 严重度依据写清楚，不由模型 risk score 决定；
  • 策略争议样本不会强行进入模型分母；
  • 真实地区差异经过适用性评审，不由工程师猜测；
  • 未覆盖范围在产品能力合同中显式限制。

数据与 Oracle

  • case、family、pair、source 和策略快照可追溯；
  • 安全测试载荷使用最小化、惰性占位或受控隔离表示；
  • action Oracle 与 response postcondition Oracle 分开；
  • ALLOW、SAFE_REWRITE、REFUSE、ESCALATE 都有正向样本；
  • benign lexical contrast 不与风险样本共用错误标签；
  • 标注先看策略和上下文，不先看模型输出；
  • 分歧、仲裁、invalid 和 unknown 原样保存；
  • Judge 失败不补零，高风险分歧进入人工仲裁；
  • 公开 benchmark、开发集和发布保留集血缘隔离；
  • 事故与申诉原文遵循隐私、权限和保留要求。

覆盖与变形

  • 标签、严重度、上下文、受众、地区、语言全部进入 coverage 模型；
  • 单轮与多轮都测，会话历史视图可审计；
  • 字节、Unicode、编码、格式和同义变形有 manifest；
  • 变形后语义改变的 case 不进入等价 pair；
  • 渠道、客户端和模态的数据流差异被覆盖；
  • 高风险组合切片不被逐字段均值隐藏；
  • TrafficCoverage 与 RiskCoverage 分开；
  • 最低 case 数按独立家族而非模板复制数定义；
  • 样本不足显示 unknown，不自动通过；
  • critical 路径即使低流量也保留硬门。

指标与分母

  • 所有比例同时报告分子、分母、unknown 和加权方式；
  • policy-ineligible 不进入语义分母但不从报告消失；
  • infra no-result 不记成拒答、安全或 miss=0；
  • 重试保留每个 attempt，不只保留最终成功；
  • 漏拦截基于最终 containment postcondition；
  • 误拒答覆盖 ALLOW 和 SAFE_REWRITE 机会损失；
  • 安全改写同时检查无受限内容和意图保留；
  • 升级 recall、误升级、SLA 和队列容量并列；
  • 等价 pair 只用 complete pair 作分母；
  • policy version mismatch 是独立门禁；
  • 总体、最差切片和 critical hard gate 并列；
  • 零观察失败仍报告统计上界。

校准与自动化

  • 训练、校准和发布保留集没有混用；
  • 分数正类定义、采样先验和权重明确；
  • 阈值在看发布集结果前预注册；
  • 标签/语言分层阈值有足够证据，不任意过拟合；
  • mandatory signal 缺失不会被当作零风险；
  • eligibility、precedence、threshold boundary 有组件测试；
  • 模型隔离轨与生产端到端轨都运行；
  • ALL_REFUSE 能触发误拒答和改写门禁；
  • BAD_REWRITE 能触发最终内容门禁；
  • TIMEOUT、STALE_POLICY、DROP_HISTORY、ENCODING_BYPASS 均有 mutation；
  • 存活 mutation 会阻断发布或进入明确评审。

发布与运营

  • 候选绑定模型、Prompt、策略、检测器、阈值和规范化器版本；
  • 影子执行的数据处理和副作用得到控制；
  • incumbent 与 candidate 分歧不把 incumbent 当真值；
  • 灰度有流量、观察窗、最低样本、人工容量和自动止损；
  • 回滚恢复已验证版本，不把永久全拒当完成修复；
  • 在线抽样区分概率、风险、事故和申诉 membership；
  • 申诉翻转按原因和策略版本分析；
  • 策略扩散能证明所有节点收敛到不可变版本；
  • 事故记录直接原因、贡献因素和检测缺口；
  • 报告把 Observation、Inference、Decision 分开；
  • 未覆盖语言、模态、受众和未来变形不被外推；
  • 内容安全通过不替代隐私、权限和系统安全测试。

二十一、总结

内容安全的第一原则，是把“安全”拆成可以被反驳的工程命题。应拒答的请求没有穿透，只证明了一侧；应允许的请求没有被误拒、可安全改写的意图得到保留、应升级的请求进入可用队列、基础设施失败没有伪装成安全，另一侧才成立。

第二原则，是先做 policy eligibility，再谈分类准确率。策略版本、地区、受众、语言、渠道和上下文缺失时，正确结果可能是不适用或升级，而不是让模型猜。作用域外样本不能混进语义分母，也不能从 coverage 报告里消失。

第三原则，是让漏拦截、误拒答、正确安全改写、人工升级、无结果和策略不一致拥有独立分母。REFUSE 不是天然安全，NO_RESULT 不是拒答，平均准确率也不能抵消 critical miss。最差切片、完整 pair 和版本一致性是识别局部失守的必要证据。

第四原则，是把内容安全当作一条分层控制栈。请求规范化、策略路由、多信号检测、校准裁决、响应执行、最终内容、人工复核与申诉，每层都可能成为首错点。只有不可变版本和 attempt trace，才能从“模型有时不一致”走到可修复的原因。
