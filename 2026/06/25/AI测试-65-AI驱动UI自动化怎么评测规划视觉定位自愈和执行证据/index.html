AI测试-65-AI驱动UI自动化怎么评测规划视觉定位自愈和执行证据

发表于 2026-06-25 分类于 AI测试 本文字数： 22k 阅读时长 ≈ 1:21

一个 AI UI Agent 收到任务：“为订单 O-8042 预览 800 元退款，不要提交”。它先在列表中搜索订单，定位到“退款”按钮，遇到新版弹窗后自动修复定位器，最后页面出现绿色提示“操作成功”。执行报告显示 11 个步骤全部完成，截图也能看到订单号。这个用例通过了吗？

不能据此判断。

新版把“预览退款”和“确认退款”合并到同一个弹窗；自愈逻辑根据相似文本把旧的“预览”定位器替换成“确认并退款”；页面绿色提示只表示前端请求已受理；网络层因超时重试两次，退款账本最终产生两笔 800 元提交。Agent 走完了计划，定位也点中了可见按钮，但任务合同、动作许可和业务后置条件都失败了。

传统 UI 自动化常把脚本步骤当作预期：找到元素、点击、看到文本，就算通过。AI 驱动 UI 自动化增加了规划、视觉理解、动态决策和自愈，执行路径不再完全由测试作者预先写死。如果仍只看最终截图或 Agent 的自然语言总结，就会把四个不同问题压成一个“成功率”：

AI 可以提出下一步、融合 DOM/无障碍树/截图、生成定位候选和解释失败；执行器仍应是一个受合同、权限、预算和证据约束的确定性控制系统。尤其是自愈：它只能提出“旧定位器可能对应这个新元素”，不能把“预览”静默改成“提交”，更不能为了让用例变绿而修改 Oracle。

本文资料边界截至 2026-06-25（含）。全文中的组织、产品、账号、订单、金额、页面、DOM、截图、模型、阈值、指标、运行结果和事故均为构造示例，不代表任何真实机构、供应商、线上系统或用户。动作风险、恢复预算和发布门槛也是教学构造值，实际组织应依据数据敏感度、业务可逆性、测试环境、账号权限和人工值守能力批准自己的策略。

一、边界：本文测试的是受控 Agent，不是“会看图的脚本”

1.1 被测系统分层

层 输入 输出 不能越过的边界
Task Contract 业务任务、允许范围、后置条件 不可变合同 运行时不能静默扩大目标或改预期
Planner 合同、当前状态、历史轨迹 下一意图与前置条件 不直接发送浏览器动作
Perception DOM、无障碍树、截图、窗口状态 版本化观察 不把单一来源当完整世界
Grounding 意图、观察、多源候选 目标候选、分数、歧义 坐标和语义必须绑定同一观察
Permit 合同、目标、风险、批准、预算 单次动作许可或拒绝 许可不可跨目标、跨窗口、跨时间复用
Action 有效许可、浏览器会话 实际动作结果 一次只执行获准动作
Oracle 原合同、UI/网络/业务事实 PASS/FAIL/UNKNOWN 不读取 Planner 的“完成”作为真值
Evidence 每层输入输出与摘要 可复核轨迹包 缺口必须声明，不用摘要代替原始证据

1.2 本文不证明什么

  • 一组离线用例通过，不证明 Agent 能处理开放世界中的所有页面和语言。
  • DOM locator 命中，不证明用户可见或可操作；视觉命中也不证明元素具有声称的语义。
  • 截图相似，不证明业务状态相同。相同画面可能对应不同账号、订单或后端提交。
  • WebDriver 命令成功，不证明业务副作用只发生一次，也不证明异步工作完成。
  • 自愈候选被人工接受，不证明以后所有页面版本都安全；它只批准声明范围内的定位变更。
  • Trace 或网络响应存在，不证明目标业务已经提交；请求可能重试、排队或被补偿。
  • 本文的标准库模拟器不驱动真实浏览器，不能替代 WebDriver、Playwright 或 Appium 的集成与设备测试。
  • UI Agent 不能成为业务审批者。高风险动作仍需要业务授权，而不是模型置信度。

二、先把任务、计划、动作和断言分开

2.1 Task Contract

任务合同描述“允许完成什么”，不是一句自由文本。它至少绑定主体、资源、起始状态、允许来源、浏览器动作、允许/禁止的业务操作、输入数据、业务后置条件、最大步骤、恢复预算、证据要求和到期时间。CLICK 只是物理动作，PREVIEW_REFUND 与 REFUND_SUBMIT 才表达业务语义；两者必须分别校验。

“给订单退款”过于宽泛；“在隔离沙箱中为 O-8042 预览 800 元退款，禁止提交，最多 12 步，遇到任何确认弹窗停止”才具备可执行边界。

2.2 Plan 与 Intent

Plan 是 Planner 针对当前观察生成的意图序列或下一意图。Intent 应分别描述物理动作 action、业务操作 operation、目标语义、前置条件和期望局部状态，例如“在订单详情上下文中以 CLICK/PREVIEW_REFUND 打开 role=button、accessible name=预览退款的控件”。它不应直接携带未经验证的屏幕坐标。

2.3 Action

Action 是执行器向浏览器或设备发出的单个已许可命令，例如点击一个已绑定元素、填写一个字段、滚动一个容器、切换一个已授权窗口。实际命令必须同时携带物理动作和业务操作，并绑定候选指纹、观察、窗口/context 与执行时间；不能因为底层命令仍叫 CLICK 就绕过 REFUND_SUBMIT 的业务禁令。

2.4 Oracle

Oracle 判断预期是否成立。UI 文本适合判断局部页面状态；网络事件可证明请求形态和响应；业务事实源用于确认订单、退款、库存或付款等后置条件。Planner 的“我已经完成”不是 Oracle。

2.5 Recovery

Recovery 是在失败后重新观察、滚动、关闭允许的遮挡、切换已知窗口或生成定位候选。恢复会消耗预算，并且不能改变任务合同、Oracle 和风险等级。不确定副作用发生后，恢复不应盲目重试同一动作。

三、十二个容易把失败跑成绿色的反例

3.1 “最终页面对了，所以计划正确”

Agent 通过未授权的管理员入口到达同一页面，结果截图相同，权限边界已经被绕过。规划评测要检查每个意图是否在允许来源、资源和动作集合内，而不是只看终点。

3.2 “模型给的坐标很准，直接点击最快”

截图坐标可能是物理像素，浏览器动作使用 CSS viewport 坐标；页面滚动、设备像素比、浏览器缩放和截图裁剪都会改变映射。坐标必须声明坐标系、观察 ID、viewport、DPR 和滚动偏移，并在动作前验证新鲜度。

3.3 “DOM 找不到就改用截图，不需要再检查”

截图中的“删除”图标可能只是禁用占位，也可能被透明遮罩覆盖。视觉候选应与无障碍语义、DOM 边界或可交互性证据融合；视觉单源不足以授权高风险动作。

3.4 “accessible name 一样就是同一个按钮”

页面顶部和每一行都可能有“退款”按钮。角色和名称只提供语义，仍需容器、订单 ID、窗口、frame、候选数量和相对关系。Locator 严格模式报多匹配时应进入歧义，不是取第一个。

3.5 “元素可见就能点击”

可见不等于稳定、接收事件、启用或未被遮挡。WebDriver 的 Element Click 和 Playwright 的 actionability 都体现了交互条件；AI 层不能用置信度跳过执行器检查。

3.6 “弹窗挡住了目标，自动点确认即可”

弹窗可能是 cookie 提示，也可能是退款确认、权限提升或浏览器证书警告。只能处理任务合同明确允许的 prompt 类型；未知弹窗保存证据并停止。

3.7 “页面没变化，再点一次”

第一次点击可能已提交，响应只是丢失。对有副作用动作，需通过幂等键、网络请求和业务账本协调不确定提交。未确认前不能按视觉无变化重试。

3.8 “自愈后用例通过，定位器就自动入库”

候选可能只在当前主题和语言下碰巧命中。永久提升需要人工查看旧语义、新语义、候选唯一性、页面范围、反例和回归结果。运行时可以临时尝试低风险候选，但不能静默修改仓库或全局 locator。

3.9 “为了适应新版页面，把断言文字也更新”

这会把产品行为变化和测试维护混在一起。自愈只能修复如何找到目标，不能改变期望退款金额、提交次数或禁止动作。Oracle 摘要必须绑定原任务合同。

3.10 “新窗口句柄列表最后一个就是支付页”

WebDriver 不保证窗口句柄返回顺序具有业务意义。广告、身份提供商和帮助页可能同时打开。窗口切换应依据 opener、来源、标题/语义和任务许可，且在切换后重新观察。

3.11 “HTTP 200 就是业务成功”

200 可能只是异步任务受理；前端重试还可能产生两个请求。业务 Oracle 要核对目标状态、金额、资源 ID、幂等键和提交次数。无法访问业务事实时返回 UNKNOWN。

3.12 “成功率 92%，可以发布”

若失败的 8% 全是误点删除或重复提交，平均成功率没有意义。报告必须拆出未授权动作率、错误目标率、未知 Oracle、证据 coverage、恢复后通过和无恢复通过，并按风险切片。

四、贯穿构造场景：退款运营台 Iris

页面初始是一个动态订单表。搜索后，行可能因虚拟列表重渲染而换 DOM 节点；订单详情在新窗口打开；退款面板需要滚动；第一次进入会出现“新流程说明”弹窗；新版把旧的“预览退款”按钮改成两个按钮：“计算预览”和“确认并退款”。视觉样式几乎相同。

五、参考架构：Planner 不能直接拿浏览器方向盘

5.1 合同层

合同由测试编排或业务 owner 生成并签名。运行时各层只读取，不原地修改。任何范围、金额、允许来源或 Oracle 变化都产生新合同版本和新批准。

5.2 认知层

Planner 与 Perception 可以使用规则、模型或混合实现。它们输出候选和置信信息，不持有浏览器写权限。模型异常不会直接产生副作用。

5.3 控制层

Grounding 把意图和当前观察绑定；Permit 检查合同、候选唯一性、来源、上下文、新鲜度、风险、批准和预算；Action Adapter 只接收单次短期许可。

5.4 事实层

Oracle 从独立 UI、网络和业务来源计算结果。Trajectory Ledger 保存每层产物摘要和链关系。证据采集失败本身会影响门禁，不能在执行结束后靠 Agent 回忆补写。

六、任务合同：把自然语言拆成可检查不变量

6.1 合同最小字段

自由文本指令可以保留给人阅读，但执行器只使用结构化合同。金额同时包含整数最小货币单位和币种，避免 800 元/800 分；资源 ID 不从页面相似文本重新推断；禁止副作用显式列出。

6.2 合同摘要贯穿全链

Plan、观察、定位候选、动作许可、自愈提案、轨迹和 Oracle 都引用同一 contract_digest。如果任何层看到不同摘要，运行立即停止。这样可以发现中途把“预览”改成“提交”或把订单号换成当前行的攻击。

6.3 合同版本与人工批准

若测试确实要从预览升级到提交，应创建 TASK-8042@2，重新定义 Oracle、幂等键、批准人和测试环境。批准票据绑定具体合同、动作、资源、金额、目标环境和有效期，不能只写“允许退款”。

七、Planner 怎么评测

7.1 计划合法率

对每个计划步骤分别检查物理动作和业务操作是否在允许集合、业务操作是否命中禁止集、声明风险是否与合同分类一致、目标资源是否仍属于合同、来源是否允许、步骤数量是否超限。分母是 Planner 生成的所有意图，不是最终被执行的意图；否则 Permit 拦住的危险计划会从质量报告中消失。

7.2 前置条件完整率

“点击退款”至少声明当前窗口、订单详情、目标角色/名称、页面修订和无阻断弹窗。缺少前置条件的意图不能靠执行器猜测。测试可以故意删除订单 ID 或窗口条件，预期 Planner 校验失败。

7.3 最短不是唯一目标

高风险流程中，多一步“重新读取订单 ID”可能比直接点击更可靠。评测应看合同满足、动作风险、证据完整和预算，而不是只奖励步数最少。优化步数时需要约束安全和成功，不把安全检查当冗余。

7.4 动态重规划

页面变化后允许重新规划，但新计划仍以原合同为根。重规划原因、旧计划未完成部分和新观察摘要都要记录。Agent 不应因为看见“管理员登录”按钮就把它作为解决权限不足的下一步。

7.5 计划覆盖与未知

如果 benchmark 只标注一条参考路径，Agent 走另一条合法路径不应自动判错。更合适的是声明允许状态和不变量，参考路径只用于诊断。无法判断路径是否等价时标 UNKNOWN 并人工复核。

八、Perception：DOM、无障碍树和截图各看见什么

8.1 DOM

DOM 提供元素属性、文本、层级、表单关系和边界框，适合稳定语义定位。但框架重渲染会使元素引用 stale；Canvas、远程桌面或原生应用可能没有可用 DOM；隐藏节点也可能存在于 DOM 中。DOM 快照必须绑定页面修订和浏览上下文。

8.2 无障碍树

无障碍树提供 role、accessible name、state 和关系。Playwright 官方文档把 getByRole、getByLabel 等作为推荐 locator；2026-05-28 的 WebDriver 2 Working Draft 定义了 Get Computed Role 与 Get Computed Label，这两项不能归到 2018 WebDriver Recommendation。语义 locator 往往比深层 CSS/XPath 更贴近用户意图。

但无障碍语义来自应用和用户代理的计算，错误 ARIA 会产生错误语义；不同平台映射也可能不同。它既是定位来源，也是产品可访问性质量信号，不能因为自动化方便就伪造 aria-label。

8.3 Screenshot / Vision

截图覆盖用户实际看到的像素，可处理 Canvas、图标和无 DOM 场景，也能发现遮挡、布局和视觉变化。Sikuli 原始工作展示了用截图模式搜索和自动化 GUI 的路径。现代视觉模型增强了开放词汇定位，但主题、缩放、语言、相似图标和动画仍会造成漂移。

视觉来源应输出候选区域、分数、图像摘要、裁剪/缩放变换和模型版本。只返回一个 (x, y) 无法复核。

8.4 多源融合不是多数表决

DOM、无障碍树和视觉并非三个独立同质投票者。DOM 与无障碍树可能来自同一节点，错误标记会共同出错；截图能看见外观，却不知道后端资源。融合器应保留来源依赖，并按判断类型选择权威输入：语义主要看 role/name/容器，坐标看可见区域，业务结果看事实源。

来源名称本身不是证据。每个候选来源还应携带由受信生产者签名的证明，至少绑定观察摘要、目标 claim 摘要和对应原始工件摘要；DOM 证明必须指向该观察的 DOM 摘要，A11y 与 Vision 同理。融合前拒绝重复来源 ID、标签与证明不一致、跨观察复用和签名篡改，避免攻击者仅把 sources 写成三项就伪造“多源一致”。

九、坐标、语义和观察新鲜度

9.1 至少区分四种坐标

  • screenshot physical pixel：截图像素；
  • CSS viewport coordinate：当前视口 CSS 像素；
  • document coordinate：包含滚动偏移的文档坐标；
  • device coordinate：移动设备或桌面输入系统坐标。

转换必须记录 viewport、DPR、浏览器缩放、截图裁剪和滚动位置。例如截图全尺寸且 DPR=2，截图 (800, 600) 对应 CSS viewport (400, 300)；若截图只截取某个 frame，还要加裁剪原点。不能在文章或代码里笼统写“坐标除以 DPR”而忽略来源空间。

9.2 语义目标不是文本搜索

同名多个候选时，系统应报告歧义度、候选清单和区分证据。取第一个、离旧坐标最近或模型分最高，都需要达到明确策略，且高风险动作不能单源自动决断。

9.3 观察与动作之间会过期

动态页面可能在 100 毫秒内重渲染。观察由采集者签名，候选引用 observation_id、DOM revision、window/context 和 URL；Permit 绑定观察摘要与上下文。动作前若 revision 改变、签名无效或观察超出新鲜度窗口，重新观察和定位，不把旧坐标带到新页面。

十、Grounding 指标：不仅是 Top-1 命中

10.1 目标定位准确率

分母是具有可验证目标标注的意图，分子是 Top-1 候选与真值元素/区域匹配。DOM 元素可按稳定测试标注或快照 ID 比较；视觉区域可以使用 IoU 阈值，但阈值、边界框来源和多目标情形要明确。

10.2 Top-k recall

Top-k recall 衡量真目标是否进入候选集，适合评价候选生成；它不证明执行安全。Top-5 中包含正确按钮，但 Top-1 是“确认并退款”，执行仍然失败。

10.3 歧义识别率与错误自信率

测试集应包含同名按钮、重复图标、遮挡、禁用副本、离屏目标和相似弹窗。系统在无法区分时返回 AMBIGUOUS 是正确行为。需要单独统计应拒绝却给出高置信唯一候选的比例。

10.4 坐标落点率

即使语义候选正确，中心点可能被浮层遮挡，或边界框包含不可点击区域。记录期望元素、计划落点、实际 hit-test 目标和事件接收者。坐标命中和语义命中是两项指标。

10.5 数据集覆盖

定位 benchmark 要按浏览器、viewport、DPR、主题、语言、缩放、响应式布局、动画、frame、Shadow DOM 和原生/混合上下文分层。只在 1280x720 英文浅色主题截图上高分，不足以支持移动端发布。

十一、动作许可：把“能点”与“允许点”分开

11.1 单次许可对象

一次许可至少绑定：合同摘要、意图摘要、观察摘要、候选指纹、窗口/context、物理动作、业务操作、高风险批准摘要、签发时间和过期时间。候选指纹覆盖来源证明与 bbox，意图摘要覆盖风险；执行器收到实际命令后，再逐项核对动作、业务操作、候选、观察和上下文。执行时间与消费时间都必须落在短 TTL 内。

11.2 许可检查顺序

  1. 合同签名、版本和有效期；
  2. 当前 URL origin、窗口、frame 与账号身份；
  3. 物理动作与业务操作是否分别允许，业务操作是否禁止或属于高风险；
  4. 候选是否来自当前观察，是否唯一且达到来源要求；
  5. 目标是否可见、稳定、启用、接收事件；
  6. 弹窗和遮挡是否在允许处理范围；
  7. 共享步骤预算是否足够，合同是否已因恢复失败进入停止态；
  8. 高风险批准是否绑定同一资源、金额和动作；
  9. 证据采集是否可用；
  10. 签发短期 permit，核对实际命令后在共享存储中原子消费。

11.3 消费记录不能放在单个执行器内存

单次语义需要所有执行器实例共享同一消费事实。验证顺序是：验 permit 签名与有效期、验签名观察、比较 permit 与实际命令、再以 permit_id 做原子 consume-if-absent；任何一步失败都不执行命令。进程内 set 只能演示接口，重启或并发实例会绕过它。生产系统应使用具备唯一约束和事务语义的持久存储，并把 permit 摘要、实际命令摘要和消费时间一并留证。

11.4 WebDriver 与 Playwright 的执行边界

WebDriver Recommendation 定义了浏览器远程控制命令与元素交互语义；Element Click 包含滚动到视图、可交互中心点与遮挡错误等概念。Playwright actionability 在点击前检查唯一、可见、稳定、接收事件和启用等条件。AI 控制层应复用这些执行器能力，不用模型判断替代协议和工具的确定性检查。

11.5 移动端与 Appium

Appium 建立在 WebDriver 生态上，并按驱动暴露 accessibility id、平台原生 locator、XPath 和图像等策略。原生/混合应用还需绑定 context、设备方向、系统弹窗、软键盘和平台权限。跨平台的“同一 locator”不意味着相同行为，驱动与平台版本必须进入证据 manifest。

十二、自愈：只生成候选，不能静默修改期望

12.1 可自愈的对象

定位器语法、稳定属性、容器路径和视觉模板可以生成候选。例如旧 getByRole('button', {name: '预览退款'}) 找不到，新页面出现 role=button,name=计算预览，系统可提交候选并附 DOM diff、无障碍语义、截图区域和命中范围。

12.2 不可自愈的对象

任务资源、金额、允许来源、动作风险、业务后置条件、期望提交次数和禁止副作用不能由运行时自愈。若产品语义真的变化，测试 owner 应修改合同和 Oracle，并审查产品需求，而不是让模型“理解一下新版意思”。

12.4 提升流程

候选必须来自当前签名观察，并且是 Grounder 对同一 Intent、观察和候选集合给出的唯一签名 Resolution；跨 window/context、单来源或歧义结果不得生成提案。候选随后在 held-out 页面、主题、语言和 viewport 上回放，检查唯一性、误命中和旧版兼容。人工审阅语义与截图后，针对同一合同和 oracle_digest 签署 PROMOTED。仓库变更走普通代码评审；运行时 Agent 无权直接写测试源码。

十三、动态页面、弹窗、滚动与多窗口

13.1 等待的是状态，不是固定睡眠

页面加载完成不等于业务数据稳定。等待条件应绑定目标状态，例如订单行出现且 aria-busy=false、网络请求完成、按钮稳定并可交互。固定 sleep 既慢又无法处理长尾；无限自动等待又会掩盖性能问题。每个等待有预算、观察记录和超时状态。

13.2 虚拟列表

订单行离开 viewport 后可能被回收并复用 DOM 节点。元素引用必须在动作前重新验证订单 ID；滚动后旧引用失效是正常现象。测试应注入列表排序、数据插入和滚动抖动，确认 Agent 不按旧行号点击。

13.3 弹窗与遮挡

先识别类型：浏览器 prompt、应用 modal、cookie banner、权限弹窗或系统对话框。只有合同允许的低风险遮挡可自动处理。退款确认属于业务动作的一部分，不能当作“挡路弹窗”关闭或确认。

13.4 Frame 与 Shadow DOM

Frame 改变浏览上下文，Shadow DOM 改变节点查找边界。候选应携带完整 context 路径，切换后重新观察。跨源 frame 还受安全边界约束，不能通过脚本注入绕过。

13.5 多窗口

新窗口通过 opener、创建事件、允许 origin 和资源语义识别。WebDriver 句柄集合顺序不应被当成创建顺序；WebDriver BiDi 的 browsing context 事件更适合记录创建、导航和关闭，但截至本文边界它仍是 W3C Working Draft，使用时应锁定实现版本与能力。

13.6 滚动

区分页面滚动、容器滚动和元素滚动。滚动是动作，也消耗步骤并产生 before/after 观察。滚动后重新计算 bbox 和遮挡，不沿用旧 screenshot 坐标。

十四、Oracle：页面提示只是一个证据源

14.1 三层 Oracle

层 能证明 不能单独证明
UI 页面显示、控件状态、可见提示 后端是否唯一提交、金额是否落账
Network 请求、响应、重试、状态码、请求 ID 异步任务最终业务状态
Business 订单/退款账本、提交次数、金额、幂等键 用户当时看到的界面是否正确

Iris 的预览任务需要 UI 显示 80000 minor units 对应的格式化金额，同时业务事实确认 refund_commit_count=0。若业务事实源不可用，不能仅凭预览页面返回 PASS。

14.2 Oracle 不读取自愈后的“新预期”

运行开始时保存 oracle_digest。自愈提案、重规划和执行证据都引用它。任何层提交不同摘要立即 DENY。产品需求变化应创建新合同，不在失败现场修改断言。

14.3 不确定提交

副作用请求发出后连接断开，状态既不是简单失败也不是可安全重试。系统先停止同类动作，用业务幂等键、网络 request ID 和目标账本查询结果；查不到时保持 UNKNOWN 并转人工。恢复预算不能授权“再点一次看看”。

14.4 业务快照必须覆盖动作时间

签名正确的旧快照仍不能证明本次动作后的状态。快照的 observed_at 必须不早于动作完成、不晚于 Oracle 求值，求值时刻不能超过 valid_until，年龄不能超过合同策略窗口；要求强一致后置条件时，EVENTUAL 快照返回 UNKNOWN，只有声明为 FINAL 的新鲜快照才进入金额、资源和提交次数比较。动作完成时间晚于求值时间属于无效时间线，直接 DENY。

截至 2026-06-25，可固定引用 2026-06-22 WebDriver BiDi Working Draft。它定义双向协议以及 browsing context、network、log 等模块和事件，为流式采集导航、窗口和网络证据提供标准化方向。Working Draft 会变化，客户端、浏览器和功能能力必须进入 manifest。

15.5 轨迹验证必须检查语义闭合

哈希连续只证明“已写入的记录未被改”，不能证明动作没有漏记。追加步骤时还要验证：合同在执行时有效，before/after 观察签名有效，permit 已由同一实际命令消费，Intent、Candidate、Permit 与命令的动作/业务操作/目标/上下文完全一致，before/after 时间包围执行时刻，网络引用非空，Oracle 引用原合同。最终 sequence 数必须等于独立 manifest 的预期步骤数；空链或少一步都不能通过。

十六、指标：每个成功率都要带机会分母

16.1 任务合同通过率

Oracle 缺失的运行进入 unknown 分母并单列，不能从分母删除。

16.2 计划非法率

即使 Permit 全部拦截，Planner 仍产生了风险信号。还要统计禁止副作用、错误资源、错误来源和超预算四类原因。

16.3 定位指标

报告 Top-1 accuracy、Top-k recall、应拒绝场景的 abstention recall、错误高置信率、语义命中率和实际落点命中率。分母按拥有真值的意图计算，真值缺失单列。

16.4 动作安全指标

第二个值必须为 0；第一个值反映 Planner/Grounding 质量和攻击流量，不能因为执行器拒绝就不记录。

16.5 Oracle coverage

UI、网络和业务事实分别统计。页面文本存在不能补业务事实缺失。

16.6 恢复指标

区分无恢复通过、恢复后通过、预算耗尽停止、不确定提交停止和人工接管。恢复后通过率高可能说明自愈有效，也可能说明基础定位器长期无人维护，需要结合恢复原因。

16.7 轨迹完整率

分母来自每个动作类型的证据 profile，例如点击要求 before/after、候选、permit、实际落点和 driver result。缺一项就进入 gap，不按“文件数量看起来差不多”判断。

十七、恢复预算与安全停止

17.1 预算维度

不只限制总步骤，还分别限制重新观察、重新定位、滚动、窗口切换、页面刷新和模型调用。某些动作成本和风险不同，不能共享一个无限重试计数器。总步骤和恢复次数必须按合同摘要保存在所有执行实例共享的原子状态中；服务重启、重规划或换执行器不能把计数清零。

17.2 可恢复失败

stale element、低风险遮挡、合法窗口刚创建、内容尚在加载，可以在预算内重新观察。恢复原因使用封闭枚举；未知字符串采取 fail-closed 并停止合同，避免拼写错误落入“普通可重试”。每次恢复都从 Perception 开始，不从旧坐标继续。

17.3 不可自动恢复

高风险无批准、合同摘要不一致、未知 origin、账号身份变化、证据采集失效、实际目标与许可不一致、疑似不确定提交，直接安全停止。停止动作本身写入轨迹，并确保后续副作用命令被拒绝。

17.4 转人工需要什么

人工接管包包含当前合同、最后可信观察、候选与歧义、已执行动作、可能副作用、网络/业务查询和剩余预算。不能只发一句“Agent 失败，请处理”，否则接管者还要重新猜现场。

十八、发布门禁与故障注入概览

构造门槛可以要求：合同合法率 100%，高风险未授权执行 0，Top-1 定位准确率不低于 0.95，应拒绝场景识别率不低于 0.98，业务 Oracle coverage 不低于 0.99，轨迹完整率不低于 0.98，关键任务通过率不低于 0.97。数字只是示例，必须按风险切片并绑定评测 manifest。

需要注入的故障包括 DOM 重渲染、A11y 名称错误、视觉相似按钮、DPR/缩放变化、透明遮挡、动态弹窗、虚拟列表换行、新窗口并发、网络响应丢失、业务提交延迟、重复请求、证据存储失败和自愈试图修改 Oracle。代码部分将这些边界实现为可执行状态。

十九、完整离线实现：合同、定位、许可、自愈、Oracle 与轨迹

下面的纯 Python 标准库示例不连接浏览器，也不调用模型。它把 UI Agent 的关键控制面模拟成可单元测试对象：Planner 只能生成意图；Grounder 验证签名观察与来源证明；Permit 把授权绑定到实际命令并通过共享存储单次消费；步骤/恢复预算跨实例共享；Oracle 校验快照时效；轨迹按预期步骤 manifest 闭合；自愈只生成绑定原合同与上下文的待审提案。

19.1 为什么合同把 Oracle 单独摘要

contract_digest 覆盖整个任务，oracle_digest 只覆盖资源、金额、币种和提交次数。自愈提案同时引用两者：定位实现可以变，业务预期不能跟着变。若需求确实改变，必须由合同签发者创建新版本，不能在失败运行里替换摘要。

19.2 为什么视觉单源被限制在阈值下

视觉能够在 DOM 不可用时生成很有价值的候选，但它看见的是像素，不天然知道元素是否属于 O-8042、是否禁用、是否被透明层遮挡。示例允许视觉参与多源定位，却不让视觉单源自动跨过执行阈值。实际系统可以按低风险动作放宽，但应由策略显式配置，而不是由模型自己提高置信度。

19.3 为什么 permit 同时绑定 candidate 与 observation

只绑定元素名称会让同名按钮复用许可；只绑定坐标会让页面重排后点到另一个对象；只绑定 observation 会让其中任一候选被替换。示例同时绑定候选、观察、window/context、物理动作和业务操作，并在消费时与 ActualCommand 逐项比较。十秒 TTL 只是构造值：命令执行和原子消费都必须发生在窗口内，消费事实由多个 authority 实例共享，因此改 operation、跨上下文、过期补记或跨实例重放都会失败。

19.4 为什么高风险批准还要绑定目标指纹

“允许退款”这样的批准范围过宽。示例把合同、物理动作、业务操作、资源、候选指纹和有效期一起签名，并把批准摘要写入 permit，因此 O-8042 的批准不能拿去点击 O-9001，也不能从“确认退款”移到“修改收款账户”。生产批准还应绑定金额、币种、审批职责分离和业务幂等键。

19.5 为什么业务事实缺失返回 UNKNOWN

预览页面正确并不能证明没有真实退款提交。Iris 合同明确要求提交次数为 0，所以业务账本是必需 Oracle。访问失败、签名无效会 DENY；来源暂不可用、快照早于动作、来自未来、过期、超龄或尚未达到 FINAL 时没有资格输出 PASS，而是 UNKNOWN。三态区分完整证据下的不满足与暂时无法判定。

19.6 为什么恢复预算遇到不确定副作用立即归零

不确定提交不是普通 locator 失败。第一次请求可能已经被目标接受，再点一次会重复副作用。此时剩余三次恢复预算没有意义，正确动作是锁住该运行、按幂等键和业务账本查询、转人工。预算约束的是可安全重试的感知和导航，不授权重复业务动作。

19.7 为什么哈希链仍不等于完整轨迹

示例链能发现链内步骤被改、重排或断开，并要求最终步骤数等于独立 expected_steps，所以空链和缺步不能伪装成完整轨迹。追加时还验证签名 before/after 观察、已消费 permit、实际命令、候选、时间包络、上下文、网络引用和 Oracle 摘要。生产实现仍需从独立动作代理取得预期序号，把检查点锚定到持久存储，并用浏览器/业务事实交叉对账；若同一进程同时控制动作和分母，它仍可能一起隐瞒整次执行。

二十一、完整排障：绿色 Toast 后为什么出现两笔退款

21.1 场景与初始报告

TASK-8042 在 UI Agent 平台显示 PASS：Planner 完成 11/12 步，定位平均置信度 0.93，最后截图有绿色 Toast，网络面板最后一个请求为 200。自愈模块报告把旧 locator 成功更新为 button:has-text("确认并退款")。

业务值班五分钟后发现沙箱账本出现两笔 800 元退款。平台第一反应把原因标成“测试环境网络抖动”，准备加长超时。

21.2 先冻结现场

先停止该账号的退款权限和所有同版本 Agent 任务，冻结合同、Planner 版本、Perception 模型、页面构建、Playwright trace、自愈提案、网络 request ID 和账本快照。不能为了复现继续点击真实按钮，也不能重新运行后覆盖原 trace。

21.3 对齐四条时间线

把 Planner 意图、浏览器动作、网络事件和业务提交分别按发生/观察时间对齐：

最终截图只对应第二次响应，无法表达第一次请求已经在途。延长超时可能减少重试概率，却不能修复许可和幂等边界。

21.4 核对合同与计划

合同禁止 REFUND_SUBMIT，Planner 的自然语言意图仍写“打开退款预览”。问题发生在 Grounding：自愈把“预览退款”映射到“确认并退款”，随后执行层只检查 locator 是否存在，没有把候选语义和合同动作重新分类。也就是说，Planner 文本合法不能证明实际动作合法。

21.5 核对多源感知

DOM 与无障碍树都清楚给出 accessible name“确认并退款”，视觉模型则因为位置和颜色与旧按钮接近给出 0.93。自愈摘要只展示视觉分数，隐藏了语义冲突。正确融合应把 A11y 名称冲突作为阻断证据，而不是让视觉位置覆盖语义。

21.6 核对坐标与实际目标

Playwright action snapshot 显示点击确实落在“确认并退款”，不是坐标漂移。这个事实排除了“点错像素”，却强化了“语义目标错误”。排障不能看到命中坐标就停止；要继续比较 Intent、Candidate、Permit 和实际 hit target。

21.7 核对网络与业务 Oracle

两个请求没有共享业务幂等键，后端各自提交。Agent 把 HTTP 超时分类为可恢复 UI 失败，消耗一次普通 retry；业务 Oracle 只读 Toast，没有查询提交次数。四个控制同时缺失：动作重分类、单次许可、未知提交停止和业务事实 Oracle。

21.8 修复

第一，Task Contract 分开约束 CLICK 与 REFUND_SUBMIT，候选业务操作与意图或合同不一致时 DENY。第二，Grounder 验证每个来源的签名证明与当前观察工件，不允许视觉覆盖 A11y 的高风险语义。第三，每个动作使用绑定实际命令的单次 permit，由共享存储原子消费，任何 observation revision 或 context 变化都重新授权。第四，副作用请求必须带合同派生的业务幂等键；响应未知后进入 UNCERTAIN_SIDE_EFFECT，禁止重试。第五，Oracle 同时核对 UI 预览金额和动作后的新鲜最终账本快照。第六，轨迹按独立步骤 manifest 验证完整性。

21.9 回归与恢复门禁

新增用例覆盖旧/新版双按钮、相似视觉、错误 ARIA、两个同名按钮、透明遮挡、响应丢失、第一次提交晚到和重复 request。恢复后连续运行 500 个构造任务，无未授权执行；所有响应未知场景安全停止；业务 Oracle coverage 为 100%。这些数字仍只对冻结 manifest、沙箱页面和已列故障成立。

21.10 复盘结论

根因不是“视觉模型选错”一个点。系统允许 locator 自愈改变动作语义，执行器不理解合同，网络重试没有副作用状态，Oracle 又依赖 UI。模型错误是触发条件，控制缺失让它变成两笔退款。复盘 action item 要分别修四层并提供完成证据。

二十二、评测集怎么设计

22.1 任务合同集

覆盖读取、搜索、填写、预览、下载、提交和删除等风险级别。每个任务有允许状态集合、禁止副作用和独立 Oracle，不只提供一条参考轨迹。加入提示注入、错误账号、过期合同和跨 origin 链接。

22.2 规划集

给定相同合同和不同页面状态，标注合法意图集合、必要前置条件和应停止状态。评测 Planner 是否越权、遗漏资源约束、循环、超预算或在未知副作用后重试。开放路径用状态约束评价，不强迫逐 token 匹配参考计划。

22.3 定位集

保存 DOM、无障碍树、截图、viewport、DPR、scroll、window/context、目标元素和可点击区域。构造同名、多语言、主题、缩放、响应式、Shadow DOM、Canvas、遮挡和离屏场景。训练、阈值开发和测试按页面组件/版本分隔，避免同一截图轻微裁剪后跨集合。

22.4 自愈集

同时包含“locator 变化但语义不变”和“视觉相似但语义已变”。后者是关键反例。标注应接受的候选、必须人工升级的候选和必须拒绝的产品行为变化。Oracle 永远从合同读取，不作为自愈标签。

22.5 执行集

在真实浏览器/设备沙箱注入动画、迟到弹窗、元素移动、窗口并发、网络中断和目标延迟。检查实际 hit target、请求、幂等键和业务后置条件。离线截图定位不能替代这一层。

22.6 证据集

删除 before screenshot、替换 DOM 摘要、伪造来源标签、打乱网络事件、篡改 permit、跨实例重放、复用批准、断开业务事实源或提供动作前旧快照。验证报告显示 gap、DENY 或 UNKNOWN，不生成看似完整的自然语言轨迹。

二十三、分层验证策略

23.1 单元层

测试 URL origin、合同签名、计划合法性、候选打分、来源证明、歧义、坐标转换、permit 与实际命令绑定、TTL/共享单次消费、批准绑定、Oracle 三态与快照时效、共享步骤/恢复预算和轨迹 manifest。数值输入覆盖 NaN、Infinity、负数和空分母。

23.2 组件层

固定观察 manifest，分别替换 Planner、Grounder、Permit 和 Oracle，确认层间契约。恶意 Planner 不能直接调用 Action；伪造 Resolution 不能获得 permit；自愈服务不能写合同或 Oracle。

23.3 浏览器集成层

使用固定浏览器和页面构建验证 WebDriver/Playwright 的元素语义、actionability、frame、窗口、网络与 trace。记录浏览器、驱动、操作系统、viewport、locale 和工具版本。浏览器升级需要回归，而不是假定协议相同就行为完全相同。

23.4 移动设备层

Appium 场景覆盖原生、WebView、context 切换、方向、软键盘、系统权限和 accessibility id。真机与模拟器的截图、字体和系统弹窗不同，需要独立切片。

23.5 端到端业务层

从合同签发到业务事实核对，使用隔离账号与可清理数据。每个副作用有幂等键、额度和清理证明。测试成功条件包括数据恢复，不以脚本退出码结束。

23.6 人因层

让审阅者处理高置信错误候选、隐藏语义冲突和看似合理的自愈 diff，测量是否发现风险、界面是否诱导一键接受、人工接管包是否足够。人工在环不自动等于安全，界面和负荷也要测。

23.7 按动作风险分级，而不是按模型分数授权

只读动作包括读取页面、展开非敏感区域和查询状态，可以在合同、来源与证据有效时自动执行；即使如此，也要限制跨账号、跨租户和敏感字段截图。低风险可逆动作包括填写尚未提交的表单、切换筛选条件和滚动，允许在小预算内恢复，但页面刷新或窗口切换后重新许可。

中风险动作会改变暂存状态、发送内部通知或创建可撤销草稿。它们需要更强的多源定位、明确业务幂等键、动作后 Oracle 和自动清理；连续失败或证据缺口转人工。高风险动作包括付款、退款提交、删除、权限与收款账户修改、对外发送和不可逆确认，只能在隔离环境、目标绑定批准和独立业务 Oracle 完整时执行。模型置信度再高也不降低风险等级。

同一个 CLICK 在不同目标上风险完全不同，因此风险分类不能只看浏览器命令。Permit 应根据目标语义、资源、业务动作和环境计算有效风险：点击分页按钮是低风险，点击“确认并退款”是高风险，点击未知图标则是 UNKNOWN 并停止。产品页面改版导致语义无法映射时，系统不能沿用旧分类。

风险升级规则也要明确：候选仅来自视觉、出现未知 modal、账号身份变化、origin 跳转、业务事实源不可用或第一次副作用状态不确定，都会把当前动作提升到人工处理。降级只能由新合同和有权批准发生，运行时 Planner 与自愈服务没有修改风险的权限。

二十四、运行与发布清单

24.1 合同与规划

  • 合同结构化、签名、版本化并有有效期。
  • 资源、账号、origin、物理动作、业务操作、金额和禁止副作用明确。
  • Oracle 与证据 profile 在运行前冻结并有摘要。
  • Planner 无浏览器写权限，所有意图经过合同校验。
  • 动态重规划引用原合同并记录原因。

24.2 感知与定位

  • 观察绑定 URL、window、frame/context、revision、viewport、DPR 和 scroll。
  • DOM、A11y、Vision 来源分别保存签名证明并绑定当前观察工件，不压成一个分数。
  • 候选包含语义、容器、bbox、来源、模型/规则版本和观察 ID。
  • 同名、相似、离屏和遮挡能进入 AMBIGUOUS/UNKNOWN。
  • 动作前重新验证候选新鲜度和实际 hit target。

24.3 许可与执行

  • permit 绑定合同、意图、候选、观察、窗口、动作/业务操作、批准摘要和 TTL。
  • 实际命令逐项匹配 permit，消费记录使用跨实例共享的原子持久存储。
  • 步骤与恢复预算按合同共享；未知恢复原因和耗尽状态 fail-closed。
  • 高风险批准绑定资源、金额、动作、目标和有效期。
  • 未知 modal、origin、身份或证据失败会安全停止。
  • 副作用请求带业务幂等键，不确定提交不自动重试。
  • force click、任意脚本注入和关闭安全检查被策略禁止。

24.4 自愈

  • 自愈只产候选，不直接修改仓库、合同或 Oracle。
  • 候选至少包含两类签名来源证据、唯一签名 Resolution 及完整 diff。
  • 提案和提升都绑定当前 contract/oracle、observation 与 window/context。
  • 永久提升经过 held-out 回放、人工审核和代码评审。
  • 统计误命中、撤销和掩盖产品回归的案例。
  • 自愈失败不循环生成无限候选。

24.5 Oracle 与证据

  • UI、Network、Business Oracle 的职责和必需性写入合同。
  • 业务快照签名、动作后时效、valid_until 与一致性等级全部验证。
  • 每项指标有分子、机会分母、未知和适用切片。
  • 每步 before/after、候选、已消费 permit、实际命令和 network ref 齐全。
  • 实际步骤数与独立 manifest 一致，空链和缺步不能通过。
  • 截图、DOM、网络正文按最小化、脱敏和保留策略处理。
  • 轨迹链有独立检查点和动作/业务对账，不迷信单一哈希。

24.6 发布与值班

  • 未授权执行数为 0，Planner 未授权尝试单独可见。
  • 定位准确、歧义识别、Oracle coverage 和证据 coverage 分开门禁。
  • 关键任务按风险、浏览器、语言、viewport 和页面版本切片。
  • 降级到确定性脚本或人工队列的容量已验证。
  • 值班 runbook 能处理不确定提交、账号冻结、对账和人工接管。

二十五、局限与不适用场景

第一，开放式 UI 探索和固定回归测试目标不同。核心资金、删除和权限流程更适合确定性脚本加严格数据合同；AI Agent 可以用于候选生成和探索，不必为了“智能化”接管所有动作。

第二，视觉定位容易受数据分布和供应链变化影响。闭源模型升级、截图预处理和 OCR 版本都可能改变分数；需要固定版本、回放和漂移门禁。

第三，DOM 与无障碍树不是绝对真值。应用错误标记、浏览器映射和平台差异会共同误导，需要实际 hit-test、截图和业务事实交叉验证。

第四，业务 Oracle 也可能延迟或错误。账本快照需要版本、时间和一致性语义；最终一致系统应定义等待窗与 UNKNOWN，不能无限等待到想要的结果出现。

第五，执行证据包含高敏数据。截图裁剪和 DOM 脱敏可能降低调试能力，需要按任务风险设计最小必要证据；本文不提供具体隐私或法律结论。

第六，HMAC、短 TTL、线程锁和哈希链只是教学实现。示例的消费与预算存储虽由多个 authority 对象共享，仍只存在单进程内存中；生产系统需要托管身份、密钥轮换、撤销、可信时间、具备唯一约束的事务存储、追加日志、独立检查点和最小权限网络隔离。

第七，人工批准可能疲劳或橡皮图章化。审批界面应展示动作语义、资源、金额、候选冲突和业务影响，不能只显示模型摘要与绿色置信度。

第八，本文没有模拟真实浏览器事件循环、跨进程竞态、操作系统输入或移动设备差异。标准库测试验证控制逻辑，真实兼容性仍需工具和设备矩阵。

二十六、一手资料与引用边界

以下资料均在本文发布日期 2026-06-25 之前发布或形成相应固定快照。标准描述协议或可访问性语义，工具文档描述具体实现能力，论文说明视觉自动化思路；它们不替本文构造业务定义统一安全阈值。

  1. W3C WebDriver, Recommendation 5 June 2018。用于远程控制、会话、元素定位、窗口、用户提示和元素交互的稳定标准边界。具体浏览器实现与后续草案仍需锁定版本测试。
  2. W3C WebDriver 2, Working Draft 28 May 2026。用于 Shadow Root、Get Computed Role、Get Computed Label 等本文提及的后续协议能力。它是 Working Draft，不是 Recommendation。
  3. W3C WebDriver BiDi, Working Draft 22 June 2026。用于双向协议及 browsing context、network、log 等事件能力。它是 Working Draft，不应被描述为最终 Recommendation。
  4. Web Content Accessibility Guidelines (WCAG) 2.2, W3C Recommendation。用于理解 Name/Role/Value、focus、target size 等可访问性要求边界；本文没有把 locator 命中等同于 WCAG 合规。
  5. WAI-ARIA 1.2, W3C Recommendation 6 June 2023。用于 role、state、property、无障碍树和命名语义。错误使用 ARIA 可能同时伤害用户与自动化。
  6. Accessible Name and Description Computation 1.2, Working Draft 29 May 2026。用于名称与描述计算概念。它是 Working Draft，不是 Recommendation；工程证据应记录浏览器与实现版本。
  7. Playwright Locators、Auto-waiting and Actionability 与 Trace Viewer。官方在线文档用于 locator、动作检查和 trace 能力边界；页面会更新，生产 manifest 应锁定实际 Playwright 版本。
  8. Appium Finding Elements。用于 accessibility id、平台 locator、XPath 和图像候选等历史官方能力说明；实际使用应以安装的 Appium 与驱动文档为准。
  9. Yeh, Chang and Miller, Sikuli: Using GUI Screenshots for Search and Automation, UIST 2009。原始论文用于截图模式搜索和视觉脚本思想的来源背景，不代表现代视觉模型或本文安全控制已被该论文验证。

二十七、结语：让 Agent 提议，让控制面决定，让事实源验收

AI 驱动 UI 自动化不是把自然语言接到 click(x, y)。一条可发布的链路应始终保留四个独立判断：

动态页面可以重新观察，stale 元素可以重新定位，低风险遮挡可以在预算内恢复，自愈可以生成候选；合同、业务预期、禁止副作用和人工责任不能在运行时被“修好”。遇到歧义、证据缺失或不确定提交时，安全停止不是自动化失败，而是受控系统正确执行了边界。

最终报告也不应只给“任务成功率”。它要能说明 Planner 是否越权、定位是否错误自信、哪些动作被拒绝、哪些运行因 Oracle 缺失而未知、恢复消耗了什么预算、证据链缺了什么，以及谁批准了高风险动作。只有这样，AI 带来的路径灵活性才不会以责任和可复核性为代价。
