AI测试-63-AI生成测试用例怎么控制重复覆盖错觉断言质量和维护成本

发表于 2026-06-21 分类于 AI测试 本文字数： 21k 阅读时长 ≈ 1:16

AI 在十分钟内为一个权限模块生成了 480 个测试，测试数增长了 12 倍，语句覆盖率从 71% 升到 96%。这是否说明风险覆盖显著提升？

不能。

其中 310 个测试可能只是同一模板替换用户 ID；90 个虽然语法不同，却走相同分支并检查同一个宽松条件；40 个只断言 HTTP 200 或结果非空；20 个依赖共享管理员账号，单独运行通过、并行运行漂移；另有一批测试覆盖了已经无法从生产入口到达的兼容代码，却没有覆盖“跨租户访问必须拒绝”这个高风险不变量。最终测试数量、语句覆盖率和流水线时长都增加了，发现缺陷的能力却可能没有增加。

因此，生成数量不等于覆盖。生成数量描述候选产量；覆盖需要一个经批准的风险或代码机会分母；测试资产还要证明自身有区分错误实现的断言、独立数据、稳定信号、可诊断失败和可承担的维护成本。

更准确的闭环是：

本文资料边界截至 2026-06-21（含）。全文的组织、产品、仓库、需求、代码、测试、数据、故障、变异体、运行次数、耗时、比例、阈值、预算和结果均为构造示例，不代表任何真实公司、工具、模型或项目。构造门槛只用于说明如何实现门禁；实际组织应按业务风险、历史测试分布、运行资源、缺陷成本和维护能力批准自己的分母、阈值与生命周期。

一、边界：生成器生产的是候选，不是覆盖证明

1.1 五种对象不能混用

对象 定义 何时能进入统计分子
风险需求 需要被验证的业务不变量、威胁或失效模式 经 owner 批准并有明确可达性状态
生成尝试 一次模型或规则生成动作 只进入生成效率分母
候选测试 有源码、来源、目标风险和候选 oracle 的产物 通过基础解析后进入候选池，不算正式覆盖
观察期测试 已过静态、执行、断言、变异和数据门禁 可参与非阻塞或受控门禁，持续收集稳定性证据
正式资产 有 owner、寿命、维护预算、稳定证据和淘汰规则 才能支持批准范围内的风险覆盖声明

删除一个重复候选不会删除风险需求；新增十个候选也不会让同一个风险被覆盖十次。资产与需求通常是多对多：一个测试可能支撑多个风险，一个高风险需求也可能需要多个不同层级测试共同支撑。

1.2 本文要测什么

本文关注 AI 生成测试的质量控制面：

  • 风险需求如何形成稳定分母；
  • 候选与仓库、生成配置、数据来源如何绑定；
  • 结构、行为和语义重复如何识别；
  • 语句/分支覆盖如何声明 source、排除和不可达；
  • mutation testing 如何与等价变异、超时和未知共存；
  • 断言是否会因相关故障而失败；
  • 测试数据、顺序、并发和环境是否独立；
  • flaky 如何重复测量并给出不确定性；
  • 运行与维护预算如何进入晋级和淘汰。

1.3 本文流程不能证明什么

  • 不能证明生成器理解了需求；只验证候选与批准证据的关系。
  • 不能证明高代码覆盖等于高风险覆盖。执行到一行不等于检查了它的后置条件。
  • 不能证明 mutation score 高就没有真实缺陷。变异算子只代表选定的错误模型。
  • 不能自动判定所有等价变异。一般程序等价问题无法靠一个简单规则完整解决。
  • 不能证明重复运行全过的测试永远不 flaky；有限次数只支持带区间的声明。
  • 不能证明当前低维护成本会持续。接口、fixture、数据和依赖变化会改变成本。
  • 不能用 AI 生成测试替代风险分析、代码评审、生产监控和事故回灌。
  • 不能把本文的构造阈值复制成行业标准。

二、十三个会制造“测试很多”错觉的方案

2.1 先让模型自由生成，再按数量验收

没有风险需求和分母时，生成器会偏向容易表达的 happy path。数量验收奖励重复、浅断言和无成本意识。更合适的顺序是先建立需求、可达性与 oracle 合同，再按未覆盖风险生成候选。

2.2 文件名不同就算不同测试

test_admin_can_read_01 与 test_admin_can_read_02 可能只换了 ID；重命名变量、把 assertEqual 改成 assert 也不增加行为。文件、函数名和文本哈希只适合找完全重复，不能控制近重复。

2.3 AST 不同就视为语义不同

一个测试用循环，一个展开三行；一个调用 helper，一个直接调 API。结构不同仍可能执行同一路径、使用同一数据类并检查同一后置条件。因此还要比较行为轨迹与语义合同。

2.4 语句覆盖 100% 就停止生成

一行 if tenant_id != document.tenant_id: return DENY 可以被管理员 happy path 执行到条件判断，却从未取 true 分支。即使分支覆盖也高，测试可能只断言非空，没有验证 DENY。覆盖描述执行，不描述 oracle 强度。

2.5 把不可达代码直接从分母排除

“当前测试跑不到”不等于“生产不可达”。排除需要入口、配置、调用图、特性开关、版本和时间范围的证明，以及 owner 批准。证据不足时状态是 UNKNOWN；从分母静默删除会人为抬高覆盖率。

2.6 mutation score 用 killed / all generated

等价变异无论如何都不能被测试区分；编译失败、超时、未执行和工具错误也不是普通存活。把它们全部放进一个分母会误导方向，直接删除又可能掩盖工具问题。至少分出 killed、survived、equivalent-approved、timeout 和 invalid。

2.7 测试失败就算杀死变异

测试可能因环境、共享数据或无关 assertion 失败。有效 kill 要证明目标变异被执行，并由与该失效机制相关的断言失败；基础设施错误和随机失败不能算杀伤。

2.8 断言越多质量越高

十个 assert response is not None 仍可能放过错误授权；精确比较所有 JSON 字段又可能因无关时间戳变得脆弱。断言要对应业务后置条件，既能对相关故障敏感，又不绑定无关实现细节。

2.9 用生产数据副本提高真实性

真实数据可能包含个人信息、秘密和未知关联；共享副本也使测试相互污染。更可靠的做法是从风险合同构造最小数据，使用每个 case 独立命名空间，并记录来源、清理与用途。

2.10 失败后自动重跑直到通过

重跑可以采样不确定性，不能把第一次失败抹掉。pass on retry 是 flaky 证据，不是成功证据。原始序列、代码与环境摘要、顺序、并发和随机种子都要保存。

2.11 只在固定顺序运行

共享全局状态、缓存和数据残留会被稳定顺序掩盖。候选至少要单独、随机顺序、反向顺序和并发条件下重复；失败后检查前序 case 与资源所有权。

2.12 测试进主干后永不删除

风险退出、接口替换或测试被更强资产覆盖后，旧测试可能只增加时间与噪声。退役不是删除历史：需要保存理由、替代关系、最后有效版本和 owner 批准。

2.13 用失败率惩罚测试作者

这会激励放宽断言、隐藏失败和跳过不稳定测试。flaky 指标用于修复信号与系统状态，不适合脱离上下文评价个人。维护治理应关注根因、owner、隔离时限和风险缺口。

3.3 第一轮生成为什么 180 个只留下 11 个候选簇

构造生成器输出 180 个测试：

  • 84 个是管理员读取活动文档，只有 ID 不同；
  • 37 个把 assertEqual(decision, "ALLOW") 换成不同语法；
  • 26 个走 READER happy path 并只断言非空；
  • 18 个使用共享 admin fixture，行为与前两组重叠；
  • 9 个目标是 UNKNOWN 的 legacy 分支；
  • 6 个真正覆盖暂停、跨租户、删除、clearance、owner 与 reader 边界。

文本哈希得到 180 个不同值，AST 常量归一后形成 29 个结构簇，隔离 runner 的路径/调用/结果向量形成 14 个行为簇，风险与 oracle 语义归一后只剩 11 个语义簇。其中 3 个语义簇没有有效风险需求，9 个 legacy 候选因可达性未知进入待调查，不得计入正式覆盖。

所有数字均为构造示例。关键不是“去掉 169 个测试”，而是保留每层聚类依据，并检查被合并候选是否真的具有相同失效检测能力。

四、从风险需求到候选：先定义分母再调用生成器

4.1 风险需求的最小字段

oracle 不只写一个返回值，还包含副作用和不可见性。跨租户请求对外统一为 NOT_FOUND，内部审计保留 TENANT_MISMATCH；未授权请求不访问文档存储，避免时序与缓存侧信道。

4.2 来源与版本变化

风险可来自需求、威胁建模、代码不变量、事故、支持工单和合规控制。每条都要链接事实源，不把模型生成的解释直接当批准需求。需求变化产生新版本，已有测试重新做关联分析：继续适用、需修改、被替代或退役。

4.3 生成 Prompt 不是质量合同

“请覆盖边界并写高质量断言”无法验证。生成请求应包含：

  • 当前未覆盖的风险 ID 与版本；
  • 被测公共接口和允许依赖；
  • fixture 与数据创建规范；
  • 不允许访问的网络、生产数据和时钟；
  • 必须表达的 oracle 与禁止宽松断言；
  • 输出 Schema：源码、目标风险、前置条件、数据所有权、预期故障；
  • 候选只是草稿，最终关联由独立检查决定。

4.4 候选 manifest

后续运行、覆盖、变异、故障注入和观察期证据都绑定 candidate 与 policy 摘要。源码或风险登记变化后，旧证据不得重放。

manifest 中的仓库 tree 和生成器摘要是候选声明，不是候选自己就能确立的信任根。门禁必须将它们与控制面预先冻结的 repository_tree_digest 和 generator_manifest_digest 精确对账；否则攻击者可以为另一棵树或另一个生成器自签一套内部一致的报告。

五、三层去重：文本相似只是最外层

5.1 结构重复

结构指纹对 AST 做规范化：忽略测试函数名、局部变量名和不影响路径类别的具体 ID，保留被调入函数身份、控制流、比较关系、关键枚举和断言形式。authorize() 和 delete_everything() 不能因为都是直接调用就被归一为同一结构。它能发现“同模板换数据”，但可能把边界值差异错误合并，所以只用于候选聚类和进一步比较，不是语义等价证明。

5.3 语义重复

语义指纹来自经批准的风险 ID、关系型前置条件、动作、外部/内部后置条件和禁止副作用。例如 tenant_a != tenant_b 比具体字符串更稳定；“返回 NOT_FOUND 且不读取存储”比响应 JSON 文本更能表达意图。

模型自报 risk_id=R-NEW 不能逃避去重。风险 ID 必须存在于签名登记表，oracle 必须与批准版本一致；新增风险先经过 owner 审查。

5.4 重复不是简单删除

同簇候选仍可能在以下方面有价值差异：

  • 一个使用最小 fixture，另一个依赖完整系统；
  • 一个失败信息清晰，另一个只报布尔不等；
  • 一个覆盖边界关系，另一个只覆盖普通值；
  • 一个能杀死关键变异，另一个不能；
  • 一个稳定且快，另一个更贴近生产但成本高。

因此簇内选择应比较故障敏感度、诊断、稳定性和成本，保留代表资产与必要互补资产；被淘汰候选保存 duplicate_of 和证据，避免下次重复生成。

六、覆盖分母：执行到哪里与验证了什么分开报告

6.1 语句覆盖

报告要保存 source roots、omit/include、coverage 工具版本、解释器、动态上下文和生成代码政策。只对被 import 的文件测量，会漏掉从未加载的模块并抬高比例；coverage.py 官方文档强调指定 source 有助于识别未执行文件。

source_manifest_digest 相同不足以防止 runner 把 18/20 缩成 1/1。批准 policy 还要从同一份冻结的 coverage 制品保存可测量语句和分支的预期总数，运行证据中的两个分母必须精确相等。真实实现应保存机会 ID 集合或工具原始制品，示例用固定总数表达这个约束。

6.2 分支覆盖

分支覆盖比较实际执行的 source-destination 对与静态可能的转移。它能暴露只走 if 一侧的问题，但仍不说明断言是否检查结果。异常、短路、生成器、模式匹配和结构性部分分支需要结合工具定义解释。

6.3 风险需求覆盖

一个风险有十个重复测试仍只计一次。观察期候选可另报 provisional coverage，不能混入正式分子。

  • 所有生产入口与动态加载机制已枚举；
  • 特性开关、路由和配置快照有摘要；
  • 静态调用图与运行遥测在声明窗口一致；
  • 反射、插件和外部调用边界已说明；
  • owner 批准适用版本和复核日期；
  • 重新可达的触发条件与告警存在。

“代码很老”“测试从没走到”“搜索不到调用”都只是线索，不是完整证明。

七、Mutation Testing：问测试能否区分受控错误

7.1 基本机制

mutation testing 对生产代码做小的、系统化变化，例如把 != 改成 ==、删除授权检查、改变边界或替换返回值，再运行相关测试。若测试因目标断言失败，变异被 killed；若仍通过，说明测试可能缺少输入或 oracle。

它测的是测试集对选定错误模型的敏感度，不直接测真实缺陷率。变异算子应与风险相关：对授权模块，删除 tenant 检查比把日志字符串改一个字符更有价值。

7.2 五种结果

状态 含义 统计处理
KILLED 变异被执行且相关断言失败 进入杀死分子与可杀分母
SURVIVED 变异被执行，相关测试仍通过 进入可杀分母，形成缺口
EQUIVALENT_APPROVED 经独立证据支持，语义与原程序等价 从可杀分母排除，单列数量
TIMEOUT/ERROR 无法得到有效行为结论 进入未知，不伪装为 killed 或 survived
INVALID 变异无法构建或违反算子前置条件 记录工具质量，不进入语义分母

7.3 等价变异为什么棘手

等价变异在所有输入上与原程序行为相同，没有测试可以杀死。自动优化、约束和状态感染分析能识别部分情况，但不能完整解决一般等价问题。人工裁决也可能错，因此批准需要绑定原程序摘要、变异程序摘要、算子、适用输入域、证据和 reviewer，代码变化后失效。

只冻结 mutant ID 仍不够：同一 ID 可被替换成更容易杀死的程序。执行前的 mutant manifest 应将 ID、变异程序摘要和允许归因的 assertion ID 一起绑定；等价裁决再额外绑定原程序摘要和批准输入域。

7.4 分数与上下界

EQUIVALENT_APPROVED 和 INVALID 单列。未知多时，即使 known score 很高也不能放行。对每个高风险算子还可设硬门，避免大量低价值 killed 稀释一个关键 tenant-check survivor。

7.5 杀死要归因到相关断言

如果变异运行时另一个 flaky 测试失败，不能算 killed。runner 应记录目标变异是否到达、哪个 assertion ID 失败、失败与哪个风险 oracle 对应。必要时只运行稳定、相关测试并对原程序做同环境对照。

assertion ID 不能由 runner 自由填字符串。门禁先从候选 AST 重算断言清单，再要求 killed mutant 报告的 assertion ID 同时存在于该清单和 mutant manifest 允许集。明显常量真值、纯 None 检查等静态弱断言不进入有效清单；这仍只能拦截明显情况，不能代替故障敏感度。

8.2 断言敏感度

未到达、注入失败和环境错误不进入分子，另列执行完整率。每个 fault ID 绑定风险需求、注入点、预期失败 assertion 和目标后置条件。

同样，fault manifest 必须绑定 fault ID、实际注入后的程序摘要和允许失败的 assertion ID；否则 runner 可以保留同一 fault ID，却换成不同、更容易被发现的错误世界。

8.3 不要把实现细节当 oracle

授权测试关心决策、对外原因、存储调用和审计原因，不应强制内部 helper 必须按固定顺序调用，除非顺序本身是安全不变量。过度 mock 和逐调用断言会让等价重构失败，形成脆弱测试。

8.4 失败诊断也是资产质量

好的失败信息给出风险 ID、关系型输入、预期/实际后置条件、被测版本和证据 ID。只显示 False is not true 会增加排障成本。生成器可以帮助补诊断，但错误消息不能包含个人数据或秘密。

九、测试数据独立：每个 case 对自己的状态负责

9.1 数据所有权合同

每项测试声明：

  • 创建哪些数据、命名空间和账号；
  • 读取哪些只读基线；
  • 是否依赖时钟、随机、locale、时区和顺序；
  • 清理或回滚方式；
  • 并发时的唯一键；
  • 数据来源与敏感分类；
  • 失败后保留哪些最小证据。

9.2 独立不等于每次全量搭环境

可以共享不可变镜像、只读参考表和服务进程，但可变业务状态应按测试或 worker 隔离。事务回滚适合单数据库测试，跨队列和异步系统可能需要命名空间与垃圾回收。选择取决于 fidelity、速度和清理可靠性。

9.3 时间与随机

不要用真实 sleep 等待过期，也不要依赖当前日期。通过可注入时钟、确定种子或事件推进控制；同时保留少量真实调度系统测试验证集成。固定种子只解决复现，不自动覆盖随机空间。

9.4 清理失败不能静默

清理是测试结果的一部分。主断言通过但清理失败会污染后续 case，应把资产标为 ERROR 或隔离。共享环境下记录资源 owner、创建时间和回收证明；后台清扫不能替代每项测试的责任边界。

十、Flaky：同一代码与环境出现多个结果

10.1 基本定义与危害

同一代码和声明环境下，测试既通过又失败，就是不稳定信号。根因可能是并发、顺序、未控制状态、时间、随机、资源竞争、基础设施或产品本身的非确定缺陷。自动把 flaky 归为“测试问题”可能错过生产竞态。

10.3 分母

未完成矩阵的候选不进入分母，单列 UNKNOWN。运行级失败率与测试级 flaky 率不同：一个测试失败 10 次仍是一个 flaky/稳定失败资产，不能混算。

10.4 隔离不是永久跳过

flaky 测试应从阻塞门禁隔离，防止噪声吞掉真实回归；同时建立 owner、风险缺口、修复时限和替代监控。无 owner 的 quarantine 会变成永久垃圾场。修复后从同一代码/环境重复矩阵重新进入观察期。

十一、维护预算：测试不是免费的永久附属物

11.1 单次运行成本

记录 CPU 时间、墙钟、内存、网络、外部服务、fixture 初始化和制品量。主干门禁关注关键路径时延，夜间套件关注总资源；不能只看单测文件执行时间，忽略构建与环境准备。

11.2 结构耦合成本

可用 fixture 扇出、mock 层数、内部 API 引用、共享数据依赖、代码行和自定义 helper 数作为线索。指标触发审查，不机械删测试。一个高风险端到端资产可能昂贵但必要，需要明确频率与替代的低层检查。

11.3 变更维护成本

还要区分需求真变、接口真变、脆弱实现耦合、数据漂移和 flaky 修复。总修改次数会混淆必要演进与无效维护。

11.4 失败诊断成本

记录首次归因分钟、误报重跑、owner 转派和证据缺失。一个每次失败都要读 2 MB 日志的测试，维护成本可能高于运行成本。要求结构化 reason、最小重现和关联 ID 可以降低这部分负担。

11.5 资产组合预算

预算按层和风险分配，不要求所有测试都极快：

层 角色 构造频率 预算关注
小型确定测试 快速保护纯逻辑 每次变更 毫秒级反馈、无共享状态
组件测试 验证存储/队列边界 受影响变更 环境准备与数据隔离
契约/集成 验证公共协议 合并前或定时 版本组合、诊断与稳定性
端到端 验证关键用户结果 受控频率 fidelity、长尾、外部依赖
mutation/fault 验证测试敏感度 变更相关或定期 算子价值、超时与计算量

表中的频率不是固定标准。关键是每项昂贵资产都能说明保护什么风险，为什么不能由更低成本测试完全替代。

十二、候选晋级与淘汰：用状态机保护主干信号

12.1 状态

状态不是只进不退。正式资产出现 flaky、数据越权或维护超支时先隔离；修复后重新观察。风险需求退出或被更强资产替代时退役，并保留历史决定。

12.2 进入 PROBATION 的构造硬门

  • 风险 ID 存在且为 REACHABLE；
  • 候选的仓库 tree 和生成器 manifest 与批准 policy 一致；
  • 源码可解析，存在非空且对应 oracle 的断言；
  • 三层指纹没有与现有正式资产完全重复，或有批准的互补理由；
  • source/branch 摘要和固定机会总数都与 manifest 一致；
  • 必需 mutation 与 fault manifest 的 ID、程序摘要和 assertion 允许集完整；
  • 关键变异被杀死，等价裁决有独立签名，未知不越界；
  • 相关故障能使目标断言失败；
  • 数据命名空间、外部读写和清理满足合同；
  • 最低重复矩阵完成，失败率区间不越界；
  • 运行、fixture、代码量和 owner 在预算内。

12.3 从 PROBATION 到 OFFICIAL

观察期至少覆盖规定数量的主干变更、随机顺序和并发运行；没有未解释的不一致结果；失败信息能定位；维护分钟未超预算；风险与 oracle 未漂移；owner 仍有效。观察证据绑定同一候选、策略、环境族和起止时间，由 CI 观察者签发。

晋级时不接受调用方单独传入一个可替换的 requirement，而是从 policy 绑定的完整 registry 中重新取得当前版本。OFFICIAL 记录保存 risk version、registry digest、policy digest 和 candidate digest，并由 asset-gate 对整个资产主体签发晋级收据。风险覆盖统计必须验证该收据和当前版本；旧版资产、被篡改资产和仅有 state="OFFICIAL" 的自报记录都不进入分子。

12.4 淘汰规则

  • 风险正式退役，且无其他需求依赖该资产；
  • 被更快、更稳定且故障敏感度不低的资产替代；
  • 长期不可修复 flaky，已有等价风险控制补位；
  • 维护成本持续超预算，owner 批准重写或下移层级；
  • oracle 已失效或测试一直未执行；
  • 数据使用不再获准。

退役前要重新计算风险覆盖。如果删除后 R-TENANT 没有正式资产，系统应显示覆盖缺口，而不是因为测试总数仍很多就保持绿色。

十三、指标：每个比例都带机会集合、未知和状态

13.1 候选唯一率

它反映生成冗余，不等于覆盖率。唯一率低可优化生成 prompt、检索和负反馈记忆。

13.2 正式晋级率

仍在观察、环境中断和风险取消分列。把未完成候选从分母静默删除会高估。

13.3 oracle 故障敏感度

按 risk 和 fault class 报告，不只给全局平均。安全关键 fault 存活时硬门失败，不能由大量格式类 fault 被杀死抵消。

13.4 mutation unknown rate

工具错误率高时先修基础设施，不应继续优化测试分数。

13.5 flaky 上界

单项候选用 Wilson 或精确二项区间描述重复失败概率；资产组合同时报告“至少一次不一致”的测试比例。零失败仍有正上界，重复次数越少，不确定性越大。

13.6 维护预算消耗

不同单位不能未经批准硬加。实际可分别列出 CPU 分钟、墙钟、外部调用和人时，再由治理层根据成本模型换算。

15.1 为什么代码不执行候选测试

测试代码与生产候选代码一样是不可信输入。它可以读环境变量、联网、删除文件或无限循环。示例只解析 AST，并验证由可信 runner 签发的结构化运行证据。真实平台要在进程外的操作系统或虚拟化隔离中执行，runner 需要独立凭据、资源限额、网络策略和制品出口控制。

RunEvidence 不是候选自己写的 JSON。签名绑定 candidate digest 与 policy digest；验证端从可信目录读取 issuer 角色。生成器即使在 payload 里自称 runner，也不能签发有效运行证明。

示例中的签发器与验证目录是两个不同类：前者固定一个 principal，后者没有 issue 方法。这防止普通验证调用方按 issuer 名称选择 runner 密钥。生产环境仍要把签发服务放到候选代码不可读的进程或主机，并优先使用非对称签名或远程受保护签发器。

15.2 为什么结构指纹不能单独删除测试

AST 规范化忽略测试名、局部名和大部分常量，故意把同模板换 ID 聚到一起；但它保留直接被调函数，不会把 authorize() 与 delete_everything() 规范成同一名称。常量归一仍可能把 0、边界最大值和普通值合并，所以门禁要求结构之外再看行为或语义：语义相同且结构/行为任一相同才阻断；单层相同只给 warning，交给簇内评审。

示例的规范化器仍然很粗糙：它不了解数据关系、helper 展开、动态参数化和框架 fixture。生产实现应保存算法版本，并允许 reviewer 纠正错误聚类；算法升级后重新计算，不把旧指纹当永久事实。

15.3 为什么等价变异需要另一种身份

runner 能观察执行结果，却不应单方面把存活变异改成 EQUIVALENT 来抬分。代码要求 mutation-reviewer 对 candidate、mutant ID、原程序摘要、变异程序摘要和批准输入域签发裁决。候选源码变化后，旧裁决找不到匹配 subject，重放失败。

在进入等价裁决前，policy 中的 MutantSpec 还会核对每个 mutant ID 的变异程序摘要与允许 assertion ID；FaultSpec 对注入程序做同样绑定。assertion ID 从当前候选 AST 重算，所以仅在报告中填一个存在或伪造的字符串都不能让错误 kill 或 fault 进入分子。

这并不证明裁决必然正确。人类与自动等价分析都可能漏判，因此报告保存数量、理由和抽样复核；高风险 survivor 不能只靠一句“看起来等价”排除。

15.4 为什么 mutation timeout 进入下界分母

两个已杀死变异加一个 timeout 时，known score 可以写成 100%，但下界是 2/3。示例按下界做门禁，防止把基础设施未知删除后宣称高分。上界仍保留“timeout 最终可能被杀死”的可能性。大量 timeout 首先是 runner、选择策略或测试性能问题。

15.5 为什么零失败也计算 Wilson 上界

候选在六种批准模式中各重复 10 次且全部通过，观测失败率是 0，但真实失败概率的区间上界大于 0。示例先检查唯一 run ID 和每种模式的最小次数，再用全部 60 个结果计算 Wilson 近似上界并与构造政策比较。对极低概率、高影响或自相关失败，独立二项假设并不成立，需要更长窗口、分层环境和专门的并发/时序实验。

15.6 为什么通过首门只进入 PROBATION

首轮证据通常来自固定代码和受控环境，还没有经历主干变化、不同顺序、不同 worker 与维护事件。evaluate_candidate 返回 PROBATION；独立 asset-gate 再签发绑定具体 runner 证据的门禁收据，调用方不能自行构造状态。只有 CI 观察者证明运行数、持续时间、变更上下文、零不一致、owner 有效与维护预算后，promote_official 才从 policy 绑定的 registry 取得当前 requirement，创建带 risk version、registry/policy/candidate digest 的 OFFICIAL 资产，并用 asset-gate 签发另一份晋级收据；观察结束时间也不得晚于观察证明的签发时间。

risk_coverage_bounds 不会因为一条记录的 state 文本是 OFFICIAL 就计入分子。它会重新核对当前 registry/policy、risk version、资产主体摘要和晋级收据 payload；旧版或被篡改资产进入 invalid_assets，不伪装已覆盖。

十七、一个实际排障链：mutation 大量 KILLED，原程序却也偶发失败

17.1 现象

夜间 mutation 报告显示 12 个变异全部 KILLED，分数 100%；同一 candidate 的原程序对照在 200 次中失败 7 次。CI 聚合器仍把每个变异标为 killed，因为变异运行里至少出现过失败。

17.2 正确排查顺序

  1. 对齐原程序与变异程序的 candidate、source manifest、runner image、测试选择和数据 namespace；
  2. 检查 kill 是否记录 mutant_reached 与 target_assertion_id；
  3. 把原程序同环境、同 seed、同顺序作为每批变异的对照；
  4. 比较失败 assertion、前序测试、worker、资源和时间；
  5. 暂停 mutation 分数门禁，把测试本身标为可疑信号；
  6. 单独、随机顺序、反向顺序和并发重放。

17.3 证据

12 个“kill”中，9 个失败在 teardown 的 document count == 0，目标 tenant assertion 没有失败；原程序也出现相同 teardown 错误。所有失败集中在 worker-3，前序 case 会创建相同固定 document ID。runner 旧 Schema 没有 mutant_reached 字段，只要进程非零就记 killed。

17.4 根因

直接根因是跨 candidate 共享固定 document ID，teardown 删除了其他 worker 的对象；度量根因是 nonzero exit = killed，没有关联目标变异与断言；流程根因是 mutation 任务没有原程序并行对照。

17.5 修复

  • document ID 加 candidate、worker 和 run nonce；
  • teardown 只删除 owner 匹配的资源，并验证清理证明；
  • kill 必须同时满足变异已到达、目标 assertion 失败、原程序对照通过；
  • 基础设施/清理失败记 ERROR，不进入 killed/survived；
  • 原 12 个结果作废，生成新 evidence subject 后重跑；
  • 故障注入加入“原程序与变异同样失败”和“无关 flaky 失败”。

重跑后 8 KILLED、3 SURVIVED、1 EQUIVALENT_APPROVED。这个结果比虚假的 100% 更有价值，因为三个 survivor 明确指出测试缺口。

十九、测试策略：生成能力放在哪些层更有价值

19.1 单元与纯函数层

适合从决策表、边界、等价类和性质生成大量低成本候选。属性测试工具可以探索广泛输入并缩小失败样例，但性质本身仍需人工或事实源定义；一个错误性质可以稳定验证错误实现。

19.2 组件层

适合根据 Schema、状态机和故障模型生成存储、队列、超时与重试组合。数据命名空间、虚拟时间和可控 fake 是前置条件，否则候选很快变成 flaky。

19.3 契约层

适合从 API/消息 Schema 生成兼容、缺失字段、未知枚举和错误码测试。要区分消费者真正依赖的语义与序列化实现细节，防止生成大量脆弱快照。

19.4 端到端层

生成器可以提出用户路径和数据组合，但不适合无预算地扩张。每项昂贵候选先说明独有风险、为什么低层不能覆盖、所需环境和失败诊断。UI 文案、时间和异步等待尤其容易造成脆弱断言。

19.5 mutation 与故障层

AI 可帮助从事故、diff 和威胁模型提出相关变异/故障，但执行 manifest、到达证明和 kill 归因必须由独立工具链完成。生成器不能自己删除不利结果或批准等价。

二十、发布与运营清单

20.1 风险与分母

  • 每个风险 ID 有版本、来源、owner、关系型前置条件、oracle 和禁止副作用。
  • REACHABLE、PROVEN_UNREACHABLE、UNKNOWN 分开，排除有批准证据和复核日。
  • source manifest 明确 include/omit、工具版本、动态上下文与生成代码政策。
  • 风险覆盖、语句覆盖和分支覆盖分开报告。
  • 未运行、跳过、timeout 和工具错误不从分母静默删除。

20.2 候选与去重

  • 保存 generator、仓库 tree、风险登记和源码摘要。
  • 结构指纹忽略哪些字段、保留哪些字段有版本说明。
  • 行为签名来自隔离 runner，不来自候选自报。
  • 语义必须映射已批准风险与 oracle。
  • 聚类内按敏感度、稳定性、诊断和成本选代表，淘汰项保存 duplicate_of。

20.3 断言与 mutation

  • 拒绝常量、仅非空、允许所有状态等明显弱断言。
  • 每个高风险 oracle 有相关 fault，并记录到达和 assertion ID。
  • mutation manifest 在执行前冻结，省略项会被发现。
  • kill 需要目标变异到达、相关断言失败和原程序对照通过。
  • equivalent 裁决绑定两个程序摘要、输入域、理由与独立 reviewer。
  • killed、survived、equivalent、timeout、invalid 分列并给上下界。

20.4 数据与 flaky

  • 每个 case 有独立 namespace、owner 和清理证明。
  • 生产数据和真实秘密不作为默认 fixture。
  • 时间、随机、locale、时区、顺序和并发均有控制或记录。
  • 单独、随机、反向和并发重复矩阵按风险执行。
  • 原始 PASS/FAIL/ERROR 序列保留，重跑不覆盖首次失败。
  • quarantine 有 owner、修复时限、风险补位和退出条件。

20.5 维护与生命周期

  • 运行、fixture、源码、外部依赖和诊断人时有预算。
  • 进入 PROBATION 前硬门完整，观察期不直接算正式覆盖。
  • OFFICIAL 需要足够运行、持续时间、变更上下文和 owner。
  • 需求、接口、数据、生成器、runner 或策略变化触发重新评估。
  • SUPERSEDED/RETIRED 保存替代关系、最后有效版本和覆盖重算。
  • 删除测试前确认不会留下高风险需求缺口。

二十一、局限与升级方向

21.1 语义指纹依赖风险登记质量

风险登记写得过宽，互补测试会被误判重复；写得过细，同一语义又会拆成大量 ID。需要定期从缺陷、评审和聚类结果校准粒度，并允许多风险、多 oracle 映射。

21.2 行为插桩会改变和遗漏行为

路径或调用跟踪可能影响时序，也不一定观察动态代码、外部服务和隐式状态。行为签名只在指定插桩版本与环境成立，不能当完整语义证明。

21.3 mutation 算子可能偏离真实缺陷

容易生成和杀死的算子会抬高分数，复杂并发、配置和跨服务缺陷却没有代表。算子集要从事故、代码变更和威胁模型回灌，按风险分层，不追求一个全局漂亮分数。

21.4 等价判断仍是高成本工作

完全人工审查会拖慢流水线，完全自动又会误判。可以对低风险使用保守自动规则，对高风险 survivor 做抽样或强制审查，并优先减少无价值算子。未知应诚实保留。

21.5 flaky 不是独立同分布硬币

失败常按 worker、时段、负载和顺序聚集。Wilson 二项上界只是教学近似；生产分析要分层、检查自相关和环境组合，必要时做生存、可靠性或并发专项分析。

21.6 维护收益有延迟

候选在两周观察期很稳定，不代表六个月后仍廉价。需要按接口和 fixture 变化持续记录维护事件，定期重算资产组合，而不是在晋级时永久盖章。

21.7 工具覆盖报告仍需独立验证

coverage.py、pytest、Hypothesis 或 mutation 工具提供机制，不替组织定义 risk denominator 和 oracle。版本、配置、插件与采集失败都影响结果；重要报告保存原始制品和工具版本，并做故障注入。

以下资料均在本文资料边界 2026-06-21（含） 前发布或可获得。EntitleX、状态机、风险登记、分数、阈值、运行次数和结果均为本文构造，不是工具或论文规定的统一标准。

  1. pytest: Flaky tests。官方文档把同一测试有时通过、有时失败描述为不稳定行为，并讨论系统状态、顺序、并行、全局状态、过严断言和线程等来源。本文据此强调不稳定信号不能靠重跑隐藏；具体重复矩阵是构造方案。
  2. pytest: How to use skip and xfail。用于区分 skip、预期失败和普通通过。本文要求它们分别进入分母，避免把未执行当成功。
  3. Coverage.py: Branch coverage measurement 与 Specifying source files。官方资料解释语句与分支机会、source/omit/include 和未执行文件识别。本文的风险覆盖不是 coverage.py 内置指标。
  4. Hypothesis 官方文档。Hypothesis 是 Python 属性测试工具，可从性质生成并缩小样例。本文引用它说明生成输入的价值和边界，不要求完整脚本安装第三方包。
  5. Google Testing Blog: Test Sizes，2010 年。文章用资源和外部系统等属性区分测试规模。本文借此强调按 fidelity 与成本组织资产，不把单元/集成名称当唯一分类。
  6. Google Testing Blog: Where do our flaky tests come from?，2017 年。该文讨论测试规模与不稳定性观察。文中的 Google 数据属于其历史环境，本文不把数字外推到 EntitleX。
  7. Google Testing Blog: How I Learned To Stop Writing Brittle Tests and Love Expressive APIs，2024 年。用于说明测试应表达重要性质，避免无关实现细节造成脆弱失败。
  8. A. Jefferson Offutt 与 W. Michael Craft，Using compiler optimization techniques to detect equivalent mutants，1994 年。原始论文讨论用编译优化识别部分等价变异，支持本文“等价问题只能部分自动化”的边界。
  9. René Just、Michael D. Ernst 与 Gordon Fraser，Using State Infection Conditions to Detect Equivalent Mutants and Speed up Mutation Analysis，2013 年。原始研究使用状态感染条件减少执行并辅助识别等价变异；本文只借鉴分类思想，没有实现其算法。
  10. Yue Jia 与 Mark Harman，An Analysis and Survey of the Development of Mutation Testing，IEEE Transactions on Software Engineering，2011 年。用于 mutation testing 发展、技术与等价变异背景；本文门禁不是论文中的统一标准。
  11. Python unittest 官方文档。完整脚本用标准库实现独立测试和 unittest.main(verbosity=2)；脚本中的 59 个用例只验证教学控制面。

二十三、结语：让测试资产增长发现能力，而不是只增长仓库体积

AI 让生成候选变得便宜，但便宜的候选会把稀缺资源转移到执行、评审、诊断和维护。控制重点因此不再是“还能生成多少”，而是每个候选能否回答：

最终需要优化的不是测试文件数量，也不是一个孤立覆盖率，而是风险发现信号的有效性：分母诚实、oracle 有力、证据可复核、数据独立、结果稳定、维护可持续。生成数量不等于覆盖；只有经过这些证据门的候选，才有资格成为长期资产。
