AI测试-53-长上下文应用怎么测试信息遗漏位置偏差和上下文冲突

发表于 2026-06-01 分类于 AI测试 本文字数： 25k 阅读时长 ≈ 1:29

模型的产品页写着支持 128K、200K 或更长的上下文，接口也确实接受了整段输入，能不能说明应用可以稳定处理这么长的材料？

不能。

“请求被接收”只证明序列没有在协议入口被拒绝。它没有证明位于第 50% 位置的关键条款被保留，没有证明模型在十几个近似条款之间选中了生效版本，没有证明跨三份文档的因果链被完整连接，也没有证明回答中的引用真的支持结论。更没有证明应用自己的检索、排序、模板、序列化、截断和摘要没有在模型调用前先把信息弄丢。

同样，做一张全部变绿的 Needle-in-a-Haystack 热力图，也远远不够。单个独特字符串的检索，是长上下文能力中最容易构造、最容易判定的一类。生产任务往往要求找到多项信息、忽略近似干扰、识别同一实体、按权威和生效时间裁决冲突、跨文档完成多跳推理，再给出能够回到原文的引用。一个系统可以百分之百找回“特殊号码 739184”，同时漏掉合同中间的否定词，或者引用旧政策支持新结论。

因此，长上下文应用真正要回答的是：

这段定义里没有“窗口越大越好”。它把 advertised max window——厂商或模型声明的最大可接收窗口——与 effective context——在一个明确任务和质量门槛下有证据支持的有效上下文——分开。有效上下文不是模型名的常数，更不是能跨任务复用的营销数字；它是整条应用链路的条件属性。

本文资料边界截至 2026-06-01（含）。文中的场景、案例、数据、阈值、时间线与发布结果均为构造示例；“构造数据”和“构造案例”也都只用于说明方法，不代表任何供应商、模型或线上系统的实测结果。

一、边界：本文测长上下文质量，不重写上下文工程和推理性能

《AI测试-27-Context Engineering怎么管理指令知识工具结果和Token预算》已经系统讨论上下文来源分型、权限、时效、冲突、Token 预算、裁剪、摘要、缓存和 Assembly Trace。本文把“上下文能够被类型化、组装并留下 Trace”视为前置能力，不重复 AI测试-27 的上下文管理设计。这里专门回答：如何把位置、长度、密度、多跳、冲突、引用、截断和压缩变成可复现的压力实验，如何判定首错层，以及如何据此作发布决定。

《AI测试-42-大模型推理性能怎么分析TTFT-TPOT吞吐批处理和KV Cache》已经讨论 prefill、decode、TTFT、TPOT、吞吐、连续批处理和 KV Cache 容量。长输入当然会影响延迟、成本与容量，但本文只把这些指标作为并行门禁，不重复 AI测试-42 的 KV Cache 与推理性能分析。质量下降不能自动归因于 KV 压力；性能告警也不能自动解释信息遗漏。

本文测量对象包含四层：

层 被测对象 典型失败
用例与真值层 问题、证据、冲突规则、允许输出 真值漏标、时间规则写错、引用跨度不完整
上下文链路层 召回、排序、组装、截断、压缩、序列化 必需片段未选中、边界切断、旧摘要残留
模型使用层 从可见上下文中提取、整合、裁决和推理 中间位置遗漏、多跳断链、同级冲突强猜
输出与执行层 答案、引用、结构化字段、工具参数 结论正确但引用错、范围丢失、动作依据不充分

不在本文证明范围内的事项也要写清楚：

  • 通过本文测试不等于模型“理解”了任意长文档；测试只支持已覆盖任务与切片。
  • 合成压力样本的高分不等于生产质量高；真实文档分布、语言、格式和业务后置条件仍需独立证据。
  • 模型回答正确不等于上下文链路正确；它可能靠参数知识或猜测得到答案。
  • 一次失败不等于位置偏差；只有在控制其他变量的配对实验中，位置才是可支持的解释之一。
  • 一个供应商版本的表现不能推广为某种架构、某个上下文长度或整个行业的规律。
  • benchmark 排名不能代替当前 Prompt、应用模板、输出协议和数据分布上的发布门禁。

二、问题边界与反例：先拆掉六个看似合理的结论

2.1 “没有超出最大窗口，所以没有截断”

反例：API 接受 96K Token，但应用在调用前给输入设置了 80K 的软上限，模板渲染后又追加 6K 的工具 Schema 和输出预留。原始文档最后 22K 被客户端裁掉，服务端看到的请求当然合法。此时供应商没有截断，信息仍然丢了。

正确测试要同时保存：原始候选 Token 数、组装后 Token 数、发送前字节摘要、供应商可见 usage、每个 item 的最终 span，以及被丢弃项的 reason code。只看 HTTP 200 或总输入 Token 无法知道哪一项消失。

2.2 “答案正确，所以模型使用了给定证据”

反例：问题询问公开常识，模型在删除证据后仍能答对；或者新政策把期限从 30 天改为 14 天，模型凭训练记忆回答 30 天，恰好基准真值仍是旧版。答案匹配既可能来自上下文，也可能来自参数知识、模板泄漏或评测污染。

对需要上下文归因的 case，应优先使用构造标识、私有版本化事实或反事实值，并增加“移除必要证据”“替换为另一确定性值”的对照。若输出不随受控证据变化，不能把正确答案归功于上下文使用。

2.3 “单 Needle 全绿，所以长上下文能力足够”

反例：系统能找到唯一 UUID，却无法列全同一键对应的四个值；能找到两个事实，却无法沿 A→B→C 合成结论；能复述新旧两条政策，却不能按生效时间选择；能给出正确答案，却引用了包含相反条件的段落。

Needle 检索适合做基础连通性冒烟和位置扫描校准，不适合作为唯一发布证据。它回答“能否找到一个显著目标”，不回答“能否完整、正确、可追溯地完成业务任务”。

2.4 “中间位置差，根因就是模型 Lost in the Middle”

反例：模板在 32K 边界处插入分隔符失败，导致中间文档被解析为上一段的 metadata；或者组装器只保留头尾候选；或者评测代码按字符位置移动片段，但 Tokenizer 后片段根本没有落在预期分位。最终热力图同样会呈现中间低谷。

“中间低谷”是观测，不是根因。只有确认必需 item 被选择、span 完整、实际 Token 位置正确、请求字节一致、输出判定可靠后，才可以把模型对可见信息的利用作为下一层推断。

2.5 “把关键条款复制到开头和结尾就能解决”

反例：复制提高某些提取任务的命中，却让两个副本在更新时版本不一致；相同事实重复出现被模型误解为多个独立证据；复制挤掉另一条必要证据；引用只能回到拼接副本，无法回原文。

位置冗余是一种需要评测的缓解手段，不是普遍修复。高风险规则应在模型外执行，关键证据可以结构化置顶，但必须保持单一真值、版本一致和可回源。

2.6 “长文档摘要后回答没变，所以压缩无损”

反例：当前十道回归题没有询问被摘要遗漏的例外条件，答案自然不变；摘要保留“允许退款”，却删除“仅限未发货商品”；第一代摘要正确，第二代摘要把“尚未批准”改写成“已批准”。压缩是否忠实，只能相对于明确的事实、约束、未决项、时间和引用集合判断，不能靠少量最终答案等价证明。

5.1 真值与素材层

这里保存原子事实、文档版本、有效时间、权威关系、实体 ID、依赖边和引用跨度。每个 case 明确：

  • 哪些是 helpful 但非必需；
  • 哪些是 hard distractor；
  • 哪些已经 stale 或 revoked；
  • 哪些构成 conflict group；
  • 哪些结论允许唯一答案，哪些必须输出未决或澄清；
  • 每个答案 claim 最少由哪些 span 支持。

真值不能只是一段参考答案。参考答案把事实、推理和表达混在一起，难以判断“答案措辞不同但语义正确”与“漏掉关键条件”。更稳的做法是先定义结构化 outcome，再保留一段仅供人工理解的 canonical explanation。

若 Judge 超时，结果是 UNKNOWN_JUDGE_FAILURE，不是自动失败，更不是自动通过。若引用解析器找不到文档版本，结果是 UNRESOLVED_CITATION，不能只因答案文字正确而忽略。

5.5 发布控制层

发布控制不只读取总体均值。它要检查：

  • 高风险硬错误是否为零；
  • 每个承诺长度内的最差位置是否达标；
  • 生产高密度、多跳、冲突、语言和格式切片是否达标；
  • 相比基线的配对退化是否超过容忍区间；
  • 未知结果比例是否在限额内；
  • 质量、时延和成本是否同时满足门槛；
  • 失败是否已有可执行回退，例如限长、检索模式或人工接管。

六、统一数据模型：case、item、variant、run、claim 分开

6.1 ContextItem：一段文本不是一个完整证据对象

建议至少保存：

valid_from 与出现在上下文中的先后顺序无关；authority 与语气强硬程度无关；status=active 也不能代替实体和适用范围匹配。把这些字段留在 metadata 里，才能构造“低权文本放最后”“旧版放开头”“撤销记录与批准记录相隔很远”的独立测试。

6.2 EvaluationCase：定义不变量

一个 case 保存：

字段组 示例 用途
身份 case_id、suite_version、risk 稳定定位与门禁分层

真值 expected_outcome、allowed_uncertainty 不依赖固定自然语言答案

case 是不变量，variant 只改变压力条件。若变体生成器顺便改了答案、证据数量和问题难度，就不能把差异归因于位置或长度。

6.3 VariantManifest：记录怎样施压

位置必须在 Tokenizer 后测量。中文字符数、UTF-8 字节数、单词数和 Token 数都不是可互换单位。报告可以额外给字符或页数帮助理解，但用于窗口和相对分位的坐标必须绑定实际 Tokenizer 版本。

6.4 RunTrace：一次调用的观测事实

建议包含：

  • run_id、variant_id、attempt、seed；
  • 应用、检索器、reranker、assembler、compressor、Prompt、Tokenizer、模型固定版本；
  • 候选 item 及 rank、score 和过滤理由；
  • selected、dropped、compacted、truncated 状态；
  • 每个最终 item 的 Token start/end；
  • 发送前规范化字节摘要与供应商 usage；
  • 完整输出、解析结果、停止原因；
  • 输出 claim、引用 span 和工具动作；
  • 各判定器结果与最终门禁状态。

只记录最终 Prompt 原文也不够。没有候选集，就不能知道是检索没找到还是组装没选择；没有 span，就不能知道是 item 整体在场但关键句被切断；没有 claim-citation 映射，就不能知道引用是装饰还是支持。

6.5 ClaimEvidence：把回答拆成可验证主张

一个引用编号靠近句子，不代表它支持句子。引用判定至少分三步：引用对象存在且版本正确；span 包含需要的前提；claim 没有超出 span 的适用范围。对于金额、时间、否定、比较和例外，最好有确定性字段 Oracle 或人工复核，不把词面相似度当成支持关系。

七、建立四段失败漏斗：Selection、Visibility、Utilization、Generation

为了定位“信息遗漏”，把必需事实从源到输出的路径拆成四个事件。

7.1 Selection：必需信息是否被选择

required item 是否进入候选集？进入候选后是否被排序、去重、权限过滤或预算裁剪淘汰？如果没有进入最终组装结果，模型没有机会使用它。

选择层指标由确定性 Trace 计算，不需要 Judge。常见 reason code 包括：

ACL_FILTERED 对禁止访问内容可能是正确行为，不能和 NOT_RETRIEVED 一起算普通遗漏。required 标注若要求一个无权限 item，本身就是用例缺陷。

7.2 Visibility：被选择的信息是否完整可见

item selected 不等于关键 span 可见。可能发生：

  • 文档 chunk 只保留条款标题，例外在下一 chunk；
  • 边界截断切掉否定词或数值；
  • XML/JSON 转义错误让一段内容落入注释或字段外；
  • 摘要保留结论却丢失状态与来源；
  • Prompt 模板覆盖同名字段；
  • 发送前日志与真正请求体不是同一版本。

Visibility 需要 item-to-token-span map、最终渲染摘要和边界哨兵。对于高风险片段，可在前后放置不会进入答案的构造 marker，验证整个 span 而非只验证 item ID。

7.3 Utilization：可见信息是否被正确使用

确认必需 span 完整出现在模型输入后，仍可能出现：找到但不采用、只采用一部分、被近似干扰覆盖、多跳中间节点丢失、时效和权威裁决错误。这个层才是位置偏差、密度压力和长距离整合真正要测的对象。

判断 Utilization 不应只看最终自然语言。可以要求模型输出结构化中间字段，如选中的 policy version、事实 ID、影响实体集合，但不能假设模型给出的“思维过程”是真实内部因果。结构化字段只是可测试输出，不是对隐状态的读取。

7.4 Generation：推断正确后是否生成错误

模型可能选对事实，却在输出时：

  • 把 180 写成 18；
  • 漏列集合中的一个系统；
  • 把“不允许，除非重新审批”写成绝对永久禁止；
  • 结论正确但引用编号错位；
  • JSON 解析后枚举映射错误；
  • 工具参数使用旧实体 ID。

若结构化内部选择字段正确、最终文字错误，应先查输出协议、解码、解析和 post-processing，而不是立即调整检索或位置布局。

7.5 首错层不是唯一贡献因素

首错层回答“最早在哪一层偏离了预期”，不是“只有这一层有问题”。例如必需条款被组装器放在中间且模型也容易忽略：生产轨首错层是组装布局，模型位置敏感是扩大因素。修复组装器能止损，但模型升级仍可能改善余量。事故报告应分别写 root cause、contributing factor 与 detection gap。

八、长度测试：不要从 4K 直接跳到 advertised max

8.1 长度档位来自生产分布和机制边界

建议同时包含：

  • 生产输入 Token 的 P50、P75、P90、P95、P99；
  • 应用软上限前后，例如 31K/32K/33K；
  • 压缩或裁剪触发阈值前后；
  • 模型声明长度以内的多个几何档，如 8K、16K、32K、64K；
  • 预期拒绝或降级的超限档位。

只测整齐的 8K 倍数，容易错过应用在某个模板、chunk 数或缓存阈值处出现的离散故障。只测生产分位，又可能没有覆盖新上线后输入变长的风险。二者要结合。

8.2 增长长度时保持什么不变

若目标是测纯长度效应，保持：问题、必需证据、答案、证据位置分位、相关信息密度定义、干扰类型分布、Prompt 和输出预算不变。增加的 Token 来自同一干扰池的确定性采样。

但“绝对证据数量不变”会让密度随长度降低。因此要建立两条轨：

  1. 固定信号轨：必需事实数量固定，长度增加，测信号被更多噪声稀释；
  2. 固定密度轨：相关 Token 比例固定，随长度增加更多相关项，测全量聚合与输出负担。

两条轨回答不同问题，不能混在一条曲线上。

8.3 有效上下文用连续通过区间，不用孤立最高点

若 32K 通过、64K 失败、96K 偶然通过，不能把 96K 宣称为有效长度。至少要求从短到长形成连续满足门槛的区间，并对非单调点重跑、检查样本与错误类型。孤立高点可能来自样本更容易、位置更有利、输出更短或随机波动。

  • 输出必须列全的目标数量；
  • 相关信息是否需要聚合而非选择一个答案。

10.1 easy noise 只适合校准

完全无关、词汇差异很大的文本适合验证长度拼接、Token 计数和基础位置扫描，但会低估生产难度。hard distractor 应在主题、实体、键名或措辞上接近正确证据，只在版本、生效时间、否定、范围或数值上不同。

10.2 相关信息多不是噪声少的反面

全量摘要、聚合、风险枚举任务需要使用大量上下文。此时增加相关信息会提高密度，也提高完整召回和输出集合的难度。不要假设密度越高质量必然越好。测试应把“找一个”“找全部”“聚合统计”“总结约束”分成不同 task type。

10.3 重复会制造虚假密度

同一事实复制十次会让相关 Token 占比上升，却不增加十份独立证据。建议同时报告：

若重复使答案改变，检查模型是否把频次误当权威；若去重使引用丢失，检查来源合并是否保留所有文档关系。

11.4 RULER 的可借鉴边界

RULER 将长上下文评测从单一 NIAH 扩展到多种检索、变量追踪、聚合和问答。论文在 13 个代表性任务上评测 17 个长上下文模型；主实验按 4K 到 128K 多个长度、每个任务每个长度 500 个自动生成样例运行，并在论文指定的模型、模板、推理硬件和 greedy decoding 设置下报告结果。论文发现，vanilla NIAH 接近满分并不保证更复杂任务在长度增长后仍保持表现。

这些数字只能描述 RULER 原论文实验，不能当作本文应用的目标值。RULER 自身是可控合成任务，论文也明确列出位置控制不足、与真实长上下文任务相关性不足、未验证 Prompt 鲁棒性等限制。工程使用方式是借鉴“多针、多查询、变量追踪、聚合、长度与复杂度可控”的任务设计，再用生产文档、业务 Oracle 和真实后置条件补足外部有效性。

十二、冲突与时效：顺序不是权威，最近出现也不是最新生效

长上下文的难点经常不是“找不到”，而是“找到多个互相不兼容的候选后选错”。冲突测试必须先由业务规则定义裁决关系，再让模型解释或应用；不能把两段矛盾文本塞进去，事后按模型答案反推规则。

12.1 冲突最小分类

冲突类型 构造方式 期望行为
版本冲突 同一政策 v7 与 v8 值不同 按 valid_at 和 supersedes 选择生效版本
权威冲突 正式政策与会议纪要冲突 选择适用范围内更高权威来源
同级冲突 两个同级、同时间源给出不同值 输出未决、请求澄清或进入人工，不强猜
撤销冲突 批准记录与后续撤销记录并存 在撤销生效后不得继续使用批准
范围冲突 总则允许，地区/产品特别条款禁止 先验证实体与范围，再应用更具体规则
否定冲突 “允许 X”与“不允许 X”措辞接近 完整保留否定、条件和作用域
时间轴冲突 发布时间、事件时间、生效时间不同 使用业务定义的 effective time，不按 ingestion time 猜测
引用冲突 答案来自 v8，引用指向 v7 答案与证据版本必须一致，否则引用失败

12.2 四个时间不能压成一个 timestamp

建议区分：

一份旧规则可能晚摄取，一条撤销记录可能先发生后补录，一份政策可能提前发布但下月才生效。若测试只改变文本出现顺序，模型“选最后一条”可能在样本上偶然正确。应构造以下变形：

  • 新规则放开头、旧规则放结尾；
  • 旧规则晚摄取但早已失效；
  • 新规则已发布但查询时尚未生效；
  • 撤销记录在批准记录之前出现于上下文；
  • 同一日缺少可决定先后的业务字段。

期望由结构化 Oracle 计算。没有足够字段时正确结果是 INSUFFICIENT_TEMPORAL_EVIDENCE，不是让模型根据措辞、顺序或常识补齐。

12.3 Authority、freshness 与 specificity 不是一个加权总分

把冲突裁决写成 0.5 × 新鲜度 + 0.3 × 权威 + 0.2 × 相关性 会产生危险补偿：极新的低权评论可能超过稍旧但仍有效的正式政策。更稳的做法是先按硬条件过滤适用范围和有效区间，再依据明确的权威偏序或业务优先级裁决；只有同一可比较集合内，才考虑相关性排序。

如果两个源不可比较，系统应保留冲突。UNRESOLVED_CONFLICT 是一种正确结果，不应在准确率计算中自动算错。测试用例需要提前声明是否存在唯一 winner。

十三、引用测试：有链接不等于可追溯，有引用不等于支持

长上下文应用常用引用提升可信度，但引用也是独立输出任务。必须把“答案正确”和“引用正确”拆开。

13.1 四级引用判定

  1. Resolvable：引用 ID 能解析到存在的文档、固定版本和 span；
  2. Relevant：span 与当前 claim 主题相关；
  3. Entailing/Supporting：span 实际支持 claim 的数值、否定、范围和条件；
  4. Complete：所有需要外部证据的关键 claim 都有足够支持，且多跳边没有漏引。

一个段落提到“日志保留”只满足主题相关，不一定支持“华东 G-17 必须 180 天”。如果适用范围在另一段，单引用不完整；如果引用旧版 90 天条款，哪怕结论写 180 天也不支持。

13.2 引用精度与召回的分母

设输出引用集合为 C_out，其中真正支持某 claim 的引用为 C_supported；需要引用的 gold claim 集合为 G_claim，已被足够证据覆盖的为 G_covered：

若没有输出引用，Precision 不应自动记 1；应记为不可定义，并由 Recall=0 或“缺失必需引用”硬门禁体现。若一个 claim 需要两个 span 才完整支持，只命中一个不能算 covered。

还可以按 span 严格度给两种口径：

  • strict：引用必须落在 gold 支持跨度或批准等价跨度；
  • document-level：只要求文档版本正确，用于早期系统但不能宣传精确可追溯。

两种结果不可混报。

13.3 答对引错是高价值故障信号

答案正确、引用错误通常提示四种可能：

  • 模型靠参数知识或猜测答对，再选择一个看似相关引用；
  • 正确 span 可见，但引用编号映射在 post-processing 中错位；
  • 组装器把旧、新文档显示为同一标题；
  • Judge 只检查答案，没有独立检查引用。

这种 case 不应被总准确率淹没。对于审计、法律、财务和运维变更，高风险 claim 的 unsupported citation 可以设置零容忍。

13.4 引用变形测试

  • 把支持段落移动到中间，但保留同主题干扰在尾部；
  • 交换文档展示序号，稳定 ID 不变；
  • 删除支持跨度，期望拒答而非引用邻近段落；
  • 把数值保留、否定词删除，期望判定器发现语义不完整；
  • 让答案需要两段联合支持，验证引用集合完整性；
  • 插入标题相同、版本不同的文档，验证版本绑定；
  • 让引用 span 在截断边界上，验证不接受半段证据。

十四、截断测试：先找谁截、从哪截、是否留下半条事实

截断不是单一机制。可能发生在文档读取器、chunker、检索 payload、上下文 assembler、HTTP 客户端、模型适配器、供应商接口或输出解析器。每层都要有自己的前后计数和摘要。

14.1 截断方向矩阵

至少测试：

模式 注入 主要风险
tail truncation 保留头部、删除尾部 问题或最近工具结果丢失
head truncation 保留尾部、删除头部 System/定义/早期证据丢失
middle truncation 拼接头尾、删除中间 日志看似完整、关键主体消失

14.2 边界哨兵验证机制，不证明语义

在 gold span 前后加入构造 marker，例如 BOUNDARY_017_START 和 BOUNDARY_017_END，可以确认 span 是否完整通过链路。marker 不能成为答案线索，也不应出现在生产内容。它只能证明字节/Token 片段存在，不能证明模型使用了其中语义。

14.3 “优雅截断”仍要失败显式化

如果预算不足以容纳全部 mandatory 证据，系统应返回结构化状态：

不能静默丢一半证据后继续生成流畅答案。优雅降级是明确缩小任务、检索补充或拒绝，不是让模型在未知中猜测。

14.4 输出截断与输入遗漏分开

模型可能正确找到全部事实，却因 max_output_tokens 太小只列出一半影响系统。需要记录 finish reason、已生成集合和预期集合；重跑时只提高输出预算，若结果恢复，则首错层不是输入上下文。输入和输出共同占用总窗口的接口上，更要在长度矩阵中冻结输出预留。

十五、压缩测试：把摘要当作有损派生数据做差分

压缩策略可能是抽取、摘要、检索式选择、结构化状态、分层摘要或多轮 compaction。无论哪种，都要保留原文轨、压缩轨和必要时的回源轨。

15.1 压缩前先定义必须保持的语义单元

对每个 case 标注：

  • required facts；
  • 否定、例外、数量、单位、时间和范围；
  • 未决问题与不确定性；
  • 决策及其理由；
  • 实体与别名关系；
  • 证据和版本引用；

压缩率高不是质量。若从 80K 压到 8K，却把 REVOKED 压成 APPROVED，属于硬失败。

同一模型家族既做摘要又做回答，可能共享对某类否定或格式的盲区。异源复核可以降低部分相关风险，但也不是独立性的数学保证。高风险结构字段优先由规则抽取、业务系统直接提供或人工确认；模型摘要用于叙述辅助，不承担唯一真值。

十六、LongBench 的用途：补任务多样性，不照抄一个平均分

LongBench 原论文构建了中英双语长上下文基准，包含 21 个数据集、6 类任务：单文档问答、多文档问答、摘要、Few-shot 学习、合成任务和代码补全；论文在其统一格式和实验设置下评测 8 个模型。论文还报告英文样本平均 6,711 词、中文样本平均 13,386 字符。这些数字只属于原论文数据集和实验条件，不能换算成本文 Token 门槛，也不能外推到当前供应商版本。

对工程团队，LongBench 的价值主要是提醒任务多样性：只测问答会遗漏摘要的覆盖问题，只测抽取会遗漏代码跨文件依赖，只测英文会遗漏中文标点、实体和 Tokenizer 差异。使用公开 benchmark 时需要：

  • 固定数据版本和官方评测脚本；
  • 检查训练/Prompt/调试污染；
  • 报告各任务与语言切片，不只报宏平均；
  • 区分原 benchmark 分数和加入应用模板后的分数；
  • 不把公开集通过当作私有业务集通过；
  • 用真实文档与后置条件做补充轨。

RULER 的可控合成压力、Lost in the Middle 的位置配对方法、LongBench 的任务与语言多样性互补，但三者都不能单独代表生产质量。

十九、统计与重复：非确定输出也要有可比较设计

19.1 先使用配对样本

同一 case 的位置、长度、冲突变体共享真值，适合比较每个 case 的差值。随机化执行顺序，避免某个位置总在服务冷启动、限流或版本切换期间运行。

19.2 重复运行回答稳定性，不替代用例多样性

对温度为零的远程模型也不能假设绝对确定。重要切片可重复 r 次，报告：

  • pass@all：每次都通过；
  • pass rate：通过次数/运行次数；
  • modal outcome：最常见结构化结果；
  • disagreement rate：同变体结果不一致比例。

重复同一个 case 一百次不能替代一百个不同 case。前者估计运行波动，后者覆盖语义与格式多样性。

19.3 置信区间不能修复系统偏差

可以对 case 做 bootstrap 得到配对差异区间，但如果真值同源错误、样本只含英文、干扰都是 easy noise，窄区间只表示对偏置样本估计得很稳定。报告中把采样不确定性、标注不确定性和分布覆盖缺口分开。

19.4 多重比较与挑格子

大量位置、长度、任务组合容易出现偶然好点。预先定义主指标、关键切片和停止规则；探索性发现标为 exploratory，在独立保留集复验。不要在 42 个格子中选一个最佳位置宣称模型支持该长度。

二十一、自动化策略：编译不变量，而不是维护一堆巨大 Prompt 文件

21.1 用例即代码，但真值不是临时脚本

推荐存储小而结构化的 case：原子 item、关系图、冲突规则、gold span 和 outcome。测试时编译为不同长度和布局。这样可以：

  • 对所有位置复用同一真值；
  • 调整 Tokenizer 后重新放置；
  • 自动生成 manifest 和摘要；
  • 缩小失败样本；
  • 证明变体只改变批准轴；
  • 在模型/Prompt/组装器变更时复跑相同 case 家族。

业务 Oracle 需经过评审、版本化和单元测试。错误 Oracle 会让自动化更快地产生错误结论。

21.2 三层测试金字塔

  1. 确定性组件测试：Token 计数、位置编译、span 完整、冲突 Oracle、引用解析、截断 reason；
  2. 模型隔离测试：绕过检索，验证模型在可见上下文上的位置、密度、多跳、冲突和引用；
  3. 端到端应用测试：走生产检索、组装、压缩、模型和后置条件。

组件测试定位快，模型隔离测试区分链路与使用，端到端测试才支持应用发布。三者互相不能替代。

21.3 变形关系比固定答案文本更稳

可自动验证的变形关系包括：

  • 同级无关文档重排，不应改变结论；
  • required 证据移动，只允许在门槛内波动；
  • 删除一个必要 hop，应从结论变为证据不足；
  • 替换事实值，结构化答案应同步变化；
  • 追加已失效旧版，不应覆盖当前版本；
  • 交换展示编号，不应改变稳定引用 ID；
  • 缩小预算到 mandatory 不可容纳，应失败显式化；
  • 原文压缩后，关键事实和引用仍应保留或通过回源恢复。

21.4 评测污染控制

公开 benchmark、调试会话、失败报告和 gold answer 不得直接进入 Few-shot、RAG 或 Prompt 优化语料。至少记录祖先数据集和 transform lineage。若模型可能见过公开题，使用构造事实、私有保留集与反事实变体，避免把记忆当上下文使用。

21.5 CI、夜间和发布前分层

  • PR CI：小型确定性编译器测试、固定 4K/16K 冒烟、一个冲突与一个压缩注入；
  • 夜间：关键任务的全位置 × 多长度矩阵，模型隔离与生产轨；
  • 候选发布：生产加权回放、组合故障、重复运行、时延成本并行门禁；
  • 上线后：影子或只读回放、真实长度/失败切片漂移、抽样引用复核。

远程模型版本不可完全冻结时，每次报告保存供应商返回的版本标识和时间窗；发现静默漂移就重跑核心矩阵，不用旧结论永久背书。

二十二、判定器设计：确定性 Oracle 优先，Judge 只处理剩余语义

22.1 可以确定判定的内容

  • 枚举、布尔、数值、日期和单位；
  • item/span 是否被选择和完整可见；
  • 版本与有效区间；
  • 依赖边集合；
  • 引用 ID、版本和跨度；
  • JSON Schema 与业务后置条件；
  • forbidden claim 与禁止动作。

这些不应交给模型 Judge 以“整体看起来合理”方式评分。

22.2 Judge 的最小职责

开放叙述中的等价表达、解释是否覆盖某个非结构化原因，可以由人工或 Judge 复核。Judge 应看最小必要内容，输出逐 rubric 的 verdict 与证据，不给一个不可解释的 1–10 总分。

22.3 Judge 不能证明什么

  • Judge 同意不是真值；
  • 高置信度不是准确概率，除非经过对应分布校准；
  • 与被测模型同家族的 Judge 可能共享错误；
  • 长输入也会影响 Judge 自己；
  • Judge 看到参考答案后可能偏向词面；
  • Judge API 成功不代表判定完整。

高风险分歧进入盲化人工队列；人工也要记录指南版本、分歧和仲裁，不把单人判断伪装成绝对事实。

故障注入不是随机塞垃圾文本，而是有假设、有可观察首错层、有预期告警的受控变更。

23.3 使用层注入

在 mock 中可故意实现“忽略中间位置”“永远选最后出现”“只取第一跳”等错误策略，验证指标和定位逻辑会报警。对真实模型，使用层不是修改模型内部，而是构造能暴露行为的输入变体。

23.4 生成层注入

  • 输出集合删除最后一个元素；
  • 把引用编号整体偏移一位；
  • 把数值单位从天改成月；
  • 在 post-processing 中把 DENY 映射成 ALLOW；
  • 模拟输出 Token 预算不足。

如果测试只检查关键词，它可能抓不到这些故障。每种注入都应至少杀死一个测试；长期 mutation survived 表示断言没有覆盖真实风险。

23.5 组合注入

例如同时注入“中间 gold span 被压缩遗漏”和“旧版放在尾部”。预期生产轨选择旧版，原文隔离轨通过，压缩隔离轨失败。若系统只看到最终错误而无法区分三轨，Trace 设计仍不完整。

24.2 这个 mock 明确不能证明什么

它不能证明任何真实模型具有长上下文能力，不能模拟 Transformer 的注意力、Tokenizer、位置编码或随机生成，不能测供应商截断、真实摘要语义、自然语言蕴含、网络与推理性能，也不能说明 0%、50% 或 100% 位置在真实模型上的质量。示例 tokenizer 只是教学计数器，不能替代目标模型官方或实际 tokenizer。

二十五、自动化执行流程：从 manifest 到可审计报告

25.1 编译前校验

编译器先拒绝：required item 不存在、gold span 越界、冲突无 resolution rule、时间区间非法、hop graph 不连通、forbidden 与 required 重叠、引用指向非固定版本等用例缺陷。坏真值不能进入大规模模型调用。

25.2 生成变体

按测试计划展开参数，但使用 pair ID 绑定同一 case：

位置是配对中唯一变化时，才计算位置差。编译后再次用目标 Tokenizer 检查 actual length、actual position 和 span 完整性。

25.3 随机化与限流

执行顺序按稳定 seed 打乱，避免 P0 总在早晨、P50 总在下午。并发、重试和 Deadline 固定；重试保存新 attempt，不覆盖原失败。远程调用预算不足时优先保留完整 pair，不要运行一半位置后把缺失位置当零。

25.4 在线判定顺序

基础设施未知先于质量判定。如果实际模型版本缺失、请求摘要对不上、Trace 丢字段，本次运行不能进入可比较主结果。

25.5 报告必须能下钻

汇总表的每个分子都链接到 run ID；每个失败 run 展开：case、变体轴、原始/最终 item、span、模型输出、判定结果和首错层证据。只给热力图不提供样本，会让团队在图上猜根因。

二十六、失败定位手册：从现象到证据，不从熟悉的组件开始猜

26.1 只有长输入失败

先检查真实发送长度和应用阈值，再看 required selection/visibility。若必需 span 完整可见，比较模型直连隔离轨；同时检查输出预算是否随输入被挤压。不要因为“长”就直接归因 KV Cache 或位置编码。

26.2 只有中间位置失败

验证实际 Token 分位、模板序列化、middle truncation 与 item span。确认生产轨和直连轨是否同样下陷。若仅生产轨失败，优先查组装与解析；若两轨在相同 case 上均下陷，才支持模型/Prompt 利用位置是候选因素。

26.3 答案对但引用错

删除或替换正确证据做反事实运行。检查引用稳定 ID 与展示编号映射、文档版本标题、claim-citation 解析。答案可能来自参数知识，不要把“答对”当作证据链成功。

26.4 新旧冲突时选旧版

先验证 query business time、valid_from/to、authority 和 scope 是否进入模型前确定性层；再交换新旧位置。若总选最后一条，是位置近因倾向；若总选措辞更强的旧文，是权威语义混淆；若 Trace 中只有旧版，首错在选择层。

26.5 压缩后失败，原文通过

比较 retained facts、否定、范围、未决项和 lineage；运行 rehydrate 轨。摘要正确但回答错时再看压缩布局与模型；摘要已错，先修压缩器和回源门禁。

26.6 多跳只漏最后一跳

检查最后一条边是否被召回、是否因去重合并、是否在输出预算尾部被截断。要求输出 edge 集和引用。不能从最终实体漏失单独断言模型推理深度不足。

26.7 告警同时伴随延迟上升

这只是相关观测。把质量失败按 timeout、completed、truncated output 分层；对完整完成的相同变体再比较。服务压力可能导致超时和输出不全，但也可能恰逢模型/Prompt 版本变化。性能 Trace 与质量 Trace 用 run ID 关联，不互相替代根因证据。

第一步：验证评测基础设施

第七步：检查引用

可解析率 98.9% 看似高，但关键 claim 完整引用只有 85.4%。引用解析器能找到文档，不代表 span 支持结论。失败包含：引用 policy-v8 的范围段但没引用 180 天数值段；结论使用撤销记录但引用旧批准；三跳只引用首尾实体，漏中间依赖边。

第八步：排除性能告警冒充根因

96K 的尾延迟确实上升，少量输出达到上限。但 11 个 stale authority 错误均完整生成、finish reason 正常；相同时间窗的原文直连轨多数通过。性能压力可能影响另外一批集合不完整 case，却不能解释压缩文本极性已经在模型前丢失。两类问题分别进入质量和性能修复。

27.7 根因、贡献因素与检测缺口

事故记录分三栏：

根因： c-4 的保留检查只验证实体和日期出现，没有把否定、状态与适用范围作为 critical fact，导致撤销语义在 compaction 中丢失。

贡献因素：

  1. assembler a-13 的标题近重复合并会删除不同资产边；
  2. 模型/Prompt 在“winner 中间、loser 尾部”的冲突布局下不稳；
  3. 输出要求一次列全，96K 下部分集合受输出预算影响；
  4. 引用报告只把 resolvable 当作主要指标，没有把 claim support 置顶。

检测缺口：

  1. compactor 单元测试只有实体保留，没有极性、撤销和范围变异；
  2. 旧回归只测“新在后”；
  3. 单 Needle 被放在发布看板第一位；
  4. 引用可解析率掩盖完整支持率；
  5. Selection Trace 只有 item ID，最初没有 critical field manifest。

二十八、发布门禁怎样落地：拒绝一个总分决定所有任务

28.1 能力合同按任务写

能力合同随整条栈版本变化，不只绑定模型。上线路由器根据任务类型、风险和实际 Token 选择能力，不允许把 96K 单事实能力误用于 96K 冲突裁决。

28.2 四种发布动作

  1. 放行：关键切片和硬门禁通过；
  2. 限长：更长档失败，但较短连续区间有证据；
  3. 限任务/限动作：只读抽取通过，写工具或高风险裁决不通过；
  4. 阻断/回退：硬错误、Trace 不完整或 unknown 过高。

“继续观察”不是第五种无责任状态。若继续灰度，必须写流量、任务、租户、时间、自动止损和人工容量上限。

28.3 降级不能静默改变语义

从“分析全部合同”降级为“只分析检索到的前三段”，必须向调用方返回范围缩小和证据缺口。更好的降级包括：

  • 将任务拆为可验证子问题；
  • 先检索候选，再分批读取并汇总结构化事实；
  • 对关键冲突回源；
  • 请求用户指定实体或时间范围；
  • 转人工或确定性流程；
  • 明确拒绝。

静默截短后给完整口吻回答，是最危险的“成功”。

二十九、监控上线后的 effective context 漂移

离线门禁通过后，生产分布仍会变。线上不一定有即时真值，但可以监控领先信号与延迟真值。

29.1 输入与组装信号

  • 实际 Token 长度、文档数和语言分布；
  • required 类别 item 的 selected/dropped reason；
  • 截断、压缩、回源和拆任务比例；
  • 位置分布与关键 span 跨距；
  • conflict group 数、stale 候选数；
  • duplicate token ratio 与 unique evidence density。

这些是链路观测，不直接等于答案质量。

29.2 输出信号

  • 拒答、澄清、人工接管；
  • 引用可解析、版本正确、抽样 claim-support；
  • 集合输出长度与 finish reason；
  • 同一事实在回答与工具参数中的一致性；
  • 业务后置条件失败；
  • 延迟到达的人工/业务真值。

引用率突然下降是告警，不是根因。它可能来自模型、解析器、文档 ID 变更或输出截断。

29.3 哨兵与回放

在不泄漏用户内容的前提下，定期运行小型构造哨兵：位置 P0/P50/P100、一个撤销冲突、一个三跳、一个压缩极性。哨兵只能监测已知机制，不能代替真实抽样和事故回放。

29.4 触发重评测的变化

  • 模型或供应商版本；
  • Tokenizer；
  • System/Developer Prompt；
  • 检索、rerank、chunk、assembler；
  • 压缩器与阈值；
  • 输出 Schema、引用协议和 max_output_tokens；
  • 文档分布、语言、格式或业务政策；
  • 上下文软上限与路由策略。

只要变化可能改变可见内容、位置或使用方式，就不应永久沿用旧 effective context 声明。

三十、常见误区

30.1 把 advertised max 当 effective max

最大可接收长度是接口/模型容量条件，不是任务质量证据。应用还可能有更小的软限制与压缩阈值。

30.2 只跑 Needle 热力图

Needle 通过不证明多值完整、多跳、聚合、冲突、时效或引用。它适合基础校准，不是发布全证据。

30.3 只报平均准确率

平均值会掩盖最差位置、高风险冲突和少数语言。报告任务、长度、位置、密度、hop、冲突和 transform 切片。

30.4 看到中间低谷就引用论文当根因

论文提供受限实验观察。当前低谷还可能来自组装、截断、Token 坐标、模板或判定器。

30.5 用字符位置冒充 Token 位置

中文字符、英文单词、UTF-8 字节和 Token 不等价。位置 manifest 绑定实际 Tokenizer。

30.6 新文档总放在最后

这会让“选最后一条”的坏策略通过时效测试。必须交换顺序并构造尚未生效和迟到摄取。

30.7 selected item 等于完整可见

item ID 在 Trace 中不证明关键 span、否定和范围仍在。检查最终 span 与 critical fields。

30.8 答案正确就算引用正确

答案可能猜对，引用可能只是主题相关。claim-support、版本和完整性独立判定。

30.9 压缩率越高越好

压缩是有损变换。关键事实丢失率、unsupported summary claim 和回源成功率比压缩率更重要。

30.10 让同一个 Judge 看完超长输入打总分

Judge 自己也受长上下文和位置影响。先用确定性 Oracle，Judge 只看最小必要 claim 与证据。

30.11 用更多重复代替更多 case

重复估计随机波动，不增加语义、格式、冲突和任务覆盖。

30.12 用 benchmark 冒充生产门禁

公开 benchmark 支持可比较研究与回归，不包含当前权限、工具、文档、模板和后置条件。

30.13 用供应商一个版本泛化全行业

位置、长度和冲突行为绑定具体模型版本与实验。不同模型、任务和 Prompt 必须实测。

30.14 告警就是根因

“P50 失败率高”“延迟上升”“引用率下降”都是观测。根因需要 Trace、隔离轨和排除证据。

30.15 相关性就是因果

长度增加时质量下降，可能同时伴随密度下降、压缩触发和输出变长。控制变量或明确写成相关观测。

30.16 把 unknown 从分母删除

超时、版本缺失和 Judge 失败不是成功。单列 UnknownRate 并限制其上限。

三十一、从零到一的实施顺序

阶段一：先盘点真实长上下文链路

记录原始素材、候选、selected/dropped、最终 span、模型输入、输出 claim 和引用。没有 Trace 时，先不要做巨大矩阵；否则得到的只是无法定位的红绿格。

阶段二：建立 20–50 个高价值 case

覆盖单事实、多值、多跳、冲突、时效、引用与压缩；每个 case 有结构 outcome、required span 和 forbidden claim。优先回放真实失败和高风险业务规则。

阶段三：实现确定性编译器与组件测试

支持 Token 长度、位置、干扰、冲突布局和截断注入。先用 mock 杀死故障，确保评测 harness 不是永远绿。

阶段四：模型隔离位置/长度矩阵

在 gold context 完整可见时测有效使用，得到模型/Prompt 的基础曲线。不要绕过此轨直接把所有错误归给模型。

阶段五：生产轨与三轨差分

加入检索、组装、压缩和引用解析，比较 raw/compressed/rehydrate。按首错层修复。

阶段六：生产加权回放与组合故障

基于联合分布估计影响，同时保留最差切片和硬门禁。把质量、性能、成本和安全分别验收后汇总决策。

阶段七：能力合同、灰度与持续漂移

按任务声明 effective context，路由器执行限长/限任务。上线运行哨兵、抽样引用、延迟真值与变更触发重评测。

三十二、可执行上线检查清单

边界与承诺

  • advertised max window 与应用 effective context 分开表述；
  • effective context 绑定模型、Prompt、Tokenizer、assembler、compactor 和任务；
  • 没把 API 接受请求写成质量通过；
  • 没把单 Needle 结果写成长上下文完整能力；
  • 已声明本文/报告覆盖的语言、格式、任务、长度和风险；
  • 未测试更长区间标为未知，不外推；
  • AI测试-27 的上下文管理与本文质量测试职责分开；
  • AI测试-42 的性能门禁与质量根因分析分开。

真值与数据模型

  • 每个 case 有稳定 ID、版本、风险和 task type；
  • outcome 是结构化业务结果，不只是一段参考答案；
  • required/helpful/forbidden/stale item 分开；
  • gold span 绑定固定文档版本；
  • conflict group 有 winner 规则或明确无 winner；
  • event time、valid time、published time、ingested time 分开；
  • authority、scope、entity 和 supersedes 可查询；
  • hop graph 的节点、边和引用齐全；
  • 构造数据明确标为构造，不冒充生产统计；
  • benchmark、调试集、Few-shot 和保留集血缘隔离。

变体编译

  • 长度使用目标 Tokenizer 计算；
  • 位置按实际 Token span 分位记录；
  • 目标位置与实际位置偏差有容忍阈值；
  • pair 中除批准压力轴外其余变量冻结；
  • 固定信号轨与固定密度轨分开；
  • easy noise 与 hard distractor 分开；
  • 多值数量、hop 数、跨距和分支可控；
  • 新旧、权威、撤销、否定和同级冲突均覆盖；
  • winner/loser 顺序与距离交叉；
  • seed、编译器、语料和 item order digest 可回放。

选择与可见性

  • 候选、rank、score、selected/dropped 全量 Trace；
  • 每个 dropped item 有 reason code；
  • item selected 不会被当作 span 完整；
  • 最终 item-to-token-span map 可用；
  • 截断层、方向和边界可定位；
  • mandatory 证据超预算时失败显式化；
  • head/tail/middle/per-item/output 截断均测试；
  • critical fact 保留值、极性、范围、时间和来源；
  • 原文、压缩、回源三轨可配对；
  • 压缩代际和 lineage 可追溯。

模型使用与任务

  • 单事实只是基础校准；
  • 同键多值与多查询检查完整召回；
  • 聚合任务不与选择任务混分；
  • 多跳输出包含可验证 edge/entity 集；
  • 缺一个必要 hop 时能正确表示证据不足；
  • 冲突测试同时测唯一 winner 与无 winner；
  • 不把最后出现当作最新生效；
  • 参数知识通过删除/替换证据对照识别；
  • 高风险规则在模型外有确定性控制；
  • 结构化中间字段不被宣传为内部思维因果证明。

引用与输出

  • 引用可解析到固定文档版本和 span；
  • relevant 与 supporting 分开；
  • 每个关键 claim 有 claim-citation 映射；
  • 多 span 支持的 claim 检查完整性；
  • 答对引错作为独立失败；
  • stale/forbidden 文档不得作为权威引用；
  • 展示编号变化不影响稳定引用 ID；
  • 输出预算足以列全目标和引用；
  • finish reason、解析错误与集合遗漏分开；
  • 工具参数和最终文字使用同一事实版本。

指标与统计

  • Selection、Visibility、Utilization、Generation 分层统计；
  • 每个比例保存分子、分母和 unknown；
  • 最差位置、PositionSpread 和配对 delta 都报告；
  • effective context 要求连续通过区间；
  • RequiredSelectionRecall 有 item 与 span 两级；
  • SetRecall 与 ExactSetMatch 分开；
  • FullChainSuccess 要求边完整且结果正确；
  • resolvable conflict 与 unresolvable conflict 分开；
  • 引用 Precision/Recall 与关键 unsupported rate 分开；
  • UnknownRate 有发布上限；
  • 重复运行与 case 多样性没有混淆；
  • 探索性格子在独立保留集复验。

自动化与故障注入

  • 编译器、Token 位置、span 和 Oracle 有单元测试；
  • 离线 mock 能杀死选择、截断、压缩、偏位、多跳和引用故障；
  • 模型隔离轨与生产端到端轨都运行；
  • 失败注入有预期首错层和告警；
  • mutation survived 会阻断或进入评审；
  • 执行顺序随机化，完整 pair 优先；
  • retry 使用新 attempt，不覆盖失败；
  • Judge 失败记 unknown，不补零；
  • 高风险分歧进入盲化人工仲裁；
  • 评测基础设施缺证据时不产出强结论。

发布与运营

  • 门槛在看结果前预注册；
  • 高风险硬错误不能被均值抵消；
  • 能力合同按任务和风险写 effective context；
  • 放行、限长、限任务、阻断条件明确；
  • 降级会显式返回范围与证据缺口；
  • 灰度有流量、时间、预算、人工容量和自动止损；
  • 质量、性能、成本和安全门禁并列；
  • 报告把 Observation、Inference、Decision 分开；
  • 告警没有被直接写成根因；
  • benchmark 没有冒充生产质量；
  • 单一供应商特性没有泛化为行业规律；
  • 组件、模型、Prompt、数据分布变化会触发重评测。

三十三、总结

长上下文测试的第一原则，是把“放得进去”与“用得正确”分开。

advertised max window 只描述声明的接收边界；effective context 描述某个具体应用栈、任务、压力切片和质量门槛下，经证据支持的可靠区间。它必须按任务声明：单事实检索、多值全量抽取、多跳、冲突裁决和长文摘要不共享一个有效长度。

第二原则，是把单 Needle 放回它应有的位置。它适合校准长度拼接、位置扫描和基础检索连通性，却远远不能证明信息完整、多跳整合、时效裁决、引用支持或压缩忠实。RULER、Lost in the Middle 和 LongBench 分别提供了可控复杂任务、位置实验和任务/语言多样性的研究依据，但所有结论都要限定在原论文模型、数据、任务构造与实验设置内，再用当前业务证据验证。

第三原则，是用四段漏斗定位信息遗漏：

必需事实没有被选中，不是模型忽略；item ID 在场但否定被摘要删除，不是位置偏差；事实完整可见却选旧版，才进入使用与冲突裁决；结论正确但引用错位，属于输出与证据映射。首错层、贡献因素和检测缺口要分别记录。

第四原则，是让压力矩阵可解释。长度、位置、密度、多跳、冲突/时效、引用、截断与压缩先做正交或配对测试，再做生产联合分布和组合故障。最差位置、高风险硬错误和 unknown 不能被总体均值隐藏。
