AI测试-42-大模型推理性能怎么分析TTFT-TPOT吞吐批处理和KV Cache

发表于 2026-05-10 分类于 AI测试 本文字数： 15k 阅读时长 ≈ 55 分钟

大模型接口平均 1.8 秒返回，能不能说明性能很好？

不能。这个平均值可能来自三类完全不同的体验：短问题 300 毫秒开始输出但长答案断断续续，长 Prompt 排队 5 秒后流畅生成，或者大部分请求很快、少量请求在 KV Cache 紧张时等待几十秒。三者的平均端到端延迟可能接近，容量风险却完全不同。

同样，“每秒 2,000 Token”也不是一个自解释指标。它可能是：

  • 单个请求解码阶段的输出速度
  • 全服务实例在一个时间窗内完成的输出 Token 数
  • 输入与输出相加后的总 Token 吞吐
  • 只统计成功请求，或者把超时后仍生成的 Token 也算进去
  • 在无限速率压测下得到的最大值，或者在尾延迟达标时得到的可交付值

如果没有时钟边界、工作负载和分母，这些数字不能比较，更不能据此决定 GPU 数量、并发上限或上线门禁。

本文从一条请求的事件时间线出发，建立 queue、prefill、decode、TTFT、TPOT/ITL、E2E、tokens/s、requests/s 的可执行定义，再讨论开放与闭环负载、ISL/OSL 分布、动态与连续批处理、KV Cache 容量与碎片、PagedAttention、量化、投机解码、warmup、Goodput、尾延迟和饱和拐点。贯穿示例只分析合成事件，所有数字都是构造数据，不代表任何真实 GPU、模型或推理框架的测量结果。

资料核对截止 2026-07-26。文中涉及 vLLM 的能力限定为该日期可访问的官方文档；PagedAttention 与 Orca 的性能数字只描述对应论文的实验，不外推到其他版本、硬件和负载。

一、先给结论：性能测试要证明一段可交付工作区间

推理性能验收的产物不应是“某配置跑到 120 requests/s”，而应是带约束的容量包络：

工程上至少遵守十条原则：

  1. 客户端体验与服务端阶段必须分开测。 客户端 TTFT 包含网络、网关和流解析，服务端 queue/prefill/decode 用于归因，二者不能混成一个时间戳。
  2. TPOT 不是单请求 tokens/s 的简单同义词。 平均 Token 间隔、逐 Token 间隔分位数和聚合输出吞吐回答不同问题。
  3. 开放负载与闭环并发不能互相替代。 一个控制到达率，一个由响应速度反向控制发压速度。
  4. ISL/OSL 必须是分布，不是一个固定均值。 长尾输入占用 prefill，长尾输出长期占用 KV Cache 和 decode 槽位。
  5. 批越大不保证用户越快。 批处理提高设备利用率，也可能让短请求被长 prefill 或大 decode 批干扰。
  6. KV Cache 是容量资源，不只是显存百分比。 可用块、碎片、抢占、换出、前缀复用和序列生命周期共同决定在途请求数。
  7. 优化必须在相同语义下比较。 量化、投机解码、前缀缓存、并行策略改变后，要重新验证质量、输出长度和工作负载。
  8. warmup 与稳态分开报告。 冷启动是产品场景时就单独验收，不能先丢弃再宣称线上没有冷启动。
  9. 最大吞吐只是压力边界。 上线容量应位于饱和拐点之前，并保留故障、突发和工作负载漂移余量。
  10. HTTP 200 不是 Goodput。 协议成功、Schema 合法、模型置信度或相似度都不能保证业务结果正确。

二、工程定义与边界：先说明本文测什么、不测什么

本文讨论的是自回归大语言模型在线推理服务。一次典型生成包含：请求进入服务、等待调度、处理输入上下文、建立或复用 KV Cache、随后逐步生成输出 Token。它适用于文本生成接口，也可作为多模态生成的基础，但多模态编码器耗时、音视频传输和实时双向会话需要额外分段，不能直接套用本文阈值。

1. 测量对象

需要同时观察四层：

层级 主要问题 典型证据
客户端 用户多久看到首个有效内容，后续是否流畅 send、first content token、last content token、取消
网关与网络 请求何时被接收，是否排队、限流或缓冲 admission、转发、首字节、SSE 帧、连接错误
推理调度器 等待多久，何时进入 prefill/decode，是否抢占 enqueue、scheduled、phase、batch、preemption
设备与运行时 算力、带宽、显存和通信是否成为瓶颈 GPU 利用率、显存、KV 块、kernel、collective

只在客户端计时，可以评价用户体验，却无法区分网络和模型；只读 GPU 指标，可以定位设备，却不知道用户是否已经超时。性能工程要求两侧通过稳定的 request_id 和 attempt 标识关联，但不能拿跨机器墙钟直接相减。跨主机阶段优先用各自单调时钟计算，再依靠 Trace 事件顺序和经过校准的时钟做辅助关联。

2. 本文不把什么当成性能结论

  • 不把模型给出的置信度当作正确率，也不把高吞吐当作质量不变。
  • 不把 HTTP 200、流正常关闭或 JSON 可解析当作任务完成。
  • 不把固定短 Prompt 的峰值吞吐外推到真实长上下文。
  • 不把单张卡、单副本结果直接外推到多卡通信或多副本路由。
  • 不把 PagedAttention 论文、Orca 论文或厂商样例中的倍率当作当前环境承诺。
  • 不用合成事件示例冒充真实硬件测量；示例的目的只是校验公式和测试方法。

3. 性能与质量的共同边界

改变量化精度、最大输出、停止词、采样参数、投机策略或模型版本，都可能改变输出内容和长度。比较性能前必须先定义业务等价条件，例如：测试集版本相同、请求参数相同、关键任务通过率不低于基线、拒答与安全策略没有倒退、输出长度分布在允许范围内。否则“提速”可能只是少生成、提前停止或生成了不可用结果。

三、统一事件时间线：所有公式都从可观察事件开始

建议至少记录以下事件。名字可以不同，语义不能含糊：

“有效内容 Token”必须排除仅用于协议的空 SSE、心跳、角色帧、usage 帧和 [DONE]。如果工具把首个空事件当首 Token，TTFT 会虚低；如果把最终 [DONE] 当最后 Token，E2E 会包含额外网络与缓冲时间。两种时间也可以都记录，但字段名要说明 last_content 与 stream_done。

1. Queue

本文把服务端排队时间定义为：

它表示请求已经进入推理调度器、但尚未首次获得 prefill 执行机会的时长。网关限流、认证、请求体上传和路由等待不在这个 queue 内，应分别记录。

实际工具的 queue 起点和终点可能不同。有的从 HTTP 接收到首次调度，有的只统计调度器 WAITING 状态，有的把 KV 预留失败、抢占后重新等待或远程 KV 传输也算入等待。vLLM 截止本文资料日期的生产指标中，request_queue_time_seconds 描述请求处于 WAITING 阶段的时间，并另有等待请求数和等待原因指标。跨工具比较前必须核对状态机，而不是只看同名字段。

2. Prefill

本文把 prefill 定义为：

它是处理输入 Token 并形成当前上下文 KV 状态的阶段。首次输出 Token 是否归入 prefill，要看引擎埋点：有的把首步采样并入 prefill，有的单列 first decode step。为避免争论，数据模型应同时保留 prefill_end 与 first_token_generated，并在报告中说明公式。

长输入通常增加 prefill 工作量，但耗时并不只由 ISL 决定。前缀缓存命中、分块 prefill、批内其他序列、张量并行通信、多模态编码、量化 kernel 和调度优先级都会改变观测值。因此不能只画 TTFT versus input_tokens，还要按缓存命中、批大小和并发切片。

3. Decode

Decode 是在已有上下文上自回归生成后续 Token 的迭代过程。若第一枚输出也算一次 decode，则服务端 decode 起点可以是 s_prefill_end；客户端可见的生成区间通常从 c_token[0] 到 c_last_token。

Decode 具有多迭代特征。Orca OSDI 2022 论文提出 iteration-level scheduling，原因正是固定请求级批处理无法在每次迭代及时移出已完成请求或加入新请求。论文在其 GPT-3 175B 实验设置下报告了相对 FasterTransformer 的结果，该倍率只属于论文实验，不能当作所有连续批处理实现的通用收益。

客户端 TTFT 定义为：

7. tokens/s

至少区分三种：

第一种近似是单请求 1 / mean_itl，不等于实例聚合吞吐。聚合输出吞吐更适合容量，输入吞吐更能反映 prefill 压力，总 Token 吞吐将两类计算混在一起，只能在输入输出组成一致时比较。

还要说明 Token 在何时计入：生成时、发送时，还是请求完成时。完成口径在短窗口会出现边界偏差；产生口径需要服务端逐 Token 事件。取消后后台仍生成的 Token 应进入资源浪费指标，不能进入用户收到的 Goodput。

8. requests/s

请求大小差异巨大时，requests/s 单独没有意义。一个 32 Token 分类请求和一个 8K 输入、2K 输出请求都只算一次。报告 requests/s 必须同时给出 ISL/OSL 分布与 Token 吞吐。

完成定义也要明确：收到最后内容、协议结束、状态成功、质量验收通过，还是只要服务端返回。本文将“完成吞吐”和 Goodput 分开：前者可用于资源分析，后者才用于上线容量。

四、指标数据模型：不要从一张聚合表反推真相

一份可重算的基准至少包含五类实体。

1. Benchmark Run

Run 是一次不可变实验，包含：

  • run_id、开始结束时间、操作者和变更单
  • 客户端、负载生成器、网关、服务端和监控版本
  • 模型精确标识、权重摘要、tokenizer 摘要和 revision
  • 服务引擎版本、容器 digest、启动参数和环境变量摘要
  • GPU 型号与数量、显存、驱动、CUDA/ROCm、互联和功耗策略
  • 并行方式、量化、KV dtype、最大上下文、批与调度参数
  • 工作负载清单、随机种子、数据集摘要和预处理代码版本
  • warmup 规则、稳态窗口、超时、取消与重试策略

仅写“vLLM + A100”远远不够。同一框架不同版本、同一 GPU 不同功耗与互联、同一模型不同量化和上下文上限，结果都可能显著变化。

五、开放负载与闭环负载：两种模型回答两种问题

1. 开放负载

开放模型按外部过程产生请求，响应变慢不会自动降低到达率。例如 Poisson 到达以给定平均 RPS 独立产生请求，突发可以用更高变异的到达间隔或真实流量回放模拟。

它适合回答：

  • 生产到达率下队列是否稳定
  • 突发后多久恢复
  • 到达率超过服务率时如何排队、拒绝和超时
  • P99 TTFT 在饱和附近如何变化
  • admission control 是否保护高优先级流量

开放负载必须设置最大在途请求或安全停止条件，否则当到达率持续高于服务率，负载生成器会无限积压，最终测到的是客户端内存或连接上限。

2. 闭环负载

闭环模型维持固定并发：每个虚拟用户收到响应后才发下一请求。系统越慢，发压端产生的新请求越少。它适合测固定会话数、寻找特定并发下的稳态，或者模拟用户等待回复后继续对话。

它的危险是自节流：被测服务进入过载后，完成变慢导致新请求减少，图上可能看到吞吐平稳而不是到达队列爆炸。不能拿“并发 64 闭环稳定”证明“外部 64 RPS 开放流量稳定”。

3. 同一个报告怎样同时使用

推荐三组互补实验：

  1. 闭环并发扫描：1、2、4、8、16……，找资源利用和批处理效率。
  2. 开放到达率扫描：从低负载逐步接近并超过预计容量，找队列拐点。
  3. 生产 Trace 回放：保留时间间隔、ISL/OSL、租户与缓存局部性，验证代表性。

每组实验独立报告，不能把不同到达模型的数据点连成一条“容量曲线”。vLLM 截止资料日期的 benchmark CLI 分别提供 request rate、burstiness 与 max concurrency 等控制项，这恰好说明到达速率和在途上限不是同一参数；具体参数语义仍应绑定使用的 vLLM 版本。

六、ISL/OSL：平均长度会隐藏真正的资源竞争

ISL 是输入序列长度，OSL 是实际输出序列长度。二者至少影响：

  • ISL 增大 prefill 计算和首 Token 等待
  • ISL + 已生成 OSL 决定序列当前 KV Cache 占用
  • OSL 决定请求在 decode 调度中存活多久
  • 长 OSL 请求会与后来短请求持续共享 decode 批
  • max_tokens 只是上限，实际停止长度由内容、EOS 和停止词决定

1. 不要只用固定 512/128

固定长度方便微基准，但不足以做容量规划。真实流量常呈多峰：短问答、带历史对话、长文总结、工具返回和异常超长输入混在一起。均值相同的两个分布，P99 TTFT 和 KV 占用可以完全不同。

建议至少报告：

  • ISL 与 OSL 的 P50/P90/P95/P99、最大值和直方图
  • ISL 与 OSL 的联合分布，而非两个独立边际分布
  • 实际 OSL / 请求上限的比例与停止原因
  • 缓存命中 Token 比例
  • 按任务、租户、语言、多模态和优先级切片

2. 长度分桶不能破坏相关性

如果先独立抽样 ISL，再独立抽样 OSL，可能产生生产中不存在的组合。真实长文总结可能长输入短输出，创作任务可能短输入长输出。最好重放配对样本；若必须合成，使用联合分桶或条件分布 P(OSL | ISL, task_type)。

3. 输出长度本身也是结果变量

性能优化后 OSL 下降，E2E 和成本自然下降，但可能是 EOS 行为、模板、量化误差或停止配置改变。比较时同时报告长度分布和任务验收。不能把“输出少了 40%”默认解释为更高效。

七、并发与批处理：Batch Size 不是一个常数

传统静态批处理先收集一批请求，整批一起执行，可能要等最慢序列完成。自回归生成中不同请求会在不同迭代结束，新请求也持续到达，因此现代在线服务通常采用迭代级、动态或连续批处理。

1. 三个容易混淆的量

名称 含义 为什么不同
客户端并发 未完成 HTTP/流请求数 包含网络、网关与服务端所有阶段
运行序列数 当前被调度器管理或执行的序列 可能含 prefill、decode、抢占与等待
单步批大小 某次模型迭代实际一起执行的 Token/序列 连续变化，受 Token 预算与 KV 限制

报告“batch=32”必须说明是最大序列数、最大 batched tokens、静态输入批，还是某一步实测值。

2. 动态批处理

动态批处理通常在短等待窗口内聚合兼容请求。等待稍久可能形成更大批、提高利用率，却直接增加低负载 TTFT。需要扫描 batch delay，而不是默认“越大越好”。对严格交互 SLO，等待窗口应受剩余 TTFT 预算控制。

3. 连续批处理

连续批处理在迭代边界加入新请求、移出已完成请求，减少整批被最长序列拖住的问题。但它引入新的公平性和干扰：

  • 大 prefill 插入可能延迟正在 decode 的请求
  • 长序列长期占用 KV 块和批槽位
  • 高吞吐策略可能牺牲单个会话的 ITL
  • 抢占与重计算可以恢复容量，却增加 TTFT/E2E
  • 优先级策略若无配额，低优先级请求可能饥饿

所以要同时画 batch 组成、prefill tokens、decode sequences、queue 和 Token gap，才能说明调度策略为何改变体验。

4. Chunked Prefill

将长 prefill 分块并与 decode 迭代交错，可以限制一次 prefill 对已有 decode 的阻塞，但会增加调度复杂度和额外边界。块大小过大仍造成 ITL 尖峰，过小可能降低 prefill 效率。验收要覆盖混合流量，而不是只在全长 Prompt 上比较总耗时。

八、Prefill 与 Decode 的资源特征和相互干扰

简化理解中，prefill 往往具有较大的并行计算机会，decode 每步只为活跃序列推进少量 Token，更容易受内存带宽、KV 读取和批规模影响。这个描述是分析起点，不是对所有模型、硬件和 kernel 的定律。

1. 为什么 TTFT 与 TPOT 可能反向变化

调度器优先接纳更多 prefill，队列和新请求 TTFT 可能下降，但已有序列的 decode 间隔可能扩大；优先保障 decode，流式输出更平滑，新请求却等待更久。所谓吞吐与延迟权衡，本质上需要决定有限设备时间在新请求和存量请求之间如何分配。

1. 为什么 OSL 长尾会拖垮容量

长输出请求每生成一个 Token 都增长 KV，并长期占用块。即使平均 OSL 很小，少量超长请求也可能让新请求无块可分，出现等待、抢占、换出或重计算。需要观察“当前 KV Token 数”和“剩余块”随时间变化，而不是只看实验结束后的平均显存。

2. 内部碎片与外部碎片

若每个请求预留最大连续区域，实际只生成一部分，未使用空间形成内部浪费；不同长度序列不断结束与进入，空闲区域无法满足大连续分配，会形成外部碎片。工程实现对碎片的定义可能不同，报告应区分：

  • 已分配但当前无有效 KV 的空间
  • 最后一个块因未填满产生的尾部浪费
  • 空闲总量足够但无法按分配粒度使用
  • 前缀共享或 Copy-on-Write 引入的引用与元数据

3. PagedAttention 的边界

PagedAttention 论文借鉴操作系统分页思想，把每个序列的 KV Cache 划分为块，通过非连续物理块映射逻辑序列，从而减少碎片并支持 KV 共享。论文作者在其模型、硬件、工作负载和对比系统下报告 vLLM 在相近延迟水平获得 2 到 4 倍吞吐提升，且长序列、较大模型和复杂解码下更明显。

这个结果不能改写为“启用 PagedAttention 就一定提升 2 到 4 倍”。当前系统可能已经有分页式缓存，对比基线、块大小、调度器、kernel 和硬件也不同。正确做法是把论文作为设计依据，把本环境的无碎片率、可容纳 Token、抢占率和 Goodput 作为验收证据。

4. 块大小的权衡

较大块减少块表和调度开销，却增加序列尾部浪费；较小块降低尾部浪费，却增加元数据、映射和 kernel 处理成本。最优值依赖长度分布和实现，不能只用平均长度推导。

十、容量曲线、尾延迟与饱和拐点

低负载时，请求几乎不排队，增加并发可以扩大批、提高设备利用率，完成吞吐明显增加。继续加压后，设备或 KV 资源接近瓶颈，吞吐增益变小；再往后，到达率超过可持续服务率，队列和 P99 TTFT 快速上升，超时与取消增加。完成吞吐可能仍平稳，Goodput 却因 SLO 和质量失败下降。

1. 如何识别拐点

不要凭肉眼挑最大点。可以结合：

  • 相邻负载级吞吐增益率显著下降
  • queue P95/P99 的一阶斜率突然增大
  • KV 使用率长期贴近上限，等待与抢占开始持续出现
  • TTFT 或 ITL 超过门槛的比例明显上升
  • Goodput 达峰后下降
  • 负载停止后队列恢复时间显著延长

统计方法可以用分段回归、变化点检测或受约束的 Pareto 前沿，但最终上线点由 SLO 与风险余量决定，不是数学拐点本身。

2. 尾延迟为什么比平均值重要

推理请求长度异质、批内干扰明显，平均值对少量长等待不敏感。P99 仍需要样本量：只有 100 个请求时，P99 几乎由单个样本决定；每个负载级应报告样本数、置信区间或重复运行分布。还要按长度、租户和缓存切片，避免总体 P99 被流量组成掩盖。

3. 上线容量不是峰值的固定百分比

“取峰值 70%”只是经验起点。余量应覆盖：

  • 生产 ISL/OSL 与压测样本偏差
  • 单副本故障与滚动发布
  • 突发和热点前缀
  • 监控、日志和安全检查开销
  • 驱动或框架升级后的变化
  • 多租户噪声与区域网络

应通过故障容量实验推导，而不是统一套一个比例。

十二、Warmup：冷启动、热稳态和长时稳定性分开报告

1. 会被预热的东西

  • 模型权重加载与内存映射
  • kernel 编译、自动调优和 CUDA graph 捕获
  • 通信组、连接池和容器网络
  • tokenizer 与模板缓存
  • allocator 与 KV 块池
  • 前缀缓存和文件系统页缓存
  • JIT、Python import 和监控初始化

丢弃前 N 个请求并不能证明所有层已经稳定。应观察阶段指标和资源状态达到稳定区间，再定义 warmup 结束。

2. 三类结果不要合并

场景 目的 报告方式
Cold start 扩容、重启、故障恢复体验 从进程/Pod 创建到 ready，再到首个合格响应
Warm steady state 常规容量与延迟 明确预热过程、排除窗口和稳态判据
Soak 泄漏、碎片、热降频、缓存漂移 长时间趋势、周期峰值、恢复能力

若生产会频繁弹性缩容，冷启动就是用户路径，不能只给热稳态数字。若生产依赖前缀缓存，基准既要测冷 cache，也要按真实局部性测 warm cache，并分别报告。

3. 不要让 warmup 污染测量窗口

warmup 请求结束时可能仍有异步日志、后台编译或缓存写入。开始正式窗口前，应确认队列清空、在途请求归零、资源状态进入预期，并记录切换事件。否则前几秒数据不是稳定测量。

十三、量化：容量收益必须同时过质量和 kernel 门槛

量化可能作用于权重、激活或 KV Cache。它可能减少显存占用、提高可容纳批量，并在有匹配硬件与 kernel 时提升吞吐；也可能引入反量化开销、兼容性限制或质量变化。

1. 权重量化的验收

比较至少固定：模型 revision、tokenizer、服务版本、采样参数和工作负载。除性能外检查：

  • 目标任务成功率和风险切片
  • 输出长度、停止原因和拒答率
  • 数值、代码、结构化字段与工具参数正确性
  • GPU 显存、功耗、kernel 时间与批规模
  • 首次加载和 warmup 时间

不能以“模型能加载”和输出看起来流畅作为质量证明。

2. KV Cache 量化的边界

截至资料日期，vLLM 官方文档说明 FP8 KV Cache 可降低 KV 内存占用，容纳更多 Token，并可能改善吞吐和长上下文支持；文档同时提供不同 scale 策略，并建议用数据集校准以获得更好的准确性。这里的“可能改善”依赖硬件、attention backend、校准和工作负载。

需要单独测试长上下文、不同层敏感性、校准集代表性和实际 kernel。显存下降并不保证 TPOT 下降；如果额外量化开销或 backend 路径较慢，容量与单请求延迟可能一升一降。

3. 量化前后不能只比较峰值

应比较两条受相同 Goodput 条件约束的容量曲线。量化版即使最大 tokens/s 更高，只要质量底线下降、P99 TTFT 超限或输出分布变化，就不能宣布业务容量提升。

十四、投机解码：验证加速边界，不宣传一个固定倍率

投机解码通常由较便宜的 proposer/draft 一次提出多个候选 Token，再由目标模型验证并接受其中一部分。其收益取决于接受率、draft 成本、验证效率、模型匹配、序列长度、批规模和系统当前瓶颈。

截至资料日期，vLLM 官方文档将其适用场景明确描述为中低 QPS、内存受限工作负载下减少 ITL，并列出多种 proposal 方法。这个边界很重要：高负载时额外 draft 工作可能争夺设备资源；某方法在单请求上降低 ITL，不代表聚合 Goodput 一定提高。

1. 必测指标

  • accepted tokens / proposed tokens
  • 每个 draft 位置的接受率
  • proposer 与 verifier 各自耗时
  • TTFT、gap P99、E2E 与完成吞吐
  • 额外显存和 KV 占用
  • 不同 OSL、采样温度和任务切片
  • 输出一致性与质量回归

2. “无损”也需要环境验证

算法目标可能是保持目标分布，但浮点数值、批调度、随机状态和 logprob 稳定性仍可能让逐 Token 输出不同。vLLM 文档也提示当前不保证稳定 logprobs，并说明启用与未启用投机解码时可能因运行因素出现输出差异。因此验证重点应是目标质量与分布约束，不要用少量逐字符串相等替代全部质量，也不要用“理论无损”跳过回归。

3. 何时应关闭

接受率低、proposer 过重、高并发计算已饱和、额外显存挤压 KV、短输出不足以摊薄启动成本，或者目标任务质量证据不足时，投机解码可能得不偿失。路由层可以按任务和负载选择，但策略本身也要版本化和压测。

十五、前缀缓存：命中率必须和节省 Token、容量代价一起看

前缀缓存可以复用相同前缀已有 KV，减少重复 prefill。命中率本身不够：一个请求命中 16 Token 与命中 8K Token 都可能算一次命中。至少报告：

缓存键必须包含会改变语义或权限的维度，例如模型 revision、tokenizer、模板、租户、权限域和相关采样/适配器配置。高命中但跨租户复用错误属于安全事故，不是性能成功。

真实流量局部性决定收益。将所有请求打乱后压测会低估命中，重复同一个 Prompt 又会高估。应从生产中提取脱敏的前缀群组和到达顺序，或构造明确的冷、热、混合三组场景。

十六、基准实验矩阵：一次只改一个变量还不够

推理系统存在交互效应，例如 KV 量化只有在长上下文和高并发下才显著影响容量，投机解码在低 QPS 有收益、在高 QPS 反而竞争资源。实验既要有单变量扫描，也要覆盖关键交互。

十九、自动化测试：指标代码本身也必须被测试

性能分析脚本出错会制造稳定而错误的结论。自动化测试至少覆盖以下类别。

1. 公式单元测试

  • 已知时间线的 queue、prefill、TTFT、E2E 与 ITL 精确值
  • 输出 1 Token 时 ITL 为不可定义
  • P50/P95 插值规则固定
  • 时间窗分母使用首个发送到最后有效完成，或使用显式稳态窗口
  • requests/s 与 tokens/s 的成功/失败纳入规则
  • Goodput 同时检查时延、完整性和质量门

2. 事件契约测试

  • Token 时间必须单调
  • Token 事件数与 tokenizer/usage 口径不一致时标记异常
  • 首内容事件不能早于服务端生成
  • attempt 不能跨 logical request 混合
  • 空 SSE、心跳和 done 不计内容 Token
  • 客户端取消后到达的事件标为 late，不改写用户 E2E

3. 聚合性质测试

可以用性质断言避免只覆盖一个 Fixture：

  • 给所有事件平移相同时间，阶段时长不变
  • 在同一请求末尾增加更晚 Token，E2E 不减
  • 质量从 pass 改为 fail，完成吞吐不变但 Goodput 不增
  • 在测量窗口不变时增加合格完成，Goodput 不减
  • 分桶之和与全量样本数一致

4. 端到端基准冒烟

在每次工具升级后运行一个小模型或 Stub 服务，验证负载生成、流解析、事件导出、分析和报告链路。冒烟不用于性能基线，只防止“客户端不再识别首 Token”“usage 字段改名”等测量故障。

二十、失败注入：证明指标能揭示故障，而不是只在健康时画图

1. Queue 注入

在 admission 后人为限制调度并发或占用 worker，使 s_enqueue -> s_prefill_start 增长。预期：queue 和客户端 TTFT 上升，prefill 本身不一定变化。若报告只看到 TTFT 上升却没有 queue，说明阶段埋点不足。

2. Prefill 干扰

向短请求流量中注入受控长 ISL，并记录 chunked prefill 配置。预期：长请求 prefill 增长；若调度隔离不足，已有短请求 ITL 也出现尖峰。通过 batch 事件证明同一时段是否发生干扰。

3. Decode Stall

注入受控 worker pause、通信延迟或服务端发送缓冲，观察 gap P99、最大停顿和客户端取消。要区分服务端 Token 生成停顿与 Token 已生成但网络未送达。

4. KV 压力

构造长 ISL/OSL 与高并发，使 KV 接近上限，验证 waiting reason、抢占、换出/重计算、拒绝和恢复。禁止把 GPU OOM 当作唯一通过信号；可靠系统应在 OOM 前通过 admission 或负载丢弃保护。

5. 客户端与观测故障

  • 注入重复、乱序和空流事件，分析器应拒绝或标记
  • 让客户端 CPU 饱和，证明客户端解析也能抬高 TTFT/ITL
  • 注入墙钟跳变，单调时钟阶段不受影响
  • 暂停指标采集器，报告必须显示数据缺口而不是用 0 补齐

6. 组合故障

真实事故常是“缓存命中下降 + 长 Prompt 增加 + 一个副本退出”。组合注入要验证：负载均衡是否将流量瞬间压到剩余副本，queue 是否快速预警，admission 是否保护核心任务，恢复后是否出现冷副本抖动。

二十一、完整失败案例一：平均 E2E 变好，用户却说输出卡顿

现象

发布后平均 E2E 从 3.4 秒降到 3.0 秒，完成吞吐提高 12%，但用户反馈“经常停住再一次出来很多字”。这些数字为案例构造数据。

错误结论

团队认为平均延迟和吞吐都改善，问题来自客户端主观感受。

证据链

  1. 客户端逐 Token gap 显示 P99 从 110ms 升到 760ms，平均 TPOT 变化很小。
  2. 服务端 Token 生成时间也出现同一时段尖峰，排除纯网络缓冲。
  3. 调度事件显示每次尖峰前都有大块长 Prompt prefill 插入。
  4. 按 ISL 分桶，长输入流量占比从 4% 升到 11%。
  5. 配置差异显示 chunked prefill 的 Token 预算在发布中被提高。

根因与修复

更大的 prefill chunk 提高了聚合吞吐，却让 decode 序列等待更久。调整 chunk 与调度权重后，以 gap P99、TTFT P99 和 Goodput 联合门禁。这个案例说明请求平均 TPOT 会平滑掉局部停顿，必须保留 gap 分布。

二十二、完整失败案例二：吞吐平台期被误判为容量安全

现象

开放负载从 20 RPS 加到 32 RPS，完成吞吐仍维持约 24 RPS，GPU 利用率接近 100%。团队据此把容量写成 24 RPS。数字为构造数据。

证据链

  1. 到达率 20 RPS 时 queue P99 为 180ms；24 RPS 时为 900ms；28 RPS 时升到 8s。
  2. 负载生成器在途请求持续增长，测试末尾仍有大量未完成。
  3. 报表只用完成请求计算延迟，遗漏窗口结束时仍排队的删失样本。
  4. 客户端 10s timeout 后取消，但服务端没有及时传播取消，仍继续生成。
  5. 账面完成 throughput 平台掩盖队列不稳定和浪费 Token。

根因与修复

24 RPS 接近服务极限，不是满足 SLO 的容量；结果还存在协调遗漏。修复后报告到达、完成、超时、取消、未决队列和 Goodput，稳定容量取 queue 不发散且 P99 达标的负载级，并给单副本故障留余量。

二十三、完整失败案例三：KV 使用率不高却频繁抢占

现象

监控显示 KV usage 平均只有 72%，但高峰期 TTFT 尾部恶化并出现 preemption。数字为构造数据。

证据链

  1. 平均值按 1 分钟聚合，瞬时使用率多次达到 98%。
  2. 长输出请求在峰值前集中进入，KV Token 生命周期显著变长。
  3. 可用块指标呈锯齿，尾块浪费和保留块未包含在粗粒度 usage 中。
  4. 抢占后重算 Token 增加，prefill 指标被二次工作抬高。
  5. 按请求最大长度预留的 admission 估算与实际块分配策略不一致。

根因与修复

粗粒度平均 KV 百分比无法表达瞬时块压力和碎片。增加可用块、已用 Token、尾部浪费、抢占原因与重算 Token，按真实联合长度分布重新设置并发和安全余量。

二十四、完整失败案例四：投机解码单请求更快，线上 Goodput 更低

现象

并发 1 的微基准中 ITL 降低 28%，上线影子流量却使目标负载 Goodput 降低 9%。数字为构造数据。

证据链

  1. 低并发接受率较高，draft 开销能被一次验证接受的多个 Token 摊薄。
  2. 高并发下 verifier 已计算饱和，proposer 争用资源，batch 每步耗时增加。
  3. 额外模型占用显存，KV 可用容量下降，queue 和抢占上升。
  4. 线上任务采样参数与微基准不同，接受率更低。
  5. 只看成功请求 ITL，没有纳入超时和排队，导致上线前判断失真。

根因与修复

把投机策略按模型、采样参数、OSL 与负载级做矩阵，在目标开放负载下比较 Goodput，而不是采用单请求倍率。高负载自动关闭策略需要迟滞和回归测试，避免频繁切换。

二十五、完整失败案例五：量化版“更快”来自输出提前结束

现象

量化后 E2E 降低 18%，输出 tokens/s 略升，成本也下降。人工抽样发现答案缺段。数字为构造数据。

证据链

  1. OSL P50 从 240 降到 168，EOS 比例增加。
  2. 相同输入的业务后置条件通过率下降。
  3. 结构化 Schema 仍全部合法，因此原门禁没有报警。
  4. 数值与长文切片退化最明显，整体平均质量下降较小。
  5. 性能报告固定 max_tokens，却未对实际 OSL 与停止原因做等价检查。

根因与修复

性能收益部分来自生成更少，不是纯执行加速。恢复质量基线，增加输出长度、停止原因和关键切片门禁。Schema 合法只证明形状，不能证明业务内容完整。

二十六、完整失败案例六：TTFT 突增被错误归因到模型

现象

客户端 TTFT P99 从 1.1s 升到 4.8s，而服务端 engine TTFT 变化不大。数字为构造数据。

证据链

  1. 网关首字节延迟增加，服务端首 Token 时间稳定。
  2. 某代理升级后默认缓冲流式响应，达到一定字节才刷新。
  3. 客户端记录的首事件其实是累计多个 Token 的数据块。
  4. 直接连接服务端时 TTFT 恢复，经过代理时复现。
  5. HTTP 200 和服务端 GPU 指标始终正常。

根因与修复

代理缓冲破坏流式体验。修复刷新配置，并保留服务端生成与客户端接收双时钟。这个案例说明模型正常、协议成功仍可能有严重用户性能故障。

二十八、指标看板与告警口径

1. 流量与结果

  • 到达 RPS、admitted、rejected、completed、cancelled、timed out
  • input/output/generated-but-not-delivered Token rate
  • 完成吞吐、Goodput、质量失败与安全失败
  • 在途请求、队列长度、队列年龄和恢复时间

2. 延迟

  • client TTFT、engine TTFT、queue、prefill、first step
  • request mean ITL、gap P99、最大 gap、E2E content、E2E protocol
  • 按 ISL/OSL、缓存、任务、租户、worker 与状态切片

3. 调度与 KV

  • running/waiting 序列、每步 batch sequences/tokens
  • prefill/decode Token 预算与 chunk 分布
  • KV usage、可用块、有效 Token、尾部浪费、eviction
  • preemption、swap、recompute 与等待原因

4. 设备与运行时

  • GPU 利用、显存、功耗、时钟、温度、ECC
  • kernel 与通信时间、host-to-device、CPU、网络
  • worker 重启、OOM、allocator 和编译事件

5. 告警不要只盯绝对阈值

绝对 SLO 告警用于用户影响，变化告警用于提前发现容量趋势。例如 queue P95 连续增长、Goodput/完成吞吐比下降、KV 抢占从零出现，都可能早于 TTFT SLO 全面失败。告警窗口要带最低样本量，避免低流量分位数抖动。

二十九、基准报告必须回答的复现问题

读者应能从报告回答：

  1. 测的是哪个模型 revision、tokenizer、精度和最大上下文？
  2. 哪种硬件、多少设备、什么并行与互联？
  3. 服务引擎、容器、驱动与关键参数是什么？
  4. 客户端在哪里，网络路径和流式解析如何实现？
  5. 到达模型、并发、ISL/OSL、缓存局部性和采样参数是什么？
  6. TTFT/ITL/E2E 的事件、空帧、单 Token 与分母怎样定义？
  7. warmup 删除了什么，稳态怎样判断？
  8. 超时、取消、重试、未决请求和失败 Token 怎样统计？
  9. 质量与业务验收怎样进入 Goodput？
  10. 原始数据、分析代码、环境 manifest 和重复运行结果在哪里？

缺一项不一定让数据完全无效，但必须限制结论范围。没有真实 OSL 分布的测试可以比较 kernel 微性能，不能直接用于线上容量。

优化边界

  • 权重/KV 量化绑定具体格式、backend、硬件和校准集
  • 量化前后运行相同质量与风险切片
  • 投机解码记录接受率、额外成本和目标负载 Goodput
  • 前缀缓存按复用 Token 而非只按请求命中率评估
  • 优化没有通过缩短输出或改变停止条件伪造收益
  • 组合优化经过独立回归，不从单项收益相乘估算

Warmup 与复现

  • cold start、warm steady state 和 soak 分开报告
  • warmup 结束由资源和阶段稳定性判定
  • 模型、tokenizer、引擎、容器和配置有摘要
  • 硬件、驱动、功耗、并行与互联有记录
  • 工作负载、随机种子、原始事件和分析代码可回放
  • 多次运行的方差和异常排除原因已披露

质量与失败

  • Goodput 同时要求协议、完整性、时延、质量与业务后置条件
  • HTTP 200、Schema、相似度和模型置信度未被当作业务正确保证
  • 重试 attempt、取消后生成和未决请求没有被隐藏
  • queue、prefill、decode、KV、网络与观测故障已注入
  • 组合故障与恢复阶段已演练
  • 指标缺失会报未知，不会自动补 0

三十一、总结

大模型推理性能不是一个延迟数字，也不是一个最大 Token 吞吐。它是一组受工作负载、调度、内存、质量和测量边界共同约束的系统行为。

完整方法可以收敛为九步：

  1. 用客户端与服务端事件建立统一时间线，精确定义 queue、prefill、decode、TTFT、TPOT/ITL 和 E2E。
  2. 把单请求输出速度、聚合 output tokens/s、total tokens/s 与 requests/s 分开。
  3. 分别使用开放到达率、闭环并发与生产 Trace，避免负载模型自节流或失真。
  4. 用 ISL/OSL 联合分布、实际停止原因和缓存局部性表达真实工作量。
  5. 观察连续批处理中 prefill 与 decode 的干扰，而不是把 batch size 当成常数。
  6. 以有效 KV Token、块、碎片、抢占和生命周期分析容量；把 PagedAttention 的论文结果限定在原实验。
  7. 对量化、投机解码和前缀缓存同时做性能、质量和边界验证。
  8. 通过 warmup、重复运行、环境指纹、原始事件和自动化公式测试保证可解释与可复现。
  9. 用满足尾延迟、完整性、质量和业务后置条件的 Goodput 找到饱和拐点之前的可交付区间。

最终应能回答的不是“这台机器最快能吐多少 Token”，而是：

在可复现的真实负载下，当请求长度、并发和缓存状态变化时，系统能在质量底线与尾延迟预算内持续完成多少业务任务；一旦超过容量，证据能否明确指出时间花在排队、prefill、decode、网络还是 KV 资源上。
