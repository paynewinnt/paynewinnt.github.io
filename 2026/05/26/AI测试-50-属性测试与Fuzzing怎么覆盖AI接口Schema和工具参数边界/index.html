AI测试-50-属性测试与Fuzzing怎么覆盖AI接口Schema和工具参数边界

发表于 2026-05-26 分类于 AI测试 本文字数： 23k 阅读时长 ≈ 1:24

给 AI 接口准备二十个手写 JSON 样例，全部返回 200，能不能说明工具参数链路足够健壮？

不能。二十个样例可能只覆盖了同一个正常模板：字段齐全、类型正确、金额居中、状态顺序合理、依赖永不超时。真实链路却要面对缺字段与多字段、整数与布尔值的语言差异、Unicode 与长度边界、相互依赖字段、并发状态变化、流式响应截断、同一工具调用重放，以及“写入已经成功但响应丢失”这类最难处理的不确定结果。更麻烦的是，随机制造一团同时含十种错误的 JSON，虽然很容易让接口报错，却几乎不能说明究竟是哪条约束生效，也不能提供可修复的最小反例。

属性测试与 Fuzzing 的工程价值，不是“多发一些随机请求”，而是把下面这条链做成可重复、可归因、可预算的系统：

本文以“AI Agent 调用报价与退款工具”为贯穿场景，深入讨论 generator、shrinker、状态机、valid/invalid 输入、Schema 属性与业务属性、mutation fuzz、coverage-guided fuzz、资源预算、失败最小化和 corpus。所有订单、比例、阈值、时延、样本量与发布结果都是构造示例，仅用于说明测试口径，不代表任何企业、模型、框架或公开基准的实际表现。资料核对截止 2026-05-26。

一、本文不重复什么，也不讨论什么

《AI测试-04-LLM Function Calling在测试工具里怎么设计输入输出和容错》已经讨论工具注册、调用协议、输入输出、错误分类与一般容错；《AI测试-25-大模型结构化输出怎么用JSON Schema做约束校验和失败恢复》已经讨论结构化输出的分层校验、拒答、截断和恢复；《AI测试-40-合成数据怎么生成过滤并防止偏差污染和虚假覆盖》已经讨论合成数据血缘、独立验证、污染和名义覆盖；《AI测试-43-AI应用成本怎么拆Token缓存检索工具和单位任务预算》已经讨论单位任务成本与预算账本。

本文不重复上述文章里的通用工具协议、完整结构化输出恢复流程、评测集治理或成本分摊。本文只回答一个更窄的问题：

当 AI 接口接收或产生结构化参数，并通过工具改变状态时，怎样系统地产生边界输入与动作序列，怎样判断失败，怎样把复杂失败收缩成仍然有效且可修复的最小反例？

本文还明确排除以下范围：

  • 不把 Fuzzing 扩展成漏洞利用、绕过权限、窃取数据或破坏服务的教程；这里只讨论授权环境中的质量工程与健壮性验证。
  • 不向生产账户、真实支付、真实邮件、真实工单或真实外部系统发送随机写操作；写工具只能进入隔离沙箱、幂等执行器或模拟执行器。
  • 不把随机测试通过解释成形式化证明，也不把代码覆盖率解释成业务正确率。
  • 不把 mock 的结果解释成真实模型语义、真实供应商协议、完整 JSON Schema 实现、生产沙箱隔离或系统安全性的证明。
  • 不依赖模型自己给自己的工具参数打分来建立最终真值；模型评审可以提供线索，发布门禁仍需确定性校验、参考状态机、受控回放或人工复核证据。
  • 不提供无限流量压测方案。资源上限、停止条件、租户隔离和紧急终止是测试设计的一部分，不是跑完后再补的运维配置。

1.1 问题边界内的对象

本文所称“AI 接口”可以是：

  • 接收 JSON 请求并返回结构化模型结果的 HTTP 接口；
  • 接收模型生成的 Function Calling 参数并调用本地或远程工具的执行层；
  • 由多个工具动作组成、带状态和重试的 Agent 工作流；
  • 在模型前后包含解析、Schema 校验、业务校验、权限校验和幂等账本的应用链路。

被测对象不是只有模型。它至少包括序列化器、解析器、验证器、适配器、状态管理、重试器、执行器、结果映射和审计记录。模型可能产生输入，规则代码也可能产生输入；只要对象跨越了不可信边界，就需要同样的验证。

二、先把术语统一：样例、属性、生成、变异、覆盖与证明

2.1 Example-based test 与 property-based test

QuickCheck 的原始工作把属性写成可执行函数，并通过随机输入与自定义 generator 检验；它的核心启发不是某一种语言 API，而是“生成一类输入—执行性质—失败后给出反例”的分工。手写样例仍然重要：协议示例、历史事故、监管案例和可读的金丝雀都不该被随机生成替代。属性测试扩展的是输入空间和序列空间，不是取消样例测试。

2.2 Random testing 与 Fuzzing

本文把两者按反馈使用方式区分：

  • 随机属性测试：generator 按预先定义的分布产生输入，Oracle 判断属性，失败后 shrinker 最小化；覆盖信息可以记录，但不一定反向影响下一轮生成。
  • Fuzzing：持续变异 seed/corpus，并根据覆盖、新状态、响应差异或失败信号决定保留哪些样本、给哪些样本更多执行预算。

两者不是互斥工具。一个工程通常先用 Schema 感知的 generator 建立高有效率输入，再用 mutation 与覆盖反馈探索实现细节；发现失败后，使用保持语义的 shrinker，而不是只做字节删除。

2.3 Generator 与 Mutator

generator 从约束和随机源构造一个对象，知道字段类型、依赖关系和状态前缀。mutator 从已有 seed 出发做变化，可以知道结构，也可以只操作字节。对于 AI 工具参数，纯字节变异常把大部分预算浪费在 JSON 解析失败上；结构感知变异则能把更多预算投向深层业务和迁移逻辑。

2.4 Shrinker 与普通删减

Shrinker 的任务不是让 JSON 字节数越小越好，而是在某个偏序下寻找更简单、仍触发同一失败的反例。对状态机故障，简单度可能同时考虑：

  • 动作数更少；
  • 无关字段更少；
  • 字符串更短；
  • 数值更靠近语义边界；
  • 状态前缀更短；
  • 故障注入次数更少；
  • 依赖对象数量更少。

如果删掉“先报价”后，提交请求在迁移校验层就被拒绝，原本的“写后超时导致重复退款”已经不可达。这个结果更短，却不是同一个失败。正确的 shrinker 必须同时保持触发前置条件和失败谓词。

2.5 Coverage 是导航信号，不是正确性证明

AFL 系列的技术说明展示了以边覆盖和粗粒度命中计数识别新行为、维护输入队列、裁剪 corpus 和最小化输入的思路；Coverage Guided Property Based Testing 则把覆盖反馈引入属性测试的输入生成过程。迁移到 AI 接口时，需要把覆盖扩展成多维信号：

  • 代码边或分支；
  • JSON Schema 关键字的通过与失败结果；
  • 业务规则的命中、接受与拒绝；
  • 状态与状态转移；
  • 模型终态、工具选择、错误类别和恢复分支；
  • 资源桶，例如输入长度、工具次数、重试次数、时延与预算区间。

覆盖只回答“是否观察过某种路径或状态”，不回答“结果是否正确”，更不回答“生产分布中是否足够可靠”。

2.6 Oracle 是可执行判断，不等于唯一标准答案

Oracle 可以是：

  • 确定性 Schema 验证器；
  • 固定政策快照上的规则函数；
  • 参考状态机；
  • 执行前后数据库或沙箱状态的不变量；
  • 两种独立实现的差分结果；
  • 同一输入变换前后的 metamorphic relation；
  • 对高风险歧义样本的人工裁决。

模型打分可以作为弱 Oracle 或排队信号，但不能独自证明工具参数可执行、金额正确、权限合法或副作用只发生一次。

三、分层架构与数据流：每一层只回答自己的问题

上图把系统分成五个执行阶段和四个反馈资产。关键不是组件名字，而是信息不能被过早压扁。

3.1 契约注册层

契约注册层保存：

  • 原始 JSON Schema、规范方言和解析后的规范化表示；
  • 业务规则版本、有效期、地区、租户和政策快照；
  • 参考状态机的状态、动作、前置条件、后置条件与禁止边；
  • 工具副作用等级、是否支持 dry-run、幂等键语义和补偿能力；
  • 每条属性的适用输入域、失败签名和严重度；
  • provider/model/adapter 的能力画像，例如是否支持并行工具调用、工具结果关联和严格结构化输出。

Schema 文件哈希、业务快照 ID 和状态机版本必须进入每次运行记录。否则同一个 seed 下周失败时，无法区分是实现变化、契约变化还是生成器漂移。

3.2 生成与调度层

调度器先选择测试族，再选择 seed 和变异策略，而不是先随机造 JSON 再猜它属于哪类：

3.3 三层验证与分类层

验证顺序固定为 Schema、业务、迁移。每层都输出结构化结果，而不是抛出一个统一异常：

NOT_RUN 与 PASS 必须分开。上游失败后跳过下游，不意味着下游已经验证通过。Invalid 生成器的质量也从这里判断：目标是单个 minimum 失败，却同时触发 required 和 type，就应该把样本标成“多缺陷/不可归因”，而不是混入单缺陷指标。

3.4 沙箱执行层

只有满足当前测试族执行条件的样本才能进入执行器。写工具至少采用以下一种边界：

  1. 模拟执行器：状态完全在内存或临时数据库中，适合每次提交的高频属性测试；
  2. 幂等沙箱执行器：指向独立租户、独立凭据、可清理数据，并用幂等键和配额限制真实协议路径；
  3. dry-run 执行器：服务端计算权限与计划但不提交写入，前提是 dry-run 与真实提交共享足够多的验证路径；
  4. 可补偿执行器：仅用于补偿语义经过单独验证、风险可接受的动作，不能把“有补偿接口”误当成任意副作用都可逆。

生产凭据、真实收件人、真实支付工具和不可逆动作不在 Fuzzing 范围。沙箱仍要有网络出口白名单、租户配额、时间上限和全局 kill switch。

3.5 Oracle 与证据层

五、Schema 契约：完整示例与可测属性

下面的 Schema 是贯穿本文的工具参数契约，使用 JSON Schema Draft 2020-12。它故意只表达结构约束；可退余额、订单状态、权限和报价绑定关系留给业务规则与状态机。

5.1 Schema 属性不是“拿几个 JSON 跑 validator”

至少应为每个适用关键字建立正反属性：

JSON Schema Draft 2020-12 的 integer 按数值的数学性质判断，而不是按 JSON 文本有没有小数点判断。因此 1 与 1.0 都满足 integer；JSON 的 true 不满足，非有限浮点数也不是合法 JSON 数值。若传输适配器业务上只接受无小数点的词法形式，那是 Schema 之外的额外契约，必须另行命名和测试，不能冒充 type: integer 的规范语义。

关键字或组合 正向属性 单缺陷反例 必须记录
required 所有必填字段存在 只删除一个必填字段 缺失字段、实例路径、无工具调用
type 字段 JSON 类型正确 只替换一个字段类型 注意 JSON true 不应被当整数
enum/const 值来自允许集合 使用不在集合中的近似值 实际值与 Schema 版本
minimum/maximum 值含边界并在闭区间 min-1 或 max+1 边界来源与数值表示
minLength/maxLength 按 Unicode 字符长度满足 空串或超一字符 库的长度语义与规范方言
pattern 正则匹配 改一个字符破坏格式 正则实现与 Unicode 行为
additionalProperties/unevaluatedProperties 只出现被求值字段 增加一个未知字段 被拒字段与组合分支
if/then commit 带 quote_id commit 只缺 quote_id 触发分支和失败关键字

JSON Schema 2020-12 将 format 的 annotation 与 assertion 词汇区分开。工程上不能看到 Schema 写了 format 就假定所有验证器都用相同方式拒绝实例；必须固定方言、词汇支持、实现版本和 format 策略，并用 conformance 样例验证实际行为。

5.2 JSON 语法边界与 Schema 边界分开

RFC 8259 定义 JSON 文本及对象、数组、数字、字符串和字面值。Fuzz 计划应把“传输字节无法解析”与“可解析 JSON 违反 Schema”分成不同测试族：

  • 语法无效：截断字符串、无效转义、尾随内容、错误编码边界；预期停在解析层；
  • 语法有效但 Schema 无效：字段缺失、类型错误、枚举越界、未知字段；预期停在 Schema 层；
  • Schema 有效但更深层无效：业务或状态反例；预期解析与 Schema 都通过。

如果三类混跑，解析错误数量很容易淹没真正重要的深层失败。

5.3 OpenAPI 3.1 不等于任意 JSON Schema 文档可无损搬运

OpenAPI 3.1 的 Schema Object 使用其指定的 JSON Schema 方言并包含 OpenAPI Base Vocabulary。测试平台若从 OpenAPI 文档提取工具参数，必须记录 OpenAPI 版本、方言、引用解析、只读/只写语义、媒体类型和参数序列化方式。不能只复制 properties，丢掉 $ref、组合关键字或请求体编码后再声称“按原契约生成”。

7.1 生成器的三层组合

一个实用生成器可以拆成：

Schema generator 不该通过“随机 JSON，直到 validator 接受”的拒绝采样作为唯一策略。约束变窄时，接受率可能极低，预算不可控；更重要的是，它不知道为什么某些业务状态永远生成不到。优先从约束直接构造，再用独立 validator 复核。

随机分布要混合典型值、边界值和广域值：

7.3 从 Schema 生成 valid 对象

以报价为例，生成顺序应遵守依赖：

  1. 选择或创建一个业务订单快照；
  2. 选择当前主体及其允许动作；
  3. 从订单货币派生 currency；
  4. 在 1..refundable_balance 之间生成金额；
  5. 生成满足长度和模式的 request_id、idempotency_key；
  6. 若 action 是 quote_refund，不生成 quote_id；
  7. 若 action 是 commit_refund，先由状态前缀产生与金额绑定的 quote_id；
  8. 独立运行 Schema、业务和迁移验证器，验证实际向量为 (T,T,T)。

第 8 步是对 generator 的测试，不是多余成本。Generator 自己的逻辑可能误读 Schema、忘记新关键字或引用旧业务规则。

7.4 Invalid 尽量只制造一个缺陷

单缺陷生成采用“先构造全有效对象，再做一次定向变异，再独立确认”的模式：

常见单缺陷操作包括：

  • 删除一个 required 字段；

  • 把枚举值改成一个未注册但视觉相近的值；
  • 设为 minimum-1 或 maximum+1；
  • 增加一个未知属性；
  • 对条件分支只删除其新增必填字段；
  • 在数组中只制造一个重复、越界或错误类型元素。

“尽量单缺陷”不是声称任何 Schema 组合都能轻易得到唯一错误。oneOf、allOf、unevaluatedProperties 和级联条件可能让一个改动产生多个验证报告。此时要保留目标变异 ID，并把实际失败集合完整记录；若无法唯一归因，就进入多缺陷探索池，不纳入单缺陷拒绝率。

  • 第一次提交到达写入点；

  • 最终仍观察到重复写入或违反 at-most-once 属性。

8.3 分层收缩顺序

一个稳健顺序是：

  1. 序列级：删除不影响触发的动作块，做 delta debugging；
  2. 实体级：删除无关订单、用户、工具返回和 metadata；
  3. 结构级：删除非 required 字段、数组元素和可选分支；
  4. 关联级：同步简化 request/quote/commit 中共享的 ID 与金额；
  5. 值级：整数向 0、最小值、边界和简单代表值移动；字符串向最短合法形式移动；
  6. 故障级：减少故障次数、缩小故障范围、把触发时点移向最直接位置；
  7. 环境级：减少 worker、并发动作和外部对象，但保留竞态 happens-before 关系。

每一步都重新执行目标属性。不能先用静态规则把整个对象“优化完”再只跑一次，否则不知道是哪一步改变了根因。

8.4 Valid 与 Invalid 使用不同 shrinker

对于全有效测试发现的深层实现失败，shrinker 要保持 (T,T,T)；对于 Schema 单缺陷测试，要保持同一个目标关键字失败且不进入执行器；对于业务反例，要保持 schema=T 与同一 business_rule_id 失败；对于迁移反例，要保持目标边之前的前缀有效和同一非法边。

这也是为什么一个通用 JSON 删除器不够。它不知道 quote_id 与 amount 的绑定，不知道余额快照，也不知道删除哪一步会让深层路径不可达。

真实模型或并发系统的失败可能不稳定。可采用顺序复核：

9.4 长序列与状态空间爆炸

如果每个状态有 8 个动作、每个动作有 10 组参数，长度 12 的穷举不可行。工程上结合：

  • 状态/边覆盖权重：优先尚未观察的边；
  • 历史失败邻域：在触发序列附近插入、删除、交换动作；
  • size 参数：早期短序列，后期逐渐增加长度和实体数；
  • 等价归并：只保留产生新状态摘要或新属性结果的序列；
  • 风险优先：写后超时、重试、取消与并发版本变化得到更多预算；
  • 有界并发调度：显式枚举少量关键 interleaving，而不是依赖线程随机性碰运气。

十、Mutation Fuzz：变什么，以及怎样知道变异有价值

10.1 字节级变异适合最外层解析器

对 HTTP body、JSON 解码、流分帧和压缩边界，字节级变异仍然有用：

  • 截断不同字节位置；
  • 翻转引号、反斜杠、UTF-8 多字节序列；
  • 插入或删除分隔符；
  • 重复消息帧、打乱 chunk 边界；
  • 在资源上限附近扩张输入。

预期 Oracle 是“不崩溃、不无限占用、不越过解析层、不留下副作用、返回已分类错误”。这类测试不应直接复用深层业务通过率作为指标。

10.2 结构级变异负责 Schema 边界

JSON AST 上的 mutator 可以：

  • 删除、复制、重命名一个属性；
  • 在整数、字符串、布尔、null 之间替换类型；
  • 对数字做 ±1、符号翻转和边界替换；
  • 对字符串做空串、最大长度、Unicode 类别替换；
  • 在组合分支间切换 discriminator 或 action；
  • 对数组删除、复制、交换元素；
  • 增加一个未知属性。

每次单缺陷轮只应用一个 operator。探索轮可以叠加 mutation，但必须记录 operator 栈，并在发现失败后尝试拆成单变异复现。

10.3 语义级变异负责业务关系

语义 mutator 需要领域模型：

  • amount = balance 改成 balance+1；
  • 保持格式但换成其他订单的 quote_id；
  • 保持 action 不变，改变主体权限；
  • 将时间移到有效期前一毫秒、边界时刻、后一毫秒；
  • 在货币与订单之间制造单一不一致；
  • 保持总金额不变，拆分或合并行项目；
  • 生成语义等价但字段顺序、空白或 metadata 不同的请求。

这类变异的目标不是“更随机”，而是围绕业务谓词的决策边界形成成对样本。

10.4 序列级变异负责状态边

序列 mutator 包括：

  • 删除一个动作；
  • 重复一个动作；
  • 交换相邻动作；
  • 把一个动作移到状态前缀之前；
  • 更换一个关联 ID；
  • 在成功与响应之间插入超时；
  • 在读取快照与提交之间插入另一主体的更新；
  • 将同一动作改用相同或不同幂等键重放。

对每个 operator 标明预期 validity 向量。比如“删除 quote”预期只让 transition 失败；如果同时让 commit 缺 quote_id，则变异器还应生成一个格式合法但无对应实体的 quote_id，确保 Schema 仍通过。

10.5 Mutation testing 与 mutation fuzz 不要混淆

Mutation fuzz 改输入以探索被测系统；mutation testing 改程序或规则实现，检查测试能否杀死错误版本。二者可以组合：

11.2 Coverage Guided Property Based Testing 的可迁移思想

Coverage Guided Property Based Testing 的原始研究把程序覆盖反馈与属性测试结合，使 generator 能从执行反馈中探索更多行为。应用到 AI 接口时，应该保留属性测试的两个核心约束：

  1. 输入仍有明确生成域和可执行属性，不是覆盖越高就越正确；
  2. 失败后仍由语义 shrinker 最小化，而不是只追求相同覆盖位图。

对于黑盒模型 API，没有进程内代码边时，可以使用可观察的代理覆盖：适配器分支、校验规则、工具选择、状态边、错误类别、重试决策、响应终态和资源桶。但这些是测试导航信号，不应声称等价于模型内部神经路径覆盖。

11.3 TensorFuzz 能说明什么，不能说明什么

TensorFuzz 的原始工作研究了用覆盖导向 Fuzzing 调试神经网络，并通过近似新颖性判断保留输入。它启发我们把“行为新颖”用于神经系统测试，但不能直接推出某个 LLM 工具调用系统的业务正确性。神经激活距离、输出嵌入距离或文本差异可以帮助寻找新样本，最终仍要回到 Schema、业务规则、状态机和副作用 Oracle。

11.4 Corpus 调度与能量

每个 corpus entry 的执行能量可以依据：

  • 高风险写动作和历史事故提高权重；
  • 已被大量相似样本覆盖的新颖度随时间衰减；
  • 长期不产生新信号的 seed 降权但不一定删除；
  • 执行极慢的 seed 进入专门队列，避免拖垮快速循环；
  • 受保护的事故样本即使不新颖，也固定进入回归套件。

11.5 防止覆盖作弊

常见虚假增长包括：

  • 每个随机错误消息被当作新路径；
  • request_id、时间戳或 quote_id 进入覆盖哈希；
  • 相同业务状态因字段顺序不同被当作新状态；
  • 重试次数增加让事件数增长，却没有新决策；
  • mock 中的分支被计入生产实现覆盖；
  • 同一 Schema 错误在不同实例路径无限膨胀。

应先规范化动态字段，按稳定语义构造 coverage key，并分别报告“名义事件数量”和“去重语义覆盖”。

12.4 Metamorphic properties

当没有单一标准答案时，可以验证输入变换关系：

  • JSON 对象属性顺序变化，不应改变工具参数语义；
  • 增加允许的无关 metadata，不应改变退款金额和动作；
  • 同一请求用相同幂等键重放，不应增加物理写入；
  • 对只读报价，重复调用的业务结论在快照不变时应相同；
  • 在允许精确表达的情况下，把金额从 x 增到 x+1，不得让返回金额反而降低且仍声称同一 quote；
  • 请求规范化前后，签名、路由和验证结果应符合约定关系；
  • 将一个不影响业务的自然语言说明做等义改写，不应改变确定性业务规则结果。

最后一条若经过模型解释层，只能检验系统定义的稳定关系，不能假设自然语言等义由模型自动保证。需要人工或独立数据确认变换确实保持语义。

13.1 工具分级

13.2 幂等属性

对支持幂等的写工具，至少检查：

幂等账本需要跨“写入已提交、响应未返回”的故障点。只在客户端缓存成功响应，无法处理第一次结果丢失。

13.3 模拟执行器要测试什么

模拟器至少保留真实接口的重要语义：状态边、关联 ID、幂等键、错误分类、调用账本和故障时点。一个永远返回固定成功 JSON 的 mock 只能证明测试代码会解析固定 JSON，不能证明状态机或恢复策略。

同时必须明确：即使模拟器很细致，也不能证明真实模型会产生相同工具选择，不能证明供应商流式协议完全一致，不能证明生产 IAM、网络和数据隔离有效，更不能证明系统安全。它是高频质量反馈层，不是生产认证替代品。

13.4 Sandbox 的最小控制面

  • 独立 tenant/project/account；
  • 最小权限测试凭据与短生命周期；
  • 网络出口 allowlist；
  • 每 case 或每 worker 独立命名空间；
  • 物理写入总量、金额、工具次数与并发硬上限；
  • 全局超时、熔断与 kill switch；
  • 测试数据标记、到期清理和泄漏扫描；
  • 完整 side-effect ledger；
  • 禁止将模型生成值直接用作目标 URL、收件人或生产资源 ID；
  • 测试结束后验证“应清理对象已清理、保留证据仍可审计”。

十四、Corpus：失败资产、探索种子和事故证据不能混成一个目录

14.1 五类 corpus

  1. handwritten seeds：协议最小合法对象和关键人工边界；
  2. coverage corpus：曾带来新代码边、规则、状态或错误类别的输入；
  3. failure corpus：经过收缩且能稳定复现属性失败的最小反例；
  4. incident corpus：来自真实事故的脱敏、授权回放与其合成邻域；
  5. canary corpus：每次发布前固定执行、结果易读的少量样本。

分类影响保留策略。Coverage entry 可以在等价覆盖下被更小更快的样本替代；事故条目和人工 seed 应受保护，不能因当前代码覆盖重复而删除，因为它们承载业务与历史证据。

14.2 去重键不能只用 JSON 哈希

建议分三层：

两个 JSON 规范化后相同但故障时序不同，不能合并；两个字符串不同但触发相同状态边，也不一定都值得长期保留。Corpus culling 是有约束的集合覆盖问题：尽量用更小、更快的条目覆盖全部受保护语义信号，同时保留多样性和历史来源。

14.3 版本适用性

Schema 改版后，旧反例可能从 schema-invalid 变成 schema-valid，或反过来。不要直接删掉“过期”条目，应记录：

  • 首次发现时的契约；
  • 当前重放的实际 validity 向量；
  • 适用版本范围；
  • 是已修复、契约接受、重复、无法复现还是环境退役；
  • 若被替代，新条目的链接与等价依据。

14.4 Corpus 污染与敏感数据

事故输入进入 corpus 前要做授权、最小化和敏感字段处理。不可把生产 Prompt、访问令牌、真实姓名、真实地址或工具响应原样提交到仓库。哈希也不自动消除敏感性；低熵标识可被猜测。必要时只保存可合成重建的结构与安全占位符，把受限原件放到有访问控制和保留期的证据存储。

15.3 Size schedule

属性测试中的 size 是复杂度控制信号，可以映射到：

  • JSON 深度和数组长度；
  • 字符串长度；
  • 状态机动作数；
  • 同时存在的订单或工具数；
  • 故障事件数量；
  • 并发 schedule 数量。

15.4 停止条件

可组合以下条件：

  • 时间或执行次数耗尽；
  • 新覆盖/新状态在连续窗口内低于阈值；
  • 发现 blocker 属性失败，立即停止发布门禁但继续最小化；
  • 基础设施错误率过高，停止以免污染结果；
  • 沙箱写量、成本或未清理对象达到硬上限；
  • 目标 Schema 关键字、业务规则与状态边已达到预定覆盖；
  • 所有受保护 corpus 条目已在当前版本稳定重放。

“24 小时无崩溃”只有在记录了执行量、有效输入率、覆盖停滞、资源分布和 Oracle 范围时才有意义。

21.1 先问证据是否可用

二十二、属性目录：从 Schema 到资源不变量

下面给出可直接改写成项目属性注册表的目录。

22.1 输入与解析

  • 任意输入在 case 时间与内存上限内得到成功或已分类失败，不使 worker 崩溃；
  • 不完整 JSON 不得进入 Schema、业务和执行层；
  • 单个完整 JSON 后的尾随内容按协议明确拒绝或分帧，不静默忽略；
  • 请求规范化不能改变数值、Unicode 字符和字段语义；
  • 超过大小/深度上限的输入在分配不可控资源前被拒绝；
  • 解析失败不产生工具副作用。

22.2 Schema

  • 每个 required 字段缺失都能被定位；
  • 每个字段错误类型都被拒绝，bool/int 等宿主语言细节不绕过契约；
  • minimum/maximum 和长度边界正反成对覆盖；
  • enum 只接受注册值，不做未声明大小写或空白修复；
  • 未知字段策略与组合关键字一致；
  • 条件分支在 action 切换时正确要求或禁止 quote_id；
  • validator 配置失败与实例无效分开；
  • Schema invalid 永不触发工具执行。

22.3 业务

  • 金额不超过冻结快照中的可退余额；
  • 币种与订单一致；
  • 主体、租户、区域和动作权限全部满足；
  • 业务拒绝带稳定 rule ID，不靠自由文本分类；
  • 同一快照下，语义等价请求得到相同业务结论；
  • 快照变化后重新验证，不复用过期 verdict；
  • 业务 invalid 保持 Schema valid，保证拒绝层可归因。

22.4 状态与序列

  • 只有允许边能改变状态；
  • 非法边拒绝且 state hash 不变；
  • quote 与 commit 的订单、金额、币种和主体绑定；
  • quote 过期、取消或替换后旧 ID 不可提交；
  • 同 key 同请求重放不产生新效果；
  • 同 key 不同请求明确冲突；
  • 写后超时恢复不重复写；
  • 最终响应与 side-effect ledger 一致；
  • shrinker 不删除目标深层失败所需的状态前缀。

22.5 模型与工具编排

  • 模型自然语言声称“已执行”不能替代工具结果；
  • 不存在、禁用或未授权工具不能被执行；
  • 多工具调用的 call ID 与 result ID 完整关联；
  • 参数在本地三层验证通过前不进入写执行器；
  • 拒答、截断、内容过滤和超时不会被包装成合法业务结果；
  • 重试不会偷偷改变幂等键、主体或目标资源；
  • 模型输出变化不影响确定性权限与金额规则。

22.6 资源与审计

  • 单 case 的 Token、动作、时长、写量和响应大小均受硬上限；
  • 停止或取消后不再启动新副作用；
  • 每个 attempt 单独记录，失败成本不被成功重试覆盖；
  • seed、生成路径、契约快照和故障计划足以重放；
  • observation、inference、decision 不互相覆盖；
  • 敏感输入按分类存储，普通 corpus 不包含真实秘密；
  • campaign 停止后沙箱对象数量回到允许基线。

二十三、常见错误与对应反例

23.1 “Schema 由模型供应商保证，所以本地不用测”

反例：拒答、截断、适配器反序列化、SDK 版本和工具结果映射发生在不同边界；即使提供商在某个模式下约束输出，本地系统仍要处理非正常终态和业务规则。更重要的是，Schema 不知道余额、权限和当前状态。

23.2 “Invalid 越乱，鲁棒性越强”

反例：一个对象同时缺字段、类型错误、超长、枚举错误并带未知字段，永远在第一道校验失败，无法证明后面的错误都能正确分类。先做单缺陷归因，再用多缺陷探索检查错误聚合和资源上限。

23.3 “Shrinker 只要还能失败就对”

反例：深层重复退款被缩成 JSON 解析异常，虽然仍失败，修复方向完全不同。保持同一属性、阶段、状态前置和副作用谓词。

23.4 “覆盖率增长就是模型质量增长”

反例：随机 request_id、自然语言错误消息和时间戳让外部行为哈希不断变化，业务规则与状态边没有新增。覆盖是调度信号，业务 Oracle 决定正确性。

23.5 “Mock 通过就可以开生产写工具”

反例：mock 没有 IAM、网络、事务、供应商流、真实幂等实现和并发时序。Mock 适合高频逻辑反馈，发布前仍需授权沙箱协议验证和独立生产控制审查。

23.6 “相同 seed 就一定可复现”

反例：generator 版本、Schema、corpus 顺序、Python 版本、模型版本和并发调度变化都会改变结果。保存规范化输入、动作序列、快照、版本与 fault schedule，seed 只是来源证据之一。

23.7 “Fuzz 一直跑，总会覆盖边界”

反例：均匀随机整数很少命中精确业务边界，纯字节变异大多停在解析器，长慢 seed 吞掉预算。边界池、结构/语义 mutator、覆盖反馈和预算调度缺一不可。

23.8 “错误率低于阈值就能发布”

反例：一百万个只读成功无法抵消一个可稳定复现的重复扣款。严重度、不变量、暴露范围和可关闭能力优先于总体失败比例。

二十四、可执行清单

A. 契约与边界

  • 固定 JSON Schema 方言、原文哈希、引用解析和 validator 配置。
  • 明确解析有效、schema-valid、business-valid、transition-valid 的定义。
  • 为每层定义 PASS、FAIL、NOT_RUN、NOT_APPLICABLE、UNKNOWN。
  • 业务规则使用稳定 rule_id 和版本化快照。
  • 状态机列出状态、允许边、guard、后置条件与非法边。
  • 工具按只读、可控写、外部通知、不可逆动作分级。
  • 明确本文/本轮不验证的模型语义、生产环境与安全边界。

B. Generator

  • valid generator 从约束构造，不只靠无限拒绝采样。
  • 整数、长度、数组和状态序列都有边界池。
  • 随机权重、size schedule 与 generation path 可记录。
  • 用独立 validator 检查 generator 实际有效性向量。
  • schema-invalid 从全有效对象只做一次定向变异。
  • business-invalid 保持 Schema valid 且只违反一个规则。
  • transition-invalid 保持目标边之前的前缀有效。
  • 无法构造唯一缺陷时显式进入多缺陷池，不伪装可归因。

C. Mutation 与 coverage guidance

  • 分开字节级、结构级、语义级和序列级 mutator。
  • 每次变异记录 operator、parent 与目标 validity。
  • 代码、Schema、业务、状态、Oracle、错误和资源覆盖分维度报告。
  • coverage key 去除 request_id、时间戳和随机文案。
  • 新颖度只影响保留与预算，不替代属性 Oracle。
  • 高风险状态与事故邻域有最低预算，不被便宜 seed 饿死。
  • coverage instrumentation 失败时结果标 UNKNOWN。

D. 状态、故障与副作用

  • 参考状态机独立于生产实现的关键函数。
  • 每个 command 有 precondition、参数生成、执行、后置和 shrink 逻辑。
  • 写工具只进入 mock、隔离沙箱、dry-run 或已批准可补偿环境。
  • 同 key 同请求、同 key 不同请求、不同 key 同请求分别测试。
  • 写前、写后、响应截断和客户端崩溃时点分别注入。
  • Side-effect ledger 能证明物理写入次数与顺序。
  • 网络出口、目标资源、金额、次数、并发和总时长有硬上限。
  • 全局 kill switch 和测试后清理验证已演练。

E. Shrinker 与失败证据

  • 失败前先冻结 property、class、stage 与副作用谓词。
  • Shrinker 同时保持生成目标、触发前置和失败谓词。
  • 关联字段同步收缩，不制造无关 guard 失败。
  • 收缩候选逐个重放，记录接受/拒绝原因。
  • 非确定性失败使用有界重复与明确接受规则。
  • 报告 operator set、执行预算和停止原因，不夸称全局最小。
  • 原始反例、最小反例和 shrink trace 都保留内容寻址证据。

F. Corpus

  • 手写 seed、coverage、failure、incident、canary 分类管理。
  • 事故与人工条目标记 protected。
  • 同时保留 byte、canonical、semantic 去重视角。
  • Culling 保持目标语义覆盖并考虑执行成本与多样性。
  • 每个条目标明适用契约范围、来源、保留理由和最近重放。
  • 生产事故数据经过授权、最小化和敏感信息处理。
  • Schema 改版后重新分类 validity，不静默删除旧反例。

G. 指标、自动化与发布

  • 分别报告生成目标命中率、单缺陷归因率和深层执行率。
  • 属性失败率排除 NOT_APPLICABLE，并单列 UNKNOWN。
  • 覆盖率只对已知有限目标集给百分比。
  • Shrink 报告前后动作、字段、字节、复现率和成本。
  • 每次提交固定 seed；每日多 seed；长跑 coverage-guided。
  • 所有受保护最小反例进入发布候选回归。
  • 发布报告分开 observation、inference、decision。
  • 写出已验证范围、未验证范围、补偿控制和回滚条件。
  • Blocker 不变量按严重度阻断，不被总体成功率稀释。
  • 失败 campaign 不自动访问生产、不自动扩大权限、不自动创建外部工单或执行不可逆操作。

二十五、最后的判断框架

把 AI 接口做成“能返回 JSON”并不难，难的是证明它在广阔输入空间和状态空间里仍守住边界。属性测试与 Fuzzing 真正带来的不是随机性，而是四种工程纪律：

  1. 输入域有名字。 schema-valid、business-valid、transition-valid 分开，invalid 知道自己故意破坏哪一层。
  2. 失败有谓词。 不以“抛了异常”为结束，而是固定属性、阶段、状态和副作用，再做保持型收缩。
  3. 探索有预算。 coverage、corpus 和 mutation 把资源导向新行为，同时接受覆盖不等于正确。
  4. 证据有边界。 Mock、固定 seed、Schema 和随机通过各自只能证明有限事实；观测、推断与发布决策分开保存。
