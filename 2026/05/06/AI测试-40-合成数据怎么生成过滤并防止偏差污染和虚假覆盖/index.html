AI测试-40-合成数据怎么生成过滤并防止偏差污染和虚假覆盖

发表于 2026-05-06 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:12

合成数据最容易制造一种工程错觉：数据量增加得很快，覆盖报表也很快变绿，于是生成流水线看起来比真实数据建设更高效。

问题在于，生成器并不观察真实世界。它只是根据种子、Prompt、模型参数和已有分布，产出一个“像数据”的对象。只要种子遗漏了尾部场景，生成器就可能把遗漏放大；只要生成器把政策理解错了，同源验证器就可能用相同理由证明错误标签正确；只要私有训练资料被模型记住，改了姓名的输出仍可能逐字泄漏罕见片段；只要把同一条成功路径改写一百次，场景计数就会增长，真正能触发不同故障状态的覆盖却没有增加。

  1. 生成器和验证器具有共同训练来源、共同表达偏好或同一模型家族，错误并不独立；
  2. 生成器同时给出问题、标签和标签理由，形成无法外证的标签自证循环；
  3. 合成分布覆盖种子里已有的表面类别，却进一步压低真实世界的少数群体和尾部状态；
  4. “记录不对应真实个人”被错误等同于匿名、不可重识别或满足差分隐私；
  5. 同义改写、评测答案回流和标签计数共同制造测试污染与虚假覆盖。

一、工程定义与边界：合成的是记录，不是事实

1.1 什么算合成数据

本文把合成数据定义为：

由规则、模拟器、统计模型、生成模型或它们的组合产生，并以训练、评测、红队或受控数据共享为目的的数据记录。

这个定义关注生成过程，不以“看起来像不像真人写的”作为判据。下面这些都属于合成数据：

  • 状态机枚举出的订单边界条件；
  • 模板加参数组合产生的 API 请求；
  • 从真实分布估计后采样出的表格记录；
  • 大模型根据种子任务生成的指令、输入、答案和解释；
  • 模拟用户与 Agent 多轮交互得到的轨迹；
  • 经过差分隐私机制训练或计算后发布的合成表；
  • 故意包含越权、提示注入和矛盾证据的红队样本。

真实日志脱敏后仍然是经过转换的真实观测，不会因为替换姓名就自动变成合成数据。反过来，一条由模型生成的订单记录即使与某个真实订单偶然相同，来源仍然是合成过程，但这次碰撞会产生隐私和污染风险。

1.2 四类用途必须分开

“合成数据”不是一个统一资产类型。至少要把训练、评测、红队和隐私型合成数据分开，因为它们的正确性证据、可接受噪声和发布边界完全不同。

类型 主要目标 最低证据 可以容忍什么 不能据此声称什么
训练型合成数据 扩展监督信号、补充特定能力或困难样本 数据来源、生成器版本、抽样策略、独立训练后评测 一定比例可识别噪声，但要测其净效用和切片影响 数据量增加就必然提升模型；训练分布等于真实分布
评测型合成数据 验证明确行为、边界和风险 独立 Oracle、真实锚点、密封用途、失败可复现 为风险测试而过采样，不必模拟自然发生率 测试通过就代表总体业务质量；场景标签等于行为覆盖
红队型合成数据 主动寻找安全、权限和鲁棒性失败 攻击目标、威胁模型、预期阻断、真实副作用证据 极端、不自然和高攻击性输入 攻击通过率代表生产发生率；未攻破就证明系统安全
隐私型合成数据 在限制原始记录暴露的前提下支持分析或共享 威胁模型、生成机制、隐私单位、参数、实现审计、效用测试 为隐私保证付出可量化效用代价 普通生成数据天然匿名；删除直接标识符就有数学保证

同一条记录不能只靠增加一个 purpose 标签就在四类用途之间自由流转。例如训练型数据的标签允许带少量噪声，并不意味着它适合成为发布门禁的金标准；红队样本为了攻击成功而刻意提高危险表达比例，也不适合估计自然流量中的发生率；隐私型合成数据如果没有明确的差分隐私机制和参数，不能因为“人物是虚构的”就贴上 differentially_private=true。

1.3 本文不解决什么

本文不重复以下通用数据治理问题：

  • 如何从生产日志定义目标总体；
  • 如何做分层抽样和样本量估计；
  • 如何按用户、会话、文档族或时间切分数据；
  • 如何组织双标、仲裁和数据卡；
  • 如何用通用评测集比较两个系统版本；
  • 如何评测 RAG 的召回率、忠实度和引用质量。

这些问题仍然需要解决，只是不能替代本文的合成特有控制。一个按会话正确切分的数据集，仍可能在每个切分里都包含由同一模型生成并自证的错误标签。一个完全没有行级重复的数据集，仍可能是一百种措辞表达同一个状态转换。一个 Schema 全部合法的数据集，仍可能把“订单已发货”错误标成“允许自动全额退款”。结构成功、相似度、模型置信度、协议成功和 HTTP 200 都不能单独证明业务正确。

二、贯穿场景：退款测试为什么需要合成数据

假设系统需要判断用户的订单诉求，并输出以下动作之一：

系统输入包括用户文本、订单状态、金额、商品类型、地区、时间、会员权益和历史操作；输出不仅有标签，还有解释、证据 ID 和是否允许调用退款工具。

2.1 真实数据提供锚点，但不一定提供所有风险

假设构造的真实锚点池包含 320 条经过业务专家确认的案例。它能够说明：

  • 真实用户怎样表达诉求；
  • 订单系统实际有哪些状态组合；
  • 政策在某个版本下怎样映射到动作；
  • 哪些少数语言、辅助技术用户或特殊商品容易被遗漏；
  • 已发生事故的输入、输出和副作用是什么。

但真实池可能没有“退款工具返回未知提交状态后用户立即重复请求”这一组合，也可能只有一条“已发货地址变更”的高风险记录。直接复制真实记录会制造重复，直接等待生产再发生则把测试变成事故采集。

合成数据适合承担三项补充任务：

  1. 围绕真实锚点做受控变形，例如只改变订单状态、金额边界或否定词；
  2. 用状态机枚举尚未出现但业务上可达的转换；
  3. 主动构造安全、权限、泄漏和恢复失败，验证系统是否阻断。

2.2 合成数据不能替代真实锚点

如果完全从政策文档和模型常识生成样本，生成器可能不知道生产系统里存在 PARTIALLY_SHIPPED，也不知道某个旧客户端把金额单位传成分。生成器会围绕自己理解的世界制造越来越多一致样本，而真实事故恰好落在它没有建模的地方。

三、完整架构：控制面、数据面和证据面

图里的主链不是简单的 generate -> save。一套可审计实现至少分成三个平面。

3.1 控制面

控制面保存不会随单条生成请求任意变化的约束：

  • 用途契约和禁止用途；
  • 种子分类体系；
  • 真实锚点与政策快照；
  • 允许的生成器、验证器和家族关系；
  • 泄漏哨兵与禁止祖先清单；
  • 风险切片的最低证据要求；
  • 精确重复阻断和语义重复复核阈值；
  • 偏差、隐私、覆盖和人工复核门槛；
  • 保留期限、撤回和删除传播规则。

控制面配置需要不可变版本。一次生成批次必须指向确切的配置摘要，不能只记录“使用当前规则”。否则同一批数据在下周重新验收时，过滤结果可能变化，却无法判断是样本变了还是规则变了。

3.2 数据面

数据面执行真正的处理：

原始响应和解析后的记录应分开。解析失败不能通过手工编辑原文件“修好”后继续沿用原记录 ID。更稳的做法是保留原始对象，新增一个带转换器版本的派生记录。这样才能区分生成失败、解析器失败和人工修复。

3.3 证据面

证据面回答每个结论凭什么成立：

  • 规则命中了哪个字段和哪条规则；
  • Oracle 使用哪个政策版本计算出预期动作；
  • 模型验证器是谁、看到了什么、输出什么结构化理由；
  • 人工复核者是否对生成器身份盲化；
  • 哪个哨兵或片段产生泄漏命中；
  • 哪两条记录进入近重复候选簇，人工最后保留了谁；
  • 某个覆盖格子依赖哪些真实锚点和变形关系；
  • 某条上游记录撤回后，哪些后代被标为不可用；
  • 历史报告当时使用了哪个有效清单。

四、数据模型：把生成记录变成可追踪对象

4.1 最小记录结构

一条合成记录不应只有 prompt 和 answer。建议至少包含以下字段组。

字段组 关键字段 作用
身份 record_id、batch_id、created_at 稳定定位，不依赖文件行号
用途 purpose、allowed_uses、prohibited_uses 防止训练、评测、红队和共享用途混用
种子 seed_ids、seed_taxonomy、anchor_ids 说明样本从哪类需求和真实证据派生
生成 generator_id、generator_family、generator_version、prompt_hash、parameters 识别生成器共同故障和批次差异
内容 raw_output_ref、normalized_input、expected_behavior、label 保存原始对象与评测对象
验证 oracle_version、validator_id、validator_family、review_id、evidence 判断标签是否有独立支持
风险 privacy_claim、sentinel_hits、duplicate_cluster、bias_slices 保存过滤和风险结果
血缘 parent_ids、transform_id、source_snapshot 构造可传播删除的有向无环图

五、种子分类：不是给 Prompt 几个例子

5.1 种子决定生成空间的上限

生成模型可以改写和组合，却不会稳定发现业务系统从未告诉它的隐藏状态。种子分类至少应覆盖：

  • 意图：退款、取消、地址变更、发票、物流查询；
  • 状态：未支付、已支付、部分发货、全部发货、签收、退款处理中；
  • 动作风险：只读、低额写入、高额资金、跨账户、不可逆动作；
  • 证据形态：完整、缺失、冲突、过期、来源无权限；
  • 表达现象：否定、条件句、反问、指代、多轮修正、代码混排；
  • 用户与渠道切片：语言、地区、客户端版本、辅助技术、企业租户；
  • 故障状态：超时、重复提交、未知提交、部分成功、供应商切换；
  • 攻击目标：越权、提示注入、敏感数据外发、策略绕过；
  • Oracle 类型：确定性状态机、数值边界、专家裁决、暂无可靠 Oracle。

最后一项尤其重要。没有可靠 Oracle 的格子可以生成探索候选，但不能和有确定性答案的记录一起计算自动通过率。

5.3 真实锚点有三种角色

真实锚点不只负责“让语言更自然”。它至少有三种角色：

  1. 事实锚点：证明状态、政策和预期动作在某个版本下成立；
  2. 分布锚点：提供真实群体、表达和状态的比例基线；
  3. 失败锚点：证明某类故障真实发生过，并保存完整证据链。

一条合成记录可以引用多个锚点。例如它的表达来自真实客服会话，状态转换来自订单状态机，预期动作来自政策快照。只保存一个模糊的 source=production 会丢失这种组合关系。

5.4 锚点不是要被复制进 Prompt 的原文

为了减少隐私和污染风险，生成器通常只需要最小必要特征：状态、约束、关系和经过批准的短片段。把完整私有会话原样塞给模型，再要求“改写成匿名版本”，会让生成器具备复现原文的机会。更稳的路径是先在受控环境提取结构化事实，经授权后构造种子；必要原文单独加访问控制、哨兵和保留期限。

六、生成器版本：可追溯不等于可精确复现

6.1 一次生成批次冻结什么

至少冻结：

  • 生成器产品和固定模型版本；
  • API 或本地推理运行时版本；
  • 系统指令、任务模板和 Few-shot 摘要；
  • 采样参数、最大输出、停止条件；
  • 种子和真实锚点快照；
  • 工具、检索和后处理版本；
  • 请求顺序、并发策略和重试策略；
  • 生成时间、区域与供应商请求 ID；
  • 内容过滤和安全策略版本；
  • 原始响应摘要和解析器版本。

即使全部记录，远程模型服务也未必能逐 Token 重放历史输出。供应商可能更新后端，底层并行计算也可能带来差异。因此，版本记录支持的是“解释和比较生成条件”，不能夸大成“未来一定逐字复现”。真正需要稳定的评测样本，应把已接受记录固化为不可变资产，而不是每次回归时重新调用生成器。

  1. 可执行确定性 Oracle：状态机、计算规则、数据库约束、编译器、单元测试、模拟器后置条件；

  3. 异源模型交叉验证：模型家族、Prompt 和上下文尽量独立，输出结构化分歧；
  4. 盲化人工复核：隐藏生成器身份和已有判断，按规范独立判定；

八、过滤流水线：规则、模型和人工各自负责什么

8.1 规则过滤负责可确定约束

适合规则处理的内容包括：

  • 必填字段、类型、枚举和长度；
  • 固定事实是否被非法改写；
  • 数值边界与状态机是否一致；
  • 禁止祖先或密封评测 ID 是否出现；
  • 生成器与验证器家族是否满足隔离策略；
  • 直接标识符、秘密格式和泄漏哨兵；
  • 精确内容重复；
  • 发布用途是否与记录用途一致。

规则结论应可复现，错误码应稳定。不要把一句自然语言模型提示包装成“规则层”。

8.2 模型过滤负责发现候选，不负责抹平不确定性

模型适合辅助判断：

  • 语义是否偏离种子意图；
  • 是否出现隐含冲突、歧视表达或不自然措辞；
  • 两条记录是否可能是近重复；
  • 生成解释是否遗漏关键前提；
  • 开放式红队输入是否仍针对预期攻击面。

模型输出是风险信号，不是业务真值。模型置信度高也可能来自熟悉自己的表达风格。高风险记录需要把模型结论转换为可复核证据，例如具体冲突字段、引用的政策条款和建议的人审队列。

8.3 人工过滤处理价值判断和证据不足

人工复核适合：

  • 政策本身存在例外或解释空间；
  • 群体伤害不能由简单比例代表；
  • 红队输入可能造成真实危害，需要控制披露；
  • 两个独立验证器持续分歧；
  • 语义近重复是否保留取决于测试目标；
  • 隐私风险涉及罕见组合和外部可链接数据。

人工不是无限兜底。队列应有优先级、容量、抽样复核和一致性检查。若某个生成批次把 60% 记录送人工，说明自动生成契约或种子设计需要重做，而不是继续扩充审核人力。

NIST AI 600-1 把有害偏差与同质化列为生成式 AI 风险，并建议评估训练数据中合成与非合成数据比例，避免训练数据过度同质或过度由生成式 AI 产生。Shumailov 等人的 Nature 论文研究了模型在递归使用模型生成数据训练时的分布退化；其结论来自论文设定下的递归生成实验，不能简化成“加入任何合成数据都会坍塌”。更精确的工程含义是：

  • 记录每一代数据的来源和比例；

十一、隐私误区：虚构人物不等于数学匿名

11.1 普通合成数据可能泄漏什么

生成器可能复现：

  • 罕见姓名、地址、邮箱和订单号；
  • 私有文档里的长文本片段；
  • 多字段组合形成的唯一身份；
  • 训练数据中特别重复或特别独特的记录；
  • 受版权或合同限制的内容；
  • 密封评测答案和内部事故细节。

把姓名替换成“张三”只处理直接标识符。年龄、邮编、职业、事件日期和罕见病症的组合仍可能支持重识别。大模型生成的文本也可能记忆并逐字输出训练片段。Carlini 等人在 GPT-2 家族上的原始提取研究证明了从该实验中的语言模型提取逐字训练序列是可行的；这不等于所有模型、所有数据都会以相同比例泄漏，但足以否定“模型生成内容天然与训练记录无关”的假设。

真正解释这个式子时，至少要同时说明：

  • 相邻数据集怎样定义；

11.4 DP 不是零代价包装层

差分隐私通过随机化限制单个隐私单位对输出分布的影响。更强的隐私通常需要更多噪声，并降低某些统计和下游任务的效用。低频类别、长尾相关性和高维组合尤其可能受到影响。

NIST 关于差分隐私合成数据的官方文章明确区分：许多合成数据技术不满足差分隐私或任何正式隐私性质；差分隐私合成数据可以提供数学支持的保证，但准确构造很难，针对特定分析设计的差分隐私查询通常可能比先发布通用合成数据再分析获得更高准确性。这个结论不能被改写成“DP 合成数据发布后适合所有用途”。

如果任务只需要三个固定统计量，直接为这些统计量设计差分隐私机制，可能比发布一份试图支持任意分析的合成表更合适。若任务需要高保真罕见关联，团队需要明确接受效用损失，或改用受控安全环境而不是强行发布数据。

11.5 不要手写生产级 DP 算法

本文后面的 Python 示例实现泄漏哨兵和数据验收，不实现差分隐私机制。NIST SP 800-226 提醒随机化算法实现容易出错，建议尽可能使用经过严格验证的库。生产系统还需要专业隐私评审、预算会计、威胁模型和实现审计。给计数加一个随机数，再把输出称为 DP，是错误做法。

十二、测试污染：合成器可以把密封答案扩散成无数变体

12.1 污染链不只发生在训练文件

密封评测内容可能通过以下路径进入生成器：

  • 被复制到 Few-shot 示例；
  • 作为“失败样本”进入 Prompt 优化记录；
  • 通过 RAG 索引或调试知识库被检索；
  • 评测报告把标准答案和理由写入工单；
  • 开发人员要求模型“围绕这些测试失败再生成相似数据”；
  • 路由器或验证器训练使用了带评测标签的日志；
  • 上一轮合成评测样本被误标为训练种子。

即使最终文本没有逐字重复，生成器也可能扩散同一题的答案模式。普通字符串去重发现不了这种祖先污染。

14.1 代码怎样对应生产职责

这个示例刻意把“检测到风险”和“允许发布”分开。

deterministic_screen 只处理能够给出稳定错误码的约束。泄漏哨兵、禁止祖先、Oracle 不一致和高风险同源验证任何一项命中，记录就进入隔离。即使一条记录同时命中三个原因，也不会只保留第一个异常。

run_pipeline 先做硬规则，再做精确和近重复处理。精确重复可以自动隔离；近重复只进入 NEEDS_HUMAN_REVIEW。这个区别防止相似度把一对关键反事实自动删掉。

acceptance_report 只在已接受记录上计算发布覆盖，同时要求待复核队列归零。初次运行故意失败，因为一条近重复候选尚未被人工收口。夹具中的“人工结果”确认它只改了连接词，随后将其隔离，第二次验收才通过。

propagate_deletion 从撤回的真实锚点开始，沿 anchor_ids、seed_ids 和 parent_ids 传播墓碑。它不删除行，也不把历史报告改写成“当时从未使用”。生产实现需要把当前有效视图与历史审计视图分开：当前训练和评测构建排除墓碑记录，历史报告仍显示当时使用记录及后续失效原因。

14.2 这个示例没有证明什么

代码执行通过只证明这组确定性夹具满足实现断言。它没有证明：

  • 字符三元片段能识别所有语义重复；
  • 泄漏哨兵未命中就不存在隐私泄漏；
  • 三个构造群体能代表真实公平风险；

十七、指标口径：每个分数都说明分母和用途

17.1 生成接受率

网络失败和无法解析的原始响应另报，不能从分母消失。接受率过低可能说明生成器差，过高也可能说明过滤器松。它是过程效率，不是数据正确率。

17.2 独立验证率

高风险与低风险分开报告。来源不明的验证器不能算已知异源。

17.3 标签自证暴露率

这个指标用于发现流水线结构风险，不应因为这些记录最后被隔离就停止监控。若比例持续上升，生成配置已经偏离设计。

17.4 精确重复率与近重复簇集中度

近重复率要注明算法、阈值和人工复核口径。不同版本不能直接比较。

17.5 泄漏指标

至少分开：

  • sentinel_hit_count：唯一测试哨兵命中数；
  • verbatim_overlap_rate：与受控私有源长片段逐字重叠候选率；
  • identifier_pattern_hit_rate：敏感格式候选率；
  • privacy_attack_success：在明确威胁模型和攻击集下的成功率；
  • unknown_privacy_risk：无法测量或数据来源不透明的风险说明。

这些指标不能合成“匿名分数”。哨兵为零也不能把 privacy_claim 从 none 自动升级为 DP。

17.7 覆盖指标

报告：

这些指标按顺序增加证据强度，但后一个也不自动包含前一个。行为覆盖可能在少量场景很高，却遗漏真实总体；名义覆盖可能很广，却没有有效 Oracle。

17.8 删除传播完整率

还要记录传播延迟、无法访问副本数、缓存清除状态和下游确认。100% 只对“已知后代”成立，血缘漏记会制造虚高。

17.9 单条接受数据成本

只计算生成 API 费用会鼓励生成大量低质量候选，把昂贵复核成本隐藏到其他预算里。

处置的第一步不是立即改 Prompt，而是冻结：

  • 路由到的模型和固定版本；

18.5 逐层排查

第一步：检查被测模型是不是退化

把失败输入换成手工构造的完整事实，并明确列出每个商品行状态。发布候选模型能够正确返回 MANUAL_REVIEW，说明模型不是对部分发货概念完全无能力。问题更可能来自评测数据没有约束它学习或验证拆行逻辑。

第二步：运行确定性 Oracle

使用订单状态机根据每个商品行计算最大可自动退款金额。对合成集中 1,840 条标记为 PARTIALLY_SHIPPED 的接受记录重算，发现 1,612 条期望标签不一致。合成集的 98.7%“准确率”来自模型 Judge 对生成标签的同意，不是状态机准确率。

第三步：查生成器与验证器家族

记录里只有不同的 generator_id 和 validator_id，初看满足“双模型验证”。继续查模型注册表，发现两者指向同一基础家族，只是一个端点使用生成 Prompt，另一个端点使用评分 Prompt。失败记录的 Judge 理由大量复述生成器里的“订单已发货前可退”模板，没有独立拆分商品行。

第四步：查标签来源

label_source 被统一写成 model_validated，覆盖了最初由生成器给出标签的事实。查看原始响应才发现问题、标签和理由在一次调用里生成，Judge 只做同意或拒绝。数据模型把“标签创建者”和“标签验证者”压成一个字段，导致自证关系在报表里不可见。

第五步：查覆盖分子

覆盖 SQL 只判断：

只要文本带 PARTIALLY_SHIPPED 标签，就算覆盖对应格子。它没有检查：

  • 是否有场景对应的真实锚点；
  • Oracle 是否按商品行执行；
  • 测试是否触发拆分分支；
  • 计划退款金额是否满足后置条件；
  • 同一模板簇是否重复贡献。

因此 97.9% 是名义标签覆盖，不是锚定覆盖或行为覆盖。

第六步：查近重复簇

重新用结构字段聚类后，1,840 条部分发货记录中有 1,506 条来自同一个模板，只替换商品名、金额和用户称呼。文本相似度因为实体变化而低于原阈值，但状态路径完全相同。原来的 2.1% 近重复率测的是文本表面，不是业务状态重复。

第七步：查真实锚点

大部分记录都写了 anchor_ids，报表因此声称锚定覆盖很高。但这些 ID 指向通用退款政策，不是部分发货真实案例。锚点存在性通过，不代表锚点支持当前标签。锚点关系还需要类型：FACT_SUPPORT、DISTRIBUTION_REFERENCE、FAILURE_REPLAY 或 STYLE_ONLY。

第八步：查测试污染

生成 Prompt 的 Few-shot 中有一条来自上一版密封评测失败报告。报告没有完整标准答案，却包含“预期转人工”的结论。生成器围绕这个模式产生大量措辞变体，使密封集上的得分虚高。由于中间工单没有继承密封样本 ID，禁止祖先检查未命中。

第九步：查隐私扫描

最终发布文件中的哨兵为零，但原始响应对象里发现一条私有政策备注哨兵。记录因为解析失败未进入发布文件，所以旧报表没有统计。虽然没有交付给被测系统，内容已经进入生成日志和对象存储，仍需按泄漏事件处理。

18.6 排除的错误方向

排查过程中可以排除：

  • 订单模拟 API 故障：输入状态和返回账本可重放，确定性 Oracle 稳定复现；
  • JSON 解析错误：失败结果均符合 Schema，字段值错误而非结构错误；
  • 单次随机采样：固定 100 条失败记录重复运行仍保持同类错误；
  • 只有少数语言翻译问题：主流语言同一状态也存在错误，只是少数语言因多轮更正再增加一层失败；
  • 真实锚点标签错误：政策专家和状态机对 4 条真实记录重新确认，三条失败结论不变。

这些排除动作很重要。不能看到同源 Judge 就直接断言所有错误都由 Judge 引起。政策摘要遗漏是首因，同源验证、标签字段覆盖、近重复漏检和覆盖口径则让首因逃过门禁。

18.7 根因与贡献因素

根因是：policy-7.4 的部分发货语义没有被编码进可执行 Oracle，生成器根据不完整摘要自行补全标签。

贡献因素包括：

  1. 生成器同时产生标签和理由；
  2. 验证器与生成器同家族，且只判断理由是否自洽；
  3. 数据模型覆盖了原始标签来源；
  4. 覆盖按场景标签计数，没有真实锚点关系和行为后置条件；
  5. 文本近重复没有结合结构化状态路径；
  6. 密封评测报告经过工单丢失血缘后进入 Few-shot；
  7. 泄漏扫描只看最终发布文件，没有覆盖被拒绝原始响应；
  8. 真实锚点轨退化被大规模合成集平均分压过。

18.8 止损与修复

立即动作：

  • 冻结批次，不再用于训练、Prompt 和评测；
  • 从密封失败报告节点开始补齐血缘并传播墓碑；
  • 删除或限制原始响应对象访问，轮换测试哨兵；
  • 灰度回退到旧策略，部分发货全部转人工；
  • 保留历史报告，但标记结论已失效。

结构修复：

  • 用订单商品行状态机实现 policy-7.4 Oracle；
  • 分开保存 label_creator、label_source 和 validators[]；
  • 模型注册表增加 family 与“来源不明”状态；
  • 高风险记录要求确定性 Oracle 或异源模型加盲化人工双证据；
  • 覆盖报告拆成名义、锚定、行为和变异杀伤四层；
  • 近重复同时使用文本候选和结构路径指纹；
  • 所有工单、报告和 Few-shot 继承密封数据血缘；
  • 泄漏扫描覆盖接受、拒绝、解析失败、日志、缓存和导出。

十九、从零到一的落地顺序

阶段一：先隔离用途

建立训练、评测、红队和隐私四个物理或逻辑隔离区，发布清单明确禁止用途。还没有自动化时，宁可用小规模人工审批，也不要先建一个所有数据自由流转的大池。

阶段二：补生成记录和血缘

先记录生成器、Prompt、种子、锚点、父节点和原始响应，再讨论复杂质量模型。没有血缘时，任何删除传播、污染排查和生成器回归都只能靠猜。

阶段三：把确定性 Oracle 前置

状态机、计算规则、编译执行和业务不变量应先于模型 Judge。每增加一个可执行 Oracle，就减少一部分由模型自证的空间。

阶段四：建立独立验证和分歧队列

模型注册表加入家族关系，人工复核对生成器身份盲化，分歧按风险排序。先治理高风险和高批量种子，不追求所有开放式内容自动判断。

阶段五：补泄漏、偏差和覆盖门禁

从唯一哨兵、逐字片段、分层分母和真实锚定覆盖开始。语义攻击、成员推断和复杂公平分析需要专门能力，但不能因为暂时做不全就把未知风险记成零。

阶段六：演练撤回和事故

选择一个测试锚点执行撤回，验证训练快照、评测清单、缓存、对象存储和历史报告怎样响应。再注入同源验证、密封祖先污染和泄漏哨兵，证明门禁确实会失败。

二十、上线检查表

用途与边界

  • 训练、评测、红队和隐私型合成数据有独立用途契约；
  • 每类数据写明允许用途、禁止用途和失效条件；
  • 合成红队比例不会被解释成生产发生率；
  • 训练型标签噪声不会被直接当作评测金标准；
  • 没有正式隐私机制的数据明确标为无 DP 声明；
  • 通用数据治理与合成特有控制都有责任人。

种子与真实锚点

  • 种子按意图、状态、风险、证据、表达、群体和故障分类；
  • 每个种子区分固定事实、可变轴和禁止变形；
  • 真实锚点标明事实、分布、失败或仅风格关系；
  • 高风险格子没有用通用政策 ID 伪装具体事实支持；
  • 私有原文只按最小必要原则进入生成上下文；
  • 锚点过期、撤回和政策版本变化会触发后代重算。

生成记录

  • 生成器 ID、家族、固定版本和运行时已记录；
  • Prompt、Few-shot、参数、种子与来源快照有摘要；
  • 原始响应和解析后记录分开保存；
  • 解析失败没有通过覆盖原文件变成成功；
  • 批次之间的主要变量可归因；
  • 远程模型可追溯性没有被夸大成逐 Token 可复现。

标签与验证

  • 标签创建者、标签来源和所有验证者分别记录；
  • 确定性 Oracle 优先于模型判断；
  • 高风险生成器与验证器满足家族隔离；
  • 来源不明的验证器没有被当作已知独立；
  • 验证器先独立作答，再查看生成理由；
  • 分歧进入有容量和时限的盲化人工队列；
  • 模型置信度没有被当作业务真值。

过滤与去重

  • 规则、模型和人工过滤职责明确；
  • 每层保留输入分母、拒绝原因和版本；
  • 精确规范化保留否定、数字、单位和标识符；
  • 语义相似只产生候选，关键反事实不会被自动删除；
  • 文本簇与业务状态路径簇分别统计；
  • 最大模板簇不会支配训练权重或评测分数；
  • 被拒绝原始输出仍执行泄漏扫描。

隐私

  • 威胁模型覆盖重识别、逐字记忆、链接和成员推断；
  • 哨兵有授权、轮换、撤回和全链扫描；
  • 未命中哨兵不会被写成匿名证明；
  • 若声明 DP，记录 ε、δ、隐私单位、邻接关系和组合预算；
  • DP 实现使用经过评估的库并接受专业审查；
  • 原始数据存储、访问和删除不依赖输出 DP 保证；
  • 隐私效用代价按任务和群体切片验证。

污染与血缘

  • 密封样本、答案、报告、工单和调试会话都有禁止祖先标识；
  • Few-shot、RAG、路由训练和验证训练都做祖先检查；
  • 派生树按簇隔离，不跨开发、校准和密封集合；
  • 外部数据无血缘时补相似度与来源审计；
  • 生成记录、锚点、种子和转换构成无环可查询图；
  • 删除传播覆盖快照、缓存、导出和下游副本；
  • 历史报告保留墓碑而不静默改写过去。

覆盖与指标

  • 名义、锚定、行为和变异杀伤覆盖分别报告；
  • 覆盖格子保存具体样本、锚点、执行和后置条件证据；
  • 新事故可以回溯修正历史覆盖结论；
  • 接受率不会被称为正确率；
  • 偏差指标包含生成、规则、模型、人工各层分母；
  • 泄漏指标不会被压成单一匿名分数；
  • 每个比例保存分子、分母、阈值版本和不确定性。

测试与发布

  • 自动测试覆盖自证、同源验证、重复、哨兵、污染和删除传播；
  • 组合故障注入能让发布门禁真实失败；
  • 待人工复核记录不会进入发布清单；
  • 真实锚点轨退化不能被合成平均分抵消；
  • 发布清单不可变并绑定所有配置版本；
  • 回滚能停止数据继续进入训练、Prompt 和评测；
  • 事故包能从错误输出追到生成器、种子、验证器和所有后代。

二十一、总结

合成数据的价值在于把真实世界稀缺、危险或尚未发生的状态变成可控制的工程输入。它的风险也来自同一件事：数据由系统自己创造，系统很容易同时创造问题、答案、理由和通过证明。

一条可信链路需要守住以下边界：

  1. 训练、评测、红队和隐私型数据按用途隔离，证据标准不混用；
  2. 种子不仅保存例子，还定义固定事实、可变轴、风险切片和禁止变形；
  3. 每条记录连接真实事实、分布或失败锚点，并保存完整生成器版本与血缘；
  4. 确定性 Oracle、异源验证和盲化人工共同切断标签自证循环；
  5. 精确重复可自动处理，语义相似只作为复核线索，关键反事实不能被相似度删除；
  6. 生成与过滤各层都检查群体和尾部变化，递归回流保留真实数据锚；
  7. 普通合成数据不天然匿名，泄漏哨兵是检测手段而非隐私证明；
  8. 差分隐私只在明确机制、参数、隐私单位、组合预算和实现条件下提供数学保证，并伴随效用代价；
  9. 污染控制沿禁止祖先和派生图工作，不能只靠最终文本相似度；
  10. 覆盖分成名义、锚定和行为证据，并用变异与事故回放校准；
  11. 上游撤回沿血缘传播墓碑，当前有效资产与历史审计事实分开；
  12. 发布门禁通过说明既定证据齐全，不意味着未知风险为零。
