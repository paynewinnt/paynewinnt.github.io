AI测试-48-蜕变测试怎么解决AI输出没有唯一标准答案的问题

发表于 2026-05-22 分类于 AI测试 本文字数： 18k 阅读时长 ≈ 1:06

“这个回答和参考答案不一样，所以测试失败。”

“开放问题本来就没有唯一答案，所以不能自动化测试。”

这两句话看似站在相反方向，实际犯了同一个错误：都把“输出文本是否唯一”当成了“系统行为是否可验证”的前提。

一个客服助手可以用不同句式解释同一条退款政策，但不能因为换了证据顺序就把“需要人工复核”改成“已自动退款”；一个摘要系统可以调整段落结构，却不能在加入一条与结论无关的说明后丢失原来的关键风险；一个检索增强问答系统可以在新增支持证据后补充引用，但不能引用一个根本没有进入上下文的文档；一个 Agent 可以选择不同的无副作用查询路径，却不能把同一个只读请求随机升级为写操作。

这些要求都不需要先写出唯一的完整答案。它们验证的是多个输入和多个输出之间必须成立的关系。

蜕变测试（Metamorphic Testing，MT）的价值就在这里：当单次执行很难获得完整测试 Oracle 时，不强行伪造一个逐字参考答案，而是从已有测试输入构造满足特定条件的跟随输入，并检查源执行与跟随执行之间是否满足预先声明的蜕变关系（Metamorphic Relation，MR）。

但这不是把唯一答案偷换成“只要大致相似就通过”。一条可用于工程门禁的 MR 至少要回答：

  • 什么输入才属于关系的适用域；
  • 具体改变了输入中的哪个变量，哪些环境变量必须冻结；
  • 输出中哪些字段必须完全不变；
  • 哪些部分可以变化，变化范围和方向是什么；
  • 单次关系必须成立，还是只要求多次运行后的概率关系成立；
  • 随机采样怎样配对，重复次数和停止规则是什么；
  • 关系违反是系统故障、变换无效、评测器错误还是证据不足；
  • 这条关系能发现哪类故障，又有哪些共同错误永远发现不了；
  • 发布门禁如何同时使用关系强度、适用覆盖、统计区间和业务严重度。

本文围绕这些问题建立一套可执行方法。文中的退款案例、样本量、阈值、违例率、事故时间和发布数字，除明确引用论文外，全部是构造示例，只用于解释方法，不代表任何生产系统、供应商模型或公开 benchmark 的结果。资料范围冻结在 2026-05-22；任何论文结论都只限定于原论文的数据、系统与实验设置，不能直接外推为生产质量承诺。

《AI测试-16-AI测试怎么组合确定性断言和语义断言》已经讨论 Schema、规则、语义评分与人工裁决的分层组合。本文不重复所有断言类型，只说明这些断言怎样共同构成关系 Oracle。关系 Oracle 的单位不是“一个输出是否像参考答案”，而是“一组输出之间是否满足必要关系”。

《AI测试-17-LLM-as-Judge怎么设计评分规则并控制裁判偏差》已经讨论裁判模型的校准、偏差和人工对照。本文不会把 LLM Judge 当成默认关系 Oracle；能用字段、状态机、集合、数值或工具副作用确定性验证的关系，必须先用确定性方法。使用裁判时，还要把裁判顺序、版本和不确定性纳入证据。

《AI测试-20-非确定性AI应用怎么做稳定的自动化回归测试》已经讨论冻结配置、重复运行和分层回归。本文进一步聚焦于：同一候选系统接受成对或成组输入时，怎样定义跨执行关系。随机重复是 MR 的执行手段，不等于 MR 本身。

《AI测试-24-Prompt怎么像代码一样做模板化版本化评审和回归测试》已经讨论 Prompt 工件治理。本文把 Prompt、模型、检索索引和工具 Schema 都视为被测系统快照的一部分，不展开其单独发布流程。

本文也不把蜕变测试写成候选系统的横向排名方法。这里的主问题是“输入发生已声明变化后，同一系统应保持或定向改变什么”。模型、Prompt、参数与检索版本之间的共同输入配对比较，需要独立的差分实验合同。

二、问题边界与反例：没有唯一答案不等于没有必要性质

2.1 三个层次不要混在一起

对一个开放式 AI 输出，可以同时存在三种事实：

  1. 表面文本不唯一。 同一个意思可以有多种词序、长度、语气和段落组织。
  2. 业务语义受约束。 资格、金额、权限、引用、动作和风险不能任意变化。
  3. 完整正确性仍可能未知。 即使所有已知关系都成立，系统仍可能在所有运行里共同给出同一个错误事实。

蜕变测试主要增强第二层的可检验性，并对第三层提供额外的错误暴露机会。它不会消除完整 Oracle 问题。

下面的反例很重要。

反例一：相同输出不证明正确。

源输入与改写输入都回答“退款已到账”，关系看起来完美稳定；但订单系统实际没有退款记录。这里是共同错误，稳定性甚至让错误更隐蔽。必须使用工具副作用或业务后置条件 Oracle。

反例二：不同输出不必然错误。

源输入返回三段解释，跟随输入返回项目符号；动作、金额、依据和风险完全一致。若 MR 只允许逐字相等，就会制造误报。

反例三：所谓语义保持变换可能改变任务。

把“不要自动退款”改写成“请自动退款”只差一个词，却翻转了意图。用通用相似度证明两句接近，不能证明它们属于同一关系适用域。

反例四：新增信息不总是应该保持结果。

向问题追加“订单已经发货”可能改变资格；追加“箱子是蓝色的”也可能在某个包装政策下有关。只有经过领域规则证明与决策无关的信息，才适合做无关上下文 MR。

反例五：顺序变化不总是无语义。

集合字段可以置换；时间线、优先级列表、聊天历史和检索排名通常不能任意置换。若系统规范允许“首条政策覆盖后续政策”，打乱顺序后结果变化并不是模型故障。

反例六：概率稳定不等于逐次稳定。

同一个生成系统在合法采样下可能输出不同措辞。要求每个 seed 都逐字相等过强；只比较整体均值又可能掩盖高风险动作偶发翻转。必须按字段风险选择硬关系、容差关系或概率关系。

三、方法来源：1998 技术报告，不是 2020 年发明

T. Y. Chen、S. C. Cheung 与 S. M. Yiu 的《Metamorphic Testing: A New Approach for Generating Next Test Cases》原始载体是香港科技大学计算机科学系技术报告 HKUST-CS98-01，1998。arXiv 页面显示的提交时间是 2020 年 2 月，因为它是后来上传的重印入口；不能据此把蜕变测试称为 2020 年提出的方法。

原报告关注测试 Oracle 难以获得时，怎样从已有成功测试中导出新的测试，并利用输入—输出关系检查后续执行。这个核心思想对 AI 系统仍然适用，但生产生成系统增加了几个原报告时代不必以同样方式处理的问题：

  • 输出可能受采样随机性影响；
  • 被测对象常由模型、Prompt、检索、工具和安全策略共同构成；
  • 外部知识和工具状态会随时间变化；
  • 语义保持变换本身可能需要人工或确定性验证；
  • 输出中的部分字段是硬业务动作，部分只是可变文本；
  • 关系不一定是精确等式，可能是集合、方向、容差或概率约束；
  • 自动裁判本身也是一个有版本、有偏差的系统。

所以不能只写“改一下输入，看看答案是否一致”。需要把 MR 变成完整、可审计的测试合同。

五、完整分层架构与数据流

5.1 源资产层

保存原始测试案例、业务切片、来源、权限级别、敏感标记和可使用范围。源案例不必有完整参考文本，但至少要有足够的结构事实判断 MR 前置条件。

5.2 关系目录层

关系目录管理 MRSpec，包括负责人、风险级别、适用域、变换器、观察字段、允许变化、统计规则和历史故障。关系定义改动必须产生新版本，不能静默覆盖旧报告。

5.3 变换层

变换器接收源案例和参数，输出跟随案例、字段级 diff、可逆信息与变换有效性证据。变换器自身需要单元测试和变异测试，因为它一旦写错，会稳定制造假缺陷。

5.4 执行编排层

编排器冻结系统快照，将源输入和跟随输入按配对设计运行。它负责：

  • 分配共同 seed 或预注册 seed 集；
  • 随机化源/跟随执行先后，降低时间和缓存效应；
  • 控制并发与重试；
  • 保存每次物理 attempt；
  • 阻止源执行和跟随执行跨越索引、政策或模型发布；
  • 将超时、取消和缺失保留为结果。

5.5 原始证据层

保存完整输入、输出、检索文档 ID 与版本、工具请求与响应、模型调用元数据、Trace 和环境指纹。原始证据不可因后续解析器升级而改写。

5.6 观察投影层

8.3 单调关系

形式：

可能用于：

  • 在不冲突且可信的支持证据加入后，证据覆盖不能下降；

8.4 包含关系

适合摘要增量更新：新增一段不冲突材料后，旧的关键风险仍应保留，同时允许增加新事实。若摘要有固定长度预算，包含关系可能不成立，应改为“最高严重度事实不得被挤出”。

十一、随机性：seed 是证据字段，不是确定性保证

11.1 随机性来自多层

  • 采样温度、top-p、top-k 和随机数实现；
  • 模型服务的批处理与并行规约；
  • 相同分数文档的检索排序；
  • 工具返回顺序和超时；
  • 重试路由到不同副本；
  • 动态安全策略；
  • 裁判模型本身的采样；
  • 并发写入与缓存命中；

十二、关系强度：关系越严格不代表越有价值

12.1 五个独立维度

一条 MR 的工程强度至少包括：

  1. 逻辑约束力：精确相等通常比宽容差更强，但可能误报。
  2. 适用覆盖：能应用到多少目标案例和关键切片。
  3. 故障杀伤力：能杀死多少与声明相关的已知变异。
  4. 独立性：是否只是重复另一条关系的相同观察字段。
  5. 可诊断性：违反后能否定位到字段、变换和执行证据。

不能只按“关系数量”衡量能力。十条都比较同一个 action 字段，不等于覆盖十种风险。

十四、指标与公式：报告关系证据，而不是只报通过率

14.1 有效派生率

低有效派生率通常先说明变换器或适用域有问题，不应直接归因于被测系统。

14.2 可执行率

超时、限流、环境故障和取消分别报告。把未完成配对从分母静默删除会产生成功者偏差。

若一条高风险违反就会造成不可逆副作用，发布合同可以规定任何已确认实例都阻断，而不是等待总体显著。

14.5 不确定率

不确定不是通过。它可能来自区间跨门槛、裁判顺序翻转、输出解析失败或样本不足。各原因必须分开。

14.6 误报确认率

十五、发布门禁：硬关系、概率关系与证据质量分开

15.1 硬门

以下构造规则可以直接阻断：

  • 已确认的权限或数据驻留关系违反；
  • 同一业务请求因无语义格式变化触发了额外写操作；
  • 金额、币种、对象或幂等键不守恒；
  • 输出引用了跟随输入未提供的证据；
  • 高风险安全决策在合法改写后翻转；
  • 关系评测使用了错误系统快照且无法重建证据。

最后一项阻断的是“发布证据有效性”，不等于候选系统一定有缺陷。

15.2 概率门

概率关系可使用：

如果关系跨多个高风险切片，应为切片预先设门，不能只看总体。多次试验、多个关系和多个切片还会增加偶然告警机会；需要预注册主关系、确认集或适当的多重比较策略。

15.3 关系质量门

即使系统关系全绿，若出现以下情况也不应发布：

  • 适用覆盖低于合同；
  • 变换有效性未知比例过高；
  • Oracle 或解析器版本未冻结；
  • 源/跟随跨系统快照；
  • 关系没有杀死必杀故障；
  • 高风险告警未完成分诊；
  • INCONCLUSIVE 被错误映射成 PASS；
  • 证据包缺失原始输出或 Trace。

15.4 例外审批

例外必须包含：

“模型输出本来就随机”不是可接受理由。随机性只能改变统计方法，不能取消业务约束。

16.1 代码中的观测、推断和决策

观测

Violation 只保存哪个案例、哪个 seed、哪些硬字段发生变化。Wilson 区间由违例计数计算。它们都可以从原始执行重建。

推断

当注入候选在合法改写后出现显著更高的动作翻转时，可以推断“候选违反了当前概率 MR”。代码没有尝试把它自动命名为某种真实模型内部机制。

决策

硬关系有任一违反即 FAIL；概率关系只有区间整体位于阈值一侧才给出 PASS 或 FAIL，跨界时返回 INCONCLUSIVE。这个门禁是构造规则，不是通用行业阈值。

16.2 为什么文本不进入硬 Oracle

模拟器会在三种表面措辞中选择，但 business_oracle 只检查动作、批准金额和证据集合。这不是忽略自然语言，而是把允许变化从禁止变化中分离。真实系统还可以增加命题抽取、事实校验和风格关系，但不能用全文相似度替换资金字段。

16.3 为什么随机源使用哈希

Python 进程默认的 hash() 可能受哈希随机化影响。示例用 sha256(snapshot_id|case_id|seed) 生成稳定整数，使同一候选、案例和 seed 跨进程可复现。实际模型 API 是否遵守 seed，要以对应官方合同和实测为准。

16.4 这个 mock / 模拟不能证明什么

这段代码不能证明：

  • 任一真实大模型能正确理解退款政策；
  • 两条中文改写在所有语境中都等价；
  • 8% 是合理生产阈值；
  • Wilson 二项区间适合存在案例内相关的全部数据；
  • 一个 seed 能控制供应商服务的全部随机性；
  • 通过三条 MR 就代表系统事实正确、安全或可上线；
  • 构造的故障分布等于真实故障分布；
  • 离线输出关系能证明线上工具副作用成功。

它只能证明测试框架的控制流、区间公式、确定性样例和两种已声明失败注入按预期工作。真实落地必须替换业务数据、变换有效性证据、系统执行适配器、关系阈值与线上后置条件。

18.2 常见漏报来源

关系太弱。 只检查 JSON 可解析，无法发现字段值错误。

共同错误。 源输入与跟随输入都返回同一个错误结果。

观察投影丢信息。 归一化器删除了否定、单位或重复副作用。

容差过宽。 为减少告警不断放大 ε，最终任何退化都能通过。

源案例单一。 所有案例都来自同一模板，关系只验证表面格式。

变换未触达目标机制。 声称检查顺序偏差，却在进入模型前被排序器恢复原顺序。

随机配对抵消真实风险。 共同 seed 有助于降噪，但若风险只在不同并发或副本组合出现，还需专门设计环境关系。

18.3 误报治理不能靠静默忽略

合理流程是：

  1. 冻结原始证据；
  2. 判断前置条件和变换有效性；
  3. 核对系统与外部快照；
  4. 复算观察投影；
  5. 用独立 Oracle 或人工复核；
  6. 分类为系统缺陷、关系缺陷、基础设施缺陷或不确定；
  7. 修复后回放；
  8. 更新关系质量指标。

把某个 case_id 加进永久忽略列表，只会积累不可解释的盲区。确需豁免时必须说明关系、切片、原因和到期时间。

十九、怎样阅读已有研究：论文数字不能替代自己的关系校准

19.1 DeepTest 的启发与边界

Tian、Pei、Jana 和 Ray 在 ICSE 2018 的 DeepTest 工作中，对自动驾驶 DNN 的图像输入施加亮度、模糊、雨雾与仿射等变换，并利用变换前后驾驶行为关系寻找错误。它说明视觉输入没有逐像素唯一参考输出时，仍可用场景相关关系测试行为。

但它的对象是论文选定的自动驾驶模型、Udacity 相关数据与实验变换。不能据此声称：

  • 所有亮度变化都应保持方向盘角度；
  • 图像变换一定符合真实物理世界；
  • 神经元覆盖增长等于生产风险覆盖；
  • 论文发现数量可以换算为当前 LLM 应用缺陷率；
  • 同一阈值适用于摄像头、文本客服和 Agent 工具调用。

从这项工作可迁移的是“变换必须对应领域必要性质”，不是某个固定倍率或阈值。

19.2 深度学习预测器案例为什么值得同时看正反证据

Dwarakanath 等人在其深度学习预测应用研究中开发了 19 条 MR；论文摘要报告，在其实际应用上发现 8 个此前未知问题，并在其参考实现与构造变异条件下杀死 65.9% 的假设故障。这些数字只能描述该预测器、关系集、参考实现和变异设计。

Saha 与 Kanewala 对监督分类器既有 MR 的故障检测能力做了另一项实证研究。其摘要说明实验使用多个变异引擎产生的 709 个可达变异，所考察关系检测到其中 14.8%。这个结果同样不能外推为“蜕变测试通常只有 14.8% 有效”，却清楚提醒我们：关系数量和历史论文中的高检测率不能免除当前系统的变异校准。

两项结果放在一起，合理结论是：

不能选择其中一个数字做营销，也不能把另一个数字当作否定整个方法的普遍定律。

19.3 统计区间的适用边界

NIST/SEMATECH 电子手册对置信区间的重复抽样含义给出正式说明。本文代码采用 Wilson 二项比例区间，是为了避免直接使用 p_hat 做无不确定性的门禁。它仍依赖二项观测建模；案例内相关、时间相关、分层抽样和选择偏差需要相应的簇级或设计型分析。

Bootstrap 的基本思想可以追溯到 Efron 1979 年的原始论文。对 AI 关系评测，按 case_id 重采样而不是按每个 seed 独立重采样，常能更诚实地保留案例内结构。但 percentile bootstrap 也不是任何样本下都自动可靠；小样本、极端比例、强偏斜和非代表性抽样仍需专门分析。

二十、故障注入：证明测试链路真的会失败

一套只在健康候选上全绿的 MR 流水线，没有证明它能发现问题。至少要覆盖下面六层。

20.1 关系目录故障

注入 预期观测 不应发生
删除 precondition 不适用案例进入变换，invalid 率上升 将全部告警归为模型缺陷
放宽金额容差十倍 必杀金额变异存活，杀死率下降 因通过率提高而自动批准关系
把 INCONCLUSIVE 映射为 PASS 关系合同测试失败 报告继续显示绿色
覆盖旧 relation version 历史摘要哈希不一致 静默重算并覆盖旧证据

20.2 变换器故障

  • 改写时删除否定词；
  • 元转分时使用浮点并发生舍入；
  • 置换时遗漏最后一条证据；
  • 添加所谓无关句时带入另一个订单号；
  • 对 Unicode 规范化时破坏用户标识；
  • 生成跟随输入后忘记更新内容哈希。

预期信号是变换器单元测试、字段 diff 或有效性 Oracle 先失败。若这些错误只能由系统关系告警间接发现，说明变换层缺少自检。

20.3 执行器故障

  • 源输入使用候选模型，跟随输入误用稳定模型；
  • 两侧检索索引差一个版本；
  • 总是先执行源请求，缓存只惠及跟随请求；
  • 跟随超时后自动重试却覆盖第一次 attempt；
  • 将取消请求从分母删除；
  • seed 列表被并发任务重复或截断。

预期信号包括快照一致性门、顺序区组差异、attempt 数守恒和 seed 清单哈希变化。

20.4 被测系统故障

  • 只读取第一条证据；
  • 只处理最后一个结构字段；
  • 长上下文中忽略中间关键事实；
  • 改写出现同义词后走到错误动作；
  • 金额单位转换后执行两次工具；
  • 相同只读请求因格式变化获得写权限；
  • 新增无关上下文后引用不存在的文档。

这些是 MR 要杀死的目标。每个故障应绑定至少一条主关系和一条独立观察，防止测试只对某段实现细节过拟合。

20.5 Oracle 与观测故障

  • 解析器把缺失金额补成 0；
  • 集合比较前错误去掉一个重复副作用；
  • 裁判看到候选名称；
  • 裁判 A/B 与 B/A 结果翻转；
  • 语义抽取器漏掉“不”；
  • 区间函数把 n=0 当成零失败；
  • 报表只展示总体，不展示高风险切片。

预期结果是评测器合同测试失败或结果进入 INCONCLUSIVE，不能继续作为发布证据。

20.6 证据与门禁故障

  • 原始输出对象丢失；
  • Trace 指向另一个 attempt；
  • 关系告警没有 case_id；
  • 已过期豁免仍生效；
  • 发布服务只读最后一次重跑的绿色结果；
  • 硬关系被软分数平均；
  • 门禁 API 超时后默认放行。

这里要执行 fail-closed 还是 fail-open，取决于业务风险和可用性合同；对于资金、权限和数据外发发布门，证据不可用通常应停止推进，并把“无法证明可发布”与“候选已证明有错”分开记录。

二十二、关系生命周期与治理

22.1 状态机

DRAFT 只描述想法；REVIEWED 表示业务声明和反例已审；CALIBRATING 用历史案例、人工结果和变异确定阈值；ACTIVE 才能进入门禁；误报或规范冲突时进入 QUARANTINED，不能静默当通过；业务能力删除后才能 RETIRED。

22.2 三方责任

  • 业务负责人确认必要性质、适用域和严重度；
  • 测试/质量负责人实现变换、Oracle、统计与证据；
  • 系统负责人确认快照、可观察性、修复和回滚。

让模型团队单独定义所有关系，容易把当前实现行为当成规范；让测试团队脱离业务定义关系，又容易把语义改变误当保持。

22.3 关系变更评审

评审必须回答：

  1. 是产品规范变化，还是为了让失败候选通过？
  2. 哪些历史结果会改变？
  3. 旧版本是否继续保留？
  4. 前置条件扩大或缩小了哪些切片？
  5. 允许变化是否触及资金、权限、安全或事实？
  6. 必杀变异是否仍被杀死？
  7. 阈值依据是否在看到当前候选前确定？

22.4 关系退役

关系可以因功能下线、规范改变或被更强确定性检查完全替代而退役。退役记录要保存替代控制和历史关联。不能因为关系长期发现真实问题而把它称为“太不稳定”后删除。

二十三、从零到一实施顺序

阶段一：从硬结构关系开始

选择三个高价值、低争议关系：

  • 金额单位等价；
  • 集合字段置换；
  • 工具副作用守恒。

建立 case_id、系统快照、原始输出、字段投影和回放能力。先让证据链可靠。

阶段二：补变换有效性

为每个变换写前置条件、字段 diff、反例和单元测试。引入 VALID / INVALID / UNKNOWN，禁止把所有跟随案例都算入分母。

阶段三：加入随机重复

冻结 seed、顺序区组、最小样本和停止规则。区分案例数与重复数，使用区间而不是单点比例。

阶段四：校准关系强度

收集已知事故和目标变异，计算适用覆盖、杀死率、重叠与告警确认率。弱关系进入改造，不因数量需求直接激活。

阶段五：接入发布门

先以报告模式运行，验证误报分诊能力；再将资金、权限、安全等高风险硬关系接入阻断；概率关系在区间和样本合同稳定后接入。

阶段六：影子与持续治理

使用无副作用影子流量验证分布变化，监控关系适用率和未知率。规范、Prompt、检索或工具变化时，重新审查关系。

二十四、可执行检查清单

问题与边界

  • 已说明单次输出为什么没有完整唯一 Oracle
  • 已列出仍可确定验证的动作、金额、权限、引用和副作用
  • 已声明 MR 是必要性质，不是完整正确性证明
  • 已提供至少一个“关系通过但答案共同错误”的反例
  • 已提供至少一个“输出不同但业务上都正确”的反例
  • 已将关系违反记录为观测，而不是直接写成根因

关系合同

  • 每条关系有稳定 relation_id 和版本
  • 可证伪业务声明已由领域负责人确认
  • 适用域和不适用反例完整
  • 输入变换及参数可重放
  • 改变变量与冻结变量分开
  • 禁止变化、映射变化、允许变化和条件变化分开
  • 硬、容差、方向、集合或概率关系类型明确
  • 严重度、门禁动作和豁免条件明确

变换有效性

  • 实体、数字、单位、否定、时间和权限经过检查
  • 变换前后字段 diff 被保存
  • INVALID_PRECONDITION 不进入系统失败分母
  • UNKNOWN_VALIDITY 不被映射为通过
  • 变换器有单元测试和失败注入
  • 变换器版本进入缓存键和证据包
  • 有序序列不会被误当集合
  • 所谓无关上下文已用业务规则证明无关

执行与快照

  • 被测对象包含模型、Prompt、参数、检索、工具和策略快照
  • 源与跟随执行使用同一不可变系统快照
  • 外部时间、政策、索引和工具 fixture 已冻结
  • seed 配对语义经过实测，而非只相信参数名
  • 源/跟随执行顺序按区组随机化
  • 每个物理 attempt 都被保留
  • 超时、取消、限流和缺失不会静默删除
  • 有副作用测试使用隔离环境、幂等键或只读 fixture

Oracle 与允许变化

  • 先检查实际副作用和业务终态
  • 再检查结构字段、证据和安全决策
  • 语义命题与表面文本分开
  • 能确定性判断的字段不交给 LLM Judge
  • 裁判版本、Prompt、顺序和候选名称盲化有记录
  • A/B 与 B/A 翻转进入不确定或人工复核
  • 缺失字段不会被默认补成成功
  • 硬错误不能被风格或相似度平均抵消

随机性与统计

  • 案例数和每案例重复数分别报告
  • seed 集、最小样本和停止规则预先冻结
  • 违例率同时给出区间
  • 案例内相关时使用案例聚合或簇级方法
  • 零失败不会被表述为真实概率为零
  • 区间跨门槛时返回 INCONCLUSIVE
  • 多关系、多切片与重复查看结果的影响已处理
  • 统计门与业务严重度门同时生效

关系强度与故障注入

  • 每条主关系绑定目标故障
  • 必杀变异在 CI 中持续被杀死
  • 等价和不可达变异不进入杀死率分母
  • 适用覆盖按目标总体计算
  • 关系重叠和独立观察字段可见
  • 误报只在完成分诊后统计
  • 关系、变换、执行、Oracle、证据和门禁六层都做注入
  • 至少演练一次组合故障

发布与运营

  • 高风险硬关系有明确阻断规则
  • 证据质量不足能阻止发布证明失效
  • 例外有负责人、范围、缓解、到期和回滚触发
  • 发布报告列出未适用与未覆盖风险
  • 原始输出、Trace、关系结果和分诊决定可追溯
  • 修复后同时回放原失败对和完整关系矩阵
  • 影子探针不会对真实账户产生危险副作用
  • 关系生命周期和规范变更联动

二十五、总结

蜕变测试解决的不是“怎样为开放输出编造唯一标准答案”，而是“怎样把系统必须满足的跨输入、跨输出关系变成可执行证据”。

完整做法可以收敛为十二步：

  1. 把被测对象定义为模型、Prompt、检索、工具、策略和运行时的完整快照。
  2. 从业务必要性质出发，不从“看起来相似”出发。
  3. 为每条 MR 写前置条件、输入变换和不适用反例。
  4. 分开禁止变化、映射变化、允许变化与条件变化。
  5. 先观察副作用和结构字段，再评估语义与表面表达。
  6. 把变换有效性作为独立门，不让坏变换制造模型误报。
  7. 用配对 seed、顺序区组、重复样本和区间处理随机性。
  8. 区分案例数量与 seed 重复，避免伪独立。
  9. 用适用覆盖、变异杀死率、重叠和分诊结果衡量关系强度。
  10. 对关系、变换器、执行器、Oracle、证据和门禁持续做失败注入。
  11. 让硬业务严重度与概率区间共同决定发布，任何一方都不被平均分抵消。
  12. 保留原始证据，将观测、推断、根因和决策分开记录。
