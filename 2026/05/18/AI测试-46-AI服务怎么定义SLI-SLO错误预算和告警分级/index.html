AI测试-46-AI服务怎么定义SLI-SLO错误预算和告警分级

发表于 2026-05-18 分类于 AI测试 本文字数： 18k 阅读时长 ≈ 1:05

一个 AI 服务的 HTTP 成功率是 99.98%，能不能据此宣布可靠性已经达标？

不能。网关返回 200，只能说明某次请求在协议层得到响应。它可能返回了合法 JSON，却没有完成用户任务；可能在三次重试后才成功，用户已经等待二十秒；可能生成了语义错误的退款结论；也可能把高风险任务转给人工，自动链路的成功率看起来很好，真正的任务积压却在增长。

反过来，某天抽样质检正确率下降，也不能立刻推导出“线上正在发生需要叫醒值班人的事故”。样本可能很少，标签可能迟到，任务分布可能变化，质检规则也可能刚升级。这里有一个异常观测，但根因、用户影响和响应时效仍待证据支持。

AI 服务要把 SLI、SLO、错误预算和告警接到工程决策，必须同时回答五个问题：

  1. 对象是谁。 指标在数物理请求、工作流执行、业务任务、用户会话，还是有真值的质量样本？
  2. 什么算好。 协议成功、时延达标、业务完成、语义正确和安全合规不能互相替代。
  3. 什么进入分母。 重试、取消、超时、未知结果、无标签样本和测试流量怎样处理？
  4. 什么时候知道。 请求结果近实时可见，业务结果与人工真值可能数小时甚至数天后才到。
  5. 谁据此行动。 Page、工单、发布冻结、回滚和接受风险必须有不同触发条件与 owner。

本文从事件账本出发，建立 request、task、semantic quality 三组独立 SLI，解释延迟真值、标签覆盖率、错误预算、multi-window burn rate、告警分级、发布冻结与责任人机制，并给出一段只用 Python 标准库、可离线运行且包含故障注入和 unittest 的参考实现。

一、先声明交界：本文不重复什么

本文不重讲这些实现，而只处理它们在可靠性治理中的交界：哪些事件形成 SLI，哪些目标形成 SLO，预算怎样消耗，何时告警，何时阻止发布，以及谁有权作出例外决定。

本文还不把 SLA、合规承诺或客户赔付条款混进内部工程目标。SLA 是外部契约，SLO 是内部目标，二者可以相关，但不应默认数值相同。本文给出的所有业务数字均标为构造示例，不代表任何生产服务，也不构成通用阈值。

二、先给结论：一套可执行的 SLO 系统应满足十四条约束

  1. 先写用户旅程，再选指标。 指标必须对应用户实际等待或依赖的结果。
  2. Request 与 Task 分账。 一次业务任务可能产生多个 attempt，最终成功不能擦掉中间失败。
  3. Good、Bad、Unknown、Excluded 四态分开。 缺失证据不是成功，也不应被静默补成失败。
  4. 协议、延迟、业务完成、语义质量、安全各有判定。 一个指标不能冒充另一层结论。
  5. 质量分母只包含有可接受真值的样本。 没有标签的线上请求不能被伪装成质量 SLO 的成功分母。
  6. 标签覆盖率单独报告。 质量分数必须与覆盖率、标签时延和样本分布一起看。
  7. 延迟从用户可观察边界计时。 服务端模型耗时不能替代客户端端到端等待。
  8. 重试和降级保留原始事实。 成功的最终结果不能覆盖尝试次数、降级质量与额外等待。
  9. 每个 SLO 独立计算预算。 不同分母、时间窗和用户影响不能直接相加成一个“总健康分”。
  10. Burn rate 描述预算消耗速度。 它是告警输入，不是根因定位结果。
  11. Page 只用于需要立即人工行动的可操作风险。 并非所有语义质量异常都适合 paging。
  12. 发布策略必须预先批准。 预算耗尽后冻结什么、谁可豁免、何时解冻不能在事故中临时争论。
  13. 监控本身要测试。 事件上报、规则计算、路由和值班通知都要做故障注入。
  14. 结论标明证据层级。 观测、推断和决策分别记录，不能把告警名称写成根因。

三、术语契约：SLI、SLO、错误预算与告警不是同一个对象

1. SLI specification

SLI specification 描述用户在意的结果，暂不绑定采集方式。例如：

在退款资格审核任务中，从用户提交完整材料到系统给出可执行决定，结果在十分钟内完成且最终决定正确的任务比例。

这是结果语义。它尚未说明从哪个日志取时间、正确性由谁标、缺失事件怎样处理。

5. Alert

告警是对某种需要行动的条件发出的通知。SLO 告警通常回答“预算是否以危险速度消耗”；调试告警回答“某个依赖或资源是否异常”；安全告警可能回答“是否发生单次不可容忍事件”。这些告警可以关联，但不应混成同一规则。

告警触发只是一条观测：某个表达式在某个时间窗超过阈值。它不证明根因是模型、检索、供应商或刚发布的版本。

四、四态事件模型：不要让 Unknown 偷走分母

最小事件分类不是二元成功/失败，而是四态：

good 有完整证据且满足 good 条件 是 消耗 0 个坏事件
bad 有完整证据且不满足条件 是 消耗预算
unknown 本应有证据，但在截止时间缺失、冲突或不可判 否，单独计数 数据质量告警、补数或人工核验
excluded 按事先规则不属于 population 否 保留原因和批准记录

Unknown 必须有独立的覆盖硬门：unknown_rate <= max_unknown_rate。等于已批准上限时仍可继续评价其他门，严格超过上限时，SLO 状态标成 insufficient_data，发布门禁进入 HOLD/BLOCK，不能因为已知样本 SLI 变高而放行。阈值、比较符号和恢复条件都应由组织事先批准；这是决策政策，不是数学自动得出的事实。

反例：丢失失败日志后可用性上升

假设网关只有完成响应时才递增计数。一次后端连接中断让 500 个请求没有产生响应日志，剩余 9,500 个请求全成功。看板显示 100%，用户实际只收到 95% 响应。

问题不是阈值太宽，而是分母在失败路径消失。入口计数器和终态计数器必须独立，二者差值进入 unknown；仅在出口采集无法形成可靠的可用性分母。

五、从入口到决策的分层架构与数据流

建议把系统拆成八层，每层只承担一种主要责任。

1. 用户边界与接入层

客户端、SDK、API 网关记录用户真正发起请求的时间、首个可用内容、最终内容、取消原因、网络失败和可见错误。服务端收到请求之前的失败只能从这一层看到。

2. Request attempt 层

每一次物理调用都有 request_id、attempt_id、开始与结束事件。限流、认证失败、超时、供应商错误、模型响应和网关重试都不能覆盖前一次 attempt。

3. Workflow run 层

Agent、RAG 或多步骤 Workflow 把检索、模型、工具、审批和恢复步骤挂到 run_id。该层记录完成图、首错步骤、降级路径和副作用提交状态。

4. Business task 层

task_id 对应用户要完成的业务目标。它聚合多个 request 与 run，并以业务后置条件决定终态。Task 是完成率、端到端时延、返工和人工接管的主要分母。

5. Outcome 与 label 层

确定性规则、业务数据库终态、人工双标、申诉结果或经过批准的评审器产生质量证据。每个 label 记录来源、rubric 版本、标注者角色、时间和冲突状态。

6. SLI ledger 层

事件分类器按版本化 SLI 规则生成 good/bad/unknown/excluded 判定。原事件不可因规则修改而覆盖；新规则回放形成新的 sli_version。

7. Budget 与 rule evaluation 层

窗口聚合器计算 SLI、标签覆盖、剩余预算、burn rate、低流量置信状态和遥测新鲜度。规则配置作为代码评审、测试和发布。

8. Decision 层

Alert router 只负责把已命名的条件路由给 owner；发布控制器读取经批准的预算政策；事故指挥、产品和服务 owner 基于证据作出回滚、冻结、豁免或继续发布的决定。

六、统一数据模型：原始事实、分类结果和决策记录分离

1. RequestAttempt

attempt_id 必须幂等。同一个逻辑请求被重试三次，应保留三个 attempt。最终成功是 task 结果，不是删除前两个失败的理由。

2. BusinessTask

accepted_at 是任务进入承诺边界的时间，不一定等于用户第一次输入时间。若产品先等待用户补齐材料，应明确哪一刻开始计服务时钟，并在界面和契约中保持一致。

3. QualityLabel

质量标签不能只存一个浮点分数。需要知道评价维度、阈值、真值来源和冲突解决状态。模型自报置信度可以作为诊断特征，不能自动升级为真值来源。

4. SLIClassification

分类结果是派生数据，必须能由原始证据和规则版本重放。reason_code 使用受控枚举，如 UPSTREAM_TIMEOUT、TASK_POSTCONDITION_FAILED、LABEL_PENDING、CLIENT_CANCELLED_AFTER_DEADLINE，避免把自然语言根因猜测写进指标标签。

5. DecisionRecord

发布冻结或告警豁免不是对时间序列的修改。它是基于某组观测作出的独立决定，必须保留 owner、有效期和复审条件。

4. 降级

降级不是天然成功或失败。若产品明确承诺“检索不可用时给出带提示的基础回答”，且用户目标仍完成，可以在 availability 中算 good，同时在 undegraded_quality SLI 中算 bad。若基础回答不能满足高风险任务，则 task 应失败或转人工，不能借降级掩盖。

1. Task completion

3. 人工接管

4. 标签覆盖不是一个总百分比

  • task type 与风险等级；

  • 自动完成、降级、重试和人工接管；
  • 高频常见任务与长尾任务；
  • 随机样本、风险样本、投诉样本和发布样本。

全站覆盖率 5% 可能掩盖高风险退款任务覆盖率为零。报表应同时给总体和关键切片，且展示抽样策略版本。

5. 抽样偏差与置信区间

随机抽样有助于估计总体，风险抽样有助于发现缺陷，二者目的不同。风险样本的失败率不能直接外推总体；随机样本也可能因样本量不足而看不到稀有严重问题。

对二元质量结果，可以报告 Wilson 区间等抽样不确定性，但区间只处理抽样波动，不会修复标签偏差、标注误差、遗漏切片或分布漂移。区间越窄也不等于真值越可靠。

6. 标签迟到

质量 SLO 需要固定 label deadline，例如任务完成后 48 小时。到期前显示 provisional；到期后仍无标签记入 coverage 缺口。迟到标签到达后可以追加修订版本，但要保留原报表生成时间和决策历史，不能悄悄改写一次发布审批当时看到的证据。

反例：把所有未投诉任务算正确

投诉是一个高精度、低召回且受用户行为影响的信号。用户可能没有发现错误、没有时间投诉，或直接离开。1 - complaint_rate 可以是体验指标，不能未经验证就定义为语义正确率。

6. 取消与截尾

用户在阈值前主动改变主意，可能按预定义原因排除；用户因为长时间无响应而取消，应计 bad。系统无法区分时，记 unknown 并改进埋点。窗口结束时仍在途的任务是 right-censored，不应暂时算成功；等待成熟或按 deadline 规则转 bad。

7. 跨机器时钟

不要直接用未校准的客户端墙钟减服务端墙钟。单段持续时间优先用本机单调时钟；跨系统链路用 Trace 顺序、客户端端到端持续时间和时钟偏差监控关联。发现负延迟时必须拒绝该样本并产生遥测质量事件，不能取绝对值“修复”。

十二、目标怎样定：先确定不可接受的用户结果

目标不能从当前线上平均值机械取整，也不能因为行业常见“几个九”就复制。一个可解释的设置过程包含：

  1. 列出关键用户旅程和失败后果。
  2. 区分可重试低价值请求与不可逆高价值任务。
  3. 从用户研究、支持记录和业务截止时间确定什么是可感知失败。
  4. 测量当前基线，但把基线当约束信息，不当用户需求。
  5. 估算达到候选目标所需的容量、冗余、人工与工程成本。
  6. 让产品 owner 接受目标以上继续发布、目标以下转向可靠性工作的权衡。
  7. 设置复审日期，并约定改变 population 或 good 定义等同于新版本。

1. 不同风险层不同目标

“推荐相似文章”和“自动发起退款”不应共享一个聚合目标。前者失败可能只影响体验，后者可能产生资金与合规后果。风险分层后可以有不同 SLO，也可以对高风险动作设置零容忍安全不变量。零容忍性质不必强行转成 99.999% 比例，例如：

十四、错误预算的四种表达

设 SLO 目标为 S，完整 SLO 周期长度为 P。完整周期内有 G_P 个 good 和 B_P 个 bad，某个子窗口 w 内有 G_w 个 good 和 B_w 个 bad。

1. 已观察 SLI

Unknown 和 Excluded 不进入这个值，但必须在旁边报告。

2. 允许坏比例

若 S = 99.5%，则 E = 0.5%。这是目标的代数结果，不代表任何服务都应该选择 99.5%。

3. 完整周期的事件预算

滚动周期的请求量会变化，因此 allowed_bad_events_P 也会随当前完整滚动周期的实际有效事件量变化。报表应保留小数计算并明确最终显示如何舍入；不能先把每分钟预算取整再累加。

4. Budget consumed：窗口坏事件占完整周期额度

低流量反例

一个每小时只有 10 个请求的服务，单次失败就形成 10% 小时错误率。对于严格 SLO，它可能计算出极高 burn rate，但单个样本的统计稳定性很差。Google SRE Workbook 也专门提醒 multi-window burn 方法在低流量服务上会遇到问题，并给出合并服务、合成流量或调整产品影响等方向。

工程上还可以：

  • 对不可重试高价值请求逐事件处置，而不是等待比例；
  • 在 Page 条件外增加最小坏事件数，但记录由此增加的检测延迟；
  • 对可合并的同质任务使用更长窗口；
  • 让合成探针验证基础可用性，同时明确它不代表真实任务分布；
  • 将统计不确定性标记为 low_traffic，交给值班手册处理。

Burn rate 不是错误率

相同 1% 错误率，对 99% SLO 的 burn rate 是 1，对 99.9% SLO 的 burn rate 是 10。告警必须绑定具体 SLO target 和版本，不能只传一个没有上下文的 burn=10。

Burn rate 不是根因

高 burn 只说明用户结果正在快速偏离目标。模型版本、依赖超时、标签规则变化、流量构成、数据丢失都可能造成它。Page 标题应写“任务时限 SLO 快速消耗”，而不是“模型供应商故障”。

十七、语义质量为什么通常不适合直接套实时 Page

语义质量往往具备三个特征：标签迟到、样本较少、判定需要裁决。把每批质检下降直接接到 pager，会产生不稳定且不可立即处置的通知。

适合 Page 的质量相关情况

  • 确定性后置条件显示大量任务产生同类错误副作用；
  • 高风险安全性质被可靠探针或策略执行日志直接证明突破；
  • 新版本上线后，在线可验证的不变量快速失败，且有明确回滚动作；
  • 标签流水线本身故障会让关键发布在错误数据上自动继续，且值班能立即恢复。

更适合工单或工作时段通知的情况

  • 人工抽样正确率在一批标签中低于目标；
  • 某语言切片的质量趋势缓慢下降；
  • 标签覆盖率不足但没有证据表明用户结果已经恶化；
  • Judge 与人工分歧率升高，需要重新校准 rubric；
  • 长尾场景在一周窗口内累积了少量失败。

应只进入报告而非告警的情况

  • 样本量低于事先定义的最低解释条件；
  • 标签未成熟；
  • 单次非高风险主观维度评分波动；
  • 没有 owner、没有运行手册、也没有立即动作的探索性指标。

关键原则是：Page 要同时满足用户影响可信、需要尽快响应、值班人有可执行动作。异常严重度与通知紧迫度相关，却不是同一个字段。

二十、错误预算政策：冻结是风险控制，不是惩罚

Google SRE Workbook 提供的 Example Error Budget Policy 明确标为示例。该示例在前四周预算超出后暂停除 P0 与安全修复外的变更，并强调暂停变更不是惩罚，而是允许团队在数据表明可靠性更重要时集中投入。本文借鉴其政策结构，但不复制数值或适用范围。

AI 服务的预算政策应明确：

  1. 哪个 SLO 状态触发 release_at_risk、frozen 或 manual_approval。
  2. 冻结范围是模型、Prompt、检索索引、工具、应用代码，还是全部生产变化。
  3. 哪些修复性变更、安全补丁和数据纠正可以继续。
  4. 谁能批准例外，例外最长多久，必须附哪些证据。
  5. 如何验证一次变更会减少而不是增加风险。
  6. 何时解冻，是当前 burn 停止、预算重新为正，还是完成指定行动项。
  7. 质量标签迟到时，发布证据需要成熟到什么程度。
  8. 多个服务共享依赖时，预算责任怎样分配而不互相甩锅。

1. 冻结范围要与故障域匹配

若错误来自检索索引更新，不一定要阻止一个独立的监控文案发布；若无法证明隔离，应默认进入人工审批。冻结粒度越细，越需要可靠的变更血缘和依赖图。

2. 修复发布也要门禁

预算耗尽时允许可靠性修复，不等于跳过测试。修复应具备最小差异、可回滚、针对首错性质的回归、影子或小流量验证和明确停止条件。

3. 安全修复优先级

安全补丁可能短期增加可用性风险。政策应让安全 owner 与服务 owner共同评估，而不是让可用性预算机械阻止必要补丁。决定和接受的剩余风险必须记录。

二十一、质量 SLO 与发布门禁的组合

由于标签迟到，质量门禁通常分三阶段：

1. 离线发布集

固定、版本化、有真值的代表性和高风险集合必须通过。它能快速阻止已知回归，但不能证明生产分布质量。

2. 影子与灰度样本

新旧版本在同一任务 cohort 上生成候选，使用确定性断言和盲化标注比较。需要防止只标“有趣”样本，并报告每个切片的覆盖。

3. 生产迟到结果

发布后持续连接真实业务终态与人工标签。当成熟 cohort 低于目标或关键切片失效时，按工单、暂停扩量或回滚政策处理。不能因为发布已经完成就把迟到标签从版本归因中剥离。

二十三、监控数据契约：指标新鲜度本身也是可靠性对象

一个 SLO 看板可能显示绿色，只因为聚合任务停了。至少要监控以下元指标：

1. 双入口计数

在用户承诺边界记录 candidate，在终态记录 result。两者通过稳定 ID 对账。仅采结果会漏掉无结果故障；仅采入口无法判断最终体验。

2. 单调 Counter 与受控标签

Good、bad、unknown、excluded 适合用单调 Counter 累计，再由监控系统计算窗口增量。task_id、user_id、Prompt 文本等高基数字段留在日志或 Trace，不作为时间序列标签。指标标签只保留受控低基数维度，如 SLO 版本、任务类型、风险层、地区和 reason class。

3. 日志与指标同源判定

请求完成时由同一个分类库同时写结构化事件和递增指标：指标用于快速告警，事件用于重放与定位。若两个系统各自复制一套 5xx、超时和排除规则，SLO 报表与 Page 很快会不一致。

4. 迟到与回填

实时指标允许小范围迟到修正，结算账本保留最终事件。对质量标签使用明确 watermark，例如“只结算 labeled_at <= report_cutoff 的标签”。每次回填生成 revision 和差异说明，不覆盖已作决策时的快照。

5. 规则版本

一条 reason code 从 bad 改为 excluded 会直接提高 SLI。此类变更必须像代码一样评审，并在历史固定样本上展示前后差异、受影响数量和业务理由。不能为了让预算恢复而临时改分母。

二十四、自动化策略：从事件单测到值班通知演练

Google SRE Workbook 的 Monitoring 章节建议分三层测试监控：验证程序上报、验证规则计算、验证告警路由。AI 服务可以把它扩展成六层。

1. 事件生产单测

对每个终态验证 good/bad/unknown/excluded 与 reason code。重点覆盖异常路径：连接中断、客户端取消、部分流、超时后迟到完成、人工接管、重复任务和策略拒绝。

2. 分类器契约测试

使用固定原始事件夹具运行版本化分类器，断言每个 subject 只有一个最终分类；Unknown 不会误入 good；excluded 必须有允许的 reason 和批准来源。

3. 聚合数学测试

验证窗口边界、时区、滚动删除、分数精度、无数据、目标为 100% 的非法 burn 计算、低流量标记和迟到修订。使用 Fraction、Decimal 或足够精确的计数比值，避免过早舍入。

4. 合成时间序列测试

构造正常、短尖峰、持续慢烧、故障恢复和交替抖动，断言 multi-window 何时触发、何时恢复以及哪个级别被抑制。每次修改阈值都要跑历史事件回放，估算 Page 数和漏检案例。

5. 路由测试

在非生产通知通道发送带真实标签结构的测试告警，确认团队、地区、服务和严重度能路由到预期队列；验证静默、维护窗、升级与恢复通知不会永久吞掉 Page。

6. 发布政策演练

在测试环境注入预算耗尽状态，确认发布控制器阻止受影响范围、允许经批准的修复路径、记录豁免并在过期后重新阻止。不要等真实事故才第一次验证 owner 是否有回滚权限。

二十五、故障注入：测试的是证据链和决策链

1. 丢终态事件

让入口事件正常、一个原本为 bad 的终态写入失败。期望：任务进入 unknown，known SLI 数值可能因 bad 离开分母而假性上升，但 unknown rate 上升；一旦严格超过 max_unknown_rate，发布门禁进入 HOLD/BLOCK，决策不会随这个假性改善而放宽。

2. 重复投递

同一 classification_id 重放多次。期望：幂等去重，计数不增加；重复率有诊断指标。

3. 时钟偏差

把某节点墙钟拨快，制造 completed_at < accepted_at。期望：样本拒绝并标记 telemetry invalid，不能取绝对值或截为零。

4. 重试风暴

第一次 attempt 大量超时，第二次成功。期望：task delivery 可能保持，attempt availability 和 retry amplification 明显恶化，端到端时延从第一次接受开始。

5. 标签全断

停止标签导入。期望：质量状态是 insufficient data，coverage 降低；不能显示 100%，也不应因“质量下降”直接 Page 服务值班，除非标签系统本身属于立即恢复职责。

6. 标签偏斜

只让中文低风险样本到达，其他切片迟到。期望：总体 coverage 和必需切片 coverage 同时显示，发布门禁不能被总体样本量掩盖。

7. 规则错误分类

把内部容量 429 错误注入为 excluded。期望：历史夹具和 reason allowlist 测试失败；规则差异审计显示预算变化。

8. 聚合器停滞

停止聚合但保留旧时序。期望：freshness 告警先触发，SLO 状态转 invalid；发布控制器不接受陈旧绿色。

9. 告警路由故障

让 Page endpoint 返回失败。期望：路由系统重试、切换备份并从外部探针发现“通知未送达”，不能只在自身失败日志中记录。

10. 低流量单点失败

在十个请求中注入一个普通可重试失败。期望：显示高 burn 与 low-traffic 标记，按 runbook 核验；若该任务是不可逆高风险事件，则走事件级响应而非等待比例稳定。

Label coverage 每个 24h 成熟 cohort 至少 20%，高风险切片至少 50 个 不足时阻止继续扩量

发布政策规定：Task 快速 burn Page 触发后，由服务值班暂停扩量；若错误与当前 canary 高度相关且回滚风险较低，值班可先回滚。模型、Prompt、Workflow adapter 和工具 Schema 变更都属于同一发布单元。安全修复不受普通冻结机械阻止，但要由安全与服务 owner 联合批准。

2. 发布前证据

版本 R-217 的离线集全部通过确定性 Schema、权限和幂等断言；1,200 个分层质量样本中通过率达到预设门槛。影子测试没有真实写队列权限，只验证了工具调用参数和模拟返回。发布评审记录明确写着：影子环境不能证明异步提交终态和生产队列延迟。

这是一个已知剩余风险，不是遗漏说明。团队决定先放 10% canary，并让 task_postcondition_committed SLO 作为在线止损信号。

09:00，R-217 开始承接 10% 流量。

09:12，网关 Request availability 为 99.97%，没有请求 SLO 告警。模型依赖延迟与错误率也在基线范围。

09:18，Task SLO 的 1 小时窗口累计 3,000 个有效任务，其中 150 个超过十分钟仍未提交：

最近 10 分钟有 500 个有效任务，其中 30 个 bad：

长短窗都超过团队自定义阈值 8，SEV-1 Page 触发。通知中 unknown=2、遥测年龄 1 分钟，数据新鲜度通过。

4. 当时可以说什么

观测： Task 提交时限预算正在快速消耗；网关协议响应正常；失败任务高度集中在 R-217 canary；队列消费者总体容量尚有余量；同一时刻没有全局依赖事故。

推断： 新发布是高优先级候选触发因素，且问题位于模型响应之后、业务提交之前。但这些事实还不能证明根因是 Prompt、adapter、队列还是事件分类。

决策： 09:21，服务值班依据预先政策停止扩量并回滚 R-217。这是为了减少继续暴露，不是宣告根因已经找到。发布 authority 同时冻结该发布单元的新功能变更，允许观测修复与针对此问题的最小可靠性修复进入审批。

5. 为什么没有因 HTTP 99.97% 继续发布

HTTP 200 在该版本中只代表系统返回“已接受退款申请”。用户承诺是十分钟内出现可追踪的退款队列记录。Request 与 Task 的用户结果不同，Task SLO 应主导这次发布决策。

如果把异步工具的 202 当 task good，Task 看板也会全绿。该团队提前把提交后置条件作为独立事件，才看见真实失败。

6. 为什么没有等待 28 天窗口耗尽

错误预算政策不是要求等 SLO 已经失败才行动。长短窗 burn 显示当前速率若持续会快速损害周期预算，并且回滚动作明确、可逆、风险较低。团队据此止损。是否回滚仍是政策决定，不是 burn 公式自动执行的物理定律。

7. 根因证据

回滚后 10 分钟短窗下降，说明发布相关性增强，但仍不是单独的因果证明。工程师重放失败 Trace 后发现：

  1. R-217 的 workflow adapter 把写工具返回的 accepted 状态映射为 completed。
  2. 新版随后关闭等待循环并向用户返回成功。
  3. 生产队列在租户级限速下延迟，部分任务十分钟后仍未 committed。
  4. 旧版等待明确的 committed 或到期失败。
  5. 在隔离环境注入队列延迟，可稳定复现新版早退；恢复状态机检查后测试通过。

此时可以把“终态映射错误在队列延迟条件下导致早退”记录为经复现支持的根因。队列延迟是触发条件，不等于队列服务是唯一责任方。

8. 迟到质量标签怎样处理

当天 16:00，首批成熟 cohort 有 600 个 eligible task，120 个完成裁决标签，覆盖率恰好 20%。其中 102 个通过，quality_on_labeled=85%，低于 96% 目标。失败集中在系统向用户声称“已提交”、实际仍排队的答案。

质量结果生成 SEV-2 工单，并作为继续冻结的附加证据，没有再次 Page：事故已经被服务 Page 接管，风险不再快速扩散，值班动作也没有变化。其余 480 个无标签任务保持未知，不被算成质量成功。

高风险切片只有 36 个标签，低于预先要求的 50 个，因此即使总体覆盖达到 20%，发布也不能进入再扩量。质量 owner追加分层抽样，而不是从低风险样本复制结论。

9. 修复、复测与解冻

修复版本 R-218 完成以下证据：

  • 状态机只在 committed 后产生 task good；
  • 注入 accepted 长时间不变、队列限流、重复 callback 和 callback 丢失；
  • 验证用户超时后迟到提交仍保留原 deadline bad；
  • 历史失败 Trace 全部重放；
  • 合法快速提交对照集无回归；
  • 影子环境增加可控异步队列模拟；
  • 5% canary 的 Task 长短窗均低于门槛，unknown rate 正常；
  • 成熟质量样本和高风险切片达到覆盖要求。

发布 authority 在证据包评审后解除该发布单元冻结。解冻记录没有删除 R-217 消耗的历史预算；滚动窗口恢复前，团队仍减少其他高风险变更，并跟踪行动项。

二十八、常见失败模式与反例

1. 用 HTTP 200 / total 代表 AI 质量

协议完整不等于语义正确。应把 request、task 和 labeled quality 分开。

2. 无标签样本默认正确

这会让停止标注成为提高质量的办法。无标签必须进入 coverage 缺口。

3. 只报质量、不报覆盖

10/10 的 100% 与 10,000/10,000 的 100% 证据量不同；更重要的是样本策略和切片代表性可能不同。

4. 从服务端模型开始计用户延迟

排队、网关、网络和重试全部消失。应保留客户端端到端与服务端阶段两个视图。

5. 只看成功请求的延迟

最慢的请求往往超时并被删除，条件延迟变好。用户 SLO 应把未在时限内成功的有效任务记 bad。

6. 所有异常都 Page

没有即时动作的批量质量波动会消耗值班注意力。按用户影响可信度、响应时限和可操作性分级。

7. Page 名称写根因

“模型退化”可能只是推断。通知应命名受影响 SLO，并附候选关联变更。

8. 复制 Google 14.4/6/1

这些值来自文档中的特定 99.9%、30 天设计示例。实际系统必须按自己的周期、阈值、流量和响应能力推导并回放。

9. 预算耗尽后口头冻结

没有范围、owner、豁免和解冻条件的冻结会被绕过。政策必须版本化并接入发布控制器。

10. SLO 规则在事故中临时改分母

这会改变历史事实并破坏信任。可以修正错误分类，但要发布新版本、回放差异并保留决策快照。

二十九、从零落地的四个阶段

阶段一：先建立 Task 身份与入口/终态对账

  • 选一个关键用户旅程；
  • 定义 request、run、task 和 attempt；
  • 在承诺入口与业务后置条件各写事件；
  • 先展示 good、bad、unknown、excluded 原始计数；
  • 对重试、取消、超时和人工接管做夹具测试。

阶段二：发布第一版 SLO 文档

  • 与产品确认 population、good 和用户时限；
  • 选择滚动窗口和数据新鲜度；
  • 指定 owner 与复审日期；
  • 把分类器、聚合规则和 dashboard 配置纳入评审；
  • 先观察历史基线，不立即接 Page。

阶段三：引入预算与告警

  • 从用户结果 SLO 推导 burn 候选；
  • 用历史事件和合成序列调节长短窗；
  • 演练通知路由、抑制、恢复和 runbook；
  • 统计每周 Page 数、可操作率和漏检事件；
  • 低流量与无数据走单独状态。

阶段四：连接质量与发布治理

  • 建立版本化标签、抽样和裁决；
  • 同时报质量、覆盖、时延与切片；
  • 将离线、影子、canary 和迟到生产结果串联；
  • 让预算政策控制扩量、冻结、修复豁免与解冻；
  • 定期故障注入并复审目标是否仍反映用户需求。

三十、上线与运维可执行清单

边界与身份

  • 每个 SLO 明确用户、旅程、scope、population 与风险层
  • Request、attempt、run、task 使用稳定 ID 关联
  • 入口 candidate 与终态 result 可独立计数并对账
  • 重试不会覆盖失败 attempt，也不会重置用户时钟
  • 业务后置条件而非模型输出决定 Task good

分类与分母

  • good、bad、unknown、excluded 四态有版本化 reason 映射
  • Unknown 不会静默变 good 或 bad
  • Excluded 仅允许预先批准原因，并持续报告排除率
  • 取消、限流、部分流、迟到完成和人工接管语义明确
  • 规则变更会在固定夹具和历史数据上输出差异

质量与标签

  • 无可接受真值时质量状态为 insufficient data
  • quality_on_labeled 与 label_coverage 分开显示
  • 抽样策略、rubric、真值来源与裁决版本可追溯
  • 必需 task type、语言、风险与版本切片有覆盖门
  • 模型自评、相似度和未校准 Judge 不冒充真值
  • 迟到标签追加修订，不覆盖历史发布证据快照

延迟

  • client send、首个有意义内容、完整内容和后置提交边界明确
  • 心跳、header 和隐藏 token 不冒充首个可用内容
  • 失败与超时任务不会从用户延迟 SLO 删除
  • 成功条件延迟只作为诊断指标
  • 跨机器墙钟不直接相减，负持续时间会被拒绝
  • 未决任务按成熟截止处理，不暂算成功

预算与告警

  • 每个 SLO 独立计算目标、预算和 burn rate
  • 多窗口条件、最小流量与数据新鲜度经过回放
  • Google 示例参数没有被包装成通用标准
  • Page、工单、看板按响应紧迫度和可操作性分级
  • 语义质量异常只有在证据及时、影响紧急且有动作时 Page
  • 告警载荷包含计数、窗口、版本、freshness、runbook 与 owner
  • 同一事故的 fast、slow、ticket 能去重并正确恢复

发布政策与 owner

  • Service、Product、SLI data、Quality、Alert、Release owner 明确
  • 预算耗尽后的冻结范围、豁免、到期与解冻条件已批准
  • 修复发布仍有最小差异、复测、灰度和回滚
  • 安全修复由安全与服务 owner 联合评估
  • 所有风险接受都有 owner、期限、证据和复审
  • 发布控制器对 stale、unknown 和覆盖不足采取批准过的保守动作

自动化与故障注入

  • 事件生产、分类器、聚合数学、时间序列和路由逐层测试
  • 已注入丢终态、重复、乱序、时钟偏差与聚合停滞
  • 已注入重试风暴、标签中断、切片偏斜与规则误分类
  • 告警传输失败能被独立发现并升级
  • 发布冻结、修复豁免和解冻权限已演练
  • 事故记录明确区分观测、推断、根因证据和决策

三十一、总结

AI 服务可靠性不能压缩成一个 HTTP 成功率，也不能把少量人工标签外推成全量质量。可执行的方法是从用户旅程出发，把 request、task 和 semantic quality 分开建模，并让每个指标拥有稳定身份、明确分母、证据截止时间和独立 owner。

完整闭环可以归纳为十步：

  1. 在用户承诺入口建立 candidate，并在业务后置条件建立终态。
  2. 保留 request attempt、workflow run 与 business task 的层级关系。
  3. 用 good、bad、unknown、excluded 防止缺失证据污染分母。
  4. 从客户端可观察时间建立延迟真值，重试不重置时钟。
  5. 质量只在有可接受真值的样本上计算，并单报标签覆盖与切片。
  6. 将 SLO 目标、窗口、规则、freshness、owner 和政策版本化。
  7. 用错误预算表达允许坏结果，用 burn rate 表达消耗速度。
  8. 通过长短窗、低流量处理和告警分级减少漏检与噪声。
  9. 让错误预算政策真正控制扩量、冻结、修复豁免和解冻。
  10. 用故障注入、历史回放、路由演练和事故复盘持续验证整条链路。

最终应能证明的不是“看板今天是绿色”，而是：

每一个进入 SLO 的好坏结论都有可回放证据；没有真值的样本不会伪装成质量成功；预算危险消耗时通知能在合适时限到达有权限行动的人；发布速度与用户可靠性之间的取舍由预先批准、可审计的政策完成。
