AI测试-49-差分测试怎么比较模型Prompt参数和检索版本

发表于 2026-05-24 分类于 AI测试 本文字数： 18k 阅读时长 ≈ 1:04

模型换了、Prompt 改了、温度调了、Reranker 升级了、索引重建了，怎样判断候选版本能不能发布？

最直接的做法是把同一批问题分别发给旧版和新版，然后“看看答案哪里不一样”。这一步确实能快速产生差异，却没有自动产生结论。

两个系统不一致，可能是：

  • 候选修复了基线错误；
  • 候选引入了回归；
  • 两个答案都符合规范，只是表达不同；
  • 两个答案都错，只是错法不同；
  • 两个答案都错，而且给出了完全相同的错误；
  • 一边使用了更新后的知识或工具状态；
  • 一边超时，报告却只保留成功输出；
  • 裁判偏爱更长答案或某个显示位置；
  • 检索候选改变了文档集合，Prompt 候选又同时改变了引用规则；
  • 总体平均改善，但一个资金、权限或安全切片发生不可接受退化。

因此，disagreement 不等于 truth。差异是调查入口，不是自动 Oracle；一致也不是正确性证明。

差分测试真正有价值的地方，是把同一测试输入送给可比较的多个实现，廉价找出行为分歧，再用规范、确定性 Oracle、业务后置条件、盲化人工或经过校准的裁判判断差异性质。对于 AI 应用，这要求一份比“模型 A 对模型 B”更严格的配对实验合同：

  • 共同输入是否来自同一目标总体；
  • 除目标变量外是否使用同一个外部快照；
  • 每个候选是否是可复现的完整系统工件；
  • 随机 seed、执行顺序、缓存和并发如何配对；
  • 结构、事实、引用、动作、性能和成本差异如何分类；
  • 裁判 A/B 与 B/A 是否一致，是否看见候选身份；
  • 配对统计区间怎样计算；
  • 非劣边际与改善条件何时冻结；
  • 关键严重度怎样作为不可交易硬门；
  • 多候选筛选、归因、灰度与回滚怎样保留证据。

本文建立这套方法。文中的候选数量、样本量、通过率、区间、成本、时延、事故和发布数字，除明确引用论文外，全部是构造示例，不代表任何供应商、模型或真实生产系统。资料范围冻结在 2026-05-24；论文数字只限定在原论文的数据、系统和实验设计内，不能直接外推为生产结论。

二、方法来源：McKeeman 1998 的正式论文及其边界

William M. McKeeman 的《Differential Testing for Software》发表于 Digital Technical Journal，Volume 10，Number 1，1998，pages 100–107。论文以多个可比较 C 编译器为主要例子：同一测试输入交给多个实现，一个实现给出不同结果时，可能暴露缺陷，从而用大量机器执行减少人工逐个计算预期结果的成本。

原论文同时明确指出差分测试的关键难题。生成输入必须足够深入；多个程序不同仍可能都符合规范，因为 C 中存在未指定、未定义或由实现定义的行为；失败测试需要缩减；跨平台执行还要控制环境。这些限制对 AI 系统尤其重要。

不能从 McKeeman 的方法推出：

  • 多数候选一致的一方就是真值；
  • 最老版本一定是 Oracle；
  • 任意两个输出不同都算缺陷；
  • 比较越多候选，根因越清楚；
  • 随机字符串或随意 Prompt 能提供有效覆盖；
  • 编译器的确定性输出假设可以原样套到生成模型；
  • 一次差分可以同时归因到模型、Prompt、参数和索引。

差分测试首先是差异发现机制。真值判断与发布决策仍需要独立证据。

2011 年 Csmith 论文《Finding and Understanding Bugs in C Compilers》进一步展示了随机生成程序、规避未定义行为与多编译器比较的工程价值。论文报告只属于其 Csmith、编译器、时间范围和实验环境。对 AI 的可迁移经验是：输入生成器必须理解规范并减少无效差异，发现后需要最小化和归因；不能拿编译器缺陷数量估算模型质量。

  • 查看中间结果后是否还能沿用原区间解释；
  • 最终候选是否在未用于选择的确认集重跑。

七、分层架构与数据流

7.1 合同与工件注册层

冻结实验问题、候选 manifest、非劣边际、主指标、切片、统计方法和停止规则。候选 manifest 不可用“latest”。

7.2 共同案例与快照层

为每个 case_id 生成 CaseSnapshot，包含输入、会话、有效时间、权限、语料/工具/政策哈希。所有候选只读同一逻辑快照。

7.3 扇出执行层

同一个案例按预注册 seed 扇出到所有候选。执行顺序按区组随机化，限制单个候选总在高缓存或低负载位置。每个物理 attempt 单独保存。

7.4 原始结果层

保留原始输出、检索列表、工具计划、实际副作用、延迟、成本、错误和 Trace。失败和缺失不是空白值，而是差分结果的一部分。

7.5 多 Oracle 层

按风险顺序使用：

  1. 协议与 Schema；
  2. 确定性业务规则；
  3. 引用和证据可达性；
  4. 工具副作用与业务终态；
  5. 密封参考与规则命题；
  6. 盲化人工；
  7. 经校准的 LLM Judge。

后面的信号不能覆盖前面的硬失败。

7.6 配对记录层

每个 case_id × candidate_id × repeat 形成与基线的 PairRecord，保留原始两侧、投影、差值、差异类别、裁判双顺序和外部真值。

7.7 统计与严重度层

计算配对差、区间、四格表、切片、缺失和顺序效应。业务严重度硬门在统计平均之外单独执行。

7.8 发布与回滚层

输出 IMPROVED / NONINFERIOR / INCONCLUSIVE / REGRESSED / INVALID_EXPERIMENT，再映射到影子、灰度、拒绝或回滚。所有决定绑定候选完整工件和证据快照。

八、数据模型：保存逐样本事实，不要只留排行榜

8.1 ExperimentContract

created_before_results_at 用于证明合同不是看到候选分数后补写。修改合同应生成新实验，而不是覆盖时间戳。

8.2 CandidateSpec

changed_factors 是声明，artifact_digest 与逐字段 diff 是证据。若声明只改 Prompt，实际 manifest 还变了 Reranker，实验应标成无效或组合候选。

8.3 CaseSnapshot

同一用户的多轮会话不能当成独立案例随意拆分。source_group_id 用于簇级抽样和防泄漏。

8.4 ExecutionAttempt

最终成功 attempt 不覆盖超时。若候选比基线更常超时，删除失败会让质量和延迟同时虚好。

8.6 JudgeRecord

8.7 DifferenceFinding

truth_status 可以是 baseline_correct、candidate_correct、both_valid、both_wrong、unknown。仅有 disagreement 时默认 unknown。

8.8 ReleaseDecision

  • 冷缓存轮次；
  • 热缓存轮次；

十一、差异分类：从字节到业务终态

11.1 协议与可用性差异

  • 一边超时、崩溃或返回 5xx；
  • 一边 JSON 无法解析；
  • 一边缺少必填字段；
  • Token 截断或流式响应不完整；
  • 重试次数不同。

这是确定性差异，优先于语义裁判。

11.2 结构差异

  • 动作枚举不同；
  • 金额、币种、时间或对象不同；
  • 引用 ID 集合不同；
  • 工具名或参数不同；
  • 审批节点不同。

结构不同仍不等于谁错，但能缩小调查范围。

11.3 允许的表达差异

  • 同义句；
  • 段落与列表格式；
  • 合法引用顺序；
  • 在长度预算内的解释增减；
  • 同一动作的不同礼貌表达。

它们可以标为 BOTH_VALID_DIFFERENT，不进入回归计数。

11.4 事实与证据差异

  • 一边多出未被证据支持的事实；
  • 一边漏掉必要条件；
  • 引用存在但不支持命题；
  • 使用撤回或越权文档；
  • 两边都引用同一错误来源。

最后一种不会产生差异，需要独立文档和事实 Oracle。

11.5 动作与副作用差异

  • 查询与写入不同；
  • 自动执行与人工审批不同；
  • 金额、目标对象或幂等键不同；
  • 工具返回成功但业务终态不同；
  • 一边产生重复副作用。

动作差异通常比文本偏好更高优先级。实际副作用必须在隔离环境或影子模式验证。

11.6 安全与权限差异

  • 一边泄漏敏感信息；
  • 一边绕过租户边界；
  • 一边接受间接提示注入；
  • 一边把低权限用户提升为可执行；
  • 两边都拒绝，但理由和审计字段不同。

安全标签需要明确威胁模型和政策版本，不能用通用“安全分”替代具体控制。

十二、裁判偏差与顺序效应

12.1 三种裁判方式

逐项确定性裁判

检查 Schema、金额、引用和工具终态。可用时优先。

单答评分

分别给每个输出打分。易扩展，但评分尺度可能随裁判版本漂移。

成对偏好

直接判断 A、B 或 tie。对细微差异敏感，但候选数量增加时比较数近似按平方增长，而且容易受位置和长度影响。

12.2 A/B 与 B/A 双顺序

对同一输出对执行：

映射回候选身份后：

  • 两次都选候选 C：形成较强偏好证据；
  • 两次都选基线 B：形成较强反向证据；
  • 一次选第一位置、一次仍选第一位置：位置偏差；
  • 一次 C、一次 tie：不稳定；
  • 两次 tie：没有可分辨偏好。

保守策略是只有两个顺序都选择同一身份才记胜，其余进入 tie 或人工复核。随机单顺序可以在大样本下平衡位置，但不能告诉你某一条关键案例是否被位置翻转。

12.3 候选盲化

裁判不应看到：

  • 模型或供应商名字；
  • “baseline”“new”“premium”等标签；
  • 不同颜色或固定位置；
  • 生成时间和成本；
  • 与质量无关的系统元数据。

盲化映射必须由评测器保存，不能让被测输出自己声明身份。

12.4 长度与格式控制

更长不必然更好。可以：

  • 在 rubric 中单列相关性和冗余；
  • 提供任务允许的长度预算；
  • 构造重复列表失败注入；
  • 比较截去重复内容前后的裁判结果；
  • 同时使用事实和命题覆盖 Oracle；
  • 把答案长度作为裁判诊断变量。

不要简单把两边裁成相同字符数，因为裁剪可能删除关键事实并创造新偏差。

12.5 自偏好和共同盲区

裁判与候选来自同一模型家族时，可能共享表达偏好、训练来源或事实盲区。使用异源裁判也不保证独立。需要用有业务真值的样本校准，并按任务、语言、长度、候选来源和差异难度切片。

12.6 论文结果的适用边界

Zheng 等人的《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》在其 MT-Bench、Chatbot Arena、所选模型和人类投票条件下研究了 pairwise、single-answer 与 reference-guided 裁判，并分析位置、冗长、自增强偏差和推理限制。论文中的人机一致率只属于其采样和定义，不能转写为“LLM Judge 在生产中有固定准确率”。

这项研究给差分流水线的直接启发是：

  • 交换位置能暴露部分位置偏差；
  • 提供有效参考可帮助某些可判定任务；
  • 一致性不等于准确性；
  • 开放偏好、数学正确、安全和业务动作需要不同 Oracle；
  • 裁判必须先在目标任务上对照人工或确定真值。

12.7 裁判变化也是候选变化

升级裁判模型、Prompt 或 rubric 后，不能把新分数直接接在旧时间序列后。应让新旧裁判在同一冻结输出集上差分，量化：

  • 评分尺度漂移；
  • 胜负翻转；
  • tie 率；
  • 顺序一致率；
  • 与人工真值的一致；
  • 各候选来源的偏好变化。

十六、回滚不是重新选模型名

16.1 稳定指针绑定完整组合

回滚只恢复模型而保留新 Prompt 和新索引，可能无法恢复原行为。

16.2 保留期

旧稳定工件至少在灰度和事故窗口内保持可服务。还要保留：

  • 依赖镜像；
  • Prompt 和模板；
  • 索引 manifest 与数据合法性；
  • 工具兼容版本；
  • 缓存命名空间；
  • 评测器与证据；
  • 路由配置。

如果旧模型已下线或旧索引违反当前删除要求，不能盲目回滚到不再合规的版本，需要准备次级稳定候选。

16.3 自动回滚触发

示例：

  • 任一确认 blocker；
  • 候选业务失败率的短窗口与长窗口同时越门；
  • 高风险切片超过预算；
  • 超时或工具副作用异常；
  • 线上配对结果与离线方向显著冲突；
  • 观测数据覆盖不足，无法继续证明安全。

最后一项属于证据保护。自动回滚动作本身必须演练，并防止候选缓存、异步任务或队列在切回后继续产生副作用。

16.4 回滚后仍要归因

回滚恢复服务，不会自动解释事故。应冻结候选输出、配对记录、线上输入、路由概率、工具状态和时间线，再做最小化与消融。否则下一次发布会重复同一问题。

十七、仅用 Python 标准库的完整离线配对实验

下面的代码不调用在线模型，而是构造四个可复现候选系统：

  • stable：稳定基线；
  • prompt-improved：修复一组普通案例；
  • prompt-balanced：修复一例，同时新增一例普通回归；
  • prompt-critical-fault：总体仍有改善，但新增 blocker 错误。

代码实现完整候选 manifest、共同案例、同快照校验、按 repeat 分块且严格平衡的执行顺序、配对输出、四格表、按案例聚合重复、确定性 paired bootstrap 区间、非劣与改善门、严重度硬门、裁判 A/B 与 B/A 顺序检查、故障注入和 unittest。不需要 API Key 或第三方包。

17.1 代码怎样保证配对

run_paired_experiment 对每个 case_id 和 seed 同时执行基线与候选；balanced_execution_schedule 先在每个 repeat 区组内按稳定哈希排列全部案例，再交替分配 B→C 与 C→B，因此每个区组的两种顺序数量最多相差 1。单条记录的哈希奇偶不能保证总体平衡，不能替代这个预生成步骤。两个候选的语料、政策和工具 fixture 必须与合同一致，否则直接抛出 snapshot mismatch，不生成一个看似完整的报告。

17.2 为什么先按案例聚合重复

三个 seed 是同一业务案例的条件重复。aggregate_case_deltas 先计算案例内平均，再让 bootstrap 重采样案例，避免把 40 个案例 × 3 个 seed 伪装成 120 个独立业务对象。

17.3 四格表和区间回答不同问题

n10 显示候选新增失败，n01 显示候选修复；bootstrap 区间表达案例层净差的不确定性。报告同时保留两者，避免净差为正时隐藏具体回归。

17.4 为什么 blocker 先于平均差

prompt-critical-fault 修复了多条普通案例，所以 mean_delta 仍为正；它却在 case-001 产生 blocker。decide_release 先执行绝对严重度门，因此结果为 BLOCKED。这正是“配对统计区间与业务严重度共同决策”的最小实现。

17.5 故意有偏的裁判

judge_once 给左位置固定奖励，并对长文本加分，却完全看不到业务真值。A/B 与 B/A 交换后，映射回候选身份的胜者不同，dual_order_judge 将其标成不稳定。代码没有通过多调用一次就宣称裁判准确，只是暴露位置敏感。

17.6 这个 mock / 模拟不能证明什么

这段程序不能证明：

  • 任一真实模型、Prompt 或索引版本会得到示例中的效果；
  • 构造的 wrong_case_ids 等于真实模型错误机制；
  • 10% 非劣边际适合任何生产业务；
  • percentile bootstrap 在所有离散、小样本或相关数据上覆盖准确；
  • 共同 seed 能让不同模型共享真正相同的随机轨迹；
  • 双顺序一致的 LLM Judge 就是正确裁判；
  • 40 个构造案例代表真实用户总体；
  • 离线动作字段通过就代表工具副作用成功；
  • 候选总体改善具有组件级因果归因；
  • 一次灰度结果可以长期外推。

代码只验证实验框架、快照拒绝、配对聚合、区间实现、严重度优先、顺序偏差检测和已知故障注入能够按预期执行。生产统计方法、margin、样本量、严重度和 Oracle 必须由目标业务重新审查。

18.1 Pull Request 级

19.1 工件注册故障

19.2 共同快照故障

  • 候选语料多一天数据；
  • 基线 ACL 是旧快照；
  • 工具 fixture 中库存不同；
  • 政策有效时间相差一小时；
  • 某一候选读取真实时钟；
  • 检索结果内容相同但文档撤回状态不同。

预期结果是 INVALID_EXPERIMENT 或受影响配对作废，并明确“无法归因”。不应自动把快照更新视为候选改善。

19.3 执行故障

  • 总是先跑基线；
  • 候选享受热 Prompt cache；
  • 基线触发限流而候选没有；
  • 候选超时后静默删除；
  • 重试覆盖第一次失败；
  • seed 列表漏掉候选最后一轮；
  • 多设备任务把 case_id 错配。

必须通过顺序区组、attempt 守恒、配对完整率和关联 ID 检测。只看最终样本数相等不够，因为案例可能错配。

19.4 被测候选故障

  • Prompt 新增“优先第一条证据”；
  • 温度变化导致高风险动作偶发翻转；
  • 新模型输出合法 JSON 但金额字段错；
  • 新索引返回另一个租户的近重复文档；
  • Reranker 把撤回政策排到首位；
  • 工具 Schema 变化使金额单位扩大 100 倍；
  • fallback 路由到不支持所需工具的模型。

每种故障都要有确定性或业务 Oracle。若只能靠“裁判更喜欢哪个答案”发现资金或权限错误，测试层次不够。

19.5 裁判故障

  • 固定选择第一位置；
  • 固定选择更长回答；
  • 看到模型品牌后偏爱某一方；
  • 两个顺序给出相反胜者；
  • 参考答案本身错误；
  • 裁判升级后评分尺度整体漂移；
  • 裁判与候选共享错误政策文档。

预期信号包括顺序一致率下降、重复列表攻击成功、品牌盲化前后翻转、与人工真值偏离。裁判失败应降低语义证据可信度，不应直接给候选判负。

19.6 统计故障

  • 把基线和候选当独立样本；
  • 把三个 seed 当三个独立用户；
  • 在看到结果后改非劣 margin；
  • 只报告点估计；
  • 从 30 个候选里只保留冠军；
  • 将 INCONCLUSIVE 映射为非劣；
  • 总体改善掩盖预注册高风险切片；
  • 对缺失配对做有利删除。

统计代码要有构造数据测试：已知改善、已知回归、完全相同、平衡修复/回归、小样本、全部缺失、极端比例和簇内完全相关。

19.7 门禁与回滚故障

  • blocker 进入加权平均；
  • 门禁服务超时后默认放行；
  • 豁免过期仍生效；
  • 自动回滚只换模型，不换 Prompt 和索引；
  • 回滚后候选异步队列继续执行；
  • 新旧缓存共享命名空间；
  • 回滚指针指向已删除工件；
  • 回滚完成但没有验证业务终态。

发布演练至少证明：触发信号可达、决策可审计、稳定工件可服务、候选副作用能停止、缓存能隔离、恢复指标能回到预算。

19.8 组合故障

构造一次更真实的演练：

正确系统应由 ACL 硬门最先阻断；裁判胜率和正区间不能放行；回滚演练应发现索引仍在候选版本。这个组合验证“统计与严重度共同决策”是否真正落实到控制面。

  6. Reranker 是否改变过滤边界；
  7. 生成端是否伪造不存在的文档 ID。

原始检索 Trace 证明越权 ID 真实来自 idx42，不是生成伪造。查询请求的 tenant 和过滤表达式正确；Reranker 输入已经含越权文档，因此问题在它之前。两个索引语料截止时间相同，排除“新数据带来差异”。

20.7 根因确认

idx42 的新去重算法先按规范化内容哈希合并近重复文档，再选择一个代表文档。构建器错误地把代表文档 ID 写入所有重复成员的 posting，却只保留代表文档自己的 ACL。两个租户拥有文本近似但权限不同的操作手册时，查询可能通过本租户成员命中簇，最终返回另一个租户的代表 ID。

最小复现只需要两份内容相同、tenant 不同的文档。恢复“ACL 是去重键的一部分”后失败消失；再次移除 ACL 维度后稳定复现。构建日志与代码 diff 共同确认根因。

贡献因素：

  • manifest 只校验 ACL 快照文件哈希，没有校验 posting 到代表文档的权限守恒；
  • 去重离线指标只看压缩率和近重复召回；
  • 探索集租户文档重叠不足；
  • 单顺序裁判偏爱更长、引用更多的候选答案，制造额外正面信号；
  • 团队最初关注总体提升，幸好硬门独立执行。

20.8 回滚与清理

虽然候选尚未交付，控制面仍执行候选撤销：

  • candidate-index 指针恢复为无流量；
  • 删除 idx42 的预热缓存命名空间；
  • 取消尚未执行的影子查询；
  • 保留 idx42 对象只供受限取证，不再可路由；
  • 验证稳定版仍指向 idx41；
  • 检查没有异步摘要由越权文档生成；
  • 将 7 个案例提升为永久 blocker 回放。

如果只回滚模型，索引风险不会消失；这证明回滚单位必须是完整系统组合。

20.9 修复与重新决策

修复包括：

  1. 去重键加入 ACL 等价类和租户边界；
  2. posting 写入后执行“查询主体可访问最终文档”的确定性审计；
  3. 索引 manifest 增加 ACL 守恒统计与随机抽样证据；
  4. 构建器加入跨租户近重复失败注入；
  5. 查询层在返回前再次执行文档级权限检查；
  6. 裁判报告默认使用双顺序稳定结果；
  7. 硬门先于总体统计出现在发布摘要顶部。

新候选必须重新构建 artifact digest，并在同一合同和全确认集上执行。旧的 +1.4 个百分点不能直接转移到修复候选，因为 ACL 去重变化可能改变召回和质量。

20.10 案例结论边界

可确认的是：

  • idx42 在冻结确认集上总体主指标改善；
  • 同一候选新增 7 个 ACL blocker；
  • 根因位于去重代表文档的权限映射；
  • 发布阻断与候选撤销是正确决策。

不能确认的是：

  • 新去重算法在所有未来语料上都不安全；
  • 生成模型导致了越权；
  • 单顺序裁判的全部偏好都来自位置；
  • 修复版必然保留原质量收益；
  • 离线 2,400 个案例完全代表生产。

这种边界写法比“新索引虽然更准但有安全问题”更可审计。

二十一、排障手册：从差异回到最小可复现因素

21.1 先看实验是否有效

任一答案为否，先修实验。无效实验不能支持候选优劣。

21.2 再看差异在哪一层出现

寻找第一个有证据的分叉点，而不是直接阅读最终自然语言猜根因。

21.3 最小化

保留触发差异所需的最少：

  • 会话轮次；
  • 文档；
    -工具字段；
  • Prompt 片段；
    -候选变量；
  • seed；
    -权限和时间状态。

最小化过程中每次只删除一个因素，并确保差异仍可复现。自然语言最小化可能改变语义，必须重新验证案例有效性。

21.4 消融与重放

对单因素候选可恢复旧因素；对组合候选建立中间点：

矩阵不一定全跑，但关键交互需要实证。若结果只在最终组合出现，不能把责任分给单个组件。

二十二、从零到一实施顺序

阶段一：建立候选身份

先让模型、Prompt、参数、索引、工具、策略和运行时都有不可变版本和摘要。没有完整工件，不开始效果排名。

阶段二：建立共同案例与快照

冻结 case_id、输入、有效时间、权限、政策、语料和工具 fixture。实现 PairRecord 并保留每次 attempt。

阶段三：先接确定性 Oracle

接入协议、Schema、金额、权限、引用来源和业务后置条件。用四格表区分修复、回归和共同失败。

阶段四：加入语义裁判

只覆盖确实无法确定性判断的开放维度。候选盲化、双顺序、人工校准和裁判版本化必须一起上线。

阶段五：实现配对统计

在看到候选结果前确定主指标、margin、区间、切片、样本和停止规则。按案例或自然簇重采样。

阶段六：候选矩阵与确认集

探索单因素候选，保留所有尝试；最终组合在密封确认集重跑，防止冠军偏差。

阶段七：接入影子、灰度和回滚

将离线证据映射到线上停止条件，演练完整组合回滚、缓存隔离、异步任务停止和业务终态验证。

二十三、可执行检查清单

问题与声明

  • 已写清比较要支持的发布决策
  • 已指定目标总体，而非只给 benchmark 名称
  • 已明确输出差异不等于真值
  • 已准备共同错误和双方都合法的反例
  • 已区分改善、非劣、相等和不确定
  • 非劣候选有预声明的成本、延迟、可用性或隐私收益

候选矩阵

  • 基线绑定完整不可变工件
  • 每个候选绑定模型、Prompt、参数、检索、工具、策略和运行时
  • changed_factors 与 manifest diff 一致
  • 单因素候选和组合候选分开
  • 组合结果不被错误归因给单组件
  • 使用可变别名时已记录不可冻结限制
  • 所有探索候选都留在实验台账
  • 最终候选在独立确认集重跑

共同输入与快照

  • 每个案例有稳定 case_id 和自然簇 ID
  • 用户输入、会话、身份、权限和有效时间已冻结
  • 比较生成时冻结了相同检索结果
  • 比较检索时冻结了相同语料截止点和 ACL
  • 政策与工具 fixture 一致
  • 快照差异会让实验无效，不会被计成候选效果
  • 缓存冷、热和共享边界明确
  • 输入和快照哈希进入证据包

配对执行

  • 所有候选运行同一案例清单
  • seed 清单在运行前冻结
  • 共同 seed 的实际语义经过验证
  • 候选执行顺序使用平衡区组
  • 每个 repeat 与 attempt 分开
  • 重试不覆盖原失败
  • 超时、取消和缺失不会被静默删除
  • PairRecord 能回到两侧原始输出和 Trace
  • 案例错配和重复配对有自动检测

差异与 Oracle

  • 协议、结构、事实、引用、动作、安全、性能分别分类
  • 允许表达差异不会进入回归
  • 双方共同失败显式可见
  • 多数一致未被当成真值
  • 基线未被默认当成 Oracle
  • 资金、权限和副作用使用确定性后置条件
  • UNKNOWN_TRUTH 是允许状态
  • 原始差异、真值状态和根因状态分开

裁判

  • 候选身份、品牌和新旧标签已盲化
  • A/B 与 B/A 结果映射回同一候选身份
  • 顺序翻转不会被强制判胜
  • 长度、重复和格式偏差有失败注入
  • 参考答案版本和适用域明确
  • 裁判在目标任务上与人工或确定真值校准
  • 裁判模型、Prompt、rubric 和采样参数已版本化
  • 裁判升级后在冻结输出集上做过差分
  • 裁判一致不被表述成业务正确

配对统计

  • 主指标方向和单位明确
  • 差值按同一案例计算
  • 二元结果保留 n11/n10/n01/n00
  • 不一致率与净改善率分开
  • 重复先按案例或自然簇聚合
  • 区间方法和 alpha 在看结果前冻结
  • margin 来自业务损失预算
  • 区间跨门时返回 INCONCLUSIVE
  • 零差异不被表述成两者等价
  • 多候选选择和多切片问题已处理
  • 点估计、区间、样本量和缺失同时报告

严重度与发布

  • blocker 在平均统计之外独立执行
  • 高风险切片有单独门和最低证据
  • 总体改善不能抵消越权、泄漏或错误资金动作
  • 非劣只支持“未越过 margin”，不写成更优
  • 性能和成本收益以质量完整为前提
  • 证据无效可以阻止发布
  • 例外有范围、负责人、缓解、到期和回滚触发
  • 发布结论限定到数据、快照、候选和时间

归因与回滚

  • 观察、推断、排除、消融和确认分开记录
  • 找到了最早有证据的分叉层
  • 最小复现仍保持业务语义
  • 隐藏供应商变化被列为限制
  • 稳定指针包含完整系统组合
  • 旧工件在回滚窗口内可服务且合规
  • 缓存、队列和异步副作用纳入回滚
  • 自动回滚触发与恢复条件已演练
  • 回滚后仍冻结候选证据并完成归因

二十四、总结

差分测试不是让两个模型互相当答案，也不是让多数候选投票产生真值。它是一种高吞吐的差异发现方法，只有和共同输入、同快照、独立 Oracle、配对统计、严重度门和可回滚工件结合，才能支持发布。

完整方法可以归纳为十三步：

  1. 把每个候选注册为模型、Prompt、参数、检索、工具、策略和运行时的完整工件。
  2. 在看到结果前冻结问题、目标总体、主指标、margin、切片、样本和停止规则。
  3. 对所有候选使用共同 case_id、权限、时间、政策和工具快照。
  4. 比较生成时冻结检索结果，比较检索时冻结语料源与非目标组件。
  5. 用配对 seed 和平衡执行顺序减少无关波动，并保留全部 attempt。
  6. 将协议、结构、事实、引用、动作、安全、性能和成本差异分层。
  7. 用确定性规则、业务终态、人工和校准裁判建立真值，承认未知。
  8. 对裁判执行身份盲化和 A/B、B/A 双顺序，检查长度与自偏好。
  9. 保存 n11/n10/n01/n00，让候选修复、回归与共同失败同时可见。
  10. 按案例或自然簇计算配对差和统计区间，避免伪独立。
  11. 用区间判断改善或非劣，用业务严重度阻断不可交易风险。
  12. 对单因素做受控归因，对组合候选只声明组合效果。
  13. 将候选完整工件接入影子、灰度、自动回滚和事故证据冻结。
