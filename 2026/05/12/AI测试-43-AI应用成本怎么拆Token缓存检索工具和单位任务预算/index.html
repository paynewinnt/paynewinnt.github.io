AI测试-43-AI应用成本怎么拆Token缓存检索工具和单位任务预算

发表于 2026-05-12 分类于 AI测试 本文字数： 16k 阅读时长 ≈ 58 分钟

一个 AI 应用本月模型账单下降 20%，能不能说明优化成功？

不一定。它可能把更多请求转给了人工，可能关闭 rerank 后让任务返工，可能把失败重试记在另一个项目，也可能因为回答变短而降低业务完成率。反过来，模型 Token 成本上升也不一定是退化：系统可能增加了必要证据、减少人工复核并提高一次任务完成率。

成本治理最常见的错误，是把厂商控制台上的 Token 总额直接除以 HTTP 请求数。这个公式遗漏了至少三层事实：

  1. 一个用户任务可能包含多次模型请求、检索、rerank、工具、网络和重试。
  2. 目录价、合同后价格、账单实际成本与分摊到业务的成本不是同一个数。
  3. 请求返回 200、JSON 合法或模型置信度较高，并不代表任务被业务验收。

因此，真正需要建立的是一套从使用事件到业务结果的成本账本：每一笔量来自哪里，按哪一版价格计算，属于哪个 request、run、task 和 tenant，失败是否被保留，共享 GPU 或平台成本如何守恒分摊，最终每个合格业务任务消耗了多少成本。

本文建立这套完整方法，覆盖输入、输出、reasoning、cache write/read/storage、embedding、rerank、vector DB、工具、网络、重试、失败浪费、人工复核和自建推理摊销；明确区分 list price、effective cost、allocated cost 与 quality-adjusted unit cost；并给出不需要真实 API Key 的 Decimal 账本、预算门禁和自动化测试。

所有厂商价格均具有时间、产品、模型、区域、上下文长度、服务层和合同条件。正文不写死任何厂商单价，代码中的费率全部是构造参数。资料与官方价格页面核对截止 2026-07-26，不能把该日快照当作永久事实。

一、先给结论：成本控制对象应是合格任务，不是便宜 Token

一套可用的 AI 成本系统至少遵守十二条原则：

  1. 原始用量与价格分离。 用量事件不可因价格更新而改写，价格簿必须有生效区间和来源。
  2. 计费项互斥。 cached input、reasoning 等如果已经包含在总量中，不能再无条件相加。
  3. 一次物理调用一个 request/attempt。 重试不得覆盖第一次失败。
  4. 一次工作流执行一个 run。 模型、检索、工具和恢复步骤都挂在同一执行图上。
  5. 一个业务目标一个 task。 多个 run、人工补救和延迟结果最终归到任务。
  6. tenant 是责任与隔离边界。 产品、客户、成本中心和环境维度要稳定，不能靠 Prompt 文本猜。
  7. List、Effective、Allocated 分开。 目录价基线、实际经济成本和责任分摊回答不同问题。
  8. 失败成本不删除。 超时、取消、废弃回答和工具重试都是已经消耗的资源。
  9. 共享成本按版本化规则守恒分配。 分摊和必须等于来源成本，未分摊部分显式保留。
  10. 预算门禁是估算与预留，不是精确预言。 运行中还要持续扣减，结束后再用实算校正。
  11. 任何成本优化都受质量与安全底线约束。 HTTP 200、Schema、相似度和模型置信度不能代替业务验收。
  12. 报表必须可对账。 账本与供应商账单可能因延迟、税费、信用和舍入暂时不同，但差异要能解释。

二、工程定义与边界：先区分价格、成本、预算和价值

1. List Price 与 List Cost

list price 是某个 SKU 在特定条件下公开或标准的单位价格，例如每百万 Token、每千次工具调用或每 GB-day。它本身不是本次使用的总成本。

FOCUS 1.3 将 List Cost 定义为 List Unit Price 与 Pricing Quantity 的乘积，并用于与 Contracted、Billed、Effective Cost 比较。本文沿用这个思想，但 AI 内部账本还要增加模型、服务层、上下文区间和计费项等细粒度维度。

2. Contracted、Billed 与 Effective Cost

  • contracted_cost：合同单位价乘计价数量，反映谈判折扣，但不一定包含承诺购买的摊销。
  • billed_cost：发票或应付账单基础，接近现金口径；预付、信用、税和调整会影响它。
  • effective_cost：将折扣及相关预付/承诺购买按规则摊销后的经济成本，更适合观察消费趋势。

FOCUS 1.3 对 Effective Cost 的定义强调折扣与预付购买的摊销，并明确同一账期 Effective Cost 总和可能与发票总和不同。本文的内部 effective_cost 应尽量与采购/FinOps 的批准口径对齐；在账单未到时可以先标记为 estimated，不能假装已经实算。

3. Allocated Cost

allocated_cost 是把 effective cost 归属到 request、run、task、tenant 或产品后的责任成本：

它不是厂商原生价格概念，而是组织内部责任口径。分摊方法必须公开：按有效 Token、GPU-seconds、预留显存、任务数、活跃用户、收入，还是固定比例。FOCUS 1.3 的 split cost allocation 要求分摊记录在可聚合指标上加总回来源记录，并记录方法标识和细节；这个守恒原则非常适合 AI 成本账本。

5. Budget

预算是对未来允许消耗的约束，不是已发生成本。至少区分：

  • task 硬上限：单任务超过即停止或转人工
  • run 软上限：接近时降低非必要步骤或请求审批
  • tenant 周期预算：日、周、月的总额和增长率
  • 风险预算：高价值任务允许更高成本，但安全底线不变
  • 预留额：在异步调用开始前占住最坏合理成本，结束后释放差额

把账单告警称为“预算控制”太晚了；控制必须在请求前和运行中发生。

三、四级身份模型：Request、Run、Task、Tenant

成本无法归因，通常不是缺一列 cost，而是身份模型不稳定。

1. Request

Request 表示一次对外部模型、内部推理、embedding、rerank、vector DB 或工具的物理调用 attempt。至少包含：

2. Run

Run 表示一次工作流执行图。一个 run 可以包含多个模型请求、检索、工具和校验，也可能因为恢复策略生成分支。它至少包含：

Agent 循环中“又想了一次”不是免费内部行为：只要产生可计量调用，就必须形成 request 并挂到 run。

3. Task

Task 是业务目标，例如“完成一张工单分类并落库”“生成一份通过审核的合同摘要”“完成一次退款资格判断”。一个 task 可能经历：

  • 初次自动 run
  • 自动 retry run
  • 降级 run
  • 人工复核与纠错
  • 延迟到达的业务真值

Task 才是单位经济分母。HTTP 请求、对话 turn 或模型调用不一定等于一个任务。

4. Tenant

Tenant 是成本责任和数据隔离边界，可以映射客户、产品线、成本中心、环境或内部团队。建议使用稳定 ID，并把展示名、组织变更和结算关系放到维表。不要直接把用户输入中的公司名当 tenant，也不要让模型决定成本归属。

四、完整架构：从原始事件到可对账单位经济

推荐把系统拆成七层。

1. Usage Collectors

从供应商响应、网关、SDK、推理引擎、检索服务、工具平台、云账单和人工系统采集原始用量。Collector 只负责忠实记录，不在边缘节点写死最终价格。

2. Provider Adapters

把厂商字段映射到内部语义，但保留原始 payload、文档版本和映射版本。适配器必须处理“总量包含子量”的关系，不能把名字相似的字段直接求和。

3. Price Book

价格簿由 provider、SKU、region、service tier、usage kind、unit、currency、valid_from、valid_to、来源 URL 和合同版本组成。费率变更追加新版本，不覆盖历史。

4. Immutable Ledger

将用量与当时有效价格结合，生成不可变成本分录。更正通过冲销和新分录完成，不能直接修改历史金额。每条分录记录估算/实算状态、舍入规则和来源。

5. Allocation Engine

把共享池成本按版本化方法分给对象，输出来源、权重、比例、分摊金额和未分摊余量。引擎执行守恒检查和重复检查。

6. Outcome Join

将 Task 的业务后置条件、质量、安全、人工裁决、申诉和最终真值连接到账本。质量数据可以晚到，因此单位成本需要 provisional 与 final 状态。

7. Controls and Views

同一事实层提供预算门禁、预测、异常检测、showback、chargeback、优化实验和财务对账。不同视图不应各自重算一套成本，否则定义会漂移。

五、原始用量模型：观测事实不要先压成一个 total_tokens

建议保存三层数据。

1. Raw Observation

原始响应可能包含敏感内容，usage 通常可以与内容分开保留。对账需要 provider request ID、时间、项目和 SKU，不一定需要保存 Prompt 全文。

2. Normalized Usage Event

一个 observation 可拆成多个互斥事件，例如 uncached input、cache read、visible output、reasoning、tool call。事件数量允许为零，但缺失与零要区分。

3. Cost Entry

同一用量可以生成多种估值列，却不能生成多条都进入总额的重复分录。

输出至少区分用户可见文本、结构化字段、工具调用参数、音频/图片等 modality，以及供应商报告的总输出。流式取消后，供应商已经生成但客户端未收到的 Token 仍可能计费，需保留 delivered 与 billed 两个状态。

八、Embedding、Rerank 与 Vector DB：检索链路不是免费前处理

本文不重复通用 RAG 召回率、忠实度与可追溯性评测，而只讨论成本归集及其与已有质量结果的连接。

1. Embedding

区分离线索引和在线查询：

  • 文档切分后的 embedding Token
  • 查询 embedding Token
  • 模型/维度/批处理模式
  • 重建索引、失败重试和重复写入
  • 多语言或多模态编码

离线重建不能全部压到某一次在线请求。可按索引版本受益窗口、文档数、查询量或业务所有权分摊，并保留未摊余额。

2. Rerank

可能按请求、文档对或 Token 计费。必须记录候选数、实际送入数、截断和失败。把 top_k=100 改成 20 可能降低成本，也可能降低目标任务质量；优化门禁应连接独立检索/任务评测。

3. Vector DB

成本可能来自查询、读写单元、容量、索引、备份、节点、复制、网络和最低承诺。在线 query 能直接归属 request；基础容量与闲置部分属于共享成本。仅按 API 查询次数分摊，可能让大向量、高过滤开销或跨区流量被错误平均。

4. 数据处理

解析、OCR、切分、清洗和增量同步也会消耗计算与人工。它们不一定进入每次任务边际成本，却应进入产品总拥有成本和索引版本摊销。否则 SaaS 模型看起来昂贵，自建数据管道却被当作免费。

九、工具与网络：一次 Agent 任务可能有多种计费单位

1. 内建工具

Web search、file search、code execution、容器、地图或第三方连接器可能按调用、会话、搜索查询、存储和附加 Token 收费。工具返回内容进入后续模型上下文时，还可能再次形成输入 Token 成本。

截至资料日期，OpenAI、Anthropic 与 Gemini 的官方价格页面均展示了 Token 之外的工具或缓存计费维度，但产品、模型和条件各不相同。账本必须按实际产品快照建 SKU，不能维护一个永远有效的“搜索一次多少钱”常量。

2. 自定义工具

自定义工具即使没有供应商调用费，也有：

  • 第三方 API 费用
  • 内部服务计算、数据库和队列
  • 凭证、审计和安全网关
  • 幂等查询与对账
  • 超时后仍执行的副作用

工具返回成功只说明协议结果，业务后置条件仍需校验。

3. 网络

网络成本可能按跨区、跨云、互联网出口或 CDN 计价。长检索证据、图片、音频和多 Agent 传输会放大它。记录源区域、目标区域、字节和方向；不要用 Prompt Token 推算所有网络字节。

4. 双重成本

一次搜索可能同时产生工具调用费、搜索内容 Token、普通输入/输出 Token和网络。它们是不同事件，不是重复；但同一个搜索内容 Token 如果已经包含在输入总量，又不能再按普通输入外额外加一次。关键在于使用供应商官方计费语义定义互斥项。

十一、人工复核：自动化系统最容易漏掉的成本

人工成本至少包括：

  • 正常审批或复核分钟数
  • 纠错、重写和补录
  • 申诉、退款或事故处理
  • 标注与质量抽样
  • 专家升级与等待占用
  • 培训和规则维护

2. 人工不是失败垃圾桶

十二、自建推理摊销：GPU 小时价只是成本的一部分

1. 成本池

自建推理至少包含：

  • GPU/加速器租赁或折旧
  • CPU、内存、本地盘和对象存储
  • 电力、机房和网络
  • 集群、编排、负载均衡与观测
  • 模型下载、镜像、冷启动和缓存
  • 预留但未使用的容量
  • 工程维护、值班和升级验证
  • 故障冗余与灾备

3. 闲置成本不能消失

将成本只分给实际请求会导致低利用率时单位成本急升，这正是事实。也可以把“业务使用成本”和“平台闲置成本”分开 showback，但两者加总必须等于成本池。不能用理论满载 Token 数做分母，把闲置当作不存在。

4. 自建与 API 的可比边界

比较应使用同一质量、可用性、区域、合规、尾延迟和业务任务。API 价格可能包含托管和弹性，自建成本可能包含长期承诺；只比一百万 Token 单价会遗漏利用率、人工和故障余量。

十三、价格簿设计：厂商价格是带版本的外部配置

1. Price Key

缺任何会改变价格的维度，都可能把历史请求套上错误费率。

2. 来源与批准

每版价格记录：官方 URL、抓取时间、人工复核人、合同附件摘要、税前/税后、汇率来源和审批状态。公开价格变化不应自动覆盖合同价；合同价也不能公开到不该访问的报表。

3. 价格快照策略

至少在以下时点快照：

  • 厂商公告或页面变化
  • 模型/产品版本上线
  • 合同或承诺购买生效
  • 区域、服务层或上下文档位变化
  • 账单出现未知 SKU

代码配置中只引用 price_book_version，不散落单价常量。

4. 价格页面的时间边界

截至 2026-07-26，官方页面展示的模型、缓存、批处理、工具和存储项目会随产品变化。本文参考资料保留这些页面用于核对，但不会把某个单价写成架构事实。实施时应归档组织有权使用的当日快照，并遵守页面和合同条款。

十四、计价规则：Decimal、单位和舍入不能靠感觉

1. 禁止二进制浮点计钱

0.1 + 0.2 的二进制浮点表示不精确。账本使用 Decimal 或数据库定点数，从字符串解析费率和数量。对 Token 这类整数数量仍使用 Decimal 计算金额。

2. 统一单位

供应商可能写 per token、per 1K、per 1M、per call、per second、per GB-day。价格簿应明确 pricing_unit 和 unit_size，规范化时进行量纲检查。token 与 token_hour 不能因名字相近相加。

3. 舍入时机

中间计算保留足够精度，在合同规定的结算层级舍入。每请求先四舍五入到分再求和，会让大量微额请求全部变成零；只在月末舍入又可能与供应商逐项目账单不同。账本同时保留高精度计算额和结算额。

4. 多币种

原币成本、汇率、汇率日期和本位币金额分别记录。不同币种不能直接求和。汇率变化属于财务因素，不应被误判为 Token 优化回归。

十五、分摊设计：守恒、可解释、可回放

1. 直接归属优先

模型 request、在线检索、工具和人工处理如果已有 task/tenant，直接归属，不要再按比例平均。

2. 共享成本分配

常见规则：

成本池 可选因子 风险
GPU 池 GPU-second、Token、KV token-second 指标缺失时可能偏向某类任务
Vector DB 容量 索引字节、查询量、租户文档量 公共索引收益难划分
平台基础设施 活跃 task、直接成本比例、固定配额 小租户可能被不合理分摊
人工质检 抽样任务或业务线 公共改进工作需单列
预付承诺闲置 预留份额或平台中心 全部分给活跃请求会扭曲边际成本

3. 分摊事件

若规则更新，生成新 allocation version；历史财务已关闭时按更正流程处理。

4. 守恒检查

任何不等都阻止发布到 chargeback。比例总和为 1 仍不够，还要检查同一来源是否重复参与两次分摊。

十六、Showback 与 Chargeback：透明和结算不是同一动作

showback 向团队展示其用量与分摊成本，不实际转移预算；适合先发现标签缺失和规则争议。chargeback 将金额记入成本中心或内部结算，对数据完整性、审批、账期冻结和更正要求更高。

建议演进：

  1. 先做覆盖率和对账，标出 estimated 与 unallocated。
  2. 运行 showback，让业务验证归属和分摊解释。
  3. 对稳定直接成本启用 chargeback。
  4. 对高争议共享成本保留平台中心或只 showback。
  5. 账期关闭后使用冲销与补充分录，不静默改历史。

成本报表必须允许从 tenant 下钻到 task、run、request、usage event 和价格版本，同时受权限控制。只给总额而无法解释，会让 chargeback 失去信任。

十七、预算门禁：事前估算、运行中预留、事后实算

1. 事前估算

2. 预算预留

异步并发步骤启动前先预留可能成本，防止多个分支各自看到同一剩余额度。步骤结束后以实算释放差额。预留服务需要幂等键、TTL 和崩溃回收。

4. 质量底线优先

候选路由即使预算内，只要其目标任务质量、安全或能力低于最低契约，就不能自动使用。预算门禁返回的是 authorized_to_spend，不是 business_correct。

十八、估算误差：预算系统必须承认自己会错

至少报告：

对 actual=0 或 estimate=0 需单独定义，避免除零。总体可使用 WAPE，并按任务、模型、路由、输出长度和失败类型切片。

1. 偏低估的来源

  • 实际输出或 reasoning 长于预计
  • Agent 循环、工具重试和恢复分支

  • 价格簿漏掉工具、网络或存储
  • 人工复核晚到

2. 偏高估的来源

  • 提前满足停止条件
  • cache 命中更高
  • 路由到更低费率层
  • 用户取消且供应商未产生完整用量
  • 预留按最坏上限，实际较短

3. 校准动作

预测分布按最近稳定窗口更新，但价格和策略变更后分段建模。只把 P95 乘一个越来越大的安全系数，会降低预算利用率；应修复最主要误差来源。

2. 分母攻击

成本看板常见的“美化”方式：

  • 把模型调用数当任务数，一个 Agent 循环产生多个“单位”

二十二、成本指标体系：从覆盖、对账到业务结果

1. 数据健康

覆盖率不足时，总成本图应标记不完整，不能默认缺失为零。

2. 对账

按账期、币种、账号、SKU 和区域逐层下钻。差异可能来自账单延迟、信用、税、最低消费、舍入和未知 SKU。

3. 使用强度

  • input/output/reasoning Token per task
  • cache write/read/storage per task
  • embedding Token、rerank documents、vector queries per task
  • tool calls、network bytes、attempts 与 Agent steps per task
  • human minutes per accepted task

4. 成本

  • list、contracted、billed、effective 与 allocated cost
  • direct/shared/unallocated cost
  • failure waste、retry cost、cancelled-but-billed cost
  • cost per request/run/task/tenant
  • quality-adjusted unit cost

5. 效率与价值

  • cache net saving，而非只看 hit rate
  • effective/list cost ratio
  • accepted tasks per GPU-hour
  • cost per avoided human minute
  • cost per incremental accepted task
  • 优化的净节省与回收期

“节省”必须指定反事实基线。目录价减 effective cost 是采购/承诺节省，不等于工程优化节省；模型切换前后成本差需要控制质量和任务 mix。

二十三、成本异常检测：先分解数量、费率、Mix 和质量

总成本变化可近似分解：

异常检测分别观察：

1. Volume Anomaly

任务数或租户数增加。可能是业务增长，也可能是重复消费、队列回放或攻击。检查唯一 task、幂等键与来源。

2. Usage Intensity Anomaly

每任务 input、output、reasoning、检索候选、工具和步数上升。常见根因是 Prompt 膨胀、历史未裁剪、Agent 循环和工具返回过大。

3. Rate Anomaly

相同 SKU 的有效单位价变化。检查价格版本、服务层、上下文档位、区域、合同和汇率。不要把价格变化归因于 Prompt 优化。

4. Mix Anomaly

更多任务路由到昂贵模型、高优先级层、长上下文或人工。总体平均会变，但单切片可能稳定。

5. Reliability Anomaly

retry、失败、超时、取消后生成增加。完成任务数可能不变，失败浪费率先升。

6. Quality Anomaly

账面单位调用成本下降，但 accepted task 比例下降、人工复核增加。此时 quality-adjusted unit cost 可能上升。

异常门槛使用季节性、发布窗口和最低样本量；每个异常保留贡献分解和相关 Trace，而不是只发“今日成本高 30%”。

二十四、优化策略一：Prompt 与上下文

1. 删除无效 Token

从系统指令重复、历史对话、工具 Schema、检索证据和序列化包装入手。使用 tokenizer 计量并做语义回归。删除一段看似重复的安全要求可能造成风险，不能只按 Token 数决定。

2. 上下文压缩

摘要、裁剪和结构化状态能减少输入，但可能丢失关键约束。测试需要覆盖长会话、引用、新鲜度和冲突事实。摘要模型自身也有成本和失败率，应进入 run 账本。

3. 输出预算

明确任务需要的最大输出与停止条件，避免无边界生成。若截断导致任务不完整，成本下降不算成功。对结构化任务可使用字段级完成验证，但 Schema 仅保证形状。

二十五、优化策略二：Cache

1. 提高可复用前缀

将稳定指令放在前缀、避免无意义动态字段破坏匹配、按授权域设计键。收益通过复用 Token、写/读/存储总成本和质量验证计算。

2. TTL 优化

过短导致反复写，过长产生存储和陈旧风险。按复用间隔分布计算期望净收益，并为政策、权限和数据版本提供主动失效。

3. 不要跨供应商假设语义一致

不同厂商的自动缓存、显式缓存、写入倍率、读取价、TTL 和存储费不同。Price Adapter 和 Usage Adapter 必须绑定产品版本。

二十六、优化策略三：模型路由与服务层

1. 能力契约

为任务定义最低质量、安全、上下文、工具和结构能力。低价模型只有通过目标切片评测才进入候选。

2. 路由成本

路由器自身可能调用分类模型、增加延迟并产生误路由。比较：

只看被选模型单价会高估收益。

3. Batch/Flex/Priority 等层

厂商可能为异步批量、低优先级或高优先级服务提供不同费率与时限。选择必须匹配任务 deadline、可用性和产品支持；价格页面的当前选项不能外推为永久承诺。

二十七、优化策略四：检索与工具

1. 候选数和 Rerank

减少候选可降 vector DB、rerank 和输入 Token，但要用已有检索与任务评测证明质量底线。本文不以相似度阈值直接代表业务正确。

2. 工具调用治理

用确定性条件避免重复查询，缓存幂等结果，限制 Agent 循环和并行扇出。工具失败要区分可重试与业务拒绝，避免把安全/权限失败换参数重试。

3. 返回载荷

工具只返回完成任务所需字段，减少网络和后续输入 Token；但字段裁剪必须通过业务契约，不得丢失审计证据。

二十八、优化策略五：自建容量与利用率

1. 提升利用率不等于追求 100%

提高批处理、共享副本和弹性可以降低单位成本，但接近饱和会抬高排队和尾延迟。使用上一篇的 Goodput 与饱和拐点确定可交付容量，再计算单位成本。

2. 预留与按需组合

稳定基线用承诺容量，突发用按需；effective cost 要把未使用承诺摊入。容量策略通过故障和滚动发布实验验证。

3. 多租户公平

一个租户的长上下文可能占据 KV 和 GPU，影响其他租户。成本分摊可以反映资源占用，但不能替代限额、优先级和隔舱。

二十九、优化回归：成本下降必须同时证明质量不退化

每个优化 PR 或配置发布至少包含：

1. 离线阶段

在固定任务集上比较 Token、检索、工具次数与目标质量。控制输出长度和停止原因，避免少生成伪造收益。

2. 影子阶段

记录候选路径的成本与质量，不执行副作用。影子仍会产生成本，应归入实验成本池。

3. 灰度阶段

随机分流并按任务切片比较 quality-adjusted unit cost、P99 延迟、人工升级和失败浪费。价格变化与模型发布要作为协变量。

4. 发布门禁

只有成本置信区间改善且所有硬质量/安全门槛通过才扩量。总体成本下降但某高风险切片退化时停止。任何 Schema、HTTP 或模型自评分成功都不能覆盖业务真值失败。

5. 失败注入：验证账本会拒绝、保留并告警

成本系统的失败注入不能直接篡改生产账单，也不能只看接口是否报错。安全做法是在隔离账本、固定价格快照和构造任务上注入一项故障，提前声明预期的不变量、告警、证据字段与恢复动作，再验证异常不会被后续成功覆盖。至少覆盖下面几类注入：

注入点 构造动作 必须出现的证据 自动化断言
事件去重 将同一 event_id 投递两次 原始事件哈希、首次入账位置、第二次拒绝原因 账本总额不变，重复事件进入拒绝队列
价格版本 删除某 usage_kind 的有效价格，或制造重叠有效期 价格键、发生时间、候选 price_id 列表 不得回退到零价或最新价，结算批次停止

三十、完整失败案例一：Cached Tokens 被重复计费

现象

内部账本比供应商明细高 18%，cache hit 越高的 tenant 差异越大。数字为构造数据。

证据链

  1. 适配器将 input_tokens 全量按普通输入计价。
  2. 又把 cache_read_input_tokens 按缓存读取价追加一笔。
  3. 官方字段语义表明 cached input 已包含在 input total。
  4. 差异与 cached/total 比例近似线性。
  5. 同一 observation 生成的 normalized events 不是互斥项。

根因与修复

把普通输入事件改为 uncached = total - cached_subsets，并针对厂商版本写 Fixture。增加子量不大于总量、互斥计价和账单抽样对账测试。历史通过冲销与新分录更正，不直接覆盖。

三十一、完整失败案例二：最终成功掩盖重试浪费

现象

成功任务单位成本稳定，但供应商账单持续上升。数字为构造数据。

证据链

  1. 应用表每个 logical request 只有一行，retry 更新同一记录。
  2. provider request ID 显示一次任务实际调用三次。
  3. 网关与 SDK 同时重试，Agent 又重跑整个步骤。
  4. 成功任务聚合只保留最后 usage。
  5. 超时 attempt 在供应商侧已经生成输出并计费。

根因与修复

建立 immutable attempt，保存父子关系和 retry owner；集中重试预算，统计 attempts/task 和 failure waste。最终 run 可以成功，但全部 attempt 成本进入 task。

三十二、完整失败案例三：更便宜模型导致人工成本反超

现象

模型 effective cost 每任务下降 45%，人工复核率从 8% 升到 31%，最终 quality-adjusted unit cost 上升 22%。数字为构造数据。

证据链

  1. 路由实验只看模型账单与 Schema 合法率。
  2. 高风险长文和数字切片错误增加。
  3. 自动结果返回 200 且字段齐全，但业务后置条件失败。
  4. 人工系统的分钟数晚两周才入账，首周看板显示“显著节省”。
  5. 观察窗口关闭太早，把 provisional task 当 accepted。

根因与修复

延长真值窗口，连接人工与申诉成本；以目标任务质量为硬门，按稳定 cohort 比较。Schema 合法不再作为 accepted 充分条件。

三十三、完整失败案例四：共享 GPU 成本被重复分摊

现象

tenant 报表合计比平台成本池高一倍，但各 tenant 内明细看起来合理。

证据链

  1. GPU 原始成本作为 shared-platform tenant 保留在总表。
  2. 同一金额又按 Token 分到业务 tenant。
  3. 汇总视图同时选择来源分录和 allocation 分录。
  4. allocation 没有 origin_entry_id 唯一约束。
  5. 团队只检查比例和为 1，没有检查最终守恒。

根因与修复

在责任视图中使用“来源或分摊”二选一语义；每个 active allocation 绑定唯一来源与版本；CI 断言 allocated + remainder = origin，并让全层级合计回到账本 effective cost。

三十四、完整失败案例五：价格更新改写了历史

现象

没有任何流量变化，三个月前的成本报表在今天下降。数字为构造数据。

证据链

  1. 查询时使用当前价格表与历史 Token 重新相乘。
  2. 价格表没有 valid_from/valid_to。
  3. 新模型 SKU 与旧 SKU 使用同一个展示名。
  4. 账期关闭时未固化 price_id。
  5. 财务发票仍按历史价格，导致对账失败。

根因与修复

价格簿版本化，每条 ledger entry 固定 price_id 和计算结果。重估场景另建 what-if 视图，不改写历史 actual。未知 SKU 阻止自动结算。

三十五、完整失败案例六：缓存命中率上升但净成本增加

现象

请求命中率从 40% 升到 78%，总 cache 相关成本却增加，TTFT 没改善。数字为构造数据。

证据链

  1. 新策略为大量一次性长前缀创建显式缓存。
  2. write 与 storage 成本上升，许多缓存只读一次。
  3. 命中率按请求算，未观察复用 Token 数。
  4. TTL 远长于真实复用间隔，过期前占用持续计费。
  5. 部分命中只复用很短前缀，对 prefill 无明显作用。

根因与修复

按缓存群组计算写、读、存储与 avoided uncached cost，设置最低期望复用和 TTL。门禁使用 cache net saving、复用 Token 和性能/质量，不使用请求命中率单指标。

三十六、完整失败案例七：预算门禁在并发 Agent 中超卖

现象

单任务预算 USD 1，三个并行分支各估算 USD 0.4，都在读取剩余 USD 1 后获准，最终成本超过预算。数字为构造数据。

证据链

  1. 门禁只查询 posted cost，未包含 active reservations。
  2. 三个分支非原子读取与写入。
  3. usage 在请求完成后才到达，执行中看不到消耗。
  4. 分支失败后自动重试，没有新增预留。
  5. 预算超限告警在账单日才触发。

根因与修复

引入原子预留和幂等 reservation ID，计算 posted + active + new estimate；完成后结算和释放，崩溃有 TTL 回收。Agent 调度器在创建分支前就申请预算。

三十七、完整失败案例八：自建推理“低价”来自假设满载

现象

方案报告称自建每百万 Token 成本只有 API 的三分之一，上线后总拥有成本反而更高。数字为构造数据。

证据链

  1. 分母使用理论峰值 tokens/s × 全月秒数。
  2. 实际利用率受夜间低谷、故障余量和长尾延迟限制。
  3. 只计 GPU 租金，遗漏 CPU、存储、网络、平台和工程值班。
  4. 模型质量较低，人工复核增加。
  5. 为满足 P99 和单节点故障，必须保留更多副本。

根因与修复

使用 Goodput 约束下的实际 accepted tasks，按 effective pool cost 含闲置和运维分摊。API 与自建在相同任务、质量、可用性、区域和观察窗口比较。

三十八、证据排查手册：从总额异常回到单条事件

1. 总成本突增

2. 账本与账单不一致

按 currency、billing account、SKU、账期、区域逐层比较。检查迟到 usage、credit、税、最小消费、批量折扣、舍入、未知 SKU 和重复 observation。保留原始 provider request ID 以便抽样追踪。

3. 单位成本下降但总成本上升

可能是任务增长；检查 accepted task 数和总业务价值。也可能是分母被放大或质量下降，需审计 task 去重与终态。

4. 成本下降但人工上升

连接人工系统的迟到事件，按任务看自动结果、升级原因、处理分钟和最终解决。不要把人工视为另一个部门的成本。

5. 某 tenant 异常

下钻 task/run/request，比较任务 mix、长度、缓存、路由、重试和工具。检查 tenant 标签是否在网关可信注入，而非来自客户端可伪造字段。

三十九、数据治理与安全

1. 最小化内容

成本归因通常需要 ID、用量、SKU、状态和业务结果，不需要保存完整 Prompt。内容与 usage 分表，使用摘要或安全标签，权限和保留期分开。

2. Tenant 防伪

tenant_id、cost_center 和预算来自认证上下文或服务端映射，不能接受模型输出或未签名请求字段。否则调用者可以把成本转嫁给他人。

3. 价格与合同权限

公开 list price 可以广泛查看，合同折扣、承诺量和 chargeback 属于敏感财务数据。视图按角色隐藏，但计算层保持一致。

4. 审计

记录价格审批、规则发布、手工更正、预算豁免和账期关闭。任何强制覆盖都必须有主体、原因、时间与关联工单。

四十、从 0 到 1 的落地顺序

阶段一：建立身份与原始事件

  1. 定义 request/attempt、run、task、tenant。
  2. 在网关和工作流传播不可伪造 ID。
  3. 保留供应商原始 usage 和 request ID。
  4. 记录 retry、取消、工具和人工事件。
  5. 先做覆盖率，不急于 chargeback。

阶段二：价格簿与账本

  1. 建立互斥 usage kind 和单位字典。
  2. 接入带有效时间的价格簿。
  3. 用 Decimal 生成 immutable entries。
  4. 建立 unknown SKU 隔离与账单对账。
  5. 区分 estimated 与 final effective cost。

阶段三：分摊与单位经济

  1. 直接成本优先归属。
  2. 选少量可解释共享池与分摊规则。
  3. 做守恒、重复和未分摊检查。
  4. 接入业务 accepted task 与人工成本。
  5. 运行 showback 并收集争议。

阶段四：预算与优化

  1. 建立任务 P50/P95 用量估算。
  2. 实现原子预算预留与运行中门禁。
  3. 建立成本异常贡献分解。
  4. 将 quality-adjusted unit cost 接入实验。
  5. 在门槛稳定后逐步 chargeback。

四十一、上线检查清单

身份与事件

  • 每个物理调用有唯一 request_id 和 attempt_no
  • run、task、tenant 由服务端稳定传播
  • retry 不覆盖前序 attempt
  • 工具、检索、网络、人工和共享资源都有事件来源
  • 原始 observation 与 normalized event 可关联
  • 缺失 usage 标为未知，不自动记零

Token 与缓存

  • 输入总量和 cache 子量的包含关系按供应商版本验证
  • 输出总量和 reasoning 子量不会重复计价
  • cache write/read/storage 使用互斥 usage kind 和单位
  • 工具内容 Token 与工具调用费边界明确
  • 取消后计费 Token 与客户端交付 Token 分开
  • tokenizer 估算与最终供应商计量分开

价格与账本

  • price key 包含 SKU、region、tier、context band、unit 和 currency
  • valid_from/valid_to、官方来源、合同和批准状态完整
  • 历史 ledger 固定 price_id，不套当前价格重算
  • 金额使用 Decimal/定点数，舍入层级明确
  • unknown/ambiguous price 阻止自动结算
  • 更正使用冲销分录，不静默改历史

分摊与对账

  • 直接归属优先于共享分摊
  • 每个共享规则有 method_id、版本、权重和解释
  • allocated + remainder 等于 origin
  • 来源分录与 allocation 在责任视图不重复
  • unallocated 与 idle cost 显式可见
  • 账本按账号、SKU、币种和账期与账单对账

预算

  • task/run/tenant 的硬软预算边界明确
  • 估算使用条件 P50/P95，而非全站均值
  • 并发步骤使用原子 reservation 防超卖
  • posted、active reservations 和 new estimate 一起判断
  • 预算不足时返回完整、可解释的停止/审批状态
  • 迟到 usage、过期预留和最终实算有 reconciliation

质量与单位经济

  • Task accepted 绑定业务后置条件、质量和安全门
  • HTTP 200、Schema、相似度或模型置信度不是 accepted 保证
  • 失败、重试、废弃输出和人工成本留在分子
  • 分母按 task 去重且观察窗口完整
  • 优化前后 cohort 或重加权方式一致
  • 高风险质量/安全门不可被成本收益抵消

运营与权限

  • showback 与 chargeback 状态明确
  • 财务账期冻结和更正流程已演练
  • 合同价、Prompt 内容和 tenant 数据按权限隔离
  • 预算豁免、价格更新和分摊发布有审计
  • 成本异常能下钻到 usage event 与 Trace
  • 价格快照标明 2026-07-26 或实际生效日期，未声明永久有效

四十二、总结

AI 应用成本治理不是把 input_tokens × price + output_tokens × price 写进一个函数。真实系统的成本跨越模型、缓存、检索、工具、网络、重试、人工和自建容量，并跨越 request、run、task、tenant 四个责任层级。

完整做法可以归纳为十步：

  1. 让每个物理 attempt、工作流 run、业务 task 和 tenant 都有稳定身份。
  2. 原样保留供应商与内部服务的 usage observation，再映射为互斥事件。
  3. 正确处理 input/cache、output/reasoning 的包含关系，防止重复计费。
  4. 用有生效时间、单位、币种、区域和服务层的价格簿估值。
  5. 区分 List、Contracted、Billed、Effective 与 Allocated Cost。
  6. 用 immutable Decimal 账本保留重试、失败、取消和更正。
  7. 对 GPU、索引和平台等共享成本执行有版本、可解释、守恒的分摊。
  8. 将人工复核和业务最终真值连接到 Task，计算 quality-adjusted unit cost。
  9. 用事前估算、原子预留、运行中扣减和事后实算实现预算门禁。
  10. 所有优化在固定任务分布下同时通过成本、质量、安全、延迟和容量回归。

最终需要证明的不是“这次调用比上次少花了多少 Token”，而是：

在价格会变化、调用会重试、共享资源会闲置、质量真值会迟到的现实条件下，每一笔成本都能回到使用事件和责任对象；每一个被计入分母的任务都真正通过业务验收；任何节省都没有把错误、人工和风险转移到看板之外。
