AI测试-41-多模型路由怎么权衡质量延迟成本隐私和可用性

发表于 2026-05-08 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:12

多模型路由常被简化成一句话：简单问题发给便宜模型，困难问题发给强模型。

这句话只覆盖了路由问题的一小部分。

一个请求可能包含只能留在特定区域的数据，调用方只被授权使用部分部署，任务要求某个安全策略和写工具，输入加输出预算超过某些模型的上下文上限，主候选所在供应商正在限流，备用候选虽然便宜却不支持图片或函数调用。此时“哪个模型质量成本比更高”不是第一道问题。第一道问题是：

只有这个集合不为空，才轮到第二道问题：

顺序不能颠倒。把数据驻留、权限、安全或工具能力写成一个可被低成本抵消的分数惩罚，优化器迟早会选出“不允许但很便宜”的候选。即使最终返回符合 Schema 的 JSON、模型自信、接口成功且 HTTP 200，数据外发、越权、工具未执行或业务后置条件错误仍然存在。

《AI测试-26-模型API怎么处理超时限流重试幂等和供应商故障》已经讨论模型调用的超时、重试、限流和幂等；《AI测试-33-AI功能怎么做模型降级功能熔断和确定性兜底》已经讨论能力阶梯、熔断和恢复。本文不重复这些通用韧性实现，而是聚焦路由器本身：

  • 如何表达请求契约和模型能力；
  • 为什么硬约束必须先于质量、延迟和成本优化；
  • 规则路由、级联和学习路由各自解决什么问题；
  • RouteLLM 与 FrugalGPT 的实验能说明什么、不能说明什么；
  • 如何校准路由概率、识别分布外输入并保留受控探索；
  • 如何设计 Fallback，避免供应商相关故障和能力缩水；
  • 如何用离线全候选矩阵、影子流量、在线真值、后悔值和质量约束成本评价路由器。

全文使用四个虚构候选模型和构造请求，不需要真实 API Key。模型名称、价格、质量、延迟、上下文和通过率都明确属于构造数据，不代表任何供应商产品。论文数字只限定在论文原有数据、模型版本、价格时点和实验设置。资料核对截止日期为 2026-07-26。

一、工程定义与边界：路由器输出的是受约束执行计划

1.1 路由器不只是分类器

本文把多模型路由器定义为：

根据请求契约、模型能力快照、预测质量、资源状态和策略版本，从当前允许的候选中选择主执行模型、受控探索概率和 Fallback 顺序，并为每次保留或淘汰提供可审计原因的决策系统。

输入不仅是用户 Prompt，还包括：

  • 调用主体、租户和权限；
  • 数据敏感等级、允许区域和出站限制；
  • 请求意图、风险等级和预期输出；
  • 输入 Token 估算、输出预留和端到端 Deadline；
  • 必需工具、模态、结构和安全策略；
  • 成本预算与最低质量；
  • 模型、区域、配额、熔断和故障域的当前快照；
  • 路由预测器、校准器和 OOD 检测器版本。

输出至少包含：

  • selected_model；
  • feasible_candidates；
  • 每个淘汰候选的原因；
  • 质量下界、延迟和成本估计；
  • 是否探索及选择概率 propensity；
  • Fallback 候选和故障域关系；
  • 当可行集为空时的拒绝、人工或确定性工作流动作；
  • 完整策略与能力快照版本。

如果输出只有一个模型名，出了问题就很难区分：候选从未有权限、能力注册错误、质量预测错误、阈值配置错误，还是执行期故障触发了不合格 Fallback。

1.2 区分五个容易混用的机制

机制 主要输入 主要目标 是否需要理解任务质量
负载均衡 同质实例健康与负载 分散流量 通常不需要
供应商网关 协议、认证、配额 统一调用和治理 不一定
静态规则路由 租户、地区、意图、风险 执行明确政策 由规则显式表达
学习路由 Prompt 特征和历史结果 预测候选相对质量 需要训练与校准
级联 已产生的响应和质量门 不足时升级模型 需要判断中间输出

一个系统可以同时使用这些机制。先由静态策略过滤区域和权限，再由学习路由在合格模型中选择；首个响应不满足确定性后置条件时，再进入受限级联。不能因为统一网关支持多个供应商，就认为已经实现质量路由；也不能因为级联最终调用了强模型，就忽略前几次调用的延迟、费用和数据暴露。

1.3 路由优化不是业务正确性证明

路由器可以提高在已知分布和指标下选中合适模型的概率，却不能保证每次输出正确。下面这些信号都不构成业务保证：

  • Prompt 与历史高分样本 Embedding 相似；
  • 路由分类器输出 0.94；
  • 候选模型自报高置信度；
  • 返回通过 JSON Schema；
  • 工具调用协议完整；
  • API 返回 200；
  • 自动 Judge 偏好当前结果。

业务正确性还需要独立事实、权限检查、工具真实状态和业务后置条件。路由器负责选择执行路径，不替代被选路径的质量工程。

1.4 本文不讨论的边界

本文不提供实时供应商价格表或模型排行榜，也不声称某个具体厂商在所有地区、账户和版本上支持相同能力。厂商的上下文、工具、数据处理和区域能力会变化，还可能因产品形态和合同不同而不同。生产模型注册表必须来自对应产品、固定版本、账户配置、合同和实际契约测试，不能从模型名称猜测。

本文也不重复通用 RAG 召回评测。若某条路径包含检索，检索质量仍按独立分层评测处理；路由器只能使用经过定义的端到端任务结果，不能拿“召回率高”替代最终任务成功。

二、贯穿场景：企业理赔助手的四个构造模型

  1. 解释公开政策，只需只读 policy_lookup；

  3. 分析新出现的复杂法律条款，需要更高质量和保守处理。

同一个用户文本在不同租户、数据等级和工具目标下可能得到不同路由。路由键不能只包含规范化 Prompt，否则缓存会把低敏公开请求的决定错误复用于高敏案件。

2.2 硬约束和软目标的区别

本场景的硬约束包括：

  • 部署区域属于请求允许区域；
  • 主体和租户被授权调用该模型；
  • 模型最大敏感级别不低于请求；
  • 安全策略满足请求；
  • 输入估算加输出预留不超过上下文限制；
  • 所有必需工具与模态可用；
  • 模型、配额和故障域当前没有被策略停用。

软目标包括：

  • 在质量下界达标后降低成本；
  • 在 Deadline 内降低尾延迟；
  • 避免供应商故障域过度集中；
  • 为校准和新模型收集少量探索证据。

“质量下界达标”在实现上通常也是准入门槛，但它来自统计预测而非绝对事实，因此必须连同校准误差和 OOD 状态解释。

三、完整架构：先求可行集，再优化

3.1 请求契约层

请求契约由业务入口、权限系统、数据分类器和任务规划器共同提供。关键字段不能全部让大模型从文本猜测。例如租户、主体和数据驻留必须来自可信认证上下文；必需工具来自确定性工作流定义；敏感级别可以由 DLP 辅助，但高风险请求需要保守默认。

契约层还要区分：

  • 用户希望的能力；
  • 业务完成任务真正需要的能力；
  • 当前授权允许的能力。

用户说“帮我保存案件”表达意图，不等于已经获得 case_write 权限。路由器只能使用授权系统确认后的工具集合。

3.2 模型能力注册表

模型注册表保存固定部署而不是营销型号：

同一型号在两个区域是两个候选，因为配额、延迟、数据边界和故障域可能不同。同一供应商的两个型号也不能自动视为独立 Fallback，它们可能共享认证、区域控制面、配额或内容安全依赖。

3.3 硬策略引擎

策略引擎使用集合交集形成：

集合为空时，正确结果是明确拒绝、转人工、缩小任务或走已验证的确定性工作流。系统不能为了“保持可用”把被硬约束淘汰的模型加回来。

3.4 预测和校准层

对 F_hard(x) 中每个候选，预测：

  • 任务质量均值与保守下界；
  • 延迟分位数而非只看平均；
  • 输入、输出、工具和路由开销的期望成本；
  • 路由置信度与校准区间；
  • OOD 分数；
  • 故障、限流和冷启动风险。

预测模型需要版本化。模型本身升级、Prompt 改变、价格变化或业务分布漂移都会让历史校准失效。

3.5 多目标决策层

先过滤质量下界和 Deadline，再在剩余候选中做成本或综合目标优化。选择过程保存所有候选的比较值，而不只保存赢家。这样才能在延迟真值回填后计算后悔值并判断路由器是否做错选择。

3.6 执行与 Fallback 层

执行器处理 Deadline、熔断、取消和供应商错误。发生 Fallback 时，使用当前请求与最新状态重新执行硬约束；不能直接取静态列表的下一个模型。若主路径已经把数据发给某供应商，Fallback 还要记录额外数据暴露和成本。

3.7 结果和真值层

即时结果包括协议、延迟、Token、成本、工具状态和同步业务断言。延迟结果包括人工纠正、案件真正保存、申诉、损失和用户完成任务。代理 Judge 可以辅助早期质量观测，但不能覆盖真实业务后置条件。

四、硬约束详解：任何一项都不能被便宜抵消

4.1 数据驻留和出站边界

数据驻留不是供应商名称级别属性，而是具体产品、部署、区域、处理链和合同属性。路由器至少要检查：

  • 请求允许的数据处理区域；
  • 模型推理部署区域；
  • Prompt、文件、Embedding 和日志的处理区域；
  • 安全过滤、遥测和备份是否跨区；
  • 供应商是否允许使用输入改进服务；
  • 组织合同与租户覆盖是否匹配。

最隐蔽的错误发生在“路由前”。如果路由分类器先把完整敏感 Prompt 发给全局 Embedding 服务，再决定最终模型留在 EU，驻留约束已经被违反。硬过滤需要覆盖特征提取、缓存、日志和 Judge，而不仅是最终生成端点。

NIST AI 600-1 将数据隐私、本地化合规和价值链风险列为需要测试和管理的内容。具体法律义务仍应由组织的法律、隐私和安全人员根据适用地区与合同确定，不能从通用文章推导。

4.2 主体、租户和模型权限

权限至少有三层：

  1. 调用主体能否使用路由服务；
  2. 租户能否使用某个模型或供应商；
  3. 当前任务能否调用请求里的工具和数据对象。

模型允许列表变化时，应使旧路由缓存失效。缓存键至少绑定主体权限摘要、租户、数据等级和策略版本。只按 Prompt 哈希缓存决策会跨权限复用。

4.3 安全策略不可通过换模型绕过

若请求命中安全阻断，路由器不能把它解释成“主模型质量不足”后换一个限制更少的模型。候选必须支持并启用请求要求的安全策略版本，输出仍要经过统一后置检查。

模型拒答也不能直接等同安全正确。拒答可能是误拒，另一个模型也可能在合规上下文下完成任务。更合适的做法是：安全策略先确定允许的任务范围，再在这个范围内路由；真正禁止的内容没有自动 Fallback。

4.5 工具、模态和输出能力

工具能力不应只用 supports_tools=true。需要更细：

  • 支持哪个工具协议和版本；
  • 并行或串行调用；
  • 是否支持强制工具、工具选择和多轮回传；
  • 参数约束和结构化输出子集；
  • 图片、音频、文件和文档类型；
  • 流式过程中工具事件的顺序语义；
  • 已通过哪个适配器契约测试。

即使模型生成了一个长得像工具参数的 JSON，如果执行器没有收到有效工具调用事件，业务动作仍未发生。

4.6 可用性包含当前状态

模型静态注册为可用，不代表此刻可选。动态状态包括：

  • 模型或部署熔断；
  • 区域配额不足；
  • 剩余 Deadline 不够；
  • 租户预算耗尽；
  • 安全服务或必要工具不可用；
  • Fallback 故障域与当前故障相关；
  • 冷启动预估超过请求预算。

状态快照也要带时间。使用十分钟前的“健康”缓存决定高风险路由，没有足够时效性。

六、路由策略：规则、级联和学习路由不是替代关系

6.1 规则路由

规则适合：

  • 数据区域和租户合同；
  • 高风险任务固定走已验证模型；
  • 某工具只由特定适配器支持；
  • 已知语言或模态专用模型；
  • 紧急停用与迁移窗口；
  • 流量很小、没有可靠训练标签的早期系统。

规则的优点是可解释、可审计、容易做确定性测试。缺点是规则数量随模型、任务和状态组合增长，难以从历史结果学习细粒度质量差异。

第一版通常应从规则和完整日志开始。没有可信全候选结果时，直接训练学习路由器只会学习旧策略的选择偏差。

6.2 级联

级联先调用较便宜模型，根据响应质量门决定接受还是升级。它可以使用生成后信息，例如：

  • 代码是否通过测试；
  • SQL 是否执行并满足只读约束；
  • 工具后置条件是否成立；
  • 确定性答案是否匹配；
  • 经校准的响应质量模型是否达标。

代价是最坏情况下会调用多个模型，累计 Prompt、输出、延迟和数据暴露。第一个模型已经生成的 Token 不会因为升级而免费消失。开放式文本如果没有可靠质量门，级联可能把错误的小模型答案错误地提前接受。

6.3 学习路由

学习路由在调用候选前，根据请求特征预测模型相对表现。适合：

  • 请求量足够大；
  • 候选间确有互补；
  • 有同请求多模型结果或可靠偏好标签；
  • 任务分布相对稳定且可监控；
  • 路由开销明显小于生成收益。

它的关键风险包括：

  • 只看到旧策略选择模型的结果；
  • Judge 标签偏好某种模型或风格；
  • 新模型、语言、工具和任务属于 OOD；
  • 训练时价格和延迟已经过期；
  • 原始概率未校准；
  • 学到敏感属性代理特征；
  • 路由器本身增加隐私处理和延迟。

6.4 混合策略

更实用的组合是：

学习模型只优化允许范围内的选择，不获得覆盖合规或安全策略的权力。

  • 工具调用；
  • 失败和取消后仍产生的计费。

7.5 质量下界不是万能护栏

质量预测来自有限评测。即使统计下界达标，也只对数据、标签和模型假设成立。高风险业务还需要零容忍硬错误、关键切片门槛和人工路径。总体质量高不能抵消跨租户访问或未批准资金动作。

八、RouteLLM 与 FrugalGPT：只在论文实验范围内理解收益

8.1 RouteLLM 研究了什么

RouteLLM 将问题主要形式化为强、弱两个模型之间的二元路由，用偏好数据训练强模型相对获胜概率，再通过阈值控制调用强模型比例。论文探索了相似度加权排名、矩阵分解、BERT 分类器和因果语言模型分类器。

论文 v4 的核心实验使用 gpt-4-1106-preview 作为强模型、Mixtral-8x7B-Instruct-v0.1 作为弱模型，并在 MMLU、MT-Bench 和 GSM8K 上评估。训练数据主要来自 Chatbot Arena；论文报告处理后约 65K 对比，语言以英语为主，中文约占 3.1%。这些细节决定了结论不能直接替代中文企业理赔场景的本地评测。

论文还给出一个重要反例：只使用 Arena 数据训练时，路由器在 MMLU 和 GSM8K 这类分布外任务上接近或差于随机路由；加入对应的金标或 Judge 扩增数据后才改善。这正说明 OOD 和任务匹配是路由生产化的核心，不是训练出一个概率后永久通用。

RouteLLM 论文在其基准、模型对和当时成本估算上报告超过两倍、最高约 3.66 倍的成本节省；项目仓库也展示特定基准上的更高宣传数字。这些都是实验结果，不是对任意新模型、中文流量、工具任务、现行价格或 SLO 的承诺。论文的二元强弱设定也没有自动解决数据驻留、权限、安全、工具、供应商故障域和 N 路候选约束。

8.2 FrugalGPT 研究了什么

FrugalGPT 讨论 Prompt 适配、LLM 近似和 LLM 级联，并实现学习式级联。论文 2023 年实验选择当时 5 个供应商的 12 个 API，在 HEADLINES、OVERRULING 和 COQA 三类任务上评估，重点级联长度为 3。

论文报告在其任务、API 和价格设置下，可在匹配最佳单一 API 表现时最高降低 98% 推理成本，或在相同成本下最高提高 4% 准确率。这个数字只能限定到论文实验。供应商型号、定价、任务标签、Prompt 和质量评分器都已是历史快照，不能拿 98% 作为当前预算目标。

FrugalGPT 的启发是：不同模型错误具有互补性，且可以通过响应评分决定是否升级。落地时还要补：

  • 每一级重新检查数据和工具边界；
  • 累计 Deadline、Token 和调用成本；
  • 评分器的校准与相关偏差；
  • 开放式任务没有确定性答案时的误接受风险；
  • 多次发送敏感数据的隐私代价；
  • 供应商相关故障和同一认证域失效。

8.3 论文不是二选一模板

RouteLLM 更接近“调用前只选一个模型”，延迟和费用通常更可控；FrugalGPT 更接近“先试便宜模型，质量不足再升级”，能够使用响应信息，但最坏会多次调用。

实际系统可以按任务组合：

  • 有可靠请求级难度和低延迟要求：优先单次学习路由；
  • 有确定性响应 Oracle：允许受控级联；
  • 高风险、无可靠质量门：规则固定强路径或人工；
  • 新任务和 OOD：保守候选加影子收集，不立即自动下放；
  • 小流量：规则路由通常比复杂训练更可维护。

十、OOD：识别“路由器没有见过”的请求

10.1 OOD 不只指新主题

路由器的分布外输入包括：

  • 新语言、方言和混合语言；
  • 新工具或新工具 Schema；
  • 新模型加入候选池；
  • Prompt 模板和系统指令变化；
  • 超长上下文和新的文件模态；
  • 新政策、产品或攻击方式；
  • 供应商模型升级后质量关系反转；
  • 线上高风险流量比例突然变化。

10.2 OOD 分数也会失败

Embedding 距离、分类器能量、集成分歧和密度估计都只能提供信号。一个新型法律条款可能在词汇上与旧条款很相似，却需要完全不同的推理；一个拼写奇怪的简单问题可能距离很远但容易回答。

10.3 监控 OOD 后的真实结果

只看 OOD 拒绝率会鼓励路由器把难题全部拒绝。还要报告：

  • OOD 请求量与切片；
  • 升级后任务成功率；
  • 人工队列负载与等待；
  • 后来确认其实可由便宜模型处理的比例；
  • OOD 漏检导致的质量违例；
  • 新分布进入校准集的时间。

十一、受控探索：不探索会固化旧策略，乱探索会制造事故

11.1 为什么需要探索

如果旧策略总把高质量模型用于某类请求，就永远看不到便宜模型在这些请求上的真实结果。历史日志只包含旧策略选择的动作，直接训练新路由器会产生选择偏差。

探索用于获得反事实信息，但必须在硬约束之后。禁止用探索测试：

  • 不允许区域；
  • 无权限模型；
  • 不支持必需工具的模型；
  • 高风险不可逆动作；
  • 安全策略不足的路径。

11.2 安全探索集合

定义：

只有低风险、可回滚、具有独立后置校验的请求进入 E(x)。探索有总量、租户、模型、切片和时间上限。出现质量、安全或延迟止损信号立即停用。

11.3 记录选择概率

每次探索保存：

  • 候选集合；
  • 被选动作；
  • 选择概率 propensity；
  • 策略和随机源版本；
  • 当时所有硬约束与模型状态；
  • 最终奖励和延迟真值。

没有 propensity 的历史日志很难做可靠的逆倾向加权或双重稳健离线评估。即使记录了概率，候选覆盖不足、概率过小、奖励延迟和分布漂移仍会导致高方差或偏差。

11.4 确定性哈希分桶

工程上可以用 request_id + policy_version 的稳定哈希决定是否进入探索桶，避免重试时随机改变模型。它对大量独立请求近似分流，但不是密码学随机实验，也不能替代实验设计。高风险请求把探索率固定为零。

十二、Fallback 与供应商相关故障

12.1 Fallback 不是候选数组的下一个元素

主调用失败后，以下条件可能已经变化：

  • 剩余 Deadline 和成本预算；
  • 已外发的数据范围；
  • 主故障影响的供应商、区域、认证或配额域；
  • 工具调用是否产生未知副作用；
  • 请求是否仍适合自动执行。

所以 Fallback 应重新计算可行集。若写工具状态未知，先对账而不是换模型重新生成同一动作。

下面的 Python 示例只使用标准库，不发起网络请求。它把四个构造模型、三条请求契约和离线全候选结果写成固定夹具，因此每次执行结果确定。

实现顺序是：

  1. 对每个候选执行驻留、权限、敏感等级、安全策略、上下文、工具、模态和熔断检查；
  2. 只对硬约束通过的候选读取质量、延迟、成本、校准置信和 OOD 预测；
  3. 使用质量下界、Deadline 和请求成本预算形成统计可行集；
  4. 在可行集中最小化“期望成本加少量延迟代价”；
  5. 只有低风险请求能够进入稳定哈希探索桶，并记录选择概率；
  6. Fallback 从同一可行集生成，优先不同供应商故障域；
  7. 离线评测用每个请求对所有硬约束合格模型的实际构造结果计算 Oracle 和后悔值。

示例没有使用模型名称推断能力，所有能力都来自显式 ModelSpec。这些能力和价格是构造数据，不对应现实产品。

13.1 为什么先累计全部淘汰原因

hard_rejection_reasons 不在第一个失败处返回。例如 us-fast-v4 对欧洲高敏写请求同时可能违反区域、租户、敏感级别、安全策略和工具能力。完整原因能支持两类判断：

  • 某候选是否只差一个可修复能力；
  • 注册表或产品设计是否从根本上不适合这类任务。

但错误原因不能包含完整敏感 Prompt。日志保存合同字段摘要和策略版本即可。

13.2 为什么 OOD 只允许高保障候选继续

示例中的 eu-general-v5 对新法律条款预测质量下界为 0.91，表面超过 0.90 门槛；但置信只有 0.55，OOD 分数为 0.85。代码不相信这个单点下界，要求不确定请求使用 assurance_tier=high 的 global-reasoner-v2。

这不是说“高保障模型一定正确”。它只是构造策略里的保守升级。真实系统还要核验高保障层具体意味着哪些评测、人工和安全证据。

13.3 为什么探索使用稳定分桶

同一 request_id 和策略版本得到同一探索决定，重试不会随机换模型。只有 risk=low 时 epsilon 才非零，且探索候选已经通过全部硬约束、质量下界、延迟和成本预算。

选择概率仍被记录：选择主候选时是 1-epsilon，选择任一替代候选时是 epsilon/(n-1)。这为离线策略评估保留必要信息。生产实验还需要检查请求 ID 是否足够均匀、是否存在重复主体聚类，以及分桶是否需要按用户或会话隔离。

13.4 为什么 Fallback 只是计划

示例把剩余可行候选按故障域排序，但执行时不能无条件调用。主调用失败后必须带最新 Deadline、成本、熔断和副作用状态再次路由。代码返回的 fallbacks 是事故前的候选计划，不是绕过动态策略的授权票据。

15.1 单元测试先证明决策顺序

  • 缺少 case_write 的模型不能处理写任务；
  • FAQ 在质量下界达标后选择构造成本更低的模型；
  • 高风险任务不探索；
  • OOD 且校准不足的普通保障候选被淘汰；

十六、评测架构：离线、影子和在线证据互补

16.1 离线全候选矩阵

对评测请求 x_i 和当时硬约束合格的候选 m_j，尽量保存完整矩阵：

同一请求对多个模型执行，才能知道“如果当时选另一个会怎样”。若只保存旧路由器选中模型的结果，新策略偏好的候选没有可比真值。

全矩阵成本高，可以按风险和不确定性分配：

  • 小型密封集执行所有候选；
  • 高频稳定切片抽样执行；
  • OOD、新模型和决策边界附近提高矩阵密度；
  • 高敏数据只在合规环境比较，不为评测突破驻留约束；
  • 写操作使用沙箱、模拟器或只读后置验证，不重复真实副作用。

“Oracle 模型”在这里指基于已观察候选结果选出的事后最优动作，不代表该模型绝对正确。

16.2 离线切分与版本控制

训练路由器、校准概率、选择阈值和最终盲测使用独立集合。相同用户、会话、模板或事故家族不能跨集合泄漏。每次比较冻结：

  • 请求集和权重；
  • 候选池；
  • 模型与部署版本；
  • Prompt、工具和适配器；
  • 价格与延迟快照；
  • 质量标签和 Judge 版本；
  • 路由器、校准器与 OOD 检测器；
  • 硬策略和权限模拟。

若候选池变化，旧后悔值不再直接可比，需要桥接评测。新增一个便宜强模型会降低 Oracle 成本，即使旧路由器行为不变，后悔值也会变大。

16.3 影子流量

影子路由读取生产请求合同，计算新策略选择，但不交付结果。根据合规和预算，可以只记录决策，也可以执行影子模型。

影子阶段验证：

  • 新策略可行集与旧策略差异；
  • 预计成本、延迟和供应商流量迁移；
  • OOD 与空集比例；
  • 新模型契约和冷启动；
  • 权限、驻留和日志边界；
  • 旧、新策略在真实分布的质量差异。

影子执行仍是真实数据处理和真实费用，不能因为“不展示给用户”就绕过隐私、驻留、许可和内容安全。

16.4 在线灰度

在线灰度从低风险、可回滚、有明确后置条件的请求开始。按租户或主体稳定分桶，避免同一会话前后模型摇摆。每个阶段有：

  • 最小样本和最短观察时间；
  • 硬约束零违规门禁；
  • 质量、延迟和成本阈值；
  • 人工队列容量；
  • 供应商流量与配额上限；
  • 自动停止与回滚；
  • 延迟真值等待窗口。

即时代理指标通过后仍要等待足够的案件完成、人工纠正或申诉真值。只看当天 Judge 结果就扩大流量，会漏掉几天后才出现的业务失败。

16.5 日志策略和反事实评估

受控探索记录 propensity 后，可以使用逆倾向加权、直接奖励模型或双重稳健方法估计新策略价值。Dudík、Langford 和 Li 的原始工作讨论了上下文决策中的双重稳健策略评估；应用到模型路由时仍需满足相应统计假设。

实际限制包括：

  • 新策略选择了旧策略概率为零的动作，无法从旧日志评估；
  • 很小的 propensity 产生高方差；
  • 奖励模型与路由器共享偏差；
  • 业务真值缺失不是随机的；
  • 供应商和流量分布已经变化；
  • 工具任务的奖励取决于完整轨迹，不只取决于一次模型调用。

因此离线策略估计用于筛选和风险判断，不能完全替代影子与受控在线实验。

十七、指标口径：质量、效率和约束不能压成一个分数

17.1 硬约束违规率

目标通常是零，任何一次都单独事故化。不能让大量低成本成功抵消一次跨区或越权。

同时报告“阻断调用数”和“实际违规数”。阻断多说明门禁工作或上游合同质量差；实际违规说明控制失效。

17.2 可行集空集率

按原因切片：真实无候选、能力注册缺失、策略过严、状态过期或预测缺失。空集率低不一定好；若系统通过放松硬约束避免空集，反而更危险。

17.3 质量约束违例率

分母不能包含没有真值的请求。缺失真值率另报，避免只标注容易样本。高风险切片使用独立门槛，不能被总体均值抵消。

17.4 质量约束成本

把质量失败请求排除后必须同时报告失败率，否则系统可以通过只处理简单请求降低成本。更完整的报表并列：每请求成本、成功任务成本和质量违例率。

17.5 延迟

至少报告：

  • 路由决策 P50/P95/P99；
  • 排队、特征提取和策略查询；
  • 模型首 Token 与完整响应；
  • 工具和后处理；
  • 级联或 Fallback 累计延迟；
  • 按模型、任务、地区和 OOD 切片的端到端 P95/P99。

平均延迟会掩盖尾部。路由器自身只占 20 ms，也可能调用一个尾延迟超过 Deadline 的模型。

  • 原始流事件与工具调用事件数；
  • JSON 解析与 Schema 结果；
  • 案件库查询结果；
  • 供应商、区域、认证和配额故障域；
  • 自动 Judge 输入、输出和版本。

若只保留最终 JSON，会错误得出“模型说已写入但数据库偶发丢失”。原始流事件能证明工具从未被调用。

18.6 排查顺序

第一步：核对外部事实

查询案件库和工具审计，确认没有写入。检查模型流事件，case_write 调用次数为零。由此排除“工具执行后数据库读取延迟”和“重复幂等键返回旧结果”。

第二步：重放请求合同

使用事故时的模型注册表和策略版本离线重放。旧策略稳定选中 us-fast-v4，说明不是瞬时随机。把区域、工具和安全从惩罚改成过滤后，可行集只剩 eu-general-v5 与 global-reasoner-v2。

第三步：检查数据路径

网络 Trace 显示完整 Prompt 先去全局特征服务。最终生成端点的区域阻断没有消除这次数据处理。驻留检查位置错误，必须移动到任何内容特征提取之前。

第四步：检查能力注册和执行器

eu-economy-v3 注册表正确写着只有 policy_lookup，所以不是文档错误。执行器使用静态 Fallback 数组，没有重新运行注册表过滤。能力合同存在，但没有作用于恢复路径。

第五步：检查成功口径

任务成功来自：

它从未查询工具事件或案件库。模型可以生成任何合法 status 字符串。成功口径需要改成工具回执与业务后置条件，而不是模型声明。

第六步：检查路由置信度

simple=0.93 是分类器 Softmax，不是“便宜模型有 93% 概率完成写入”。在新政策文本切片上，历史 0.9-1.0 分箱实际准确率只有 61%。整体 ECE 因 FAQ 样本占比高仍然较低，切片校准暴露了问题。

第七步：检查供应商相关故障

主模型和第一备用模型虽然型号不同，却共享 provider-a/account-main 认证域。静态列表只按模型 ID 去重，没有故障域。认证故障时两次尝试必然相关失败，并消耗相同 Deadline。

18.7 排除的错误方向

证据可以排除：

  • JSON 解析器损坏：解析与 Schema 都正确，错在业务事实；
  • 案件库写后延迟：工具事件为零，不存在待可见写入；
  • 单个模型幻觉就是全部根因：执行器本不应把无工具候选用于写任务；
  • 供应商区域中间件完全保护了数据：路由前特征服务已经处理完整内容；
  • 随机探索选错：事故请求高风险，Trace 显示走的是确定性主策略；
  • 只有认证故障导致：跨区和假写入发生在认证故障窗口之前。

18.8 根因与贡献因素

根因是架构把不可交易的驻留、工具和安全约束建模为可被质量成本分数抵消的惩罚，并且在内容特征提取之后才执行部分硬策略。

贡献因素：

  1. Fallback 使用静态数组，没有重新计算可行集；
  2. 模型输出的 status 被当作真实工具状态；
  3. 路由分类器概率未经新政策切片校准；
  4. OOD 信号只看文本相似度；
  5. 自动 Judge 与被偏好的模型家族相关；
  6. 模型 ID 去重替代了供应商、认证、区域和配额故障域；
  7. 影子评测只比较输出文本，没有执行工具模拟器；
  8. 成本节省报告没有硬约束违规独立门禁。

18.9 修复

立即止损：

  • 停用学习路由，恢复 EU 固定规则；
  • 禁止全局特征服务接收高敏内容；
  • 所有写请求临时固定到已验证写工具路径；
  • 按 Trace 确认受影响请求和数据处理范围；
  • 轮换相关日志访问并启动隐私事故流程；
  • 认证故障期间按真实故障域熔断。

架构修复：

  • 在任何内容离开入口前执行驻留、主体和敏感等级策略；
  • 特征提取也注册成数据处理候选并接受相同约束；
  • 先求 F_hard(x)，优化器无法看到不合格模型；
  • Fallback 重新运行硬约束与剩余预算；
  • 写任务成功绑定工具调用事件、幂等键和业务查询；
  • 路由预测按任务、语言、风险和 OOD 分层校准；
  • 新政策先进入影子和高保障路径；
  • 注册表显式保存认证、配额、区域和供应商故障域；
  • 报告把硬约束违规置于成本指标之前。

十九、从零到一的实施顺序

阶段一：模型注册和硬策略

先做固定部署注册表、请求契约、权限、驻留、上下文、工具和安全过滤。所有决定写 Trace。此阶段可以始终选择可行集里最保守候选。

阶段二：规则路由和真实成功口径

按任务、风险和工具写少量规则，接入业务后置条件。建立空集、拒绝、人工和确定性工作流路径。先证明错误候选不会被调用。

阶段三：离线全候选矩阵

在合规沙箱对共同请求执行多个候选，补独立标签、成本和延迟。先用简单基线：总是强模型、总是便宜模型、随机、规则和 Oracle。复杂路由器若不能稳定超过简单规则，没有上线价值。

阶段四：校准、OOD 和影子

训练预测器后单独校准，按关键切片画可靠性图。新策略只做影子决策，观察候选集、空集、供应商迁移和预计预算。新模型先通过契约与影子。

阶段五：低风险灰度与探索

低风险、可回滚任务小流量上线，记录 propensity 和业务真值。设置质量、延迟、成本、人工容量和供应商配额止损。高风险保持固定策略。

阶段六：学习路由和持续重校准

当日志覆盖足够，再逐步扩大任务和候选。模型、Prompt、工具、价格、路由特征或业务分布变化时，自动触发桥接评测与重校准。路由器本身按正式产品发布，支持版本、灰度、回滚和审计。

二十、上线检查表

请求契约

  • 主体、租户和权限来自可信上下文；
  • 数据敏感等级和允许区域在路由前确定；
  • 必需工具、模态和业务后置条件明确；
  • 输入、历史、检索、工具 Schema 和输出预留均计入上下文；
  • 每类任务有质量下限、Deadline、成本预算和风险等级；
  • 高风险空集有人工、确定性流程或明确拒绝路径。

模型注册表

  • 候选指向具体产品、固定版本、部署和区域；
  • 能力来自对应官方资料、合同和真实契约测试；
  • 上下文、工具、模态和结构化输出能力细分记录；
  • 数据处理、日志、训练使用和驻留属性已审查；
  • 安全策略和最大敏感等级有证据；
  • 供应商、区域、认证、配额和网络故障域分别记录；
  • 价格、延迟和能力快照有生效时间与过期时间。

硬约束

  • 驻留、权限、安全、上下文、工具和可用性先形成可行集；
  • 硬约束没有作为可被成本抵消的分数惩罚；
  • 特征提取、Embedding、Judge、日志和缓存也执行数据边界；
  • 被淘汰候选不会因高相似度或高置信度恢复；
  • 可行集为空不会自动放松策略；
  • 决策缓存绑定权限、数据等级、策略和注册表版本；
  • 每个候选保存完整淘汰原因和零调用证据。

优化与质量

  • 优化目标明确是质量约束成本、预算内最高质量或其他定义；
  • 质量使用独立真值和保守下界，而非模型自信；
  • 成本包含路由、模型、级联、Judge、工具和失败调用；
  • 延迟包含排队、路由、完整生成、工具和后处理；
  • Pareto 前沿按请求计算，长期被支配候选会审查；
  • 高风险硬错误不被总体质量平均值抵消；
  • Schema、协议和 HTTP 成功未被当作业务成功。

校准与 OOD

  • 预测事件定义清楚，是模型胜出、质量达标还是任务完成；
  • 校准集与路由训练、阈值选择和盲测隔离；
  • Brier、ECE、可靠性图和分箱样本量均报告；
  • 校准按任务、语言、风险和模型对切片；
  • OOD 覆盖新语言、工具、模态、模型、政策和超长上下文；
  • OOD 高或置信不足时采用保守升级、人工或拒绝；
  • 模型、Prompt 和分布变化会触发重校准。

探索

  • 探索集合是硬约束和质量约束可行集的子集；
  • 高风险、不可逆和无后置校验任务不探索；
  • 分桶按主体或会话稳定，不因重试换模型；
  • 每次记录候选、动作、propensity 和策略版本；
  • 有租户、模型、切片、预算和时间上限；
  • 质量、安全、延迟和人工容量止损可自动触发；
  • 探索收益按新增反事实证据而非流量比例评价。

Fallback 与故障

  • 主调用失败后使用最新状态重新求解；
  • 所有尝试共享端到端 Deadline 和成本预算；
  • Fallback 仍检查驻留、权限、安全、工具和上下文；
  • 写操作未知状态先查询或对账，不直接换模型重做；
  • Fallback 优先不同真实故障域；
  • 同供应商不同型号没有被自动视为独立；
  • 能力缩水向用户和下游显式表达；
  • 恢复经过探测、影子、灰度和自动回退。

评测与指标

  • 离线数据包含共同请求上的多候选结果；
  • 候选池、模型、Prompt、工具、价格和标签均版本化；
  • 简单规则、随机、固定强弱模型和 Oracle 是基线；
  • 影子流量仍遵守隐私、驻留和费用约束；
  • 在线灰度等待延迟业务真值；
  • 硬约束违规率独立且目标为零；
  • 质量违例、条件成本、尾延迟和后悔值并列报告；
  • Fallback 成功由业务后置条件定义；
  • 报告包含分子、分母、置信区间、切片和版本。

可观测与发布

  • 每次决定保存可行集、淘汰原因、预测、分数和选择概率；
  • 路由、每个 Attempt、工具和业务真值可由 route_id 关联；
  • 内容日志最小化并有独立权限和保留期；
  • 策略和注册表采用不可变版本与原子发布；
  • 配置读取失败进入保守路径，不猜宽松默认值；
  • 紧急停用按模型、能力和故障域生效并自动过期；
  • 回滚同时恢复策略、校准器和兼容注册表快照；
  • 故障注入覆盖硬约束、OOD、探索、级联和相关 Fallback。

二十一、总结

多模型路由不是一个“哪个模型更聪明”的分类问题。它是策略、测量和分布式执行共同组成的约束决策系统。

可靠实现需要遵守下面的顺序：

  1. 用请求契约表达主体、租户、数据、工具、风险、质量、Deadline 和预算；
  2. 用具体部署和固定版本的注册表表达能力、区域、合同与故障域；
  3. 在任何内容特征处理前执行数据驻留、权限和安全策略；
  4. 先用硬约束求可行集，不允许成本或置信度恢复被淘汰候选；
  5. 使用校准后的质量下界和尾延迟继续收缩候选；
  6. 在剩余候选内做质量约束成本或预算约束质量优化；
  7. 把规则路由、学习路由和级联按任务组合，而不是互相替代；
  8. 将 RouteLLM、FrugalGPT 的收益限定到论文模型、数据、任务和价格环境；
  9. 对校准不足和 OOD 请求保守升级、人工处理或拒绝；
  10. 探索只发生在低风险可行集中，并记录 propensity 与止损；
  11. Fallback 使用最新合同和状态重新求解，优先不同真实故障域；
  12. 用业务后置条件定义成功，不让 Schema、相似度、模型置信度或 HTTP 200 代替业务正确；
  13. 离线全候选矩阵、影子、在线灰度和延迟真值共同评价策略；
  14. 将硬约束违规、质量违例、条件成本、尾延迟、校准、OOD、Fallback 和后悔值分开报告。
