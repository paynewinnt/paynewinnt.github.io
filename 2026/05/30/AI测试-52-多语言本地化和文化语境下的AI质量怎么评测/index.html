AI测试-52-多语言本地化和文化语境下的AI质量怎么评测

发表于 2026-05-30 分类于 AI测试 本文字数： 23k 阅读时长 ≈ 1:25

把一套英文评测集机器翻译成二十种语言，逐条运行同一个模型，再按平均分排序，能不能说明产品已经支持二十个市场？

不能。

翻译会改变任务。一个英语句子里的省略主语、敬语距离、双关、否定范围、性别线索、地址层级或金额表达，在目标语言中可能没有唯一对应形式。翻译器为了让句子自然，会补出源文没有的主语；为了适应当地用户，会把英里换成公里；为了保留字面可比性，又可能留下当地人几乎不会说的“翻译腔”。此时目标样本不再只是源样本的另一个字符串，而是带有翻译方向、译者判断、Locale 默认值和文化语境的新测试任务。

更麻烦的是，所谓“多语言问题”经常根本不在模型的语言能力层：

  • 模型正确抽取了 2026-06-07，显示层却把它渲染成让用户理解为 6 月 7 日以外的日期；
  • 回复使用了正确语言，价格却沿用错误币种，退款工具收到的仍是另一种货币单位；
  • 文本在界面上看起来相同，账户比较键却因兼容归一化发生碰撞；
  • 阿拉伯语和英文混写的输入被语言路由器截断，模型只看到后半句；
  • 自动翻译分数很高，但对当地权力关系、禁忌、称谓和风险提示的处理具有冒犯性；
  • 总体成功率上升，低资源语言、高风险任务和非标准方言切片同时退化；
  • 告警显示“语言不匹配”，真正首错却是检索索引只摄取了英文政策；
  • 供应商 A 在一组公开 benchmark 上领先，不等于它在本产品的地址、工具、副作用和文化风险上更可靠。

因此，多语言 AI 质量评测不能只问“译得像不像”，而要建立一条从任务契约到发布决策的证据链：输入到底是哪种语言和文字系统，面向哪个 Locale 与业务地区，哪些事实必须保持，哪些表达允许本地化，Unicode 与 Tokenizer 怎样处理，日期货币地址怎样进入工具，方言和 code-switch 是否保真，文化判断由谁复核，自动指标的分母是什么，最终哪个切片可以发布、回退或必须阻断。

本文所有订单号、样本数、比例、阈值、故障时间线和发布结果均为构造示例，只用于说明工程口径，不代表任何企业、供应商、语言或人群的真实表现。涉及论文数字时，只按原论文的数据集、模型与实验条件解释，不外推为生产结论。参考资料均不晚于本文日期 2026-05-30。

一、问题边界：本文测的是产品任务，不是给语言排能力名次

本文把多语言本地化质量定义为：

在明确的任务、语言、文字系统、Locale、地区、受众、文化情境和风险契约下，系统能保全用户输入，正确完成业务目标，以可接受的语言与本地格式表达结果，不放大不可接受的伤害，并留下足以重放、复核和决定发布范围的证据。

这个定义里有四个关键词。

第一，评测对象是系统任务。语言模型只是链路的一部分；语言检测、检索、Prompt、Tokenizer、工具 Schema、日期库、币种配置、地址解析、字体渲染和人工流程都会改变结果。

第二，质量总是有条件的。不能把“支持西班牙语”写成没有地区、任务、文字系统、输入方式和风险范围的永久属性。更准确的声明是：“在版本 v52.8、es-US Locale、拉丁文字、退款解释与受控工单创建任务、指定输入分布和政策版本下，哪些门禁证据通过。”

第三，文化不是从语言标签计算出的常量。说同一种语言的人可能生活在不同地区、属于不同世代和职业、使用不同称谓，也可能拒绝团队预设的群体习惯。文化语境必须以场景、来源、有效期和适用范围记录，允许 unknown、混合和个体覆盖。

第四，结论必须是可回放的决策。一个总体分数只是一项观测；从观测推断可能的首错层，再决定放量、限流、回退或阻断，是三个不同阶段。

1.2 本文不重复什么

本文不提供某个模型的“语言排行榜”，不尝试为所有文化建立固定规则库，不教读者从 IP 或姓名猜用户文化，不把自动翻译指标当作通用业务 Oracle，也不声称一次人工评审可以认证一个国家或群体。

以下问题也需要独立专业方案，本文只定义接口：

  • 特定司法辖区的法律合规与受监管翻译；
  • 医疗、司法、金融等高风险领域的持证语言服务；
  • 无障碍、字体、输入法、语音识别与语音合成的完整标准符合性；
  • 内容安全政策本身是否正当以及申诉机制怎样设计；
  • 生产级 Unicode 欺骗检测、国际化域名和身份标识符规范；
  • 每个国家的税务、邮政和地址可投递性认证。

把边界写清楚不是缩小责任，而是防止一个“多语言平均分”替这些领域做它无法做出的保证。

二、先拆开五个常被混用的概念

language、script、locale、region 和 culture 经常被塞进同一个 lang 字段。这样做会让数据无法解释，也让故障无法定位。

2.1 Language 不是 Locale

en-US 和 en-GB 可以共享主要语言，却使用不同的日期、地址和部分术语约定。fr-FR 与 fr-CA 也不能因为都以 fr 开头就共用一套未经验证的文案、币种和政策。

反方向同样成立：一个 Locale 内可以存在多种语言、方言和 code-switch。把设备 Locale 当作用户本轮输入语言，可能让路由器忽略用户主动切换语言。设备偏好、账户偏好、请求显式选择、检测结果和内容片段标签应分开保存，并定义冲突优先级。

2.2 Script 不是 Language

塞尔维亚语可以使用西里尔和拉丁文字；中文存在简体和繁体相关书写约定；同一句混语消息可能同时包含 Latn、Arab、数字和 Emoji。转写把一种文字系统映射到另一种表示，不等于把一种语言翻译成另一种语言。

Script 也不能只靠“字符多数”粗暴决定。品牌、代码、URL、订单号和引用原文经常使用另一文字系统。系统可以给整段设置主 Script，同时保存片段级 Script 观测和 mixed 状态；不能为了让标签整洁而删掉少数片段。

2.3 Locale 不是 Region

用户选择 en-US 界面，不表示订单一定发生在美国；人在加拿大也可能偏好 fr-FR 显示；跨境旅行者可能要求用中文解释日本交通票券。Locale 是格式和资源选择入口，业务 Region 则决定实际政策、商品、时区或合规范围。两者相同时也应分别记录，因为它们的来源与变更方式不同。

2.4 Culture 不是第六个固定枚举

团队若把 culture=Japanese 后面绑定“更间接”“更集体主义”等静态形容词，就已经把复杂群体压成了刻板印象。工程上更安全的结构是：

三、问题边界的反例：一句“翻译正确”为什么仍然会失败

下面反例中的输入与结果均为构造数据。

3.1 语义等价，但业务任务变了

源任务要求“解释政策，不执行退款”。译文为了自然省略了“不执行”，模型随后调用退款工具。译文读起来流畅，通用翻译分数甚至可能不低，但业务权限边界已经改变。

测试必须把 action_allowed=false 作为不可变事实槽，而不是只比对整句相似度。最终还要观察工具是否真的没有执行，不能只检查模型文本说“我不会操作”。

3.2 文字正确，Locale 错误

系统以法语回复加拿大用户，显示 1 250,00 $，文本语言没有问题；后台却将币种默认为 EUR，工具实际提交 1250 EUR。视觉格式通过不等于结构值正确。必须分别验证 amount=1250.00、currency=CAD、显示字符串和工具载荷。

3.3 日期每个字符都对，用户理解仍相反

源值是 ISO 日期 2026-06-07。界面输出 06/07/2026，没有注明 Locale，也没有月份名称。在某些读者眼中它是 6 月 7 日，在另一些读者眼中是 7 月 6 日。测试不应争论哪个顺序“正确”，而应根据目标 Locale 的格式资源和产品消歧规范验证；高风险场景可以要求月份名称或同时保留机器可读 ISO 值。

3.4 NFC 相等，不代表原文可以被覆盖

é 可能以单个预组字符表示，也可能由 e 加组合重音表示。NFC 可以为指定比较场景生成稳定的规范等价键，但存储系统若直接覆盖用户原始字节，就丢失了审计、签名、光标位置或上游证据。原文与派生比较键应并存。

3.5 NFKC 方便搜索，却可能消掉有意义区别

兼容归一化会把一些兼容字符映射到更一般的形式，例如某些圈号、宽窄形式或排版形式。因此 NFKC，或按明确顺序组合 NFKC 与 case folding 的派生策略，适合在明确威胁模型与字段契约下生成搜索、安全候选或标识符比较键，却不能无条件改写用户消息、法律文本、密码、签名内容、产品编号或需要保留排版区别的字符串。两个不同原文映射到同一个兼容键时，正确动作通常是记录碰撞并进入二次判定，而不是宣称它们本来相同。

3.6 Code-switch 被“主语言”吞掉

构造输入：“Necesito cambiar la dirección, but do not cancel the order.” 如果路由器只保留西班牙语片段，英语中的禁止动作会消失；如果强制整句翻译，订单号、品牌或法律用语又可能被改写。测试需要片段级观测、任务不变项和原文保全，不是只要求语言检测输出一个标签。

3.7 当地化得很自然，却文化本质化

模型根据用户地区自动假定家庭结构、宗教、性别角色或支付习惯，并用“当地人通常……”解释建议。表面上它在做文化适配，实际上把群体统计或刻板模板施加给个体。更稳妥的行为是说明选项、询问偏好、避免不必要推断，并在确有地区规则时引用规则来源。

3.8 Benchmark 领先，生产仍失败

XTREME 是跨语言表征研究的多任务 benchmark，原论文在其任务、语言、数据和实验设置内比较模型；NLLB 论文与 FLORES-200 为大规模机器翻译研究提供重要数据与实验。它们能帮助发现模型的跨语言能力差异，但不能自动覆盖本产品的实时政策、工具权限、地址可投递性、金额副作用、文化伤害或生产输入分布。

把 benchmark 结果当候选能力证据是合理的；把它当生产发布证书，就是把不同问题的分母和 Oracle 混在一起。

四、贯穿场景：跨境订单助手的任务契约

五、分层架构与数据流：把观测、判断和决策分舱

图中主链从控制面开始，经过两类样本、原文保全、被测执行链、自动证据、母语人工复核和发布门禁，最后进入不可变证据包。它不是简单的 translate -> model -> score。

5.1 控制面

控制面冻结一次运行的解释条件：

  • 任务、受众、风险和允许副作用；
  • 语言、Script、Locale、业务 Region 与时区；
  • 数据集、翻译器、术语表、模型、Prompt 和检索语料版本；
  • Tokenizer、Unicode 处理、CLDR/格式库及业务地址规则版本；
  • 自动 Oracle、语义 rubric、母语复核和仲裁版本；
  • 切片门槛、人工容量、例外审批、回退和停止条件。

Locale 数据会更新，业务政策也会更新。测试记录不能只写“使用当前 CLDR”或“采用最新版术语”，而要保存实际部署版本或内容摘要。否则一次回放发生差异时，无法区分模型变化、数据变化和格式资源变化。

5.2 数据面

数据面保留原生轨与翻译轨，并为每条记录生成不同用途的派生表示：

这些表示之间是有向派生关系，不是互相覆盖的临时变量。任何派生失败都保留源输入；任何碰撞都能反查所有原文。

5.3 执行面

执行面包含语言路由、检索、上下文组装、模型、工具调用、格式化和安全兜底。必须记录每层输入输出，因为最终的“语言错误”可能来自不同首错：

  1. 语言检测错，把请求路由到错误 Prompt；
  2. 检索只召回源语言政策；
  3. Prompt 把翻译文本误标成可信指令；
  4. Token 预算在目标语言下提前截断否定词；
  5. 模型结构值正确，格式化器用错 Locale；
  6. 工具适配器把显示字符串当结构金额解析；
  7. UI 双向文本或字体渲染破坏可读性；
  8. 人工队列没有目标语言复核员，超时后被静默自动放行。

六、数据模型：一条多语言样本要能追到原文、格式与复核

推荐把记录拆成 TaskCase、TextArtifact、ExecutionTrace、ReviewEvent 和 ReleaseDecision，而不是在一张表里不断加 lang_1、lang_2。

6.1 TaskCase

language 与 script 不从 locale 临时切字符串得到。BCP 47 语言标签提供了语言、Script、Region、Variant、Extension 等结构，但产品还需要把业务 Region、用户选择和观测值分开。Locale 的回退与 likely-subtag 可以帮助选择资源，不能被当成用户真实属性推断器。

6.2 TextArtifact

偏移量必须写明按字节、Unicode 标量值、UTF-16 code unit 还是字素簇计。前端光标常按 UTF-16 或字素行为，后端库可能按 code point，日志又记录 UTF-8 字节；不声明单位会让 span 看似合法却指向错误文本。

6.3 ExecutionTrace

Trace 至少关联：语言路由结果与置信度、路由输入摘要、检索 query 与文档语言、组装后 Prompt 的段落来源、各阶段 Token 数、模型与 Prompt 版本、结构化输出、格式化前结构值、格式化后显示值、工具载荷、工具响应、幂等键和外部后置条件。

高风险写操作不能只保存模型回复。模型说“已为你创建工单”是文本观测，真正成功需要工单系统返回且可查询到对应记录；模型说“不会取消订单”也不是安全证据，订单状态与工具审计才是。

6.4 ReviewEvent

“母语者”不是无限资格。一个人可能母语流利却不了解目标地区的金融术语、无障碍写作或业务规则。资格需要按语言、Locale 经验、领域训练和复核任务拆开；同时不要要求复核员代表整个群体。

6.5 ReleaseDecision

发布决策保存切片表达式、输入运行、通过和失败证据、风险接受人、有效期、开放比例、Fallback、监控指标与回滚条件。例外不是删除失败记录，而是追加一个带范围和到期日的决定。

七、测试集设计：覆盖矩阵，不制造“每种语言一百条”的假均衡

矩阵的重点不是把每个格子都填成绿色，而是防止不同维度互相代理。language=fr 不能代理 locale=fr-CA，region=EG 不能代理用户语言，culture_context_id 不能代理个体偏好。

7.1 先定义目标总体

对每个市场至少盘点：

  • 真实任务类型与风险等级；
  • 输入语言、Script、混语方式、长度和渠道；
  • 账户 Locale、请求显式语言和业务 Region 的组合；
  • 真实设备、键盘、输入法、客户端和字体条件；
  • 格式对象：日期、时间、时区、金额、币种、数字、单位、地址、姓名；
  • 政策与知识文档是否存在目标语言版本，哪个版本为权威；
  • 哪些任务可自动执行，哪些必须人工或禁止；
  • 母语复核容量、申诉与用户反馈入口。

若生产尚未开放，目标总体只能来自研究、试点、当地团队和受控用户测试，不能伪装成生产分布。此时报告应把自然发生率写为未知。

7.2 分层而非平均撒样本

推荐的切片键是：

这个笛卡尔积可能非常大，不需要机械穷举。先用风险和流量选主效应，再用成对组合、事故先验和状态机选择交互项。高风险写操作、币种转换、日期截止、地址变更、安全拒绝与低资源切片应获得比低风险寒暄更高的证据密度。

7.3 三类锚点

每个关键切片最好同时有三种锚点：

  1. 原生表达锚点：当地作者或真实授权样本，说明用户怎样表达；
  2. 平行事实锚点：多语言共享同一结构事实，说明跨语言不变项；
  3. 事故/风险锚点：历史问题或主动构造的边界，说明系统是否能发现关键失败。

机器翻译扩增只能补第二类和部分边界变形，不能替代第一类。合成的方言拼写也不能证明真实说话者会这样表达。

7.4 切分必须防翻译族泄漏

同一源样本的所有译文、回译、释义、转写和轻微改写属于一个 translation_family_id。训练、开发、校准和密封测试必须按族切分。若英语源样本进入训练、阿拉伯语译本进入测试，即使字符串完全不同，任务答案已经泄漏。

7.5 不要强求各语言行数相等

行数相等不能保证任务、风险、长度、翻译来源和人工质量相等。一个语言切片全是短翻译寒暄，另一个切片全是原生高风险写操作，直接比较准确率没有意义。报告需要给出构成、权重来源和分母，并同时提供等权宏平均与按目标总体加权结果。

八、翻译等价性：先承认翻译改变任务，再定义什么必须保持

翻译评测的首要产物不是一个相似度分数，而是等价契约。

8.1 四类内容分别处理

8.2 建立语义槽与关系图

对高风险任务，把源文解析成人工确认的槽和关系：

译文无需复刻源语词序，但必须能由目标语言复核员重建同一关系图。否定范围尤其要单列；“不要取消订单，只改地址”和“取消订单，不只是改地址”共享大量词，却产生相反动作。

8.3 允许不可译与多解

有些双关、亲属称谓、礼貌层级、法律术语和历史指涉没有一对一对应。数据模型应允许：

  • equivalence=partial；
  • 多个可接受译文；
  • 需要解释性注释；
  • 该样本只用于目标语言原生轨，不参与平行分数；
  • 因文化负载过高而退出自动门禁。

强迫每条都进入一个数字，会让不确定性消失在表格里，却不会让任务真的等价。

8.4 回译只是诊断变形

回译可以暴露实体丢失、否定反转或术语漂移，但它有三项边界：

  1. 正向与反向模型可能共享训练来源和表达偏好；
  2. 两次错误可能相互抵消，得到看似正确的源文；
  3. 一个自然目标句回译后不自然，不代表目标句错误。

所以 source ≈ back_translation 是候选告警，不是等价证明。高风险样本仍需独立双语人工或确定性事实 Oracle。

8.5 翻译方向和 Pivot 单独评测

若系统用英语作 pivot，把 ar -> en -> fr 与直接 ar -> fr 放在不同切片。每多一跳，都可能丢失敬语、性别、否定、数字或当地术语。记录每跳中间文本，不允许只保存最终译文。故障注入可以在 pivot 中故意删除一个限制条件，验证最终门禁是否能通过事实槽发现。

九、Unicode、规范化和 Tokenization：字符串不是“字符数组”那么简单

Unicode UAX #15 定义了 NFC、NFD、NFKC、NFKD 等规范化形式。工程上最重要的不是背名称，而是为每个字段回答：原文是否必须逐字保留，比较需要哪种等价，兼容差异是否有语义，安全威胁模型是什么，哪个版本的库执行了派生。

特别要避免一句常见但错误的要求：“入库前对所有用户原文 NFKC，保证兼容。”这会把兼容等价误当成无损。对自然语言消息，NFKC 可能改变作者有意使用的表示；对账号、产品码、法律证据和密码字段，后果更严重。是否使用必须逐字段建模。

9.2 NFC 也不是万能语义比较器

NFC 处理规范等价，不会解决大小写、空格、标点、变体字、同形异码、语言学排序或拼写差异。把两段文本 NFC 后不同，不能推断语义不同；NFC 后相同，也只说明在该规范化定义下得到相同序列，不说明两个业务实体必然相同。

拼接、截断和分片后还要重新考虑规范化边界。不要在未知 code unit 边界切开组合序列，再假设局部 NFC 等价于完整文本处理。

9.3 字节、码点、字素簇和 Token 是四个量

  • UTF-8 字节数影响传输与数据库限制；
  • Unicode code point 数影响部分后端 API；
  • 扩展字素簇更接近用户看到和光标移动的“字符”；
  • 模型 Token 数由具体 Tokenizer 词表和算法决定。

它们之间没有固定比例。一个 Emoji 序列可能由多个 code point 组成但显示为一个字素簇；没有空格的文本用 split() 统计会严重失真；同一句话在不同模型 Tokenizer 下可能有不同 Token 数。UAX #29 给出默认字素、词和句边界算法，并允许按需要裁剪；生产 UI、搜索和模型 Tokenizer 仍需各自验证，不能用 Python len() 或正则 \b 冒充完整实现。

9.4 Tokenizer 必须进入版本与回归

每个请求至少记录：

  • Tokenizer 标识、词表摘要和库版本；
  • 原文、模板、检索片段、工具结果分别消耗多少 Token；
  • 截断发生在哪一层、哪一段和哪个边界；
  • 输入与输出预算是否按目标语言实测；
  • 模型切换后是否重新计数，而不是沿用旧供应商估算。

测试要注入长复合词、无空格文本、组合字符、Emoji、RTL/LTR 混排、稀有文字和 code-switch。验收目标不是各语言 Token 数相等，而是在任务预算内关键指令、否定和证据不被截断，并对成本与延迟切片有真实观测。

9.5 双向文本和不可见字符

阿拉伯语、希伯来语与拉丁订单号混排时，视觉顺序和存储顺序可能不同。日志、代码块、表格、复制粘贴和工具载荷都要测试。安全场景还要关注默认可忽略字符、方向控制、零宽字符和易混淆字符。

UTS #39 提供 Unicode 安全机制与混淆检测框架，但它不是“一键删除所有可疑字符”的许可证。自然语言允许的字符比程序标识符广得多。更合理的做法是按字段采用 allowlist/profile、记录可疑信号、显示安全提示，并在身份或资金操作中二次确认；不要静默改写用户表达。

十、Locale 正确性：结构值、显示值和业务规则三层验证

Unicode UTS #35 与 CLDR 定义和提供 Locale 数据、标识、日期时间、数字、复数、单位、消息格式等国际化资源。它们是本地化基础，不是全部业务真值。货币是否允许退款、地址是否可配送、税率和法律截止期仍来自业务系统与地区政策。

10.1 日期与时间

日期测试至少区分：

  • 不含时间的民用日期，如生日或账单日；
  • UTC 时间点与带偏移时间；
  • 时区规则下的当地时间；
  • 日历系统；
  • 解析格式与显示格式；
  • 夏令时跳变、重复时间和不存在时间；
  • “下周五”“月底”等相对表达的参考时钟。

内部交换优先使用结构化值和明确时区，不要让模型输出的 03/04/2026 成为唯一事实。显示层按 Locale 格式化，高风险文案要求消歧；解析用户输入时若存在多解，应询问而不是猜测。

10.2 金额、币种与数字

金额必须是数值与 ISO 币种代码的组合，显示符号只是派生。$ 不能独立确定 USD、CAD、AUD 或其他使用类似符号的货币。测试同时验证：

小数与分组分隔符、数字字形、负号位置和不换行空格都可能变化。不要用删除逗号再 float() 的自制解析器处理所有 Locale；也不要把显示舍入后的值反向用于资金计算。

10.3 单位与量纲

英里换公里属于数值转换，不是纯文本翻译。必须保存源值、源单位、目标值、目标单位、转换规则和舍入策略。温度更不能只替换 °F 为 °C。变形测试可验证往返转换误差在定义范围内，并确保工具接收的量纲与 UI 显示一致。

10.4 地址

全球地址不是 street/city/state/zip/country 五个固定字段。地址可能包含多级行政区、楼栋、单元、村镇、邮政编码、本地文字与拉丁转写；字段顺序和必填项随业务地区变化。

AI 可以辅助解析或补问，不能凭语言模型“常识”补出不存在的行政区。测试需要：

  • 原始地址逐字保存；
  • 结构化字段带置信度和来源 span；
  • 不支持字段不会被静默丢弃；
  • 本地文字与转写分别保存，不互相覆盖；
  • 地址验证服务结果与 AI 推断分开；
  • 修改前后比较关键字段，写工具后验证可查询状态；
  • 低置信或多候选时要求用户确认。

10.5 姓名、称谓与排序

姓名不应强制拆成固定的 first/last，也不能从姓名推断性别、国籍或称谓。产品若确实需要称呼，应允许用户提供 display name 和称谓偏好。排序、搜索和唯一性分别使用适合的规则；语言学 collation 结果不承担身份唯一键职责。

10.6 复数、语法性别与消息模板

把英文模板拆成 "You have " + n + " items" 再翻译，经常无法处理目标语言的复数类别、词序和格变化。使用 Locale 消息格式资源，并测试 0、1、2、少量、大量、小数和负数等业务允许边界。模型生成文案也要保留结构槽，不让它擅自改变数量。

十一、方言、Romanization 与 Code-switch：真实输入不是标准语考试

11.1 方言不是错误标签

方言、地区变体、社群用语、拼写变体和口语缩写是生产输入的一部分。数据清洗若只保留“标准语”，会让评测集天然看不见最容易失败的用户。报告也不要把标准语切片命名为 normal、其他切片命名为 noisy，这种命名会把社会层级偷渡进质量模型。

更合适的字段是 variety_label_source、self_identified_or_annotated、orthography_standardization 和 uncertainty。标签体系由当地语言专家审阅，允许复核员选择“无法可靠判断”。

11.2 Romanization 不是单一规则

用户可能用拉丁字母输入通常使用另一 Script 的语言，拼法未必遵循官方转写标准。评测应覆盖真实输入分布、品牌与订单号混合、长短元音或声调省略等情况。不要把转写器输出当原文替代；转写候选只是检索或路由辅助。

11.3 Code-switch 需要片段与任务双层指标

语言识别的目标不一定是给每个 Token 贴完美标签。对订单助手，更重要的问题是：所有影响动作的片段是否进入上下文，语言切换后语义槽是否完整，回复语言是否符合用户当前选择，工具字段是否保真。

可以同时记录：

  • 片段语言/Script 检测的精确率与召回率；
  • 混语任务成功率；
  • 非主语言关键约束保留率；
  • 模型是否不必要地强迫用户改用标准语；
  • 语言切换后的回复一致性；
  • 人工复核认为自然且不居高临下的比例。

片段标签错误不一定造成任务失败，任务成功也不能证明片段处理正确。两类证据分别报告。

11.4 变形测试

从一条人工确认的任务生成受控变形：

  1. 只把礼貌开场换成另一语言，动作槽应不变；
  2. 只把否定条件换成另一语言，系统必须仍保留禁止动作；
  3. 将订单号附近加入 RTL/LTR 边界，工具 ID 不变；
  4. 把标准拼写换成真实授权的方言变体，任务结果等价；
  5. 在品牌与技术词周围切换语言，不应把品牌翻译或删除；
  6. 改变设备 Locale 但保持请求显式语言，验证优先级；
  7. 将短输入扩展为长混语历史，关键约束不能因 Token 预算消失。

这些变形只证明定义的不变关系，不证明所有方言都已覆盖。

十二、文化语境与偏差：本地化不是把刻板印象写进 Prompt

12.1 从场景假设开始，不从群体画像开始

文化测试应围绕具体交互：谁对谁说话、在什么机构、执行什么任务、风险是什么、用户能否纠正默认、来源何时有效。比如“客服升级拒绝措辞是否让用户理解还有申诉入口”是可测试问题；“某国用户更服从权威”不是合格的产品规则。

每个文化假设都要记录：

  • 谁提出、依据是研究、政策、用户反馈还是复核经验；
  • 适用于哪个任务和受众，不适用于什么；
  • 是否存在群体内分歧；
  • 用户显式偏好怎样覆盖默认；
  • 何时复审、谁能撤回；
  • 错误适配可能造成什么伤害。

12.2 文化适配有时应选择“询问”

当系统不知道称谓、家庭关系、宗教日历、饮食偏好或身份术语时，最可靠的本地化可能不是猜一个“当地默认”，而是给出中性选项或询问用户。测试因此不能只比较输出与唯一参考答案，还要把适当澄清作为可接受行为。

12.3 翻译会改变安全与伤害

伤害词、隐喻、侮辱、身份术语和威胁强度在翻译后可能减弱、增强或转类。源语言安全标签不能自动复制到目标文本。高风险安全评测需要目标语言原生样本、目标语言政策解释、当地复核员和跨语言一致性检查。

同样一句拒绝在某种语言里可能显得礼貌，在另一语境里可能模糊到让用户误以为动作已经执行。安全不是“所有语言输出同一句模板”，而是保留相同边界、申诉与可理解性。

12.4 偏差至少看四层

  1. 数据层：某些语言只有翻译短句，另一些有原生复杂任务；
  2. 系统层：路由、检索、Token 预算和工具在不同切片的可用性；
  3. 结果层：任务成功、拒答、伤害、人工转交和副作用差异；
  4. 体验层：礼貌、清晰、被尊重感、纠错成本与申诉可达性。

发现群体差异是观测，不自动给出因果。可能解释包括样本难度、翻译来源、政策可用性、网络条件、模型能力或人工队列差异。需要通过匹配任务、分层重加权、版本对照和受控实验逐步排除。

HolisticBias 原始研究展示了一种用人口属性描述词与句子模板主动探测语言模型偏差的研究路径。此类构造模板适合发现需要复核的候选关联，却不是生产人群分布、实际伤害发生率或因果机制的替身；迁移到产品时仍要经过当地复核、任务校准和伤害评估。

12.5 反事实测试的边界

仅替换姓名、方言或地区标识，观察输出是否变化，可以发现敏感候选；但反事实必须保持任务事实可比。把“邮政编码”“政策”“货币”一起改掉后，结果变化可能是合法业务差异。

反事实不应制造或传播侮辱性群体模板，也不能因为一组替换没有差异就宣称系统公平。它是一种局部诊断，不是社会层面的因果证明。

十三、母语人工复核：把不可自动化的判断变成可审计流程

自动规则擅长检查结构值、格式、Schema、实体和后置条件；对于语用、自然度、含蓄威胁、称谓、幽默、污名与文化伤害，母语人工复核仍是关键证据。但“找一个母语者看一下”不是质量系统。

13.1 先拆复核任务

不同评审问题需要不同能力：

复核任务 主要问题 评审需要看到什么 适合谁
双语等价 事实、否定、条件、语气强度是否保持 源文、译文、语义槽、术语表 双语且受过任务训练的复核员
单语自然度 目标文本是否清晰自然、像真实产品表达 目标文本、受众、上下文，不一定显示供应商 目标语言母语/高熟练当地复核员
Locale 格式 日期、货币、数字、单位是否正确且消歧 结构值、Locale、显示值、业务规则 本地化工程或受训复核员
文化/伤害 是否冒犯、刻板化、误导或破坏申诉 场景、受众、政策、完整对话 当地情境专家与受影响群体顾问
业务动作 工具与后置条件是否正确 结构输出、工具 trace、业务系统 领域专家，不要求其独自判断语言自然度

让同一个人同时判断全部维度会造成认知负担，也使错误来源不可分。复核界面应按任务最小披露必要证据，同时允许评审查看上下文而不是孤立句子。

13.2 双标与仲裁

高风险样本采用独立双标。两名评审先独立作答，不看模型供应商、候选版本、自动分数和对方意见，降低锚定。分歧后先要求各自给出 span、类别和理由，再由具备语言与领域能力的仲裁员处理。

仲裁不是把两个分数取平均，而是产生新事件：采用哪个标签、依据什么、rubric 是否含糊、样本是否退出金标。若分歧反映真实多解，可以保留多个可接受答案或标记 contested，而不是强迫共识。

13.3 错误分类与严重度

可以借鉴 MQM 的多维错误分类思想，把错误落在 accuracy、terminology、fluency、style、locale convention、audience appropriateness 等可操作类别，再按产品补充 SIDE_EFFECT、POLICY_SCOPE、CULTURAL_HARM。但分类树必须版本化，不能把任何领域的自定义树冒充 MQM 官方唯一实现。

严重度由业务影响定义：

  • critical：造成资金、权限、法律、安全或不可逆副作用，或对群体产生严重伤害；
  • major：任务失败、关键事实误导、用户需要明显返工；
  • minor：不改变任务但降低清晰度、自然度或一致性；
  • preference：多个可接受表达中的风格偏好，不计作错误。

不要把出现次数直接等同严重度。一个币种错误可能只出现一次，却必须阻断；十个标点偏好不应抵消它。

13.4 评审质量也要评测

复核流程至少跟踪：

  • 金标哨兵的通过率与错误类型；
  • 双标一致与分歧矩阵，不只报一个总体一致率；
  • 各类别的仲裁翻转率；
  • 每位评审的语言、领域和 Locale 覆盖边界；
  • 平均用时、排队时间、疲劳与异常快审；
  • 分歧是否集中在 rubric 含糊项；
  • 供应商/模型盲化是否有效；
  • 评审意见是否被产品团队采纳及后续结果。

一致率低不自动表示评审差，可能说明任务确有多解或规则定义不足。一致率高也不保证正确，两名评审可能共享同一培训偏差。金标、仲裁、复审和当地用户反馈需要互补。

13.5 人工容量是发布约束

如果某高风险 Locale 每周只能复核 50 条，却计划放量到每天 10 万次写操作，系统不能假设“异常时转人工”是无限兜底。发布门禁要把人工到达率、服务时限、积压、语言覆盖和节假日纳入容量模型。队列超时不能静默自动批准；应回退为只读、停止动作或明确告诉用户稍后处理。

十四、指标与公式：每个分数都要说明分母、切片和不能证明什么

多语言评测至少同时报告任务、语言、Locale、伤害、人工和覆盖指标。不要先把它们压成一个总分。

14.1 切片任务成功率

对切片 (s)：

[
TSR_s = \frac{\sum_{i \in s} w_i \cdot \mathbb{1}(task_i_accepted)}{\sum_{i \in s} w_i}
]

task_accepted 要包含结构结果与必要后置条件。若任务要求创建工单，仅回复文本正确不进入分子。权重 (w_i) 来自目标总体、风险或等权设计，必须说明来源；没有可靠生产分布时，同时给未加权结果，不伪造自然权重。

14.2 语义不变项保留率

设样本 (i) 有必须保持的事实集合 (F_i)：

[
SIR = \frac{\sum_i \sum_{f \in F_i} \mathbb{1}(f\ preserved)}{\sum_i |F_i|}
]

总体 SIR 仍会隐藏关键槽，因此否定、权限、币种、金额、日期、实体 ID 分开报告。高风险 forbidden_action 可以设置零容忍，而不是与大量普通实体平均。

14.3 Locale 结构与显示正确率

把两层拆开：

[
LVA_s = \frac{\left|{结构值、币种、时区、单位均正确}\right|}{N_s}
]

[
LDA_s = \frac{\left|{在目标 Locale 下显示正确且无歧义}\right|}{N_s}
]

只有 LDA 高而 LVA 低，说明“看起来本地化”掩盖业务值错误；只有 LVA 高而 LDA 低，说明模型或工具可能正确但用户体验和理解风险仍不合格。

14.4 严重度加权错误密度

构造一个产品错误权重 (c(e))，在固定机会单位上统计：

[
WED_s = \frac{\sum_{e \in errors_s} c(e)}{opportunities_s}
]

opportunities 可以是源词数、目标词数、消息数或任务数，但跨语言词边界差异很大。产品任务通常更适合以任务或已标注槽位为分母，并另报原始错误数。权重由业务风险批准，不能声称是自然界客观常数。

14.5 自动翻译指标怎样使用

BLEU 原始方法基于修正 n-gram 精确率与 brevity penalty，适合在明确语料和参考条件下做系统级比较；chrF 使用字符 n-gram 的精确率与召回率，能减少某些分词依赖；COMET 使用源文、候选和参考等信号训练评价模型。它们回答的都不是“生产任务已正确完成”。

自动指标的使用纪律是：

  • 同一数据版本、同一规范化与聚合方式比较；
  • 记录语料级还是句级、参考数量与语言方向；
  • 先在目标语言和错误类型上用人工锚点校准；
  • 不把不同指标的数值直接横比；
  • 不用平均增益抵消否定、权限、金额等关键错误；
  • 对方言、混语、文化改写和多参考不足切片保持谨慎；
  • learned metric 本身也可能有训练分布与语言覆盖边界。

公开论文报告的数字只在原数据、模型与实验条件内成立。本文不搬用任何分数作为构造系统阈值。

14.6 宏平均、微平均和最差切片

设有 (K) 个预注册切片：

[
MacroTSR = \frac{1}{K}\sum_{s=1}^{K} TSR_s
]

若 14.1 的 TSR_s 使用样本权重，跨切片的微平均也必须沿用同一估计目标：

[
WeightedMicroTSR =
\frac{\sum_s\sum_{i\in s}w_i\cdot\mathbb{1}(task_i_accepted)}
{\sum_s\sum_{i\in s}w_i}
]

如果还需要描述“评测集每一行等权”的观察值，应另名为未加权行微平均：

[
UnweightedRowMicroTSR = \frac{\sum_s success_s}{\sum_s N_s}
]

两者不能都简称 MicroTSR：前者估计权重所声明的目标总体，后者只描述当前评测集的行构成。未加权行微平均容易由样本量大的语言支配；按生产权重的微平均则容易由真实高流量语言支配；宏平均又可能让极小、极不稳定切片与主切片同权。报告三者时必须带全名、权重版本和分母，同时给出 min_slice_TSR、样本量和区间。切片必须在看结果前预注册，避免只展示有利分组。

14.7 差异与公平观察

对切片 (a,b)：

[
Gap(a,b)=TSR_a-TSR_b
]

这个差值是观测，不是歧视原因的证明。若任务难度、翻译轨比例、设备或政策资源不同，差异不能直接归因到模型语言能力。排查时先做相同源任务的平行比较，再看原生轨；再检查路由、检索、Token、工具和人工流程。

14.8 伤害与不必要拒答

安全至少同时报告：

[
HarmRate_s = \frac{harmful\ accepted_s}{eligible_s}
]

[
OverRefusal_s = \frac{safe\ tasks\ incorrectly\ refused_s}{safe\ eligible_s}
]

分母必须区分本应拒绝与本应帮助的任务。只降低伤害率可能通过对某语言全面拒答实现，这不是合格改进。

14.9 人工复核指标

人工指标包括 native_review_coverage、双标覆盖、仲裁率、争议率、关键错误漏检率、P95 排队时间和超时回退正确率。母语复核覆盖率的分母应是按契约要求复核的任务，不是所有请求，以免把低风险自动任务稀释进去。

14.10 覆盖完整性

对必需格子集合 (G)：

[
EvidenceCoverage = \frac{\left|{g \in G: native\ anchor \land automated\ run \land oracle \land decision}\right|}{|G|}
]

只有样本而没有执行、Oracle 或发布决定，不算证据完整。行数覆盖与证据覆盖分开。翻译样本不能自动满足 native_anchor。

十五、自动化策略：规则先守事实，模型找候选，人工处理价值判断

15.1 第一道：Schema 与结构 Oracle

先检查语言标签格式、必填字段、金额 Decimal、币种代码、ISO 时间、地址字段来源、工具参数、幂等键和后置条件。这些可确定规则不需要 LLM Judge。

对每个错误返回稳定代码，例如 CURRENCY_CHANGED、NEGATION_DROPPED、RAW_TEXT_OVERWRITTEN、NFKC_KEY_COLLISION、TOKEN_TRUNCATED_REQUIRED_SPAN。稳定错误码便于趋势分析，也避免把模型解释当唯一证据。

15.2 第二道：Unicode 与 Token 合同

自动保存原文摘要、派生键与碰撞集合；对组合字符、双向控制、混淆候选和非法序列执行字段特定策略。再用部署中的真实 Tokenizer 计数，比较预算、截断点和关键 span。

测试环境可以用 mock 演示控制流，但发布验收必须运行真实 Tokenizer 与真实序列化模板，因为模型、供应商和版本之间不可互换。

15.3 第三道：翻译不变项与变形关系

从人工确认的语义槽生成自动断言：实体、数字、币种、否定、条件、许可和关系图保持。对允许变换的单位和日期，比较结构值与转换规则，而不是逐字相同。

变形测试成对运行：原生/翻译、直接/pivot、标准/方言、单语/混语、NFC 组合方式、Locale 变化、长短上下文。若预期关系被破坏，保留两次完整 trace 以便定位首个分叉层。

15.4 第四道：多模型或语义 Judge 只做候选

Judge 可以识别自然度、相关性、可能冒犯与事实遗漏候选，但必须：

  • 用目标语言和错误类型人工锚点校准；
  • 记录 Judge 模型、Prompt、语言能力和输出理由；
  • 对供应商与候选盲化，避免品牌锚定；
  • 高风险不让同一生成器自证；
  • Judge 分歧进入人工队列，不静默取多数；
  • 不把 Judge 置信度当真实正确概率。

15.5 第五道：母语复核与业务复核

自动规则把样本按风险、分歧、OOD、低资源切片和新文化情境排序。人工结果以事件追加，不能覆盖模型原输出或第一轮标签。业务写操作另外验证工具和后置条件。

15.6 CI、影子与灰度

CI 运行小而密封的关键切片：Unicode 契约、事实槽、Locale 格式、工具 Schema 和已知事故。影子阶段使用生产输入的授权、去标识副本，不执行真实副作用；灰度阶段只开放低风险或可逆任务，并按 Locale 设独立停止条件。

新增语言不能只复制英语门禁阈值。先验证样本构成、人工可用性和基线，再设风险等价的门槛。供应商切换也必须重跑 Token、格式、工具和安全链，而不是只复用模型层分数。

十七、故障注入：让每一层在发布前真实失败一次

健康样本全绿只能说明主路径能跑。故障注入要验证探针、门禁、人工队列、回退和证据包是否在错误发生时按预期工作。

17.1 翻译层

  • 删除或反转否定，期望 SEMANTIC_INVARIANT 阻断；
  • 把条件从“仅当”弱化为“如果”，检查权限是否扩大；
  • 更改实体、金额或币种符号但保持句子流畅；
  • 插入 pivot language 并在中间跳丢失称谓或警告强度；
  • 用同一模型正向翻译和回译，检查系统是否错误地把闭环一致当独立证据；
  • 让译文完全正确但标错 translation family，检查切分污染门禁。

17.2 Unicode 与 Token 层

  • 使用规范等价的预组/分解序列，验证比较键相等而原文分别保存；
  • 使用会在兼容归一化下碰撞的标识符，验证不自动合并；
  • 插入组合字符、Emoji 序列、变体选择符、零宽和双向控制候选；
  • 在 UTF-8、UTF-16 与 code point 边界故意截断；
  • 用空格估算低估无空格文本，让关键否定落在预算外；
  • 切换模型但不切 Tokenizer 版本，期望契约测试失败。

17.3 Locale 层

  • 只换显示符号不换结构币种；
  • 日期月日互换但保持字符串格式合法；
  • 时区缺失、夏令时边界或相对日期参考时钟漂移；
  • 把 1,250.00 按另一 Locale 解析为不同数值；
  • 单位只换标签不换数值；
  • 地址适配器丢弃一个不认识的行政层级；
  • 复数模板只覆盖英语的一与其他两类。

17.4 方言、混语与文化层

  • 将禁止动作放入非主语言片段；
  • 将品牌、订单号和 URL 置于另一 Script；
  • 使用授权的方言变体与 Romanization，检查是否被贬为无效输入；
  • 改变设备 Locale 而不改变用户显式语言；
  • 让文化提示词含有刻板群体规则，检查安全审查能否发现；
  • 给出用户明确偏好与 Locale 默认冲突，检查个体偏好是否优先；
  • 制造两位合格母语复核员的合理分歧，检查系统是否保留 contested。

17.5 系统与流程层

  • 目标语言检索索引为空，验证不会用源语言旧政策静默回答；
  • 母语人工队列积压、评审离线或 SLA 超时，验证写操作回退；
  • Judge 服务不可用，验证高风险任务不自动通过；
  • Locale 配置版本回滚但缓存未失效，检查版本键；
  • 工具返回未知提交状态，验证幂等与人工恢复；
  • 日志删除原文或误记归一化文本，检查证据完整性门禁；
  • 监控聚合漏掉低量语言，检查最小切片和缺失数据告警。

17.6 组合故障

最危险的是看似互相补偿的组合：pivot 翻译丢否定，模型仍生成礼貌解释；币种结构错误，显示层又渲染成当地符号；人工队列超时，系统把 pending 映射成 passed。单层单测可能全绿，端到端副作用已经错误。

组合注入要预先写出首错层、扩大因素、可观测信号和预期停止动作。实验结果若与预期不同，先修探针和门禁，再讨论模型优化。

18.5 逐层排查

第一步：验证数据与切分

检查同一 translation family 没有跨训练与密封集；复核 fr-CA 两条是原生任务，不是翻译错误；ar-EG 三条共享一个英语源族和同一 pivot 配置。发现发布报表 SQL 把 review_state IN ('passed','pending') 都计入覆盖，这解释了人工覆盖虚高，但不解释四类产品错误。

第二步：找每条链的首个分叉

fr-CA 的订单结构值最初为 CAD，模型结构输出仍为 CAD；工具适配器通过 locale.startswith('fr') 选择了 EUR 默认。首错在工具适配层，不在模型或法语翻译。

ar-EG 的源语义槽包含 forbidden_action=ISSUE_REFUND_DIRECTLY，直接阿拉伯语译文也保留；启用英语 pivot 的压缩 Prompt 后，中间文本丢失否定，后续模型忠实执行了错误任务。首错在 pivot 翻译配置，模型动作是下游表现。

es-US 的语言路由只输出单标签；检索器将 en 结果绑定英语索引，即使西班牙语片段包含订单问题也未生成双语 query。权限过滤和索引内容正常。首错是单标签路由契约，缺少片段与任务级策略。

zh-Hant-HK 的原文与结构 ID 都不同；身份缓存为了“统一全角和装饰字符”只保存 NFKC 后 casefold 的派生键，没有原文二级比较。首错是缓存身份键设计，不是中文模型。

第三步：检查扩大因素

  • 自动总分按行微平均，高流量低风险解释任务稀释关键失败；
  • UI 只显示 $，掩盖 CAD/EUR 结构差异；
  • 同一个翻译模型承担正向、pivot 与回译，回译没有暴露共同盲区；
  • 人工覆盖报表把 pending 当 passed；
  • 发布会上先展示总体和供应商 benchmark，切片证据排在附录；
  • 缓存告警只统计命中率，没有记录归一化碰撞数。

这些是贡献因素，不等于首错层。

18.6 排除的错误方向

重放显示真实 Tokenizer 没有截断三条阿拉伯语样本，因此本次不能归因为“阿拉伯语 Token 更多”；模型在直接译文上动作正确，因此不能泛化成“模型不支持阿拉伯语”；fr-CA 文本自然度经母语双标通过，因此不是法语质量问题；zh-Hant-HK 碰撞发生在任何模型调用前，和生成模型无关。

排除这些方向很重要。否则团队可能更换模型、增加 Prompt 或扩大 Token 预算，既增加成本又不修真正缺陷。

18.7 发布决策

最终不是“一起上线”或“全部取消”的二元决定：

范围 决策 条件
四个切片的低风险政策解释 20% 灰度 只读、引用目标地区政策、独立停止指标
fr-CA 退款工单 阻断 修复结构币种来源，重跑 CAD/EUR/AUD 反例与后置条件
ar-EG 写操作 阻断；保留只读 移除不合格 pivot，独立重译，关键否定双标归零
es-US 混语任务 回退到人工/双语检索试点 片段路由和检索契约通过后再灰度
zh-Hant-HK 地址修改 阻断 缓存使用内部不可变 ID；兼容键只作候选并处理碰撞
人工 pending 样本 不计覆盖 复核完成或明确退出，不允许报表自动转绿

这是风险约束下的发布决定，不是宣称某个 Locale “质量差”。只读解释与写操作有不同副作用，因此允许不同发布范围。

18.8 修复与验收

修复包括：币种只从订单与显式业务规则读取，Locale 只控制显示；翻译链在每跳执行语义槽断言；语言路由输出片段、主任务语言和 fallback query；缓存唯一键改用后端不可变 ID，NFKC 与 case folding 派生只用于搜索候选；报表要求复核事件最终态。

重新验收时运行：

  • 四个 Locale 的金额结构值/显示值/工具后置条件矩阵；
  • 直接与 pivot 翻译的否定、条件、数字和权限变形；
  • 原生西英混语与非主语言关键约束测试；
  • NFC 规范等价、NFKC 兼容碰撞、双向文本复制粘贴；
  • 人工队列积压与超时回退注入；
  • 旧事故逐条回放和新 run 的证据差分；
  • 每个发布切片的下界、关键错误数和证据覆盖。

只有新证据包通过才更新决定；旧失败不会从历史报表消失。

18.9 这次案例真正说明什么

它说明四件工程事实：总体平均可能掩盖高风险切片；翻译改变任务且中间跳必须可见；Locale 错误可能发生在模型外；Unicode 兼容键不能承担原始身份。它不说明任何现实模型、供应商或语言存在相同缺陷，也不能从构造样本估计生产发生率。

十九、排障手册：从症状回到首错层

19.1 回复语言错误

依次检查请求显式偏好、账户/设备 Locale、语言与 Script 片段、路由输入、路由输出、Prompt 语言要求、检索文档语言、Fallback 和模型输出。不要看到最终英语回复就直接归因模型；索引为空或系统 Prompt 覆盖也会产生同样症状。

19.2 翻译指标下降

先核对数据、参考、规范化、分词和指标实现版本；再看下降集中在什么错误类型。自然本地化可能降低逐字 n-gram 重合但提高任务表现；反过来，参考重合上升也可能复制了错误参考。用人工锚点和语义槽确定是否是真退化。

19.3 Token 或成本异常

检查 Tokenizer 是否与部署模型一致，系统模板、检索片段、输出长度和重试是否变化，再按 language/script/input mode 切片。Token 数差异是观测，不要把成本差异包装成语言本身“效率低”的本质属性。

19.4 Locale 显示错误

从结构值开始，沿业务 Region、用户 Locale、格式库版本、缓存键、客户端渲染逐层比较。若结构值已错，换显示模板无效；若结构值正确，模型重训可能没有必要。

19.5 文化伤害告警

保留完整上下文，联系具备当地情境能力的复核者，判断伤害类别、受众、严重度和用户申诉；再追踪是数据模板、Prompt、模型、安全策略还是后处理引入。不要让一个自动分类器宣布“文化已合规”，也不要要求单个复核员代表整个群体。

19.6 某语言成功率低

先比较同一平行任务，再比较原生任务；对齐风险、长度、工具和政策可用性；检查翻译轨比例、检索覆盖、Token 截断、路由、延迟、Fallback 与人工积压。只有在这些条件得到控制后，才能谨慎讨论模型能力差异。即使发现稳定相关，也不要越过证据声称因果机制。

二十、从零到一的实施顺序

阶段一：拆字段与支持声明

先把 lang 拆成语言、Script、Locale、业务 Region、用户偏好和文化情境；为现有市场写实际支持范围、风险边界与未知项。没有这一层，后续任何分数都无法定位。

阶段二：保全原文与结构值

建立 raw text、NFC 比较键、NFKC 与 case folding 候选键的有向派生；金额、币种、日期、地址、动作从显示文本中分离。补处理顺序、Tokenizer、格式库和政策版本。

阶段三：双轨数据与关键 Oracle

为每个关键任务建立少量高质量原生锚点与平行事实锚点；先自动检查实体、否定、权限、金额、日期、工具与后置条件。按 translation family 切分，防止跨语言泄漏。

阶段四：母语复核与错误分类

明确复核任务、资格、双标、仲裁、严重度和容量。先覆盖高风险、方言混语、文化伤害与自动分歧，不追求所有低风险文本逐条人工。

阶段五：故障注入与切片门禁

让翻译、Unicode、Tokenizer、Locale、检索、Judge、人工队列和工具分别失败；确认门禁真实变红、回退可用、证据能回放。发布按切片和副作用分级。

阶段六：生产闭环

灰度收集授权反馈、纠正成本、人工转交和外部后置条件；定期重估输入分布与文化假设。新政策、新 Locale 数据、模型和 Tokenizer 都触发相关切片回归，而不是等待年度大测。

二十一、可执行上线检查清单

概念与支持边界

  • Language、Script、Locale、业务 Region、Culture/情境是独立字段；
  • 设备 Locale、账户偏好、请求显式语言和检测结果没有混为一项；
  • 支持声明绑定任务、风险、版本、输入模式与未覆盖范围；
  • Locale 不被当作国籍、文化、币种或个体偏好的自动证明；
  • 文化假设记录来源、适用场景、异质性、有效期与撤回人；
  • 用户显式偏好可以覆盖非强制默认。

数据与翻译

  • 原生任务轨与平行翻译轨分开采样、报告和门禁；
  • 翻译方向、pivot、译者/模型、Prompt、术语表和修订有血缘；
  • 同一 translation family 不跨训练、校准和密封测试；
  • 每条高风险样本定义事实、否定、条件、权限与实体不变项；
  • 可本地化变量、不可译项和多解状态明确；
  • 回译只作为候选诊断，不被当作独立真值；
  • 机器翻译扩增不计作原生表达覆盖。

Unicode 与 Tokenizer

  • 原始字节/文本与所有归一化派生键分开保存；
  • NFC 只用于字段契约允许的规范等价比较；
  • NFKC 或其与 case folding 的组合不无条件覆盖用户原文；
  • 兼容归一化可能丢失区别的字段已识别；
  • 派生键碰撞能反查全部原文并触发二次判定；
  • span 单位明确为字节、code point、UTF-16 code unit 或字素簇；
  • 组合字符、Emoji、RTL/LTR、不可见字符与混淆候选有测试；
  • 真实 Tokenizer 标识、版本、词表摘要、各段 Token 数已记录；
  • 模型切换后重新计算预算与截断，不沿用字符估算。

Locale 与结构值

  • 日期值、时间点、时区、日历和显示字符串分开；
  • 歧义日期会询问或按高风险消歧规范显示；
  • 金额使用 Decimal/整数小单位与显式币种，不从 $ 猜币种；
  • Locale 只控制显示时，不会静默改变业务币种；
  • 单位转换保存源值、目标值、规则与舍入；
  • 地址原文保留，结构字段有来源 span、置信与用户确认；
  • 本地文字地址与转写分别保存；
  • 姓名不被强制 first/last，称谓与性别不由姓名推断；
  • 复数和消息模板使用版本化 Locale 资源并覆盖边界值；
  • CLDR/格式库、业务地区规则与缓存键版本化。

方言、混语与文化

  • 评测集包含授权的方言、Romanization、混语和非标准输入；
  • 标准语没有命名为 normal 并把其他表达贬为噪声；
  • code-switch 同时验证片段与任务，不只输出一个主语言标签；
  • 关键约束位于非主语言片段时仍被保留；
  • 文化适配以具体场景为单位，不把群体模板施加给个体；
  • 不确定偏好时允许中性表达、选项或询问；
  • 翻译后的安全、伤害与不必要拒答由目标语言重新标注；
  • 反事实测试保持任务事实可比，不把合法地区差异当偏差；
  • 复核意见存在合理分歧时允许 contested。

自动化与人工

  • Schema、结构值、工具与后置条件优先使用确定性 Oracle；
  • 自动错误码稳定，命中被记录为观测而非根因；
  • 语义 Judge 按目标语言与错误类型用人工锚点校准；
  • 高风险样本不由同一生成器自证；
  • 母语复核按双语等价、单语自然度、Locale、文化和业务拆责；
  • 复核员资格包含语言、Locale 经验与领域训练边界；
  • 高风险采用独立双标、理由、仲裁和异议保留；
  • 人工队列容量、P95 等待和超时回退进入发布门禁；
  • pending、contested 和 passed 不会在报表中混合。

指标与决策

  • 每个比例保存分子、分母、权重、切片和数据版本；
  • 原生轨、翻译轨、宏平均、微平均和最差切片分别报告；
  • 关键否定、权限、币种和副作用设不可补偿门禁；
  • BLEU、chrF、COMET 等自动指标未被称为生产任务证明；
  • 供应商 benchmark 未被泛化为本产品质量；
  • 群体差异明确标为观测，因果解释需要额外实验；
  • 告警未被直接写成根因；
  • Evidence Coverage 要求样本、执行、Oracle 和决定齐全；
  • 发布决定按 Locale、任务、风险和副作用切片；
  • 例外有责任人、范围、期限、监控和回滚条件。

故障、灰度与回滚

  • 否定丢失、币种错误、日期歧义、地址丢字段已注入；
  • NFC 等价、NFKC 碰撞、双向文本与 Token 截断已注入；
  • 方言、混语、pivot 和目标语言索引缺失已注入；
  • Judge 不可用、母语队列积压和报表分母错误已注入；
  • 组合故障能让端到端门禁真实失败；
  • 低风险影子与灰度有独立的 Locale 停止指标；
  • 写操作回退不会产生未审计副作用；
  • 修复使用新 run 追加证据，不覆盖旧失败；
  • 回滚同时处理模型、Prompt、格式资源、缓存和工具适配器。

二十二、常见误区

22.1 “翻译成目标语言就有了目标语言测试集”

翻译轨只能提供受控平行任务。真实表达、当地任务、方言、混语和文化情境需要原生轨。

22.2 “NFC/NFKC 后一样，所以原文等价”

NFC 是规范等价派生，NFKC 还会应用兼容映射。两者都不是任意业务语义证明；NFKC 尤其可能消掉区别。永远保留原文并按字段定义用途。

22.3 “Locale 已经包含语言和地区，存一个字段就够”

Locale 标签适合资源选择，业务 Region、用户偏好、输入语言和 Script 有不同来源与权限，必须分开。

22.4 “母语者看起来没问题，就能上线”

单人非盲复核无法覆盖领域、Locale、文化伤害、业务动作和群体内多样性。高风险需要拆责、双标、仲裁和后置条件。

22.5 “文化适配就是按国家改语气”

这是文化本质化的快捷方式。文化语境应绑定具体场景和来源，允许用户覆盖、未知与分歧。

22.6 “自动指标与人工分数都高，工具就正确”

文本层质量不证明结构币种、工具权限或外部状态。业务动作必须独立验收。

22.7 “差异说明模型歧视某语言”

差异值得调查，但翻译来源、任务难度、检索覆盖、Token、网络和人工流程都可能贡献。相关性不能直接替代因果。

22.8 “公开 benchmark 最好的模型对所有市场最好”

benchmark 只支持其数据、任务和实验条件内的比较。生产需要自己的任务、分布、工具、安全与文化证据。

22.9 “低流量语言样本少，可以合并到 Other”

这样最容易让关键退化从平均值消失。可以使用分层统计和不确定性，但必须保留风险切片与缺失证据状态。

22.10 “人工队列是无限 Fallback”

人工有语言覆盖、容量和时限。超载策略必须预先定义为限流、只读、延迟处理或停止，不能把 pending 当成功。

二十三、总结

多语言 AI 质量不是给同一个 Prompt 换几十种语言后求平均。它是一个跨数据、字符串、模型、国际化、业务工具与人类判断的系统工程。

一套可信方法需要守住以下边界：

  1. Language、Script、Locale、Region 和 Culture 分开建模，任何一项都不能替另一项推断用户；
  2. 原生任务轨回答生产表达，平行翻译轨回答跨语言可比性，翻译族按血缘隔离；
  3. 翻译明确改变任务，必须定义硬不变事实、语义功能、Locale 可变项和不可译/多解项；
  4. 用户原文、NFC 比较键、NFKC 与 case folding 搜索/安全候选分别保存；兼容归一化可能丢失区别，不能无条件覆盖原文；
  5. 字节、code point、字素簇和模型 Token 分开计量，Tokenizer 与截断证据版本化；
  6. 日期、时间、金额、币种、单位、地址和姓名的结构值与显示值分离，CLDR 资源与业务规则各守边界；
  7. 方言、Romanization 和 code-switch 是真实输入，不是等待清洗掉的噪声；
  8. 文化测试从具体场景与伤害开始，允许未知、异议和用户覆盖，避免文化本质化；
  9. 自动规则守确定事实，语义模型发现候选，母语人工处理语用与伤害，业务系统验证副作用；
  10. 指标说明分母、切片与用途，benchmark、告警和相关差异都不冒充生产质量、根因或因果；
  11. 故障注入覆盖翻译、Unicode、Token、Locale、检索、人工和工具，并验证门禁与回退真实生效；
  12. 发布按 Locale、任务、风险和副作用决定，历史失败追加修复证据而不被抹掉。
