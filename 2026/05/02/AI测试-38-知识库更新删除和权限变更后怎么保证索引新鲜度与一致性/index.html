AI测试-38-知识库更新删除和权限变更后怎么保证索引新鲜度与一致性

发表于 2026-05-02 分类于 AI测试 本文字数： 19k 阅读时长 ≈ 1:08

知识库系统最危险的状态，通常不是“完全不可用”，而是看起来正常、检索也有结果，但结果来自已经修改、已经删除或当前用户已经无权访问的旧投影。

一次源文档更新，可能依次经过业务数据库、对象存储、CDC、消息队列、解析器、分片器、Embedding 服务、向量索引、关键词索引、重排缓存和答案缓存。任何一段都可能延迟、重试、乱序或只完成一半。源系统里的“保存成功”与查询端的“新内容已经可见”不是同一个时刻。

删除与权限撤销更加严格。更新延迟几分钟可能让用户看到旧制度；删除延迟可能违反数据保留承诺；ACL 撤销延迟则可能把仍然存在的内容暴露给已经失去权限的主体。三者不能共用一个模糊的“同步成功率”。

本文讨论的是知识进入索引以及从索引退出的控制面，不重复 AI测试-18 已经展开的 Recall、忠实度、引用正确性和通用 RAG 评测。这里也不把以下信号当成业务正确性保证：

  • CDC 连接器处于运行状态；
  • 消息已经被消费或提交 offset；
  • 向量数据库返回 HTTP 200；
  • 文档 Schema 校验通过；
  • 向量相似度很高；
  • 模型声称自己“有信心”；
  • 查询协议成功返回结果。

这些信号各自只能证明局部步骤。本文要建立的是另一组可验证结论：

  1. 一个源版本是否已经传播到所有应该存在的投影；
  2. 一个删除或撤权版本是否已经让所有不应再见的副本不可见；
  3. 乱序、重复和部分失败后，系统是否一定收敛到源真值；
  4. Embedding 版本迁移期间，新旧索引是否保持可解释、可回滚；
  5. 当在线链路悄悄漏事件时，对账能否发现并修复；
  6. 用户写入后要求立即读取时，系统究竟承诺到哪个边界。

文中所有示例指标和事故数字均为构造数据，只用于演示口径和排查方法。厂商行为按资料截止日 2026-07-26 对应文档描述，不能外推到其他产品、部署模式或未来版本。

一、工程定义：索引不是第二份真值，而是可丢弃、可重建的投影

1. 源系统真值是什么

“源系统”不是固定等于某个数据库。它是对某项业务事实拥有最终裁决权的系统。例如：

  • 文档正文由内容管理系统裁决；
  • 文档是否删除由内容生命周期服务裁决；
  • 用户、组、租户和资源之间的授权关系由权限服务裁决；
  • 合规冻结与强制下架由治理系统裁决；
  • 当前有效版本由带事务语义的版本记录裁决。

一个知识对象可能有多个权威来源，但每个字段必须有唯一责任边界。若正文说文档存在、权限服务说资源已经冻结，查询层不能自行“折中”。冻结属于安全否决条件，应优先阻断读取。

向量索引、倒排索引、缓存和生成答案都是派生状态。派生状态允许暂时落后，也允许删除后重建；它不能反向覆盖源真值。把索引当主库，会立即产生三个无法回答的问题：

  • 索引中的内容来自哪个源版本；
  • 索引缺少记录表示“尚未同步”还是“已经删除”；
  • 两个索引内容冲突时由谁裁决。

因此第一条架构不变量是：

对每个可检索单元，都能追溯到源实体、源纪元、单调版本、转换版本和投影时间；源系统能够独立枚举当前应存在的集合。

W3C PROV-O 把实体、活动、代理以及 wasDerivedFrom 等关系定义为来源描述词汇。工程上不必照搬 RDF，但应保留同等信息：哪个源实体经过哪一次解析、切分和嵌入活动生成了哪个索引记录，活动由哪个代码与配置版本执行。

2. “一致性”至少有六个维度

知识索引的一致性不能压成一个布尔字段。

维度 要回答的问题 典型错误
内容一致性 查询到的正文是否来自当前有效源版本 标题是 v18，正文仍是 v17
集合一致性 应存在的分片是否完整，不应存在的分片是否消失 更新后旧分片残留，形成冲突证据
权限一致性 当前主体是否只看到此刻有权读取的资源 组成员被移除后旧缓存仍命中
模型一致性 同一索引代的向量是否由声明的 Embedding 版本生成 新旧维度或归一化规则混写
缓存一致性 缓存键和失效范围是否覆盖内容、ACL、索引代 向量已删，答案缓存仍返回原文
证据一致性 账本、水位、索引实际内容和源清单能否互相印证 账本标记成功，索引副作用实际失败

这六个维度里，内容更新通常追求低延迟最终一致；删除和 ACL 撤销通常需要更短、更明确的暴露上限。若风险无法接受异步窗口，应在查询入口增加权威权限守卫或同步拒绝列表，而不是假装异步索引具备强一致。

3. “新鲜”必须绑定对象、起点和终点

一句“索引五分钟内更新”缺少三个定义：

  • 哪类变更：正文更新、删除、ACL 授权还是 ACL 撤销；
  • 从何时开始：用户点击保存、源事务提交、Outbox 可见还是 CDC 读到；
  • 到何时结束：索引写请求返回、refresh 后可搜索、权限过滤生效，还是缓存也已失效。

本文采用以下主要终点：

“索引 API 接收了写请求”只是一项中间事件。以 Elasticsearch 为例，官方近实时搜索文档明确区分写入与 refresh；refresh 会让上次 refresh 以来的操作可供搜索，并可以等待刷新间隔、使用 refresh 选项或调用 Refresh API。这个事实只适用于对应 Elasticsearch 行为，不代表所有搜索产品都采用相同机制。

4. 边界：本文保证什么，不保证什么

本文关注投影正确性与可见性：事件不丢、版本不倒退、删除不复活、撤权优先、迁移可回滚、差异可修复。

它不自动保证：

  • 分片语义合理；
  • Embedding 能召回业务相关证据；
  • 重排器顺序正确；
  • 生成答案忠于证据；
  • 源文档本身事实正确；
  • 权限策略定义符合组织制度。

即使投影与源 100% 一致，源数据也可能错误。即使 Recall@10 很高，旧权限缓存仍可能泄露内容。层间责任必须分开，故障证据才能指向实际修复点。

二、先写一致性合同，再选 CDC、队列和向量库

一个可测试的知识索引合同至少包含以下字段。

合同项 示例 设计目的
真值所有者 content-service、authz-service 冲突时知道向谁对账
实体键 (tenant_id, document_id) 隔离租户并维持实体顺序
源纪元 content-db-prod-03 灾备恢复或导入后避免版本号碰撞
单调版本 document_version=58 不用到达时间判断新旧
操作 UPSERT/DELETE/ACL_REVOKE/ACL_GRANT 不把空内容误当删除
事件 ID 全局唯一 UUID 支持重复检测与审计
提交时间 数据库提交对应时间 计算端到端新鲜度
安全级别 normal/security_critical 撤权与删除独立调度
目标投影 lexical-v3/vector-e5-v2/cache 明确传播扇出
完成条件 可搜索 + 旧片消失 + 缓存失效 防止过早确认
SLO 更新 p99、撤权 p99 与最大值 把风险变成可告警目标
修复责任 自动重放、人工审批、源修复 避免发现差异后无人处理

合同还要写出三个“不承诺”。

第一，不承诺跨所有实体的全局顺序。大多数系统只需要同一实体或同一聚合内有序。强求全局顺序会降低吞吐，却不一定改善正确性。

第二，不承诺消息只投递一次。网络超时、消费者崩溃和 offset 提交失败都会制造重复。系统应接受至少一次投递，并让相同事件重复执行后结果不变。

第三，不承诺所有读都自动 read-your-writes。写入端和检索端之间有异步链路，必须通过写入回执、最低版本、有限等待或源回退显式实现这一会话保证。

三、完整架构：普通更新最终收敛，删除和撤权先阻断再清理

图中的主路径可以拆成九个责任单元。

1. 源写入服务

源写入服务在一个事务里完成：

  1. 校验调用者是否有权修改；
  2. 更新业务实体并递增实体版本；
  3. 写入不可变 Outbox 事件；
  4. 返回包含 source_epoch 与 entity_version 的写入回执。

如果业务表提交而事件没有可靠产生，后续只能依赖周期扫描“猜”出变化。Outbox 的价值正是让业务变更和待发布事实共享事务边界。Debezium 3.6 Outbox Event Router 文档说明 Outbox 模式用于避免服务内部状态与消费事件之间的不一致；其默认表结构包含唯一事件 ID、聚合类型、聚合 ID、类型与载荷。

2. CDC 捕获器

CDC 捕获事务日志或 Outbox 表变化，形成可重放事件流。Debezium 3.6 文档描述其连接器捕获数据库表的行级变化并形成变更事件流。这里应谨慎理解“顺序”：

  • 数据库日志提供源侧顺序信息；
  • 进入消息系统后，顺序通常受 topic 分区、路由键和并行消费者影响；
  • Outbox 文档指出 aggregateid 作为消息键对于维持 Kafka 分区内正确顺序很重要；
  • 这不等于跨分区全局有序，也不等于下游副作用按顺序完成。

因此事件信封必须携带源版本，消费者也必须自行拒绝倒退。

3. 事件总线与优先级调度

正文更新可以进入普通队列。删除、ACL 撤销、租户冻结和法律下架进入安全关键队列，拥有：

  • 独立吞吐预留；
  • 更短的排队年龄告警；
  • 不被大规模回填挤占的消费者；
  • 更严格的死信升级；
  • 端到端最大暴露时间，而不只看分位数。

“同一个 topic 设置高优先级字段”往往不够，因为消费者积压时仍然按旧消息顺序读取。安全通道需要资源隔离，或者由查询守卫同步消费一份紧急拒绝状态。

4. 解析与分片

解析器把源对象转换成规范文档，分片器生成稳定 chunk_id。稳定不意味着永远不变，而是由显式规则生成，例如：

若更新采用“只覆盖新分片”而不清除旧分片，分片数量减少时会留下幽灵片段。可靠做法有两种：

  • 先生成该实体某版本的完整清单，原子切换可见版本；
  • 在同一投影操作中 upsert 新清单并删除不再属于目标清单的旧 ID。

二者都需要实体级版本与清单，不能只依赖向量相似度找旧片删除。

5. Embedding 与投影器

Embedding 服务只负责把指定文本按指定模型与预处理规则变成向量。投影器负责更高层的不变量：

  • 检查目标索引允许的维度与模型版本；
  • 比较实体当前账本版本；
  • 生成所有目标索引代的副作用；
  • 写墓碑、清理旧分片、失效缓存；
  • 保存结果哈希、重试次数和完成时间；
  • 暴露失败阶段供修复器重放。

Embedding 请求成功不代表索引完成；向量维度正确也不代表向量来自声明的模型。投影记录需要保存 embedding_model_id、preprocessor_hash 与输入内容哈希。

6. 双检索索引

生产常同时使用倒排索引和向量索引。两者必须共享源身份、版本、ACL 摘要与墓碑语义。否则关键词结果已撤权、向量结果仍可见，混合召回器依然会把禁止内容送进上下文。

Embedding 迁移时还会同时存在旧向量索引和新向量索引。读别名不能在“新索引记录数差不多”时直接切换，后文会定义完整门禁。

7. 缓存层

至少区分：

  • 文档解析缓存；
  • Embedding 缓存；
  • 检索候选缓存；
  • 重排缓存；
  • 最终答案缓存；
  • ACL 判定缓存。

每类缓存依赖的版本不同。正文更新未必需要清除共享 Embedding 缓存中的其他文本；ACL 撤销却必须清除可能包含原文的检索和答案结果，并使授权缓存失效。

8. 查询守卫

查询守卫在索引返回候选后，再依据当前主体、租户、资源版本和风险策略做确定性检查。对于高敏感知识，它应读取权威权限快照或短时拒绝集合，做到撤权先阻断。

守卫不是修复脏索引的借口。索引仍要最终清理，否则会持续增加暴露面、统计噪声和旁路风险。它的作用是在异步清理窗口内缩短可见性风险。

五、CDC 与 Outbox：解决“事实如何可靠出现”，不替下游完成一致性

1. 为什么业务写入后直接发消息容易裂开

最直观的实现是：

如果数据库提交后进程崩溃，消息没有发出，源和索引永久分叉。如果先发消息再提交数据库，消费者可能投影一个最后回滚的版本。把数据库事务与外部消息发送做成“看起来同时”也不等于原子，除非引入经过证明的跨系统事务协议及其恢复机制。

Outbox 把待发布事件先写入与业务表相同的本地事务。CDC 再读取已提交的 Outbox 行。这样能够保证“源变更提交则事件事实存在”，但仍有以下工程工作：

  • CDC 可能重发；
  • 事件总线可能重复投递；
  • 同一实体的事件可能被错误路由到不同分区；
  • 消费者可能在任意副作用边界崩溃；
  • Outbox 清理可能早于审计和重放需要；
  • 快照与增量切换可能产生边界错误；
  • Schema 变化可能让消费者无法解释旧事件。

因此 Outbox 解决双写裂缝，不提供端到端 exactly-once。下游仍要以版本化幂等和对账完成闭环。

2. Outbox 表只追加，不原地改事件

Debezium 3.6 Outbox Event Router 的文档把 Outbox 表视为队列，期望变化为 INSERT，并说明事件唯一 ID 可用于移除重复消息。工程上也应把已经提交的事件当不可变事实：

  • 载荷错误时发布更高实体版本的纠正事件；
  • 不修改旧事件让审计历史悄悄变化；
  • 清理前先确认 CDC、归档和重放窗口都已越过；
  • Schema 演进使用显式 schema_version，消费者支持兼容窗口。

事件 ID 不应由当前时间和实体 ID 简单拼接。重试创建同一业务事件时，要明确是复用原事件 ID，还是创建一个指向原事件的修复事件。两种方式均可，但语义必须稳定。

3. 快照与增量的交界要专项测试

新建连接器或全量重建通常先扫描快照，再切换到日志增量。危险边界包括：

  • 快照读取 v20，增量从 v22 开始，v21 丢失；
  • 快照中的旧 v20 在增量 v21 后才写入索引，造成倒退；
  • 删除对象不在当前快照里，又没有保留历史墓碑，目标索引残片无法清除；
  • 快照按表读取正文和 ACL，两个表不在同一一致性视图，拼成从未真实存在过的组合。

测试不能只比较最终记录数。至少要在快照进行中并发注入更新、删除、撤权、租户迁移和 Schema 变化，再验证每个实体最终版本、集合清单、ACL 摘要及墓碑都与源一致。

七、删除和 ACL 撤销：安全性优先于普通内容新鲜度

1. 删除是业务事件，不是索引维护命令

删除事件至少表达：

  • 谁或哪个策略触发；
  • 源实体最终版本；
  • 删除范围是整个文档、某附件、某租户还是某索引代；
  • 是否允许恢复；
  • 墓碑保留多久；
  • 哪些派生副本必须清理；
  • 完成时限和审计责任。

不要只向向量库发送 delete(filter=document_id) 然后立即把业务状态标为完成。以 Pinecone 当前删除文档为例，它支持按 ID、元数据、命名空间等方式删除，同时明确说明其数据面最终一致，新增或变更记录到查询可见可能有短暂延迟。这个产品事实意味着调用成功与查询不可见之间需要可见性探针；其他产品必须查各自文档和实际测试，不能套用相同延迟假设。

2. 先阻断再物理清理

高敏感删除的推荐顺序是：

  1. 源事务提交删除版本；
  2. 安全通道把 (tenant, entity, deleted_version) 写入查询拒绝集合；
  3. 查询守卫立即拒绝该实体；
  4. 删除所有在役倒排、向量、对象缓存和答案缓存副本；
  5. 对生产查询路径做负向探针；
  6. 写完成证据并保留墓碑；
  7. 在保留期后按政策物理清理审计材料。

拒绝集合应有版本，且失效条件不能只靠固定 TTL。若清理持续失败，TTL 到期会重新暴露。应由“所有目标已验证清理完成”驱动退出，固定 TTL 只能作为刷新机制。

3. ACL 撤销与 ACL 授权不是对称风险

授权延迟会让合法用户暂时看不到内容，主要影响可用性。撤销延迟会让不再授权的用户继续看到内容，影响保密性。二者可采用不同服务目标：

4. 权限快照与主体变化

文档 ACL 可能只保存组 finance-readers，用户是否属于该组由身份系统决定。仅在索引时展开用户列表会产生巨大扇出：一个用户离组，需要更新成千上万文档。

常见方案有三类：

方案 优点 风险与适用边界
索引主体 ID 查询快；易过滤 成员变化扇出大，撤权传播难
索引组/角色，查询时展开主体 文档变更少 身份缓存必须新鲜，查询复杂
候选后权威逐项鉴权 最接近当前真值 延迟和权限服务容量压力大

高风险系统常组合使用：索引元数据做粗过滤，查询守卫做最终鉴权，紧急撤权用拒绝集合。无论采用哪种方式，都要保存本次查询使用的 principal_snapshot_version 和 policy_version，否则事故后无法证明当时为什么放行。

5. 删除所有衍生物，而不只删向量

一份知识可能存在于：

  • 原始对象存储；
  • 解析后的纯文本；
  • OCR 中间文件；
  • 分片清单；
  • Embedding 缓存；
  • 向量索引；
  • 倒排索引；
  • rerank 特征缓存；
  • 检索缓存；
  • 最终答案缓存；
  • 离线评测快照；
  • 调试 trace 和人工标注队列。

删除合同要按用途和保留政策逐项定义。不是所有审计证据都应立即消失，也不是所有调试副本都可以无限保留。工程实现应使用数据资产清单与派生关系，而不是事故发生后靠搜索文件名发现副本。

6. 负向验证比“删除成功”更接近用户风险

删除完成探针应模拟真实查询路径：

  • 用原文精确词检索；
  • 用语义改写检索；
  • 用文档 ID 或标题检索；
  • 以撤权主体、同组主体、管理员和匿名主体分别查询；
  • 经过生产别名、混合召回、缓存和答案层；
  • 检查结果、上下文、引用和缓存头中均无目标实体。

探针通过仍不是数学证明，因为查询样本有限。它与目标索引枚举、版本账本和源对账结合，才构成合理证据。

八、Embedding 版本迁移：双索引比原地混写更容易验证和回滚

1. 为什么不能在同一向量空间里悄悄替换模型

Embedding 模型变化可能改变：

  • 向量维度；
  • 归一化方式；
  • 分词与截断；
  • 输入前缀；
  • 距离度量适配；
  • 语言和领域分布；
  • 文档与查询编码约定。

即使维度相同，新旧向量也不一定处于可比较空间。把两代向量混写到一个索引，再依靠 embedding_version 过滤，会增加遗漏过滤和错误查询编码的风险。更可控的方式是建立新索引代。

2. 双索引迁移的七个阶段

关键是 G2 与 G3 的交界。回填必须记录源快照位置；实时流从该位置之后追赶。若回填 v100 晚于实时 v101 到达 B，版本条件写要拒绝 v100 覆盖 v101。

3. 迁移验收不只比较记录数

应至少比较：

  • 源有效实体数与 B 的实体数；
  • 每实体目标分片清单与 B 的实际分片清单；
  • entity_version、acl_version、内容哈希；
  • 删除墓碑在 A、B 的执行状态；
  • 不同租户、语言、文档类型和长度的覆盖；
  • B 的索引新鲜度和失败率；
  • 查询编码器是否与 B 的文档编码器匹配；
  • 在固定评测集上的检索质量、延迟和成本；
  • 安全过滤与查询守卫是否使用同一权限版本。

记录数相等可能同时少了实体 X、多了实体 Y。平均 Recall 提升也可能掩盖某个语言切片或受限租户的严重退化。迁移门禁必须包含集合差异和风险切片。

4. 双写失败的语义

实时事件写 A 成功、写 B 失败时，不应让消息静默成功。可选策略：

  • A 是当前主读：允许用户路径继续，但事件进入 B 的修复队列，B 水位停滞；
  • B 已进入灰度：受影响实体暂时只路由 A，或停止扩大灰度；
  • B 已成为主读：按发布策略回退 A，前提是 A 仍持续双写且新鲜。

每个目标索引代要有独立状态，不能用一个 processed=true 表示全部成功。

5. 回滚窗口不是“旧索引还在”这么简单

旧索引要能回滚，必须继续接收切换后的增量，或者有足够快的追赶方案。停止写 A 后保留七天，只保留了一个越来越陈旧的快照，不是可用回滚目标。

回滚演练要验证：

  • 读别名在受控时间内切回；
  • A 已追平切换后的源水位；
  • 切回不会重新暴露 B 期间发生的删除和撤权；
  • 查询编码器同步切回 A 对应版本；
  • 缓存键包含索引代，不会把 B 的结果带到 A；
  • 回滚原因和影响租户可审计。

九、缓存失效：版本化键、依赖清单与主动撤销共同工作

1. 只设置短 TTL 为什么不够

TTL 可以限制普通陈旧时间，但不能精确满足删除和撤权时限：

  • 已经生成的长 TTL 答案可能包含原文；
  • 多层缓存 TTL 相加，实际窗口大于单层配置；
  • 热 key 在滑动过期策略下可能一直续命；
  • 节点时钟和后台淘汰并非精确计时器；
  • 缓存旁路或本地进程缓存可能不受集中失效控制。

因此普通更新可依靠版本化键自然淘汰，安全关键变更还需主动失效。

  • 幂等失效；
  • 重试与死信；
  • 按实体或权限版本拒绝旧失效覆盖新状态；
  • 失效完成时间指标；
  • 周期性扫描异常长寿命条目；
  • 查询守卫对撤权实体的最终兜底。

十一、状态机：把每种事件映射为可验证转换

1. ACTIVE

ACTIVE vN 表示目标清单完整、内容与 ACL 摘要匹配、该版本已经通过生产可见性条件。它不是“至少写入一个 chunk”。

2. MIGRATING

MIGRATING vN 表示同一源版本正在两个索引代中建立投影。状态必须分别记录 A 与 B 的完成情况。只有 B 覆盖、权限、墓碑和质量门禁通过，读别名才可灰度切换。

3. REVOKED

REVOKED vR 表示特定主体或范围已被拒绝。索引物理记录可能短暂存在，但查询守卫必须已经生效。授权恢复需要更高权限版本和明确 ACL_GRANT，不能因低版本重放自动恢复。

4. TOMBSTONED

TOMBSTONED vD 表示实体在该源纪元的删除版本已经生效。低于或等于 vD 的 UPSERT 不得恢复；合法恢复必须由源系统产生高于 vD 的版本，并符合业务恢复政策。

5. RETRY / REPAIR

外部副作用部分完成或对账发现差异时进入可重试状态。修复不是绕过版本检查的管理员覆盖，而是重新读取源目标版本、重新生成完整清单、幂等写入，再做复验。

十四、自动化测试与失败注入设计

1. 契约测试

事件生产者与消费者共同维护版本化 Schema，并测试：

  • 必填身份、版本、操作和提交时间不可缺失；
  • 未知操作进入隔离，不默认为 UPSERT；
  • 相同实体版本出现不同内容哈希时硬失败；
  • 旧 Schema 在兼容窗口内仍能解码；
  • 新字段默认值不会放宽权限；
  • 载荷引用必须包含不可变版本或内容哈希；
  • 租户 ID 不能由下游从可变路径猜测。

Schema 通过只能说明事件形状合法。它不能说明源版本真实、ACL 符合政策或正文业务正确。

2. 顺序与重复测试

为每类操作生成所有关键排列：

测试中不仅断言最终版本，还在每一步查询，确保没有短暂倒退或越权窗口超过合同。

3. 崩溃点注入

至少在以下边界主动终止进程：

  • 读取消息后、任何副作用前；
  • Embedding 生成后、索引写前；
  • 第一个索引代成功后、第二个索引代前；
  • upsert 新片后、删除旧片前；
  • 向量索引成功后、倒排索引前；
  • 索引完成后、缓存失效前；
  • 缓存失效后、账本提交前；
  • 账本提交后、offset 提交前。

每个点恢复后重放同一事件，验证：

  • 版本不倒退；
  • 不产生重复可见分片；
  • 删除与撤权不会因重试暂时恢复；
  • 账本最终与所有目标副作用一致；
  • 重试次数和失败阶段被记录。

4. 依赖故障注入

模拟：

  • Embedding 超时、限流和返回错误维度；
  • 向量索引写成功但客户端超时；
  • 倒排索引 refresh 延迟；
  • 缓存节点部分不可达；
  • 权限服务超时与返回旧快照；
  • 消息分区暂停、重分配和重复投递；
  • 对象存储读到不存在或哈希不符的版本；
  • 双索引中只有一代写入失败；
  • 对账扫描被限流或中途中断。

权限服务不可用时的策略必须预先决定。高敏感路径通常失败关闭；低风险公开知识可以使用带明确版本和短期限的缓存。不能在异常分支里临时“为了可用性”跳过鉴权。

5. 性能与积压测试

大批量回填容易挤压实时撤权。压测应同时放入：

  • 稳态更新流；
  • 突发大文档；
  • 全量迁移回填；
  • 删除风暴；
  • ACL 大组成员变更；
  • 消费者扩缩容和分区重平衡。

验收目标不是总吞吐最高，而是普通更新新鲜度、撤权最大暴露、队列隔离和恢复时间都在预算内。测试要观察最老事件年龄，不能只看每秒消费数。

6. 查询旁路测试

列出所有真实读入口：Web 搜索、聊天、内部 API、批量导出、管理后台预览、调试工具、离线评测和缓存直读。对同一撤权实体逐一验证。主入口有守卫而导出 API 直接查索引，是常见的安全缺口。

十五、对账与修复：事件链路之外的第二条正确性防线

1. 为什么成功消费仍需对账

事件链路可能发生不可见错误：

  • 生产者漏写 Outbox；
  • CDC 配置排除了某张表；
  • 消费者代码错误地确认消息；
  • 索引服务返回成功但写入错误租户；
  • 人工脚本直接修改索引；
  • 恢复备份带回旧记录；
  • 账本和副作用在崩溃窗口分叉。

对账从源真值重新推导“应该是什么”，不相信此前每个绿色状态。

2. 三层对账

第一层是清单对账：比较每租户的有效实体集合、墓碑集合和分片数量摘要，快速发现大面积缺失或多余。

第二层是实体对账：比较源版本、内容哈希、ACL 哈希、目标分片清单、Embedding 版本和索引代。

第三层是生产可见性对账：通过生产等价查询验证目标版本可搜索、删除不可见、撤权主体被拒绝。

三层频率可以不同。清单每小时，实体采用持续哈希分桶，生产探针重点覆盖安全事件和近期变更。高风险租户可以提高频率。

3. 哈希分桶减少全量扫描成本

把实体按稳定键分桶：

源和索引分别计算每桶的实体数、版本摘要和内容摘要。摘要不同再下钻实体。分桶数、哈希算法和规范化规则必须版本化，否则两边摘要不可比较。

摘要相同只能在所用哈希和清单模型下提供高概率一致证据。删除与 ACL 高风险对象仍应进行直接核验。

4. 差异分类决定修复动作

差异 可能根因 修复动作
源有、索引无 漏事件、永久失败、错误过滤 按源当前版本重建
源无、索引有 删除漏传播、恢复残留 写/恢复墓碑并删除所有代
索引版本落后 积压、乱序错误、修复失败 重放当前源快照
索引版本超前 源恢复、写错环境、纪元错误 隔离并人工裁决，不能盲目覆盖

“索引超前”尤其不能自动按源覆盖。它可能表示源从旧备份恢复，也可能是生产索引被测试环境写入。先冻结相关实体、核对源纪元和审计，再决定方向。

5. 修复任务也要有版本保护

对账在 10:00 发现 v30 缺失，10:01 创建修复任务；源在 10:02 更新到 v31；修复任务 10:03 执行。如果它携带旧快照并无条件覆盖，会把索引降回 v30。

修复任务应在执行时重新确认目标源版本，或者由条件写要求 repair.version >= current.version。修复完成后再次对账，不能仅以任务执行成功关闭差异。

6. 修复风暴控制

当解析器 bug 导致百万实体不一致时，立即全速重建可能压垮源、Embedding 和在线索引。修复器需要：

  • 按安全风险、租户等级和差异年龄排序；
  • 为在线流预留容量；
  • 限制每租户并发；
  • 支持暂停、续跑和幂等重放；
  • 对同一根因聚合告警；
  • 在修复前验证新转换版本；
  • 记录预计完成时间与未修复暴露面。

十六、完整失败案例：撤权事件被回填流压住，旧答案缓存继续泄露

下面是一组构造事故，用于展示如何从证据定位，而不是描述某个真实厂商事故。

1. 系统背景

某企业知识助手正在把 vector-A/embed-v1 迁移到 vector-B/embed-v2。生产读取仍以 A 为主，10% 租户灰度 B。实时正文更新采用同一个普通 topic 双写 A/B；ACL 变化也进入该 topic。查询先查 15 分钟 TTL 的候选缓存，再根据候选元数据做权限过滤。团队以为索引里的 allowed_groups 足够，没有独立权威守卫。

目标合同是：

  • 正文更新 p99 在 120 秒内可搜索；
  • ACL 撤销 p99 在 5 秒内生效，任何单次不得超过 30 秒；
  • 所有缓存条目按租户、主体组摘要和索引代隔离；
  • A、B 在迁移期间都必须接收删除和撤权。

3. 为什么第一轮监控没有报警

当时看板显示：

  • Debezium 连接器 RUNNING；
  • 消息生产成功率 100%；
  • 消费者无进程崩溃；
  • 向量写 API 2xx 比率 99.99%；
  • 全站搜索可用率 99.98%；
  • RAG 答案“有引用率”正常；
  • A 与 B 的记录总数差异小于 0.1%。

这些都不是撤权正确性指标。系统没有测：

  • 安全关键事件最老排队年龄；
  • 源 ACL 提交到被撤主体首次拒绝的暴露时间；
  • 每个目标索引代的独立完成状态；
  • 缓存条目使用的主体快照版本；
  • B 中 ACL 哈希与源的差异；
  • 真实读路径的负向权限探针。

HTTP 200 只说明请求完成。Schema 合法只说明字段可解析。向量相似度高只说明旧内容与问题相近。三者反而可能让越权答案更稳定地返回。

系统性原因还有四个：

  • 团队把索引元数据过滤当作最终授权，而没有定义撤权窗口；
  • 上线门禁只看平均新鲜度与索引记录数；
  • 故障测试覆盖更新重试，没有覆盖回填压力下的撤权；
  • 对账每小时运行，且先比数量，ACL 哈希只在下钻时检查。

6. 临时止血

事故处理中按以下顺序操作：

  1. 暂停 B 灰度扩张和低优先级回填；
  2. 将受影响主体与实体写入集中拒绝集合；
  3. 清除包含目标实体的候选与答案缓存；
  4. 直接从源生成 ACL v12 修复任务，分别投影 A/B；
  5. 对该主体通过所有读入口做负向验证；
  6. 扩大同时间窗撤权事件审计，确认影响范围；
  7. 保留源、消息、账本、索引和查询 trace 证据。

没有直接删除整个索引或清空共享缓存集群，因为那会扩大可用性影响并破坏证据。止血动作仍遵守最小范围和可审计原则。

7. 永久修复

  • 把 ACL_REVOKE/DELETE/tenant_freeze 路由到独立安全 topic 和预留消费者；
  • 查询入口订阅安全事件，先更新拒绝集合，再异步清理索引；
  • 缓存键加入 principal_scope_hash 与 policy_version，条目保存引用实体反向依赖；
  • 账本改为每个索引代、倒排索引和缓存分别记录状态；
  • 只有所有必需目标达到可见性条件，事件才标记完整完成；
  • 安全 SLI 采集源提交、守卫拒绝、索引不可见和缓存失效四个时间点；
  • 对账直接比较 ACL 哈希，并提高近期安全事件的核验频率；
  • 在全量回填压力下持续注入撤权，验证最大暴露时间；
  • 枚举并测试批量导出、调试搜索和离线工具等旁路。

8. 关闭事故需要什么证据

不能因为当前 Alice 搜不到就关闭。至少需要：

  • 受影响时间窗全部撤权事件清单；
  • 每个事件的源版本、分区 offset、各目标完成时间；
  • A/B 与缓存的当前 ACL 或不可见证明；
  • 所有读入口的负向探针结果；
  • 同根因历史残留扫描；
  • 修复后在峰值与回填压力下的故障测试；
  • 新 SLI 和告警已实际触发演练；
  • 回滚和拒绝集合退出条件经过复核。

十七、值班排查手册：从用户证据反向走到源真值

1. 先冻结问题描述

记录：

  • 租户、主体、查询和实体 ID；
  • 用户看到的具体内容与时间；
  • 请求 trace ID、区域、读入口和索引代；
  • 期望源版本、删除版本或 ACL 版本；
  • 是否属于仍在暴露的安全事件。

若是潜在越权，先阻断读取再深挖，不等待根因完整确定。

2. 检查源状态

确认当前正文、生命周期、ACL、源纪元和实体版本。找出对应事务与 Outbox 行。若源本身错误，投影链路再一致也应由源所有者纠正。

3. 检查事件存在与路由

按事件 ID、实体键和事务位置查 CDC。确认 topic、分区、offset、Schema 版本和优先级。没有事件时调查事务边界与 CDC 配置；有事件时继续看水位。

4. 检查积压和缺口

同时看最大已见、连续完成、最老待处理和安全待处理年龄。不要只看 consumer group 总 lag；某个分区或租户可能独自阻塞。

5. 检查每个副作用

逐项核对解析、Embedding、向量 A/B、倒排索引、缓存、查询守卫和账本。保存实际记录的版本、哈希和 ACL，不用“任务成功”替代读取事实。

6. 检查生产可见性

以受影响主体和对照主体走真实路径。禁用某层缓存只适合定位，不代表用户路径已修复。修复后必须恢复正常配置再次验证。

7. 选择修复方向

  • 索引落后：以当前源目标版本幂等重建；
  • 索引多余：根据墓碑删除并保留版本屏障；
  • 权限不一致：先拒绝，再更新所有目标和缓存；
  • 索引超前或源纪元冲突：隔离并人工裁决；
  • 大面积转换错误：停止扩散、修复转换器、分批重建。

8. 复验并扩大范围

验证单实体后，按相同代码版本、事件类型、分区、租户和时间窗扩大扫描。一个用户报告往往只是差异集合中的第一个样本。

十八、上线前检查表

真值与合同

  • 每个正文、生命周期和权限字段都有唯一真值所有者
  • 索引被定义为可重建投影，不接受反向覆盖源
  • 实体键包含租户边界
  • 源纪元与实体单调版本的分配规则明确
  • 更新、删除、撤权和授权使用不同操作语义
  • 内容新鲜、删除不可见和撤权暴露分别定义起止点
  • read-your-writes 的实体范围、等待上限和回退行为明确
  • 不支持的跨实体快照保证已经写入接口合同

CDC 与事件

  • 业务变更和 Outbox 在同一事务提交
  • Outbox 事件不可变且有唯一事件 ID
  • 事件载荷或引用绑定不可变源版本和哈希
  • 同实体路由到稳定分区
  • 消费者不依赖到达时间判断新旧
  • 相同版本不同事实会进入隔离
  • 快照到增量边界经过并发更新、删除和撤权测试
  • Outbox、日志和墓碑保留期覆盖最大重放窗口

投影与幂等

  • 每个外部副作用都能按目标版本安全重试
  • 新分片清单完成后才切换可见版本
  • 旧分片通过 manifest 集合差删除
  • 账本使用条件更新，只允许版本前进
  • 账本按每个索引代和缓存目标记录状态
  • offset 在必需副作用完成后提交
  • 所有崩溃边界都做过故障注入
  • 重复、乱序和旧纪元重放不会改变最终正确状态

删除与权限

  • 删除产生可审计墓碑，且不会被低版本更新复活
  • ACL 撤销拥有独立队列、容量和告警
  • 高敏感查询有权威守卫或等效同步拒绝机制
  • 权限服务异常时的失败开闭策略已按风险确定
  • 索引过滤、候选后鉴权和主体展开的责任明确
  • 缓存键包含租户、主体范围和权限版本
  • 删除与撤权主动失效候选及答案缓存
  • 所有读入口和旁路都通过负向权限测试

Embedding 迁移

  • 新旧模型、预处理、维度、距离和查询编码器均有指纹
  • 新模型使用独立索引代，没有原地混写不可比向量
  • 回填快照水位与实时双写交界可证明
  • 回填旧版本不能覆盖实时新版本
  • A/B 分别核对实体、分片、版本、ACL 和墓碑
  • 检索质量按业务与风险切片验收
  • 旧索引在回滚窗口持续接收增量
  • 切回不会复活迁移期间的删除和撤权

指标、对账与运维

  • 新鲜度终点是生产等价路径可搜索，而非写请求返回
  • 超时和未完成事件保留在 SLO 分母
  • 安全事件报告最大暴露时间与超硬上限数量
  • 水位同时展示最大已见、连续完成、缺口和最老年龄
  • 对账比较集合、版本、内容哈希、ACL 哈希与索引代
  • 修复任务执行前重新确认源版本
  • 修复完成后再次对账和生产探测
  • 修复风暴有容量隔离、限速、暂停和续跑机制
  • 证据能从用户 trace 回到源事务和每个副作用
  • 告警、拒绝集合、索引切换与回滚经过演练

十九、总结

知识库新鲜度与一致性的核心，不是把所有组件改造成强一致数据库，而是建立一条可恢复、可裁决、可观测的投影协议。

这条协议从源系统开始：正文、删除和 ACL 都有明确真值所有者；业务变更与 Outbox 在同一事务中产生；事件携带源纪元、实体单调版本和唯一事件 ID。

进入异步链路后，系统默认接受重复、乱序和部分失败。消费者先比较版本，所有外部副作用按目标版本幂等，低版本不能覆盖高版本，墓碑不能被旧更新复活。最大已见水位不能掩盖中间缺口，账本成功也不能替代对索引实际状态的核验。

删除与 ACL 撤销采用更严格路径：安全事件拥有独立容量和硬暴露上限，查询守卫先阻断，索引和缓存随后清理，最终以负向探针与对账证明不可见。授权成功、Schema 合法、HTTP 200、相似度或模型信心都不能替代这个证明。

Embedding 迁移使用独立双索引：固定新代指纹，从有水位的源快照回填，实时双写，用实体集合、版本、ACL、墓碑、检索质量和运行指标联合验收。旧索引只有持续接收增量，才是真正的回滚目标。

最后，事件链路之外必须有对账与修复。对账从源清单重新推导目标状态，发现缺失、多余、版本、ACL、分片和模型代差异；修复仍受版本保护，并在完成后复验。

可以把全文压缩成五条发布原则：

  1. 索引是带来源证据的派生投影，不是第二份业务真值。
  2. 新旧由源单调版本裁决，不由到达时间、写响应或相似度裁决。
  3. 删除和撤权的安全时限优先于普通更新吞吐。
  4. 双索引、缓存和 read-your-writes 都必须进入显式一致性合同。
  5. 只有事件证据、生产可见性探针和周期对账共同闭环，系统才有资格声称最终收敛。
