AI测试-44-AI应用上线后怎么做在线评测抽样反馈和影子流量验证

发表于 2026-05-14 分类于 AI测试 本文字数： 21k 阅读时长 ≈ 1:18

一个 AI 助手上线后，点赞率从 61% 升到 68%，影子候选在自动裁判中又赢了当前版本 57% 的配对样本，能不能直接发布候选？

不能。点赞的人可能只占全部用户的 2%，新版按钮可能只在桌面端正常展示，自动裁判可能偏爱更长的回答，影子候选也从未真正改变用户行为。三个数字都可能是正确观测，却回答了三个不同问题。把它们拼成“候选让用户结果改善”的结论，中间缺少抽样总体、选择机制、成熟真值、用户暴露和反事实设计。

上线后的 AI 系统会遇到离线集没有覆盖的真实输入、动态知识、工具失败、政策变化和人机反馈环。NIST AI 800-4 将部署后监控概括为功能、运行、人因、安全、合规和大范围影响等类别，同时明确指出高质量真值缺失、纵向跟踪成本、用户反馈负担、隐私与方法尚不成熟等挑战。它是一份挑战与开放问题报告，不是一个可以照抄阈值的认证标准。工程团队仍需为自己的任务建立可执行契约。

本文给出这套契约：先定义目标总体和评测单位，再构造可审计的 sampling frame；用分层、保留和概率抽样控制成本与选择偏差；把自动检查、人工反馈和延迟业务结果作为不同证据；在隔离环境中运行影子流量；最后以覆盖率、业务验收率、延迟标签完整率和不确定性作发布决策。

全文中的比例、任务、租户、阈值与事故均为构造示例，不代表任何真实产品。资料截止 2026-05-14，引用的论文实验结论只限于原论文的数据、模型与条件，不外推为生产保证。

一、先给结论：在线评测要管理证据链，不是堆积评分

一套可用的在线评测系统至少遵守十五条原则：

  1. 先写决策，再选指标。 是继续观察、扩大灰度、暂停、回滚，还是只更新离线集，必须在看数据前定义。
  2. 目标总体与抽样框分开。 日志里看见的请求不天然等于希望代表的用户任务。
  3. 评测单位固定。 request、turn、run、task、session 和 user 不能在同一个比例中混用。
  4. 选择概率可追溯。 分层或过采样后，每个样本都要保留纳入概率和抽样策略版本。
  5. 事故身份与概率身份正交。 同一单位可同时是 probability_selected=true 和 incident_forced=true：概率命中保留原纳入概率并进入总体估计，强制身份只增加事故审查用途，不得覆盖概率身份。仅由事故触发、未命中概率抽样的单位不进入总体比例。
  6. 保留随机基线。 风险触发样本之外持续抽一小份均匀或分层随机样本，才能发现选择器看不见的新问题。
  7. 覆盖、验收和标签完整率分别计算。 三者分母不同，互相不能代替。
  8. 真值允许迟到和修订。 指标必须带 as_of，未到期、到期未到、已到、申诉中和已终裁分开。
  9. 反馈是观测，不自动是真值。 点赞、重问、停留时长、客服工单各有选择机制和替代解释。
  10. 自动裁判是带版本的测量工具。 裁判分数、规则命中和模型置信度不能自动变成业务验收。
  11. 影子流量仍然处理真实数据。 它消耗算力，可能越过驻留边界，也可能因工具或下游写操作产生真实副作用。
  12. 影子流量不能直接证明用户结果。 用户没有看到候选输出，也没有因候选改变后续行为。
  13. 回放不是时间旅行。 外部知识、权限、工具和随机采样若未快照，历史输入无法还原历史世界。
  14. 观测、推断、决策分栏记录。 告警和相关性不能被写成根因或因果效果。
  15. 隐私预算属于评测契约。 多存一份 Prompt、多跑一个候选都属于新的数据处理与暴露面。

本文也不提供某个业务通用的合格阈值。医疗辅助、客服摘要、广告生成和代码代理的后果不同，抽样强度、真值窗口、人工资格、停止规则和隐私控制必须由具体风险决定。

1. 适用对象

方法适用于生成、分类、检索、推荐和 Agent 工作流，但评测单位会不同。例如客服回复可按“关闭且未重开工单”的 task 评估；搜索问答可按 query-session 评估；自动退款应按一次业务决策及其后续申诉评估，而不是按模型调用评估。

2. 不足以单独构成在线质量结论的信号

  • HTTP 200、JSON 合法、没有异常堆栈
  • 模型自报置信度、平均 log probability 或裁判单分
  • 用户是否点击复制、停留多久、是否重问
  • 投诉数、客服转人工数或工单数量
  • 影子候选与当前输出的文本相似度
  • 候选在离线集或 benchmark 上的排名
  • 单个时间窗的均值，没有总体、成熟窗口和误差

这些信号都可以进入证据层，但各自都有替代解释。工程目标不是排斥弱信号，而是限制它能支持的结论。

三、先区分观测、推断与决策

在线事故中最危险的句子往往只有一句：“新 Prompt 导致满意度下降。”它可能把三层信息压扁了。

1. 观测 Observation

观测是可回到原始事件的事实：某窗口桌面端收到 820 份反馈，移动端收到 61 份；候选影子运行有 3.2% 超时；到期样本中 88% 已连接最终工单状态；prompt_version 在 10:05 从 P17 变为 P18。观测包含时间、单位、分母、来源和版本，不包含“为什么”。

2. 推断 Inference

推断是带假设的解释：移动端反馈按钮可能不可见；影子超时可能来自候选输出更长；验收率变化可能与 Prompt 版本相关。推断必须写出替代解释、所需补证和置信范围。即便统计检验拒绝了“两个窗口分布相同”，也只是分布证据，不是业务损害或根因证明。

3. 决策 Decision

决策由风险容忍度和证据充分性共同驱动：冻结扩大灰度、修复按钮、延长标签观察、回滚 P18、继续 1% 实验，或接受残余风险。相同观测在低风险文案建议和高风险资格判断中可导致不同决策，这是治理差异，不是统计矛盾。

建议每份在线评测报告固定三栏：

层次 必填内容 禁止写法
观测 事件、时间窗、单位、分母、版本、缺失与误差 “原因是……”
推断 假设、支持证据、反例、混杂、待验证动作 把相关性写成因果
决策 owner、动作、阈值、截止时间、回滚与复核条件 没有责任人的“持续观察”

四、在线评测契约：在读取分数前冻结语义

评测契约是版本化配置和审计记录，不应只存在于看板说明里。最小字段如下：

契约先回答“这个数字要改变什么决策”。如果没有对应动作，采集更多用户内容只会增加成本和隐私风险。若指标达到阈值后团队仍然不会发布、暂停或调查，说明它是观察性指标，不该伪装成门禁。

1. 冻结而不是永久不变

契约可以升级，但不能用新定义静默重算旧结论。修改“合格任务”或“到期标签”规则时，应生成新版本，并在重叠窗口同时产出旧、新口径，解释断点。历史决策继续指向当时版本。

2. 缺失策略也属于契约

缺失不是一个布尔值。至少区分：事件根本未采集、字段因隐私删除、用户选择退出、依赖超时、标签尚未到期、到期未返回、证据损坏、权限不足、冲突待裁决。把所有缺失都填成零，会同时污染覆盖率、验收率和延迟完整率。

3. 负面结果不能被重试覆盖

如果一次 task 先生成危险输出，用户重试后获得合格答案，最终状态可以是业务完成，但第一次输出仍是一个需要安全评测的 attempt。业务验收按 task 去重，故障与安全事件按 attempt 保留，两套分母不能互相覆盖。

五、评测单位、聚类单位与暴露单位

1. Request 不是 Task

一个用户目标可能触发分类、检索、rerank、两次模型调用、工具重试和人工审批。如果按 request 计算通过率，长工作流会被重复计数，重试多的失败任务反而拥有更大权重。业务验收通常应落在 task；协议、模型和工具可靠性可以落在 attempt。

2. Session 不是 User

连续对话的多个 turn 相关，同一用户多次 task 也相关。将所有 turn 当独立样本会低估不确定性。报告至少保留 cluster_id，常见聚类单位是 user、tenant、case 或 session。统计方法若假设独立样本，要么按聚类抽样和估计，要么明确这个假设可能不成立。

3. 暴露单位决定反事实设计

影子流量没有用户暴露。随机灰度若按 request 分流，同一用户可能在两个版本间来回切换，引入记忆和学习污染；若按 user 固定分流，又要处理多设备身份、共享账号和跨租户权限。暴露单位必须与预期作用路径匹配。

4. 时间窗不能只按事件开始时间

长任务可能跨窗，延迟真值可能数日后到达。建议分别保存：

  • occurred_at：生产任务发生时间，用于 cohort 归属
  • selected_at：进入样本时间
  • label_due_at：按业务规则应当成熟的时间
  • label_observed_at：真值实际到达时间
  • adjudicated_at：冲突被终裁时间
  • as_of：本次报告只使用此前可见的证据

报告按 occurred_at 固定 cohort，再用 as_of 更新完整性，避免每天滚动窗口把难以到达的失败样本挤出去。

六、分层架构与数据流：从生产事件到可执行决策

推荐把在线评测拆成八层。

1. Event Envelope

网关、工作流、模型、检索、工具和业务系统只写不可变事实。事件带 task/run/attempt 身份、版本、时间和内容引用，不在边缘节点决定最终质量。内容与元数据分离，默认不把原始 Prompt 复制到每个消费者。

2. Contract Validator

验证身份、时间、版本、用途和必需字段。失败记录进入隔离队列并计入覆盖缺口；不能因为“无法评测”就在总体中消失。这里也执行租户、地区、年龄、合规和 opt-out 的 eligibility 规则。

3. Privacy Transformer

按评测目的删除、令牌化或摘要化字段，生成受控内容引用。用户标识与抽样键分离；评审者只看到完成任务所需的最少内容。删除请求沿 raw、sample、annotation、shadow 和 replay 派生关系传播。

4. Sampling Frame Builder

按评测单位去重，记录每个生产单位是否进入抽样框、为什么排除、所属分层和可纳入时间。抽样框是可重建快照，不是每天覆盖的临时查询。

5. Selector

运行均匀、分层、保留、风险触发或组合策略。概率抽样决定与事故强制决定分别执行，每个单位写入 probability_selected、incident_forced、inclusion_probability、sampling_policy_version 和确定性随机键摘要。两个布尔字段可同时为真，不使用单一 lane 做覆盖式分类。策略升级不改写既有决定。

6. Evidence Plane

并列保存规则、自动裁判、人工标注、用户反馈、业务结果和安全事件。不同来源不先压成一个 final_score。裁决服务把冲突证据合成版本化 label，并保留原始意见。

7. Estimator and Gate

按总体和分层权重估计指标，报告样本量、缺失、设计效应和不确定性。门禁先检查证据完整性，再检查质量与安全；证据不足时进入“未知/停止扩大”，而不是默认通过。

8. Replay and Learning Loop

事故样本、代表性盲点和新风险进入回放包与离线集候选。回流需要去重、授权、污染检查和版本审批，不能把生产用户内容自动变成训练数据。

七、数据模型：保存选择过程，而不只保存被选结果

只有一张 evaluations 表无法解释谁没被看见。至少需要以下实体。

1. ProductionUnit

unit_id 必须稳定且幂等。若同一业务任务被事件总线重复投递，不能产生两个抽样机会。

2. FrameDecision

即使 eligible=false 也保留最小计数和原因；否则团队只能知道框里有什么，不知道框外漏了什么。

3. SelectionDecision

这些是可重叠的成员身份，不是互斥的 selection_reason。例如一个严重失败在分层随机抽样中已经命中，随后又触发事故规则，它应保留同一 unit_id 下的两个真值和原 inclusion_probability。概率估计器按 probability_selected 取数，事故队列按 incident_forced 取数；同一单位可在两种用途中被查看，但在任一指标分母内只按 unit_id 计一次。只有概率机制明确且实际命中的部分才做设计加权。

4. Evidence

不要把裁判信心和业务概率塞进同一个 confidence。字段必须有语义类型；不适用时用 null + reason，不用零。

5. LabelState

censored 表示因为退出、法律删除、业务流程终止等原因无法按原计划观察。它不是通过或失败，需要在完整性和偏差分析中单列。

6. ShadowRun

候选 bundle 不只有模型名，还包括 Prompt、知识、工具 Schema、策略、运行时和随机参数。否则所谓“候选”无法复现。

7. DecisionRecord

DecisionRecord 是监控与发布控制之间的责任边界。它防止看板颜色替人做高风险决定。

八、Sampling frame：日志集合不是目标总体

目标总体 U 是希望结论覆盖的全部评测单位；抽样框 F 是系统在窗口内实际有机会选择的单位。理想情况下二者一致，现实中通常存在：

1. 常见欠覆盖

  • 客户端在发送遥测前崩溃，最差体验没有日志
  • 移动端、旧版本、弱网或特定地区缺少字段
  • 安全拦截发生在统一 Trace 建立之前
  • 用户退出内容采集后，系统连最小计数也一并删除
  • 外部渠道任务只在合作方系统里完成
  • 长任务在窗口结束时仍在执行，被查询条件排除
  • 失败请求没有业务 task_id，无法进入去重逻辑

2. 常见过覆盖

  • 消息总线至少一次投递造成重复
  • 一个 task 的多个 retry 被当成独立业务结果
  • 预加载、健康检查、机器人和内部测试流量混入
  • 客户端与服务端各记一条但没有统一事件 ID
  • 取消后仍执行的候选被计为用户看到的结果
  • 跨天分区回填在两个窗口重复出现

3. 覆盖审计不能依赖同一条坏链路

如果 frame 与 coverage 分母都来自同一日志管道，管道丢 10% 事件时 coverage 仍可能显示 100%。分母应尽量来自独立控制面，例如入口 admission 计数、业务数据库提交记录、账单事件或队列 offset。独立来源也会错，但能减少共同故障造成的自证循环。

4. 退出采集不等于从分母消失

具体法律和产品义务需由组织确认。工程上可以在不保留内容和直接标识的前提下，按批准目的保存聚合的 eligible/opt-out 计数，以诚实报告“多少目标总体因选择退出而不可评测”。不能把不可观察人群默认为与可观察人群相同。

九、选择偏差：谁愿意反馈，谁就会定义产品吗

用户反馈是典型的自选择样本。NIST AI 800-4 记录了反馈收集的负担和非响应问题，例如弹窗可能被忽略，特别不满的人可能更愿意响应。这个提醒不能被简化为“负反馈一定过多”：方向取决于界面、激励、用户关系和任务。

1. 按置信度送审造成 verification bias

只把低置信输出给人工，人工标签集自然包含更多难例。它很适合风险控制，却不代表全量质量。若直接用送审通过率做总体通过率，模型置信策略一变，指标也会变，即使真实质量不变。

2. 只看成功链路造成 survivorship bias

只有完成响应才展示点赞按钮，超时、崩溃、拒绝和工具失败无法反馈。点赞率上升可能只是失败请求从分母中消失。应先按 admitted task 记录终态，再在可展示反馈的子总体上报告 response rate。

3. 支持工单造成 severity enrichment

客服工单对发现严重问题非常有价值，但它富集了愿意投诉、能找到入口、认为值得投入时间的人。工单率还受客服渠道、宣传、工作日和合并规则影响。它是 incident sensor，不是无权重总体估计器。

4. 主动抽样也会被策略污染

“抽所有长回答”会把答案长度和错误混在一起；“抽新模型流量”看不到当前模型盲点；“抽高价值客户”无法代表免费用户。选择器每次利用线上特征，都必须把特征和概率写入记录，并保留独立随机样本。

5. 反馈界面本身是测量仪器

按钮位置、默认焦点、文案、颜色、是否登录、网络请求是否成功，都会改变响应。上线 Prompt 的同时改反馈 UI，就不能把反馈率变化只归因于 Prompt。测量仪器版本必须与模型版本一样进入 lineage。

十、分层抽样：把预算花在方差与风险上

简单随机抽样容易被高流量、低风险、主语言请求淹没。分层抽样先将抽样框划分为互斥且完备的 strata，再为每层设置概率或固定配额。

1. 分层维度

常用维度包括风险等级、任务类型、语言、地区、渠道、租户等级、模型路由、Prompt 版本、知识域、输入长度、工具链和新老用户。不要一次把所有维度笛卡尔积，否则大量稀疏小格无法估计。优先选择会改变风险、质量机制或发布决策的维度。

2. 比例分配

3. 风险与方差分配

工程上常设置每层最小样本，再按历史方差、审查成本和风险增加配额。这样可以更快发现稀有问题，但输出总体指标时必须使用原始层权重或纳入概率，不能直接平均各层样本比例。

4. 动态层必须版本化

风险分类器、语言识别器或路由器升级会改变样本落层。保存 stratum_key 还不够，还要保存产生它的特征和规则版本。否则层内质量跳变可能只是分层边界变化。

5. 极小层的处理

极小层可以全量评审，此时纳入概率为 1；也可以跨多个窗口累积，但要防止版本和业务季节混合。若样本仍不足，应报告“证据不足”，而不是用全站均值填充。

十一、保留抽样：同时看横截面与纵向变化

每个窗口重新随机抽用户适合估计当期总体，却不擅长观察同一对象随时间的变化。保留样本或 panel sampling 固定一部分 cluster，持续观察其任务；另一部分继续刷新以覆盖新用户、新地区和新用法。

1. 推荐的双样本结构

两者分别报告。保留组可能因为知道反馈机制而改变行为，也可能因流失越来越不代表当前总体；刷新组则无法提供稳定个体对照。

2. 用户疲劳与隐私

同一用户频繁收到问卷会增加负担。保留策略应设冷却时间、最大邀请次数、退出机制和用途 TTL。panel ID 应是受控伪名，不应成为跨产品跟踪标识。

3. 回归保留样本

也可以保留“任务模板”而不是用户：例如每周从真实流量中选择已脱敏、已授权的代表性 case，固定加入在线回放。它能检查版本回归，却不能继续代表变化后的总体，因此仍需 fresh sample。

十二、随机样本、风险样本与事故样本三账分离，成员身份可重叠

建议每个窗口维护三条证据流：

样本流 选择目的 可支持结论 主要限制
概率样本 估计目标总体与分层指标 有权重的总体估计 成本、非响应、框覆盖
风险触发样本 快速发现已知高风险模式 风险队列中的失效模式 选择器变化，不能代表总体
事故/投诉强制样本 排障、复现和修复验证 个案事实与机制线索 强制机制本身不提供总体纳入概率；严重富集

风险样本多并不表示总体风险一定上升，也不表示它不重要。正确做法是同时显示“风险触发率”和“触发后失败率”，再用概率样本估计总体。“三账分离”分离的是用途、分母和权重，不是强迫每个单位只能有一种身份。若事故单位也独立命中了概率抽样，它按原纳入概率进入概率账，同时进入 case review；不能因为后来触发事故就把它从估计中删掉，否则得到的是“非事故总体”的条件化基线。若它仅由强制规则进入，则只进事故账。存储层保留一条单位记录和多个成员标记，汇总时先按 unit_id 去重，避免双重身份变成双重计数。

2. 权重过大会放大方差

极低纳入概率对应极大权重，一个标签就可能推动总体估计。应在设计阶段设置最小概率和必要样本，而不是在报告阶段随意截断权重。若确需截断，必须同时报告规则、偏差风险和敏感性结果。

3. 比率估计与已知总体

十五、不确定性：样本量之外还要看设计效应

同样抽 1,000 条，简单随机、极端过采样、用户内多 turn 和评审者重复标注的有效信息量不同。在线报告至少考虑：

  • 分层与不等概率权重
  • user/session/tenant 内相关性
  • 时间自相关和活动突发
  • 人工评审者偏差与重复测量
  • 标签非响应和延迟删失
  • 多指标、多分层同时告警造成的多重比较

可用按 cluster 的 bootstrap、重复权重或适配抽样设计的方差估计。具体方法应由统计设计确定。不要把普通二项分布置信区间机械套在高度加权且聚类的数据上。

1. 最小样本不是固定常数

样本量取决于希望检测的最小有意义变化、基线率、风险容忍度、方差、分层数量和可接受等待时间。高风险罕见事件通常不能仅靠总体随机样本，需要全量规则、风险触发、事故渠道和场景化故障注入共同覆盖。

2. 顺序查看会改变误报

每天盯同一实验，任何一天低于阈值就停止，与只在预定终点查看不是同一个统计过程。若需要连续监控，应预先使用顺序设计、错误预算或保守门禁，并记录每次查看。工程团队不能一边反复窥视，一边沿用单次检验的显著性解释。

3. 实际意义优先于显著性

大流量下极小差异也可能统计显著。决策契约应同时定义安全硬门、业务最小有意义变化、置信要求和成本。p < 0.05 本身既不说明影响大小，也不说明值得发布。

十六、三个核心指标：Coverage、Acceptance、Delayed-label completeness

这三个词经常出现在同一张看板，却必须使用不同分母。下面先固定符号：

  • A：窗口内按契约应进入目标总体的 admitted 去重单位数
  • F：通过 frame 校验并可参与抽样的唯一单位数
  • S：由概率或保留策略选中的唯一单位集合
  • D(as_of)：截至报告时间已经达到 label_due_at 的样本
  • L(as_of)：已到期且已获得可用业务真值的样本
  • Y_i：样本 i 是否通过版本化业务验收规则
  • w_i：设计权重，简单情形为 1 / π_i

1. Frame coverage

它回答“应纳入的生产单位中，有多少形成了有效、唯一、可选择的框记录”。分子不能只数成功请求，分母尽量来自独立 admission 或业务提交事实。还应按平台、渠道、地区、任务和失败终态分层，否则 99% 总覆盖可能隐藏移动端只有 72%。

3. Delayed-label completeness

4. 为什么不能相互替代

构造示例：某日 frame_coverage=99%、delayed_label_completeness=55%、已知标签上的 acceptance=96%。正确观测是事件链完整但成熟真值大量缺失；不能宣布总体 96% 合格。另一天完整率 99%、验收率 90%，可能说明证据充足且质量较差。门禁通常先要求前两项达到下限，才解释第三项。

5. 分层覆盖向量比单值更可靠

建议看板同时显示 coverage[stratum]，并定义关键层硬门。例如总 coverage 不能抵消高风险层 coverage。若某个层因隐私限制无法评测，决策记录应写“该层未知及其业务占比”，而不是将其从 target population 删除。

十七、延迟真值：用 cohort 和成熟度管理时间

许多业务结果不会在模型响应时出现：退款是否被申诉、工单是否重开、代码是否通过后续构建、推荐是否退货、摘要是否在合规审核中被纠正。NIST AI 800-4 明确把部署后高质量真值延迟、昂贵或不可得，以及长期跟踪开销列为挑战。

1. 为每类标签定义到期规则

2. Provisional 与 final 分开

响应时可生成 provisional 规则分；业务结果到达后生成 observed label；多来源冲突经裁决后成为 final。最终标签不要覆盖早期值，而应以 supersedes 连接。这样团队能分析早期代理指标和最终结果的关系，也能发现代理失效。

3. 右删失不是失败

观察窗结束时尚未成熟、用户退出、任务合法取消或业务系统永久缺失，都可能造成删失。它们需要单独状态。把删失记为失败会低估质量，把它删除又可能高估质量。应报告上下界或敏感性分析，例如把全部 due-missing 分别假设为通过与失败，展示可行区间。

4. 标签到达顺序可能有偏

自动成功状态常实时到达，投诉和追偿可能数周后到达。过早读取 cohort 会产生“质量先高后低”的机械形状。发布门禁应等待预定成熟度，紧急安全信号可以先触发暂停，但不能把早期 acceptance 当最终效果。

5. Backfill 必须幂等

延迟 join 作业应以 (unit_id, label_definition_version, source_event_id) 幂等。回填只能新增 label revision，不能改写历史报表使用的 as_of 快照。每次重算记录输入 snapshot 和代码版本。

十八、反馈分类：显式、隐式与业务真值不是同一层

1. 显式反馈

点赞、点踩、星级、原因标签和自由文本表达用户在特定界面下愿意提交的意见。它们可用于发现问题和理解感知，但受响应倾向、文案、位置、身份、情绪和任务成功后的离场影响。

2. 隐式行为

复制、点击引用、继续追问、改写、撤销、人工接管、停留时长和会话退出都是行为观测。它们通常有多种解释：复制可能是采用，也可能是拿去批评；重问可能是答案差，也可能是任务自然推进；短停留可能是答案直接，也可能是用户放弃。

3. 业务后置条件

工单是否关闭且未重开、工具写入是否被下游接受、代码是否合并并稳定、资格判断是否在申诉后维持，才更接近任务结果。即使如此，它也可能受人工、价格、界面和外部事件影响，不能自动归因给模型。

4. 专家与受影响人群反馈

NIST AI RMF 的 Measure 与 Govern 结果强调纳入领域专家、用户、受影响社区和外部相关方，并将经裁决反馈纳入评估。工程上要分别记录角色、资格、利益关系和看到的上下文，不能把开发者自测与受影响用户意见混为一票。

5. 反馈层级建议

每次转换都要能回到上层，且保留处理版本。

十九、反馈去噪：清洗不能变成删除坏消息

1. 身份与幂等

同一 UI 重试、离线同步或双击可能生成重复反馈。使用稳定 feedback_event_id、幂等写入和客户端 attempt；不要只按相同文本去重，因为两个用户可能提交同样原因。

2. 可见性与邀请分母

记录用户是否有资格看到反馈控件、控件是否实际渲染、请求是否提交成功。推荐分开报告：

没有 exposure 分母，移动端按钮故障会被误判为“移动用户更满意，所以不反馈”。

3. 机器人、滥用与批量操作

过滤规则需要原因码和复核样本。过于激进的去重可能删除同一故障造成的大量真实投诉。风控评分只能标记和分层，不能在无审计的情况下把负面意见静默丢弃。

4. 冲突反馈

同一任务可能先点赞后点踩，也可能用户满意但专家判定不合规。不要强求合成一个“真值”。保留维度：用户感知、任务完成、事实正确、安全合规、过程可接受。发布契约可以规定安全失败优先，但这是一条决策规则，不代表用户感知不存在。

5. 自由文本最小化

反馈文本可能再次包含身份证号、账号、健康和商业机密。进入评审前执行用途校验、字段检测、受控遮蔽和访问审计；原文与脱敏视图分离。自动摘要会遗漏细节，因此原文是否可见应由权限和调查需要决定，不应默认全员可见。

6. 负面反馈采样

严重负面应全量进入安全/事故队列，但用于总体估计时仍需随机基线。可以对负面做高概率纳入、正面做低概率纳入，并使用已记录权重；未知响应机制的自愿反馈则单独报告，避免伪精确校正。

二十、人工评审：盲法、分派与裁决同样会漂移

1. 盲化候选身份

配对比较中随机左右位置，隐藏模型、Prompt、路由和发布时间。否则评审者对“新版本”或特定供应商的预期可能影响结果。必要时将同一对输出重复换位，用于检查位置偏差，但重复样本不能作为独立总体单位。

2. 分派要避免选择泄漏

如果高级专家只看候选争议样本、普通评审看当前版本简单样本，评审者差异与版本差异混杂。分派器应在风险资格约束内随机或平衡，并保存 reviewer pool 与 assignment policy。

3. 评审量规版本

评分 rubric、示例、政策和工具访问都会更新。标签必须指向版本；新量规上线时对一组 bridge sample 双标，估计测量断点。不能把评分标准变严造成的下降归因给模型。

4. 一致性不是正确性

评审者高度一致可能共同误解规则；低一致性可能说明任务本身模糊。既要测一致性和冲突率，也要由领域专家审查构造效度。黄金题可以检查明显偏离，但黄金题泄漏后会变成记忆测试。

5. 申诉与终裁

高风险任务需要明确谁能推翻自动/初审标签、基于什么证据、在多久内完成。终裁生成 revision，不删除原意见。报告既看初审质量，也看终裁后业务结果和申诉率。

二十一、自动评测与弱标签：用于扩展，不用于偷换真值

确定性 Schema、禁用动作、引用存在、工具参数、权限和业务不变量适合全量自动检查。语义裁判、相似度、毒性分类器和规则组合可以扩展覆盖，但它们仍是测量系统。

1. 双层使用

弱 evaluator 的阈值变化会改变送审样本，必须纳入 sampling lineage。

2. 校准子集

从概率样本中抽取盲审子集，比较自动评测与人类/业务标签在不同语言、风险、长度和版本上的误差。不要只在裁判高置信样本上校准。若分层误差不同，单一全局阈值可能掩盖小群体失败。

3. 同源偏差

候选和裁判共享模型家族、训练偏好或提示风格时，胜率可能体现风格一致而非业务改进。可使用确定性规则、不同方法的裁判、盲审和成熟业务结果形成三角证据；不能因为“多裁判投票”就假定独立。

4. 自动分不能反向覆盖硬事实

业务写入失败、权限越界或人工终裁不合规时，较高语义分不能抵消。聚合分数前先执行硬门，避免平均值把严重失败稀释。

二十二、影子流量是什么：复制输入，不复制用户暴露

影子流量通常把已获准的生产输入或受控表示复制给候选链路，候选结果不返回给用户，只用于配对比较、兼容性、容量和故障发现。它特别适合验证：

  • 候选能否解析真实输入与上下文
  • Prompt、工具 Schema、检索和输出结构是否兼容
  • 相同输入下规则失败、拒答、引用和工具计划如何变化
  • 候选延迟、Token、超时和资源需求
  • 新模型或新索引是否覆盖长尾语言、长度和任务
  • 回滚包、Trace 和比较器是否工作

它不天然适合证明用户满意度、任务完成率、长期行为或社会影响，因为用户没有看到候选，后续输入仍由当前版本塑造。

二十三、影子流量的真实风险：没有展示不等于没有执行

“影子”容易让人误以为完全无副作用。实际上它至少发生了新的数据处理和计算。

1. 真实数据处理

候选可能接收用户原文、历史对话、检索片段、权限元数据和工具结果。即使输出不展示，也可能越过地域、供应商、用途和保留边界。生产链有权使用某字段，不代表新候选、外部 API 或评审存储自动有权使用。

2. 算力与容量风险

镜像 100% 流量可能近似增加一套推理、检索和网络负载。共享 GPU、向量库、缓存、限额或数据库连接池会被争用，进而伤害主链路。影子成本必须独立计量、限额和可停止，容量实验不能偷偷借用生产余量。

3. 下游副作用

Agent 候选可能发送邮件、创建工单、写数据库、支付、修改日历、触发 webhook 或污染缓存。仅在 UI 层丢弃候选输出远远不够。工具执行层必须使用 deny-by-default：读操作也要按权限控制，写操作使用模拟器、事务回滚、隔离租户或明确阻断。

4. 安全与滥用风险

候选可能生成敏感内容并进入日志，或被真实 Prompt Injection 驱动去探测内部工具。影子环境要执行同等或更严格的安全策略，不能因“不展示”而关闭审计。

5. 外部依赖风险

影子调用第三方 API 可能产生真实计费、速率限制、合同或数据外发；即使 GET 请求也可能记录访问、改变推荐状态或触发审计。所有下游按“可能有副作用”建模，只有经过清单批准的接口才能真实访问。

二十四、影子执行隔离：先构造能力沙箱

推荐在入口复制一个最小化的 ShadowEnvelope，而不是克隆整个生产请求对象。Envelope 只包含候选评测所需字段、用途、TTL 和 trace linkage。

1. 控制面

  • 按 tenant、region、risk、channel 和 opt-out 检查 eligibility
  • 设置全局、租户和候选的 QPS/Token/成本预算
  • 支持一键停止，不依赖候选服务健康
  • 固定候选 bundle、sampling policy 和隔离策略版本
  • 主链路背压时优先丢弃影子，不反向阻塞用户请求

2. 数据面

  • 使用独立队列、线程池、连接池和缓存命名空间
  • 内容引用按最短 TTL，比较完成后删除不必要副本
  • 禁止影子结果写入用户会读取的会话状态或长期记忆
  • 候选检索若访问生产索引，保持只读并记录 snapshot
  • 工具使用 stub、record/replay 或专用沙箱账号

3. Egress Broker

所有外发经过 broker。Broker 按 tool/action 分类：pure_read、stateful_read、reversible_write、irreversible_write。影子默认只允许经批准的 pure read；其余返回确定性模拟结果并记录“如果真实执行会调用什么”。分类本身也需测试，因为很多名为 query 的接口会更新 last-access 或触发计费。

4. 主链路隔离 SLO

设立硬门：影子开启前后主链路 P95/P99 延迟、错误率、队列深度和资源水位不得退化超过预算。观察到相关变化先停影子，再通过资源 Trace 判断；不能因为候选质量评测重要而牺牲线上可用性。

二十五、配对比较：影子最强的证据是“同输入下行为差异”

同一个生产单位同时运行 current 与 candidate，可降低输入构成差异。比较包至少包含：

1. 保持配对完整

候选超时不能从胜率分母删除。配对状态应是 both_complete、current_only、candidate_only、both_failed。只比较双方成功的样本会产生条件选择偏差。

2. 比较顺序与盲法

人工或裁判输入随机左右顺序，隐藏版本名称。若裁判 Prompt 更新，建立新的 comparison version；不要用新裁判重算后静默覆盖旧发布证据。

3. 随机性

单次生成比较可能把采样噪声当版本差异。对高风险或接近门槛的样本可做有限重复，保存 seed、采样参数和重复编号。重复结果属于同一 unit cluster，不能膨胀独立样本量。

4. 候选胜率的正确读法

同时报告 tie、current win、双方失败、候选独有失败、不可裁决和 coverage。这个胜率只能说明在该 frame、比较器和完成条件下候选输出更常被偏好，不能说明用户结果改善。

二十六、反事实证据：影子输出不是用户结果的潜在结果

1. 什么时候需要随机暴露

若决策问题是“候选是否提高任务完成率/降低申诉/改善用户体验”，通常需要在风险允许时做稳定分配的随机灰度或其他经审查的因果设计。要预先定义实验总体、暴露单位、排除规则、护栏、最小效果、停止与分析计划。

2. 随机化也不是万能保证

身份切换、跨组污染、推荐网络效应、用户学习、非响应、并发产品改动和提前停止都可能破坏解释。随机化支持因果推断依赖设计与执行，不是因为控制台显示了 A/B 标签。

3. 影子仍是重要前置门

影子可以在不暴露候选的情况下发现 Schema、权限、延迟、拒答和明显质量回归，缩小真正灰度的风险。正确证据梯度是：离线回放 → 影子配对 → 内部/受控使用 → 小比例随机灰度 → 扩大，而不是把影子当最终用户实验。

4. 不可随机的高风险场景

若候选错误可能造成不可接受损害，不能为获得因果证据而随机暴露。可以使用专家模拟、受控沙箱、历史自然变化与更保守上线，但必须诚实记录仍未知的反事实问题。证据不足有时意味着不发布，而不是降低统计门槛。

二十七、回放：让历史输入与历史依赖一起成为证据包

只保存 Prompt 文本通常无法回放。完整 ReplayBundle 至少包括：

  • 评测单位与父子 Trace
  • 经过授权的输入内容或不可逆特征
  • system/developer/user Prompt 模板与渲染后摘要
  • 模型、参数、tokenizer、路由和安全策略版本
  • 检索 query、过滤、候选 ID、chunk 内容摘要与索引 snapshot
  • 工具 Schema、调用参数、响应 snapshot 和副作用分类
  • 时区、locale、feature flag、tenant policy 和权限快照
  • 原始规则、裁判、人工与业务标签引用
  • 运行环境和随机性信息

1. Replay fidelity 分级

不同级别回答不同问题。L1 适合模型/Prompt 配对回归，无法证明当前知识；L3 更接近当前系统，却不是历史状态重现。

2. 记录不可回放项

外部网页、实时库存、权限服务和不可控模型可能无法快照。ReplayBundle 应列出 unreplayable_dependencies，比较报告据此降级。不能用缺失依赖的 stub 结果声称完整复现了生产事故。

3. 防止评测污染

生产事故进入固定回归集后，开发者可能针对样本调 Prompt。它适合证明已知事故不复发，却不再是独立泛化证据。应将 regression、fresh holdout 和 online probability sample 分开。

二十八、隐私与数据治理：在线评测是新增处理活动

NIST AI 800-4 特别指出监控本身可能侵犯安全与隐私，时间戳和活动细节即使没有直接标识也可能帮助重新识别。NIST SP 800-122 则要求根据上下文识别并保护 PII 的机密性。工程实现应由适用法律、合同和组织政策审查，本文不是法律意见。

1. 目的绑定

为运行服务收集的数据，不自动允许用于人工评审、影子候选、训练或跨境处理。契约明确 purpose；新的候选供应商、评审队伍或长期 replay 可能需要新的审批。

2. 数据最小化

抽样和 coverage 通常只需 unit ID、分层与状态；人工事实核验才可能需要内容；影子兼容测试有时只需结构化特征。按阶段发放最小视图，不要把“以后可能排障”当无限保留理由。

3. 伪名化不是匿名化承诺

哈希用户 ID 仍可被时间、租户、任务和文本关联。将身份映射存放在独立权限域，限制 join，轮换抽样 salt，并在风险评估中考虑组合重识别。

4. 保留与删除传播

为 raw event、selection、annotation、shadow output、replay bundle 和导出报告分别设置 TTL。建立派生图，使删除或限制处理请求能定位全部副本；聚合统计是否保留由批准策略决定。

5. 评审访问

按任务分派临时访问，默认隐藏 tenant、版本和不必要身份；高敏内容使用专用队伍与环境。禁止评审者下载到个人设备，导出和截图能力按风险控制，访问必须可审计。

6. 供应链与地域

候选模型、裁判、标注平台、日志仓库和分析工具都可能成为数据处理方。影子链路要单独验证 region、subprocessor、训练使用、日志保留和删除能力，不能沿用主链路假设。

7. 聚合发布

小 strata 的指标可能暴露个人或客户。设置最小展示单元、权限和合并规则，但内部风险响应仍需有受控细节通道。为保护隐私合并分层后，要明确公平性或小群体盲点，而不是宣称覆盖完整。

三十、自动化策略：按风险、时间和事件三种节奏运行

1. 每请求同步门

只放置低开销、确定性的硬规则：权限、Schema、禁用工具、敏感字段外发、预算和关键后置条件。同步门失败可阻断或降级，但不要在请求路径运行昂贵语义裁判。

2. 近实时流处理

按分钟聚合 frame coverage、影子完成率、主链路隔离 SLO、规则失败和安全事件。使用事件时间与 watermark 处理迟到事件；修正通过新版本窗口完成，不能静默改历史告警。

3. 日批抽样与评审

冻结每日 frame snapshot，执行分层选择、评审分派和 shadow pairing。固定随机键保证重跑同一策略得到同一选择。配额不足、稀疏层和评审 backlog 形成显式状态。

4. 延迟标签回填

按标签类型的 due rule 扫描 cohort，只更新到期状态与 revision。每日生成 completeness aging：到期 0–1 日、2–3 日、4–7 日和更久，帮助区分暂时延迟与系统性丢失。

5. 周期性独立审计

每周或每个发布周期重抽一批不受风险选择器影响的随机样本，校验 evaluator、反馈 UI、标签 join 和删除传播。高风险系统还要由非一线开发者或独立评估者复核契约与案例。

6. 事件触发加密

模型、Prompt、知识、工具、反馈 UI、抽样策略、label 定义或基础设施版本变化时，自动提高受影响 strata 抽样率，并建立 bridge window。突发投诉、coverage 下跌、安全事件或候选超时也触发加密，但强制样本仍与概率账分开。

7. 自动停止而非自动归因

系统可以自动暂停影子、停止扩大灰度或回滚到批准版本，因为动作由预定义硬门触发；告警描述仍应是“观察到何种越界”。根因字段只有在回放、变更对照或调查证据满足标准后填写。

三十一、故障注入：验证评测系统会揭露自己的盲区

在线评测平台也会失败。只给它健康事件，最多证明 happy path 能画图。故障注入应覆盖数据、选择、标签、评审、影子、隐私和控制动作。

1. Frame 丢失

在入口 admission 产生 1,000 个构造 task，仅让事件管道接收 930 个，且集中丢失某渠道。预期：总 coverage 降低，该渠道硬门触发，acceptance 不得用 930 条伪装全量；隔离队列和 offset 证据能定位丢失阶段。

2. 重复与重试放大

重复投递同一 unit_id，再为一个失败 task 生成三个 attempt。预期：task frame 去重，attempt 故障仍保留；抽样器只给 task 一次概率机会。若样本量或通过率变化，说明身份边界错误。

3. 选择概率丢失

删除一批 inclusion_probability 或写入零。预期：加权估计拒绝生成，报告显示受影响 strata 和策略版本；不能自动按权重 1 补齐。

4. 标签延迟与选择性缺失

让负面标签比正面标签晚三天到达，或只丢失高风险层。预期：early acceptance 与 final 分开，completeness 分层下降，证据门先 hold；到期回填后历史 as_of 不被覆盖。

5. 反馈 UI 故障

构造移动端控件未渲染、提交 API 50% 失败和双击重复。预期：exposure、response、validity 三层分别变化；系统不把“没有负评”解释为满意。

6. 评审偏差

给盲审样本泄露 candidate 标签，或固定候选总在左侧。预期：位置/版本盲化测试失败，发布证据作废；历史标签保留但状态改为 measurement_invalid。

7. 影子写操作

候选工具计划尝试发送邮件、支付或写长期记忆。预期：egress broker 阻断，outbound_write_attempts 告警，真实下游零写入，候选比较标记策略失败。若只在 UI 丢弃输出，注入会暴露真实副作用。

8. 影子资源争用

逐步提高影子比例并限制共享连接池。预期：主链路隔离 SLO 先触发自动降采样或停止，影子队列可丢弃且不反压生产。团队同时看到候选覆盖下降，不能继续解释质量胜率为全流量。

9. 删除传播

对一个构造 subject 发起删除，检查 raw、sample、annotation、shadow、replay 和导出缓存。预期：按政策删除或不可逆解除关联，派生状态可审计；统计聚合是否保留符合批准规则。

10. 门禁执行失败

让指标服务返回 stale snapshot、decision worker 重复消费、回滚目标不存在。预期：门禁 fail closed 或进入人工审批，action 幂等，旧快照不能覆盖新决定。评测正确但控制面不执行，同样是发布系统故障。

故障注入报告固定写四项：注入位置与范围、预期可观察证据、实际检测延迟、恢复后的对账结果。不要只记“告警触发成功”，还要验证错误样本没有进入最终分母。

三十二、看板设计：先显示证据健康，再显示质量

推荐从上到下排列，而不是把大号 acceptance 放在第一屏。

1. 目标总体与 Frame

  • admitted target units、frame units、重复数、排除原因
  • 总体与关键 strata 的 frame coverage
  • 客户端/服务端/业务控制面计数差异
  • 事件延迟、隔离队列、未知版本和无 task_id 数

2. 抽样与评审

  • 各 lane 的 selected 数、纳入概率分布与最大权重
  • fresh、retained、risk、incident 的独立计数
  • 评审 backlog、assignment、盲化失败、冲突与终裁时延
  • evaluator 版本、校准子集误差和不可裁决率

3. 延迟真值

  • not_due、due_missing、observed、disputed、final、censored
  • delayed-label completeness 总体与分层
  • label latency P50/P95、aging bucket 和 source failure
  • provisional 到 final 的迁移矩阵

4. 质量与安全

  • 加权 acceptance 及不确定性，不加权样本值作为诊断
  • 关键 strata 与安全硬门，不用总体均值抵消
  • attempt 级严重事件、task 级业务验收和申诉率
  • 当前、候选、历史基线的同口径比较

5. Shadow

  • eligibility、mirrored、both complete、candidate only/current only
  • pairwise win/tie/loss、硬规则差异、不可裁决
  • 候选延迟、成本、超时、Token 和资源预算
  • real-data region、TTL、删除状态、write attempts 与 broker blocks
  • 主链路影子开启前后隔离 SLO

6. Decision

  • 当前 action、owner、依据的 contract/as_of/snapshot
  • 观测、推断、替代解释和未知项
  • 下个证据成熟时间、停止/扩大条件和回滚目标
  • 决策过期时间，防止一份旧“通过”长期复用

颜色只表示契约状态，不表达根因。红色 coverage 是“证据不足或采集故障”，不是“模型变差”；红色 acceptance 是“成熟证据显示低于门槛”，仍需归因调查。

三十三、发布门禁：证据充分性优先于候选胜率

一个保守的门禁顺序如下：

1. Unknown 是一等状态

门禁至少有 pass、fail、unknown、not_applicable。标签未成熟、关键层 coverage 低或比较器失效时应是 unknown。把 unknown 当 pass 会奖励观测故障，把 unknown 当 fail 又会混淆质量与证据；动作可以同样是暂停扩大，但原因必须不同。

2. 安全硬门不做平均交换

候选帮助度提高不能抵消越权工具写入。风险契约先定义不可交易条件，再在可行集合中比较质量、延迟和成本。高风险 incident 即使不在概率估计中，也能按硬门触发停止。

3. 门槛冻结与例外

阈值在窗口打开前冻结。任何豁免都需记录 owner、理由、范围、截止、补偿控制和复核时间。不能因候选“整体很好”临时降低高风险层完整率。

三十四、完整事故案例：点赞率上升来自反馈按钮欠覆盖

以下为构造事故，数字只用于展示推理链。

1. 背景与变更

客服摘要 Prompt P18 在周一 10:00 灰度到 30%。同次移动端发布重构了消息底部操作栏。发布看板到周二显示 P18 点赞率 72%，P17 为 64%；团队准备扩大到 100%。

2. 初始观测

  • P18 有 1,840 份有效点赞/点踩，P17 有 4,210 份
  • 自动裁判配对胜率 55%，无安全硬门失败
  • 桌面端 response rate 基本不变
  • 移动端负反馈绝对数下降 78%

错误推断是“P18 明显改善移动体验”。点赞率分母只有提交反馈者，且模型与 UI 同时变更。

3. 证据审计

团队先查 feedback funnel：移动端 eligible sessions 正常，widget rendered 从 91% 降到 18%，提交 API 成功率正常。frame coverage 仍是 99.4%，因为任务日志存在；但 feedback exposure coverage 严重下降。按平台查看，P18 灰度恰好在新版移动客户端占比更高。

概率盲审样本不依赖按钮。盲审显示 P18 与 P17 总体差异不确定，高风险长工单中 P18 还更常漏掉时间条件。到期业务标签完整率只有 62%，不足以估计最终重开率。

4. 观测、推断与根因

观测：按钮渲染事件在移动新版缺失，反馈 exposure 下降，版本分配与客户端版本相关。推断：点赞率上升主要受测量欠覆盖影响。通过复现和前端事件发现操作栏高度计算错误，按钮落在可视区外；这是反馈缺失的根因。它并不能自动成为 P18 质量变化的根因，后者仍未知。

5. 决策与恢复

团队停止扩大 P18，但没有仅凭该事故回滚 Prompt；先回滚移动 UI，恢复 exposure。P18 维持 30% 并提高长工单概率抽样，等待 delayed-label completeness 达到 90%。历史点赞看板标记 measurement_invalid，不删除原始事件。

修复后三天，反馈 exposure 恢复，P18 点赞差异缩小；成熟业务标签显示总体无明显改善，长工单低于安全余量，于是 P18 回滚并进入 Prompt 修复。这个案例说明：反馈仪器事故和候选质量结论要分开归因。

三十五、完整发布决策案例：影子胜出，仍只进入 1% 随机灰度

以下同样是构造示例。

1. 决策问题

候选 C2 更换模型和 Prompt，目标是减少退款资格说明中的遗漏，同时不增加错误批准。团队要决定是否从 0% 进入用户灰度，而不是直接决定是否全量。

2. 影子设计

两周内按风险 × 语言 × 渠道分层镜像 8% 概率样本，严重投诉另进事故流。候选使用独立连接池；支付、邮件和工单写操作全部由 broker 模拟。输入按地域策略路由，原文 TTL 24 小时，比较结果只保留脱敏证据和摘要。

3. 影子观测

  • frame coverage 99.1%，关键高风险层 98.7%
  • both-complete 96.8%，候选独有超时 1.9%，当前独有超时 0.6%
  • 盲审已裁决配对中候选 win/tie/loss 为 49%/34%/17%
  • 候选在“资格日期说明”规则上失败更少
  • 候选平均计算成本更高，P95 影子完成时间接近预算
  • broker 阻断 23 次候选支付计划；这些是计划差异，没有真实写入

4. 不能得出的结论

不能说 C2 让退款完成率提升 32 个百分点，也不能说 23 次支付计划一定会伤害用户。用户没有看到 C2，工具写入被模拟，后续对话仍由当前版本生成。影子只证明 C2 在该样本上更常被盲审偏好、规则遗漏较少，同时更常计划支付动作且更慢。

5. 发布门与动作

安全团队检查 23 个计划，发现其中 21 个在真实工作流中应等待人工确认，候选 Prompt 漏了确认条件。修复为 C3 后重新影子，写计划硬门通过。团队决定进入 1% 用户级稳定随机灰度，限定低金额、可撤销场景，支付仍需人工确认；预注册任务完成、错误批准、申诉、人工接管和延迟门槛。

6. 灰度结果与最终决策

七天后标签尚未成熟，系统保持 1%。十四天后 delayed-label completeness 达到 93%，错误批准护栏未越界，任务完成率估计改善达到预设最小效果下界，人工接管未恶化，才扩大到 10%。结论限定在实验总体和观察窗，不推广到高金额或未覆盖地区。

三十六、完整事故案例：延迟标签“改善”来自失败先缺失

构造的代码代理在周五发布候选，周一 provisional 编译通过率从 86% 升到 91%。团队忽略了失败项目的 CI 队列更长，且一些仓库周末不运行完整测试。

1. 证据链

按 merge cohort 查看，成功项目标签中位延迟 20 分钟，失败项目 31 小时；周一 delayed_label_completeness 仅 58%，其中大型仓库为 32%。早期 91% 只覆盖快返回项目。到周三完整率 94% 后，最终 acceptance 为 84%，候选引入的依赖冲突集中在大型仓库。

2. 决策

团队在完整率跌破门槛时停止扩大，并未把 early acceptance 当发布证据。完整标签到齐后回滚候选，新增 repository size × build system 分层和三次成功流水线的 due rule。

3. 根因边界

标签延迟差异解释了“周一指标虚高”；依赖冲突通过锁文件回放和候选/当前配对构建确认，是质量回归根因。两者相关但不是同一个问题。若只修 join，不修候选，最终质量仍差；若只修候选，不修完整性门，未来还会误判。

三十七、排障手册：从异常数字回到选择过程

1. Acceptance 突然升高

先查 frame、label completeness、label latency、评审量规和分层构成，再查模型。确认失败是否从分母消失、成功标签是否先到、风险路由是否把难例转人工、反馈 UI 是否变化。只有在口径稳定后才比较输出。

2. 负反馈突然增多

查 widget exposure、邀请策略、重复、机器人、产品事件和渠道宣传。负反馈可立即触发个案安全响应，但总体退化需要概率样本或可解释的曝光分母补证。

3. Shadow win rate 下降

查 both-complete、候选超时、左右随机、裁判版本、输入 snapshot 和候选 bundle。若只有候选失败对被排除，win rate 甚至可能反向升高。先恢复配对分母，再讨论质量。

4. Coverage 仍为 100% 但业务投诉缺日志

检查 coverage 分母是否与 frame 同源。用 admission、业务提交、账单或队列 offset 对账；检查失败是否发生在 Trace 建立前。100% 自洽不等于覆盖真实总体。

5. 影子拖慢主链路

先按预案停影子，确认主链路恢复；再比较连接池、GPU、缓存、索引和外部限额。性能相关性不是根因证明，但停止影子后的可逆变化可加强资源争用假设。

6. 用户与人工意见相反

拆成帮助度、事实、安全、合规和任务完成维度。检查评审看到的上下文与用户是否一致。决策按风险优先级处理，不通过简单多数把安全失败平均掉。

三十八、从 0 到 1 的落地顺序

阶段一：身份与分母

  1. 选一个可验证业务 task，建立 task/run/attempt 身份。
  2. 从独立入口获得 admitted 分母，构造去重 frame。
  3. 先上线 frame coverage 和缺失原因，不急着做综合分。
  4. 固定 contract、as_of、label due 和决策 owner。

阶段二：概率样本与证据

  1. 建立少量随机样本和关键风险分层。
  2. 保存 inclusion probability、策略版本和 cluster。
  3. 接入确定性规则、盲审与一个成熟业务标签。
  4. 分别显示 acceptance 和 delayed-label completeness。

阶段三：反馈与回放

  1. 为反馈建立 exposure/response/validity funnel。
  2. 加入冲突、申诉和终裁 revision。
  3. 建立最小 ReplayBundle 与删除传播。
  4. 用事故样本扩展回归集，保持 fresh holdout。

阶段四：影子与灰度

  1. 先完成数据用途、地域、预算和工具副作用清单。
  2. 从纯读、低比例、独立资源的影子开始。
  3. 验证配对完整、主链路隔离与一键停止。
  4. 只有在风险允许且问题需要用户结果时进入随机灰度。

三十九、可执行上线检查清单

契约与责任

  • decision question、owner、允许动作和复核截止明确
  • 目标总体、评测单位、cluster、去重键和时区固定
  • contract、公式、阈值、label 和 sampling policy 都有版本
  • pass、fail、unknown、not_applicable 的动作分别定义
  • 回滚目标真实存在并完成演练

Sampling frame

  • admitted 分母尽量来自独立控制面
  • 成功、失败、取消、超时和无 Trace 任务均有去向
  • 重试按 attempt 保留、按 task 去重
  • undercoverage、overcoverage 和排除原因可计数
  • 总 coverage 与关键 strata coverage 都有硬门

抽样

  • 概率、保留、风险和事故用途分账，成员身份可重叠
  • 每个概率样本保存 π_i > 0 和策略版本
  • 动态 strata 的分类器和规则版本可追溯
  • 持续存在不受风险选择器影响的随机基线
  • 权重范围、极端权重和 cluster 相关性已评估

标签与反馈

  • label_due_at、observed_at、adjudicated_at 和 as_of 完整
  • not_due、due_missing、disputed、final、censored 分开
  • feedback exposure、response、validity 分别报告
  • 用户感知、专家判断、安全与业务结果不压成同义标签
  • 评审盲化、平衡分派、量规版本与申诉流程已验证

指标与报告

  • frame coverage、acceptance、delayed-label completeness 分母独立
  • acceptance 使用成熟且可用标签，并说明设计权重
  • 不确定性方法适配分层、权重和 cluster
  • 样本原始比例不冒充总体估计
  • 观测、推断、替代解释和决策分栏

Shadow

  • 影子处理真实数据的用途、地域、供应链与 TTL 已批准
  • 独立队列、连接池、缓存命名空间、配额和停止开关可用
  • 工具 deny-by-default，写操作由 broker 阻断或确定性模拟
  • both-complete、单边失败与不可裁决都进入分母报告
  • 主链路资源和 SLO 在影子开启前后有隔离门
  • 报告明确影子不能直接证明用户结果

隐私与回放

  • raw、sample、annotation、shadow、replay 各有最小字段和 TTL
  • 伪名映射与内容存储分离，join 权限受控
  • 删除/限制处理可沿派生图传播并审计
  • ReplayBundle 标出无法快照的依赖和 fidelity 等级
  • 生产样本进入回归或训练前有授权、去重和污染审查

故障与运营

  • 已注入 frame 丢失、重复、概率缺失和标签迟到
  • 已注入反馈 UI 故障、评审泄漏和影子写操作
  • stale snapshot、重复决策和回滚失败有控制面测试
  • 告警能自动停止风险动作，但不会自动宣称根因
  • 证据包可由非一线开发者复核

四十、总结

AI 应用上线后，真实流量提供了离线集无法完全复制的上下文，也同时引入选择、延迟、人机互动、隐私和副作用。在线评测的价值不在于收集更多分数，而在于知道每个分数代表谁、遗漏谁、何时成熟、由什么测量工具产生，以及足以支持什么动作。

完整方法可以归纳为十二步：

  1. 从发布决策反推评测契约，固定总体、单位、窗口与 owner。
  2. 用独立分母审计 production sampling frame，不让失败和退出静默消失。
  3. 通过分层、保留和随机基线兼顾代表性、风险与纵向变化。
  4. 记录每个概率样本的纳入概率；事故标记只增加排查用途，不覆盖已命中的概率身份。
  5. 将规则、裁判、人工、反馈和业务真值作为不同证据层。
  6. 为延迟真值定义 due、as_of、revision、删失与完整率。
  7. 分别量化 frame coverage、weighted acceptance 和 delayed-label completeness。
  8. 对反馈记录可见、响应、有效与裁决过程，避免自选择偷换总体。
  9. 让影子流量在最小化数据、独立资源和 deny-by-default 工具沙箱中运行。
  10. 承认影子仍处理真实数据、消耗算力并可能触及下游，而且不能直接证明用户结果。
  11. 用回放、变更对照和风险允许下的随机灰度逐级加强反事实证据。
  12. 把观测、推断和决策分开，以故障注入验证评测系统本身会失败得足够响亮。

最终需要证明的不是“候选在线分更高”，而是：

在目标总体、选择概率、成熟真值、隐私用途和版本 lineage 都可追溯的条件下，团队知道哪些生产行为被看见、哪些仍未知；影子候选没有把真实数据和下游暴露在未批准风险中；发布动作只使用其证据设计真正支持的结论。
