AI测试-45-模型漂移Prompt漂移和知识漂移怎么监控与归因

发表于 2026-05-16 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:14

线上答案拒答率突然上升，输入 embedding 的分布检验也报警了，能不能判定“模型漂移导致质量下降”？

不能。输入用户群可能变了，标签先验可能变了，业务规则可能重新定义了“正确”，模型别名可能仍指向同一权重，Prompt 可能被 feature flag 改写，知识索引可能漏了新文档，运行区域也可能切换到不同 tokenizer 或缓存配置。更基础的问题是：分布检测只证明某个统计量在当前样本和基线间出现差异，它既没有自动证明用户受到损害，也没有证明哪项变化是根因。

“漂移”在生产讨论里经常被当成一个万能词，结果是所有团队都在看红灯，却没有人知道该回滚模型、修 Prompt、重建索引、调整阈值，还是仅仅更新季节基线。本篇建立一套可执行的分类和归因方法，严格区分：

然后用黄金探针、两样本检测、变点、成熟标签、版本与数据 lineage、配对回放和单组件替换，把“发现变化”逐步提升为“支持损害”“候选原因”“支持根因”和“处置决策”。

一、先给结论：漂移检测是告警系统，不是自动根因分析

一套可靠的漂移治理至少遵守十六条原则：

  1. 先定义随机变量和系统组件。 不说明 X、Y、预测、Prompt、知识和基础设施，“数据漂移”没有可执行含义。
  2. 无标签只能直接观察输入分布与系统行为。 仅凭 P(X) 变化不能断言 P(Y|X) 已变。
  3. covariate shift 是带条件不变假设的情形。 看见输入变化不等于已经证明条件分布稳定。
  4. 一般 label marginal 变化与严格 label shift 分开。 后者要求 P(X|Y) 稳定等额外条件。
  5. concept drift 指目标关系变化。 它可能发生在输入边际几乎不变时，需要成熟标签、专家规则或受控实验补证。
  6. 模型、Prompt、知识和基础设施是四条独立版本轴。 它们可以同时变，也可以在同一公开版本名下悄悄变。
  7. 知识漂移还要拆成现实、语料与索引。 世界事实更新、源文档更新和摄取失败不是同一根因。
  8. 黄金探针负责早发现已知能力回归。 探针通过不代表真实总体没有漂移。
  9. 分布距离必须绑定窗口、基线与样本量。 单一阈值不能跨语言、季节、渠道和版本复用。
  10. 变点回答“何时开始不同”，不回答“为什么”。 时间邻近只用于缩小候选集合。
  11. 所有告警保存原始统计量与 detector 版本。 阈值升级不能删除旧事实。
  12. lineage 先求交，再做可证伪对照。 哪些组件实际服务了这条 task，比发布日历更可信。
  13. 损害与原因分开验证。 成熟标签证明质量/业务后果，组件替换和配对回放支持归因。
  14. 重校准只修映射，不修能力。 概率校准、阈值调整、Prompt 修复、索引重建和重训对应不同机制。
  15. 观测、推断与决策分栏。 “检测到漂移”不能被自动改写为“模型退化”。
  16. 用故障注入测检测器。 既注入有害变化，也注入无害分布变化和纯遥测变更，检查误报与漏报。

Shimodaira 2000 在其预测推断框架中讨论了观察与目标 covariate 分布不同、条件关系保持时的加权。这个术语包含“条件关系不变”的假设。生产监控仅看到 X 变化时，应写 input drift detected，不能直接写 covariate shift confirmed。

3. 哪些 X 值值得监控

  • 原始结构：缺失率、Schema、枚举、数值范围
  • 使用构成：语言、渠道、租户、任务、风险、地区
  • 复杂度：输入 Token、附件数、对话轮数、工具数量
  • 语义表示：意图分类、主题、聚类、embedding
  • 检索上下文：query 长度、过滤、候选数、来源域
  • 安全面：注入模式、编码、异常字符和拒答触发

embedding 漂移会同时受输入和 embedding 模型版本影响。若表示器从 E3 升到 E4，向量分布变化首先是 measurement drift；要在同一表示器下重算可比窗口，或明确重建基线。

五、Label distribution drift 与严格 label shift

1. 一般标签边际变化

当成熟真值可用时，可以观察：

例如欺诈任务中正例比例变化、客服高风险工单占比变化、人工合规失败比例变化。它可能来自真实总体变化、抽样/标签缺失、label 定义更新或业务政策变化。

2. Strict label shift

Lipton、Wang 与 Smola 的 Black Box Shift Estimation 关注：

论文还要求用于估计的混淆矩阵满足可识别条件，例如可逆。它说明一种特定假设下如何利用黑盒预测估计目标标签分布；不能把“线上预测类别比例变了”直接等同于真实 label shift，更不能在 Pr(X|Y) 已变化时无条件应用修正。

3. 预测分布不是标签分布

Pr(Ŷ) 变化可能来自模型/阈值改变，即使 Pr(Y) 不变；Pr(Ŷ) 不变也可能掩盖 Pr(Y) 改变和模型错误相互抵消。标签监控必须指向成熟标签、label 版本和 completeness。

4. 构造反例

某退款分类器输出正例比例从 10% 升到 18%。同期阈值从 0.7 调到 0.5，真实批准资格比例仍为 10%。这是 decision policy/model behavior 变化，不是 label drift。反过来，促销导致真实合格比例升到 18%，模型经重校准后输出也升高，可能是 label marginal 变化而非模型退化。

六、Concept drift：目标关系发生变化

常用操作定义是：

例如法规改变后，同一申请特征对应的资格标签变化；相同错误日志在新版依赖下对应不同根因；用户对相同推荐内容的接受关系因市场变化而改变。

1. 输入分布可以不变

构造反例：请求字段、语言和金额分布几乎不变，但业务在某日调整高风险定义。Pr(X) detector 不报警，黄金政策探针和成熟标签却显示同类输入的目标已改变。这是 concept drift 候选，说明只监控输入会漏报。

2. 性能下降不自动等于 concept drift

模型 artifact、Prompt 或知识索引变坏也会使 Pr(Ŷ|X) 与误差变化，但目标关系 Pr(Y|X) 可能没变。此时是系统组件回归，不应把所有性能下降都命名为 concept drift。

3. 标签定义变更

若 Y 的构造规则从 L7 升到 L8，观测关系变化可能是测量定义改变。要用 bridge sample 同时按 L7/L8 标注，区分“现实概念变化”和“标签仪器变化”。没有 label lineage，concept 结论不可审计。

4. 延迟与局部性

Concept drift 可能只在某个 region、产品或风险层发生，并且标签数周后才成熟。监控需要按 cohort、as_of 和 strata 比较，不能用快速返回的标签代替全量关系。

七、Model drift：组件身份或固定条件下行为发生变化

“模型漂移”有多种行业用法。本文为可归因性采用窄定义：模型 bundle 的物理身份或固定输入/固定其余组件下的行为发生变化。

1. Model bundle

公开别名如 latest 不是物理版本。供应方在别名后更新部署时，若没有可用 deployment ID，至少保存响应指纹、时间和行为探针，并把“供应方内部变更”标为受限可见候选，不能伪造精确权重 lineage。

2. 参数变化也会造成行为漂移

温度、top-p、最大输出、停止条件、seed 支持、上下文截断和工具选择策略改变，即使权重相同，也会改变输出分布。这些应在 model/runtime bundle 中独立记录。

3. 非确定性不是版本变化

同一 bundle 重复生成不同结果属于随机性或运行时不确定性。监控要先建立同版本重复分布，再判断新窗口是否超出基线；不能看到一次文本不同就称模型 drift。

4. 性能随输入变化不是 artifact drift

模型完全没变，新的长尾语言使错误率上升，这是输入构成与能力边界问题。处置可能是路由、扩展数据或换模型，但根因不应写成“模型版本漂移”。

八、Prompt drift：模板之外还有运行时上下文

Prompt 漂移不只是一份文本 diff。完整 PromptBundle 至少包括：

1. 同模板、不同渲染

模板 P17 未变，但变量缺失、转义升级、locale fallback 或 context 排序改变，会使实际输入变化。只保存模板 Git SHA 无法归因，必须保存 render pipeline 和实际结构摘要。

2. 工具 Schema 属于 Prompt 语义

工具名称、描述、必填字段和枚举会影响模型计划。工具后端没变而 Schema 改了，出现调用变化应优先归到 Prompt/tool-contract drift，而不是 model drift。

3. 动态 policy

安全策略、租户指令、记忆摘要和检索证据在运行时拼接。它们既可能属于 Prompt，也可能来自知识或策略服务。lineage 应允许一条实体由多个 activity 生成，不能强迫所有内容只有一个版本号。

4. Prompt drift 不必然有害

P18 可能只修复标点或添加清晰引用，输出风格显著变化而业务验收不变。告警用于触发探针和抽样，不是回滚理由。

九、Knowledge drift：现实、源、摄取和索引四层

1. Reality drift

外部世界事实改变，例如价格、法规、组织结构、库存和产品版本。系统知识即使技术上完全一致也会过时。监控需要 freshness SLA、权威源更新时间与业务事件，不只看索引 checksum。

2. Source corpus drift

源文档新增、修改、删除或权限变更。记录 source ID、revision、effective time、owner 和内容摘要。相同 URL 不代表相同实体版本。

3. Ingestion drift

解析器、清洗、去重、chunk、metadata、embedding 和 ACL 传播变化。源文档没变，派生 chunk 可能变。摄取 pipeline 版本必须进入知识 lineage。

4. Index and serving drift

索引 build、分片、replica、过滤器、rerank、cache 和查询路由变化。正确索引若只有部分副本更新，会产生按 region 或副本的间歇差异。

5. Retrieved evidence drift

最终回答真正使用了哪些 chunk，比“当前索引版本”更接近归因事实。每条 Trace 保存候选、过滤、分数、rerank 和最终证据 ID；内容本身按隐私与授权保留引用或摘要。

6. 构造反例

答案开始引用旧政策。模型和 Prompt 均未变，源站已更新，但摄取任务因 ACL 403 未抓到新版本。正确分类是 source reality 已变、ingestion/index 未跟随；若只写“知识漂移”，仍不足以决定修源、修抓取还是重建索引。

十、Infrastructure drift：系统行为可能在代码不变时改变

基础设施 bundle 包括：

  • container image、运行时、库、编译器和 kernel
  • GPU/CPU 类型、驱动、精度、并行与批处理配置
  • region、zone、网络、DNS 和服务发现
  • cache 版本、TTL、key、容量与命中策略
  • 队列、限流、重试、超时和熔断
  • 数据库、向量库、对象存储与外部依赖版本
  • feature/config service snapshot
  • telemetry schema、采样、时钟和聚合版本

1. 可见质量变化

上下文在网关超时后被截断、缓存返回旧 Prompt、区域副本索引滞后、tokenizer 库不同或重试改变工具顺序，都可能改变答案。基础设施不是只影响延迟。

2. 纯观测漂移

埋点字段重命名、采样率改变、时钟偏差或 dashboard 查询升级，会让指标跳变而用户行为不变。监控系统自身版本必须进入 lineage，并用独立计数与黄金遥测事件校验。

3. 构造反例

P95 延迟与拒答率同时升高，模型版本没变。调查发现新 region 的网关把 64KB 上下文截成 32KB，长请求缺少政策段落。这是 infrastructure drift 导致固定模型输入变化；不能只按错误结果叫 model drift。

十二、分层架构：检测、损害、归因和处置四层分开

1. Observation Plane

采集生产输入的最小化特征、输出行为、黄金探针、成熟标签、业务结果、组件 bundle 和运行 Trace。原始内容受权限保护，统计 sketch 也记录生成版本。

2. Baseline Registry

基线不是“上个月所有数据”。它包含目标总体、窗口、季节/渠道、模型与组件版本、样本量、feature schema、表示器、label as_of 和批准用途。固定 release baseline 与滚动 recent baseline 同时存在。

3. Detector Plane

确定性契约、单变量/多变量两样本、输出行为、黄金探针和变点检测各自生成 typed alert。Detector 不直接写 root cause，只写统计量、阈值、样本、窗口、分层、版本和已知限制。

4. Outcome Plane

延迟标签与业务结果用于判断是否有性能、校准、安全或业务损害。它消费上一篇的 sampling frame 和 completeness；标签不完整时产生 unknown，而不是零损害。

5. Lineage Graph

将 task 使用的输入、模型、Prompt、知识、工具、基础设施和测量版本表示为实体与活动。W3C PROV 的 entity/activity/agent 与 derivation 思路可以作为通用骨架，具体字段由系统扩展。

6. Attribution Workbench

按告警时间、受影响 strata 和 lineage diff 生成候选集合，再运行固定输入配对回放、单组件替换、2×2 组合和故障复现。它保存每个 case 的成对结果、有效对数、方向性改善/恶化/平局、效应与不确定性，默认结论是 inconclusive。只有预注册门槛和机制条件同时满足时才输出“支持原因”的干预证据，不输出不可解释的“根因分数”，也不把没有改善自动写成反驳。

7. Decision and Remediation

根据安全硬门、损害、证据充分性和风险选择观察、加密标签、重校准、修组件、回滚、重建索引或重训。每个处置生成新版本并进入再验证。

十三、数据模型：窗口摘要不能替代单条 lineage

1. ComponentBundle

Bundle 是不可变快照。配置平台上的“当前值”只能用于创建新 bundle，不能回填历史。

2. ServedTrace

同一发布可能因路由、地区和 flag 实际服务多个 bundle。归因以 ServedTrace 为准，不以发布公告为准。

3. ObservationWindow

若窗口混合多个 bundle，应按 bundle 分层或显式保留 mix。直接与单一基线比较会把路由构成变化误认为行为 drift。

4. DistributionSketch

Sketch 的 bin、top-k、截断和表示器固定才可比较。动态分桶若未保存边界，会制造或隐藏差异。

5. ProbeRun

黄金探针既可针对输出，也可针对关系：权限更低的用户不能看到更多文档，加入无关文本不应改变结构字段，工具重试不能重复写入。

6. DriftAlert

evidence_level 初始必须是 alert_only。后续 attribution case 引用它，而不是修改成 root cause。

7. AttributionCase

8. CalibrationArtifact

校准器不是一个无版本常数。基础模型、总体或 label 定义变化后，它可能失效。

十四、Lineage：归因要回答“这条任务实际用了什么”

1. 版本字符串不够

prompt=v18 可能被不同 locale override；index=latest 可能每个 region 指向不同 build；model=m7 可能是路由策略选择的别名。使用内容/配置 digest 与部署 ID，把展示名当标签而不是身份。

2. 数据派生关系

源文档经解析、清洗、chunk、embedding 和 index build 形成可检索实体。每一步记录 used 与 generated，才能在错误 chunk 上溯到源 revision 和 parser，也能在删除时找到派生副本。

3. 时间语义

配置的提交时间、发布开始、某实例加载、请求实际服务和监控发现是不同时间。候选原因必须与 served_at 重叠。只看 Git merge 时间会把尚未生效或已回滚的版本纳入。

4. Lineage coverage

归因前先检查 coverage。若异常层一半 task 缺 index snapshot，最诚实结论是 knowledge attribution 受限，而不是默认它们用了当前 index。

5. 变更事件目录

模型、Prompt、知识、工具、infra、label、detector 和 UI 每次变化都写统一 ChangeEvent：生效窗、owner、审批、影响范围、回滚和 digest diff。外部政策、节日、流量渠道与供应商事件也可作为 external event，和内部变更区分。

十五、基线设计：固定、滚动、季节和反事实基线并存

1. 固定发布基线

以批准 release 的稳定窗口为参照，适合判断长期偏离。它会随业务增长越来越旧，因此不能单独承担季节变化解释。

2. 滚动基线

比较最近窗口与此前若干窗口，适合早期变点，却可能逐步追随慢漂移，使长期变化“煮熟”。固定与滚动同时看。

3. 季节基线

工作日/周末、小时、节日、账期和活动流量不同。可以比较同星期同小时或经过批准的季节模型，但不要为了消除告警把真实新风险全当季节性。

4. 分层基线

全站 mix 改变时，总体分布会变；层内可能稳定。反之总体稳定也可能由两个 strata 反向变化抵消。总量、关键层和 bundle mix 三层都要报告。

5. 配对反事实基线

对黄金探针或影子样本，在相同输入上运行旧、新 bundle，控制 X。存储单位必须是配对 case，不是两个可能样本量不同的失败总数；任一 arm 缺失的 case 计入 incomplete_pair_count，不能单边进入效应分母。它比时间窗口更适合组件回归，但仍无法复现用户互动和动态外部世界。

6. 基线再认证

新业务成为主要流量时，旧基线可能失去决策意义。重建基线必须先通过质量与风险验收，并保留旧基线重叠报告。不能因为长期红灯就直接把当前异常设为新正常。

十六、检测指标：先从数据契约与缺失开始

最便宜且最可解释的漂移检测通常不是 embedding，而是 Schema 和计数。

1. 结构漂移

  • 必填字段缺失、类型变化、枚举新值
  • 数值越界、单位变化、时间格式和时区变化
  • JSON 层级、数组长度、附件类型和编码变化
  • 工具参数、检索 metadata 和标签字段版本变化

2. 缺失率

分母是该字段按契约应存在的单位。可选字段缺失不能与解析失败混在一起。

3. 唯一性与重复

event/task 重复会改变频率分布。先检查主键冲突、retry mix、消息重放和机器人，再运行复杂 detector。错误数据上的精确检验只会稳定地产生错误告警。

4. Coverage 与 lineage

每个窗口同时报告 sampling frame coverage、label completeness、lineage coverage 和 detector feature coverage。任一不足时，告警状态应包含 measurement_degraded。

5. 观测管道黄金事件

持续注入不含真实用户数据的确定性事件，验证每个 region、Schema 和聚合查询会得到预期计数。黄金事件失败说明测量系统 drift；它不能证明生产质量正常。

十七、单变量分布：距离、检验与业务阈值回答不同问题

1. 类别变量的 Total Variation

对固定类别集合，经验分布 p 与 q 的总变差距离：

它位于 0 到 1，便于解释“需要搬移多少概率质量才能匹配”，但经验值受样本量、top-k 合并和未知类别处理影响。必须把 OTHER、缺失和新枚举单列。

2. Jensen–Shannon divergence

它对称且有限，但对数底、平滑和零频处理会改变数值。不同实现的 0.1 不一定同义。阈值要固定 detector version，并用历史无变化/已知变化窗口校准。

3. 数值变量

输入长度、延迟和分数可监控分位数、尾部超限率、固定业务桶与经验 CDF 差异。Kolmogorov–Smirnov 类统计量关注最大 CDF 距离；它对某些位置差异敏感，但不能自动说明业务重要性。大量样本会让极小差异显著，少量长尾又可能没有足够检验力。

4. 分桶稳定性

基线与当前使用同一 bin edges。按当前窗口重新等频分桶会把变化吸收进边界。极端值要有 overflow 桶，截断率单列；否则 clipping 可能让尾部风险消失。

5. 距离与假设检验

距离回答“经验分布差多远”，检验回答“在特定零假设和采样条件下，这种差异是否难由随机波动解释”。业务门还要回答“是否足以改变动作”。三者应分别保存：statistic、p-value/校准概率（若使用）、effect threshold 和 action threshold。

十八、多变量与高维检测：表示器本身是测量组件

逐字段稳定不代表联合关系稳定。例如语言和风险各自占比不变，但高风险从中文转到英文。需要联合 strata、域分类器或多变量两样本方法。

1. MMD

Gretton 等 2012 提出的 Maximum Mean Discrepancy 在 RKHS 中比较两个分布的函数期望差，并给出两样本检验构造。核、带宽、样本量和估计方式会影响检测能力。论文在其研究问题和数据上验证方法，不意味着一个默认 RBF 核可以可靠监控所有 LLM embedding。

2. Domain classifier

将基线标为 0、当前标为 1，训练分类器区分来源；可区分说明窗口含有可学习差异。要用独立验证、固定特征、时间泄漏控制和类别平衡。高准确率不说明质量损害，特征重要性也不自动是因果根因。

3. Failing Loudly 的正确引用边界

Rabanser、Günnemann 与 Lipton 的《Failing Loudly》在论文所探索的数据集、协变量/标签扰动、表示和方法中，比较了多种 dataset shift 检测方案；其摘要报告使用预训练分类器降维的两样本方法在所探索 shift 上表现最好，并讨论域分类器用于定性表征和判断 harmfulness。这个经验结论不能泛化为“预训练 embedding + 某检验永远最佳”，也不能证明生产告警一定有害。

4. 表示 drift

文本 embedding 压缩了原始输入，可能忽略结构化金额、权限和少数语言，也可能放大表示模型自身变化。保存 representation_version，用固定旧表示器回算 bridge window；同时保留可解释的原始特征和样本 exemplar。

5. Exemplar 只用于理解

选择最能区分窗口的样本帮助人工发现新意图、乱码或渠道变化，但 exemplar 是被 detector 挑出的极端，不代表频率。报告它在总体中的权重和选择规则，防止几个醒目案例替代统计结论。

6. 隐私边界

embedding 和域分类特征仍可能编码敏感信息。分布 sketch、exemplar 和训练域分类器都是数据处理，应遵守用途、访问、保留与删除。不能把“不保存原文”误写成匿名。

十九、输出与行为漂移：不要只盯输入

1. 输出结构

JSON 合法率、字段缺失、引用数、工具调用数、拒答、截断、语言、长度和安全规则可全量监控。它们通常比语义分数更快、更可解释。

2. 决策分布

分类、路由和 Agent 计划可以比较 Pr(Ŷ)、置信区间、阈值距离和动作类型。预测分布变化可能来自输入 mix、模型、Prompt、知识或决策阈值，不能直接归因。

3. 语义输出

主题、风格、引用支持和裁判分数都依赖 evaluator。保存 evaluator model、Prompt、量规、随机参数和校准误差。Evaluator 升级时建立 bridge window；否则 evaluator drift 会伪装成系统 drift。

4. 工具行为

监控计划与实际执行分开：候选可能计划更多写操作，但 policy 阻断；后端也可能拒绝合法计划。指标包括计划率、授权率、Schema 失败、重试、幂等冲突、人工确认和副作用完成。

5. 稳定输入探针

若生产输入 mix 变化，输出率也随之变化。黄金探针在固定输入下观察输出关系，可帮助区分 input mix 与组件行为，但覆盖仅限探针集合。

二十、黄金探针：固定风险能力的早期哨兵

黄金探针是小而高价值、可重复运行的输入与断言集合。它不必要求文本逐字一致，更重要的是固定不可违反的关系。

1. 探针类型

  • 契约探针：Schema、字段、引用和工具参数
  • 政策探针：拒绝越权、敏感操作必须确认
  • 知识探针：已知生效/过期文档、删除和 ACL
  • 变形探针：无关措辞变化不改变结构结论
  • 跨版本探针：同一 case 在当前/候选 bundle 配对
  • 基础设施探针：跨 region、replica、冷/热 cache 一致性
  • 观测探针：确定性事件应完整进入指标

2. 断言关系

权限关系要谨慎定义：更高权限用户可看到更多文档，不代表最终答案必然更长。探针应断言安全属性，而不是脆弱文本表面。

3. 随机模型的重复

对于非确定输出，运行固定次数并保存每次结果。可以要求严重失败零容忍，或对非关键评分设置分布门。重复属于同一 probe cluster，不能把 20 次运行当 20 个独立业务案例。

4. 探针泄漏

长期固定探针可能被开发者或模型优化记住。将其定位为回归哨兵，另保留受控 holdout、随机生产样本和轮换探针。探针通过只说明已知场景未检测到回归。

5. 探针所有者

每个探针记录风险、来源、适用 bundle、owner、过期条件和失败动作。政策更新后旧期望可能失效，必须通过 label/policy 版本迁移，而不是静默改答案。

二十一、变点检测：定位时间，不替代分布和因果解释

1. 固定窗口的问题

一小时窗口响应快但噪声大，一周窗口稳定但发现慢。不同流量 strata 需要不同最小样本与最大等待时间。窗口只有在 coverage 和 component mix 可比时才有意义。

2. CUSUM 思路

3. Page–Hinkley 类实现

4. 自适应窗口

5. 变点与发布事件

检测到 10:20 变点，Prompt 在 10:05 发布，只能说明时间相邻。模型路由 mix、索引 replica、流量渠道和观测 Schema 也可能在附近变化。用 ServedTrace 按 bundle 分层，并通过单组件回放验证。

6. 缓慢漂移

阈值型变点可能漏掉小幅持续变化。固定 release baseline、滚动 slope、累计偏差和周期性成熟标签复核共同使用。滚动基线不能逐步吞掉长期退化。

二十二、阈值与告警工程：检测器也要有 SLO

1. 训练阈值的窗口

选取经确认稳定、覆盖完整且包含正常季节变化的历史窗口，计算 detector 在无处置期间的自然波动。再用已知变更和构造注入评估检测延迟与漏报。不能用当前异常窗口调到不报警。

2. 双门设计

两者同时满足再创建普通 drift alert；安全硬规则可独立触发。样本极大时 practical gate 防止微小变化淹没团队，样本不足时 evidence gate 阻止伪稳定。

3. 多重比较

数百特征 × strata × 窗口持续检验会产生大量偶然告警。可以控制 detector family 的错误预算、分层优先级、合并相关告警并要求持续窗口，但不能通过只保留“看起来合理”的告警事后选择。

4. 告警去重

一个渠道切流会同时改变语言、长度、意图和输出。关联同一 change point、strata 与 lineage 的告警聚合成 incident，底层 alert 仍保留。聚合用于降低认知负担，不等于已经找到共同根因。

5. 冷却与迟滞

触发阈值和恢复阈值分开，避免边界抖动；恢复还需最小稳定窗口和 coverage。回滚后指标恢复可支持因果假设，但若流量同时恢复，仍需对照。

6. Detector SLO

  • no-change 注入下误报率
  • 已知幅度注入的检出率与 detection delay
  • feature/lineage coverage
  • stale baseline 比例
  • 告警到 owner 确认和处置时间
  • 归因后被反驳的候选比例

这些 SLO 只评价监控系统，不代表 AI 业务质量。

二十三、漂移告警为什么不是损害证明

1. 输入变了，模型仍可正确

模型可能对新 mix 覆盖良好，或变化发生在无关字段。只有成熟标签、风险断言或用户结果能支持损害。

2. 统计显著，业务影响很小

大样本会检测到极小差异。需要最小有意义变化、分层风险和结果指标。

3. 性能指标变了，测量系统可能先变

label definition、反馈 UI、裁判、采样、coverage 或 completeness 变化会改变观察值。先验证 measurement lineage。

4. 代理指标退化，最终结果可能不变

输出变长、拒答增加或裁判分下降可能由更严格安全策略造成，同时减少高风险错误。多目标门禁不能把一个代理当总损害。

5. 损害发生，分布告警也可能不响

局部 concept drift、权限漏洞或少数高风险场景可能不改变总体 P(X)。黄金探针、全量硬规则、事故渠道和成熟标签是必要补充。

二十四、归因流程：从时间共现到可证伪证据

1. 固定异常签名

先写清影响窗口、strata、输出/结果、severity、coverage 和 detector。不要在调查中不断改变“异常是什么”，否则每个变更都能被解释成相关。

2. 生成 change inventory

查询异常窗口前后所有 model、Prompt、knowledge、tool、infra、label、detector 和 traffic change。按 ServedTrace 计算受影响 task 实际使用比例，不只看部署状态。

3. 求影响面交集

若只有 region B 异常，而 Prompt P18 全局启用、index K42 仅 region B 缺副本，则 K42/infra 候选优先。优先级是调查顺序，不是根因概率。

4. 保留未变化对照

同一时间的未受影响 strata、继续使用旧 bundle 的实例、旧 region 和相同输入回放提供反例。只收集支持假设的证据会制造确认偏差。

5. 单组件替换

6. 复现出现与消失

支持原因至少需要：只替换候选组件；达到预注册的最小有效配对数；净改善效应及其不确定性通过预注册门槛；并且异常能随候选变化出现/消失，或独立机制探针通过。影响机制还要与生产 strata 一致，替代解释经测试被削弱。高风险事故还要验证修复不引入新失败。这是受限实验条件下的干预证据，不是对生产世界的因果证明。

7. 成熟结果验证损害

配对回放可以提供输出机制差异的干预证据，不能直接证明真实用户结果，也不能排除未快照依赖、回放选择偏差或组件交互。连接概率样本、完整延迟标签或受控实验，限定结论总体。

8. 记录反驳

“没有改善”默认只是 inconclusive，不是 cause_refuted。0 vs 0 可能表示候选无影响，也可能表示回放集根本没触发异常；样本不足、配对缺失或检验功效不足时同样不能反驳。只有事先注册了反驳规则、达到该规则的 power 和有效对数，并观测到规定的反驳模式，才能记为 refuted。本文代码采取更保守的策略：所有未达到支持门槛的结果一律返回 inconclusive，继续查知识、infra 与替代假设。

二十五、版本与数据 Lineage 的归因查询

一个实用查询不是“昨天发布了什么”，而是：

1. Bundle odds 只用于筛选

可以比较异常组与正常组中某 bundle 的暴露比例，得到关联强度。但输入路由、租户和风险会同时影响 bundle 与错误，存在混杂。这个统计量用于挑选回放候选，不直接写根因。

2. Trace join 完整性

如果错误 task 更容易丢 Trace，完整记录中的 bundle 分布会偏。先报告 lineage coverage，并对缺失原因分层。无法归因的严重事件进入保守处置，而不是从事故中删除。

3. 时间对齐

分布窗口使用事件时间，变更使用实际加载/服务时间，标签使用 as_of。跨机器时钟漂移要监控。不要把数据仓库入库时间当生产生效时间。

4. 数据删除与可审计性

隐私删除后可保留经批准的不可逆版本计数和决策摘要，但不能伪称仍能逐条回放。AttributionCase 标记证据已删除和可复核范围。

二十六、延迟标签下的 Concept 与损害检测

1. 快慢双轨

快轨可暂停高风险发布，慢轨负责确认影响和更新长期策略。快轨正常不能取消慢轨，慢轨未成熟也不能让安全硬门继续扩大。

2. Cohort 固定

按任务发生时间固定 cohort，每日随 as_of 更新 not_due、due_missing、observed 和 final。若负面标签更慢，早期 error rate 必须标 provisional，并显示极端假设上下界。

3. 条件关系分层

在可解释的离散 strata 中比较成熟 Pr(Y|X_group)，例如语言 × 风险 ×任务。连续高维 X 无法靠简单分桶完整证明 concept drift，结果应写“这些已测 strata 中的条件关系证据”。

4. 模型性能与目标关系同时看

比较 Pr(Y|X_group) 判断目标关系，比较 Pr(Ŷ≠Y|X_group) 判断系统误差。前者变而后者不变，模型可能适应；后者变而前者稳定，优先查组件回归或输入细节。

5. 标签版本 bridge

政策从 L7 到 L8 时，用同一批样本双标，得到 label transition matrix。若变化主要来自定义，基线和校准器要迁移；若同一定义下关系仍变，再讨论现实 concept drift。

二十七、Label Shift 的检测与修正边界

1. 先验证适用假设

Black Box Shift Estimation 依赖 source 上预测器的混淆矩阵以及 Pr_t(X|Y)=Pr_0(X|Y) 等条件。生产中渠道、文案和采集设备变化常让条件输入也变。应按 strata 检查、做敏感性分析，并在小批成熟目标标签上验证估计。

2. 混淆矩阵病态

类别几乎不可区分时，混淆矩阵接近不可逆，小噪声会放大估计。此时应报告不可识别或高不确定性，不要强行得到新的 prior。

3. 预测器不必校准不等于什么都不需要

Lipton 等论文指出 BBSE 可使用有偏、不准确或未校准的黑盒预测器，但要求其混淆矩阵满足可逆等条件。这不表示任意生产模型、任意标签缺失和任意 shift 下都可靠。

4. 修正后仍要验收

按估计 prior 调整决策或概率后，在独立、成熟目标标签上验证 discrimination、calibration、错误成本和分层风险。修正 label shift 不会修 Prompt、知识或 concept drift。

二十八、重校准：修概率映射，不掩盖能力变化

1. 什么叫校准

对二分类概率，理想含义是预测约 0.8 的样本中长期约 80% 为正。可观察 Brier score：

它同时受校准和判别等因素影响。可靠性图和分桶 ECE 依赖 bin 设计，不能单凭一个 ECE 宣布已校准。

2. 何时重校准

基础排序能力仍满足要求、label 定义稳定、目标总体有足够成熟标签，但概率到实际频率的映射偏移时，可以拟合新 calibration artifact。来源、窗口、strata、方法、参数和过期条件必须版本化。

3. 何时不能只重校准

  • 安全探针和任务能力失败
  • concept drift 改变了可用特征与目标关系
  • Prompt 漏掉约束、知识缺失或工具越权
  • 输入出现训练范围外的新语义
  • 基础模型区分能力明显下降

这些问题需要修组件、重训、重建知识或限制使用。调整阈值让 dashboard 变绿只会隐藏风险。

4. Temperature scaling 的引用边界

Guo 等 2017 在其论文使用的现代神经网络、图像和文档分类数据集上比较后处理校准方法，并报告单参数 temperature scaling 在多数所测数据集上有效。它不能直接外推到生成式回答质量、所有 LLM 置信、分布外数据或任意分层生产总体。

5. 校准数据隔离

拟合、选择方法和最终验证使用独立数据或适当交叉验证。不能在同一小批标签上不断调温度、阈值和分层后，再用它证明改善。校准 artifact 随 model/Prompt/label/population 变化设置失效触发。

6. 阈值重设不是概率校准

根据新成本选择 decision threshold 只改变动作边界，不一定让概率更可信。报告中分开 calibration_method 与 decision_policy_version。

二十九、自动化策略：检测快、归因稳、处置可逆

1. 请求级契约

同步检查 Schema、版本缺失、权限、索引 snapshot、工具副作用和严重安全规则。失败形成 typed event，不在请求路径运行昂贵全局检验。

2. 流式窗口

按事件时间维护固定 bins、计数、缺失、bundle mix 和关键输出。达到最小样本或最大等待时间后运行 detector。迟到事件生成 window revision，历史 alert 保持原 as_of。

3. 黄金探针调度

每次 bundle change 前后、每个 region/replica、冷启动和固定周期执行。探针失败与实际 served bundle 绑定，避免测试控制面版本而生产实例未加载。

4. 慢标签回填

每日更新 label completeness、error、calibration 和条件 strata。成熟度不足时维持 damage_unknown；达到门槛自动打开 attribution 补证任务，而不是直接宣布 root cause。

5. ChangeEvent 触发

模型、Prompt、知识、工具、infra、label、detector 或 traffic policy 变化，自动建立 bridge window、提高相关 strata 抽样并运行组件探针。多组件同发时标记 interaction risk。

6. Alert correlation

按 change point、strata、bundle 和 Trace 合并告警，生成一个 AttributionCase。系统列出候选 diff 和未变化对照，调查人选择回放矩阵。候选排名可辅助优先级，但不写成概率根因。

7. 自动处置边界

  • 安全硬门、越权写入、关键探针失败：可自动暂停/回滚到批准 bundle
  • input drift 且损害未知：加密抽样、限制扩大、请求标签
  • 校准漂移且成熟标签充分：发布新 calibration artifact，经独立门禁
  • 已支持的 Prompt/knowledge/infra 根因：修复该组件并配对再测
  • 广泛 concept/能力变化：限制适用范围、重训或重新设计

自动动作记录幂等 key、owner、回滚和过期。告警服务故障时不能触发无限回滚循环。

三十一、多证据门禁：检测、损害、归因、处置逐级升级

建议把门禁状态设计成证据状态机，而不是一个总 drift score。

Gate 0：Measurement valid

检查 sampling frame coverage、feature coverage、lineage coverage、label completeness、时钟、Schema 和 detector 版本。测量退化时可以因风险暂停发布，但不能输出质量下降幅度。

Gate 1：Drift alert

契约、两样本、变点或黄金探针越界。记录类型、statistic、effect、样本量和 strata。动作通常是关联告警、加密抽样或触发回放。

Gate 2：Damage supported

安全硬事实、成熟质量标签、校准或业务结果支持损害。严重安全探针可直接触发阻断；普通质量需要达到预定完整性与实际意义门。

Gate 3：Cause candidate

ServedTrace 显示某组件或外部事件与影响面、时间重叠。它只确定调查候选。多个组件共同发布时必须保留交互候选。

Gate 4：Cause supported

固定其他条件的回放、组件替换、跨实例对照或可逆变更支持异常随候选出现/消失，替代解释被削弱。结论限定在重放 case 与实验总体。

Gate 5：Remediation verified

修复在已知事故、随机 holdout、关键 strata、容量与安全门上通过；上线后新 bundle 继续观察成熟结果。不能因为 detector 恢复就删除原始事件。

1. 状态迁移必须可逆

新证据可能反驳旧推断。cause_candidate 可以变为 refuted，damage_unknown 可以变为 supported。状态迁移新增 revision 与理由，不覆盖旧报告。

2. 安全动作和知识结论分开

证据不足时仍可保守回滚，这是风险决策；事故报告应写“因关键探针失败按预案回滚，根因调查中”，不能写“已证明模型根因”。

三十二、故障注入：既注入有害漂移，也注入无害变化

只注入明显性能下降会把 detector 训练成“见变化就报灾难”。测试矩阵必须包含 true positive、true negative、measurement failure 和 attribution confounder。

1. 无害 Input drift

改变语言或任务 mix，但为每层保持相同条件质量。预期：input_distribution alert，damage 未检测或未知；系统增加抽样，不自动回滚。这个注入检查告警和损害是否解耦。

2. 无 Input alert 的 Concept drift

保持 X 构成不变，改变构造 label rule，让相同 strata 的 Pr(Y|X_group) 变化。预期：输入 detector 可不响，政策黄金探针和成熟标签报警。检查团队是否错误依赖 embedding 单通道。

3. Label marginal 变化但条件稳定

改变各 strata 占比，使总体 Pr(Y) 变化但层内关系稳定。预期：label marginal 与 input mix 告警，concept evidence 不应由粗粒度实现误触发。若尝试 label-shift 修正，先验证条件假设。

4. Model artifact 替换

在一部分实例将权重/量化 digest 改为 M8，公开别名仍为 stable。预期：ServedTrace 能区分实例，model component alert 只覆盖 M8 task；按别名聚合的旧监控应在测试中失败。

5. Prompt 动态注入

模板 Git SHA 不变，只修改 locale override 或 feature flag 拼接的安全 policy。预期：render pipeline/digest 变化，黄金探针定位 Prompt/context；若系统只存模板版本，应产生 lineage coverage 告警。

6. Knowledge 源与索引错位

发布 source revision S12，但故意让一个 replica 保持 index K11。预期：source freshness 看似正常，retrieved evidence 与 replica lineage 暴露 K11；跨 replica 探针失败，重建后恢复。

7. Infrastructure 截断

把一个 region 的网关上下文上限降低，模型、Prompt、knowledge digest 不变。预期：infra change、输入 Token/截断、输出规则和 region 探针关联；不能产生 model component drift。

8. Telemetry Schema 变化

将拒答字段从布尔改为枚举但 dashboard 仍按旧值过滤。预期：黄金遥测事件和 measurement component 先报警，用户探针不变；质量告警应标 measurement invalid。

9. 选择性标签延迟

让高风险失败标签比成功慢五天。预期：早期 performance 标 provisional，completeness 分层门阻止“质量改善”；标签到齐后生成新 as_of revision。

10. 基线污染

在异常期间自动滚动更新 baseline。预期：固定 release baseline 仍报警，滚动 detector 可能逐步恢复；baseline registry 禁止未审批窗口成为新正常。

11. 多组件同发

同时改 P18 与 K42，使只有组合失败。预期：单独回放都通过，2×2 的组合格失败；归因记录 interaction，不把责任随机分配给先被检查的组件。

12. Detector 自身变更

升级 embedding 表示器或分桶边界。预期：新旧 detector 在 bridge window 双跑，旧 alert 不被新统计量重算覆盖；没有 bridge 时状态为 incomparable。

每个注入保存 ground-truth injection manifest。它只作为监控测试真值，不应与生产未知根因混合。成功标准包括检测延迟、类型正确、错误动作未发生、lineage 完整和恢复对账。

三十三、看板与告警：不要做一张“漂移热力图”就结束

1. 证据健康层

  • target/frame/feature/lineage coverage
  • label completeness、label latency、删失和 as_of
  • detector/representation/telemetry 版本
  • baseline age、bundle mix、unknown version
  • 样本量、权重与关键 strata

2. 分布层

  • Schema 与 missingness
  • 类别 TV/JS、数值 quantile/CDF、联合 detector
  • effect size、阈值、持续窗口和 change point
  • exemplar 的选择权重与受控内容引用

3. 行为与探针层

  • 输出结构、拒答、工具计划/执行、引用和截断
  • probe suite pass、重复分布、region/replica 差异
  • evaluator 版本与不可裁决率
  • 延迟、错误、缓存、资源和依赖

4. 结果层

  • label marginal 与 label definition
  • 分层 error、Brier、可靠性和业务后置条件
  • provisional/final 迁移、实际意义和不确定性
  • 安全硬门与受影响单位数

5. 归因层

  • alert cluster、异常签名和估计变点
  • candidate ChangeEvent、实际暴露 task 和未变化对照
  • replay 矩阵、支持/反驳结果和证据限制
  • damage/cause/remediation 独立状态

6. 决策层

  • observe、sample、hold、rollback、recalibrate、rebuild、retrain
  • owner、截止、回滚目标、残余风险和下一证据成熟时间
  • action 使用的 snapshot 与幂等状态
  • 例外、审批和过期

单值总分会掩盖“输入显著变但无损害”“无输入告警但安全探针失败”等关键组合。typed panel 比红黄绿总分更可执行。

三十四、完整事故案例一：被误判为 Prompt 漂移的知识副本滞后

以下数字和版本均为构造示例。

1. 背景

合规问答在周二发布 Prompt P22，目标是让引用更简洁。同日上午政策源从 S104 更新到 S105，知识流水线生成 index K105。下午 14:20，region B 的“引用过期政策”告警上升，embedding 两样本检测也报告输入语义 mix 变化。

2. 错误结论

发布日历显示 P22 在 14:00 全量，因此群聊直接写“P22 导致幻觉”。这只是一项时间共现；输入 mix、知识和 region 也在变化。

3. 观测

  • P22 在 region A/B 都启用，模板与 rendered digest 一致
  • region A 错误率稳定，region B 在 14:20 后上升
  • 模型 M11、tool schema 和 runtime image 相同
  • source registry 显示 S105，控制面显示 K105 已发布
  • ServedTrace 中 region A 检索 K105，region B 有 43% task 实际命中 K104 replica
  • 错误回答引用的 evidence ID 全来自 K104

这些事实支持 knowledge/index serving 候选，并削弱“P22 单独造成”的假设，但还要复现。

4. 2×2 配对回放

团队按事先登记的回放规则固定 60 个受影响输入、模型 M11、infra I7 和工具响应，对每个 case 运行：P21+K104、P22+K104、P21+K105、P22+K105。规则预注册最小 50 个有效对、最小净改善效应及区间下界，并要求故障出现/消失或跨 replica 机制探针成立。有效对、缺失对、改善、恶化和平局分别报告，不比较两个非配对失败总数。两个 K104 组合都复现旧引用，两个 K105 组合都通过；P21/P22 只改变表述长度。跨 replica 探针也只在 K104 失败。这些结果是固定回放环境中的干预证据，不是生产因果证明。

5. 根因与机制

进一步检查 index deploy activity：region B 一个 replica 因磁盘水位拒绝加载 K105，但控制面将 rollout aggregate 错误标为 complete，路由仍向其发送流量。结合逐 task served digest、单组件干预和跨 replica 探针，证据支持知识索引部署/基础设施健康判定缺陷为原因候选。P22 在这组回放中未获支持；因没有为 P22 预注册具有足够 power 的反驳规则，它的状态保守记为 inconclusive，不写成已被因果反驳。

6. 决策与修复

立即摘除 K104 replica，恢复后黄金政策探针和成熟人工标签回到基线。修复 rollout 必须以每 replica loaded digest 为完成条件，查询 Trace 增加 served_index_digest 硬要求，并加入旧政策删除探针。P22 继续小流量观察，因为它的质量问题需要独立评估。

7. 经验边界

回放证明这些 case 的旧引用由 K104 触发，region 恢复加强了生产机制证据。它不证明所有知识错误都来自 replica，也不说明 P22 对其他任务没有影响。

三十五、完整事故案例二：模型未变，基础设施截断制造拒答漂移

1. 现象

代码审核助手拒答率从 4% 升到 11%，输出长度下降，模型控制台仍显示 M9。input embedding 总体无显著变化，团队最初怀疑供应方悄悄更新模型。

2. 分层观测

按 region 分层后，变化只在新扩容的 region C；短请求稳定，输入超过 40k Token 的 task 明显异常。ServedTrace 的模型 deployment ID、Prompt P31、knowledge K8 相同，但 region C 的 gateway_config_digest 不同，context_truncated=true 从 0.2% 升到 37%。

3. 可证伪回放

固定同一长输入，在 region A/I12 与 region C/I13 回放；I13 丢失末尾开发者政策段，模型触发保守拒答。将 I13 上限恢复后差异消失；把 M9 换成另一个模型但继续截断，同样失败。

4. 根因与处置

扩容模板沿用了旧网关 32k 上限，是 infrastructure/config drift。模型供应方内部是否还有不可见变化仍不能完全排除，但它不是解释当前 region/长度交互所必需的候选。团队回滚网关配置、为 bundle 增加 effective context limit，并添加跨 region 长上下文探针。

5. 为什么总体 embedding 没报警

原始文本分布没有明显改变，变化发生在系统实际交给模型的截断表示。以后同时监控 received input 和 effective model input。这个事故是“输入经过基础设施后的 serving drift”，说明随机变量边界也必须进入 Trace。

三十六、完整发布决策案例：只重校准，暂不重训

以下仍为构造示例，展示何时可以选择校准 artifact。

1. 背景

风险分类器 M12 连续两周 AUC/排序型业务指标在成熟标签上稳定，关键黄金探针通过，但预测 0.7–0.9 区间的实际正例率降低，Brier score 变差。同期新渠道上线，label marginal 和输入渠道 mix 变化。

2. 证据检查

  • frame coverage 99%，delayed-label completeness 95%
  • M12 artifact、Prompt、知识与 infra 未变
  • 在固定渠道 strata 内，排序能力和主要 Pr(Y|X_group) 证据基本稳定
  • 新渠道占比提升，原 calibration artifact C4 的训练总体不含该渠道
  • strict label shift 的 Pr(X|Y) 稳定条件无法完全确认，因此团队不直接套 BBSE 修正
  • 安全硬门、错误成本与极端风险层没有新增失败

观测支持“当前总体的概率映射失准”，不支持“模型能力已经全面退化”。

3. 校准设计

团队按渠道与风险预先定义 calibration population，用已成熟的一段数据拟合候选 C5；另留后续 cohort 做独立验证。比较 reliability、Brier、关键阈值错误成本和分层稳定性。决策阈值 D7 与 calibration C5 分别版本化。

4. 发布门

C5 只能与 M12、label L9、指定渠道总体绑定；若 model、Prompt、label definition 或渠道 mix 越出认证范围即过期。影子先验证概率字段与决策 API 兼容，再做小比例稳定灰度，业务动作仍受安全硬门。

5. 决策

独立验证满足预设门后发布 C5，暂不重训 M12。这个决定不是说 concept 永远稳定，而是当前证据显示校准修复足以解决已观察映射问题，重训成本和风险没有必要立即承担。后续成熟标签若显示判别能力下降，则重新打开重训决策。

6. 不能做的事

不能在同一数据上反复选择方法和阈值后声称泛化；不能用新阈值隐藏安全失败；不能把 C5 应用到未验证地区；不能因 dashboard 恢复就把原 calibration incident 删除。

三十七、排障决策树：先问“变的是谁”

1. 只有 P(X) 报警

检查 Schema、coverage、representation 和 traffic event；按 strata 跑黄金探针并请求成熟标签。若质量稳定，更新容量/抽样计划，暂不归因模型。若标签未知，状态保持 unknown。

2. P(Y) 变化

先检查 label definition、completeness 和抽样，再比较 P(X|Y) 适用性与条件 strata。预测比例变化不能代替标签。需要 prior 修正时保留假设与验证集。

3. 性能下降但所有组件 digest 不变

检查输入/label/concept、外部环境、供应商不可见部署、运行参数和实际内容 digest。也要查 measurement drift。无可见版本变化不等于系统完全相同。

4. 组件变化但性能稳定

记录 component drift，继续 bridge 与黄金探针；不要制造事故。对于高风险未成熟标签，限制扩大直到证据充分。

5. 黄金探针失败但生产指标正常

关键安全探针按硬门处理；可能因场景稀有尚未影响总体。先复现 probe、验证期望版本和 served bundle。非关键探针则检查是否过期或过拟合。

6. 多个组件同时变化

禁止单因子口头归因。构造最小组合矩阵，寻找主效应与交互；无法重放时用实例/流量分流对照，并诚实记录剩余不确定性。

7. 回滚后指标恢复

检查回滚是否同时改变流量、cache、index 和观测。可逆恢复是有力证据，但只有当其他条件受控时才能提升 cause status。

三十八、从 0 到 1 的落地顺序

阶段一：版本事实

  1. 先让每条 task 记录实际 model、Prompt、knowledge、tool、infra bundle。
  2. 建立 ChangeEvent 和每组件 loaded/served 时间。
  3. 上线 lineage coverage 与 unknown version 门。
  4. 为 label、detector 和 telemetry 同样建版本。

阶段二：可解释检测

  1. 从 Schema、缺失、类别 mix、输入长度和输出结构开始。
  2. 同时建立固定 release 与滚动基线。
  3. 按关键风险 strata 校准 effect/统计双门。
  4. 用无害变化、真实回归和测量故障注入验证。

阶段三：黄金探针与成熟结果

  1. 为权限、政策、知识、工具和 region 建关键探针。
  2. 接入 sampling frame、延迟标签和业务后置条件。
  3. 分开 drift、damage、cause 三个状态。
  4. 建立 probe/label bridge 以应对定义升级。

阶段四：归因与处置

  1. 自动生成 lineage diff 与候选矩阵。
  2. 建配对回放和单组件替换环境。
  3. 版本化 calibration、threshold、rollback 和 rebuild 动作。
  4. 让修复后的再验证成为关闭 incident 的必要条件。

三十九、可执行检查清单

定义与边界

  • X、Y、Ŷ、评测单位、总体和 as_of 明确
  • input drift 与 strict covariate shift 分开
  • label marginal drift 与 strict label shift 分开
  • concept drift 不由无标签 P(X) 直接推断
  • model、Prompt、knowledge、infrastructure 有独立定义
  • 漂移告警、损害和根因使用独立状态

Lineage

  • 每条 ServedTrace 保存实际 bundle，不只保存公开别名
  • model artifact、tokenizer、参数与 route policy 可追溯
  • Prompt template、render pipeline、policy、tools 与实际摘要可追溯
  • source、ingestion、chunk、embedding、index、ACL 与 evidence ID 可追溯
  • runtime、region、cache、依赖、telemetry 和 loaded time 可追溯
  • lineage coverage 按关键 strata 达标

基线与窗口

  • 固定发布、滚动、季节和配对基线用途分开
  • 窗口按事件时间，迟到事件与 revision 规则明确
  • 基线保存总体、bundle mix、feature/representation 与 label 版本
  • 新基线经质量再认证，不因长期红灯自动接受
  • bridge window 支持 detector、label 和组件升级

检测器

  • Schema、missingness、重复和 coverage 先于复杂 detector
  • 类别集合、数值 bins、平滑、clipping 和表示器固定
  • statistic、effect、样本量、阈值和限制完整记录
  • 多重比较、告警合并、冷却和恢复迟滞有策略
  • detector 在无变化、有害、无害与测量故障注入上验证
  • exemplar 标注选择机制，不冒充总体

黄金探针

  • 关键权限、安全、知识、工具和 region 探针存在
  • 断言关系适配非确定输出，不依赖脆弱逐字文本
  • 每次 bundle change 前后和实际实例加载后运行
  • 重复运行按 probe 聚类，不膨胀样本量
  • 探针版本、owner、过期条件和失败动作明确
  • 固定探针与 fresh holdout、在线随机样本分开

标签与损害

  • label definition、due、observed、final 和 completeness 可追溯
  • provisional 与 final 结果不互相覆盖
  • 选择性延迟和删失按 strata 分析
  • error、calibration、安全与业务结果分维度报告
  • 实际意义门与统计门同时存在
  • 无成熟标签时明确 damage unknown

归因

  • 异常签名在调查开始时冻结
  • 候选来自实际 ServedTrace 与 ChangeEvent 交集
  • 未变化对照和替代解释同时收集
  • 单组件替换或最小组合矩阵可执行
  • 复现出现/消失，且机制与生产影响面一致
  • 被反驳候选会更新状态，不为报告简洁保留

重校准与处置

  • 重校准只在概率映射问题、成熟标签充分时使用
  • calibration data、方法、参数、验证和过期条件版本化
  • calibration 与 decision threshold 分开
  • Prompt 修复、知识重建、infra 回滚和重训按机制选择
  • 高风险硬门可自动阻断，但不会自动生成根因文本
  • 修复通过事故、holdout、关键 strata、容量与安全再验证

四十、总结

漂移监控的第一步不是选择一个算法，而是停止把所有变化叫“模型漂移”。生产 AI 系统同时受输入与标签总体、目标概念、模型、Prompt、知识、工具、基础设施和测量系统影响。只有给这些对象独立身份，检测与归因才有操作意义。

完整方法可以归纳为十三步：

  1. 定义 X、Y、Ŷ 和系统 bundle，固定总体、窗口与 as_of。
  2. 将 input drift 与有条件不变假设的 covariate shift 分开。
  3. 将 label marginal drift 与严格 label shift 分开。
  4. 用成熟标签或领域规则验证 concept evidence，不从 P(X) 越级推断。
  5. 为模型、Prompt、知识和基础设施建立独立 digest 与实际 ServedTrace。
  6. 同时维护固定、滚动、季节、分层和配对基线。
  7. 先监控 Schema、缺失和 coverage，再使用单变量与高维检测。
  8. 用黄金探针覆盖已知安全、知识、工具和跨环境关系。
  9. 用变点定位时间，用 lineage 缩小候选，保留未变化对照。
  10. 用单组件替换、组合矩阵和成熟结果分别验证原因与损害。
  11. 只在映射失准且标签充分时重校准；能力和组件问题按机制修复。
  12. 让 alert、damage、cause 和 remediation 成为可反驳、可版本化状态。
  13. 用无害、有害、测量和多组件故障注入验证监控不会乱下结论。

最终要证明的不是“漂移分数已经报警”，而是：

团队能够指出发生变化的随机变量或组件、列出仍未知的条件、用实际版本与数据 lineage 构造可证伪对照，并把检测事实、业务损害、根因证据和处置决策保持在各自层级。
