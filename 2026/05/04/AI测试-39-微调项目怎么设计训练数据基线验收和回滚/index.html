AI测试-39-微调项目怎么设计训练数据基线验收和回滚

发表于 2026-05-04 分类于 AI测试 本文字数： 20k 阅读时长 ≈ 1:12

微调项目最容易被误解成一个训练任务：准备 JSONL，选择基座模型，设置 epoch，等待平台返回一个新模型 ID，然后比较几条演示答案。

真正进入生产后，问题会迅速变成另一组：

  • 为什么必须改参数，Prompt、RAG 或确定性工具约束真的不够吗；
  • 候选究竟在修复哪一种稳定行为缺口；
  • 它比哪个可复现基线更好；
  • 训练数据是否有合法用途、隐私风险和明确血缘；
  • 哪个训练、验证、测试版本参与了这次决策；
  • 近重复或公开 benchmark 是否穿过了隔离边界；
  • 使用 SFT、全量微调、PEFT、LoRA 或 QLoRA 的理由是什么；
  • 一个 checkpoint 如何成为可验收的候选产物；
  • 总体分数提高时，哪个语言、客户、风险或长上下文切片退化；
  • 安全回归和灾难性退化能否被总分抵消；
  • 灰度失败后，路由、模型、数据和缓存分别回到哪里；
  • 如果训练数据后来被认定不可用，怎样证明受影响模型已经退出。

这些问题不由一次训练 loss 回答。它们需要一份在训练前冻结的实验合同、一条可追溯的产物链、一组按风险分层的候选门禁，以及真的演练过的模型与数据回滚。

与 AI测试-13、AI测试-15 的边界

AI测试-13 已经完整讨论 Prompt、RAG、微调、工具调用与 Agent 的选型。本文只保留一个必要性入口：若没有证据表明参数化行为适配能解决已确认缺口，就不启动微调实验。 不再复述整套选型树。

AI测试-15 已经系统讨论评测集采集、清洗、去重、污染、切分和版本化。本文不会再写一套数据集教程。本文只关心这些原则如何成为微调实验合同中的硬证据：

  • 哪些样本允许用于训练；
  • 哪些组被固定在 validation 或 test；
  • 哪份近重复与 benchmark contamination 扫描报告获批；
  • 哪个不可变数据指纹实际进入训练；
  • 候选验收是否仍使用未被训练过程接触的测试资产。

换句话说，39 的中心不是“怎样清洗一份数据”，而是怎样让一次微调候选从立项到回滚都可证明。

文中的样本量、得分、成本、时延和事故数字如未明确引用论文，均为构造数据，只用于演示门禁。论文数字只限定在论文报告的模型、硬件与实验设置内。厂商格式和支持范围按资料截止日 2026-07-26 对应官方页面记录，不能推广到其他产品、账号权限、区域、基座快照或未来版本。

一、先过必要性门：只有稳定行为缺口才进入微调候选

1. 用最小对照证明缺口位于哪里

在微调立项单中，至少保存四个基线结果：

基线 固定条件 要排除的问题
B0 确定性规则/传统模型 相同输入与业务约束 任务是否根本不需要生成模型
B1 基座模型 + 最佳已知 Prompt 固定模型快照、参数与模板 提示是否已经足够
B2 B1 + 正确外部证据 固定 Oracle 或生产 RAG 输入 缺口是否来自知识而非行为
B3 B1 + 受控工具结果 固定工具响应与验证器 缺口是否来自实时状态或动作能力

只有当缺口在这些控制之后仍稳定存在，且它表现为可学习的输出行为，微调才有清晰假设。例如：

  • 同一任务格式长期不稳定；
  • 特定标签体系的边界在 Prompt 下持续混淆；
  • 领域表达或固定风格需要大量重复示范；
  • 调用工具的结构模式在代表性输入上反复失败；
  • 在满足成本或时延预算时，较小模型需要行为适配。

以下问题通常不应靠微调“记住”：

  • 每天变化的价格、库存、政策和权限；
  • 当前订单、账户余额或设备状态；
  • 必须精确引用的知识来源；
  • 生产删除权限与审批规则；
  • 可以由 Schema、编译器或业务代码确定性验证的约束。

微调可能改善模型产生某种结构的倾向，但 Schema 通过不等于业务语义正确。模型输出的 refund_allowed=true 即使 JSON 完全合法，也不能替代订单状态、政策版本和权限服务的确定性裁决。

2. 必要性门的退出条件

出现以下任一情况，应关闭或暂停微调立项：

  • 最佳 Prompt 已达到合同目标，继续训练只有不确定的边际收益；
  • Oracle 证据能修复问题，说明应该建设 RAG 或数据访问；
  • 确定性工具能精确返回结果，参数记忆反而增加陈旧风险；
  • 没有可合法使用且代表目标行为的数据；
  • 没有独立测试集和可靠指标，无法判断候选好坏；
  • 基座模型或厂商微调能力将在项目周期内退役；
  • 线上无法并存稳定版与候选版，回滚时间不满足风险预算；
  • 失败后不能定位到数据、训练、评测或服务层。

“已经采购训练预算”或“平台提供微调按钮”不是必要性证据。

二、工程定义：把微调项目拆成合同、运行、产物、候选和发布

1. 实验合同

实验合同是在看到训练结果之前确定的比较规则，包含：

  • 任务与禁止用途；
  • 稳定基线身份；
  • 可证伪假设；
  • 训练、validation、test 数据指纹；
  • 基座模型快照与推理配置；
  • 评测器、指标、切片、门槛和统计方法；
  • 安全硬门禁；
  • 时延、吞吐、成本与资源预算；
  • 最大实验次数和停止条件；
  • 候选推进、拒绝和例外审批规则；
  • 影子、灰度、提升与回滚策略。

合同不是项目简介。它要让另一个团队在不问作者意图的情况下，能重跑基线、检查产物并得到相同发布判定。

2. 训练运行

一次运行是对固定输入资产执行固定训练代码的实例。它有唯一 run_id，记录：

  • 数据 manifest 哈希；
  • 基座模型精确 ID 或权重哈希；
  • tokenizer、聊天模板和特殊 token；
  • SFT/PEFT/LoRA/QLoRA 等方法；
  • 可训练模块、rank、alpha、dropout；
  • optimizer、学习率计划、batch、梯度累积；
  • epoch、step、seed 与采样顺序；
  • 精度、量化、硬件和关键库版本；
  • 训练/validation loss 与资源事件；
  • 每个 checkpoint 的内容哈希。

“同一份代码再次运行”不一定得到字节完全相同的权重。GPU kernel、并行规约、库版本和非确定性算子都可能影响结果。因此合同要区分：

  • 位级复现：权重字节完全一致；
  • 过程复现：输入、配置和环境一致，训练轨迹在容差内；
  • 行为复现：候选在冻结评测上的结果落在预定容差内。

不能做到位级复现时，要诚实记录并用重复运行度量方差。

3. 训练产物

产物不只是最终模型文件。完整产物包包括：

  • 权重或 Adapter；
  • tokenizer 与聊天模板；
  • 模型配置和生成默认参数；
  • 训练数据 manifest 与每个 split 指纹；
  • 训练代码提交哈希和未提交补丁摘要；
  • 容器镜像或环境锁定文件；
  • 运行配置、日志、曲线和 checkpoint 清单；
  • 训练时安全扫描与异常记录；
  • 评测逐样本结果和汇总报告；
  • 模型卡、用途、限制和已知失败；
  • 部署兼容性与回滚说明。

Model Cards 原始论文建议随模型记录预期用途、评测过程和不同相关条件下的表现。工程上应把模型卡连接到不可变产物，而不是发布后手工写一篇与实际 checkpoint 脱节的说明。

4. 候选

checkpoint 是某个训练时刻的权重快照；候选是绑定完整服务配置并准备接受同一合同验收的系统版本。候选身份至少包含：

只比较 Adapter 文件会漏掉推理时真正改变行为的 Prompt、模板、tokenizer 和安全策略。反过来，候选更换多个变量又会失去归因，因此实验阶段应尽量一次只改变已声明因素。

5. 发布与稳定指针

发布不是复制模型文件，而是把流量路由从 stable 指针逐步转向某个候选。稳定指针必须指向不可变组合，而不是会被同名覆盖的“latest”。

回滚就是把路由恢复到上一个仍可服务、仍满足当前政策的稳定组合。若旧基座已被供应商退役、旧权重已删除、旧 Prompt 与新工具不兼容，则名义上的回滚入口并不存在。

三、完整生命周期：每个推进动作都有反向路径

阶段 0：必要性证明

固定 B0 到 B3，收集持续失败切片，确认问题属于稳定行为适配。产物是立项证据，不是训练数据。

阶段 1：冻结实验合同

在训练前批准基线、数据版本、评测版本、门槛、预算与停止条件。训练完成后临时降低门槛属于重新定义实验，必须开新合同并说明原因，不能覆盖原判定。

阶段 2：数据准入

数据负责人、隐私/安全责任人和任务专家分别确认用途许可、最小化、隔离与标签语义。训练只读取获批 manifest 中的对象。

阶段 3：训练与产物登记

运行平台记录输入指纹、环境、配置、日志和 checkpoint。训练作业成功只表示过程结束，不表示候选可发布。

阶段 4：冻结基线重跑

用同一测试集、评测器、推理预算和服务包装重新运行稳定基线。若基线无法复现历史报告，应先调查环境或评测漂移，不能直接比较候选。

阶段 5：离线验收

执行总体、关键切片、安全、鲁棒性、成本和运行门禁。保存逐样本配对差异，不只保存一个总分。

阶段 6：影子与灰度

影子阶段用真实输入调用候选但不交付结果；灰度只向明确白名单和小比例流量交付。每一步都有最短稳定窗口、扩大条件和自动回滚信号。

阶段 7：提升与保留

候选成为稳定版后，旧稳定版在回滚窗口继续可服务。产物、数据与评测证据按保留政策冻结。新模型接受持续漂移、安全和业务监控。

阶段 8：退役或数据撤回

基座退役、许可证变化、数据主体请求或事故可能要求停用模型。控制面应能由数据版本反查所有派生运行、候选和发布，先停止路由，再决定销毁、隔离或从干净父版本重训。

5. 停止条件

  • 最多三轮数据修订；
  • 固定计算或供应商预算；
  • 连续两轮关键切片无实质改善则停止；
  • 任何许可或密封测试泄漏立即停止；
  • 基座能力/平台生命周期变化重新立项；
  • 候选虽改善质量但无法达到服务预算则停止。

停止并不等于项目失败。它可能证明 Prompt、工具、基座升级或产品流程更值得投入。

五、训练数据准入：聚焦许可、隐私与实验用途证明

1. 每条样本都要有用途链

训练 manifest 至少保存：

字段 说明

“来自生产日志”不等于获得训练许可。“网上公开”也不等于可以按任意方式训练。具体法律结论应由组织的法务与隐私流程确定；工程系统的责任是保存依据、执行最小化、阻止未批准样本进入训练，并支持撤回追踪。

2. 数据最小化发生在训练之前

如果任务是意图分类，不需要把姓名、手机号、地址、订单号和完整对话都保留。优先：

  • 只提取与任务有关的消息片段；
  • 用稳定但不可逆的替代标识保持组关系；
  • 对直接标识符做删除或经过审核的占位替换；
  • 限制自由文本中的隐含敏感信息；
  • 把访问日志和训练语料分开授权；
  • 让原始数据只在受控区内生成最小训练视图。

脱敏扫描“未命中”不是隐私保证。规则可能漏掉上下文身份、罕见格式和可组合信息。高风险数据需要抽样人工复核、访问控制和保留限制。

3. 删除训练样本不等于从模型参数中精确删除影响

数据撤回后可以立即：

  • 阻止该样本进入新运行；
  • 撤销训练数据版本；
  • 由血缘图找出所有受影响 run 和候选；
  • 停止受影响候选的新增流量；
  • 按政策隔离或退役模型；
  • 从不含该样本的干净父版本重新训练。

但一般不能仅删除 JSONL 行就证明已从既有权重中移除其影响。除非使用并验证了特定可遗忘机制，数据回滚通常意味着路由撤回加重新训练，不是在原权重上改一个 manifest。

4. 训练服务的产品数据政策也要进入合同

使用托管服务时，合同需记录当时官方条款与配置：数据是否用于提供商训练、保留时间、区域、加密、访问角色、删除接口和日志可见性。这些能力会随产品、账号类型和时间变化，不能用一句“云平台合规”代替逐项核对。

5. 数据质量责任没有因为平台托管而消失

供应商接受 JSONL 或训练任务进入 succeeded，只说明格式和作业条件满足其平台要求。它不证明：

  • 示例是合法获得的；
  • 标注代表正确业务行为；
  • train 与 test 没有泄漏；
  • 分布覆盖目标用户；
  • 候选没有安全退化；
  • 训练收益超过基线和运行成本。

这些仍由使用方的实验合同和验收承担。

六、train、validation、test 隔离：只保留实验需要的证据

AI测试-15 已经展开切分、近重复与污染方法，本文不重复算法细节。微调项目只需要把隔离结果变成不可变合同。

1. 三个集合在实验中的职责

train 用于参数更新。训练人员可以分析其标签与覆盖，模型会直接接触其目标输出。

validation 用于训练过程中的 checkpoint 选择、早停和有限超参数决策。一旦被反复用于选择，它就是开发反馈的一部分，不能再充当最终盲测。

test 用于候选与稳定基线的最终发布比较。训练代码不可读取，数据工程报告不向调参人员暴露逐样本答案，运行次数和访问者受审计。

若一个团队看过 test 失败并据此补训练样本，原 test 已转化为开发资产。应提升新的密封版本，而不是继续把原分数称为盲测结果。

逐行随机切分容易让同一会话、客户、模板或源文档的近似内容横跨集合。实验合同应直接声明 group_key，例如：

训练前保存：

  • 规范化与候选生成器版本；
  • 相似判定策略与阈值；
  • 跨 split 候选对数量；
  • 人工复核结论；

4. benchmark contamination 的边界

如果训练数据包含公开 benchmark 题、改写、答案或翻译，候选在该 benchmark 上的提升可能只是接触效应。实验需要：

  • 维护禁止进入训练的 benchmark 清单与版本；
  • 扫描精确、规范化和经过批准的语义候选；
  • 记录无法验证的基座预训练污染；
  • 把已知污染 benchmark 降级为开发诊断，不承担发布结论；
  • 使用来源独立、时间或组织隔离的任务测试补充证据。

“没有发现”表示在已声明扫描能力下未命中，不等于证明不存在污染。候选门禁应记录残余不确定性。

5. 数据冻结点

训练 run 创建时解析一个不可变 manifest，包含有序样本 ID、内容哈希、split、用途状态和转换版本。作业运行中禁止读取会变化的“latest dataset”视图。

如果某条样本被撤回，创建新 manifest 版本。不要原地改旧版本后继续沿用同一指纹和报告，否则历史训练无法复现，派生模型也无法准确追踪。

七、任务基线：候选必须赢过可部署系统，而不只是训练前的裸模型

1. 稳定基线的完整身份

基线通常是当前生产组合：

如果只拿微调候选与裸基座比较，而生产稳定版已经有成熟 Prompt 和验证器，得到的“提升”不能支持替换决策。

2. 至少保留一个简单基线

分类、抽取和路由任务应包含传统或确定性基线，例如关键词规则、逻辑回归、小型分类器或 Schema 验证后的映射。它可以揭示：

  • 大模型是否为简单任务增加了不必要成本；
  • 指标改善是否来自数据修复而非微调；
  • 灾难时是否有低能力但安全的降级路径；
  • 某些高风险切片能否用硬规则兜底。

简单基线不必总体最强，但要作为成本、可解释性和故障行为参照。

3. 基线要在候选验收时重跑

历史报告可能使用旧评测器、旧 Prompt、旧依赖或不同服务区域。候选报告应在同一执行批次重跑稳定版，形成逐样本配对结果。

若基线重跑从 86% 变成 81%，先调查：

  • 测试数据版本是否变化；
  • 评测器或标签映射是否变化；
  • 基座别名是否指向新快照；
  • 推理参数和重试是否一致；
  • 外部工具、RAG 或安全策略是否漂移；
  • 随机性和运行次数是否足够。

不能沿用旧 86% 与当前候选 84% 做跨环境比较，也不能只因为候选高于当前异常基线就发布。

4. 训练 loss 不是任务基线

loss 是优化目标的过程信号。它可帮助发现不收敛、过拟合或数据异常，但不直接表示：

  • 业务标签正确率；
  • 关键切片风险；
  • 工具参数业务合法；
  • 拒答边界；
  • 隐私泄漏；
  • 线上时延与成本。

validation loss 更低的 checkpoint 可以在业务门禁上更差，因此 checkpoint 选择要结合预先定义的任务评测，而不是训练曲线自动替代发布决策。

5. 人类或规则上界的作用

如果标签本身需要专家判断，保存标注一致性和复核上界。假设专家在同一量表上只有 88% 一致，而合同要求模型达到 99%，问题可能在标签定义而非训练算法。

上界不是给模型降标准，而是帮助判断应先改任务定义、证据输入还是训练。高风险动作仍可以要求模型输出进入人工或确定性审批，不能用“人也会错”取消安全控制。

八、SFT、全量微调、PEFT、LoRA 与 QLoRA 的工程边界

1. SFT 描述目标，不等于某一种参数更新方式

监督微调 SFT 使用输入与期望输出示范来优化模型。它描述训练信号。底层可以更新全部参数，也可以只训练 Adapter。讨论方案时应分开两个问题：

  • 学习目标是什么：监督示范、偏好、奖励或其他目标；
  • 哪些参数被更新：全部权重、部分层、Adapter、低秩矩阵。

把“SFT”和“LoRA”当互斥选项会混淆目标与参数化方法。

2. 全量微调

全量微调更新全部或大部分模型权重。它可能提供更高适配容量，但带来：

  • 更高显存、计算和存储成本；
  • 每个候选产物更大；
  • 更复杂的分布式训练与复现；
  • 对学习率、数据量和灾难性退化更敏感；
  • 多租户或多任务版本管理成本高。

它适合什么任务不能仅凭“任务复杂”判断。需要同预算对照，确认 PEFT 容量不足且全量更新的增益能通过风险门禁。

3. PEFT 是一类方法

参数高效微调 PEFT 只更新较小参数子集或增加可训练模块。它通常降低训练和存储成本，便于为不同任务保留独立 Adapter。但它不自动保证：

  • 质量等同全量微调；
  • 不发生灾难性退化；
  • Adapter 可与任意基座快照兼容；
  • 合并权重与动态加载行为一致；
  • 服务并发和热切换没有额外复杂度。

产物 manifest 必须把 Adapter 绑定到精确基座、tokenizer、目标模块与 PEFT 库版本。对错误基座加载成功也可能产生无意义行为。

4. LoRA 的论文结论要限定实验

LoRA 原始论文提出冻结预训练权重，在 Transformer 层注入可训练低秩分解矩阵。论文摘要报告：相对于用 Adam 全量微调 GPT-3 175B 的对应设置，可训练参数减少约 10,000 倍、GPU 内存需求约减少 3 倍，并在论文测试的 RoBERTa、DeBERTa、GPT-2 和 GPT-3 任务上得到可比或更好结果。

这些数字属于论文具体架构、目标模块、优化器和实验，不是“任何 LoRA 项目都节省 10,000 倍”或“一定不降质量”的承诺。实际项目必须记录并测量：

  • rank r；
  • alpha 与缩放；
  • 注入哪些线性层；
  • dropout；
  • 可训练参数占比；
  • 是否训练 bias、embedding 或输出头；
  • Adapter 合并方式；
  • 服务时动态加载还是预合并；
  • 与基座许可证和分发约束的关系。

5. QLoRA 的论文结论也只属于论文设置

QLoRA 原始论文描述通过冻结的 4-bit 量化预训练模型反向传播到 LoRA Adapter，并引入 NF4、double quantization 和 paged optimizers。论文摘要报告在单张 48GB GPU 上微调 65B 参数模型，并在其论文实验中比较 16-bit 微调任务表现。

这不意味着任何 65B 模型、序列长度、batch 或硬件都能放入 48GB，也不意味着量化误差对所有任务无影响。项目要测试：

  • 量化数据类型与计算精度；
  • 基座量化版本和校准方式；
  • 长序列峰值显存；
  • 梯度检查点与 paged optimizer 配置；
  • 合并后与未合并 Adapter 的行为差异；
  • 训练运行时和生产服务量化是否一致；
  • 数值不稳定、NaN、overflow 和恢复点。

6. 方法选择矩阵

条件 优先实验方向 必须补的证据
数据少、缺口未稳定 不训练，先强化基线 缺口定位与数据可用性
行为窄、多个任务版本 LoRA/其他 PEFT 对照 Adapter 绑定与服务隔离
显存受限、开源权重可控 QLoRA 对照 量化与数值稳定性
PEFT 明确容量不足 小规模全量微调试验 同预算增益和退化风险
托管模型不暴露权重 厂商支持的方法 平台模型 ID、数据政策、退役和导出边界

这个矩阵只决定下一项实验，不直接决定生产方案。

7. 灾难性退化不是全量微调独有

只要训练把输出分布推向新示范，就可能损害原能力。常见形式包括：

  • 过度拒答或拒答减少；
  • 只会训练模板，不再处理自然表达；
  • 多语言能力下降；
  • 长上下文指令遵循退化；
  • 工具调用转成自然语言“假装执行”；
  • 输出变短但遗漏必要字段；
  • 对训练中高频类别产生先验偏置；
  • 安全策略被有问题的目标答案覆盖。

因此所有方法都要运行保留能力集与安全回归，不能因为只训练少量参数就省略。

页面还分别列出 preference tuning、tuning checkpoints 与 continuous tuning 的支持范围。不能因为某个模型出现在 supervised tuning 列表，就推断它也支持其他方法、所有模态、所有区域或同样的 checkpoint 行为。每个 run manifest 应保存产品名、区域、精确模型 ID、官方页面核对时间和任务 API 返回的能力字段。

3. 托管平台与自托管产物的指纹不同

自托管权重通常可以记录每个文件 SHA-256、训练框架、optimizer 状态和 checkpoint。托管平台可能只返回：

  • job ID；
  • base model ID；
  • training/validation file ID；
  • 方法与超参数；
  • seed；
  • result file；
  • fine-tuned model ID；
  • checkpoint ID 和平台指标。

无法获得权重哈希时，不应伪造“模型权重可复现”。应把供应商不可变 ID、API 响应快照、输入文件本地哈希、创建时间和组织/区域作为可获得的身份，并明确平台外无法重建相同权重的限制。

4. 格式支持不等于行为支持

厂商接受带工具调用或结构化消息的训练格式，不保证候选在业务上安全调用工具。工具名正确、参数 Schema 通过、请求成功，都不能证明：

  • 选择了正确工具；
  • 参数值来自可靠事实；
  • 调用者有权执行；
  • 重复调用不会产生副作用；
  • 工具返回被正确解释；
  • 最终用户结果满足业务规则。

这些要在系统候选层用确定性断言和端到端测试验收。

十、训练与模型指纹：能够回答“这个候选到底是什么”

1. 数据指纹

不要只对压缩包做哈希。压缩时间戳、文件顺序和元数据会改变字节。建议同时保存：

  • 每条样本规范化 JSON 的 SHA-256；
  • 按稳定 sample_id 排序后的 split manifest 哈希；
  • 全数据 manifest 哈希；
  • 转换代码与 Schema 版本；
  • 原始资产映射的受控引用。

内容指纹用于复现，原始引用用于许可和撤回。二者权限可以不同。

2. 训练运行指纹

运行指纹不含运行结束后才产生的权重。它标识“计划执行的训练输入与配置”。若两个 run 指纹相同但权重或指标差异大，说明存在未捕获非确定性或环境变量。

3. 模型产物指纹

托管产物以供应商不可变 model/checkpoint ID 和完整创建响应为主，再对本地可得 manifest 哈希。不能把可变展示名当身份。

4. 候选服务指纹

同一模型在不同 Prompt、temperature、tool schema、安全策略和运行时下会表现不同。候选报告必须引用服务指纹。线上 trace 也记录该指纹，事故才能准确回放。

8. 复现门禁

候选必须满足：

  • 合同、数据、代码、基座、环境、训练和评测指纹齐全；
  • 所有哈希对象可读取且权限有效；
  • 基线重跑在容差内；
  • 候选重复推理结果方差在预算内；
  • 关键报告可由逐样本结果重算；
  • 模型或 Adapter 能在隔离环境加载；
  • 稳定版和候选可以并存并快速切换。

无法复现不一定说明模型质量差，但说明它不适合承担受控发布。

9. 多候选选择偏差

如果对同一 validation/test 运行 30 个候选再挑最高分，即使每个候选没有真实差异，也容易选到随机高点。应：

  • 用 validation 选择超参数；
  • 限制 test 使用次数；
  • 记录所有候选而非只保留赢家；
  • 对最终候选使用新的密封确认集或重复实验；
  • 报告选择过程和不确定性。

不能把“最佳 checkpoint”当作事先指定候选。

十二、安全回归与灾难性退化要覆盖参数外的系统行为

1. 训练目标可能教会错误能力声明

如果示范答案写着“退款已为您处理”，但训练输入里没有成功工具回执，模型会学习把语言风格当执行事实。训练数据审计应检查目标答案中的每项外部事实是否在输入证据中存在。

OpenAI 当前微调最佳实践页面也以类似例子提醒：若训练示范让模型声称自己完成了实际不能完成的动作，数据本身会教出错误行为。这个原则适用于数据设计，但具体平台安全检查不替代项目自己的工具与权限验收。

2. 安全回归分四层

第一层是模型层：拒答、敏感信息、危险指令和训练样本记忆探测。

第二层是协议层：结构、工具名、参数类型和停止条件。协议通过只说明形状。

第三层是业务层：订单状态、金额边界、授权主体、幂等键、审批和副作用结果。

第四层是系统层：RAG 污染、工具超时、重复回调、缓存、并发和审计证据。

微调候选必须在完整系统候选层验收，因为相同模型放进不同工具包装可能产生不同风险。

3. 隐私与记忆探测

可以使用获批的合成 canary 检查模型是否在异常提示下复述训练特征，并对生产敏感模式做扫描。结果要谨慎解释：

  • 未提取出 canary 不能证明模型没有记忆其他样本；
  • 成功提取表示存在明确风险，需要隔离候选；
  • canary 不应使用真实秘密；
  • 测试 Prompt 和解码策略要版本化；
  • 托管平台的服务政策与模型本身记忆风险分开评估。

4. 分布外与拒绝能力

训练集越窄，候选越可能在相似格式上自信输出。加入：

  • 完全无关任务；
  • 缺字段或冲突字段；
  • 工具结果为空、超时、过期；
  • 多语言混合与拼写噪声；
  • 超长输入和截断；
  • 恶意指令覆盖系统规则；
  • 要求模型伪造引用、审批或执行结果。

期望行为可能是澄清、拒绝、调用确定性工具或转人工。模型置信度高不能把未知输入变成已知事实。

5. 训练时安全检查与应用安全门禁并存

厂商可能对微调作业或产物执行平台安全检查。它证明候选满足该平台当时定义的类别和阈值，不证明符合本应用的租户隔离、退款权限、医疗边界或内部政策。

平台检查通过是必要输入之一，应用门禁仍由使用方定义并保存证据。

十四、自动化测试与失败注入：训练成功路径远远不够

1. 训练前静态门禁

在任何 GPU 或托管训练费用发生前，流水线先验证：

  • contract_id 存在且状态为已批准；
  • train、validation、test manifest 不可变且哈希一致；
  • test 对训练作业身份不可读；
  • 许可、用途、隐私和保留状态全部有效；
  • 禁止 benchmark 和跨 split 报告针对当前 manifest；
  • 基座、tokenizer、聊天模板和许可证兼容；
  • 训练方法所需目标模块确实存在；
  • 输出目录、日志与 checkpoint 不包含原始敏感样本；
  • 预算、区域、硬件和最大运行时间符合合同；
  • 稳定回滚目标仍可部署。

这些检查失败时，状态应为 REJECTED_BEFORE_TRAINING，而不是自动修正后继续。自动删除一条不合规样本会改变数据指纹和覆盖，需要生成新 manifest 并重新批准。

2. 训练过程不变量

运行中持续检查：

  • 实际加载样本数与 manifest 一致；
  • 每个 epoch 的样本身份摘要符合预期；
  • test 文件从未被打开；
  • 可训练参数集合与合同一致；
  • loss、gradient norm、学习率和吞吐没有 NaN、Inf 或异常跳变；
  • checkpoint 写入采用临时路径、校验后原子登记；
  • 恢复后 global step、optimizer、scheduler 和数据游标一致；
  • 分布式 worker 使用相同代码、配置与基座；
  • 预算或安全停止信号能终止所有 worker；
  • 训练失败不会把半成品登记成候选。

训练作业返回退出码 0 只说明进程认为自己完成。产物登记还要独立核对文件哈希、大小、配置和可加载性。

4. 产物篡改测试

在隔离环境复制候选包，分别修改一个因素：

  • Adapter 一个字节；
  • tokenizer 配置；
  • 聊天模板；
  • base model ID；
  • target module 列表；
  • system Prompt；
  • serving runtime 镜像；
  • 安全策略版本。

注册表应拒绝哈希不匹配，候选服务指纹也应变化。若修改模板后仍沿用原评测报告，发布门禁必须识别报告绑定的候选 ID 不一致。

5. 评测流水线故障注入

模拟：

  • 基线和候选使用不同温度；
  • 候选部分请求重试而基线不重试；
  • 评测器版本漂移；
  • 测试样本被静默跳过；
  • 某语言解析失败后被计为 NA；
  • 模型裁判超时后默认通过；
  • 逐样本结果与汇总不一致；
  • 安全复核队列未完成却生成总报告；
  • 报告引用错误 checkpoint；
  • 多候选只保留最高分运行。

预期是门禁失败并指出证据缺口。任何异常默认填 0、填通过或从分母移除，都会让报告比系统更乐观。

6. 候选加载与服务兼容测试

微调产物在训练框架可加载，不代表生产服务可用。测试：

  • 冷启动与首次请求；
  • Adapter 动态加载、卸载和并发隔离；
  • 合并权重与动态 Adapter 的逐样本差异；
  • tokenizer 特殊 token 与最大长度；
  • 流式输出、停止 token 和超时；
  • 批处理不同长度请求；
  • 工具调用、结构化输出和安全中间件；
  • 服务滚动升级中的版本粘性；
  • 模型缓存淘汰后重新加载；
  • 稳定版与候选同时驻留的资源峰值。

7. 回滚演练是发布测试的一部分

在候选尚未接真实用户前，主动执行：

  1. 部署 stable 与 candidate；
  2. 发送带版本断言的合成请求；
  3. 把 1% 测试流量切到 candidate；
  4. 注入安全硬失败信号；
  5. 验证自动停止扩大并把新请求切回 stable；
  6. 等待或终止 candidate 在途请求；
  7. 清除与候选服务指纹绑定的缓存；
  8. 验证稳定版指标、trace 与业务结果恢复；
  9. 保存实际 RTO 与未回滚状态清单。

若回滚只在文档里有命令、从未在当前服务拓扑演练，不能作为上线保证。

十五、从离线候选到生产稳定版：影子、灰度和提升

1. 影子阶段

复制经过批准的真实请求到候选，候选结果不交付用户，也不允许执行写工具。对敏感字段做与生产观测一致的最小化。比较：

  • 稳定版与候选的逐请求差异；
  • 输入分布与离线测试覆盖；
  • 结构和工具调用倾向；
  • 延迟、token、错误和资源；
  • 新失败簇与人工复核结果。

影子不能测用户交互反馈，也不能完全模拟候选结果会改变后续会话或工具状态。它是灰度前的分布检查，不是最终线上证明。

2. 灰度单元

优先按可隔离单位灰度，例如内部员工、测试租户、低风险意图或明确白名单。避免纯随机逐请求切换导致同一会话在两个模型之间来回跳，破坏上下文与归因。

灰度记录：

身份字段按隐私政策最小化或哈希化，但要能支持一致分桶和事故范围分析。

3. 扩大条件

示例阶段可以是 1%、5%、20%、50%、100%，比例不是通用最佳实践。每阶段必须满足：

  • 最小样本量或最短稳定时间；
  • 无安全硬失败；
  • 核心业务与保留能力在门槛内；
  • 投诉、人工接管和撤销动作无异常；
  • p95/p99 延迟、错误和成本达标；
  • 关键租户、语言和意图有足够证据；
  • 候选与稳定版本路由、trace 可准确区分；
  • 回滚目标健康且容量足够。

高峰前刚达到样本量，不代表已经观察到高峰行为。最短时间要覆盖重要业务周期。

4. 自动回滚信号

适合自动触发的信号通常清晰且高置信：

  • 严重安全策略命中；
  • 越权或错误副作用；
  • 错误率、超时或资源超过硬阈值；
  • 模型/数据/服务指纹不匹配；
  • 关键输出 Schema 大面积失败；
  • 稳定版与候选差异监控失去证据。

语义质量下降可能需要聚合与人工确认，但不能等到日终总分才处理严重样本。安全事件应先停止扩大并隔离候选。

5. 线上实验不改写离线合同

灰度可以发现离线集未覆盖的新分布。它产生的是新证据和下一版数据候选，不应把失败请求即时加入训练并在线更新当前候选。在线学习会让服务指纹持续变化，破坏归因、审批和回滚。

需要持续训练时，也应以离散批次形成新数据版本、新 run、新候选和新门禁。

6. 提升后的观察窗

100% 流量不是项目结束。保持：

  • 旧稳定版的可服务副本；
  • 持续安全和业务 SLI；
  • 分切片漂移与新增失败采样；
  • 基座或供应商退役监控；
  • 数据许可与撤回监控；
  • 定期回滚演练；
  • 模型卡和已知限制更新。

观察窗结束后再按政策退役旧版，且要确认没有异步任务、缓存或离线消费者仍引用它。

十六、模型回滚与数据回滚是两条不同路径

1. 模型回滚

模型回滚目标是停止候选影响并恢复已验证服务。完整动作包括：

  • 冻结灰度扩大；
  • 稳定指针切回明确版本；
  • 处理候选在途请求；
  • 禁止候选继续执行工具副作用；
  • 清除候选专属缓存和会话路由；
  • 恢复 stable 对应 Prompt、tokenizer、工具和安全策略；
  • 验证容量、延迟和业务结果；
  • 隔离候选产物，保留证据但禁止新流量。

只切模型 ID 可能制造不兼容：新 Prompt 为微调候选缩短了指令，旧稳定模型切回后可能失去必要约束。回滚单位应是完整服务指纹。

2. 数据回滚

数据回滚表示某个训练 manifest 不再可用于后续运行，常见原因包括许可撤回、隐私问题、标签错误、污染或转换 bug。动作包括：

  1. 冻结数据版本；
  2. 由血缘找到所有派生 run、checkpoint、候选和报告；
  3. 阻止受影响候选提升；
  4. 若受影响版本已生产，先执行模型回滚；
  5. 从最近干净父 manifest 派生修复版本；
  6. 重做准入、隔离、训练和验收；
  7. 根据政策隔离或销毁旧产物；
  8. 保存撤回依据、影响范围和完成证据。

数据 manifest 指针回退不会改变已经训练的参数。需要消除受影响训练的生产使用时，必须停用模型；需要得到不含该数据影响的新模型时，通常需要重新训练。

3. 评测数据回滚

若发现 test 泄漏或标签错误，不能简单改几行后沿用原候选通过结论。应：

  • 撤销受影响评测报告；
  • 标记哪些候选决策使用了它；
  • 建立修复测试版本；
  • 用相同候选重新评测；
  • 重新执行门禁和审批；
  • 对已发布候选决定是否暂停或限制流量。

评测修复可能改变基线和候选，必须同时重跑。

4. 基座或平台退役时的回滚

托管基座退役可能让旧 stable 无法继续推理。项目需要在退役前：

  • 记录供应商时间线；
  • 选择新基座并建立未调基线；
  • 验证旧微调产物是否可迁移；
  • 把迁移视为新候选，而不是透明替换；
  • 在旧端点关闭前完成并行验证；
  • 更新回滚目标和最长保留窗口。

如果供应商不允许导出权重，无法把旧微调模型迁往自托管。这个锁定边界应在立项合同中明确。

5. 回滚目标也会腐化

旧模型文件存在，但依赖镜像被删、GPU 不兼容、密钥过期、工具 Schema 升级或安全政策变化，都可能让它不可用。定期合成探测 stable-1：

  • 能加载；
  • 能处理代表性输入；
  • 能调用当前只读工具或明确拒绝不兼容写工具；
  • 满足当前强制安全策略；
  • 容量足以接回全量；
  • RTO 在合同内。

6. 回滚完成条件

路由配置返回成功只是第一步，不是完成条件。

十七、完整失败案例：评测的是 ckpt-2400，生产部署成 ckpt-3000

下面是构造案例，所有时间、样本数和分数均为演示数据。

1. 项目背景

团队要让一个 8B 自托管模型完成退款意图分类和客服答复。稳定版由基座、长 Prompt、订单只读工具和响应验证器组成。立项假设是：LoRA SFT 能稳定 12 类标签并缩短 Prompt，从而降低成本。

合同规定：

  • 密封 test refund-eval-v6 共 2,400 条；
  • 核心准确率至少提升 2.0 个百分点；
  • 高风险拒答切片退化不超过 0.5 个百分点；
  • “未收到成功工具回执却声称退款已执行”严重事件必须为 0；
  • p95 不超过 900ms，单位成功成本不超过 1.05 倍；
  • 评测、灰度和生产必须使用同一 candidate service fingerprint；
  • 灰度异常 60 秒内切回 stable-2026-04-12。

2. 表面成功

训练平台产生 ckpt-1800、ckpt-2400 和 ckpt-3000。工程师在 ckpt-2400 上运行离线评测：

报告页面显示绿色，团队把服务从 1% 扩到 20%。两小时后，灰度用户在订单工具超时时收到“退款已经处理，将在三个工作日到账”。实际上没有任何写工具，也没有成功回执。

3. 第一轮止血

值班人员执行：

  1. 冻结灰度扩大；
  2. 禁止候选流量进入任何退款相关意图；
  3. 将新请求切回完整 stable-2026-04-12 服务组合；
  4. 清除 candidate service fingerprint 的答案缓存；
  5. 核对工具审计，确认候选没有真实执行退款；
  6. 查找已经收到错误承诺的会话并进入人工处理；
  7. 冻结候选、训练 manifest、评测报告和线上 trace。

实际回滚用时 47 秒，满足 60 秒目标，但用户沟通影响仍需单独处理。

4. 证据 A：线上服务指纹不匹配

事故请求 trace：

离线报告绑定：

部署脚本读取了对象存储可变别名 candidate/latest。评测后训练任务继续到 3000 step，并覆盖该别名。注册表只保存逻辑名，没有强制产物哈希，因此未经评测的 checkpoint 进入生产。

5. 证据 B：真正的安全切片并未通过

重新读取 ckpt-2400 的逐样本报告发现：

汇总器把六个维度按权重平均，安全切片只占 5%，总体仍高于阈值。合同写的是硬门禁，流水线实现却用了加权总分。UI 的绿色不是合同结论。

6. 证据 C：训练目标包含无证据的动作声明

训练 manifest 中 14% 的退款答复来自历史客服话术。抽查发现 63 条示范在输入中没有工具结果，却以“已为您退款”结尾。数据转换器只保留用户和客服文本，丢掉了原工单中的实际动作状态。

模型学到的不是正确工具使用，而是“退款语境下给出完成承诺”的表面模式。JSONL、角色和标签都合法，业务因果却错误。

7. 证据 D：隔离报告绑定了旧 manifest

候选 manifest 引用 train-manifest-v9，但近重复与 contamination 报告的输入哈希对应 v8。v9 在最后一天加入 320 条客服样本，其中 37 条是 test 题的轻微改写或同一工单后续轮次。

这不需要重新讲一遍近重复算法；关键控制失败是发布门禁没有验证报告输入哈希等于训练 manifest 哈希。因此“扫描通过”与实际训练数据无关。

8. 证据 E：ckpt-3000 比 ckpt-2400 更过拟合话术

对冻结 test 重跑：

指标 stable ckpt-2400 ckpt-3000
总体准确率 86.2% 89.1% 89.4%
高风险拒答 97.8% 93.9% 88.9%
严重错误执行声明 0 2 7
无关输入正确拒绝 96.0% 94.8% 89.2%

总体仍上升，安全和分布外能力继续下降。训练 loss 也继续下降，说明 loss 无法替代应用门禁。

9. 根因

直接根因：

  • 部署使用可变 latest，没有固定 Adapter 哈希；
  • 门禁错误地把安全硬失败加权平均；
  • 训练示范丢失工具执行证据，目标答案教会虚假承诺；
  • 数据隔离报告与实际 manifest 指纹不一致。

系统性根因：

  • 项目把 checkpoint 训练完成误当候选完成；
  • 模型、Prompt、工具策略和评测报告没有共同服务指纹；
  • 训练数据审查关注格式与标签，未审查输出陈述所需证据；
  • 灰度扩张只看总体正确率和延迟；
  • 上线检查没有执行“报告候选与部署候选一致”的故障注入。

10. 永久修复

  • 对象存储禁止候选别名覆盖；部署只接受内容哈希；
  • 候选注册时验证 Adapter、基座、tokenizer、Prompt、工具和策略完整指纹；
  • 门禁引擎逐项执行硬失败，不产生可抵消安全总分；
  • 训练转换保留工具回执，缺少证据的动作声明样本被拒绝；
  • 每份许可、隐私、近重复和污染报告都绑定精确 manifest 哈希；
  • checkpoint 只有通过完整验收后才能登记为候选；
  • 灰度实时检查虚假执行声明，首个严重事件自动回滚；
  • 新增 ckpt-2400 与 ckpt-3000 对比，验证训练后期退化；
  • 回滚单位改为完整服务组合，并定期演练。

11. 数据与模型回滚决定

由于 v9 包含不合格示范和 test 泄漏：

  1. 撤销 train-manifest-v9；
  2. 血缘系统隔离所有由 v9 派生的 checkpoint 与候选；
  3. 保持生产 stable，不再使用 ckpt-2400 或 ckpt-3000；
  4. 从干净 v8 派生 v10，恢复工具证据并移除不合格样本；
  5. 建立新的密封确认集，因为 v6 test 已参与事故分析；
  6. 创建新 contract/run/candidate，不复用原通过报告；
  7. 完整重跑离线、影子和灰度。

这才是数据回滚。仅把 v9 的 320 行从仓库删除，却继续服务 ckpt-3000，不会消除模型影响。

12. 关闭事故所需证据

  • 所有 v9 派生模型已无生产路由和异步任务引用；
  • 错误承诺会话影响范围与人工处理完成；
  • 稳定版业务与安全探针恢复；
  • 可变别名部署被技术上禁止；
  • 门禁硬失败测试在 CI 中实际失败过；
  • 新数据转换保证动作声明有对应工具证据；
  • 新 manifest 的所有审计报告哈希一致；
  • 回滚演练达到 RTO 且清理候选缓存；
  • 新候选使用新的密封确认集，不沿用已暴露结论。

十八、上线前检查表

必要性与实验合同

  • 已用确定性、Prompt、Oracle RAG 和工具基线定位缺口
  • 缺口属于稳定可学习行为，而非实时事实或权限
  • 任务、禁止用途与业务责任边界明确
  • 基线是完整可部署服务组合并有不可变指纹
  • 可证伪假设在训练前登记
  • 主指标、切片、硬门禁、预算和停止条件预注册
  • 统计单位、分母、重复运行和不确定性方法明确
  • 最大实验次数与 test 使用预算明确

数据许可、隐私与隔离

  • 每条样本有来源资产、用途和许可依据
  • 数据最小化和脱敏在训练前完成
  • 高风险自由文本经过规则与人工抽查
  • 撤回键能反查所有派生数据和模型
  • train/validation/test 的职责与访问权限分离
  • 会话、客户、模板和源文档按合同 group 隔离
  • 近重复与 benchmark 报告绑定当前 manifest 哈希
  • 已知与未知基座预训练污染风险已记录
  • test 一旦用于调参会被降级并建立新密封版本

训练运行与产物

  • 基座使用精确模型或权重指纹，不使用可变 latest
  • tokenizer、聊天模板和特殊 token 已锁定
  • SFT 目标与参数更新方法分别说明
  • LoRA/QLoRA 目标模块、rank、alpha、量化和精度已记录
  • seed、代码、未提交补丁、镜像和硬件环境可追溯
  • 训练样本身份摘要与 manifest 一致
  • checkpoint 原子写入、哈希校验且能独立加载
  • 中断恢复、磁盘满、worker 失败和 NaN 已注入
  • 训练日志不泄露原始敏感样本
  • 托管平台能力、区域、模型支持与退役时间按截止日核对

候选与验收

  • checkpoint 经过服务组合绑定后才成为候选
  • 评测报告绑定精确 candidate service fingerprint
  • 稳定基线在同批次、同参数、同评测器重跑
  • 保存逐样本配对改善与新增回归
  • 总体改善和关键切片非劣分别判定
  • 样本不足切片标记证据不足，不自动通过
  • 严重安全事件为独立硬门禁
  • Schema、模型置信度和协议成功未被当成业务正确性
  • 保留能力、分布外、工具真实性和隐私探测已覆盖
  • 延迟、吞吐、错误、资源和单次成功成本达标
  • 所有汇总可以从逐样本结果重算

灰度与发布

  • 影子候选不能执行真实写副作用
  • 灰度按会话或租户稳定分桶
  • 每阶段有最小样本、时间和业务周期要求
  • 安全硬失败能自动停止扩大并回滚
  • 线上 trace 记录模型、服务、合同和策略指纹
  • 候选和稳定版容量可以同时承载预期流量
  • 100% 提升后仍有观察窗和旧版保留期
  • 在线失败只进入下一版数据候选，不原地持续训练

模型与数据回滚

  • 回滚单位包含模型、Prompt、tokenizer、工具和安全策略
  • 旧稳定版仍可加载、兼容当前政策且容量充足
  • 候选在途请求、写工具和缓存的处理方式明确
  • 数据撤回能隔离所有派生 run、checkpoint 和候选
  • 明确数据指针回退不能改变既有模型参数
  • 污染或许可事故有从干净父版本重训方案
  • 评测集撤销会触发基线与候选重新判定
  • 供应商基座退役前有迁移和新回滚目标
  • 回滚完成条件、RTO、审批和证据已经演练

十九、总结

微调项目的工程目标不是得到一个 loss 更低的 checkpoint，而是得到一个相对于明确基线、在明确用途内通过验收、可以追溯并可以撤销的候选服务。

开始之前，先用 Prompt、RAG、工具和确定性基线定位缺口。微调适合稳定行为适配，不适合存储实时事实、当前权限或替代业务验证。这个入口只承担必要性判断，避免重复更完整的选型讨论。

训练数据进入 run 之前，要有用途许可、隐私状态、不可变 manifest 和隔离证据。train 用于参数更新，validation 用于选择，test 用于最终判定。近重复与 benchmark contamination 在这里不是一套清洗教程，而是必须与实际 manifest 哈希一致的准入报告。

训练方法要拆清目标和参数化：SFT 是监督目标；全量微调、PEFT、LoRA 与 QLoRA描述更新方式。论文中的参数、显存和质量数字只属于论文实验，实际项目要用自己的模型、任务、硬件和服务栈验证。

一个完整候选绑定基座、权重或 Adapter、tokenizer、聊天模板、Prompt、工具、安全策略和运行时。训练成功、checkpoint 存在、JSONL 合法、厂商安全检查通过，都不能替代应用验收。

验收同时包含：

  1. 主任务达到预注册改善；
  2. 关键切片和保留能力不劣于边界；
  3. 严重安全事件为零；
  4. 延迟、成本和资源在预算内；
  5. 数据、训练、产物、评测和服务指纹完整；
  6. 基线和候选在同一环境形成逐样本配对证据。

发布从影子到灰度逐步扩大，每一步都有停止和回滚条件。模型回滚切换完整服务指纹；数据回滚隔离 manifest 及所有派生产物，必要时从干净父版本重训。删除训练行不等于从既有权重中删除影响。

最终，成熟的微调体系应能对任一线上响应回答：它来自哪个候选、哪个基座、哪份数据、哪次运行、哪套评测和哪项审批；也能在任一数据或模型失效时，准确找到影响范围并在风险预算内退出。
